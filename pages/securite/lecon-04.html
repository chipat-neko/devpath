Module 2 · Les failles classiques — Leçon 04

XSS et CSRF

~40 min Intermédiaire Leçon 03 requise

À la fin de cette leçon, tu sauras

  • expliquer le XSS et le prévenir par l'encodage ;
  • comprendre le rôle du Content-Security-Policy ;
  • expliquer le CSRF et le prévenir ;
  • employer les jetons anti-CSRF et l'attribut SameSite.
Sommaire de la leçon

Deux failles emblématiques du web visent non pas le serveur, mais le navigateur de l'utilisateur. Le XSS fait exécuter du code malveillant dans la page que voit la victime ; le CSRF fait exécuter une action à son insu. Toutes deux exploitent la confiance — entre l'utilisateur et le site, ou entre le site et le navigateur. Et toutes deux se préviennent avec des techniques bien établies.

Le XSS : du script injecté

Le XSS (Cross-Site Scripting) est, on l'a vu en leçon 2, une injection dans le contexte HTML. Si une application affiche une donnée utilisateur sans l'encoder, un attaquant peut y placer du <script> qui s'exécutera dans le navigateur de quiconque voit la page.

Les conséquences sont graves : vol de cookies de session (donc usurpation de compte), modification de la page, redirection vers un site piège, actions au nom de la victime. Le script s'exécute avec tous les droits de l'utilisateur sur le site, puisque le navigateur croit qu'il vient du site légitime.

Le XSS prend trois formes selon le trajet du script, mais toutes se corrigent de la même façon. Le XSS stocké (le plus grave) enregistre le script côté serveur — un commentaire, un profil — et frappe tous les visiteurs ; c'est le cas ci-dessus. Le XSS réfléchi glisse le script dans un lien piégé (un paramètre d'URL) renvoyé dans la page à la victime qui clique. Le XSS DOM se joue entièrement dans le navigateur : du JavaScript de la page insère lui-même une donnée non fiable dans le document.

La parade : encoder à la sortie

La défense est l'encodage HTML (assainissement contextuel de la leçon 2) : avant d'insérer une donnée dans la page, on convertit les caractères spéciaux pour qu'ils s'affichent comme du texte au lieu d'être interprétés comme des balises.

En pratique : les frameworks modernes (React, Vue, les moteurs de templates) encodent par défaut tout ce qu'on affiche — c'est pourquoi ils sont plus sûrs. Le danger réapparaît quand on les force à insérer du HTML brut (innerHTML, dangerouslySetInnerHTML, v-html) : à ne faire qu'avec une donnée de confiance, ou après un nettoyage par une bibliothèque dédiée.

Cas réel — le ver « Samy » sur MySpace (2005)

Un développeur a placé du JavaScript dans son profil MySpace, en exploitant un XSS (le site n'encodait pas correctement le contenu des profils). Le script faisait deux choses chez quiconque visitait son profil : l'ajouter comme ami, puis se recopier dans le profil de la victime. Résultat : en environ 20 heures, plus d'un million de comptes étaient touchés — l'un des vers les plus rapides de l'histoire. Il n'a rien détruit, mais a montré la puissance d'un XSS : du code exécuté dans le navigateur de chaque visiteur, avec ses droits.

Le Content-Security-Policy

Une seconde ligne de défense contre le XSS : l'en-tête Content-Security-Policy (CSP). Il indique au navigateur quelles sources de scripts sont autorisées ; tout script venu d'ailleurs (ou inséré inline) est bloqué.

Le CSP ne remplace pas l'encodage : c'est une défense en profondeur. Même si une faille XSS passe, un CSP bien réglé peut empêcher le script injecté de s'exécuter. On combine les deux : encoder (empêcher l'injection) et CSP (limiter les dégâts si elle survient).

Le CSRF : une action forgée

Le CSRF (Cross-Site Request Forgery) est différent : il n'injecte pas de code, il abuse de ta session existante. Si tu es connecté à ta banque et que tu visites un site piège, ce site peut déclencher une requête vers ta banque ; le navigateur y joint automatiquement tes cookies de session, et la banque croit que la demande vient de toi.

La faille tient à ce que le navigateur joint les cookies à toute requête vers la banque, même déclenchée par un autre site. L'attaquant n'a pas besoin de connaître ton mot de passe : il emprunte ta session active.

Prévenir le CSRF

Deux protections, souvent combinées :

  • le jeton anti-CSRF : le serveur place un secret imprévisible dans chaque formulaire légitime et le vérifie à la réception. Un site tiers ne peut pas le deviner, donc sa requête forgée est rejetée.
  • l'attribut de cookie SameSite : SameSite=Lax ou Strict dit au navigateur de ne pas envoyer le cookie de session lors de requêtes venues d'un autre site. La requête forgée arrive alors sans session, et échoue.

Les frameworks web intègrent généralement ces protections ; ton rôle est de ne pas les désactiver et de les appliquer aux actions sensibles (toute opération qui modifie l'état : POST, PUT, DELETE).

Piège fréquent

Tu poses HttpOnly sur le cookie de session et tu considères le CSRF réglé. Non : HttpOnly empêche seulement le JavaScript de lire le cookie, ce qui contre son vol par XSS. Le navigateur, lui, continue de joindre automatiquement ce cookie à une requête déclenchée depuis un site tiers, donc la requête forgée passe toujours. Contre le CSRF, il te faut SameSite et un jeton anti-CSRF ; HttpOnly répond à un tout autre problème.

XSS et CSRF se renforcent

Les cookies HttpOnly protègent une session contre le vol par XSS (le JavaScript ne peut pas les lire). Mais un XSS reste dangereux : le script injecté peut agir directement dans la page. D'où l'importance de traiter les deux failles : encoder pour le XSS, jetons + SameSite pour le CSRF. La sécurité fonctionne par couches, pas par une parade unique.

Le point exact où le XSS revient

Les frameworks (React, Vue, Angular) encodent par défaut : tant que tu affiches une donnée normalement, tu es protégé. Le danger resurgit à un seul endroit — quand tu forces l'insertion de HTML brut : innerHTML, dangerouslySetInnerHTML (React), v-html (Vue). Réserve-les à une donnée de confiance, ou nettoie-la d'abord avec une bibliothèque dédiée (par exemple DOMPurify).

Antisèche

Glossaire

XSS (Cross-Site Scripting)
Injection d'un script dans une page ; il s'exécute dans le navigateur des visiteurs.
Encodage HTML
Conversion des caractères spéciaux (<, >…) en entités, pour qu'ils s'affichent comme texte au lieu d'être interprétés.
CSP (Content-Security-Policy)
En-tête qui restreint les sources de scripts autorisées : défense en profondeur contre le XSS.
CSRF (Cross-Site Request Forgery)
Attaque où un site tiers déclenche une action authentifiée en réutilisant la session de la victime.
Jeton anti-CSRF
Secret imprévisible placé dans chaque formulaire légitime et vérifié côté serveur.
SameSite
Attribut de cookie qui empêche son envoi lors de requêtes venues d'un autre site.
HttpOnly
Attribut rendant un cookie inaccessible au JavaScript : limite le vol de session par XSS.
XSS réfléchi
Variante où le script est glissé dans un lien piégé (paramètre d'URL) et renvoyé dans la page à la victime qui clique, par opposition au XSS stocké, enregistré côté serveur.

Récap et vérification

  • XSS : un script injecté s'exécute dans le navigateur de la victime ; parade = encoder à la sortie (+ CSP en défense en profondeur).
  • Les frameworks encodent par défaut ; le danger vient de l'insertion de HTML brut.
  • CSRF : un site tiers déclenche une action en empruntant ta session (cookies joints automatiquement).
  • Parades CSRF : jeton anti-CSRF + cookies SameSite (et HttpOnly, Secure).

Vérifie ta compréhension

  1. Quelle est la parade principale contre le XSS ?
  2. En quoi le CSRF diffère-t-il du XSS ?
  3. Comment l'attribut SameSite aide-t-il contre le CSRF ?

Exercices

Exercice 1Échauffement

Corrige ce code vulnérable au XSS : element.innerHTML = pseudo; (où pseudo vient de l'utilisateur).

Voir une solution

Utiliser textContent (ou encoder avant un innerHTML) empêche l'interprétation d'éventuelles balises.

Exercice 2Application

Cite les trois attributs de cookie de session importants pour la sécurité et le rôle de chacun.

Voir une solution

HttpOnly : le cookie est inaccessible au JavaScript (limite le vol par XSS). Secure : le cookie n'est envoyé qu'en HTTPS (pas en clair). SameSite (Lax/Strict) : le cookie n'est pas joint aux requêtes venues d'un autre site (protège du CSRF).

Exercice 3Défi

Un site permet de changer l'e-mail du compte via POST /compte/email sans protection CSRF. Décris l'attaque possible et les deux mesures pour la bloquer.

Voir une solution

Attaque : un site piège visité par la victime (connectée) soumet automatiquement un formulaire vers POST /compte/email avec l'e-mail de l'attaquant. Le navigateur joint les cookies de session ; le serveur change l'e-mail, ce qui permet ensuite une réinitialisation de mot de passe et la prise du compte. Mesures : 1) exiger un jeton anti-CSRF dans le formulaire et le vérifier côté serveur (le site tiers ne peut pas le fournir) ; 2) configurer le cookie de session en SameSite=Lax ou Strict pour qu'il ne soit pas envoyé sur la requête inter-sites. On peut aussi redemander le mot de passe pour une action aussi sensible.
