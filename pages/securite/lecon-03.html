Les injections

~40 min Intermédiaire Leçon 02 requise

À la fin de cette leçon, tu sauras

  • expliquer le mécanisme d'une injection ;
  • prévenir l'injection SQL avec les requêtes préparées ;
  • éviter l'injection de commande système ;
  • appliquer le principe séparer code et données.
Sommaire de la leçon

Les injections figurent en tête de l'OWASP Top 10 depuis des années, et pour une raison simple : elles sont fréquentes et dévastatrices. Le principe est toujours le même : une donnée fournie par l'utilisateur est interprétée comme du code au lieu d'être traitée comme une simple valeur. Bonne nouvelle : une seule bonne pratique — séparer le code des données — neutralise l'immense majorité des injections.

Le mécanisme d'une injection

Une injection survient quand on construit une instruction (requête SQL, commande shell, page HTML…) en collant directement une entrée utilisateur dans une chaîne de texte. Si cette entrée contient des caractères spéciaux du langage cible, elle déborde de son rôle de donnée et modifie l'instruction.

L'image juste : tu dictes une phrase à quelqu'un qui l'écrit. Si la « donnée » que tu dictes contient l'ordre « … et maintenant efface tout », et que le scribe l'exécute, c'est une injection. Le scribe (l'interpréteur) n'a pas su distinguer ce qui était contenu de ce qui était instruction.

La parade : les requêtes préparées

La solution n'est pas d'essayer d'échapper les apostrophes à la main (liste noire, fragile). C'est d'utiliser des requêtes préparées (prepared statements) avec des paramètres liés : la requête et les valeurs voyagent séparément, et la base traite les valeurs comme de pures données, jamais comme du code.

C'est la règle d'or, sans exception : toute valeur variable dans une requête passe par un paramètre lié. Les ORM modernes (vus dans les cours back-end) le font par défaut. Ne construis jamais une requête SQL par concaténation de chaînes contenant une entrée utilisateur.

L'injection de commande

Le même mécanisme frappe les commandes système. Si une application passe une entrée utilisateur à un shell, l'attaquant peut y glisser ses propres commandes.

Principe identique au SQL : au lieu de bâtir une chaîne de commande, on appelle le programme avec une liste d'arguments que le système ne ré-interprète pas. En général : évite d'appeler un shell avec des entrées utilisateur ; si tu dois lancer un programme, passe ses arguments séparément.

Le principe unificateur

Injection SQL, injection de commande, et même le XSS de la prochaine leçon partagent une seule cause : du code et des données mélangés dans une même chaîne, qu'un interpréteur lit ensemble. La parade est toujours la même idée : séparer le code des données (paramètres liés, arguments séparés, encodage contextuel) pour que l'interpréteur ne puisse jamais prendre une donnée pour une instruction.

Cas réel — TalkTalk (2015)

Le fournisseur d'accès britannique TalkTalk a vu les données d'environ 157 000 clients exfiltrées via de banales injections SQL sur des pages web mal protégées : aucune requête préparée, l'entrée était concaténée dans le SQL. Le régulateur a infligé une amende record à l'époque, et une partie de l'attaque a été menée par des adolescents à l'aide d'outils automatisés. La leçon : l'injection SQL n'est pas une menace théorique ni réservée à des experts ; c'est une des premières choses que testent les scanners automatiques.

La culture « Bobby Tables »

Une célèbre bande dessinée (xkcd nº 327) met en scène une mère qui a prénommé son fils Robert'); DROP TABLE Students;--. En inscrivant l'enfant, l'école exécute la requête… et perd sa table des élèves. C'est devenu le symbole de l'injection SQL. La morale de la vignette : « j'espère que vous avez appris à assainir vos entrées » — ou plutôt, à utiliser des requêtes préparées.

Antisèche

Glossaire

Injection
Faille où une entrée utilisateur est interprétée comme du code au lieu d'une simple donnée.
Injection SQL
Injection visant une requête de base de données, exploitant la concaténation d'entrées non contrôlées.
Requête préparée (prepared statement)
Requête où le code et les valeurs sont séparés ; les valeurs sont liées à des emplacements et jamais interprétées.
Paramètre lié
Valeur fournie séparément de la requête (via un emplacement ?), traitée comme une pure donnée.
Injection de commande
Injection où une entrée passe dans une commande shell et permet d'exécuter des commandes arbitraires.
Séparer le code des données
Principe unificateur des parades anti-injection : empêcher l'interpréteur de confondre contenu et instruction.

Récap et vérification

  • Une injection = une entrée utilisateur interprétée comme du code au lieu d'une donnée.
  • SQL : jamais de concaténation ; toujours des requêtes préparées à paramètres liés.
  • Commande système : éviter le shell ; passer les arguments séparément (execFile).
  • Cause et parade communes : séparer le code des données.

Exercice 2Application

Explique ce que ferait l'entrée nom = "'; DROP TABLE utilisateurs; --" dans une requête construite par concaténation, et pourquoi la version préparée est sans danger.

Voir une solution

Par concaténation, la requête deviendrait quelque chose comme : SELECT * FROM utilisateurs WHERE nom = ''; DROP TABLE utilisateurs; --'. L'attaquant termine la requête prévue, puis en ajoute une seconde qui supprime la table (le -- commente la fin). Avec une requête préparée, toute cette chaîne est traitée comme une simple valeur de recherche : la base cherche un utilisateur dont le nom est littéralement ce texte. Rien n'est exécuté ; aucune table n'est supprimée.

Exercice 3Défi

Une application redimensionne une image avec exec("convert " + nom + " -resize 100x100 out.png"). Identifie la faille et corrige-la.
