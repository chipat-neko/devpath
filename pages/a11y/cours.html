Accessibilité web (a11y)

Un site accessible, c'est un site que tout le monde peut utiliser — au clavier, au lecteur d'écran, avec une vue partielle ou des troubles moteurs. Ce cours t'apprend à concevoir pour tous : HTML sémantique, navigation clavier, ARIA, contrastes, et l'audit d'une page selon les règles WCAG. Ce n'est pas une option : c'est de la qualité, et souvent une obligation légale.

Bien s'équiper

Les extensions VS Code pour l'accessibilité

Ouvre le panneau Extensions de VS Code (Ctrl+Shift+X) et installe :

À installer pour ce cours

  • axe Accessibility Linter (Deque) — repère les problèmes d'accessibilité dans ton HTML.
  • webhint — analyse a11y, performance et bonnes pratiques.
  • HTMLHint — valide la structure et les attributs.
  • Error Lens — affiche les avertissements directement dans le code.

Et dans le navigateur, l'extension axe DevTools ou WAVE, ainsi que l'audit Lighthouse intégré aux DevTools.

Prérequis

Connaître les bases de HTML et de CSS suffit. Aucun outil particulier n'est requis pour pratiquer : un éditeur et un navigateur. Tester au clavier (touche Tab) ne coûte rien et révèle déjà beaucoup.

Ce que tu vas apprendre

Objectifs du cours

À la fin du cours, tu sauras

  • expliquer pour qui et pourquoi on rend un site accessible (et le cadre WCAG) ;
  • écrire un HTML sémantique bien structuré ;
  • rendre images, formulaires et navigation utilisables au clavier ;
  • utiliser ARIA à bon escient pour les composants interactifs ;
  • garantir des contrastes suffisants et un focus visible ;
  • auditer une page et corriger ses problèmes.

Pour qui, et pourquoi

Ce cours est pour toi si tu construis des pages web et veux qu'elles soient utilisables par le plus grand nombre — y compris les personnes en situation de handicap. L'accessibilité profite à tous : sous-titres dans le bruit, fort contraste en plein soleil, navigation clavier pour les power users…

Le fil conducteur est simple : un bon HTML, sémantique et ordonné, résout déjà l'essentiel. ARIA et le reste viennent compléter, pas remplacer.

Astuce

La première règle d'ARIA : ne pas utiliser ARIA s'il existe un élément HTML natif qui fait le travail. Un vrai <button> vaut mieux qu'un <div role="button">.

Récapitulatif

À retenir & glossaire

Les points clés du cours, puis les termes essentiels à connaître.

À retenir

  • L'accessibilité sert tout le monde ; les WCAG en sont le référentiel.
  • Un HTML sémantique bien structuré règle déjà la majorité des problèmes.
  • Tout doit être utilisable au clavier, avec un focus visible.
  • ARIA complète le HTML natif — on ne s'en sert que si nécessaire.
  • Des contrastes suffisants et des alternatives textuelles sont indispensables.
a11y
Abréviation d'« accessibility » (a + 11 lettres + y) : l'accessibilité numérique.
WCAG
Web Content Accessibility Guidelines : le référentiel international des règles d'accessibilité.
Lecteur d'écran
Un logiciel qui lit l'interface à voix haute pour les personnes aveugles ou malvoyantes.
Sémantique
Utiliser la balise qui correspond au sens (bouton, titre, liste…), pas seulement à l'apparence.
Texte alternatif (alt)
La description d'une image, lue quand l'image n'est pas vue.
Repère (landmark)
Une grande zone de la page (header, nav, main, footer) qui aide à se repérer.
Focus
L'élément actuellement sélectionné au clavier ; il doit rester visible.
Ordre de tabulation
L'ordre dans lequel la touche Tab parcourt les éléments interactifs.
ARIA
Des attributs (rôles, états, propriétés) qui complètent le HTML pour les technologies d'assistance.
Contraste
L'écart de luminosité entre un texte et son fond ; il doit être suffisant pour être lisible.
Lien d'évitement (skip link)
Un lien en début de page pour sauter directement au contenu principal.
