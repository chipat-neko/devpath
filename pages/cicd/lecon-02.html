Le pipeline : étapes et déclencheurs

~35 min Débutant Leçon 01 requise

À la fin de cette leçon, tu sauras

  • décrire les étapes d'un pipeline (build, test, deploy) ;
  • connaître les déclencheurs (push, PR, tag, planifié) ;
  • lire un statut de pipeline ;
  • appliquer la règle « échouer vite ».
Sommaire de la leçon

Le cœur de la CI/CD est le pipeline : une suite d'étapes automatisées que le code traverse, du commit jusqu'au déploiement. Comme une chaîne de montage, chaque étape ajoute une vérification ou une transformation, et le code n'avance que si l'étape précédente a réussi. Comprendre l'anatomie d'un pipeline est la clé pour en lire et en écrire un.

Les déclencheurs

Un pipeline ne se lance pas tout seul : un déclencheur (trigger) le démarre en réponse à un événement. Les principaux :

Le déclencheur le plus important est la pull request (ou merge request) : le pipeline s'exécute sur la proposition de fusion, et l'on peut bloquer la fusion tant qu'il n'est pas vert. C'est ce qui garantit que rien d'inspecté n'entre dans la branche principale. Le tag de version, lui, déclenche typiquement le déploiement d'une release.

À chaque exécution, le pipeline produit un statut visible (sur la plateforme, et souvent à côté du commit ou de la pull request) :

Le statut vert/rouge est le langage universel de la CI/CD. Un commit vert est sûr à fusionner ; un commit rouge demande qu'on aille lire les logs de l'étape échouée pour comprendre. La transparence est un atout : tout le monde voit l'état du projet d'un coup d'œil.

Échouer vite

Un bon pipeline applique le principe « fail fast » (échouer vite) : placer les vérifications rapides et les plus susceptibles d'échouer en premier. Inutile d'attendre vingt minutes de tests d'intégration pour apprendre qu'une erreur de syntaxe bloquait le build dès le début.

L'idée rejoint la pyramide des tests (cours Tests) : les vérifications rapides et nombreuses d'abord, les lentes et rares ensuite. Échouer tôt, c'est donner un retour rapide au développeur et économiser des ressources : le pipeline s'arrête dès le premier problème détecté.

Cas réel

Sur un projet aussi massif que Kubernetes, aucun changement n'atteint la branche principale sans passer une batterie de vérifications automatiques (son système de CI, Prow, lance des milliers de jobs par jour). La règle des « checks requis » (branch protection) bloque la fusion tant que le pipeline n'est pas vert : c'est le déclencheur pull request poussé à l'échelle industrielle. Résultat : des centaines de contributeurs répartis dans le monde fusionnent chaque jour sans casser la branche principale.

Le pipeline « comme du code »

Un pipeline moderne n'est pas configuré en cliquant dans une interface : il est décrit dans un fichier (souvent en YAML, cours Formats de données) versionné avec le projet. Avantages : le pipeline évolue avec le code, son historique est tracé dans Git, et il se rejoue à l'identique. C'est l'idée « pipeline as code » ; on en verra la structure concrète à la leçon suivante.

Glossaire

Étape (stage)
Une phase du pipeline (build, test, package, deploy). Elle doit réussir pour que la suivante démarre.
Déclencheur (trigger)
L'événement qui démarre un pipeline : push, pull request, tag de version, planification (cron) ou lancement manuel.
Pull request / merge request
Proposition de fusion d'une branche ; on y exécute le pipeline et l'on peut bloquer la fusion tant qu'il n'est pas vert.
Statut
Le résultat visible d'une exécution : vert (succès), rouge (échec), en cours, en attente. Le langage universel de la CI/CD.
Porte de qualité (quality gate)
Une condition à franchir avant de passer à l'étape suivante ; le pipeline en est une série.
Fail fast (échouer vite)
Placer les vérifications rapides et les plus susceptibles d'échouer en premier, pour obtenir le retour d'erreur au plus tôt.
Tag de version
Un repère nommé (ex. v1.2) posé sur un commit ; il déclenche souvent la livraison ou le déploiement d'une release.
Pipeline as code
Décrire le pipeline dans un fichier (souvent YAML) versionné avec le projet, plutôt qu'en cliquant dans une interface : tracé et rejouable.

Récap et vérification

  • Un pipeline enchaîne des étapes (build → test → package → deploy) ; chaque étape doit réussir pour passer à la suivante.
  • Déclencheurs : push, pull request (avec blocage de fusion), tag de version, planification, manuel.
  • Statut : vert (succès), rouge (échec → lire les logs), en cours, en attente.
  • « Échouer vite » : placer les vérifications rapides et probables d'abord (comme la pyramide des tests).

Vérifie ta compréhension

  1. Que se passe-t-il quand une étape du pipeline échoue ?
  2. Pourquoi le déclencheur « pull request » est-il si important ?
  3. Que recommande le principe « échouer vite » ?

Exercices

Exercice 1Échauffement

Cite, dans l'ordre, quatre étapes typiques d'un pipeline CI/CD.

Voir une solution

Par exemple : 1) build (compiler / installer les dépendances) ; 2) test (lancer les tests, le linter) ; 3) package (créer l'image/l'artefact déployable) ; 4) deploy (mettre en production ou sur un environnement). Chaque étape ne démarre que si la précédente a réussi.

Exercice 2Application

Un pipeline lance d'abord 20 minutes de tests E2E, puis le linter (5 secondes). Quel problème, et comment réordonner ?

Voir une solution

Problème : cela viole « échouer vite ». Une simple faute de style détectable en 5 secondes ne sera signalée qu'après 20 minutes de tests — du temps machine et d'attente gaspillé. Réordonner : mettre le linter (et les tests unitaires rapides) en premier, puis le build, et enfin les tests E2E lents. Ainsi, une erreur rapide arrête le pipeline en quelques secondes.

Exercice 3Défi

Tu veux qu'un déploiement en production ne se déclenche que pour une version officielle, pas à chaque commit. Quel déclencheur utiliser, et pourquoi pas le push sur la branche principale ?

Voir une solution

On utilise un tag de version (par ex. v1.2.0) comme déclencheur du déploiement en production. Pourquoi pas chaque push sur la branche principale ? Parce qu'on n'a pas forcément envie de déployer tout commit : la branche principale peut recevoir plusieurs changements avant qu'on décide de publier une version. Le tag marque explicitement « ceci est une release », ce qui rend les déploiements intentionnels et traçables (on sait exactement quelle version est en production). Les pushs, eux, déclenchent la CI (build + tests) sans aller jusqu'à la production.
