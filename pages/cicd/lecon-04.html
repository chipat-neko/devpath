Module 2 · Construire un pipeline — Leçon 04

Tester et vérifier dans le pipeline

~37 min Intermédiaire Leçon 03 requise

À la fin de cette leçon, tu sauras

  • placer les garde-fous qualité (linter, tests) ;
  • tester sur plusieurs versions avec une matrice ;
  • accélérer avec le cache des dépendances ;
  • produire et conserver des artefacts.
Sommaire de la leçon

Un pipeline n'a de valeur que par les vérifications qu'il exécute. C'est ici que la CI/CD rejoint le cours Tests & qualité : le pipeline est l'endroit où l'on rejoue automatiquement toute la chaîne qualité, à chaque changement. Cette leçon montre comment y brancher les garde-fous, et comment rendre l'ensemble rapide et utile.

Les garde-fous qualité

Dans le pipeline, on enchaîne les contrôles vus dans le cours Tests, du plus rapide au plus lent (principe « échouer vite ») :

Le mécanisme est simple : une commande qui renvoie un code de sortie non nul fait échouer l'étape, donc le job, donc le pipeline. C'est pourquoi tes outils de test et de lint doivent sortir en erreur quand quelque chose ne va pas — ce qu'ils font tous par défaut. Le pipeline ne fait qu'orchestrer et lire ces codes de sortie.

Tester sur plusieurs versions : la matrice

Souvent, on veut s'assurer que le code marche sur plusieurs versions d'un langage ou plusieurs systèmes. Une matrice (matrix) lance automatiquement le même job pour chaque combinaison, en parallèle.

La matrice évite de copier-coller le job trois fois : on déclare les valeurs, la plateforme génère les combinaisons. C'est précieux pour une bibliothèque qui doit fonctionner sur plusieurs versions, ou une application testée sur Linux, macOS et Windows à la fois.

Le cache des dépendances

Installer les dépendances à chaque exécution est lent. Le cache conserve d'une exécution à l'autre ce qui ne change pas (le dossier des dépendances), pour ne le retélécharger que lorsque c'est nécessaire.

Le cache peut transformer un pipeline de plusieurs minutes en quelques dizaines de secondes. La règle : la clé de cache est liée au fichier qui décrit les dépendances (le lock file) ; tant qu'il ne change pas, on réutilise le cache. C'est l'équivalent, pour le pipeline, du cache des couches Docker (cours Docker).

Les artefacts

Un pipeline produit souvent quelque chose qu'on veut conserver : un exécutable compilé, un rapport de couverture, des captures de tests. Ce sont des artefacts : on les téléverse pour les télécharger ensuite, ou les passer à un autre job.

Les artefacts relient les étapes du pipeline : un job build produit un artefact, qu'un job deploy récupère et envoie en production — sans tout reconstruire. Ils servent aussi au débogage : garder le rapport de couverture ou les logs d'un test échoué aide à comprendre ce qui s'est passé sur le runner.

Cas réel

Une équipe voyait sa CI durer plusieurs minutes à chaque exécution : l'essentiel du temps partait à retélécharger les mêmes dépendances. En activant le cache (cache: npm), le pipeline est tombé à quelques dizaines de secondes, débloquant des dizaines d'allers-retours par jour. À l'inverse, une bibliothèque testée uniquement sur macOS a cassé chez des utilisateurs Windows à cause d'un séparateur de chemin (\ contre /) : une matrice Linux/macOS/Windows aurait attrapé le bug avant publication. Le cache rend la CI rapide ; la matrice la rend fiable partout.

« Build once, deploy many »

Bonne pratique : construire l'artefact une seule fois, puis déployer ce même artefact sur chaque environnement (test, pré-production, production). Reconstruire à chaque environnement risquerait de produire des binaires légèrement différents ; en réutilisant l'artefact validé, on garantit que ce qui a été testé est exactement ce qui est déployé. C'est un principe clé de fiabilité.

Glossaire

Garde-fou qualité
Une vérification automatique du pipeline (linter, types, tests) qui doit passer pour continuer.
Code de sortie
L'entier renvoyé par une commande : 0 = succès, non nul = échec. Le pipeline le lit pour décider vert ou rouge.
Matrice (matrix)
Une déclaration qui lance le même job pour chaque combinaison de valeurs (versions, systèmes), en parallèle.
Cache
Conservation, d'une exécution à l'autre, de ce qui ne change pas (les dépendances) pour éviter de tout retélécharger.
Lock file
Fichier qui fige les versions exactes des dépendances (ex. package-lock.json) ; sert de clé de cache.
Artefact
Un fichier produit par le pipeline qu'on veut conserver ou transmettre : exécutable, rapport de couverture, logs.
Rapport de couverture
Mesure de la part du code exécutée par les tests ; souvent gardée en artefact pour la suivre.
Build once, deploy many
Construire l'artefact une seule fois, puis déployer ce même artefact sur chaque environnement : ce qui est testé est exactement ce qui est déployé.

Récap et vérification

  • Le pipeline enchaîne les garde-fous qualité (lint, types, tests) du plus rapide au plus lent ; un code de sortie non nul fait échouer.
  • Une matrice lance le même job pour plusieurs versions/systèmes, en parallèle.
  • Le cache des dépendances (clé liée au lock file) accélère fortement les exécutions.
  • Les artefacts conservent les sorties (build, rapports) pour les télécharger ou les passer à un job ultérieur — « build once, deploy many ».

Exercices

Exercice 1Échauffement

Dans quel ordre placerais-tu ces étapes dans un job : tests E2E, linter, tests unitaires ? Pourquoi ?

Voir une solution

Ordre : linter (très rapide), puis tests unitaires (rapides), puis tests E2E (lents). C'est le principe « échouer vite » : on place les vérifications les plus rapides et probables en premier, pour obtenir un retour immédiat et ne pas gaspiller de temps sur les étapes lentes si une erreur simple bloque déjà.

Exercice 2Application

Écris une stratégie de matrice qui teste une application sur Python 3.10, 3.11 et 3.12.

Voir une solution

La matrice génère trois exécutions parallèles, une par version de Python.

Exercice 3Défi

Explique le principe « build once, deploy many » et pourquoi il améliore la fiabilité.

Voir une solution

« Build once, deploy many » signifie : construire l'artefact une seule fois (dans le pipeline), puis déployer ce même artefact sur tous les environnements successifs (test, pré-production, production), au lieu de reconstruire à chaque étape. Pourquoi c'est plus fiable ? Parce que reconstruire à chaque environnement peut produire des binaires légèrement différents (dépendances mises à jour entre-temps, environnement de build qui change…). En déployant exactement l'artefact qui a été testé et validé, on garantit que « ce qui tourne en production est ce qui a passé les tests » — aucune surprise due à une reconstruction. On stocke l'artefact (via upload-artifact) et les jobs de déploiement le récupèrent.
