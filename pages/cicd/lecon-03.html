Module 2 · Construire un pipeline — Leçon 03

Anatomie d'un workflow

~38 min Intermédiaire Leçon 02 + YAML utiles

À la fin de cette leçon, tu sauras

  • lire un workflow CI/CD écrit en YAML ;
  • distinguer job, step et runner ;
  • réutiliser des actions existantes ;
  • écrire un pipeline build + test minimal.
Sommaire de la leçon

Place à la pratique : à quoi ressemble concrètement un pipeline ? On le décrit dans un fichier de workflow, en YAML, versionné avec le projet. Les plateformes diffèrent dans les détails (GitHub Actions, GitLab CI, Jenkins…), mais les concepts sont communs. On prend ici une syntaxe proche de GitHub Actions, la plus répandue, pour en disséquer l'anatomie.

Un workflow complet, commenté

Voici un pipeline qui, à chaque push et pull request, installe les dépendances et lance les tests. Lis-le de haut en bas : chaque mot-clé a un rôle.

Ce fichier dit : « à chaque push sur main et à chaque pull request, sur une machine Ubuntu, récupère le code, installe Node 20, installe les dépendances, et lance les tests ». Tout est explicite et versionné. Décortiquons les pièces.

Jobs, steps, runners

Trois niveaux structurent un workflow :

  • un job : une unité de travail qui s'exécute sur une machine, avec un but (tester, construire, déployer). Un workflow peut avoir plusieurs jobs.
  • un step (étape) : une action élémentaire dans un job — soit une commande shell (run), soit une action réutilisable (uses). Les steps s'exécutent dans l'ordre.
  • un runner : la machine (souvent une VM neuve, ou un conteneur) qui exécute le job. runs-on: ubuntu-latest demande un runner Ubuntu fourni par la plateforme.

Point clé : le runner part d'un environnement propre à chaque exécution — d'où l'étape checkout pour récupérer le code, et setup-node pour installer l'outillage. Rien n'est supposé présent : c'est ce qui rend le pipeline reproductible, indépendamment de « ta machine ».

Les actions réutilisables

Tu remarques les uses: actions/checkout@v4 : ce sont des actions, des briques réutilisables partagées par la communauté, qu'on assemble au lieu de tout réécrire. Récupérer le code, installer un langage, mettre en cache, publier un artefact : il existe une action pour la plupart des tâches courantes.

La distinction : uses appelle une action existante (avec sa version, @v4, pour la reproductibilité) ; run exécute des commandes shell que tu écris toi-même. On combine les deux : des actions pour les tâches standard, des run pour la logique propre à ton projet. C'est l'esprit « ne pas réinventer la roue ».

Cas réel

En mars 2025, l'action très populaire tj-actions/changed-files a été compromise : du code malveillant y a été injecté et a exposé les secrets de milliers de pipelines qui l'appelaient via une étiquette mobile (@v35). La parade : épingler une action à un commit précis (SHA) plutôt qu'à une étiquette, pour que uses pointe toujours vers le code exact que tu as inspecté. Réutiliser des briques fait gagner un temps fou, mais une action reste du code tiers qui s'exécute dans ton pipeline : on choisit ses dépendances avec soin.

Plusieurs jobs

Un workflow peut orchestrer plusieurs jobs, en parallèle ou en séquence grâce aux dépendances (needs). Par exemple : tester et vérifier le style en parallèle, puis déployer seulement si les deux ont réussi.

Les jobs sans dépendance tournent en parallèle (plus rapide) ; needs impose un ordre quand c'est nécessaire. Ici, deploy attend que test et lint soient verts : on ne déploie jamais sans avoir tout vérifié. Cette composition donne des pipelines à la fois rapides et sûrs.

Les concepts dépassent l'outil

GitLab CI, Jenkins, CircleCI… nomment parfois différemment (stages, pipelines, agents), mais on retrouve partout les mêmes idées : des déclencheurs, des unités de travail (jobs), des étapes, une machine d'exécution, et des briques réutilisables. Apprends les concepts : tu liras n'importe quel fichier de pipeline, quelle que soit la plateforme.

Antisèche

Glossaire

Workflow
Le fichier YAML qui décrit un pipeline (déclencheurs, jobs, steps), versionné avec le projet.
Job
Une unité de travail qui s'exécute sur une machine avec un but (tester, construire, déployer). Un workflow peut en contenir plusieurs.
Step (étape)
Une action élémentaire dans un job, soit une commande (run), soit une action (uses) ; les steps s'exécutent dans l'ordre.
Runner
La machine (souvent une VM neuve ou un conteneur) qui exécute un job ; elle part d'un environnement propre à chaque exécution.
Action
Une brique réutilisable partagée par la communauté, appelée avec uses (ex. actions/checkout@v4) ; on l'épingle par version.
run
Un step qui exécute des commandes shell que tu écris toi-même, pour la logique propre à ton projet.
needs
Déclare qu'un job dépend d'autres jobs : il ne démarre que lorsque ceux-ci ont réussi. Sans needs, les jobs tournent en parallèle.
YAML
Format texte structuré par l'indentation, utilisé pour décrire les workflows ; lisible par l'humain et versionnable dans Git.

Récap et vérification

  • Un workflow se décrit en YAML, versionné avec le projet : déclencheurs (on), jobs, steps.
  • Job (unité sur une machine) > step (commande run ou action uses) > exécuté sur un runner propre.
  • Les actions (uses) sont des briques réutilisables ; run exécute tes propres commandes.
  • Plusieurs jobs tournent en parallèle ; needs impose des dépendances (déployer seulement si tout est vert).

Vérifie ta compréhension

  1. Quelle différence entre un step avec uses et un step avec run ?
  2. Pourquoi le runner exécute-t-il une étape checkout au début ?
  3. À quoi sert needs entre deux jobs ?

Exercices

Exercice 1Échauffement

Dans un workflow, à quel niveau se situe un step par rapport à un job ?

Voir une solution

Un step (étape) est à l'intérieur d'un job. Un workflow contient un ou plusieurs jobs ; chaque job s'exécute sur un runner et contient une suite de steps (commandes run ou actions uses) exécutées dans l'ordre.

Exercice 3Défi

Tu veux un job deploy qui ne s'exécute qu'après la réussite de deux jobs test et build. Montre comment l'exprimer.

Voir une solution

needs: [test, build] rend deploy dépendant des deux autres ; test et build, sans dépendance, tournent en parallèle, puis deploy démarre seulement si les deux sont verts.
