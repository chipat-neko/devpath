Module 4 · CI/CD en pratique — Leçon 09

Conteneurs et registres dans le pipeline

~38 min Intermédiaire Leçon 08 recommandée

À la fin de cette leçon, tu sauras

  • construire une image et la pousser vers un registre depuis le pipeline ;
  • étiqueter une image par une empreinte immuable plutôt que latest ;
  • lancer des services conteneurisés (base de données) pour les tests d'intégration ;
  • accélérer la construction avec le cache de couches.
Sommaire de la leçon

Jusqu'ici, le pipeline vérifiait le code. Il peut aussi le fabriquer : construire une image (cours Docker) et la publier dans un registre, d'où le déploiement la tirera. L'image devient alors l'artefact déployable unique : on la construit une fois, on la promeut d'environnement en environnement. C'est le cœur du « build once, deploy many ». Cette leçon montre comment le pipeline construit, étiquette et publie cette image — et comment il s'appuie sur des conteneurs jetables pour tester.

Construire et publier une image

La chaîne est toujours la même : on construit l'image à partir du Dockerfile, on l'étiquette (un ou plusieurs tags), puis on la pousse vers un registre. Le déploiement, plus tard, n'aura qu'à la tirer. Un registre courant et gratuit pour un dépôt GitHub est GHCR (ghcr.io) ; Docker Hub, GitLab Registry ou ceux des clouds fonctionnent pareil.

Le GITHUB_TOKEN est fourni automatiquement à chaque run : avec packages: write, il suffit à s'authentifier auprès de GHCR — aucun mot de passe à stocker. build-push-action enchaîne la construction et le push en une étape.

Bien étiqueter ses images

Une même image peut porter plusieurs tags. Le piège classique : ne déployer que latest. Ce tag bouge — il désigne « la dernière poussée », donc une image différente d'un jour à l'autre. Impossible de savoir ce qui tourne, ni de revenir en arrière proprement. La règle : déployer une référence immuable, typiquement le SHA du commit (ou un digest sha256:…), et réserver latest au confort local.

Cas réel

Une équipe déployait toujours monimage:latest. Un soir, un correctif urgent est poussé, mais l'orchestrateur, ayant déjà latest en cache, ne retéléchargeait pas l'image : le correctif n'est jamais parti en production, et personne ne comprenait pourquoi. Pire, impossible de dire quelle version tournait réellement. En passant au tag par SHA (app:sha-9f3c1a), chaque déploiement référence une image unique et vérifiable : le retour arrière consiste simplement à redéployer le SHA précédent.

Des services pour les tests d'intégration

Tester une application qui parle à une base de données demande… une base de données. Plutôt que d'en installer une sur le runner, on déclare un service : la plateforme lance un conteneur (Postgres, Redis…) à côté du job, joignable en localhost, et le supprime à la fin. Éphémère, isolé, identique à chaque run.

Le --health-cmd fait attendre que la base soit prête avant de lancer les tests : sans lui, le job démarrerait parfois plus vite que Postgres et échouerait au hasard — un test instable déguisé.

Astuce — mettre en cache les couches de build

Construire une image relance les mêmes étapes à chaque commit. Active le cache de couches pour ne reconstruire que ce qui a changé : avec build-push-action, ajoute cache-from: type=gha et cache-to: type=gha,mode=max. Combiné à un Dockerfile multi-étapes bien ordonné (les couches stables d'abord, le code applicatif en dernier), une image qui prenait plusieurs minutes se reconstruit en quelques dizaines de secondes.

Glossaire

Image
Paquet figé contenant l'application et son environnement d'exécution ; construite depuis un Dockerfile, elle est l'artefact déployable.
Registre
Dépôt distant d'images (GHCR, Docker Hub, registres des clouds) : on y pousse après construction, on y tire au déploiement.
GHCR
GitHub Container Registry (ghcr.io), le registre intégré à GitHub ; l'authentification passe par le GITHUB_TOKEN.
Tag
Étiquette lisible attachée à une image (app:1.4.2, app:latest) ; un tag peut être réassigné à une autre image.
Digest (SHA256)
Empreinte immuable du contenu d'une image (sha256:…) : elle désigne toujours exactement la même image.
build-push-action
Action officielle qui construit une image et la pousse vers un registre en une étape.
Service (conteneur de service)
Conteneur lancé à côté du job (base de données, cache…), joignable en localhost et détruit à la fin du job.
Cache de couches
Réutilisation des couches d'image inchangées entre deux constructions, pour ne rebâtir que ce qui a bougé.

Récap et vérification

  • Le pipeline peut construire et pousser une image (build-push-action + login-action) vers un registre comme GHCR.
  • On déploie une référence immuable (tag par SHA, digest) ; latest bouge et casse la reproductibilité.
  • Un service conteneurisé fournit une base jetable pour les tests d'intégration, joignable en localhost.
  • Le cache de couches (type=gha) et un Dockerfile bien ordonné accélèrent la construction.

Vérifie ta compréhension

  1. Pourquoi éviter de déployer le tag latest en production ?
  2. À quoi sert la permission packages: write dans le job ?
  3. Pourquoi ajouter un --health-cmd à un service de base de données ?
