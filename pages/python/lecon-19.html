Module 07 · Python en pratique — Leçon 19

Outils du quotidien : CLI, logging, pathlib

~34 min Intermédiaire Leçon 18 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire une interface en ligne de commande avec argparse (arguments, types, aide auto) ;
  • savoir remplacer print par le module logging et configurer niveaux, format et destination ;
  • savoir manipuler les chemins de façon portable avec pathlib et lire des données (json, csv, config) ;
  • savoir lire des variables d'environnement et lancer des commandes externes avec subprocess sans faille d'injection.
Sommaire de la leçon

Tu sais déjà écrire des fonctions, manipuler des listes, lire des fichiers et lever des exceptions. Maintenant on franchit un cap : transformer un script jetable en outil qu'on lance depuis un terminal, qui prend des arguments, écrit des journaux propres et manipule des chemins sans casser dès qu'on change de machine. Tout ça avec la bibliothèque standard : aucun paquet à installer.

On va voir les modules que tu retrouveras dans presque tous les scripts « sérieux » : argparse pour la ligne de commande, logging pour les journaux, pathlib pour les chemins, et le trio config (json, csv, tomllib), variables d'environnement et subprocess. Aucune nouvelle syntaxe : que de l'outillage pratique.

Donner des arguments à ton script

Le plus brut : sys.argv, la liste des mots tapés après le nom du script. Utile à comprendre, mais vite pénible (pas de types, pas d'aide, pas de validation).

Dès qu'un script a plus d'un argument, passe à argparse. Tu déclares ce que tu attends, et tu obtiens gratuitement la conversion de type, les valeurs par défaut, les messages d'erreur et une aide --help.

Pour un outil avec plusieurs actions (comme git add, git commit), tu utilises des sous-commandes via add_subparsers().

Note

Pour des CLI riches (couleurs, complétion, sous-commandes auto à partir de fonctions typées), regarde typer ou click. Mais argparse couvre l'immense majorité des besoins et ne demande aucune installation.

Journaliser proprement avec logging

Quand un script grossit, print devient un piège : impossible de couper les messages de débogage sans les supprimer, pas d'horodatage, pas de niveau d'importance, et tout part sur la sortie standard. Le module logging règle tout ça avec quatre niveaux courants : DEBUG, INFO, WARNING, ERROR.

L'intérêt : tu changes une ligne (level=logging.DEBUG) pour voir tous les détails, sans toucher au reste. Tu peux aussi envoyer les journaux dans un fichier au lieu de la console grâce à un handler.

Un handler décide où vont les messages : console, fichier, les deux. On peut en ajouter plusieurs.

Astuce

Dans un bloc except, utilise log.exception("message") : il enregistre ton message et la trace complète de l'erreur (traceback), sans que tu aies à la formater.

Manipuler les chemins avec pathlib

Construire un chemin en collant des chaînes (dossier + "/" + nom) marche mal : Windows utilise le séparateur antislash, Linux et macOS utilisent /, et tu finis avec des doubles barres ou des erreurs. pathlib fournit un objet Path qui gère tout, avec l'opérateur / pour assembler.

Path sait aussi lire et écrire un fichier texte d'un coup, et lister des fichiers avec glob (motifs avec *).

Préfère pathlib à os.path : c'est plus lisible et orienté objet. Beaucoup de fonctions de la stdlib acceptent directement un Path.

Lire et écrire des données structurées

Tes scripts échangent souvent des données : json pour des structures imbriquées, csv pour des tableaux, et un format de configuration pour les réglages.

Pour la configuration, le format .toml est devenu le standard Python (c'est celui de pyproject.toml). Depuis Python 3.11, tomllib le lit dans la stdlib ; sinon il reste configparser pour le vieux format .ini.

Note

tomllib lit le TOML mais ne l'écrit pas ; tomllib.loads attend une chaîne de texte, alors que tomllib.load attend un fichier ouvert en binaire ("rb"). Si tu dois générer du TOML, il faut le paquet externe tomli-w. Pour de la config simple que ton programme modifie, json reste le plus pratique.

Variables d'environnement et config par environnement

Une règle d'or : jamais de secret (mot de passe, clé d'API) écrit en dur dans le code. On les lit depuis l'environnement via os.environ. Ça permet aussi d'avoir des réglages différents entre ta machine et le serveur de production, sans changer une ligne.

Lancer des commandes externes avec subprocess

Parfois ton script doit appeler un autre programme (git, un convertisseur, un outil système). subprocess.run le fait. Tu passes la commande sous forme de liste, et tu peux récupérer sa sortie.

Piège fréquent

N'utilise pas shell=True avec une entrée que tu ne contrôles pas : c'est une faille d'injection de commande. Si un utilisateur fournit fichier.txt; rm -rf /, le shell exécute les deux. Garde la forme en liste, qui ne passe pas par le shell.

Cas réel

Une équipe fait tourner chaque nuit un script de sauvegarde via une tâche planifiée (cron). Personne ne le regarde s'exécuter à 3 h du matin. Les quatre outils de cette leçon le transforment en véritable outil de production : argparse permet de le relancer à la main sur un seul dossier pour diagnostiquer (backup.py /data/clients --verbeux) ; logging vers un fichier horodaté laisse une trace lisible le lendemain (combien de fichiers copiés, quelles erreurs) ; os.environ garde le mot de passe du stockage distant hors du code ; et pathlib fait tourner le même script à l'identique sur le portable Windows d'un dev et sur le serveur Linux. C'est toute la différence entre un script jetable et un outil fiable.

Pièges fréquents

Piège fréquent

Garder des print de débogage partout : tu ne peux ni les filtrer ni les rediriger. Passe à logging dès qu'un script dépasse quelques lignes.

  • Concaténer des chemins à la main (dossier + "/" + nom) : casse selon l'OS. Utilise Path(dossier) / nom.
  • Oublier type= dans argparse : args.nombre reste une chaîne et range(args.nombre) plante. Déclare type=int.
  • Secrets dans le code : une clé écrite en dur finit sur Git et fuite. Lis-la depuis os.environ.
  • Chemins absolus codés en dur : le script ne marche que chez toi. Calcule les chemins relativement au script avec Path(__file__).parent.
  • shell=True sur une entrée non fiable : faille d'injection. Reste sur la forme en liste.

Pour aller plus loin

Pour aller plus loin

Côté CLI : typer et click pour des interfaces riches, rich pour une sortie colorée et des tableaux. Côté config : python-dotenv pour charger un fichier .env. Côté journaux : structlog pour des logs structurés (JSON). Pour planifier des tâches récurrentes : APScheduler. Ce sont tous des paquets externes (pip install), à explorer une fois les bases de la stdlib maîtrisées.

Glossaire

argparse
Module standard qui construit une interface en ligne de commande : on déclare les arguments attendus et on obtient la conversion de types, les valeurs par défaut, l'aide --help et les messages d'erreur.
Argument positionnel / option
Un positionnel est requis et repéré par sa place (nom) ; une option est facultative et nommée par un tiret (-n, --nombre). action="store_true" en fait un drapeau booléen.
logging
Module de journalisation : classe les messages par niveau (DEBUG, INFO, WARNING, ERROR, CRITICAL) et les envoie vers une ou plusieurs destinations.
Handler
Composant de logging qui décide où partent les messages : la console (StreamHandler), un fichier (FileHandler)… On peut en cumuler plusieurs.
pathlib / Path
Représentation orientée objet d'un chemin ; l'opérateur / assemble les segments de façon portable et des propriétés (.name, .suffix, .parent) le décomposent.
subprocess
Module pour lancer un programme externe ; subprocess.run([...]) prend la commande sous forme de liste et récupère code de retour, sortie standard et erreurs.
Injection de commande
Faille où une entrée non maîtrisée est interprétée par le shell (shell=True) et exécute des commandes arbitraires ; on l'évite en passant les arguments en liste.
Variable d'environnement
Réglage lu hors du code via os.environ (secrets, APP_ENV…) ; permet des configurations différentes selon la machine sans modifier le programme.

Récap et vérification

  • argparse donne une vraie interface en ligne de commande : arguments typés, aide et erreurs automatiques, sous-commandes.
  • logging remplace print : niveaux, format, console ou fichier, filtrage par une seule ligne.
  • pathlib manipule les chemins de façon portable avec /, exists, glob, read_text/write_text.
  • json, csv, tomllib/configparser couvrent les données et la configuration.
  • os.environ pour les secrets et la config par environnement ; subprocess.run (jamais shell=True sur une entrée non fiable) pour les commandes externes.
