Module 07 · Python en pratique — Leçon 18

Environnements virtuels et écosystème (pip)

~33 min Intermédiaire Cours Python recommandé

À la fin de cette leçon, tu sauras

  • savoir créer et activer un environnement virtuel avec python -m venv ;
  • savoir installer des paquets avec pip et figer les versions dans requirements.txt ;
  • savoir évaluer un paquet sur PyPI et reconnaître les bibliothèques phares de l'écosystème ;
  • savoir utiliser une bibliothèque tierce comme requests sans committer son .venv.
Sommaire de la leçon

Jusqu'ici, tu as travaillé avec ce que Python apporte d'origine : la bibliothèque standard. Mais la vraie force de Python, c'est son écosystème : des centaines de milliers de bibliothèques tierces que tu peux installer en une commande. Encore faut-il les installer proprement, sans transformer ta machine en champ de mines de versions incompatibles.

Cette leçon te montre l'outillage pratique du quotidien : isoler les dépendances par projet, les installer avec pip, les figer pour rendre ton projet reproductible, puis utiliser une vraie bibliothèque tierce. C'est ce qui sépare un script qui « marche chez moi » d'un projet partageable.

Le problème : tout installer globalement

Quand tu installes un paquet sans précaution, il atterrit dans le Python global de ta machine, partagé par tous tes projets. Imagine deux projets : l'un a besoin de la version 1.0 d'une bibliothèque, l'autre de la version 2.0 (incompatible). Une seule peut être installée à la fois. Tu es coincé.

Une installation globale impose une seule version pour toute la machine.

Les conflits de versions sont la première source de galère du débutant. La solution n'est pas de jongler à la main, mais d'isoler chaque projet dans son propre environnement.

Les environnements virtuels avec venv

Un environnement virtuel est un dossier qui contient une copie isolée de Python et de ses paquets, propre à un projet. Tu en crées un par projet, et ses bibliothèques n'ont aucun effet sur les autres. L'outil est livré avec Python : le module venv.

Un environnement par projet : crée, active, travaille isolé.

Une fois l'environnement activé, python et pip pointent vers cette copie isolée. Pour en sortir, tape deactivate. La convention est de nommer le dossier .venv (le point le rend discret) et d'en mettre un à la racine de chaque projet.

Note

Il existe des outils plus modernes qui gèrent environnement et dépendances ensemble : uv (très rapide, en plein essor), poetry, ou conda (populaire pour la data science). Le module venv reste le socle universel à connaître : il est partout et ne demande rien à installer.

pip : installer et figer les dépendances

pip est le gestionnaire de paquets de Python. Une fois ton environnement activé, tu installes ce dont tu as besoin, et tout reste confiné dans .venv.

pip freeze dresse la liste exacte des versions présentes.

La sortie de pip freeze est précieuse : on la sauvegarde dans un fichier requirements.txt. Ce fichier devient la « liste de courses » de ton projet : n'importe qui peut recréer le même environnement.

Le redirecteur > écrit la liste dans le fichier ; -r la relit.

Épingler les versions (avec ==) garantit la reproductibilité : ton collègue, ton serveur et toi exécutez le même code avec les mêmes bibliothèques. Sans épinglage, une mise à jour silencieuse d'une dépendance peut casser ton projet du jour au lendemain.

PyPI : trouver et évaluer un paquet

Tous ces paquets viennent de PyPI (Python Package Index), le dépôt central. pip install nom va y chercher le paquet. Avant d'ajouter une dépendance, prends trente secondes pour l'évaluer : tu fais entrer du code étranger dans ton projet.

  • Popularité : nombre de téléchargements, étoiles GitHub. Un paquet très utilisé est mieux testé.
  • Maintenance : date de la dernière version, activité des commits, issues traitées. Un projet abandonné depuis trois ans est un risque.
  • Sécurité : vérifie l'orthographe exacte du nom (les pirates publient des paquets aux noms proches, c'est le « typosquatting »), et regarde s'il a des vulnérabilités connues.

Astuce

Avant d'installer une bibliothèque entière, demande-toi si la bibliothèque standard ne suffit pas déjà. Pour lire un JSON local, manipuler des dates ou parcourir des fichiers, la stdlib (json, datetime, pathlib) fait le travail sans aucune dépendance.

Les bibliothèques phares en survol

Tu n'as pas à les connaître par cœur, mais sache qu'elles existent : le jour où tu en as besoin, tu sauras vers quoi te tourner.

  • requests : faire des requêtes HTTP (appeler une API web) de façon lisible.
  • numpy et pandas : le calcul numérique et l'analyse de données tabulaires (l'écosystème data). L'idée : manipuler de gros tableaux de chiffres très efficacement.
  • Pillow : ouvrir, redimensionner et transformer des images.
  • rich et typer : afficher du texte coloré et des tableaux dans le terminal, et construire des interfaces en ligne de commande propres.

Chacune résout un problème que la stdlib ne couvre pas (ou couvre mal). Le réflexe sain : stdlib d'abord, bibliothèque tierce quand elle apporte une vraie valeur.

Utiliser une bibliothèque tierce

Une fois requests installé dans ton environnement, tu l'importes comme n'importe quel module. Voici un appel HTTP complet : on interroge une API publique et on lit le JSON de la réponse.

requests.get récupère la page, .json() la convertit en dictionnaire.

En trois lignes, tu as parlé à un serveur distant et exploité sa réponse comme un dictionnaire ordinaire. C'est exactement le genre de tâche pour lequel une bibliothèque tierce brille : la version en stdlib pure (urllib) existe, mais est nettement plus verbeuse.

Bonnes pratiques et pyproject.toml

Quelques habitudes te feront gagner un temps fou et t'éviteront des bugs sournois.

  • Ne committe jamais .venv dans Git : il est lourd, spécifique à ta machine, et se recrée en une commande. Ajoute-le à ton .gitignore.
  • Committe toujours requirements.txt : c'est lui, et non l'environnement, qui décrit tes dépendances.
  • Épingle les versions pour des builds reproductibles.

Le .gitignore garde l'environnement hors du dépôt.

Pour les projets plus structurés, le fichier moderne pyproject.toml centralise les métadonnées (nom, version, dépendances) en un seul endroit standardisé. Tu le croiseras de plus en plus ; voici à quoi il ressemble.

Aperçu d'un pyproject.toml : les dépendances déclarées au même endroit que le projet.

Cas réel

Un nouveau développeur rejoint une équipe. Sans environnements ni requirements.txt, l'installation vire au cauchemar : « ça marche sur ma machine », des heures perdues à deviner les bonnes versions. Avec la bonne hygiène, son intégration tient en trois commandes : git clone, python -m venv .venv puis pip install -r requirements.txt — et il obtient exactement le même environnement que le reste de l'équipe et que le serveur de production. C'est aussi ce que rejoue un serveur d'intégration continue (CI) à chaque changement : repartir d'un environnement propre et reproductible.

Pièges fréquents

Piège fréquent

Tu fais pip install sans avoir activé ton environnement : le paquet part dans le Python global et pollue toute ta machine. Vérifie toujours que (.venv) apparaît dans ton invite avant d'installer quoi que ce soit.

  • Committer .venv : des milliers de fichiers inutiles dans ton dépôt, et qui ne marcheront même pas sur une autre machine.
  • Requirements non épinglés : sans ==, une future version d'une dépendance peut casser ton projet sans que tu changes une ligne.
  • Confondre python/python3 et pip/pip3 : sur certains systèmes, python renvoie encore une vieille version. Une fois ton venv activé, le souci disparaît : python y désigne sans ambiguïté la bonne version.
  • Faire confiance à un paquet non maintenu : dernière version il y a quatre ans, issues ignorées… cherche une alternative vivante.

Glossaire

Environnement virtuel
Dossier (.venv) contenant une copie isolée de Python et de ses paquets, propre à un projet ; évite les conflits de versions entre projets.
venv
Module de la bibliothèque standard qui crée un environnement virtuel : python -m venv .venv.
pip
Gestionnaire de paquets de Python : installe, met à jour et liste les bibliothèques depuis PyPI.
PyPI
Python Package Index, le dépôt central public où pip télécharge les paquets.
Dépendance
Bibliothèque tierce dont ton projet a besoin ; une dépendance peut elle-même en tirer d'autres (dépendances transitives).
requirements.txt
Fichier listant les paquets et leurs versions exactes ; permet de recréer l'environnement à l'identique.
Épingler (pin)
Fixer une version précise avec == pour des installations reproductibles dans le temps et entre machines.
Typosquatting
Publication de paquets malveillants aux noms proches des vrais ; vérifie toujours l'orthographe exacte avant d'installer.

Récap et vérification

  • Installer globalement crée des conflits de versions : isole chaque projet.
  • python -m venv .venv crée un environnement ; tu l'actives avant de travailler.
  • pip install installe, pip freeze > requirements.txt fige les versions.
  • pip install -r requirements.txt recrée l'environnement à l'identique.
  • Évalue un paquet PyPI (popularité, maintenance, sécurité) avant de l'adopter ; la stdlib suffit souvent.
  • Ne committe pas .venv, committe requirements.txt, épingle les versions.
