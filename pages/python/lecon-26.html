La concurrence : threads, processus et asyncio

~38 min Avancé Leçon 24 recommandée

À la fin de cette leçon, tu sauras

  • expliquer ce qu'est le GIL et pourquoi il compte ;
  • distinguer une tâche d'attente (I/O) d'une tâche de calcul (CPU) ;
  • accélérer des téléchargements avec des threads (concurrent.futures) ;
  • répartir du calcul lourd sur plusieurs cœurs avec les processus ;
  • découvrir asyncio (async/await) et savoir quel outil choisir.
Sommaire de la leçon

« Mon script télécharge 100 pages, ça prend deux minutes : peut-on aller plus vite ? » Presque toujours, oui — en faisant plusieurs choses en même temps. Mais Python propose trois outils pour ça (threading, multiprocessing, asyncio) et choisir le mauvais ne change rien, voire ralentit. La clé pour trancher tient en une question : ta tâche attend-elle, ou calcule-t-elle ? Et pour comprendre pourquoi, il faut d'abord rencontrer le GIL.

Le GIL : un seul cœur pour le code Python

Le GIL (Global Interpreter Lock) est un verrou interne de CPython : à tout instant, un seul thread exécute du bytecode Python. Même sur un processeur à 8 cœurs, deux threads ne calculent jamais réellement en parallèle. Ce verrou simplifie l'interpréteur, mais il a une conséquence énorme sur le choix de l'outil.

À retenir

Le GIL n'empêche pas la concurrence de l'attente : quand un thread attend une réponse réseau, il lâche le verrou, et un autre thread avance. C'est pourquoi les threads restent très utiles… tant qu'on attend. Python 3.13 introduit un mode expérimental « sans GIL », mais la règle ci-dessous reste la référence.

Deux natures de tâches

Tout se joue ici. Une tâche I/O-bound passe l'essentiel de son temps à attendre quelque chose d'extérieur (réseau, disque, base de données). Une tâche CPU-bound passe son temps à calculer (traiter une image, compresser, faire des maths).

Threads : pour tout ce qui attend

Pour télécharger 100 pages, le goulot n'est pas le processeur mais le réseau : pendant qu'une requête attend, une autre peut partir. Le module de haut niveau concurrent.futures rend ça limpide avec un ThreadPoolExecutor.

Processus : pour le calcul lourd

Pour du calcul pur, les threads ne servent à rien (le GIL les sérialise). Il faut de vrais processus, chacun avec son propre interpréteur et son propre GIL. Même API, un seul mot change : ProcessPoolExecutor.

Attention

Les processus ne partagent pas la mémoire : échanger des données a un coût (elles sont copiées entre processus). Pour de petites tâches, ce coût dépasse le gain. Les processus valent le coup quand chaque tâche calcule longtemps. Sur Windows, protège toujours le lancement par if __name__ == "__main__":.

asyncio : l'attente, sans threads

asyncio obtient le même résultat que les threads pour l'I/O, mais avec un seul thread et une « boucle d'événements ». Tu marques les fonctions async def et tu attends avec await : à chaque await, Python part faire autre chose au lieu de bloquer. C'est le choix des serveurs qui gèrent des milliers de connexions simultanées.

Bonne pratique

Threads ou asyncio ? Les threads conviennent au code existant (bibliothèques classiques comme requests), sans réécriture. asyncio brille à très grande échelle mais impose des bibliothèques compatibles (httpx, aiohttp) et de « colorer » tout le code en async. Pour commencer, un ThreadPoolExecutor suffit presque toujours.

Cas réel : un agrégateur de prix

Cas réel

Un comparateur qui interroge 20 boutiques pour un même produit est un cas d'école I/O-bound : chaque requête passe son temps à attendre le réseau. En séquentiel, 20 × 300 ms = 6 secondes ; avec un ThreadPoolExecutor, les 20 attentes se superposent et le tout prend ~300 ms. À l'inverse, un script qui redimensionne 500 photos est CPU-bound : seul multiprocessing exploitera les 8 cœurs de la machine. Diagnostiquer la nature de la tâche avant de coder évite d'optimiser dans le vide.

Pour aller plus loin

Quand plusieurs threads modifient une même donnée, on risque une situation de compétition (race condition) : on protège alors la section critique avec un threading.Lock. Pour du calcul distribué au-delà d'une machine, on regarde Dask, Ray ou multiprocessing.Pool à grande échelle. Et l'écriture asynchrone irrigue tout l'écosystème web moderne (FastAPI, ASGI).

Glossaire

Concurrence
Faire progresser plusieurs tâches sur une même période ; distincte du parallélisme, qui les exécute réellement au même instant.
GIL (Global Interpreter Lock)
Verrou de CPython garantissant qu'un seul thread exécute du bytecode Python à la fois ; il limite le parallélisme du calcul.
I/O-bound
Tâche dont le temps est dominé par l'attente d'une ressource externe (réseau, disque) ; accélérée par les threads ou asyncio.
CPU-bound
Tâche dont le temps est dominé par le calcul ; accélérée par plusieurs processus.
Thread
Fil d'exécution partageant la mémoire du programme ; léger, idéal pour l'attente, soumis au GIL pour le calcul.
Processus
Programme indépendant avec sa propre mémoire et son propre GIL ; permet un vrai calcul parallèle.
Coroutine
Fonction async def pouvant se suspendre à un await pour laisser tourner d'autres coroutines.
Boucle d'événements
Cœur d'asyncio qui orchestre les coroutines sur un seul thread ; lancée par asyncio.run.

Récap et vérification

  • Le GIL n'autorise qu'un thread à exécuter du bytecode Python à la fois : pas de calcul vraiment parallèle avec les threads.
  • Une tâche I/O-bound (attente) profite des threads ou d'asyncio ; une tâche CPU-bound (calcul) réclame des processus.
  • concurrent.futures unifie l'API : ThreadPoolExecutor et ProcessPoolExecutor, avec executor.map.
  • asyncio (async/await, gather) gère l'attente à très grande échelle sur un seul thread.
  • Diagnostique la nature de la tâche avant de choisir l'outil.

Voir une solution

CPU-bound : (a) décimales de π, (d) compression vidéo → multiprocessing. I/O-bound : (b) lecture disque, (c) appels API → threads ou asyncio. Le critère : la tâche calcule-t-elle ou attend-elle ?
