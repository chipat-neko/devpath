Module 15 · Python à l'échelle — Leçon 45

Python en production

~34 min Avancé Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • savoir structurer un pyproject.toml moderne et produire des wheels reproductibles avec lockfiles ;
  • savoir charger configuration et secrets selon les principes 12-factor via pydantic-settings ;
  • savoir instrumenter l'observabilité (logs JSON structurés, métriques, tracing corrélé) et profiler en prod avec py-spy ;
  • savoir conteneuriser en multi-stage non-root et garantir la fiabilité (retries, health checks, arrêt propre).
Sommaire de la leçon

Tu connais le langage en profondeur. Reste la partie qui décide si ton code survit à un incident à 3 h du matin : le déploiement et l'exploitation. Cette leçon ne parle pas de syntaxe mais d'opérabilité — comment un service Python se construit de façon reproductible, se configure sans fuite de secrets, raconte ce qu'il fait, et s'arrête sans couper les requêtes en cours.

Le fil conducteur est le manifeste 12-factor : dépendances déclarées et isolées, configuration dans l'environnement, logs comme flux d'événements, processus sans état jetables. Chaque section ci-dessous est une application directe d'un de ces principes à l'écosystème Python contemporain (2024-2026).

Le packaging moderne : pyproject.toml et wheels

Le setup.py impératif appartient au passé. La source de vérité est pyproject.toml (PEP 621 pour les métadonnées, PEP 517/518 pour le build backend). Tu déclares quoi construire, l'outil décide comment.

Distinction capitale : les contraintes dans pyproject.toml décrivent ce qui est compatible ; le lockfile fige ce qui est réellement installé, transitivement, hash compris. Sans lock, deux builds à une semaine d'écart n'embarquent pas les mêmes versions — la non-reproductibilité commence là.

La wheel (.whl) est un artefact installable sans recompilation ; publie-la sur un index interne (devpi, Artifactory, registre privé) plutôt que de redéployer depuis les sources.

Note

Une app et une bibliothèque n'ont pas les mêmes règles : une app épingle tout via un lock ; une bibliothèque reste permissive sur ses bornes pour ne pas imposer de conflits à ses consommateurs, et ne committe pas son lock.

Configuration et secrets : l'environnement comme contrat

Principe III du 12-factor : la config vit dans l'environnement, jamais dans le code. pydantic-settings transforme les variables d'environnement en objet typé et validé au démarrage — un secret manquant fait échouer le boot, pas la 10 000e requête.

Le type SecretStr n'est pas cosmétique : il évite qu'un repr() d'objet ou un dump de config ne crache la clé dans un log. En production, les secrets viennent d'un coffre (Vault, AWS Secrets Manager, Kubernetes Secrets monté en variable), jamais du .env.

Observabilité : logs structurés, métriques, tracing

À l'échelle, un log texte print("user 42 ok") est illisible : tu ne peux ni filtrer, ni agréger, ni corréler. Le log doit être un événement JSON avec des champs exploitables par ton backend (Loki, ELK, Datadog).

Trois piliers complémentaires : les logs (événements), les métriques (séries temporelles agrégées : latence p99, taux d'erreur — Prometheus) et le tracing (le chemin d'une requête à travers les services — OpenTelemetry). La corrélation est l'élément clé : un même trace_id relie une ligne de log, un span de trace et le pic de latence d'une métrique.

Profilage en production : le sampling non intrusif

En prod, tu ne peux pas relancer le service sous cProfile : l'instrumentation ralentit tout et fausse les mesures. La bonne approche est le profileur par échantillonnage qui s'attache à un processus vivant et lit sa pile à intervalles réguliers, sans modifier le code ni le redémarrer.

py-spy lit la mémoire de l'interpréteur depuis l'extérieur ; aucun import, aucun redéploiement. Pyroscope industrialise ce sampling en continu sur toute la flotte.

Le réflexe : repère d'abord le goulot par les métriques (quel endpoint, quel p99), puis échantillonne le processus coupable pour localiser la fonction chaude. Profiler à l'aveugle toute l'application gaspille du temps.

Conteneurisation : minimal, multi-stage, non-root

Une image Python naïve fait facilement 1 Go et tourne en root — surface d'attaque et lenteur de déploiement. Le pattern multi-stage sépare la construction (compilateurs, outils) de l'exécution (juste le runtime), et un utilisateur non privilégié réduit l'impact d'une compromission.

Côté serveur d'application : WSGI (synchrone : gunicorn) ou ASGI (asynchrone : uvicorn, ou gunicorn pilotant des workers uvicorn). Règle de dimensionnement classique pour du CPU-bound synchrone : workers ≈ 2 × cœurs + 1 ; pour de l'I/O-bound async, peu de workers mais forte concurrence par worker.

Astuce

Mets PYTHONUNBUFFERED=1 : sinon stdout est tamponné et tes logs JSON arrivent en retard (ou jamais, si le conteneur est tué brutalement). Sans buffer, chaque ligne part immédiatement vers le collecteur.

Fiabilité : retries, health checks, arrêt propre

Un service distribué vit dans un réseau qui échoue. Deux mécanismes non négociables : le retry avec backoff exponentiel et jitter (pour absorber les pannes transitoires sans synchroniser des avalanches de tentatives) et l'arrêt propre (drainer les requêtes en cours avant de mourir).

Côté santé, distingue liveness (le process est-il vivant ? sinon, redémarrage) de readiness (peut-il recevoir du trafic ? sinon, retiré du load-balancer sans être tué). Un service qui charge un gros modèle ML est live mais pas ready pendant le chargement — les confondre coupe le trafic à tort.

Cas réel

Le déploiement du vendredi soir. Un service de facturation part en prod sans lockfile. Le jour J, une dépendance transitive publie une version mineure qui change une politique de retry : le build « identique » à celui de la veille ne l'est plus, et des timeouts se propagent. Pire, le rollback envoie un SIGKILL immédiat aux pods : les captures de paiement en vol sont coupées net, quelques transactions restent incohérentes. Deux corrections définitives : (1) uv sync --frozen sur un uv.lock committé rend le build reproductible au bit près ; (2) un handler SIGTERM qui draine 30 s laisse les requêtes en cours se terminer avant l'arrêt. Depuis, les déploiements sont devenus des non-événements.

L'écosystème et par où continuer

Selon le domaine, l'outillage de production diverge. Web : FastAPI (ASGI, validation pydantic native, idéal microservices) ou Django (batteries incluses, ORM mature). Data : pandas reste la référence, mais Polars (moteur Rust, exécution lazy, multi-thread sans GIL côté natif) le surclasse sur les gros volumes. ML : scikit-learn, PyTorch, et le serving via BentoML ou un endpoint FastAPI.

Pièges fréquents

Piège fréquent

Dépendances non épinglées. Sans lockfile, ton build n'est pas reproductible : une release transitive change le comportement entre deux déploiements identiques. Verrouille avec hashes et installe en --frozen.

Piège fréquent

Secrets dans le code ou l'image. Un secret COPYé dans une couche Docker y reste pour toujours, même supprimé ensuite (les couches sont immuables). Passe-les par l'environnement à l'exécution. Et n'utilise pas de logs texte non structurés : à l'échelle, ils sont illisibles et non corrélables.

Piège fréquent

Profileur intrusif en prod (ralentit, fausse) ; conteneur root et trop gros (surface d'attaque, déploiement lent) ; pas d'arrêt propre — un SIGKILL direct coupe les requêtes en vol et perd des données. Gère SIGTERM et draine.

Pour aller plus loin

Pour aller plus loin

uv (packaging et résolution ultra-rapides en Rust), OpenTelemetry (standard unifié logs/métriques/traces), py-spy et Pyroscope (profilage continu), Polars (dataframes performants), FastAPI en prod, les plateformes d'orchestration (Kubernetes) et Sentry (agrégation d'erreurs et release tracking). Lis le manifeste 12-factor en entier — chaque facteur a un corollaire opérationnel.

Antisèche : la checklist de mise en production

Glossaire

Wheel (.whl)
Artefact de distribution Python précompilé, installable sans recompilation ; produit par uv build (ou build) et publiable sur un index.
Lockfile
Fichier qui fige les versions exactes de tout l'arbre de dépendances, empreintes comprises : garantit des installations identiques dans le temps.
12-factor
Manifeste de bonnes pratiques pour applications exploitables : dépendances déclarées, configuration dans l'environnement, logs en flux, processus jetables.
SecretStr
Type pydantic qui masque une valeur sensible dans repr() et les logs ; la vraie valeur n'est lisible que via get_secret_value().
trace_id
Identifiant unique d'une requête propagé à travers les services ; il corrèle une ligne de log, un point de métrique et un span de trace.
Profileur par échantillonnage
Outil (ex. py-spy) qui lit la pile d'un processus vivant à intervalles réguliers, sans l'instrumenter ni le ralentir : exploitable en production.
WSGI / ASGI
Interfaces entre serveur et application Python : WSGI est synchrone (gunicorn), ASGI est asynchrone (uvicorn) et gère nativement async et les WebSockets.
Liveness / readiness
Sondes de santé : la liveness (vivant ?) déclenche un redémarrage ; la readiness (prêt ?) retire du load-balancer sans tuer.

Récap et vérification

  • Packaging : pyproject.toml (PEP 621 + backend PEP 517), wheels, et lockfile (uv/pip-tools/poetry) pour la reproductibilité.
  • Config : environnement typé via pydantic-settings, SecretStr, principes 12-factor — échec au boot, pas en prod.
  • Observabilité : logs JSON (structlog), métriques (Prometheus), tracing (OpenTelemetry), corrélés par trace_id.
  • Profilage : sampling non intrusif (py-spy) sur un PID vivant ; cibler via les métriques d'abord.
  • Conteneur : multi-stage, slim, utilisateur non-root ; servir via gunicorn/uvicorn (WSGI/ASGI), workers dimensionnés.
  • Fiabilité : timeouts + retries backoff/jitter, liveness vs readiness, arrêt propre sur SIGTERM.

  3. Pourquoi py-spy est-il préférable à cProfile pour diagnostiquer un service en production ?
