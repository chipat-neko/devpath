Module 14 · Au-delà de Python pur — Leçon 42

Interfacer Python avec le code natif

~30 min Avancé Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • savoir appeler une bibliothèque partagée avec ctypes en déclarant correctement argtypes et restype ;
  • savoir quand préférer Cython, l'API C de CPython ou pybind11 pour écrire une extension native ;
  • savoir reconnaître que la vectorisation NumPy est souvent la bonne réponse avant tout code C ;
  • savoir profiler avant d'optimiser et éviter les pièges de types qui corrompent la mémoire.
Sommaire de la leçon

Tu maîtrises maintenant le langage en profondeur : le data model, les générateurs, l'asyncio, le GIL, la métaprogrammation. Mais il reste une frontière. Pour le calcul intensif, CPython interprète chaque opération et le GIL sérialise les threads : une boucle numérique pure peut être cent à mille fois plus lente que son équivalent compilé. Quand le profilage désigne un point chaud incompressible, ou quand tu veux réutiliser une bibliothèque existante écrite en C, tu descends au natif.

Cette leçon parcourt l'éventail des options, de la plus légère (ctypes, sans compilation) à la plus engageante (extensions C/C++), sans oublier que la meilleure réponse est souvent de ne pas écrire de C du tout et de vectoriser avec NumPy. On finit toujours par le même refrain : mesure avant d'agir.

1. Pourquoi descendre au natif

CPython paie un coût à chaque opération : déréférencement d'objets, comptage de références, dispatch dynamique. Pour de l'I/O ou du code de coordination, ce coût est invisible. Pour une boucle qui additionne dix millions de flottants, il domine tout. Deux motivations légitimes : la performance sur un point chaud avéré, et la réutilisation d'une bibliothèque native éprouvée (FFTW, BLAS, un SDK matériel) plutôt que de la réécrire.

Note

Le natif ne contourne pas magiquement le GIL : il faut le libérer explicitement dans le code C (macro Py_BEGIN_ALLOW_THREADS, bloc nogil en Cython) pour que d'autres threads progressent en parallèle pendant un calcul lourd.

2. ctypes : appeler une bibliothèque partagée

ctypes charge une bibliothèque dynamique (.so sous Linux, .dll sous Windows, .dylib sous macOS) et appelle ses fonctions sans compilation. La règle d'or : déclarer argtypes et restype. Sans cela, ctypes suppose des int C, ce qui corrompt silencieusement les arguments 64 bits et les pointeurs.

Sans argtypes/restype, hypot(3.0, 4.0) renverrait une valeur fausse : les flottants seraient passés comme des entiers et le retour tronqué.

Pour échanger des données structurées, on décrit la disposition mémoire avec ctypes.Structure, dont l'attribut _fields_ reflète exactement le struct C côté natif.

byref évite de recopier la structure ; le natif écrit directement dans la mémoire Python.

3. CFFI : une alternative plus sûre

Écrire les signatures à la main avec ctypes est verbeux et fragile. CFFI (utilisé par cryptography, PyPy) prend l'approche inverse : tu lui donnes les déclarations C telles quelles, il génère le pont. En mode API, il compile un petit stub et vérifie les types via le vrai en-tête, ce qui élimine toute une classe d'erreurs de correspondance ABI.

La signature est lue depuis du C véritable : moins de risque de se tromper sur un type qu'en transcrivant à la main dans ctypes.

4. Cython : du Python annoté compilé en C

Quand le code chaud est écrit par toi (et non dans une lib externe), Cython est souvent le meilleur compromis. Tu pars de Python presque inchangé, tu ajoutes des annotations de type statique (cdef), et Cython traduit le tout en C compilé. Les boucles numériques perdent l'overhead d'objets Python et tournent à la vitesse du C.

Ici n, d, count sont des int C : la boucle interne devient une boucle C native. Le même code sans cdef resterait du Python interprété.

Astuce

Lance cython -a primes.pyx : le rapport HTML colore en jaune les lignes qui « touchent » encore Python. Plus c'est blanc, plus c'est rapide. C'est ton guide pour savoir où ajouter des cdef.

5. L'API C de CPython et pybind11

Au niveau le plus bas, on écrit une extension directement avec l'API C de CPython : chaque fonction Python devient une fonction C manipulant des PyObject*, avec gestion manuelle des références (Py_INCREF/Py_DECREF). C'est puissant mais verbeux et propice aux fuites mémoire.

Pour du C++, pybind11 change radicalement l'expérience : une bibliothèque d'en-têtes qui expose des fonctions et des classes C++ comme module Python en quelques lignes, en gérant les conversions de types et le comptage de références pour toi.

Le wrapper est la fine couche qui traduit les appels Python en appels natifs et reconvertit les valeurs de retour.

6. Vectoriser avec NumPy d'abord

Avant d'écrire la moindre ligne de C, demande-toi si NumPy ne fait pas déjà le travail. Une opération vectorisée délègue la boucle à du C optimisé (souvent avec SIMD et appels BLAS), sans que tu quittes Python. Le gain est énorme et le code reste lisible.

np.dot(xs, xs) évite le tableau intermédiaire de np.sum(xs * xs) et appelle directement BLAS. La version NumPy est typiquement deux ordres de grandeur plus rapide que la boucle pure, pour zéro ligne de C à maintenir.

Note

Si NumPy ne couvre pas ton algorithme mais qu'il opère sur des tableaux, regarde Numba : un décorateur @njit compile ta fonction Python en code machine à la volée, sans changer de langage ni de fichier.

Cas réel

Les bibliothèques scientifiques que tu utilises tous les jours sont exactement cette leçon en action. NumPy est un cœur C ; pandas est écrit en bonne partie en Cython ; la lib cryptography s'appuie sur CFFI pour lier OpenSSL ; scikit-learn mêle Cython et C ; PyTorch expose des noyaux C++/CUDA via pybind11 et l'API C. À chaque fois, le même motif : une fine couche Python agréable à écrire, posée sur un noyau natif pour la performance. Quand tu tapes import numpy, tu franchis déjà la frontière décrite ici.

7. Profiler d'abord, toujours

L'erreur capitale est d'optimiser à l'aveugle. Avant de sortir l'artillerie native, mesure : cProfile pour localiser le point chaud à la fonction près, timeit pour comparer deux implémentations. Souvent, 90 % du temps tient dans 3 % du code — et parfois ce point chaud disparaît avec un meilleur algorithme, sans aucun natif.

On ne descend au natif qu'après avoir prouvé, chiffres en main, où se trouve le coût réel.

Pièges fréquents

Piège fréquent

Optimiser sans profiler. Tu peux passer des jours à réécrire en C une fonction qui pèse 2 % du temps total. Mesure d'abord, sinon tu optimises ton intuition, pas ton programme.

Piège fréquent

De mauvais types ctypes. Oublier argtypes/restype, confondre c_int et c_long, passer un objet là où un pointeur est attendu : pas d'exception propre, mais une corruption mémoire ou un segfault. Le natif ne te protège pas comme l'interpréteur.

Piège fréquent

Réécrire ce que NumPy fait déjà. Un produit scalaire maison en C sera presque toujours battu par np.dot, qui appelle BLAS. Et sous-estimer le surcoût d'appel : franchir la frontière Python ↔ natif a un coût fixe ; appeler une fonction C un million de fois dans une boucle Python peut être plus lent que de tout faire en Python.

Pour aller plus loin

Pour aller plus loin

Explore PyO3 et maturin pour écrire des extensions en Rust (sûreté mémoire + performance), Numba pour la compilation JIT sans quitter Python, la libération du GIL dans le code natif pour le vrai parallélisme, et le packaging de wheels binaires (cibuildwheel, manylinux) pour distribuer tes extensions sans imposer un compilateur à tes utilisateurs.

Antisèche : quelle porte vers le natif ?

Glossaire

FFI
Foreign Function Interface : mécanisme permettant à un langage d'appeler du code écrit dans un autre (ici, du natif depuis Python).
ctypes
Module standard qui charge une bibliothèque partagée et appelle ses fonctions sans compilation ; exige argtypes et restype.
CFFI
Pont vers le C piloté par les déclarations C réelles (ffi.cdef), plus sûr que la transcription manuelle de ctypes.
Cython
Sur-ensemble de Python annoté de types C (cdef) et compilé en C : supprime l'overhead de l'interpréteur sur les boucles serrées.
Extension native
Module compilé (C/C++/Rust) chargé par CPython comme n'importe quel module Python, exposé via l'API C ou pybind11.
Wrapper
Fine couche qui traduit un appel Python en appel natif et reconvertit la valeur de retour.
Vectorisation
Remplacer une boucle Python par une opération sur tableaux entiers (NumPy), déléguée à du C optimisé (SIMD, BLAS).
Surcoût d'appel
Coût fixe de chaque traversée de la frontière Python↔natif (conversions, marshalling) ; ruineux s'il est payé par élément.

Récap et vérification

  • ctypes : appelle une lib partagée sans compiler ; déclare toujours argtypes et restype.
  • CFFI : alternative plus sûre, pilotée par les déclarations C réelles.
  • Cython : Python annoté (cdef) compilé en C, idéal pour tes propres boucles numériques.
  • API C / pybind11 : extensions natives ; pybind11 expose du C++ avec un wrapper concis.
  • NumPy : vectorise d'abord ; la boucle part en C optimisé sans écrire de C.
  • Profiler : cProfile/timeit avant toute optimisation.

Vérifie ta compréhension

  1. Pourquoi argtypes et restype sont-ils indispensables avec ctypes, et que se passe-t-il si on les omet ?
  2. Qu'est-ce que Cython accélère concrètement par rapport à du Python pur, et grâce à quel mécanisme ?
  3. Pourquoi essayer de vectoriser avec NumPy avant d'écrire du C, et dans quel cas le surcoût d'appel inter-langages peut-il annuler le gain ?
