Module 07 · Python en pratique — Leçon 20

Qualité, tests et distribution

~34 min Intermédiaire Leçon 19 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire et lancer des tests pytest (assert, fixtures, parametrize) et mesurer la couverture ;
  • savoir vérifier le typage avec mypy et imposer la qualité avec ruff (format + lint) et pre-commit ;
  • savoir structurer un projet (src/, pyproject.toml) et le distribuer (build, install éditable, PyPI) ;
  • savoir documenter (docstrings, README) et automatiser tests et lint en CI.
Sommaire de la leçon

Tu sais écrire du Python. Maintenant, la question change : comment rendre un projet fiable, lisible par d'autres (et par toi dans six mois), et partageable ? Cette leçon couvre l'outillage qui transforme un script qui « marche sur ma machine » en un vrai projet : tests, vérification de types, formatage automatique, structure de dossiers, et publication.

Aucun de ces outils n'est dans la bibliothèque standard, mais tous sont quasi universels dans l'écosystème. Tu vas voir comment ils s'enchaînent autour d'un seul fichier de configuration central, pyproject.toml. On reste sur l'usage pratique : pas de théorie, juste les commandes et les fichiers que tu écriras réellement.

Tester avec pytest

Tester, c'est écrire du code qui vérifie ton code. L'intérêt : quand tu modifies une fonction six mois plus tard, les tests t'alertent immédiatement si tu as cassé quelque chose. Avec pytest, un test est une simple fonction dont le nom commence par test_, qui utilise le mot-clé assert.

Par convention, tes tests vivent dans des fichiers test_*.py (souvent dans un dossier tests/). pytest les découvre tout seul.

Tu lances la suite avec une commande. pytest affiche un point par test réussi.

Pas besoin de print : pytest réécrit les assert pour te montrer la valeur attendue contre la valeur obtenue en cas d'échec.

Fixtures et paramétrage

Deux outils rendent les tests propres. Une fixture prépare un objet réutilisable (une connexion, des données, un fichier temporaire) et l'injecte dans tes tests via leur signature. Le paramétrage rejoue le même test sur plusieurs jeux de données sans dupliquer le code.

Pour savoir quelle proportion de ton code est réellement exercée par les tests, mesure la couverture avec pytest-cov.

Une couverture élevée ne garantit pas l'absence de bug, mais une couverture faible révèle des zones jamais testées.

Vérifier le typage avec mypy

Tu connais déjà les annotations de types (prix: float, -> float). À l'exécution, Python les ignore. Un vérificateur de types comme mypy (ou pyright) les lit sans lancer ton programme et signale les incohérences : c'est un filet qui attrape une classe entière de bugs avant même de tester.

Une str est itérable, donc le code aurait tourné (en comptant les lettres une à une) sans planter mais en donnant un résultat faux. mypy l'attrape sans exécution.

Astuce

Commence avec un typage léger sur les fonctions publiques, puis durcis progressivement (option --strict). Annoter d'abord les frontières (entrées/sorties) donne déjà l'essentiel de la valeur.

Formater et linter avec ruff

Le formatage impose une mise en forme cohérente (espaces, longueur de ligne, guillemets) de façon automatique : tu ne discutes plus du style, l'outil tranche. Le linting repère les problèmes — imports inutilisés, variables non utilisées, erreurs probables. ruff fait les deux, très vite, et remplace à lui seul black, flake8 et isort.

Pour que ces vérifications tournent avant chaque commit et bloquent un commit non conforme, on utilise pre-commit : un fichier .pre-commit-config.yaml déclare les outils à lancer automatiquement par Git.

Note

Formateur et linter sont complémentaires : le premier touche à l'apparence (sans changer le sens), le second à la qualité et aux bugs potentiels. ruff réunit les deux casquettes, mais ce sont bien deux rôles distincts.

Structurer le projet

Un script unique devient vite ingérable. Le layout recommandé place ton code dans un sous-dossier src/, ce qui évite des imports trompeurs et force à installer le paquet pour le tester (comme le feront tes utilisateurs).

Le fichier __init__.py transforme un dossier en paquet. À l'intérieur, préfère les imports absolus (depuis la racine du paquet), plus lisibles et robustes que les imports relatifs.

Le pyproject.toml

C'est le fichier central, défini par un standard (PEP 621). Il décrit ton paquet (nom, version, dépendances) et configure tes outils, le tout au format TOML. Un seul endroit à connaître.

Métadonnées sous [project], configuration des outils sous [tool.xxx] : tout cohabite dans un seul fichier.

Construire et distribuer

Pendant le développement, installe ton projet en mode éditable : Python pointe vers tes fichiers source, donc tes modifications sont prises en compte sans réinstaller.

Pour partager, tu construis les artefacts de distribution (une archive et un fichier .whl) avec l'outil build, puis tu les téléverses sur PyPI (l'index public des paquets) avec twine.

Entraîne-toi d'abord sur TestPyPI, une copie de PyPI prévue pour les essais, avant la publication réelle.

Piège fréquent

Une publication sur PyPI est définitive : un numéro de version ne peut pas être remplacé. Et surtout, ne mets jamais de clé d'API ni de mot de passe dans ton code ou ton dépôt — un secret poussé est un secret compromis.

Documenter et automatiser (CI)

La documentation commence par les docstrings (déjà vues) et un README qui explique en quelques lignes ce que fait le projet et comment l'installer. C'est la première chose que lit un nouvel arrivant.

L'intégration continue (CI) lance automatiquement tes tests et ton linter à chaque push, sur un serveur. Avec GitHub Actions, tu décris cela dans un fichier YAML sous .github/workflows/.

À chaque modification poussée, GitHub rejoue lint + typage + tests : un échec est visible avant de fusionner.

Cas réel

Un projet open-source reçoit chaque semaine des contributions de développeurs que le mainteneur ne connaît pas (pull requests). Impossible de tout revérifier à la main. La CI (GitHub Actions) rejoue automatiquement ruff, mypy et pytest sur chaque proposition : le mainteneur voit une pastille verte ✓ ou rouge ✗ sans rien installer, et une contribution qui casse un test ne peut pas être fusionnée. C'est ce filet automatique qui permet à des milliers d'inconnus de collaborer sur un même paquet (requests, Django…) sans que la qualité s'effondre.

Pièges fréquents

  • Ne pas écrire de tests. Sans tests, chaque modification est un pari. Même trois tests valent mieux que zéro.
  • Ignorer mypy et le linter. Désactiver les avertissements « pour que ça passe » revient à éteindre l'alarme incendie : les bugs restent.
  • Structure incohérente. Mélanger imports relatifs et absolus au hasard, oublier un __init__.py : les imports cassent dès que tu déplaces un fichier.
  • Tout mettre dans un seul fichier. Un module de 2000 lignes est impossible à tester et à relire. Découpe par responsabilité.
  • Publier des secrets. Clés d'API, mots de passe : jamais dans le dépôt. Utilise des variables d'environnement et un fichier ignoré par Git.
  • Oublier le pyproject.toml. Sans lui, pas d'installation propre, pas de dépendances déclarées, pas de configuration d'outils centralisée.

Pour aller plus loin

Pour aller plus loin

tox et nox rejouent ta suite sur plusieurs versions de Python (matrices de tests). GitHub Actions mérite d'être creusé, notamment pour suivre la couverture en CI. Côté domaines : FastAPI et Django pour le web, ruff a une configuration très riche à explorer, et Sphinx ou MkDocs génèrent une documentation complète à partir de tes docstrings. Pour la suite : web (Django/FastAPI), data (pandas, scikit-learn) ou automatisation de tâches.

Glossaire

pytest
Cadre de test le plus répandu : des fonctions test_* avec de simples assert, découvertes et exécutées automatiquement.
Fixture
Objet préparé à l'avance et injecté dans un test via sa signature (données, connexion, fichier temporaire) ; recréé selon sa portée.
Paramétrage (parametrize)
Rejoue un même test sur plusieurs jeux de données ; chaque cas devient un test distinct, sans dupliquer le corps de la fonction.
Typage statique
Vérification de la cohérence des annotations de types sans exécuter le programme, par un outil comme mypy ou pyright.
Linter / formateur
Le linter repère erreurs et mauvaises pratiques ; le formateur impose un style uniforme. ruff remplit les deux rôles.
pyproject.toml
Fichier central normalisé (PEP 621) : métadonnées du paquet, dépendances et configuration des outils, au format TOML.
Wheel / PyPI
Une wheel (.whl) est un paquet prêt à installer, produit par build ; PyPI est l'index public où twine le publie et pip le télécharge.
Intégration continue (CI)
Serveur qui rejoue tests, lint et typage à chaque push (ex. GitHub Actions) ; un échec est signalé avant toute fusion.

Récap et vérification

  • pytest : fonctions test_*, assert, fixtures, parametrize, couverture via pytest-cov.
  • mypy/pyright : vérifient les annotations de types sans exécuter le code.
  • ruff : formate et linte ; pre-commit l'applique avant chaque commit.
  • Layout src/ + __init__.py + imports absolus pour une structure saine.
  • pyproject.toml centralise métadonnées, dépendances et config des outils.
  • pip install -e . en dev ; build + twine pour distribuer (TestPyPI d'abord).
  • README, docstrings et CI (GitHub Actions) finissent de fiabiliser le projet.

Vérifie ta compréhension

  1. Quel nom doivent porter un fichier et une fonction de test pour que pytest les découvre automatiquement ?
  2. Quelle différence concrète entre ce que vérifie mypy et ce que vérifie ruff ?
  3. Pourquoi installer ton projet avec pip install -e . plutôt que pip install . pendant le développement ?
