Journalisation avec le module logging

~34 min Intermédiaire Leçon 17 en écho

À la fin de cette leçon, tu sauras

  • choisir le bon niveau de log (DEBUG → CRITICAL) et régler un seuil ;
  • distinguer les trois briques logger / handler / formatter et leur rôle ;
  • comprendre la hiérarchie des loggers par nom et la propagation ;
  • configurer proprement plusieurs sorties avec dictConfig et un handler rotatif ;
  • appliquer les bonnes pratiques : getLogger(__name__), formatage paresseux, exc_info.
Sommaire de la leçon

Un print() de débogage a trois défauts : il ne dit ni quand, ni d'où, ni à quel point c'est grave ; on ne peut pas le filtrer ; et il faut le retirer avant la mise en production. Le module logging de la bibliothèque standard résout les trois. C'est la fondation sur laquelle s'appuient les outils modernes vus en leçon 17 (structlog produit des logs JSON, mais par-dessus ce socle). Le maîtriser, c'est comprendre ce qui se passe réellement sous le capot.

Les niveaux : un seuil de gravité

Chaque message porte un niveau de gravité. Le logger n'émet que les messages dont le niveau atteint ou dépasse son seuil : régler le seuil sur WARNING fait taire tout le bruit DEBUG et INFO sans toucher une ligne de code. C'est le grand avantage sur print : on ajuste la verbosité depuis la configuration.

Astuce

Repère mental : DEBUG = détail utile en développement ; INFO = étape normale attendue ; WARNING = anormal mais géré ; ERROR = une opération a échoué ; CRITICAL = le programme ne peut plus continuer. En production, on tourne souvent à INFO, et l'on bascule à DEBUG le temps d'un incident.

L'architecture : logger, handler, formatter

basicConfig est pratique pour un script, mais dès qu'une vraie application grandit, il faut connaître les trois briques. Le logger est le point d'entrée (tu appelles log.info(...)) ; il crée un enregistrement et le passe à un ou plusieurs handlers qui décident de la destination (console, fichier, réseau) ; chaque handler s'appuie sur un formatter qui décide de la mise en forme de la ligne finale.

Hiérarchie et propagation

Les loggers forment un arbre fondé sur leur nom, séparé par des points : monapp est le parent de monapp.db, lui-même parent de monapp.db.pool. Au sommet trône le logger racine. Un enregistrement émis par un logger « remonte » vers ses ancêtres (c'est la propagation) : chaque ancêtre applique ses handlers. D'où la convention universelle : logging.getLogger(__name__) dans chaque module, et la configuration des handlers une seule fois, tout en haut.

Configurer proprement : dictConfig

Câbler les handlers à la main devient vite verbeux. La méthode recommandée est déclarative : décrire toute la configuration dans un dictionnaire (souvent chargé d'un fichier YAML/JSON) et l'appliquer d'un coup avec logging.config.dictConfig. On y branche typiquement deux sorties : la console pour l'humain, un fichier rotatif pour l'archive (qui limite la taille et garde N fichiers de sauvegarde).

Piège fréquent

Appeler plusieurs fois addHandler (ou basicConfig) sur le même logger duplique les lignes : chaque log s'affiche deux, trois fois. Configure les handlers une seule fois, au démarrage, sur le logger racine — jamais dans une fonction appelée en boucle.

Bonnes pratiques

Trois réflexes distinguent un logging amateur d'un logging professionnel.

1. Formatage paresseux. Passe les valeurs en arguments, pas en f-string : log.info("user %s", uid). Si le niveau est filtré, l'interpolation n'a jamais lieu — économie réelle sur les logs DEBUG volumineux.

2. Trace d'exception. Dans un except, utilise log.exception("...") (ou exc_info=True) : la stack trace complète est jointe automatiquement.

3. Bibliothèques discrètes. Une bibliothèque ne configure jamais le logging global ; elle ajoute un NullHandler et laisse l'application décider.

Cas réel

L'incident qu'on a résolu grâce aux niveaux. Un service de paiement renvoie par intermittence des erreurs 500, impossibles à reproduire en local. Comme chaque module utilise getLogger(__name__) et que la racine est configurée une fois, il suffit de basculer le seuil du logger paiement.gateway de INFO à DEBUG via la config — sans redéployer — pour capturer, le temps d'un pic, la requête brute envoyée au prestataire. Les logs (avec exception() et sa stack trace) révèlent un délai d'expiration côté partenaire mal géré. On remet ensuite le seuil à INFO. Sans cette hiérarchie de loggers, il aurait fallu inonder toute l'application de DEBUG : illisible et coûteux.

Glossaire

Niveau de log
Gravité d'un message (DEBUG, INFO, WARNING, ERROR, CRITICAL) ; le logger n'émet que ceux qui atteignent son seuil.
Logger
Point d'entrée nommé de la journalisation ; on l'obtient par getLogger(nom) et les loggers forment un arbre selon leur nom.
Handler
Composant qui envoie les enregistrements vers une destination (console, fichier, réseau) ; un logger peut en avoir plusieurs.
Formatter
Objet qui transforme un enregistrement en ligne de texte selon un gabarit (%(asctime)s, %(levelname)s…).
Propagation
Mécanisme par lequel un enregistrement remonte du logger émetteur vers ses ancêtres, chacun appliquant ses handlers.
dictConfig
Configuration déclarative du logging via un dictionnaire (formatters, handlers, loggers) appliquée en un appel.
Handler rotatif
Handler fichier (RotatingFileHandler) qui limite la taille d'un journal et conserve un nombre fixe de sauvegardes.

Récap et vérification

  • Niveaux : DEBUG → CRITICAL ; un seuil réglable filtre le bruit sans modifier le code.
  • Trio : le logger émet, le handler choisit la destination, le formatter met en forme.
  • Hiérarchie : loggers en arbre par nom (getLogger(__name__)) ; la propagation remonte vers la racine, configurée une seule fois.
  • dictConfig : configuration déclarative ; console + fichier rotatif est le duo classique.
  • Bonnes pratiques : formatage paresseux (%s), log.exception() dans un except, NullHandler dans les bibliothèques.

Vérifie ta compréhension

  1. Quel avantage concret le seuil de niveau offre-t-il par rapport à des print qu'il faut retirer ?
  2. Décris le rôle respectif du logger, du handler et du formatter dans le trajet d'un message.
  3. Pourquoi log.info("x=%s", x) est-il préférable à log.info(f"x={x}") ?
