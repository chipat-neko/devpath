Module 15 · Python à l'échelle — Leçon 43

Patterns et architecture pythonique

~35 min Avancé Cours Python avancé recommandé

À la fin de cette leçon, tu sauras

  • savoir choisir entre abc.ABC et typing.Protocol selon le besoin de duck typing structurel typé ;
  • savoir transposer les design patterns en versions pythoniques (fonctions de première classe, modules) plutôt qu'en calques Java ;
  • savoir inverser les dépendances par injection et exposer un système de plugins via entry points ;
  • savoir arbitrer entre composition, héritage et mixins en appliquant les principes SOLID à un gros projet.
Sommaire de la leçon

Tu connais le data model, les descripteurs, le MRO et le typage statique. Cette leçon ne te réapprend pas class : elle traite de la question qui se pose quand le code dépasse les 50 000 lignes et plusieurs équipes — comment découper pour que le système reste testable, extensible et compréhensible. Python n'est pas Java : la majorité des patterns du Gang of Four existent pour contourner l'absence de fonctions de première classe et de modules de premier ordre. En Python, ils fondent souvent à une fonction ou un import.

On va donc raisonner en termes d'abstractions (Protocol vs ABC), de couplage (injection de dépendances), d'extension (plugins), et de composition, le tout passé au filtre de SOLID — mais d'une version pythonique, pas dogmatique.

ABC contre Protocol : l'abstraction par défaut

Une abc.ABC impose un héritage nominal : la sous-classe doit déclarer explicitement le parent. Un typing.Protocol définit un contrat structurel : tout objet qui a les bonnes méthodes le satisfait, sans déclaration. Pour des frontières de typage, le Protocol est presque toujours supérieur — il découple le fournisseur du consommateur et formalise le duck typing que mypy vérifie statiquement.

Le Protocol décrit ce que le consommateur attend, pas ce que le fournisseur est.

Note

Garde l'ABC quand tu veux fournir du comportement partagé (méthodes concrètes, __init_subclass__, validation à la définition) ou forcer un opt-in explicite. Le Protocol sert à typer une frontière, pas à factoriser du code. Attention : @runtime_checkable ne vérifie que la présence des méthodes au runtime, jamais leur signature.

Design patterns pythoniques : la fonction d'abord

Le pattern Stratégie classique encapsule un algorithme dans une hiérarchie de classes à méthode unique. En Python, une stratégie est juste un Callable. Inutile d'instancier ConcreteStrategyA() : passe la fonction.

Stratégie + Fabrique tiennent dans un alias de type et un dictionnaire.

De même : le Singleton est presque toujours une mauvaise idée — un module Python est déjà un singleton mis en cache par sys.modules. Mets ton état partagé dans une fonction @lru_cache ou un objet créé une fois au démarrage et injecté. L'Adaptateur reste utile (envelopper une API tierce derrière un Protocol maison), et l'Observateur se réduit souvent à une liste de callbacks.

Inversion de dépendances et injection

Le D de SOLID : les modules de haut niveau ne dépendent pas des détails, mais d'abstractions. Concrètement, ne construis pas tes dépendances dans la classe — reçois-les. Une fonction qui fait requests.get(...) en dur est intestable ; la même avec un client injecté se teste avec un faux.

L'injection manuelle par le constructeur suffit à 95 % des cas.

Astuce

Avant d'adopter un conteneur DI comme dependency-injector, demande-toi si une simple fonction build_app() qui câble tout au démarrage (le composition root) ne suffit pas. Les conteneurs brillent surtout quand le graphe de dépendances devient profond et que tu veux des scopes (requête, singleton).

Systèmes de plugins par entry points

Pour qu'un code tiers étende ton application sans que tu l'importes, utilise les entry points de importlib.metadata. Chaque paquet installé déclare ses extensions dans ses métadonnées ; ton hôte les découvre à l'exécution. C'est le mécanisme derrière les plugins pytest ou les backends de fsspec.

L'hôte ne connaît pas les plugins à la compilation ; il les charge par groupe nommé.

Note

Le paramètre group= d'entry_points() n'existe que depuis Python 3.10. Sous 3.9, l'appel renvoie un dict et l'on écrit entry_points()["myapp.codecs"] ; importlib_metadata (le backport) uniformise l'API.

Cas réel

Les plugins de pytest. Quand tu fais pip install pytest-cov, tu n'ajoutes aucune ligne de configuration : pytest découvre le plugin via l'entry point du groupe pytest11 déclaré par le paquet, puis l'active à l'exécution. C'est exactement ce mécanisme — l'hôte ignore ses plugins à l'écriture et les charge par groupe nommé. SQLAlchemy (dialectes de bases), fsspec (systèmes de fichiers) et Airflow (providers) reposent tous sur la même mécanique.

Composition contre héritage, et le piège des mixins

L'héritage modélise « est-un » ; il crée le couplage le plus fort du langage (la sous-classe dépend des internes du parent). Préfère la composition (« a-un ») dès que la relation n'est pas une vraie spécialisation. Les mixins sont un compromis : des fragments de comportement injectés via le MRO — puissants, mais source de conflits si deux mixins définissent la même méthode ou attendent des attributs implicites.

Le mixin économise du code au prix d'un contrat implicite ; la composition rend la dépendance explicite et testable.

Organiser un gros projet : couches et hexagone

Découpe par responsabilité, pas par type technique. Évite le fourre-tout utils.py et les dossiers models/, views/, services/ qui forcent à toucher trois répertoires par fonctionnalité. L'architecture hexagonale (ports/adaptateurs) place le domaine au centre, isolé du monde extérieur par des Protocols (les ports) ; les détails (DB, HTTP, files) sont des adaptateurs branchés depuis l'extérieur.

Les flèches de dépendance pointent vers le domaine ; jamais l'inverse.

Le domaine définit ports.py (les Protocols), l'application en dépend, et composition.py injecte les adaptateurs concrets. Résultat : tu testes les cas d'usage avec des faux ports, sans base de données ni réseau, et tu remplaces Stripe par PayPal en écrivant un seul adaptateur.

SOLID, version pythonique

SOLID n'est pas un dogme à appliquer à chaque classe. En Python : SRP — un module cohérent autour d'une raison de changer ; OCP — l'extension passe par injection/plugins, pas par modification ; LSP — un sous-type doit respecter le contrat du Protocol ; ISP — des Protocols petits et ciblés plutôt qu'une interface obèse ; DIP — dépendre de Protocols, câbler au composition root. La plupart de ces principes se réduisent, en Python, à « expose des fonctions et des Protocols, injecte les dépendances ».

Pièges fréquents

Piège fréquent

Transposer les patterns Java. Une AbstractStrategyFactoryBuilder en Python est un anti-pattern : tu réimplémentes à la main des fonctions de première classe. Avant d'écrire une classe à méthode unique, demande-toi si une fonction ou un dict ne suffit pas.

Piège fréquent

Singleton mutable global. Un objet d'état partagé modifiable casse l'isolation des tests (état qui fuit entre cas) et la concurrence. Si tu dois mémoïser, utilise @lru_cache avec cache_clear() pour les tests, et préfère injecter l'instance plutôt que d'y accéder via une variable globale.

Piège fréquent

Mixins en conflit de MRO. Deux mixins qui définissent save() ou oublient d'appeler super().__init__(**kwargs) coopérativement provoquent des résolutions silencieusement fausses. Vérifie Cls.__mro__ et exige que chaque mixin appelle super() ; au moindre doute, compose plutôt qu'hérite.

Pour aller plus loin

Pour aller plus loin

Explore dependency-injector pour les graphes complexes avec scopes ; l'architecture hexagonale/clean et le DDD (agrégats, bounded contexts) pour le découpage métier ; attrs et pydantic pour des modèles validés sans boilerplate ; et le mécanisme des entry points (vu chez pytest, Airflow, fsspec) pour bâtir un écosystème de plugins ouvert.

Antisèche : le pattern GoF et son idiome Python

Glossaire

Protocol
Contrat structurel (typing) : toute classe possédant les bonnes méthodes le satisfait, sans héritage ; vérifié statiquement par mypy.
ABC
Classe de base abstraite : couplage nominal (héritage déclaré), peut fournir du code partagé et forcer l'implémentation via @abstractmethod.
Duck typing structurel
« Si l'objet a les méthodes attendues, c'est le bon type » : principe des Protocols, ici rendu vérifiable statiquement.
Injection de dépendances
Fournir à un objet ses collaborateurs depuis l'extérieur (par le constructeur) au lieu qu'il les instancie lui-même ; c'est le D de SOLID.
Composition root
Point unique, au démarrage, où l'on câble les implémentations concrètes sur les abstractions (build_app()).
Entry point
Extension déclarée dans les métadonnées d'un paquet et découverte à l'exécution par groupe nommé (importlib.metadata).
Architecture hexagonale
Le domaine au centre, isolé par des ports (Protocols) ; les détails (DB, HTTP) sont des adaptateurs branchés de l'extérieur.
Mixin
Petite classe qui injecte un comportement via l'héritage et le MRO ; pratique, mais porteuse de contrats implicites et de conflits.

Récap et vérification

  • Protocol pour typer une frontière (duck typing structurel) ; ABC pour partager du comportement ou forcer l'opt-in.
  • Les patterns GoF fondent souvent en une fonction, un dict ou un module ; ne calque pas Java.
  • Injecte les dépendances par le constructeur ; câble-les au composition root, conteneur DI seulement si le graphe l'exige.
  • Étends par entry points ; le domaine reste isolé derrière des ports (hexagonal).
  • Préfère la composition ; les mixins introduisent des contrats implicites et des conflits de MRO.
  • SOLID en Python se ramène à : fonctions + Protocols + injection.
