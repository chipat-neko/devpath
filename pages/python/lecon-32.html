Le typage statique (typing & mypy)

~35 min Avancé Module 1 recommandé

À la fin de cette leçon, tu sauras

  • annoter paramètres et retour (->) avec les conteneurs intégrés list[int], dict[str, int], tuple[int, ...] ;
  • manier X | None, l'union X | Y, Final, Literal et distinguer Any de object ;
  • écrire du code générique avec TypeVar/Generic[T] et définir un Protocol pour un typage structurel ;
  • utiliser TypedDict, NewType, cast, Self et lancer mypy pour détecter les erreurs avant l'exécution.
Sommaire de la leçon

Python reste un langage dynamiquement typé : à l'exécution, c'est toujours le duck typing qui décide. Mais depuis la PEP 484, tu peux annoter ton code avec des types. Ces annotations ne changent rien au runtime — elles servent un outil externe (mypy, pyright) qui analyse ton code avant de le lancer et te signale les incohérences. Tu gagnes la sécurité d'un langage typé sans renoncer à la souplesse de Python.

Cette leçon couvre le typage moderne (idiomes 3.10 à 3.12) : annotations de base, unions X | Y, génériques avec TypeVar, protocoles structurels, TypedDict, et le lancement de mypy. On montre systématiquement l'erreur que mypy signalerait en commentaire.

Pourquoi annoter ? Un outil, pas un runtime

Trois bénéfices concrets : la lisibilité (la signature documente le contrat), le refactoring sûr (renommer ou changer un type propage les erreurs là où il faut), et la détection statique de bugs avant exécution. Point crucial : les annotations ne sont pas vérifiées à l'exécution. Python les stocke, mais ne les contrôle jamais tout seul.

Le typage est un filet posé par un outil d'analyse, pas par l'interpréteur.

Note

Les annotations sont accessibles via fonction.__annotations__ ou typing.get_type_hints(). Des bibliothèques comme pydantic les exploitent pour valider à l'exécution, mais c'est leur choix, pas celui de Python.

Les bases modernes : paramètres, retour, conteneurs

On annote chaque paramètre avec nom: type et le retour avec -> type après la parenthèse. Pour les conteneurs, utilise les génériques intégrés (depuis 3.9) : list[int], dict[str, int], tuple[int, ...] pour un tuple homogène de longueur variable, tuple[str, int] pour un couple précis.

Une fonction sans return de valeur renvoie None : annote-la -> None. C'est explicite et mypy vérifiera qu'aucune valeur ne s'échappe par erreur.

Optional, union X | Y, Any, alias, Final, Literal

Quand une valeur peut être None, dis-le. La forme moderne (3.10+) est l'union avec la barre : int | None, équivalente à l'ancien Optional[int]. L'union X | Y exprime « l'un ou l'autre ».

Quelques outils complémentaires :

Distingue Any et object. Any est une trappe d'évasion : mypy ne vérifie plus rien dessus. object est le sommet de la hiérarchie : tout y rentre, mais pour l'utiliser concrètement tu dois d'abord prouver son type (via isinstance). Préfère object quand tu veux rester vérifié.

Les génériques : TypeVar, Generic, types abstraits

Une fonction générique travaille avec « un type quelconque, mais le même partout ». On le capture avec un TypeVar. Le lien entre entrée et sortie est ainsi préservé.

Pour les paramètres, vise large : accepte un Iterable, une Sequence ou un Mapping abstrait plutôt qu'un list ou dict concret. Ton code accepte ainsi plus de types d'entrée. Callable type les fonctions passées en argument.

Astuce

Importe Iterable, Sequence, Mapping, Callable depuis collections.abc, pas depuis typing (ces derniers sont dépréciés). Règle générale : accepte large (types abstraits en entrée), renvoie précis (type concret en sortie).

Les protocoles : le typage structurel

Un Protocol décrit un contrat par la forme : « tout objet qui possède telles méthodes convient », sans héritage explicite. C'est le duck typing rendu vérifiable statiquement. Aucune classe n'a besoin de déclarer qu'elle implémente le protocole.

Le protocole découple le contrat de l'implémentation : tu peux typer une dépendance sans imposer de classe de base commune. Annote le protocole avec @runtime_checkable si tu veux aussi l'utiliser dans un isinstance (vérification limitée à la présence des attributs).

TypedDict, NewType, cast, Self, et mypy en ligne de commande

TypedDict type un dictionnaire dont les clés et types de valeurs sont fixés — idéal pour du JSON structuré. NewType crée un type distinct sans coût runtime (pour ne pas mélanger deux int qui n'ont pas le même sens). cast force mypy à accepter un type quand toi seul connais la vérité. Self (3.11) type le retour d'une méthode comme « le type courant ».

Pièges fréquents

  • Croire que les annotations sont vérifiées à l'exécution. Elles ne le sont pas. Sans mypy (ou pyright), double("ab") tourne. Le contrôle vient de l'outil, pas de l'interpréteur.
  • Abuser de Any. Chaque Any est un trou dans le filet : mypy cesse de vérifier ce qui en découle. Préfère object, un Protocol ou un TypeVar.
  • Oublier | None alors que None est possible. Un dict.get(), un paramètre optionnel… renvoient souvent None. Annote-le, et fais le test is not None pour rétrécir le type.
  • Importer List, Dict, Tuple de typing. Obsolète depuis 3.9. Écris list[int], dict[str, int], tuple[int, ...] avec les types intégrés.

Piège fréquent

Une annotation fausse passe inaperçue sans vérificateur. Annoter du code sans jamais lancer mypy, c'est écrire une documentation jolie mais potentiellement mensongère. Intègre mypy à ton flux dès le départ.

Cas réel

Le typage statique a quitté les laboratoires. mypy est né chez Dropbox pour fiabiliser des millions de lignes ; Instagram a créé pyre pour la même raison. FastAPI et pydantic lisent tes annotations pour valider les requêtes entrantes et générer automatiquement la documentation OpenAPI : le type age: int devient à la fois une contrainte de validation et un schéma d'API. Au quotidien, l'autocomplétion et le soulignement rouge de VS Code (Pylance) ou PyCharm reposent sur ces mêmes types, et la bibliothèque standard est livrée avec des stubs typés (projet typeshed). Annoter, c'est donc à la fois documenter, sécuriser et outiller son code.

Pour aller plus loin

pydantic exploite les annotations pour valider et convertir les données à l'exécution (entrées d'API, fichiers de config) : un complément runtime au contrôle statique de mypy. Pour typer des décorateurs sans perdre la signature de la fonction décorée, regarde ParamSpec et typing.Concatenate. Les génériques avancés (bornes via TypeVar("T", bound=...), variance, @overload) couvrent les cas pointus.

Pour aller plus loin

Branche mypy (ou pyright) en CI avec un mypy --strict qui fait échouer la build sur erreur de type. Active-le progressivement (module par module) sur une base de code existante via le fichier mypy.ini ou la section [tool.mypy] de pyproject.toml.

Glossaire

Annotation de type
Indication de type attachée à une variable, un paramètre ou un retour (x: int, -> str). Stockée mais jamais vérifiée par l'interpréteur.
Typage statique / dynamique
Statique : les types sont contrôlés avant l'exécution par un outil. Dynamique : Python vérifie (ou non) au moment de l'exécution. Les annotations ajoutent le premier sans retirer le second.
mypy / pyright
Vérificateurs de types externes qui analysent le code annoté et signalent les incompatibilités avant de le lancer. pyright alimente Pylance dans VS Code.
Optional / union
X | None (ex-Optional[X]) autorise l'absence de valeur ; X | Y accepte l'un ou l'autre type. Un test is not None « rétrécit » ensuite le type.
TypeVar / générique
Variable de type capturant « un même type quelconque » pour relier entrée et sortie (def premier[T](xs: list[T]) -> T). Rend une fonction ou classe paramétrable.
Protocol (typage structurel)
Contrat défini par la forme : tout objet possédant les bonnes méthodes est compatible, sans héritage déclaré. Le duck typing rendu vérifiable statiquement.
TypedDict
Décrit un dictionnaire dont les clés et les types de valeurs sont fixés — pratique pour typer du JSON structuré.
Any vs object
Any désactive toute vérification (échappatoire) ; object accepte tout mais reste contrôlé et n'autorise que les opérations communes tant qu'on n'a pas restreint le type.

Récap et vérification

  • Les annotations documentent et permettent une vérification par un outil (mypy/pyright) ; elles n'agissent pas au runtime.
  • Paramètres nom: type, retour -> type ; conteneurs intégrés list[int], dict[str, int], tuple[int, ...].
  • X | None (= Optional[X]), union X | Y, Final, Literal ; préfère object à Any.
  • Génériques avec TypeVar/Generic[T] et la syntaxe def f[T](...) (3.12) ; accepte des types abstraits (Iterable, Sequence, Mapping, Callable).
  • Protocol = typage structurel ; TypedDict, NewType, cast, Self pour les cas précis ; vérifie avec mypy fichier.py.

Vérifie ta compréhension

  1. Pourquoi double("ab") s'exécute-t-il sans erreur alors que la signature attend un int ? Qui détecte le problème, et quand ?
  2. Quelle différence pratique entre Any et object pour le vérificateur de types ?
  3. En quoi un Protocol diffère-t-il d'une classe de base abstraite dont on hériterait explicitement ?
