Module 05 · Vers le confirmé — Leçon 15

Bonnes pratiques & synthèse

~33 min Intermédiaire Leçon 14 recommandée

À la fin de cette leçon, tu sauras

  • appliquer les conventions PEP 8 (nommage snake_case, 4 espaces, espaces autour des opérateurs) et automatiser avec black et ruff ;
  • ajouter des annotations de type et des docstrings pour rendre ton code lisible et vérifiable ;
  • isoler les dépendances d'un projet avec un environnement virtuel (venv) et pip ;
  • tester ton code avec assert et connaître unittest/pytest.
Sommaire de la leçon

Tu sais désormais écrire des programmes Python qui fonctionnent : variables, conditions, boucles, fonctions, structures de données. Cette dernière leçon change d'objectif. On ne va pas apprendre une nouvelle fonctionnalité, mais te montrer comment écrire du code propre, lisible et durable — celui qu'un autre développeur (ou toi dans six mois) comprendra sans effort. C'est ce qu'on appelle écrire du code « pythonique ».

On termine aussi par une synthèse du chemin parcouru et des pistes pour continuer. Garde un interpréteur ouvert : plusieurs exemples se recopient et se testent en deux secondes.

Le style PEP 8

La communauté Python suit un guide de style officiel appelé PEP 8. Ce n'est pas une obligation technique — ton code marche même s'il ne le respecte pas — mais c'est une convention partagée par presque tout le monde. La suivre rend ton code immédiatement familier aux autres.

Les règles de nommage sont les plus importantes : snake_case (mots en minuscules reliés par des tirets bas) pour les variables et les fonctions, PascalCase pour les classes, et MAJUSCULES_AVEC_TIRETS pour les constantes.

Les autres règles tiennent en quelques points : 4 espaces d'indentation (jamais de tabulation), des espaces autour des opérateurs (x = 1 + 2, pas x=1+2), et des lignes de longueur raisonnable (souvent 79 ou 88 caractères) pour rester lisibles.

Astuce

Tu n'as pas à appliquer PEP 8 à la main : des outils le font pour toi. black reformate automatiquement ton fichier, et ruff (ou flake8) signale les écarts de style et les erreurs probables. Installe-les avec pip install black ruff, puis lance black mon_fichier.py dans ton terminal.

Cas réel

Les grands projets open source (Django, pandas, la bibliothèque requests) ne laissent pas le style au hasard : à chaque proposition de contribution, un robot d'intégration continue lance black --check et ruff. Si le code n'est pas formaté ou comporte un écart, la contribution est refusée automatiquement, avant même toute relecture humaine. Beaucoup d'équipes branchent aussi ces outils en pre-commit : impossible de valider un commit mal formaté. PEP 8 n'est donc pas un détail cosmétique, c'est un passage obligé du travail en équipe.

Les annotations de type

Python reste dynamiquement typé : tu n'es jamais obligé d'indiquer les types. Mais tu peux les annoter pour documenter tes intentions. Une annotation se lit après le nom, derrière un : pour un paramètre, et derrière une flèche -> pour la valeur de retour.

Important : ces annotations ne sont pas vérifiées à l'exécution. Python ne plantera pas si tu passes un nombre là où un str est annoté ; le typage reste dynamique. Elles servent à la lisibilité et permettent à des outils comme mypy de détecter des incohérences avant de lancer le programme.

Quand une valeur peut être absente, on utilise None et on l'annote avec | None (ou Optional dans l'ancienne syntaxe).

Les docstrings

Une docstring est une chaîne placée juste après la ligne def (ou en haut d'un fichier) pour expliquer ce que fait une fonction. On l'écrit entre triple guillemets. C'est la façon standard de documenter en Python.

L'avantage : cette documentation vit dans le code, ne se périme pas, et reste consultable avec help() sans ouvrir le fichier. Une bonne docstring dit ce que fait la fonction, pas comment elle le fait.

Les environnements virtuels

Un vrai projet utilise souvent des bibliothèques externes (installées avec pip). Le problème : deux projets peuvent avoir besoin de versions différentes de la même bibliothèque. Un environnement virtuel (module venv) résout ça en créant un dossier isolé avec sa propre copie de Python et ses propres paquets. Les commandes ci-dessous se tapent dans le terminal, pas dans l'interpréteur Python.

Une fois l'environnement activé, on fige la liste des dépendances dans un fichier requirements.txt. N'importe qui pourra alors recréer exactement le même environnement.

Note

Le dossier .venv ne se partage pas : on l'ajoute à .gitignore. Ce qu'on partage, c'est requirements.txt, qui suffit à reconstruire l'environnement.

Tester son code

Plus ton code grandit, plus tu as besoin de vérifier qu'il marche encore après chaque modification. Le premier outil de test est le mot-clé assert : il vérifie qu'une condition est vraie, et lève une AssertionError sinon.

Attention

N'utilise jamais assert pour valider des données en production (entrée utilisateur, arguments d'une fonction publique). Lancé avec l'option python -O (optimisation), l'interpréteur supprime tous les assert : ta vérification disparaît sans prévenir. Pour un vrai contrôle, lève une exception explicite (raise ValueError(...)). Réserve assert aux tests et aux invariants internes.

Pour des projets sérieux, on utilise un vrai cadre de tests. Python en fournit un dans sa bibliothèque standard, unittest ; et la communauté plébiscite pytest, plus concis. Avec pytest, une fonction de test est simplement une fonction nommée test_… qui contient des assert.

Le Zen de Python

Python a une philosophie revendiquée. Tape import this dans le REPL pour lire le « Zen de Python », une liste de principes qui résument ce qu'est un code « pythonique ».

L'idée centrale : privilégie le code simple, explicite et lisible plutôt que malin et compact. Écrire pythonique, c'est utiliser les outils naturels du langage — une boucle for sur les éléments plutôt qu'un index, une compréhension de liste quand elle clarifie, des noms parlants — au lieu de plaquer les habitudes d'un autre langage.

Et après

Fais le point : tu maîtrises maintenant les variables et les types, les conditions et les boucles, les fonctions, les principales structures de données (listes, dictionnaires, ensembles, tuples), et tu sais écrire du code propre et testé. Ce sont des bases solides — celles qui te permettent d'apprendre à peu près n'importe quoi en Python par toi-même.

Pour continuer, plusieurs directions s'offrent à toi. Un cours Python avancé (décorateurs, générateurs, programmation asynchrone avec async, typage avancé, classes et objets en profondeur). La data, domaine où Python brille, avec NumPy et pandas pour manipuler des données, puis la visualisation et le machine learning. Le web, avec Flask (léger) ou Django (complet) pour construire des sites et des API. Et l'automatisation du quotidien : scripts de fichiers, scraping, petits outils en ligne de commande.

Pour aller plus loin

La meilleure façon de progresser, c'est de construire un petit projet qui te tient à cœur : un jeu en console, un script qui range tes fichiers, une mini-API. Tu rencontreras de vrais problèmes — et c'est en les résolvant qu'on devient confirmé.

Checklist de qualité

Avant de considérer un bout de code comme « fini », passe-le en revue :

  • Nommage PEP 8 : snake_case pour variables et fonctions, PascalCase pour les classes, MAJUSCULES pour les constantes.
  • Mise en forme : 4 espaces d'indentation, espaces autour des opérateurs, lignes courtes — ou laisse black s'en charger.
  • Lisibilité : des noms parlants, des fonctions courtes qui font une seule chose.
  • Annotations de type sur les fonctions publiques pour clarifier les entrées et la sortie.
  • Docstring sur chaque fonction non triviale.
  • Tests : au moins quelques assert qui couvrent les cas normaux et les cas limites.
  • Dépendances isolées dans un venv et listées dans requirements.txt.
  • Vérification statique avec ruff (style/erreurs) et, si possible, mypy (types).

Glossaire

PEP 8
Guide de style officiel de Python : conventions de nommage, d'indentation et de mise en forme partagées par la communauté.
snake_case / PascalCase
Casses de nommage : snake_case (minuscules et tirets bas) pour variables et fonctions, PascalCase pour les classes.
Annotation de type
Indication du type attendu (x: int, -> str) ; purement documentaire, non vérifiée à l'exécution.
Docstring
Chaîne entre triple guillemets placée en tête d'une fonction ou d'un module pour la documenter ; consultable via help().
Environnement virtuel (venv)
Dossier isolé (python -m venv .venv) contenant les dépendances propres à un projet, sans conflit avec les autres.
requirements.txt
Fichier listant les dépendances et leurs versions ; pip install -r recrée l'environnement à l'identique.
assert
Mot-clé qui vérifie qu'une condition est vraie et lève AssertionError sinon ; à réserver aux tests et aux invariants internes.
Zen de Python
Liste de principes (import this) résumant l'idéal pythonique : simple, explicite, lisible.

Récap et vérification

  • PEP 8 fixe le style : snake_case, PascalCase, CONSTANTES, 4 espaces, espaces autour des opérateurs — automatisé par black et ruff.
  • Les annotations de type (x: int, -> str, list[int], int | None) documentent et se vérifient avec mypy, sans changer le typage dynamique à l'exécution.
  • Une docstring (triple guillemets) documente une fonction, consultable via help().
  • Un environnement virtuel (python -m venv .venv) isole les dépendances ; requirements.txt les fige.
  • assert vérifie une condition ; unittest et pytest structurent les tests d'un projet.
  • Le Zen de Python (import this) résume l'idéal : simple, explicite, lisible.

Vérifie ta compréhension

  1. Quel nommage PEP 8 utilises-tu pour une variable, une classe et une constante ?
  2. Si tu annotes def f(x: int) -> int et que tu appelles f("abc"), Python lève-t-il une erreur ? Pourquoi ?
  3. À quoi sert un environnement virtuel, et quel fichier permet de le recréer ailleurs ?
