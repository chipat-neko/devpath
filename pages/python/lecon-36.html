Module 12 · Asynchrone & concurrence — Leçon 36

Threads, processus et le GIL

~35 min Avancé Leçon 07 recommandée

À la fin de cette leçon, tu sauras

  • expliquer le rôle du GIL et distinguer les charges I/O-bound (threads) des charges CPU-bound (processus) ;
  • écrire du code threading correct : Lock/RLock, Event, queue.Queue, et éviter les conditions de course ;
  • contourner le GIL avec multiprocessing et piloter ThreadPoolExecutor/ProcessPoolExecutor via l'API unifiée de concurrent.futures ;
  • choisir le bon modèle de concurrence selon la charge et connaître le no-GIL (3.13) et les sous-interpréteurs.
Sommaire de la leçon

Tu sais déjà écrire du code asynchrone avec asyncio. Mais asyncio ne couvre qu'un cas : un seul thread qui jongle entre des attentes d'E/S. Dès qu'il faut du vrai parallélisme — saturer plusieurs cœurs pour un calcul lourd, ou paralléliser des appels réseau bloquants venus d'une bibliothèque synchrone — il faut sortir l'artillerie : threads et processus. Et là, une particularité de CPython change tout : le GIL.

Cette leçon démêle ce qui ralentit, ce qui accélère, et pourquoi. On part du GIL (le « pourquoi »), puis on outille threading, multiprocessing et concurrent.futures (le « comment »), avant de poser la règle de décision et de regarder vers l'avenir sans-GIL.

Le GIL : un seul thread de bytecode à la fois

Le GIL (Global Interpreter Lock) est un verrou global de l'interpréteur CPython. Sa règle est brutale : un seul thread peut exécuter du bytecode Python à un instant donné. Tes threads existent bien, le système d'exploitation les ordonnance, mais ils se passent le GIL en relais — jamais deux n'avancent du code Python en même temps.

Conséquence directe : pour un calcul pur (CPU-bound), N threads ne vont pas plus vite qu'un seul, et même un peu moins vite à cause du coût de bascule. En revanche, le GIL est relâché pendant les attentes d'E/S (lecture réseau, disque, time.sleep) : là, pendant qu'un thread attend, un autre travaille. Les threads brillent donc en I/O-bound.

Quatre threads font quatre fois le travail en quatre fois le temps : aucune parallélisation du calcul.

threading : verrous, événements, et conditions de course

Le GIL protège l'interpréteur, pas ta logique. Une opération qui « a l'air atomique » comme compteur += 1 se décompose en plusieurs bytecodes (lire, ajouter, réécrire). Si un changement de thread tombe entre les deux, tu perds des incréments : c'est une condition de course (race condition).

Un Lock ne peut pas être repris par le thread qui le détient déjà (réacquisition = blocage). Si une fonction verrouillée en appelle une autre qui reverrouille, utilise un RLock (reentrant), qui compte les acquisitions du même thread. Pour signaler un état entre threads (« c'est prêt », « stop »), Event est l'outil idiomatique.

Pour échanger des données entre threads sans gérer toi-même les verrous, privilégie queue.Queue : elle est thread-safe par construction. C'est le patron producteur/consommateur de référence.

multiprocessing : de vrais processus contournent le GIL

Pour accélérer un calcul, il faut échapper au GIL. multiprocessing lance de vrais processus système, chacun avec son propre interpréteur et donc son propre GIL : ils tournent réellement en parallèle sur plusieurs cœurs.

Le prix à payer : les processus ne partagent pas la mémoire. Tout argument et tout résultat traverse une frontière via sérialisation pickle. Pour de petites tâches, ce coût (sérialiser, copier, démarrer le processus) dépasse le gain. L'échange explicite se fait par Queue (multi-producteurs/consommateurs) ou Pipe (canal entre deux extrémités).

Note

Le garde if __name__ == "__main__": n'est pas décoratif. Sous Windows et macOS, la méthode de démarrage par défaut est spawn : chaque processus enfant réimporte ton module. Sans ce garde, le code de lancement se rejoue à l'infini et crée une bombe à fork.

concurrent.futures : une API unifiée

concurrent.futures offre une façade commune aux deux mondes : ThreadPoolExecutor (threads, I/O-bound) et ProcessPoolExecutor (processus, CPU-bound) partagent exactement la même interface. Tu écris ton code une fois, tu changes une ligne pour basculer de stratégie.

On soumet du travail avec submit(), qui renvoie un Future — une promesse de résultat — ou avec map() pour appliquer une fonction à un itérable. as_completed() donne les résultats dans l'ordre où ils finissent.

Pour le CPU-bound, un seul mot change. La fonction et les données doivent rester picklables (définies au niveau module, pas une lambda ni une closure locale).

Choisir : I/O-bound ou CPU-bound

Toute la décision tient en une question : ton goulot d'étranglement, c'est l'attente ou le calcul ?

  • I/O-bound (réseau, disque, base de données) : le programme passe son temps à attendre. Choisis asyncio si l'écosystème est asynchrone (clients async), sinon des threads (ThreadPoolExecutor) pour envelopper du code bloquant synchrone.
  • CPU-bound (calcul numérique, parsing intensif, compression) : le programme calcule. Le GIL bloque les threads, il faut des processus (ProcessPoolExecutor / multiprocessing).

Astuce

Au sein d'asyncio, ne lance jamais un calcul lourd directement dans une coroutine : il bloque toute la boucle. Délègue-le à un pool de processus via await loop.run_in_executor(pool, fonction, *args), avec un ProcessPoolExecutor. Tu gardes l'await tout en libérant la boucle.

Cas réel

Un pipeline de traitement de photos illustre les deux régimes dans un même programme : télécharger 500 images depuis un stockage objet (S3) est I/O-bound → un ThreadPoolExecutor recouvre les attentes réseau ; puis les redimensionner et recompresser est CPU-bound → un ProcessPoolExecutor sature les cœurs. C'est aussi pourquoi les serveurs comme Gunicorn lancent plusieurs workers processus (souvent un par cœur) plutôt que des threads : chaque requête Django/Flask exécute du bytecode que le GIL sérialiserait. Et quand une bibliothèque en C — NumPy, pandas, Pillow — relâche le GIL pendant ses calculs vectorisés, les threads redeviennent utiles autour d'elle.

L'horizon : no-GIL et sous-interpréteurs

Le GIL est en train de bouger. Depuis Python 3.13, une build « free-threaded » (no-GIL) existe à titre expérimental (PEP 703) : les threads y exécutent du bytecode réellement en parallèle, rendant threading pertinent même pour le CPU-bound. C'est encore opt-in, plus lent en mono-thread, et incompatible avec une partie de l'écosystème C — à surveiller, pas à déployer aveuglément.

Autre piste, les sous-interpréteurs (PEP 734, exposés dans la stdlib via concurrent.interpreters en 3.14) : plusieurs interpréteurs dans un même processus, chacun avec son propre GIL, plus légers que des processus système et sans sérialisation systématique. Une troisième voie entre threads et processus.

Pièges fréquents

  • Attendre une accélération CPU avec des threads. Le GIL sérialise le bytecode : 4 threads sur un calcul pur ne font qu'ajouter de la bascule. Pour du calcul, passe aux processus.
  • État partagé sans verrou. x += 1, l'ajout dans une liste, la mise à jour d'un dict : rien n'est garanti atomique pour ta logique. Protège la section critique avec Lock/RLock, ou échange via queue.Queue.
  • multiprocessing pour de petites tâches. Démarrer un processus et sérialiser ses données coûte cher. Si le travail unitaire est minuscule, le surcoût pickle + spawn mange tout le gain : regroupe (chunks) ou reste en thread.
  • Envoyer un objet non picklable. Une lambda, une fonction locale, un fichier ouvert, une connexion réseau, un verrou : impossible à sérialiser, donc PicklingError. Vers un processus, ne passe que des objets simples et des fonctions de niveau module.

Piège fréquent

Un Future qui lève une exception ne la propage qu'à l'appel de .result(). Si tu soumets sans jamais lire le résultat, l'erreur reste silencieuse et tu crois ton traitement réussi. Lis toujours les futures (via as_completed ou en itérant map).

Pour aller plus loin

Côté concurrent.futures, explore initializer (préparer chaque worker une fois, ex. ouvrir une connexion), chunksize sur map pour amortir la sérialisation, et max_workers calibré sur os.cpu_count(). Pour la parallélisation de boucles scientifiques, joblib offre une Parallel/delayed très ergonomique et du caching.

Surtout, retiens que NumPy relâche le GIL pendant ses opérations vectorisées en C : un gros produit matriciel se parallélise déjà sous le capot, et les threads redeviennent utiles autour de lui. Enfin, pour passer à l'échelle au-delà d'une machine, regarde les files distribuées et exécuteurs distants : Celery, Dask, Ray.

Pour aller plus loin

ProcessPoolExecutor(mp_context=...) te laisse choisir la méthode de démarrage (spawn, fork, forkserver). fork est rapide mais dangereux avec des threads ou des verrous déjà pris ; spawn est plus lent mais propre et portable — c'est désormais le défaut recommandé partout.

Glossaire

GIL
Global Interpreter Lock : verrou de CPython n'autorisant qu'un seul thread à exécuter du bytecode Python à la fois ; relâché pendant les E/S.
I/O-bound
Charge dont le goulot est l'attente (réseau, disque, base de données) : le processeur reste inactif. Les threads et asyncio y excellent.
CPU-bound
Charge dont le goulot est le calcul (nombres, parsing, compression) : elle réclame de vrais processus pour utiliser plusieurs cœurs.
Thread
Fil d'exécution au sein d'un processus, partageant sa mémoire ; léger, mais soumis au GIL pour le bytecode Python.
Processus
Instance système isolée avec sa propre mémoire et son propre interpréteur (donc son propre GIL) ; échange ses données par pickle.
Condition de course
Race condition : résultat qui dépend de l'ordre imprévisible d'exécution des threads sur un état partagé non protégé (ex. x += 1).
Verrou (Lock)
Primitive garantissant qu'un seul thread entre dans une section critique à la fois, éliminant les conditions de course sur l'état partagé.
Future
Objet renvoyé par submit() représentant un résultat à venir ; .result() attend la fin et propage l'exception éventuelle.

Récap et vérification

  • Le GIL n'autorise qu'un thread de bytecode à la fois : pas d'accélération CPU avec des threads, mais il est relâché pendant les E/S.
  • threading convient à l'I/O-bound ; protège l'état partagé avec Lock/RLock, signale avec Event, échange en sécurité via queue.Queue.
  • multiprocessing lance de vrais processus qui contournent le GIL pour le CPU-bound ; coût de sérialisation pickle et garde if __name__ == "__main__": obligatoire.
  • concurrent.futures unifie les deux via submit/map et les objets Future ; bascule thread ↔ processus en changeant une ligne.
  • Règle : I/O-bound → asyncio ou threads ; CPU-bound → processus. Le no-GIL (3.13) et les sous-interpréteurs rebattront les cartes.

Vérifie ta compréhension

  1. Pourquoi lancer 4 threads sur une boucle de calcul pur ne va-t-il pas (sensiblement) plus vite qu'un seul thread ?
  2. Tu dois interroger 50 URLs via un client HTTP synchrone bloquant. ThreadPoolExecutor ou ProcessPoolExecutor ? Justifie.
  3. Pourquoi une lambda passée à ProcessPoolExecutor.submit() échoue-t-elle, et qu'écrire à la place ?
