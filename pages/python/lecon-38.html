Tests et qualité (pytest)

~35 min Avancé Module 3 recommandé

À la fin de cette leçon, tu sauras

  • savoir structurer des tests pytest avec assert, des fixtures et @pytest.mark.parametrize ;
  • savoir tester les erreurs avec pytest.raises, les approximations avec pytest.approx et isoler des dépendances avec unittest.mock ;
  • savoir écrire des doctests et mesurer la couverture avec coverage ;
  • savoir déboguer avec breakpoint() et garder un code propre avec ruff, black et mypy.
Sommaire de la leçon

Un code qui « marche sur ma machine » ne vaut rien sans filet : dès que tu refactores, ajoutes une feature ou montes de version, ce sont les tests qui te disent si tu as cassé quelque chose. pytest est le standard de fait de l'écosystème Python : syntaxe minimale (un simple assert), introspection riche des échecs, et un système de fixtures et de plugins qui couvre tout du test unitaire au test d'intégration.

Cette leçon part du principe que tu écris déjà des fonctions typées. On va voir comment les verrouiller : organiser des tests, partager du contexte, paramétrer, isoler les dépendances, mesurer la couverture et garder le tout propre.

Pourquoi tester, et la pyramide

On distingue les tests unitaires (une fonction ou une classe isolée, rapides, nombreux) des tests d'intégration (plusieurs composants ensemble : base de données, HTTP, fichiers) et des tests end-to-end (le système complet). La pyramide des tests recommande beaucoup de tests unitaires à la base, moins d'intégration au milieu, très peu d'E2E au sommet : les premiers sont rapides et précis, les derniers lents et fragiles.

La fonction sous test pour la suite de la leçon.

Écrire et lancer des tests pytest

pytest découvre automatiquement les fichiers test_*.py et les fonctions test_*. Pas de classe ni de méthode assertEqual obligatoires : un assert nu suffit, et pytest réécrit l'expression pour t'afficher les valeurs réelles en cas d'échec.

On lance avec pytest -q (mode silencieux) ou pytest -v (verbeux, un test par ligne).

Fixtures : préparer et partager le contexte

Une fixture est une fonction décorée par @pytest.fixture qui prépare un objet (connexion, fichier temporaire, jeu de données) et le fournit aux tests qui la nomment en paramètre. Tu peux y faire du teardown avec yield : tout ce qui suit le yield s'exécute après le test.

La portée se règle avec scope= : "function" (défaut, recréée à chaque test), "module", "session". Une fixture coûteuse mais immuable (un client HTTP factice) gagne à être en scope="session" ; une fixture qui porte un état muté doit rester en portée fonction. Les fixtures partagées entre fichiers vont dans un conftest.py, automatiquement découvert.

Paramétrer un test

Plutôt que de copier-coller un test pour chaque jeu de données, @pytest.mark.parametrize exécute le même corps sur plusieurs entrées ; chaque cas compte comme un test distinct dans le rapport.

Tester les erreurs et les approximations

Une fonction robuste doit lever les bonnes exceptions : pytest.raises capture l'exception attendue et te laisse inspecter son message via match= (une regex cherchée dans le message, pas une égalité). Pour les flottants, l'égalité stricte est piégeuse : pytest.approx compare à une tolérance près.

Isoler les dépendances avec les mocks

Un test unitaire ne doit pas dépendre du réseau, de l'horloge ou du disque. unittest.mock fournit Mock / MagicMock (des objets qui enregistrent leurs appels) et patch (qui remplace temporairement un attribut). Règle d'or : on patche là où l'objet est utilisé, pas là où il est défini.

Le pendant horloge : figer datetime.now() en remplaçant la classe dans le module testé, par exemple avec patch("module.datetime") puis mock.now.return_value = ..., ou un monkeypatch.setattr(...) (fixture pytest) pour le même effet de façon plus locale.

doctest : des tests dans les docstrings

Tu peux glisser des exemples exécutables dans une docstring : ils servent à la fois de documentation et de test. pytest --doctest-modules les exécute en même temps que le reste.

Garde les doctests pour de petits exemples illustratifs ; les cas tordus et les mocks restent dans des fichiers test_*.py.

Couverture, débogage et linting

La couverture mesure quelles lignes sont exécutées par les tests. Avec le plugin pytest-cov : pytest --cov=account --cov-report=term-missing. La colonne Missing liste les lignes jamais atteintes — utile pour repérer une branche oubliée. Attention : 100 % de couverture ne prouve pas l'absence de bug, juste que la ligne a tourné au moins une fois.

Pour déboguer, breakpoint() (équivalent moderne de import pdb; pdb.set_trace()) ouvre pdb : n (next), s (step), c (continue), p expr (print). Avec pytest, lance pytest --pdb pour entrer dans le débogueur sur le premier échec.

Côté qualité statique : ruff (linter et formateur ultra-rapide qui remplace flake8/isort/pyupgrade), black (formatage déterministe — ruff sait aussi le faire) et mypy (vérification de types). En CI, on enchaîne typiquement ruff check ., mypy . puis pytest --cov sur chaque push.

Cas réel

Dans une équipe, la fonction de calcul de TVA est refactorée à la veille d'une mise en production. Sans la suite parametrize qui couvrait taux normal, réduit et exonéré, le bug — le taux 0 % traité comme « absent » — serait passé en prod. Ici, la CI (GitHub Actions) enchaîne ruff check, mypy puis pytest --cov à chaque push : un test rouge bloque la fusion de la pull request. Et parce que les appels réseau sont mockés, la suite complète tourne hors-ligne en une fraction de seconde — donc à chaque sauvegarde, sans friction.

Astuce

Configure tout dans pyproject.toml (sections [tool.pytest.ini_options], [tool.ruff], [tool.mypy]) : une seule source de vérité, partagée par ton éditeur et la CI.

Pièges fréquents

Piège fréquent

Tests couplés ou dépendants de l'ordre. Un test qui ne passe que si un autre a tourné avant (état global muté, ordre d'exécution) casse dès qu'on lance un sous-ensemble ou qu'on parallélise. Chaque test doit partir d'un état propre : c'est exactement le rôle des fixtures avec teardown.

  • Tout mocker. Si tu remplaces la moitié de la logique par des mocks, tu testes tes mocks, pas ton code. Ne mocke que les frontières (réseau, horloge, disque, services externes).
  • Négliger les cas limites. Le chemin heureux passe toujours : ce sont le zéro, le vide, le négatif, le très grand et les exceptions qui révèlent les bugs.
  • Fixtures à portée trop large. Une fixture scope="session" qui porte un état mutable fait fuiter cet état d'un test à l'autre : réserve les portées larges aux objets immuables ou recréés proprement.

Pour aller plus loin

Pour aller plus loin

hypothesis génère automatiquement des entrées pour tester des propriétés (ex. : « décoder puis encoder rend l'original ») et trouve les contre-exemples minimaux. tox/nox exécutent ta suite sur plusieurs versions de Python. Creuse aussi les vrais tests d'intégration (bases de données éphémères, testcontainers) et l'approche TDD (écrire le test avant le code).

Glossaire

Test unitaire
Test d'une unité isolée (fonction, classe) sans dépendance externe : rapide, précis et nombreux — la base de la pyramide.
Fixture
Fonction pytest qui prépare et fournit un contexte à un test ; avec yield, la partie qui suit assure le nettoyage (teardown).
Paramétrisation
Exécuter le même test sur plusieurs jeux d'entrées via @pytest.mark.parametrize ; chaque cas est compté séparément.
Mock
Objet factice qui remplace une dépendance et enregistre ses appels (unittest.mock), pour tester sans réseau, horloge ni disque.
patch
Remplacement temporaire d'un objet, appliqué là où il est utilisé (référence importée) et non là où il est défini.
Couverture
Proportion des lignes de code exécutées par les tests ; utile pour repérer les branches oubliées, mais ne prouve pas l'absence de bug.
doctest
Exemple exécutable placé dans une docstring, servant à la fois de documentation et de test (pytest --doctest-modules).
Teardown
Phase de nettoyage après un test (fermer un fichier, une connexion…) ; en pytest, c'est le code après le yield d'une fixture.

Récap et vérification

  • pytest découvre test_*.py / test_* et utilise un simple assert introspecté.
  • Les fixtures préparent et partagent du contexte ; yield gère le teardown ; scope contrôle la durée de vie.
  • @pytest.mark.parametrize multiplie un test sur plusieurs jeux de données.
  • pytest.raises teste les exceptions, pytest.approx les flottants.
  • unittest.mock (patch là où c'est utilisé) isole les dépendances ; doctest met des exemples testables dans les docstrings.
  • coverage mesure les lignes exécutées ; breakpoint() ouvre pdb ; ruff/black/mypy tiennent la qualité.

Vérifie ta compréhension
