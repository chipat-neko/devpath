Module 13 · Robustesse, performance & métaprogrammation — Leçon 39

Performance et profilage

~35 min Avancé Leçon 10 recommandée

À la fin de cette leçon, tu sauras

  • savoir mesurer avec timeit, cProfile/pstats et tracemalloc avant de toucher au code ;
  • savoir choisir la bonne structure de données (set, dict, deque, bisect) selon la complexité visée ;
  • savoir appliquer les idiomes rapides (compréhensions, génération paresseuse, mémoïsation, __slots__) ;
  • savoir déléguer aux extensions (NumPy, multiprocessing) et repérer un O(n²) caché.
Sommaire de la leçon

« Premature optimization is the root of all evil » (Knuth) reste vrai, mais son corollaire l'est tout autant : quand la performance compte, tu n'as pas le droit de deviner. L'intuition d'un développeur sur ce qui est lent est notoirement mauvaise — le coupable est presque toujours ailleurs que là où tu l'imagines. Cette leçon suit une discipline simple : mesure d'abord, change ensuite, re-mesure pour confirmer.

On part du micro-benchmark, on monte au profilage de programme entier, on couvre la mémoire, puis on passe en revue les structures et idiomes qui changent réellement les ordres de grandeur. Tous les chiffres ci-dessous sont indicatifs (CPython 3.12, une machine donnée) : ce qui compte, ce sont les rapports entre variantes, pas les valeurs absolues.

Mesurer d'abord : timeit

timeit isole une micro-opération et la répète des milliers de fois pour gommer le bruit. Il désactive le ramasse-miettes pendant la mesure et te laisse garder le meilleur essai (le plus représentatif du coût réel, hors contention système).

En ligne de commande : python -m timeit -s "data=list(range(1000))" "[x*2 for x in data]".

Note

Passe le code à mesurer en chaîne ou en callable, et place tout ce qui ne doit pas être chronométré (imports, construction des données) dans setup. En notebook, le magique %timeit fait la même chose en une ligne.

Profiler un programme : cProfile + pstats

timeit répond à « cette ligne est-elle rapide ? ». cProfile répond à la vraie question : « où mon programme passe-t-il son temps ? ». Il compte les appels et le temps par fonction ; pstats trie et filtre le résultat.

tottime = temps passé DANS la fonction (hors appels enfants) ; cumtime = temps cumulé avec les enfants. sum est appelé une fois par tour externe (2000 fois) ; le générateur, lui, ~2 millions de fois. Trie sur tottime pour le point chaud.

Astuce

Depuis le shell : python -m cProfile -s tottime mon_script.py. Pour explorer un gros profil visuellement, dumpe-le (stats.dump_stats("out.prof")) et ouvre-le avec snakeviz.

Mesurer la mémoire : tracemalloc

Le temps n'est qu'une moitié de l'histoire. tracemalloc (stdlib) trace les allocations et te dit quelle ligne consomme la mémoire, avec un pic précis.

Compare le pic d'une liste matérialisée à celui d'un générateur (section suivante) : c'est là que la génération paresseuse gagne des ordres de grandeur.

Les bonnes structures de données

Le levier le plus rentable, et de loin, n'est pas l'idiome mais la complexité. Choisir set au lieu de list pour un test d'appartenance transforme un O(n) en O(1) — gain qui explose avec la taille.

Note

Si tu testes l'appartenance dans une boucle, construis le set une fois avant la boucle. Le reconstruire à chaque itération annule tout le gain (et c'est un piège classique).

Les idiomes rapides

À complexité égale, certains réflexes réduisent le facteur constant. Les compréhensions sont compilées en bytecode dédié ; la génération paresseuse économise la mémoire ; la mémoïsation supprime le travail redondant.

Astuce

Dans une boucle serrée, relie les attributs/méthodes à des variables locales : append = liste.append avant la boucle évite une recherche d'attribut par itération. CPython accède aux locales plus vite qu'aux globales et aux attributs. Ne fais ça qu'après avoir confirmé par la mesure que la boucle est bien le point chaud.

__slots__ pour l'empreinte mémoire

Par défaut, chaque instance porte un __dict__ pour stocker ses attributs — souple mais coûteux quand tu crées des millions d'objets. __slots__ remplace ce dictionnaire par un emplacement fixe : moins de mémoire et un accès d'attribut plus rapide.

Contrepartie : avec __slots__, tu ne peux plus ajouter d'attribut hors de la liste déclarée (ni avoir de __dict__/__weakref__ par défaut). C'est un compromis pour les objets nombreux, pas un réglage à mettre partout.

Note

Pour du calcul CPU, utilise des process (le GIL sérialise les threads). Pour de l'I/O (réseau, disque), asyncio ou les threads suffisent. Pour pousser plus loin sans réécrire en C : Cython ou des extensions natives. Python 3.13 introduit aussi un mode free-threaded expérimental (sans GIL).

Repérer la complexité cachée

Le bug de perf le plus fréquent n'est pas un facteur constant, c'est un O(n²) involontaire : une boucle qui en cache une autre, ou une copie répétée. La mesure le révèle en faisant varier n et en observant si le temps quadruple quand n double.

Méfie-toi aussi des copies invisibles : liste[:] dans une boucle, + sur des listes, ou un slicing répété qui duplique des données déjà en mémoire.

Cas réel

Un tableau de bord interne affichait la liste des commandes avec le nom du client. En développement (200 commandes de test), la page s'ouvrait instantanément. En production, passé 60 000 commandes, elle mettait 40 secondes puis expirait. Le code n'avait pas changé : seule la taille des données avait franchi un seuil. Un cProfile a montré 98 % du temps dans une fonction qui, pour chaque commande, retrouvait son client par for c in clients: if c.id == cmd.client_id — une boucle dans une boucle, soit O(n·m). Le correctif a tenu en deux lignes : indexer les clients une fois dans un dict {c.id: c for c in clients}, puis lire en O(1). La page est repassée à 0,3 seconde. Morale : un O(n²) reste invisible sur de petits jeux de test et n'explose qu'en production.

Pièges fréquents

Piège fréquent

Optimiser sans mesurer. Tu réécris une fonction « évidemment lente » qui ne pesait que 2 % du temps total, et tu ignores le vrai goulot. Profile avant de toucher quoi que ce soit, et après pour prouver le gain.

Piège fréquent

Concaténer des chaînes avec += dans une boucle (O(n²) car la chaîne est immuable et recopiée), et recréer une structure à chaque itération (reconstruire un set dans la boucle au lieu d'une fois avant). Les deux annulent tes gains de complexité.

Pour aller plus loin

Pour aller plus loin

line_profiler (temps ligne par ligne, décorateur @profile) et memory_profiler affinent le diagnostic au-delà de la granularité fonction. functools.cache / lru_cache mémoïsent proprement. L'interpréteur PyPy (compilation JIT) accélère du code Python pur sans rien changer. Et revois le cours Algorithmes pour raisonner en complexité avant même de coder.

Antisèche : la boîte à outils performance

Glossaire

Profilage
Mesure automatique de l'exécution d'un programme pour savoir où il passe son temps ou sa mémoire, fonction par fonction.
Micro-benchmark
Mesure d'un très petit fragment de code répété des milliers de fois pour comparer deux implémentations (rôle de timeit).
Point chaud (hotspot)
La portion de code responsable de l'essentiel du temps d'exécution ; la seule qu'il vaut la peine d'optimiser.
tottime vs cumtime
Dans cProfile : temps passé dans une fonction seule (tottime) contre temps cumulé avec ses appels enfants (cumtime).
Complexité (grand O)
Façon dont le coût croît avec la taille des données : O(1) constant, O(n) linéaire, O(n²) quadratique.
Mémoïsation
Mémoriser le résultat d'une fonction pour chaque entrée afin de ne jamais le recalculer (@cache, lru_cache).
__slots__
Déclaration qui remplace le __dict__ d'une instance par des emplacements fixes : moins de mémoire, accès plus rapide.
Vectorisation
Remplacer une boucle Python par une opération globale sur un tableau (NumPy) exécutée en code C compilé.

Récap et vérification

  • Mesure d'abord : timeit pour une micro-opération, cProfile/pstats pour localiser le point chaud, tracemalloc pour la mémoire.
  • La structure prime sur l'idiome : set/dict en O(1), deque aux extrémités, bisect pour une liste triée.
  • Idiomes : compréhensions, génération paresseuse, mémoïsation, "".join, variables locales.
  • Mémoire : __slots__ (ou dataclass(slots=True)) pour des millions d'instances.
  • Déléguer : NumPy (vectorisation), Cython/C, multiprocessing (CPU), et traquer l'O(n²) caché.
