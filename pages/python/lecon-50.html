Projet de synthèse : concevoir un module professionnel

~40 min Intermédiaire Leçon 21 recommandée

À la fin de cette leçon, tu sauras

  • structurer un projet moderne (src layout, pyproject.toml, tests/) ;
  • concevoir une API publique claire, typée et documentée ;
  • rendre un module robuste avec exceptions dédiées, validation et logging ;
  • organiser des tests selon la pyramide unitaires / intégration / bout-en-bout ;
  • dérouler la démarche complète, du besoin à la distribution.
Sommaire de la leçon

Tu as parcouru les décorateurs, le modèle de données, le typage, l'asynchrone, les tests, la journalisation, la performance… Ces briques ne valent que si elles tiennent ensemble dans un livrable propre. Cette dernière leçon est un projet fil : transformer un petit besoin en un module Python professionnel, de l'arborescence à la distribution, en réunissant le meilleur du cours. Fil conducteur : un mini-module facturation qui calcule des totaux TTC.

La structure d'un projet moderne

Un projet sérieux sépare le code source (dans src/), les tests, et les métadonnées déclarées dans un seul fichier : pyproject.toml. Le src layout (le code sous src/ plutôt qu'à la racine) évite un piège classique : importer accidentellement le dossier de travail au lieu du paquet installé, ce qui masque les erreurs d'empaquetage.

Concevoir l'API avant le code

Un bon module se pense « de l'extérieur » : quelle est l'interface publique, ce que l'utilisateur importe et appelle ? On la garde petite, typée et documentée. Les dataclasses décrivent les données, les annotations de type documentent les contrats, et __init__.py choisit ce qui est exposé.

Astuce : une API se juge à ce qu'elle cache

Expose le strict nécessaire. Préfixe les détails internes d'un _, liste l'API publique dans __all__, et fais passer les types par la signature (mypy documente et vérifie à la fois). Un utilisateur doit pouvoir se servir de ton module sans lire son code source.

Rendre le code robuste

Du code de production valide ses entrées, signale ses erreurs avec des exceptions dédiées (pas un return None silencieux), et journalise au lieu d'imprimer. Une hiérarchie d'exceptions propre au module permet à l'appelant d'attraper précisément ce qui le concerne.

Erreur fréquente : avaler les exceptions

Un try/except Exception: pass transforme un bug en donnée fausse silencieuse. N'attrape que ce que tu sais traiter, relance le reste, et si tu enregistres l'erreur, garde la trace avec logger.exception(...). Une exception dédiée (LigneInvalide) vaut mille codes de retour ambigus.

La démarche, étape par étape

Concevoir un module professionnel suit toujours le même fil : partir du besoin, dessiner l'API, typer, tester, journaliser, documenter, puis publier. Chaque étape s'appuie sur une leçon du cours ; assemblées, elles font la différence entre un script et un livrable.

Côté tests, tout n'a pas le même poids. La pyramide de tests recommande beaucoup de tests unitaires (rapides, ciblés), quelques tests d'intégration (plusieurs modules ensemble), et très peu de tests de bout en bout (lents, fragiles, mais réalistes).

Cas réel

Le script d'un stagiaire devenu bibliothèque de l'équipe. Un calcul de facturation vit d'abord dans un unique facturation.py de 400 lignes, avec des print partout et un except: pass qui masquait les prix négatifs. Trois mois plus tard, deux autres équipes en dépendent — et personne n'ose y toucher. La remise à plat : un src layout, une API réduite à total_ttc et Ligne, des exceptions dédiées, du logging, et une trentaine de tests unitaires. Résultat : un paquet installable, une montée de version tranquille, et des bugs attrapés avant la production. La différence n'était pas le langage : c'était la démarche.

Antisèche : la checklist du module pro

Pour aller plus loin

Pour aller plus loin

Pour industrialiser : ruff (lint + format ultra-rapide), pre-commit (garde-fous avant chaque commit), tox/nox (tester sur plusieurs versions de Python), la couverture (pytest --cov), les property-based tests (Hypothesis), et une CI (GitHub Actions) qui rejoue tout à chaque push. Pour la doc : MkDocs ou Sphinx. Ces outils se déclarent presque tous dans le même pyproject.toml.

Glossaire

Disposition src (src layout)
Organisation où le code du paquet vit dans src/monpaquet/ ; elle force à tester la version installée, pas les fichiers du dossier de travail.
pyproject.toml
Fichier standard (PEP 518/621) qui déclare les métadonnées, les dépendances et la configuration des outils d'un projet Python.
API publique
Surface qu'un module expose et s'engage à maintenir ; le reste est un détail d'implémentation, signalé par un préfixe _.
dataclass
Décorateur qui génère automatiquement __init__, __repr__ et __eq__ pour une classe surtout porteuse de données.
Exception dédiée
Classe d'erreur propre au module (class MonErreur(Exception)) qui laisse l'appelant capter précisément ce qui a échoué.
logging
Module standard de journalisation par niveaux (de DEBUG à CRITICAL) ; à préférer à print pour tracer une bibliothèque.
Pyramide de tests
Beaucoup de tests unitaires rapides à la base, moins de tests d'intégration, quelques tests bout-en-bout au sommet.
Indice de type (type hint)
Annotation comme x: int qui documente le code et permet à un vérificateur (mypy, Pyright) d'attraper des erreurs avant l'exécution.

Récap et vérification

  • Structure : src layout, pyproject.toml, dossier tests/ séparé du code livré.
  • API d'abord : interface publique petite, typée, documentée ; expose le minimum (__all__).
  • Robustesse : valider les entrées, exceptions dédiées (hiérarchie), logging plutôt que print.
  • Tests : la pyramide — beaucoup d'unitaires rapides, quelques intégrations, très peu de bout en bout.
  • Démarche : besoin → API → types → tests → journal → doc → publier ; itérative en pratique.

Vérifie ta compréhension

  1. Quel piège le src layout évite-t-il par rapport au code posé à la racine ?
  2. Pourquoi préférer une exception dédiée à un return None en cas d'erreur ?
  3. Que recommande la pyramide de tests, et pourquoi ?

Mini-projet fil rouge — un décorateur de chronométrage

Pour clore ce cours, écrivons un décorateur de chronométrage. Il réunit une dataclass, un décorateur qui préserve la fonction (functools.wraps), les arguments variadiques (*args, **kwargs), une clôture et time.perf_counter — un condensé de Python avancé.

Ce que tu vas construire

Un décorateur @chronometrer qui mesure le temps d'exécution d'une fonction et l'affiche via une dataclass Mesure, sans changer la signature de la fonction décorée.

Étapes

La dataclass

Définis @dataclass class Mesure avec nom: str et duree: float.

Le décorateur

Écris chronometrer(fn) qui renvoie un emballage décoré par @wraps(fn).

Mesurer

Encadre l'appel par deux time.perf_counter() et calcule la durée.

Transmettre les arguments

Accepte *args, **kwargs et renvoie le résultat inchangé.

Utiliser

Décore une fonction de calcul et appelle-la.

ProjetFil rouge

Assemble le tout. Essaie d'abord par toi-même, puis compare avec la solution de référence.
