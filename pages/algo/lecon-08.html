Piles et files

~34 min Intermédiaire Leçon 07 recommandée

À la fin de cette leçon, tu sauras

  • savoir distinguer une pile (LIFO) d'une file (FIFO) et choisir la bonne structure selon le problème ;
  • savoir implémenter une Pile et une File avec des opérations en O(1) (amorti pour la file) ;
  • savoir appliquer une pile à un problème réel comme la vérification de parenthèses équilibrées ;
  • savoir reconnaître et éviter le piège de Array.shift() en O(n) dans une file.
Sommaire de la leçon

Un tableau te laisse lire et écrire n'importe où, n'importe quand. Mais beaucoup d'algorithmes n'ont pas besoin de cette liberté : ils veulent juste un endroit où poser des éléments et les reprendre dans un ordre précis. En se restreignant volontairement à deux ou trois opérations, on gagne des garanties fortes—chaque opération en temps constant—et un code plus simple à raisonner.

Les deux structures d'accès restreint les plus courantes sont la pile (on reprend le dernier posé) et la file (on reprend le premier posé). Elles sont partout : la pile d'appels qui exécute ton code, le bouton « annuler », les parcours de graphes, les files d'attente de tâches. L'idée clé de cette leçon : ces structures sont triviales tant qu'on respecte la discipline d'accès, et le moindre écart (comme utiliser shift() pour une file) fait s'effondrer la complexité.

La pile : LIFO

Une pile suit le principe LIFO (Last In, First Out) : le dernier élément entré est le premier à sortir. Pense à une pile d'assiettes : tu poses au sommet, tu reprends au sommet. On ne touche jamais le milieu.

Trois opérations suffisent :

  • empiler (push) : ajouter un élément au sommet ;
  • dépiler (pop) : retirer et renvoyer l'élément au sommet ;
  • sommet (peek) : regarder le sommet sans le retirer.

Toutes les trois sont en O(1) : elles agissent sur une seule extrémité, sans parcourir quoi que ce soit. Usages typiques : annuler/refaire (la dernière action est la première annulée), la pile d'appels (le dernier appel de fonction démarré est le premier à finir), l'évaluation d'expressions, et le retour arrière (backtracking) où l'on revient sur le dernier choix exploré.

Déroulé pas à pas d'une pile

Suivons une pile vide, opération par opération. La colonne de droite montre le contenu, sommet à droite.

OpérationRenvoiePile (sommet →)
empiler(A)–[A]
empiler(B)–[A, B]
empiler(C)–[A, B, C]
sommet()C[A, B, C]
dépiler()C[A, B]
dépiler()B[A]

Remarque l'ordre de sortie : C puis B, soit l'inverse de l'ordre d'entrée. C'est la signature du LIFO, et c'est exactement pourquoi une pile sert à inverser une séquence.

Cas réel — annuler/refaire, la pile d'appels et les files de tâches

Le Ctrl+Z de ton éditeur repose sur deux piles : chaque action va sur une pile « annuler » ; annuler dépile la dernière action et la pousse sur une pile « refaire ». La pile d'appels de JavaScript est elle aussi une pile : le dernier appel démarré est le premier à finir — et quand une récursion trop profonde la remplit, tu obtiens le fameux RangeError: Maximum call stack size exceeded. Côté file : la file de tâches de l'event loop, une file d'impression ou une file de messages (RabbitMQ, files de jobs) servent les éléments dans l'ordre d'arrivée — du FIFO pur, où utiliser shift() à grande échelle mettrait le service à genoux.

Implémentation avec un tableau

En JavaScript, un tableau fait déjà tout le travail : Array.push et Array.pop opèrent à la fin du tableau en O(1) amorti. On les enveloppe dans une classe pour figer l'interface et interdire les accès non conformes.

Le champ privé #items garantit qu'on ne peut pas contourner la discipline LIFO depuis l'extérieur.

Note

« O(1) amorti » pour push tient compte du redimensionnement occasionnel du tableau interne : la plupart des ajouts sont instantanés, et les rares réallocations se répartissent sur l'ensemble. En moyenne, chaque ajout reste constant.

Application : parenthèses équilibrées

Voici un problème classique résolu élégamment par une pile : une chaîne contient des parenthèses (), accolades {} et crochets []. Sont-ils correctement imbriqués ? L'idée : chaque fermeture doit correspondre à la dernière ouverture non encore fermée—du LIFO pur. On empile chaque ouvrant ; à chaque fermant, on dépile et on vérifie la correspondance.

Déroulé de "([)]" : ( → pile ["("] ; [ → ["(", "["] ; ) → on dépile "[" qui n'égale pas paires[")"] soit "(" → false. La pile a détecté le croisement.

Complexité : O(n) en temps (un seul passage sur la chaîne, chaque push/pop en O(1)) et O(n) en espace dans le pire cas (une chaîne entièrement composée d'ouvrants remplit la pile).

La file : FIFO

Une file suit le principe FIFO (First In, First Out) : le premier arrivé est le premier servi—comme une file d'attente à la caisse. Deux opérations :

  • enfiler : ajouter à la queue (l'arrière) ;
  • défiler : retirer et renvoyer l'élément de tête (l'avant).

On ajoute d'un côté et on retire de l'autre. Usages : files d'attente réelles, ordonnancement de tâches, et surtout le parcours en largeur (BFS, leçon 12) où l'on traite les nœuds dans l'ordre de découverte. L'objectif est que les deux opérations soient en O(1)—et c'est là que se cache un piège.

Le piège de la file naïve

La tentation est d'utiliser un tableau : push pour enfiler, shift pour défiler. Mais Array.shift() retire le premier élément, ce qui oblige le moteur à décaler tous les autres d'un cran vers la gauche : c'est O(n). Défiler n éléments coûte alors O(n²) au total. Inacceptable pour un BFS sur un grand graphe.

Plusieurs solutions existent : un tableau avec un index de tête, une liste chaînée avec référence de queue, ou deux piles. Voyons la version « tableau + index de tête », simple et rapide : on n'efface jamais en tête, on avance juste un curseur.

Déroulé : après trois enfiler, #items=[A,B,C], #tete=0. defiler() renvoie A et passe #tete à 1, sans décaler le reste. defiler() renvoie B, #tete=2. La tête « glisse » au lieu de tout déplacer.

Chaque enfiler et chaque defiler est en O(1) amorti : avancer un index est constant, et le compactage occasionnel (un slice en O(n) déclenché seulement quand la moitié du tableau est déjà consommée) se répartit sur les défilements. L'espace est O(n) pour n éléments présents.

Une autre façon de le faire

La même file, sans tableau : c'est la deuxième solution annoncée plus haut, la liste chaînée avec référence de queue. Chaque élément devient un petit objet qui pointe vers le suivant ; la file ne retient que deux bouts, #tete et #queue.

Ce qu'elle coûte
De la mémoire, et une ligne qu'on oublie facilement. Chaque élément traîne désormais un objet à deux champs : un million d'entiers occupent 38,2 Mo en liste chaînée contre 10,0 Mo avec le tableau et son index de tête (heapUsed relevé avant et après remplissage, ramasse-miettes forcé, une seule file par processus, trois essais au chiffre près), soit 3,8 fois plus. Le ramasse-miettes s'en ressent : sur un cycle complet — un million d'enfilements suivis d'un million de défilements — les deux structures se tiennent (médianes 12,2 ms pour le tableau, 13,1 ms pour la chaînée), mais le pire des cinq essais passe de 17,8 ms à 51,0 ms : un million de petits objets à ramasser, ça se paie. La ligne qu'on oublie, c'est this.#queue = null quand la file se vide : sans elle, #queue désigne encore un nœud que plus personne ne tient, le prochain enfiler l'accroche à ce fantôme, et la file annonce taille = 1 pendant que defiler() lève TypeError: Cannot read properties of null (reading 'suivant') — mesuré : 999 allers-retours fautifs sur 1 000 une fois la faute introduite. Enfin, on perd l'accès indexé : plus de #items[k] pour inspecter la file au débogueur, il faut la parcourir.
Ce qu'elle apporte
Elle n'a plus rien à compacter, donc plus rien à régler. Le tableau, lui, doit se recopier de temps en temps, et la règle qui décide quand tient dans deux constantes arbitraires du code publié plus haut : > 32 et * 2. Trois effets mesurés. (1) Le défilement seul est deux fois plus rapide : vider un million d'éléments prend 2,4 à 2,5 ms en liste chaînée contre 4,8 à 5,7 ms avec le tableau — l'écart, c'est le compactage. (2) Les pointes prévisibles disparaissent : le tableau paie 0,40 à 0,46 ms au 499 999e défilement et 0,21 ms au 749 999e, aux mêmes rangs sur trois essais — ce sont ses recopies. (3) Les deux files se comportent par ailleurs à l'identique : 200 000 opérations tirées au hasard, 0 écart sur la valeur défilée, la taille et le premier élément. ⚠ Mais ne va pas en conclure une garantie de latence : la plus grosse pointe n'est pas le compactage, c'est le ramasse-miettes, et il frappe les deux — jusqu'à 0,96 ms côté tableau et 0,79 ms côté chaînée, à des rangs qui changent d'un essai à l'autre. En JavaScript, aucune des deux structures ne promet un plafond par opération.
Quand la préférer
Quand les éléments sont gros : le surcoût d'un nœud ne dépend pas de ce qu'il contient, donc le facteur 3,8 mesuré ici sur des entiers fond dès que la valeur pèse quelques centaines d'octets. Quand tu veux une structure sans réglage, dont le coût ne dépend d'aucun seuil choisi à la main. Et quand il faudra retirer ailleurs qu'en tête — mais attention, pas avec ce code-ci : une liste simplement chaînée ne sait pas décrocher un nœud dont elle ne connaît pas le prédécesseur, et le retrouver coûte n/2 sauts en moyenne (mesuré : 499 999 sauts pour le nœud du milieu d'une file d'un million). Il faut un double chaînage pour que ce retrait devienne O(1), et c'est aussi ce qu'exige le deque de la section suivante : avec le simple chaînage écrit ici, retirer par la queue demande de reparcourir toute la liste, alors que le tableau le fait d'un pop(). Partout ailleurs, garde le tableau avec index de tête : il tient en moins de lignes, il est près de quatre fois plus compact, et sur un cycle complet il est même légèrement devant.

Analyse de complexité comparée

Récapitulons les coûts. Pour la file, « naïve » désigne la version push/shift à éviter.

Structure / opérationTempsEspace
Pile : empiler / dépiler / sommetO(1) amortiO(n)
File efficace : enfiler / défilerO(1) amortiO(n)
File naïve : défiler (shift)O(n)O(n)
Parenthèses équilibréesO(n)O(n)

Pourquoi O(1) plutôt que O(log n) ou O(n) ? Parce qu'on touche toujours une extrémité fixe : pas de recherche, pas de tri, pas de décalage. C'est précisément le bénéfice de l'accès restreint : en renonçant à l'accès arbitraire, on rend chaque opération autorisée triviale et constante.

Variantes et usages : le deque

Le deque (double-ended queue, file à deux bouts) généralise les deux : il permet d'ajouter et de retirer aux deux extrémités en O(1), servant donc à la fois de pile et de file selon le côté utilisé. Il sous-tend des algorithmes comme la fenêtre glissante de maximum.

Pièges fréquents

Piège fréquent

Utiliser arr.shift() comme « défiler » d'une file. C'est en O(n) car tous les éléments suivants sont décalés. Sur un BFS, ton parcours passe insidieusement de O(V+E) à O(V²). Utilise un index de tête, une liste chaînée ou deux piles.

Piège fréquent

Dépiler ou défiler une structure vide. Array.pop() et l'accès par index renvoient undefined silencieusement : tu confonds alors « pile vide » et « valeur undefined stockée ». Vérifie estVide() explicitement (ici on lève une erreur).

Piège fréquent

Confondre LIFO et FIFO. Demande-toi : « le prochain à sortir est-il le plus récent ou le plus ancien ? » Annuler/backtracking → pile (récent). Traiter dans l'ordre d'arrivée, BFS → file (ancien).

Pour aller plus loin

Pour aller plus loin

Une pile évalue une expression en notation polonaise inverse (RPN) : on empile les opérandes, et à chaque opérateur on dépile deux valeurs pour empiler le résultat—le tout en O(n). Explore aussi la file circulaire (buffer à taille fixe, utile en streaming) et la file de priorité (leçon 11), où l'on défile non pas le plus ancien mais le plus prioritaire—implémentée par un tas en O(log n).

Récap et vérification

  • Pile (LIFO) : dernier entré, premier sorti. push/pop/peek en O(1) amorti, espace O(n).
  • File (FIFO) : premier entré, premier sorti. enfiler/défiler en O(1) amorti avec index de tête, espace O(n).
  • Piège majeur : shift() est en O(n)—jamais pour une file performante.
  • Parenthèses équilibrées : application directe d'une pile, O(n) temps et espace.
  • Toujours gérer le cas vide avant de dépiler ou défiler.

Vérifie ta compréhension

  1. On enfile 1, 2, 3 puis on défile deux fois : quelles valeurs sortent, et dans quel ordre ? Et avec une pile ?
  2. Pourquoi shift() est-il en O(n) alors que pop() est en O(1) ? Qu'est-ce qui diffère entre les deux extrémités du tableau ?
  3. Pour vérifier la correspondance des balises HTML imbriquées, choisirais-tu une pile ou une file ? Pourquoi ?

Antisèche

Glossaire

Pile (stack)
Structure à accès restreint LIFO : on empile et on dépile au même bout, le sommet.
File (queue)
Structure à accès restreint FIFO : on enfile à la queue et on défile à la tête, deux extrémités distinctes.
LIFO
Last In, First Out : le dernier élément entré est le premier à sortir (pile).
FIFO
First In, First Out : le premier élément entré est le premier à sortir (file).
Sommet / tête
Le sommet est l'extrémité active d'une pile ; la tête est l'extrémité de sortie d'une file (la queue étant l'extrémité d'entrée).
Deque
Double-ended queue : file à deux bouts permettant ajout et retrait aux deux extrémités en O(1).
Coût amorti
Coût moyen par opération lissé sur une longue suite d'opérations, même si l'une d'elles est parfois plus chère (compactage ou transfert occasionnel).
Parenthèses équilibrées
Problème classique résolu par une pile : chaque fermant doit correspondre au dernier ouvrant non fermé, c'est-à-dire au sommet de la pile.
