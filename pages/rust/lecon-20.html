Sérialiser en JSON avec serde

~34 min Intermédiaire Structures (leçon 4) & crates (leçon 11) utiles

À la fin de cette leçon, tu sauras

  • ajouter serde et serde_json et dériver Serialize / Deserialize ;
  • convertir une struct en JSON (to_string) et l'inverse (from_str) ;
  • gérer les types imbriqués, Vec et Option ;
  • adapter le JSON avec les attributs rename, default, skip.
Sommaire de la leçon

Dès qu'un programme échange avec le monde — une API web, un fichier de configuration, un cache sur disque — il doit traduire ses valeurs vers un format de texte et les relire. En Rust, cette traduction s'appelle la sérialisation, et elle a un nom : serde (pour SERialize / DEserialize). Couplée à serde_json, elle transforme une struct en JSON, et du JSON en struct, presque sans code — juste une annotation.

Installer serde

serde vit dans deux crates : le cœur serde (avec l'option derive) et le format serde_json. On les ajoute au Cargo.toml.

La ligne features = ["derive"] active la macro qui écrira, à ta place, tout le code de conversion. Sans elle, il faudrait implémenter les traits à la main : fastidieux et source d'erreurs.

Le voyage aller-retour

Un seul #[derive(Serialize, Deserialize)] au-dessus d'une struct suffit : serde_json::to_string l'écrit en JSON, serde_json::from_str la reconstruit.

Remarque la magie du typage : from_str ne devine pas seul le type — c'est l'annotation let recu: Joueur qui le lui dit. Si le JSON manque un champ ou lui donne le mauvais type, from_str renvoie un Err détaillé plutôt qu'une valeur incohérente. La chaîne r#"…"# est un littéral brut : les guillemets à l'intérieur n'ont pas besoin d'être échappés.

Lisible pour un humain, et imbriqué

to_string_pretty indente le JSON : idéal pour un fichier de config qu'on relit. Et rien n'empêche d'imbriquer des structs, des Vec et des Option — serde suit la structure des types.

Un Option::None devient null ; un Some("Zoé") devient "Zoé". Côté lecture, un champ null ou absent redonne None sans effort — c'est le pont naturel entre l'absence en Rust et l'absence en JSON.

Adapter le JSON avec des attributs

Le JSON d'une API impose souvent ses conventions : camelCase, champs optionnels, valeurs par défaut. Les attributs #[serde(...)] ajustent la traduction sans changer les noms Rust.

rename_all traduit tous les champs d'un coup ; default comble un champ manquant à la lecture ; skip_serializing_if évite d'écrire les None. Ces trois-là couvrent 90 % des besoins d'interopérabilité avec des API existantes.

Du JSON sans struct : Value

Parfois la forme du JSON est inconnue ou variable. serde_json::Value représente n'importe quel document, et la macro json! en fabrique un à la volée.

Value est pratique pour explorer ou bricoler, mais on perd la vérification de types : v["ville"] compile même si le champ n'existe pas (il vaudra Null). Dès que la forme est stable, préfère une struct dédiée — plus sûre et plus lisible.

Cas réel — une réponse d'API en une ligne

Un service météo répond par du JSON : {"ville":"Nantes","tempC":14.2,"humidite":81}. Avant serde, il aurait fallu parcourir le texte à la main, extraire chaque champ, convertir les nombres — dix lignes fragiles. Avec serde, on décrit la forme attendue par une struct Meteo, et : let m: Meteo = serde_json::from_str(&corps)?;. En une ligne, on obtient une valeur fortement typée : m.temp_c est un f64, garanti. Et si l'API change un champ de type demain, l'erreur pointe l'endroit exact, à la désérialisation — pas trois écrans plus loin, au moment d'un calcul.

Astuce — décris le résultat, pas le parsing

La philosophie serde : tu déclares la forme de tes données (une struct), et la bibliothèque s'occupe du « comment ». Le même derive marche pour d'autres formats en changeant juste la crate : serde_yaml, toml, bincode… Écris tes types une fois, sérialise-les partout.

Erreur fréquente

Par défaut, les noms des champs Rust doivent correspondre exactement aux clés JSON. Un JSON en "userName" et un champ Rust user_name provoquent une erreur « missing field ». La solution n'est pas de renommer ton champ Rust en userName (non idiomatique) mais d'ajouter #[serde(rename_all = "camelCase")] ou #[serde(rename = "userName")].

Pour aller plus loin

Pour aller plus loin

serde dépasse largement JSON : serde_yaml, la crate toml (pour lire ton propre Cargo.toml !), bincode (binaire compact), csv. Explore #[serde(flatten)] pour aplatir une sous-struct, les enums balisés (#[serde(tag = "type")]) pour du polymorphisme, et serde_json::to_writer pour sérialiser directement dans un fichier sans passer par une String.

Antisèche

Glossaire

serde
Cadre de (dé)sérialisation de Rust : il définit les traits Serialize et Deserialize, indépendants du format.
Sérialisation
Traduire une valeur Rust en un format de texte ou binaire (ici JSON) pour la transmettre ou la stocker.
Désérialisation
L'opération inverse : reconstruire une valeur Rust typée à partir du texte reçu.
serde_json
Crate qui implémente le format JSON pour serde : to_string, from_str, Value, json!.
#[derive(...)]
Macro qui génère automatiquement le code d'un trait ; avec serde, elle écrit toutes les conversions.
Value
Type de serde_json représentant un document JSON quelconque, quand la forme n'est pas connue à l'avance.
Attribut #[serde(...)]
Annotation qui ajuste la traduction : rename, default, skip_serializing_if, flatten…
Littéral brut r#"…"#
Chaîne où \ et " ne sont pas interprétés : pratique pour écrire du JSON dans le code.

Récap et vérification

  • serde = Serialize + Deserialize ; serde_json = le format JSON.
  • Un #[derive(Serialize, Deserialize)] engendre les deux conversions.
  • to_string / to_string_pretty écrivent ; from_str relit (le type cible guide).
  • Vec, Option et structs imbriquées suivent naturellement ; None ⇄ null.
  • Les attributs rename_all, default, skip adaptent le JSON aux conventions d'une API.
