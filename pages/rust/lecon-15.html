Traits avancés et programmation générique

~36 min Avancé Leçon 14 recommandée

À la fin de cette leçon, tu sauras

  • savoir choisir entre type associé et paramètre générique, et entre dyn Trait et générique selon le dispatch ;
  • savoir écrire des bornes complexes (where, supertraits, bornes sur types associés) et des blanket implementations en respectant l'orphan rule ;
  • savoir exploiter les marker traits (Send, Sync, ?Sized) et surcharger des opérateurs via std::ops, From/Into, Deref ;
  • savoir réduire la répétition avec une macro déclarative macro_rules!.
Sommaire de la leçon

Tu connais déjà les traits comme contrats partagés et les génériques bornés. Cette leçon pousse le système de traits dans ses retranchements : c'est là que Rust devient à la fois très expressif et un peu intimidant. On va clarifier des choix de conception qui reviennent sans cesse : faut-il un type associé ou un paramètre ? Un dyn Trait ou un générique ? Comment réutiliser une implémentation pour tout un ensemble de types sans tout recopier ?

Chaque section répond à une de ces questions avec un exemple compilable par cargo build. À la fin, tu sauras lire la signature d'une API standard comme Iterator ou From et comprendre pourquoi elle est écrite ainsi.

Types associés ou paramètres génériques ?

Un type associé est un type fourni par l'implémentation, pas par l'appelant. Iterator en est l'exemple canonique : chaque itérateur produit un seul type d'élément, donc Item est un type associé, pas un paramètre.

Si Item avait été un paramètre générique (Iterator<Item>), un type aurait pu l'implémenter plusieurs fois (Iterator<u32> et Iterator<String>), forçant l'appelant à toujours annoter le type. Le type associé dit : « il n'y a qu'une bonne réponse par type ».

Note

Règle pratique : si l'appelant doit pouvoir choisir le type, utilise un paramètre générique (From<T>, qu'un type peut implémenter pour plusieurs sources). Si le type est déterminé par l'implémentation, utilise un type associé (Iterator::Item).

Trait objects (dyn) ou génériques ?

Un générique fn f<T: Trait>(x: T) est résolu à la compilation : c'est le dispatch statique (monomorphisation, zéro coût à l'exécution). Un Box<dyn Trait> est résolu à l'exécution via une table de méthodes (vtable) : c'est le dispatch dynamique, légèrement plus lent mais qui permet de mélanger des types derrière un même type statique.

Un point clé : un trait n'est utilisable en dyn que s'il est object-safe (on dit aussi « dyn-compatible » dans les versions récentes de Rust). En gros, ses méthodes ne doivent pas renvoyer Self par valeur ni être génériques, car la vtable ne peut pas représenter ces cas.

Blanket implementations et orphan rule

Une blanket impl implémente un trait pour tous les types qui satisfont une borne. La bibliothèque standard le fait massivement : par exemple impl<T: Display> ToString for T, c'est pourquoi .to_string() existe partout.

La contrepartie, c'est l'orphan rule (règle de cohérence) : tu ne peux implémenter un trait pour un type que si le trait ou le type t'appartient. Implémenter un trait externe pour un type externe est interdit, sinon deux crates pourraient fournir des impls contradictoires.

Astuce

Pour contourner l'orphan rule, emballe le type externe dans un newtype à toi : struct MonVec(Vec<i32>), puis implémente le trait sur MonVec. Le type t'appartient maintenant.

Marker traits : Send, Sync, Sized, ?Sized

Un marker trait n'a pas de méthode : il marque une propriété. Send (transférable entre threads) et Sync (partageable par référence entre threads) sont auto-implémentés par le compilateur ; tu les as croisés en concurrence. Sized signifie « taille connue à la compilation » et est ajouté implicitement à tout paramètre générique.

Surcharge d'opérateurs et conversions

Les opérateurs sont des traits de std::ops. Implémenter Add donne le sens de + ; Default fournit une valeur par défaut ; From définit une conversion (et Into en découle gratuitement) ; Deref permet à un type de se comporter comme une référence vers un autre.

Deref est puissant mais à manier avec prudence : il sert aux types « pointeur intelligent » (Box, Rc), pas à simuler de l'héritage entre structs métier.

Un cas réel : l'abstraction à coût nul des itérateurs

Cas réel

Le dispatch statique n'est pas un détail théorique : c'est la promesse « zero-cost abstraction » de Rust. Quand tu écris v.iter().map(|x| x * 2).filter(|x| x > &4).sum(), chaque adaptateur (map, filter) est un type générique distinct, monomorphisé puis inliné par le compilateur. Le code machine produit est identique à celui d'une boucle for écrite à la main : mêmes instructions, aucune allocation, aucun appel virtuel. La documentation officielle le démontre en comparant une chaîne d'itérateurs à une boucle manuelle — performances égales au cycle près. C'est pourquoi des outils comme ripgrep se permettent un style très haut niveau tout en rivalisant avec du C : l'expressivité des traits et des génériques ne coûte rien à l'exécution. Le revers de la médaille : la monomorphisation duplique le code pour chaque type concret, ce qui allonge la compilation et grossit le binaire — exactement le compromis inverse du dyn.

Pièges fréquents

Piège fréquent

Utiliser Box<dyn Trait> avec un trait non object-safe (méthode renvoyant Self ou générique) déclenche E0038. Si tu as besoin de dyn, retire ces méthodes du trait ou mets-les derrière une borne where Self: Sized : elles deviennent alors inaccessibles via dyn, mais le trait redevient object-safe.

  • Confondre type associé et générique : si tu écris trait T<X> alors qu'un seul X a du sens par type, tu forces des annotations inutiles. Préfère type X;.
  • Oublier une borne : appeler x.clone() dans un générique sans T: Clone donne E0599 (méthode introuvable). Le compilateur ne déduit pas les bornes, il faut les déclarer.
  • Choisir le mauvais dispatch : du dyn dans une boucle chaude alors qu'un générique suffirait coûte des appels virtuels inutiles ; à l'inverse, un générique sur un type figé à l'exécution ne compile pas. Le dyn sert quand la liste de types est ouverte ou hétérogène.

Antisèche

Glossaire

Type associé
Type fourni par l'implémentation d'un trait, pas par l'appelant (ex. Iterator::Item) : une seule « bonne réponse » par type.
Dispatch statique
Résolution des appels à la compilation via monomorphisation (une copie par type concret) : aucun coût à l'exécution.
Dispatch dynamique (dyn)
Résolution à l'exécution via une vtable (table de méthodes) : permet des collections hétérogènes, au prix d'un appel indirect.
Object safety
Propriété d'un trait utilisable derrière dyn : ses méthodes ne renvoient pas Self par valeur et ne sont pas génériques (sinon la vtable ne peut les représenter).
Blanket impl
Implémentation d'un trait pour tous les types satisfaisant une borne (impl<T: Display> ToString for T).
Orphan rule
Règle de cohérence : on n'implémente un trait pour un type que si le trait ou le type appartient à la crate. Contournement : le newtype.
Marker trait
Trait sans méthode qui marque une propriété (Send, Sync, Sized), souvent auto-implémenté par le compilateur.
macro_rules!
Macro déclarative : génère du code par motif à la compilation pour supprimer une répétition mécanique.

Récap et vérification

  • Un type associé fixe un type par implémentation ; un paramètre générique laisse l'appelant choisir.
  • dyn Trait = dispatch dynamique pour des collections hétérogènes, sous réserve d'object safety ; les génériques = dispatch statique sans coût.
  • where, supertraits et bornes sur types associés expriment des contraintes riches ; les blanket impls couvrent tous les types satisfaisant une borne.
  • L'orphan rule exige que le trait ou le type t'appartienne ; les marker traits (Send, Sync, Sized) décrivent des propriétés sans méthode.
  • std::ops, From/Into, Default, Deref intègrent tes types au langage ; macro_rules! supprime la répétition mécanique.
