Module 07 · Rust au quotidien — Leçon 21

Écrire une application en ligne de commande

~33 min Intermédiaire Entrées/sorties (leçon 19) utile

À la fin de cette leçon, tu sauras

  • lire les arguments à la main avec std::env::args ;
  • renvoyer un code de sortie et écrire les erreurs sur stderr ;
  • lire l'entrée standard (stdin) pour t'enchaîner dans un pipe ;
  • analyser les arguments proprement avec clap et son mode derive.
Sommaire de la leçon

Rust brille pour écrire des outils en ligne de commande — rapides, autonomes (un seul binaire), sans dépendances à installer chez l'utilisateur. Beaucoup des remplaçants modernes des classiques Unix (ripgrep pour grep, bat pour cat, fd pour find) sont écrits en Rust. Voyons comment lire des arguments, dialoguer avec l'entrée/sortie standard, et signaler le succès ou l'échec — d'abord à la main, puis avec l'outil de référence, clap.

Lire les arguments à la main

std::env::args renvoie un itérateur sur les arguments. Attention : args[0] est le nom du programme ; les vrais arguments commencent à l'indice 1.

On passe par args.get(1) (qui renvoie une Option) plutôt que args[1] : si l'utilisateur ne fournit rien, get donne None au lieu de paniquer. Le .map(|s| s.as_str()) convertit l'Option<&String> en Option<&str> pour pouvoir comparer aux littéraux dans le match.

Codes de sortie et flux d'erreur

Un outil en ligne de commande communique son résultat de deux façons : son code de sortie (0 = succès, ≠0 = échec) et la séparation stdout / stderr. Le résultat exploitable va sur stdout (println!) ; les messages et erreurs vont sur stderr (eprintln!).

Le shell et les scripts s'appuient sur ce code : mon_outil && suite n'exécute suite que si mon_outil a renvoyé 0. Alternative plus idiomatique : faire renvoyer Result à main (leçon 19) — un Err produit automatiquement un code non nul.

Lire l'entrée standard

Un bon outil sait aussi lire stdin : cela permet de l'enchaîner dans un pipe. Ici, un filtre qui met chaque ligne reçue en majuscules.

entree.lock() prend un verrou sur stdin (plus efficace pour lire beaucoup de lignes), puis .lines() itère comme pour un fichier. Ce petit programme s'insère dans une chaîne : cat notes.txt | ./crie | wc -l.

clap : l'analyseur d'arguments

Dès qu'il y a plusieurs options, écrire l'analyse à la main devient pénible et bogué. clap le fait pour toi : tu décris tes arguments dans une struct, et clap génère l'analyse, la validation, --help et --version.

Chaque commentaire /// devient un texte d'aide ; #[arg(short, long)] crée -r et --repete ; default_value_t fixe la valeur par défaut. Args::parse() fait tout : si l'utilisateur tape --help, clap affiche une aide soignée et quitte ; s'il oublie nom, clap affiche l'erreur et sort avec un code non nul. Tu n'écris que la déclaration.

Cas réel — pourquoi les outils Rust s'enchaînent si bien

Les commandes Unix (grep, wc, sort) partagent une discipline : lire stdin ou des fichiers en argument, écrire le résultat sur stdout, les erreurs sur stderr, renvoyer 0 si tout va bien. Un outil Rust qui respecte cette convention se branche dans un pipe : cat acces.log | mon_filtre | wc -l. C'est précisément ce qui a fait le succès de ripgrep : même interface que grep, mais bâti sur des lectures bufferisées et du parallélisme sûr. La leçon : une CLI de qualité, ce n'est pas mille options ; c'est respecter les conventions pour se composer avec le reste du système.

Astuce — déclare, ne parse pas

Avec clap en mode derive, la struct est la spécification : types, valeurs par défaut, aide, tout est au même endroit. Ajouter une option = ajouter un champ. Le typage fait le reste : un champ u8 refuse automatiquement --repete abc avec un message clair, sans une ligne de validation de ta part.

Erreur fréquente

env::args().nth(0) (ou args[0]) n'est pas le premier argument utilisateur : c'est le nom du programme. Le premier vrai argument est à l'indice 1. Et n'indexe jamais args[1] sans vérifier sa présence : sur une commande sans argument, ça panique. Utilise args.get(1), ou laisse clap gérer.

Glossaire

CLI
Command-Line Interface : un programme piloté par des arguments texte dans un terminal.
Argument positionnel
Valeur identifiée par sa place sur la ligne (ex. le nom de fichier), sans nom d'option.
Option (flag)
Argument nommé comme --repete 3 ou -v ; peut porter une valeur ou être un simple interrupteur.
std::env::args
Itérateur des arguments du programme ; l'élément 0 est le nom du binaire.
Code de sortie
Entier renvoyé au système à la fin : 0 = succès, tout autre = échec (lu par le shell et la CI).
stdin / stdout / stderr
Les trois flux standard : entrée, sortie du résultat, sortie des erreurs.
Pipe
Connexion du stdout d'un programme au stdin d'un autre (a | b), pour composer des outils.
clap
Crate de référence pour analyser les arguments ; en mode derive, une struct décrit toute l'interface.

Récap et vérification

  • env::args donne les arguments ; args[0] est le nom du programme, les vrais commencent à 1.
  • Utilise args.get(1) (une Option) pour ne pas paniquer si l'argument manque.
  • Résultat sur stdout (println!), messages sur stderr (eprintln!) ; code de sortie 0 / ≠0.
  • Lire stdin (io::stdin().lock().lines()) rend l'outil composable dans un pipe.
  • Au-delà de deux options : clap + #[derive(Parser)] — la struct décrit toute l'interface.
