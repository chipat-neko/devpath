La concurrence sans peur

~32 min Avancé Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • Savoir lancer des thread::spawn, récupérer leur résultat avec join et transférer la possession via move ;
  • Savoir communiquer entre threads avec un channel mpsc et partager un état avec Arc<Mutex<T>> ;
  • Savoir pourquoi les traits marqueurs Send et Sync garantissent l'absence de data race à la compilation ;
  • Savoir reconnaître les pièges (oubli de move, deadlock, Rc au lieu d'Arc) et situer async/await avec Tokio.
Sommaire de la leçon

En C, écrire du code multithread, c'est marcher sur un champ de mines : un accès concurrent oublié, et tu obtiens une data race — un bug qui n'apparaît qu'une fois sur mille, en production, le vendredi soir. Rust appelle sa réponse la fearless concurrency : la concurrence sans peur. L'idée est aussi belle qu'efficace : les mêmes règles de possession qui te protègent en mono-thread protègent aussi tes threads. Si ton code compile, il est exempt de data race. Garanti par le compilateur.

Ce n'est pas un slogan marketing : c'est une propriété du système de types. Dans cette leçon, on va lancer des threads, les faire dialoguer par messages, partager un état avec un verrou, et comprendre la mécanique des traits Send et Sync qui rend tout cela possible. Le borrow checker, ton vieil adversaire, devient ici ton meilleur allié.

Lancer un thread avec thread::spawn et join

Un thread se crée avec thread::spawn, à qui tu passes une closure. La fonction renvoie un JoinHandle ; appeler .join() dessus attend la fin du thread et récupère sa valeur de retour, emballée dans un Result.

join renvoie un Result parce que le thread peut paniquer : dans ce cas tu obtiens un Err plutôt qu'un crash silencieux. Sans join, le thread principal pourrait se terminer avant le thread enfant, qui serait alors brutalement interrompu.

Transférer la possession : le mot-clé move

Un thread peut vivre plus longtemps que la fonction qui l'a lancé. Si la closure emprunte une variable locale, Rust ne peut pas garantir que cette variable existera encore : il refuse de compiler. La solution est move, qui transfère la possession des variables capturées au thread.

Piège fréquent

Sans move, le compilateur affiche : closure may outlive the current function, but it borrows `donnees` et suggère help: to force the closure to take ownership ... use the `move` keyword. Le message te donne la correction exacte. Lis-le, ne le combats pas.

Pourquoi le partage est dangereux — et comment Rust l'empêche

Une data race survient quand deux threads accèdent à la même donnée, qu'au moins un écrit, sans synchronisation. En C, le compilateur t'y autorise sans broncher. En Rust, c'est impossible en code sûr. Tente de partager une variable mutable par référence entre deux threads :

Les règles d'emprunt (un seul accès mutable, ou plusieurs accès partagés en lecture) s'appliquent à travers les threads. Pour partager légitimement, il faut des outils dédiés : les channels, ou Arc + Mutex.

Communiquer par messages : les channels mpsc

Une philosophie répandue : « ne communiquez pas en partageant la mémoire ; partagez la mémoire en communiquant ». Rust fournit std::sync::mpsc — multiple producer, single consumer. Tu obtiens un émetteur tx (transmitter) et un récepteur rx (receiver) ; tx.send envoie, rx.recv reçoit (en bloquant jusqu'à l'arrivée d'un message).

La possession voyage avec le message : après tx.send(valeur), tu ne peux plus utiliser valeur dans l'émetteur. Là encore, aucune donnée n'est partagée — elle est déplacée, donc aucune course possible. Pour plusieurs producteurs, clone tx avec tx.clone().

État partagé : Mutex<T> et Arc<T>

Parfois, plusieurs threads doivent vraiment partager la même donnée mutable. Il faut alors deux ingrédients :

  • Mutex<T> (verrou d'exclusion mutuelle) : un seul thread accède à la donnée à la fois. lock() renvoie un garde ; tant qu'il vit, tu as l'accès exclusif. À sa libération (fin de portée), le verrou se relâche automatiquement.
  • Arc<T> (Atomically Reference Counted) : un compteur de références atomique qui permet à plusieurs threads de posséder ensemble la même valeur. C'est la version thread-safe de Rc<T>.

On les combine très souvent en Arc<Mutex<T>> : Arc pour partager la possession entre threads, Mutex pour synchroniser les accès.

Arc::clone ne copie pas les données : il incrémente seulement le compteur de références. lock().unwrap() peut renvoyer une erreur si un autre thread a paniqué en tenant le verrou (verrou « empoisonné ») — c'est une sécurité de plus.

Astuce

Garde un verrou le moins longtemps possible. Pour relâcher tôt, ouvre un bloc { ... } autour du lock(), ou appelle drop(garde) explicitement avant un calcul long. Un verrou tenu = les autres threads attendent.

La magie de la sûreté : les traits Send et Sync

Comment le compilateur sait-il ce qui peut traverser un thread ? Grâce à deux traits marqueurs (sans méthode), appliqués automatiquement :

  • Send : un type est Send si sa possession peut être transférée vers un autre thread. Presque tout l'est ; Rc<T> ne l'est pas (son compteur n'est pas atomique).
  • Sync : un type est Sync si une référence partagée &T peut être utilisée depuis plusieurs threads en sécurité. Mutex<T> est Sync ; RefCell<T> ne l'est pas.

Le rapprochement avec la possession

Prends du recul. Tu n'as appris aucune règle nouvelle de sûreté dans cette leçon : ce sont les principes de possession et d'emprunt vus plus tôt, appliqués au-delà d'un seul thread. « Une seule référence mutable, ou plusieurs partagées » empêche aussi bien le double-free en mono-thread que la data race en multi-thread. Send et Sync sont simplement la formalisation de « cette donnée peut franchir une frontière de thread ». Le système qui t'agaçait au début est exactement celui qui te permet aujourd'hui d'écrire du parallélisme sans crainte.

async/await en survol

Les threads conviennent au calcul. Pour gérer des milliers de connexions réseau qui passent leur temps à attendre, on préfère l'asynchrone : une fonction async renvoie une Future (une tâche à terminer), et .await suspend l'exécution sans bloquer le thread. Rust fournit la syntaxe ; l'exécuteur qui fait tourner les futures vient d'une bibliothèque externe, le plus souvent Tokio.

La beauté : Send, Sync et la possession protègent aussi le code async. Les mêmes garanties, un modèle d'exécution différent. On approfondira async dans un cours dédié.

Pièges fréquents

Piège fréquent

Oublier move dans la closure du thread : le compilateur le réclame et te donne la correction. Utiliser Rc au lieu d'Arc : Rc n'est pas Send, il ne traverse pas les threads. Deadlock : deux threads prennent deux verrous dans l'ordre inverse et s'attendent mutuellement — verrouille toujours dans le même ordre. Tenir un verrou trop longtemps : tout le reste attend ; relâche-le au plus tôt. Oublier join : le thread principal peut finir avant les enfants et les couper net.

Pour aller plus loin

Explore Tokio et l'écosystème async pour les serveurs ; rayon pour le parallélisme de données (un iter() devient par_iter() et c'est tout) ; les atomics (AtomicUsize) pour des compteurs sans verrou ; crossbeam pour des channels et structures concurrentes avancées ; et les détails de Send/Sync et du code unsafe sous-jacent.

Un cas réel : Firefox Quantum, la concurrence sans peur

Cas réel

L'expression « fearless concurrency » n'est pas qu'un slogan. Mozilla a passé près d'une décennie à tenter de paralléliser le moteur de style CSS de Firefox en C++ : à chaque essai, les data races rendaient le code trop instable pour la production, et les tentatives étaient abandonnées. L'équipe a alors réécrit ce moteur en Rust, sous le nom de Stylo. Cette fois, le compilateur garantissait l'absence de course à la compilation — impossible de partager une donnée mutable sans Arc<Mutex<…>> ou passage de message. Résultat : Stylo a livré en 2017, dans Firefox 57 « Quantum », un moteur CSS parallèle exploitant tous les cœurs de la machine — là où quinze ans de C++ avaient échoué. Le même système d'emprunt qui « agace au début » a rendu sûr un parallélisme que des experts n'avaient pas su sécuriser autrement.

Antisèche

Glossaire

Thread (spawn / join)
Fil d'exécution parallèle : thread::spawn le lance, join attend sa fin et récupère son résultat.
Data race
Accès concurrent non synchronisé à une même donnée, dont au moins un en écriture ; impossible en Rust sûr, refusé à la compilation.
Channel mpsc
Canal multiple producer, single consumer : on envoie par tx.send, on reçoit par rx.recv ; la valeur est déplacée, jamais partagée.
Mutex<T>
Verrou d'exclusion mutuelle : lock() donne un accès exclusif à la donnée, relâché automatiquement en fin de portée.
Arc<T>
Atomically Reference Counted : compteur de références atomique qui laisse plusieurs threads posséder ensemble la même valeur (version thread-safe de Rc).
Send / Sync
Traits marqueurs auto-déduits : Send = la valeur peut être transférée entre threads ; Sync = une référence &T peut être partagée entre threads.
Deadlock
Interblocage : deux threads prennent deux verrous dans l'ordre inverse et s'attendent mutuellement pour toujours. Parade : verrouiller toujours dans le même ordre.
async / .await
Modèle asynchrone : une fonction async renvoie une Future, et .await suspend sans bloquer le thread. L'exécuteur (souvent Tokio) fait avancer les futures.

Récap et vérification

  • thread::spawn lance un thread ; join() attend sa fin et récupère son Result.
  • move transfère la possession des variables capturées au thread.
  • Les data races sont impossibles en Rust sûr : le borrow checker s'applique à travers les threads.
  • Les channels mpsc communiquent par messages (tx.send / rx.recv) ; la possession voyage avec le message.
  • Arc<Mutex<T>> partage un état mutable : Arc pour la possession partagée, Mutex pour la synchronisation.
  • Send (transférable entre threads) et Sync (référence partageable) permettent au compilateur de garantir la sûreté.
