Module 04 · Rust en pratique — Leçon 13

Construire un projet et aller plus loin

~34 min Avancé Leçon 12 recommandée

À la fin de cette leçon, tu sauras

  • savoir structurer un petit outil en ligne de commande qui lit des arguments et un fichier avec gestion d'erreur par Result ;
  • savoir écrire et lancer des tests avec #[test], assert_eq! et cargo test ;
  • savoir choisir entre Box<T>, Rc<T> et RefCell<T> selon le besoin ;
  • savoir documenter, lancer clippy/fmt et situer l'écosystème pour aller plus loin.
Sommaire de la leçon

Tu as appris la possession, les emprunts, les traits, les énumérations et la gestion d'erreur. Il est temps d'assembler tout cela dans un vrai projet : un petit outil en ligne de commande, testé, documenté, et propre. Cette dernière leçon te montre comment passer d'un fichier main.rs bricolé à un projet que tu pourrais publier — puis ouvre les portes de l'écosystème Rust.

Le fil rouge : un outil wordcount qui lit un fichier passé en argument et compte ses lignes, ses mots et ses octets. Simple, mais l'occasion de voir les arguments, la lecture de fichier, les tests et les bonnes pratiques au même endroit.

1. Un projet concret : lire des arguments et un fichier

On part de zéro avec cargo new wordcount. Les arguments du programme arrivent via std::env::args() — le premier élément est toujours le nom du binaire, on prend donc le deuxième avec nth(1). Toute opération qui peut échouer (argument manquant, fichier introuvable) remonte un Result : la fonction main peut elle-même renvoyer Result<(), Box<dyn Error>> pour propager proprement.

Le -- sépare les arguments de cargo de ceux de ton programme.

Note

texte.len() renvoie le nombre d'octets UTF-8, pas de caractères. Un texte ASCII donne le même résultat, mais un caractère accentué comme « é » compte pour 2 octets. Pour compter des caractères, utilise texte.chars().count().

Astuce

Pour un vrai CLI avec sous-commandes, options et --help automatique, ajoute la crate clap avec ses dérivations : tu décris une structure, clap parse pour toi. std::env suffit pour les cas simples.

2. Les tests intégrés

Rust intègre les tests dans le langage. Une fonction annotée #[test] est compilée et lancée par cargo test. Les tests unitaires vivent dans le même fichier que le code, dans un module tests marqué #[cfg(test)] — ce cfg(test) garantit que ce code n'est compilé QUE pendant les tests, jamais dans le binaire final.

Les tests d'intégration, eux, vivent dans un dossier tests/ à la racine : chaque fichier y est compilé comme un crate séparé qui utilise ta bibliothèque de l'extérieur, exactement comme un utilisateur le ferait. Pratique pour tester l'API publique de bout en bout.

Note

assert_eq!(a, b) affiche les deux valeurs en cas d'échec ; assert!(cond) teste un booléen. Pour vérifier qu'un code panique comme prévu, ajoute #[should_panic] sur le test.

3. Les smart pointers : Box, Rc, RefCell

Un smart pointer est un type qui se comporte comme une référence mais ajoute un comportement. Trois reviennent sans cesse :

  • Box<T> — alloue T sur le tas. Indispensable pour les types récursifs (une valeur ne peut pas se contenir elle-même ; un Box a une taille connue).
  • Rc<T> — Reference Counted : plusieurs propriétaires d'une même donnée en mono-thread. La donnée est libérée quand le dernier Rc disparaît.
  • RefCell<T> — mutabilité intérieure : tu peux muter à travers une référence partagée, les règles d'emprunt étant vérifiées à l'exécution (panique si tu violes la règle, au lieu d'une erreur de compilation).

Quand utiliser quoi ? Box pour posséder sur le tas ou casser une récursion. Rc quand plusieurs parties lisent la même donnée. Rc<RefCell<T>> quand elles doivent aussi la muter — mais c'est souvent le signe qu'un autre design (passer &mut, repenser la propriété) serait plus clair.

4. Documentation, fmt et clippy en routine

Les commentaires /// placés au-dessus d'un élément sont de la documentation : cargo doc --open génère un site HTML navigable. Mieux : les blocs de code dans la doc sont exécutés comme tests par cargo test (les doctests), donc ta doc ne ment jamais.

Lance fmt et clippy avant chaque commit : c'est gratuit et ça te rend meilleur.

5. Bonnes pratiques : écouter le compilateur

Rust a une réputation de compilateur exigeant. Le secret : ses messages sont pédagogiques. Quand il refuse ton code, il explique pourquoi et propose souvent le correctif exact. Ne cherche pas à le contourner — lis-le, comprends-le, le combat avec le borrow checker se gagne en l'écoutant. 6. L'écosystème et la suite

Le cœur du langage est maîtrisé ; voici où Rust brille au-delà :

  • serde — sérialisation/désérialisation JSON, TOML, etc. via dérivation (#[derive(Serialize, Deserialize)]).
  • Tokio — le runtime asynchrone de référence ; async/.await pour des milliers de connexions concurrentes sans threads bloquants.
  • Axum et Actix — frameworks web rapides et typés, bâtis sur Tokio.
  • WebAssembly via wasm-bindgen — compiler du Rust pour le navigateur.
  • Embarqué avec no_std — Rust sans bibliothèque standard, pour microcontrôleurs.

7. Récap du parcours

Tu es parti des variables et des types, tu as franchi la possession et les emprunts, dompté les durées de vie, structuré avec struct/enum et les traits, géré l'absence et l'erreur avec Option et Result. Aujourd'hui tu sais empaqueter tout cela dans un projet testé et documenté. Rust te donne la sûreté mémoire sans ramasse-miettes, vérifiée à la compilation — un atout rare.

Un cas réel : ripgrep, un outil CLI qui a détrôné grep

Cas réel

Le petit wordcount de cette leçon n'est pas un jouet isolé : c'est exactement la forme des grands outils en ligne de commande écrits en Rust. Le plus célèbre est ripgrep (rg), un chercheur de texte récursif créé par Andrew Gallant. Bâti sur les mêmes briques que ta leçon — std::env pour les arguments (avec clap pour les options), lecture de fichiers, Result pour les erreurs, et une batterie de tests lancés par cargo test — il est devenu plus rapide que grep tout en respectant les .gitignore par défaut. Résultat : ripgrep est le moteur de la recherche « dans tous les fichiers » de VS Code, donc installé de fait sur des dizaines de millions de machines de développeurs. Même recette que ton projet : un binaire unique, sans dépendance d'exécution, compilé pour Windows, macOS et Linux. Ton wordcount et rg partagent le même squelette ; seule l'ambition diffère.

Pièges fréquents

Piège fréquent

Ne pas écrire de tests : cargo test est gratuit et intégré, profites-en dès la première fonction. Abuser de unwrap() : chaque unwrap est une panique potentielle en production — préfère ?. Mettre Rc<RefCell<T>> partout : si tu en sèmes dans tout le code, repense la conception, l'emprunt simple suffit souvent. Ignorer clippy : il t'apprend les idiomes (par exemple, il te dira de remplacer assert_eq!(x, true) par assert!(x)). Vouloir « combattre » le compilateur : écoute son message, il a presque toujours raison.

Pour aller plus loin

Glossaire

Cargo
Le gestionnaire de projet et de paquets de Rust : cargo new, build, run, test, doc. Il lit le manifeste Cargo.toml.
Crate
Unité de compilation et de distribution en Rust : soit un binaire (main.rs), soit une bibliothèque (lib.rs). Les crates externes viennent de crates.io.
#[cfg(test)]
Attribut de compilation conditionnelle : le module de tests n'est compilé que pendant cargo test, jamais dans le binaire final.
Doctest
Bloc de code placé dans un commentaire de doc /// et exécuté comme un test par cargo test : la documentation ne peut pas mentir.
Box<T>
Smart pointer qui alloue T sur le tas ; indispensable pour les types récursifs, dont il fixe la taille.
Rc<T> / RefCell<T>
Rc = plusieurs propriétaires en mono-thread (compteur de références) ; RefCell = mutabilité intérieure, emprunts vérifiés à l'exécution.
clippy / fmt
cargo clippy = le linter officiel, qui repère les tournures non idiomatiques ; cargo fmt reformate le code selon le style standard.
Smart pointer
Type qui se comporte comme une référence mais ajoute un comportement : allocation sur le tas, comptage de références ou mutabilité intérieure.

Récap et vérification

  • std::env::args() lit les arguments ; fs::read_to_string lit un fichier ; ? propage les erreurs jusqu'à main.
  • #[test] + cargo test pour les tests ; unitaires dans #[cfg(test)] mod tests, d'intégration dans tests/.
  • Box<T> (tas, récursion), Rc<T> (partage mono-thread), RefCell<T> (mutabilité intérieure vérifiée à l'exécution).
  • /// + cargo doc documentent ; cargo fmt et cargo clippy gardent le code propre et idiomatique.
  • Écoute le compilateur, renvoie des Result, évite unwrap en prod, garde des fonctions petites.
