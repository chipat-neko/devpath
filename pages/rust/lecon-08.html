Module 03 · Rust idiomatique — Leçon 08

Traits et génériques

~37 min Avancé Leçon 7 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire des fonctions et types génériques et comprendre la monomorphisation ;
  • savoir définir un trait, l'implémenter et utiliser une borne de trait pour contraindre un générique ;
  • savoir dériver les traits standard (Debug, Clone, PartialEq) et écrire des méthodes par défaut ;
  • savoir choisir entre dispatch statique (impl Trait) et dynamique (Box<dyn Trait>) et utiliser From/Into.
Sommaire de la leçon

Jusqu'ici, tu as écrit du code pour des types précis : une fonction qui prend un i32, une struct qui contient un String. Mais répéter la même logique pour chaque type, c'est fastidieux et source d'erreurs. Rust te donne deux outils complémentaires pour abstraire sans rien sacrifier à la performance ni à la sûreté : les génériques (du code paramétré par un type) et les traits (un contrat de comportement, l'équivalent des interfaces d'autres langages).

La promesse de Rust ici est inhabituelle : cette abstraction est gratuite à l'exécution (zero-cost abstraction). Le compilateur génère du code spécialisé aussi rapide que si tu l'avais écrit à la main, tout en vérifiant à la compilation que chaque type respecte bien le contrat. Tu vas voir que le compilateur reste ton meilleur allié : ses messages t'indiquent presque toujours la borne de trait qui manque.

1. Les génériques : du code paramétré par un type

Un paramètre générique, noté par convention T, est un type que tu ne fixes pas à l'écriture mais que l'appelant choisit. On le déclare entre chevrons après le nom de la fonction.

Les types aussi se paramètrent. Voici une paire générique : elle peut contenir deux i32, deux String, ou n'importe quoi d'autre.

Note

Le <T> juste après impl déclare le paramètre ; celui après Paire l'utilise. Les deux sont nécessaires : impl<T> Paire<T> se lit « pour tout type T, voici les méthodes de Paire<T> ».

Comment Rust fait-il pour être rapide ? Par monomorphisation : à la compilation, il duplique le code générique en versions concrètes pour chaque type réellement utilisé. premier::<i32> et premier::<&str> deviennent deux fonctions distinctes et spécialisées. Aucun coût à l'exécution, contrairement aux génériques de Java qui passent par l'effacement de type.

2. Les traits : un contrat de comportement

Un trait décrit un ensemble de méthodes qu'un type s'engage à fournir. C'est l'équivalent d'une interface. On définit le contrat, puis on l'implémente pour chaque type concerné.

Deux types très différents partagent maintenant une capacité commune : on peut appeler .aire() sur l'un comme sur l'autre. Le trait est le point d'ancrage qui rend ce code uniforme.

3. Les bornes de trait : contraindre un générique

Un générique pur ne sait rien faire avec son T : pour le compilateur, T pourrait être n'importe quoi, donc tenter de l'additionner ou de l'afficher échoue. Une borne de trait (trait bound) promet que T implémente tel trait, ce qui débloque les méthodes correspondantes.

4. Les traits dérivés et les traits standard

Beaucoup de traits courants ont une implémentation évidente que le compilateur peut écrire pour toi avec l'attribut #[derive(...)]. Plus besoin de coder à la main l'égalité ou l'affichage de débogage.

Quelques traits standard à connaître : Debug (affichage {:?} pour développer), Display (affichage {} destiné à l'utilisateur, à écrire à la main), Clone (copie explicite en profondeur), PartialEq (égalité ==), Iterator (parcours élément par élément). Contrairement à Debug, Display ne se dérive pas : tu décides toi-même du format lisible.

Piège fréquent

Vouloir println!("{:?}", x) sur un type qui ne dérive pas Debug donne l'erreur « Point doesn't implement Debug ». La correction est presque toujours d'ajouter #[derive(Debug)] sur la struct.

5. Les méthodes par défaut dans un trait

Un trait peut fournir une implémentation par défaut de certaines méthodes. Les types qui l'implémentent en héritent gratuitement, mais peuvent la redéfinir. C'est idéal pour bâtir du comportement à partir de quelques méthodes de base.

6. Dispatch statique vs dispatch dynamique

Quand une fonction accepte « quelque chose qui implémente Aire », deux stratégies existent. Le dispatch statique via génériques ou impl Trait : le compilateur connaît le type exact, monomorphise, et l'appel est aussi direct qu'un appel normal — rapide, mais le type est figé à la compilation.

Le dispatch dynamique via &dyn Trait ou Box<dyn Trait> : le type concret n'est résolu qu'à l'exécution, par une table de méthodes (vtable). Léger surcoût d'indirection, mais cela permet de mélanger plusieurs types dans une même collection.

Astuce

Règle simple : préfère le générique (statique) par défaut, plus rapide. Passe à dyn uniquement quand tu as besoin de stocker des types différents ensemble, par exemple un Vec<Box<dyn Aire>>.

7. Les traits de conversion : From et Into

Les traits standard From et Into définissent des conversions idiomatiques entre types. Implémente From : tu obtiens Into automatiquement, dans l'autre sens et gratuitement.

Pièges fréquents

  • Oublier la borne de trait. « method not found » ou « operator cannot be applied » signifie presque toujours qu'il manque une contrainte (T: Display, T: PartialOrd…). Lis le help: du compilateur, il te donne la borne exacte.
  • Confondre statique et dynamique. &dyn Trait a un coût d'indirection et autorise l'hétérogénéité ; le générique est figé mais sans surcoût. Choisis selon le besoin, pas par réflexe.
  • Ne pas dériver le trait requis. {:?} exige Debug, == exige PartialEq, .clone() exige Clone. Ajoute le #[derive(...)] manquant.
  • La règle d'orphelin (orphan rule). Tu ne peux pas implémenter un trait externe (comme Display) sur un type externe (comme Vec) : au moins le trait ou le type doit t'appartenir. Sinon, enveloppe le type externe dans une struct à toi (motif « newtype »).
  • Sur-généraliser. Rendre tout générique « au cas où » alourdit le code et les messages d'erreur. Abstrais quand au moins deux types réels le justifient.

Pour aller plus loin

Pour aller plus loin

Explore les objets de trait (dyn) et leurs limites de « dyn-compatibilité », les types associés (comme type Item dans Iterator, plus élégants qu'un générique de trait), les supertraits (un trait qui en requiert un autre, ex. trait Aire: Debug), et l'écriture de tes propres Iterator. Le combat avec le borrow checker laisse alors place à un autre plaisir : composer des abstractions vérifiées à la compilation.

Un cas réel : Serde, trois idées réunies

Cas réel

Presque tous les projets Rust dépendent de Serde, la bibliothèque de (dé)sérialisation. Son interface tient en deux traits — Serialize et Deserialize — et une ligne, #[derive(Serialize, Deserialize)], suffit à les implémenter pour tes struct. Le compilateur génère alors, par monomorphisation, un code de conversion JSON, YAML ou autre spécialisé pour chaque type, aussi rapide qu'un analyseur écrit à la main — sans réflexion à l'exécution comme en Java ou en Python. Mieux : si un champ ne correspond pas, l'erreur surgit à la compilation, pas en production. Serde réunit les trois idées de cette leçon : un contrat (trait), du code paramétré (générique) et une spécialisation gratuite (monomorphisation).

Antisèche

Glossaire

Générique
Code paramétré par un type T non fixé à l'écriture ; l'appelant choisit le type concret.
Trait
Contrat de comportement (un ensemble de méthodes) qu'un type s'engage à fournir ; l'équivalent Rust d'une interface.
Borne de trait (trait bound)
Contrainte T: Trait (ou clause where) qui promet que T implémente un trait et débloque ses méthodes.
Monomorphisation
Duplication, à la compilation, d'un code générique en une version concrète par type utilisé : l'abstraction devient zero-cost.
#[derive(…)]
Attribut qui fait générer par le compilateur l'implémentation de traits standard (Debug, Clone, PartialEq…).
Dispatch statique / dynamique
Statique : type connu à la compilation, appel direct (impl Trait). Dynamique : type résolu à l'exécution via une vtable (dyn Trait).
Objet de trait (dyn Trait)
Valeur manipulée par son trait plutôt que par son type concret ; permet des collections hétérogènes (Vec<Box<dyn Trait>>).
From / Into
Traits de conversion idiomatiques : implémenter From<A> for B fournit gratuitement a.into() vers B.

Récap et vérification

  • Les génériques (fn f<T>, struct S<T>) factorisent du code par type ; la monomorphisation les rend gratuits à l'exécution.
  • Un trait est un contrat de comportement ; on l'implémente type par type.
  • Une borne de trait (T: Display ou clause where) débloque les méthodes attendues sur un générique.
  • #[derive(...)] écrit pour toi Debug, Clone, PartialEq ; Display reste à coder à la main.
  • Les méthodes par défaut donnent du comportement gratuit, redéfinissable.
  • Dispatch statique (impl Trait, rapide) vs dynamique (Box<dyn Trait>, hétérogène).
  • From offre Into automatiquement pour des conversions idiomatiques.

Vérifie ta compréhension

  1. Pourquoi un générique fn f<T>(x: T) ne peut-il pas faire x > 0 sans borne ? Quelle borne ajouterais-tu ?
  2. Dans quel cas dois-tu obligatoirement utiliser Box<dyn Trait> plutôt qu'un générique ?
  3. Pourquoi #[derive(Display)] n'existe-t-il pas, alors que #[derive(Debug)] oui ?
