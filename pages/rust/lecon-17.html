Module 06 · Tester son code — Leçon 17

Tester avec cargo test

~36 min Intermédiaire Modules (leçon 11) utiles

À la fin de cette leçon, tu sauras

  • écrire des tests avec #[test] et les lancer avec cargo test ;
  • utiliser assert!, assert_eq! et les messages d'échec ;
  • tester une panique avec #[should_panic] et un Result ;
  • distinguer tests unitaires et tests d'intégration.
Sommaire de la leçon

Le compilateur de Rust attrape déjà énormément d'erreurs : types, possession, durées de vie. Mais il ne peut pas vérifier que ta logique est correcte — qu'additionner renvoie bien la somme. Pour ça, on écrit des tests. Et là encore, Rust se distingue : tester est intégré au langage et à Cargo, sans aucune bibliothèque à installer. Une annotation, une commande, et tu as ton filet de sécurité.

Le premier test

Un test est une fonction annotée #[test]. La convention idiomatique : la placer dans un module tests au bas du fichier, marqué #[cfg(test)] pour qu'il ne soit compilé que pendant les tests (jamais dans le binaire final).

On lance tout avec cargo test : Cargo compile, exécute chaque fonction #[test] dans un fil séparé, et affiche un récapitulatif test result: ok. 1 passed; 0 failed. use super::*; remonte au module parent pour accéder à additionner.

Les macros d'assertion

Rust fournit trois macros d'assertion. assert! vérifie un booléen ; assert_eq! et assert_ne! comparent deux valeurs et, en cas d'échec, affichent les deux valeurs — précieux pour comprendre ce qui a cassé.

En cas d'échec, assert_eq! imprime left: 4, right: 5 : tu vois immédiatement l'écart sans relire le test. Le message optionnel (dernier argument) suit la syntaxe de format! et accepte l'interpolation {solde}.

Tester une panique

Certaines fonctions doivent paniquer sur une entrée invalide (par ex. une division par zéro). #[should_panic] vérifie que le test panique bien ; l'option expected contrôle même le message.

Si la fonction ne panique pas, le test échoue. Le expected exige en plus que le message de panique contienne ce texte : on teste ainsi que c'est la bonne panique, pas une autre.

Tester un Result

En Rust idiomatique, on préfère souvent renvoyer un Result plutôt que paniquer (module 3). Une fonction de test peut elle-même renvoyer un Result : l'opérateur ? y propage l'erreur, et tout Err fait échouer le test.

Ce style évite les unwrap() dans les tests : si analyser renvoie une erreur, le ? la remonte et le test échoue avec le détail. On termine par Ok(()) pour signaler le succès.

Unitaires et intégration

Rust distingue deux familles de tests. Les tests unitaires vivent dans le fichier du code (le module #[cfg(test)]) : ils peuvent tester des fonctions privées. Les tests d'intégration vivent dans un dossier tests/ à la racine : ils utilisent ta crate de l'extérieur, comme le ferait un utilisateur, et ne voient que l'API publique.

Chaque fichier de tests/ est compilé en binaire séparé. cargo test lance tout : unitaires, intégration, et même les exemples de la documentation (doctests). Pour ne lancer qu'un sous-ensemble : cargo test addition filtre par nom.

Cas réel — le test qui a figé un bug pour toujours

Dans une petite boutique en ligne écrite en Rust, une fonction prix_ttc arrondissait mal certains montants : 0,015 € tombait à 0,01 au lieu de 0,02. Le correctif tenait en une ligne, mais l'équipe a surtout ajouté un test : assert_eq!(prix_ttc(0.015), 0.02). Six mois plus tard, un remaniement des arrondis a réintroduit exactement le même bug… et cargo test l'a bloqué avant la mise en production. Trois lignes écrites une fois ont évité deux fois une facture fausse envoyée à des clients. C'est ça, un test de non-régression : il transforme un bug corrigé en garantie permanente.

Astuce

Par défaut, cargo test masque la sortie println! des tests qui réussissent. Pour la voir, ajoute -- --nocapture. Et comme les tests tournent en parallèle, ne fais jamais dépendre un test d'un état partagé mutable : chacun doit être indépendant, exactement comme dans les autres langages.

Antisèche

Glossaire

#[test]
Attribut qui marque une fonction comme test ; cargo test la découvre et l'exécute dans son propre fil.
#[cfg(test)]
Compilation conditionnelle : le module de tests n'est inclus que pendant cargo test, jamais dans le binaire de production.
Test unitaire
Test placé dans le fichier du code (module #[cfg(test)]) ; il partage la portée du module et peut atteindre les fonctions privées.
Test d'intégration
Test placé dans le dossier tests/, compilé comme un crate séparé : il n'utilise que l'API publique, comme un utilisateur extérieur.
assert_eq!
Macro qui compare deux valeurs et, en cas d'échec, affiche les deux (left/right) — bien plus lisible que assert!(a == b).
#[should_panic]
Fait réussir le test si le corps panique ; l'option expected exige que le message de panique contienne un texte donné.
Doctest
Exemple de code écrit dans un commentaire de documentation /// ; cargo test le compile et l'exécute, garantissant que la doc reste juste.
Test de non-régression
Test ajouté après la correction d'un bug pour garantir qu'il ne réapparaîtra pas : il fige le comportement corrigé.

Récap et vérification

  • Tester est intégré : #[test] + cargo test, sans bibliothèque externe.
  • Les tests unitaires vivent dans un module #[cfg(test)] mod tests avec use super::*;.
  • assert!, assert_eq!, assert_ne! ; assert_eq! affiche les deux valeurs si échec.
  • #[should_panic(expected = "…")] vérifie une panique ; un test peut renvoyer Result et utiliser ?.
  • Les tests d'intégration (dossier tests/) testent l'API publique de l'extérieur.

  2. Quel avantage assert_eq! a-t-il sur assert!(a == b) ?
  3. Quelle différence entre un test unitaire et un test d'intégration ?
