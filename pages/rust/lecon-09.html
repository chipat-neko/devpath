Module 03 · Rust idiomatique — Leçon 09

La gestion d'erreurs

~35 min Avancé Leçon 8 recommandée

À la fin de cette leçon, tu sauras

  • Distinguer les erreurs récupérables (Result) des bugs irrécupérables (panic!) ;
  • Gérer un Result par match et propager une erreur avec l'opérateur ? ;
  • Manipuler Option et ses combinateurs (map, unwrap_or, ok_or) ;
  • Définir des erreurs personnalisées avec Box<dyn Error> et savoir quand utiliser unwrap/expect.
Sommaire de la leçon

En C, une erreur se signale souvent par un code de retour qu'on est libre d'ignorer, ou par un NULL qu'on oublie de vérifier. En Rust, il n'y a pas d'exceptions, et c'est une excellente nouvelle : les erreurs voyagent dans le système de types. Une fonction qui peut échouer le dit dans sa signature, et le compilateur refuse de te laisser ignorer le cas d'échec. Tu ne combats plus le borrow checker ici, mais tu profites de la même philosophie : ce qui compile a déjà passé un grand nombre de vérifications.

Dans cette leçon, tu vas voir comment Rust sépare proprement les deux familles d'erreurs, comment Result et Option forcent une gestion explicite, et comment l'opérateur ? rend tout cela élégant plutôt que verbeux.

Deux familles : récupérable et irrécupérable

Rust distingue nettement deux situations. Une erreur récupérable est attendue dans le cours normal du programme : un fichier absent, une saisie utilisateur invalide, une connexion réseau qui tombe. On la représente avec Result<T, E>. Une erreur irrécupérable est un bug : un état qui ne devrait jamais arriver, une invariante violée. On déclenche alors panic!, qui arrête le thread (par défaut).

La règle de pouce : si l'appelant peut raisonnablement réagir à l'erreur, renvoie un Result. Si l'erreur signale que le programme est dans un état impossible, panic! est légitime.

Result<T, E> : le compilateur t'oblige à gérer

Result<T, E> est une énumération à deux variantes : Ok(valeur) en cas de succès, Err(erreur) en cas d'échec. Comme match doit être exhaustif, tu ne peux pas oublier la branche Err. La signature de la fonction documente à la fois le type de succès et le type d'erreur.

Note

Result est marqué #[must_use] : si tu appelles une fonction qui renvoie un Result sans utiliser sa valeur, le compilateur t'avertit (warning: unused `Result` that must be used). Le langage refuse de te laisser jeter une erreur par inadvertance.

L'opérateur ? : propager élégamment

Écrire un match à chaque appel faillible deviendrait vite pénible. L'opérateur ? est l'idiome central : placé après une expression de type Result, il déballe le Ok et continue, ou il renvoie immédiatement le Err de la fonction courante. La fonction doit donc elle-même renvoyer un Result compatible : un ? posé sur un Result ne compile pas dans une fonction qui renvoie Option (et réciproquement).

On peut même enchaîner : let n: i32 = ligne.trim().parse()?; propage l'erreur de parsing en une seule ligne. C'est le cœur d'un code Rust idiomatique.

Astuce

Depuis Rust 2021, fn main() peut renvoyer Result<(), Box<dyn Error>>. Tu peux donc utiliser ? directement dans main et finir par Ok(()) : pratique pour les petits programmes et les exemples.

Option et ses combinateurs

Option<T> est le cousin de Result : Some(valeur) ou None. Il modélise l'absence (pas d'erreur, juste « rien »), et remplace le NULL du C de façon sûre. Ses combinateurs évitent les match répétitifs : map transforme la valeur si elle existe, unwrap_or fournit une valeur par défaut, ok_or convertit un Option en Result.

Note

? fonctionne aussi sur Option : dans une fonction qui renvoie Option<T>, x? renvoie None si x vaut None, sinon déballe le Some. Les deux types partagent la même logique de court-circuit.

unwrap / expect : déballer en paniquant

unwrap() et expect("message") extraient la valeur d'un Ok/Some — mais paniquent si c'est un Err/None. Ils sont parfaits pour un prototype, un script jetable ou un test, là où l'échec doit faire crasher bruyamment. En production, on les évite : un unwrap mal placé transforme une erreur récupérable en arrêt du programme. Préfère expect à unwrap : son message documente pourquoi tu pensais que ça ne pouvait pas échouer.

Erreurs personnalisées et Box<dyn Error>

Une vraie application a souvent plusieurs sources d'erreur. Deux approches coexistent. La rapide : Box<dyn Error>, un type « fourre-tout » qui accepte n'importe quelle erreur implémentant le trait Error ; combiné à ?, les conversions se font automatiquement. La rigoureuse : définir ton propre enum d'erreur, ce qui rend chaque cas explicite et testable.

En pratique, on n'écrit pas ces impl à la main : les crates thiserror (pour des erreurs typées, côté bibliothèque) et anyhow (pour un type d'erreur souple, côté application) génèrent tout cela. On les survole dans « Pour aller plus loin ».

panic! : quand l'utiliser

panic! n'est pas un mécanisme de gestion d'erreur ordinaire : c'est le signal « ce code a un bug ». Réserve-le aux invariantes internes — un état logiquement impossible, une assertion de programmation. Pour tout ce qui dépend du monde extérieur (fichiers, réseau, saisie), reste sur Result.

Pièges fréquents

Piège fréquent

unwrap() partout. En prototype c'est tolérable, mais en production chaque unwrap est une panique potentielle. Remplace-les par ?, match, ou au minimum expect avec un message clair. Clippy peut signaler les unwrap avec le lint clippy::unwrap_used.

Piège fréquent

Utiliser ? dans une fonction qui ne renvoie pas Result/Option. Le compilateur refuse : error[E0277]: the `?` operator can only be used in a function that returns `Result` or `Option`. Change la signature de retour de la fonction, ou gère l'erreur localement.

Piège fréquent

Mélanger des types d'erreur sans conversion. Si une fonction appelle deux API aux erreurs différentes, ? a besoin d'une conversion via le trait From. Box<dyn Error> ou anyhow::Error l'absorbent automatiquement ; avec un enum typé, implémente From (ou laisse thiserror le faire avec #[from]).

Pour aller plus loin

Explore thiserror (dérive Error, Display et From pour tes enum typés) et anyhow (un type d'erreur dynamique avec contexte via .context(...)). Approfondis la conversion d'erreurs avec le trait From et l'élargissement automatique fait par ?, ainsi que le choix entre erreurs typées (bibliothèques) et dynamiques (applications). Côté combinateurs, regarde and_then, or_else, map_err et ? sur Option.

Un cas réel : l'unwrap qui bloque le déploiement

Cas réel

Un service Rust lit sa configuration au démarrage avec std::fs::read_to_string("config.toml").unwrap(). En local, le fichier existe toujours : tout va bien pendant des mois. Un jour, un déploiement oublie de copier config.toml sur le nouveau serveur : au premier lancement, l'unwrap() panique et le service refuse de démarrer avec un message brut — called `Result::unwrap()` on an `Err` value: Os { code: 2, kind: NotFound } — suivi d'une pile d'appels illisible pour l'astreinte. En repassant à ? dans un main() -> Result<(), Box<dyn Error>>, la même panne devient un message propre ; et avec anyhow et .context("config.toml introuvable — copie config.example.toml"), le journal dit quoi faire. Le bug n'a pas changé : c'est le diagnostic qui passe de dix minutes de fouille à une lecture. La morale des vrais outils (ripgrep, bat, fd) est la même : ? partout, unwrap nulle part sur le chemin critique.

Glossaire

Result<T, E>
Énumération à deux variantes — Ok(T) (succès) ou Err(E) (échec) — qui modélise une erreur récupérable dans le système de types.
Option<T>
Énumération Some(T) ou None qui modélise l'absence de valeur sans recourir au NULL.
Opérateur ?
Placé après une expression Result/Option : déballe le succès, ou fait un return anticipé de l'erreur (avec conversion via From).
panic!
Macro qui interrompt le thread ; réservée aux bugs et états impossibles, pas aux erreurs prévisibles du monde extérieur.
unwrap / expect
Extraient la valeur d'un Ok/Some mais paniquent sinon ; expect ajoute un message de diagnostic. À réserver au prototype et aux tests.
Récupérable / irrécupérable
Récupérable : erreur attendue que l'appelant peut gérer (→ Result). Irrécupérable : bug logique (→ panic!).
Box<dyn Error>
Type d'erreur « fourre-tout » qui accepte toute erreur implémentant le trait Error ; les conversions se font automatiquement avec ?.
#[must_use]
Attribut porté par Result : le compilateur avertit si sa valeur est ignorée, empêchant de jeter une erreur par inadvertance.

Récap et vérification

  • Result<T, E> modélise les erreurs récupérables ; panic! signale un bug irrécupérable.
  • Le compilateur force la gestion : match exhaustif et #[must_use] empêchent d'ignorer une erreur.
  • L'opérateur ? propage l'Err/None et déballe le succès — l'idiome central.
  • Option et ses combinateurs (map, unwrap_or, ok_or) gèrent l'absence sans NULL.
  • unwrap/expect conviennent au proto ; en prod, on gère proprement.
  • Box<dyn Error>, thiserror et anyhow structurent les erreurs réelles.
