Module 04 · Rust en pratique — Leçon 11

Modules, crates et écosystème

~31 min Avancé Leçon 10 recommandée

À la fin de cette leçon, tu sauras

  • organiser un crate en modules avec mod, pub et les chemins (crate::, super::, self::) ;
  • importer proprement avec use et renommer avec as ;
  • gérer les dépendances avec Cargo (Cargo.toml, cargo add, Cargo.lock, features) ;
  • puiser dans la bibliothèque standard et structurer un projet (main.rs, lib.rs, modules).
Sommaire de la leçon

Jusqu'ici, ton code tenait sans doute dans un seul main.rs. Ça marche pour s'entraîner, mais un vrai projet a besoin de structure : des modules pour ranger les fonctions par responsabilité, des crates pour réutiliser du code, et Cargo pour tirer parti des milliers de bibliothèques de l'écosystème. Bonne nouvelle : ce système est cohérent et le compilateur te guide à chaque erreur.

Dans cette leçon, tu vas apprendre à découper un crate en modules, à exporter ce qu'il faut avec pub, à importer avec use, puis à ajouter une dépendance externe et à explorer la bibliothèque standard. À la fin, organiser un projet Rust te paraîtra naturel.

Les modules : ranger le code dans un crate

Un module est un espace de noms qui regroupe des éléments (fonctions, structs, autres modules). On le déclare avec mod. Par défaut, tout est privé : le mot-clé pub rend un élément visible depuis l'extérieur du module.

Note le :: qui sépare les segments d'un chemin : geometrie::aire_rectangle descend dans le module puis nomme la fonction.

Les chemins : crate, super, self

Pour atteindre un élément, on écrit un chemin. Il peut être absolu (depuis la racine, avec crate::) ou relatif (depuis le module courant). Trois préfixes utiles : crate:: (la racine du crate), super:: (le module parent, comme .. dans un dossier) et self:: (le module courant).

Note

Choisis crate:: quand l'élément ne bougera pas de place, et super:: quand parent et enfant déménagent ensemble. L'idée est de limiter les chemins à corriger lors d'un refactor.

Modules dans des fichiers et dossiers

Garder tous les modules dans un seul fichier devient vite illisible. Rust permet de mapper un module sur un fichier ou un dossier. Dans le crate racine, mod geometrie; (avec un point-virgule, sans corps) dit au compilateur : « le contenu de ce module est dans geometrie.rs ».

Quand un module a lui-même des sous-modules, le style moderne (édition 2018+) place le fichier du module à côté d'un dossier du même nom qui contient les sous-modules. Ainsi src/geometrie.rs déclare pub mod cercle;, ce qui charge src/geometrie/cercle.rs. (L'ancien style équivalent, encore valide, place tout dans src/geometrie/mod.rs.)

use : importer (et renommer avec as)

Écrire le chemin complet à chaque appel est fatigant. use apporte un nom dans la portée courante. Le mot-clé as crée un alias, pratique pour éviter une collision entre deux types portant le même nom.

Astuce

Convention idiomatique : on importe le module parent pour les fonctions (use std::io; puis io::stdin()), mais le type lui-même pour les structs et enums (use std::collections::HashMap;). Cela rend l'origine d'une fonction lisible au point d'appel.

Crates : binaire vs bibliothèque

Un crate est l'unité de compilation de Rust. Il en existe deux sortes. Un crate binaire a une fonction main et produit un exécutable ; sa racine est src/main.rs. Un crate bibliothèque n'a pas de main, expose une API réutilisable, et sa racine est src/lib.rs.

Le fichier racine est le sommet de l'arbre de modules : c'est lui qui forme le module crate. Un même projet peut contenir les deux : le binaire (main.rs) appelle alors la bibliothèque (lib.rs) par le nom du paquet.

Note

Si le nom du paquet contient un tiret (par ex. mon-outil), Rust le remplace par un tiret bas dans le code : tu écris alors mon_outil::saluer(...). Le nom d'identifiant ne peut pas contenir de tiret.

Cargo et les dépendances

Cargo est le gestionnaire de paquets et de build. Le manifeste Cargo.toml décrit ton paquet et ses dépendances, récupérées depuis le dépôt public crates.io. Les versions suivent le versionnage sémantique (semver) : major.minor.patch.

Plus pratique que d'éditer le manifeste à la main : cargo add choisit une version compatible.

Une contrainte comme "0.8" signifie « toute version compatible » (ici jusqu'à, mais sans inclure, 0.9.0). Cargo écrit les versions exactes réellement utilisées dans Cargo.lock : ce fichier garantit des builds reproductibles, on le versionne pour un binaire.

Les features : compilation à la carte

Une feature est une option de compilation qu'une crate expose pour activer une partie de son code. Tu n'actives que ce dont tu as besoin, ce qui réduit le temps de compilation et la taille du binaire. On peut aussi couper les features par défaut avec default-features = false.

La bibliothèque standard (std)

Rust fournit une std riche, sans dépendance externe : std::collections (HashMap, HashSet, VecDeque…), std::fs pour les fichiers, std::io pour les entrées/sorties. Un sous-ensemble très courant, le prelude, est importé d'office dans chaque fichier : Option, Result, Vec, String, println!… Pas besoin de use pour eux.

Remarque le match exhaustif sur Ok/Err et l'opérateur ? qui propage l'erreur : des idiomes que tu retrouveras partout.

La structure d'un projet

Un projet bien rangé suit une arborescence prévisible. Cargo et le compilateur s'appuient dessus, donc respecte les noms.

Pièges fréquents

Piège fréquent

Oublier pub. Un élément privé reste invisible hors de son module, et le compilateur le dit clairement : error[E0603]: function `aire_rectangle` is private. Ajoute pub devant l'élément… et n'oublie pas que le module lui-même doit aussi être pub pour être traversé depuis l'extérieur.

Piège fréquent

Confondre crate:: et super::, ou prendre le nom du crate pour un nom de module. Le nom du paquet (dans Cargo.toml) désigne la bibliothèque entière ; à l'intérieur, on part de crate::. Autre travers : tout entasser dans main.rs au lieu de découper — et oublier que chaque feature inutile alourdit la compilation.

Pour aller plus loin

Pour aller plus loin

Les workspaces regroupent plusieurs crates dans un même dépôt avec un Cargo.lock partagé (idéal pour découper une grosse application). Tu peux publier sur crates.io avec cargo publish, documenter avec les commentaires /// rendus par cargo doc --open, et activer du code selon la cible grâce aux attributs de configuration #[cfg(...)] (par exemple #[cfg(test)] pour les tests).

Un cas réel : le build qui casse en CI

Cas réel

Une équipe développe un service en Rust. En local, tout compile depuis des semaines. Mais un matin, l'intégration continue échoue — sans qu'une seule ligne n'ait changé. La cause ? Cargo.lock figurait dans le .gitignore et n'était donc pas versionné. Entre-temps, une dépendance transitive était passée de 0.8.4 à 0.8.5 — une version « compatible » au sens semver, mais porteuse d'une régression. Chaque développeur gardait son ancien Cargo.lock local ; la CI, elle, repartait d'un clone propre et résolvait la version la plus récente. La correction tient en une décision : versionner Cargo.lock pour un binaire, pour que développeurs et CI compilent exactement le même arbre de dépendances. C'est toute la différence entre « ça marche chez moi » et « ça marche partout ».

Glossaire

Module (mod)
Espace de noms qui regroupe des éléments (fonctions, types, sous-modules) ; forme un nœud de l'arbre du crate.
pub
Mot-clé de visibilité qui rend un élément accessible hors de son module ; sans lui, tout est privé.
Chemin
Suite de segments séparés par :: pour désigner un élément : absolu depuis crate::, ou relatif via super:: (parent) et self:: (courant).
use / as
use importe un nom dans la portée courante ; as lui donne un alias pour éviter les collisions.
Crate
Unité de compilation de Rust : binaire (src/main.rs, avec main, produit un exécutable) ou bibliothèque (src/lib.rs, expose une API).
Cargo · Cargo.toml / Cargo.lock
Cargo est le gestionnaire de build et de dépendances. Cargo.toml décrit le paquet et ses contraintes ; Cargo.lock fige les versions exactes.
Semver
Versionnage sémantique major.minor.patch : patch/minor restent compatibles, un changement de major peut casser l'API.
Feature
Option de compilation qu'une crate expose pour n'activer qu'une partie de son code (moins de temps de compilation, binaire plus léger).

Récap et vérification

  • mod crée un module ; tout est privé par défaut, pub exporte.
  • Les chemins utilisent :: avec crate:: (racine), super:: (parent), self:: (courant).
  • Un module peut vivre dans un fichier (mod nom;) ; ses sous-modules vont dans un dossier du même nom.
  • use importe un nom dans la portée ; as le renomme.
  • Crate binaire (main.rs, avec main) vs bibliothèque (lib.rs, API publique).
  • Cargo gère le build et les dépendances : Cargo.toml, cargo add, semver, Cargo.lock, features.
  • La std (collections, fs, io) et son prelude couvrent l'essentiel sans dépendance externe.

Vérifie ta compréhension

  1. Pourquoi geometrie::aire_rectangle ne compile-t-il pas si la fonction n'a pas pub, et quels deux pub faut-il parfois ajouter ?
  2. Quelle est la différence entre super::connecter() et crate::reseau::connecter() ?
  3. À quoi sert Cargo.lock et en quoi diffère-t-il de la contrainte "0.8" écrite dans Cargo.toml ?
