Module 05 · Rust en profondeur — Leçon 16

Async, unsafe et performance

~36 min Avancé Leçon 15 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire et lancer du code asynchrone avec async/.await et un exécuteur Tokio ;
  • savoir utiliser un bloc unsafe en l'encapsulant derrière une API sûre ;
  • savoir appeler une fonction C via le FFI (extern "C", repr(C)) ;
  • savoir raisonner sur la performance (abstractions à coût nul, mesure avant optimisation).
Sommaire de la leçon

Tu maîtrises maintenant la possession, les traits, les erreurs et la concurrence par threads. Cette leçon t'emmène aux frontières du langage : trois domaines où Rust se distingue radicalement des autres langages — l'asynchrone, le code non sûr et la quête de performance. Ce sont des sujets profonds ; l'objectif ici n'est pas de tout couvrir, mais de te donner les bons modèles mentaux pour ne plus avoir peur d'y entrer.

Le fil rouge : Rust refuse de te cacher le coût des choses. Une Future ne tourne pas toute seule, un bloc unsafe ne désactive pas le vérificateur d'emprunt, et une abstraction « gratuite » l'est vraiment — mais seulement si tu comprends pourquoi.

L'asynchrone : des Futures paresseuses

En Rust, async fn ne lance rien. Une fonction async renvoie une Future : une valeur qui décrit un calcul à faire, mais qui reste inerte tant que personne ne la polle. C'est le point qui surprend tout le monde au début.

Pour faire avancer une Future, il faut un exécuteur (runtime). Rust n'en impose aucun dans la bibliothèque standard : tu choisis le tien. Le plus répandu est Tokio. La macro #[tokio::main] transforme ton main en point d'entrée asynchrone et démarre l'exécuteur pour toi.

Le .await est l'endroit où ta tâche peut céder la main si le calcul attend (un réseau, un timer…). Pendant ce temps, l'exécuteur fait avancer d'autres tâches. Pour lancer plusieurs choses « en même temps », on crée des tâches avec tokio::spawn.

Note

spawn renvoie un JoinHandle<T> qui est lui-même une Future. L'attendre avec .await récupère un Result<T, JoinError> : la tâche pourrait avoir paniqué, d'où le .unwrap() ici.

Pourquoi l'async de Rust est différent

Dans beaucoup de langages, l'asynchrone vient avec un runtime imposé et un coût caché (garbage collector, allocations par tâche). En Rust, le compilateur transforme ton async fn en une machine à états générée à la compilation. Chaque .await devient un état. Il n'y a ni allocation cachée par .await, ni runtime imposé : c'est le principe d'abstraction à coût nul appliqué à la concurrence.

Conséquence pratique : tu choisis l'exécuteur adapté (Tokio pour le réseau, un exécuteur minimal sur l'embarqué no_std…). Le revers : l'async « colore » les fonctions. Une fonction qui veut faire un .await doit elle-même être async ; tu ne peux pas attendre une Future depuis une fonction synchrone ordinaire sans repasser par un exécuteur.

Unsafe : ce que ça débloque, et ce que ça ne désactive pas

Le bloc unsafe est souvent mal compris. Il ne désactive PAS le vérificateur d'emprunt ni le typage. Il débloque exactement cinq super-pouvoirs que le compilateur ne peut pas prouver sûrs tout seul :

  • déréférencer un pointeur brut (*const T, *mut T) ;
  • appeler une fonction unsafe ou une fonction externe (FFI) ;
  • accéder ou modifier une variable static mut ;
  • implémenter un trait unsafe (par ex. Send/Sync à la main) ;
  • accéder aux champs d'une union.

unsafe est un contrat : tu dis au compilateur « je garantis l'invariant que tu ne peux pas vérifier ». Si tu mens, c'est un comportement indéfini (UB).

Note

Parmi ces cinq pouvoirs, static mut est le plus dangereux : un accès partagé en écriture est presque toujours un UB. Rust moderne t'en décourage activement (avertissement static_mut_refs), et l'édition 2024 le proscrit. Préfère OnceLock, Mutex ou AtomicUsize : tu n'as alors plus besoin d'unsafe du tout.

Encapsuler l'unsafe derrière une API sûre

La bonne pratique est de confiner unsafe dans un petit bloc, dont tu as prouvé la sûreté, et d'exposer une fonction sûre par-dessus. Tout l'art consiste à garantir l'invariant en amont pour que l'appelant n'ait jamais à écrire unsafe.

Astuce

Le assert! avant le bloc unsafe n'est pas décoratif : c'est lui qui transforme une promesse fragile en invariant garanti. Documente toujours, dans un commentaire // SÛRETÉ :, la condition que ton bloc unsafe suppose — c'est la convention de l'écosystème.

Le FFI : appeler du C depuis Rust

Le FFI (Foreign Function Interface) permet d'appeler du code C — et inversement. Du côté Rust, on déclare les fonctions externes dans un bloc extern "C" ; l'appel est unsafe car le compilateur ne connaît pas le code de l'autre côté. Les structures partagées doivent être annotées #[repr(C)] pour adopter la disposition mémoire du C, et non celle (non garantie) de Rust.

Performance : des abstractions à coût nul

Le slogan de Rust : « ce que tu n'utilises pas, tu ne le paies pas ; ce que tu utilises, tu ne pourrais pas le coder mieux à la main ». Concrètement, une chaîne d'itérateurs compile vers le même code machine qu'une boucle écrite à la main, grâce à l'inlining et aux optimisations de LLVM en mode --release.

Quelques leviers concrets : compiler en --release (sans quoi toute mesure est trompeuse), éviter les allocations inutiles (réutiliser un Vec, préférer &str à String quand on ne possède pas la donnée), et surtout mesurer. Pour des micro-benchmarks fiables, l'outil de référence est criterion, qui gère l'échauffement et les statistiques.

Toujours profiler en mode release : un build de debug peut être 10 à 100 fois plus lent.

Bonnes pratiques

  • Minimise la surface unsafe : le moins de lignes possible, encapsulées dans une API sûre, chacune commentée // SÛRETÉ :.
  • Teste le code unsafe avec Miri, un interpréteur qui détecte de nombreux comportements indéfinis invisibles à la compilation.
  • Ne devine jamais la performance : mesure avant et après. Beaucoup d'« optimisations » intuitives sont neutres, voire nuisibles.
  • En async, n'appelle jamais d'opération bloquante (lecture fichier synchrone, std::thread::sleep) dans une tâche : elle gèle le thread de l'exécuteur.

Miri requiert la toolchain nightly et le composant ajouté via rustup (rustup +nightly component add miri).

Un cas réel : Discord passe de Go à Rust

Cas réel

En 2020, Discord a expliqué publiquement pourquoi il avait réécrit en Rust son service « Read States » (qui suit, pour chaque utilisateur, quels messages sont lus). La version en Go souffrait de pics de latence réguliers : à intervalles fixes, le ramasse-miettes (GC) s'interrompait pour balayer la mémoire, provoquant des à-coups visibles malgré tous les réglages tentés. Réécrit en Rust — sans GC, avec la gestion mémoire par possession et un runtime async (Tokio) — le même service a vu ses latences s'effondrer et devenir régulières, tout en consommant moins de mémoire et de CPU. C'est l'illustration directe de cette leçon : aucun coût caché, une concurrence async à coût nul, et un contrôle mémoire qui élimine les pauses imprévisibles. Le même argument a depuis conduit des acteurs comme Cloudflare ou AWS (Firecracker) à écrire leurs briques critiques en Rust.

Pièges fréquents

Piège fréquent

Croire qu'une Future s'exécute dès sa création. Sans .await ni exécuteur, elle ne fait rien — le compilateur t'avertit d'ailleurs souvent avec « unused implementer of `Future` that must be used ».

Piège fréquent

Bloquer dans une tâche async. Un std::thread::sleep ou un appel réseau synchrone fige le thread de l'exécuteur et bloque les autres tâches qui partagent ce thread. Utilise les versions async (tokio::time::sleep, le client réseau de Tokio), ou tokio::task::spawn_blocking pour isoler le travail bloquant.

Piège fréquent

Un bloc unsafe mal encapsulé, ou un FFI sans #[repr(C)] et sans règle claire de propriété mémoire (qui libère ? Rust ou le C ?), provoque un UB silencieux. Et n'optimise jamais sans mesurer : tu risques de compliquer le code pour un gain nul.

Pour aller plus loin

Pour aller plus loin

Explore Tokio en profondeur (canaux, select!, runtime multi-thread), Miri pour traquer l'UB, criterion pour des benchmarks rigoureux, les traits Pin/Unpin (au cœur des Futures auto-référentielles), les autres exécuteurs de l'écosystème (async-std, la crate futures), et le mode no_std pour viser l'embarqué.

Antisèche

Glossaire

Future
Valeur qui décrit un calcul asynchrone paresseux : elle ne progresse que lorsqu'un exécuteur la polle (ou via .await).
Exécuteur (runtime)
Composant qui fait avancer les Future et ordonnance les tâches. Absent de la std : on en choisit un (souvent Tokio).
.await
Point où une tâche peut céder la main pendant une attente ; chaque .await devient un état de la machine à états générée.
Coloration async
Une fonction qui fait .await doit elle-même être async : la « couleur » async se propage à ses appelants.
unsafe
Débloque cinq opérations non vérifiables (pointeurs bruts, fonctions unsafe/FFI, static mut, traits unsafe, union). Ne désactive ni le typage ni l'emprunt ; c'est un contrat.
UB (comportement indéfini)
Ce qui arrive si un contrat unsafe est violé : le programme n'a plus aucune garantie. Miri aide à en détecter.
FFI
Foreign Function Interface : appeler du C (ou l'inverse) via extern "C" ; les structs échangées portent #[repr(C)].
Abstraction à coût nul
Abstraction (itérateurs, async) qui compile vers le même code qu'un équivalent écrit à la main : on ne paie pas ce qu'on n'utilise pas.

Récap et vérification

  • Une async fn renvoie une Future paresseuse ; il faut un .await et un exécuteur (Tokio) pour l'exécuter.
  • tokio::spawn crée des tâches concurrentes ; n'y bloque jamais le thread.
  • unsafe débloque cinq pouvoirs précis et ne désactive ni le typage ni l'emprunt ; encapsule-le derrière une API sûre.
  • Le FFI utilise extern "C", #[no_mangle] et #[repr(C)] ; les appels externes sont unsafe.
  • Les abstractions de Rust sont à coût nul, mais on profile en --release et on mesure avant d'optimiser.

Vérifie ta compréhension

  3. Pourquoi une structure échangée via FFI doit-elle porter #[repr(C)] ?
