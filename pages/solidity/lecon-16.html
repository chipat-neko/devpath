Module 05 · Solidity avancé — Leçon 16

Interagir entre contrats : interfaces, call et delegatecall

~50 min Avancé Avoir suivi « Contrats évolutifs : proxy et UUPS »

À la fin de cette leçon, tu sauras

  • appeler un autre contrat proprement via une interface ;
  • comprendre la différence call / staticcall / delegatecall ;
  • pourquoi delegatecall exécute du code étranger dans ton stockage ;
  • gérer l'échec d'un appel externe.
Sommaire de la leçon

Un contrat vit rarement seul. Il lit un oracle de prix, dépose dans un protocole, appelle un jeton… Savoir appeler un autre contrat — proprement et sans se faire piéger — est une compétence centrale du développement Solidity. Il existe plusieurs façons de le faire, de la plus sûre (l'interface typée) à la plus brute et dangereuse (l'appel bas niveau .call).

La voie propre : les interfaces

La méthode par défaut pour appeler un autre contrat est de décrire ses fonctions dans une interface, puis d'appeler comme s'il s'agissait d'un objet typé. Une interface ne contient que des signatures (pas de corps) : elle dit « ce contrat expose telle fonction ».

Les avantages sont décisifs : l'appel est typé (le compilateur vérifie le nom, les arguments et le type de retour), lisible (jeton.transfer(...) se lit comme un appel normal) et robuste. C'est la méthode que tu dois employer dans la quasi-totalité des cas.

La voie bas niveau : .call

Solidity expose aussi un appel bas niveau sur n'importe quelle address : .call. Il est flexible — on peut appeler une fonction inconnue à la compilation, ou joindre de l'ether — mais dangereux, car il ne vérifie rien pour toi.

abi.encodeWithSignature("f(uint256)", 42) construit la donnée d'appel (le calldata) : elle prend la signature textuelle de la fonction, en calcule le sélecteur (4 octets), puis y accole les arguments encodés. .call renvoie deux valeurs : un booléen ok (l'appel a-t-il réussi ?) et les data renvoyées.

Interface d'abord, .call en dernier recours

Par défaut, privilégie l'appel via interface typée : c'est vérifié à la compilation et lisible. Ne descends au .call que quand tu en as vraiment besoin : pour envoyer de l'ether à un contrat, ou appeler une signature dynamique inconnue à la compilation.

Un .call vers une adresse sans code renvoie ok = true

Piège classique : si adresse ne contient aucun code (un compte ordinaire, ou une adresse erronée), le .call réussit quand même et renvoie ok = true sans rien exécuter. Ne jamais supposer qu'un .call réussi a vraiment fait quelque chose : vérifie ok, et au besoin que l'adresse a bien du code.

call, staticcall, delegatecall

L'appel bas niveau existe en trois variantes, qui diffèrent par le contexte dans lequel le code cible s'exécute :

  • call : appel normal. Le code s'exécute dans le contexte de la cible, avec son stockage. C'est ce qu'on veut presque toujours.
  • staticcall : comme call, mais toute modification d'état est interdite. Sert à lire une valeur chez un autre contrat sans risque d'effet de bord (les fonctions view sont appelées ainsi).
  • delegatecall : le code de la cible s'exécute dans le contexte de l'appelant. C'est ton stockage, ton msg.sender et ton solde qui sont utilisés — on emprunte seulement le code de la cible.

Ce delegatecall est exactement le mécanisme des proxies vus à la leçon 11 : un proxy sans logique délègue l'exécution au contrat d'implémentation, tout en gardant les données chez lui.

Le piège du delegatecall : la disposition du stockage

Puisque delegatecall écrit dans le stockage de l'appelant en suivant la disposition des slots (le storage layout) telle que la voit le code appelé, une divergence de disposition entre le proxy et l'implémentation est catastrophique : le code croit écrire dans la variable X à un certain slot, mais chez l'appelant ce slot contient la variable Y. Les données se retrouvent corrompues silencieusement.

delegatecall : code de confiance et dispositions alignées, sans exception

N'utilise delegatecall que vers du code de confiance et avec des dispositions de stockage rigoureusement alignées entre l'appelant et la cible. Un slot qui ne correspond pas, une variable ajoutée au mauvais endroit, et tu écrases l'adresse du propriétaire ou le solde d'un utilisateur. C'est l'erreur la plus grave — et la plus courante — autour des proxies.

Gérer l'échec proprement

Un appel externe peut échouer : la cible révoque, manque de gas, ou n'existe pas. Il faut le prévoir.

Enfin, rappelle-toi le motif Checks-Effects-Interactions vu à la leçon 7 : place l'appel externe en dernier, après avoir mis à jour ton état, pour éviter la réentrance.

L'appel externe, toujours en dernier

Un appel externe peut rappeler ton contrat avant qu'il ait fini (réentrance). En appliquant Checks-Effects-Interactions — vérifier, modifier ton état, puis seulement appeler l'extérieur — un rappel arrive sur un état déjà à jour et la faille se referme.

Cas réel — le gel du multisig Parity (2017)

Quand un code externe disparaît, tout s'effondre

Les portefeuilles multisig Parity déléguaient (delegatecall) leur logique à une bibliothèque partagée unique. En 2017, un utilisateur a réussi à en devenir « propriétaire », puis a appelé selfdestruct sur cette bibliothèque. D'un coup, tous les portefeuilles qui en dépendaient sont devenus inutilisables : leur code délégué avait disparu, gelant plus de 500 000 ETH (des centaines de millions de dollars) définitivement inaccessibles. La leçon : delegatecall lie ton contrat au sort d'un code externe ; si le contrat dont tu dépends disparaît, il peut tout emporter avec lui. Confiance, contrôle des permissions et immuabilité du code délégué ne sont pas optionnels.

Antisèche

Glossaire

Interface
Description des seules signatures des fonctions d'un contrat, sans corps ; permet de l'appeler de façon typée via IContrat(adresse).f().
ABI
Application Binary Interface : la convention qui encode l'appel d'une fonction et ses arguments en octets (le calldata) ainsi que les valeurs de retour.
call
Appel bas niveau où le code de la cible s'exécute dans le contexte de la cible (son stockage) ; renvoie un booléen de succès à vérifier soi-même.
staticcall
Variante de call qui interdit toute modification d'état ; utilisée pour lire une valeur chez un autre contrat sans effet de bord.
delegatecall
Appel où le code de la cible s'exécute dans le contexte de l'appelant (son stockage, son msg.sender, son solde) ; base des proxies.
Contexte d'exécution
L'ensemble stockage + msg.sender + solde dans lequel un code s'exécute ; call utilise celui de la cible, delegatecall celui de l'appelant.
Collision de stockage (storage layout)
Divergence entre la disposition des slots du proxy et de l'implémentation ; avec delegatecall, elle fait écrire une variable par-dessus une autre et corrompt l'état.

Récap et vérification

  • Appelle un autre contrat via une interface typée par défaut : c'est vérifié à la compilation et lisible.
  • call s'exécute dans le stockage de la cible, staticcall lit sans modifier, delegatecall s'exécute dans le stockage de l'appelant.
  • delegatecall exige un code de confiance et des dispositions de stockage alignées, sous peine de corruption (cf. le gel Parity).
  • Gère l'échec : try/catch pour un appel typé, require(ok, "...") après un .call, et l'appel externe en dernier.

Exercices

Exercice 1Échauffement

Tu veux appeler transfer(address,uint256) d'un jeton dont tu connais l'adresse, de façon typée. Écris la déclaration d'interface minimale et la ligne d'appel.

Voir une solution

On décrit la signature dans l'interface (aucun corps), on « caste » l'adresse en IJeton(...), puis on appelle comme une méthode normale. Le compilateur vérifie le type de retour bool pour nous.

Exercice 2Application

Un collègue écrit adresse.call(abi.encodeWithSignature("f(uint256)", 3)); sans regarder la valeur de retour. Que corriges-tu ?

Voir une solution

Un .call ne révoque pas tout seul en cas d'échec : il renvoie ok = false. Sans require(ok, ...), le code continue comme si l'appel avait réussi. Pire : si adresse n'a aucun code, ok vaut true sans que rien ne se passe. On récupère et on teste toujours ok.

Exercice 3Défi

Explique en une ou deux phrases pourquoi la catastrophe Parity de 2017 a pu geler plus de 500 000 ETH, en te servant du mot delegatecall.

Voir une solution

Les portefeuilles Parity ne contenaient pas leur logique : ils la déléguaient par delegatecall à une unique bibliothèque partagée. Quand un utilisateur a pris le contrôle de cette bibliothèque et l'a détruite (selfdestruct), le code délégué a disparu ; tous les portefeuilles qui en dépendaient se sont retrouvés sans logique, donc incapables de bouger leurs fonds. La leçon : delegatecall lie le sort de ton contrat à celui d'un code externe — n'y délègue que du code de confiance et, idéalement, non destructible.
