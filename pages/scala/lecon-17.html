Module 5 · Projet — Leçon 17

Projet : un gestionnaire d'inventaire fonctionnel

~55 min Projet Prérequis : tout le cours

À la fin de cette leçon, tu sauras

  • assembler case class, immutabilité, Option, Either et pattern matching ;
  • modéliser un état comme une valeur immuable mise à jour par copy ;
  • brancher une type class Show pour un affichage soigné ;
  • livrer un petit programme complet et sûr, condensé du cours.
Sommaire de la leçon

Dernière ligne droite : on réunit tout. Ce projet — un gestionnaire d'inventaire — n'ajoute aucune notion nouvelle ; il tisse ensemble celles du cours. Une case class pour le modèle, une List immuable pour le stock, Option pour la recherche, Either pour valider un ajout, du pattern matching pour réagir, et la type class Show de la leçon 15 pour l'affichage. À la fin, tu auras un programme Scala idiomatique de bout en bout.

L'architecture : chaque brique vient d'une leçon

Avant de coder, visualisons l'ossature. Au centre, l'Inventaire — une valeur immuable qui contient la liste des produits. Autour, les capacités, chacune héritée d'un chapitre du cours.

Étape 1 — le modèle et son affichage

On repart de la type class Show (leçon 15). Le Produit porte une méthode valeur, et son instance Show vit dans le companion object pour être trouvée automatiquement.

Étape 2 — l'inventaire immuable

L'Inventaire enveloppe une List[Produit]. Toutes ses « lectures » s'appuient sur les collections : total (map+sum), rechercher (find → Option), enRupture (filter), un tri par valeur (sortBy).

Astuce — find renvoie déjà un Option

Pas besoin d'un try ni d'un test manuel : produits.find(prédicat) renvoie Some(produit) ou None. La recherche « qui peut ne rien trouver » est encodée dans le type de retour — l'appelant est obligé de gérer l'absence, exactement l'esprit de la leçon 8.

Étape 3 — l'ajout validé, sans mutation

Ajouter un produit ne modifie pas l'inventaire : on en renvoie un nouveau via copy. Et l'ajout n'a lieu que si le produit est valide — d'où un retour Either[List[String], Inventaire] qui accumule les erreurs (leçon 16).

Cas réel — la gestion de stock d'une boutique

Ce modèle est celui d'un vrai back-end de e-commerce. L'inventaire immuable rend les mises à jour sûres face à la concurrence : deux requêtes qui ajoutent un produit partent chacune d'une version connue, sans se marcher dessus (pas de mutation partagée). La validation accumulée sert lors des imports de catalogue : on renvoie au fournisseur la liste complète des lignes fautives d'un fichier, plutôt que de rejeter au premier défaut. Et la type class Show découple l'affichage (ticket, export CSV, log) du modèle métier.

Immuable ne veut pas dire figé

« Immuable » décrit chaque valeur, pas le système : l'état vit dans une var stock: Inventaire qu'on réaffecte à la nouvelle version après chaque ajout (stock = stock.ajouter(p).getOrElse(stock)). On combine ainsi un point mutable unique et contrôlé avec des données immuables partout ailleurs : le meilleur des deux mondes.

Glossaire

Capstone
Projet de synthèse qui mobilise, sans notion nouvelle, l'ensemble des acquis d'un cours.
État immuable
Modélisation où chaque changement produit une nouvelle valeur (copy) au lieu de muter l'existante ; l'ancienne version reste valide.
copy
Méthode générée par une case class qui crée une copie modifiée sur certains champs, sans toucher à l'original.
find
Méthode de collection renvoyant un Option : Some(x) pour le premier élément satisfaisant le prédicat, None sinon.
Companion object
Objet de même nom qu'une classe, hébergeant ses fabriques et ses instances given pour qu'elles soient trouvées automatiquement.
Point mutable contrôlé
Unique var réaffectée à la nouvelle version de l'état, entourée de données immuables : mutation localisée et maîtrisée.

Récap et vérification

  • Un projet Scala idiomatique est un assemblage de briques connues, pas une nouveauté.
  • L'état se modélise en valeur immuable ; on « modifie » avec copy, l'ancienne version survit.
  • Option pour l'absence, Either pour l'ajout validé, match pour réagir, collections pour les stats.
  • La type class Show découple l'affichage du modèle métier.

Vérifie ta compréhension

  1. Pourquoi ajouter renvoie-t-il un nouvel Inventaire plutôt que de muter le sien ?
  2. Quel type de retour choisit-on pour rechercher, et pourquoi ?
  3. Où range-t-on l'instance Show[Produit] pour qu'elle soit trouvée sans import ?

Exercices

Exercice 1Application

Ajoute à l'Inventaire une méthode quantiteTotale: Int qui somme les quantités de tous les produits, puis plusChere: Option[Produit] qui renvoie le produit de plus grande valeur (ou None si le stock est vide).

Voir une solution

maxByOption est la variante sûre de maxBy : sur une liste vide, elle renvoie None au lieu de lever une exception — encore l'esprit « l'absence est un Option ». quantiteTotale, lui, réutilise le trio map+sum déjà vu pour total : même patron, autre champ.

Exercice 2Défi

Écris ajouterTout(ps: List[Produit]): (Inventaire, List[String]) qui tente d'ajouter chaque produit : renvoie l'inventaire final (avec ceux qui passent) et la liste de toutes les erreurs rencontrées. Indice : un foldLeft.

Voir une solution

Le foldLeft promène un accumulateur — ici une paire (inventaire courant, erreurs cumulées) — à travers la liste. À chaque produit, le pattern matching sur le résultat d'ajouter décide : on avance l'inventaire (Right) ou on empile les erreurs (Left). C'est le mariage des trois piliers du module : état immuable transporté par le fold, validation par Either, aiguillage par pattern matching. Exactement le genre de fonction qu'on écrit pour importer un fichier fournisseur.

Exercice 3Synthèse

Où placer given Show[Produit] pour que la résolution implicite le trouve sans import, et pourquoi cet emplacement ?

Voir une solution

Dans l'objet compagnon de Produit. Scala inclut d'office le compagnon d'un type dans la portée implicite de ce type : un given Show[Produit] qui y réside est trouvé partout où l'on affiche un Produit, sans import. C'est l'emplacement canonique de l'instance « par défaut » d'une type class — la ranger ailleurs obligerait chaque appelant à l'importer.

Mini-projet fil rouge — l'inventaire complet

Assemble maintenant les trois étapes en un programme entier et exécutable. C'est le condensé du cours : modèle, immutabilité, Option, Either, pattern matching, collections et type class, réunis en une trentaine de lignes.

Ce que tu vas construire

Un object Boutique qui crée un inventaire, l'affiche via Show, calcule son total, liste les ruptures, puis tente deux ajouts : un valide et un invalide, en réagissant par pattern matching.

Étapes

La type class Show

Déclare trait Show[A] et l'extension .show, comme à la leçon 15.

Le modèle Produit

case class Produit(nom, prix, quantite) avec def valeur et un given Show[Produit] dans son companion.

L'inventaire immuable

case class Inventaire(produits: List[Produit]) avec total, rechercher, enRupture.

L'ajout validé

ajouter renvoyant un Either[List[String], Inventaire] via valider + copy.

Le programme

Dans object Boutique, crée le stock, affiche-le, puis teste deux ajouts avec match.

ProjetFil rouge

Assemble les cinq étapes en un programme complet. Essaie d'abord par toi-même, puis compare avec la solution de référence.

Voir une solution complète

Ce programme tient dans un écran, et pourtant il condense tout le cours : une case class pour modéliser, l'immutabilité pour l'état (chaque ajouter renvoie une nouvelle version), Option pour la recherche, Either pour la validation cumulée, le pattern matching pour réagir, les collections pour les statistiques et une type class pour l'affichage. C'est cette capacité à composer des briques sûres qui fait la valeur de Scala en production — que ce soit pour une boutique ou un pipeline de données. Félicitations : tu as bouclé le cours.
