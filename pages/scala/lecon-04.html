Module 1 · Les bases de Scala — Leçon 04

Les collections

~50 min Avancé Prérequis : leçon 3

À la fin de cette leçon, tu sauras

  • créer et parcourir les collections immuables List, Vector, Set et Map ;
  • enchaîner les méthodes fonctionnelles (map, filter, flatMap, foldLeft, groupBy…) au lieu de boucler ;
  • écrire des for-comprehensions lisibles avec filtres et yield ;
  • construire un pipeline de données réaliste et comprendre l'évaluation paresseuse avec LazyList.
Sommaire de la leçon

Une collection, c'est un sac à plusieurs cases : une liste de courses, un ensemble d'identifiants uniques, un annuaire qui associe un nom à un numéro. Dans presque tous les programmes, l'essentiel du travail consiste à transformer une collection en une autre : filtrer, regrouper, additionner. Scala excelle exactement là : ses collections sont immuables par défaut et viennent avec une boîte à outils de méthodes fonctionnelles qui remplacent les boucles à compteur.

Dans cette leçon, tu vas découvrir les quatre collections de base, la galaxie de méthodes qui les transforment, le sucre élégant des for-comprehensions, puis tu assembleras un vrai pipeline d'analyse de ventes. On finit par les collections paresseuses, qui ne calculent que ce dont tu as besoin.

Les quatre collections de base

Scala te propose quatre familles immuables que tu utiliseras tous les jours. Immuable signifie : une fois créée, la collection ne change jamais ; toute « modification » renvoie une nouvelle collection. C'est la voie par défaut, et c'est une bénédiction pour éviter les bugs de partage.

La flèche -> construit une paire clé/valeur : "FR" -> 0.20 équivaut à ("FR", 0.20). Choisis List quand tu parcours du début à la fin, Vector quand tu accèdes par index, Set pour l'unicité, Map pour les associations.

Note

Il existe des versions mutables dans scala.collection.mutable (par exemple mutable.ListBuffer). Elles sont parfois utiles pour des raisons de performance dans une boucle locale, mais reste sur les immuables tant qu'un besoin précis ne t'oblige pas à changer. L'immutabilité est le réglage idiomatique.

Accès, head et tail

Une List se pense comme une tête (le premier élément) suivie d'une queue (le reste). Cette décomposition head / tail est le pain quotidien du code récursif en Scala.

L'opérateur :: (lu « cons ») ajoute un élément en tête et renvoie une nouvelle liste ; l'originale reste intacte. Remarque headOption : il renvoie une Option (vue à la leçon précédente) plutôt que de planter sur une liste vide.

map, filter, flatMap : transformer plutôt que boucler

Voici le cœur du style fonctionnel. Au lieu d'écrire une boucle qui modifie un accumulateur, tu décris la transformation. map applique une fonction à chaque élément, filter garde ceux qui satisfont une condition, flatMap mappe puis aplatit le résultat.

Compare avec ce que tu écrirais en Java pour doubler puis filtrer : une boucle for, un ArrayList temporaire, un if, un add. En Scala, c'est une seule ligne déclarative qui dit quoi, pas comment.

Piège fréquent

Le placeholder _ ne représente qu'un seul argument utilisé une seule fois. _ * 2 marche, mais _ * _ dans un map ne veut pas dire « le carré » : chaque _ est un argument distinct (le compilateur attend alors une fonction à deux paramètres). Dès que tu réutilises la variable, nomme-la : x => x * x.

Réduire : foldLeft, reduce, sum

Réduire, c'est combiner tous les éléments en une seule valeur. sum et count sont les cas tout faits ; foldLeft est le couteau suisse : tu pars d'une valeur initiale et tu accumules de gauche à droite.

Préfère foldLeft à reduce quand la collection peut être vide : foldLeft a une valeur de départ et ne plantera jamais, alors que reduce lève une exception sur une collection vide.

Regrouper et découper : groupBy, partition, sortBy

Ces méthodes restructurent une collection. groupBy fabrique une Map à partir d'une clé calculée, partition coupe en deux selon une condition, sortBy trie selon un critère.

zip assemble deux collections en paires, en s'arrêtant à la plus courte. C'est parfait pour associer des éléments à leur position ou à une seconde série de données.

Interroger : find, exists, forall

Souvent tu ne veux pas transformer mais simplement questionner la collection. Ces méthodes renvoient un booléen ou une Option, sans construire de nouvelle collection.

find renvoie une Option : Some(valeur) s'il trouve, None sinon. Tu ne risques jamais de null ni d'index hors bornes.

Les for-comprehensions : le sucre élégant

Quand plusieurs map, filter et flatMap s'enchaînent, la lecture devient dense. La for-comprehension est une syntaxe plus lisible pour exactement la même chose. Avec yield, elle produit une collection ; sans yield, elle exécute juste un effet.

Sous le capot, le compilateur traduit cette for en flatMap/map/withFilter. Choisis la forme la plus lisible selon le cas : une seule transformation simple en map, un enchaînement avec filtres en for ... yield.

Option dans les collections : flatten

Tu obtiens souvent une List[Option[...]], par exemple après avoir tenté de parser des chaînes. flatten élimine les None et déballe les Some ; flatMap fait la même chose en une étape.

Ce motif « flatMap avec une fonction renvoyant Option » est l'idiome standard pour filtrer et transformer en même temps, sans null ni exception.

Un pipeline de données réaliste

Mettons tout en musique sur un cas concret : analyser une liste de ventes. Chaque vente a un produit, une catégorie et un montant. On veut le chiffre d'affaires par catégorie, trié du plus gros au plus petit.

Lis le pipeline de haut en bas comme une phrase : « groupe par catégorie, pour chaque groupe somme les montants, transforme en liste, trie par CA décroissant ». Le .view devant mapValues évite de matérialiser une Map intermédiaire ; -ca inverse l'ordre du tri. Note la forme { case (cat, ca) => ... } : pour déstructurer une paire dans une lambda, Scala demande un case entre accolades. Aucune boucle, aucun accumulateur mutable : ce code se relit dans six mois sans effort.

Lazy : LazyList

Toutes les collections vues jusqu'ici sont strictes : chaque map calcule tout immédiatement. Une LazyList est paresseuse : elle ne calcule un élément que lorsqu'on le demande. Cela permet des séquences potentiellement infinies.

Avec une List normale, List.from(1) chercherait à construire une infinité d'éléments et planterait. La LazyList ne produit que les 10 carrés réclamés par take(10). Utilise-la pour des flux, des générateurs ou des calculs coûteux dont tu ne veux qu'un préfixe.

Pièges fréquents

Piège fréquent

Les méthodes ne modifient pas la collection : elles en renvoient une nouvelle. liste.filter(...) seul ne sert à rien si tu n'affectes pas le résultat à un val. Pense toujours : « une transformation renvoie une valeur, je dois la récupérer ».

Deux autres écueils classiques. D'abord, head, last et reduce lèvent une exception sur une collection vide : privilégie headOption, lastOption et foldLeft. Ensuite, l'accès par index liste(i) sur une List est lent (il parcourt depuis le début) : si tu indexes souvent, choisis Vector.

Astuce

Quand tu enchaînes beaucoup d'opérations sur une grosse collection, glisse un .view au début et un .toList à la fin : les étapes intermédiaires deviennent paresseuses et tu évites de construire des collections temporaires à chaque maillon.

Pour aller plus loin

Pour aller plus loin

Ces mêmes méthodes (map, filter, groupBy, reduce) se retrouvent presque à l'identique dans Apache Spark, le moteur de big data écrit en Scala. Un pipeline qui tourne sur une List de quelques lignes se transpose sur un Dataset de milliards de lignes réparties sur un cluster. Apprendre les collections, c'est déjà apprendre Spark.

Cas réel

Cas réel

Le tableau de bord d'une boutique en ligne affiche « chiffre d'affaires par catégorie ». Derrière, c'est exactement le pipeline de cette leçon : groupBy(_.categorie), puis somme des montants, puis sortBy décroissant. Le même code, sans y toucher, passe d'une List de démonstration à un Dataset Spark de plusieurs milliards de ventes réparties sur un cluster — Netflix agrège ainsi ses journaux de visionnage. Maîtriser map/filter/groupBy, c'est déjà tenir la clé du big data.

Glossaire

Collection immuable
Structure qui ne change pas ; toute « modification » renvoie une nouvelle collection.
List / Vector
Séquences ordonnées ; List optimise head/tail, Vector l'accès par index.
Set / Map
Set = éléments uniques ; Map = associations clé → valeur.
map / filter / flatMap
Transformer chaque élément, en sélectionner, mapper puis aplatir.
Réduction (fold)
Combiner tous les éléments en une seule valeur via un accumulateur.
for-comprehension
Syntaxe for … yield … traduite en flatMap/map/withFilter.
Évaluation paresseuse
Calcul différé jusqu'à la demande ; LazyList autorise des séquences infinies.
:: (cons)
Ajoute un élément en tête d'une liste et renvoie une nouvelle liste.

Récap et vérification

  • Quatre collections immuables : List (séquentielle), Vector (indexée), Set (sans doublon), Map (clé/valeur).
  • Transformer plutôt que boucler : map, filter, flatMap décrivent le quoi, pas le comment.
  • Réduire avec sum, count, foldLeft (sûr sur collection vide) ou reduce.
  • Restructurer avec groupBy, partition, sortBy, zip, take/drop.
  • Interroger avec find (renvoie Option), exists, forall.
  • for-comprehensions (for x <- liste if cond yield ...) = sucre lisible pour flatMap/map/filter.
  • LazyList calcule à la demande : séquences infinies, on borne avec take.

Vérifie ta compréhension

  1. Quelle différence y a-t-il entre map et flatMap, et quand le second est-il utile ?
  2. Pourquoi préférer foldLeft(0)(...) à reduce(...) si la collection peut être vide ?
  3. Réécris liste.filter(_ > 0).map(_ * 2) sous forme de for ... yield.
  4. Que se passe-t-il si tu appelles .toList sur LazyList.from(1) sans take avant ?
