Module 3 · Scala en pratique — Leçon 11

sbt, tests et outillage

~50 min Avancé Prérequis : leçon 10

À la fin de cette leçon, tu sauras

  • savoir créer et lire un build.sbt et lancer compile, run, test, console ;
  • savoir écrire des tests avec ScalaTest et MUnit, et générer des cas avec ScalaCheck ;
  • savoir mener une courte session TDD et utiliser scala-cli pour un script ;
  • savoir activer les warnings du compilateur et formater/linter le code avec scalafmt et scalafix.
Sommaire de la leçon

Tu sais maintenant écrire du Scala idiomatique : val par défaut, expressions, pattern matching, classes et objets réconciliés. Mais un langage seul ne suffit pas : pour passer du fichier isolé au vrai projet — celui qu'on compile, qu'on teste, qu'on partage et qui finira peut-être à tourner sur un cluster Spark — il te faut un outillage. C'est le sujet de cette leçon.

On va voir le couteau suisse de l'écosystème : sbt, le build tool historique ; scala-cli, l'outil moderne et léger pour les scripts ; les bibliothèques de test (ScalaTest, MUnit, ScalaCheck) ; et enfin les outils qui font de ton compilateur et de ton formateur des alliés du quotidien. Rien d'abstrait : chaque section a son exemple que tu peux reproduire.

sbt : le build tool de Scala

Un build tool orchestre la compilation, la récupération des dépendances, le lancement des tests et l'exécution de ton programme. En Scala, l'outil de référence s'appelle sbt (pour « Scala Build Tool »). Toute sa configuration tient dans un fichier build.sbt, écrit… en Scala.

Le double %% est important : il dit à sbt d'aller chercher l'artefact compilé pour ta version de Scala. Le suffixe % Test indique que la dépendance n'est utile que pour les tests, pas pour le code de production.

sbt s'appuie sur une convention de répertoires héritée de Maven : le code de production va dans src/main/scala, les tests dans src/test/scala. Tu n'as rien à déclarer, sbt regarde au bon endroit.

Astuce

Lance sbt sans argument pour entrer dans le shell interactif, puis tape ~test. Le tilde relance les tests à chaque sauvegarde de fichier : une boucle de feedback continue, idéale en TDD.

scala-cli : l'outil moderne et léger

sbt est puissant mais lourd pour un simple script. Pour ça, l'écosystème a adopté scala-cli : un outil qui exécute, compile et package un fichier .scala isolé, sans aucune arborescence de projet. C'est aujourd'hui le point d'entrée recommandé pour apprendre et prototyper.

Les lignes //> using sont des directives lues par scala-cli : elles déclarent la version de Scala et les dépendances dans le fichier lui-même. Plus besoin de build.sbt.

Tests à propriétés avec ScalaCheck

Au lieu d'écrire des cas un par un, le property-based testing décrit une propriété qui doit toujours être vraie, puis laisse l'outil générer des centaines de cas aléatoires. ScalaCheck est le portage Scala de QuickCheck (né en Haskell), l'ancêtre de toutes ces bibliothèques.

ScalaCheck génère automatiquement des Int variés (y compris 0, négatifs, valeurs extrêmes). Si une propriété échoue, il réduit le cas fautif au plus petit contre-exemple — un confort précieux pour déboguer.

Note

Le ==> est l'implication de ScalaCheck : « si la condition de gauche est vraie, alors teste celle de droite ». Les cas qui ne satisfont pas la prémisse sont simplement écartés.

Une courte session TDD

Le TDD (Test-Driven Development) inverse l'ordre habituel : on écrit d'abord le test (qui échoue, étape rouge), puis le code minimal qui le fait passer (vert), puis on nettoie (refactor). Implémentons un fizzbuzz.

Le compilateur, scalafmt et scalafix

Le compilateur Scala est ton premier relecteur. En activant des options, il signale du code mort ou des API dépréciées avant même l'exécution. L'option -Wunused:all est particulièrement utile :

Pour la mise en forme, scalafmt réécrit ton code selon des règles partagées (un fichier .scalafmt.conf), éliminant les débats de style en équipe. Et scalafix va plus loin : c'est un outil de refactoring et de linting capable, par exemple, de supprimer les imports inutiles automatiquement.

Cas réel

Sur un projet en équipe, ces outils forment le garde-fou de l'intégration continue. À chaque push, la CI (GitHub Actions, GitLab CI…) enchaîne sbt test, scalafmt --check (le format est-il respecté ?) et scalafix --check : si l'un échoue, la fusion de la pull request est bloquée. Personne ne débat plus du placement des accolades, et aucun code non testé ne part en production — exactement le pipeline qui build et teste les jobs Spark avant leur déploiement sur le cluster.

Documenter avec Scaladoc

Enfin, on documente le code avec des commentaires Scaladoc, ouverts par /**. L'outil en génère un site HTML navigable, et ton IDE affiche ces descriptions au survol.

Pièges fréquents

Piège fréquent

Confondre % et %% dans libraryDependencies. Le double %% ajoute le suffixe de version Scala à l'artefact (ex. scalatest_3). Avec un simple % sur une lib Scala, sbt ne trouvera pas l'artefact et l'échec de résolution est déroutant.

Piège fréquent

Oublier le suffixe % Test sur une dépendance de test. Sans lui, ScalaTest se retrouve embarqué dans ton artefact de production : inutile, et plus lourd à livrer.

Pour aller plus loin

Pour aller plus loin

Un projet réel se découpe souvent en plusieurs sous-projets sbt (multi-module), partage des versions via un fichier Dependencies.scala, et tourne en intégration continue. Côté big data, Apache Spark se déclare comme une simple dépendance sbt : le même outillage te mène du script de la leçon 1 jusqu'au job distribué.

Glossaire

Build tool
Outil qui orchestre compilation, dépendances, tests et exécution ; en Scala, sbt.
build.sbt
Fichier de configuration d'un projet sbt, écrit en Scala : nom, version, scalaVersion, dépendances.
Maven Central
Dépôt public de bibliothèques de l'écosystème JVM, d'où sbt télécharge les dépendances déclarées.
scala-cli
Outil léger qui compile et exécute un fichier .scala isolé, dépendances déclarées par directives //> using, sans arborescence de projet.
Property-based testing
Test par propriété : on énonce une règle vraie pour toute entrée et l'outil (ScalaCheck) la confronte à de nombreux cas générés.
TDD
Test-Driven Development : cycle rouge (test qui échoue) → vert (code minimal) → refactor (nettoyage).
Matchers
Écriture expressive des assertions dans ScalaTest (should be, shouldBe) qui rend l'intention lisible.
scalafmt / scalafix
Formateur automatique (style unifié) et outil de refactoring/linting (imports inutiles, règles de code) de l'écosystème.

Récap et vérification

  • sbt compile, teste et exécute ; tout se configure dans build.sbt, avec la convention src/main / src/test.
  • scala-cli exécute un fichier isolé grâce aux directives //> using, sans projet.
  • On teste avec ScalaTest (styles + matchers), MUnit (minimaliste) ou ScalaCheck (propriétés et cas générés).
  • Le TDD écrit le test d'abord ; le compilateur (-Wunused), scalafmt, scalafix et Scaladoc complètent l'outillage.
