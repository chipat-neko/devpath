Option, Try et la gestion d'erreur

~50 min Avancé Prérequis : leçon 7

À la fin de cette leçon, tu sauras

  • savoir remplacer null par Option[T] et le manipuler avec map, getOrElse, flatMap et filter ;
  • savoir enchaîner plusieurs Option dans une for-comprehension qui court-circuite proprement sur None ;
  • savoir choisir entre Either[E, A] pour des erreurs avec contexte et Try[T] pour encapsuler du code qui lève ;
  • savoir préférer les valeurs d'erreur typées aux exceptions pour parser et valider une entrée utilisateur.
Sommaire de la leçon

Dans beaucoup de langages, l'absence de valeur se représente par null. Le problème : null est invisible dans le type. Une méthode qui renvoie un User peut très bien te rendre null, et tu ne le découvres qu'au moment du NullPointerException, à l'exécution, souvent loin de la cause. Tony Hoare, l'inventeur de null, l'a lui-même appelé « mon erreur à un milliard de dollars ».

Scala propose une autre voie : rendre l'absence et l'échec visibles dans le type. Au lieu d'espérer qu'une valeur soit là, tu manipules un conteneur qui dit honnêtement « il y a peut-être quelque chose » (Option), « c'est un succès ou une erreur décrite » (Either) ou « ce calcul a pu lever » (Try). Le compilateur t'oblige alors à traiter le cas qui manque. C'est le cœur de la gestion d'erreur fonctionnelle : l'erreur devient une valeur ordinaire, qu'on transforme et qu'on enchaîne comme les autres.

Option : l'absence rendue visible

Option[T] a exactement deux formes : Some(x) quand la valeur existe, None quand elle est absente. Le type t'avertit qu'il faudra gérer les deux. Beaucoup de méthodes de la bibliothèque standard renvoient déjà un Option plutôt qu'un null ou une exception.

Option(x) est le pont sûr depuis le monde de null : Option(null) donne None.

Note

Distingue Option(x) et Some(x). Some(x) emballe toujours, même un null (et tu te retrouves avec un piégeux Some(null)). Option(x) regarde si x est null et choisit Some ou None pour toi. À l'interface avec du code Java, utilise Option(...).

Transformer sans déballer : map, getOrElse, filter

L'intérêt d'un Option, c'est qu'on travaille à l'intérieur sans le casser. map applique une fonction à la valeur si elle existe, et ne fait rien sur None. getOrElse fournit une valeur de repli pour sortir du conteneur. filter retient la valeur seulement si elle passe un test, sinon None.

Tu décris la transformation ; le conteneur se charge de ne rien faire quand il n'y a rien.

Astuce

Évite .get sur un Option : il lève une exception sur None et te ramène exactement aux ennuis de null. Préfère getOrElse, map ou le pattern matching. Si tu vois .get dans ton code, c'est presque toujours un signal d'alarme.

flatMap : enchaîner des étapes qui peuvent échouer

Quand une étape renvoie elle-même un Option, map t'imbrique un Option[Option[...]], peu pratique. flatMap « aplatit » le résultat : il enchaîne deux opérations faillibles et s'arrête net dès la première qui rend None.

flatMap court-circuite : si parseInt rend None, la recherche dans la Map n'est même pas tentée.

Pattern matching sur Option

Parfois tu veux explicitement traiter les deux cas avec des branches lisibles. Le pattern matching déconstruit l'Option et lie la valeur interne directement.

Le compilateur sait qu'un Option n'a que deux formes : il te prévient si tu oublies un cas.

For-comprehension : enchaîner plusieurs Options proprement

Empiler les flatMap devient vite illisible. La for-comprehension est du sucre syntaxique qui se traduit en flatMap/map : chaque <- déballe un Option, et si l'un d'eux est None, tout le bloc rend None sans exécuter la suite. Le résultat se lit comme une séquence d'étapes, mais le court-circuit est gratuit.

Trois étapes faillibles, une lecture linéaire, et un seul None en sortie quelle que soit l'étape qui a échoué. Option.when(cond)(v) donne Some(v) si cond, sinon None.

Either : une erreur qui dit pourquoi

None est honnête mais muet : il ne dit pas quoi a échoué. Either[E, A] porte deux types : par convention Left(e) contient l'erreur (souvent un message ou un type d'erreur), Right(a) contient le succès (moyen mnémotechnique : « right » = correct). On l'utilise quand le pourquoi de l'échec compte, par exemple pour répondre à un utilisateur.

Comme pour Option, map et flatMap travaillent sur le succès (Right) et laissent l'erreur (Left) intacte : l'échec se propage avec son message.

Try : encapsuler du code qui lève

Tout le code ne renvoie pas des Option bien rangés. Certaines API (souvent venues de Java) lèvent des exceptions. Try[T] capture ce risque : Success(x) pour le résultat, Failure(e) pour l'exception attrapée. Tu transformes une exception en valeur, puis tu l'enchaînes comme une Option.

Try(bloc) exécute le bloc et range automatiquement une éventuelle exception dans Failure.

Exceptions vs valeurs d'erreur typées

Scala garde try/catch (il tourne sur la JVM), mais l'idiome fonctionnel préfère les valeurs d'erreur typées. Pourquoi ? Une exception est invisible dans la signature : rien ne t'oblige à la gérer, et elle interrompt le flot par un saut. Un Option/Either/Try apparaît dans le type de retour : le compilateur te force à traiter l'échec, et tu l'enchaînes avec map/flatMap au lieu de l'attraper plus loin.

toRight(err) convertit un Option en Either : Some(v) devient Right(v), None devient Left(err). La règle pratique : réserve les exceptions aux pannes vraiment exceptionnelles (bug, ressource indisponible) ; pour tout ce qui est attendu (entrée invalide, valeur absente), renvoie une valeur typée.

Exemple complet : parser et valider une entrée

Réunissons tout. On reçoit du texte brut (nom et âge), on le valide étape par étape, et l'on rend soit un objet propre, soit le premier message d'erreur. La for-comprehension sur Either court-circuite dès le premier Left.

Aucune exception, aucune pyramide de if imbriqués : chaque validation rend un Either, et le premier échec rencontré ressort tel quel avec son message.

Cas réel

Ce schéma est le standard des API web modernes en Scala. Un point d'entrée HTTP (avec des bibliothèques comme http4s ou Play) modélise sa réponse par un Either[Erreur, Resultat] : un Left se traduit en réponse HTTP 400 avec le message d'erreur en JSON, un Right en réponse 200 avec les données. Le compilateur garantit qu'aucune branche d'erreur n'est oubliée avant d'envoyer la réponse. La même idée a essaimé dans les langages récents : Optional en Swift, Option/Result en Rust, les types nullable et Result de Kotlin — tous nés du constat de Tony Hoare sur le « milliard de dollars » qu'a coûté null.

Pièges fréquents

Piège fréquent

Appeler .get sur un Option pour « sortir vite » la valeur. Sur None, ça lève NoSuchElementException et tu perds tout le bénéfice du typage. Même chose avec .head sur une liste vide. Utilise toujours getOrElse, map, fold ou le pattern matching.

Piège fréquent

Mélanger les types dans une même for-comprehension. Un for ne peut enchaîner que des conteneurs du même genre : que des Option, ou que des Either (avec le même type d'erreur). Pour passer de l'un à l'autre, convertis d'abord avec toRight, toOption ou toEither.

Piège fréquent

Croire que Some(null) est sûr. Some(x) emballe sans vérifier : si x vaut null, tu obtiens un Some(null) qui repassera tes tests d'existence et explosera plus tard. Depuis l'extérieur (interop Java), construis toujours avec Option(x).

Pour aller plus loin

Pour aller plus loin

fold traite les deux cas en une expression : sur Option, opt.fold("défaut")(v => v.toString) ; sur Either, e.fold(err => ..., ok => ...). Quand tu veux cumuler toutes les erreurs d'un formulaire au lieu de t'arrêter à la première, regarde le type Validated de la bibliothèque Cats. Et pour des effets faillibles asynchrones (appels réseau, base de données), cats-effect ou ZIO généralisent ces idées au monde concurrent.

Antisèche

Glossaire

Option[T]
Conteneur à deux cas, Some(x) ou None, qui rend l'absence visible dans le type et remplace null.
Some / None
Les deux formes d'un Option : valeur présente ou absente.
Either[E, A]
Résultat à deux voies : Left(e) pour l'erreur décrite, Right(a) pour le succès.
Try[T]
Capture d'un calcul qui peut lever : Success(x) ou Failure(exception).
getOrElse
Extrait la valeur d'un Option, ou renvoie un repli si None.
For-comprehension
Sucre for … yield … qui enchaîne des conteneurs et court-circuite au premier échec.
Court-circuit
Arrêt d'une chaîne dès qu'une étape échoue (None/Left), sans exécuter la suite.
Valeur d'erreur typée
Échec représenté par une valeur dans le type de retour, que le compilateur force à traiter (vs exception).

Récap et vérification

  • Option[T] remplace null : Some(x) ou None, l'absence devient visible dans le type.
  • map transforme la valeur, flatMap enchaîne une étape qui rend elle-même un Option, filter conditionne, getOrElse fournit un repli.
  • La for-comprehension enchaîne plusieurs Option (ou Either) et court-circuite dès le premier échec.
  • Either[E, A] ajoute le pourquoi de l'erreur (Left) ; Try[T] capture les exceptions (Failure) en valeur.
  • Idiome Scala : erreurs attendues en valeurs typées, exceptions réservées aux pannes vraiment exceptionnelles.

Vérifie ta compréhension

  1. Quelle est la différence entre Some(x) et Option(x) quand x peut valoir null ?
  2. Dans une for-comprehension qui enchaîne trois Option, que se passe-t-il si la deuxième étape rend None ? La troisième est-elle exécutée ?
  3. Tu dois valider une entrée et expliquer à l'utilisateur pourquoi elle est rejetée. Choisis-tu Option, Either ou Try, et pourquoi ?

Exercices

Exercice 1Échauffement

Écris une fonction premierMot(phrase: String): Option[String] qui rend le premier mot d'une phrase, ou None si la phrase est vide (ou seulement des espaces). Teste-la sur "bonjour le monde", " " et "".

Voir une solution

headOption rend None sur une collection vide au lieu de lever : c'est la version sûre de head.

Exercice 2Application

On a une Map[String, Int] de stocks par produit. Écris retirer(stock, produit, n): Either[String, Int] qui rend le nouveau stock si le produit existe et qu'il reste assez d'unités, sinon un Left expliquant le problème (produit inconnu, ou stock insuffisant). Utilise une for-comprehension.

Voir une solution

Option.toRight transforme l'absence en Left ; Either.cond(test, ok, err) rend Right(ok) ou Left(err) selon le test.

Exercice 3Défi

Écris moyenne(lignes: List[String]): Either[String, Double]. Chaque ligne devrait contenir un entier. Si une ligne n'est pas un entier, rends un Left qui la nomme. Si la liste est vide, rends Left("aucune valeur"). Sinon rends la moyenne dans un Right. Indice : traverse peut convertir une List[Either] en Either[List], mais ici tu peux le faire à la main avec foldLeft.

Voir une solution

Le foldLeft enchaîne les Either : tant que tout va bien on accumule la liste des entiers ; dès qu'une ligne échoue, le Left se propage et stoppe l'accumulation.
