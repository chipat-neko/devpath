Pattern matching

~50 min Avancé Prérequis : leçon 6

À la fin de cette leçon, tu sauras

  • savoir écrire un match qui filtre des valeurs littérales, des types et des structures avec déstructuration ;
  • savoir utiliser les gardes, le wildcard _ et les bindings (case c @ Motif) pour affiner un cas ;
  • savoir garantir l'exhaustivité grâce aux sealed trait et laisser le compilateur repérer un cas manquant ;
  • savoir déstructurer dans un val et un for, et construire un évaluateur d'expressions arithmétiques.
Sommaire de la leçon

Si tu retiens une seule chose de Scala, ce sera peut-être celle-ci. Le pattern matching est le joyau du langage : il ressemble de loin au switch de Java, mais il va infiniment plus loin. Là où un switch compare des valeurs, un match Scala décompose des données : il regarde leur forme, en extrait les morceaux, vérifie des conditions, et tout cela en restant une expression qui produit une valeur.

Dans cette leçon, on part des bases (matcher une valeur) pour arriver au cœur de la programmation fonctionnelle objet : déstructurer des case class, garantir qu'aucun cas n'est oublié, et construire un petit évaluateur d'expressions arithmétiques qui te servira de fil rouge. Tu verras que c'est à la fois plus lisible et plus sûr qu'une cascade de if/else.

Le match, une expression qui renvoie une valeur

Première surprise pour qui vient de Java : match n'est pas une instruction, c'est une expression. Chaque branche produit une valeur, et le match entier vaut la valeur de la branche retenue. Pas de break, pas de fallthrough : dès qu'un cas correspond, c'est fini.

Le _ est le wildcard : il attrape tout ce qui n'a pas été pris avant. Comme match renvoie une valeur, on peut l'affecter directement à une val ou la retourner depuis une fonction, sans variable temporaire.

Note

On utilise ici la syntaxe à indentation de Scala 3 (pas d'accolades autour du match). Tu peux aussi écrire couleur match { case ... } avec des accolades : les deux sont valides. Choisis ce qui reste lisible.

Matcher sur le type

Un case peut tester le type d'une valeur et lier le résultat à un nom, déjà transtypé. Plus besoin de instanceof suivi d'un cast comme en Java : le motif x: String fait les deux d'un coup.

Dans case n: Int, le nom n est de type Int dans la branche. On voit aussi apparaître une garde avec if b : on y revient en détail plus bas. Et case autre (un simple nom sans type) joue le rôle de wildcard nommé : il attrape tout en gardant accès à la valeur.

Déstructurer une case class

C'est ici que le pattern matching devient irremplaçable. Une case class peut être déconstruite : le motif rappelle le constructeur, mais au lieu de fournir des valeurs, on en extrait. Mettons en place le décor de notre fil rouge avec quelques formes géométriques.

Dans case Cercle(r), le rayon stocké dans l'objet est extrait et lié au nom r. C'est de la déstructuration : une seule ligne pour reconnaître la forme et sortir ses champs. Compare avec l'équivalent en if/else qui exigerait un test de type puis un accès .rayon manuel à chaque fois.

Gardes, wildcard et bindings

Trois outils affinent les motifs. La garde (if condition) ajoute une vérification booléenne : le cas ne s'applique que si le motif correspond et que la garde est vraie. Le wildcard _ ignore un morceau dont on ne veut pas le nom. Le binding nom @ motif capture la valeur entière tout en vérifiant sa forme.

Détaille la deuxième ligne : c @ Cercle(_) dit « n'importe quel Cercle, dont je ne regarde pas le rayon (_), mais je veux l'objet entier sous le nom c ». Le binding est précieux quand tu veux à la fois vérifier la forme et réutiliser l'objet tel quel.

Piège fréquent

Un nom qui commence par une minuscule dans un motif est un binding qui attrape tout, pas une comparaison à une variable existante. Pour comparer à la valeur d'une variable seuil, écris case `seuil` (avec les accents graves) ou une garde case x if x == seuil.

Tuples et listes

Les motifs s'appliquent aussi aux tuples et aux listes. Un tuple se déstructure par position ; une liste se décompose avec :: (tête et reste) et Nil (liste vide). C'est le cœur du traitement récursif des collections.

Lis case tete :: reste comme « une liste dont le premier élément est tete et le reste est reste ». Quand on tombe sur Nil, la récursion s'arrête. Ce schéma « cas de base + cas récursif » est l'archétype fonctionnel du parcours de liste.

Exhaustivité sur un sealed trait : la sûreté

Voici l'argument décisif face aux if/else. Un sealed trait ne peut être étendu que dans le même fichier : le compilateur connaît donc toutes ses sous-classes. Quand tu fais un match dessus, il vérifie que tu as couvert chaque cas ; s'il en manque un, il te prévient à la compilation.

Ce filet de sécurité est inestimable : le jour où tu ajoutes une nouvelle forme Triangle au trait, le compilateur te signale chaque match à compléter, partout dans le projet. Aucune branche oubliée silencieuse. C'est une garantie qu'une cascade de if/else ne t'offrira jamais.

Astuce

Réserve le case _ attrape-tout aux situations où tu veux vraiment ignorer le reste. Sur un sealed trait, l'éviter laisse le compilateur t'avertir des cas manquants : tu transformes un oubli en erreur de compilation plutôt qu'en bug à l'exécution.

Déstructurer dans un val et dans un for

Le pattern matching n'est pas réservé au match. Il fonctionne partout où Scala attend une liaison de noms : dans une val et dans un for. C'est la façon idiomatique d'extraire les composantes d'un tuple ou d'une case class.

Dans le for, le motif (x, y) déstructure chaque tuple de la liste à la volée : c'est plus clair que d'accéder à p._1 et p._2. Pour le val Cercle(monRayon), le motif est ici sûr car Cercle a un seul constructeur. Avec un motif qui pourrait ne pas correspondre (par exemple déstructurer une Forme générale en Cercle), le compilateur t'avertit : ajoute alors : @unchecked au côté droit pour assumer le risque, comme dans val Cercle(r) = (f: Forme): @unchecked.

Fil rouge : un évaluateur d'expressions

Rassemblons tout. On modélise des expressions arithmétiques par un sealed trait, puis on les évalue par récursion sur leur structure. C'est l'exemple canonique où le pattern matching brille : chaque cas du match correspond à un nœud de l'arbre.

Remarque comme la déstructuration rend le code limpide : case Add(g, d) nomme directement les deux sous-expressions, qu'on évalue récursivement. Le trait étant sealed, si tu ajoutes un cas Sub sans compléter evaluer, le compilateur te le rappelle aussitôt. L'évaluateur est à la fois court, lisible et sûr : c'est exactement la réconciliation de l'objet (les case classes) et du fonctionnel (le filtrage) que promet Scala.

Cas réel

Cet évaluateur n'est pas un jouet : c'est l'architecture des vrais moteurs. Spark SQL (le moteur d'analyse de données massives d'Apache) représente chaque requête SQL par un arbre d'expressions du même genre, puis son optimiseur Catalyst applique des règles par pattern matching sur cet arbre — remplacer x + 0 par x, réordonner des filtres, etc. Les compilateurs, les moteurs de règles métier, les linters (ESLint) et les formateurs de code (Prettier) reposent tous sur le même principe : modéliser en ADT, transformer par match. Ce que tu viens d'écrire en vingt lignes est la brique de base de ces outils.

Pièges fréquents

  • Le nom minuscule capture au lieu de comparer. case pi => ... attrape toute valeur dans pi, il ne la compare pas à une constante pi. Utilise les accents graves case `pi` ou une garde.
  • Oublier que match est une expression. Toutes les branches doivent renvoyer un type compatible. Si une branche renvoie un Int et une autre un String, le type commun déduit sera Any ou Matchable, rarement ce que tu veux.
  • Court-circuiter l'exhaustivité avec case _. Sur un sealed trait, un attrape-tout désactive l'avertissement de cas manquant et masque les futurs oublis. Ne l'ajoute que si tu en as vraiment besoin.
  • Ordre des cas. Les motifs sont essayés de haut en bas : place les cas spécifiques (avec gardes) avant les cas généraux, sinon le général les masque.

Pour aller plus loin

Pour aller plus loin

Le pattern matching repose sur la méthode unapply (les extracteurs) : les case classes en fournissent une gratuitement, mais tu peux écrire la tienne pour déstructurer n'importe quel objet. Explore aussi le filtrage sur Option (case Some(x) / case None), omniprésent en Scala, et les motifs de séquence comme case List(a, b, _*) pour les premiers éléments d'une liste.

Glossaire

Pattern matching
Filtrer une valeur selon sa forme, en extraire les morceaux et produire un résultat — le tout comme expression.
Motif (pattern)
Gabarit décrivant la forme attendue : littéral, type, déconstruction, tuple, liste.
Déstructuration
Extraire les champs d'une case class, d'un tuple ou d'une liste directement dans le motif.
Garde
Condition if ajoutée à un cas ; il ne s'applique que si le motif correspond ET la garde est vraie.
Wildcard _
Motif attrape-tout, ou trou pour ignorer un champ qu'on ne veut pas nommer.
Binding (@)
Lier l'objet entier à un nom tout en vérifiant sa forme : c @ Cercle(_).
Exhaustivité
Garantie qu'un match couvre tous les cas d'un sealed trait ; vérifiée à la compilation.
Extracteur (unapply)
Méthode qui déconstruit un objet ; fournie gratuitement par les case classes.

Récap et vérification

  • match est une expression qui renvoie une valeur ; chaque case est un motif testé de haut en bas.
  • On matche sur des valeurs, des types (case s: String), et on déstructure case classes, tuples et listes (case head :: tail).
  • Les gardes (if), le wildcard _ et les bindings (c @ Motif) affinent les motifs.
  • Un sealed trait donne l'exhaustivité : le compilateur signale tout cas manquant.
  • La déstructuration marche aussi dans val (a, b) = ... et dans les for.

Vérifie ta compréhension

  1. Quelle est la différence entre case x et case `x` dans un motif ?
  2. Pourquoi le compilateur peut-il vérifier l'exhaustivité sur un sealed trait mais pas sur un trait ordinaire ?
  3. Comment lirais-tu à voix haute le motif case Rectangle(l, h) if l == h ?
