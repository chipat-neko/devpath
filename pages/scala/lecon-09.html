Module 3 · Scala en pratique — Leçon 09

Génériques et given/using

~55 min Avancé Prérequis : leçon 8

À la fin de cette leçon, tu sauras

  • écrire des classes et fonctions génériques avec bornes et un survol de la variance +A / -A ;
  • fournir et requérir des valeurs implicites avec given et using ;
  • implémenter une type classe (ex. Ordering) et trier de façon générique ;
  • ajouter des méthodes à un type existant avec une extension method.
Sommaire de la leçon

Tu sais déjà manipuler des classes et des fonctions en Scala. Il manque deux pièces pour écrire du code vraiment réutilisable : les génériques (du code qui marche pour n'importe quel type) et les given/using (le mécanisme par lequel Scala fournit automatiquement le bon comportement au bon endroit). Ensemble, ils donnent le polymorphisme ad-hoc : la capacité d'ajouter un comportement à un type sans le modifier ni en hériter.

C'est l'un des traits les plus distinctifs de Scala, et celui qui fait tourner des bibliothèques entières (Cats, ZIO, et même les collections standard). On part du concret : une boîte générique, puis le tri d'une liste sans coder le tri pour chaque type. Tu vas voir que ces deux idées se répondent.

Génériques : du code qui ne connaît pas son type

Un type générique est un paramètre noté entre crochets, par convention une lettre majuscule comme A. La classe ou la fonction est écrite une fois et fonctionne pour tous les types.

Remarque que tu n'écris jamais Boite[String] ni premier[Int] à l'appel : le compilateur infère le type depuis l'argument. Le code reste sûr (un Boite[Int] ne peut pas contenir une String) sans verbosité.

Bornes : exiger une capacité du type

Un type générique pur ne sait rien faire de sa valeur : A pourrait être n'importe quoi. Parfois tu veux exiger que A possède une certaine capacité. Une borne supérieure A <: T impose que A soit un sous-type de T.

La borne <: est une promesse vérifiée à la compilation : à l'intérieur de maxDe, tu as le droit d'appeler compareTo parce que tu as exigé que A le fournisse. Tu verras bientôt une approche plus souple que cet héritage : les type classes.

Variance : un survol clair

Question : si Chat est un sous-type d'Animal, est-ce qu'un Boite[Chat] est un sous-type de Boite[Animal] ? Par défaut, non — les génériques sont invariants. La variance permet de choisir. Un +A rend le type covariant (suit le sens du sous-typage), un -A le rend contravariant (sens inverse).

Retiens la règle de pouce : un conteneur qui ne fait que produire des A (on en sort des valeurs) est covariant +A ; un type qui consomme des A (on en reçoit, comme une fonction A => ...) est contravariant -A. Tu n'as pas besoin de la maîtriser tout de suite : sache la reconnaître quand tu la croises dans List[+A] ou Function1[-A, +B].

given/using : passer une valeur implicitement

Voici LE concept Scala. Un paramètre using est un paramètre que tu ne passes pas à la main : le compilateur cherche dans le contexte une valeur given du bon type et l'injecte pour toi. (En Scala 2, on appelait ça les implicits ; Scala 3 a séparé les deux mots-clés pour plus de clarté.)

Ce n'est pas une variable globale magique : la valeur given doit être visible (dans la portée ou importée). Si aucune n'est trouvée, le code ne compile pas — l'erreur t'oblige à fournir ce qui manque. C'est sûr et explicite, juste sans le bruit de répéter le même argument partout.

Note

Un given peut être anonyme : given String = "EUR" suffit, le nom devise est optionnel et sert surtout à la lisibilité. La recherche se fait par type, pas par nom.

Type classes : le tri générique sans héritage

Le vrai usage des given/using, ce sont les type classes. Idée : au lieu de demander à un type d'hériter d'une interface (impossible pour Int ou pour une classe Java que tu ne contrôles pas), tu fournis séparément une instance qui décrit le comportement. La bibliothèque standard en a déjà une parfaite : Ordering[A], qui dit comment ordonner des A.

Tout se joue ici : trier ne connaît rien de A, mais le paramètre using ord: Ordering[A] dit « donne-moi quelqu'un qui sait comparer des A ». Pour Int et String, Scala a déjà des given tout prêts ; pour Personne, tu as fourni le tien. Aucune classe n'a eu besoin d'hériter de quoi que ce soit.

Astuce

La forme courte def trier[A : Ordering](xs: List[A]) (appelée context bound) est strictement équivalente au using ord: Ordering[A]. Tu récupères l'instance par summon[Ordering[A]] si tu en as besoin nommément.

Cas réel

Un tableau de bord affiche une table de clients. L'utilisateur clique sur l'en-tête « Nom », puis « Date d'inscription », puis « Chiffre d'affaires » : trois tris différents sur les mêmes données. Avec l'héritage, la classe Client n'a qu'un seul ordre naturel — impossible. Avec les type classes, tu déclares un Ordering par colonne (Ordering.by(_.nom), Ordering.by(_.date)…) et tu passes celui que l'utilisateur a choisi à .sorted. C'est très exactement le mécanisme des tables triables des UI et des ORDER BY combinés d'un ORM comme Slick, où chaque colonne fournit son propre given Ordering.

Extension methods : ajouter une méthode à un type existant

Dernier outil du même esprit : ajouter une méthode à un type que tu ne possèdes pas, comme Int ou String, sans le modifier. C'est le mot-clé extension.

Le compilateur réécrit 5.carre en carre(5) : il n'y a aucune modification de la classe Int, juste du sucre syntaxique résolu à la compilation. C'est ce qui permet aux bibliothèques d'offrir des méthodes .map, .show, etc. sur des types qu'elles n'ont pas écrits.

Pourquoi les given remplacent l'héritage

Avec l'héritage classique, pour qu'un type ait un comportement, il doit déclarer au moment de sa définition qu'il implémente une interface. Impossible donc pour Int, pour une classe Java tierce, ou pour donner deux comportements différents (trier des Personne par âge ici, par nom ailleurs). Les given/using découplent le comportement du type : l'instance vit à côté, on en fournit autant qu'on veut, et le compilateur choisit la bonne par le type. C'est ça, le polymorphisme ad-hoc — et c'est pourquoi tout l'écosystème fonctionnel de Scala est bâti dessus.

Pièges fréquents

Piège fréquent

Un given doit être dans la portée pour être trouvé. S'il est défini dans un autre fichier ou objet, il faut souvent l'importer : import monModule.given. L'erreur « no given instance of type Ordering[X] » veut presque toujours dire « tu n'as pas importé / défini l'instance », pas « c'est impossible ».

Deux autres pièges classiques. D'abord, ne mets pas deux given ambigus du même type dans la même portée : le compilateur ne saura pas lequel choisir et refusera (« ambiguous given instances »). Ensuite, n'abuse pas des given pour passer des valeurs « ordinaires » (un Int de configuration, par exemple) : réserve-les aux comportements (un Ordering, un encodeur JSON). Un given Int traîné partout rend le code illisible et fragile.

Pour aller plus loin

Pour aller plus loin

Les type classes sont le socle de bibliothèques comme Cats (avec Monoid, Functor, Show...) et des dérivations automatiques de codecs JSON dans circe. Dans le monde du big data, Spark s'appuie sur des given Encoder[A] pour sérialiser tes case class dans un Dataset[A] typé. Le réflexe « j'ai besoin d'un comportement pour un type → je fournis un given » te suivra partout.

Antisèche

Glossaire

Générique (paramètre de type)
Un type-variable noté entre crochets ([A]) qui rend une classe ou une fonction réutilisable pour n'importe quel type, tout en restant vérifiée à la compilation.
Inférence de type
Déduction automatique du type par le compilateur à partir des arguments : on écrit premier(List(1,2,3)), pas premier[Int](…).
Borne (<:)
Contrainte sur un paramètre de type ; A <: T exige que A soit un sous-type de T, autorisant l'usage des membres de T.
Variance (+A / -A)
Règle qui décide si le sous-typage d'un type se propage à son conteneur : covariant (+A), contravariant (-A) ou invariant (par défaut).
given
Déclaration d'une valeur (souvent une instance de type classe) mise à disposition du compilateur pour remplir les paramètres using.
using
Paramètre implicite : la fonction déclare en avoir besoin, le compilateur l'injecte en cherchant un given du bon type dans la portée.
Type classe
Motif qui découple un comportement d'un type : on fournit séparément une instance (ex. Ordering[A]) au lieu de faire hériter le type d'une interface.
Extension method
Méthode ajoutée à un type existant via extension, résolue à la compilation, sans modifier ni hériter de ce type.
Polymorphisme ad-hoc
Capacité d'ajouter un comportement à un type sans le modifier ni en hériter, obtenue en Scala par les given/using et les type classes.

Récap et vérification

  • Les génériques [A] écrivent du code une fois pour tous les types, avec inférence à l'appel.
  • Une borne A <: T exige que A soit un sous-type de T ; la variance +A / -A décide du sous-typage du conteneur.
  • Un given fournit une valeur dans le contexte ; un paramètre using la réclame et le compilateur l'injecte par type.
  • Une type classe (ex. Ordering[A]) découple comportement et type : tu fournis une instance given, la fonction la requiert via using.
  • Les extension methods ajoutent des méthodes à un type existant sans le modifier.

Vérifie ta compréhension

  1. Pourquoi premier(List(1,2,3)) n'a-t-il pas besoin qu'on écrive premier[Int] ?
  2. Quelle est la différence entre given et using dans la même fonction ?
  3. Pour trier une List[Personne] par nom plutôt que par âge, que faut-il changer — et pourquoi est-ce impossible à faire proprement avec de l'héritage seul ?
