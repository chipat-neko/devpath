Module 4 · Scala avancé — Leçon 15

Type classes : la polymorphie avec given/using

~52 min Avancé Prérequis : leçon 9

À la fin de cette leçon, tu sauras

  • expliquer ce qu'est une type class et le polymorphisme ad hoc ;
  • définir un trait paramétré et fournir des instances avec given ;
  • requérir une instance avec using et l'appeler via une extension method ;
  • ajouter un comportement à n'importe quel type, même sans en posséder le code.
Sommaire de la leçon

Tu as croisé given/using à la leçon 9 pour passer des dépendances sans les épeler. C'était la première marche vers un motif central de Scala : la type class. L'idée : donner un comportement (afficher, comparer, sérialiser) à un type sans le modifier ni hériter de quoi que ce soit. Même à un type que tu n'as pas écrit, comme Int ou une classe d'une bibliothèque tierce.

Le problème : ajouter un comportement de l'extérieur

En orienté objet « classique », pour qu'un type sache s'afficher joliment, on lui fait implémenter une interface : class Produit extends Affichable. Mais c'est intrusif — il faut posséder et modifier la classe — et impossible sur Int, String ou un type venu d'une lib. La type class renverse la logique : le comportement vit à côté du type, dans une valeur séparée que le compilateur va chercher pour toi.

Anatomie d'une type class

Trois pièces : (1) un trait paramétré qui décrit la capacité ; (2) des instances given, une par type concerné ; (3) un point d'usage qui requiert l'instance avec using.

Rendre l'appel naturel : les extension methods

Écrire afficher(x) fonctionne, mais on préfère la syntaxe pointée x.show, comme si la méthode appartenait au type. Une extension method l'ajoute « par-dessus », en s'appuyant sur l'instance de type class disponible.

Astuce — l'absence d'instance est une erreur à la compilation

Si aucun given Show[Double] n'est en portée, 3.14.show ne compile pas : le manque est détecté avant l'exécution, pas sous forme de crash. C'est toute la force du polymorphisme ad hoc typé : le compilateur vérifie que la capacité existe pour ce type précis.

Sur ses propres types

La même mécanique s'applique à une case class. On fournit l'instance given à côté du type, souvent dans son companion object pour qu'elle soit trouvée automatiquement.

given/using, l'héritage de implicit

En Scala 2, ce motif s'écrivait avec le mot-clé fourre-tout implicit (implicit val, implicit def, paramètre implicit). Scala 3 l'a scindé en deux intentions claires : given pour fournir une instance, using pour en réclamer une. Tu rencontreras encore implicit dans du code existant : c'est le même concept.

Déjà dans la bibliothèque : Ordering

Tu utilises des type classes sans le savoir. sorted exige un Ordering[A] — une type class fournie d'office pour les types usuels. Pour trier tes propres objets, tu fournis l'instance, exactement comme pour Show.

Cas réel — la sérialisation JSON

C'est l'usage phare des type classes en Scala. Les bibliothèques JSON (Circe, uPickle, zio-json) reposent dessus : un given Encoder[A] décrit comment transformer un A en JSON. Le compilateur assemble l'encodeur d'une case class à partir de ceux de ses champs — automatiquement.

Pour aller plus loin — la dérivation automatique

Écrire l'instance d'une case class à la main est répétitif. Scala 3 sait la dériver tout seul : case class Produit(...) derives Encoder génère l'instance à la compilation à partir de la structure du type. C'est ce que font Circe & co pour t'éviter d'écrire un seul encodeur — la métaprogrammation au service de la concision.

Attention — l'ambiguïté des instances

Si deux given Show[Int] se trouvent en portée en même temps, le compilateur ne sait pas lequel choisir et refuse de compiler (ambiguous given). La règle d'or : une seule instance canonique par type, rangée dans le companion object du type ou dans un objet qu'on importe explicitement. N'éparpille pas tes given.

Glossaire

Type class
Motif où un comportement est défini à part du type, dans un trait paramétré, et fourni par des instances ; permet d'étendre un type sans le modifier.
Polymorphisme ad hoc
Capacité d'un même appel (show) à se comporter différemment selon le type, la bonne implémentation étant choisie à la compilation.
given
Déclare une instance de type class que le compilateur pourra fournir automatiquement (remplace l'implicit val/def de Scala 2).
using
Marque un paramètre comme requis mais résolu automatiquement par le compilateur à partir des given en portée.
Extension method
Méthode ajoutée à un type existant « de l'extérieur » (extension (a: A) def …), sans hériter ni modifier ce type.
Résolution implicite
Recherche, par le compilateur, de l'instance given du bon type dans la portée ; échoue à la compilation si aucune (ou plusieurs) n'est trouvée.
Ordering[A]
Type class standard décrivant l'ordre d'un type ; exigée par sorted, min, max.
Dérivation
Génération automatique d'une instance de type class à partir de la structure d'un type (derives en Scala 3).

Récap et vérification

  • Une type class associe un comportement à un type sans le modifier : idéal pour Int ou un type tiers.
  • Trois pièces : un trait paramétré, des instances given, un point d'usage using.
  • Une extension method offre l'appel pointé x.show ; l'absence d'instance est une erreur de compilation.
  • Ordering et les encodeurs JSON (Circe) sont des type classes que tu utilises déjà.

Vérifie ta compréhension

  1. Pourquoi une type class peut-elle donner un comportement à Int, contrairement à l'héritage ?
  2. Quelle est la différence de rôle entre given et using ?
  3. Que se passe-t-il si aucune instance Show[Double] n'est en portée quand tu écris 3.14.show ?

Exercices

Exercice 1Échauffement

On te donne trait Show[A]: def show(a: A): String. Écris l'instance given Show[Boolean] qui renvoie "oui" pour true et "non" pour false.

Voir une solution

Une instance given n'est rien d'autre qu'une valeur qui implémente le trait pour un type précis. Ici le type est Boolean : le compilateur saura désormais « montrer » un booléen partout où un Show[Boolean] est requis.

Exercice 2Application

Tu veux trier une List[Produit] (nom, prix) par prix décroissant. Fournis le bon given Ordering[Produit] et appelle sorted.

Voir une solution

On construit l'ordre à partir du champ prix avec Ordering.by, puis on l'inverse avec .reverse. Aucun besoin de faire hériter Produit d'une interface : l'ordre est une instance externe que sorted réclame via using. Changer de critère de tri ne touche jamais la case class.

Exercice 3Défi

Écris une fonction afficherListe[A](xs: List[A])(using Show[A]): String qui rend une chaîne du style [a, b, c] où chaque élément est passé par show. Elle doit marcher pour List[Int] comme pour List[Produit], sans code dupliqué.

Voir une solution

La signature [A](xs: List[A])(using Show[A]) dit : « je fonctionne pour tout type A, à condition qu'il sache se montrer ». C'est le cœur du polymorphisme ad hoc : un unique corps générique, spécialisé à la compilation par l'instance Show[A] que le compilateur injecte. On combine ainsi la généricité (leçon 9) et la type class : la première dit « n'importe quel A », la seconde impose « pourvu qu'il ait telle capacité ».
