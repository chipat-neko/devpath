Asynchrone : Future et async/await

~55 min Avancé Prérequis : leçon 6

À la fin de cette leçon, tu sauras

  • savoir manipuler un Future<T> et l'attendre avec async/await ;
  • savoir gérer les erreurs asynchrones avec try/catch et .catchError ;
  • savoir paralléliser plusieurs futures avec Future.wait et simuler une attente avec Future.delayed ;
  • savoir expliquer l'event loop de Dart et pourquoi oublier un await est une erreur fréquente.
Sommaire de la leçon

Quand ton application interroge un serveur, lit un fichier ou patiente sur un minuteur, il s'écoule un temps non négligeable. Si ton programme bloquait pendant cette attente, l'interface se figerait : aucun bouton ne répondrait, l'animation se gèlerait. Dart résout ce problème avec un modèle asynchrone élégant, bâti autour d'un type central — le Future<T> — et de deux mots-clés qui rendent le code asynchrone aussi lisible que du code séquentiel : async et await.

Cette leçon est l'une des plus importantes du cours : en Flutter, tout chargement de données passe par là. On va partir du problème, construire la solution pas à pas, puis comprendre le moteur qui tourne dessous — l'event loop.

Le problème : ne pas bloquer pendant une attente

Imagine une fonction qui attend trois secondes puis renvoie un résultat. Si elle bloquait le thread, plus rien d'autre ne pourrait s'exécuter pendant ces trois secondes. Dart est mono-thread par défaut : un seul fil d'exécution traite ton code. Bloquer ce fil, c'est tout figer.

La solution n'est pas de lancer un autre thread, mais de déléguer l'attente et de continuer à travailler. Dart représente « un résultat qui n'est pas encore là » par un objet : le Future.

Remarque l'essentiel : chargerNom() rend la main immédiatement. Le Future est une promesse de valeur, pas la valeur elle-même. Il faudra l'attendre pour récupérer le 'Noah'.

Future.delayed : simuler une attente

Tout au long de cette leçon, on simule des opérations lentes (réseau, disque) avec Future.delayed. Il prend une Duration et, optionnellement, une fonction qui produit la valeur une fois le délai écoulé. C'est l'outil idéal pour apprendre l'asynchrone sans dépendre d'un vrai serveur.

async / await : lire l'asynchrone de façon séquentielle

Attendre un Future à la main serait pénible. Dart offre await : il suspend la fonction jusqu'à ce que le Future se résolve, puis reprend avec la valeur déballée. On ne peut utiliser await que dans une fonction marquée async.

Le code se lit de haut en bas, comme s'il était synchrone, alors qu'il ne bloque rien : pendant l'await, l'event loop est libre de traiter d'autres événements. await « déballe » le type : await sur un Future<String> te donne une String.

Note

Toute fonction async renvoie un Future, même si tu écris return 3; dedans : le type effectif sera Future<int>. Et main peut être async — c'est le point d'entrée naturel de tes programmes asynchrones.

Gérer les erreurs : try/catch autour d'await

Un Future peut échouer : au lieu d'une valeur, il porte alors une erreur. Avec await, cette erreur est relancée au point d'attente ; tu l'attrapes donc avec un try/catch classique, exactement comme pour du code synchrone.

C'est l'un des grands atouts d'async/await : la gestion d'erreur asynchrone réutilise la syntaxe que tu connais déjà. Tu peux aussi cibler un type précis avec on Exception catch (e).

Le style chaîné : then, catchError, onError

Avant async/await, on enchaînait les callbacks avec .then() pour la valeur et .catchError() pour l'erreur. Tu croiseras encore ce style dans du code existant ; il faut savoir le lire.

Compare avec la version await : final score = await recupererScore(); sur une ligne, puis tu utilises score. Dès que tu enchaînes plusieurs étapes ou que tu mêles conditions et boucles, les .then() imbriqués deviennent vite illisibles, tandis qu'await reste plat et linéaire. Privilégie async/await ; réserve then aux cas ponctuels où tu ne veux pas rendre la fonction englobante async.

Note

.then() accepte un paramètre nommé onError : future.then(onValeur, onError: onErreur). Subtile différence avec .catchError() : onError n'attrape que les erreurs du Future initial, alors que .catchError() placé après attrape aussi celles levées dans le then précédent.

Future.wait : paralléliser plusieurs futures

Si tu as deux requêtes indépendantes, les attendre l'une après l'autre est un gâchis : await a; await b; prend la somme des durées. Lance-les en même temps et attends-les ensemble avec Future.wait, qui prend une liste de futures et renvoie un Future de la liste des résultats — disponible quand tous sont terminés.

Le point clé : dans Future.wait([requeteA(), requeteB()]), les deux appels sont déclenchés avant tout await, donc ils s'exécutent concurremment. Si n'importe quel future de la liste échoue, le Future.wait échoue : entoure-le d'un try/catch au besoin.

Astuce

Quand tes opérations sont indépendantes (deux endpoints distincts, plusieurs fichiers), Future.wait divise ton temps d'attente. Garde le await séquentiel uniquement quand l'étape B a besoin du résultat de l'étape A.

L'event loop : microtasks vs events (survol)

Comment Dart fait-il tourner tout ça sur un seul thread ? Grâce à une boucle d'événements (event loop). Quand le code synchrone courant est terminé, la boucle pioche le prochain travail à faire dans deux files d'attente : la file des microtasks (priorité haute : continuations d'await, scheduleMicrotask) et la file des events (priorité normale : timers, I/O, Future classiques). À chaque tour, Dart vide entièrement la file des microtasks avant de prendre un seul event.

Tu n'as pas besoin de jongler avec ces files au quotidien, mais ce modèle explique pourquoi ton code synchrone s'exécute toujours en entier avant le moindre then, et pourquoi un await ne « saute » jamais une ligne déjà commencée.

Pourquoi c'est partout en Flutter

En Flutter, l'interface est redessinée en continu sur le thread principal. Toute opération longue — appel HTTP, lecture d'une base locale, accès aux préférences — renvoie un Future que tu await dans une méthode async, puis tu déclenches un rafraîchissement de l'écran. C'est exactement le schéma que tu retrouveras avec FutureBuilder et la gestion d'état. Maîtriser Future/async/await maintenant, c'est t'épargner 80 % des futurs maux de tête côté UI.

Cas réel

L'écran d'accueil d'un réseau social doit charger trois choses au démarrage : le profil de l'utilisateur, son fil d'actualité et ses stories. Écrites en séquence (await profil; await fil; await stories;), si chaque appel prend 800 ms, l'écran reste figé 2,4 secondes avant d'afficher quoi que ce soit — une éternité perçue qui fait fuir. Comme ces trois requêtes sont indépendantes, on les lance ensemble : await Future.wait([profil(), fil(), stories()]) ramène l'attente à ~800 ms, la durée de la plus lente. C'est le réflexe des écrans d'accueil rapides, et l'erreur inverse — le await en cascade — est la cause n°1 des démarrages lents en Flutter.

Pièges fréquents

Piège fréquent

Oublier le await. Sans lui, tu manipules le Future lui-même, pas sa valeur — et tu n'attends pas la fin de l'opération.

L'analyseur de Dart t'aide : la règle de lint unawaited_futures signale un Future ignoré. Si tu veux volontairement ne pas attendre, marque-le explicitement avec unawaited(...) (de dart:async) pour exprimer ton intention.

Piège fréquent

Un await dans une boucle for sérialise tout : chaque tour attend le précédent. Si les itérations sont indépendantes, construis une liste de futures et passe-la à Future.wait plutôt que d'attendre dans la boucle.

Pour aller plus loin

Pour aller plus loin

Un Future ne délivre qu'une valeur. Pour une suite de valeurs dans le temps (événements clavier, lignes d'un fichier, messages WebSocket), Dart propose les Stream et la boucle await for — sujet de la prochaine leçon. Côté calcul lourd qui bloquerait vraiment le thread (parsing massif, crypto), regarde les isolates et Isolate.run : ils offrent du vrai parallélisme, là où async ne fait que de la concurrence coopérative.

Antisèche

Glossaire

Future<T>
Objet représentant un résultat de type T qui n'est pas encore disponible ; il se complète une fois, avec une valeur ou une erreur.
async
Modificateur qui transforme une fonction en machine asynchrone : elle renvoie un Future et peut se suspendre sur await.
await
Suspend la fonction async jusqu'à la résolution du Future, puis reprend avec sa valeur déballée.
Future.delayed
Crée un Future qui se complète après une Duration ; sert à simuler une opération lente.
Future.wait
Attend une liste de Future exécutés concurremment ; échoue si l'un d'eux échoue.
Event loop
Boucle mono-thread qui ordonnance le travail : elle vide la file des microtasks avant de traiter le prochain event.
Microtask
Tâche de priorité haute (continuation d'await, scheduleMicrotask) traitée avant tout event de la file normale.
Isolate
Fil d'exécution Dart isolé (mémoire séparée) offrant un vrai parallélisme, contrairement à la concurrence coopérative d'async.

Récap et vérification

  • Future<T> représente une valeur de type T qui arrivera plus tard ; une fonction async en renvoie toujours un.
  • await suspend une fonction async jusqu'à la résolution du Future et déballe sa valeur — sans bloquer le thread.
  • Les erreurs asynchrones s'attrapent avec try/catch autour de l'await, ou avec .catchError() en style chaîné.
  • Future.delayed simule une attente ; Future.wait lance plusieurs futures en parallèle et attend qu'ils soient tous prêts.
  • L'event loop vide la file des microtasks (priorité haute) avant chaque event ; tout le code synchrone passe en premier.
  • Le piège n°1 : oublier await — tu obtiens le Future au lieu de sa valeur.

Vérifie ta compréhension

  1. Quel est le type de retour réel d'une fonction déclarée Future<void> faire() async { return; }, et pourquoi await exige-t-il une fonction async ?
  2. Tu dois charger un profil puis, avec son identifiant, ses messages : faut-il Future.wait ou deux await successifs ? Et pour charger deux profils indépendants ?
  3. Dans le code de l'event loop, pourquoi '4 event (Future)' s'affiche-t-il toujours après les microtasks, même s'il a été planifié avant ?
