Module 3 · Vers Flutter — Leçon 09

Erreurs, tests et outillage

~50 min Intermédiaire Prérequis : leçon 8

À la fin de cette leçon, tu sauras

  • savoir distinguer Exception et Error, lancer et capturer avec try/catch/finally, et créer ses propres exceptions ;
  • savoir lire et écrire un pubspec.yaml, installer des paquets avec dart pub get et naviguer la structure lib/ / bin/ / test/ ;
  • savoir écrire des tests avec package:test (test, expect, matchers, group, setUp) et suivre une boucle TDD ;
  • savoir utiliser dart analyze, dart format, les lints recommandés et documenter avec ///.
Sommaire de la leçon

Jusqu'ici, ton code Dart partait du principe que tout se passait bien. Dans la vraie vie, un fichier manque, une API renvoie n'importe quoi, un utilisateur tape une lettre là où tu attendais un nombre. Une application robuste doit anticiper ces situations, les signaler clairement, et surtout : être testée pour ne pas casser à la prochaine modification.

Cette leçon couvre les trois piliers d'un projet Dart sérieux : la gestion d'erreurs (signaler et rattraper l'imprévu), les tests automatisés (vérifier que ton code fait ce qu'il prétend), et l'outillage (pub, dart analyze, dart format) qui te tient par la main. C'est le bagage qui sépare un script jetable d'une vraie base de code Flutter.

Exception ou Error : deux familles distinctes

En Dart, tout ce qu'on lance avec throw est un objet. La bibliothèque standard distingue deux familles par convention. Une Exception représente un problème prévisible et récupérable : fichier introuvable, format invalide, réseau coupé. Tu es censé l'attraper. Un Error représente un bug de programmation : argument invalide, index hors limites, appel sur null. Tu n'es pas censé l'attraper ; tu es censé corriger ton code.

throw, try, catch, finally

On lance avec throw et on rattrape avec try / catch. Le bloc finally s'exécute toujours, qu'il y ait eu une erreur ou non : idéal pour libérer une ressource (fermer un fichier, une connexion).

Un catch sans type attrape tout. Tu peux récupérer la trace d'appels en déclarant un deuxième paramètre, et cibler un type précis avec on.

L'ordre des clauses on compte : place toujours les types les plus précis en premier, sinon une clause plus large les interceptera avant. Une note : int.parse('abc') déclenche en réalité une FormatException — celle attrapée ci-dessus.

rethrow et exceptions sur mesure

Parfois tu veux réagir à une erreur (logger, nettoyer) sans la consommer : l'appelant doit la voir passer. C'est le rôle de rethrow, qui relance l'erreur d'origine en conservant sa trace.

Tu peux créer tes propres exceptions en implémentant l'interface Exception. Une bonne pratique : un champ message et un toString() lisible.

assert : filet en mode debug

assert vérifie une condition qui doit être vraie. Si elle est fausse, le programme s'arrête avec une AssertionError. Point essentiel : les assert ne s'exécutent qu'en mode debug (développement et tests). En production, ils sont totalement ignorés et n'ont aucun coût. Ils documentent tes hypothèses sans alourdir l'app livrée.

Note

N'utilise jamais assert pour valider une saisie utilisateur ou une donnée réseau : comme il disparaît en production, ta vérification s'évanouirait pile quand elle compte. Pour ces cas, lance une vraie Exception.

pub et pubspec.yaml : le gestionnaire de paquets

Chaque projet Dart a un fichier pubspec.yaml à sa racine : c'est sa carte d'identité et sa liste de dépendances. Les paquets viennent de pub.dev, le registre officiel.

Le ^ (caret) autorise les mises à jour compatibles selon le versionnage sémantique : ^1.2.0 accepte tout 1.x à partir de 1.2.0, mais jamais 2.0.0. Après modification du fichier, tu télécharges les dépendances :

Structure d'un projet

Dart suit une convention de dossiers que tous les outils comprennent. La respecter t'évite mille réglages.

Le code dans lib/ est réutilisable et importable ; lib/src/ est considéré privé par convention. Les exécutables vont dans bin/, les tests dans test/ avec le suffixe _test.dart reconnu automatiquement.

Tester avec package:test

Un test décrit un comportement attendu : on appelle du code, puis on vérifie le résultat avec expect(valeurObtenue, attendu). La fonction test('description', () { ... }) déclare un cas ; group les regroupe ; setUp prépare un état avant chaque test. Les matchers (equals, isTrue, throwsA…) rendent les attentes expressives.

Une courte boucle TDD

Le Test-Driven Development inverse l'ordre habituel : tu écris d'abord le test (qui échoue), puis le minimum de code pour le faire passer, puis tu nettoies. Rouge, vert, refactor.

Outillage : analyze, format, lints, doc

Dart embarque une chaîne d'outils de qualité. dart analyze fait de l'analyse statique : il détecte erreurs de type, variables inutilisées et code suspect sans exécuter le programme. dart format reformate le code selon le style officiel : plus jamais de débat sur l'indentation.

Cas réel

Sur pub.dev, chaque paquet reçoit un score de pub points calculé automatiquement par l'outil pana. Une partie des points se gagne précisément avec l'outillage de cette leçon : le code doit passer dart format sans changement, ne déclencher aucun avertissement de dart analyze, respecter des lints, et fournir de la documentation ///. Un paquet mal formé ou plein d'avertissements perd des points et remonte moins bien dans les résultats : tout l'écosystème Dart est donc bâti pour récompenser la rigueur que tu viens d'apprendre. C'est la même chaîne d'outils que tu branches en intégration continue pour refuser un commit non conforme.

Antisèche

Glossaire

Exception
Objet signalant un problème prévisible et récupérable (entrée invalide, réseau) ; on la rattrape dans un catch.
Error
Objet signalant une faute de programmation (index hors limites, null) ; à corriger, pas à intercepter.
finally
Bloc exécuté dans tous les cas après try/catch : libération de ressources.
rethrow
Relance l'exception courante en conservant sa pile d'appels d'origine, contrairement à throw e;.
assert
Vérification d'une condition en mode debug seulement ; supprimée en build de production.
pubspec.yaml
Fichier décrivant nom, version et dépendances d'un projet Dart ; lu par dart pub.
Matcher
Objet de package:test décrivant une attente (equals, throwsA…) passé à expect.
Analyse statique
Vérification du code sans l'exécuter (dart analyze) : types, variables inutilisées, code suspect.

Pièges fréquents

Piège fréquent

Attraper un Error (comme RangeError ou NoSuchMethodError) pour « éviter le plantage » masque un vrai bug. Laisse-le remonter et corrige la cause ; ne capture que les Exception.

Piège fréquent

Utiliser throw e; (qui relance avec une nouvelle trace) là où tu voulais rethrow. Pour préserver la pile d'appels d'origine dans un catch, c'est bien rethrow qu'il te faut, sans argument.

Pour aller plus loin

Pour aller plus loin

Le matcher throwsA(predicate) a des raccourcis prêts à l'emploi (throwsArgumentError, throwsFormatException). Pour le code asynchrone, expect sait gérer les Future avec completion(...) et await : on y reviendra avec async/await. Explore aussi dart fix --apply, qui corrige automatiquement nombre d'avertissements signalés par l'analyseur.

Récap et vérification

  • Exception = problème prévu et rattrapable ; Error = bug à corriger, pas à attraper.
  • try / catch (e, stack) / finally, ciblage par on Type, et rethrow pour relancer en gardant la trace.
  • assert documente une hypothèse mais ne tourne qu'en debug : jamais pour valider des entrées en production.
  • pubspec.yaml déclare dependencies / dev_dependencies ; dart pub get installe ; le code va dans lib/, bin/, test/.
  • package:test fournit test, expect, les matchers (equals, throwsA), group et setUp.
  • dart analyze, dart format, les lints et la doc /// maintiennent la qualité du code.

Vérifie ta compréhension

  1. Tu reçois une chaîne JSON d'une API qui peut être mal formée. Lances-tu une Exception ou un Error, et pourquoi ?
  2. Quelle différence de comportement y a-t-il entre throw e; et rethrow; à l'intérieur d'un catch ?
  3. Pourquoi est-il dangereux de valider une saisie utilisateur avec assert ?
  4. À quoi sert setUp dans un fichier de test, et combien de fois s'exécute-t-il ?
