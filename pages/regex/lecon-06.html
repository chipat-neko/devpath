Les regex en pratique

~39 min Intermédiaire Leçon 05 requise

À la fin de cette leçon, tu sauras

  • utiliser une regex en JavaScript, Python et avec grep ;
  • employer les drapeaux i, g, m, s ;
  • éviter les pièges classiques (sur-validation, gourmandise) ;
  • reconnaître le risque de ReDoS (regex trop lente).
Sommaire de la leçon

Tu connais la grammaire des regex : littéraux, classes, quantificateurs, groupes, regards. Cette dernière leçon te montre comment les utiliser pour de vrai dans tes outils quotidiens, comment régler leur comportement avec les drapeaux, et surtout quels pièges éviter — car une regex peut être correcte sur tes exemples et désastreuse en production.

Les regex dans les langages

La syntaxe des motifs est quasi universelle ; seule l'interface change d'un langage à l'autre. Voici le même motif (extraire les nombres) dans trois environnements :

Note le r"..." de Python (raw string) : il évite que le \ soit interprété par le langage avant la regex. En JavaScript, le motif s'écrit entre slashs /.../. Avec grep, l'option -E active les regex étendues. La grammaire, elle, ne change pas : \d+ (ou [0-9]+ en grep de base) partout.

Motif figé ou motif dynamique ?

Le littéral /\d+/ convient quand le motif est connu à l'écriture. Quand il dépend d'une donnée (un mot saisi par l'utilisateur), on le construit : new RegExp(mot, "gi") en JavaScript, re.compile(motif) en Python. Deux réflexes alors : dans une chaîne, les antislashs se doublent ("\\d+"), et il faut échapper les caractères spéciaux du texte injecté pour ne pas casser le motif.

On les attache selon le langage : /chat/gi en JavaScript, re.findall(motif, texte, re.IGNORECASE) en Python. Le drapeau i est le plus courant ; g est indispensable pour traiter toutes les occurrences ; m et s changent le sens des ancres et du point sur du texte multiligne.

Le piège du drapeau g en JavaScript

Une regex /g rangée dans une variable retient sa position de lecture (lastIndex) d'un appel à l'autre. Appeler à répétition regex.test(x) sur la même instance renvoie alors true, false, true… en alternance, car la recherche repart d'où elle s'était arrêtée. La parade : réécrire le littéral à chaque fois, ou remettre regex.lastIndex = 0 avant chaque test.

Les pièges à éviter

Trois erreurs reviennent constamment :

  • Sur-valider : vouloir une regex « parfaite » pour les e-mails ou les URL mène à des monstres illisibles et souvent faux. Pour un e-mail, ^\S+@\S+\.\S+$ suffit en pratique ; la validation réelle, c'est d'envoyer un message de confirmation.
  • La gourmandise (leçon 3) : ".*" sur "a" et "b" matche tout d'un bloc. Préfère "[^"]*" (tout sauf un guillemet) pour s'arrêter au bon endroit.
  • Oublier d'ancrer : une validation sans ^…$ accepte une chaîne qui contient le motif au lieu d'être le motif.

Le piège ReDoS

Un dernier danger, plus subtil : certaines regex deviennent catastrophiquement lentes sur des entrées particulières, parce que le moteur explore un nombre explosif de combinaisons (backtracking). C'est le ReDoS (Regular expression Denial of Service) : une faille où une entrée malveillante fait geler le serveur.

Le coupable typique : des quantificateurs imbriqués sur des motifs qui peuvent matcher de plusieurs façons ((a+)+). La parade : éviter d'emboîter les +/*, préférer des classes précises ([^"]* plutôt que .*), et tester ses regex sur de longues entrées. Pour valider des données venues d'utilisateurs, sois particulièrement vigilant : une regex est du code, et du code peut avoir des failles.

Quand renoncer à la regex

Les regex décrivent des motifs plats : elles ne savent pas compter des parenthèses imbriquées ni suivre une structure arborescente. Analyser du HTML complet, valider du JSON, apparier des balises imbriquées : mieux vaut un vrai analyseur (parser). La regex, elle, reste imbattable pour repérer un motif local — une date, un identifiant, un mot-clé — dans un texte.

Pour aller plus loin

Tu as désormais de quoi lire et écrire l'immense majorité des regex du quotidien. Pour approfondir : les groupes nommés et le mode verbeux (re.VERBOSE en Python, le flag x) qui autorise espaces et commentaires dans un motif long ; les classes POSIX et les propriétés Unicode (\p{L}) pour le texte international ; et les moteurs sans backtracking (RE2) qui garantissent une vitesse linéaire. Et garde le réflexe : si une regex devient illisible, un peu de code ordinaire est parfois plus clair.

Cas réel

Cas réel

En juillet 2019, une seule regex a mis à genoux Cloudflare : un motif aux quantificateurs imbriqués a déclenché un ReDoS qui a fait grimper le processeur à 100 % et provoqué une panne mondiale d'environ 30 minutes. À ton échelle, le même piège guette la moindre validation d'e-mail « trop maligne ». La parade est toujours la même : des classes précises ([^"]* plutôt que .*), pas de +/* emboîtés, et un test sur de longues entrées. Côté outillage quotidien : grep -E pour fouiller des logs, le rechercher-remplacer par regex de l'éditeur, et les drapeaux i/g pour tout traiter d'un coup.

Antisèche

Glossaire

Drapeau (flag)
Option qui modifie le comportement global du moteur : i, g, m, s.
lastIndex
Position de lecture mémorisée par une regex /g en JavaScript ; source de bugs si la même instance est réutilisée sans la remettre à zéro.
Raw string (r"...")
En Python, chaîne où le \ n'est pas interprété avant la regex ; évite de doubler les antislashs.
grep -E
Commande Unix qui filtre les lignes d'un fichier avec une regex étendue.
Sur-validation
Vouloir un motif « parfait » (e-mail, URL) au point de le rendre illisible et souvent faux.
Backtracking
Retours en arrière du moteur pour tenter d'autres combinaisons ; explosif si le motif est ambigu.
Gourmand (greedy)
Un quantificateur qui prend le plus de texte possible : .* déborde jusqu'au dernier guillemet, là où [^"]* s'arrête au premier.
ReDoS
Regular expression Denial of Service : une entrée qui fait exploser le temps de calcul d'une regex mal conçue.

Récap et vérification

  • La grammaire est universelle ; seule l'interface change : /.../ (JS), re (Python), grep -E.
  • Drapeaux : i (casse), g (global), m (multiligne), s (point = saut de ligne).
  • Évite la sur-validation, la gourmandise de .*, et l'oubli des ancres.
  • Le ReDoS : des quantificateurs imbriqués peuvent rendre une regex exponentiellement lente.

Exercice 3Défi

Explique pourquoi le motif ^(\d+)+$ est dangereux, et propose une version sûre pour valider une suite de chiffres.

Voir une solution

(\d+)+ peut découper une même suite de chiffres d'innombrables façons : sur une entrée qui finit par un caractère non-chiffre, le moteur explore un nombre exponentiel de combinaisons avant d'échouer. ^\d+$ exprime exactement la même chose (« une suite de chiffres ») sans imbrication, donc en temps linéaire.
