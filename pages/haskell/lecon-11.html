Module 3 · Haskell en pratique — Leçon 11

Modules, outils et tests

~50 min Avancé Prérequis : leçon 10

À la fin de cette leçon, tu sauras

  • Savoir déclarer un module avec sa liste d'exports et l'importer (qualified, hiding, masquage) ;
  • Savoir initialiser un projet avec Cabal, lire le fichier .cabal et ajouter une dépendance depuis Hackage ;
  • Savoir écrire des tests d'exemple avec Hspec et des tests par propriétés avec QuickCheck ;
  • Savoir formater son code (ormolu) et profiter de l'outillage moderne (HLS).
Sommaire de la leçon

Jusqu'ici tu as écrit des fonctions dans GHCi ou dans un fichier unique. Mais un vrai programme, c'est plusieurs fichiers, des bibliothèques externes, et des tests qui te disent que tu n'as rien cassé. Bonne nouvelle : l'outillage Haskell moderne (GHC 9.x) est mûr et cohérent. On va voir comment découper ton code en modules, comment Cabal orchestre le tout, comment piocher dans l'écosystème Hackage, et surtout comment tester.

Et c'est là que Haskell offre quelque chose de spécial. Tu connais sans doute les tests « par exemple » (« avec cette entrée, j'attends cette sortie »). Haskell a popularisé une idée plus puissante : les tests par propriétés, où tu décris une règle universelle et où la machine génère des centaines de cas pour la mettre en défaut. Cette façon de penser, tu la réutiliseras dans tous les langages.

Découper en modules

Un module, c'est une unité de code avec un nom et une liste de ce qu'il rend public. Le nom du module doit correspondre au chemin du fichier : le module Geometrie.Cercle vit dans Geometrie/Cercle.hs. C'est la hiérarchie des modules, exactement comme les paquets en Java ou les dossiers de modules en Python.

La liste entre parenthèses après le nom du module est la liste d'exports. Tout ce qui n'y figure pas reste privé. Si tu omets complètement la liste (module Geometrie.Cercle where), tout est exporté : pratique au début, mais une liste explicite documente l'interface et protège tes détails internes.

Importer : qualified, hiding, masquage

Côté consommateur, import amène les noms d'un autre module dans ta portée. Il y a plusieurs variantes, et elles comptent dès que des noms se télescopent.

Le plus important au quotidien : import qualified … as. Beaucoup de modules conteneurs (Data.Map, Data.Set, Data.Text) exposent des fonctions aux mêmes noms que le Prelude (lookup, filter, map, null). En les important qualifiés, tu écris Map.lookup et Map.filter : zéro ambiguïté. C'est l'idiome standard.

Note

Pour redéfinir un nom déjà fourni par le Prelude sans conflit, retire-le à l'import avec hiding : import Prelude hiding (lookup) libère le nom lookup pour ta propre version. C'est ainsi qu'on évite le masquage (« shadowing »), c'est-à-dire l'ambiguïté entre deux définitions d'un même nom visibles en même temps.

Cabal : le chef d'orchestre du projet

Cabal est l'outil de build de référence. Il décrit ton projet, télécharge les dépendances, compile et lance. On démarre un projet avec cabal init.

Le cycle de base. cabal repl est précieux : c'est GHCi déjà configuré pour ton projet.

Note

Stack est une alternative à Cabal, appréciée pour sa reproductibilité : il épingle un « resolver » (un ensemble de paquets dont les versions sont garanties compatibles). Les commandes se ressemblent : stack new, stack build, stack run, stack ghci. Pour débuter, Cabal seul suffit largement ; les deux lisent le fichier .cabal.

Hackage et les dépendances

Hackage est le dépôt central des paquets Haskell (l'équivalent de PyPI ou npm). Pour utiliser une bibliothèque, tu l'ajoutes à build-depends dans le .cabal, puis Cabal la récupère au prochain build. Pas de commande « install » à retenir : la déclaration dans le fichier est la source de vérité.

Au prochain cabal build, les paquets sont téléchargés et compilés. Tu peux alors écrire import Data.Text (Text) ou import Data.Aeson dans ton code.

Tester par l'exemple avec Hspec

Hspec donne des tests lisibles, structurés en describe (un groupe) et it (un cas), avec des attentes comme shouldBe. On l'ajoute en build-depends d'une cible test-suite.

Chaque it est un cas isolé. shouldBe teste l'égalité, shouldSatisfy teste un prédicat.

C'est clair et familier si tu viens de Jest ou de pytest. Mais ces tests ne couvrent que les cas que tu as imaginés. D'où l'étape suivante.

Tester par propriétés avec QuickCheck

Voici l'idée qui a changé la façon de tester dans toute l'industrie. Au lieu d'écrire « pour [3,1,2] j'attends [1,2,3] », tu énonces une propriété universelle et QuickCheck génère des centaines d'entrées aléatoires pour tenter de la briser.

QuickCheck a deviné, grâce aux types ([Int]), comment fabriquer des listes d'exemples : vides, courtes, longues, avec des nombres négatifs… Et le plus beau : quand une propriété échoue, il réduit le contre-exemple à sa plus petite forme. Une propriété fausse te montrera quelque chose comme :

Astuce

Cherche des invariants plutôt que des exemples : « la longueur ne change pas », « l'opération inverse annule l'opération », « le résultat est toujours trié ». Ces propriétés couvrent des milliers de cas que tu n'aurais jamais écrits à la main. L'idée est née ici : on la retrouve aujourd'hui dans presque tous les langages (Hypothesis en Python, fast-check en JS).

Cas réel — QuickCheck traque les bugs des voitures

QuickCheck naît en 1999-2000 dans un article de Koen Claessen et John Hughes à l'université de Chalmers, en Suède : à peine cent lignes de Haskell qui posent une idée qui essaimera partout. Hughes fonde ensuite Quviq pour porter le concept dans l'industrie, et là ça devient spectaculaire. En testant le logiciel embarqué de constructeurs automobiles (le standard AUTOSAR, utilisé notamment par Volvo), leur QuickCheck a mis au jour plus de 200 problèmes dans des spécifications signées par plusieurs équipementiers — dont des bugs qui dormaient là depuis des années, jamais attrapés par les tests d'exemple classiques. Le fameux shrinking réduisait des scénarios de milliers de messages CAN à une séquence minimale de trois ou quatre, seule façon rendant le défaut compréhensible par un humain. Morale du terrain : une bonne propriété explore l'espace des entrées bien plus loin que n'importe quelle liste d'exemples écrite à la main.

Formatage et serveur de langage

Deux outils rendent l'expérience moderne agréable. Ormolu (ou son cousin Fourmolu, plus configurable) est un formateur automatique : un seul style, zéro débat. Et HLS (Haskell Language Server) apporte dans ton éditeur l'autocomplétion, les types au survol, les erreurs en direct et les corrections rapides.

ghcup est l'installateur recommandé pour GHC, Cabal, Stack et HLS.

Pièges fréquents

Piège fréquent

Le nom du module doit refléter le chemin du fichier. module Geometrie.Cercle hors de Geometrie/Cercle.hs donne File name does not match module name. Et n'oublie pas de lister tout module non-Main dans other-modules du .cabal, sinon : Could not load module 'Geometrie.Cercle' au build.

Piège fréquent

Une propriété QuickCheck a besoin d'un type concret pour générer ses cas. Si tu écris prop_reverseReverse xs = reverse (reverse xs) == xs sans signature, GHC laisse xs polymorphe et ne sait pas quoi générer (Ambiguous type variable). Annote toujours, typiquement avec [Int].

Pour aller plus loin

Explore cabal test pour lancer toutes tes test-suite d'un coup, et la combinaison hspec + QuickCheck via Test.Hspec.QuickCheck (la fonction prop) pour intégrer tes propriétés dans la jolie sortie de Hspec. Côté écosystème, regarde hedgehog (une approche alternative des tests par propriétés où les générateurs sont explicites) et les « golden tests » pour comparer des sorties à des fichiers de référence.

Antisèche — modules, outils et tests

Glossaire

Module
Unité de code nommée dont le nom suit le chemin du fichier (Geometrie.Cercle ⟷ Geometrie/Cercle.hs).
Liste d'exports
Parenthèses après le nom du module : définit l'interface publique. Ce qui n'y figure pas reste privé.
qualified
Mode d'import qui force à préfixer les noms (Map.lookup), pour lever les collisions avec le Prelude.
Cabal
Outil de build de référence : lit le fichier .cabal, résout et télécharge les dépendances, compile et lance le projet.
Hackage
Dépôt central des paquets Haskell, équivalent de PyPI ou npm ; on y puise via build-depends.
Prelude
Module importé automatiquement dans chaque fichier : fournit map, filter, ++, show, etc.
Test par propriétés
Énoncer une loi vraie pour toute entrée ; QuickCheck génère des centaines de cas pour tenter de la briser.
Shrinking
Réduction automatique d'un contre-exemple fautif jusqu'à sa plus petite forme, bien plus lisible que l'entrée aléatoire initiale.

Récap et vérification

  • Un module a un nom calqué sur son chemin et une liste d'exports qui définit son interface publique.
  • import qualified … as évite les conflits de noms ; hiding retire des noms ; une liste explicite documente l'origine.
  • Cabal (init/build/run/repl) pilote le projet via le fichier .cabal ; Stack est l'alternative.
  • Les dépendances viennent de Hackage et se déclarent dans build-depends.
  • Hspec teste par l'exemple ; QuickCheck teste par propriétés, génère des centaines de cas et réduit les contre-exemples.
  • Ormolu/Fourmolu formatent automatiquement ; HLS outille l'éditeur.

Vérifie ta compréhension

  1. Pourquoi importer Data.Map en qualified plutôt que normalement ?
  2. Où déclares-tu une dépendance Hackage, et que se passe-t-il ensuite au build ?
  3. Quelle est la différence de philosophie entre un test Hspec it … shouldBe et une propriété QuickCheck ?
