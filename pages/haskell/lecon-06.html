Module 2 · Le système de types — Leçon 06

Type classes

~55 min Avancé Prérequis : leçon 5

À la fin de cette leçon, tu sauras

  • comprendre qu'une type class est un contrat de comportement, pas une classe objet ;
  • lire et écrire des contraintes de classe comme Eq a => a -> a -> Bool ;
  • définir une instance et créer sa propre class avec des méthodes par défaut ;
  • expliquer ce que deriving génère et le rapprocher des interfaces Java et traits Rust.
Sommaire de la leçon

Tu as déjà croisé un mystère : comment == marche-t-il à la fois sur des Int, des String et des listes ? Comment show transforme-t-il presque n'importe quoi en texte ? La réponse tient en deux mots : type classes. C'est l'idée la plus puissante du système de types de Haskell, et la plus mal nommée : malgré le mot « class », ça n'a rien à voir avec les classes de Java ou Python.

Une type class, c'est un contrat de comportement. Elle dit : « tout type qui veut être membre de ce club doit savoir faire ces opérations ». Si tu viens de l'impératif, le bon réflexe est de penser interface (Java, C#) ou trait (Rust) — pas classe. On va démonter le mécanisme depuis zéro.

Le contrat, pas l'objet

Regardons la classe Eq (égalité), celle qui donne == et /=. Sa définition dans la bibliothèque standard ressemble à ceci :

Lis-le ainsi : « un type a appartient à la classe Eq s'il fournit une fonction == et une fonction /=, chacune prenant deux a et rendant un Bool ». La classe ne contient aucune donnée, juste des signatures : un cahier des charges. Le a est une variable de type — n'importe quel type pourra prendre sa place, à condition de remplir le contrat.

Note

En Java, une interface décrit ce qu'un objet sait faire. Une type class décrit ce qu'un type sait faire — il n'y a pas d'instance d'objet, pas de this. C'est une différence de vocabulaire qui change tout : le contrat porte sur le type lui-même.

Les classes standard à connaître

Le Prelude (la bibliothèque chargée par défaut) fournit une poignée de classes que tu rencontreras partout :

  • Eq — l'égalité : ==, /=.
  • Ord — l'ordre : compare, <, <=, >, max, min (a besoin de Eq au préalable).
  • Show — produire une représentation texte : show.
  • Read — l'inverse, lire depuis du texte : read.
  • Enum — énumérer : succ, pred, et les intervalles [1..10].
  • Bounded — les bornes : minBound, maxBound.
  • Num — les opérations numériques : +, *, -, abs…

Méthodes par défaut

Un contrat peut fournir une implémentation par défaut qu'on hérite gratuitement. C'est pourquoi définir Eq ne demande souvent qu'une seule méthode : si tu donnes ==, le /= se déduit tout seul.

On n'a écrit que == ; /= arrive avec. Les méthodes par défaut allègent les instances et garantissent la cohérence : l'auteur de la classe décide une fois pour toutes comment les opérations se déduisent l'une de l'autre. Attention : comme == et /= se définissent ici mutuellement, il faut en fournir au moins une, sinon les deux tourneraient en rond à l'infini.

Astuce

Pour Ord, il suffit de définir compare (ou seulement <=) : <, >, max, min en découlent par défaut. Vise toujours le minimum : tape :info Ord dans GHCi et lis la ligne « {-# MINIMAL ... #-} » qui indique le jeu minimal de méthodes à fournir.

deriving, revisité

Écrire show ou == à la main est fastidieux et mécanique. Le mot-clé deriving demande au compilateur de générer l'instance évidente pour toi :

Voici concrètement ce que GHC fabrique : Eq compare constructeur à constructeur ; Ord ordonne selon l'ordre de déclaration (Rouge < Vert < Bleu) ; Show rend le nom du constructeur tel quel ; Enum numérote dans l'ordre ; Bounded prend le premier et le dernier comme bornes.

Le show dérivé donne "Vert" (le nom du constructeur), pas "vert" : deriving vise une représentation valide en code Haskell, pas une jolie phrase. Pour de l'affichage soigné, écris l'instance à la main comme plus haut. Note d'ailleurs qu'un type ne peut pas avoir à la fois un Show dérivé et un Show écrit à la main : il faut choisir.

Deux polymorphismes, une intuition

On distingue deux familles de polymorphisme, et les type classes incarnent la seconde :

  • Paramétrique : length :: [a] -> Int marche pour tout a, de la même façon. Le code ne regarde jamais le contenu — il compte, point.
  • Ad-hoc (via classes) : show :: Show a => a -> String marche pour tout a qui est Show, mais d'une façon différente selon le type. Chaque instance a son propre code.

Autrement dit : le polymorphisme paramétrique ignore le type, l'ad-hoc en dépend — proprement, via un contrat. Si tu connais Java, c'est exactement la différence entre les generics (List<T>) et la programmation par interface.

Note

Les traits de Rust s'inspirent directement des type classes — la filiation est assumée. impl Display for Couleur en Rust, c'est l'écho de instance Show Couleur en Haskell. Apprendre ce mécanisme ici, c'est aussi mieux le comprendre là-bas.

Cas réel — un seul tri pour tous les types

La classe Ord illustre le gain concret des contrats. La fonction sort :: Ord a => [a] -> [a] trie n'importe quelle liste dont le type sait se comparer : entiers, chaînes, dates, tuples, tes types maison. Un seul algorithme, écrit une fois, réutilisé partout — il suffit que le type soit membre de Ord. C'est le même principe que Comparable/Comparator en Java ou __lt__ en Python, mais vérifié à la compilation : trier un type non ordonnable devient une erreur avant même de lancer le programme. Et comme Ord se dérive (deriving Ord), tu obtiens ce tri gratuitement sur tes énumérations.

Pièges fréquents

Piège fréquent

Une type class n'est pas une classe objet : pas de champs, pas d'héritage de données, pas de new. Un type « est membre » d'une classe via une instance ; il n'en « hérite » pas. Oublie le modèle objet en lisant class ici.

Piège fréquent

Le sens du => et du -> n'est pas le même. Dans Eq a => a -> a -> Bool, le => introduit une contrainte (une exigence sur le type), le -> sépare des arguments. Tu peux avoir plusieurs contraintes, mais elles vivent toutes à gauche d'un unique =>, par exemple (Eq a, Show a) => a -> String.

Piège fréquent

Tu ne peux pas avoir deux instances différentes pour le même couple (classe, type). Haskell choisit l'instance d'après le type seul ; deux instance Show Couleur rivales sont une erreur de compilation. Une classe, un type, une instance.

Pour aller plus loin

Pour aller plus loin

Les superclasses (class Eq a => Ord a : « tout Ord doit déjà être Eq ») construisent une hiérarchie de contrats. Plus loin t'attendent Functor, Applicative et Monad — des type classes elles aussi, rien de plus effrayant que Show. Tu sais désormais lire leur signature : ce ne sont que des contrats.

Antisèche — type classes

Glossaire

Type class
Contrat de comportement sur un type (proche d'une interface Java, d'un trait Rust) : une liste d'opérations, sans donnée.
Instance
Déclaration instance C T where … qui rend le type T membre de la classe C en fournissant ses méthodes.
Contrainte de classe
Partie avant le => d'une signature (Eq a => …) : exige que le type respecte une classe.
Méthode par défaut
Implémentation fournie par la classe et héritée gratuitement (/= déduit de ==).
deriving
Clause qui demande au compilateur de générer l'instance évidente (Show, Eq, Ord…).
Polymorphisme ad-hoc
Comportement qui dépend du type, réalisé via les classes (show diffère par type).
Polymorphisme paramétrique
Comportement identique pour tout type, qui ignore le contenu (length).
Superclasse
Classe exigée par une autre (class Eq a => Ord a : tout Ord est déjà Eq).

Récap et vérification

  • Une type class est un contrat de comportement sur un type — proche d'une interface Java ou d'un trait Rust, loin d'une classe objet.
  • Eq, Ord, Show, Read, Enum, Bounded, Num sont les contrats standard à connaître.
  • Une contrainte C a => dans une signature signifie « pour tout a membre de C ».
  • instance rend un type membre ; class définit un nouveau contrat ; les méthodes par défaut réduisent le code à écrire.
  • deriving génère l'instance mécanique évidente (Show donne le nom du constructeur).
  • Le polymorphisme ad-hoc (via classes) dépend du type ; le paramétrique l'ignore.

Vérifie ta compréhension

  1. Dans elem :: Eq a => a -> [a] -> Bool, que t'apprend la partie Eq a =>, et pourquoi est-elle nécessaire ici ?
  2. Tu écris instance Eq Couleur et définis seulement ==. Pourquoi /= fonctionne-t-il quand même ?
  3. Quelle est la différence entre une instance dérivée de Show et une instance écrite à la main pour afficher "rouge" au lieu de "Rouge" ?
