Module 3 · Haskell en pratique — Leçon 13

Un vrai programme et l'écosystème

~55 min Avancé Prérequis : leçon 12

À la fin de cette leçon, tu sauras

  • structurer un programme Haskell complet en séparant logique pure et IO ;
  • gérer la persistance fichier et les erreurs avec Maybe et Either ;
  • situer les grandes briques de l'écosystème (Megaparsec, aeson, Servant) et savoir où Haskell brille ;
  • tracer un plan pour continuer et réinvestir cette façon de penser dans tous tes langages.
Sommaire de la leçon

Tu as parcouru un long chemin. Depuis la leçon 1, tu as rencontré l'immutabilité, les fonctions pures, les types algébriques, la paresse, Maybe, Either, les typeclasses, et ce fameux IO qui n'est finalement qu'une valeur comme une autre. Il est temps d'assembler tout ça dans un vrai programme : un petit gestionnaire de tâches en ligne de commande, persisté dans un fichier. Rien de spectaculaire, mais tout y est : modéliser avec des types, écrire la logique en pur, isoler l'IO, et gérer les erreurs proprement.

Ensuite, on prendra un peu de hauteur : un survol honnête de l'écosystème (parsing, web, JSON, bases de données), un mot sur les domaines où Haskell brille vraiment, et surtout pourquoi t'être frotté à ce langage te rend meilleur dans tous les autres.

Modéliser le domaine avec des types

On commence toujours par les données, jamais par le code. La règle d'or en Haskell : rends les états impossibles… impossibles. Une tâche a un identifiant, un titre, et un statut. Le statut n'est pas une chaîne libre ni un booléen flou, c'est un type somme à deux cas.

Avec ces quelques lignes, le compilateur garantit qu'une tâche ne peut pas être à la fois faite et pas faite, ni avoir un statut inventé. Comparé à un dictionnaire Python où tache["statut"] pourrait valoir "done", "Done" ou True, c'est une tranquillité d'esprit qu'on ne mesure qu'à l'usage.

Note

La syntaxe { champ :: Type } est un record. Elle génère gratuitement les fonctions d'accès tacheId, titre, statut. Tu obtiens donc des accesseurs typés sans rien écrire.

La logique : des fonctions pures, et rien d'autre

Toute la mécanique de l'application — ajouter, cocher, lister, supprimer — ne touche jamais au disque. Ce sont des transformations de Todos vers Todos. Pures, testables, déterministes.

Remarque cocher : son type Int -> Todos -> Maybe Todos annonce honnêtement qu'elle peut échouer (id introuvable). Pas d'exception cachée, pas de null surprise : l'échec est dans le type, et le compilateur t'obligera à le traiter.

Parser les commandes de l'utilisateur

L'utilisateur tape ajouter Faire les courses ou cocher 3. On transforme cette saisie brute en une valeur typée. Ici, Either String Commande : à gauche un message d'erreur lisible, à droite une commande valide.

C'est du parsing « à la main », suffisant pour une CLI. Pour des grammaires sérieuses (un langage, un format de fichier), on sortira l'artillerie : Megaparsec, dont on reparle plus bas.

Astuce

reads est la version « qui peut échouer » de read. Là où read "abc" :: Int plante à l'exécution, reads te rend une liste vide que tu peux inspecter sans risque.

La persistance : isoler l'IO au bord du programme

Le disque, c'est le monde extérieur, donc c'est IO. On garde ces fonctions fines : elles lisent, écrivent, et délèguent tout calcul aux fonctions pures. Le format de fichier est volontairement trivial — une tâche par ligne, au format id|statut|titre.

Note le motif : charger :: IO Todos et sauver :: Todos -> IO () sont les seuls points de contact avec le système de fichiers. Toute la richesse de l'application vit dans des fonctions pures, faciles à tester en GHCi sans jamais créer de fichier. C'est l'architecture « functional core, imperative shell » : un cœur pur, une coquille impérative mince autour.

Note

La compréhension de liste [tache | Just tache <- ...] garde uniquement les lignes qui se sont décodées en Just. C'est l'équivalent lisible de mapMaybe deserialiser (de Data.Maybe) : les lignes corrompues sont silencieusement ignorées plutôt que de faire planter le programme.

Le point d'assemblage : main

Tout converge dans main. On charge l'état, on lit une commande, on la parse, on l'applique, on sauve. L'arbre de décision suit exactement les types qu'on a définis — le compilateur nous tient la main.

Le programme tourne via cabal run ; chaque appel recharge et resauve le fichier todos.txt.

L'écosystème, en survol honnête

Ce petit outil suffit à voir où tu irais chercher des bibliothèques dès qu'il s'agit de faire sérieux. Voici la carte, sans complaisance.

  • Parsing — Megaparsec. Quand words ne suffit plus (un langage, un DSL, un format binaire), Megaparsec te donne des combinateurs : tu composes des petits parseurs pour en bâtir un gros, avec des messages d'erreur excellents. C'est l'une des plus belles vitrines de la composition fonctionnelle.
  • JSON — aeson. La référence pour (dé)sérialiser. Tu décris tes types, tu dérives les instances, et la conversion vers et depuis JSON est gérée. Notre couple serialiser / deserialiser maison deviendrait quelques lignes robustes.
  • Web — Servant et Yesod. Servant est spectaculaire : tu décris ton API au niveau des types, et le compilateur garantit que ton serveur et tes clients respectent le contrat. Une route qui renvoie le mauvais type ne compile pas. Yesod vise les applications web complètes, plus intégrées.
  • Bases de données — persistent, esqueleto, hasql. Des requêtes typées, vérifiées à la compilation, qui t'évitent une bonne part des erreurs SQL classiques.

Pour aller plus loin

Le fil rouge de tout l'écosystème Haskell : déplacer les erreurs de l'exécution vers la compilation. Servant typant les API, persistent typant les requêtes, aeson typant le JSON — partout, le même pari. Moins de tests à écrire parce que des classes entières de bugs deviennent impossibles à exprimer.

Où Haskell brille (et pourquoi t'en sortir grandi)

Haskell n'est pas le langage de tous les projets, et c'est sain de le dire. Mais là où la correction prime sur tout, il excelle : compilateurs et outils de langage (GHC lui-même, des linters, des transpileurs), finance (où une erreur coûte des millions ; des banques l'utilisent pour leurs moteurs de pricing), blockchain (Cardano est écrit en Haskell), et tout outillage où un bug silencieux est inacceptable.

Cas réel — la banque Standard Chartered

La banque britannique Standard Chartered fait tourner une bonne partie de sa plateforme de marché en Haskell depuis la fin des années 2000 : des centaines de milliers de lignes servent à valoriser des produits dérivés, là où un écart d'arrondi ou un état incohérent se chiffre vite en millions. Leur pari est exactement celui de cette leçon : on modélise chaque instrument financier par un type qui rend les combinaisons absurdes impossibles à écrire, on garde tout le calcul de pricing dans un cœur pur rejouable à l'identique, et on repousse la lecture des données de marché et l'écriture des résultats dans une fine coquille d'effets. Résultat concret : des classes entières de bugs — un champ oublié, un cas non traité — deviennent des erreurs de compilation attrapées avant même d'atteindre un serveur. L'équipe a même publié un dialecte maison, « Mu », pour rapprocher Haskell de ses quants ; l'idée motrice, elle, est restée la même que dans notre petit gestionnaire de tâches.

Mais voici le vrai cadeau, celui qui te suit partout. Ce que Haskell t'a forcé à intérioriser — l'immutabilité, les fonctions pures, rendre les états illégaux impossibles par les types, séparer le calcul des effets — n'est pas du folklore réservé à Haskell. Tu retrouveras :

  • l'immutabilité dans les const de JS, les frozen dataclasses de Python, les records de Java, tout React ;
  • Maybe et Either sous les noms Optional, Result, ?. dans Rust, Swift, Kotlin, TypeScript ;
  • map, filter, fold devenus le pain quotidien de tous les langages modernes ;
  • le réflexe « cœur pur, coquille impérative » qui rend n'importe quelle base de code plus testable.

Tu ne réécriras peut-être jamais ton travail en Haskell. Mais tu écriras du meilleur Python, du meilleur JS, du meilleur Java — parce que tu auras vu, une fois, à quoi ressemble la rigueur poussée au bout.

Pièges fréquents

Piège fréquent

Vouloir mettre de l'IO partout « pour aller plus vite ». C'est l'inverse : plus tu repousses l'IO vers main, plus ton cœur logique reste pur, testable et réutilisable. Si une fonction de calcul a un type en IO, demande-toi d'abord si elle en a vraiment besoin.

Deux autres écueils courants au moment d'assembler un projet :

  • Lire un fichier inexistant. readFile lève une exception IO si le fichier manque. D'où le doesFileExist dans charger : on vérifie d'abord, on renvoie [] sinon.
  • La paresse de readFile. Le readFile standard lit le fichier paresseusement. Si tu lis puis réécris le même fichier dans la foulée, tu peux te heurter à un verrou. C'est pourquoi on emploie ici readFile' (strict, fourni par System.IO) ; un vrai projet passerait à Text ou ByteString.

Pour aller plus loin

Pour aller plus loin

Trois caps pour continuer seul : (1) remplace String par Text partout — c'est l'idiome moderne pour les performances ; (2) ajoute aeson pour persister en JSON au lieu de ton format maison ; (3) ouvre « Programming in Haskell » (Hutton) ou les exercices d'Exercism pour ancrer les réflexes. Et garde GHCi ouvert en permanence : c'est ton meilleur professeur.

Antisèche — assembler un vrai programme

Glossaire

Cœur pur / coquille IO
Architecture (functional core, imperative shell) où la logique vit dans des fonctions pures au centre, entourées d'une fine couche IO qui lit et écrit aux frontières.
Type somme
Type à plusieurs cas exclusifs (AFaire | Faite). Il rend les états illégaux impossibles : on ne peut pas fabriquer un statut inventé.
Record
Type produit à champs nommés ({ champ :: Type }). Il génère gratuitement les accesseurs typés et permet la mise à jour partielle t { champ = … }.
Maybe
Type d'un résultat qui peut manquer : Just x (une valeur) ou Nothing (absence). Il rend l'échec visible dans le type, sans en dire la cause.
Either
Type d'un résultat qui peut échouer avec une raison : Left err (l'erreur, souvent un message) ou Right x (le succès). Plus riche que Maybe.
Sérialisation
Convertir une valeur en texte (serialiser) pour l'écrire dans un fichier, et l'opération inverse (deserialiser) pour la relire. Ici, une tâche ⟷ une ligne id|statut|titre.
Combinateur de parseurs
Principe des bibliothèques comme Megaparsec : composer de petits parseurs pour en bâtir un gros, avec de bons messages d'erreur, plutôt que de découper à la main avec words.
Écosystème typé
Fil conducteur des bibliothèques Haskell (aeson, Servant, persistent) : déplacer les erreurs de l'exécution vers la compilation en décrivant JSON, API ou requêtes SQL au niveau des types.

Récap et vérification

  • Un programme Haskell sain sépare un cœur pur (types + fonctions sans effets) d'une coquille IO fine, concentrée près de main.
  • On modélise d'abord avec des types pour rendre les états illégaux impossibles, puis on écrit la logique en fonctions pures.
  • Maybe et Either rendent l'échec visible dans les types : pas d'exception cachée, le compilateur force à le traiter.
  • L'écosystème (Megaparsec, aeson, Servant, persistent) prolonge la même idée : déplacer les bugs vers la compilation.
  • Les réflexes appris ici — immutabilité, pureté, types expressifs — te rendent meilleur dans tous les langages.

Vérifie ta compréhension

  1. Pourquoi cocher renvoie-t-elle Maybe Todos plutôt que Todos ? Qu'est-ce que ça oblige l'appelant à faire ?
  2. Dans l'architecture « functional core, imperative shell », quelles fonctions de la todo sont « le cœur » et lesquelles sont « la coquille » ?
  3. Cite un mécanisme d'un langage que tu connais déjà (Python, JS, Java…) qui reprend l'idée de Maybe ou de l'immutabilité.
