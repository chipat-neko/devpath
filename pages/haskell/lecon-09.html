Module 3 · Haskell en pratique — Leçon 09

IO et le monde réel

~55 min Avancé Prérequis : leçon 8

À la fin de cette leçon, tu sauras

  • comprendre qu'un IO a est une recette d'action, pas l'action elle-même, et pourquoi cela préserve la pureté ;
  • écrire des programmes interactifs avec la notation do, <-, putStrLn, getLine et return ;
  • lire des nombres avec read, boucler avec la récursion ou forM_, et lire les arguments via getArgs ;
  • structurer une appli en séparant le cœur pur de la coquille IO.
Sommaire de la leçon

Tu as appris à écrire des fonctions pures : mêmes entrées, même sortie, aucun effet de bord. C'est élégant, mais une question te taraude sûrement : comment un programme Haskell affiche-t-il quoi que ce soit ? Comment lit-il le clavier, écrit-il un fichier, parle-t-il au réseau ? Un programme qui ne fait rien au monde extérieur n'a pas beaucoup d'intérêt.

La réponse tient en deux lettres : IO. Et la bonne nouvelle, c'est que Haskell réussit l'exploit de faire des effets sans renoncer à la pureté. Le secret n'est pas un compromis honteux caché sous le tapis : c'est une idée nette qui, une fois comprise, change ta façon de structurer n'importe quel programme, dans n'importe quel langage.

Le problème : pureté contre effets

Une fonction pure ne peut pas, par définition, lire le clavier. Si getLine renvoyait directement une String, alors deux appels identiques rendraient des résultats différents (selon ce que tu tapes). La pureté serait brisée. Pourtant Haskell fait des entrées-sorties. Comment ?

L'astuce : getLine ne renvoie pas une chaîne, il renvoie une recette qui, quand on l'exécute, produira une chaîne. Cette recette, elle, est une valeur parfaitement pure et déterministe : c'est toujours « la même recette ». Vérifions son type dans GHCi.

Un IO String est « une action qui, exécutée, donnera une String ».

Lis IO String comme : « une description d'action qui, lorsqu'elle sera lancée par le système d'exécution, produira une String ». Le type () (prononcé « unit ») est le type qui ne porte aucune information utile, l'équivalent du void : putStrLn affiche du texte mais ne rend rien d'intéressant, donc son action est un IO ().

Un IO a est une valeur, pas une exécution

C'est LE point qui débloque tout. En Python, print("salut") fait quelque chose au moment où la ligne est évaluée. En Haskell, écrire putStrLn "salut" ne fait rien du tout : tu fabriques juste une valeur de type IO (), une recette posée sur la table. Tu peux la nommer, la mettre dans une liste, la passer à une fonction — rien ne s'affiche.

Alors qui exécute ces recettes ? Une seule chose : le système d'exécution (le runtime) de Haskell, qui prend la recette nommée main et la lance. main est le point d'entrée obligatoire de tout programme, et son type est IO ().

Note

Pense à une recette de cuisine écrite sur une fiche. Écrire la fiche ne te nourrit pas. Quelqu'un doit la suivre. En Haskell, ton code écrit les fiches ; le runtime suit celle qui s'appelle main. C'est exactement pour ça que la pureté tient : fabriquer une description est pur, seul le runtime « impur » l'exécute, et il est hors de ton langage.

Séquencer des actions : la notation do

Un vrai programme enchaîne plusieurs actions dans l'ordre. La notation do sert exactement à ça : elle colle des actions IO bout à bout pour en former une seule, plus grande.

Chaque ligne d'un bloc do est une action IO. Le bloc do tout entier est, lui aussi, une seule action IO — celle qui consiste à faire la première, puis la deuxième, puis la troisième. L'indentation compte : aligne tes actions sur la même colonne.

Récupérer une valeur : la flèche <-

Afficher, c'est bien ; lire, c'est mieux. Quand une action produit une valeur utile (comme getLine qui produit une String), on l'extrait avec <-. Lis nom <- getLine comme : « exécute l'action getLine, et donne le nom nom à la chaîne qu'elle produit ».

Attention à ne pas confondre <- et =. Le signe = nomme une valeur pure (let x = 2 + 3). La flèche <- exécute une action IO et nomme son résultat. On n'écrit jamais nom = getLine pour obtenir la chaîne : ça nommerait l'action elle-même, pas son résultat.

Piège fréquent

La valeur extraite par <- n'existe que dans le bloc IO. Tu ne peux pas « sortir » une String d'un IO String pour la rendre depuis une fonction pure. C'est voulu : si tu pouvais, la pureté s'effondrerait. Une fonction qui a besoin d'une entrée clavier est une action IO, son type le dit, et ça contamine honnêtement toute la chaîne d'appel.

return : emballer une valeur pure en action

Parfois, dans un bloc do, tu veux produire une valeur sans aucun effet. return prend une valeur pure et l'emballe dans une action IO qui « ne fait rien d'autre que rendre cette valeur ».

Méfie-toi du faux ami : return n'est pas le return de Python ou Java. Il n'interrompt rien, ne « sort » pas de la fonction. Il se contente d'emballer une valeur. Une action return placée au milieu d'un do ne stoppe pas les lignes suivantes. En Haskell moderne, on écrit d'ailleurs souvent pure à la place de return : c'est le même emballage.

Lire des nombres et boucler

getLine rend toujours une String. Pour obtenir un nombre, on convertit avec read, en précisant le type visé. On boucle, comme toujours en Haskell, par récursion — ou avec des combinateurs comme forM_ et mapM_ pour répéter une action sur chaque élément d'une liste.

Remarque le let n = ... sans in : dans un bloc do, let introduit une liaison pure pour les lignes suivantes. Tu utilises let pour du calcul pur et <- pour des actions IO. mapM_ est le cousin de forM_ avec les arguments dans l'ordre inverse : mapM_ print [1, 2, 3].

Les arguments de la ligne de commande

Pour lire ce qui suit le nom du programme sur la ligne de commande, on utilise getArgs du module System.Environment. Il rend une [String], une liste d'arguments.

On filtre la forme des arguments avec un case et du filtrage par motif.

Un programme complet : deviner un nombre

Assemblons tout. Voici un petit jeu : l'ordinateur a un nombre secret, tu proposes des valeurs, il te dit « trop grand » ou « trop petit » jusqu'à la bonne réponse. La boucle est une fonction récursive de type IO ().

La récursion remplace la boucle while : tant que la proposition est fausse, boucle se rappelle elle-même ; quand c'est gagné, elle ne se rappelle pas et l'action se termine. Aucune variable mutable, aucun break.

Séparer le cœur pur de la coquille IO

Voici la leçon d'architecture qui restera avec toi pour toujours. Garde la logique dans des fonctions pures, et réserve l'IO à une fine coquille qui lit les entrées, appelle le cœur pur, et affiche les sorties. Le pur est facile à tester et à raisonner ; l'IO est concentré au bord du programme.

Cette discipline — « fonctions pures au centre, effets aux frontières » — n'est pas propre à Haskell. On la retrouve sous les noms de functional core, imperative shell, ou d'architecture hexagonale, dans des projets Python, Java ou TypeScript. Haskell ne fait que t'y forcer par son système de types : c'est lui qui t'apprend le réflexe, et tu l'emportes partout.

Cas réel — Pandoc et ShellCheck

Deux outils qu'utilisent des millions de développeurs sont écrits en Haskell exactement sur ce modèle. Pandoc, le couteau suisse de conversion de documents (Markdown → PDF, Word, HTML…), enferme presque toute sa logique dans un immense cœur pur qui transforme un document en une structure de données, puis la ré-imprime ; l'IO se limite à lire le fichier d'entrée et écrire la sortie. ShellCheck, l'analyseur de scripts Bash intégré à d'innombrables éditeurs, fait pareil : un analyseur pur produit la liste des avertissements, une fine coquille IO lit le script et affiche le rapport. Résultat : le cœur se teste par milliers de cas sans jamais toucher au disque, et les bugs d'effets de bord restent cantonnés à quelques lignes.

Lire et écrire des fichiers

Les mêmes principes s'étendent aux fichiers, via les fonctions standard du Prelude. Ce sont des actions IO comme les autres, avec des types qui annoncent franchement ce qu'elles font.

Astuce

Pour comprendre n'importe quelle fonction, demande son type à GHCi avec :t. Si tu vois IO dedans, tu sais immédiatement qu'elle a un effet sur le monde. Le type est une étiquette d'honnêteté : impossible de cacher un effet de bord, il apparaît toujours dans la signature.

Pièges fréquents

  • Croire que putStrLn agit là où il est écrit. Non : il fabrique une action. Seul le runtime, en exécutant main, la déclenche. Une action jamais reliée à main ne s'exécute jamais.
  • Confondre = et <-. x <- action exécute l'action et nomme son résultat ; let x = expr nomme une valeur pure. Inverser les deux donne une erreur de type souvent déroutante.
  • Espérer « déballer » un IO a hors de l'IO. Il n'existe pas de fonction IO a -> a sûre. C'est une garantie, pas une limitation : une fois IO, toujours IO jusqu'à main.
  • Oublier l'annotation de type pour read. read ligne seul est ambigu (lire quoi ?). Écris read ligne :: Int pour lever l'ambiguïté.

Pour aller plus loin

Pour aller plus loin

Le mot « monade » va finir par surgir : IO en est une, et do/<- sont du sucre syntaxique pour l'opérateur >>= (« bind »). Pas de panique : une monade n'est rien d'autre qu'un motif pour enchaîner des calculs en passant un contexte (ici, « le monde »). Tu l'as déjà utilisée sans le savoir. On la démystifiera entièrement dans une leçon dédiée. Côté pratique, regarde getContents (lecture paresseuse de toute l'entrée), interact (relie une fonction pure String -> String à l'entrée/sortie), et hFlush stdout pour forcer l'affichage d'un putStr sans saut de ligne.

Antisèche — les entrées-sorties

Glossaire

IO a
Type d'une description d'action qui, une fois exécutée par le runtime, produira une valeur de type a. Fabriquer cette valeur est pur.
Action / recette
Métaphore d'un IO a : une fiche décrivant un effet à réaliser. L'écrire ne l'exécute pas.
main
Point d'entrée obligatoire de tout programme, de type IO () : la seule recette que le runtime suit.
Runtime
Système d'exécution de Haskell, hors de ton langage : le seul « impur » qui exécute réellement les actions IO.
<-
Dans un do, exécute une action et donne un nom à sa valeur produite. Ce n'est pas une affectation (=).
return / pure
a -> IO a : emballe une valeur pure dans une action qui « ne fait que la rendre ». N'interrompt rien (faux ami du return impératif).
() (unit)
Type sans information utile, l'équivalent du void : IO () = une action faite pour son effet, pas pour sa valeur.
Functional core, imperative shell
Architecture où la logique vit dans un cœur pur testable, entouré d'une fine coquille IO aux frontières.

Récap et vérification

  • IO a est la description d'une action qui, exécutée, produira une valeur de type a — ce n'est pas l'exécution.
  • Seul main :: IO () est lancé par le runtime ; c'est lui qui « suit la recette ».
  • La notation do séquence des actions ; <- extrait le résultat d'une action ; return (ou pure) emballe une valeur pure.
  • read convertit une String en nombre ; on boucle par récursion ou avec forM_/mapM_ ; getArgs lit les arguments.
  • Bonne architecture : un cœur pur testable entouré d'une fine coquille IO.

Vérifie ta compréhension

  1. Pourquoi écrire putStrLn "x" dans une variable n'affiche-t-il rien ? Qu'est-ce qui déclenche réellement l'affichage ?
  2. Quelle est la différence entre nom = getLine et nom <- getLine dans un bloc do ?
  3. En quoi le fait de décrire les effets dans le type IO permet-il de préserver la pureté du reste du langage ?
