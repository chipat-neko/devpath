Module 2 · Le système de types — Leçon 05

Types algébriques et pattern matching

~55 min Avancé Prérequis : leçon 4

À la fin de cette leçon, tu sauras

  • définir des types produit et somme avec data, et y accéder par pattern matching ;
  • écrire un pattern matching exhaustif et comprendre l'avertissement du compilateur ;
  • remplacer null par Maybe et modéliser le succès ou l'erreur avec Either ;
  • concevoir des types paramétrés qui rendent l'état invalide impossible.
Sommaire de la leçon

Jusqu'ici tu as manipulé des types que Haskell te fournit : Int, String, des listes, des tuples. Mais la vraie puissance du système de types arrive quand tu crées tes propres types. En Python ou en Java, modéliser un domaine veut dire empiler des classes, des champs nullables, des constantes entières pour les « statuts ». En Haskell, tu décris la forme exacte de tes données avec un seul mot-clé : data. Et une fois cette forme décrite, le compilateur devient ton allié : il refuse les valeurs impossibles et te rappelle les cas que tu as oubliés.

C'est le cœur du changement de mentalité de ce module : au lieu de coder des règles à la main et d'espérer qu'elles tiennent, tu les inscris dans les types. Si le code compile, des familles entières de bugs ont déjà disparu. On va construire ça pas à pas, sans jargon.

Les types produit : assembler des valeurs

Un type produit regroupe plusieurs valeurs en une seule, comme une struct en C ou une classe à champs en Java. « Produit » parce qu'un Point contient une coordonnée x ET une coordonnée y : l'ensemble des points possibles est le produit des x possibles par les y possibles.

Note que Point apparaît deux fois : à gauche c'est le nom du type, à droite le nom du constructeur. Il est courant de leur donner le même nom quand il n'y a qu'un seul cas, mais ce sont deux choses distinctes vivant dans deux espaces différents.

Note

Les noms de types et de constructeurs commencent toujours par une majuscule. Les variables et fonctions, toujours par une minuscule. Ce n'est pas un style, c'est une règle de syntaxe : le compilateur s'en sert pour savoir de quoi tu parles.

Lire un type produit : le pattern matching

Pour extraire les valeurs d'un Point, on ne fait pas p.x : on filtre par motif (pattern matching). On décrit à quoi ressemble la valeur, et Haskell relie les morceaux à des noms.

Le motif (Point x y) dit : « si l'argument est un Point, appelle ses deux champs x et y ». C'est l'inverse du constructeur : là où Point 3 4 assemble, (Point x y) désassemble.

La syntaxe record : nommer les champs

Avec deux Double identiques, rien ne t'empêche d'inverser x et y par erreur. La syntaxe d'enregistrement (record) nomme les champs et génère automatiquement des fonctions d'accès.

La syntaxe pt { y = ... } ne modifie rien (l'immutabilité reste sacrée) : elle fabrique un nouveau Point identique sauf pour y. C'est l'équivalent fonctionnel de « copier avec une modification ».

Les types somme : représenter un choix

Voici ce qui manque cruellement à la plupart des langages impératifs. Un type somme dit « cette valeur est l'un de ces cas, exclusivement ». On sépare les cas par |.

En Java, tu aurais une hiérarchie de classes Forme, Cercle extends Forme… avec du polymorphisme et le risque d'un cas manquant à l'exécution. Ici, Forme est fermé : il y a exactement deux cas, le compilateur les connaît tous, et aire les traite par pattern matching en deux lignes.

Astuce

« Produit » = ET (un Point a x ET y). « Somme » = OU (une Forme est un Cercle OU un Rectangle). La plupart des types réels combinent les deux : un type somme dont chaque cas est un petit produit. C'est exactement ce que veut dire « type algébrique ».

L'exhaustivité : le compilateur compte pour toi

Le pattern matching n'est pas qu'une commodité : il est vérifié. Si tu oublies un cas, GHC te prévient. Compile avec -Wall (ou -Wincomplete-patterns) pour activer l'avertissement.

Pense à ce que ça change. Le jour où tu ajoutes Jaune à Couleur, le compilateur listera toutes les fonctions qui ne gèrent pas encore Jaune. Tu ne peux pas oublier une mise à jour : c'est un refactoring guidé par les types, pas par la chance.

Maybe : l'alternative sûre à null

« L'erreur à un milliard de dollars », c'est le nom que son inventeur a donné au null. Le problème : n'importe quelle valeur peut secrètement être null, et tu l'apprends par un crash. Haskell n'a pas de null. À la place, quand une valeur peut être absente, tu le dis dans le type avec Maybe.

La différence est radicale : diviser renvoie Maybe Double, donc le type t'oblige à gérer l'absence avant d'atteindre la valeur. Il n'existe aucun moyen de « déballer » un Maybe sans considérer le cas Nothing. Le crash à l'exécution devient une erreur de compilation.

Either : porter une erreur, pas juste son absence

Maybe dit « il y a une valeur, ou rien ». Mais « rien » ne dit pas pourquoi. Quand tu veux expliquer l'échec, Either transporte soit une erreur (Left), soit un succès (Right). Astuce mnémotechnique : Right = la bonne (right) réponse.

Ici case … of est juste un pattern matching « en ligne ». Le motif [(n, "")] dit « reads a réussi à lire un nombre et il ne reste rien après » ; la signature Int guide reads pour qu'il lise bien un entier. Les barres verticales | sont ensuite des gardes : des conditions booléennes testées dans l'ordre. Le type de retour Either String Int annonce honnêtement au lecteur qu'un appel peut échouer, et avec quel message.

Types paramétrés : des conteneurs génériques

Tu as vu le a dans Maybe a : c'est un paramètre de type, l'équivalent des génériques (List<T> en Java). Tu peux paramétrer tes propres types, y compris des types récursifs comme un arbre binaire.

Remarque que taille fonctionne pour Arbre Int, Arbre String ou n'importe quoi : elle ne regarde que la structure, jamais les valeurs. Et la définition récursive du type se reflète dans la fonction récursive — les deux ont exactement la même forme : un cas de base (Feuille) et un cas qui se rappelle (Noeud).

Rendre l'invalide impossible

Voilà l'idée qui irrigue tout le reste. En modélisant avec des types somme bien choisis, tu peux faire en sorte que les états interdits ne soient même pas représentables.

La règle métier « un contact a au moins un moyen de le joindre » n'est plus un commentaire ni une validation à exécuter : elle est garantie par le type. Le code qui ne respecte pas la règle ne compile pas. C'est ça, « rendre l'invalide impossible ».

Cas réel — la fin du milliard de dollars de bugs

L'idée « rendre l'absence explicite dans le type » a essaimé bien au-delà de Haskell. Rust a repris Maybe/Either sous les noms Option et Result et en a fait le pilier de sa gestion d'erreurs ; Swift impose ses Optional (le ?) pour bannir le crash sur nil ; TypeScript ajoute les unions T | null vérifiées par le compilateur ; le langage Elm revendique zéro exception à l'exécution en production, précisément grâce à ces types. Le NullPointerException qui a fait planter des systèmes entiers n'est pas une fatalité : c'est un choix de conception que ces types éliminent.

Pièges fréquents

Piège fréquent

Confondre le type et le constructeur. Dans une signature (p :: Point) tu écris le nom du type ; dans une valeur ou un motif (Point 3 4) tu écris le constructeur. Maybe est un type ; Just et Nothing sont ses constructeurs — tu ne peux pas écrire x :: Just.

Piège fréquent

Oublier deriving (Show, Eq) puis s'étonner que GHCi refuse d'afficher ta valeur (No instance for Show) ou que == ne marche pas. Ces deux clauses demandent au compilateur de générer gratuitement l'affichage et la comparaison. Ajoute-les par réflexe sur tes types de données.

Pour aller plus loin

Pour aller plus loin

Maybe et Either ne sont pas que des types pratiques : ce sont des monades, ce qui permettra plus tard d'enchaîner des calculs faillibles sans pyramide de case imbriqués (la fameuse notation do). Tu peux aussi explorer maybe et either (en minuscule), des fonctions qui consomment ces types d'un coup. On y reviendra : aujourd'hui, l'essentiel est de penser tes données en termes de cas et de structure.

Antisèche — types algébriques

Glossaire

Type algébrique
Type construit avec data par combinaison de produits (ET) et de sommes (OU).
Type produit
Constructeur regroupant plusieurs valeurs simultanées, comme une struct (un Point a un x et un y).
Type somme
Type offrant plusieurs constructeurs mutuellement exclusifs, séparés par |.
Constructeur
Fonction qui fabrique une valeur d'un type (Just, Cercle) ; commence par une majuscule.
Record
Syntaxe qui nomme les champs d'un produit et génère leurs fonctions d'accès.
Pattern matching
Filtrage par motif qui désassemble une valeur selon sa forme ; vérifié comme exhaustif par GHC.
Maybe
Type somme Nothing | Just a qui remplace null en rendant l'absence explicite.
Either
Type somme Left a | Right b qui porte une erreur (Left) ou un succès (Right).

Récap et vérification

  • data crée un type ; à droite du =, un ou plusieurs constructeurs séparés par |.
  • Type produit : un constructeur qui regroupe plusieurs valeurs (ET). La syntaxe record nomme les champs.
  • Type somme : plusieurs constructeurs, chacun un cas exclusif (OU), avec ses propres données.
  • Le pattern matching désassemble les valeurs ; le compilateur vérifie qu'il est exhaustif (avec -Wall).
  • Maybe remplace null de façon sûre ; Either porte en plus une erreur explicite.
  • Les types paramétrés (Arbre a) sont génériques ; bien choisis, ils rendent l'invalide impossible.

Vérifie ta compréhension

  1. Quelle est la différence entre un type produit et un type somme ? Donne un exemple de chacun.
  2. Pourquoi Maybe Double est-il plus sûr qu'un Double qui pourrait être null ?
  3. Tu ajoutes un constructeur à un type somme existant. Que va faire le compilateur si une fonction ne le gère pas (avec -Wall) ?
