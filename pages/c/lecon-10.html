Préprocesseur et compilation multi-fichiers

~33 min Avancé Leçon 9 recommandée

À la fin de cette leçon, tu sauras

  • comprendre le rôle du préprocesseur et écrire des #define et des macros à arguments correctement parenthésées ;
  • découper un programme en fichiers .h (déclarations) et .c (définitions) protégés par des gardes d'en-tête ;
  • partager ou restreindre des symboles avec extern et static, et activer du code via #ifdef DEBUG ;
  • écrire un Makefile minimal qui compile chaque .c en .o puis lie l'exécutable.
Sommaire de la leçon

Jusqu'ici tes programmes tenaient dans un seul fichier. Mais dès qu'un projet grossit, tout entasser dans main.c devient ingérable : temps de compilation qui explose, code introuvable, réutilisation impossible. La solution est universelle en C : séparer les déclarations (dans des fichiers d'en-tête .h) des définitions (dans des fichiers source .c), puis compiler chaque source indépendamment avant de tout assembler.

Pour comprendre comment ces fichiers se recollent, il faut d'abord regarder ce qui se passe avant le compilateur proprement dit : le préprocesseur. On verra ensuite la compilation séparée, les gardes d'en-tête, le partage de symboles avec extern/static, la compilation conditionnelle, et enfin le Makefile qui automatise tout cela.

Le préprocesseur : une étape avant la compilation

Avant de traduire ton code en instructions machine, gcc lance le préprocesseur. C'est un simple manipulateur de texte : il ne connaît rien au C, il se contente de copier-coller et de substituer. Toutes ses directives commencent par #.

Note

Une macro n'a pas de type et n'apparaît pas dans le code compilé : impossible de la déboguer ou d'en prendre l'adresse. Pour de la vraie logique, préfère une fonction. Garde les macros pour les constantes et les substitutions très simples.

Compilation séparée : .h pour déclarer, .c pour définir

L'idée centrale : chaque .c se compile en un fichier objet .o indépendamment des autres, puis l'éditeur de liens (le linker) assemble tous les .o en un exécutable. Pour qu'un fichier puisse appeler une fonction définie ailleurs, il lui suffit d'en connaître la déclaration (le prototype), placée dans un .h.

Piège fréquent

N'inclus jamais un .c avec #include "calcul.c". Tu recopierais ses définitions dans plusieurs unités, et le linker refuserait avec une erreur de multiple definition. On n'inclut que des .h.

Les gardes d'en-tête contre les inclusions multiples

Un même .h finit souvent inclus deux fois (directement, puis via un autre en-tête). S'il contient des définitions de types ou de structures, le compilateur voit deux fois la même chose et renvoie une erreur de redéfinition. La parade : une garde d'en-tête qui rend l'inclusion idempotente.

Astuce

La plupart des compilateurs (gcc, clang, MSVC) acceptent #pragma once en première ligne : une seule ligne pour le même effet. C'est plus court mais non normalisé par le standard. Les deux approches sont valables ; reste cohérent dans un projet.

Partager (extern) ou cacher (static) un symbole

Une variable globale doit être définie une seule fois dans tout le programme, mais peut être déclarée dans plusieurs fichiers via extern (qui dit « elle existe ailleurs »).

Le mot-clé static sur une variable ou une fonction globale limite sa visibilité au fichier courant : les autres .c ne peuvent pas la référencer. C'est le moyen d'encapsuler les détails internes d'un module.

Piège fréquent

Écrire int compteur = 0; (sans extern) dans un .h inclus par plusieurs .c crée une définition dans chaque unité : le linker échoue sur multiple definition of 'compteur'. Dans le .h, on déclare avec extern ; on définit dans un seul .c.

Automatiser avec un Makefile

Taper toutes ces commandes à la main est vite pénible. L'outil make lit un fichier Makefile décrit en termes de cibles, de dépendances et de règles. Une cible n'est reconstruite que si l'un de ses fichiers source est plus récent que le résultat : la recompilation devient incrémentale.

Piège fréquent

La ligne de commande sous une cible doit commencer par une tabulation, jamais par des espaces. Sinon make renvoie *** missing separator. C'est l'erreur numéro un des débutants.

Modifie un seul .c puis relance make : seul cet objet est recompilé.

Note

La cible clean ne crée aucun fichier nommé « clean » : on la déclare .PHONY pour que make l'exécute toujours, même si un fichier clean existait par hasard dans le dossier.

Cas réel

Le noyau Linux compte plus de 30 millions de lignes réparties sur des dizaines de milliers de fichiers .c. Si chaque make recompilait l'ensemble, corriger une seule ligne prendrait des dizaines de minutes. Grâce à la compilation séparée, seul le .o du fichier modifié — et ceux qui dépendent d'un .h changé — est reconstruit : la boucle « j'édite, je recompile, je teste » retombe à quelques secondes. C'est exactement le mécanisme de cette leçon, appliqué à l'échelle d'un système d'exploitation.

Bonnes pratiques d'organisation

Quelques règles qui tiennent la route sur un vrai projet : un module = une paire .h/.c au nom identique ; le .h ne contient que ce que les autres doivent voir (prototypes, types publics, constantes), le reste est static dans le .c ; chaque .c inclut son propre .h en premier (pour vérifier qu'il est auto-suffisant) ; toujours une garde d'en-tête ; jamais de définition de variable dans un .h. Compile dès le départ avec -Wall -Wextra pour que le compilateur signale les incohérences tôt.

Pièges fréquents

  • Macro sans parenthèses : #define CARRE(x) x*x casse les priorités. Parenthèse chaque argument et l'expression entière.
  • Effet de bord dans une macro : CARRE(i++) devient ((i++) * (i++)) : i est incrémenté deux fois, et modifier i deux fois sans point de séquence est un comportement indéfini. Ne passe jamais d'expression à effet de bord à une macro.
  • Garde d'en-tête oubliée : double inclusion => redéfinitions et erreur de compilation.
  • Inclure un .c ou définir une variable dans un .h : multiple definition à l'édition de liens.
  • Tabulation manquante dans le Makefile : missing separator.

Pour aller plus loin

Les fonctions inline offrent la rapidité des macros avec la sécurité du typage : préfère-les dès que la logique dépasse une substitution triviale. Côté outillage, CMake génère des Makefiles portables pour des projets multi-plateformes, et l'on peut regrouper des objets en bibliothèques statiques (.a) ou dynamiques (.so). Glossaire

Préprocesseur
Première étape de gcc : manipule le texte source (directives #) avant toute compilation.
Macro
Substitution de texte définie par #define ; sans type ni existence à l'exécution.
Garde d'en-tête
Triade #ifndef/#define/#endif (ou #pragma once) rendant une inclusion idempotente.
Unité de compilation
Un fichier .c avec tous ses #include développés ; compilée en un .o.
Fichier objet (.o)
Code machine d'une unité, pas encore lié ; produit par gcc -c.
Éditeur de liens (linker)
Assemble les .o et les bibliothèques en un exécutable, en résolvant les symboles.
extern / static
extern déclare un symbole défini ailleurs ; static restreint sa visibilité au fichier.
Makefile
Fichier de règles (cible, dépendances, commandes) lu par make pour une compilation incrémentale.

Récap et vérification

  • Le préprocesseur agit avant la compilation : #include insère du texte, #define substitue constantes et macros.
  • Les macros à arguments exigent un parenthésage complet et n'acceptent pas d'effet de bord.
  • On déclare dans le .h, on définit dans le .c ; chaque .c se compile en .o, puis on lie.
  • Une garde d'en-tête (#ifndef/#define/#endif ou #pragma once) évite les inclusions multiples.
  • extern partage une globale, static la cache dans son fichier ; #ifdef active du code à la demande.
  • Un Makefile automatise la compilation incrémentale (cibles, dépendances, règles, tabulations).
