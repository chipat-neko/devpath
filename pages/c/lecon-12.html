Organiser un projet et aller plus loin

~33 min Avancé Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • savoir organiser un projet en modules .h/.c avec un découpage src/include cohérent ;
  • savoir lier la bibliothèque standard et une bibliothèque externe, et distinguer liaison statique (.a) et dynamique (.so/.dll) ;
  • savoir appliquer de bonnes pratiques (gestion d'erreur cohérente, tests avec assert, documentation) ;
  • savoir vers quoi continuer après le C : C++, Rust, programmation système POSIX, embarqué.
Sommaire de la leçon

Tu sais désormais écrire des fonctions, manipuler la mémoire, gérer des pointeurs et des structures. Mais un vrai programme ne tient pas dans un seul fichier : il se répartit en modules, s'appuie sur des bibliothèques, et se construit avec un outil de build. Cette dernière leçon te montre comment passer d'un script jetable à un projet structuré, maintenable et testé.

On va voir l'organisation des fichiers, le rôle des bibliothèques, un mini-projet réparti en modules, les bonnes pratiques de robustesse, puis un panorama de ce qui t'attend après le C : C++, Rust, la programmation système et l'embarqué.

Organiser un projet : séparer interface et implémentation

En C, un module se compose de deux fichiers : un en-tête .h (l'interface : ce que le module offre au reste du monde) et un .c (l'implémentation : comment il le fait). Compilation séparée : du .c à l'exécutable

Chaque .c se compile indépendamment en un fichier objet .o, puis l'éditeur de liens (linker) assemble tous les objets en un exécutable. C'est la compilation séparée : si tu modifies un seul module, tu ne recompiles que lui.

Le drapeau -Iinclude dit au compilateur où trouver pile.h ; -c arrête la compilation au stade objet ; la dernière commande relie tout. Active toujours -Wall -Wextra : les avertissements signalent souvent un comportement indéfini en germe.

Les bibliothèques : standard et externes

Une bibliothèque est un ensemble de fonctions précompilées qu'on lie à son programme. La bibliothèque standard du C est toujours disponible : <stdio.h> (entrées/sorties), <stdlib.h> (mémoire, conversions, exit), <string.h> (chaînes), <math.h> (maths). Statique ou dynamique ?

Une bibliothèque peut être liée de deux façons. En statique (.a sous Unix, .lib sous Windows/MSVC), le code de la lib est copié dans ton exécutable : il devient autonome mais plus gros, et figé à la version compilée. En dynamique (.so sous Linux, .dll sous Windows, .dylib sous macOS), la lib reste un fichier séparé chargé à l'exécution : l'exécutable est plus léger et profite des mises à jour de la lib, mais il faut que celle-ci soit présente sur la machine cible.

Note

Si un programme se plaint au démarrage d'une .so introuvable (error while loading shared libraries), c'est une liaison dynamique dont la bibliothèque manque ou n'est pas dans le chemin de recherche. La liaison statique évite ce souci au prix d'un binaire plus volumineux.

Bonnes pratiques : robustesse, tests, documentation

Un code de qualité respecte quelques règles simples : une gestion d'erreur cohérente (toujours le même style : par exemple 0 pour le succès et un négatif pour l'échec, comme ci-dessus) ; pas de variables globales inutiles (préfère passer les données en paramètre) ; des fonctions courtes et bien nommées ; et une documentation minimale dans les .h.

Pour les tests, pas besoin d'un framework tout de suite : la macro assert de <assert.h> suffit à vérifier des invariants. Si la condition est fausse, le programme s'arrête en signalant le fichier et la ligne.

Piège fréquent

Compiler avec -DNDEBUG (souvent activé en build « release ») désactive tous les assert : la condition n'est plus évaluée du tout. Ne mets donc jamais d'effet de bord nécessaire dans un assert (comme assert(pile_push(p, 1) == 0); hors test) — il disparaîtrait en release.

Astuce

Compile tes tests avec un sanitizer pour détecter fuites et accès mémoire invalides : gcc -fsanitize=address,undefined -g …. C'est l'un des meilleurs filets de sécurité contre le comportement indéfini en C.

Aller plus loin que le C

Le C est une base : il t'a appris la mémoire, les pointeurs, la compilation. Plusieurs chemins s'ouvrent :

  • C++ : ajoute les objets, le RAII (libération automatique des ressources), les templates et la STL (conteneurs et algorithmes prêts à l'emploi). Idéal pour de gros logiciels performants.
  • Rust : même niveau de contrôle que le C, mais avec une sûreté mémoire garantie à la compilation (système d'ownership) — plus de fuites ni de pointeurs invalides accidentels.
  • Programmation système (POSIX) : processus, fichiers, sockets réseau, threads (pthreads). C'est le terrain naturel du C sous Linux et macOS.
  • Embarqué : microcontrôleurs, registres, contraintes mémoire serrées. Le C y règne car il colle au matériel.

Cas réel

Quand une faille critique est découverte dans une bibliothèque très répandue — comme zlib ou OpenSSL —, les distributions Linux publient une .so corrigée. Tous les programmes qui la lient dynamiquement sont protégés dès leur prochain lancement, sans recompilation. À l'inverse, un logiciel qui a lié la même bibliothèque en statique embarque la version vulnérable : il faut le recompiler et le redéployer un par un. C'est tout l'arbitrage « autonomie contre mise à jour » de cette leçon, avec de vraies conséquences de sécurité.

Pièges fréquents

  • Tout mettre dans un seul fichier : illisible et impossible à recompiler partiellement. Découpe en modules dès que ça grossit.
  • Dépendances circulaires : si a.h inclut b.h qui réinclut a.h, tu crées un cycle. Les gardes d'inclusion évitent la double inclusion, mais repense plutôt le découpage.
  • Gestion d'erreur incohérente : mélanger return -1, exit(1) et codes positifs rend le code imprévisible. Choisis une convention et tiens-la.
  • Réinventer la stdlib : tu n'as pas besoin de réécrire strlen ou qsort. Connais ta bibliothèque standard avant de coder.
  • Négliger les tests : sans assert ni tests, chaque modification est un pari. Un test raté vaut mieux qu'un bug en production.

Piège fréquent

Oublier la garde d'inclusion dans un .h provoque des erreurs de redéfinition dès qu'il est inclus deux fois (directement et via un autre en-tête). Mets toujours le couple #ifndef / #define / #endif.

Pour aller plus loin

Explore CMake pour des builds portables ; les frameworks de test Unity et CMocka pour aller au-delà d'assert ; l'intégration continue (GitHub Actions) pour compiler et tester à chaque commit ; les threads POSIX (pthreads) pour le parallélisme ; et bien sûr le passage au C++ ou à Rust pour la suite de ton parcours.

Glossaire

Module
Une paire .h/.c de même nom : l'en-tête déclare, la source implémente.
Interface / implémentation
Ce qu'un module expose (.h) vs comment il le fait (.c) ; le client ne dépend que de l'interface.
Type opaque
struct déclarée sans ses champs dans le .h : le client manipule un pointeur sans voir l'intérieur.
Bibliothèque
Ensemble de fonctions précompilées liées au programme ; standard (libm…) ou externe.
Liaison statique (.a)
Le code de la bibliothèque est copié dans l'exécutable : autonome mais plus gros et figé.
Liaison dynamique (.so/.dll)
La bibliothèque reste un fichier séparé chargé à l'exécution : léger et partagé, mais requis sur la cible.
make / Makefile
Outil et fichier de règles qui automatisent la construction incrémentale.
assert
Macro de <assert.h> qui stoppe le programme si une condition est fausse ; désactivée par NDEBUG.

Récap et vérification

  • Un module = un .h (interface) + un .c (implémentation) ; on range les en-têtes dans include/ et les sources dans src/.
  • Chaque .c se compile en .o, puis l'éditeur de liens assemble l'exécutable (compilation séparée).
  • La stdlib couvre stdio, stdlib, string, math (avec -lm) ; les libs externes se lient avec -I, -L, -l.
  • Liaison statique (.a, binaire autonome) vs dynamique (.so/.dll, partagée à l'exécution).
  • make ou CMake automatisent la construction ; assert donne des tests simples (désactivés par NDEBUG).
  • Bonnes pratiques : gestion d'erreur cohérente, types opaques, gardes d'inclusion, tests, documentation.
