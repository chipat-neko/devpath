Module 04 · C en profondeur — Leçon 16

Tester son code C

~36 min Intermédiaire Compilation multi-fichiers (leçon 10) utile

À la fin de cette leçon, tu sauras

  • utiliser assert() pour vérifier des invariants ;
  • construire un mini-framework de tests en quelques macros ;
  • organiser et compter ses tests, couvrir les cas limites ;
  • traquer les bugs mémoire avec les sanitizers.
Sommaire de la leçon

En C, une erreur de logique ne se contente pas de donner un mauvais résultat : elle peut corrompre la mémoire, planter au hasard, ou ouvrir une faille. Les tests automatisés sont donc encore plus précieux ici qu'ailleurs. La bibliothèque standard du C ne fournit pas de framework de test ; mais le langage est si simple qu'on en construit un en quelques macros — et c'est exactement ce qu'on va faire, avant de citer les outils prêts à l'emploi.

assert() : vérifier un invariant

La macro assert() de <assert.h> arrête le programme si une condition est fausse, en affichant fichier et ligne. Elle exprime un invariant : une chose qui doit toujours être vraie à ce point du code.

Deux limites : assert() disparaît si on compile avec -DNDEBUG (build optimisé), et il arrête tout au premier échec. C'est idéal pour documenter une précondition pendant le développement, mais une vraie suite de tests doit tous les exécuter et faire un rapport.

Un mini-framework en quelques macros

On construit notre propre cadre : une macro qui compare un résultat à l'attendu, compte les succès et les échecs, et continue après un échec. Pas de dépendance, juste du C.

Deux astuces de préprocesseur (module 3) font tout le travail : #condition transforme l'expression en chaîne pour l'afficher, et __LINE__ donne le numéro de ligne. Le do { ... } while (0) est l'idiome qui rend une macro multi-instructions sûre à utiliser dans un if. Le code de sortie (0 = succès) permet à un script ou à la CI de savoir si la suite a réussi.

Couvrir les cas limites

Un bon test ne vérifie pas que le cas « qui marche » : il cible les frontières, là où les bugs se cachent. Pour une fonction sur des chaînes ou des tableaux : l'entrée vide, l'élément unique, le dépassement potentiel.

Chaque ligne teste un cas différent : vide, normal, borne, limite. C'est cette variété qui donne confiance — pas le nombre de tests, mais leur diversité face aux situations réelles.

Les sanitizers : tester aussi la mémoire

En C, un test peut passer tout en cachant un bug mémoire (lecture hors limites, fuite, use-after-free). Compile et lance tes tests avec l'AddressSanitizer : gcc -fsanitize=address,undefined -g test.c. Il instrumente le programme et signale précisément l'accès fautif avec sa pile d'appels. C'est l'outil le plus rentable du C moderne : active-le sur toute ta suite de tests.

Cas réel

Heartbleed (2014) reste l'illustration parfaite. Une faille dans OpenSSL — écrite en C — laissait recopier jusqu'à 64 Kio de mémoire du serveur en se fiant à une longueur fournie par le client, sans vérifier qu'elle correspondait aux données réellement reçues. Les tests fonctionnels passaient au vert : sur une requête normale, la réponse était correcte. C'était une lecture hors limites que seuls le fuzzing et les sanitizers mémoire révèlent — et qui a exposé mots de passe et clés privées sur des centaines de milliers de serveurs. La leçon : en C, « le test passe » ne veut pas dire « la mémoire est saine ». Teste les cas limites, et lance ta suite sous -fsanitize=address.

Pour aller plus loin

Pour aller plus loin

Pour de vrais projets, des frameworks dédiés évitent de réinventer la roue : Unity (très léger, idéal pour l'embarqué), Check, CMocka (avec mocks et tests isolés par processus), ou Criterion. Couple-les à valgrind ou aux sanitizers pour la mémoire, à gcov pour la couverture, et lance le tout via make test dans ta chaîne d'intégration continue.

Glossaire

Invariant
Propriété toujours vraie à un point donné du code ; assert() la vérifie et interrompt le programme si elle est fausse.
assert()
Macro de <assert.h> qui stoppe l'exécution sur condition fausse ; désactivée par -DNDEBUG.
Cas limite
Situation frontière (entrée vide, élément unique, borne atteinte, débordement) où les bugs se concentrent.
Stringification
Opérateur # du préprocesseur qui transforme un argument de macro en chaîne de caractères.
__LINE__
Macro prédéfinie donnant le numéro de la ligne courante ; utile pour localiser un test qui échoue.
Code de sortie
Entier renvoyé par le programme (0 = succès) ; permet à un script ou à la CI de savoir si la suite a réussi.
Sanitizer
Instrumentation du compilateur (-fsanitize=address,undefined) qui signale à l'exécution les accès mémoire invalides et les comportements indéfinis.
Régression
Bug réapparu après coup ; un test de non-régression, conservé après correction, empêche son retour.

Récap et vérification

  • assert() documente un invariant, mais s'arrête au premier échec et disparaît avec -DNDEBUG.
  • Un mini-framework tient en une macro VERIFIER (avec #x et __LINE__) qui compte et continue.
  • Le code de sortie (0 = succès) permet l'automatisation par script/CI.
  • On cible les cas limites (vide, unique, borne), pas seulement le cas nominal.
  • Les sanitizers (-fsanitize=address,undefined) attrapent les bugs mémoire qu'un test seul ne voit pas.

  2. À quoi servent #condition et __LINE__ dans la macro de test ?

Voir une solution

-fsanitize=address instrumente chaque accès mémoire pour détecter dépassements de tableau, use-after-free et fuites ; -fsanitize=undefined attrape les comportements indéfinis (débordement d'entier signé, décalage invalide…). En C, un test peut réussir tout en corrompant la mémoire : le programme « a l'air » de marcher mais plantera ailleurs, plus tard, de façon imprévisible. Les sanitizers transforment ces bugs silencieux en erreurs immédiates et localisées.
