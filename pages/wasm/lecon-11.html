Projet : un studio d'image WebAssembly

~40 min Intermédiaire Leçons 01 à 10

À la fin de cette leçon, tu sauras

  • assembler tout le cours en un projet réel : filtrer une image côté client ;
  • confier le calcul lourd (des millions de pixels) à un module Wasm ;
  • garder l'interface fluide grâce à un Web Worker ;
  • réutiliser le même cœur hors du navigateur avec WASI.
Sommaire de la leçon

Dernière étape ! Tu as vu ce qu'est Wasm, comment le compiler, échanger de la mémoire avec JavaScript, lire son format texte, franchir la frontière sans douleur avec wasm-bindgen, calculer sans bloquer dans un Web Worker, et l'exécuter hors du navigateur avec WASI. Ce projet réunit tout : un petit studio d'image qui applique un filtre à une photo, entièrement côté client, sans figer la page — et dont le cœur de calcul se réutilise en ligne de commande.

Le projet en un coup d'œil

L'utilisateur charge une image dans un <canvas>, clique sur « niveaux de gris », et l'image filtrée s'affiche — instantanément et sans à-coup, même sur une grande photo. Le calcul, lui, part dans un module Wasm exécuté par un Worker. Et le même filtre, recompilé pour WASI, traite un dossier entier au terminal.

Pourquoi une image ?

Une photo de 4000 × 3000 pixels, c'est 48 millions d'octets à parcourir (4 octets RGBA par pixel). C'est exactement le genre de travail lourd, régulier et répété où Wasm brille — et où le franchissement de frontière et le blocage de l'interface deviennent visibles si on s'y prend mal.

L'architecture : qui fait quoi

Chaque brique a un rôle unique. C'est le fil rouge du cours : JavaScript orchestre, Wasm calcule — et cette fois, le calcul est isolé dans un Worker.

Le cœur : le filtre (Rust + wasm-bindgen)

On écrit le calcul une seule fois. Un <canvas> range ses pixels en RGBA : quatre octets par pixel (rouge, vert, bleu, alpha). Le filtre parcourt ce tableau par paquets de quatre :

On compile en module prêt pour le web : wasm-pack build --target web. wasm-pack produit le .wasm et la colle JavaScript (le glue) qui expose niveaux_de_gris comme une fonction ordinaire.

« Sur place » = moins de copies

Le filtre modifie le tableau directement (&mut [u8]) plutôt que d'en fabriquer un nouveau. C'est le principe de la leçon 4 : beaucoup de travail, peu d'allers-retours. On confie tout le tableau d'un coup, le filtre le retraverse en entier côté Wasm, et on ne franchit la frontière qu'aux deux extrémités.

Le Worker : calculer sans bloquer

Si on filtrait sur le thread principal, la page gèlerait le temps du calcul (curseur figé, boutons morts). On délègue donc au Worker : il charge le module une fois, applique le filtre, et renvoie les pixels.

Après un transfert, le tampon est vidé

Quand tu transfères image.data.buffer, le tableau d'origine devient inutilisable côté émetteur (longueur 0) : sa propriété a changé de main. C'est justement ce qui rend le transfert gratuit (aucune copie). Ne relis donc pas les pixels après les avoir envoyés ; attends la réponse.

Réutiliser le cœur hors du navigateur (WASI)

La fonction niveaux_de_gris ne connaît ni le DOM, ni fetch : c'est du calcul pur. On peut donc la recompiler pour WASI et l'appeler au terminal, sur de vrais fichiers, sans réécrire une ligne du filtre :

Le bac à sable par capacités

Remarque le --dir=. : sans lui, le module WASI ne verrait aucun fichier. WASI n'accorde que ce qu'on lui donne explicitement (leçon 10). Le même isolement qui protège le navigateur protège ta machine au terminal.

Cas réel — le traitement d'image dans le navigateur

Figma (moteur de rendu C++ → Wasm), Photoshop web (Adobe, via Emscripten), Google Earth et Squoosh font tous exactement cela : du calcul graphique lourd compilé en WebAssembly, piloté par une interface JavaScript, souvent dans un Worker pour rester fluide. Ton studio d'image est une version miniature du même patron d'architecture.

Mini-projet fil rouge — ton studio d'image

À toi de jouer ! Construis une page qui applique un filtre à une image via un module Wasm exécuté dans un Worker, puis réutilise le même cœur au terminal. L'objectif est de relier toute la chaîne du cours en une réalisation qui tient debout.

Ce que tu vas construire

Une page servie en local qui charge une image dans un <canvas>, applique un filtre (niveaux de gris, puis luminosité) via un module .wasm exécuté dans un Web Worker, et affiche le résultat sans figer l'interface. En bonus : recompile le même filtre pour WASI et traite un dossier d'images au terminal.

Étapes

1. Le cœur

Écris le filtre (niveaux_de_gris, puis luminosite) en Rust ou C, sur un tampon RGBA sur place, et compile-le en .wasm (wasm-pack / emcc).

2. La page + le Worker

Charge une image dans un canvas, envoie ses pixels à un Worker (transfert de tampon), applique le filtre côté Wasm, réaffiche avec putImageData.

3. Hors du web

Recompile le cœur pour wasm32-wasi, exécute-le avec wasmtime sur un fichier, puis en boucle sur un dossier. Vérifie que le résultat est identique.

Et après ?

Tu sais désormais assembler un projet Wasm complet, de bout en bout. Les pistes pour aller plus loin : SIMD Wasm (traiter plusieurs pixels par instruction), les threads Wasm (mémoire partagée entre plusieurs Workers pour paralléliser le filtre), et le modèle de composants (assembler des modules de langages différents). Mais le réflexe le plus utile reste le même : mesurer, isoler la portion lourde, comparer bout en bout.

Pour aller plus loin

Wasm n'est pas un remplaçant de JavaScript mais son meilleur complément pour le calcul. Approfondis Performance web pour mesurer juste, et Rust pour écrire des cœurs de calcul sûrs et rapides.

Glossaire

ImageData
L'objet du canvas qui contient les pixels bruts : un Uint8ClampedArray en RGBA (4 octets par pixel), plus la largeur et la hauteur.
RGBA
L'agencement des octets d'un pixel : rouge, vert, bleu, puis alpha (opacité). Un filtre les parcourt par paquets de quatre.
Mémoire linéaire
Le grand tableau d'octets partagé entre JS et Wasm où transitent les pixels pendant le filtrage.
wasm-bindgen
L'outil Rust qui génère la colle pour faire passer types riches (dont les tampons d'octets) entre JavaScript et Wasm sans écrire la plomberie à la main.
Web Worker
Un fil d'exécution séparé du thread principal : le calcul y tourne sans figer l'interface.
Transfert (Transferable)
Envoyer un tampon à un Worker en cédant sa propriété plutôt qu'en le copiant : rapide, mais le tampon d'origine devient inutilisable.
WASI
L'interface système qui laisse un .wasm lire des fichiers et s'exécuter hors du navigateur, dans un bac à sable par capacités.
Runtime Wasm
Un programme (wasmtime, wasmer…) qui exécute un module .wasm en dehors du navigateur.

Récap et vérification

  • Le projet relie tout le cours : cœur Wasm → Worker → canvas, et le même cœur hors du web via WASI.
  • JS orchestre (canvas, boutons, affichage) ; Wasm calcule ; le Worker garde l'interface fluide.
  • Les pixels transitent par la mémoire linéaire ; le tampon est transféré, pas copié.
  • Un cœur de calcul pur se réutilise partout : navigateur et ligne de commande.

  2. Par où passent les pixels entre JS et Wasm ?

Exercices

Exercice 1Échauffement

Remets dans l'ordre le trajet d'un clic sur « niveaux de gris » : (a) putImageData affiche le résultat ; (b) le Worker appelle niveaux_de_gris ; (c) getImageData lit les pixels du canvas ; (d) postMessage transfère le tampon au Worker.

Voir une solution

Ordre : (c) lire les pixels du canvas (getImageData), (d) les transférer au Worker (postMessage avec le tampon), (b) le Worker applique le filtre Wasm (niveaux_de_gris), puis le résultat revient et (a) s'affiche (putImageData). C'est l'aller-retour page → Worker → Wasm → page.

Exercice 2Application

Après worker.postMessage(image, [image.data.buffer]), tu tentes de relire image.data côté page pour l'afficher tout de suite : le tableau est vide. Pourquoi ? Comment obtenir l'image filtrée ?

Voir une solution

Parce que tu as transféré le tampon : sa propriété est passée au Worker, et le tableau d'origine côté page est désormais détaché (longueur 0). C'est le prix — et l'intérêt — du transfert : aucune copie, mais l'émetteur perd l'accès. Pour afficher l'image filtrée, il ne faut pas relire image.data tout de suite ; il faut attendre la réponse du Worker dans worker.onmessage, où l'on récupère le tampon (rempli par le filtre) et où l'on appelle putImageData(e.data, 0, 0). Si tu voulais vraiment garder une copie côté page, il faudrait copier les pixels avant l'envoi (mais on perdrait le zéro-copie).

Exercice 3Défi

Ton studio filtre bien dans le navigateur. Un collègue veut appliquer le même filtre à 500 photos sur un serveur, la nuit, sans navigateur. Que lui proposes-tu, en réutilisant ton travail ?

Voir une solution

Réutiliser le cœur de calcul tel quel — c'est tout l'intérêt d'avoir écrit niveaux_de_gris comme une fonction pure (sans DOM ni fetch). On la recompile pour wasm32-wasi avec un petit main() qui lit un fichier, applique le filtre, écrit la sortie. Sur le serveur, on l'exécute avec un runtime WASI (wasmtime) en boucle sur le dossier : for f in *.png; do wasmtime --dir=. filtre.wasm "$f"; done. Avantages : un seul code pour le web et le serveur (pas de version parallèle qui divergerait), le même bac à sable par capacités (le module ne voit que le dossier accordé par --dir), et une portabilité totale du binaire, indépendante de l'OS et du processeur du serveur.
