Types riches avec wasm-bindgen

~36 min Avancé Leçons 02 & 04 conseillées

À la fin de cette leçon, tu sauras

  • pourquoi Wasm seul ne sait échanger que des nombres ;
  • faire passer chaînes et structures avec #[wasm_bindgen] ;
  • exposer une struct Rust comme une classe JS ;
  • toucher au navigateur avec js-sys et web-sys.
Sommaire de la leçon

À la leçon 4, on a vu la vérité crue : la frontière JS ⇄ Wasm ne laisse passer que des nombres. Pour une chaîne ou un objet, il faut jongler avec la mémoire linéaire à la main. wasm-bindgen automatise entièrement ce travail : on annote son code Rust, et l'outil génère la « colle » qui traduit les types dans les deux sens.

Le problème : Wasm ne parle que nombres

Une fonction Wasm brute ne peut ni recevoir ni renvoyer une chaîne : seulement des i32, i64, f32, f64. Passer "Ana" exige de l'écrire octet par octet en mémoire, puis de transmettre un pointeur et une longueur. wasm-bindgen fait exactement cela — mais à ta place.

La colle a un coût — regroupe les échanges

Chaque chaîne encodée/décodée demande une copie d'octets. C'est indolore pour quelques appels, mais si tu traverses la frontière des milliers de fois, ce coût s'accumule. Le principe de la leçon 4 tient toujours : beaucoup de travail, peu d'appels.

Exposer une structure comme une classe

wasm-bindgen sait aussi exporter une struct et ses méthodes : côté JavaScript, elle apparaît comme une classe ordinaire, avec un constructeur et des méthodes.

L'objet vit côté Wasm

new Compteur() ne crée pas un objet JS classique : la donnée reste dans la mémoire Wasm. Côté JS, tu tiens un pointeur déguisé en classe. D'où une règle : quand tu n'en as plus besoin, appelle c.free() pour libérer la mémoire — JavaScript ne le fera pas tout seul pour toi.

js-sys et web-sys : toucher au navigateur

Depuis Rust, on veut parfois appeler la console, lire l'heure, ou manipuler le DOM. Deux bibliothèques compagnes exposent ces API :

  • js-sys — les objets JavaScript standards (Array, Date, Math, Promise…) ;
  • web-sys — les API du navigateur (window, document, console, fetch, WebGL…).

Manipuler le DOM depuis Wasm reste coûteux

web-sys permet de piloter le DOM depuis Rust, mais chaque appel franchit la frontière. Pour de nombreuses mises à jour d'interface, il est souvent plus rapide de calculer en Wasm et de laisser JavaScript peindre le DOM. Réserve web-sys aux besoins ponctuels.

Cas réel — la démo « game of life » de Rust et Wasm

Le livre officiel Rust and WebAssembly guide la construction du jeu de la vie de Conway : une struct Universe (la grille de cellules) vit côté Wasm, ses règles de calcul tournent en Rust, et wasm-bindgen l'expose comme une classe JS. À chaque image, JavaScript appelle universe.tick() puis lit la mémoire pour dessiner sur un <canvas>. C'est le patron canonique : l'état et le calcul en Wasm, le rendu en JS. Des applications réelles comme l'éditeur Figma ou le terminal web xterm.js + Wasm reposent sur la même répartition.

Récapituler wasm-bindgen

Glossaire

wasm-bindgen
Bibliothèque et outil Rust qui génère la « colle » traduisant automatiquement les types entre Rust/Wasm et JavaScript.
#[wasm_bindgen]
Annotation Rust posée sur une fonction, une struct ou un impl pour l'exposer au monde JavaScript.
Colle (glue code)
Le code JavaScript généré qui encode/décode chaînes et objets par la mémoire linéaire, et masque les pointeurs.
js-sys
Bibliothèque Rust donnant accès aux objets JavaScript standards (Array, Date, Math, Promise…).
web-sys
Bibliothèque Rust donnant accès aux API du navigateur (window, document, console, fetch…).
free()
Méthode à appeler côté JS pour libérer un objet Wasm dont la donnée vit dans la mémoire linéaire.
pkg/
Dossier produit par wasm-pack contenant le .wasm, la colle JS et les déclarations de types.

Récap et vérification

  • Wasm seul n'échange que des nombres ; wasm-bindgen fait passer chaînes, structs et objets.
  • On annote avec #[wasm_bindgen] ; l'outil génère la colle qui encode/décode par la mémoire.
  • Une struct exportée devient une classe JS (pense à free()).
  • js-sys et web-sys ouvrent l'accès au JS standard et au navigateur — avec parcimonie.

Exercices

Exercice 1Échauffement

Tu écris #[wasm_bindgen] pub fn crier(t: &str) -> String. Décris ce que reçoit et renvoie le code JavaScript qui l'appelle avec crier("oui").

Voir une solution

Côté JavaScript, on manipule des chaînes ordinaires : on passe la chaîne "oui" et on récupère une string en retour (par exemple "OUI" si la fonction met en majuscules). On n'a rien à gérer soi-même côté mémoire : wasm-bindgen encode "oui" en octets UTF-8 dans la mémoire linéaire, transmet à Rust un pointeur et une longueur, puis relit la chaîne renvoyée par Rust pour la restituer en string JS. Le programmeur voit du Rust idiomatique d'un côté, du JavaScript idiomatique de l'autre.

Exercice 2Application

Un collègue crée des milliers d'objets Compteur dans une boucle JS et se plaint que la mémoire du navigateur gonfle sans cesse. Quelle est vraisemblablement la cause, et le correctif ?

Voir une solution

La cause probable : il ne libère jamais les objets. Une struct exposée par wasm-bindgen vit dans la mémoire linéaire de Wasm ; le ramasse-miettes de JavaScript ne la connaît pas et ne peut pas la récupérer automatiquement. Chaque new Compteur() réserve donc de la mémoire Wasm qui n'est jamais rendue. Le correctif : appeler c.free() sur chaque instance dès qu'elle n'est plus utile (ou restructurer pour réutiliser un seul objet). Règle générale : tout objet Wasm obtenu depuis JS doit être explicitement libéré, faute de quoi on a une fuite de mémoire.

Exercice 3Défi

Tu portes en Wasm une fonction Rust qui, pour chaque pixel d'une image, appelle document.getElementById via web-sys afin de lire une couleur. Les performances sont catastrophiques. Explique pourquoi et propose une meilleure architecture.

Voir une solution

Le problème : un appel web-sys par pixel. Chaque accès au DOM depuis Wasm franchit la frontière JS ⇄ Wasm et déclenche une opération DOM (coûteuse par nature). Multiplié par des centaines de milliers de pixels, cela écrase tout : on paie le pont et le DOM à chaque itération. Meilleure architecture : JavaScript lit une seule fois les données de l'image (par ex. ctx.getImageData() renvoie un grand tableau d'octets), les place dans la mémoire linéaire, puis appelle une seule fonction Wasm qui parcourt tout le tableau à l'intérieur de Rust et écrit le résultat en mémoire. JavaScript relit ensuite le tampon et le repose sur le canvas en un appel (putImageData). On respecte le principe fondamental : traverser la frontière le moins possible, calculer en masse côté Wasm. web-sys est réservé aux interactions ponctuelles, jamais aux boucles serrées.
