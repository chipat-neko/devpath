Module 01 · Comprendre Wasm — Leçon 03

Charger & exécuter dans le navigateur

~32 min Intermédiaire Bases de JavaScript (async)

À la fin de cette leçon, tu sauras

  • charger un module avec fetch + instantiateStreaming ;
  • appeler une fonction via instance.exports ;
  • gérer le cas où instantiateStreaming n'est pas disponible ;
  • expliquer pourquoi il faut un serveur local (pas file://).
Sommaire de la leçon

Le binaire est compilé ; reste à le faire vivre dans la page. Côté JavaScript, l'objet global WebAssembly fournit tout le nécessaire pour charger, instancier et appeler un module. Voyons le chemin complet, du téléchargement au résultat affiché.

Les trois étapes

Faire tourner un module suit toujours la même logique :

La voie rapide : instantiateStreaming

La méthode recommandée est WebAssembly.instantiateStreaming : elle compile pendant le téléchargement, sans attendre la fin. Elle prend la réponse d'un fetch et renvoie le module et l'instance.

Piège fréquent

Un jour tu écriras const instance = await WebAssembly.instantiateStreaming(fetch(url)), puis instance.exports.additionner(20, 22) — et tu récolteras une erreur, car exports n'existe pas sur cet objet. instantiateStreaming ne résout pas une instance : elle résout la paire { module, instance }. Pense à déstructurer : const { instance } = await …. Même oubli possible avec WebAssembly.instantiate(octets), qui renvoie la même paire.

module vs instance

Le module est le code compilé (réutilisable) ; l'instance est une copie vivante avec sa propre mémoire. On appelle les fonctions sur l'instance, via instance.exports.

Une solution de repli

instantiateStreaming exige que le serveur renvoie le bon type MIME (application/wasm). Si ce n'est pas le cas, on bascule sur arrayBuffer() + WebAssembly.instantiate, un peu plus lent mais robuste :

Cas réel — le bon type MIME en production

En local tout marchait ; en ligne, la console affiche « Incorrect response MIME type ». La cause : l'hébergeur servait le .wasm en application/octet-stream au lieu de application/wasm, et instantiateStreaming refuse alors de compiler en flux. Deux corrections classiques : régler le serveur pour renvoyer le bon type (une ligne de config Nginx/Apache), ou conserver le repli arrayBuffer() qui ignore le type MIME. Beaucoup d'équipes gardent les deux : réglage serveur et filet de repli.

Donner des fonctions au module : les imports

Un module peut aussi demander des fonctions à l'extérieur (par exemple pour écrire dans la console). On les fournit via un objet d'imports, au moment de l'instanciation :

Imports et exports sont les deux sens du dialogue : le module exporte ce qu'il offre, et importe ce dont il a besoin. On approfondira cet échange au module suivant.

Pourquoi un serveur local ?

Charger un .wasm passe par fetch, soumis à la politique d'origine du navigateur. En ouvrant une page en file:// (double-clic sur le fichier), fetch est souvent bloqué. Il faut donc servir la page via un petit serveur local.

Le piège du double-clic

« Ça ne marche pas » vient très souvent de l'ouverture en file://. Sers toujours ton projet Wasm via http://localhost (Live Server, python -m http.server…). C'est la cause n°1 des erreurs de chargement.

Gérer les erreurs

Le chargement est asynchrone et peut échouer (fichier absent, mauvais MIME, binaire invalide). Enveloppe l'appel dans un try/catch et affiche un message clair plutôt que de laisser la page muette.

Glossaire

fetch
Fonction du navigateur qui télécharge une ressource (ici le fichier .wasm) de façon asynchrone.
instantiateStreaming
Méthode qui compile le module pendant son téléchargement ; la plus efficace, exige le bon type MIME.
Module
Le code Wasm compilé, réutilisable, indépendant de toute exécution.
Instance
Copie vivante d'un module, avec sa propre mémoire ; c'est sur elle qu'on appelle les fonctions.
exports
Les fonctions (et la mémoire) que le module met à disposition, accessibles via instance.exports.
imports
Les fonctions extérieures fournies au module au moment de l'instanciation (ex. journaliser).
Type MIME
Étiquette du type d'un fichier ; un .wasm doit être servi en application/wasm.
Politique d'origine
Règle de sécurité du navigateur qui, en file://, bloque souvent fetch ; d'où le serveur local.

Récap et vérification

  • Trois étapes : télécharger (fetch), instancier, appeler.
  • instantiateStreaming compile pendant le téléchargement ; repli via arrayBuffer().
  • On appelle les fonctions sur instance.exports ; on fournit des imports si besoin.
  • Il faut un serveur local (http://localhost), pas file://.

Exercices

Exercice 1Échauffement

Remets ces étapes dans l'ordre : (a) appeler instance.exports.calcul() ; (b) fetch("calc.wasm") ; (c) instancier avec instantiateStreaming.

Voir une solution

Ordre : (b) télécharger avec fetch, (c) instancier le module avec instantiateStreaming, puis (a) appeler la fonction via instance.exports. C'est la séquence télécharger → instancier → appeler.

Exercice 2Application

Un développeur double-clique sur son index.html pour tester son module Wasm. La console affiche une erreur au chargement. Quelle est la cause la plus probable, et comment corriger ?

Voir une solution

La page est ouverte en file:// : le fetch du .wasm est bloqué par la politique d'origine du navigateur. C'est la cause n°1 des erreurs de chargement Wasm. Correction : servir le dossier via un serveur local — par exemple l'extension Live Server de VS Code, ou python -m http.server 8000 puis ouvrir http://localhost:8000. Une fois servi en HTTP, le fetch est autorisé et le module se charge.

Exercice 3Défi

Pourquoi prévoir un repli avec arrayBuffer() + WebAssembly.instantiate alors que instantiateStreaming est plus efficace ? Dans quel cas le repli sauve la mise ?

Voir une solution

instantiateStreaming exige que le serveur renvoie l'en-tête Content-Type: application/wasm. Or certains serveurs (statiques, mal configurés, ou un environnement de test) servent le .wasm avec un type MIME générique : instantiateStreaming échoue alors. Le repli télécharge tout le binaire en arrayBuffer() puis appelle WebAssembly.instantiate sur ces octets, sans dépendre du type MIME : il fonctionne même quand le serveur est mal configuré. C'est un peu plus lent (pas de compilation en flux), mais c'est un filet de sécurité : on tente d'abord la voie rapide, et on retombe sur le repli dans un catch. Idéal pour un code robuste qui doit marcher dans des environnements variés.
