Module 02 · Interopérer — Leçon 05

Cas d'usage & limites

~29 min Intermédiaire Leçon 04 conseillée

À la fin de cette leçon, tu sauras

  • citer les bons cas d'usage de Wasm ;
  • reconnaître les situations où il n'apporte rien ;
  • nommer ses limites concrètes ;
  • appliquer la démarche « mesurer d'abord ».
Sommaire de la leçon

WebAssembly est un outil puissant — à condition de le sortir au bon moment. Cette leçon dresse la carte : là où Wasm brille, là où il ne sert à rien, et la méthode pour décider sans se tromper.

Là où Wasm brille

Le point commun de ses bons cas d'usage : un calcul intensif et régulier, qui dure assez pour amortir le coût de chargement et d'échange.

  • Jeux et moteurs physiques/3D.
  • Traitement d'image, son, vidéo (filtres, encodage, décodage).
  • Calcul scientifique, simulation, statistiques lourdes.
  • Cryptographie et compression.
  • Portage d'applications C/C++ existantes (CAO, émulateurs, moteurs).

Cas réel — Figma dans le navigateur

L'éditeur de design Figma tourne dans un simple onglet, avec la fluidité d'un logiciel de bureau. Son moteur de rendu (le canevas, des milliers de vecteurs, le zoom instantané) est écrit en C++ compilé en WebAssembly ; l'interface autour (panneaux, menus, calques) reste en JavaScript. C'est l'archétype du bon usage : le calcul graphique lourd confié à Wasm, l'interface confiée à JS.

Là où Wasm n'apporte rien

Pour l'essentiel d'un site web, JavaScript reste le bon outil. Wasm n'aide pas à :

  • manipuler le DOM (afficher, modifier la page) ;
  • gérer des formulaires, des clics, la navigation ;
  • faire des appels réseau à une API ;
  • de la logique légère sans calcul lourd.

« Réécrire tout en Wasm » est une erreur

Sur ces tâches, Wasm n'apporte aucun gain et ajoute de la complexité (outillage, débogage, coût d'échange). Le DOM passe de toute façon par JavaScript : Wasm ne le contourne pas.

Les limites à connaître

  • Pas d'accès direct au DOM : tout passe par JS.
  • Coût d'échange JS ⇄ Wasm : pénalisant pour de nombreux petits appels.
  • Taille du binaire à télécharger : à surveiller, surtout sur mobile.
  • Outillage et débogage moins immédiats que du JavaScript.
  • Temps d'instanciation initial avant le premier appel.

La démarche : mesurer d'abord

La pire raison d'adopter Wasm, c'est « pour aller plus vite » par principe. La bonne démarche est empirique :

  1. Mesurer les performances réelles en JavaScript (avec les outils du navigateur).
  2. Identifier le vrai goulot d'étranglement — souvent ce n'est pas le calcul.
  3. Porter en Wasm uniquement cette portion lourde.
  4. Comparer bout en bout (chargement compris) avant de conclure.

Souvent, JavaScript suffit

Les moteurs JS modernes sont très rapides. Avant de sortir l'artillerie Wasm, vérifie qu'un meilleur algorithme, un Web Worker ou une simple optimisation ne règle pas déjà le problème.

Wasm et les Web Workers

Un calcul Wasm long bloque quand même le fil principal s'il s'exécute dessus. Pour garder l'interface fluide, on combine souvent Wasm avec un Web Worker : le calcul tourne à côté, et la page reste réactive. Les deux techniques se complètent très bien.

Glossaire

Goulot d'étranglement
La portion de code qui limite la performance de l'ensemble ; c'est elle, et elle seule, qu'on cherche à accélérer.
Profiler (profilage)
Mesurer, avec les outils du navigateur, où le temps est réellement passé, au lieu de le deviner.
Fil principal
Le fil d'exécution unique qui gère l'affichage et les interactions ; un long calcul dessus fige la page.
Web Worker
Fil d'exécution séparé, lancé par JavaScript, où l'on peut faire tourner un calcul (Wasm compris) sans bloquer l'interface.
Coût d'échange (frontière)
Le temps perdu à faire passer des données entre JS et Wasm ; il peut annuler le gain si les appels sont nombreux et petits.
Instanciation
La mise en route d'un module Wasm avant son premier appel ; un coût fixe à amortir.
Coût fixe
Dépense indépendante de la taille du calcul (téléchargement + instanciation) ; sur un petit calcul, elle domine et Wasm perd.
Mesurer d'abord
La démarche empirique : mesurer, isoler le goulot, porter la partie lourde, comparer bout en bout — jamais adopter Wasm « par principe ».

Récap et vérification

  • Bons cas : jeux, image/son/vidéo, calcul scientifique, crypto, portage — du calcul lourd.
  • Inutile pour : DOM, formulaires, réseau, logique légère (JS reste roi).
  • Limites : pas de DOM direct, coût d'échange, taille, outillage, instanciation.
  • Démarche : mesurer, identifier le goulot, porter la partie lourde, comparer.

Vérifie ta compréhension

  1. Pourquoi Wasm n'accélère-t-il pas un petit calcul ponctuel ?
  2. Cite deux limites concrètes de Wasm.
  3. Quelle est la première étape avant de décider de passer en Wasm ?

Exercices

Exercice 1Échauffement

Pour chaque besoin, dis si WebAssembly est pertinent : (a) un éditeur de photos en ligne avec filtres ; (b) un formulaire de contact ; (c) un émulateur de console rétro ; (d) afficher une liste d'articles depuis une API.

Voir une solution

Pertinent : (a) l'éditeur de photos (filtres = calcul d'image lourd) et (c) l'émulateur rétro (portage de code C/C++, calcul intensif). Non pertinent : (b) le formulaire de contact (DOM + réseau, aucun calcul lourd) et (d) l'affichage d'une liste depuis une API (réseau + DOM). Pour (b) et (d), JavaScript est le bon outil et Wasm n'apporterait rien.

Exercice 2Application

Ton application a une page qui « rame ». Un collègue propose de la passer en WebAssembly. Quelle démarche suis-tu avant d'accepter ?

Voir une solution

D'abord mesurer, pas réécrire. 1) Profiler la page avec les outils du navigateur pour trouver ce qui est lent. 2) Souvent, le goulot n'est pas le calcul mais le rendu, le réseau, trop de re-rendus, ou un algorithme inefficace — autant de choses que Wasm n'améliore pas. 3) Si, et seulement si, le coupable est une portion de calcul lourd, envisager de la porter en Wasm. 4) Avant d'adopter, comparer JS vs Wasm bout en bout (chargement et échange compris). Souvent, corriger l'algorithme ou déplacer le travail dans un Web Worker suffit, sans la complexité de Wasm.

Exercice 3Défi

Un calcul lourd en Wasm rend bien le bon résultat, mais l'interface se fige pendant son exécution. Pourquoi, et comment garder la page fluide ?

Voir une solution

WebAssembly est rapide, mais s'il s'exécute sur le fil principal (le même qui gère l'affichage et les clics), un calcul long bloque ce fil : la page se fige le temps du calcul, exactement comme le ferait un long calcul JavaScript. La rapidité de Wasm réduit la durée du gel, mais ne l'élimine pas pour les tâches vraiment lourdes. Solution : déplacer le calcul dans un Web Worker — un fil d'exécution séparé. Le module Wasm tourne à côté, le fil principal reste libre de répondre à l'utilisateur, et on récupère le résultat par message quand c'est fini. Wasm et Web Workers se complètent : l'un accélère le calcul, l'autre l'empêche de bloquer l'interface.
