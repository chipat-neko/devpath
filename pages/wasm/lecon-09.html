Calculer sans bloquer : Web Worker

~35 min Avancé Leçons 04 & 06 conseillées

À la fin de cette leçon, tu sauras

  • pourquoi un calcul lourd sur le fil principal gèle l'interface ;
  • déplacer un module Wasm dans un Web Worker ;
  • dialoguer avec lui par messages ;
  • transférer la mémoire au lieu de la copier, et entrevoir les threads.
Sommaire de la leçon

Wasm accélère le calcul, mais il ne change pas une règle d'or du navigateur : un seul fil principal anime la page. Si ton module Wasm y tourne pendant deux secondes, l'interface se fige tout ce temps — plus de clic, plus de défilement, plus d'animation. La solution : exécuter le calcul dans un Web Worker, un fil d'exécution séparé.

Le fil principal ne doit jamais geler

Le fil principal traite tout : les clics, le rendu, les animations. Un calcul long qui s'y installe bloque cette file d'attente : la page devient une image morte. Un worker tourne en parallèle ; pendant qu'il calcule, le fil principal reste libre de répondre.

Un worker n'accélère pas le calcul

Le worker ne rend pas Wasm plus rapide : il le déplace ailleurs, pour que l'interface ne subisse pas. C'est un gain de réactivité, pas de vitesse brute. Les deux atouts se cumulent : Wasm pour la vitesse, le worker pour la fluidité.

Déplacer le module dans un worker

Un worker est un fichier JavaScript séparé. Il charge lui-même le .wasm et attend des messages. Le fil principal se contente de lui envoyer du travail et d'écouter la réponse.

Un worker n'a pas accès au DOM

Dans un worker, document et window n'existent pas : on ne peut pas toucher à la page. Le worker calcule et renvoie ses résultats ; c'est le fil principal, à la réception du message, qui met à jour l'interface. Cette séparation est voulue.

Le dialogue par messages

Fil principal et worker ne partagent pas leurs variables : ils communiquent par messages. On envoie avec postMessage(...), on reçoit dans onmessage. Chaque côté a sa propre mémoire ; le message est copié lors du passage.

Transférer plutôt que copier

Copier un gros tableau (une image de plusieurs mégaoctets) à chaque message coûte cher. Pour l'éviter, on peut transférer la propriété d'un ArrayBuffer : au lieu de le dupliquer, on le déplace. Après transfert, l'expéditeur ne l'a plus — d'où l'appellation « transférable ».

Transfert = déplacement, pas partage

Après un transfert, un seul côté détient le tampon à la fois — on se le passe, on ne le partage pas. Pour un vrai partage simultané, il faut un SharedArrayBuffer (voir ci-dessous), avec ses conditions de sécurité.

Un aperçu des threads

Pour du calcul parallèle à l'intérieur même de Wasm (plusieurs cœurs sur la même donnée), on utilise un SharedArrayBuffer partagé entre plusieurs workers. C'est puissant mais exigeant : le navigateur ne l'autorise que si la page est « isolée » via deux en-têtes HTTP :

Cas réel — Squoosh et Figma gardent la main

Squoosh (compression d'images) exécute ses codecs Wasm dans un worker : tu déplaces un curseur de qualité et l'interface reste parfaitement fluide pendant que l'image se ré-encode à côté. Figma, dont le cœur de rendu est en C++ compilé en Wasm, s'appuie massivement sur workers et threads pour manipuler d'immenses documents sans jamais figer le pointeur. Le point commun : le calcul lourd est toujours hors du fil principal, qui reste dédié à l'interaction. C'est la combinaison gagnante : Wasm pour la vitesse, worker pour la fluidité.

Récapituler

Glossaire

Fil principal (main thread)
Le fil unique qui gère l'interface, le rendu et les événements ; le bloquer fige la page.
Web Worker
Fil d'exécution séparé, lancé depuis un fichier JS, qui tourne en parallèle sans accès au DOM.
postMessage
Méthode d'envoi d'un message d'un fil à l'autre ; la donnée est copiée (ou transférée) au passage.
onmessage
Gestionnaire déclenché à la réception d'un message ; on y lit e.data.
Transférable (transferable)
Objet, comme un ArrayBuffer, dont on peut déplacer la propriété au lieu de le copier.
Détaché (neutralisé)
État d'un ArrayBuffer après un transfert : il a changé de propriétaire et devient inutilisable côté expéditeur (longueur ramenée à 0).
SharedArrayBuffer
Tampon mémoire réellement partagé entre plusieurs fils, base des threads Wasm ; requiert une page isolée.
COOP / COEP
En-têtes HTTP (Cross-Origin-Opener/Embedder-Policy) qui isolent la page et débloquent SharedArrayBuffer.

Récap et vérification

  • Un calcul lourd sur le fil principal fige l'interface ; un worker le déporte à côté.
  • Le worker charge le .wasm et dialogue par postMessage/onmessage.
  • Il n'a pas accès au DOM : il calcule, le fil principal affiche.
  • On transfère les gros tampons ; le vrai partage passe par SharedArrayBuffer (page isolée).

  1. Pourquoi un gros calcul Wasm peut-il figer la page ?
  2. Comment le fil principal et le worker échangent-ils ?
  3. Quelle différence entre transférer et partager un tampon ?

Exercices

Exercice 1Échauffement

Une page appelle directement instance.exports.traiter(image) sur le fil principal ; le traitement dure 3 secondes et, pendant ce temps, le bouton « Annuler » ne répond pas. Explique et propose le principe du correctif.

Voir une solution

Le calcul de 3 secondes s'exécute sur le fil principal : tant qu'il tourne, ce fil ne peut ni traiter le clic sur « Annuler », ni redessiner — l'interface est figée. Le correctif : déplacer traiter dans un Web Worker. Le fil principal envoie l'image au worker via postMessage, affiche un indicateur d'attente, et reste libre de réagir (y compris au bouton « Annuler »). Quand le worker a fini, il renvoie le résultat par message, et le fil principal met à jour l'affichage. L'interface ne gèle plus.

Exercice 2Application

Dans ton worker, tu recharges le .wasm avec instantiateStreaming à chaque message reçu. Pourquoi est-ce un problème, et comment corriger ?

Voir une solution

Recharger et réinstancier le module à chaque message est un gaspillage : on paie le téléchargement (ou au moins la compilation/instanciation) à répétition, alors que le module ne change pas. Cela ajoute une latence inutile à chaque appel et sollicite le réseau et le CPU pour rien. Correctif : charger le module une seule fois et mémoriser l'instance (par exemple dans une variable du worker, ou via une promesse mise en cache comme la fonction pret() de la leçon). Les messages suivants réutilisent l'instance déjà prête et se contentent d'appeler instance.exports.…. On amortit ainsi le coût de chargement, exactement comme on l'a vu au capstone (leçon 6) : charger une fois, appeler souvent.

Exercice 3Défi

Tu envoies une image de 30 Mo au worker à chaque image d'une vidéo, et l'application rame malgré le worker. Le calcul lui-même est rapide. Où passe le temps, et comment l'éliminer ?

Voir une solution

Le temps ne part pas dans le calcul mais dans la copie du message. Par défaut, postMessage duplique la donnée transmise : copier 30 Mo à chaque image, dans les deux sens, sature la mémoire et le CPU. Solution : utiliser un transférable. On passe le ArrayBuffer sous-jacent dans la liste de transfert : worker.postMessage({ buf }, [buf]). La propriété du tampon est alors déplacée (pas copiée) — coût quasi nul, quelle que soit la taille. Attention : après transfert, le tampon est neutralisé côté expéditeur ; le worker le renvoie de la même façon quand il a fini. Pour un flux vidéo continu où les deux côtés lisent en même temps, on envisagerait plutôt un SharedArrayBuffer (avec en-têtes COOP/COEP), mais le transférable suffit et évite déjà tout le coût de copie.
