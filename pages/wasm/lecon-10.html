Hors du navigateur : WASI & runtimes

~33 min Intermédiaire Leçons 01 & 05 conseillées

À la fin de cette leçon, tu sauras

  • que le même .wasm tourne aussi hors du web ;
  • ce qu'apporte WASI et son bac à sable par capacités ;
  • exécuter un module avec un runtime (wasmtime, wasmer…) ;
  • situer le modèle de composants et l'écosystème des plugins.
Sommaire de la leçon

On a toujours parlé de Wasm dans le navigateur. Mais le format a été conçu pour être portable et isolé — deux qualités précieuses partout : sur un serveur, en périphérie de réseau, comme greffon d'une application. Reste un manque : hors du web, un module n'a ni fetch, ni console, ni accès aux fichiers. WASI comble ce vide.

Le même module, partout

Un .wasm est un binaire indépendant du système d'exploitation et du processeur. Le même fichier peut donc s'exécuter dans des contextes très différents, pourvu qu'un runtime sache le lire.

WASI : une interface système portable

Dans le navigateur, l'accès au monde extérieur passe par les API du web. Hors du web, il faut un équivalent standard pour lire un fichier, lire l'heure, écrire sur la sortie, tirer un nombre aléatoire. C'est le rôle de WASI (WebAssembly System Interface) : une interface système portable, la même quel que soit l'OS sous-jacent.

Sa particularité : la sécurité par capacités. Un module ne peut toucher que ce que l'hôte lui a explicitement accordé. Pas de dossier autorisé ? Il ne voit aucun fichier. C'est l'opposé d'un programme natif classique, qui hérite de tous tes droits.

Isolé par défaut, utile par autorisation

Ce modèle rend Wasm idéal pour exécuter du code tiers sans lui confier la machine : un plugin ne peut lire tes fichiers, ouvrir une socket ou espionner l'environnement que si tu le lui permets, dossier par dossier, droit par droit.

Un seul artefact pour toutes les plateformes

Pas besoin de recompiler par système : le même outil.wasm tourne sous Linux, macOS et Windows, du moment qu'un runtime y est installé. C'est la promesse « compiler une fois » que les binaires natifs n'ont jamais vraiment tenue.

Le modèle de composants (aperçu)

La suite de WASI (souvent appelée WASI 0.2) introduit le modèle de composants : des modules qui décrivent leurs interfaces dans un langage neutre, le WIT (Wasm Interface Types). Deux composants écrits dans des langages différents (Rust, Go, Python…) peuvent alors s'assembler et échanger des types riches sans colle sur mesure.

Un domaine qui bouge vite

WASI et le modèle de composants évoluent : les cibles (wasm32-wasip1, wasm32-wasip2) et les API changent d'une version à l'autre. Vérifie la version visée par ton runtime et fige-la dans ton projet : un module compilé pour une preview peut ne pas tourner sur une autre.

Cas réel — Wasm comme format universel de plugin

Hors du web, Wasm s'impose surtout comme format de greffon. Le proxy Envoy charge des filtres proxy-wasm pour traiter le trafic ; Shopify Functions exécute la logique métier des marchands en Wasm, isolée et rapide ; Fastly Compute@Edge fait tourner du code client en périphérie via wasmtime ; Docker peut lancer des conteneurs Wasm en plus des conteneurs Linux ; et des bases comme SingleStore ou des outils comme Envoy ou Zellij acceptent des extensions Wasm. Le fil rouge : on veut du code tiers rapide, portable et sûr — exactement ce que WASI garantit par son bac à sable.

Récapituler

Glossaire

WASI
WebAssembly System Interface : interface standard et portable donnant à un module l'accès système hors du navigateur.
Runtime Wasm
Programme (wasmtime, wasmer, WasmEdge…) qui lit un .wasm, fournit WASI et l'exécute hors du web.
Capacité (capability)
Droit accordé explicitement par l'hôte : sans elle, le module ne peut ni lire un fichier, ni ouvrir le réseau.
Moindre privilège
Principe de sécurité consistant à n'accorder que le strict nécessaire ; WASI l'applique en refusant par défaut tout accès non explicitement ouvert.
Bac à sable (sandbox)
Isolation qui empêche le module d'atteindre le système ; Wasm y ajoute le moindre privilège par capacités.
wasm32-wasip1
Cible de compilation « Wasm + WASI » (preview 1) ; wasip2 correspond au modèle de composants.
Modèle de composants
Évolution de WASI où des modules décrivent leurs interfaces (WIT) et s'assemblent entre langages.
WIT (Wasm Interface Types)
Langage neutre pour décrire les interfaces d'un composant, indépendamment du langage source.

Récap et vérification

  • Le même .wasm tourne hors du navigateur ; un runtime l'exécute.
  • WASI fournit l'accès système, avec une sécurité par capacités (refus par défaut).
  • On compile pour wasm32-wasip1/2 et on lance avec wasmtime, wasmer…
  • Le modèle de composants (WIT) vise l'assemblage entre langages ; usage phare : les plugins.

Exercices

Exercice 1Échauffement

Tu lances wasmtime outil.wasm et le programme échoue en essayant de lire ./data/entree.txt. Que se passe-t-il, et comment corriger ?

Voir une solution

Par défaut, le runtime n'accorde aucun accès au disque : le module est isolé, il ne « voit » aucun dossier. La lecture de ./data/entree.txt est donc refusée — c'est le bac à sable par capacités qui joue son rôle. Correctif : accorder explicitement le dossier, par exemple wasmtime --dir=. outil.wasm (ou --dir=./data). Le module obtient alors le droit de lire ce dossier précis, et rien d'autre. Ce n'est pas un bug mais une sécurité voulue : on ouvre le minimum nécessaire.

Exercice 2Application

Une plateforme veut laisser ses clients téléverser du code pour l'exécuter sur ses serveurs. Pourquoi Wasm + WASI est-il un choix pertinent, comparé à lancer directement un binaire natif ?

Voir une solution

Exécuter du code tiers non fiable est dangereux : un binaire natif hérite des droits du processus (fichiers, réseau, autres données des clients…). Wasm + WASI apporte trois garanties clés : (1) Isolation par capacités — le code client ne touche que ce que la plateforme accorde, dossier par dossier ; il ne peut pas s'échapper vers le reste du serveur. (2) Portabilité — un seul artefact .wasm tourne sur toute l'infrastructure, sans recompiler par machine. (3) Démarrage rapide et léger — un module s'instancie en millisecondes, bien plus vite qu'une VM, ce qui permet d'en lancer beaucoup à la demande. C'est précisément ce qui fait le succès de Wasm pour les Functions et le edge computing (Shopify, Fastly…).

Exercice 3Défi

Un collègue dit : « Wasm hors du navigateur, c'est juste comme Docker. » Nuance cette affirmation en donnant deux différences.

Voir une solution

Il y a un air de famille (portabilité, isolation), mais ce sont des outils de niveaux différents. (1) Granularité et poids : un conteneur Docker embarque tout un système de fichiers et souvent un mini-OS ; un module Wasm est un simple binaire de quelques kilo/mégaoctets, sans OS, qui démarre en millisecondes — bien plus léger et rapide à instancier. (2) Modèle de sécurité : Docker isole au niveau du processus Linux (espaces de noms, cgroups) et donne par défaut un accès assez large ; Wasm/WASI isole au niveau du module, avec un modèle par capacités où tout est refusé sauf autorisation explicite. (3) Portabilité du même artefact : une image Docker cible une architecture/OS donnés ; le même .wasm tourne partout où il y a un runtime. En pratique, les deux se combinent : Docker peut même exécuter des conteneurs Wasm. Wasm n'est donc pas « un autre Docker », mais une brique plus fine, souvent complémentaire.
