Scripts de production et outils modernes

~35 min Intermédiaire Leçon 10 recommandée

À la fin de cette leçon, tu sauras

  • savoir poser un squelette robuste avec set -euo pipefail, usage() et getopts ;
  • savoir gérer les fichiers temporaires en sécurité avec mktemp et un trap … EXIT ;
  • savoir parser du JSON avec jq et explorer un système de fichiers avec find avancé ;
  • savoir vérifier la qualité avec ShellCheck et reconnaître quand passer à Python.
Sommaire de la leçon

Tu sais écrire des scripts qui marchent sur ta machine. Mais un script de production tourne sans surveillance, sur des serveurs que tu ne vois pas, avec des données que tu n'as pas choisies. Il doit échouer proprement, ne rien laisser traîner, et hurler quand quelque chose cloche. La différence entre un script jetable et un script robuste tient dans quelques réflexes que cette leçon va te donner.

On part du principe que tu maîtrises déjà les variables, le quoting, les conditions et les fonctions. Ici, on assemble tout ça en outils fiables, et on ajoute les armes modernes du sysadmin : jq, find avancé et ShellCheck.

Le squelette robuste

Tout script sérieux commence par les mêmes lignes. Elles transforment Bash, laxiste par défaut, en interpréteur strict qui refuse de continuer dans le brouillard.

#!/usr/bin/env bash trouve bash via le PATH au lieu de le coder en dur : plus portable que #!/bin/bash. Le trio set -euo pipefail est ta ceinture de sécurité : sans lui, un script continue allègrement après une erreur et peut faire des dégâts.

Note

Avec -u, pour donner une valeur par défaut sans planter, utilise l'expansion ${VAR:-valeur}. Par exemple ${1:-} évite l'erreur si l'argument n'existe pas. Sache aussi que IFS=$'\n\t' est un choix volontairement strict : il fait itérer une boucle for ligne par ligne plutôt que mot par mot. Pratique pour les chemins, mais à connaître si une boucle ne se découpe pas comme tu l'attendais.

Cas réel

En 2015, un bug célèbre du client Steam sous Linux a effacé les fichiers personnels d'utilisateurs. Le script contenait rm -rf "$STEAMROOT/"* ; dans certains cas la variable STEAMROOT était vide, si bien que la commande devenait rm -rf /* — la suppression de tout ce à quoi l'utilisateur avait accès. Deux réflexes de cette leçon désamorcent le drame : set -u aurait fait échouer le script sur la variable non définie, et une garde [ -n "$STEAMROOT" ] || exit 1 avant tout rm aurait refusé d'agir sur un chemin vide. En scripting, une variable vide n'est jamais anodine.

Options et aide : usage() et getopts

Un outil de production se pilote par options, pas par positions devinées. getopts (intégré à Bash) lit les options courtes proprement, et usage() documente l'usage en cas d'erreur ou de -h.

La chaîne ":vo:h" se lit ainsi : le : initial active le mode silencieux (tu gères les erreurs toi-même), v et h sont des drapeaux, et o: attend un argument récupéré dans $OPTARG. Le shift $((OPTIND - 1)) est indispensable : il fait disparaître les options pour que $1 pointe enfin sur l'argument positionnel.

Fichiers temporaires sûrs

N'écris jamais dans /tmp/monfichier : deux exécutions simultanées se marcheraient dessus, et un nom prévisible est une faille de sécurité. mktemp crée un nom unique, et un trap … EXIT garantit le nettoyage, même si le script plante.

Le trap s'arme une seule fois et se déclenche sur le signal EXIT, qui couvre toutes les façons de quitter. C'est le réflexe le plus rentable de toute la leçon : zéro déchet sur le disque.

Astuce

Tu peux trapper plusieurs signaux à la fois : trap 'rm -rf "$tmp"' EXIT INT TERM. Mais EXIT suffit presque toujours, car INT (Ctrl-C) et TERM mènent eux aussi à une sortie, donc déclenchent déjà le piège EXIT.

Journalisation propre

Sur un serveur, ta seule fenêtre sur l'exécution, ce sont les logs. Les messages d'information et d'erreur doivent partir sur la sortie d'erreur (>&2), pour ne pas polluer la vraie sortie de données que d'autres commandes pourraient lire dans un pipe.

Avantage concret : ./log.sh > donnees.txt envoie les vraies données dans le fichier, et tu vois quand même les logs défiler à l'écran. Note aussi le if ! autour du cp : sous set -e, c'est ainsi qu'on teste une commande qui a le droit d'échouer sans interrompre le script. Séparer les flux, c'est la base d'un script composable.

Manipuler du JSON avec jq

Les API parlent JSON. curl le télécharge, et jq le découpe avec un vrai langage de requête. Parser du JSON à coups de grep/sed est fragile : un saut de ligne ou un champ réordonné, et tout casse.

Le -s de curl coupe la barre de progression ; jq lit le JSON sur son entrée standard.

Pour parcourir un tableau, .[] itère sur chaque élément. L'option -r (raw) retire les guillemets, parfait pour réinjecter le résultat dans une boucle Bash.

find avancé

Tu connais find pour lister. En production, on l'enchaîne avec des actions efficaces. La règle d'or : -exec … {} + regroupe les fichiers en un minimum d'appels, là où -exec … {} \; lance un processus par fichier (lent sur des milliers de fichiers).

Le duo -print0 / xargs -0 sépare les noms par un octet nul plutôt que par un retour à la ligne : c'est la seule façon fiable de traiter des fichiers dont le nom contient des espaces ou des caractères exotiques. -newer FICHIER filtre par date de modification, idéal pour des traitements incrémentaux.

Portabilité et qualité : ShellCheck

ShellCheck est le linter de référence pour les scripts shell. Il attrape les bugs avant l'exécution : variables non quotées, comparaisons fausses, pièges de quoting. Lance-le sur chaque script, sans exception.

Attention au shebang. #!/bin/sh n'est pas Bash : c'est un shell POSIX minimal. Les « bashismes » comme [[ … ]], les tableaux arr=(a b c) ou $'\n' n'y existent pas. Si tu utilises ces fonctionnalités, mets #!/usr/bin/env bash ; sinon, reste en POSIX strict. ShellCheck adapte ses avertissements au shebang déclaré.

Quand passer à un vrai langage

Bash brille pour coller des commandes, déplacer des fichiers, enchaîner des outils. Mais dès que tu manipules des structures de données complexes, de l'arithmétique flottante, du JSON imbriqué profond ou plus de ~100 lignes de logique, Python devient plus lisible et plus testable. Pièges fréquents

Piège fréquent

Oublier set -euo pipefail. Sans lui, cd /dossier/inexistant; rm -rf * exécute quand même le rm dans le mauvais répertoire après l'échec du cd (le ; enchaîne sans condition). Avec set -e, le script s'arrête net dès que le cd échoue : le scénario catastrophe est désamorcé.

Piège fréquent

Parser du JSON avec grep/sed, utiliser -exec … \; au lieu de + sur des milliers de fichiers, glisser des bashismes dans un script #!/bin/sh, ou ne jamais lancer ShellCheck. Chacun marche « chez toi » et casse en production.

Glossaire

Shebang
La 1re ligne #!/usr/bin/env bash : désigne l'interpréteur qui exécute le script.
set -euo pipefail
Mode strict : arrêt sur erreur (-e), variable non définie interdite (-u), échec propagé dans un pipe (pipefail).
getopts / OPTARG
Analyseur d'options courtes intégré ; l'argument d'une option (ex. -o fichier) atterrit dans OPTARG.
mktemp
Crée un fichier ou un dossier (-d) au nom unique et imprévisible : pas de collision, pas de faille.
trap … EXIT
Planifie un nettoyage déclenché à toute sortie du script : normale, erreur ou signal.
jq
Processeur JSON en ligne de commande ; -r (raw) retire les guillemets pour réinjecter dans Bash.
ShellCheck
Linter des scripts shell : repère guillemets manquants, comparaisons fausses et bashismes avant l'exécution.
stdout / stderr
Sortie standard (données, canal 1) vs sortie d'erreur (logs, canal 2, via >&2).

Récap et vérification

  • Commence par #!/usr/bin/env bash + set -euo pipefail + IFS sûr.
  • Pilote par getopts, documente avec usage(), gère -h et les erreurs.
  • Fichiers temporaires : mktemp + trap 'rm -rf "$tmp"' EXIT.
  • Logs horodatés sur >&2 ; données sur la sortie standard.
  • JSON avec jq, jamais avec grep/sed.
  • find … -exec {} + et -print0 | xargs -0 pour la vitesse et la sûreté.
  • Passe chaque script à ShellCheck ; au-delà de la logique simple, vise Python.

Vérifie ta compréhension

  1. Pourquoi créer un dossier temporaire avec mktemp -d et le nettoyer via un trap … EXIT plutôt qu'un nom fixe dans /tmp ?
  2. Pourquoi -exec commande {} + est-il plus rapide que -exec commande {} \; ?
  3. Pourquoi envoyer les logs sur >&2 plutôt que sur la sortie standard ?
