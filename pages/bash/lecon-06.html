Module 02 · Scripter en Bash — Leçon 06

Écrire son premier script

~35 min Intermédiaire Leçon 5 recommandée

À la fin de cette leçon, tu sauras

  • savoir créer un script Bash exécutable avec un shebang (#!/usr/bin/env bash), chmod +x et l'appel ./script.sh
  • savoir lire les arguments de position ($1, $#, "$@", shift) et une entrée interactive avec read -r -p
  • savoir gérer le code de retour avec exit 0/exit 1 et $?, et afficher proprement avec printf
  • savoir protéger un script avec set -euo pipefail et éviter les pièges classiques (droits, CRLF, $@ non cité) .
Sommaire de la leçon

Jusqu'ici, tu as tapé tes commandes une par une dans le terminal. Ça marche, mais dès que tu refais la même suite d'opérations chaque jour — ranger des fichiers, sauvegarder un dossier, vérifier un site — retaper tout devient pénible et source d'erreurs. La bonne nouvelle : tout ce que tu sais déjà taper, tu peux le ranger dans un fichier et le rejouer d'une seule commande. Ce fichier, c'est un script.

Dans cette leçon, on transforme pas à pas une suite de commandes en un vrai outil réutilisable : on lui donne un point de départ (le shebang), le droit de s'exécuter, des commentaires pour s'y retrouver, la capacité de recevoir des informations (arguments et questions), un signal clair de réussite ou d'échec, et enfin un filet de sécurité. Rappel important : ces commandes tournent dans un vrai terminal (Linux, macOS, ou WSL/Git Bash sous Windows), pas dans l'éditeur du site. Recopie-les chez toi pour les essayer.

Un script, c'est juste un fichier de commandes

Un script Bash n'est rien d'autre qu'un fichier texte qui contient les commandes que tu aurais tapées à la main, une par ligne. Par convention, on lui donne l'extension .sh (mais ce n'est pas obligatoire). La toute première ligne mérite une attention particulière : c'est le shebang.

La ligne #!/usr/bin/env bash dit au système : « pour exécuter ce fichier, utilise le programme bash ». Les deux caractères #! (dièse + point d'exclamation) forment le « shebang ». Pourquoi /usr/bin/env bash plutôt que /bin/bash directement ? Parce que env va chercher bash là où il est réellement installé sur la machine (il n'est pas toujours au même endroit selon les systèmes). C'est donc la forme la plus portable.

Note

Le shebang doit être strictement la première ligne du fichier, sans espace ni ligne vide au-dessus. $(pwd) est une substitution de commande : Bash exécute pwd et insère son résultat à la place.

Le rendre exécutable

Un fichier texte n'a pas, par défaut, le droit d'être lancé comme un programme. Il faut le lui accorder avec chmod (« change mode », change les permissions) et l'option +x qui veut dire « ajoute le droit d'exécution ».

On donne le droit d'exécution, puis on lance le script en préfixant son nom par ./.

Pourquoi ./ devant le nom ? Le point-slash signifie « le fichier qui est dans le dossier courant ». Sans lui, Bash chercherait une commande nommée bonjour.sh dans les dossiers système (le PATH) et ne la trouverait pas. Autre solution, sans toucher aux permissions : passer le fichier directement à bash.

Avec bash bonjour.sh, pas besoin de chmod ni de shebang : c'est bash lui-même qu'on appelle.

Commentaires et en-tête

Tout ce qui suit un # (sauf le shebang) est un commentaire : Bash l'ignore. Les commentaires expliquent ton intention à ton « toi » de demain. Un bon réflexe : commencer chaque script par un petit en-tête qui dit ce qu'il fait et comment l'utiliser.

L'option -p de mkdir évite une erreur si photos existe déjà. Un en-tête clair fait gagner un temps fou quand tu retrouves un script six mois plus tard.

Les arguments de position

Un script devient vraiment utile quand on peut lui passer des informations au moment de l'appeler, comme un nom de fichier. Ces informations sont les arguments, accessibles via des variables spéciales : $1 est le premier argument, $2 le deuxième, et ainsi de suite. Quelques autres très utiles :

$# compte les arguments, $@ les liste tous.

Point crucial : entoure presque toujours $@ de guillemets, soit "$@". Sans guillemets, un argument contenant une espace (par exemple mon fichier.txt) serait découpé en deux. Avec "$@", chaque argument reste entier. La commande shift, elle, « décale » les arguments d'un cran : après un shift, l'ancien $2 devient $1. Pratique pour traiter une liste un par un.

Grâce à "$@", le nom avec une espace reste un seul argument.

Demander une entrée à l'utilisateur

Parfois tu veux poser une question pendant l'exécution plutôt que de tout passer en argument. La commande read lit une ligne tapée au clavier et la range dans une variable. L'option -p affiche un message d'invite (« prompt »).

L'utilisateur tape Léa puis Entrée ; la réponse atterrit dans $nom.

Prends l'habitude d'ajouter -r (pour « raw », brut). Sans lui, read interprète l'antislash \ comme un caractère spécial, ce qui casse les chemins de fichiers Windows ou les mots de passe contenant un \. read -r garde le texte tel quel : c'est la forme à utiliser par défaut.

Le code de retour : réussite ou échec

Chaque commande, en se terminant, laisse derrière elle un code de retour : un nombre entre 0 et 255. La convention universelle : 0 = tout s'est bien passé, et toute autre valeur signale une erreur. Ce code est rangé dans la variable spéciale $?, et tu peux fixer celui de ton script avec exit.

$? contient le code de la dernière commande exécutée.

Ces codes ne sont pas du décor : ils permettent à d'autres programmes (ou à toi-même) de réagir. Par exemple ./verifie.sh notes.txt && echo "OK" n'affiche OK que si le script a renvoyé 0. Le test [ -f "$1" ] vérifie que $1 est un fichier existant ; [ "$#" -eq 0 ] teste si zéro argument a été fourni.

Le filet de sécurité : set -euo pipefail

Par défaut, Bash est trop indulgent : si une commande échoue au milieu du script, il continue quand même, ce qui peut faire des dégâts. La ligne set -euo pipefail, placée juste après le shebang, active trois protections d'un coup. Décortiquons-la.

En clair : -e évite qu'un script continue sur des bases cassées après une erreur ; -u attrape les fautes de frappe dans les noms de variables (sans lui, une variable mal orthographiée vaut silencieusement la chaîne vide) ; pipefail corrige un piège des « tuyaux » | où, normalement, seul le code du dernier maillon compte. Mets cette ligne en tête de tous tes scripts sérieux : c'est l'habitude qui t'évitera le plus de mauvaises surprises.

Astuce

set -euo pipefail est spécifique à Bash. En pur POSIX (le sh minimal), set -eu existe mais pipefail n'est pas garanti : c'est une raison de plus de cibler bash via le shebang #!/usr/bin/env bash.

Cas réel

En 2015, un script d'installation de Steam (la plateforme de jeux) contenait la ligne rm -rf "$STEAMROOT/"*. Dans un cas de figure, la variable STEAMROOT se retrouvait vide : la commande devenait rm -rf "/"* et effaçait tout le disque de l'utilisateur. Deux protections de cette leçon auraient stoppé le drame : set -u aurait fait échouer le script sur la variable non définie, et un garde-fou [ -n "$STEAMROOT" ] avant le rm aurait refusé d'agir sur une valeur vide. La règle des pros : on ne fait jamais confiance à une variable, surtout devant un rm -rf.

Afficher proprement avec printf

echo est simple mais imprévisible d'un système à l'autre (gestion des \n, des options). Pour un affichage maîtrisé, printf est plus fiable et portable. Il prend un format où %s est remplacé par une chaîne, et où \n insère un retour à la ligne.

Chaque %s consomme un argument dans l'ordre ; printf n'ajoute pas de retour à la ligne tout seul, d'où les \n explicites.

Réunissons tout dans un script complet et commenté, qui salue une personne passée en argument ou affiche son mode d'emploi si on l'oublie :

Sans argument, le script explique son usage et sort en erreur ; avec un prénom, il salue et sort en succès.

Pièges fréquents

Piège fréquent

Oublier le shebang ou le droit +x. Sans chmod +x, lancer ./script.sh renvoie Permission denied. Solution : chmod +x script.sh, ou bien lance-le avec bash script.sh qui ne demande pas ce droit.

Piège fréquent

Utiliser $@ sans guillemets, ou ne pas vérifier $#. Sans "$@", un argument contenant une espace est coupé en deux ; sans test de $#, un script appelé sans argument plante sur un $1 vide. Réflexe : "$@" et un if [ "$#" -eq 0 ] en garde-fou.

Piège fréquent

Éditer le script avec des fins de ligne Windows (CRLF). Un caractère invisible se colle au shebang et tu obtiens bad interpreter: /usr/bin/env bash^M. Configure ton éditeur en fins de ligne « LF (Unix) », ou répare avec dos2unix script.sh.

Pour aller plus loin

Pour aller plus loin

Quand tes scripts grandissent : getopts gère de vraies options (-v, -h) ; les here-documents (cat <<EOF) écrivent des blocs de texte sur plusieurs lignes ; trap exécute un nettoyage automatique à la sortie (même en cas d'erreur) ; ShellCheck est un « linter » qui repère tes bugs Bash avant l'exécution ; enfin, viser des scripts idempotents (qu'on peut relancer sans dégât) est une excellente discipline.

Antisèche

Glossaire

Script
Fichier texte contenant une suite de commandes, rejouable d'un seul appel. Extension usuelle .sh.
Shebang
La 1re ligne #!/usr/bin/env bash qui indique au système quel interpréteur utiliser pour lire le fichier.
chmod +x
Ajoute la permission d'exécution à un fichier, sans laquelle ./script.sh refuse de démarrer.
Argument de position
Valeur passée au script à l'appel, lue via $1, $2… ; $# les compte, "$@" les liste.
read
Lit une ligne saisie au clavier dans une variable ; -p affiche une invite, -r préserve les antislashs.
Code de retour
Entier laissé par une commande en se terminant : 0 = succès, autre = erreur. Rangé dans $?, fixé par exit.
set -euo pipefail
Trois protections : arrêt sur erreur (-e), variable non définie interdite (-u), échec propagé dans un pipe (pipefail).
printf
Affiche selon un format (%s, \n) ; plus fiable et portable qu'echo pour un rendu maîtrisé.

Récap et vérification

  • Un script est un fichier de commandes ; sa première ligne, le shebang #!/usr/bin/env bash, indique l'interpréteur de façon portable.
  • On le rend exécutable avec chmod +x script.sh puis on le lance par ./script.sh ; sinon bash script.sh fonctionne sans droits ni shebang.
  • Les arguments arrivent dans $1, $2… ; $0 est le nom du script, $# leur nombre, et "$@" les liste tous correctement cités. shift les décale.
  • read -r -p "Question " var demande une saisie ; -r protège les antislashs.
  • Le code de retour (exit 0 succès, exit 1 échec) se lit dans $? ; set -euo pipefail et printf rendent les scripts plus sûrs et plus lisibles.

Vérifie ta compréhension

  1. À quoi sert le shebang #!/usr/bin/env bash, et pourquoi passer par env plutôt que d'écrire /bin/bash en dur ?
  2. Quelle différence y a-t-il entre $@ et "$@" quand un argument contient une espace ?
  3. Que font respectivement -e, -u et pipefail dans set -euo pipefail ?
