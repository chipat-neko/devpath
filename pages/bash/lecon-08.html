Module 02 · Scripter en Bash — Leçon 08

Fonctions, robustesse et automatisation

~35 min Intermédiaire Leçon 7 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire une fonction Bash, lui passer des arguments et récupérer son résultat (return vs echo)
  • savoir rendre un script robuste avec local, set -euo pipefail et trap
  • savoir déboguer un script (bash -x, ShellCheck) et écrire les erreurs sur stderr ;
  • savoir automatiser l'exécution d'un script avec cron.
Sommaire de la leçon

Jusqu'ici, tes scripts étaient sans doute de simples listes de commandes lues de haut en bas. Ça marche très bien pour cinq lignes. Mais dès qu'un script grandit, tu copies-colles, tu te répètes, et le moindre bug devient difficile à retrouver. Bonne nouvelle : comme dans une cuisine bien rangée où chaque ustensile a sa boîte, tu peux découper ton script en petits blocs réutilisables (des fonctions), le rendre solide pour qu'il s'arrête proprement en cas de pépin, puis le faire tourner tout seul chaque matin pendant que tu dors.

Dans cette leçon, on assemble tout ce que tu as vu jusqu'ici en un script propre, fiable et automatique. On reste en Bash (le shell par défaut de la plupart des Linux et de macOS via les outils GNU) ; sous Windows, tout ceci fonctionne dans WSL ou Git Bash. Ces commandes tournent dans un vrai terminal : lis-les, puis essaie-les toi-même dans ta console.

Les fonctions : ranger son code dans des boîtes

Une fonction, c'est un bout de script auquel tu donnes un nom. Tu l'écris une fois, tu l'appelles autant de fois que tu veux. La syntaxe la plus portable (POSIX) est nom() { … }.

Remarque essentielle : à l'intérieur d'une fonction, $1, $2, $3… désignent les arguments donnés à la fonction, pas ceux du script. C'est exactement la même mécanique que les arguments d'un script, mais à l'échelle d'un bloc. $* désigne quant à lui l'ensemble des arguments reçus.

Renvoyer un résultat : return n'est pas une valeur

C'est le point qui surprend tous les débutants. En Bash, return ne renvoie pas une donnée : il renvoie un code de sortie, un entier entre 0 et 255, où 0 signifie « tout va bien » et tout le reste « il y a eu un souci ». C'est utile pour dire « succès/échec », pas pour transmettre un nombre ou un texte.

Pour récupérer une vraie valeur, la fonction l'echo (l'affiche), et tu la captures avec $(…).

Note

Retiens la règle : return pour dire « ça a marché ou pas » (un code 0-255), echo + $(…) pour récupérer une donnée. $? contient toujours le code de sortie de la dernière commande.

Les variables locales : éviter les collisions

Par défaut, en Bash, toutes les variables sont globales. Si ta fonction utilise une variable i et que ton script en a une autre du même nom ailleurs, elles s'écrasent mutuellement. C'est une source de bugs sournois. Le mot-clé local enferme la variable dans la fonction.

Astuce

Prends l'habitude de déclarer local pour toute variable propre à une fonction. C'est gratuit et ça t'épargnera des heures de débogage. Petit détail : ne combine pas local avec une capture $(…) sur la même ligne si tu veux tester un code d'erreur, car local « avale » le code de sortie.

Déboguer : voir ce que fait vraiment le script

Quand un script ne fait pas ce que tu crois, le mode trace est ton meilleur ami : Bash affiche chaque commande juste avant de l'exécuter, valeurs des variables comprises.

Le préfixe + marque les lignes de trace. Tu peux aussi activer la trace sur une portion seulement : set -x pour démarrer, set +x pour arrêter.

Mais le vrai réflexe pro, c'est ShellCheck, un « correcteur orthographique » pour scripts Bash. Il repère les guillemets manquants, les variables non protégées et mille pièges classiques.

Gérer les erreurs proprement : stderr et messages

Un terminal a deux « tuyaux » de sortie : la sortie standard (stdout, le résultat normal) et la sortie d'erreur (stderr). Les messages d'erreur doivent partir sur stderr, avec >&2. Ainsi, si quelqu'un récupère le résultat de ton script dans un fichier, tes messages d'erreur ne le polluent pas et restent visibles à l'écran.

Piège fréquent

cron tourne dans un environnement minimal : il n'a pas le même PATH ni les mêmes variables que ton terminal interactif. Utilise toujours des chemins absolus (/home/noah/scripts/sauvegarde.sh et non ./sauvegarde.sh) et ne suppose aucune variable d'environnement.

Sur les systèmes modernes, les timers systemd offrent une alternative plus puissante (journalisation, dépendances), mais cron reste le plus simple et le plus portable pour débuter.

Cas réel

Le grand classique de tout administrateur débutant : « mon script marche à la main, mais rien ne se passe en cron ». La cause est presque toujours la même : cron démarre avec un environnement minimal (un PATH réduit, aucune variable de ton terminal). Un script qui appelait node ou docker sans chemin absolu échouait donc en silence chaque nuit — et comme personne ne lisait la sortie, la sauvegarde restait vide pendant des semaines. Deux réflexes de cette leçon règlent le problème : rediriger la sortie de la tâche vers un journal (… >> /var/log/sauvegarde.log 2>&1) pour garder une trace, et utiliser partout des chemins absolus. On teste toujours une tâche cron dans un environnement dépouillé, jamais seulement dans son terminal confortable.

Pièges fréquents

  • Croire que return renvoie une valeur. Il renvoie un code 0-255. Pour une donnée, utilise echo puis capture avec $(ma_fonction).
  • Oublier local. Sans lui, les variables d'une fonction sont globales et peuvent écraser silencieusement celles du reste du script.
  • Mal placer le trap. Définis-le juste après avoir créé la ressource à nettoyer, sinon un plantage précoce le contourne.
  • Supposer l'environnement de cron. Pas de PATH complet, pas de variables interactives : utilise des chemins absolus partout.
  • Ne pas lancer ShellCheck. Il attrape en deux secondes des bugs qui te coûteraient une heure.

Pour aller plus loin

Pour aller plus loin

Intègre ShellCheck en CI pour qu'il vérifie chaque modification automatiquement. Range tes fonctions réutilisables dans un fichier que tu charges avec source bibliotheque.sh. Explore getopts pour gérer des options en ligne de commande (-v, -h). Et quand un script dépasse 200 lignes ou manipule des structures de données, c'est le signal qu'il faut passer à un vrai langage comme Python ; pour enchaîner plusieurs scripts, regarde make.

Glossaire

Fonction
Bloc de code nommé, défini par nom() { … } et rappelé comme une commande ; reçoit ses propres $1, $2…
return
Renvoie un code de sortie (0–255), pas une donnée : 0 = succès. Lu dans $?.
local
Enferme une variable dans la fonction pour ne pas écraser une variable globale de même nom.
set -euo pipefail
Rend le script strict : arrêt sur erreur, variable non définie interdite, échec propagé dans un pipe.
trap
Planifie une commande à exécuter à un signal, souvent EXIT : garantit le nettoyage même en cas de plantage.
stderr (>&2)
Le canal des messages d'erreur, distinct de stdout pour ne pas polluer le résultat capturé.
ShellCheck
Analyseur statique (« linter ») qui repère guillemets manquants et pièges classiques avant l'exécution.
cron
Planificateur d'Unix : 5 champs d'horaire + une commande, éditée par crontab -e. Environnement minimal.

Récap et vérification

  • Une fonction nom() { … } reçoit ses arguments via $1, $2…
  • return = code 0-255 (succès/échec) ; echo + $(…) = vraie valeur.
  • local enferme une variable dans sa fonction.
  • set -euo pipefail stoppe au premier pépin ; trap '…' EXIT garantit le nettoyage.
  • bash -x et ShellCheck pour déboguer ; messages d'erreur sur stderr avec >&2.
  • cron (crontab -e) planifie, avec 5 champs d'horaire et des chemins absolus.

Vérifie ta compréhension

  1. Une fonction doit te donner le double d'un nombre. Pourquoi return $(( $1 * 2 )) est-il une mauvaise idée, et que mettrais-tu à la place ?
  2. Ton script crée un fichier temporaire au début. Quelle ligne ajouter, et où, pour qu'il soit supprimé même en cas de plantage ?
  3. Que signifie la ligne cron 0 8 * * *, et pourquoi faut-il y écrire le chemin complet du script ?
