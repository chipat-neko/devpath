Module 04 · Maîtrise du shell — Leçon 12

Déboguer ses scripts Bash

~34 min Intermédiaire Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • vérifier la syntaxe d'un script sans l'exécuter avec bash -n ;
  • voir chaque commande réellement exécutée avec set -x et personnaliser la trace via PS4 ;
  • localiser un plantage avec un trap … ERR, $LINENO et $BASH_COMMAND ;
  • attraper les pièges avant l'exécution avec ShellCheck et ses directives.
Sommaire de la leçon

Un script Bash ne « plante » pas toujours bruyamment. Le plus souvent, il tourne jusqu'au bout… mais fait la mauvaise chose : il efface le mauvais fichier, saute une boucle, ou traite un chemin coupé en deux. Le débogage, en Bash, ce n'est pas coller des echo partout au hasard : c'est utiliser les quatre outils que le shell te donne déjà. Cette leçon te les met en main.

On suppose que tu écris déjà des scripts avec variables, conditions et fonctions (leçons 5 à 8) et que tu connais le mode strict set -euo pipefail (leçon 11). Ici, on apprend à voir ce que le script fait vraiment, et à situer précisément là où il déraille.

Lire avant d'exécuter : bash -n

Avant même de lancer un script, tu peux demander à Bash de le lire sans rien exécuter. L'option -n (no-exec) ne fait qu'analyser la syntaxe : un do sans done, un if sans fi, une accolade non fermée sont signalés tout de suite, sans le moindre risque.

C'est le premier réflexe sur un gros script : bash -n attrape les fautes de structure en une fraction de seconde. Attention toutefois : il ne détecte que la syntaxe, pas la logique. Un script syntaxiquement parfait peut très bien effacer ton disque.

Voir le script s'exécuter : set -x

L'outil roi du débogage Bash, c'est la trace d'exécution. Avec set -x (ou bash -x script.sh), le shell affiche chaque commande juste avant de la lancer, mais surtout après avoir remplacé les variables et le globbing. Tu vois donc ce qui s'exécute vraiment, pas ce que tu croyais avoir écrit.

La trace révèle immédiatement le bug : la variable non quotée est découpée en deux mots, et rm reçoit deux arguments au lieu d'un seul nom de fichier.

Chaque ligne tracée commence par un +. Ce préfixe est réglable via la variable PS4 : en y glissant le numéro de ligne et le nom de la fonction, la trace devient une carte précise de l'exécution.

Astuce

Pas besoin de modifier le fichier pour tracer : bash -x script.sh trace tout le script depuis l'extérieur. Pour n'éclairer qu'une zone suspecte, encadre-la de set -x … set +x à l'intérieur du script. Tu limites ainsi le bruit à la partie qui t'intéresse.

Attraper l'erreur au vol : trap ERR

Sous set -e, un script s'arrête dès qu'une commande échoue — mais sans te dire où. Un trap … ERR comble le vide : il déclenche un gestionnaire quand une commande renvoie un statut non nul (sauf dans la condition d'un if et à gauche de || ou && ; avec set -E, il vaut aussi dans les fonctions). Deux variables magiques t'y attendent : $LINENO (la ligne fautive) et $BASH_COMMAND (la commande qui vient d'échouer).

Au lieu d'un script qui s'éteint en silence, tu obtiens un message qui pointe la ligne exacte et la commande exacte. C'est la différence entre « ça n'a pas marché » et « la copie de la ligne 8 a échoué avec le code 1 ».

Les variables qui situent le bug

Bash entretient plusieurs variables spéciales dédiées à l'introspection. Elles répondent à la question « où suis-je ? » au moment d'une erreur, surtout dans un script découpé en fonctions.

FUNCNAME est un tableau : FUNCNAME[0] est la fonction courante, FUNCNAME[1] celle qui l'a appelée, et ainsi de suite. Combiné à BASH_LINENO, il permet de reconstruire toute la pile d'appels — exactement ce qu'affiche une « stack trace » dans les autres langages.

Note

$LINENO vaut le numéro de la ligne où il est lu, pas celle de l'erreur en général. Dans un trap … ERR, il donne bien la ligne fautive car le piège s'exécute « comme si » il était à cet endroit. Ailleurs, il indique simplement sa propre ligne : pratique pour jalonner un script de repères echo "point $LINENO".

ShellCheck, le filet avant l'exécution

Tu as croisé ShellCheck à la leçon 11 : c'est le linter de référence, qui lit ton script et signale les pièges sans l'exécuter. Là où set -x montre un bug pendant qu'il se produit, ShellCheck l'anticipe. Chaque avertissement porte un code SCxxxx documenté en ligne.

Chaque code renvoie à une explication détaillée (par exemple github.com/koalaman/shellcheck/wiki/SC2086). Quand un avertissement est un faux positif assumé, tu peux le désactiver localement par une directive en commentaire — mais avec parcimonie, et jamais pour masquer un vrai problème.

La boucle de débogage

Ces outils ne se remplacent pas : ils se relaient. Chacun attrape une classe de bugs différente, à un moment différent. L'ordre naturel va du statique (sans exécuter) au dynamique (pendant l'exécution).

Cas réel

En 2017, un ingénieur de GitLab a effacé par erreur le répertoire de données de la base de production : une commande rm -rf lancée sur le mauvais serveur, dans une console où rien ne distinguait la production de la copie. L'enquête publique a recommandé, entre autres, des scripts qui affichent le contexte avant d'agir et refusent les chemins ambigus. La morale pour nous : une trace set -x qui montre quel chemin va être supprimé, ou une garde [ -n "$dir" ] || exit 1 lisible dans la trace, valent tous les echo ajoutés en panique après coup.

Pièges fréquents

Piège fréquent

Croire que bash -n valide le script. Il ne teste que la syntaxe : rm -rf / passe la vérification sans broncher. Pour la logique, rien ne remplace une trace set -x sur un jeu de données de test, dans un dossier bac à sable.

Piège fréquent

Laisser set -x actif dans un script de production : la trace peut divulguer des mots de passe ou des jetons passés en argument. Trace en développement, retire (ou encadre étroitement) avant de livrer ; et n'affiche jamais de secret en clair dans une commande tracée.

Pour aller plus loin

Pour aller plus loin

Explore trap … DEBUG (exécuté avant chaque commande, pour un pas-à-pas fin), la variable BASH_XTRACEFD qui redirige la trace vers un fichier de log, l'option set -v (affiche les lignes avant expansion, complément de -x), et l'extension Bash Debug de VS Code pour poser de vrais points d'arrêt.

Antisèche

Glossaire

bash -n
Mode no-exec : lit le script et vérifie sa syntaxe sans exécuter la moindre commande.
set -x (xtrace)
Affiche chaque commande après expansion des variables et du globbing, juste avant son exécution.
PS4
Chaîne de préfixe de la trace -x (par défaut + ) ; on y met $LINENO, $FUNCNAME, etc.
trap … ERR
Piège déclenché à chaque commande renvoyant un statut non nul (sauf dans la condition d'un if ou à gauche de || et && ; dans une fonction, seulement avec set -E) : idéal pour signaler l'échec.
$LINENO
Numéro de la ligne du script en cours de lecture.
$BASH_COMMAND
Texte de la commande en cours d'exécution : précieux dans un trap ERR.
FUNCNAME
Tableau des fonctions actives : [0] = courante, [1] = appelante… la pile d'appels.
ShellCheck
Linter statique des scripts shell : repère quoting, tests douteux et bashismes via des codes SCxxxx.

Récap et vérification

  • bash -n valide la syntaxe sans exécuter : premier réflexe, zéro risque.
  • set -x (ou bash -x) montre les commandes après expansion : on voit le vrai déroulé.
  • Un PS4 enrichi ajoute ligne et fonction à chaque étape tracée.
  • trap '…' ERR + $LINENO + $BASH_COMMAND = message qui pointe le plantage.
  • ShellCheck anticipe les pièges avant l'exécution ; désactive un warning seulement à bon escient.
  • On filtre d'abord sans risque, puis on éclaire l'exécution.
