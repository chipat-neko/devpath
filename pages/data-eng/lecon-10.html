Module 3 · Faire tourner et faire confiance — Leçon 10

La qualité des données : tester ce qui coule

~36 min Intermédiaire Prérequis : les 3 promesses (leçon 1) et les couches (leçon 6)

À la fin de cette leçon, tu sauras

  • nommer les quatre familles de tests de données — unicité, complétude, fraîcheur, volumétrie et plage de valeurs ;
  • choisir où poser un test — à l'entrée, entre les couches, à la sortie — et le formuler comme une assertion ;
  • décider quoi faire quand un test échoue — bloquer, alerter, mettre en quarantaine ;
  • écrire un test en SQL, en déclaratif (façon dbt / Great Expectations) et dans un petit harnais Python.
Sommaire de la leçon

Un pipeline peut être vert — il tourne, ne plante pas, se termine chaque nuit sans la moindre erreur — et pourtant cracher des chiffres faux. Le code s'est exécuté : aucune exception, aucun processus tué. Mais un fichier a été livré à moitié, une colonne est arrivée vide, un capteur a doublé ses événements, et le tableau de bord de 8 h affiche un total qui n'a plus aucun sens. Rien n'a « planté » ; tout est faux quand même.

C'est le grand malentendu de la qualité des données : tester le code ne suffit pas. Un test unitaire vérifie qu'une fonction de nettoyage se comporte bien sur un exemple choisi. Il ne dit rien de la donnée réelle qui coulera demain, ni après-demain. Or c'est cette donnée-là qui alimente les décisions. Cette leçon apprend à tester non pas le code, mais la donnée qui coule dedans, et à le faire à chaque exécution. On reprend les trois promesses de la leçon 1 — fraîcheur, complétude, exactitude — et l'on va voir comment chacune se traduit en un test automatique, où le placer le long du pipeline, comment réagir quand il vire au rouge, et comment l'écrire en SQL, en déclaratif et en Python. Fil rouge : Vélociti, toujours.

Tester le code ne suffit pas

Reformulons la promesse de fond. En tests logiciels, on écrit des cas figés : telle entrée doit produire telle sortie. Le jeu de test ne change pas entre deux exécutions ; c'est justement sa force pour attraper une régression de code. Mais les données, elles, changent à chaque exécution. Le fichier de trajets de mardi n'est pas celui de lundi : il peut être plus court, arriver en retard, contenir une valeur que personne n'avait jamais vue. Un test de code passe une fois pour toutes ; un test de données doit tourner sur chaque lot qui arrive.

Un test de données est donc simplement une assertion sur une table : une affirmation qu'on tient pour vraie, vérifiée automatiquement à chaque passage. « trip_id est unique ». « station_end n'est jamais vide ». « Il y a environ 150 000 lignes aujourd'hui ». Si l'assertion tient, le pipeline continue ; si elle échoue, quelque chose se déclenche. Tester la donnée, c'est transformer ces phrases en français en des vérifications que la machine rejoue sans se lasser.

Deux tests, deux mondes

Un test de code vérifie une logique sur un exemple figé (est-ce que ma fonction de dédoublonnage marche ?). Un test de données vérifie une propriété sur la donnée vivante du jour (est-ce que la table livrée ce matin est bien dédoublonnée ?). Les deux sont utiles et ne se remplacent pas : le premier attrape les bugs quand tu changes le code, le second attrape les surprises quand la donnée change.

Les quatre familles de tests de données

La quasi-totalité des tests de données tombent dans quatre familles. Les retenir, c'est déjà savoir quoi vérifier sur n'importe quelle table.

  • Unicité — la clé n'a pas de doublon. Chez Vélociti, deux lignes ne doivent jamais partager le même trip_id. Un doublon gonfle les totaux : c'est une attaque directe contre l'exactitude.
  • Non-nullité / complétude — les colonnes obligatoires sont remplies, et aucun fichier n'a été sauté. station_end, start, end ne peuvent pas être vides : un trajet sans station d'arrivée n'existe pas. C'est la promesse de complétude.
  • Fraîcheur — le dernier jour attendu est bien là. Si l'on est le 2 mai et que la table s'arrête au 30 avril, les données sont vieilles : la promesse de fraîcheur est rompue, même si tout le reste est parfait.
  • Volumétrie & plage de valeurs — le nombre de lignes est plausible, et les valeurs restent dans leur domaine. On attend ~150 000 trajets par jour : 12 000 lignes trahit un fichier tronqué, 3 millions un doublon massif. Et chaque valeur reste dans sa plage : type_velo ∈ {electrique, mecanique, inconnu} — les trois sorties du CASE du silver —, une durée > 0.

Note

La complétude a deux visages. Le premier est ligne à ligne : telle colonne obligatoire est-elle remplie ? Le second est lot à lot : a-t-on bien reçu tous les fichiers attendus ? Un pipeline peut avoir zéro valeur nulle et pourtant être incomplet parce qu'un des fichiers du jour n'est jamais arrivé. Les deux se testent : l'un compte les vides, l'autre compte les partitions présentes.

Où poser les tests

Un test ne vaut que par l'endroit où on le place. Trois positions se combinent le long du pipeline.

  • À l'entrée — la source respecte-t-elle son contrat ? Dès que le fichier de trajets arrive, avant même de le charger, on vérifie qu'il a les bonnes colonnes, un volume plausible, une date attendue. C'est le premier rempart : on refuse une source malformée avant qu'elle ne contamine tout le reste.
  • Entre les couches — le nettoyage n'a-t-il rien cassé ? En passant de bronze à silver (leçon 6), on a typé, dédoublonné, filtré. On teste alors la table silver : trip_id est-il vraiment unique maintenant ? Reste-t-il des durées négatives ? C'est là qu'on vérifie que la transformation a fait ce qu'elle promettait.
  • À la sortie — avant de publier le gold. La table d'agrégats qui alimente le tableau de bord passe un dernier contrôle avant d'être exposée : pas de trou, des totaux dans un ordre de grandeur crédible. C'est le dernier filet avant que quelqu'un ne lise un chiffre.

Ces trois positions ne sont pas exclusives : un pipeline sérieux en pose aux trois. Un test à l'entrée attrape un problème de source ; un test entre couches attrape un bug de transformation ; un test de sortie attrape ce que les deux premiers ont laissé passer.

Quand un test échoue

Un test rouge n'a de valeur que si une réaction est prévue. Trois réponses existent, et le choix dépend de la gravité.

  • Bloquer (fail) — on arrête le pipeline : ne pas publier un chiffre faux. C'est le prolongement direct de la leçon 1 : mieux vaut « données en retard » qu'un total faux. Si l'unicité de trip_id casse, le gold ne sort pas : on préfère un tableau de bord d'hier à un tableau de bord faux d'aujourd'hui.
  • Alerter (warn) — on laisse passer, mais on prévient. Pour une anomalie mineure ou incertaine — le volume est un peu bas mais pas absurde — on publie quand même et l'on envoie un signal à l'équipe, qui jugera. Le pipeline ne s'arrête pas ; un humain est mis au courant.
  • Mettre en quarantaine — on isole les lignes fautives et l'on laisse passer les bonnes. Plutôt que de tout bloquer parce que 40 trajets sur 150 000 ont une station_end inconnue, on écarte ces 40 lignes dans une table à part (à inspecter plus tard) et l'on publie les 149 960 valides. La donnée saine avance ; la douteuse attend.

Une idée relie ces réactions : le circuit breaker (coupe-circuit). Comme un disjoncteur électrique qui saute pour protéger l'installation, un test bloquant « disjoncte » le pipeline pour protéger les consommateurs d'un chiffre faux. Mieux vaut couper le courant que laisser griller la maison.

Piège fréquent

Publier malgré un test rouge. « Le test bloque, mais le patron veut son chiffre ce matin, alors on force la publication. » C'est exactement l'inverse de la promesse : on livre alors un total dont on sait qu'il est faux. Un test bloquant n'est utile que si l'on accepte qu'il bloque vraiment. Le bon réflexe est de publier le dernier état sain (celui d'hier) et de réparer, pas d'estampiller « bon » une donnée qu'on vient de déclarer mauvaise.

Écrire les tests

Passons à la pratique. Un test de données s'écrit de trois manières complémentaires : en SQL (une requête qui doit renvoyer zéro ligne fautive), en déclaratif (on déclare les attentes, un outil les traduit), et dans un petit harnais qui les exécute et fait échouer le run.

En SQL : une requête qui doit renvoyer zéro ligne

Le patron le plus simple : écrire une requête qui sélectionne exactement ce qui ne devrait pas exister. Si elle renvoie 0 ligne, le test passe ; sinon, chaque ligne rendue est une violation à examiner. Voici quatre contrôles Vélociti.

Ces quatre requêtes couvrent les quatre familles (unicité, complétude par intégrité référentielle, fraîcheur, volumétrie). Le principe est toujours le même : la bonne réponse est « zéro ligne ». Un harnais n'a plus qu'à compter les lignes rendues pour savoir si le test passe.

En déclaratif : on décrit l'attente, l'outil génère le test

Écrire chaque requête à la main devient vite répétitif. Les outils modernes — dbt avec ses schema.yml, ou Great Expectations — proposent de déclarer les attentes : on liste, colonne par colonne, ce qui doit être vrai, et l'outil génère et exécute les requêtes correspondantes. Le fichier ci-dessous se lit comme un contrat.

La force du déclaratif est la lisibilité : n'importe qui lit ce fichier et comprend le contrat de la table, sans savoir écrire une seule requête. unique, not_null, accepted_values, relationships couvrent nos quatre familles. On reverra la formalisation d'un tel contrat entre équipes à la leçon 11.

En Python : le harnais qui fait échouer le run

Que l'on écrive les tests en SQL ou en déclaratif, il faut une pièce qui les exécute et qui, en cas de violation, fait échouer le pipeline — pour que la réaction (bloquer, alerter) se déclenche vraiment. Voici un harnais minimal : chaque test est une requête « zéro ligne attendue » ; s'il en revient, on lève une erreur.

Ce harnais matérialise les réactions de la section précédente : un test fail qui trouve des lignes fait lever EchecQualite, ce qui arrête le pipeline avant la publication ; un test warn se contente d'imprimer une alerte et laisse le run continuer. C'est le coupe-circuit, en une trentaine de lignes.

Astuce

Écris tes tests pour qu'ils renvoient les lignes fautives, pas juste un compte. Savoir « 12 doublons » est utile ; voir quels trip_id sont en double te fait gagner l'enquête. Un bon test ne dit pas seulement « c'est cassé » : il tend l'échantillon exact de ce qui cloche, prêt à copier dans une requête d'analyse.

La qualité, un engagement quotidien

Le dernier point est le plus important, et le plus souvent oublié : ces tests doivent tourner à chaque exécution, à l'intérieur du DAG (leçon 9), et pas une seule fois en développement. Un test de qualité n'est pas un audit qu'on fait une fois pour cocher une case ; c'est un gardien permanent qui inspecte chaque lot de données au moment où il passe.

Concrètement, on insère les tests comme des nœuds du graphe : charger bronze → tester bronze → transformer en silver → tester silver → agréger en gold → tester gold → publier. Chaque test devient une étape dont dépend la suivante : tant qu'un test bloquant n'est pas vert, l'étape d'après ne démarre pas. La qualité cesse d'être un contrôle ponctuel : elle devient une condition de circulation de la donnée, réévaluée chaque nuit.

C'est ce changement de posture qui fait la différence entre un pipeline « qui a l'air de marcher » et un pipeline digne de confiance. Le premier a été vérifié un jour ; le second se vérifie tous les jours, tout seul, et sait s'arrêter quand il ne peut plus tenir ses promesses.

Pour aller plus loin

Tester la donnée à chaque exécution génère un historique précieux : combien de lignes, combien de rejets, quelle fraîcheur, jour après jour. Cet historique est la matière de l'observabilité (leçon 12), qui suit ces indicateurs dans la durée pour repérer les dérives lentes. Et pour muscler l'écriture des requêtes de contrôle elles-mêmes, le cours SQL est le compagnon direct : GROUP BY … HAVING, jointures, fonctions de fenêtrage sont exactement les outils d'un bon test de données.

Pièges fréquents

Piège fréquent

Tester le code mais pas la donnée. On a de beaux tests unitaires sur les fonctions de transformation, la couverture est à 90 %, et l'on croit la qualité assurée. Mais aucun test ne regarde la table livrée ce matin. Le code peut être parfait et recevoir un fichier tronqué : il le traitera parfaitement… et publiera un total faux. Les deux niveaux de test sont nécessaires ; l'un ne dispense pas de l'autre.

  • Tester une fois en dev, puis jamais. On lance les tests à la main pendant le développement, on voit qu'ils passent, et on ne les branche jamais dans le DAG. Six mois plus tard, une source dérive : personne ne le sait, car plus rien ne teste. Un test qui ne tourne pas à chaque run ne protège de rien.
  • Alerter sur tout → fatigue d'alerte. Si le moindre écart déclenche une notification, l'équipe reçoit dix alertes par jour, finit par les ignorer… et rate la vraie. Réserve le fail et l'alerte aux anomalies qui comptent ; calibre les seuils pour que rouge veuille dire quelque chose.
  • Publier malgré un test rouge — déjà vu plus haut : forcer la sortie d'un chiffre déclaré faux ruine l'intérêt même du test.

Cas réel

Cas réel

Un matin, le tableau de bord de Vélociti affiche 2,3 millions de trajets pour la veille — quinze fois le chiffre habituel. Le pipeline était pourtant vert : aucune erreur, tout s'était exécuté. En creusant, l'équipe découvre que la source des capteurs, ce jour-là, avait ré-émis ses événements en double après un incident réseau, et qu'une jointure mal cadrée avait multiplié les trajets. Aucun test de volumétrie n'existait : rien ne comparait le compte du jour à l'ordre de grandeur attendu. Le correctif a tenu en une ligne d'intention : un test bloquant « le nombre de trajets d'un jour reste entre 100 000 et 200 000 », posé à la sortie, avant publication. La fois suivante où une source a doublé, le gold n'est pas sorti : le tableau de bord est resté sur la veille (fiable) pendant qu'on réparait. Coût du test : quelques lignes de SQL. Valeur : ne plus jamais afficher un chiffre quinze fois trop grand comme s'il était vrai.

Antisèche

Glossaire

Qualité des données
Aptitude d'un jeu de données à tenir ses promesses (fraîcheur, complétude, exactitude) ; se garantit en la testant automatiquement, comme du code.
Test de données (assertion)
Affirmation tenue pour vraie sur une table, vérifiée automatiquement à chaque exécution : par exemple « trip_id est unique ».
Unicité
Absence de doublon sur une clé : chaque valeur de la clé n'apparaît qu'une fois (aucun trip_id répété).
Complétude
Rien ne manque : colonnes obligatoires remplies (non-nullité) et tous les fichiers/partitions attendus bien reçus.
Fraîcheur
Caractère à jour de la donnée : le dernier jour attendu est présent dans la table.
Volumétrie
Nombre de lignes d'un lot : on le compare à un ordre de grandeur attendu (~150 000 trajets/jour) pour repérer un fichier tronqué ou doublé.
Plage de valeurs (accepted values)
Ensemble ou intervalle des valeurs autorisées pour une colonne : type ∈ {electrique, mecanique}, durée > 0.
Quarantaine
Mise à l'écart des lignes fautives dans une table à part, pour laisser passer les lignes valides sans bloquer tout le lot.
Circuit breaker (coupe-circuit)
Test bloquant qui arrête le pipeline pour protéger les consommateurs d'un chiffre faux, comme un disjoncteur qui saute.
Fail vs warn
Deux réactions à un test rouge : fail bloque la publication ; warn laisse passer mais alerte un humain.

Récap et vérification

  • Un pipeline vert peut produire des données fausses : tester le code ne dit rien de la donnée qui coule ; il faut tester la donnée à chaque exécution.
  • Quatre familles couvrent l'essentiel : unicité, complétude (non-nullité + fichiers présents), fraîcheur, volumétrie & plage de valeurs.
  • On pose les tests à l'entrée (le contrat ?), entre les couches (rien cassé ?) et à la sortie (bon à publier ?) ; un test = une assertion sur une table.
  • Trois réactions à un échec : bloquer (fail, le coupe-circuit — mieux vaut en retard que faux), alerter (warn), mettre en quarantaine (isoler les fautives).
  • On écrit les tests en SQL (0 ligne attendue), en déclaratif (dbt / Great Expectations) et dans un harnais qui fait échouer le run ; le tout branché dans le DAG.

Vérifie ta compréhension

  1. Pourquoi dit-on qu'un pipeline « vert » peut quand même livrer des données fausses ? Qu'est-ce que tester le code ne teste pas ?
  2. Cite les quatre familles de tests de données, et donne pour chacune un exemple sur Vélociti.
  3. Un test d'unicité sur trip_id vire au rouge à 7 h 55, juste avant la publication du tableau de bord de 8 h. Quelle réaction choisis-tu, et pourquoi ?
