Écrire un DSL en Groovy

~46 min Avancé Prérequis : leçons 4 et 7

À la fin de cette leçon, tu sauras

  • expliquer ce qu'est un DSL et pourquoi Groovy s'y prête ;
  • identifier les ingrédients de syntaxe qui le rendent possible ;
  • rediriger les appels d'une closure avec delegate ;
  • écrire un petit DSL de configuration — le mécanisme de Gradle.
Sommaire de la leçon

Tu édites du Groovy depuis des années sans le savoir : chaque build.gradle et chaque Jenkinsfile en est un. Ces fichiers ne ressemblent pourtant pas à du « code » : ils se lisent comme un formulaire. C'est un DSL — un langage dédié — et Groovy est réputé pour être le meilleur outil de la JVM pour en écrire. Cette leçon lève le voile sur la mécanique.

Qu'est-ce qu'un DSL ?

Un DSL (Domain-Specific Language, langage dédié) est un mini-langage taillé pour un domaine : décrire une build, une configuration, un test, une facture… À l'opposé d'un langage généraliste (Java, Python), il sacrifie l'universalité pour la lisibilité dans son domaine. Un DSL interne est écrit dans un langage hôte : le DSL de Gradle est du Groovy valide, simplement arrangé pour se lire naturellement — c'est le compilateur Groovy qui le lit, sans outillage supplémentaire. À l'inverse, un DSL externe (SQL, un fichier .yml, une grammaire maison) est un langage à part entière : il a sa propre syntaxe, donc son propre analyseur à écrire et à maintenir.

Les ingrédients de syntaxe

Trois libertés de Groovy, déjà croisées, rendent l'illusion possible :

  • les parenthèses sont optionnelles pour un appel avec argument : hote("x") s'écrit hote "x" ;
  • les points-virgules sont inutiles ;
  • une closure passée en dernier argument sort des parenthèses (leçon 4) : serveur({ … }) devient serveur { … }.

Rappel

Tu as déjà vu un DSL à la leçon 11 : MarkupBuilder. page.ul { li "Java" } génère <ul><li>Java</li></ul>. Les builders sont des DSL de construction d'arbres.

La clé de voûte : delegate

Reste une question : dans serveur { hote "exemple.com" }, à qui s'adresse l'appel hote(...) ? Il n'y a pas d'objet devant. La réponse est le delegate de la closure. Chaque closure possède une propriété delegate : quand un appel de méthode n'a pas de cible explicite, Groovy le résout sur ce délégué. En le fixant sur un objet de configuration, on redirige tout le contenu de la closure vers cet objet.

Astuce

resolveStrategy = Closure.DELEGATE_FIRST demande à Groovy de chercher d'abord sur le délégué avant le contexte englobant (owner). Sans cela, la stratégie par défaut (OWNER_FIRST) pourrait résoudre hote ailleurs. Pour un DSL de configuration, DELEGATE_FIRST est presque toujours le bon choix.

Imbriquer les blocs

Un délégué peut lui-même exposer des méthodes qui prennent une closure : on obtient des blocs imbriqués, comme android { defaultConfig { … } }. Le principe se répète à chaque niveau : chaque bloc a son propre délégué.

Quand écrire un DSL ?

Piège fréquent

Un DSL a un coût : il faut le documenter, et un lecteur non averti se demande d'où sort hote. Ne bâtis un DSL que si le gain de lisibilité est réel et répété (configuration lue par beaucoup de monde, règles métier). Pour du code jeté une fois, de simples fonctions suffisent. Et gare à la magie : trop d'indirection rend le débogage pénible.

Antisèche

Glossaire

DSL
Domain-Specific Language : mini-langage taillé pour un domaine précis, privilégiant la lisibilité à l'universalité.
DSL interne
DSL écrit dans un langage hôte (ici Groovy) et qui reste du code valide de ce langage, arrangé pour se lire naturellement ; il profite du compilateur et des outils de l'hôte.
DSL externe
DSL formant un langage à part (SQL, YAML, grammaire maison) : syntaxe totalement libre, mais analyseur et outillage à écrire et à maintenir.
delegate
Propriété d'une closure désignant l'objet sur lequel sont résolus les appels de méthode et de propriété sans cible explicite.
resolveStrategy
Réglage indiquant l'ordre de résolution des noms d'une closure : OWNER_FIRST (défaut) ou DELEGATE_FIRST.
owner
Le contexte englobant où la closure a été définie ; consulté avant ou après le delegate selon la stratégie.
Builder
Objet dont chaque appel de méthode construit une partie d'une structure (arbre XML/HTML, config) ; forme courante de DSL.
Bloc imbriqué
Closure passée à une méthode du délégué, ouvrant un sous-contexte de configuration avec son propre delegate.

Récap et vérification

  • Un DSL est un mini-langage lisible ; un DSL interne reste du Groovy valide.
  • Parenthèses optionnelles + closure en dernier argument = une syntaxe déclarative.
  • Le delegate redirige les appels sans cible d'une closure vers un objet.
  • DELEGATE_FIRST et les blocs imbriqués reproduisent le fonctionnement de Gradle.

Vérifie ta compréhension

  1. Qu'est-ce qui distingue un DSL interne d'un DSL externe ?
  2. Quelle propriété d'une closure reçoit les appels sans cible ?
  3. Pourquoi règle-t-on souvent resolveStrategy sur DELEGATE_FIRST ?

Exercice 3Défi

Explique en une phrase pourquoi dependencies { implementation 'x' } dans un build.gradle n'a rien de magique une fois qu'on connaît delegate.

Voir une solution

dependencies { … } est un simple appel de méthode qui reçoit une closure en dernier argument ; Gradle fixe le delegate de cette closure sur un objet collecteur de dépendances, puis l'exécute. À l'intérieur, implementation 'x' n'est qu'un appel de méthode implementation('x') — parenthèses omises — résolu sur ce délégué. Aucune syntaxe spéciale : seulement les libertés de Groovy et le mécanisme du delegate.
