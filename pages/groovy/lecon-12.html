Tester avec Spock

~48 min Avancé Prérequis : leçons 4 et 6

À la fin de cette leçon, tu sauras

  • écrire une spécification Spock lisible ;
  • structurer un test avec les blocs given/when/then ;
  • vérifier une exception et piloter un test par les données (where) ;
  • isoler du code avec un Mock ou un Stub.
Sommaire de la leçon

Tu as croisé Spock à la leçon 9 : le framework de test le plus lisible de la JVM. Il n'est pas un hasard que ce soit un projet Groovy — il exploite tout ce que tu as appris (closures, opérateurs surchargés, métaprogrammation) pour transformer un test en une spécification qui se lit presque comme une phrase. Et le meilleur : il teste aussi bien du code Groovy que du code Java.

Une première spécification

Une spec Spock est une classe qui étend Specification. Chaque test est une méthode dont le nom est une phrase entre guillemets : c'est le libellé qui apparaîtra dans le rapport. Le bloc expect: énonce une condition qui doit être vraie.

Note

Spock s'exécute sur le moteur de JUnit : tes IDE, Gradle et Maven le lancent comme n'importe quel test. Tu profites de la lisibilité de Spock sans changer d'outillage.

Les blocs given / when / then

Le cœur de Spock est le triptyque given / when / then : préparer le contexte, exécuter l'action, vérifier le résultat. Dans le bloc then:, chaque expression booléenne est automatiquement une assertion — pas besoin d'écrire assert.

Vérifier une exception

Pour tester qu'un cas d'erreur lève bien une exception, on place l'action dans when: et on l'attend avec thrown() dans then:.

Astuce

def e = thrown(IllegalArgumentException) capture l'exception : tu peux ensuite vérifier son message avec e.message.contains("solde"). Pour affirmer qu'aucune exception n'est levée, il existe notThrown().

Tests pilotés par les données : le bloc where

Voici l'atout signature de Spock : rejouer le même test sur une table de données. Au lieu de copier-coller cinq tests presque identiques, on écrit un test et une table ; chaque ligne devient un cas distinct dans le rapport.

Cas réel

Les tables where sont idéales pour couvrir les cas limites d'une règle métier : barème d'impôt par tranches, remises par palier, validation d'un mot de passe… Une équipe peut lister dans la table tous les couples (entrée, sortie attendue) convenus avec le métier ; la table devient la spécification exécutable, lisible même par un non-développeur. C'est cette proximité avec la spec écrite qui a fait le succès de Spock.

Isoler le code : Mock et Stub

Pour tester une classe qui dépend d'une autre (une base, un service d'e-mail…), on remplace la dépendance par une doublure. Spock en crée en une ligne :

  • Stub : fournit des réponses toutes prêtes (>>). On simule une entrée.
  • Mock : en plus, on vérifie que telle méthode a bien été appelée (et combien de fois).

Piège fréquent

La vérification d'un Mock (1 * mailer.envoyer(...)) doit être placée dans then:, jamais dans when:. L'ordre compte : Spock enregistre l'attente dans then, puis la confronte à ce qui s'est passé pendant when. Le symbole _ est un joker qui accepte n'importe quel argument.

Pour aller plus loin

Pour aller plus loin

Spock offre bien plus : le bloc cleanup: (libérer une ressource), setup()/cleanup() partagés, @Shared pour un état commun, les data pipes (where: x << [1, 2, 3]), et une intégration fine avec Spring (spock-spring). Toute cette lisibilité repose sur ce que tu as appris : les closures forment les blocs, la métaprogrammation réécrit les assertions pour afficher un diagnostic détaillé quand un test échoue.

Glossaire

Spock
Framework de test et de spécification écrit en Groovy, reconnu pour sa lisibilité ; il teste du code Groovy comme du code Java et tourne sur JUnit.
Specification
Classe de base dont hérite toute spec Spock ; elle active les blocs (given/when/then…) et les assertions implicites.
Bloc (block)
Section étiquetée d'un test (given, when, then, expect, where, cleanup) qui découpe le scénario en étapes claires.
Assertion implicite
Dans then: et expect:, toute expression booléenne est évaluée comme une vérification, sans écrire assert.
thrown()
Méthode Spock qui affirme qu'une exception d'un type donné a été levée pendant le bloc when.
Test piloté par les données
Test rejoué sur chaque ligne d'une table where ; chaque ligne est un cas distinct (data-driven testing).
Mock
Doublure d'un collaborateur dont on vérifie les interactions (quelle méthode, combien de fois).
Stub
Doublure qui fournit des réponses prédéfinies (avec >>) sans vérifier les appels.

Récap et vérification

  • Une spec étend Specification ; chaque test est une méthode au nom parlant.
  • given / when / then = préparer, agir, vérifier ; les assertions sont implicites.
  • thrown() teste les exceptions ; where: rejoue le test sur une table de données.
  • Mock vérifie des interactions, Stub fournit des réponses fixes.

Vérifie ta compréhension

  1. Dans quel bloc écrit-on les vérifications d'un test Spock ?
  2. À quoi sert le bloc where ?
  3. Quelle est la différence entre un Mock et un Stub ?
