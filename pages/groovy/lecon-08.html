Gradle et Jenkins : Groovy au travail

~55 min Avancé Prérequis : leçon 7

À la fin de cette leçon, tu sauras

  • comprendre pourquoi Gradle utilise Groovy ;
  • lire un fichier build.gradle ;
  • écrire un pipeline Jenkins simple ;
  • voir les DSL Groovy en action.
Sommaire de la leçon

Pourquoi apprendre Groovy, concrètement ? Parce que tu le croiseras forcément si tu travailles sur la JVM : Gradle, l'outil de build de Java et d'Android, et Jenkins, le serveur d'intégration continue le plus répandu, utilisent tous deux Groovy comme langage de configuration. Cette leçon te montre Groovy « au travail » : comment lire un build.gradle et écrire un pipeline Jenkins. Tout ce qu'on a vu (closures, DSL, métaprogrammation) prend ici tout son sens.

Gradle : construire avec Groovy

Gradle automatise la compilation, les tests et le packaging d'un projet. Sa configuration s'écrit dans un fichier build.gradle… qui est un script Groovy. Ce que tu y vois n'est pas une syntaxe spéciale : c'est du Groovy, exploitant le DSL qu'on a découvert leçon 7.

Décryptons : plugins, repositories, dependencies sont des méthodes recevant chacune une closure. À l'intérieur, implementation '...' est un appel de méthode. La tâche bonjour contient une closure doLast exécutée à la fin. Tout est du Groovy : closures + méthodes + DSL.

Définir une tâche personnalisée

Une force de Gradle : comme la config est un vrai langage, on peut y écrire de la logique. Une tâche peut faire des calculs, lire des fichiers, appeler du code.

On retrouve l'interpolation (${...}), la navigation sûre (?.) et l'Elvis (?:) : les outils Groovy des leçons précédentes, directement utiles dans un build.

Astuce

Lance toujours le build avec le wrapper du projet : ./gradlew build (et gradlew.bat sous Windows), jamais le gradle installé globalement. Le wrapper est versionné avec le code et fige la version de Gradle attendue : chaque développeur — et le serveur d'intégration continue — utilise exactement la même, ce qui élimine les « ça marche chez moi » dus à des versions divergentes.

Jenkins : les pipelines en Groovy

Jenkins orchestre l'intégration et le déploiement continus (CI/CD). Les pipelines Jenkins se décrivent dans un fichier Jenkinsfile, lui aussi en Groovy (via un DSL dédié). On y définit les étapes de construction, test et livraison.

Là encore, pipeline, stages, stage, steps sont des méthodes recevant des closures. La structure imbriquée décrit le flux du pipeline. Comprendre Groovy te permet de lire et écrire ces fichiers que tout projet sérieux possède.

Le pipeline scripté

Jenkins propose aussi un mode « scripté », du Groovy plus libre où l'on peut utiliser des boucles, des conditions, des variables — toute la puissance du langage.

Ici, une closure each génère dynamiquement une étape par environnement. C'est tout l'intérêt d'un DSL fondé sur un vrai langage : on peut y mettre de la logique réelle, pas seulement de la configuration figée.

Cas réel

Avant le Jenkinsfile, la configuration d'un pipeline vivait dans l'interface web de Jenkins : on cliquait pour ajouter des étapes, réglages non versionnés, invisibles dans le dépôt et perdus si le serveur tombait. En déplaçant cette configuration dans un fichier Groovy commité avec le code, Jenkins a lancé le mouvement « pipeline as code » : le pipeline suit les branches, passe en revue de code, se restaure à l'identique et redevient reproductible. C'est aujourd'hui la norme dans toute l'industrie.

Pièges fréquents

Piège fréquent

Confondre les deux styles de pipeline Jenkins : le déclaratif (avec pipeline { }, structuré et limité) et le scripté (avec node { }, du Groovy libre). Le déclaratif est plus simple et recommandé pour la plupart des cas ; le scripté offre toute la puissance mais demande de bien connaître Groovy. Mettre du code scripté libre dans un bloc déclaratif (hors d'un script { }) provoque des erreurs. Sache lequel tu écris.

Pour aller plus loin

Pour aller plus loin

Gradle propose désormais une alternative en Kotlin (build.gradle.kts), qui apporte la complétion et la vérification de types d'un langage statique. Mais des millions de projets utilisent encore la syntaxe Groovy, plus concise et historiquement dominante. Savoir lire un build.gradle en Groovy reste indispensable : c'est l'un des fichiers que tu ouvriras le plus souvent dans la vie d'un projet JVM.

Antisèche : Gradle et Jenkins

Glossaire

Gradle
Outil de build de la JVM (et d'Android) dont la configuration est un script Groovy (ou Kotlin).
build.gradle
Fichier de configuration d'un projet Gradle : plugins, dépôts, dépendances et tâches, écrits en Groovy.
Tâche (task)
Unité de travail d'un build (compiler, tester, packager) ; déclarée avec tasks.register.
Gradle wrapper
Script gradlew versionné qui fige la version de Gradle utilisée par le projet.
Jenkins
Serveur d'intégration et de déploiement continus (CI/CD) très répandu sur la JVM.
Jenkinsfile
Fichier décrivant, en Groovy, le pipeline CI/CD d'un projet ; versionné avec le code.
Pipeline déclaratif
Style structuré (pipeline { }), à la structure fixe, lisible et recommandé par défaut.
Pipeline scripté
Style libre (node { }) donnant accès à toute la puissance de Groovy, plus flexible mais plus complexe.

Récap et vérification

  • Gradle : le build.gradle est un script Groovy (closures + DSL) ; dependencies { }, tâches…
  • On peut mettre de la logique Groovy dans un build (interpolation, ?., ?:).
  • Jenkins : le Jenkinsfile décrit un pipeline (stages, stage, steps) en Groovy.
  • Deux styles : pipeline déclaratif (structuré) ou scripté (Groovy libre).

Exercice 1Échauffement

Dans un build.gradle, qu'est-ce que dependencies { ... } du point de vue Groovy ?

Voir une solution

Un appel de méthode (dependencies) auquel on passe une closure (le bloc { ... }) comme dernier argument, sorti des parenthèses.

Exercice 3Défi

En quoi le fait que Gradle utilise un vrai langage (Groovy) est-il un avantage par rapport à un format figé (comme du XML) ?

Voir une solution

Parce qu'un vrai langage permet d'écrire de la logique dans le build : boucles, conditions, calculs, variables, appels de fonctions. On peut générer des tâches dynamiquement, adapter la configuration selon l'environnement, factoriser du code répétitif — toutes choses impossibles dans un format de données statique comme le XML (utilisé par l'ancien Maven), où l'on ne peut que décrire, sans programmer. Le DSL Groovy combine la lisibilité d'une configuration et la puissance d'un langage.
