Module 19 · Aux frontières de JavaScript — Leçon 59

La sécurité côté client

~36 min Avancé Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • savoir neutraliser le XSS par échappement contextuel, textContent, DOMPurify et Trusted Types ;
  • savoir durcir une CSP (nonce, hashes, suppression de l'inline) et comprendre le rôle de l'en-tête ;
  • savoir défendre un merge/parse contre la prototype pollution et auditer la chaîne de dépendances ;
  • savoir choisir le stockage des jetons et bannir eval/Function pour réduire la surface d'attaque.
Sommaire de la leçon

Tu maîtrises l'event loop, les Proxy et les flux async, mais une application front impeccablement architecturée reste exploitable si elle injecte du DOM sans précaution, expose ses jetons ou fait confiance à une dépendance compromise. La sécurité côté client n'est pas une couche que l'on ajoute : c'est un invariant que chaque écriture dans le DOM, chaque fetch et chaque import peut briser. Le modèle de menace est particulier : tout le code s'exécute chez l'attaquant potentiel, donc aucune vérification côté client n'est une garantie de sécurité, seulement une amélioration d'UX.

Cette leçon couvre les vecteurs concrets — XSS, prototype pollution, supply chain, eval, vol de jetons, clickjacking — avec le mauvais code, le bon code et la défense en profondeur qui survit à une erreur isolée.

XSS en profondeur et échappement contextuel

Le XSS se décline en trois familles : stocké (la charge persiste en base et est resservie à tous), réfléchi (la charge transite par l'URL et revient dans la réponse), et DOM-based (la charge ne touche jamais le serveur, elle naît d'un sink côté client comme innerHTML alimenté par location.hash). C'est cette troisième famille qui te concerne le plus en tant qu'expert front : elle vit entièrement dans ton JavaScript, hors de portée des protections serveur.

La règle fondamentale est que l'échappement dépend du contexte d'insertion. Une même donnée n'a pas le même échappement dans un corps HTML, dans un attribut, dans une URL ou dans un littéral JS : échapper pour le mauvais contexte ne protège pas, et peut même ouvrir une brèche.

Quand tu dois réellement insérer du HTML riche (un éditeur WYSIWYG, du Markdown rendu), l'échappement ne suffit plus : il faut sanitizer. N'écris jamais ton propre filtre par regex — la grammaire HTML est trop hostile (commentaires conditionnels, entités, mXSS par re-parsing). Utilise DOMPurify, maintenu et durci contre ces évasions.

Le cran au-dessus est Trusted Types : une API navigateur qui transforme les sinks dangereux (innerHTML, script.src…) en erreur de type sauf si on leur passe un objet produit par une policy explicite. Cela rend le XSS DOM-based structurellement impossible plutôt que de compter sur la discipline.

La CSP côté client

La Content-Security-Policy est une seconde ligne de défense : même si une injection passe, la CSP peut empêcher le code injecté de s'exécuter. Elle se transmet via un en-tête HTTP (préférable) ou une balise meta. Le levier décisif est de bloquer le inline : sans 'unsafe-inline', un onerror=... ou un <script>alert(1)</script> injecté ne tourne pas.

Pour des scripts statiques sans nonce, on autorise par hash ('sha256-...' du contenu exact). Nonce et hash sont les deux moyens propres de garder du contrôle fin sans réactiver 'unsafe-inline', qui annulerait la protection. Note d'ailleurs qu'un navigateur moderne ignore 'unsafe-inline' dès qu'un nonce ou un hash est présent : les deux ne coexistent pas, c'est un mécanisme de repli pour anciens agents.

Note

Un nonce DOIT être imprévisible et unique par réponse. Un nonce constant ou recyclé d'une page à l'autre est trivialement contournable : l'attaquant le lit dans le DOM et l'appose à son script injecté.

Prototype pollution

Cette vulnérabilité spécifique à JavaScript exploite le fait que la clé __proto__, dans un objet littéral parsé, désigne Object.prototype. Un merge récursif ou un parseur naïf de query-string qui copie une clé __proto__ pollue tous les objets du programme, ce qui mène à des contournements d'authentification, du déni de service, voire du RCE si une clé polluée alimente un template ou un child_process.

Les défenses complémentaires : utiliser une Map plutôt qu'un objet pour des clés issues de l'utilisateur (les clés n'interagissent pas avec le prototype), geler le prototype avec Object.freeze(Object.prototype) en amont, et valider la forme des entrées par un schéma (Zod, Ajv) avant tout traitement.

Sécurité de la chaîne de dépendances

Une application front moderne tire des centaines de paquets transitifs : chacun s'exécute avec tes privilèges. Les vecteurs supply chain sont le typosquatting (un paquet légitime cross-env contre un malveillant crossenv), la compromission d'un mainteneur, et l'injection dans une version mineure. Pour les ressources chargées depuis un CDN, l'attribut SRI (integrity) garantit que le fichier servi correspond bien au hash attendu : si le CDN est compromis et sert un script altéré, le navigateur refuse de l'exécuter.

Cas réel

En 2018, l'attaque Magecart contre British Airways a compromis un script tiers déjà chargé par le site : une vingtaine de lignes de JavaScript injectées ont copié, à la volée, les données de carte saisies dans le formulaire de paiement et les ont exfiltrées vers un domaine ressemblant. Environ 380 000 transactions ont fuité, avec à la clé une sanction retentissante de l'autorité britannique (ICO). Le vecteur n'était ni le serveur ni la base : du JavaScript côté client altéré. Les parades exactes de cette leçon l'auraient stoppé — SRI sur le script tiers (hash divergent => blocage), une CSP à connect-src restreint (exfiltration refusée) et la minimisation des scripts tiers sur les pages sensibles.

Astuce

La meilleure dépendance est celle que tu n'installes pas. Pour un besoin trivial (un leftpad, un debounce), écris quelques lignes : tu réduis la surface d'attaque, le poids du bundle et le risque de typosquatting d'un coup.

eval, Function et setTimeout(string)

eval, le constructeur Function et la forme setTimeout("code", ...) compilent une chaîne en code. Dès qu'une partie de cette chaîne dérive d'une entrée, tu as un XSS/RCE direct. Ils sont aussi non optimisables par le moteur et incompatibles avec une CSP stricte (qui requiert 'unsafe-eval' pour les autoriser — signal d'alarme à lui seul).

Jetons, CSRF/CORS et clickjacking

Le stockage des jetons est un arbitrage souvent mal tranché. localStorage est lisible par tout JavaScript de la page : un seul XSS et le JWT part en exfiltration. Un cookie HttpOnly est inaccessible au JS, donc immunisé contre le vol par XSS — au prix d'une exposition CSRF que l'on neutralise avec SameSite et un jeton anti-CSRF.

Côté CORS, rappelle-toi que c'est une politique de lecture cross-origin imposée par le navigateur, pas un contrôle d'accès : Access-Control-Allow-Origin: * sur une API authentifiée par cookie est une faute. Et n'utilise jamais credentials: 'include' avec un origin générique. Contre le clickjacking, le serveur doit envoyer X-Frame-Options: DENY ou la directive CSP frame-ancestors 'none' pour interdire l'iframe de ton app par un site piège.

Bonnes pratiques transversales

Deux principes dominent. Le moindre privilège : un token au scope minimal, une CSP qui n'autorise que les origines réellement utilisées, des appels postMessage avec targetOrigin explicite (jamais '*' pour des données sensibles). Et la validation côté serveur AUSSI : la validation client améliore l'UX mais n'a aucune valeur de sécurité, puisque l'attaquant contrôle entièrement le client.

Pièges fréquents

Piège fréquent

innerHTML avec une donnée utilisateur reste le XSS numéro un. Même « juste un nom », même « déjà validé au formulaire » : si la valeur peut transiter par une autre voie (API, import, ancien enregistrement), elle est non fiable. Réflexe : textContent par défaut, sanitization explicite sinon.

Piège fréquent

Se reposer sur la validation client seule, stocker un JWT en localStorage, faire un merge récursif non protégé, passer une entrée à eval ou installer une dépendance sans l'auditer : chacun, isolément, suffit à compromettre toute l'application. La défense en profondeur suppose qu'une couche tombera.

Pour aller plus loin

Pour aller plus loin

Approfondis avec DOMPurify et la Trusted Types API pour neutraliser le XSS DOM-based, la CSP stricte à nonce (et son mode report-only pour migrer sans casser), Snyk / npm audit pour la supply chain, le Subresource Integrity pour les CDN, et le référentiel OWASP (Top 10, cheat sheets XSS et prototype pollution) comme socle de revue.

Antisèche

Glossaire

XSS (Cross-Site Scripting)
Injection de code exécuté dans le navigateur d'une victime ; la variante DOM-based naît d'un sink côté client (innerHTML) sans passer par le serveur.
Sink
Point du code où une donnée devient active (parsée en HTML, exécutée) : innerHTML, eval, script.src… C'est là que le XSS se déclenche.
Sanitization
Nettoyage d'un HTML non fiable en ne gardant que des balises et attributs autorisés, via une bibliothèque durcie comme DOMPurify — jamais une regex maison.
Trusted Types
API navigateur qui transforme les sinks dangereux en erreur de type, sauf si la valeur provient d'une policy explicite : rend le XSS DOM-based structurellement impossible.
CSP (Content-Security-Policy)
En-tête qui restreint les sources autorisées (scripts, styles, connexions). Bien réglée (sans 'unsafe-inline'), elle empêche un script injecté de s'exécuter.
Nonce
Jeton aléatoire, unique par réponse, apposé sur les scripts légitimes (nonce-…) ; un script injecté ne peut pas le deviner, donc la CSP le refuse.
Prototype pollution
Vulnérabilité JS où l'écriture d'une clé __proto__ lors d'un merge ou d'un parse contamine Object.prototype, donc tous les objets du programme.
SRI (Subresource Integrity)
Attribut integrity contenant le hash attendu d'une ressource externe ; si le CDN sert un fichier altéré, le navigateur refuse de l'exécuter.

Récap et vérification

  • Le XSS DOM-based naît d'un sink (innerHTML, eval) : privilégie textContent, échappe selon le contexte, sanitize avec DOMPurify, verrouille avec Trusted Types.
  • La CSP est une défense en profondeur : bloque l'inline, autorise par nonce (unique par réponse) ou par hash, jamais 'unsafe-inline'/'unsafe-eval'.
  • La prototype pollution se défend par filtrage de __proto__/constructor, Object.create(null), Map et validation par schéma.
  • La supply chain se maîtrise par npm audit en CI, SRI sur les CDN, vigilance au typosquatting et minimisation des dépendances.
  • eval/Function/setTimeout(string) sont bannis ; le JWT va dans un cookie HttpOnly; Secure; SameSite, pas dans localStorage.

Vérifie ta compréhension

  1. Pourquoi un même fragment de donnée exige-t-il un échappement différent en corps HTML, en attribut et en URL ? Donne le bon outil pour chacun.
  2. En quoi un cookie HttpOnly protège-t-il un jeton contre le XSS là où localStorage échoue ? Quel risque réintroduit-il et comment le couvrir ?
  3. Pourquoi 'unsafe-inline' dans script-src annule-t-il l'essentiel de la valeur d'une CSP, et que mettre à la place ?
