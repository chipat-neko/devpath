Module 12 · JavaScript en pratique pro — Leçon 37

Outils, qualité et déploiement d'un projet

~30 min Intermédiaire Leçon 36 recommandée

À la fin de cette leçon, tu sauras

  • Savoir structurer un package.json propre : scripts, dependencies vs devDependencies et lockfile ;
  • Savoir builder avec un bundler (Vite/esbuild) et garantir la qualité avec ESLint, Prettier et un hook pre-commit ;
  • Savoir écrire et lancer un test unitaire avec Vitest sur une fonction pure ;
  • Savoir déployer un site statique avec build, variables d'environnement et CI/CD GitHub Actions.
Sommaire de la leçon

Jusqu'ici tu as écrit du code qui marche. Maintenant on attaque le reste du métier : transformer un dossier de fichiers en projet outillé, reproductible, testé et déployable. C'est ce qui sépare un script bricolé d'un vrai produit front. Bonne nouvelle : même sans framework, tu peux brancher exactement la même chaîne d'outils que les équipes pro.

On va monter la chaîne complète : npm pour les dépendances et les scripts, un bundler pour assembler et optimiser, ESLint/Prettier pour la qualité, Vitest pour les tests, les DevTools pour déboguer, puis le déploiement statique avec sa CI/CD. Chaque brique est indépendante : tu peux en adopter une seule aujourd'hui et compléter plus tard.

npm et package.json : le cœur du projet

Le fichier package.json décrit ton projet : son nom, ses scripts, ses dépendances. npm install lit ce fichier, télécharge les paquets dans node_modules/ et écrit un package-lock.json qui fige les versions exactes de tout l'arbre. Ce lockfile rend tes installations reproductibles : sans lui, deux machines peuvent récupérer des versions différentes et « ça marche chez moi » devient ton quotidien.

Distingue bien dependencies (ce dont le code a besoin à l'exécution) et devDependencies (les outils de build, lint et test, inutiles en production). Le versioning suit le SemVer : MAJEUR.MINEUR.CORRECTIF. Le préfixe ^ autorise les montées mineures et correctifs (^1.4.2 accepte 1.5.0 mais pas 2.0.0).

Un package.json typique : les scripts deviennent npm run dev, npm run build, etc.

Note

Commite toujours package.json et package-lock.json, jamais node_modules/. Sur un serveur, npm ci (au lieu de npm install) installe strictement ce que dit le lockfile : c'est la commande des builds reproductibles.

Les bundlers : assembler et optimiser

Ton code est éclaté en dizaines de modules import/export. Un bundler les résout, les regroupe et optimise le résultat pour le navigateur. Aujourd'hui le standard est Vite (qui s'appuie sur esbuild et Rollup). En développement, il sert tes modules natifs avec un rechargement à chaud quasi instantané ; en production, vite build produit un dossier dist/ minifié et découpé.

Deux optimisations clés s'appliquent au build : le tree-shaking élimine le code exporté mais jamais importé, et le minify supprime espaces, commentaires et raccourcit les noms internes. Résultat : un bundle bien plus léger à télécharger.

De zéro à un serveur de dev en quatre commandes.

Le tree-shaking ne fonctionne qu'avec des modules ES statiques (import/export en haut de fichier).

La qualité : ESLint et Prettier

Deux outils complémentaires, à ne pas confondre. ESLint est un linter : il détecte les bugs probables et les mauvaises pratiques (variable inutilisée, == au lieu de ===, promesse non attendue). Prettier est un formateur : il n'a pas d'opinion sur la logique, il réécrit la mise en forme (indentation, guillemets, points-virgules) de façon uniforme. La règle d'or : ESLint pour la correction, Prettier pour le style.

Une règle "error" fait échouer npm run lint ; "warn" affiche juste un avertissement.

Pour que personne n'oublie de lancer ces outils, on les branche sur un pre-commit hook avec husky : avant chaque git commit, le code est automatiquement linté et formaté. Un commit qui casse le lint est refusé.

Désormais chaque commit passe par le linter avant d'être accepté.

Les tests automatisés avec Vitest

Tu connais déjà le principe des tests vu en débogage ; ici on l'applique à l'outillage projet. Vitest est le testeur naturel d'un projet Vite (API quasi identique à Jest, mais plus rapide et configuré d'emblée pour les modules ES). Les fonctions pures — même entrée, même sortie, aucun effet de bord — sont les plus simples et les plus rentables à tester.

Un test = une assertion claire. Couvre le cas normal ET les cas limites (panier vide).

Astuce

Pendant le dev, vitest (sans run) reste en mode watch et relance uniquement les tests touchés à chaque sauvegarde. En CI, on utilise vitest run pour qu'il s'exécute une fois et rende un code de sortie exploitable.

Le débogage pro avec les DevTools

Le console.log dépanne, mais les DevTools du navigateur vont beaucoup plus loin. L'onglet Sources permet de poser des breakpoints : l'exécution s'arrête sur la ligne choisie et tu inspectes la valeur de chaque variable, la pile d'appels, et avances pas à pas. C'est radicalement plus efficace que de semer des logs.

L'onglet Network montre chaque requête (statut, durée, charge utile) — indispensable pour déboguer un appel d'API. L'onglet Performance enregistre un profil pour repérer ce qui rame. Et comme ton code livré est minifié, les source maps (générées par défaut par Vite) font le pont : les DevTools t'affichent ton code source original, pas le bundle illisible.

Le mot-clé debugger agit comme un breakpoint posé directement dans le code (à retirer avant de livrer).

Déployer un site statique

Un site front sans backend est dit statique : après le build, tu n'as qu'un dossier dist/ de HTML, CSS et JS à servir. Des hébergeurs comme Netlify, Vercel ou GitHub Pages font ça gratuitement et se connectent à ton dépôt Git : à chaque git push, ils relancent le build et publient. C'est la base du CI/CD (intégration et déploiement continus).

Cas réel

Sur un vrai projet hébergé chez Netlify ou Vercel, tu ne « déploies » plus jamais à la main : tu ouvres une pull request, l'hébergeur build tout seul une URL de prévisualisation pour la relire, puis un merge sur main publie en production en quelques secondes. C'est exactement la chaîne de cette leçon (build + CI/CD) branchée sur Git — le quotidien des équipes front modernes.

Les variables d'environnement gèrent ce qui change entre dev et production (URL d'API, clé publique). Avec Vite, seules les variables préfixées par VITE_ sont exposées au navigateur, ce qui évite de fuiter un secret par mégarde. Et un secret vraiment sensible n'a rien à faire dans un front : il vit côté serveur.

Le préfixe VITE_ est volontaire : il rend explicite ce qui finit dans le bundle public.

Un workflow GitHub Actions qui valide chaque push avant déploiement : install, lint, test, build.

Les bonnes pratiques finales

Avant de livrer, trois axes à surveiller. Accessibilité : HTML sémantique, attributs alt, navigation au clavier, contrastes suffisants. Performance : l'outil Lighthouse (intégré aux DevTools) note ton site sur la performance, l'accessibilité, le SEO et les bonnes pratiques, avec des pistes concrètes. Sécurité : jamais de secret dans le front, valide toujours les données côté serveur, et utilise HTTPS (automatique chez ces hébergeurs).

Note

Lighthouse mesure aussi les Core Web Vitals (LCP, INP, CLS), les métriques que Google utilise pour le référencement. Vise du vert sur les quatre catégories avant un déploiement public.

Pièges fréquents

Piège fréquent

Committer node_modules/ ou un fichier .env rempli de secrets. Crée un .gitignore dès le premier commit avec au minimum node_modules/, dist/ et .env. Un secret poussé sur Git doit être considéré comme compromis, même après suppression.

Autres erreurs classiques : oublier le lockfile (builds non reproductibles, bugs « fantômes » en prod) ; ignorer les avertissements du linter jusqu'à ce qu'ils deviennent des bugs ; ne pas tester ses fonctions de calcul ; déployer le code source non buildé (lourd, lent, non minifié). Et la plus courante : ranger Vite ou ESLint dans dependencies au lieu de devDependencies — ces outils n'ont rien à faire dans le bundle livré.

Glossaire

npm
Gestionnaire de paquets de l'écosystème JavaScript : installe les dépendances et lance les scripts déclarés dans package.json.
package.json
Fichier manifeste du projet : nom, version, scripts, dependencies et devDependencies.
Lockfile
package-lock.json : fige les versions exactes de tout l'arbre de dépendances pour des installations reproductibles (npm ci).
dependencies / devDependencies
Les premières sont nécessaires à l'exécution en production ; les secondes ne servent qu'au développement (build, lint, test) et ne partent pas dans le bundle.
SemVer
Versionnage MAJEUR.MINEUR.CORRECTIF. Le préfixe ^ autorise les montées mineures et correctifs compatibles.
Bundler
Outil (Vite, esbuild, Rollup) qui résout les import/export, regroupe les modules et optimise le résultat pour le navigateur.
Tree-shaking
Élimination, au build, du code exporté mais jamais importé ; ne fonctionne qu'avec des modules ES statiques.
CI/CD
Intégration et déploiement continus : à chaque push, un pipeline (ex. GitHub Actions) installe, lint, teste, build et déploie automatiquement.

Récap et vérification

  • npm : package.json décrit scripts et dépendances ; le lockfile rend les installs reproductibles ; sépare dependencies et devDependencies.
  • Bundler (Vite) : serveur de dev rapide, build minifié avec tree-shaking.
  • Qualité : ESLint corrige la logique, Prettier formate, husky branche tout sur le pre-commit.
  • Tests : Vitest teste les fonctions pures ; vitest run en CI.
  • Déploiement : build statique vers Netlify/Vercel/Pages, variables VITE_, pipeline GitHub Actions.
