Module 14 · Le langage en profondeur — Leçon 43

Symboles et propriétés cachées

~35 min Avancé Cours JavaScript confirmé requis

À la fin de cette leçon, tu sauras

  • Savoir créer des symboles et les utiliser comme clés de propriété garanties sans collision ;
  • Savoir lire et manipuler les propriétés cachées avec Object.getOwnPropertySymbols et Reflect.ownKeys ;
  • Savoir personnaliser le comportement du langage via les symboles bien connus (Symbol.iterator, Symbol.toPrimitive) ;
  • Savoir distinguer registre global et symboles locaux, et reconnaître les limites des symboles face aux vrais champs privés.
Sommaire de la leçon

Tu manipules déjà des objets comme des tables clé/valeur où les clés sont des chaînes. Jusqu'ici, deux modules qui ajoutent une propriété id au même objet entrent en collision silencieuse : le second écrase le premier. Le type primitif Symbol, introduit avec ES2015, résout ce problème à la racine en fournissant des clés uniques par construction — et, plus profondément, il sert de point d'extension officiel du langage : c'est par des symboles que tu branches ton objet sur for...of, sur la coercition de type ou sur instanceof.

Cette leçon part de ton acquis sur les objets, les itérables et les classes pour aller jusqu'aux well-known symbols : tu vas voir comment fabriquer des protocoles personnalisés et comprendre pourquoi les bibliothèques exposent (et cachent) des clés internes via des symboles.

Créer un symbole : une valeur unique

Un symbole se crée avec la fonction Symbol(), qui n'est pas un constructeur — new Symbol() lève une TypeError. La description passée en argument est purement documentaire : elle n'a aucune incidence sur l'identité.

Chaque appel à Symbol() produit une valeur neuve, même avec une description identique.

C'est cette unicité qui fait toute la valeur : un symbole ne peut entrer en collision avec aucune autre clé, pas même un autre symbole de même description. Tu obtiens une clé privée par construction, sans convention de nommage fragile du type _internalId.

Le symbole comme clé : la propriété cachée

Utilise un symbole entre crochets pour indexer un objet. La propriété existe bel et bien, mais elle est invisible pour les mécanismes qui itèrent sur les clés de type chaîne.

Les clés symboles sont ignorées par Object.keys, for...in et JSON.stringify.

Note

« Caché » signifie ici « non énuméré par les API qui ciblent les chaînes », pas « inaccessible ». La métadonnée attachée par symbole reste lisible par quiconque détient le symbole — ou appelle Object.getOwnPropertySymbols.

Le registre global : Symbol.for

Un symbole créé par Symbol() est local : deux fichiers qui appellent Symbol("id") obtiennent deux valeurs incompatibles. Quand tu veux au contraire partager le même symbole à travers tout le programme (voire entre realms comme un iframe), passe par le registre global avec Symbol.for.

Symbol.for mémoïse par chaîne ; Symbol.keyFor fait le chemin inverse, mais seulement pour les symboles enregistrés.

Astuce

Préfixe tes clés de registre par un espace de noms ("app.session" plutôt que "session"). Le registre est global au processus : sans préfixe, deux bibliothèques peuvent se voler la même entrée.

Cas réel

React s'appuie sur ce registre pour sa sécurité. Chaque élément JSX porte une propriété $$typeof égale à Symbol.for("react.element"). Comme un symbole ne survit pas à JSON.stringify/JSON.parse, un objet reçu d'une API ne peut pas se faire passer pour un élément React : sa clé $$typeof ne serait qu'une simple chaîne, jamais le vrai symbole. C'est une barrière contre une famille d'injections (XSS) — et une raison concrète de préférer Symbol.for à une chaîne magique.

Les symboles bien connus

Le langage expose une poignée de symboles prédéfinis sur l'objet Symbol — les well-known symbols. Ils servent de points d'accroche : en définissant une méthode ou une propriété sous l'une de ces clés, tu reconfigures un comportement interne du moteur.

  • Symbol.iterator : rend un objet utilisable avec for...of et le spread.
  • Symbol.asyncIterator : équivalent pour for await...of.
  • Symbol.toPrimitive : contrôle la conversion vers nombre, chaîne ou défaut.
  • Symbol.toStringTag : personnalise la sortie de Object.prototype.toString.
  • Symbol.hasInstance : redéfinit le résultat de instanceof.

Symbol.toStringTag remplace le générique [object Object] par une étiquette parlante.

Rendre un objet itérable

Le protocole d'itération repose entièrement sur Symbol.iterator : une fonction qui retourne un itérateur (objet doté d'une méthode next() renvoyant { value, done }). Le plus simple est de la déclarer comme générateur — le moteur fournit alors l'itérateur pour toi.

Définir [Symbol.iterator] branche d'un coup for...of, le spread et Array.from.

Note la portée : tu n'as rien réimplémenté de la boucle ni du spread. Tu as fourni le contrat que ces constructions interrogent. C'est exactement ainsi que Map, Set et NodeList deviennent itérables.

Contrôler la coercition avec Symbol.toPrimitive

Quand un objet est utilisé dans un contexte attendant une primitive (arithmétique, concaténation, gabarit), le moteur appelle [Symbol.toPrimitive] avec un hint — "number", "string" ou "default". Tu pilotes ainsi finement chaque conversion.

Un seul point d'entrée gère les trois contextes de conversion, sans valueOf ni toString séparés.

Note

Attention à ne pas confondre les deux + : le + unaire (+t) envoie le hint "number", alors que le + binaire (t + " dehors") et la comparaison lâche envoient "default". Le hint "default" ne signifie pas « number » : il laisse l'objet décider (pour Date, il se comporte comme "string"). Si [Symbol.toPrimitive] existe, il a la priorité absolue sur valueOf et toString.

Pièges fréquents

Piège fréquent

Aucune coercition implicite vers une chaîne. sym + "" et `${sym}` lèvent une TypeError. Pour afficher un symbole, sois explicite : String(sym) (donne "Symbol(id)") ou sym.description (donne juste "id").

Deux autres écueils : les symboles disparaissent en JSON — ni les clés ni les valeurs symboles ne sont sérialisées, donc ne stocke jamais d'état que tu dois persister sous une clé symbole. Et surtout, ce ne sont pas de vraies propriétés privées : Object.getOwnPropertySymbols et Reflect.ownKeys les exposent à qui veut. Pour de l'encapsulation réelle, utilise les champs privés de classe #champ, qui sont inaccessibles depuis l'extérieur.

Un symbole organise sans masquer ; #champ masque réellement.

Pour aller plus loin

Pour aller plus loin

Pour parcourir toutes les clés propres d'un objet — chaînes et symboles — utilise Reflect.ownKeys(obj), le seul appel qui les renvoie ensemble. Explore aussi comment les bibliothèques définissent des protocoles maison : elles exportent un symbole partagé via Symbol.for et un objet « répond » au protocole en implémentant une méthode sous cette clé, exactement comme le langage le fait avec Symbol.iterator. C'est le mécanisme derrière des clés internes (états React, marqueurs RxJS) invisibles à l'inspection ordinaire.

Antisèche : manipuler les symboles

Glossaire

Symbole (Symbol)
Type primitif dont chaque valeur est unique par construction ; sert de clé de propriété sans risque de collision.
Description
Étiquette facultative passée à Symbol("…"), purement documentaire (lisible via .description ou String(sym)) et sans effet sur l'identité.
Registre global
Table interne indexée par chaîne qu'utilise Symbol.for pour partager un même symbole dans tout le programme (et entre realms).
Propriété cachée
Propriété indexée par un symbole : absente de Object.keys, for…in et JSON, mais lisible par qui détient le symbole.
Symbole bien connu
Symbole prédéfini sur Symbol (iterator, toPrimitive, toStringTag, hasInstance…) servant de point d'accroche pour reconfigurer le langage.
Symbol.iterator
Clé bien connue dont la méthode renvoie un itérateur ; sa présence rend un objet utilisable avec for…of, le spread et Array.from.
Coercition (Symbol.toPrimitive)
Conversion d'un objet en primitive ; la méthode reçoit un hint (number, string ou default) et prime sur valueOf/toString.
Reflect.ownKeys
Seule API renvoyant d'un coup toutes les clés propres d'un objet, chaînes et symboles réunis.

Récap et vérification

  • Symbol() produit une primitive unique ; deux symboles homonymes ne sont jamais égaux.
  • Une clé symbole est ignorée par Object.keys, for...in et JSON.stringify, mais lisible via Object.getOwnPropertySymbols ou Reflect.ownKeys.
  • Symbol.for/Symbol.keyFor partagent un symbole par le registre global ; Symbol() reste local.
  • Les symboles bien connus (iterator, toPrimitive, toStringTag, hasInstance) personnalisent le comportement du langage.
  • Pas de coercition implicite ; pas de sérialisation JSON ; pas d'encapsulation réelle — pour ça, #champ.
