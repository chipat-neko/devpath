Projet de synthèse : un store réactif

~38 min Avancé Leçon 22 recommandée

À la fin de cette leçon, tu sauras

  • assembler les primitives du cours — Proxy, EventTarget, structuredClone, gestion d'erreurs, modules — en un composant réel ;
  • construire un cœur réactif qui ne notifie que sur un vrai changement ;
  • isoler les abonnés pour qu'une erreur de l'un n'empêche pas les autres de recevoir ;
  • exposer des instantanés immuables et empaqueter le tout en module réutilisable.
Sommaire de la leçon

Vingt-deux leçons durant, tu as isolé des primitives : Proxy et Reflect, les générateurs, la boucle d'événements, les WeakRef, EventTarget, structuredClone, la gestion fine des erreurs, les modules ES. Prises séparément, ce sont des outils. Assemblées, elles forment une bibliothèque. Ce capstone construit un store réactif : un objet qui détient un état, notifie automatiquement ses abonnés à chaque changement, et le fait de façon robuste. C'est précisément le cœur de Redux, Zustand, Pinia ou de la réactivité de Vue — que tu vas comprendre de l'intérieur en le réécrivant.

L'idée : assembler, pas empiler

Un bon composant ne juxtapose pas des fonctionnalités : il fait collaborer quelques briques bien choisies. Notre store en mobilise cinq, chacune vue dans une leçon précédente. Le Proxy rend l'état réactif, EventTarget gère les abonnements, structuredClone protège les lectures, un try/catch isole les pannes, et un module ES rend le tout réutilisable.

Le cœur réactif : un Proxy qui notifie

Le principe : envelopper l'état dans un Proxy dont le piège set écrit la valeur puis notifie. Un raffinement crucial par rapport à la version naïve : ne notifier que si la valeur a réellement changé. Réaffecter la même valeur ne doit déclencher aucun re-rendu — c'est ce qui évite les mises à jour inutiles et les boucles.

Astuce

La garde if (cible[cle] === valeur) return true; est ce qui sépare un jouet d'un vrai store. Sans elle, chaque affectation notifie ; avec elle, seules les transitions comptent. Les bibliothèques réelles poussent l'idée plus loin (comparaison structurelle, lots de changements), mais l'égalité de référence suffit dans l'immense majorité des cas.

Notifier sans se saborder : isoler les abonnés

Plusieurs abonnés peuvent réagir au même changement : mettre à jour l'UI, journaliser, persister. Le danger : si l'un lève une erreur, il ne doit pas empêcher les suivants de recevoir la notification, ni faire remonter l'erreur dans le code qui a modifié l'état. On enveloppe chaque abonné dans un try/catch (leçon 21) et on journalise sans propager.

Deux détails de conception professionnels apparaissent ici. abonner renvoie une fonction de désabonnement (le même patron que AbortController), ce qui évite les fuites mémoire de la leçon dédiée. Et snapshot() renvoie une copie figée via structuredClone : un abonné peut la garder, la comparer, la sérialiser, sans risquer de muter l'état réel par mégarde.

Le résultat, à l'usage

Cas réel

Ce que tu viens d'écrire est l'ADN des vraies bibliothèques d'état. Zustand expose un store minimaliste avec getState/setState/subscribe — exactement notre trio. Redux ajoute l'immuabilité stricte et un reducer pur, mais garde le patron subscribe. Et la réactivité de Vue 3 repose littéralement sur un Proxy qui intercepte lectures et écritures pour savoir quels composants re-rendre. En comprenant ce capstone, tu ne « subis » plus ces outils : tu sais ce qu'ils font sous le capot, et tu peux en écrire un en cinquante lignes quand une dépendance serait de trop.

Aller vers la version robuste

Piège fréquent

La version naïve (un Set d'abonnés notifiés sans garde) fonctionne… jusqu'au premier abonné qui plante, ou à la première réaffectation en boucle. Trois oublis classiques : notifier sans vérifier le changement (re-rendus en cascade), ne pas isoler les abonnés (une erreur casse la chaîne), et exposer l'état vivant (des mutations « fantômes » impossibles à tracer). Le passage à la version robuste tient en trois gardes.

Pour aller plus loin

Enrichis le store : des abonnements par clé (ne notifier que les abonnés d'une propriété donnée), un middleware (journalisation, temps de trajet) façon Redux, la persistance automatique dans localStorage (avec l'événement storage pour la synchro multi-onglets de la leçon 22), un Proxy récursif pour la réactivité profonde (objets imbriqués), ou des sélecteurs mémoïsés (WeakMap) pour ne recalculer que le nécessaire. Chaque ajout mobilise une brique déjà vue.

Antisèche

Glossaire

Store
Objet qui détient un état applicatif partagé et notifie ses abonnés à chaque changement ; base des bibliothèques d'état (Redux, Zustand, Pinia).
Réactivité
Propriété d'un état qui déclenche automatiquement des effets (re-rendu, journalisation) quand il change, sans appel manuel ; obtenue ici via un Proxy.
Piège set (trap)
Fonction du Proxy qui intercepte les écritures ; elle applique le changement, notifie, et doit renvoyer true.
Abonné (subscriber)
Fonction enregistrée pour réagir aux changements ; on l'appelle dans un try/catch pour qu'une erreur reste isolée.
Désabonnement
Fonction renvoyée par abonner() qui retire l'écouteur (removeEventListener) ; évite les fuites mémoire.
Instantané (snapshot)
Copie profonde et figée de l'état à un instant donné, produite par structuredClone ; sûre à lire, comparer ou sérialiser.
Immuabilité
Garantie qu'une valeur ne sera pas modifiée ; l'instantané protège l'état vivant des mutations externes accidentelles.
Module ES
Unité de code avec export/import ; empaquette le store pour le réutiliser proprement dans plusieurs fichiers.

Récap et vérification

  • Un store réactif = un Proxy (réactivité) + EventTarget (abonnements) + structuredClone (instantanés) + try/catch (isolation) + un module ES.
  • Le piège set ne notifie qu'en cas de vrai changement pour éviter les re-rendus inutiles.
  • Chaque abonné est appelé dans un try/catch : une panne est contenue, la chaîne continue.
  • snapshot() renvoie une copie immuable ; abonner() renvoie une fonction de désabonnement.
  • Ce patron est celui de Redux, Zustand et de la réactivité de Vue : tu sais désormais l'écrire toi-même.

Vérifie ta compréhension

  1. Pourquoi le piège set vérifie-t-il l'égalité avant de notifier ? Que se passe-t-il sans cette garde ?
  2. Pourquoi appeler chaque abonné dans un try/catch plutôt que dans une simple boucle ?
  3. Quel intérêt de renvoyer un structuredClone de l'état plutôt que l'état lui-même ?

Mini-projet fil rouge — un store réactif

Pour clore ce cours, (re)construisons la graine du store, dans sa version minimale. Elle réunit les clôtures, un Set d'abonnés, un Proxy avec piège set, les fonctions d'ordre supérieur et le patron observateur — un condensé de JavaScript avancé, et le point de départ de la version robuste vue plus haut.

Ce que tu vas construire

Un store qui notifie automatiquement ses abonnés à chaque modification de l'état, grâce à un Proxy qui intercepte les écritures.

Étapes

Les abonnés

Dans une clôture, garde un Set de fonctions abonnées.

Le Proxy

Enveloppe l'état dans un Proxy dont le piège set écrit la valeur puis notifie.

Notifier

Dans le piège, parcours les abonnés et appelle chacun avec le nouvel état.

L'interface

Renvoie un objet exposant etat et une méthode abonner(fn).

Utiliser

Abonne-toi, puis modifie store.etat.compteur et observe les notifications.

ProjetFil rouge

Assemble les étapes en un programme complet. Essaie d'abord par toi-même, puis compare avec la solution de référence.
