La gestion professionnelle des erreurs

~36 min Avancé Leçon 20 recommandée

À la fin de cette leçon, tu sauras

  • concevoir des erreurs personnalisées typées avec un code et un contexte métier ;
  • chaîner les erreurs avec l'option { cause } sans perdre l'origine ;
  • distinguer les erreurs synchrones des rejets de promesse et poser des filets globaux ;
  • choisir entre exception et pattern Result selon la nature de l'échec.
Sommaire de la leçon

Le code qui « marche » gère le chemin heureux. Le code professionnel gère l'échec : réseau qui tombe, JSON malformé, quota dépassé, entrée invalide. Un try { … } catch (e) {} vide n'est pas de la gestion d'erreur — c'est de la dissimulation, et c'est la source numéro un des bugs impossibles à diagnostiquer en production. Cette leçon traite l'erreur comme une donnée de première classe : on la type, on l'enrichit, on la propage avec son origine, et on décide en connaissance de cause de la rattraper ou de la laisser remonter.

La hiérarchie Error et les erreurs personnalisées

Tout ce qu'on lance devrait dériver de Error : on hérite ainsi de message, name et surtout de la pile d'appels (stack) capturée à la construction. Lancer une chaîne ou un objet nu (throw 'oops') prive du diagnostic. Le langage fournit des sous-types (TypeError, RangeError, SyntaxError…) ; pour le métier, on crée les siens.

Une erreur typée se filtre proprement dans le catch : on réagit différemment selon instanceof ou selon un code, au lieu de faire du pattern matching fragile sur le texte du message.

Chaîner les erreurs avec cause

Quand tu attrapes une erreur bas niveau pour en lancer une plus parlante, ne jette pas l'originale : passe-la via l'option { cause }. Tu obtiens une erreur métier lisible sans perdre la trace technique qui explique la vraie racine.

Astuce

Prends le réflexe { cause: e } à chaque fois que tu relances depuis un catch. Cela crée une chaîne d'erreurs que les logs, les débogueurs et les outils de suivi savent dérouler : tu ne choisis plus entre « message clair » et « trace utile », tu as les deux.

Plusieurs erreurs d'un coup : AggregateError

Quand plusieurs opérations parallèles peuvent échouer et que tu veux toutes les erreurs (pas seulement la première), AggregateError les regroupe. C'est ce que renvoie Promise.any() quand toutes les promesses rejettent, et c'est utile pour agréger des échecs de validation.

Synchrone vs asynchrone : le piège du try/catch

Un try/catch classique n'attrape que les erreurs synchrones lancées dans son bloc. Une promesse qui rejette plus tard lui échappe : il faut soit await la promesse dans le try, soit un .catch(). Confondre les deux laisse passer des rejets silencieux.

Comme filet de sécurité — jamais comme stratégie principale — pose des gestionnaires globaux. Ils rattrapent ce qui a échappé à tout catch local et sont l'endroit idéal pour journaliser vers un service de suivi.

Note

Depuis Node 15, un rejet de promesse non géré termine le process par défaut (unhandledRejection fatal). Ce n'est pas une punition : un état incohérent silencieux est plus dangereux qu'un arrêt franc. La bonne réponse est de gérer les rejets, pas de masquer le symptôme.

Exception ou Result ? Choisir sa stratégie

Les exceptions conviennent à l'exceptionnel : elles remontent la pile jusqu'au premier catch, ce qui traverse plusieurs niveaux sans code intermédiaire. Mais pour un échec attendu et fréquent (validation, parsing d'entrée utilisateur), le pattern Result — renvoyer { ok, value | error } — rend l'échec visible dans le type de retour : impossible de l'oublier, car il n'y a pas de valeur tant qu'on n'a pas vérifié ok.

Pièges fréquents

Piège fréquent

Le catch (e) {} vide (ou réduit à un console.log) avale l'erreur : le programme continue dans un état incohérent, et le bug ressurgit dix étapes plus loin, indéboguable. Si tu attrapes, tu dois agir : réparer, dégrader proprement, ou relancer (avec cause).

Attention

Attraper trop large masque les vrais bugs. Un catch qui traite un TypeError (souvent une faute de programmation) comme une erreur métier va « réussir » sur du code cassé. Filtre par type et relance ce que tu ne sais pas traiter (else throw e).

Pour aller plus loin

Pour aller plus loin

Explore Error.captureStackTrace (Node) pour nettoyer la pile, la remontée d'erreurs vers Sentry avec tags et fingerprint, les error boundaries React (componentDidCatch) qui isolent une panne d'UI, les stratégies de retry avec backoff exponentiel, et la proposition de type system pour les erreurs (TypeScript n'a pas de throws vérifié — d'où l'intérêt du pattern Result typé).

Cas réel

Depuis Node.js 15 (2020), une promesse rejetée sans catch ne se contente plus d'un avertissement : elle termine le processus (unhandledRejection fatal par défaut). Des applications qui « marchaient » en avalant silencieusement leurs rejets se sont mises à planter après la montée de version — un rappel que gérer ses erreurs de façon explicite n'est pas optionnel en production.

Glossaire

Error
Type de base des erreurs ; fournit message, name et la pile d'appels (stack). Tout ce qu'on lance devrait en dériver.
Pile d'appels (stack trace)
Chaîne des appels capturée à la création de l'erreur ; indique où le problème est survenu. Perdue si l'on lance une valeur non-Error.
Erreur personnalisée
Sous-classe de Error (class XError extends Error) portant un name, un code et des données métier, filtrable par instanceof.
cause
Option new Error(msg, { cause }) qui rattache l'erreur d'origine à une erreur enveloppante ; préserve la racine technique dans la chaîne.
AggregateError
Erreur qui regroupe plusieurs erreurs (.errors) ; renvoyée par Promise.any() quand tout rejette, ou pour agréger des validations.
Rejet non géré (unhandled rejection)
Promesse rejetée sans .catch() ni await attrapé ; déclenche unhandledrejection et, en Node moderne, termine le process.
Frontière d'erreur (error boundary)
Périmètre qui isole une panne pour éviter qu'elle ne fasse tomber toute l'application (ex. un composant de secours en UI).
Pattern Result
Renvoyer { ok, value | error } au lieu de lancer ; rend l'échec explicite dans le type de retour, idéal pour les erreurs attendues.

Récap et vérification

  • Lance toujours des sous-types de Error (jamais une chaîne) : tu gardes stack, name et un filtrage par instanceof.
  • Relance depuis un catch avec { cause: e } pour garder l'origine ; regroupe plusieurs échecs avec AggregateError.
  • Un try/catch n'attrape le rejet d'une promesse que si tu l'await ; sans quoi c'est un rejet non géré.
  • Pose des gestionnaires globaux (error, unhandledrejection) comme filet et point de journalisation, jamais comme stratégie unique.
  • Exception pour l'imprévu, pattern Result pour l'échec attendu ; ne jamais avaler une erreur.

Vérifie ta compréhension

  1. Pourquoi vaut-il mieux throw new Error(...) qu'un throw 'message' ? Que perd-on avec la chaîne ?
  2. À quoi sert l'option { cause } et qu'apporte-t-elle au diagnostic ?
  3. Pourquoi un try/catch autour d'un fetch() sans await ne rattrape-t-il rien ?
