Web Workers et parallélisme

~30 min Avancé Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • savoir déléguer un calcul CPU lourd à un Web Worker via postMessage et onmessage ;
  • savoir distinguer la copie (structured clone) du transfert d'un ArrayBuffer sans copie ;
  • savoir partager de la mémoire avec SharedArrayBuffer et synchroniser les threads avec Atomics ;
  • savoir construire un pool de workers pour paralléliser un calcul et juger quand le parallélisme en vaut le coût.
Sommaire de la leçon

Tu sais orchestrer l'asynchrone avec une précision d'horloger : promesses combinées, files de microtâches, annulation, flux paresseux. Mais tout ce travail se déroule sur un seul thread. L'async ne rend pas ton code parallèle : il l'entrelace. Tant qu'une fonction calcule — sans await interne —, rien d'autre ne s'exécute, et l'interface gèle. Pour du vrai parallélisme, il faut un autre thread d'exécution : c'est le rôle des Web Workers.

Cette leçon descend d'un cran sous l'async : tu vas faire tourner du JavaScript sur un thread distinct, lui passer des données par messages (copie ou transfert), partager de la mémoire avec SharedArrayBuffer, synchroniser avec Atomics, et répartir un calcul sur un pool de workers. Les exemples qui touchent au worker ne tournent pas dans l'éditeur intégré (pas de thread navigateur ici) : leur effet est décrit en commentaire.

Le problème : un seul thread pour tout

Le thread principal d'une page fait tout : exécuter ton code, calculer la mise en page, peindre les pixels, traiter les événements. Une boucle de calcul qui monopolise ce thread pendant 500 ms, c'est 500 ms pendant lesquelles aucun clic n'est traité, aucune animation ne s'anime. L'interface est gelée.

Le calcul est correct, mais sur le thread principal il fige l'interface tant qu'il tourne. Aucune promesse n'y change rien : c'est du travail synchrone.

Un Web Worker exécute ce même code sur un autre thread du système. Le thread principal reste libre pour répondre aux interactions, et le résultat revient par un message quand il est prêt.

Créer un worker et échanger des messages

Un worker vit dans un fichier séparé. On l'instancie avec new Worker(url), puis on communique exclusivement par messages : postMessage pour envoyer, onmessage (ou addEventListener("message", …)) pour recevoir. Côté worker, le contexte global est self.

Deux fichiers, un seul canal : postMessage/onmessage. Le worker n'a aucun accès au DOM : il calcule, il répond.

Note

Le worker n'hérite ni de window, ni de document, ni du DOM. Il dispose en revanche de fetch, des timers, de WebSocket, de crypto, des TextEncoder/TextDecoder et de l'importScripts (worker classique) ou des modules ES (type: "module"). Tout résultat destiné à l'écran doit transiter par un message vers le thread principal, seul habilité à toucher le DOM.

Copie (structured clone) ou transfert

Par défaut, postMessage applique l'algorithme de clonage structuré : la donnée est copiée en profondeur (objets, Map, Set, Date, ArrayBuffer, TypedArray… mais ni fonctions ni nœuds DOM). Pour un gros tableau binaire, copier des mégaoctets à chaque message coûte cher. On peut alors transférer la propriété d'un ArrayBuffer au lieu de le copier : le buffer change de thread sans duplication, mais devient inutilisable côté émetteur (il est « détaché »).

Sans le tableau [buffer], le buffer serait copié (clone structuré) ; avec, il est transféré et byteLength tombe à 0 côté émetteur.

SharedArrayBuffer : une mémoire vraiment partagée

Copie et transfert déplacent la donnée d'un thread à l'autre ; aucun des deux ne la partage. Pour que plusieurs threads lisent et écrivent la même mémoire simultanément, il faut un SharedArrayBuffer. Posté à un worker, il n'est ni copié ni détaché : les deux threads voient le même bloc d'octets.

Le même SharedArrayBuffer reste accessible des deux côtés : c'est de la mémoire partagée, pas un message.

Piège fréquent

Deux threads qui font compteur[0]++ en même temps créent une condition de course : lecture, incrément et écriture ne sont pas atomiques, des incréments se perdent. Une mémoire partagée n'est sûre que combinée aux opérations Atomics. De plus, SharedArrayBuffer n'est disponible que dans un contexte cross-origin isolated — voir la section suivante.

Atomics : synchroniser sans condition de course

L'objet Atomics fournit des opérations atomiques sur les tableaux entiers d'un SharedArrayBuffer : Atomics.add, Atomics.load, Atomics.store, Atomics.compareExchange… Chacune lit-modifie-écrit en une seule étape indivisible, donc sans perte d'incrément. Et Atomics.wait/Atomics.notify offrent un mécanisme de blocage : un thread peut dormir jusqu'à ce qu'un autre signale un changement.

Atomics.add et consorts garantissent l'indivisibilité ; wait/notify coordonnent les threads sans boucle d'attente active.

Note

Atomics.wait bloque le thread : interdit sur le thread principal (qui ne doit jamais se figer), il n'est permis que dans un worker. Sur le thread principal, utilise plutôt Atomics.waitAsync, qui renvoie une promesse au lieu de bloquer.

Les variantes de workers

Le Worker que tu viens de voir est un dedicated worker : lié à une seule page, il disparaît avec elle. Deux autres familles existent.

  • Shared Worker (new SharedWorker(url)) : partagé par plusieurs onglets ou iframes de la même origine ; la communication passe par un port (worker.port.postMessage). Utile pour mutualiser une connexion ou un cache entre onglets.
  • Service Worker : un proxy réseau installé pour l'origine, central dans les PWA (mise en cache, mode hors ligne, notifications push). Son cycle de vie et son rôle diffèrent profondément : il intercepte les requêtes plutôt que de calculer.

Pour ce cours, retiens surtout le dedicated worker pour le calcul ; les autres répondent à des besoins de partage inter-onglets et de réseau hors ligne.

Un pool de workers pour diviser le travail

Un seul worker ne fait tourner qu'un thread : pour exploiter plusieurs cœurs, on lance plusieurs workers et on leur distribue des morceaux du problème — diviser pour régner. La taille du pool se cale en général sur navigator.hardwareConcurrency (le nombre de cœurs logiques).

Chaque worker, dès qu'il a fini, réclame la tâche suivante : le pool reste occupé jusqu'à épuisement, puis on appelle terminate() sur chacun.

Astuce

Créer un worker coûte (chargement du script, mise en place du contexte). Pour des tâches répétées, garde le pool vivant et réutilise-le au lieu d'instancier puis détruire à chaque appel : tu amortis le coût de démarrage sur de nombreuses tâches.

Quand paralléliser — et quand s'en abstenir

Les workers brillent sur le calcul CPU lourd : traitement d'image, cryptographie, compression, parsing de gros fichiers, simulation. Ce sont des tâches qui occupent le processeur longtemps et bloqueraient le thread principal. En revanche, ils n'apportent rien à l'I/O : fetch, lecture de fichier, requête réseau sont déjà non bloquants — ils n'occupent pas le CPU pendant l'attente. Y dédier un worker, c'est ajouter du surcoût sans gagner de parallélisme réel.

Règle d'ingénieur : parallélise ce qui sature le CPU assez longtemps pour amortir le coût des messages ; laisse l'I/O à l'asynchrone.

Cas réel

Les éditeurs graphiques du web s'appuient massivement sur les workers. Figma déporte son moteur de rendu (compilé en WebAssembly) hors du thread principal pour garder l'interface fluide pendant que le document se recalcule ; Google Sheets, Photopea ou un outil de retouche photo font tourner filtres, recalculs et export d'image dans des workers. À l'inverse, un simple fetch de données JSON reste sur le thread principal : l'attente réseau ne consomme pas de CPU, un worker n'y apporterait rien.

Pièges fréquents

Piège fréquent

Croire que les threads partagent la mémoire par défaut. Sauf SharedArrayBuffer, chaque message est copié : muter l'objet reçu côté worker ne change rien côté principal. Accéder au DOM depuis un worker est impossible — pas de document ; renvoie les données et touche le DOM côté principal. Oublier worker.terminate() laisse des threads vivre inutilement : termine-les dès qu'ils ne servent plus. Muter un SharedArrayBuffer sans Atomics ouvre la porte aux conditions de course. Enfin, le surcoût de création et de sérialisation peut dépasser le gain : pour une micro-tâche, un worker est plus lent que le calcul direct.

Pour aller plus loin

Pour aller plus loin

Comlink masque le protocole de messages derrière des appels de fonction transparents (RPC sur worker) : tu appelles await api.calcul(x) comme une méthode locale. OffscreenCanvas permet de peindre depuis un worker, en déchargeant le rendu du thread principal. Les threads WebAssembly s'appuient sur le même SharedArrayBuffer et Atomics pour du calcul natif multi-thread. Et pour activer SharedArrayBuffer, ta page doit être cross-origin isolated via les en-têtes Cross-Origin-Opener-Policy: same-origin et Cross-Origin-Embedder-Policy: require-corp (COOP/COEP).

Glossaire

Web Worker
Script JavaScript exécuté sur un thread séparé, sans accès au DOM, communiquant avec le thread principal par messages.
Thread principal
Le fil d'exécution unique qui fait tourner ton code, calcule la mise en page et peint la page : le bloquer fige l'interface.
postMessage / onmessage
Le seul canal entre threads : postMessage envoie, onmessage reçoit. Les données sont copiées, sauf transfert ou SharedArrayBuffer.
Clonage structuré (structured clone)
Algorithme de copie en profondeur appliqué par défaut aux messages (et par structuredClone) : objets, Map, ArrayBuffer… mais ni fonctions ni nœuds DOM.
Transfert (transferable)
Envoi d'un ArrayBuffer sans copie en le listant dans le 2e argument de postMessage ; le buffer d'origine devient détaché (byteLength à 0).
SharedArrayBuffer
Bloc de mémoire réellement partagé entre threads (ni copié ni détaché) ; nécessite un contexte cross-origin isolated (COOP/COEP).
Atomics
Opérations indivisibles (lire-modifier-écrire en une étape) sur un tableau entier partagé, plus wait/notify pour coordonner les threads.
Condition de course (race condition)
Bug où le résultat dépend de l'entrelacement imprévisible de deux threads accédant à la même mémoire sans synchronisation.

Récap et vérification

  • JavaScript est mono-thread : un calcul CPU lourd gèle l'interface ; un Web Worker l'exécute sur un autre thread.
  • On communique par messages : worker.postMessage/worker.onmessage côté principal, self.postMessage/self.onmessage côté worker ; aucun accès au DOM.
  • Par défaut les données sont copiées (clone structuré) ; un ArrayBuffer peut être transféré sans copie via le 2e argument [buffer], ce qui le détache de l'émetteur.
  • SharedArrayBuffer partage la même mémoire entre threads ; Atomics rend les opérations indivisibles et permet wait/notify.
  • Un pool de workers répartit un calcul sur plusieurs cœurs (navigator.hardwareConcurrency) ; pense à terminate().
  • Workers = calcul CPU lourd, jamais pour l'I/O (déjà asynchrone) ; gare au surcoût pour les petites tâches.

Vérifie ta compréhension

  1. Pourquoi async/await ne suffit-il pas à empêcher une boucle de calcul de geler l'interface, alors qu'un worker y parvient ?
  2. Pourquoi cale-t-on la taille d'un pool de workers sur navigator.hardwareConcurrency ?
  3. Que se passe-t-il si deux workers incrémentent compteur[0] d'un SharedArrayBuffer sans Atomics, et comment Atomics.add corrige-t-il le problème ?
