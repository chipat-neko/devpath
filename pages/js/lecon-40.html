Web Workers : calculer sans figer l'interface

~36 min Avancé Leçon 22 recommandée

À la fin de cette leçon, tu sauras

  • expliquer pourquoi un calcul lourd fige une page (le fil principal unique) ;
  • créer un Worker et communiquer par postMessage / onmessage ;
  • déporter un calcul coûteux pour garder l'interface fluide ;
  • comprendre ce qui traverse la frontière (structured clone) et ce qui ne la traverse pas ;
  • transférer un gros tampon sans copie avec les Transferable.
Sommaire de la leçon

Tu le sais depuis la boucle d'événements : JavaScript s'exécute sur un seul fil dans la page — le fil principal. Il dessine l'interface, réagit aux clics et exécute ton code. Tant qu'une fonction tourne, tout le reste attend. Un calcul de quelques secondes ? La page se fige : plus de défilement, plus de bouton qui répond, le fameux « la page ne répond pas ». Les Web Workers résolvent ça : ils exécutent du JavaScript sur un second fil, en parallèle, sans jamais bloquer l'affichage.

Le problème : un fil unique

Un calcul lourd sur le fil principal monopolise tout : pendant qu'il tourne, l'interface est gelée. Avec un worker, ce calcul part « à côté » et l'utilisateur continue d'interagir.

Le modèle : deux fils qui s'échangent des messages

Un worker ne partage pas la mémoire de la page : les deux fils communiquent uniquement par messages. On envoie avec postMessage(donnée) et on reçoit dans un gestionnaire onmessage. C'est un dialogue : le fil principal envoie le travail, le worker renvoie le résultat.

Créer un worker

Un worker est un fichier JavaScript séparé. Le fil principal l'instancie avec new Worker(url) ; le fichier du worker écoute les messages et répond.

Bonne pratique

Pour utiliser import dans le worker, crée-le en module : new Worker("worker.js", { type: "module" }). Et quand le worker n'a plus d'utilité, libère-le avec worker.terminate() — sinon son fil reste vivant en mémoire.

Ce qui traverse la frontière : le structured clone

Les données envoyées par postMessage ne sont pas partagées : elles sont copiées par un mécanisme appelé structured clone. Beaucoup de types passent (nombres, chaînes, objets, tableaux, Map, Set, Date, ArrayBuffer…), mais pas les fonctions, les nœuds DOM, ni les objets liés à leur prototype (une instance de classe perd ses méthodes).

Attention

Un worker n'a aucun accès au DOM : pas de document, pas de window. Son rôle est de calculer et de renvoyer un résultat ; c'est le fil principal qui met à jour l'affichage. En revanche le worker dispose de fetch, setTimeout, WebSocket et IndexedDB — de quoi travailler sérieusement.

Zéro copie : les objets Transferable

Copier un gros ArrayBuffer (une image de plusieurs mégaoctets) coûte cher. Pour ces objets Transferable, on peut transférer la propriété au lieu de copier : on passe une liste de transfert en second argument. C'est instantané, mais l'émetteur perd l'accès au tampon transféré.

Cas réel : garder 60 images par seconde

Cas réel

Figma applique des filtres et des exports d'image dans des workers pour que la toile reste fluide pendant qu'on manipule. Un éditeur photo qui applique un flou à une photo de 12 mégapixels a des millions de pixels à traiter : fait sur le fil principal, le curseur se bloquerait ; dans un worker, l'utilisateur continue de déplacer les curseurs pendant le calcul. On croise le même schéma pour l'analyse de gros fichiers CSV, le chiffrement, la compression, ou un tableur qui recalcule des milliers de cellules.

Quand un worker n'en vaut pas la peine

Créer un worker et s'échanger des messages a un coût fixe (démarrage du fil, copie des données). Pour une tâche courte (quelques millisecondes), ce coût dépasse le gain : garde-la sur le fil principal. Le worker brille pour les calculs vraiment lourds ou répétés — au-delà de ~50 ms de blocage perceptible.

Pour aller plus loin

La bibliothèque Comlink masque postMessage derrière de simples appels de fonction (await api.calculer(n)), bien plus lisible. Il existe aussi les Shared Workers (partagés entre plusieurs onglets), les Service Workers (vus en HTML avancé, pour le hors-ligne et le cache), et SharedArrayBuffer pour une vraie mémoire partagée entre fils (sous conditions de sécurité strictes).

Antisèche

Glossaire

Fil principal (main thread)
Le fil unique où la page dessine l'interface, traite les événements et exécute ton JavaScript ; le bloquer fige tout.
Web Worker
Script JavaScript exécuté sur un fil séparé, en parallèle du fil principal, sans accès au DOM.
postMessage
Méthode d'envoi d'un message (donnée copiée) entre le fil principal et un worker, dans les deux sens.
onmessage
Gestionnaire déclenché à la réception d'un message ; la donnée est dans event.data.
Structured clone
Algorithme de copie des données échangées : gère objets, tableaux, Map/Set, Date, ArrayBuffer… mais pas les fonctions ni le DOM.
Transferable
Objet (comme ArrayBuffer) dont on peut transférer la propriété sans copie ; l'émetteur en perd alors l'accès.
terminate()
Arrête définitivement un worker et libère son fil.

Récap et vérification

  • La page a un seul fil : un calcul lourd la fige tant qu'il tourne.
  • Un Web Worker exécute du JS sur un second fil ; les fils dialoguent par postMessage/onmessage.
  • Les données sont copiées (structured clone) : pas de fonctions, pas de DOM dans le worker.
  • Les Transferable (ArrayBuffer) se transfèrent sans copie ; l'émetteur perd l'accès.
  • À réserver aux tâches lourdes : le coût d'un worker n'est rentable qu'au-delà de quelques dizaines de millisecondes.

Vérifie ta compréhension

  1. Pourquoi un calcul long fige-t-il la page ?
  2. Par quel mécanisme le fil principal et le worker communiquent-ils ?
  3. Cite deux choses qu'on ne peut pas envoyer à un worker.
  4. Quelle est la différence entre copier et transférer un ArrayBuffer ?
