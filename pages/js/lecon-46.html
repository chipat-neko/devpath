Module 15 · Asynchrone expert — Leçon 46

Maîtriser la boucle d'événements et la concurrence

~37 min Avancé Module 1 recommandé

À la fin de cette leçon, tu sauras

  • savoir distinguer file de microtâches et de macrotâches et prédire l'ordre d'exécution d'un code mêlant await, queueMicrotask et setTimeout ;
  • savoir choisir entre exécution séquentielle et parallèle et plafonner la concurrence avec un pool maison ;
  • savoir découper un calcul lourd pour rendre la main à la boucle et éviter de bloquer le rendu ;
  • savoir repérer les conditions de course et la famine de microtâches dans du code asynchrone.
Sommaire de la leçon

Tu écris déjà du async/await sans broncher : tu enchaînes des fetch, tu gères les rejets, tu sais qu'une fonction async renvoie une promesse. Ce que tu n'as peut-être jamais eu à formuler explicitement, c'est quand exactement ton code reprend la main après un await, et dans quel ordre s'exécutent plusieurs tâches en attente. C'est précisément ce qui sépare un code qui « marche » d'un code qui reste fluide sous charge.

Cette leçon te donne le modèle mental précis de la boucle d'événements (event loop), puis les outils pour contrôler l'ordonnancement (microtâches), doser la concurrence (séquentiel, parallèle, parallèle plafonné) et ne jamais bloquer le thread. Tu sortiras capable de prédire l'ordre des logs d'un code piégeux et d'écrire un pool de concurrence en quelques lignes.

Le modèle : pile, macrotâches, microtâches

JavaScript est mono-thread : une seule pile d'appels (call stack) exécute le code synchrone jusqu'au bout. Quand la pile se vide, l'event loop regarde deux files distinctes :

  • la file de macrotâches : callbacks de setTimeout/setInterval, événements DOM, I/O. On en prend une seule par tour de boucle ;
  • la file de microtâches : réactions de promesses (.then, reprise après await), queueMicrotask, MutationObserver. On la vide entièrement avant de rendre la main.

La règle d'or : après chaque macrotâche (et après le script initial), le moteur draine toutes les microtâches en attente — y compris celles ajoutées pendant ce drainage — avant de prendre la macrotâche suivante et avant tout rendu visuel.

Note

Un await découpe ta fonction : tout ce qui suit le await devient une réaction de promesse, donc une microtâche. « Attendre » ne bloque pas : la fonction rend la main et reprend plus tard, en microtâche.

Prédire l'ordre des logs

L'exemple canonique qui révèle tout le mécanisme :

D'abord tout le synchrone (1, 5, 7), puis la file de microtâches dans l'ordre d'inscription (3, 4, 6), enfin la macrotâche (2).

Décortiquons : 1, 5 et 7 s'exécutent sur la pile, immédiatement. Le setTimeout dépose 2 en macrotâche. queueMicrotask dépose 3, le .then dépose 4, et le await null programme 6 comme microtâche — inscrite après 3 et 4 car la fonction async n'atteint le await qu'après avoir loggé 5. Le script se termine, la pile se vide : on draine 3, 4, 6 dans l'ordre. Seulement ensuite, tour suivant, la macrotâche 2.

queueMicrotask vs setTimeout(fn, 0)

Les trois manières de « reporter à plus tard » ne sont pas équivalentes :

Utilise queueMicrotask quand tu veux différer juste un peu — laisser le code synchrone courant finir — tout en restant avant le prochain rendu et le prochain timer. Cas typique : garantir qu'un callback s'exécute toujours de façon asynchrone (cohérence) sans payer le délai d'un timer ni risquer un rendu intermédiaire. Réserve setTimeout(fn, 0) à quand tu veux céder la main au navigateur (laisser un rendu, traiter un événement utilisateur en attente).

Astuce

setTimeout(fn, 0) n'est jamais vraiment à 0 : le navigateur impose un plancher (~4 ms après plusieurs timers imbriqués). Pour « juste après le code courant », queueMicrotask est à la fois plus rapide et plus prévisible.

La famine de microtâches

Puisque la file de microtâches se vide entièrement avant tout rendu, une microtâche qui s'auto-replanifie sans fin affame la boucle : aucun rendu, aucun timer, aucun événement ne passe jamais. L'onglet gèle.

La différence est structurelle : enchaîner des microtâches reste dans le même tour de boucle ; enchaîner des macrotâches rend la main entre chaque. Pour tout travail répété qui doit cohabiter avec une UI réactive, espace-le par macrotâches.

Séquentiel vs parallèle

Le piège le plus coûteux en pratique. await dans une boucle for attend la fin de chaque itération avant la suivante : c'est séquentiel, donc lent si les tâches sont indépendantes.

Le séquentiel est le bon choix quand chaque étape dépend du résultat de la précédente, ou quand l'ordre des effets de bord compte (écritures en base liées). Le parallèle est le défaut pour des tâches indépendantes : tu divises le temps total par le nombre de tâches (à concurrence du réseau). Le critère est la dépendance des données, pas une préférence stylistique.

Note

Promise.all rejette dès le premier rejet (fail-fast) mais n'annule pas les autres promesses, qui continuent en arrière-plan. Si tu veux toutes les issues — succès comme échecs — utilise Promise.allSettled.

Plafonner le parallélisme (pool)

Le « tout en parallèle » de Promise.all a un revers : lancer 5 000 fetch d'un coup sature l'API, déclenche du rate limiting ou épuise les sockets. La bonne pratique est un pool qui n'exécute que N tâches simultanément. Idée : un curseur partagé, et N « ouvriers » qui piochent chacun la tâche suivante tant qu'il en reste.

Chaque ouvrier boucle : il prend l'index suivant, le traite, recommence. Le débit s'auto-régule à n tâches en vol.

Cas réel

Une galerie doit charger 200 vignettes. En séquentiel, l'utilisateur attend une éternité ; en tout-parallèle, 200 fetch simultanés saturent le serveur, qui répond en 429 Too Many Requests. La solution de production est un pool de 4 à 8 requêtes en vol — et ce n'est pas un hasard : les navigateurs eux-mêmes plafonnent à ~6 connexions HTTP simultanées par domaine. Un pool maison applique la même sagesse à tes propres tâches.

Le point subtil est const i = curseur++ exécuté avant le await : l'incrément est synchrone, donc deux ouvriers ne peuvent jamais réserver le même index. C'est une propriété, pas un hasard — elle tient parce que JS est mono-thread et que rien ne s'intercale entre la lecture et l'écriture de curseur++ tant qu'on n'a pas franchi un await.

Ne pas bloquer le thread (chunking)

Un calcul synchrone lourd (parser 1 million de lignes, agréger un gros tableau) monopolise la pile et fige l'UI. La parade : découper en morceaux et rendre la main à la boucle entre chaque, via setTimeout (laisse un rendu) ou en cédant régulièrement.

Pour un travail qui doit juste éviter de bloquer, le chunking par setTimeout suffit. Pour du calcul intensif réel (CPU-bound), seul un Web Worker apporte du vrai parallélisme : il tourne sur un autre thread et communique par messages. En contexte navigateur, requestIdleCallback permet aussi de caler du travail non urgent dans les temps morts, et requestAnimationFrame de synchroniser une mise à jour visuelle juste avant le prochain rendu.

Pièges fréquents

Piège fréquent

Le await séquentiel par mégarde. Écrire for (const x of xs) { await f(x); } pour des appels indépendants multiplie le temps total par le nombre d'éléments. Si les tâches ne dépendent pas l'une de l'autre, passe par map + Promise.all (ou un pool si le volume est grand).

Piège fréquent

Les microtâches passent avant le rendu. Mettre à jour le DOM puis enchaîner une longue chaîne de .then synchrones (microtâches) empêche le navigateur de peindre l'écran tant que la file n'est pas vide. L'utilisateur ne voit rien bouger. Pour laisser respirer l'affichage, cède par macrotâche (setTimeout) ou requestAnimationFrame.

Piège fréquent

Conditions de course sur un état partagé. Si tu lis une variable, fais un await, puis la réécris (x = (await calcul()) + x), une autre tâche a pu modifier x pendant l'attente. Réserve ce dont tu as besoin avant le await (comme l'index du pool), ou sérialise les accès.

Pour aller plus loin

Pour aller plus loin

Choisis ta stratégie de combinaison : Promise.all (tout ou rien, fail-fast), Promise.allSettled (toutes les issues, jamais de rejet global), Promise.race (la première réglée, succès ou échec — utile pour un timeout), Promise.any (le premier succès, ignore les rejets). Explore aussi structuredClone pour copier en profondeur des structures avant de les passer à un worker, et les Web Workers (voire les SharedArrayBuffer) pour du vrai parallélisme CPU.

Antisèche : ordonnancer et doser la concurrence

Glossaire

Boucle d'événements (event loop)
Mécanisme qui, une fois la pile vide, draine les microtâches puis prend une macrotâche, en boucle ; il ordonne tout le code asynchrone.
Pile d'appels (call stack)
Structure où s'empilent les appels de fonctions synchrones ; JavaScript n'en a qu'une (mono-thread).
Macrotâche
Unité de travail prise une par tour : callback de setTimeout/setInterval, événement DOM, I/O.
Microtâche
Réaction de promesse (.then, reprise après await) ou queueMicrotask ; la file entière est vidée avant tout rendu et toute macrotâche.
Famine de microtâches
Blocage où une microtâche se replanifie sans fin : la file ne se vide jamais, aucun rendu ni événement ne passe, l'onglet gèle.
Pool de concurrence
Motif n'exécutant que N tâches asynchrones en même temps : N « ouvriers » piochent la tâche suivante via un curseur partagé.
Condition de course (race condition)
Bogue où le résultat dépend de l'entrelacement des tâches : lire une valeur, faire un await, la réécrire alors qu'elle a changé entre-temps.
Chunking
Découpe d'un gros travail synchrone en lots, en rendant la main à la boucle entre chaque, pour ne pas figer l'interface.

Récap et vérification

  • Une seule pile ; à son vidage, on draine toute la file de microtâches, puis une macrotâche, puis on recommence.
  • queueMicrotask ≈ Promise.resolve().then (microtâche, avant rendu) ; setTimeout(fn, 0) = macrotâche (après rendu possible).
  • Une microtâche qui s'auto-replanifie sans fin affame la boucle et fige l'UI : pour du travail répété, espace par macrotâches.
  • await en boucle = séquentiel (dépendances) ; map + Promise.all = parallèle (indépendant) ; pool = parallèle plafonné à N.
  • Découpe les gros calculs (chunking) pour rendre la main ; délègue le CPU-bound réel à un Web Worker.
