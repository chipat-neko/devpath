Les modules ES (import / export)

~32 min Avancé Leçon 25 recommandée

À la fin de cette leçon, tu sauras

  • distinguer un fichier classique d'un module ES et comprendre sa portée isolée ;
  • écrire et consommer un export nommé ainsi qu'un export default, et renommer un import avec as ;
  • charger un module dans une page avec <script type="module"> en respectant ses contraintes ;
  • éclater le gestionnaire de tâches en plusieurs fichiers (tache.js, stockage.js, ui.js, app.js).
Sommaire de la leçon

Jusqu'ici, tout ton gestionnaire de tâches tenait dans un seul fichier : les données, le rendu DOM, la persistance dans localStorage, les écouteurs d'événements. Ça marche, mais à mesure que le fichier grossit, retrouver le bon morceau devient pénible, et chaque fonction ou variable que tu déclares se retrouve potentiellement accessible de partout. Tu connais déjà les fonctions, les classes et les objets : il est temps de les ranger dans des fichiers séparés.

Dans cette leçon, tu vas apprendre les modules ES (ESM) : le système standard de JavaScript pour découper un programme en fichiers qui s'importent les uns les autres. À la fin, ton projet ne sera plus un bloc monolithique mais une petite arborescence claire où chaque fichier a une responsabilité.

Le problème du fichier unique

Un script classique partage tout avec les autres scripts de la page. Si tu déclares const PI = 3.14 dans a.js et que b.js déclare aussi PI, tu obtiens un conflit : ils vivent dans la même portée globale. Plus le projet grandit, plus le risque de collision et de dépendances invisibles augmente.

Un module résout ça : chaque fichier-module a sa propre portée. Ce qu'il déclare reste privé, sauf ce qu'il décide d'exporter. Et pour utiliser ce qu'un autre module exporte, on l'importe explicitement. Les frontières deviennent visibles et contrôlées.

Note

Un module est toujours en mode strict automatiquement (pas besoin de "use strict"), et son this au niveau racine vaut undefined et non l'objet global. C'est plus sûr par défaut.

Export nommé

L'export nommé permet d'exposer plusieurs éléments d'un même fichier, chacun avec son nom. Il suffit de préfixer une déclaration par le mot-clé export.

Chaque export rend l'élément visible de l'extérieur ; le reste du fichier reste privé.

Import nommé

De l'autre côté, on récupère ces éléments par leur nom, entre accolades, en indiquant le chemin du fichier.

Le chemin commence par ./ (même dossier) et conserve l'extension .js dans le navigateur.

Piège fréquent

Dans le navigateur, import { x } from "./utils" (sans .js) échoue : l'extension est obligatoire. Les outils de build comme Vite la rendent optionnelle, mais pour du code chargé directement par le navigateur, garde-la toujours.

Export par défaut

Quand un fichier expose une seule chose principale — souvent une classe — on utilise l'export par défaut. Il n'y en a qu'un par fichier, et à l'import on choisit librement le nom (sans accolades).

Note

On peut combiner les deux dans un même import. La syntaxe est import LeDefaut, { unNomme } from "./fichier.js"; : le premier (sans accolades) est l'export par défaut, ceux entre accolades sont les exports nommés du même fichier.

Renommer un import

Deux modules peuvent exporter un nom identique, ou bien un nom court manque de contexte chez toi. Le mot-clé as renomme à l'import.

as fonctionne aussi à l'export : export { ajouter as somme };.

Charger un module dans le HTML

Un module ne se charge pas avec un <script> ordinaire. Il faut l'attribut type="module".

Tu n'inclus que le point d'entrée (app.js) : le navigateur suit ensuite la chaîne des import tout seul. Trois conséquences utiles : un module type="module" est différé par défaut (il s'exécute après l'analyse du HTML, comme defer), il est en mode strict, et ses variables ne fuient pas dans le global.

Piège fréquent

Les modules exigent généralement un serveur local (http://). En ouvrant ton fichier via file:// (double-clic), les imports sont bloqués par la sécurité du navigateur (CORS). Lance un petit serveur, par exemple l'extension « Live Server » de ton éditeur, ou npx serve.

Cas réel

Quand tu installes une bibliothèque avec npm et que tu écris import { useState } from "react", tu utilises exactement ce mécanisme. Un projet React ou Vue moderne, c'est des centaines de petits modules ES qu'un outil de build (Vite, esbuild) fusionne et optimise pour la production. Découper le code en fichiers à responsabilité unique, comme dans cette leçon, est la structure de base de tout projet front-end professionnel.

Le cache des modules

Un module n'est évalué qu'une seule fois, même s'il est importé par plusieurs fichiers. Le navigateur le met en cache et renvoie la même instance partout.

Si a.js et b.js importent tous deux compteur.js, le message « module chargé » n'apparaît qu'une fois, et ils partagent la même valeur. C'est idéal pour un état ou une configuration unique.

Note

Les noms importés sont des liaisons « vives » (live bindings) : tu ne peux pas les réassigner depuis le fichier qui importe (valeur = 5 lève une erreur), mais leur valeur reflète toujours celle du module source. Après un appel à incrementer(), lire valeur renvoie bien la valeur à jour.

Pièges fréquents

  • Extension oubliée : dans le navigateur, le chemin doit finir par .js.
  • type="module" manquant : sans lui, import provoque une erreur de syntaxe.
  • Confondre défaut et nommé : import { Tache } alors que Tache est un export par défaut renvoie undefined. Le défaut s'importe sans accolades.
  • Attendre une variable globale : ce que tu déclares dans un module n'est plus accessible depuis la console ou un autre script ; il faut l'exporter/importer.
  • Croire qu'un module se recharge : il est mis en cache et exécuté une fois seulement.

Pour aller plus loin

Pour aller plus loin

L'import dynamique import("./gros-module.js") renvoie une promesse et charge un module à la demande (utile pour ne télécharger un écran que lorsqu'on l'ouvre). Les re-exports ou « barrels » (export * from "./tache.js"; dans un index.js) regroupent plusieurs modules derrière une seule porte d'entrée. En production, les bundlers (Vite, esbuild) fusionnent et optimisent tes modules. Enfin, l'ancien système CommonJS de Node (require/module.exports) reste courant ; les modules ES sont la norme moderne, y compris côté Node.

Projet fil rouge — épisode 26

On éclate le gestionnaire en quatre fichiers, chacun avec sa responsabilité :

  • tache.js : la classe Tache (export par défaut) ;
  • stockage.js : sauver et charger via localStorage (exports nommés) ;
  • ui.js : rendre, qui affiche les tâches dans le DOM (export nommé) ;
  • app.js : le point d'entrée qui importe et orchestre tout.

Chaque fichier a un rôle clair ; app.js est le chef d'orchestre.

Astuce

Repère ta nomenclature : une classe isolée par fichier va bien en export par défaut ; un ensemble de fonctions (utilitaires, accès stockage) va mieux en exports nommés. C'est une convention répandue qui rend les imports prévisibles.

Antisèche

Glossaire

Module ES (ESM)
Fichier JavaScript à portée isolée : ce qu'il déclare reste privé sauf s'il l'exporte. Système standard depuis ES2015.
export
Rend un élément (variable, fonction, classe) visible hors du fichier. Nommé (plusieurs) ou par défaut (un seul).
import
Récupère dans un fichier ce qu'un autre module a exporté, en indiquant le chemin (avec l'extension .js dans le navigateur).
Export par défaut
L'export principal d'un fichier (export default) : unique, importé sans accolades et sous le nom de ton choix.
as
Renomme un élément à l'import ou à l'export (import { x as y }) : utile en cas de collision de noms.
type="module"
Attribut de <script> qui active les modules : chargement différé, mode strict, portée non globale. Exige une origine http(s).
Live binding
Un nom importé reflète toujours la valeur à jour de sa source ; il reste en lecture seule côté fichier importateur.
Point d'entrée
Le module de départ (souvent app.js) chargé par le HTML ; le navigateur suit ensuite toute la chaîne des imports.

Récap et vérification

  • Un module a sa propre portée ; on partage via export et import.
  • Export nommé (plusieurs, avec accolades à l'import) vs export par défaut (un seul, nom libre, sans accolades).
  • as renomme un import ; le chemin commence par ./ avec l'extension .js.
  • On charge le point d'entrée avec <script type="module">, sur un serveur local.
  • Un module est mis en cache et évalué une seule fois.

Vérifie ta compréhension

  1. Pourquoi import { Tache } from "./tache.js" renvoie-t-il undefined si tache.js fait export default class Tache ?
  2. Que se passe-t-il si tu ouvres ton index.html par double-clic plutôt que via un serveur local ?
  3. Si deux fichiers importent le même stockage.js, combien de fois son code de niveau racine s'exécute-t-il ?
