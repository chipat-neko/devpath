Module 09 · Robustesse & outillage — Leçon 25

La gestion des erreurs

~35 min Avancé Module 8 recommandé

À la fin de cette leçon, tu sauras

  • distinguer les erreurs de programmation des erreurs attendues et choisir la bonne réaction ;
  • utiliser try / catch / finally et lever une erreur avec throw new Error() ;
  • créer une classe d'erreur personnalisée et tester son name plutôt que son message ;
  • rattraper proprement une erreur async et appliquer les bonnes pratiques de robustesse.
Sommaire de la leçon

Jusqu'ici, ton gestionnaire de tâches part du principe que tout se passe bien : la saisie est valide, localStorage répond, le JSON se parse. Dans la vraie vie, ce n'est jamais garanti. Un champ vide, un réseau qui tombe, des données corrompues : autant de situations qui font planter ton code et laissent l'utilisateur devant un écran figé. Tu connais déjà .catch() sur les promesses depuis la leçon sur l'asynchrone ; on va maintenant construire une vraie stratégie de gestion des erreurs, synchrone et asynchrone.

L'objectif de cette leçon est d'anticiper les défaillances plutôt que de les subir : repérer le code risqué, réagir avec try/catch, signaler les problèmes avec throw, et concevoir tes propres types d'erreur. À la fin, ton projet validera proprement l'ajout d'une tâche.

Deux familles d'erreurs

Toutes les erreurs ne se traitent pas pareil. Il faut d'abord les classer en deux familles, car la réaction diffère radicalement.

Les erreurs de programmation sont des bugs : tu appelles une méthode sur undefined, tu te trompes de nom de propriété, tu passes un nombre là où une fonction attend un tableau. Ces erreurs ne doivent pas être « rattrapées » pour être masquées : elles signalent un défaut dans ton code, et la bonne réponse est de les corriger, pas de les cacher.

Les erreurs attendues sont des situations normales mais défavorables que tu ne contrôles pas : une saisie utilisateur invalide, un serveur injoignable, un fichier absent, un quota de stockage dépassé. Elles vont arriver ; ton travail est de les gérer élégamment (afficher un message, réessayer, proposer une alternative).

Note

Règle pratique : si l'erreur révèle un bug, laisse-la remonter bruyamment (tu veux la voir en développement). Si c'est une condition externe prévisible, attrape-la et réagis. Avaler un bug dans un catch silencieux te coûtera des heures de débogage plus tard.

try / catch / finally

Le bloc try contient le code risqué. Si une erreur est levée à l'intérieur, l'exécution saute immédiatement au bloc catch, qui reçoit l'objet d'erreur. Le bloc finally, optionnel, s'exécute toujours — que tout se soit bien passé ou non — ce qui en fait l'endroit idéal pour le nettoyage.

Le flux saute du point d'erreur directement au catch, puis passe par finally avant de continuer.

Depuis ES2019, tu peux même omettre le paramètre si tu n'as pas besoin de l'erreur : catch { ... }. Mais c'est rare : l'objet d'erreur porte presque toujours une information utile.

Astuce

finally s'exécute même si le try ou le catch contient un return. Utilise-le pour fermer une ressource, masquer un indicateur de chargement, ou réactiver un bouton — quelque chose qui doit arriver quoi qu'il advienne.

L'objet Error

Quand tu attrapes une erreur, tu reçois un objet. Les erreurs standards sont des instances de Error (ou d'une de ses sous-classes) et exposent trois propriétés clés.

name identifie le type, message décrit, stack localise.

JavaScript fournit plusieurs sous-types intégrés que tu rencontreras souvent :

  • TypeError : une valeur n'est pas du type attendu (appeler une méthode sur null, traiter un nombre comme une fonction).
  • RangeError : une valeur est hors des limites permises (par exemple new Array(-1)).
  • SyntaxError : du code ou des données mal formés, typiquement JSON.parse sur une chaîne invalide.
  • ReferenceError : tu utilises une variable qui n'existe pas.

Tous héritent de Error, donc e instanceof Error reste vrai pour chacun. C'est cette relation d'héritage que nous exploiterons pour créer nos propres types.

Lever une erreur avec throw

Tu n'es pas obligé d'attendre que JavaScript lève une erreur : tu peux le faire toi-même avec throw. C'est la façon propre de signaler qu'une fonction ne peut pas remplir son contrat.

throw arrête net la fonction et « remonte » la pile jusqu'au premier catch rencontré.

Point capital : throw interrompt l'exécution exactement comme return, mais au lieu de rendre une valeur à l'appelant, il propage l'erreur vers le haut. Si aucun catch ne l'attrape, elle remonte jusqu'à la racine et le programme s'arrête (ou la promesse rejette).

Note

On peut techniquement lancer n'importe quoi (throw "texte", throw 42), mais ne le fais jamais. Lance toujours un objet Error : lui seul porte un stack et fonctionne avec instanceof. Un throw de chaîne te prive de toute trace.

Créer ses propres erreurs

Pour distinguer tes erreurs métier des erreurs techniques, crée une classe qui étend Error. Tu obtiens un type que tu peux reconnaître avec instanceof, sans jamais comparer de texte.

L'appel à super(message) est obligatoire : c'est lui qui configure le message et la pile.

L'intérêt est énorme : dans le catch, tu peux trier. Une ErreurValidation ? On affiche un message à l'utilisateur. Autre chose ? On relance avec throw e pour ne pas masquer un vrai bug. C'est la base d'un code robuste.

Les erreurs en mode asynchrone

Tu sais qu'une promesse peut rejeter et que .catch() récupère ce rejet. Avec async/await, un await qui porte sur une promesse rejetée lève une erreur exactement comme un throw synchrone. Tu la rattrapes donc avec un try/catch tout à fait classique.

Un seul try/catch couvre le réseau, le statut HTTP et le parsing JSON.

Le danger guette quand tu oublies le await ou le catch : une promesse qui rejette sans personne pour l'attraper produit un unhandled rejection (rejet non géré), visible dans la console mais qui ne déclenche aucune réaction dans ton interface. C'est une cause classique de bugs silencieux.

Piège fréquent

Appeler une fonction async sans await ni .catch() (« fire and forget ») rend toute erreur invisible à ton flux. Si tu lances une opération asynchrone sans l'attendre, attache-lui au moins un .catch().

Bonnes pratiques

Quelques principes transforment la gestion d'erreurs d'une corvée en filet de sécurité solide.

  • Échouer tôt : valide les entrées en début de fonction et lève dès qu'un cas est invalide. Plus l'erreur surgit près de sa cause, plus elle est facile à diagnostiquer.
  • Messages utiles : « E-mail invalide : pas-un-email » vaut mille fois mieux que « Erreur ». Donne le quoi et le contexte.
  • Ne jamais avaler en silence : un catch vide est presque toujours un bug en puissance. Au minimum, journalise.
  • Attraper étroit : n'entoure de try que la portion réellement risquée, et trie par type dans le catch plutôt que de tout traiter pareil.

Cas réel

Sur une boutique en ligne, un catch (e) {} vide entourait l'enregistrement des commandes. Le jour où l'API de paiement a changé de format, l'enregistrement échouait : mais le client voyait quand même « Merci pour votre achat ! » et l'erreur disparaissait dans le catch vide. Personne ne s'en est aperçu pendant trois jours, jusqu'au rapprochement comptable. Un simple console.error(e) — ou mieux, une remontée vers un outil de suivi — aurait sonné l'alarme dès la première commande perdue.

Pièges fréquents

Piège fréquent

Le catch vide qui masque tout. Écrire catch (e) {} fait disparaître l'erreur sans rien régler : ton programme continue dans un état incohérent et le bug réapparaît ailleurs, indéchiffrable. Attraper trop large est le cousin du problème : un try géant qui enveloppe trente lignes attrape aussi les bugs que tu voulais voir. Oublier que throw interrompt le flux : le code après un throw dans le même bloc n'est jamais exécuté. Enfin, comparer le message (if (e.message === "...")) est fragile — le texte change ; teste plutôt e instanceof MonErreur ou e.name. Et n'oublie pas : une erreur async non rattrapée ne déclenchera aucune réaction visible dans ton interface.

Pour aller plus loin

Pour aller plus loin

La pile (stack) liste la chaîne d'appels qui a mené à l'erreur : c'est ta première piste de débogage. Tu peux relancer une erreur depuis un catch (throw e) après l'avoir journalisée, voire l'envelopper dans une erreur plus parlante (new Error("Échec du chargement", { cause: e }), l'option cause conservant l'originale). Les frameworks proposent des error boundaries qui isolent un composant en panne sans casser toute la page. Côté production, la journalisation centralisée (Sentry et consorts) capture les erreurs réelles des utilisateurs pour que tu les corriges sans attendre un signalement.

Projet fil rouge — épisode 25

Jusqu'ici, ajouter une tâche vide ou interminable polluait silencieusement ta liste. On va valider avant d'ajouter, en séparant proprement la logique métier (qui lève des erreurs) de l'interface (qui les attrape et les affiche).

La fonction métier ne sait rien de l'interface : elle se contente de lever une ErreurValidation claire.

Côté interface, le gestionnaire d'événement appelle cette fonction dans un try/catch. On trie : une erreur de validation s'affiche calmement à l'utilisateur ; tout autre type est relancé, car c'est probablement un bug à corriger.

L'interface ne contient plus aucune règle de validation : elle réagit à des erreurs typées.

Cette séparation est précieuse : tu pourras réutiliser ajouterTache ailleurs (import de données, tests) sans dupliquer les règles, et le catch reste lisible parce qu'il distingue le prévu de l'imprévu.

Antisèche

Glossaire

Exception
Signal d'erreur qui interrompt le flux normal et remonte la pile d'appels jusqu'à un catch.
try / catch / finally
try isole le code risqué, catch reçoit l'erreur et réagit, finally s'exécute toujours (nettoyage).
throw
Lève une erreur volontairement ; interrompt la fonction comme return, mais propage l'erreur au lieu de rendre une valeur.
Objet Error
Porte name (le type), message (texte lisible) et stack (la pile d'appels). Lance toujours un Error, jamais une chaîne.
instanceof
Teste si un objet descend d'une classe donnée ; sert à trier les erreurs par type plutôt que par message.
Erreur personnalisée
Classe étendant Error (avec super(message) et un name propre) pour distinguer tes erreurs métier.
Unhandled rejection
Rejet d'une promesse que personne n'attrape (ni await + catch, ni .catch()) : l'erreur passe inaperçue.
Échouer tôt (fail fast)
Valider les entrées en début de fonction et lever aussitôt : plus l'erreur surgit près de sa cause, plus elle est facile à corriger.

Récap et vérification

  • Distingue les bugs (à corriger) des erreurs attendues (à gérer).
  • try isole le risque, catch réagit avec l'erreur reçue, finally nettoie toujours.
  • Un objet Error porte name, message et stack ; les sous-types intégrés sont TypeError, RangeError, SyntaxError…
  • throw interrompt la fonction et remonte jusqu'au premier catch.
  • Une classe étendant Error crée un type reconnaissable par instanceof ; teste le type, pas le message.
  • Un await qui rejette se rattrape avec try/catch ; sinon, c'est un rejet non géré.

Vérifie ta compréhension

  1. Dans quel ordre s'exécutent try, catch et finally quand le bloc try lève une erreur ? Et quand il n'en lève aucune ?
  2. Pourquoi vaut-il mieux écrire if (e instanceof ErreurValidation) que if (e.message === "Le texte ne peut pas être vide") ?
  3. Que se passe-t-il si une fonction async rejette et que personne ne l'attend avec await ni .catch() ?
