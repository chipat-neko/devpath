Module 08 · Asynchrone & réseau — Leçon 22

La boucle d'événements en profondeur

~35 min Avancé Module 7 recommandé

À la fin de cette leçon, tu sauras

  • expliquer pourquoi JavaScript est mono-thread et ce qu'est la pile d'appels ;
  • décrire le rôle de la boucle d'événements et de la file de tâches alimentée par les API du navigateur ;
  • distinguer microtâches (promesses) et macrotâches (setTimeout) pour prédire l'ordre des logs ;
  • écrire du code qui ne bloque pas l'interface en découpant un gros travail.
Sommaire de la leçon

Depuis la leçon 9, tu utilises l'asynchrone sans accroc : setTimeout, des promesses avec .then/.catch, async/await. Tu sais écrire du code asynchrone. Mais sais-tu dans quel ordre il s'exécute réellement ? Pourquoi un setTimeout(fn, 0) ne se déclenche-t-il pas tout de suite ? Pourquoi une promesse résolue « immédiatement » passe-t-elle quand même après la fin du code qui suit ?

Dans cette leçon, on ouvre le capot. Tu vas comprendre le moteur qui orchestre tout cela : la boucle d'événements (event loop). Ce n'est pas une API que tu appelles, c'est le mécanisme invisible qui décide quoi exécuter et quand. Une fois ce modèle mental en place, l'ordre d'exécution du code asynchrone n'aura plus rien de mystérieux — et tu sauras précisément à quel moment ton état est vraiment sauvegardé.

JavaScript fait une seule chose à la fois

Le cœur de JavaScript est mono-thread : il n'exécute qu'une seule instruction à la fois, dans l'ordre. Il n'y a pas deux morceaux de ton code qui tournent en parallèle. Pour suivre où il en est, le moteur utilise une pile d'appels (call stack) : chaque fonction appelée est empilée dessus, et dépilée quand elle se termine.

Quand multiplier retourne, elle est dépilée ; puis carre, puis afficher. La pile se vide.

Tant qu'une fonction est sur la pile, le moteur lui est entièrement consacré. Et c'est là le piège : si une fonction met du temps, tout le reste attend. Aucun clic n'est traité, aucun rendu n'est rafraîchi, l'interface gèle.

Note

Le navigateur fait bien plein de choses en parallèle (réseau, rendu, minuteurs) : ce sont ses propres composants natifs. Mais ton code JavaScript, lui, reste sur un seul fil.

Les API du navigateur travaillent à côté

Si tout passait par cette unique pile, un setTimeout de trois secondes bloquerait la page trois secondes. Ce n'est pas le cas, et la raison est simple : setTimeout, fetch et les écouteurs d'événements ne sont pas du JavaScript pur. Ce sont des API fournies par le navigateur (les « Web APIs »), gérées par ses composants natifs, en dehors de la pile d'appels.

Quand tu écris setTimeout(fn, 1000), voici ce qui se passe : tu remets ta fonction fn au navigateur en lui disant « rappelle-la dans une seconde ». L'appel à setTimeout se termine immédiatement et est dépilé. Ton code continue. Pendant ce temps, le navigateur compte. Quand le délai est écoulé, il ne peut pas interrompre ta pile pour exécuter fn : à la place, il dépose fn dans une file d'attente (la file des tâches).

Note

Un callback (rappel) déposé dans la file n'est pas exécuté tout de suite : il attend son tour. C'est cette attente qui explique presque tous les ordres « surprenants » qu'on va voir.

La boucle d'événements : le chef d'orchestre

Comment les tâches en attente finissent-elles par s'exécuter ? Grâce à la boucle d'événements. Son fonctionnement tient en une phrase : quand la pile d'appels est vide, elle prend la prochaine tâche de la file et la pousse sur la pile.

Même avec un délai de 0, le callback attend que console.log("fin") soit terminé et la pile vidée.

Le mot-clé est vide. La boucle d'événements ne peut jamais interrompre du code en cours. Elle patiente que la pile soit complètement retombée à zéro avant de servir la tâche suivante. C'est pourquoi une boucle lourde (vue plus haut) empêche tout : tant qu'elle occupe la pile, la boucle d'événements ne peut rien servir.

Microtâches contre macrotâches

Voici le point qui déroute presque tout le monde. Il n'y a pas une file, mais deux niveaux :

  • Les macrotâches : les callbacks de setTimeout, setInterval, les événements du DOM…
  • Les microtâches : tout ce qui vient des promesses (.then, .catch, la reprise après un await).

La règle d'or : après chaque tâche, et avant de prendre la prochaine macrotâche, la boucle d'événements vide entièrement la file des microtâches. Les microtâches sont donc prioritaires. Regarde l'exemple canonique :

On lit souvent « 1, 2, 3, 4 » en pensant ligne par ligne. Faux : la réalité est 1, 4, 3, 2.

Déroulons pas à pas :

  • console.log("1") est synchrone : il s'exécute, on voit 1.
  • setTimeout(..., 0) dépose son callback dans la file des macrotâches.
  • Promise.resolve().then(...) dépose son callback dans la file des microtâches.
  • console.log("4") est synchrone : on voit 4. La pile est maintenant vide.
  • La boucle vide d'abord les microtâches : on voit 3.
  • Seulement ensuite, elle sert la macrotâche : on voit 2.

Astuce

Mémo simple en trois temps : tout le synchrone d'abord, puis toutes les microtâches (promesses), puis une macrotâche (setTimeout) — et on recommence le cycle.

Pourquoi setTimeout(fn, 0) n'est pas immédiat

Le délai 0 ne veut pas dire « maintenant ». Il veut dire « dès que possible, après avoir vidé la pile et toutes les microtâches ». Le délai est un minimum, pas une garantie. Si la pile est occupée 200 ms par un calcul, ton callback à délai 0 attendra ces 200 ms.

setTimeout(fn, 0) sert surtout à « reporter » du travail après le code en cours, pas à l'accélérer.

Ne pas bloquer : découper le travail

Puisqu'un long calcul gèle la page, la parade consiste à le découper en tranches et à rendre la main entre chaque tranche. En cédant la pile via setTimeout, tu laisses la boucle d'événements traiter les clics et rafraîchir l'affichage entre les morceaux.

Entre deux lots, la page respire : l'interface reste réactive même sur un gros volume.

Cas réel

Un tableau de bord affichait 50 000 lignes importées d'un fichier. Au clic sur « Trier », la page se figeait deux à trois secondes : le tri monopolisait la pile, donc la boucle d'événements ne pouvait plus traiter ni le survol, ni le curseur d'attente, ni même le bouton « Annuler ». Le correctif n'a pas été d'accélérer le tri, mais de le sortir de la pile : délégué à un Web Worker, il tourne sur un autre fil et l'interface reste vivante pendant le calcul.

Pièges fréquents

Piège fréquent

Croire que setTimeout(fn, 0) s'exécute « tout de suite ». Non : il attend que la pile soit vide ET que toutes les microtâches soient traitées. Une promesse résolue le doublera toujours.

Piège fréquent

Vouloir lire un résultat asynchrone de façon synchrone. const x = fetch(url); console.log(x); n'affiche pas les données mais une Promise en attente : le résultat n'arrivera que plus tard, par une microtâche. Il faut await ou .then.

Piège fréquent

Bloquer la boucle avec un calcul lourd sur la pile (tri d'un million d'éléments, boucle géante). Pendant ce temps, plus aucun événement n'est traité : la page semble plantée. Découpe, ou délègue à un Web Worker.

Pour aller plus loin

Pour aller plus loin

requestAnimationFrame planifie un callback juste avant le prochain rendu (idéal pour les animations fluides). Les Web Workers offrent un vrai parallélisme : ils tournent sur un autre fil et ne bloquent pas l'interface, parfaits pour les gros calculs. Attention enfin à la famine de la file : une microtâche qui en replanifie une autre sans fin empêche toute macrotâche de passer — l'interface se fige.

Projet fil rouge — épisode 22

Revenons au gestionnaire de tâches. À chaque modification, on persiste le tableau taches dans localStorage. Imaginons une sauvegarde construite autour d'une promesse (par exemple parce qu'on prépare un envoi réseau). Quel ordre de logs obtient-on ?

On lit « avant », puis « après », et seulement ensuite « sauvegardé ».

Pourquoi ? Le .then d'une promesse, même déjà résolue, ne s'exécute jamais sur-le-champ : il est mis dans la file des microtâches. Le code synchrone de sauvegarder (les deux premiers logs) termine d'abord, la pile se vide, puis la microtâche s'exécute et écrit dans localStorage.

Note

Conséquence pratique : juste après l'appel à sauvegarder(), l'état n'est pas encore écrit dans localStorage. Si tu dois agir après la persistance réelle, fais-le dans le .then (ou avec await), jamais sur la ligne qui suit l'appel.

Antisèche

Glossaire

Mono-thread
Propriété du moteur JavaScript qui n'exécute qu'une seule instruction à la fois, sur un unique fil d'exécution.
Pile d'appels (call stack)
Structure « dernier entré, premier sorti » où le moteur empile les fonctions appelées et les dépile quand elles retournent.
Boucle d'événements (event loop)
Mécanisme qui, dès que la pile est vide, prend la prochaine tâche de la file et la pousse sur la pile.
File des tâches (task queue)
Liste d'attente où les API du navigateur déposent les callbacks prêts à être exécutés.
API du navigateur (Web API)
Services natifs (minuteurs, réseau, événements) qui travaillent en dehors de la pile et alimentent la file.
Macrotâche
Tâche issue de setTimeout, setInterval ou d'un événement ; une seule est servie par tour de boucle.
Microtâche
Tâche issue d'une promesse (.then, reprise après await) ; toutes sont vidées avant la prochaine macrotâche.
Bloquer le fil
Occuper la pile par un calcul long, empêchant la boucle d'événements de traiter clics et affichage : la page se fige.

Récap et vérification

  • JavaScript est mono-thread : une pile d'appels, une instruction à la fois. Un calcul long bloque tout.
  • Les API du navigateur travaillent à côté et déposent leurs callbacks dans une file.
  • La boucle d'événements sert la file uniquement quand la pile est vide.
  • Les microtâches (promesses) passent avant les macrotâches (setTimeout).
  • Pour rester réactif : ne bloque pas, découpe le gros travail ou délègue à un Web Worker.
