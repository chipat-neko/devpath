Les formulaires et FormData

~35 min Intermédiaire Leçon 32 recommandée

À la fin de cette leçon, tu sauras

  • savoir lire les champs d'un formulaire avec form.elements et collecter ses données via FormData ;
  • savoir valider côté client avec l'API des contraintes (checkValidity, setCustomValidity) ;
  • savoir intercepter submit, envoyer en fetch POST et gérer l'état d'envoi ;
  • savoir traiter un input type="file" avec FileReader et l'envoyer via FormData.
Sommaire de la leçon

Tu connais déjà le DOM, les événements et fetch. Il te manque la pièce qui relie tout ça côté navigateur : le formulaire, sa collecte et son envoi. Un formulaire HTML n'est pas qu'un assemblage de champs visuels, c'est une API à part entière que JavaScript peut lire, valider et soumettre sans jamais quitter la page.

Dans cette leçon, tu vas apprendre à accéder aux champs, à les empaqueter avec FormData, à les valider avec l'API des contraintes, puis à les envoyer en fetch POST en gérant proprement le succès, l'erreur et l'état d'envoi.

Accéder aux champs

Un élément <form> expose une collection form.elements. Tu y accèdes par index, mais surtout par name. La lecture dépend ensuite du type de champ.

Note

Une case à cocher se lit avec .checked (un booléen), jamais avec .value qui vaut toujours "on" par défaut. Idem pour les boutons radio : c'est le champ coché qui porte la valeur utile.

Astuce

Object.fromEntries(fd) écrase les doublons : si plusieurs champs partagent le même name (cases à cocher multiples), garde plutôt fd.getAll("tags") qui renvoie un tableau de toutes les valeurs.

Note

Une case à cocher non cochée n'apparaît pas du tout dans le FormData : seules les cases cochées y figurent (avec leur value, ou "on" à défaut). Côté serveur, l'absence de la clé signifie donc « non coché ».

Valider côté client : l'API des contraintes

Les attributs HTML required, pattern, min, max ou type="email" définissent des contraintes. JavaScript les inspecte via l'objet validity de chaque champ et déclenche l'affichage natif avec reportValidity().

Pour un message sur-mesure, utilise setCustomValidity(). Tant que la chaîne n'est pas vide, le champ est considéré comme invalide. Pense à la vider dès que la valeur redevient correcte.

Note

L'événement invalid se déclenche sur un champ quand la soumission échoue à cause de lui. Tu peux l'écouter pour remplacer le style natif par tes propres messages accessibles, ou pour faire défiler la page jusqu'au premier champ fautif.

Soumettre sans recharger la page

On intercepte l'événement submit du formulaire, on appelle preventDefault() pour bloquer le rechargement, on valide, puis on envoie le FormData en fetch POST. Passé directement à fetch, il génère automatiquement un corps multipart/form-data, fichiers compris.

Piège fréquent

Ne fixe jamais Content-Type: multipart/form-data toi-même. Le navigateur doit ajouter le boundary qui sépare les champs ; si tu écris l'en-tête à la main, ce boundary manque et le serveur ne sait plus découper les données.

Gérer les fichiers

Un <input type="file"> expose un FileList via input.files. Chaque élément est un objet File (avec name, size, type). Pour un aperçu local d'image, FileReader lit le fichier en URL de données, sans aller-retour serveur.

Astuce

Pour les gros fichiers, URL.createObjectURL(fichier) est plus léger que FileReader : il crée une URL pointant vers le fichier sans le charger en mémoire. Pense alors à URL.revokeObjectURL() une fois l'aperçu remplacé.

Une UX et une accessibilité soignées

Désactiver le bouton pendant l'envoi évite les doublons, mais l'accessibilité va plus loin. Lie chaque message d'erreur à son champ avec aria-describedby et signale l'état avec aria-invalid, pour que les lecteurs d'écran annoncent le problème.

Pièges fréquents

Piège fréquent

Un champ sans attribut name est totalement absent du FormData : il s'affiche, l'utilisateur le remplit, mais rien n'est envoyé. Si une donnée manque côté serveur, vérifie d'abord le name.

Cas réel

Sur un formulaire de commande, un champ « étage / interphone » avait été ajouté en copiant une ligne voisine… sans reporter son attribut name. Les clients le remplissaient, mais l'information n'arrivait jamais côté serveur : les livreurs sonnaient dans le vide. Le champ s'affichait, se validait, se soumettait — et restait pourtant invisible dans le FormData. Morale : une donnée absente à l'arrivée, on regarde d'abord le name.

  • Fixer soi-même le Content-Type multipart casse le boundary : laisse fetch faire.
  • Valider uniquement côté client : le navigateur est contournable. Le serveur DOIT toujours revalider les données reçues.
  • Oublier l'état d'envoi : sans bouton désactivé ni message, l'utilisateur clique trois fois et envoie trois requêtes.
  • Oublier preventDefault() : la page se recharge et ton fetch n'a jamais le temps de partir.

Pour aller plus loin

Pour aller plus loin

Pour un upload avec barre de progression, fetch ne suffit pas : il faut revenir à XMLHttpRequest et son événement upload.onprogress, ou explorer les flux. Côté écosystème, des bibliothèques de formulaires gèrent validation et état pour toi, et les Web Components de formulaire (avec formAssociated) permettent de créer tes propres champs participant nativement à FormData et à la validation.

Antisèche

Glossaire

FormData
Objet qui collecte les couples name/valeur d'un formulaire. Passé à fetch, il produit un corps multipart/form-data, fichiers compris.
form.elements
Collection des champs d'un formulaire, accessible par index ou, surtout, par name (form.elements.email).
API des contraintes
Ensemble natif de validation (Constraint Validation API) : les attributs required, pattern, min… inspectés via l'objet validity de chaque champ.
checkValidity()
Teste la validité d'un champ ou d'un formulaire et renvoie un booléen, sans rien afficher à l'utilisateur.
reportValidity()
Comme checkValidity(), mais déclenche en plus l'affichage des bulles d'erreur natives du navigateur.
setCustomValidity(msg)
Impose un message d'erreur sur-mesure à un champ : tant que le message n'est pas vide, le champ est invalide ; une chaîne vide le rend de nouveau valide.
multipart/form-data
Format d'encodage d'un envoi de formulaire capable de transporter des fichiers. Le navigateur le choisit et le structure automatiquement pour un FormData.
boundary
Séparateur unique inséré par le navigateur dans le Content-Type pour délimiter les champs d'un envoi multipart. Fixer l'en-tête à la main le supprime et casse l'analyse serveur.

Récap et vérification

  • form.elements.nom accède à un champ ; lis .value, .checked selon le type.
  • new FormData(form) collecte tous les champs nommés ; Object.fromEntries le convertit en objet.
  • L'API des contraintes (validity, checkValidity, setCustomValidity) valide côté client.
  • Sur submit : preventDefault, valide, envoie le FormData en fetch POST sans fixer le Content-Type.
  • Gère l'état (bouton désactivé, messages accessibles) et n'oublie jamais la revalidation serveur.
