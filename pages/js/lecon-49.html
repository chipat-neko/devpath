Module 16 · Conception & qualité — Leçon 49

Patterns de conception en JavaScript

~36 min Avancé Module 2 recommandé

À la fin de cette leçon, tu sauras

  • savoir reconnaître quand un pattern GoF devient superflu en JavaScript grâce aux closures et aux fonctions de première classe ;
  • savoir implémenter les patterns module, singleton, observateur (pub/sub) et fabrique de façon idiomatique ;
  • savoir remplacer un switch géant par un objet de stratégies et envelopper une fonction avec un décorateur ;
  • savoir éviter la sur-ingénierie, les singletons à état caché et les fuites d'abonnés.
Sommaire de la leçon

Tu maîtrises déjà les closures, les classes, les modules ES et l'asynchrone. Tu as donc tout l'outillage pour aborder les patterns de conception non pas comme un catalogue figé hérité du Java, mais comme des solutions que JavaScript exprime souvent en quelques lignes. La plupart des patterns du Gang of Four (GoF) ont été inventés pour contourner les limites de langages sans fonctions de première classe ni fermetures : en JS, ces limites n'existent pas.

Cette leçon te montre la version idiomatique de six patterns clés. L'objectif n'est pas de les appliquer partout, mais de savoir lequel résout réellement ton problème — et lequel n'est qu'une fonction déguisée.

Avertissement : le JS change la donne

En Java, encapsuler de l'état privé impose une classe et des accesseurs. En JS, une closure suffit : la variable capturée est invisible de l'extérieur. Une stratégie n'a pas besoin d'interface ni de hiérarchie de classes : une fonction passée en argument fait l'affaire. Un décorateur n'a pas besoin d'envelopper une classe : il enveloppe une fonction.

Note

Un pattern reste un vocabulaire partagé : dire « c'est un observateur » communique une intention. Mais en JS, beaucoup de patterns se résument à « passe une fonction » ou « capture une variable dans une closure ». Garde le nom, allège l'implémentation.

Module : encapsuler état et API

Le pattern module isole un état privé et n'expose qu'une API publique. Historiquement on utilisait une IIFE qui retourne un objet ; la closure rend count inaccessible de l'extérieur.

Le compteur expose trois points d'entrée et cache totalement count.

Aujourd'hui, le module ES est le pattern module : tout ce qui n'est pas export reste privé au fichier. Préfère-le à l'IIFE quand tu écris du code moderne.

Singleton : une instance partagée

Un singleton garantit une seule instance partagée. En JS, un module en est déjà un : l'objet exporté est mis en cache par le système de modules et chaque import reçoit la même référence. Tu n'as donc presque jamais besoin d'écrire un singleton « à la main ».

Piège fréquent

Un singleton est un état global déguisé. Il rend les tests pénibles : deux tests partagent la même instance, l'ordre d'exécution influence le résultat, et tu dois ajouter une fonction de réinitialisation. Préfère injecter la dépendance dans les fonctions qui en ont besoin (voir « Pour aller plus loin »).

Observateur (pub/sub) : notifier des abonnés

Un sujet maintient une liste d'abonnés et les notifie d'un événement. Voici un EventEmitter minimal : on enregistre un écouteur, off le retire, emit diffuse. On stocke les écouteurs dans une Map indexée par nom d'événement.

Le Set évite les doublons ; on renvoie une fonction de désabonnement, plus sûre que d'avoir à rappeler off avec les bons arguments.

Cas réel

L'observateur est partout dès qu'on quitte l'exercice. Le DOM entier en est un : addEventListener("click", …) abonne un écouteur que le navigateur notifie à chaque clic. Côté serveur, l'EventEmitter de Node.js est le cœur des flux (stream.on("data", …)) et des serveurs HTTP. Et un store Redux expose store.subscribe(listener) — exactement on/emit sous un autre nom : à chaque changement d'état, tous les abonnés (les composants affichés) sont notifiés et se redessinent. Quand tu écris un EventEmitter, tu réimplémentes le mécanisme qui fait tourner la moitié du web.

Fabrique (factory) : créer sans exposer new

Une fabrique est une fonction qui assemble et configure un objet, sans que l'appelant manipule new ni connaisse la classe concrète. Elle peut choisir l'implémentation selon ses arguments et appliquer des valeurs par défaut.

L'appelant reçoit une API homogène sans rien savoir de seuils ni de la logique de filtrage.

Stratégie : injecter un comportement

La stratégie remplace une grosse cascade de if/else ou un switch par un dictionnaire de fonctions, sélectionnées par clé. Chaque branche devient une entrée indépendante, testable et extensible sans toucher au dispatcher.

Ajouter un format xml ne demande qu'une entrée de plus : le code de exporter ne bouge jamais (principe ouvert/fermé).

Astuce

Un objet de stratégies fait office de table de routage. Combine-le avec une clé par défaut : const strategie = formats[format] ?? formats.json; évite le throw quand un repli est acceptable.

Décorateur (fonction) : envelopper un comportement

Un décorateur prend une fonction et en renvoie une nouvelle qui ajoute un comportement (journalisation, mémorisation, limitation de débit) sans modifier l'originale. C'est de la composition : la signature d'entrée et de sortie est préservée grâce au rest ...args.

Les décorateurs se composent : withLog(memoize(fn)) empile journalisation et cache sans coupler les deux.

Note

Pour des clés d'objet par référence (et un cache qui n'empêche pas le ramasse-miettes), remplace la Map par une WeakMap quand l'argument est un objet : le cache se vide tout seul quand l'objet n'est plus référencé ailleurs. Attention : une WeakMap ne se clé que par objet, pas par primitive.

Pièges fréquents

Piège fréquent

Sur-ingénierie. Encapsuler une fonction de trois lignes dans une « factory » avec interface et registre, c'est ajouter du coût sans valeur. Demande-toi toujours : « une simple fonction suffirait-elle ? » La réponse est souvent oui.

Les deux autres pièges majeurs : les singletons à état caché, qui transforment tes tests en champ de mines (état partagé, ordre dépendant) ; et les fuites d'abonnés dans l'observateur. Oublier off (ou removeEventListener) garde une référence vivante vers le callback — et donc vers tout ce qu'il capture en closure. Sur un composant monté/démonté en boucle, c'est une fuite mémoire classique. Retiens systématiquement l'écouteur au démontage, ou utilise la fonction de désabonnement renvoyée par on.

Pour aller plus loin

Pour aller plus loin

Composition plutôt qu'héritage : assemble des comportements (objets de fonctions, décorateurs) au lieu de bâtir des arbres de classes fragiles. Injection de dépendances : passe les collaborateurs (logger, client HTTP, horloge) en paramètres plutôt que de les importer en dur — tes fonctions deviennent testables sans mock global. Enfin, repère ces patterns dans les frameworks : les hooks mêlent stratégie (le comportement injecté) et observateur (la réaction aux changements d'état), et l'arbre de composants est un observateur géant.

Antisèche : six patterns, version JS

Glossaire

Pattern de conception
Solution éprouvée et nommée à un problème d'organisation du code récurrent ; un vocabulaire partagé plus qu'une recette à copier. Beaucoup, hérités du Gang of Four (GoF), s'allègent radicalement en JavaScript.
Closure (fermeture)
Fonction qui capture les variables de sa portée de définition ; elle garde l'accès à count même après la fin de la fonction englobante. C'est le moteur de l'encapsulation privée en JS.
IIFE
Immediately Invoked Function Expression : fonction définie et appelée sur-le-champ ((() => {…})()), historiquement utilisée pour créer une portée privée avant les modules ES.
Singleton
Objet dont il n'existe qu'une seule instance partagée. En JS, l'export d'un module l'est déjà : chaque import reçoit la même référence mise en cache.
Observateur (pub/sub)
Un sujet tient une liste d'abonnés et les notifie d'un événement via emit ; les abonnés s'inscrivent avec on et se retirent avec off. Le sujet ignore qui l'écoute.
Fabrique (factory)
Fonction qui assemble et configure un objet puis le renvoie, sans que l'appelant utilise new ni connaisse la classe concrète. Elle peut choisir l'implémentation selon ses arguments.
Stratégie (strategy)
Algorithme interchangeable sélectionné à l'exécution ; en JS, un objet { clé: fonction } qui remplace un gros switch et respecte le principe ouvert/fermé.
Décorateur (decorator)
Fonction qui prend une fonction et en renvoie une nouvelle ajoutant un comportement (log, cache, mesure) sans modifier l'originale ; les décorateurs se composent (withLog(memoize(fn))).

Récap et vérification

  • Les fonctions de première classe et les closures rendent beaucoup de patterns GoF triviaux ou inutiles en JS.
  • Le pattern module = closure/IIFE hier, export aujourd'hui ; un module est aussi un singleton naturel.
  • L'observateur se code en quelques lignes (on/off/emit) ou s'emprunte à EventTarget ; pense au désabonnement.
  • La fabrique cache new, la stratégie remplace un switch par un objet de fonctions, le décorateur enveloppe une fonction.
  • Méfie-toi de la sur-ingénierie, des singletons à état caché et des fuites d'abonnés.

Vérifie ta compréhension

  1. Pourquoi un module ES se comporte-t-il déjà comme un singleton, et quand cela devient-il un problème ?
  2. Dans l'EventEmitter, pourquoi copier le Set d'écouteurs ([...]) avant de boucler dans emit ?
  3. Quelle est la différence concrète entre une fabrique et une stratégie ? Dans quel cas choisis-tu l'une plutôt que l'autre ?
