Module 06 · Fonctions avancées — Leçon 17

this, call, apply et bind

~36 min Intermédiaire Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • déterminer la valeur de this selon la façon dont une fonction est appelée ;
  • repérer et corriger la perte de this dans un callback, avec une fléchée ou bind ;
  • forcer le contexte avec call, apply et bind ;
  • regrouper l'état et les actions d'une appli dans un objet sans casser this.
Sommaire de la leçon

Tu écris des fonctions depuis plusieurs leçons : déclarations, fléchées, méthodes d'objet. Jusqu'ici tu t'es concentré sur ce que la fonction fait. Aujourd'hui on regarde un détail qui change tout : le mot-clé this. C'est lui qui permet à une méthode de dire « moi, l'objet sur lequel on m'appelle ». Mal compris, il génère des bugs déroutants — une méthode qui marche dans un cas et plante dans un autre, sans qu'une seule ligne n'ait changé.

L'idée centrale tient en une phrase que tu vas relire souvent : this dépend de COMMENT la fonction est appelée, pas de l'endroit où elle est définie. On va décortiquer chaque manière d'appeler une fonction, voir pourquoi le contexte se « perd », et apprendre à le reprendre en main.

this se décide à l'appel

Dans la plupart des langages, le sens de this est figé là où tu écris le code. En JavaScript, non : il est calculé à chaque appel, en fonction de la façon dont tu déclenches la fonction. La même fonction peut donc avoir un this différent selon qui l'appelle.

Même fonction, deux appels, deux valeurs de this : la définition n'a pas bougé, seul l'appel change.

Retiens cette grille de lecture : pour connaître this, ne regarde pas où la fonction est écrite, regarde ce qu'il y a à gauche du point au moment de l'appel.

Méthode d'objet : this = l'objet

Quand tu appelles une fonction sous la forme obj.methode(), JavaScript fixe this sur obj : ce qui est juste avant le point devient le contexte. C'est le cas le plus courant et le plus intuitif.

Ici this.n modifie bien compteur.n, parce que l'appel passe par compteur.

Note

La syntaxe incr() { … } dans un objet littéral est un raccourci pour incr: function () { … }. Les deux créent une méthode classique avec son propre this dynamique. Ce raccourci ne change rien au comportement de this.

Fonction appelée seule : this disparaît

Quand tu appelles une fonction sans rien à gauche du point — juste fn() — il n'y a pas d'objet receveur. En mode strict (celui des modules ES et des classes, donc ton cas par défaut aujourd'hui), this vaut alors undefined. Hors mode strict, il retombe sur l'objet global (window dans le navigateur), ce qui est encore plus sournois car le bug devient silencieux.

Une fonction « simple » n'a pas de contexte : this y vaut undefined en mode strict.

Note

Que this vaille undefined au lieu d'un objet global muet est une bonne nouvelle : l'erreur explose tout de suite, au lieu d'écrire discrètement des propriétés sur window. Le mode strict te protège.

La perte de this dans un callback

Voici le piège le plus fréquent, et il découle directement des trois sections précédentes. Une méthode marche tant qu'on l'appelle obj.methode(). Mais si tu la passes en callback — à setTimeout, à addEventListener, à map — tu ne transmets que la fonction, détachée de son objet. Au moment où le moteur l'appellera, ce sera un appel « tout seul ».

compteur.incr sans parenthèses, c'est juste la fonction. Le lien avec compteur est perdu dès qu'on la sort de l'objet.

Piège fréquent

Le point reste invisible jusqu'au moment de l'appel. setTimeout(compteur.incr, …) évalue compteur.incr en une simple valeur-fonction. Plus tard, setTimeout l'appelle sans receveur : aucun objet à gauche, donc this est perdu.

Les fléchées et le this lexical

Tu connais déjà les fonctions fléchées comme une syntaxe courte. Leur vraie particularité est ailleurs : une fléchée n'a pas de this à elle. Elle ne le recalcule jamais à l'appel ; elle emprunte le this de l'endroit où elle est écrite. On dit qu'elle a un this lexical (déterminé par le texte du code, pas par l'appel). C'est exactement ce qu'il faut pour un callback défini à l'intérieur d'une méthode.

La fléchée capture le this de la méthode englobante. Une fonction classique à la place aurait, elle, perdu le contexte.

Piège fréquent

N'utilise pas une fléchée pour définir une méthode d'objet. { incr: () => { this.n++; } } capture le this extérieur à l'objet (souvent undefined ou le module), pas l'objet lui-même. La fléchée est parfaite dans une méthode, jamais comme méthode.

Forcer this : call, apply et bind

Parfois tu veux décider toi-même de la valeur de this. Trois méthodes, présentes sur toute fonction, te le permettent.

  • call(thisArg, ...args) : appelle la fonction tout de suite, avec le this imposé et les arguments listés un à un.
  • apply(thisArg, [args]) : pareil, mais les arguments sont passés dans un tableau.
  • bind(thisArg) : n'appelle rien ; renvoie une nouvelle fonction dont le this est verrouillé pour toujours.

Retiens l'opposition : call et apply appellent maintenant ; bind prépare une fonction pour plus tard.

bind est la réponse classique à la perte de this en callback : on lie d'avance la méthode à son objet, puis on passe la version liée.

La fonction liée garde son contexte même appelée toute seule par setTimeout.

Cas réel — le bouton React qui ne réagit pas

Pendant des années, les composants React écrits en classes ont buté sur ce piège. Un <button onClick={this.handleClick}> passe la méthode détachée de l'instance : au clic, this vaut undefined et this.setState(...) lève une erreur. La parade rituelle, recopiée dans des milliers de constructeurs : this.handleClick = this.handleClick.bind(this) — exactement le bind de cette leçon. Les champs-fléchés de classe et les Hooks ont depuis rendu ce réflexe moins visible, mais le mécanisme sous-jacent est identique.

Astuce

Fléchée ou bind ? La fléchée est plus lisible et idéale quand tu écris le callback sur place. bind sert quand tu dois transmettre une référence réutilisable — par exemple pour pouvoir la retirer plus tard avec removeEventListener, ce qu'une fléchée recréée à chaque fois ne permet pas.

Pièges fréquents

  • Détacher une méthode sans le voir. const f = obj.methode, ou la passer en argument (setTimeout(obj.methode, …)), supprime le receveur. Corrige avec une fléchée englobante ou obj.methode.bind(obj).
  • Croire qu'une fléchée a son propre this. Lui passer un contexte avec call, apply ou bind ne fait rien : son this est lexical et figé à la définition. Ces trois méthodes sont sans effet sur une fléchée.
  • Utiliser this dans une fonction qui n'est pas une méthode. Si rien n'est à gauche du point à l'appel, this vaut undefined (mode strict) et tu obtiens un TypeError. Passe l'objet en paramètre, ou fais-en une vraie méthode.
  • Fléchée comme méthode d'objet. { nom: "Léa", saluer: () => this.nom } ne lit pas nom : la fléchée ne voit pas l'objet. Utilise la forme méthode saluer() { … }.

Pour aller plus loin

Trois cas particuliers à connaître. Dans un gestionnaire d'événement défini avec une fonction classique, this vaut l'élément qui a déclenché l'événement (équivalent de event.currentTarget) — d'où l'intérêt de ne pas y mettre de fléchée si tu comptes là-dessus. Avec l'opérateur new, this désigne le nouvel objet en cours de création (tu verras ça avec les classes). Enfin, le mode strict (toujours actif dans les modules et les classes) est ce qui fait valoir undefined plutôt que l'objet global pour une fonction appelée seule.

Projet fil rouge — épisode 17

Jusqu'ici, ton gestionnaire de tâches était un tableau taches et des fonctions éparpillées qui le manipulaient. On va regrouper l'état et les actions dans un seul objet gestionnaire. C'est plus propre, mais ça nous expose pile au piège de cette leçon : dès qu'on branche une méthode sur un événement, on risque de perdre this.

État (taches) et comportements (ajouter, basculer) vivent désormais ensemble dans gestionnaire.

Le bug classique : gestionnaire.ajouter seul perd le lien avec gestionnaire.

La correction tient en une fléchée. On l'écrit sur place, donc elle capture le this du module ; mais surtout, à l'intérieur, on rappelle gestionnaire.ajouter(...) avec le point. Le receveur est donc bien gestionnaire.

La fléchée sert d'enveloppe : elle ne fait que rappeler la méthode proprement, point compris.

Astuce

Le réflexe à graver : pour qu'une méthode garde son this en callback, soit tu l'enveloppes dans une fléchée qui la rappelle avec le point (() => gestionnaire.ajouter(v)), soit tu passes gestionnaire.ajouter.bind(gestionnaire). Les deux marchent ; choisis selon que tu écris le callback sur place ou que tu dois en garder une référence.

Glossaire

this
Référence au contexte d'appel d'une fonction ; sa valeur est fixée à l'appel, pas à la définition.
Receveur
L'objet à gauche du point dans obj.methode() ; c'est lui qui devient this.
Perte de this
Bug survenant quand une méthode est détachée de son objet (passée en callback) : this devient undefined.
this lexical
this d'une fonction fléchée : emprunté à l'endroit où elle est écrite, jamais recalculé à l'appel.
call
Appelle la fonction immédiatement avec un this imposé et des arguments listés un à un.
apply
Comme call, mais les arguments sont fournis dans un tableau.
bind
Renvoie une nouvelle fonction dont le this est verrouillé ; n'exécute rien sur le moment.
Mode strict
Mode d'exécution (par défaut dans les modules et classes) où this vaut undefined pour une fonction appelée seule.

Récap et vérification

  • this est fixé à l'appel, par ce qu'il y a à gauche du point — pas par l'endroit où la fonction est écrite.
  • obj.methode() donne this = obj ; fn() seule donne this = undefined en mode strict.
  • Passer une méthode en callback la détache de son objet : this est perdu.
  • Une fléchée n'a pas de this propre : elle hérite du this englobant (lexical) — idéale comme callback dans une méthode.
  • call/apply appellent tout de suite avec un this imposé ; bind renvoie une nouvelle fonction au this figé.
