Module 19 · Aux frontières de JavaScript — Leçon 60

Au-delà du navigateur : runtimes et WebAssembly

~34 min Avancé Leçon 17 recommandée

À la fin de cette leçon, tu sauras

  • savoir distinguer Node.js, Deno et Bun sur leurs modèles de permissions, leurs API et leur gestion de paquets ;
  • savoir reconnaître la convergence vers les API web standard côté serveur (fetch, Web Streams, Web Crypto) et les contraintes de l'edge ;
  • savoir instancier et appeler un module WebAssembly depuis JS via WebAssembly.instantiate et comprendre la mémoire linéaire ;
  • savoir arbitrer entre JS et WASM en tenant compte du coût d'interop à la frontière.
Sommaire de la leçon

Tu as passé quinze leçons à pousser le moteur JavaScript dans ses retranchements : Proxy, générateurs, ArrayBuffer, Workers, Streams. Toutes ces primitives existent autant hors du navigateur que dedans, et la frontière du langage ne s'arrête plus à la window. Cette leçon cartographie ce qui se passe au-delà : les runtimes serveur qui se disputent l'héritage de Node, l'edge qui exécute ton code dans un isolat V8 à quelques millisecondes de l'utilisateur, et WebAssembly, le format binaire qui laisse cohabiter ton JS avec du Rust ou du C compilé.

L'enjeu n'est pas d'apprendre une API de plus, mais de raisonner sur les environnements d'exécution et sur l'interopérabilité entre langages. Quand tu maîtrises le coût d'une frontière JS↔WASM ou les permissions par défaut d'un runtime, tu choisis l'outil au lieu de le subir.

Les runtimes modernes : Node, Deno, Bun

Node.js reste la référence : V8, libuv pour la boucle d'événements, l'écosystème npm. Mais son héritage (les modules CommonJS, require, l'absence historique de permissions) pèse. Deux challengers redéfinissent les attentes.

Deno mise sur la sécurité par défaut : rien n'est autorisé sans flag explicite. TypeScript s'exécute nativement, sans étape de build, et les API suivent les standards web. Bun mise sur la performance et le tout-en-un : runtime (sur JavaScriptCore, pas V8), gestionnaire de paquets, bundler et test runner dans un seul binaire.

Trois runtimes, trois philosophies : compatibilité (Node), sécurité (Deno), vitesse intégrée (Bun).

Ce qui les distingue concrètement : le modèle de permissions (absent historiquement chez Node, central chez Deno), le gestionnaire de paquets (npm vs imports d'URL et registres chez Deno vs un client npm réécrit chez Bun) et le périmètre d'API. Bun et Deno implémentent en plus de larges pans de l'API Node pour la compatibilité, mais jamais à 100 %.

Les API web standard côté serveur

La grande convergence des dernières années : les runtimes serveur adoptent les API que tu connais déjà du navigateur. fetch est désormais global partout (Node, Deno, Bun). Les Web Streams (ReadableStream, vus en leçon Streams) et la Web Crypto API (crypto.subtle) sont disponibles côté serveur sans dépendance.

Un même code portable sur quatre environnements grâce aux standards web.

Note

Cette convergence est portée par un collectif de runtimes (le WinterCG, désormais WinterTC) qui définit un socle d'API communes côté serveur et edge. Plus tu codes contre ce socle, plus ton code est portable.

L'edge computing : du JS au plus près de l'utilisateur

L'edge déplace l'exécution vers des centaines de points de présence géographiques. Plutôt qu'un conteneur lourd, des plateformes comme Cloudflare Workers instancient un isolat V8 : un contexte JavaScript léger, démarré en moins d'une milliseconde, sans le coût d'un démarrage de processus Node.

Le contrat d'un Worker edge se résume à Request en entrée, Response en sortie.

Les contraintes sont le prix de la légèreté : pas de système de fichiers, pas d'API Node complète, un temps CPU plafonné par requête, et souvent l'absence de certaines API natives. Tu codes contre une surface volontairement réduite, proche de celle du navigateur.

WebAssembly : ce que c'est et pourquoi

WebAssembly (WASM) est un format binaire bas niveau, portable et conçu pour une exécution quasi native. Il n'est pas un langage que tu écris à la main : tu compiles du C, du C++, du Rust ou d'autres langages vers WASM. Son intérêt : le calcul lourd (traitement d'image, crypto, physique, codecs) et le portage de bibliothèques natives existantes dans un environnement JS.

WASM s'exécute dans le même bac à sable que JS, avec sa propre mémoire linéaire : un ArrayBuffer contigu (tu reconnais la leçon ArrayBuffer/TypedArray) que JS et WASM partagent pour échanger des données.

Appeler une fonction WASM depuis JS

L'API WebAssembly charge et instancie un module. instantiate est asynchrone : il compile puis lie le binaire, et renvoie une instance dont les exports sont des fonctions JS appelables.

Le module est compilé puis appelé ; memory.buffer est le pont de données entre les deux mondes.

Point crucial sur l'interop des types : WASM ne connaît nativement que des nombres (entiers et flottants 32/64 bits). Les chaînes, tableaux et objets n'existent pas à la frontière : il faut les sérialiser dans la mémoire linéaire (écrire les octets, passer un pointeur et une longueur), puis les relire de l'autre côté. C'est exactement ce coût que les outils automatisent.

Les outils : emscripten, wasm-pack

Personne n'écrit ces ponts à la main en production. Emscripten compile du C/C++ vers WASM et génère le code de collage (le glue code) JS qui gère la mémoire et les conversions de chaînes. Côté Rust, wasm-pack (avec wasm-bindgen) produit un module WASM et un wrapper JS/TypeScript typé qui masque la sérialisation.

Ces chaînes d'outils génèrent à la fois le binaire et le code JS d'interop.

Quand JS suffit, quand passer à WASM

WASM complète JavaScript, il ne le remplace pas. Il brille sur des charges CPU intensives, déterministes et longues : décodage vidéo, simulation, parsing massif, cryptographie. JS reste imbattable pour l'orchestration, l'I/O, le DOM, la logique métier et tout ce qui traverse souvent la frontière.

Astuce

La règle empirique : WASM gagne quand le calcul reste à l'intérieur du module longtemps. Si tu fais des milliers d'allers-retours JS↔WASM avec de petites données, le coût de la frontière annule le gain natif. Mesure avant de migrer.

Cas réel

Figma illustre parfaitement l'arbitrage. Son moteur de rendu graphique (manipulation de milliers de vecteurs à 60 images/seconde) est écrit en C++ et compilé en WebAssembly : c'est du calcul concentré, qui reste dans le module pendant tout le rendu — le cas idéal. Mais toute l'orchestration autour (interface, événements, réseau, DOM, collaboration temps réel) reste en JavaScript. Le passage à WASM a nettement accéléré le chargement et le rendu là où le JS pur plafonnait, sans pour autant remplacer JS : chacun fait ce qu'il fait de mieux, de part et d'autre d'une frontière franchie le moins souvent possible.

L'avenir : WASI et le modèle de composants

WASM sort du navigateur grâce à WASI (WebAssembly System Interface), une interface standardisée vers le système (fichiers, horloge, réseau) qui permet d'exécuter un même binaire WASM côté serveur ou en CLI, sans hôte JavaScript. Au-dessus, le modèle de composants définit des interfaces de haut niveau (chaînes, enregistrements, listes) pour que des modules écrits dans des langages différents s'assemblent sans glue code manuel. À terme, WASM devient un format d'échange inter-langages, pas seulement un accélérateur web.

Pièges fréquents

Piège fréquent

Croire que WASM « remplace » JS ou qu'il est toujours plus rapide. Sur du code léger ou riche en allers-retours, le coût de la frontière (conversions de types, copies dans la mémoire linéaire) dépasse souvent le gain. WASM accélère le calcul concentré, pas la colle.

Trois autres pièges récurrents : supposer que les API sont identiques entre runtimes (un script Node qui touche fs ne tournera pas tel quel sur un Worker edge) ; oublier les permissions de Deno et s'étonner d'une PermissionDenied ; et négliger le poids du module WASM téléchargé, qui peut alourdir le démarrage bien au-delà de ce qu'économise le calcul.

Pour aller plus loin

Pour aller plus loin

Explore Rust + wasm-pack pour une chaîne d'interop typée, ou AssemblyScript (un sous-ensemble de TypeScript compilé en WASM) pour rester proche de ta syntaxe. Combine Web Workers + WASM pour sortir le calcul lourd du thread principal, regarde WASI et le modèle de composants, et déploie sur l'edge avec Cloudflare Workers ou Deno Deploy. Côté frameworks, les Server Components illustrent une autre frontière : du rendu déplacé hors du navigateur.

Antisèche

Glossaire

Runtime
Environnement qui exécute du JavaScript hors navigateur (moteur + boucle d'événements + API) : Node.js, Deno, Bun.
Isolat (V8 isolate)
Contexte JavaScript léger et cloisonné, démarré en moins d'une milliseconde ; base de l'exécution edge, sans le coût d'un processus complet.
Edge computing
Exécution du code sur des centaines de points de présence proches de l'utilisateur, dans un isolat aux capacités réduites (pas de fs, CPU plafonné).
WebAssembly (WASM)
Format binaire portable, à exécution quasi native ; on y compile du C, C++ ou Rust pour le calcul lourd, jamais écrit à la main.
Mémoire linéaire
ArrayBuffer contigu partagé entre JS et WASM ; unique canal d'échange de données complexes (octets + pointeur + longueur).
Interop (frontière JS↔WASM)
Traversée entre les deux mondes : coûteuse car WASM ne manipule que des nombres. On regroupe le travail pour la franchir rarement.
Glue code
Code JS généré par Emscripten ou wasm-pack qui masque la gestion mémoire et les conversions de types à la frontière.
WASI
WebAssembly System Interface : interface standard vers le système (fichiers, horloge, réseau) permettant d'exécuter un binaire WASM sans hôte JavaScript.

Récap et vérification

  • Node / Deno / Bun diffèrent par les permissions (Deno : tout interdit par défaut), le gestionnaire de paquets et le périmètre d'API ; ils convergent vers les standards web.
  • Les API web standard (fetch, Web Streams, Web Crypto) sont disponibles côté serveur : coder contre elles maximise la portabilité.
  • L'edge exécute du JS dans un isolat V8 léger, au prix de contraintes (pas de fs, CPU plafonné, surface d'API réduite).
  • WebAssembly est un binaire portable et rapide ; on l'instancie via WebAssembly.instantiate et on échange des données par la mémoire linéaire.
  • La frontière JS↔WASM a un coût : WASM complète JS pour le calcul concentré, il ne le remplace pas.
  • WASI et le modèle de composants font de WASM un format d'échange inter-langages au-delà du web.
