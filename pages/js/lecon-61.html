Les modules ES en profondeur

~37 min Avancé Leçon 18 recommandée

À la fin de cette leçon, tu sauras

  • expliquer le graphe de modules et ses trois phases (construction, instanciation, évaluation) ;
  • distinguer les liaisons vivantes de l'ESM de la copie de valeur de CommonJS ;
  • découper ton code avec import() dynamique et exploiter le top-level await ;
  • utiliser import.meta et une import map pour résoudre des modules sans bundler.
Sommaire de la leçon

Tu écris import et export depuis longtemps, mais au niveau expert les modules ES (ESM) sont un système à part entière : un graphe de dépendances résolu en trois phases, des liaisons vivantes entre modules, un chargement dynamique à la demande, et une frontière nette avec l'ancien format CommonJS. Comprendre ces mécanismes, c'est savoir pourquoi un import circulaire fonctionne (ou casse), comment obtenir un bundle léger, et quand import() dynamique vaut mieux qu'un import statique.

La différence fondamentale avec CommonJS : l'ESM est statique et asynchrone. Les import/export sont analysés avant l'exécution — c'est ce qui rend possibles le tree-shaking, les liaisons vivantes et la résolution du graphe entier avant le premier console.log.

Le graphe de modules et ses trois phases

Quand le moteur charge un module d'entrée, il ne l'exécute pas immédiatement. Il en fait la racine d'un graphe qu'il résout en trois phases distinctes. Cette séparation explique presque tous les comportements « surprenants » des modules.

Conséquence directe : un module importé par dix autres n'est évalué qu'une fois. Son objet d'exports est un singleton mis en cache par URL résolue. C'est le mécanisme le plus fiable pour partager un état unique dans une application.

Les liaisons vivantes (live bindings)

Voici la différence la plus subtile avec CommonJS. Un import n'est pas une copie de la valeur exportée : c'est une vue en lecture seule sur la variable du module source. Si le module source réassigne la variable, tous les importateurs voient la nouvelle valeur. En CommonJS, require copie la valeur au moment de l'appel : une réassignation ultérieure reste invisible.

Note

La liaison est vivante mais en lecture seule du côté de l'importateur : seul le module qui possède l'export peut réassigner la variable. Cela évite qu'un consommateur casse l'état d'un module qu'il n'a pas écrit.

Import dynamique et découpage du code

L'import statique est résolu au chargement : son coût est payé d'entrée. Or une grande partie du code d'une application ne sert qu'à certaines routes ou après une action. La fonction import() — un opérateur, pas une déclaration — charge un module à la demande et renvoie une promesse résolue avec l'objet des exports. C'est la base du code splitting.

Le bundler (Vite, webpack, esbuild, Rollup) reconnaît chaque import() et en fait automatiquement un chunk distinct. Aucune configuration : écrire import() suffit à créer une frontière de découpage.

Cas réel

Les applications à page unique construites avec React Router ou Next.js découpent le code par route : const Dashboard = lazy(() => import('./Dashboard')). Visiter la page d'accueil ne télécharge pas le JavaScript du tableau de bord, des réglages ou de l'éditeur — souvent 60 à 80 % de JavaScript en moins au premier chargement. Sur un site marchand, chaque 100 ms gagnées au chargement se traduit mesurablement en conversions : c'est import() qui rend ce découpage trivial, là où l'ancien monde exigeait des acrobaties de configuration.

Top-level await

Dans un module ES, await est autorisé au premier niveau, hors de toute fonction async. Un module qui utilise le top-level await devient une dépendance asynchrone : les modules qui l'importent attendent sa résolution avant d'être évalués. C'est puissant pour l'initialisation (charger une config distante, ouvrir une base), à condition de mesurer que l'on bloque le graphe en aval.

Attention

Le top-level await retarde l'évaluation de tous les importateurs. Un await lent en haut d'un module partagé peut geler le démarrage de l'application entière. Réserve-le à une initialisation réellement bloquante ; sinon, exporte une promesse ou une fonction d'init explicite.

import.meta et les import maps

import.meta est un objet propre à chaque module, alimenté par l'hôte. Sa propriété la plus utile est import.meta.url (l'URL du module courant), qui permet de résoudre des ressources relativement au module plutôt qu'à la page. import.meta.resolve() donne l'URL résolue d'un spécificateur sans le charger.

Sans bundler, les navigateurs exigent des spécificateurs complets (URL ou chemin relatif) — import x from 'lodash' échoue. Une import map déclare la correspondance entre un nom nu et une URL réelle, ce qui autorise les imports lisibles directement dans le navigateur.

Astuce

Les import maps sont la base d'outils « sans build » comme importmap-rails (Ruby on Rails) ou es-module-shims. Pour un prototype ou un petit site, elles suppriment entièrement l'étape de bundling tout en gardant des imports propres.

ESM vs CommonJS et pièges fréquents

Les deux formats coexistent, surtout côté Node. Les différences ne sont pas cosmétiques : elles touchent le moment de la résolution, la nature des liaisons et la synchronicité.

Piège fréquent

Dans le navigateur, un module ES exige un chemin complet avec extension ('./m.js', pas './m') et un serveur qui renvoie le bon type MIME (text/javascript). Une balise <script> qui charge un module doit porter type="module" — sans quoi import déclenche une erreur de syntaxe.

Enfin, les imports circulaires (A importe B qui importe A) ne plantent pas en ESM grâce aux phases : les liaisons sont créées en phase d'instanciation, donc elles existent avant l'évaluation. Le seul risque est de lire une liaison avant que le module source ne l'ait initialisée — on obtient alors undefined, pas une erreur. La parade : n'utiliser les imports croisés qu'à l'intérieur de fonctions appelées plus tard, jamais au premier niveau.

Glossaire

Module ES (ESM)
Format de module standard du langage, à imports/exports statiques et chargement asynchrone ; chaque module est évalué une fois et son objet d'exports mis en cache.
Graphe de modules
Arbre des dépendances construit à partir du module d'entrée, résolu en trois phases (construction, instanciation, évaluation) avant toute exécution.
Liaison vivante (live binding)
Un import pointe vers la variable vivante du module source : sa réassignation par la source est visible chez tous les importateurs (contrairement à la copie de CommonJS).
Import dynamique
L'opérateur import() qui charge un module à la demande et renvoie une promesse ; base du découpage du code (code splitting).
Top-level await
await employé au premier niveau d'un module ; rend le module asynchrone et retarde l'évaluation de ses importateurs.
import.meta
Objet propre à chaque module fourni par l'hôte ; import.meta.url donne l'URL du module, utile pour résoudre des ressources voisines.
Import map
Balise <script type="importmap"> qui associe des noms nus ('lodash') à des URL réelles, permettant des imports lisibles sans bundler.
Tree-shaking
Élimination du code mort rendue possible par les imports nommés statiques : le bundler ne garde que les exports réellement utilisés.

Récap et vérification

  • Un module ES est chargé en trois phases (construction, instanciation, évaluation) : le graphe entier est résolu avant la première ligne exécutée.
  • Un import est une liaison vivante en lecture seule, pas une copie : la réassignation par la source est visible partout (l'inverse de CommonJS).
  • import() charge à la demande et renvoie une promesse : c'est la base du découpage du code, sans configuration.
  • Le top-level await permet une init asynchrone mais bloque les importateurs : à réserver aux cas réellement bloquants.
  • import.meta.url résout des ressources voisines ; une import map autorise les noms nus sans bundler.
