Module 08 · Asynchrone & réseau — Leçon 24

fetch et les API REST

~34 min Avancé Leçon 23 recommandée

À la fin de cette leçon, tu sauras

  • interroger une API REST avec fetch en GET et lire la réponse JSON ;
  • vérifier le succès d'une requête avec response.ok et gérer les pannes réseau avec try/catch ;
  • créer une ressource avec une requête POST (méthode, en-têtes, JSON.stringify) ;
  • synchroniser le gestionnaire de tâches avec un serveur tout en gardant un repli local hors connexion.
Sommaire de la leçon

Jusqu'ici, tes tâches vivent dans le navigateur : tu les ranges dans localStorage et tu les relis au démarrage. C'est parfait pour une seule machine, mais si tu ouvres l'application sur ton téléphone, tu ne retrouves rien : chaque navigateur a son propre coffre. Pour partager des données entre appareils, il faut un serveur commun, et un moyen de lui parler depuis le navigateur.

Ce moyen, c'est fetch. Tu connais déjà les promesses et async/await : fetch renvoie justement une promesse. Dans cette leçon, tu vas apprendre à lire des données distantes (GET), à en créer (POST), à détecter les erreurs sans planter, et à faire évoluer le gestionnaire de tâches vers une vraie synchronisation réseau — avec un repli sur localStorage quand la connexion manque.

Qu'est-ce qu'une API REST

Une API REST est une façon d'organiser un serveur autour de ressources, chacune identifiée par une URL. Pour un gestionnaire de tâches, tu aurais par exemple :

  • https://exemple.api/taches — la collection de toutes les tâches ;
  • https://exemple.api/taches/42 — la tâche d'identifiant 42.

Sur ces URL, tu agis avec des méthodes HTTP qui décrivent ton intention :

  • GET — lire (récupérer la liste, ou une tâche) ;
  • POST — créer une nouvelle tâche ;
  • PUT / PATCH — modifier une tâche existante (tout l'objet, ou seulement un champ) ;
  • DELETE — supprimer une tâche.

Les données échangées sont presque toujours au format JSON, que tu sais déjà sérialiser avec JSON.stringify et relire avec JSON.parse. Enfin, chaque réponse porte un code de statut qui résume ce qui s'est passé :

  • 200 OK — tout va bien, voici les données ;
  • 201 Created — la ressource a bien été créée (réponse typique d'un POST) ;
  • 404 Not Found — la ressource demandée n'existe pas ;
  • 500 Internal Server Error — le serveur a planté.

Note

On retient les familles de codes par leur premier chiffre : 2xx = succès, 3xx = redirection, 4xx = erreur côté client (ta requête est en faute), 5xx = erreur côté serveur.

Piège fréquent

Oublier le second await. Si tu écris const data = reponse.json();, data contient une promesse, pas le tableau. Tu obtiendras un mystérieux [object Promise] ou un undefined en parcourant les données.

Vérifier le succès : response.ok

Voici le point le plus contre-intuitif de fetch, celui qui surprend tout le monde au début : fetch ne rejette PAS sa promesse sur une erreur HTTP. Une réponse 404 ou 500 est considérée comme une réponse reçue avec succès. La promesse n'est rejetée que si la requête n'aboutit pas du tout (pas de réseau, DNS injoignable…).

Concrètement : si le serveur répond 404, ton await fetch(...) réussit, et c'est seulement en inspectant la réponse que tu découvres le problème. La propriété reponse.ok vaut true pour tout statut 2xx, et false sinon :

En levant une exception quand reponse.ok est faux, tu fais entrer les erreurs HTTP dans le même canal que les erreurs réseau : les deux pourront être attrapées par un seul try/catch, ce qui simplifie énormément le code appelant.

Piège fréquent

Croire qu'un try/catch autour de fetch attrape les 404 et 500. Faux : sans le test if (!reponse.ok), ton code continue tranquillement avec une réponse d'erreur et plante plus loin, là où c'est le plus difficile à diagnostiquer.

Cas réel

Un formulaire d'inscription affichait fièrement « Compte créé ! » même quand le serveur répondait 409 (e-mail déjà utilisé) ou 500. La cause : le code faisait await fetch(...) puis passait directement au message de succès, sans jamais regarder reponse.ok. Des dizaines de personnes croyaient posséder un compte inexistant, et le support croulait sous les « je n'arrive pas à me connecter ». Le correctif tenait en une ligne : if (!reponse.ok) throw new Error("HTTP " + reponse.status) avant d'annoncer quoi que ce soit.

Décortiquons les trois clés : method indique l'intention ("POST") ; headers annonce au serveur que le corps est du JSON via "Content-Type": "application/json" ; body contient les données, mais sous forme de texte — d'où JSON.stringify(donnees). Le corps d'une requête HTTP voyage toujours en texte, jamais en objet JavaScript.

Piège fréquent

Passer body: donnees directement (sans JSON.stringify) envoie la chaîne "[object Object]". Et omettre l'en-tête Content-Type fait souvent rejeter ou mal interpréter le corps par le serveur. Les deux vont ensemble.

Le schéma complet d'une fonction de chargement

Rassemblons tout. Voici la forme canonique d'une fonction qui charge des données et reste robuste : try/catch à l'extérieur, test reponse.ok à l'intérieur, et un état de chargement pour l'interface.

Le bloc finally s'exécute que tout se soit bien passé ou non : c'est l'endroit idéal pour masquer un spinner. Tu ne risques jamais de laisser un indicateur de chargement tourner indéfiniment.

Note

Pour tester sans écrire de serveur, des API publiques gratuites existent (par exemple JSONPlaceholder). Mais retiens que fetch a besoin d'un vrai serveur en face : hors connexion, ou si l'URL n'existe pas, tu dois prévoir un repli — c'est tout l'intérêt de garder localStorage sous le coude.

Pièges fréquents

  • Oublier que fetch ne rejette pas sur 404/500. Sans if (!reponse.ok), une erreur HTTP passe inaperçue. C'est l'erreur n°1.
  • Oublier await reponse.json(). Tu manipules alors une promesse au lieu des données.
  • Oublier les en-têtes ou JSON.stringify en POST. Le serveur reçoit du texte invalide et refuse la requête.
  • CORS. Pour des raisons de sécurité, un navigateur bloque par défaut les requêtes vers un autre domaine que celui de la page, sauf si le serveur l'autorise explicitement (en-têtes CORS). Si la console affiche une erreur Cross-Origin, le problème est côté serveur, pas dans ton code fetch.
  • Bloquer l'interface. Pendant une requête, ne « gèle » pas l'écran : affiche un état de chargement, désactive le bouton concerné, puis réactive tout dans finally.

Piège fréquent

L'erreur CORS ne vient pas de toi. Tu ne peux pas la « corriger » en changeant ton fetch : c'est au serveur d'envoyer l'en-tête Access-Control-Allow-Origin. Avec ta propre API, tu la configureras ; avec une API tierce, vérifie qu'elle autorise les appels depuis le navigateur.

Glossaire

API REST
Façon d'organiser un serveur autour de ressources identifiées par des URL, qu'on manipule avec les méthodes HTTP.
Ressource / endpoint
Une entité exposée par l'API (les tâches) et l'URL qui y donne accès, comme /taches ou /taches/42.
Méthode HTTP
Le verbe qui décrit l'intention : GET (lire), POST (créer), PUT/PATCH (modifier), DELETE (supprimer).
Code de statut
Nombre résumant l'issue d'une réponse : 2xx succès, 3xx redirection, 4xx erreur client, 5xx erreur serveur.
fetch
Fonction du navigateur qui envoie une requête HTTP et renvoie une promesse résolue en objet Response.
Response / response.ok
L'objet réponse ; .ok vaut true pour un statut 2xx, .status donne le code, .json() lit le corps.
JSON.stringify / JSON.parse
Sérialise un objet JavaScript en texte JSON (pour le body d'un POST) et relit du texte JSON en objet.
CORS
Règle de sécurité du navigateur qui bloque les requêtes vers un autre domaine, sauf si le serveur l'autorise (en-tête Access-Control-Allow-Origin).

Récap et vérification

  • Une API REST expose des ressources (URL) qu'on manipule avec GET, POST, PUT/PATCH, DELETE ; les réponses portent un code de statut.
  • fetch renvoie une promesse ; on fait await fetch(url) puis await reponse.json().
  • fetch ne rejette pas sur 404/500 : il faut tester reponse.ok et throw soi-même.
  • Un try/catch attrape les pannes réseau ; un finally nettoie l'état de chargement.
  • En POST : method, headers (Content-Type) et body: JSON.stringify(...).

Vérifie ta compréhension

  1. Le serveur répond 404. Que vaut reponse.ok, et la promesse de fetch est-elle rejetée pour autant ?
  2. Pourquoi écrit-on await reponse.json() avec un await, alors qu'on a déjà fait await fetch(...) ?
  3. Quelles sont les trois options indispensables pour envoyer un objet en POST au format JSON ?
