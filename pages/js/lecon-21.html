Module 07 · Programmation orientée objet — Leçon 21

Héritage et encapsulation

~37 min Avancé Leçon 20 recommandée

À la fin de cette leçon, tu sauras

  • réutiliser une classe parente avec extends et appeler super(...) dans le constructeur enfant ;
  • redéfinir une méthode héritée (override) tout en réutilisant la version parente via super.methode() ;
  • encapsuler un état avec des champs privés # et exposer une API par méthodes et accesseurs get ;
  • choisir entre composition (« a-un ») et héritage (« est-un ») selon le besoin.
Sommaire de la leçon

À la leçon précédente, tu as découvert les classes : class Tache { constructor(texte) { … } }, des instances créées avec new, des méthodes partagées sur le prototype. Tu sais déjà fabriquer un objet propre et réutilisable. Mais une classe seule ne suffit pas dès qu'une application grandit : certaines tâches sont prioritaires, d'autres non ; et tu veux empêcher le reste du code de trafiquer ton tableau interne n'importe comment.

Dans cette leçon, tu vas apprendre deux piliers de la programmation orientée objet : l'héritage (réutiliser une classe en la spécialisant avec extends et super) et l'encapsulation (cacher l'état derrière une API stricte grâce aux champs privés #). Tu termineras par un arbitrage essentiel : quand préférer la composition à l'héritage.

Hériter avec extends

L'héritage permet à une classe « enfant » de réutiliser tout ce que sait faire une classe « parente », puis d'ajouter ou de modifier ce qu'il faut. On l'exprime avec le mot-clé extends.

Sans rien écrire de plus, TachePrioritaire possède déjà texte, faite et libelle().

L'idée à retenir : extends établit une relation « est-un ». Une TachePrioritaire est une Tache avec quelque chose en plus. C'est exactement le sens du test instanceof, qui renvoie true pour les deux types.

Appeler le parent avec super(...)

Dès que la classe enfant a besoin de ses propres données dans le constructeur, elle doit d'abord laisser le parent faire son travail. C'est le rôle de super(...), qui appelle le constructeur parent.

La règle d'or : super(...) avant tout usage de this dans le constructeur enfant.

Piège fréquent

Si tu écris this.priorite = priorite; avant super(texte), JavaScript lève une ReferenceError : dans une classe enfant, this n'existe pas tant que le constructeur parent n'a pas été appelé. Mets toujours super(...) en première ligne.

Redéfinir une méthode (override)

L'enfant peut remplacer une méthode héritée en la redéclarant sous le même nom : c'est l'override. Le plus souvent, tu ne veux pas tout réécrire, mais étendre le comportement existant. Là encore, super entre en jeu, mais cette fois sous la forme super.methode() pour appeler la version parente.

super.libelle() exécute la méthode du parent, puis l'enfant ajoute son complément.

Pourquoi passer par super.libelle() plutôt que recopier this.texte ? Parce que si la logique du parent change un jour (par exemple, mettre le texte en majuscules), l'enfant en profite automatiquement. Tu évites la duplication et tu gardes une seule source de vérité.

Note

Quand plusieurs classes partagent une même méthode (ici libelle()) mais que chacune l'implémente à sa façon, on parle de polymorphisme : un même appel, obj.libelle(), produit un résultat adapté au type réel de l'objet, sans que le code appelant ait à le savoir.

Encapsuler avec les champs privés #

Jusqu'ici, toutes les propriétés d'un objet étaient accessibles et modifiables de l'extérieur. C'est pratique, mais dangereux : n'importe quel bout de code peut corrompre l'état. L'encapsulation consiste à cacher l'état interne et à n'exposer qu'une API contrôlée. En JavaScript moderne, un nom de champ commençant par # est strictement privé : inaccessible hors de la classe.

On ne touche plus jamais le tableau directement : tout passe par ajouter(), toutes, restantes.

Les accesseurs get (vus à la leçon précédente) brillent ici : liste.restantes s'utilise comme une propriété en lecture seule, tout en exécutant un calcul. L'appelant ignore qu'il y a un filter derrière ; il voit juste « les tâches restantes ».

Note

Accéder à #taches hors de la classe n'est pas une simple erreur d'exécution : c'est une SyntaxError détectée avant même que le code ne tourne (le moteur refuse de parser le fichier). C'est pour cela que la ligne fautive est en commentaire ci-dessus : décommentée, elle empêcherait tout le script de s'exécuter.

Piège fréquent

Exposer l'état interne par référence ruine l'encapsulation. Si get toutes() renvoyait this.#taches directement, l'extérieur pourrait faire liste.toutes.push(...) et modifier le tableau privé sans passer par ajouter(). Renvoie une copie avec le spread [...this.#taches].

Composition vs héritage

L'héritage est séduisant, mais souvent surutilisé. La bonne question à se poser : la relation est-elle « est-un » ou « a-un » ?

  • Une TachePrioritaire est une Tache → l'héritage est justifié.
  • Une ListeDeTaches a des Tache → c'est de la composition : l'objet en contient d'autres dans un champ.

Une liste n'est pas une tâche : lui faire hériter de Tache serait une erreur de conception.

Astuce

En cas de doute, préfère la composition. Elle reste souple : tu peux remplacer ou recombiner les pièces sans casser une chaîne d'héritage rigide. La maxime classique : « favoriser la composition plutôt que l'héritage ».

Cas réel — l'héritage est partout dans le navigateur

Le DOM que tu manipules chaque jour est une chaîne d'héritage bien réelle : un bouton est un HTMLButtonElement, qui est un HTMLElement, qui est un Element, qui est un Node, qui est un EventTarget. C'est pour cela que bouton.addEventListener(...) fonctionne : la méthode est héritée d'EventTarget, tout en haut de la chaîne. Vérifie-le : document.createElement("button") instanceof HTMLElement renvoie true. Côté erreurs, on crée aussi ses propres types avec class ValidationError extends Error pour les distinguer dans un try…catch.

Pièges fréquents

  • Oublier super() dans un constructeur enfant : ReferenceError dès que tu utilises this. Première ligne, toujours.
  • Héritage trop profond : A extends B, B extends C, C extends D… devient illisible et fragile (un changement dans D casse tout en cascade). Garde les hiérarchies plates ; au-delà de un ou deux niveaux, questionne ta conception.
  • Exposer l'état interne en renvoyant la référence du tableau privé au lieu d'une copie. L'encapsulation ne tient que si l'extérieur ne peut pas court-circuiter ton API.
  • Confondre super(...) et super.x() : le premier (avec parenthèses directes) appelle le constructeur parent, uniquement dans un constructeur ; le second appelle une méthode parente, dans n'importe quelle méthode.

Pour aller plus loin

Pour aller plus loin

JavaScript n'a pas de vraies classes abstraites (qu'on ne peut pas instancier directement), mais on peut le simuler « par convention » : une méthode parente qui lance throw new Error("à implémenter") force chaque enfant à la redéfinir. Côté privé, avant les champs #, on utilisait des clés Symbol (uniques et non énumérables) ou des fermetures (closures) pour cacher des données ; les champs # rendent cela bien plus simple et réellement étanche. Explore aussi le polymorphisme appliqué à un tableau d'objets hétérogènes que tu parcours en appelant la même méthode sur chacun.

Projet fil rouge — épisode 21

Jusqu'ici, ton gestionnaire manipulait un tableau taches nu, exposé à tout le code. On va l'encapsuler dans une classe ListeDeTaches qui devient la seule porte d'entrée vers l'état. On ajoute aussi TachePrioritaire pour illustrer l'héritage.

Le code de rendu ne connaît plus le tableau interne : il demande liste.toutes et appelle t.libelle() sans se soucier du type exact de chaque tâche.

Bénéfice immédiat : toute la logique d'état (ajout, bascule, suppression) est rassemblée dans ListeDeTaches. Comme ajouter() reçoit une tâche déjà construite, la liste accepte indifféremment une Tache ou une TachePrioritaire : le rendu appelle t.libelle() et chaque objet répond selon son type. Le reste de l'application devient un simple consommateur de cette API, plus court et plus sûr. Au prochain épisode, tu pourras y greffer la persistance localStorage sans toucher au reste.

Glossaire

Héritage
Mécanisme par lequel une classe enfant réutilise et spécialise les membres d'une classe parente.
extends
Mot-clé qui établit l'héritage entre une classe enfant et sa classe parente (relation « est-un »).
super(...)
Appel du constructeur de la classe parente ; obligatoire, en première ligne, avant tout usage de this.
super.methode()
Appel de la version parente d'une méthode redéfinie, pour l'étendre sans la recopier.
Override (redéfinition)
Redéclaration dans l'enfant d'une méthode héritée, sous le même nom, pour en changer le comportement.
Polymorphisme
Un même appel (obj.libelle()) produit un résultat adapté au type réel de l'objet.
Encapsulation
Cacher l'état interne derrière une API contrôlée ; en JS, les champs # le rendent réellement privé.
Composition
Relation « a-un » : un objet en contient d'autres dans un champ plutôt que d'en hériter.

Récap et vérification

  • extends crée une classe enfant qui hérite d'une parente (relation « est-un »).
  • super(...) appelle le constructeur parent (obligatoire avant this) ; super.methode() appelle une méthode parente.
  • Redéfinir une méthode (override) permet de spécialiser un comportement, en réutilisant souvent super.
  • Les champs # rendent l'état privé ; on l'expose via des méthodes et des accesseurs get, en renvoyant des copies.
  • Préfère la composition (« a-un ») à l'héritage (« est-un ») quand l'objet en contient d'autres.

Vérifie ta compréhension

  1. Pourquoi super(texte) doit-il figurer avant this.priorite = priorite dans le constructeur d'une classe enfant ?
  2. Quelle est la différence entre super(...) et super.libelle() ?
  3. Pourquoi get toutes() renvoie-t-elle [...this.#taches] plutôt que this.#taches ?
