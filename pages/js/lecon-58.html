Module 19 · Aux frontières de JavaScript — Leçon 58

Le moteur V8 et la performance fine

~32 min Avancé Cours JavaScript avancé recommandé

À la fin de cette leçon, tu sauras

  • savoir expliquer le pipeline V8 (parsing, Ignition, TurboFan) et ce qui déclenche une désoptimisation ;
  • savoir préserver des hidden classes stables et des inline caches monomorphes pour aider le JIT ;
  • savoir raisonner sur le GC générationnel de V8 et traquer les fuites (closures, listeners, caches non bornés) ;
  • savoir mesurer avec performance.now() et PerformanceObserver avant de micro-optimiser.
Sommaire de la leçon

Tu as fini les quinze leçons du cours : tu manipules les Symbol, les générateurs, Proxy, l'event loop et les ArrayBuffer sans trembler. Mais tout ce code finit par traverser un moteur — V8 sur Chrome, Node, Deno, Edge. Comprendre comment il exécute ton JavaScript change la façon dont tu l'écris : pas par superstition, mais parce que tu sais ce qui aide le compilateur et ce qui le force à abandonner ses optimisations.

Cette leçon est volontairement tournée vers V8, mais les principes (compilation par paliers, formes d'objets, caches d'accès, GC générationnel) se retrouvent dans JavaScriptCore et SpiderMonkey. L'objectif : te donner un modèle mental opérationnel, puis les outils pour mesurer avant de toucher à quoi que ce soit.

Le pipeline V8 : Ignition, TurboFan, désoptimisation

V8 ne compile pas ton code en une passe. Le source est d'abord parsé en AST (avec un pre-parsing paresseux qui saute les fonctions non encore appelées — d'où l'intérêt de ne pas tout exécuter au démarrage). L'AST alimente Ignition, l'interpréteur, qui produit du bytecode compact et l'exécute immédiatement. Pendant l'exécution, V8 collecte des retours de profil (feedback) sur les types réellement vus.

Quand une fonction devient « chaude » (appelée souvent), TurboFan la recompile en code machine optimisé, en spéculant sur ces types observés. Si plus tard une hypothèse est violée (un argument d'un type inattendu, une forme d'objet inconnue), V8 désoptimise : il jette le code optimisé et retombe sur le bytecode d'Ignition. Une déopt occasionnelle est normale ; une déopt en boucle (re-opt / re-déopt) tue la performance.

Une fonction monomorphe et chaude est le cas idéal pour TurboFan.

Note

V8 a plusieurs paliers (Ignition, le JIT léger Sparkplug, le JIT intermédiaire Maglev sur les versions récentes, puis TurboFan). Le principe reste : plus une fonction est chaude et plus son comportement est prévisible, plus elle grimpe dans les paliers optimisants.

Hidden classes : garde une forme d'objet stable

Les objets JS sont dynamiques, mais V8 leur attribue en interne une hidden class (aussi appelée shape ou map) qui décrit la disposition mémoire : quelles propriétés, dans quel ordre, à quel offset. Deux objets construits avec les mêmes propriétés dans le même ordre partagent la même hidden class — ce qui permet des accès en offset constant et des inline caches efficaces.

Ce qui casse cette stabilité : ajouter des propriétés après la construction (chaque ajout crée une nouvelle hidden class), initialiser les propriétés dans un ordre différent selon les instances, ou utiliser delete (qui peut faire basculer l'objet en mode « dictionnaire » lent).

Initialise toutes les propriétés au même endroit, dans le même ordre, et évite delete sur les chemins chauds.

Astuce

Pour « supprimer » une propriété d'un objet chaud sans casser sa forme, mets-la à null ou undefined plutôt que d'utiliser delete. Tu gardes la même hidden class et l'accès reste en offset constant.

Inline caches : monomorphe, polymorphe, mégamorphe

À chaque site d'accès à une propriété (obj.x) ou d'appel, V8 installe un inline cache (IC) qui mémorise les hidden classes vues à cet endroit. Un IC qui n'a vu qu'une forme est monomorphe (le cas le plus rapide). Deux à quatre formes : polymorphe (V8 fait un petit branchement). Au-delà : mégamorphe — V8 renonce au cache local et passe par une table globale, beaucoup plus lente, et TurboFan a du mal à optimiser.

Des arguments de forme cohérente gardent les sites d'accès monomorphes.

Note

Conséquence concrète : une fonction utilitaire générique appelée avec des dizaines de types d'objets différents (par exemple un serialize(obj) universel) sera mégamorphe. Si elle est sur un chemin critique, spécialise-la ou regroupe les appels par forme.

Le garbage collector générationnel

V8 sépare le tas en deux générations. Le young generation (petit, divisé en deux semi-espaces) accueille les nouvelles allocations ; il est nettoyé fréquemment par Scavenge, un GC par copie très rapide qui exploite l'hypothèse générationnelle : la plupart des objets meurent jeunes. Les survivants de plusieurs Scavenges sont promus vers l'old generation, nettoyé moins souvent par Mark-Sweep-Compact (marquage, balayage, compactage), avec une part de travail concurrent et incrémental pour réduire les pauses du thread principal.

Ce qui coûte : allouer massivement des objets temporaires dans une boucle chaude (pression sur le young, Scavenges fréquents), et retenir involontairement des objets vivants (ils sont promus et alourdissent les Mark-Sweep). Réutiliser les buffers et éviter les allocations inutiles réduit les pauses GC.

Sur les chemins chauds, l'allocation temporaire est souvent le vrai coût caché.

Les fuites mémoire : closures, listeners, caches non bornés

Une fuite, ce n'est pas un bug du GC : c'est une référence vivante que toi tu ne libères pas. Les trois sources classiques : une closure qui capture un gros objet et reste accrochée (timer, callback) ; un listener jamais retiré (l'élément et tout ce que le handler capture restent vivants) ; un cache (Map, tableau) qui ne fait que grossir.

Un WeakMap pour les caches à clés objets, et toujours un chemin de nettoyage pour les listeners.

Note

Tu connais déjà WeakMap / WeakRef de la leçon sur les références faibles. Côté diagnostic, le snapshot mémoire des DevTools (onglet Memory) et la comparaison de deux heap snapshots révèlent les objets qui s'accumulent entre deux moments.

Mesurer : performance.now() et PerformanceObserver

Avant toute optimisation : mesure. performance.now() donne un temps haute résolution monotone (en millisecondes), qui ne recule jamais même si l'horloge système est ajustée. Attention : sa résolution est volontairement bridée (clamp et jitter) par les navigateurs pour limiter les attaques de type Spectre, donc ne lui demande pas une précision à la nanoseconde. Pour des mesures structurées, l'API Performance offre mark() / measure(), et PerformanceObserver reçoit ces entrées de façon asynchrone (utile pour la production, sans polluer le chemin critique).

Réchauffe avant de chronométrer, sinon tu mesures l'interpréteur, pas le code optimisé.

Piège fréquent

Si le résultat de fn() n'est jamais utilisé, V8 peut éliminer l'appel par dead code elimination et tu mesures du vide. Accumule la valeur de retour quelque part (et lis-la) pour empêcher le moteur de supprimer le travail.

Le profileur DevTools : flame chart

Quand le ralentissement n'est pas localisé, le profileur fait gagner des heures. L'onglet Performance des DevTools enregistre un flame chart : largeur = temps passé, empilement = pile d'appels. Tu repères d'un coup d'œil les fonctions larges (coûteuses) et tu vois la part du scripting, du rendering et du GC (bandes jaunes/violettes). Côté Node, node --prof puis node --prof-process produisent un rapport équivalent en texte.

En local, ces traces te disent où part le temps avant que tu ne touches au code.

Cas réel

Un tableau de bord affiche une liste de 5 000 lignes qui « rame » au défilement. Réflexe de l'équipe : remplacer les forEach par des boucles for et supprimer quelques map. Zéro gain. Un flame chart révèle la vraie histoire : 70 % du temps part dans le layout, pas dans le scripting — le code lit offsetHeight puis écrit un style à chaque ligne (layout thrashing), et le rendu de ligne, appelé avec des objets de formes variées, est devenu mégamorphe. Deux correctifs : regrouper toutes les lectures puis toutes les écritures (dans un requestAnimationFrame), et normaliser la forme des objets de ligne. Résultat : défilement fluide — sans jamais avoir touché aux forEach. La leçon : mesurer avant de deviner.

Micro-optimisations : ce qui compte, ce qui ne compte pas

La plupart des « astuces » (remplacer forEach par une boucle for, éviter map…) ont un effet négligeable sur du code froid ou rarement exécuté : tu sacrifies la lisibilité pour rien. Ce qui compte réellement, c'est l'algorithme (complexité), la stabilité des formes, la pression d'allocation sur les chemins vraiment chauds, et le coût du DOM.

Justement, sur le DOM : lire une propriété de layout (offsetHeight, getBoundingClientRect()) après une écriture force un reflow synchrone. Alterner lecture/écriture dans une boucle provoque un layout thrashing. La parade : regrouper toutes les lectures, puis toutes les écritures.

Sépare lectures et écritures de layout pour éviter le layout thrashing.

Pièges fréquents

Piège fréquent

Micro-optimiser sans mesurer. Tu « optimises » une fonction qui pèse 0,2 % du temps total pendant que 80 % part dans un reflow ou un GC. Profile d'abord, puis attaque le pic le plus large.

  • Forme instable => déopt : ajouter des propriétés après coup ou delete sur un objet chaud le fait basculer en mode lent et déclenche des re-optimisations.
  • Fonction mégamorphe : un utilitaire générique appelé avec trop de formes différentes perd son inline cache et son inlining.
  • Fuites silencieuses : closures retenues par un timer, listeners jamais retirés, Map de cache non bornée. Le tas grossit, les Mark-Sweep s'allongent.
  • Temps CPU ≠ temps réel : performance.now() mesure le temps écoulé (incluant attentes, GC, autres tâches), pas le temps CPU pur. Un I/O ou une pause GC fausse l'interprétation.
  • Benchmark faussé par le JIT : sans warmup tu mesures Ignition ; avec dead code elimination tu mesures du vide. Réchauffe, et consomme le résultat.

Pour aller plus loin

Pour aller plus loin

Explore les flags V8 --trace-opt / --trace-deopt (et --print-opt-code) pour voir le JIT à l'œuvre, et --trace-gc pour les cycles GC. Côté Node, clinic.js (Doctor, Flame, Bubbleprof) automatise le diagnostic. Côté navigateur, surveille les Web Vitals (LCP, INP, CLS) avec PerformanceObserver. Pour le calcul lourd numérique, envisage de bonnes structures de données (TypedArray sur ArrayBuffer, déjà vus) voire WebAssembly quand le JS atteint ses limites.

Antisèche

Glossaire

Ignition
L'interpréteur de V8 : transforme l'AST en bytecode compact et l'exécute immédiatement, tout en collectant du feedback de types.
TurboFan
Le compilateur optimisant : recompile les fonctions chaudes en code machine en spéculant sur les types observés.
Désoptimisation (deopt)
Abandon du code optimisé et retour au bytecode d'Ignition quand une hypothèse de type ou de forme est violée.
Hidden class (shape / map)
Structure interne décrivant la disposition des propriétés d'un objet ; deux objets de même forme la partagent, d'où des accès en offset constant.
Inline cache (IC)
Cache installé à un site d'accès, mémorisant les formes vues : monomorphe (1), polymorphe (2-4), mégamorphe (au-delà, lent).
GC générationnel
Tas séparé en young (nettoyé par Scavenge, rapide) et old (Mark-Sweep-Compact, rare) ; les survivants sont promus.
Layout thrashing
Alternance de lectures (offsetHeight) et d'écritures de style dans une boucle, forçant des reflows synchrones répétés.
Warmup
Phase initiale d'un benchmark exécutant le code plusieurs fois pour laisser le JIT l'optimiser avant de chronométrer.

Récap et vérification

  • V8 compile par paliers : parsing, bytecode Ignition, code optimisé TurboFan ; une hypothèse violée provoque une désoptimisation.
  • Les hidden classes rendent les accès rapides quand les objets gardent les mêmes propriétés, dans le même ordre ; ajout tardif et delete cassent tout.
  • Les inline caches sont rapides en monomorphe, acceptables en polymorphe, lents en mégamorphe : vise des types d'arguments cohérents.
  • Le GC générationnel (Scavenge / Mark-Sweep) récompense la sobriété d'allocation et punit les références retenues.
  • Mesure d'abord avec performance.now(), les marques et le flame chart ; ne micro-optimise que le pic le plus large.

Vérifie ta compréhension

  1. Pourquoi delete obj.prop sur un objet d'un chemin chaud peut-il dégrader la performance bien au-delà de cette suppression ?
  2. Quelle est la différence concrète, en coût d'accès, entre un site monomorphe et un site mégamorphe ?
  3. Pourquoi un benchmark sans phase de warmup ni consommation du résultat donne-t-il des chiffres trompeurs ?
