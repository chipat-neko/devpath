Module 5 · Pour aller plus loin — Leçon 16

Gérer les erreurs

~37 min Avancé Prérequis : leçon 15

À la fin de cette leçon, tu sauras

  • capturer une exception avec try/catch/finally ;
  • lever une erreur riche avec ex-info et la relire avec ex-data ;
  • choisir entre exception (aux frontières) et valeur (au cœur) ;
  • libérer les ressources proprement avec with-open.
Sommaire de la leçon

Clojure tourne sur la JVM : il hérite donc des exceptions Java et de leur mécanique try/catch. Mais l'esprit fonctionnel préfère, quand c'est possible, renvoyer des valeurs plutôt que lancer des exceptions. Cette leçon montre les deux faces : la mécanique classique (indispensable aux frontières du système), et l'atout maison de Clojure — ex-info, une exception qui transporte des données, pas seulement un texte.

Le socle : try, catch, finally

La forme try évalue son corps ; si une exception surgit, le catch dont la classe correspond l'attrape. Le bloc finally, lui, s'exécute toujours — succès comme échec — pour libérer ce qui doit l'être.

Un catch attrape la classe indiquée et ses sous-classes. Exception couvre la plupart des cas ; Throwable couvre tout (à éviter : on masquerait des erreurs graves comme OutOfMemoryError). On peut empiler plusieurs catch, du plus précis au plus général.

Lever une erreur riche : ex-info

Une exception standard ne transporte qu'un message texte. Or, pour réagir correctement, le code appelant a besoin de données : quel montant ? quel identifiant ? quelle catégorie d'erreur ? C'est exactement ce qu'offre ex-info — l'idiome Clojure : un message plus une map de contexte.

throw lance une instance d'exception ; ex-info en fabrique une (de classe clojure.lang.ExceptionInfo) qui garde ta map sous le bras. Un troisième argument facultatif attache une cause (l'exception d'origine) — précieux pour ne pas perdre la trace.

Relire les données : ex-data

Côté appelant, on attrape spécifiquement clojure.lang.ExceptionInfo, puis ex-data rend la map (et nil si l'exception n'en portait pas). On peut alors brancher sur le :type pour réagir finement.

Remarque le dernier réflexe : si l'on ne sait pas traiter un cas, on throw l'exception telle quelle. Attraper une erreur pour l'ignorer en silence est l'un des pires pièges — on masque le problème sans le résoudre.

Où gérer : exceptions aux frontières, valeurs au cœur

La vraie question n'est pas « comment attraper », mais « où ». La bonne pratique fonctionnelle : laisser les frontières (lecture de fichier, appel réseau, parsing) lever des exceptions, et garder le cœur (fonctions pures) sans exception, en renvoyant des valeurs qui décrivent l'échec.

Libérer les ressources : with-open

Fichiers, connexions : il faut les fermer même en cas d'erreur. Plutôt qu'un finally manuel, with-open ferme automatiquement chaque ressource à la sortie du bloc, exception ou non.

Un cas concret

Cas réel

Dans une API web Clojure (avec Ring), un intergiciel (« middleware ») enveloppe chaque requête dans un try. Quand un handler lève (ex-info "Validation" {:type :invalide :champs …}), l'intergiciel lit l'ex-data, reconnaît :type :invalide et répond un HTTP 400 avec le détail des champs ; pour un :type :introuvable, il répond 404 ; et pour toute autre exception, un 500 générique (sans fuiter la trace au client). Le :type de la map devient ainsi la charnière entre le métier et le protocole HTTP : le handler décrit quoi, l'intergiciel décide comment le rendre. C'est ex-info qui rend ce découplage naturel.

Conseils et pièges

Un :type par catégorie d'erreur

Mets toujours une clé :type (ou :error/type) dans la map d'ex-info. Elle donne au code appelant un point d'accroche stable pour un case — bien plus robuste que d'analyser le texte du message, qui peut changer ou être traduit.

Ne jamais avaler une exception en silence

Un (catch Exception _ nil) qui ne fait rien transforme un bug en mystère : la donnée est fausse, mais tout semble marcher. Si tu attrapes, alors traite (répare, journalise, renvoie une valeur explicite) ou relance (throw e). Le pire est l'entre-deux muet.

Pour aller plus loin

Pour aller plus loin

Pour composer des calculs qui peuvent échouer sans empiler les try, regarde le style « railway » et la bibliothèque failjure (des valeurs ok/failure qui s'enchaînent). Côté Clojure « historique », la macro assert et les préconditions {:pre [...] :post [...]} d'une defn vérifient des invariants. Et pour distinguer une erreur attendue (l'utilisateur a mal saisi) d'un bug (invariant cassé), certains réservent ex-info aux premières et assert aux seconds.

Antisèche

Glossaire

try/catch
Forme qui évalue un corps et attrape les exceptions dont la classe correspond au catch.
finally
Bloc exécuté dans tous les cas (succès ou exception) ; sert au nettoyage, ne change pas la valeur renvoyée.
throw
Lève une instance d'exception, interrompant le flux jusqu'au catch englobant.
ex-info
Crée une ExceptionInfo combinant un message, une map de données et une cause optionnelle.
ex-data
Récupère la map de données d'une ExceptionInfo (nil pour les autres exceptions).
Frontière
Zone en contact avec l'extérieur (I/O, réseau, saisie) où les exceptions sont légitimes.
Erreur comme valeur
Signaler un échec en renvoyant une donnée (nil, {:erreur …}) plutôt qu'en levant une exception.
with-open
Ouvre des ressources et les ferme automatiquement à la sortie du bloc, même en cas d'erreur.

Récap et vérification

  • try/catch capture ; finally s'exécute toujours (nettoyage).
  • ex-info lève une exception porteuse de données ; ex-data les relit — mets un :type.
  • Exceptions aux frontières, valeurs ({:ok …}/{:erreur …}) au cœur.
  • Ne jamais avaler une exception en silence : traiter ou relancer. with-open ferme les ressources.

Exercice 3Défi

En une phrase, explique pourquoi brancher sur (:type (ex-data e)) vaut mieux que lire le texte du message.

Voir une solution

Le :type est une donnée stable, pensée pour être lue par le programme : un case dessus reste correct même si le message change, est reformulé ou traduit. Analyser le texte du message est fragile — c'est de la donnée destinée aux humains — et casse au premier ajustement de formulation. Séparer le message (pour l'humain) des données (pour le code) rend la gestion d'erreur robuste.
