Les résolveurs (resolvers)

~37 min Intermédiaire Leçon 04

À la fin de cette leçon, tu sauras

  • définir ce qu'est un résolveur et son rôle ;
  • lire sa signature (parent, args, context, info) ;
  • écrire des résolveurs par champ et par type ;
  • reconnaître le problème N+1 et l'idée du regroupement.
Sommaire de la leçon

Le schéma décrit ce qui existe ; les résolveurs disent comment l'obtenir. Pour chaque champ demandé, le serveur appelle une fonction qui en fournit la valeur. C'est le pont entre le schéma et tes données réelles (base de données, autre API…).

Qu'est-ce qu'un résolveur ?

Un résolveur est une fonction associée à un champ. Quand une requête demande user.name, GraphQL appelle le résolveur du champ user, puis celui de name, et ainsi de suite pour chaque champ sélectionné. La plupart sont implicites (lire une propriété de l'objet), et on n'écrit que ceux qui nécessitent une logique.

La signature d'un résolveur

Un résolveur reçoit quatre arguments, dans cet ordre :

  • parent : l'objet parent (le résultat du champ d'au-dessus).
  • args : les arguments passés au champ (ex. args.id).
  • context : un objet partagé par toute la requête (utilisateur connecté, accès aux données…).
  • info : des métadonnées sur la requête en cours (plus rarement utilisé).

Le context est précieux

Le context est construit à chaque requête : on y met l'utilisateur authentifié, les accès à la base, des chargeurs… Il évite de passer ces dépendances partout et centralise l'autorisation.

On résout au besoin

Les résolveurs ne s'exécutent que pour les champs demandés. Si le client ne réclame pas posts, le résolveur de posts n'est jamais appelé : pas de travail inutile.

Le problème N+1

Attention à un piège classique. Pour une liste de 100 utilisateurs dont on demande les posts, un résolveur naïf fera 1 requête pour les utilisateurs… puis 100 requêtes pour leurs articles : c'est le problème N+1. La parade est de regrouper ces appels (par exemple avec un DataLoader qui rassemble les identifiants et fait une seule requête groupée).

Cas réel

Une page de blog affiche 30 articles avec le nom de leur auteur. Un résolveur author naïf faisait 1 requête pour les articles… puis 30 requêtes pour les auteurs : aux heures de pointe, la charge de la base était multipliée par 30. La parade — un DataLoader qui regroupe les author_id en un seul SELECT … WHERE id IN (…) — a ramené le tout à 2 requêtes. Ce n'est pas un détail d'optimisation : Facebook a créé GraphQL et DataLoader (open source en 2015) précisément pour agréger des centaines de champs par requête sans écrouler ses bases. Aujourd'hui, le regroupement est intégré d'office dans les serveurs GraphQL (Apollo, Yoga).

Pièges fréquents

  • Mettre la logique métier dans le schéma. Le schéma décrit la forme ; la logique vit dans les résolveurs.
  • Ignorer le N+1. Sans regroupement, les relations peuvent générer une avalanche de requêtes.
  • Oublier le context pour l'autorisation. Vérifie les droits dans le résolveur, avec l'utilisateur du context.
  • Tout résoudre, même le non-demandé. Laisse GraphQL n'appeler que les résolveurs des champs réclamés.

Pour aller plus loin

GraphQL exécute les résolveurs en parcourant l'arbre de la requête, de la racine vers les feuilles. Les frères d'un même niveau sont résolus en parallèle ; un champ objet attend son résolveur avant de résoudre ses sous-champs. Comprendre cet ordre aide à raisonner sur les performances.

Pour aller plus loin

Schéma + résolveurs forment ce qu'on appelle parfois le « schéma exécutable ». Des bibliothèques (Apollo Server, GraphQL Yoga…) assemblent les deux et exposent l'endpoint HTTP — c'est ce que tu mettras en place au capstone.

Antisèche : les résolveurs

Glossaire

Résolveur
Fonction serveur associée à un champ ; elle en fournit la valeur et relie le schéma aux données réelles.
parent
Premier argument d'un résolveur : l'objet renvoyé par le résolveur du champ situé au-dessus.
args
Deuxième argument : les arguments passés au champ dans la requête (ex. args.id).
context
Objet construit à chaque requête et partagé par tous les résolveurs : utilisateur authentifié, accès aux données, autorisation.
Résolveur implicite
Champ dont la valeur est simplement lue sur l'objet parent ; aucun code à écrire.
Problème N+1
Une requête de liste qui déclenche une requête par élément pour une relation, soit 1+N appels à la base.
DataLoader
Utilitaire qui rassemble les identifiants d'un même tour d'exécution pour faire une seule requête groupée, corrigeant le N+1.
Schéma exécutable
L'assemblage du schéma (types) et des résolveurs (logique) qu'une bibliothèque comme Apollo Server expose en un endpoint HTTP.

Récap et vérification

  • Un résolveur est la fonction qui fournit la valeur d'un champ ; il relie le schéma aux données.
  • Signature : (parent, args, context, info).
  • On écrit des résolveurs par champ pour les relations et champs calculés.
  • Attention au N+1 : regroupe les appels (DataLoader) pour éviter l'avalanche de requêtes.

  2. À quoi sert le context ?
  3. Qu'est-ce que le problème N+1 et comment l'éviter ?

Exercice 3Défi

Une requête liste 50 auteurs et demande, pour chacun, ses books. Avec le résolveur de l'exercice 2, que se passe-t-il côté base de données, et comment l'améliorer ?

Voir une solution

On déclenche 1 requête pour les 50 auteurs, puis 50 requêtes (une par auteur) pour leurs livres : c'est le problème N+1 (ici 1+50). On l'améliore en regroupant les chargements, par exemple avec un DataLoader qui collecte tous les author.id et fait une seule requête booksByAuthorIds([...]), puis répartit les résultats. On passe de 51 requêtes à 2.
