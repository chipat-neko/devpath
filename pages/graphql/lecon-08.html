Pagination, connexions et erreurs

~40 min Avancé Prérequis : leçon 07

À la fin de cette leçon, tu sauras

  • comparer la pagination par offset et par curseur ;
  • lire le pattern des connexions (edges, node, pageInfo) ;
  • paginer avec first/after ;
  • comprendre les erreurs GraphQL et la data partielle.
Sommaire de la leçon

Une API renvoie rarement une liste entière d'un coup : on la pagine. GraphQL n'impose pas de méthode, mais un pattern s'est imposé — les connexions, popularisées par Relay. On verra pourquoi le curseur bat l'offset, puis comment GraphQL signale les erreurs sans jamais renvoyer de code HTTP d'échec.

Offset : simple mais fragile

La pagination par offset reprend l'idée SQL LIMIT/OFFSET : « donne-moi 10 éléments à partir du 20e ». Facile à écrire, mais deux défauts : si un élément est inséré pendant la navigation, les pages se décalent (doublons ou oublis) ; et un grand offset devient lent (la base doit compter tout ce qu'elle saute).

Curseur : stable et scalable

Un curseur est un marqueur opaque qui désigne une position précise dans la liste (souvent l'identifiant encodé du dernier élément vu). On demande alors « les 10 après ce curseur ». Insérer des éléments ailleurs ne décale rien : on reprend exactement où on s'était arrêté.

Le pattern des connexions

Une connexion enveloppe la liste dans une structure standard : une liste d'edges (chaque edge porte un node — l'élément — et son cursor), plus un objet pageInfo (y a-t-il une page suivante ? quel est le dernier curseur ?). L'edge peut aussi porter des métadonnées de la relation elle-même (par ex. une date d'ajout).

Les erreurs : toujours HTTP 200

Surprise venue de REST : une réponse GraphQL renvoie presque toujours HTTP 200, même en cas d'erreur applicative. Le détail est dans le corps : à côté de data, un tableau errors. Mieux encore, une réponse peut être partielle — certains champs résolus, d'autres à null avec une entrée d'erreur pointant le path fautif.

Le champ extensions.code (par ex. FORBIDDEN, NOT_FOUND) donne un code machine stable, plus fiable que le texte du message destiné aux humains.

Cas réel

Les connexions viennent de Relay, le client GraphQL de Facebook, et sont devenues un standard de fait. L'API de GitHub et celle de Shopify exposent toutes leurs listes en edges/node/pageInfo : parcourir 10 000 dépôts se fait page par page avec after: endCursor, sans jamais surcharger le serveur. Shopify va plus loin : elle facture le coût de chaque requête (un budget de points), ce qui pousse les clients à demander des pages raisonnables plutôt que des listes géantes — un usage direct de la pagination par curseur.

Pièges fréquents

Piège fréquent

Traiter un curseur comme un numéro de page : c'est un marqueur opaque, à ne pas décoder ni fabriquer côté client — on ne fait que renvoyer endCursor. Autre piège classique : vérifier le statut HTTP pour détecter une erreur. En GraphQL, le statut est 200 ; il faut inspecter le tableau errors du corps (et gérer la data partielle).

Pour aller plus loin

Pour aller plus loin

La spécification Relay Cursor Connections détaille les arguments symétriques first/after et last/before (paginer en avant ou en arrière). Côté erreurs, certaines API adoptent le pattern « errors as data » : modéliser les échecs métier attendus comme des types de l'union renvoyée (par ex. UserResult = User | NotFoundError), en réservant le tableau errors aux vrais incidents techniques.

Glossaire

Pagination par offset
Découper une liste par « saute N, prends M » (limit/offset) ; simple mais sensible aux insertions et lente sur de grands décalages.
Curseur (cursor)
Marqueur opaque désignant une position précise dans la liste ; on l'utilise avec after pour reprendre exactement où l'on s'était arrêté.
Connexion (Connection)
Enveloppe standard d'une liste paginée : edges + pageInfo, issue de la spécification Relay.
Edge
Élément d'une connexion : contient un node et son cursor, et parfois des métadonnées de la relation.
Node
L'objet réel transporté par un edge (le post, l'utilisateur…).
pageInfo
Objet d'état de pagination : hasNextPage, endCursor (et leurs symétriques arrière).
Champ errors
Tableau, à côté de data, listant les erreurs ; la réponse HTTP reste 200, et data peut être partielle.
extensions
Espace libre d'une erreur pour des infos machine, dont un code stable (NOT_FOUND, FORBIDDEN…).

Récap et vérification

  • L'offset est simple mais se décale aux insertions ; le curseur est stable.
  • Une connexion = edges (node + cursor) + pageInfo.
  • On charge la suite avec after: endCursor.
  • Les erreurs vivent dans errors[] (HTTP 200), avec path et extensions.code ; la data peut être partielle.

  2. Que contient un edge, et à quoi sert pageInfo ?
  3. Comment détecte-t-on une erreur, puisque le statut HTTP est 200 ?

Exercice 3Défi

Une réponse contient data.user rempli mais data.orders à null, avec une entrée dans errors. Explique comment un client doit interpréter cela.

Voir une solution

C'est une réponse partielle (HTTP 200). Le client peut afficher user, qui a bien été résolu. Pour orders, il lit l'entrée du tableau errors : son path vaut ["orders"] (ce qui a échoué) et son extensions.code donne la cause machine (ex. FORBIDDEN). Il affiche alors un message ciblé pour cette section, sans jeter toute la réponse.
