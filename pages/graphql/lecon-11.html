Module 05 · Projet — Leçon 11

Projet — une API GraphQL de production

~44 min Intermédiaire Tout le cours

À la fin de cette leçon, tu sauras

  • assembler toutes les briques du cours en une API cohérente ;
  • dérouler une checklist de production avant d'exposer une API ;
  • situer chaque notion (schéma, résolveurs, DataLoader, sécurité) ;
  • mener seul ton mini-projet fil rouge de bout en bout.
Sommaire de la leçon

Nous y voilà : la dernière leçon rassemble tout le cours. Tu sais décrire un schéma typé, écrire des requêtes et des mutations, brancher des résolveurs, paginer, gérer les erreurs, éviter le N+1 avec DataLoader et sécuriser l'endpoint. Voyons comment ces pièces s'emboîtent dans une API de production — puis lance ton propre projet.

La vue d'ensemble

Une requête traverse toujours la même chaîne : le serveur la valide (profondeur, coût), l'authentifie via le context, puis exécute les résolveurs, qui s'appuient sur des DataLoaders pour parler efficacement à la base.

La checklist de production

Avant d'exposer une API GraphQL, on déroule une liste courte mais non négociable :

Avant de mettre en ligne

  • Schéma clair et versionné ; types ! (non-null) posés à bon escient.
  • Pagination sur toute liste qui peut grandir (curseurs, leçon 8).
  • N+1 réglé : un DataLoader par requête pour chaque relation (leçon 9).
  • Bornes : limite de profondeur + analyse de coût + rate limiting (leçon 10).
  • Auth : authentification dans le context, autorisation dans les résolveurs.
  • Erreurs propres : codes dans extensions, messages internes masqués en prod.

Cas réel

Quand Shopify expose son Admin API en GraphQL à des centaines de milliers de marchands, chaque brique de cette checklist est activée : pagination par curseur obligatoire sur les grandes collections, budget de coût par requête (comme GitHub), autorisation fine par champ selon les permissions de l'app, et erreurs typées. L'API « liste de tâches » que tu vas écrire suit exactement la même colonne vertébrale, à plus petite échelle.

Mini-projet fil rouge — ton API GraphQL

À toi de jouer ! Construis une petite API GraphQL de bout en bout sur un thème de ton choix (tâches à faire, films, recettes…). L'objectif est d'enchaîner correctement schéma → résolveurs → test, puis de la durcir avec ce que tu as appris dans le module avancé.

Ce que tu vas construire

Une API « liste de tâches » : un type Task, une query pour lister les tâches, une query pour en lire une par id, et une mutation pour en ajouter — avec des résolveurs sur un tableau en mémoire, puis une touche de production.

Étapes

1. Le schéma

Un type Task (id, title, done), un input d'ajout, et les types Query/Mutation.

2. Les résolveurs

Query.tasks, Query.task(id) et Mutation.addTask sur un tableau en mémoire.

3. Tester

Une query pour lister, une mutation pour ajouter, puis relister pour vérifier.

4. Durcir (bonus)

Ajoute une vérification d'accès dans addTask (via ctx.user) et une limite de profondeur au serveur.

Mini-projetCapstone

Écris le schéma et les résolveurs. Quand tu as essayé, déplie une solution de référence.

Voir une solution complète

Et après ce cours ?

Tu maîtrises le socle de GraphQL. Les suites naturelles : brancher une vraie base de données, explorer les subscriptions (temps réel, le troisième type racine), la fédération (composer plusieurs services en un schéma unique), et l'outillage de codegen qui génère des types clients à partir du schéma.

Pour aller plus loin

Fais relire ton schéma par quelqu'un qui ne connaît pas ton domaine : s'il devine à quoi sert chaque champ sans explication, ton contrat est bon. Puis va lire un schéma public — celui de GitHub ou de Shopify s'explore par introspection — et observe leurs conventions : comment ils nomment les connexions, ce que renvoie une mutation (le payload), quels codes d'erreur ils publient. C'est la meilleure école de design de schéma : ces API vivent depuis des années sans casser leurs clients.

Glossaire

Capstone
Projet de synthèse en fin de cours qui assemble toutes les notions apprises en une réalisation cohérente.
Schéma exécutable
L'assemblage du schéma (SDL) et des résolveurs qu'une bibliothèque transforme en API interrogeable.
Checklist de production
Liste des garde-fous (pagination, N+1, bornes, auth, erreurs) à vérifier avant d'exposer une API.
Subscription
Troisième type racine (après Query/Mutation) pour recevoir des données en temps réel (push).
Fédération
Technique qui compose plusieurs services GraphQL en un seul schéma unifié.
Codegen
Génération automatique de types et de clients à partir du schéma, pour un code fortement typé de bout en bout.
Endpoint
L'URL unique du serveur GraphQL, appelée en POST : c'est la requête qui varie, pas l'adresse.

Récap et vérification

  • Une requête de production traverse : validation → context → résolveurs → DataLoader.
  • La checklist réunit schéma, pagination, N+1, bornes, auth et erreurs.
  • Le schéma reste le contrat commun sous toute la chaîne.
  • Les suites : base de données, subscriptions, fédération, codegen.

Exercices

Exercice 1Échauffement

Ta liste de tâches va grandir : tasks: [Task!]! renverrait un jour 50 000 lignes d'un coup. Transforme cette lecture en connexion paginée par curseur : déclare tasks(first: Int!, after: String): TaskConnection! et les types TaskConnection, TaskEdge et PageInfo qui vont avec.

Voir une solution
Exercice 2Application

Chaque Task a un owner. Sur une page de 100 tâches, un résolveur naïf déclenche 100 allers-retours en base : c'est le N+1. Crée un DataLoader neuf à chaque requête dans le context, puis branche-le sur Task.owner.

Voir une solution
Exercice 3Défi

Reprends la checklist de production. Pour une API « liste de tâches » exposée publiquement, cite deux bornes que tu activerais et explique brièvement contre quoi.

Voir une solution

Deux choix pertinents parmi : une limite de profondeur (contre les requêtes infiniment imbriquées), une analyse de coût (contre les requêtes plates mais très larges, ex. tasks(first: 100000)), un rate limiting par coût (contre l'abus par volume). On y ajoute l'authentification sur les mutations pour éviter que n'importe qui écrive. Chacune ferme une porte différente : on les combine, aucune ne suffit seule.
