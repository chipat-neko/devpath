Les mutations

~33 min Intermédiaire Leçon 03

À la fin de cette leçon, tu sauras

  • écrire une mutation pour créer, modifier ou supprimer ;
  • utiliser un input type pour passer un objet en argument ;
  • renvoyer la donnée modifiée dans la réponse ;
  • appliquer les conventions de nommage des mutations.
Sommaire de la leçon

Les queries lisent ; les mutations écrivent. Pour créer, modifier ou supprimer des données, GraphQL passe par un second type racine, Mutation. La mécanique est très proche des requêtes, avec quelques conventions propres.

Le type racine Mutation

Comme Query liste les lectures, le type Mutation liste les écritures possibles. Chaque champ y est une action : createUser, updatePost, deleteComment… On l'appelle avec le mot-clé mutation.

Une mutation renvoie des données

Après l'écriture, on sélectionne des champs à recevoir (ici id et name du nouvel utilisateur). Pratique : le client récupère l'objet à jour sans refaire une query.

Cas réel

Sur un réseau social, quand tu likes une publication, l'application envoie une mutation likePost(id) qui renvoie le post avec son nouveau compteur de likes. Les clients GraphQL comme Apollo reconnaissent l'objet à son id et mettent à jour le cache automatiquement : le compteur à l'écran s'incrémente sans recharger la page ni refaire une query. Mieux, Apollo sait afficher un résultat optimiste (avant même la réponse du serveur) puis se corriger en cas d'erreur. Tout cela repose sur une convention simple : une mutation renvoie l'objet modifié.

Les input types

Passer beaucoup d'arguments un par un devient lourd. Un input type regroupe ces arguments en un seul objet d'entrée, plus lisible et réutilisable.

type vs input

Un type décrit des données qu'on renvoie ; un input décrit des données qu'on reçoit en argument. On ne peut pas utiliser un type de sortie comme argument : c'est pour ça que les input existent.

Conventions de nommage

Quelques habitudes répandues rendent une API prévisible :

  • Verbe + nom : createUser, updateUser, deleteUser.
  • Une mutation = une action claire, pas un fourre-tout.
  • Renvoyer l'objet modifié (ou un type de « payload » dédié) pour éviter une query de suivi.
  • Input dédié par mutation dès qu'il y a plusieurs champs.

Plusieurs mutations dans une requête

On peut envoyer plusieurs mutations en une fois. Contrairement aux champs d'une query (résolus en parallèle), les mutations d'une même requête s'exécutent en série, de haut en bas — l'ordre est garanti.

Pièges fréquents

  • Utiliser un type comme argument. Les arguments d'objet doivent être des input.
  • Ne rien renvoyer d'utile. Renvoie l'objet modifié (ou un statut) pour éviter une query de suivi.
  • Mettre une écriture dans une query. Les lectures n'ont pas vocation à modifier les données ; les écritures passent par Mutation.
  • Compter sur un ordre en query. Seules les mutations d'une requête sont garanties en série.

Pour aller plus loin

Beaucoup d'API renvoient un type de payload dédié plutôt que l'objet brut : par exemple CreateUserPayload { user: User, errors: [Error!] }. Cela permet de transporter, à côté de la donnée, des informations sur le succès ou les erreurs métier de l'opération.

Pour aller plus loin

La validation et l'autorisation (a-t-on le droit de créer cet utilisateur ?) se font côté serveur, dans le résolveur de la mutation — l'objet de la prochaine leçon.

Glossaire

Mutation
Type racine des opérations d'écriture (créer, modifier, supprimer) ; appelée avec le mot-clé mutation.
Input type
Type d'objet destiné à être passé en argument ; regroupe plusieurs champs reçus en un seul objet d'entrée.
Type de sortie
Type renvoyé par un champ ou une mutation (ex. User) ; ne peut pas servir d'argument.
Payload
Type de retour dédié à une mutation, transportant l'objet et des informations de succès ou d'erreur.
En série
Mode d'exécution des mutations d'une même requête : l'une après l'autre, de haut en bas, ordre garanti.
Résolveur
Fonction serveur qui exécute réellement une opération (validation, autorisation, écriture) ; sujet de la leçon suivante.

Récap et vérification

  • Les mutations écrivent (créer/modifier/supprimer) ; elles vivent dans le type racine Mutation.
  • Un input type regroupe les arguments en un objet d'entrée.
  • Une mutation renvoie des champs : on récupère l'objet à jour sans query de suivi.
  • Conventions : verbe + nom, une action par mutation, input dédié.

Vérifie ta compréhension

  1. Quel type racine porte les écritures ?
  2. Pourquoi a-t-on besoin des input types ?
  3. Que renvoie-t-on typiquement après une mutation ?

Exercice 3Défi

Pourquoi ne peut-on pas réutiliser le type Book (type de sortie) comme argument d'une mutation ? Que fait-on à la place ?

Voir une solution

Parce que GraphQL distingue les types de sortie (ce qu'on renvoie) des types d'entrée (ce qu'on reçoit en argument). Un type d'objet peut contenir des champs non valides en entrée (champs calculés, relations résolues côté serveur…). On crée donc un input dédié (ex. CreateBookInput) qui ne contient que les champs réellement attendus en entrée.
