Performance : le problème N+1 et DataLoader

~42 min Avancé Prérequis : leçon 05

À la fin de cette leçon, tu sauras

  • diagnostiquer le problème N+1 dans des résolveurs ;
  • expliquer le batching et le cache par requête ;
  • écrire un DataLoader et l'appeler depuis un résolveur ;
  • citer d'autres leviers de performance (coût, cache).
Sommaire de la leçon

La flexibilité de GraphQL a un revers : un client peut demander une liste et, pour chaque élément, une relation. Si chaque relation déclenche sa propre requête à la base, on tombe dans le problème N+1 — le piège de performance le plus courant. On l'a croisé en leçon 5 ; voyons-le en détail et surtout sa solution canonique : DataLoader.

Le problème N+1

Prends une requête qui liste des posts et, pour chacun, son auteur. Le résolveur de liste fait 1 requête (les posts). Puis, pour chaque post, le résolveur author fait 1 requête. Avec N posts, cela fait 1 + N requêtes à la base — une avalanche invisible dans le code.

La solution : DataLoader

DataLoader (une petite bibliothèque de Facebook) s'intercale entre les résolveurs et la base. On ne l'appelle plus directement : on demande une clé avec .load(id). DataLoader attend la fin du tour d'exécution, rassemble toutes les clés demandées, et appelle une seule fois une fonction de lot (batch function) avec le tableau des clés.

Les N appels .load(post.authorId) du même tour sont regroupés : la batch function reçoit [1, 2, 3, …] et renvoie les utilisateurs correspondants, dans le même ordre (contrat essentiel).

Un loader neuf à chaque requête

Le cache de DataLoader vit le temps d'une seule requête HTTP. On crée donc les loaders dans le context (leçon 5), à chaque requête entrante : ainsi deux utilisateurs ne partagent jamais un cache, et une donnée modifiée entre deux requêtes n'est pas servie périmée.

Cas réel

DataLoader a été écrit par Lee Byron chez Facebook, l'un des créateurs de GraphQL. L'entreprise servait déjà des milliards de requêtes : sans regroupement, une seule page de fil d'actualité aurait déclenché des milliers de lectures unitaires. L'idée — « accumule les demandes d'un tour, résous-les en lot » — est si générale qu'elle a été portée dans presque tous les langages (Java, Python, Go, Rust…). C'est aujourd'hui la première optimisation qu'on ajoute à tout serveur GraphQL de production.

Astuce

La batch function doit renvoyer un tableau de même longueur que celui des clés, dans le même ordre. Si une clé n'a pas de valeur, mets null à sa place (pas « rien ») : DataLoader apparie résultats et clés par leur position. Un décalage d'ordre est le bug classique — l'auteur A se retrouve sur le post B.

D'autres leviers de performance

Le N+1 réglé, deux autres sujets reviennent : limiter le coût des requêtes (une requête trop profonde ou trop large peut surcharger le serveur — on le verra en leçon sécurité, avec les limites de profondeur et de complexité), et mettre en cache des réponses ou des champs stables. GraphQL propose aussi @defer/@stream pour livrer d'abord l'essentiel puis le reste en flux.

Pièges fréquents

Piège fréquent

Créer un seul loader partagé au démarrage du serveur : son cache deviendrait global et servirait des données périmées (ou celles d'un autre utilisateur). Toujours instancier les loaders par requête, dans le context. Et n'oublie pas : DataLoader résout le nombre de requêtes, pas une requête individuellement lente — profile aussi tes requêtes de base.

Antisèche

Glossaire

Problème N+1
Motif où résoudre une relation élément par élément déclenche 1 requête de liste puis N requêtes unitaires, soit 1+N appels.
Batching
Rassembler plusieurs demandes émises dans le même tour d'exécution pour les satisfaire en une seule requête groupée.
DataLoader
Bibliothèque qui, entre résolveurs et source de données, fait le batching et le cache par requête via .load(clé).
Batch function
Fonction passée à DataLoader qui reçoit le tableau des clés et renvoie les valeurs dans le même ordre et la même longueur.
Cache par requête
Mémoïsation des clés déjà demandées, valable le temps d'une seule requête HTTP ; évite de recharger une même clé.
Tour d'exécution (tick)
Le cycle de la boucle d'événements pendant lequel DataLoader accumule les .load() avant de déclencher le lot.
context
Objet créé à chaque requête et partagé par les résolveurs ; l'endroit où l'on instancie des loaders neufs.

Récap et vérification

  • Le N+1 naît d'un résolveur de relation appelé une fois par élément.
  • DataLoader le corrige par batching + cache par requête.
  • La batch function renvoie les valeurs dans le même ordre que les clés.
  • On crée les loaders par requête, dans le context.

Vérifie ta compréhension

  1. Que doit renvoyer la batch function, et dans quel ordre ?
  2. Quels sont les deux mécanismes de DataLoader ?
  3. Pourquoi créer un loader neuf à chaque requête ?

Exercices

Exercice 1Échauffement

Une requête liste 30 commentaires et demande, pour chacun, son author. Sans DataLoader, combien de requêtes la base reçoit-elle ? Explique.

Voir une solution

31 requêtes : 1 pour lister les 30 commentaires, puis 1 par commentaire pour son auteur (30). C'est le problème N+1 avec N = 30 (soit 1+30).

Exercice 2Application

Complète la batch function pour qu'elle renvoie les auteurs dans le même ordre que les ids reçus.

Voir une solution
Exercice 3Défi

Avec le loader, la requête de l'exercice 1 déclenche combien de requêtes ? Et si deux commentaires ont le même auteur, que se passe-t-il ?

Voir une solution

2 requêtes : 1 pour les commentaires, puis 1 seule requête groupée pour tous les auteurs (batching). Si deux commentaires partagent un auteur, la clé n'est demandée qu'une fois grâce au cache par requête : la batch function reçoit des identifiants dédupliqués, et les deux commentaires reçoivent le même objet auteur.
