La concurrence avec Grand Central Dispatch

~52 min Avancé Prérequis : leçon 8

À la fin de cette leçon, tu sauras

  • expliquer pourquoi il ne faut jamais bloquer le thread principal ;
  • utiliser les files de GCD (principale et globales) ;
  • distinguer dispatch_async et dispatch_sync ;
  • appliquer le motif travail en fond → retour au principal.
Sommaire de la leçon

Une application Apple s'anime sur un fil d'exécution privilégié : le thread principal. C'est lui qui dessine l'interface et réagit aux gestes de l'utilisateur. Si on lui confie une tâche longue — télécharger un fichier, lire une grosse base — il ne peut plus rien afficher : l'écran gèle. La solution s'appelle Grand Central Dispatch (GCD) : une bibliothèque C, intégrée à Foundation, qui distribue le travail sur plusieurs fils sans qu'on ait à gérer les threads à la main. Cette leçon en pose les bases.

Le problème : un thread principal qui gèle

Tout le code que tu as écrit jusqu'ici s'exécute séquentiellement sur un seul fil. Dans une vraie application, ce fil est le thread principal, et il a un contrat : rester disponible pour redessiner l'écran ~60 fois par seconde. Une opération qui dure une seconde le bloque une seconde ; pendant ce temps, plus aucune animation, plus aucun bouton ne répond.

La règle est simple : le travail long va ailleurs, et seule la mise à jour de l'interface revient au thread principal.

Les files de distribution (dispatch queues)

GCD ne raisonne pas en « threads » mais en files (queues) : on dépose un bloc de travail dans une file, et GCD se charge de l'exécuter sur un fil disponible du système. Deux familles suffisent pour commencer :

  • la file principale (dispatch_get_main_queue()) : série (une tâche à la fois), liée au thread principal — c'est la seule où l'on a le droit de toucher à l'interface ;
  • les files globales (dispatch_get_global_queue(...)) : concurrentes, partagées, faites pour le travail de fond.

Déposer du travail : async et sync

On dépose un block (leçon 8) dans une file avec deux fonctions :

  • dispatch_async(file, ^{ … }) — dépose et rend la main aussitôt : le code qui suit continue sans attendre ;
  • dispatch_sync(file, ^{ … }) — dépose et attend la fin du bloc avant de continuer.

Dans l'immense majorité des cas, on veut dispatch_async : lancer le travail sans bloquer l'appelant. dispatch_sync est un piège classique : appelé sur la file principale vers la file principale, il fige l'application (deadlock).

Jamais d'interface hors du thread principal

Modifier une vue (label.text, imageView.image…) depuis une file de fond provoque des bugs d'affichage imprévisibles, voire des plantages. Toute mise à jour d'interface doit repasser par dispatch_get_main_queue(). C'est l'erreur nº 1 des débutants en concurrence sur iOS.

Le motif fondamental : travailler en fond, revenir au principal

Ces deux idées se combinent en un motif qu'on retrouve partout dans le code Cocoa : on part sur une file de fond pour le travail long, puis on imbrique un retour sur la file principale pour l'affichage.

Cas réel

Charger l'avatar d'un contact dans une liste (par exemple une cellule de UITableView) est l'usage type. Le réseau est lent et imprévisible ; le faire sur le thread principal saccaderait le défilement. On télécharge donc l'image en fond, puis on revient au principal pour l'afficher :

C'est exactement ce que font, en coulisses, les bibliothèques d'images comme SDWebImage ; GCD en est le moteur.

Trois outils GCD bien utiles

Au-delà du motif principal, trois fonctions reviennent souvent :

dispatch_after planifie un bloc dans le futur ; dispatch_once garantit qu'un code (typiquement la création d'un singleton) ne s'exécute qu'une fois, même si plusieurs fils l'atteignent en même temps.

Choisir la bonne priorité (QoS)

Le premier argument de dispatch_get_global_queue est une classe de qualité de service qui indique au système l'urgence du travail : QOS_CLASS_USER_INTERACTIVE (quasi immédiat), USER_INITIATED (l'utilisateur attend le résultat), UTILITY (tâche longue avec barre de progression), BACKGROUND (invisible, économe en énergie). Bien la choisir aide le système à ménager la batterie.

Pour aller plus loin

Au-dessus de GCD

GCD est la couche bas niveau. Par-dessus, Cocoa offre NSOperation et NSOperationQueue, qui ajoutent l'annulation, les dépendances entre tâches et une limite de concurrence — pratique pour orchestrer plusieurs travaux. Et côté Swift moderne, async/await et les acteurs reprennent ces idées avec une syntaxe linéaire ; mais sous le capot, on retrouve toujours ces mêmes files. Comprendre GCD, c'est comprendre le socle de toute la concurrence Apple.

Glossaire

Grand Central Dispatch (GCD)
Bibliothèque C d'Apple qui répartit des blocs de travail sur des files, sans gérer les threads soi-même.
Thread principal
Le fil qui dessine l'interface et traite les gestes ; il ne doit jamais être bloqué par un travail long.
File (queue)
Une file d'attente où l'on dépose des blocs ; GCD les exécute sur un fil disponible.
File principale
dispatch_get_main_queue() : file série liée au thread principal, seule autorisée à toucher l'interface.
File globale
dispatch_get_global_queue(...) : file concurrente partagée, pour le travail de fond.
dispatch_async
Dépose un bloc et rend la main immédiatement, sans attendre son exécution.
QoS (qualité de service)
Étiquette d'urgence d'un travail qui aide le système à arbitrer priorité et énergie.
dispatch_once
Garantit qu'un bloc ne s'exécute qu'une fois dans la vie du programme, même en concurrence.

Récap et vérification

  • Le thread principal dessine l'interface : ne jamais l'occuper avec un travail long.
  • GCD distribue des blocs dans des files : principale (série, UI) et globales (concurrentes, fond).
  • dispatch_async dépose sans attendre ; dispatch_sync attend (gare aux deadlocks).
  • Motif clé : travailler en fond, puis dispatch_async(main) pour toucher l'UI.

Exercice 3Défi

Pourquoi dispatch_sync(dispatch_get_main_queue(), ^{ … }); appelé depuis le thread principal fige-t-il l'application ?

Voir une solution

Parce que dispatch_sync attend que le bloc s'exécute avant de rendre la main. Or la file principale est série : elle est justement occupée par le code qui vient d'appeler dispatch_sync. Le bloc ne pourra donc jamais démarrer, et l'appelant l'attend indéfiniment : c'est un deadlock. On utilise dispatch_async (qui n'attend pas), ou l'on vérifie qu'on n'est pas déjà sur la file visée.
