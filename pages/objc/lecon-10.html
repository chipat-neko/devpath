Gérer les erreurs : NSError et exceptions

~50 min Avancé Prérequis : leçon 9

À la fin de cette leçon, tu sauras

  • distinguer une erreur récupérable d'un bug ;
  • utiliser le pattern NSError ** de Cocoa ;
  • créer et propager un NSError depuis tes méthodes ;
  • savoir à quoi servent (rarement) les exceptions.
Sommaire de la leçon

Un programme rencontre deux familles de problèmes très différentes. Il y a ce qu'on attend — un fichier absent, un réseau coupé, une saisie invalide : ce sont des erreurs récupérables, et Objective-C les traite avec un objet NSError. Et il y a ce qu'on ne devrait jamais voir — un indice hors limites, un argument interdit : ce sont des bugs, et ils lèvent une NSException. Toute la maîtrise des erreurs en Cocoa tient dans cette distinction : on récupère des premières, on corrige les secondes.

Le pattern NSError

La convention Cocoa est constante : une méthode qui peut échouer prend un dernier paramètre (NSError **)error et renvoie une valeur sentinelle — nil pour un objet, NO pour un booléen — quand ça se passe mal. Exemple canonique : lire un fichier.

On passe l'adresse de notre variable (&error) pour que la méthode puisse la remplir. Règle d'or : on teste d'abord la valeur de retour (nil/NO), jamais error directement — error n'est fiable que si le retour a déjà signalé l'échec.

Anatomie d'un NSError

Un NSError porte trois informations : un domaine (qui a produit l'erreur), un code (un entier propre à ce domaine) et un userInfo (un dictionnaire de détails, dont le message lisible).

Le raccourci error.localizedDescription lit la clé NSLocalizedDescriptionKey du userInfo : c'est le message qu'on montre à l'utilisateur ou qu'on journalise.

Propager sa propre erreur

Quand tu écris une méthode qui peut échouer, respecte la même convention : prends un (NSError **)error et remplis-le avant de renvoyer NO.

Le if (error) avant de déréférencer est essentiel : un appelant qui ne veut pas le détail passe NULL, et déréférencer NULL planterait.

Le retour d'abord, error ensuite

Une méthode Cocoa n'est pas obligée de mettre error à nil quand elle réussit : la variable peut contenir n'importe quoi. Le seul signal fiable de succès ou d'échec est la valeur de retour. Écris toujours if (resultat == nil) { … lire error … }, jamais if (error != nil) comme premier test.

Les exceptions : pour les bugs

L'autre mécanisme, @try/@catch/@finally avec @throw, existe mais joue un rôle bien plus étroit. Une NSException signale une erreur de programmation : on l'utilise pour repérer un bug pendant le développement, pas pour piloter le déroulé normal.

En pratique, on ne rattrape presque jamais une exception : elle révèle un bug (indice hors limites, argument nil interdit, sélecteur inconnu) qu'il faut corriger, pas gérer. Le bloc @finally, lui, s'exécute quoi qu'il arrive — utile pour libérer une ressource.

Pièges fréquents

N'utilise pas les exceptions comme en Python ou Java

Dans beaucoup de langages, lever et rattraper une exception est un flux de contrôle normal. Pas en Cocoa : ici, une exception qui remonte jusqu'en haut termine l'application, et le code Foundation n'est pas « exception-safe » (rattraper au milieu peut laisser des objets dans un état incohérent). Pour tout ce qui est prévisible et récupérable, c'est NSError, pas @throw.

Glossaire

NSError
Objet décrivant une erreur récupérable : il porte un domaine, un code et un dictionnaire de détails.
Pattern error:
Convention Cocoa : dernier paramètre (NSError **) que la méthode remplit en cas d'échec.
Valeur sentinelle
Le nil ou NO renvoyé pour signaler l'échec ; c'est lui qu'on teste en premier.
domain / code
La source de l'erreur (chaîne) et un entier qui l'identifie dans ce domaine.
userInfo
Dictionnaire de détails ; sa clé NSLocalizedDescriptionKey donne localizedDescription.
NSException
Signale une erreur de programmation (bug) ; en Cocoa on la corrige plutôt que de la rattraper.
@finally
Bloc exécuté quoi qu'il arrive après un @try ; sert au nettoyage.

Récap et vérification

  • Deux familles : erreur récupérable (NSError) vs bug (NSException).
  • Pattern Cocoa : paramètre (NSError **)error, retour nil/NO, on teste le retour.
  • Un NSError = domain + code + userInfo ; message via localizedDescription.
  • Les exceptions restent pour les bugs ; ne pas s'en servir comme flux de contrôle.
