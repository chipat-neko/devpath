Module 1 · Les bases d'Objective-C — Leçon 03

Envoyer des messages

~50 min Avancé Prérequis : leçon 2

À la fin de cette leçon, tu sauras

  • envoyer un message avec [objet methode] ;
  • passer des arguments nommés (methode:avec:) ;
  • imbriquer les messages ;
  • comprendre l'envoi de message à nil.
Sommaire de la leçon

Si Objective-C n'avait qu'une seule idée à retenir, ce serait celle-ci : l'envoi de messages. Toute interaction entre objets passe par là. Comprendre précisément la syntaxe des messages — y compris ses cas étranges, comme l'envoi à nil — c'est tenir la clé de tout le langage. Cette leçon décortique cette mécanique centrale.

Envoyer un message simple

Un message demande à un objet (le receveur) d'exécuter une méthode. Syntaxe : crochet ouvrant, le receveur, le nom du message, crochet fermant.

Le résultat du message (sa valeur de retour) peut être affecté à une variable, comme ici n et maj.

Les messages avec arguments

Quand un message prend des arguments, le nom de la méthode est entrelacé avec eux, chaque partie suivie de deux-points. C'est la signature visuelle d'Objective-C.

C'est déroutant au premier abord, mais élégant : les arguments sont nommés par les morceaux du message. replaceObjectAtIndex:2 withObject:@"x" se lit presque comme une phrase : « remplace l'objet à l'indice 2 par l'objet "x" ». Le nom officiel de la méthode est l'ensemble des étiquettes : replaceObjectAtIndex:withObject:.

Compter les deux-points

Le nom complet d'une méthode s'appelle un sélecteur. Astuce de lecture : compte les deux-points. length (aucun :) ne prend pas d'argument ; objectAtIndex: (un :) en prend un ; replaceObjectAtIndex:withObject: (deux :) en prend deux. On référence un sélecteur avec @selector(objectAtIndex:).

Les messages imbriqués

Le résultat d'un message peut servir de receveur à un autre : on imbrique alors les crochets, de l'intérieur vers l'extérieur.

On lit de l'intérieur : [nom uppercaseString] produit une chaîne, à laquelle on envoie length. L'imbrication [[… alloc] init] est si fréquente (créer un objet) qu'elle devient un réflexe — on y reviendra leçon 4.

Les méthodes de classe

Certains messages s'envoient non à un objet, mais à la classe elle-même : ce sont souvent des « fabriques » qui créent un objet. Le receveur est alors le nom de la classe.

On distingue donc les messages d'instance (à un objet) des messages de classe (au type lui-même). On formalisera cette différence leçon 5.

Envoyer un message à nil : ça ne plante pas !

Voici une singularité fondamentale d'Objective-C. Dans la plupart des langages, appeler une méthode sur null provoque un plantage. En Objective-C, envoyer un message à nil est sans danger : il ne se passe rien, et le résultat est nil (ou 0).

Cette tolérance simplifie beaucoup de code : on n'a pas à vérifier nil avant chaque appel. Mais elle a un revers : un bug peut passer inaperçu si un objet est nil par erreur, car rien ne se produit au lieu de signaler le problème.

Cas réel

Le silence de nil n'est pas qu'une curiosité : des pans entiers de Cocoa en dépendent. Dans le patron delegate (leçon 7), un objet prévient son « délégué » par [self.delegate didFinish] sans jamais vérifier qu'il existe : si aucun délégué n'est branché (delegate == nil), l'appel est simplement ignoré. Cela évite des dizaines de if (delegate != nil) et allège le code — à condition de rester conscient que nil avale les erreurs autant que les cas prévus.

Pièges fréquents

Piège fréquent

Se laisser piéger par le silence de nil. Si une méthode renvoie soudain nil ou 0 sans raison apparente, vérifie que le receveur n'était pas nil : l'envoi a été ignoré silencieusement. Cette « sûreté » pratique masque parfois la vraie cause d'un bug. En cas de comportement bizarre, le premier réflexe est de vérifier qu'aucun objet impliqué n'est nil à son insu.

Pour aller plus loin

Pour aller plus loin

Derrière chaque [obj message], le compilateur génère un appel à objc_msgSend, la fonction du runtime qui cherche, à l'exécution, quelle méthode exécuter pour ce message. C'est ce mécanisme dynamique qui permet le method swizzling (échanger des implémentations à chaud), la délégation, et l'introspection — des techniques avancées qui font la richesse (et parfois la complexité) des frameworks Apple.

Antisèche — les formes d'un message

Glossaire

Message
Demande faite à un objet d'exécuter une méthode, écrite entre crochets [receveur message:arg].
Receveur
L'objet (ou la classe) à qui l'on envoie le message : le premier élément entre crochets.
Sélecteur
Nom complet d'une méthode, deux-points inclus (replaceObjectAtIndex:withObject:). Chaque : correspond à un argument.
Message d'instance
Message envoyé à un objet (une instance) : [monTableau count].
Message de classe
Message envoyé à la classe elle-même, souvent une fabrique : [NSArray array].
Message imbriqué
Message dont le receveur est le résultat d'un autre message ; évalué de l'intérieur vers l'extérieur.
Envoi à nil
Envoyer un message à nil ne fait rien et renvoie nil/0 — commode, mais peut masquer un bug.
objc_msgSend
Fonction du runtime qui, pour chaque [obj message], retrouve à l'exécution la méthode à appeler.

Récap et vérification

  • Tout passe par l'envoi de messages : [receveur message:arg].
  • Les arguments sont entrelacés et nommés : replaceObjectAtIndex:withObject:.
  • Messages imbriqués ([[… alloc] init]) ; messages de classe (receveur = nom de classe).
  • Envoyer un message à nil ne plante pas : renvoie nil/0 (commode mais peut masquer un bug).

Le résultat est 0, et il n'y a aucun plantage. En Objective-C, envoyer un message à nil est une opération valide qui ne fait rien et renvoie une valeur « nulle » (nil pour un objet, 0 pour un nombre).
