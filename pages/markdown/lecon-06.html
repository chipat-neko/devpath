Markdown en pratique

~36 min Intermédiaire Leçon 05 requise

À la fin de cette leçon, tu sauras

  • rédiger un bon README ;
  • mêler HTML et Markdown au besoin ;
  • situer les variantes (CommonMark, MDX) ;
  • appliquer les bonnes pratiques de rédaction.
Sommaire de la leçon

Tu connais toute la syntaxe ; voyons maintenant comment bien l'employer. Cette dernière leçon est pratique : structurer un README utile, savoir quand glisser du HTML, comprendre les variantes de Markdown, et adopter les habitudes qui rendent tes documents clairs. C'est ce qui transforme la connaissance de la syntaxe en documents que les gens ont plaisir à lire.

Un bon README

Le README est la première chose qu'un visiteur lit sur un projet : c'est sa vitrine et son mode d'emploi. Un bon README suit une structure éprouvée :

Les ingrédients d'un bon README : un titre et une description claire en tête (le quoi et le pour qui), une section installation avec les commandes exactes (en blocs de code), un exemple d'utilisation minimal, et les infos pratiques (fonctionnalités, contribution, licence). Tout ce que tu as appris se combine ici : titres, listes, code, liens, tableaux.

Cas réel

Sur GitHub, le README.md est la page d'accueil du dépôt : c'est lui qui s'affiche sous la liste des fichiers. Les projets populaires (React, Vue, VS Code…) l'ouvrent presque tous par une rangée de badges (build, version, licence) — de simples images-liens en Markdown — puis une description, un exemple minimal, et des liens vers la documentation complète. Un README clair fait la différence entre un projet qu'on adopte et un projet qu'on ignore : beaucoup de développeurs décident d'utiliser (ou non) une bibliothèque rien qu'en lisant son README.

Le HTML dans Markdown

Markdown ne couvre pas tout (centrer un élément, fusionner des cellules de tableau, ajouter un détail repliable). Heureusement, la plupart des outils permettent d'insérer du HTML directement dans le Markdown pour les cas non couverts.

C'est une soupape de sécurité utile : quand Markdown ne suffit pas, le HTML prend le relais. Mais à utiliser avec parcimonie : trop de HTML annule l'avantage de lisibilité de Markdown, et tous les contextes n'autorisent pas le HTML (certains le filtrent pour des raisons de sécurité, cours Sécurité). Réserve-le aux éléments vraiment absents de Markdown.

Les variantes

Markdown n'est pas un standard unique, mais une famille. Les principales saveurs à connaître :

En pratique, retiens deux noms : CommonMark (la base standardisée, lisible partout) et GFM (la plus utilisée chez les développeurs, avec ses extensions). Les autres (MDX pour les sites modernes, variantes avec maths ou notes) sont des spécialisations que tu rencontreras selon les outils. La base que tu as apprise est commune à toutes.

Les bonnes pratiques

Au-delà de la syntaxe, quelques habitudes rendent tes documents nettement meilleurs :

  • une hiérarchie de titres logique : un seul niveau 1, des niveaux 2/3 cohérents ; ne saute pas de niveau (pas de niveau 4 directement sous un niveau 2).
  • aérer : des lignes vides autour des blocs, des sections courtes ; un document compact est pénible à lire.
  • du texte alternatif sur les images, des liens au texte explicite (pas « cliquez ici ») — accessibilité et clarté.
  • prévisualiser avant de publier ; et garder à l'esprit où le document sera lu (quelles extensions sont supportées).
  • rester simple : la force de Markdown est sa lisibilité ; n'en fais pas un document HTML déguisé.

L'objectif final n'est pas d'utiliser le plus de syntaxe possible, mais de produire un document clair, structuré et durable. Markdown est un moyen au service de la communication : bien employé, il rend ta documentation et tes échanges plus efficaces, sans effort.

Pour aller plus loin

Tu sais désormais écrire du Markdown pour tous tes besoins. Pour explorer : les générateurs de sites statiques (qui transforment des fichiers .md en sites complets), les outils de conversion universelle (Pandoc transforme du Markdown en PDF, Word, diapositives…), les diagrammes en texte (Mermaid, intégré à de nombreuses plateformes, dessine des schémas depuis du Markdown), et les applications de notes en Markdown (Obsidian) pour organiser ta connaissance. Markdown est souvent la porte d'entrée de tout un écosystème de documentation.

Glossaire

README
Fichier README.md à la racine d'un projet : sa vitrine et son mode d'emploi. Sur GitHub, il s'affiche comme page d'accueil du dépôt.
Badge
Petite image d'état (build, version, licence) intégrée en Markdown sous forme d'image-lien : [![alt](image)](lien).
HTML inline
Balises HTML insérées directement dans du Markdown pour couvrir ce que Markdown ne gère pas (repliable, centrage) ; à utiliser avec parcimonie.
CommonMark
Spécification stricte et non ambiguë de Markdown : la base standardisée, lisible sur tous les outils compatibles.
GFM
GitHub Flavored Markdown : CommonMark enrichi de tableaux, listes de tâches, texte barré et autoliens ; la variante la plus répandue chez les développeurs.
MDX
Format mêlant Markdown et composants (React), utilisé pour construire des sites et de la documentation interactive.
Générateur de site statique
Outil qui transforme des fichiers .md en site web complet (pages HTML), sans base de données.

Récap et vérification

  • Un bon README : titre + description, installation (commandes), utilisation (exemple), fonctionnalités, contribution, licence.
  • Le HTML dans Markdown comble les manques (détails repliables, centrage) ; à utiliser avec parcimonie (lisibilité, sécurité).
  • Variantes : CommonMark (base standardisée), GFM (la plus courante), MDX et autres pour des cas spécialisés.
  • Bonnes pratiques : hiérarchie de titres logique, aérer, texte alternatif et liens explicites, prévisualiser, rester simple.

Exercices

Exercice 1Échauffement

Cite trois sections que tu mettrais dans le README d'une bibliothèque.

Voir une solution

Par exemple : 1) une description (ce que fait la bibliothèque, pour qui) ; 2) l'installation (la commande exacte, en bloc de code) ; 3) un exemple d'utilisation minimal (un bloc de code montrant l'API de base). On peut ajouter : fonctionnalités, contribution, licence.

Exercice 2Application

Tu veux un bloc « Détails » repliable dans ton README (caché par défaut, qu'on déplie en cliquant). Markdown ne le couvre pas : comment faire ?

Voir une solution

On utilise les balises HTML <details> et <summary>, insérées directement dans le Markdown. C'est exactement le genre de cas où le HTML comble un manque de Markdown — à utiliser ponctuellement.

Exercice 3Synthèse

Rédige un mini-README complet (en Markdown) pour un petit outil en ligne de commande, en réunissant ce que tu as appris : titre, description, installation, utilisation, une petite liste de fonctionnalités, et une licence.

Voir une solution

Ce README combine titres (hiérarchie claire), description en une phrase avec emphase, blocs de code pour l'installation et l'utilisation, une liste de tâches pour les fonctionnalités, et un lien vers la licence. Lisible brut et joliment rendu sur une plateforme : c'est tout l'esprit de Markdown.
