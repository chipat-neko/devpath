Module 5 · Projet — Leçon 11

Projet : documenter un projet de bout en bout

~40 min Avancé Tout le cours requis

À la fin de cette leçon, tu sauras

  • reconnaître les fichiers conventionnels d'un projet documenté ;
  • tenir un CHANGELOG lisible (Keep a Changelog) ;
  • écrire un guide de contribution utile ;
  • assembler une documentation complète et cohérente.
Sommaire de la leçon

Voici le projet de synthèse du cours. Tu sais écrire du Markdown pour tous tes besoins ; il reste à voir comment on documente un vrai projet — pas avec un README isolé, mais avec un petit ensemble de fichiers conventionnels qui se répondent. C'est ce qui distingue un projet qu'on adopte d'un projet qu'on abandonne : une documentation claire, à jour, où chacun trouve sa réponse.

L'anatomie d'un projet bien documenté

Au fil du temps, une convention s'est imposée : certains fichiers, à la racine du dépôt, portent toujours le même nom et le même rôle. Les connaître, c'est savoir où écrire — et où chercher.

Le README reste la porte d'entrée (leçon 06). Les autres fichiers déchargent le README de ce qui l'alourdirait : l'historique va dans le CHANGELOG, les règles de contribution dans CONTRIBUTING, la doc détaillée dans docs/ — souvent assemblée en site (leçon 09).

Cas réel

GitHub reconnaît spécialement ces fichiers : le README.md s'affiche en page d'accueil du dépôt, un lien vers CONTRIBUTING.md apparaît quand on ouvre une issue ou une pull request, et l'onglet « Insights → Community Standards » note la complétude de la documentation (README, licence, guide de contribution, code de conduite…). La présence de ces fichiers est un signal fort : un projet ainsi documenté inspire confiance et attire les contributions.

Le journal des versions (CHANGELOG)

Le CHANGELOG.md répond à une question simple mais cruciale : « qu'est-ce qui a changé ? ». Il s'adresse aux humains (utilisateurs, contributeurs), pas à la machine. La convention Keep a Changelog le structure : une section [Non publié] en haut pour les changements en cours, puis les versions datées, chacune classée par catégories : Ajouté, Modifié, Corrigé, Supprimé.

Les numéros suivent le versionnage sémantique (MAJEUR.MINEUR.CORRECTIF) : on incrémente le correctif pour un bug, le mineur pour une fonctionnalité compatible, le majeur pour une rupture. Le CHANGELOG et les numéros de version racontent ensemble l'histoire du projet.

Astuce

Tiens la section [Non publié] au fil de l'eau : chaque fois que tu ajoutes ou corriges quelque chose, note-le tout de suite. Le jour de la sortie, tu n'as plus qu'à renommer [Non publié] en [1.2.0] - date et à repartir d'une section vide. Écrire le CHANGELOG à la fin, de mémoire, mène toujours à des oublis.

Le guide de contribution, et l'assemblage en site

Le CONTRIBUTING.md explique comment participer au projet : installer l'environnement de développement, lancer les tests, respecter le style de commit, ouvrir une pull request. Il évite aux nouveaux venus de deviner, et t'évite de répéter les mêmes explications.

Quand la documentation dépasse quelques fichiers, on la range dans docs/ et on l'assemble en site avec un générateur (MkDocs, Docusaurus — leçon 09) : navigation, recherche, table des matières. La source reste du Markdown ; le site en est le rendu final.

Attention

Une documentation périmée est parfois pire que pas de documentation : elle induit en erreur. Une commande d'installation qui ne marche plus, un exemple qui référence une API disparue, un CHANGELOG figé à la version 1.0… La règle : la doc fait partie du changement. On met à jour le README et le CHANGELOG dans la même contribution que le code, pas « plus tard ».

Pour aller plus loin

D'autres fichiers conventionnels complètent l'ensemble sur les gros projets : CODE_OF_CONDUCT.md (règles de savoir-vivre de la communauté), SECURITY.md (comment signaler une faille), des gabarits d'issues et de PR dans .github/. Et pour automatiser : des outils génèrent le CHANGELOG à partir de messages de commit normalisés (Conventional Commits), reliant ainsi le cours Git à ta documentation.

Glossaire

README
Fichier vitrine à la racine (leçon 06) : dit ce que fait le projet, comment l'installer et l'utiliser ; page d'accueil du dépôt sur GitHub.
CONTRIBUTING
Guide expliquant comment participer : mise en place de l'environnement, tests, style de commit, process de pull request.
CHANGELOG
Journal des modifications destiné aux humains : une section [Non publié] puis les versions datées, classées par catégories.
Keep a Changelog
Convention d'écriture d'un CHANGELOG : catégories Ajouté / Modifié / Corrigé / Supprimé, versions datées, la plus récente en haut.
Versionnage sémantique
Numérotation MAJEUR.MINEUR.CORRECTIF : correctif pour un bug, mineur pour un ajout compatible, majeur pour une rupture.
LICENSE
Fichier précisant les droits d'utilisation, de modification et de redistribution du projet (MIT, Apache, GPL…).
docs/
Dossier de la documentation longue (guides, référence), souvent assemblée en site par un générateur (leçon 09).
Community Standards
Bilan proposé par GitHub qui note la présence des fichiers de documentation attendus (README, licence, contribution, code de conduite).

Récap et vérification

  • Un projet bien documenté n'a pas qu'un README : CONTRIBUTING, CHANGELOG, LICENSE et docs/ se répondent.
  • Le CHANGELOG (Keep a Changelog) raconte l'évolution : [Non publié] en haut, versions datées classées par catégories.
  • Le CONTRIBUTING décharge le README des détails de participation ; docs/ accueille la doc longue, assemblée en site.
  • La documentation fait partie du changement : on la met à jour en même temps que le code, jamais « plus tard ».

Vérifie ta compréhension

  1. Cite trois fichiers conventionnels et leur rôle.
  2. Comment structure-t-on un CHANGELOG « Keep a Changelog » ?
  3. Pourquoi mettre à jour la doc dans la même contribution que le code ?

Exercices

Exercice 1Échauffement

Associe chaque fichier à son rôle : README.md, CONTRIBUTING.md, CHANGELOG.md, LICENSE.

Voir une solution
  • README.md : la vitrine — ce que fait le projet, installation, usage.
  • CONTRIBUTING.md : comment contribuer — env de dev, tests, pull requests.
  • CHANGELOG.md : l'historique des versions.
  • LICENSE : les droits d'utilisation et de redistribution.
Exercice 2Application

Tu viens de corriger un bug de démarrage et d'ajouter un export CSV, non encore publiés. Écris la section [Non publié] du CHANGELOG.

Voir une solution

On regroupe les changements par catégorie (Ajouté, Corrigé). Le jour de la sortie, cette section sera renommée en [1.2.0] - date et une nouvelle section [Non publié] vide la remplacera.

Exercice 3Synthèse

Un collègue dit : « le README suffit, pas besoin des autres fichiers ». Donne deux arguments pour un CHANGELOG et un CONTRIBUTING distincts.

Voir une solution

1) Séparation des rôles : entasser historique et règles de contribution dans le README le rend illisible ; chaque fichier répond à une question précise, et le lecteur va droit à la sienne. 2) Conventions reconnues : outils et plateformes s'appuient sur ces noms (GitHub lie CONTRIBUTING.md depuis les issues/PR, note la complétude ; des outils lisent le CHANGELOG.md). On y gagne en clarté et en intégration. Le README reste la vitrine ; il pointe vers les autres.

Mini-projet fil rouge — documenter un projet de bout en bout

Pour clore le cours, produisons la documentation complète d'un petit projet. On réunit tout le cours : hiérarchie de titres, emphase, listes, badge en image-lien, blocs de code, tableau et liens — répartis dans les trois fichiers conventionnels.

Ce que tu vas construire

Trois fichiers cohérents pour un même projet : un README.md (titre + badge, description, installation, usage en tableau, licence), un CONTRIBUTING.md (mise en place, process de PR) et un CHANGELOG.md (versions datées).

Étapes

Le README

Titre # + badge [![...](img)](lien), une description avec emphase, l'installation en bloc de code, et l'usage dans un tableau.

Le guide de contribution

Un CONTRIBUTING.md : comment installer, lancer les tests, ouvrir une pull request (liste numérotée).

Le journal des versions

Un CHANGELOG.md « Keep a Changelog » : [Non publié] puis au moins une version datée, avec catégories.

Relier le tout

Depuis le README, un lien vers CONTRIBUTING.md et un vers CHANGELOG.md : la documentation forme un ensemble.

ProjetFil rouge

Assemble les trois fichiers. Essaie d'abord par toi-même, puis compare avec la solution de référence.

Voir une solution complète

Trois fichiers, un ensemble : le README oriente et renvoie aux deux autres ; le CONTRIBUTING guide la participation ; le CHANGELOG date l'évolution. Toute la syntaxe du cours est là — titres, emphase, listes, badge, blocs de code, tableau, liens — au service d'un projet lisible et durable.
