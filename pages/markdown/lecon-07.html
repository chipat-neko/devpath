Markdown étendu : notes, définitions et attributs

~34 min Avancé Leçon 06 requise

À la fin de cette leçon, tu sauras

  • ajouter des notes de bas de page et des listes de définitions ;
  • déclarer des abréviations et fixer des identifiants de titres ;
  • employer surlignage et emoji selon les variantes ;
  • juger de la portabilité d'une extension avant de t'en servir.
Sommaire de la leçon

La syntaxe de base couvre l'immense majorité des besoins. Mais pour de la documentation riche — un article technique, un manuel, un glossaire — il manque parfois quelques éléments : renvoyer une source en bas de page, définir un terme, expliciter un sigle. Ce sont les extensions de Markdown, apportées par des dialectes comme Markdown Extra, Pandoc ou kramdown. Elles sont puissantes, mais pas universelles : la leçon se termine sur la question qui décide de tout, « où mon document sera-t-il lu ? ».

Les notes de bas de page

Une note de bas de page déporte une précision hors du fil de lecture. On place un appel dans le texte avec [^1], puis on définit la note plus bas avec [^1]: …. Le rendu numérote l'appel, le rend cliquable, et regroupe toutes les notes en pied de document avec un lien de retour.

L'étiquette (gruber, cm) est un identifiant libre, pas forcément un chiffre : c'est plus lisible dans la source, et le rendu re-numérote de toute façon dans l'ordre d'apparition. La définition peut se placer n'importe où ; par convention on la met en bas de la section ou du fichier.

Cas réel

Les notes de bas de page sont supportées nativement sur GitHub depuis 2021 (dépôts, issues, discussions) et par la plupart des générateurs de documentation. C'est la façon standard de citer une source ou d'ajouter une précision sans casser le fil d'un README ou d'un article technique. Wikipédia repose entièrement sur ce mécanisme de renvois numérotés.

Les listes de définitions

Une liste de définitions associe des termes à leurs explications — exactement ce qu'il faut pour un glossaire. La syntaxe (Markdown Extra, Pandoc) place le terme sur une ligne, puis la définition sur la ligne suivante préfixée de : :

Le rendu produit une structure HTML <dl> (definition list) avec des <dt> (termes) et <dd> (définitions) — la même que le glossaire de cette page. C'est sémantiquement plus juste qu'une simple liste à puces : le sens « terme / définition » est porté par le balisage, ce qui aide les lecteurs d'écran et le style.

Abréviations et identifiants de titres

Deux extensions discrètes mais commodes pour la doc technique :

Les abréviations se déclarent une fois avec *[SIGLE]: Explication ; ensuite, chaque occurrence du sigle dans le texte reçoit une infobulle au survol.

Les identifiants de titres permettent de fixer l'ancre d'un titre au lieu de laisser l'outil la générer : ## Installation {#install}. On peut ensuite y pointer avec un lien stable [voir l'installation](#install), même si l'on renomme le titre plus tard. C'est précieux pour une documentation dont on ne veut pas casser les liens.

Astuce

Par défaut, la plupart des rendus fabriquent l'ancre d'un titre à partir de son texte (## Bonnes pratiques → #bonnes-pratiques). Un identifiant explicite {#pratiques} découple le lien du libellé : tu peux reformuler le titre sans transformer tous les liens qui y pointent en liens morts.

Surlignage, emoji et le reste

D'autres petites extensions circulent selon les plateformes :

  • Surlignage avec ==texte== → texte surligné (Pandoc, Obsidian, quelques wikis).
  • Emoji par raccourci : :tada: 🎉, :warning: ⚠️, :rocket: 🚀 (GitHub, GitLab, Slack, Discord).
  • Exposant / indice avec ^2^ et ~2~ selon les dialectes (formules simples : E=mc^2^).

Ces éléments sont agréables mais très inégalement supportés : un :tada: écrit pour GitHub s'affichera tel quel, en toutes lettres, sur une plateforme qui ne connaît pas les raccourcis emoji.

La portabilité, question centrale

Tout se joue là. La base (titres, listes, liens, code) est universelle. Les extensions, elles, dépendent du moteur de rendu qui lira ton fichier. Il faut donc les ranger mentalement en trois cercles.

Attention

Une extension non reconnue n'est pas « ignorée proprement » : elle s'affiche en clair. Une liste de définitions rendue par un moteur qui l'ignore laisse voir les : en début de ligne ; un ==surligné== montre ses signes égal. Avant de bâtir un document sur une extension, teste-la dans le contexte réel où il sera lu.

Pour aller plus loin

Ces extensions viennent de dialectes historiques : Markdown Extra (PHP, 2004) a introduit tableaux, définitions et abréviations ; kramdown (l'univers Ruby/Jekyll) a popularisé les attributs {: …} sur les blocs ; Pandoc est le plus riche de tous et sert de couteau suisse de conversion (leçon à venir). Connaître le dialecte d'un outil, c'est savoir d'avance quelles extensions tu peux utiliser.

Glossaire

Extension
Élément de syntaxe ajouté au Markdown de base par un dialecte particulier (notes, définitions, abréviations…) ; non garanti partout.
Note de bas de page
Renvoi placé dans le texte par [^id] et défini plus bas par [^id]: … ; rendu en pied de document, numéroté et cliquable.
Liste de définitions
Association de termes et d'explications produisant un <dl> (avec <dt> et <dd>) ; idéale pour un glossaire.
Abréviation
Sigle déclaré une fois par *[SIGLE]: … et affiché ensuite avec une infobulle au survol.
Identifiant de titre
Ancre explicite fixée par {#ancre} après un titre, pour des liens internes stables même si le libellé change.
Markdown Extra
Dialecte historique (PHP) ayant introduit tableaux, listes de définitions et abréviations ; base de nombreuses extensions modernes.
Portabilité
Capacité d'un document à s'afficher correctement quel que soit le moteur qui le lit ; élevée pour la base, variable pour les extensions.

Récap et vérification

  • Les notes de bas de page ([^id] + [^id]: …) déportent une précision en pied de document ; supportées sur GitHub.
  • Les listes de définitions (Terme / : déf.) produisent un <dl> sémantique, parfait pour un glossaire.
  • Abréviations (*[SIGLE]: …) et identifiants de titres ({#ancre}) enrichissent la doc technique.
  • La portabilité décide de tout : universel / répandu / spécifique — vérifie le moteur cible avant d'utiliser une extension.

Vérifie ta compréhension

  1. Comment écrit-on un appel de note et sa définition ?
  2. Quelle structure HTML produit une liste de définitions, et pourquoi est-ce mieux qu'une liste à puces ?
  3. Que se passe-t-il si un moteur ne connaît pas une extension que tu as utilisée ?

Exercices

Exercice 1Échauffement

Range ces trois éléments dans le bon « cercle » de portabilité (universel / répandu / spécifique) : un titre, une note de bas de page, une liste de définitions.

Voir une solution

Le titre est universel (partout). La note de bas de page est répandue (GitHub et la plupart des générateurs). La liste de définitions est spécifique (Pandoc, Markdown Extra, kramdown seulement). Avant d'utiliser les deux dernières, vérifie qu'elles sont supportées là où le document sera lu.

Exercice 2Application

Écris un court paragraphe qui cite une affirmation avec une note de bas de page, puis définit cette note en bas.

Voir une solution

L'appel [^lisible] est placé juste après le mot concerné ; la définition [^lisible]: … vient en bas. Le rendu ajoute un numéro cliquable et un lien de retour.

Exercice 3Synthèse

Compose un mini-glossaire de deux termes avec une liste de définitions, et déclare une abréviation pour un sigle qui y apparaît.

Voir une solution

La liste de définitions produit un <dl> sémantique ; l'abréviation *[API]: … ajoute une infobulle sur chaque « API » du texte. Les deux sont des extensions « spécifiques » : à réserver aux outils qui les gèrent (Pandoc, Markdown Extra).
