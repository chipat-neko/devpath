Module 05 · Java en profondeur — Leçon 17

La JVM, la mémoire et la performance

~30 min Avancé Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • savoir distinguer pile et tas, comprendre les générations et le rôle du garbage collector ;
  • savoir mesurer avant d'optimiser avec un micro-benchmark JMH correct et le profilage (JFR) ;
  • savoir repérer et corriger une fuite mémoire due à des références retenues ;
  • savoir choisir des structures qui évitent l'autoboxing et déclarer un module avec module-info.java.
Sommaire de la leçon

Tu écris du Java idiomatique depuis quatorze leçons : tu sais ce que ton code dit. Cette leçon parle de ce que la JVM fait avec — comment elle range les objets en mémoire, quand elle les recycle, et comment elle transforme ton bytecode en code machine optimisé à l'exécution. Ce n'est pas de la théorie gratuite : c'est ce qui sépare un correctif de performance efficace d'un rituel superstitieux.

Le fil conducteur est une seule règle : mesure avant d'optimiser. Presque toutes les erreurs de performance en Java viennent de gens qui ont deviné. On va te donner les modèles mentaux (mémoire, GC, JIT) puis les outils pour décider sur des chiffres, pas sur des intuitions.

La mémoire de la JVM : pile et tas

La JVM sépare deux zones. La pile (stack) est propre à chaque thread : elle empile un cadre par appel de méthode, contenant les variables locales et les références. Elle est rapide, automatique, et se vide au retour de la méthode. Le tas (heap) est partagé entre tous les threads : c'est là que vivent les objets. Une variable locale de type objet ne contient jamais l'objet, seulement une référence vers le tas.

Le tas est lui-même découpé en générations, fondées sur une observation empirique (l'hypothèse générationnelle) : la plupart des objets meurent jeunes. La young generation (Eden + survivor spaces) accueille les nouveaux objets ; ceux qui survivent à plusieurs collectes sont promus vers l'old generation. Collecter la young est peu coûteux car elle est petite et la majorité y est déjà morte.

Note

Une référence forte (le cas normal) empêche la collecte. Java propose aussi WeakReference et SoftReference (paquet java.lang.ref) : une WeakReference n'empêche pas la collecte, ce qui sert aux caches. WeakHashMap en est l'application directe.

Le garbage collector

Le rôle du GC est de retrouver les objets injoignables depuis les racines (variables de pile, champs statiques) et de récupérer leur mémoire. Tu n'as rien à libérer à la main. Le coût est la pause : certaines phases suspendent tes threads (stop-the-world). Les GC modernes minimisent ces pauses, et tu en choisis un selon ton objectif.

  • G1 (par défaut depuis Java 9) : bon compromis débit/latence, vise des pauses bornées. Le choix raisonnable par défaut.
  • ZGC : pauses sub-millisecondes même sur des tas de centaines de Go. Idéal pour la faible latence.
  • Parallel : débit maximal, pauses plus longues. Bon pour des traitements par lots où la latence importe peu.

Les réglages les plus utiles sont souvent -Xmx (taille maxi du tas) et le choix du GC.

Piège fréquent

Régler le GC « au hasard » en copiant des flags trouvés sur un forum dégrade souvent les performances. Commence par G1 par défaut, mesure (via -Xlog:gc*), et ne change qu'en réponse à un problème identifié.

Le JIT : warm-up et inlining

HotSpot commence par interpréter ton bytecode, puis surveille quelles méthodes sont chaudes. Les méthodes très appelées sont compilées en code machine optimisé (compilateurs C1 puis C2). C'est pourquoi le même code est lent aux premières exécutions puis accélère : c'est le warm-up. Le JIT applique aussi l'inlining (insérer le corps d'une petite méthode chez l'appelant) et des optimisations spéculatives qu'il annule si une hypothèse devient fausse (deoptimization).

Conséquence directe : chronométrer un bout de code « une fois » ne mesure rien d'utile. Tu mesures l'interpréteur, pas le code optimisé qui tournera en production. D'où la section suivante.

Mesurer avant d'optimiser : JMH et le profilage

Le micro-benchmark naïf (un System.nanoTime() autour d'une boucle) est presque toujours faux : warm-up non géré, optimisations qui suppriment ton code mort, effets de cache. JMH (Java Microbenchmark Harness, le projet officiel d'OpenJDK) gère le warm-up, exécute plusieurs forks et itérations, et fournit un Blackhole pour empêcher le JIT d'éliminer le résultat.

On lit le Score (temps moyen par opération) et l'Error (intervalle de confiance) : si deux scores se chevauchent dans leurs barres d'erreur, la différence n'est pas significative. Ici, la concaténation par + explose quand n grandit — comportement quadratique — alors que StringBuilder reste raisonnable. Le retour de la valeur sert de garde-fou contre l'élimination de code mort.

Pour trouver où ton appli dépense son temps en conditions réelles, tu profiles. JFR (Java Flight Recorder, intégré au JDK) enregistre allocations, pauses GC, points chauds avec un surcoût minime ; async-profiler donne des flame graphs très lisibles.

Astuce

Profile d'abord pour repérer le vrai goulot (souvent 5 % du code consomme 95 % du temps), puis micro-benchmarke avec JMH uniquement la portion identifiée. Profiler oriente, JMH compare.

Les fuites mémoire : références retenues

En Java, une « fuite » n'est pas un oubli de free : c'est une référence que tu gardes alors que tu ne devrais plus. L'objet reste joignable, donc le GC ne le collecte jamais, et le tas grossit jusqu'à l'OutOfMemoryError. Les coupables classiques : collections static qui ne se vident jamais, caches sans expiration, et listeners enregistrés mais jamais désinscrits.

Pour diagnostiquer, on prend un heap dump (instantané du tas) et on l'analyse avec MAT (Eclipse Memory Analyzer), qui montre les objets dominants et le chemin de rétention.

Cas réel

Un service web voit sa mémoire grimper doucement pendant plusieurs jours, jusqu'à un OutOfMemoryError quasiment chaque week-end — quand personne ne redémarre l'appli. Le heap dump analysé sous MAT désigne un seul coupable : une Map statique de sessions qui n'expiraient jamais, une entrée par visiteur, retenue à vie. Ce n'était ni un bug de calcul ni une lenteur, juste une référence oubliée : invisible en lisant le code, évidente sur le dump. Un plafond (removeEldestEntry) plus une expiration ont stabilisé la mémoire.

Les modules (JPMS) et GraalVM

Le système de modules (JPMS, depuis Java 9) ajoute une frontière au-dessus des paquets : un module-info.java à la racine déclare ce que le module exporte (visible de l'extérieur) et ce dont il a besoin (requires). Ce qui n'est pas exporté reste vraiment inaccessible, même par réflexion non autorisée — l'encapsulation forte.

Au-delà du JDK standard, GraalVM propose la native image : une compilation ahead-of-time (AOT) qui produit un exécutable natif au démarrage quasi instantané et à faible empreinte mémoire — précieux pour les fonctions serverless et les CLI. Le compromis : pas de JIT au runtime (le pic de débit d'un service long peut être moindre) et une configuration nécessaire pour la réflexion.

Bonnes pratiques de performance

Une fois le goulot identifié, les leviers les plus rentables sont presque toujours structurels, pas micro-syntaxiques.

  • Choisis la bonne structure. ArrayList pour le parcours et l'accès indexé, HashMap pour la recherche par clé, ArrayDeque pour une file. Une mauvaise complexité algorithmique ne se rattrape par aucun réglage de GC.
  • Évite l'autoboxing en boucle chaude. Une List<Integer> alloue un objet Integer par valeur ; un int[] ou les streams primitifs (IntStream) n'allouent rien.
  • Réutilise au lieu de réallouer. Un StringBuilder hors boucle, un tampon partagé, une taille initiale donnée à une collection que tu sais grande : autant d'allocations en moins, donc moins de pression sur le GC.

Pièges fréquents

Piège fréquent

Le micro-benchmark naïf (nanoTime() autour d'une boucle exécutée une fois) mesure l'interpréteur et se fait souvent supprimer par le JIT (code mort). Utilise JMH : il gère warm-up, forks et Blackhole.

  • Optimiser sans mesurer. Tu réécris une boucle « plus rapide » qui n'était pas le goulot. Profile d'abord.
  • Confondre temps CPU et temps d'horloge. Un test plus « lent » peut juste avoir attendu des I/O ou une pause GC. Regarde la bonne métrique.
  • Fuite par static ou listener. Un champ statique ou un écouteur jamais désinscrit retient ses objets indéfiniment.
  • Autoboxing dans une boucle chaude. Long au lieu de long dans un cumul alloue des millions d'objets éphémères.

Antisèche

Glossaire

Pile (stack)
Zone propre à chaque thread qui empile un cadre par appel de méthode (variables locales, références) ; vidée automatiquement au retour.
Tas (heap)
Zone partagée où vivent les objets ; découpée en générations (young/old) et gérée par le garbage collector.
Garbage collector (GC)
Mécanisme qui récupère la mémoire des objets injoignables depuis les racines ; G1 par défaut, ZGC pour la latence, Parallel pour le débit.
Stop-the-world
Phase de GC qui suspend momentanément les threads applicatifs ; les GC modernes cherchent à la réduire au strict minimum.
JIT
Compilation à la volée (C1 puis C2 dans HotSpot) : traduit à l'exécution le bytecode chaud en code machine optimisé (inlining, spéculation).
Warm-up
Période initiale où le code est encore interprété ou peu optimisé ; une mesure prise à froid ne reflète pas le régime établi.
JMH
Java Microbenchmark Harness, l'outil officiel d'OpenJDK pour des micro-benchmarks fiables (warm-up, forks, Blackhole anti-code-mort).
Fuite mémoire
Référence conservée par erreur (collection statique, cache sans expiration, listener non désinscrit) qui empêche la collecte ; se diagnostique par heap dump + MAT.
Autoboxing
Conversion automatique entre primitif et wrapper (int ↔ Integer) ; en boucle chaude, elle alloue des objets éphémères et pèse sur le GC.

Récap et vérification

  • La pile tient les variables locales par thread ; le tas, partagé et générationnel (young/old), tient les objets.
  • Le GC recycle les objets injoignables ; G1 par défaut, ZGC pour la latence, Parallel pour le débit ; -Xmx et le choix du GC sont les réglages clés.
  • Le JIT interprète puis compile à chaud (warm-up, inlining) : un code froid ne reflète pas la production.
  • Mesure d'abord : JMH pour comparer (warm-up, Blackhole), JFR/async-profiler pour localiser le goulot.
  • Une fuite est une référence retenue (static, cache, listener) ; diagnostique avec heap dump + MAT.
  • Côté structurel : bonne structure de données, éviter l'autoboxing chaud, réutiliser plutôt que réallouer.

Vérifie ta compréhension

  1. Pourquoi chronométrer une boucle exécutée une seule fois donne-t-il un résultat trompeur ?
  2. Une WeakReference empêche-t-elle le GC de collecter l'objet pointé ? Quel usage en tires-tu ?
  3. Tu observes un tas qui ne cesse de grossir jusqu'à l'OutOfMemoryError. Quels deux outils utilises-tu pour trouver la cause, et que cherches-tu ?
