Interfaces et classes abstraites

~34 min Intermédiaire Leçon 6 recommandée

À la fin de cette leçon, tu sauras

  • savoir définir une interface (contrat de méthodes) et l'implements dans une ou plusieurs classes ;
  • savoir choisir entre interface et classe abstraite, et utiliser les méthodes default et static ;
  • savoir programmer contre une interface (List<String> l = new ArrayList<>()) et exploiter le polymorphisme ;
  • savoir trier avec Comparable (compareTo) et Comparator, et reconnaître une interface fonctionnelle.
Sommaire de la leçon

Jusqu'ici, tu sais qu'une classe peut hériter d'une autre. Mais l'héritage répond mal à une question fréquente : « comment garantir que des objets très différents savent tous faire la même chose ? » Un salarié, une facture et un abonnement n'ont rien en commun structurellement, mais tous les trois doivent pouvoir être payés. C'est là qu'interviennent les interfaces : un contrat qui dit « voici ce que tu dois savoir faire », sans imposer comment.

Dans cette leçon, tu apprends à définir des contrats avec interface, à composer plusieurs comportements sur une même classe, à choisir entre interface et classe abstraite, et à exploiter tout ça pour écrire du code souple : polymorphisme, tri avec Comparable et Comparator, et un premier contact avec les interfaces fonctionnelles qui ouvrent la porte aux lambdas.

L'interface : un contrat de méthodes

Une interface liste des méthodes sans corps (juste leur signature). Une classe qui veut respecter ce contrat utilise implements et doit fournir le code de chaque méthode. Contrairement à l'héritage de classe (un seul extends), une classe peut implements plusieurs interfaces.

Les méthodes d'une interface sont implicitement public et abstract. Une classe qui implements Payable promet de fournir une méthode montantAPayer() : le compilateur le vérifie pour toi.

Note

L'annotation @Override au-dessus d'une méthode d'interface n'est pas obligatoire, mais fortement recommandée : si tu te trompes dans la signature, le compilateur t'alerte au lieu de créer silencieusement une méthode sans rapport.

Plusieurs interfaces sur une même classe

Une classe peut combiner plusieurs contrats. C'est le grand avantage des interfaces sur l'héritage : on compose des capacités indépendantes au lieu de tout faire descendre d'un seul parent.

Avec l'héritage classique, on ne peut hériter que d'une seule classe parente. Les interfaces lèvent cette limite : on en cumule autant qu'on veut, chacune ajoutant une capacité.

interface ou classe abstraite ?

Une classe abstraite (mot-clé abstract) ressemble à une interface : elle peut déclarer des méthodes sans corps. Mais elle peut aussi avoir un état (des champs d'instance) et un constructeur, et une classe ne peut en étendre qu'une seule. Règle simple : l'interface décrit ce qu'un objet sait faire ; la classe abstraite fournit une base partielle commune à des classes proches.

En résumé : choisis une interface quand des classes sans lien de parenté doivent partager un comportement (et tu en veux plusieurs) ; choisis une classe abstraite quand des classes apparentées partagent du code et un état. On peut d'ailleurs combiner les deux : une classe abstraite peut implémenter des interfaces.

Méthodes default, static et constantes

Depuis Java 8, une interface peut fournir des méthodes avec un corps : les méthodes default. Elles offrent une implémentation toute prête que les classes héritent sans rien faire, mais peuvent redéfinir. Pratique pour enrichir un contrat sans casser le code existant. Une interface peut aussi avoir des méthodes static (utilitaires) et des constantes (les champs y sont implicitement public static final).

Note

String.format("%.2f", ...) utilise la locale par défaut de la machine pour le séparateur décimal : une virgule en français (120,00), un point en anglais (120.00). Pour forcer un format, passe une Locale en premier argument, par exemple String.format(Locale.FRANCE, "%.2f", montant).

Piège fréquent

Les méthodes default sont un outil de compatibilité, pas un moyen de transformer une interface en classe. Si tu te surprends à en empiler beaucoup avec de la logique, c'est sans doute le signe qu'il te faut plutôt une classe (abstraite ou non).

Le polymorphisme par interface

Le vrai gain arrive ici : tu manipules tes objets par le type de l'interface, sans te soucier de la classe concrète. Une liste de Payable peut contenir des factures et des salariés mélangés ; tu appelles montantAPayer() sur chacun, et Java exécute la bonne version.

Idiome très courant : déclarer une variable avec le type abstrait (l'interface) et l'instancier avec une classe concrète, par exemple List<String> noms = new ArrayList<>();. Ton code dépend du contrat List, pas de l'implémentation : tu peux passer à une LinkedList en changeant une seule ligne.

Cas réel — brancher un nouveau moyen de paiement sans toucher à la caisse

Une boutique en ligne traitait les paiements via une interface MoyenPaiement à une seule méthode payer(montant). Le code de la caisse ne connaissait que ce contrat : il appelait moyen.payer(total) sans savoir s'il s'agissait d'une CarteBancaire ou d'un Virement. Le jour où il a fallu ajouter PayPal, l'équipe a écrit une classe Paypal implements MoyenPaiement… et rien d'autre : pas une ligne de la caisse n'a bougé. C'est le principe « ouvert à l'extension, fermé à la modification » : programmer contre une interface permet d'ajouter des variantes sans risquer de casser l'existant.

Interfaces fonctionnelles et lambdas (teaser)

Une interface qui ne déclare qu'une seule méthode abstraite est dite fonctionnelle. Le JDK en regorge : Runnable (une tâche à exécuter), Comparable (savoir se comparer), Comparator (comparer deux objets). Leur intérêt : comme il n'y a qu'une méthode à fournir, on peut l'écrire avec une lambda, une syntaxe ultra-compacte.

On approfondira les lambdas dans le module Java moderne. Retiens pour l'instant le lien : une interface fonctionnelle peut se remplir avec une lambda. C'est exactement ce qui rend le tri si élégant, comme on le voit tout de suite.

Trier avec Comparable et Comparator

Pour trier une liste, Java a besoin de savoir comment comparer deux éléments. Deux approches. Comparable définit l'ordre naturel de la classe : tu implémentes compareTo directement dans la classe. La convention : renvoyer un nombre négatif si this est « avant », zéro si égal, positif si « après ».

Mais un objet n'a souvent qu'un ordre naturel, alors qu'on veut parfois trier autrement (par nom, par score décroissant…). C'est le rôle de Comparator : un objet de comparaison externe, qu'on passe au tri. Comme Comparator est fonctionnel, on l'écrit en lambda ou avec les fabriques toutes prêtes.

Astuce de lecture : dans Comparator.comparingInt((Joueur j) -> j.score) on précise le type du paramètre (Joueur j) parce que, hors d'une liste déjà typée, le compilateur ne peut pas toujours deviner sur quoi porte la lambda.

Héritage multiple de type et résolution des défauts

Une classe peut implémenter plusieurs interfaces : c'est l'héritage multiple de type. Tant que les contrats sont distincts, tout va bien. Le seul cas délicat : deux interfaces fournissent une méthode default de même signature. Java refuse alors de choisir à ta place ; tu dois redéfinir la méthode, en utilisant éventuellement la syntaxe Interface.super.methode() pour appeler l'une des deux.

Ce mécanisme explique pourquoi Java autorise l'héritage multiple de type (plusieurs interfaces) mais pas l'héritage multiple de classe : les interfaces n'ont pas d'état, donc le seul conflit possible est résolvable explicitement par toi.

Pièges fréquents

Piège fréquent

Confondre implements et extends. On implémente une interface (class A implements Contrat) et on étend une classe (class B extends Parent). Une classe peut implements plusieurs interfaces mais extends une seule classe.

Piège fréquent

Oublier d'implémenter toutes les méthodes du contrat. Tant qu'il en manque une, le code ne compile pas : « Facture is not abstract and does not override abstract method montantAPayer() ». Soit tu fournis la méthode, soit tu déclares la classe abstract.

Piège fréquent

Un compareTo incohérent avec equals. Si deux objets « égaux » selon equals renvoient un compareTo non nul (ou l'inverse), des structures comme TreeSet se comportent de façon surprenante. Vise la cohérence : a.compareTo(b) == 0 devrait correspondre à a.equals(b).

Piège fréquent

Croire qu'une interface peut avoir un état. Ses champs sont implicitement public static final : ce sont des constantes partagées, jamais des champs d'instance propres à chaque objet. Si tu as besoin d'état, c'est une classe (éventuellement abstraite) qu'il te faut.

Pour aller plus loin

Pour aller plus loin

Le JDK fournit des interfaces fonctionnelles génériques très utilisées : Function<T, R> (transformer), Predicate<T> (tester vrai/faux), Supplier<T> (fournir une valeur). Couplées aux lambdas et aux streams, elles changent la façon d'écrire du Java. Ces interfaces sont aussi la clé de l'injection de dépendances : on programme contre un contrat et on branche l'implémentation au dernier moment.

Antisèche

Glossaire

Interface
Contrat listant des méthodes (sans corps par défaut) qu'une classe s'engage à fournir. Décrit ce qu'un objet sait faire.
implements
Mot-clé par lequel une classe s'engage à respecter une ou plusieurs interfaces, en implémentant leurs méthodes.
Méthode default
Méthode d'interface pourvue d'un corps : les classes en héritent sans rien écrire mais peuvent la redéfinir. Sert à enrichir un contrat sans casser l'existant.
Classe abstraite
Base partielle commune, non instanciable, qui peut avoir un état et un constructeur. Une classe n'en étend qu'une seule.
Comparable
Interface donnant l'ordre naturel d'une classe via compareTo : négatif, zéro ou positif selon la position relative.
Comparator
Objet de comparaison externe et interchangeable, passé à une méthode de tri ; souvent écrit en lambda ou via Comparator.comparing.
Interface fonctionnelle
Interface à une seule méthode abstraite, que l'on peut instancier par une lambda (ex. Runnable, Comparator).
Programmer contre une interface
Déclarer les variables avec le type du contrat (List) et non l'implémentation (ArrayList), pour pouvoir changer cette dernière librement.

Récap et vérification

  • Interface : un contrat de méthodes ; une classe l'implements et fournit le code. On peut en cumuler plusieurs.
  • Classe abstraite : base partielle avec état et code commun ; une seule par classe (extends).
  • default / static : méthodes avec corps dans une interface ; les champs y sont des constantes public static final.
  • Polymorphisme : déclare avec le type de l'interface (List<String> l = new ArrayList<>()) pour dépendre du contrat, pas de l'implémentation.
  • Interface fonctionnelle : une seule méthode abstraite (Comparable, Comparator, Runnable) ; se remplit avec une lambda.
  • Tri : Comparable.compareTo pour l'ordre naturel, Comparator pour des ordres externes et multiples.
