Consommer une API web avec HttpClient

~36 min Intermédiaire Leçon 09 (exceptions) recommandée

À la fin de cette leçon, tu sauras

  • construire une requête avec HttpClient et HttpRequest (Java 11) ;
  • lire une HttpResponse et vérifier son code de statut ;
  • envoyer du JSON en POST avec les bons en-têtes ;
  • choisir entre appel synchrone (send) et asynchrone (sendAsync).
Sommaire de la leçon

Une application isolée est rare : la plupart du temps, ton code Java doit parler à d'autres serveurs — récupérer la météo, un taux de change, la liste des dépôts d'un utilisateur GitHub, envoyer une commande à un service de paiement. Le langage de ces échanges, c'est HTTP. Depuis Java 11, la plateforme fournit un client HTTP moderne, java.net.http.HttpClient, qui remplace enfin l'antique et pénible HttpURLConnection.

Trois objets : client, requête, réponse

Le modèle est simple et repose sur trois briques. Un HttpClient (créé une seule fois, réutilisable), une HttpRequest (l'appel qu'on veut faire, construit avec un builder), et une HttpResponse (ce que le serveur renvoie : un statut, des en-têtes, un corps).

Un premier GET

Récupérons le corps d'une page ou d'une API sous forme de texte. On construit la requête avec le builder, on envoie avec send, et on précise comment lire le corps grâce à un BodyHandler — ici ofString() pour obtenir une String.

Le type HttpResponse<String> est générique : le paramètre indique le type du corps une fois lu (ici String). On retrouve les génériques du module 3. Le BodyHandler peut aussi produire un flux de lignes (ofLines()), écrire dans un fichier (ofFile(...)) ou ignorer le corps (discarding()).

Toujours vérifier le statut

Une réponse reçue n'est pas une réponse réussie. Le serveur peut répondre 404 (introuvable), 401 (non authentifié), 500 (erreur serveur). Le code de statut se lit sur la réponse ; on décide ensuite quoi faire.

Piège — ne jamais supposer 200

Un code débutant lit directement reponse.body() et le parse sans regarder le statut. Le jour où l'API renvoie 500 avec une page d'erreur HTML, ton parseur JSON explose avec un message incompréhensible. Vérifie toujours statusCode() d'abord. Pense aussi au timeout : sans .timeout(Duration.ofSeconds(10)) sur la requête, un serveur muet peut bloquer ton thread… indéfiniment.

Envoyer des données : POST avec du JSON

Pour créer ou modifier une ressource, on envoie un corps. On choisit un BodyPublisher (la source du corps à envoyer) et on précise le type de contenu via l'en-tête Content-Type.

Pas de parseur JSON dans la bibliothèque standard

Java sait envoyer et recevoir des octets, mais ne fournit pas de parseur JSON dans sa bibliothèque standard. En vrai projet, on ajoute une dépendance : Jackson (ObjectMapper) ou Gson transforment le texte reçu en objets Java (souvent des record) et inversement. Le HttpClient gère le transport ; la sérialisation JSON est un métier à part, délégué à une bibliothèque éprouvée.

Synchrone ou asynchrone ?

send est bloquant : le thread attend la réponse avant de continuer. Simple, mais si tu dois lancer cinquante appels, tu attends l'un après l'autre. sendAsync renvoie immédiatement un CompletableFuture : la requête part en arrière-plan et tu enchaînes un traitement à l'arrivée, sans bloquer.

Astuce — un seul client pour toute l'application

Le HttpClient est immuable et thread-safe : crée-le une fois (souvent un champ static final) et partage-le. Il gère en interne un pool de connexions réutilisées : en recréer un à chaque appel gaspille des ressources et empêche le maintien des connexions (keep-alive). Configure-le au besoin : HttpClient.newBuilder().connectTimeout(...).followRedirects(...).build().

Cas réel — le tableau de bord météo qui figeait

Une petite application de bureau affichait la météo de plusieurs villes au démarrage. Écrite avec send dans une boucle, elle interrogeait les villes une par une : sur le fil de l'interface graphique, chaque appel gelait la fenêtre une demi-seconde, soit plusieurs secondes de blocage visible pour dix villes. Le correctif : passer à sendAsync et lancer les dix requêtes en parallèle, puis rassembler les résultats à mesure qu'ils arrivent. Bonus imposé par l'expérience : un timeout par requête, pour qu'une seule API lente ne retienne pas tout l'affichage.

Pour aller plus loin

Le HttpClient parle HTTP/2 par défaut (avec repli en HTTP/1.1) et sait ouvrir un WebSocket. Côté corps, BodyHandlers.ofLines() renvoie un Stream<String> pratique pour les flux, ofByteArray() pour du binaire, ofFile(path) pour télécharger directement sur disque. Pour l'authentification, on ajoute un en-tête Authorization: Bearer <jeton>. Et pour les gros volumes, l'API asynchrone se marie naturellement avec les threads virtuels (leçon suivante) pour lancer des milliers d'appels sans épuiser les threads système.

Antisèche

Glossaire

HttpClient
Objet (Java 11) qui exécute les requêtes HTTP. Immuable, thread-safe et réutilisable : on en crée un seul pour toute l'application.
HttpRequest
Description immuable d'un appel (URL, méthode, en-têtes, corps), construite avec un builder puis figée par build().
HttpResponse
Réponse du serveur : un code de statut, des en-têtes et un corps. Type générique : HttpResponse<String>.
BodyHandler
Stratégie de lecture du corps reçu (ofString, ofLines, ofFile, discarding) : elle fixe le type du corps.
BodyPublisher
Source du corps envoyé pour un POST/PUT (ofString, ofFile, noBody).
Code de statut
Entier renvoyé par le serveur : 2xx succès, 4xx erreur du client, 5xx erreur du serveur. À vérifier avant d'exploiter le corps.
send / sendAsync
send bloque jusqu'à la réponse ; sendAsync rend aussitôt un CompletableFuture et n'immobilise pas le thread.
Timeout
Durée maximale d'attente d'une requête (.timeout(...)) ; au-delà, l'appel échoue au lieu de bloquer indéfiniment.

Récap et vérification

  • Depuis Java 11, HttpClient / HttpRequest / HttpResponse remplacent HttpURLConnection.
  • On crée un seul HttpClient, on construit la requête au builder, on lit le corps via un BodyHandler.
  • Toujours vérifier statusCode() avant d'exploiter body() ; poser un timeout.
  • POST envoie un corps (BodyPublishers.ofString) avec l'en-tête Content-Type.
  • send bloque ; sendAsync rend un CompletableFuture pour enchaîner sans attendre.

Vérifie ta compréhension

  1. Pourquoi ne faut-il pas exploiter body() sans regarder statusCode() ?
  2. Quelle différence entre send et sendAsync ?
  3. Pourquoi créer HttpClient une seule fois ?
