Module 03 · Robustesse et collections — Leçon 10

Les génériques

~35 min Avancé Leçon 9 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire des classes et méthodes génériques avec des paramètres de type comme <T> ;
  • savoir contraindre un type avec une borne <T extends Comparable<T>> ;
  • savoir choisir le bon wildcard (? extends / ? super) selon le principe PECS ;
  • savoir expliquer l'effacement de type et les limites qu'il impose (pas de new T()).
Sommaire de la leçon

Tu as déjà croisé des types comme List<String> ou Map<String, Integer> sans forcément savoir ce que signifient ces chevrons. Ce sont des génériques (en anglais generics) : un mécanisme qui permet d'écrire du code typé et réutilisable. Plutôt que d'écrire une classe pour les listes de chaînes, une autre pour les listes d'entiers, etc., tu écris une classe paramétrée par un type.

Dans cette leçon, on part du problème historique (avant Java 5, tout était stocké comme Object), puis on construit progressivement : classes génériques, méthodes génériques, bornes, wildcards, et enfin l'effacement de type qui explique certaines limites surprenantes.

Le problème : la vie avant les génériques

Avant Java 5, les collections ne connaissaient qu'un seul type : Object, l'ancêtre commun de toutes les classes. Tu pouvais donc y mettre n'importe quoi, mais pour récupérer une vraie valeur, il fallait caster (convertir) à la main, et rien ne t'empêchait de te tromper.

Le compilateur ne voit aucune erreur : le bug n'explose qu'à l'exécution.

C'est exactement ce qu'on veut éviter : une erreur de type devrait être détectée par le compilateur, pas par tes utilisateurs en production. Les génériques déplacent ces erreurs de l'exécution vers la compilation.

Classes et interfaces génériques

Une classe générique déclare un ou plusieurs paramètres de type entre chevrons, juste après son nom. Par convention on les nomme avec une seule lettre majuscule : T (type), E (élément), K/V (clé/valeur), R (résultat).

Le compilateur garantit que Boite<String> ne contiendra que des String.

C'est exactement le mécanisme de List<String>, List<Integer>, etc. : une seule définition List<E>, instanciée avec des types différents. L'opérateur diamant <> (depuis Java 7) évite de répéter le type à droite du = : il est déduit de la déclaration à gauche.

Note

Les génériques ne marchent qu'avec des types objets, pas avec les types primitifs. On écrit List<Integer>, jamais List<int>. Java convertit automatiquement entre int et Integer (c'est l'autoboxing).

Méthodes génériques

Une méthode peut elle-même être générique, indépendamment de sa classe. On place les paramètres de type avant le type de retour. C'est utile pour des utilitaires qui fonctionnent quel que soit le type des éléments.

Le type T est déduit de l'argument : pas besoin de l'écrire à l'appel.

Les bornes : contraindre T

Parfois, T ne doit pas être n'importe quel type : on veut pouvoir appeler certaines méthodes dessus. Une borne supérieure avec extends impose que T soit un sous-type d'une classe ou interface donnée.

Sans la borne, element.compareTo(...) ne compilerait pas : Object n'a pas cette méthode.

Note bien le mot-clé : même pour une interface comme Comparable, on écrit extends (pas implements) dans une borne générique. C'est une particularité de syntaxe à mémoriser.

Les wildcards : le type inconnu

Le caractère ? est un wildcard (joker) : il représente un type inconnu. Il est surtout utile dans les paramètres de méthode quand tu veux accepter plusieurs types apparentés. Attention au piège : List<Object> n'est pas un parent de List<String> — les génériques ne sont pas covariants par défaut.

extends pour lire, super pour écrire.

La règle mnémotechnique s'appelle PECS : Producer Extends, Consumer Super. Si le paramètre te produit des valeurs (tu lis dedans), utilise extends. S'il consomme des valeurs (tu écris dedans), utilise super. On y revient dans « Pour aller plus loin ».

L'effacement de type (type erasure)

Voici le point le plus déroutant : les génériques n'existent qu'à la compilation. Une fois le code compilé, le compilateur efface les paramètres de type et insère les casts nécessaires. À l'exécution, List<String> et List<Integer> sont la même classe : List.

L'effacement explique pourquoi new T() et new T[] sont interdits.

Conséquences pratiques : tu ne peux pas instancier un T (le constructeur n'est pas connu), ni créer directement un tableau générique new T[10]. La plupart du temps on contourne en utilisant des List<T> plutôt que des tableaux, ce qui est de toute façon recommandé.

Pourquoi c'est partout dans les collections

Tout le framework Collections de Java est générique : List<E>, Set<E>, Map<K, V>, Optional<T>, et les Stream<T>. C'est ce qui te permet d'écrire un code à la fois sûr et lisible, sans le moindre cast.

Les types imbriqués restent vérifiés de bout en bout par le compilateur.

Cas réel — les génériques qui révèlent les bugs avant la mise en production

En reprenant un service de facturation écrit à l'époque de Java 1.4, une équipe tombe sur des dizaines de List et Map bruts, sans chevrons. Tout « marchait », jusqu'à des ClassCastException sporadiques en production, impossibles à reproduire. Plutôt que de chasser chaque plantage, l'équipe a paramétré les collections une par une (List<Facture>, Map<String, Client>). Effet immédiat : le compilateur a signalé une quinzaine d'endroits où un mauvais type était inséré — des bugs latents depuis des années, tous corrigés avant le déploiement suivant. Les génériques n'ont rien changé à l'exécution ; ils ont déplacé les erreurs de la production vers l'IDE.

Pièges fréquents

Piège fréquent

Utiliser un type brut (List sans <>). Tu perds toute vérification et tu réintroduis les ClassCastException du début de leçon. Écris toujours List<String>, jamais List seul.

Piège fréquent

Confondre extends et super. Si tu lis dans la collection, c'est ? extends T ; si tu y ajoutes, c'est ? super T. Avec ? extends T, le compilateur refuse les add(...) : c'est normal, il ne connaît pas le type exact.

Piège fréquent

Croire qu'on peut faire new T() ou new T[10]. À cause de l'effacement, T n'existe plus à l'exécution. Préfère une List<T> ; si tu as vraiment besoin d'instancier, passe une fabrique (Supplier<T>) en paramètre.

Pour aller plus loin

Le principe PECS structure toute l'API : regarde Collections.copy(List<? super T> dest, List<? extends T> src) — la source produit (extends), la destination consomme (super). Explore aussi les bornes multiples (<T extends Comparable<T> & Serializable>), la variance en profondeur, et la signature générique de Stream<T> et Optional<T> dans la Javadoc.

Antisèche

Glossaire

Générique
Mécanisme permettant de paramétrer une classe ou une méthode par un ou plusieurs types, pour un code réutilisable et vérifié à la compilation.
Paramètre de type
Variable de type déclarée entre chevrons (T, E, K, V…), remplacée par un type concret à l'utilisation.
Opérateur diamant
Les chevrons vides <> qui laissent le compilateur déduire le type à droite du = (depuis Java 7).
Borne
Contrainte sur un paramètre de type (<T extends X>) autorisant à appeler sur T les méthodes de X.
Wildcard
Le joker ? représentant un type inconnu ; combiné à extends ou super pour accepter une famille de types.
PECS
Producer Extends, Consumer Super : ? extends T pour lire (la source produit), ? super T pour écrire (la cible consomme).
Effacement de type
Suppression des paramètres de type à la compilation ; à l'exécution, List<String> et List<Integer> sont la même classe List.
Type brut
Utilisation d'un type générique sans ses chevrons (List) ; désactive la vérification et rouvre la porte aux ClassCastException.

Récap et vérification

  • Les génériques apportent un typage vérifié à la compilation et suppriment les casts.
  • Une classe générique déclare des paramètres : class Boite<T> ; une méthode aussi : <T> T premier(...).
  • Les bornes (<T extends Comparable<T>>) autorisent à appeler des méthodes sur T.
  • Les wildcards suivent PECS : ? extends T pour lire, ? super T pour écrire.
  • L'effacement de type fait disparaître T à l'exécution : pas de new T(), pas de new T[].

Vérifie ta compréhension

  1. Pourquoi un type brut List peut-il provoquer une ClassCastException alors que List<String> ne le peut pas ?
  2. Tu écris une méthode qui ajoute des Integer dans une liste reçue en paramètre : quel wildcard choisis-tu, et pourquoi ?
  3. Donne deux choses interdites à cause de l'effacement de type, et explique en une phrase la raison commune.
