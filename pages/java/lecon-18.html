Module 06 · Tester son code — Leçon 18

Tester avec JUnit 5

~40 min Intermédiaire Bases de Java requises

À la fin de cette leçon, tu sauras

  • écrire un test JUnit 5 avec @Test et des assertions ;
  • maîtriser le cycle de vie (@BeforeEach, @AfterEach) ;
  • écrire des tests paramétrés et vérifier des exceptions ;
  • comprendre l'esprit du TDD et ce qui fait un bon test.
Sommaire de la leçon

Tu sais écrire du Java qui marche… le jour où tu l'écris. Mais une application vit des années : on la modifie, on la refactorise, d'autres y touchent. Comment garantir qu'un changement ne casse rien ailleurs ? La réponse de l'industrie : des tests automatisés, du code qui vérifie ton code. En Java, l'outil standard est JUnit 5. Une fois tes tests écrits, une commande les rejoue tous en une seconde : c'est ton filet de sécurité.

Le premier test

Un test est une méthode annotée @Test qui exerce ton code et affirme (assert) un résultat attendu. On teste ici une classe Calculatrice imaginaire.

La structure classique d'un test est AAA : Arrange (préparer : créer la calculatrice), Act (agir : appeler additionner), Assert (vérifier : assertEquals). Si l'affirmation est fausse, le test échoue avec un message clair : « attendu 5, obtenu 4 ».

On lance les tests avec son outil de build — mvn test (Maven) ou gradle test (Gradle) — ou en un clic depuis l'IDE. Le rapport indique combien passent et lesquels échouent.

Le cycle de vie

Quand plusieurs tests partagent une même préparation, on l'extrait dans une méthode @BeforeEach, exécutée avant chaque test. Cela garantit que chaque test part d'un état neuf et indépendant.

Le second test démarre à 100, pas à 150 : @BeforeEach a recréé un compte neuf entre les deux. L'indépendance des tests est une règle d'or : l'ordre d'exécution ne doit jamais changer le résultat. (@BeforeAll/@AfterAll, statiques, s'exécutent une seule fois pour toute la classe.)

Tester les exceptions

Un bon code échoue proprement : il faut donc aussi tester que les erreurs sont bien levées. assertThrows vérifie qu'un bloc lance bien l'exception attendue.

Le code qui doit échouer est passé en lambda (() -> compte.retirer(500)) : JUnit l'exécute, attrape l'exception et vérifie son type. Si rien n'est levé, le test échoue. On retrouve les lambdas du module 4 : tester, c'est encore du Java.

Les tests paramétrés

Quand une même logique doit être vérifiée sur plusieurs jeux de données, inutile de copier le test : un test paramétré le rejoue pour chaque valeur.

JUnit exécute la méthode cinq fois, une par valeur de la liste, et rapporte chaque cas séparément. C'est idéal pour couvrir les cas limites (zéro, négatif, très grand) sans dupliquer de code.

L'esprit TDD

Le développement piloté par les tests (Test-Driven Development) inverse l'ordre : on écrit d'abord le test (qui échoue, car le code n'existe pas), puis le code minimal pour le faire passer, puis on refactorise en confiance. Le cycle « rouge → vert → refactor » pousse à un code mieux découpé et toujours couvert. Même sans pratiquer le TDD strict, écrire le test en même temps que le code change la façon de concevoir.

Cas réel

Un utilisateur signale qu'une remise de 100 % affiche un prix négatif dans le panier. Avant de corriger, l'équipe écrit un test de non-régression qui reproduit exactement le bug : assertEquals(0, panier.total()) pour une remise totale — il échoue (rouge). Puis elle corrige le calcul jusqu'à ce qu'il passe (vert). Ce test reste dans la suite : même si quelqu'un réintroduit l'erreur des mois plus tard, la CI la rattrape aussitôt. C'est le vrai super-pouvoir des tests : un bug corrigé une fois ne revient jamais en silence.

Glossaire

Test unitaire
Méthode automatisée qui exerce une petite unité de code et affirme un résultat attendu ; rejouée en une commande à chaque changement.
Assertion
Vérification qui compare une valeur attendue à la valeur obtenue (assertEquals, assertTrue…) ; si elle est fausse, le test échoue.
AAA
Arrange, Act, Assert : les trois temps d'un test lisible — préparer le contexte, exécuter l'action, vérifier le résultat.
@BeforeEach
Méthode exécutée avant chaque test pour repartir d'un état neuf ; garantit l'indépendance des tests vis-à-vis de leur ordre.
assertThrows
Assertion qui exécute une lambda et vérifie qu'elle lève bien l'exception attendue ; échoue si aucune (ou une autre) n'est levée.
Test paramétré
Test rejoué automatiquement pour plusieurs jeux de données (@ParameterizedTest + @ValueSource) ; couvre les cas limites sans dupliquer le code.
TDD
Test-Driven Development : écrire le test d'abord (rouge), puis le code qui le fait passer (vert), puis refactoriser ; le code reste toujours couvert.
Test de non-régression
Test ajouté après un bug pour le reproduire ; conservé dans la suite, il empêche la réapparition silencieuse du défaut.

Récap et vérification

  • Un test JUnit 5 est une méthode @Test structurée en AAA (Arrange, Act, Assert).
  • Les assertions (assertEquals, assertTrue, assertThrows…) comparent attendu et obtenu.
  • @BeforeEach recrée un état neuf avant chaque test : les tests sont indépendants.
  • assertThrows (avec une lambda) vérifie qu'une exception attendue est bien levée.
  • Un test paramétré (@ParameterizedTest + @ValueSource) rejoue la logique sur plusieurs données.

Vérifie ta compréhension

  1. Que désigne la structure AAA d'un test ?
  2. Pourquoi @BeforeEach est-il important pour l'indépendance des tests ?
  3. Pourquoi passe-t-on une lambda à assertThrows ?
