Exceptions et gestion d'erreurs

~35 min Intermédiaire Leçon 8 recommandée

À la fin de cette leçon, tu sauras

  • savoir attraper une exception avec try/catch/finally et le multi-catch
  • savoir distinguer les exceptions checked et unchecked et utiliser throw et throws
  • savoir fermer ses ressources avec le try-with-resources (AutoCloseable)
  • savoir créer une exception métier et appliquer les bonnes pratiques (cause chaînée, messages utiles) .
Sommaire de la leçon

Quand ton programme tente une action impossible — diviser par zéro, ouvrir un fichier absent, appeler une méthode sur null — Java ne se contente pas de continuer en silence. Il crée un objet spécial, l'exception, qui interrompt le flux normal et remonte la pile d'appels jusqu'à ce que quelqu'un la gère. Si personne ne le fait, le programme s'arrête et affiche une stack trace.

Dans cette leçon, tu vas apprendre à attraper, lever, déclarer et concevoir des exceptions, à fermer automatiquement tes ressources, et surtout à éviter les pièges classiques qui transforment un bug visible en bug invisible.

Une exception interrompt le flux normal

Une exception est un objet qui décrit un problème survenu pendant l'exécution. Dès qu'elle est levée, les instructions qui suivent ne s'exécutent pas : le contrôle « saute » vers le premier bloc capable de la traiter, en remontant la pile d'appels (la liste des méthodes appelées les unes dans les autres).

La stack trace indique le type de l'exception, son message, et la ligne exacte où elle a été levée.

Note

Lis la stack trace de haut en bas : la première ligne at ... est l'endroit précis du problème, les suivantes montrent qui a appelé qui.

try / catch / finally

Pour gérer une exception, tu places le code risqué dans un bloc try et tu traites le problème dans un catch. Le bloc finally, optionnel, s'exécute toujours — qu'il y ait eu une exception ou non — idéal pour le nettoyage.

Tu peux enchaîner plusieurs catch, ou regrouper des types qui se traitent pareil avec le multi-catch (la barre verticale |).

Note

L'ordre des catch compte : place toujours les exceptions les plus spécifiques avant les plus générales. Un catch (Exception e) placé en premier capturerait tout et rendrait les suivants inaccessibles (erreur de compilation).

Checked vs unchecked

Java distingue deux familles d'exceptions. Les checked (filles de Exception mais pas de RuntimeException, comme IOException) représentent des problèmes prévisibles et externes : le compilateur t'oblige à les gérer (try/catch) ou à les déclarer (throws). Les unchecked (filles de RuntimeException : NullPointerException, IllegalArgumentException, ArithmeticException…) signalent en général un bug de programmation et ne sont pas imposées par le compilateur.

Astuce

Règle mnémonique : checked = « le monde extérieur peut échouer » (réseau, disque) ; unchecked = « j'ai fait une erreur de logique » (oubli d'un test, valeur invalide).

throw (lever) et throws (déclarer)

Attention aux deux mots-clés voisins : throw (sans s) lève une exception à l'instant présent ; throws (avec s) apparaît dans la signature d'une méthode pour déclarer qu'elle peut en propager une.

Valider les arguments au début d'une méthode et lever une exception immédiatement, c'est le principe fail fast : échouer tôt et clairement, plutôt que produire un résultat faux plus loin.

Le try-with-resources

Tout ce qui s'ouvre doit se fermer : fichiers, connexions, flux réseau. Oublier la fermeture provoque des fuites de ressources. Le try-with-resources ferme automatiquement, dans le bon ordre, tout objet déclaré entre ses parenthèses, à condition qu'il implémente l'interface AutoCloseable.

Plus besoin de finally pour fermer : la JVM s'en charge. C'est à la fois plus court et plus sûr (impossible d'oublier).

Note

Tu peux déclarer plusieurs ressources, séparées par ; : try (var a = ...; var b = ...). Elles sont fermées dans l'ordre inverse de leur ouverture.

Créer ses propres exceptions

Pour des erreurs métier (propres à ton domaine), crée une classe qui étend Exception (checked) ou RuntimeException (unchecked). Donne-lui un constructeur avec message, et idéalement un constructeur qui accepte la cause.

Une exception spécifique permet à l'appelant de réagir précisément (catch (SoldeInsuffisantException e)) au lieu d'attraper un vague Exception.

Bonnes pratiques

Quelques règles qui distinguent un code robuste d'un code fragile :

  • Ne jamais avaler une exception : un catch vide masque le problème.
  • Attraper le type le plus spécifique possible, pas Exception ou Throwable par défaut.
  • Messages utiles : inclure les valeurs en cause (« attendu > 0, reçu -3 »).
  • Ne pas utiliser les exceptions pour le flux normal : une valeur absente n'est pas une erreur exceptionnelle.
  • Chaîner la cause quand on relance, pour ne pas perdre la trace d'origine.

Cas réel — le catch vide qui a coûté trois jours

Une équipe importait chaque nuit un fichier de commandes. Un matin, les totaux comptables ne tombaient plus juste, sans le moindre message d'erreur. La cause : un vieux catch (Exception e) {} autour du parsing d'une ligne. Dès qu'une ligne mal formée arrivait, l'exception était avalée en silence : la ligne était ignorée, l'import se « terminait bien », et rien n'apparaissait nulle part. Trois jours de recherche pour retrouver ce bloc vide. Le correctif tenait en une ligne : journaliser l'erreur et compter les lignes rejetées (log.warn("ligne ignorée", e)). La morale : une exception avalée ne disparaît pas, elle se transforme en bug invisible bien plus coûteux.

Pièges fréquents

Piège fréquent

Le catch vide. catch (Exception e) {} fait disparaître l'erreur : le programme continue dans un état incohérent et tu cherches le bug pendant des heures. Au minimum, journalise ou relance.

Piège fréquent

Relancer en perdant la cause : throw new RuntimeException("echec"); sans passer e efface la stack trace d'origine. Passe toujours la cause : new RuntimeException("echec", e).

Piège fréquent

Utiliser les exceptions comme du if : lever/attraper une exception pour signaler « valeur absente » est lent et illisible. Pour un cas attendu, renvoie plutôt un Optional ou une valeur sentinelle.

Pour aller plus loin

Pour aller plus loin

Optional exprime « peut-être une valeur » sans null, ce qui évite des NullPointerException. La journalisation (java.util.logging, SLF4J) enregistre les erreurs sans planter. Les exceptions chaînées et la conception fail fast (valider tôt, échouer clairement) rendent le diagnostic immédiat. Explore aussi e.getCause() et printStackTrace().

Antisèche

Glossaire

Exception
Objet décrivant un problème survenu à l'exécution ; sa levée interrompt le flux normal et remonte la pile d'appels.
Stack trace
Trace affichée quand une exception n'est pas gérée : type, message et suite des appels, de l'endroit du problème vers l'appelant.
Checked
Exception (sous Exception, hors RuntimeException) que le compilateur oblige à gérer avec try/catch ou à déclarer avec throws.
Unchecked
Exception fille de RuntimeException ; non imposée par le compilateur, elle signale en général un bug de programmation.
throw / throws
throw lève une exception à l'instant présent ; throws, dans la signature, déclare qu'une méthode peut en propager une.
try-with-resources
Forme de try qui ferme automatiquement, dans l'ordre inverse d'ouverture, les ressources AutoCloseable déclarées entre parenthèses.
Cause chaînée
Exception d'origine passée en second argument (new X("…", cause)) pour conserver la trace complète quand on relance.
Fail fast
Principe consistant à valider tôt et lever une exception dès qu'une donnée est invalide, plutôt que propager un état incohérent.

Récap et vérification

  • Une exception interrompt le flux et remonte la pile ; la stack trace indique le type, le message et la ligne.
  • try/catch/finally gère les erreurs ; finally s'exécute toujours ; le multi-catch | regroupe les types.
  • Checked = imposées par le compilateur (déclarer ou gérer) ; unchecked = bugs de logique, non imposées.
  • throw lève, throws déclare ; le try-with-resources ferme automatiquement les AutoCloseable.
  • Crée des exceptions métier spécifiques, messages utiles, et chaîne toujours la cause.
