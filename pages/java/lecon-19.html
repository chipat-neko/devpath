Optional et le code sans null

~34 min Intermédiaire Leçon 12 recommandée

À la fin de cette leçon, tu sauras

  • expliquer pourquoi null mène au NullPointerException ;
  • créer un Optional avec of, ofNullable, empty ;
  • le lire sans get() (orElse, orElseThrow, ifPresent) ;
  • l'enchaîner avec map, flatMap, filter — et éviter les pièges.
Sommaire de la leçon

Le null hante Java depuis l'origine. Son inventeur, Tony Hoare, l'a même appelé son « erreur à un milliard de dollars » : une méthode renvoie null pour dire « pas de valeur », l'appelant oublie de vérifier, et le programme s'écroule plus tard sur un NullPointerException — souvent loin de la vraie cause. Depuis Java 8, Optional<T> propose une alternative : rendre l'absence visible dans le type, pour que le compilateur et le lecteur sachent qu'une valeur peut manquer.

Le problème du null

Rien, dans la signature User chercher(String email), ne dit que le résultat peut être null. L'appelant l'ignore, appelle .getNom() dessus, et découvre le problème en production. Avec Optional<User> chercher(...), le type annonce l'absence possible : impossible d'appeler .getNom() directement, il faut d'abord traiter le cas vide.

Créer et lire un Optional

Un Optional est une petite boîte qui contient soit une valeur, soit rien. On la crée avec Optional.of(x) (x non nul, sinon exception), Optional.ofNullable(x) (accepte null → vide) ou Optional.empty().

Transformer : map, flatMap, filter

Comme un stream d'un seul élément, un Optional s'enchaîne. map applique une fonction si la valeur est là ; filter garde la valeur si elle passe un test, sinon vide ; flatMap sert quand la fonction renvoie déjà un Optional (pour ne pas obtenir un Optional<Optional<…>>).

Astuce — orElseGet plutôt qu'orElse pour un défaut coûteux

orElse(x) évalue x toujours, même quand la valeur est présente : si x est le résultat d'un appel coûteux (requête, calcul), c'est du gaspillage, voire un effet de bord indésirable. orElseGet(() -> calcul()) ne l'appelle que si la boîte est vide (évaluation paresseuse). Règle simple : constante littérale → orElse ; expression à calculer → orElseGet.

Piège — Optional n'est pas fait pour tout

Réserve Optional aux valeurs de retour de méthodes qui peuvent légitimement ne rien trouver. À éviter : en champ de classe (alourdit l'objet, pas sérialisable proprement), en paramètre de méthode (surcharge plutôt), et pour une collection (renvoie une liste vide, jamais un Optional<List>). Et ne fais jamais optional.get() sans avoir vérifié la présence : c'est recréer le NullPointerException sous un autre nom.

Cas réel — le NPE du vendredi soir

Un service d'authentification exposait User findByEmail(String) qui renvoyait null quand l'adresse était inconnue. Dans 90 % du code, on avait pensé à vérifier ; mais un nouveau chemin (réinitialisation de mot de passe) appelait directement findByEmail(email).getId(). En production, un utilisateur saisit une adresse qui n'existe pas : NullPointerException, page blanche, astreinte un vendredi soir. Le correctif de fond n'a pas été d'ajouter encore un if, mais de changer la signature en Optional<User> findByEmail(...). D'un coup, le compilateur a signalé tous les appels qui ne traitaient pas le cas vide — dont le fameux chemin oublié. L'absence, devenue visible dans le type, ne pouvait plus passer inaperçue. C'est d'ailleurs pourquoi Spring Data JPA renvoie des Optional.

Pour aller plus loin

Les streams produisent des Optional naturellement : findFirst(), findAny(), max(), reduce() en renvoient un. Pour les nombres, OptionalInt/OptionalLong/OptionalDouble évitent l'emboîtage. Depuis Java 9, optional.stream() transforme un Optional en stream de 0 ou 1 élément (pratique pour aplatir une liste d'Optionals), et or(...) enchaîne des sources de repli. Enfin, des outils comme les annotations @Nullable/@NonNull (avec un analyseur statique) complètent Optional pour documenter le reste du code.

Antisèche

Glossaire

null
Référence qui ne pointe sur aucun objet. Appeler une méthode dessus lève un NullPointerException. Optional vise à en réduire l'usage comme « valeur absente ».
NullPointerException (NPE)
Exception levée à l'exécution quand on déréférence un null. Souvent détectée loin de sa cause, d'où sa réputation.
Optional<T>
Conteneur qui représente explicitement la présence (une valeur) ou l'absence (vide) d'un T. Rend l'absence visible dans le type.
ofNullable
Fabrique un Optional à partir d'une valeur qui peut être null : vide si null, présent sinon. À préférer à of quand la nullité est possible.
orElse / orElseGet
Fournissent une valeur de repli si l'Optional est vide. orElse évalue toujours son argument ; orElseGet ne le calcule que si nécessaire (paresseux).
map / flatMap
Transforment la valeur si elle est présente. flatMap s'emploie quand la fonction renvoie déjà un Optional, pour éviter l'emboîtement.
filter
Garde la valeur si elle satisfait un prédicat ; sinon rend l'Optional vide. Utile pour poser une condition dans une chaîne.
get()
Extrait la valeur mais lève une exception si l'Optional est vide : à éviter au profit de orElse/orElseThrow/ifPresent.

Récap et vérification

  • null cache l'absence ; Optional<T> la rend visible dans le type et force à la traiter.
  • On crée avec of / ofNullable / empty ; on lit avec orElse, orElseThrow, ifPresent — pas get().
  • map, flatMap, filter enchaînent les transformations ; l'absence se propage sans NPE.
  • Optional est fait pour les valeurs de retour, pas pour les champs, paramètres ou collections.

Exercice 3Défi

Pourquoi filter(a -> a.estValide()) au milieu d'une chaîne d'Optional ne provoque-t-il jamais de NullPointerException, même si l'adresse était absente ?

Voir une solution

Parce que filter (comme map) ne s'exécute que si l'Optional contient une valeur. Si un maillon précédent a rendu la boîte vide, tous les maillons suivants sont court-circuités : la lambda a -> a.estValide() n'est jamais appelée sur un null. L'absence se propage silencieusement jusqu'au orElse final, qui fournit la valeur de repli. C'est toute la force du modèle : on décrit la suite de transformations une fois, et le traitement de l'absence est intégré à chaque étape, au lieu d'être un if à ne pas oublier avant chaque déréférencement.
