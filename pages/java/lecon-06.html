Module 02 · Programmation orientée objet — Leçon 06

Héritage et polymorphisme

~34 min Intermédiaire Leçon 5 recommandée

À la fin de cette leçon, tu sauras

  • Savoir hériter et spécialiser une classe avec extends et super ;
  • Savoir redéfinir une méthode avec @Override et comprendre la liaison dynamique ;
  • Savoir exploiter le polymorphisme et redéfinir toString, equals et hashCode ;
  • Savoir écrire une classe abstract, verrouiller avec final et tester un type avec instanceof.
Sommaire de la leçon

Quand tu écris plusieurs classes qui se ressemblent — un Chien et un Chat qui ont tous deux un nom, ou un Cercle et un Carre qui ont tous deux une aire —, recopier le même code partout est une mauvaise idée. L'héritage te permet de mettre le code commun à un seul endroit (la classe parente) et de ne décrire que les différences dans chaque classe enfant. Le polymorphisme, lui, te laisse manipuler tous ces objets à travers un même type, sans connaître leur classe exacte.

Ces deux mécanismes forment le cœur de la programmation orientée objet en Java. Dans cette leçon, on part de l'héritage simple, on enchaîne sur la redéfinition de méthodes, puis on découvre comment Java choisit quelle méthode appeler à l'exécution. On finit par les classes abstraites, le mot-clé final et le instanceof moderne. Le code se compile avec javac et s'exécute sur la JVM ; je montre la sortie console en commentaire dans chaque exemple.

L'héritage : extends et super

Une classe enfant hérite des champs et méthodes de sa classe parente grâce au mot-clé extends. Elle peut ensuite ajouter ses propres membres. Le constructeur de l'enfant doit appeler celui du parent via super(...), en première instruction.

Chien n'a pas redéfini presenter() : il l'utilise tel quel. Le champ nom est déclaré protected pour rester accessible dans Chien ; en private, seul Animal y aurait accès.

Note

En Java, une classe ne peut hériter que d'une seule classe (pas d'héritage multiple). Pour combiner plusieurs comportements, on utilise les interfaces, vues à la prochaine leçon.

La redéfinition : @Override et liaison dynamique

Redéfinir (override) une méthode, c'est en fournir une nouvelle version dans l'enfant, avec exactement la même signature (même nom, mêmes paramètres). On annote la méthode avec @Override : ce n'est pas obligatoire, mais le compilateur vérifie alors que tu redéfinis vraiment quelque chose.

C'est la liaison dynamique : même si la variable est déclarée Animal, Java appelle la méthode de la classe de l'objet réellement créé. La décision se prend à l'exécution, pas à la compilation.

Astuce

Mets @Override partout où tu redéfinis. Si tu te trompes dans la signature (un paramètre de trop, une faute de frappe), le compilateur t'avertit immédiatement au lieu de créer silencieusement une nouvelle méthode.

Le polymorphisme : un type parent pour plusieurs objets

Le polymorphisme (« plusieurs formes ») découle directement de la liaison dynamique : tu peux ranger des objets de classes différentes dans une variable de leur type commun, et les traiter de façon uniforme. Le code appelant n'a pas besoin de connaître la sous-classe exacte.

La boucle ne contient aucun if pour distinguer les types : ajouter demain un Triangle ne change pas une ligne de ce code. C'est toute la puissance du polymorphisme : on programme contre le type abstrait, pas contre les détails.

Note

System.out.printf("%.2f", ...) utilise la locale de la machine pour le séparateur décimal : virgule en France, point ailleurs. Pour une sortie reproductible, passe une Locale explicite en premier argument, comme ci-dessus.

La classe Object : toString, equals, hashCode

Toute classe en Java hérite implicitement de Object, la racine de la hiérarchie. Tu hérites donc gratuitement de quelques méthodes, qu'il est souvent utile de redéfinir :

  • toString() : la représentation texte de l'objet (utilisée par System.out.println) ;
  • equals(Object) : l'égalité « de contenu » entre deux objets ;
  • hashCode() : un entier qui sert d'index dans les HashMap et HashSet.

La règle d'or : si deux objets sont equals, ils doivent avoir le même hashCode. C'est pourquoi on redéfinit toujours les deux ensemble. Sinon, un HashMap rangera ta clé dans une « case » et la cherchera dans une autre.

Astuce

Un record (record Point(int x, int y) {}) génère automatiquement toString, equals et hashCode corrects. Pour de simples porteurs de données immuables, préfère-le à une classe écrite à la main.

Cas réel — les doublons fantômes dans un HashSet

Une équipe stockait des objets Utilisateur (identifiés par leur email) dans un HashSet pour éliminer les doublons. Pourtant, deux inscriptions au même email cohabitaient dans l'ensemble ! La cause : la classe redéfinissait equals (comparer les emails) mais pas hashCode. Le HashSet rangeait les deux objets dans des « cases » différentes (hashs distincts hérités d'Object) et ne les comparait donc jamais. En ajoutant un hashCode() basé sur l'email — cohérent avec equals — les doublons ont enfin été détectés. La règle « equals et hashCode vont toujours ensemble » n'est pas théorique.

Les classes et méthodes abstract

Une classe abstraite définit un contrat partiel : elle peut contenir du code commun et des méthodes abstract sans corps, que chaque sous-classe doit obligatoirement compléter. On ne peut pas instancier une classe abstraite directement.

decrire() appelle aire() sans savoir comment elle est calculée : c'est la sous-classe qui fournira l'implémentation. La classe abstraite garantit que toute Forme saura calculer son aire.

final : verrouiller l'héritage

Le mot-clé final empêche la modification. Sur une classe, il interdit d'en hériter ; sur une méthode, il interdit de la redéfinir. C'est utile pour figer un comportement de sécurité ou garantir l'immuabilité.

La classe String de Java est final : c'est ce qui rend les chaînes immuables et sûres à partager. Déclarer final par défaut, et n'ouvrir l'héritage que quand on le conçoit vraiment, est une bonne discipline.

instanceof et le pattern matching

Parfois, il faut vraiment savoir de quel type est un objet. L'opérateur instanceof répond à cette question. Depuis Java 16, il fait mieux : si le test réussit, il déclare et caste la variable d'un coup (pattern matching).

Attention : un code truffé de instanceof est souvent le signe qu'on devrait utiliser le polymorphisme à la place (une méthode redéfinie). Réserve instanceof aux cas où tu ne contrôles pas la hiérarchie.

Pièges fréquents

Piège fréquent

Surcharge (overload) confondue avec redéfinition (override). Écrire boolean equals(Point p) au lieu de boolean equals(Object o) crée une nouvelle méthode (surcharge) au lieu de redéfinir celle d'Object. Les collections appelleront alors la version d'Object, et ton égalité sera ignorée. L'annotation @Override aurait fait échouer la compilation et révélé l'erreur.

Piège fréquent

Redéfinir equals sans hashCode. Tes objets seront « égaux » mais introuvables dans un HashMap ou un HashSet, car la recherche commence par le hashCode. Redéfinis toujours les deux ensemble. De même, super(...) doit être la première instruction d'un constructeur, sinon le code ne compile pas.

Pour aller plus loin

Pour aller plus loin

Composition plutôt qu'héritage. N'hérite que si l'enfant « est un » parent (un Chien est un Animal). Si la relation est « a un » (une Voiture a un Moteur), préfère la composition : place un champ Moteur dans Voiture. Côté Java moderne, explore les interfaces (prochaine leçon), les classes scellées (sealed) qui limitent qui peut hériter, et le pattern matching de switch, parfait pour traiter une hiérarchie scellée de façon exhaustive.

Glossaire

Héritage
Relation où une classe enfant reçoit les champs et méthodes d'une classe parente via extends, puis les complète.
super
Référence au parent : super(...) appelle son constructeur, super.methode() sa version d'une méthode redéfinie.
Redéfinition (override)
Fournir dans l'enfant une nouvelle version d'une méthode héritée, avec la même signature. Annotée @Override.
Liaison dynamique
Mécanisme par lequel Java choisit, à l'exécution, la méthode du type réel de l'objet et non celle du type déclaré.
Polymorphisme
Traiter des objets de sous-classes différentes via un type parent commun, sans connaître leur classe exacte.
Classe abstraite
Classe non instanciable définissant un contrat partiel : du code commun et des méthodes abstract à compléter.
equals / hashCode
Méthodes d'Object pour l'égalité de contenu et l'indexation en table de hachage ; à redéfinir ensemble et de façon cohérente.
final
Verrou : une classe final ne peut être étendue, une méthode final ne peut être redéfinie.

Récap et vérification

  • extends fait hériter des membres ; super(...) appelle le constructeur parent en première instruction.
  • Redéfinir = même signature + @Override ; la liaison dynamique choisit la méthode selon le type réel de l'objet.
  • Le polymorphisme manipule des objets via leur type parent, sans if sur le type.
  • Redéfinis equals ET hashCode ensemble ; toString pour l'affichage.
  • abstract = contrat partiel à compléter ; final verrouille l'héritage ou la redéfinition.
  • instanceof Type x teste et caste en une fois (Java 16+).

  3. Quelle est la différence entre surcharger et redéfinir une méthode ?
