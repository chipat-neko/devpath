Module 05 · Java en profondeur — Leçon 16

Java moderne : sealed, pattern matching et records

~34 min Avancé Leçon 15 recommandée

À la fin de cette leçon, tu sauras

  • Savoir fermer une hiérarchie avec sealed/permits et exploiter l'exhaustivité du compilateur ;
  • Savoir déconstruire des données avec les record patterns et le switch à patterns (gardes when) ;
  • Savoir modéliser des types algébriques avec sealed interface + record + switch exhaustif ;
  • Savoir utiliser les text blocks, var et des Collectors avancés (teeing, mapMulti) de façon idiomatique.
Sommaire de la leçon

Les versions récentes de Java ont introduit un noyau cohérent de fonctionnalités — records, classes scellées et pattern matching — qui, ensemble, font basculer le langage vers un style plus déclaratif et orienté données. Au lieu de manipuler des objets mutables criblés de getXxx() et de longues chaînes de if (x instanceof Y), tu décris la forme de tes données et tu laisses le compilateur vérifier que tu traites tous les cas.

Cette leçon assemble ces briques telles qu'elles existent en Java 21 LTS. Tu connais déjà les records et le switch de base ; on va ici exploiter la déconstruction, l'exhaustivité garantie et la modélisation par types algébriques (ADT), un pattern emprunté aux langages fonctionnels qui rend le code à la fois plus sûr et plus lisible.

Records approfondis : déconstruction et imbrication

Un record n'est pas qu'un porteur de données compact : c'est aussi une cible de déconstruction. Depuis Java 21, un record pattern permet d'extraire directement ses composants. Combiné à des records imbriqués, tu modélises des structures riches sans classes verbeuses.

La déconstruction Segment(Point(var x1, var y1), ...) lie quatre variables d'un coup, sans appeler un seul accesseur.

Note

Dans un record pattern, var infère le type de chaque composant. Tu peux aussi être explicite — Point(int x1, int y1) — si tu veux documenter ou contraindre le type.

Classes scellées : fermer une hiérarchie

Une classe scellée déclare explicitement la liste finie de ses sous-types autorisés via permits. La hiérarchie devient fermée : aucune autre classe ne peut l'étendre, ce qui transforme une interface en véritable union de types. Chaque sous-type doit être final, sealed ou non-sealed.

Si les sous-types sont dans le même fichier, permits peut être omis : le compilateur l'infère.

Astuce

Le binôme gagnant est sealed interface + record : l'interface fixe l'ensemble des cas, les records portent les données. Le compilateur connaît alors toute la hiérarchie et peut garantir l'exhaustivité d'un switch.

Pattern matching : instanceof, switch et gardes

Le pattern matching élimine le couple instanceof + cast. Mieux : le switch peut désormais brancher sur des types, déconstruire des records, et filtrer avec une garde when.

L'ordre des case compte : un label gardé doit précéder le label non gardé du même type, sinon le compilateur signale du code mort.

Note

Avec case null, le switch ne lève plus de NullPointerException sur une entrée nulle : tu gères le cas explicitement. Sans ce label, un switch à patterns sur null lance toujours une NPE.

Modéliser des données algébriques

Voici la synthèse. En combinant sealed + record + switch exhaustif, tu obtiens un type algébrique (ADT) : un type qui est « soit ceci, soit cela ». Modélisons une mini-expression arithmétique et évaluons-la.

Comme Expr est scellée, le compilateur sait qu'il n'existe que trois cas. Le switch couvre les trois : pas besoin de default, et l'exhaustivité est garantie.

L'intérêt est immense pour la maintenance : si tu ajoutes demain un record Soustraction(Expr g, Expr d) implements Expr au permits, tous les switch exhaustifs qui traitaient Expr cessent de compiler tant que tu n'as pas ajouté le cas manquant. Le compilateur te guide vers chaque endroit à corriger.

Cas réel

Une application de paiement modélise le moyen de règlement en sealed interface Paiement permits Carte, Virement, Paypal. Chaque écran (résumé, reçu, remboursement) traite ces cas via un switch exhaustif. Le jour où l'équipe ajoute ApplePay à la liste permits, le projet refuse de compiler partout où un cas manque : le compilateur dresse lui-même la liste des écrans à mettre à jour. Avec une hiérarchie ouverte et des default, ces oublis partiraient en production sans un mot.

Text blocks et var : usage idiomatique

Deux conforts syntaxiques bien dosés améliorent la lisibilité. Le text block (""") écrit des chaînes multilignes sans concaténation ni \n. Le mot-clé var infère le type local quand il est évident à droite du =.

Le text block supprime l'indentation commune (la incidental whitespace) automatiquement : ici la marge de gauche n'apparaît pas dans la chaîne.

Piège fréquent

var n'est pas du typage dynamique : le type est figé à la compilation. Réserve-le aux cas où il améliore la lecture ; abusé sur des appels de méthode au type opaque, il force le lecteur à deviner.

Optional et Stream avancés

Le pattern matching se marie bien avec un style fonctionnel. Quelques outils récents valent le détour. Collectors.teeing applique deux collecteurs au même flux puis fusionne leurs résultats — idéal pour calculer plusieurs agrégats en une passe.

mapMulti est une alternative à flatMap quand chaque élément produit peu de sorties : il évite d'allouer un Stream par élément.

Note

Les Stream Gatherers (Stream.gather(...)) généralisent les opérations intermédiaires personnalisées (fenêtres glissantes, regroupements…). En aperçu (preview) en Java 22-23, ils sont stabilisés ensuite : surveille-les si tes pipelines deviennent complexes.

Pourquoi ce style est plus sûr et plus lisible

Le fil conducteur est le déplacement des erreurs vers la compilation. Une union scellée + un switch exhaustif rend impossible l'oubli d'un cas. Les records garantissent l'immuabilité et une déconstruction lisible. Le pattern matching supprime les casts manuels, source classique de ClassCastException. Résultat : moins de tests défensifs à écrire, car le compilateur fait déjà une partie du travail de vérification.

Pièges fréquents

Piège fréquent

Sur une interface non scellée, le compilateur ne connaît pas tous les sous-types : ton switch exige un default et n'est donc jamais vérifié pour exhaustivité. Tu peux ajouter un cas oublié sans aucun avertissement. C'est précisément ce que sealed corrige.

  • Oublier un cas : seul un switch sur type scellé sans default profite de la vérification d'exhaustivité. Dès que tu mets un default, tu perds cette aide pour les futurs sous-types.
  • Record pattern mal imbriqué : la structure du pattern doit refléter exactement les composants du record (mêmes types, même ordre). Segment(Point p, var q) est valide ; Segment(int x, ...) ne l'est pas, car le premier composant est un Point.
  • Muter un record : un record est immuable par conception. Si tu as besoin de « changer » un champ, crée une copie — par exemple via un wither manuel with... qui renvoie un nouveau record. Stocker un tableau mutable dans un record le rend trompeusement « modifiable » : à éviter.
  • Abuser de var : un fichier truffé de var x = ... sur des appels au type non évident dégrade la relecture autant que des noms cryptiques.

Pour aller plus loin

Pour aller plus loin

Explore les Stream Gatherers (Java 22+) pour des opérations intermédiaires sur mesure, la programmation orientée données (modéliser le domaine par des ADT plutôt que par héritage de comportement), les unnamed patterns _ (Java 22) pour ignorer proprement un composant ou une variable, et le futur Project Valhalla avec ses value classes qui apporteront des objets sans identité, compacts en mémoire, dans la lignée des records.

Glossaire

record
Classe porteuse de données immuable et concise ; génère constructeur, accesseurs, equals/hashCode/toString.
Record pattern
Motif qui déconstruit un record en liant ses composants à des variables (case Point(var x, var y)), y compris de façon imbriquée.
Classe scellée
Type déclaré sealed dont la liste des sous-types autorisés est fixée par permits ; la hiérarchie est fermée.
Pattern matching
Test qui vérifie le type et lie une variable typée (o instanceof String s), sans cast manuel ; utilisable dans un switch.
Garde (when)
Condition booléenne ajoutée à un case (case Integer i when i < 0) ; le case gardé doit précéder le non gardé du même type.
Exhaustivité
Garantie du compilateur qu'un switch sur un type scellé couvre tous les cas ; un cas manquant devient une erreur de compilation.
Type algébrique (ADT)
Type « soit ceci, soit cela » obtenu par sealed interface + record + switch exhaustif ; modélise un domaine de façon sûre.
Text block
Littéral de chaîne multiligne délimité par """ ; l'indentation commune est retirée automatiquement.

Récap et vérification

  • Les record patterns déconstruisent records et records imbriqués, liant leurs composants en une expression.
  • Une classe scellée (sealed/permits) ferme une hiérarchie et en fait une union de types finie.
  • Le pattern matching branche sur les types, déconstruit, et filtre avec when ; case null gère explicitement l'absence.
  • sealed interface + record + switch exhaustif = type algébrique avec exhaustivité vérifiée par le compilateur.
  • Text blocks et var allègent la syntaxe quand ils servent la lisibilité, pas autrement.
  • Collectors.teeing et mapMulti enrichissent les pipelines ; les Gatherers généralisent les opérations intermédiaires.

Vérifie ta compréhension

  1. Pourquoi un switch sur une sealed interface n'a-t-il pas besoin de default, et qu'est-ce que cela t'apporte quand tu ajoutes un sous-type ?
  2. Quelle différence entre une garde when et un simple case Type t ? Pourquoi l'ordre des deux compte-t-il ?
  3. Donne un record pattern qui déconstruit Segment(Point debut, Point fin) pour extraire uniquement les deux abscisses.
