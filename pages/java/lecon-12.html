Lambdas et streams

~35 min Avancé Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • Savoir écrire une lambda et la passer à une interface fonctionnelle (Function, Predicate, Consumer, Supplier) ;
  • Savoir construire un pipeline de stream avec des opérations intermédiaires (filter, map, sorted) et terminales (collect, count, reduce) ;
  • Savoir collecter un résultat avec Collectors.toList, groupingBy et joining, et employer les références de méthode ;
  • Savoir représenter l'absence de valeur avec Optional au lieu de null, et éviter les pièges des streams paresseux et non réutilisables.
Sommaire de la leçon

Jusqu'ici, pour transformer une liste en Java, tu écrivais une boucle for : tu déclares un accumulateur, tu parcours, tu pousses dans une nouvelle liste. Ça marche, mais le comment noie le quoi. Depuis Java 8, le langage propose un style fonctionnel : tu décris la transformation (« garde les pairs, double-les, additionne ») et la JVM s'occupe de la mécanique. Les deux briques sont les lambdas (de petites fonctions anonymes) et les streams (des pipelines de traitement sur une séquence d'éléments).

Cette leçon part de tes acquis sur les collections, les interfaces et les classes pour t'amener à écrire des traitements concis et lisibles. Tu vas voir que tout repose sur une idée simple : en Java, une lambda n'est qu'une façon courte d'implémenter une interface à une seule méthode.

La lambda : une fonction écrite en une ligne

Une lambda est une implémentation concise d'une interface fonctionnelle — une interface qui ne déclare qu'une seule méthode abstraite. La syntaxe est (paramètres) -> corps. Le compilateur infère les types des paramètres d'après le contexte, donc tu n'as presque jamais à les écrire.

Avec un seul paramètre, les parenthèses sont optionnelles : x -> x * 2. Avec un corps d'une expression, pas de return ni de ;.

Retiens l'équivalence : (x) -> x * 2 est juste une manière compacte d'écrire une classe qui implémente apply. C'est pour ça qu'une lambda ne peut viser qu'une interface à une méthode : le compilateur doit savoir laquelle tu implémentes.

Note

L'annotation @FunctionalInterface posée sur ta propre interface n'est pas obligatoire, mais elle est utile : le compilateur refuse de compiler si tu ajoutes par erreur une seconde méthode abstraite. C'est un garde-fou.

Les interfaces fonctionnelles du JDK

Tu n'as pas à inventer tes interfaces : le paquet java.util.function en fournit pour les besoins courants. Apprends ces cinq-là, elles couvrent l'essentiel.

  • Function<T, R> : prend un T, renvoie un R — méthode apply.
  • Predicate<T> : prend un T, renvoie un boolean (un test) — méthode test.
  • Consumer<T> : prend un T, ne renvoie rien (un effet) — méthode accept.
  • Supplier<T> : ne prend rien, fournit un T — méthode get.
  • BiFunction<T, U, R> : prend deux arguments, renvoie un R — méthode apply.

Le nom de la méthode change selon l'interface (test, accept, get, apply), mais le principe est identique : une lambda la remplit.

Les références de méthode

Quand ta lambda ne fait qu'appeler une méthode existante, tu peux la remplacer par une référence de méthode, écrite avec ::. C'est plus court et plus lisible : s -> s.toUpperCase() devient String::toUpperCase.

System.out::println équivaut à x -> System.out.println(x), en plus lisible.

Astuce

N'écris une référence de méthode que si elle simplifie vraiment. x -> x.length() > 3 ne se réduit pas à une référence : garde la lambda. La règle : si la lambda transmet ses arguments tels quels à un seul appel, le :: s'applique.

Le stream : un pipeline sur une séquence

Un stream est une séquence d'éléments qu'on fait passer par un pipeline d'opérations. On part d'une source (souvent collection.stream()), on enchaîne des opérations intermédiaires (qui renvoient un nouveau stream : filter, map, sorted, distinct, limit) et on finit par une opération terminale (qui produit un résultat : collect, forEach, count, reduce, findFirst).

On lit le pipeline de haut en bas comme une phrase : « à partir des nombres, garde les pairs, dédoublonne, trie, multiplie par dix, collecte ».

Le var de Java 10 allège la déclaration quand le type est évident : var resultat = nombres.stream().... Le compilateur déduit List<Integer>.

Note

La source n'est jamais modifiée. nombres reste [5, 2, 8, 2, 9, 4, 8] après le pipeline : un stream lit la collection et produit un nouveau résultat. C'est une différence majeure avec une boucle qui mute une liste en place.

Collecter un résultat avec Collectors

L'opération terminale collect rassemble les éléments du stream dans une structure. La classe utilitaire Collectors fournit les recettes les plus utiles : toList, joining (concaténer en une chaîne) et surtout groupingBy (ranger les éléments par clé, façon « trier dans des tiroirs »).

groupingBy renvoie une Map où chaque clé pointe vers la liste des éléments qui la partagent. L'ordre d'affichage des clés dépend du hachage, pas de l'ordre d'insertion.

Depuis Java 16, l'opération terminale toList() (directement sur le stream, sans Collectors) fait presque la même chose que collect(Collectors.toList()) : mots.stream().filter(...).toList(). Plus court, à privilégier dans le code moderne ; la liste renvoyée est en plus non modifiable, ce qui évite des mutations accidentelles.

Optional : dire « peut-être rien » sans null

Certaines opérations terminales (findFirst, reduce, max) peuvent ne rien trouver. Plutôt que renvoyer null — source historique du fameux NullPointerException — elles renvoient un Optional<T> : une boîte qui contient soit une valeur, soit rien. Tu es alors forcé de gérer le cas vide.

orElse fournit un repli, map transforme la valeur si elle existe, ifPresent n'exécute son action que si la boîte est pleine.

Piège fréquent

orElse(x) évalue toujours son argument x, même si l'Optional est plein. Si calculer x coûte cher (appel réseau, base de données), utilise orElseGet(() -> calcul()) : la lambda n'est appelée que si la boîte est vide. orElse pour une constante, orElseGet pour un calcul.

Streams paresseux et non réutilisables

Deux propriétés à intégrer tôt. D'abord, un stream est paresseux : les opérations intermédiaires ne s'exécutent pas tant qu'aucune opération terminale ne les déclenche. Ensuite, un stream est à usage unique : une fois une opération terminale appelée, le stream est consommé et ne peut plus servir.

Si tu as besoin de reparcourir, repars de la collection avec un nouveau .stream(), jamais du même objet stream.

Cas réel — du null qui plante en prod à l'Optional qui force la main

Une méthode trouverClient(id) renvoyait null quand le client n'existait pas. La plupart des appelants testaient le cas ; un seul l'avait oublié. Le jour d'un pic de trafic promotionnel, cet appel a reçu null et déclenché un NullPointerException en pleine commande — une page d'erreur pour le client, une alerte à 3 h du matin pour l'équipe. Le correctif de fond n'a pas été de rajouter un test : c'était de changer la signature en Optional<Client>. Du coup, le compilateur a obligé chaque appelant à traiter le cas vide (orElseThrow, orElse…). Le type « peut-être rien » a rendu l'oubli impossible, et cette famille de plantages a disparu.

Pièges fréquents

Piège fréquent

Oublier l'opération terminale : un pipeline qui se termine par filter(...) ou map(...) ne fait rien. Tant qu'il n'y a pas de collect, forEach, count… le stream reste inerte. Si « ton code ne s'exécute pas », cherche d'abord la terminale manquante.

Trois autres écueils :

  • Effets de bord dans une lambda. Garde tes lambdas pures : elles transforment des entrées en sorties sans modifier de variable extérieure. Modifier une liste partagée depuis un forEach casse le raisonnement et devient faux en parallèle.
  • Mélanger impératif et streams. Évite un forEach qui pousse manuellement dans une liste : c'est une boucle déguisée. Préfère map(...).toList(), qui exprime l'intention.
  • Abuser des streams pour du trivial. Pour itérer une fois et afficher, une boucle for classique reste plus claire. Le stream brille sur les transformations (filtrer, mapper, grouper, réduire), pas sur tout.

Pour aller plus loin

Pour aller plus loin

Explore reduce pour replier un stream en une seule valeur (somme, produit, concaténation), et flatMap pour aplatir un stream de listes en un seul flux. Côté Collectors, regarde les variantes avancées : groupingBy avec un second collecteur (counting(), averagingInt(...)), partitioningBy, ou toMap. Enfin, parallelStream() distribue le travail sur plusieurs cœurs : spectaculaire sur de gros volumes, mais à manier avec prudence — il exige des lambdas pures et sans ordre garanti, sous peine de bugs subtils.

Glossaire

Lambda
Fonction anonyme écrite (paramètres) -> corps ; implémentation concise de l'unique méthode d'une interface fonctionnelle.
Interface fonctionnelle
Interface ne déclarant qu'une seule méthode abstraite (ex. Function, Predicate) ; cible possible d'une lambda. Marquable @FunctionalInterface.
Référence de méthode
Notation Type::methode remplaçant une lambda qui se contente d'appeler une méthode existante.
Stream
Séquence d'éléments traitée par un pipeline ; ne stocke rien et ne modifie pas sa source.
Opération intermédiaire
Étape qui renvoie un nouveau stream (filter, map, sorted…) ; paresseuse, elle ne s'exécute qu'au déclenchement d'une terminale.
Opération terminale
Étape qui produit un résultat (collect, count, reduce, forEach) et consomme le stream.
Paresseux (lazy)
Se dit d'un stream dont les opérations intermédiaires n'agissent qu'une fois une opération terminale appelée.
Optional
Conteneur qui renferme soit une valeur, soit rien ; il remplace null et force à traiter explicitement le cas vide (orElse, ifPresent).

Récap et vérification

  • Une lambda (x) -> ... implémente une interface fonctionnelle (une seule méthode) ; les types sont inférés.
  • Les interfaces clés du JDK : Function (transforme), Predicate (teste), Consumer (consomme), Supplier (fournit), BiFunction (deux arguments).
  • Une référence de méthode (String::toUpperCase) remplace une lambda qui ne fait qu'appeler une méthode.
  • Un stream = source + opérations intermédiaires (filter, map, sorted…) + une opération terminale (collect, count, reduce…).
  • Collectors.toList/groupingBy/joining rassemblent les résultats ; Optional remplace null et force à gérer l'absence.
  • Un stream est paresseux (rien sans terminale) et à usage unique (pas de réutilisation).
