Module 02 · Programmation orientée objet — Leçon 05

Classes et objets

~34 min Intermédiaire Leçon 4 recommandée

À la fin de cette leçon, tu sauras

  • savoir distinguer une classe (le plan) d'un objet créé avec new ;
  • savoir écrire des champs, des méthodes et un constructeur qui respecte les invariants ;
  • savoir encapsuler avec private et des getters/setters, et choisir le bon modificateur d'accès ;
  • savoir utiliser static, organiser en packages et redéfinir toString().
Sommaire de la leçon

Jusqu'ici tu manipulais des types simples : des int, des String, des tableaux. Mais le vrai pouvoir de Java, c'est de créer tes propres types pour représenter les choses de ton programme : un compte bancaire, un joueur, une commande. C'est le rôle des classes. Une classe décrit à quoi ressemble une catégorie d'objets ; un objet est un exemplaire concret fabriqué à partir de ce plan.

Dans cette leçon, on construit pas à pas une classe Compte (un compte bancaire avec un solde) pour découvrir les champs, les méthodes, le constructeur, l'encapsulation, les membres static et l'affichage lisible avec toString(). Tout se compile avec javac et s'exécute sur la JVM : les sorties sont montrées en commentaire ou dans un bloc Terminal.

Une classe est un plan, un objet est une instance

Imagine la classe comme le plan d'une maison : un seul plan, mais autant de maisons construites que tu veux. En Java, on construit un objet avec le mot-clé new, qui réserve la mémoire et te rend une référence vers le nouvel objet.

Chien est le plan ; rex est un objet concret. On pourrait créer dix chiens différents à partir du même plan.

Note

Une variable d'objet ne contient pas l'objet lui-même, mais une référence vers lui. Tant que tu n'as pas fait new, la référence vaut null (elle ne pointe vers rien).

Champs (état) et méthodes (comportement)

Un objet a deux facettes : son état (les données qu'il retient, ce sont les champs) et son comportement (ce qu'il sait faire, ce sont les méthodes). Dans une méthode d'instance, tu accèdes directement aux champs de l'objet courant.

La méthode deposer modifie l'état de l'objet ; consulter le lit. Chaque Compte a son propre solde.

Le constructeur et this

Laisser un compte démarrer à 0 et le remplir ensuite est fragile. Un constructeur permet d'initialiser un objet dès sa création. Il porte le même nom que la classe et n'a pas de type de retour (même pas void). Quand un paramètre porte le même nom qu'un champ, le mot-clé this lève l'ambiguïté : this.solde désigne le champ, solde le paramètre.

Le constructeur garantit qu'un Compte est toujours créé avec un titulaire et un solde.

Note

Si tu n'écris aucun constructeur, Java en fournit un par défaut sans argument (Compte()). Mais dès que tu déclares ton constructeur, ce constructeur par défaut disparaît : new Compte() ne compilera plus.

L'encapsulation : private + getters/setters

Pour l'instant, n'importe qui peut écrire c.solde = -9999; et casser la logique. L'encapsulation consiste à rendre les champs private (inaccessibles depuis l'extérieur) et à n'exposer que des méthodes contrôlées. On protège ainsi les invariants (ici : « le solde ne devient jamais négatif ») et on garde la liberté de changer l'implémentation plus tard sans casser le code qui utilise la classe.

Le solde ne peut plus être modifié n'importe comment : toute opération passe par une méthode qui vérifie les règles.

Cas réel — le champ public qui autorisait les soldes négatifs

Dans une petite appli de caisse, la classe Panier exposait public double total; « pour aller plus vite ». Un module de remise a fini par écrire panier.total -= reduction; sans garde-fou : un jour une remise mal calculée a rendu le total négatif, et la commande est passée à un montant absurde. Le correctif : mettre total en private et n'exposer qu'une méthode appliquerRemise(double) qui refuse de descendre sous zéro. Le champ caché, impossible à corrompre de l'extérieur, aurait bloqué le bug dès l'écriture.

Les modificateurs d'accès

Le mot devant un champ ou une méthode décide qui peut y accéder. Java en propose quatre niveaux, du plus ouvert au plus fermé :

  • public — accessible partout.
  • protected — accessible dans le même package et dans les sous-classes (utile avec l'héritage, prochaine leçon).
  • package-private (rien du tout, le défaut) — accessible seulement dans le même package.
  • private — accessible uniquement à l'intérieur de la classe.

Règle de pouce : champs en private, méthodes que tu veux offrir en public, et le reste aussi fermé que possible.

static : ce qui appartient à la classe

Un membre d'instance existe une fois par objet (chaque Compte a son solde). Un membre static appartient à la classe elle-même et est partagé par tous les objets : parfait pour un compteur d'instances ou une méthode utilitaire qui n'a pas besoin d'un objet pour fonctionner.

On appelle une méthode static via la classe (Compte.getNombreDeComptes()), pas via un objet. main est static pour la même raison : la JVM l'appelle sans créer d'objet.

Piège fréquent

Une méthode static ne peut pas accéder directement à un champ d'instance ni à this : elle n'est rattachée à aucun objet. À l'inverse, une méthode d'instance peut lire un champ static. Si tu vois l'erreur « non-static field cannot be referenced from a static context », c'est ce mélange.

Packages : organiser le code

Un package regroupe des classes liées, comme des dossiers. On le déclare en première ligne du fichier avec package, et on importe une classe d'un autre package avec import. Cela évite les collisions de noms et clarifie l'architecture.

Par convention, le dossier sur le disque reflète le package : une classe du package banque se trouve dans un dossier banque/. Le package java.lang (avec String, System) est, lui, importé automatiquement.

Note

Avec un package, le nom complet de la classe devient banque.Main : depuis le dossier parent, on lance alors java banque.Main. Tant que tu n'as qu'un seul fichier sans package, tu peux garder java Main comme dans les exemples précédents.

toString() : un affichage lisible

Si tu fais System.out.println(compte) sans rien préparer, Java affiche quelque chose comme Compte@1b6d3586 : le nom de la classe et un code mémoire, illisible. En redéfinissant la méthode toString() (héritée de la classe Object, ancêtre de toutes les classes), tu décides du texte affiché. C'est un premier aperçu de l'héritage : @Override indique qu'on remplace une méthode existante.

Le compilateur produit un Main.class, puis la JVM l'exécute. println appelle toString() tout seul.

Astuce

Mets toujours @Override au-dessus d'un toString() (ou de toute méthode redéfinie). Si tu te trompes dans le nom ou la signature, le compilateur refusera de compiler au lieu de créer silencieusement une méthode inutile.

Pièges fréquents

Piège fréquent

Mettre les champs en public « pour aller plus vite » brise l'encapsulation : n'importe quel code peut alors mettre un état incohérent (solde = -9999) et tu perds tout contrôle. Garde les champs private.

Piège fréquent

Oublier this quand un paramètre masque un champ : écrire solde = solde; dans le constructeur affecte le paramètre à lui-même et laisse le champ à 0. Il faut this.solde = solde;.

Piège fréquent

Appeler une méthode sur une référence null (un objet jamais créé avec new) déclenche une NullPointerException à l'exécution. Vérifie qu'un objet est bien initialisé avant de l'utiliser.

Glossaire

Classe
Plan décrivant une catégorie d'objets : ses champs (état) et ses méthodes (comportement). Écrite une seule fois.
Objet (instance)
Exemplaire concret fabriqué à partir d'une classe avec new. Chaque objet a sa propre copie des champs d'instance.
Référence
Ce que contient une variable d'objet : un lien vers l'objet en mémoire, pas l'objet lui-même. Vaut null tant qu'aucun new n'a eu lieu.
Constructeur
Méthode spéciale de même nom que la classe et sans type de retour, appelée par new pour initialiser l'objet.
this
Référence vers l'objet courant à l'intérieur d'une méthode d'instance ; sert à distinguer un champ d'un paramètre de même nom.
Encapsulation
Cacher les champs (private) et n'exposer que des méthodes contrôlées, pour protéger les invariants de l'objet.
Invariant
Règle qui doit toujours rester vraie pour un objet (ex. : « le solde n'est jamais négatif »). L'encapsulation la fait respecter.
static
Membre rattaché à la classe et non à un objet : un seul exemplaire partagé, appelé via le nom de la classe.

Récap et vérification

  • Une classe est un plan ; un objet est une instance créée avec new.
  • Les champs portent l'état, les méthodes le comportement ; le constructeur initialise l'objet (même nom que la classe, pas de type de retour).
  • L'encapsulation (champs private + getters/setters) protège les invariants ; choisis le modificateur d'accès le plus fermé possible.
  • static appartient à la classe et est partagé ; les packages organisent ; toString() donne un affichage lisible.

Vérifie ta compréhension

  1. Quelle est la différence entre une classe et un objet, et quel mot-clé crée un objet ?
  2. Pourquoi écrire this.solde plutôt que solde dans un constructeur dont le paramètre s'appelle solde ?
  3. Un champ static et un champ d'instance : lequel est partagé par tous les objets, et lequel existe une fois par objet ?
