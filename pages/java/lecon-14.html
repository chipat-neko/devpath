Module 04 · Java moderne — Leçon 14

Organiser un projet et aller plus loin

~32 min Intermédiaire Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • organiser ton code en packages et comprendre la visibilité ;
  • savoir pourquoi utiliser un outil de build comme Maven ou Gradle ;
  • écrire un premier test avec JUnit 5 et documenter avec Javadoc ;
  • connaître les bonnes pratiques et savoir par où continuer dans l'écosystème Java.
Sommaire de la leçon

Tu sais maintenant écrire des classes, manipuler des objets, gérer des exceptions et utiliser les fonctionnalités modernes de Java. Mais jusqu'ici, tes programmes tenaient souvent dans un seul fichier. Un vrai projet, lui, contient des dizaines voire des centaines de classes, des bibliothèques externes, des tests, de la documentation. Sans organisation, ça devient vite ingérable.

Cette leçon est une carte du territoire. On va voir comment ranger ton code (les packages), comment automatiser la compilation et les dépendances (Maven, Gradle), comment vérifier que ton code marche (JUnit), comment le documenter (Javadoc), et enfin vers quoi tendre ensuite. L'objectif n'est pas de tout maîtriser, mais de savoir que ces outils existent et à quoi ils servent.

Ranger son code : les packages

Un package est un dossier logique qui regroupe des classes liées. Il évite les collisions de noms (deux classes Compte dans deux packages différents ne se gênent pas) et clarifie l'architecture. La convention : on part d'un nom de domaine inversé, comme com.exemple.banque, ce qui garantit l'unicité dans le monde entier.

Note

Depuis Java 9, on peut regrouper des packages dans un module via un fichier module-info.java (le système JPMS). C'est puissant pour les grosses applications, mais la plupart des projets s'en passent. Retiens juste que ça existe.

Automatiser : les outils de build

Compiler à la main avec javac fonctionne pour quelques fichiers. Mais dès que ton projet utilise une bibliothèque externe (et il en utilisera), tu dois télécharger ses fichiers .jar, ceux dont elle dépend à son tour, gérer les versions… Un cauchemar manuel. C'est exactement ce que résolvent Maven et Gradle.

Ces outils gèrent les dépendances (ils téléchargent automatiquement les bibliothèques depuis le dépôt central Maven), compilent, lancent les tests et produisent un .jar exécutable. Ils imposent aussi une structure standard que tout développeur Java reconnaît :

Vérifier : les tests avec JUnit 5

Un test est un petit bout de code qui vérifie automatiquement qu'une méthode renvoie le bon résultat. Pourquoi tester ? Pour attraper les bugs tôt, et surtout pour modifier ton code sans peur : si les tests passent encore, tu n'as rien cassé. JUnit 5 est la bibliothèque de référence.

Cas réel

Sur un projet d'équipe, chaque pull request déclenche automatiquement mvn test sur un serveur d'intégration continue. Un jour, une optimisation anodine du calcul d'une remise casse un cas limite : la CI vire au rouge en deux minutes, avec le nom du test en échec et la valeur attendue. Sans ces tests, le bug serait parti en production et aurait faussé des milliers de commandes. C'est ça, « modifier sans peur » : le filet de sécurité alerte avant la mise en ligne.

Documenter : Javadoc

Javadoc transforme des commentaires spéciaux en documentation HTML navigable. Un commentaire Javadoc commence par /** et utilise des balises comme @param et @return.

La commande javadoc (ou mvn javadoc:javadoc) génère alors des pages web décrivant ton API. C'est ainsi qu'est produite la documentation officielle de Java elle-même. Ton éditeur affiche aussi ces descriptions quand tu survoles une méthode.

Bonnes pratiques de code

Au-delà des outils, quelques principes rendent ton code lisible et solide :

  • Nommage clair : PascalCase pour les classes, camelCase pour méthodes et variables, des noms qui décrivent l'intention (calculerTotal, pas calc).
  • Immuabilité : préfère les objets qu'on ne modifie plus après création. Les record de Java moderne sont parfaits pour ça.
  • Petites méthodes : une méthode fait une seule chose. Si elle dépasse l'écran, découpe-la.
  • Gérer les null : au lieu de renvoyer null (source du fameux NullPointerException), utilise Optional pour signaler « peut-être rien ».

Enfin, évite la sur-ingénierie : n'ajoute pas de complexité « au cas où ». Le code le plus simple qui résout le problème actuel est le meilleur.

L'écosystème Java

Java ne se limite pas au langage : c'est un immense écosystème de bibliothèques et frameworks. Voici les grandes directions selon ce que tu veux construire :

  • Spring / Spring Boot : le standard pour les applications back-end et les API web. Spring Boot démarre un serveur en quelques lignes.
  • Android : une grande partie des applications mobiles repose sur Java (et Kotlin, son cousin).
  • Bibliothèques courantes : Jackson (JSON), Guava (utilitaires), SLF4J/Logback (logs), Mockito (tests avec simulacres).

Tu installes toutes ces bibliothèques de la même façon : en ajoutant une dépendance dans ton pom.xml ou build.gradle. C'est tout l'intérêt des outils de build.

Pièges fréquents

Piège fréquent

Tout mettre dans le package par défaut (sans ligne package). Ça marche pour un exercice, mais c'est ingérable dès que le projet grandit, et on ne peut pas importer ces classes ailleurs. Crée toujours un package nommé.

  • Gérer les dépendances à la main : télécharger des .jar un par un mène vite au chaos des versions. Utilise Maven ou Gradle dès le départ.
  • Ne pas écrire de tests : « ça marche sur ma machine » n'est pas une garantie. Sans tests, chaque modification est un pari.
  • Comparer des double sans tolérance : à cause de l'imprécision des nombres à virgule flottante, préfère assertEquals(attendu, obtenu, 0.001) (le 3e argument est la marge d'erreur tolérée).
  • Les classes « God » : une classe de 2000 lignes qui fait tout. Découpe en responsabilités claires.
  • Ignorer les conventions de l'équipe : même si tu préfères un autre style, suis celui du projet. La cohérence prime sur les goûts personnels.

Pour aller plus loin

Pour aller plus loin

Quand tu seras à l'aise : Spring Boot pour créer des API et explorer les microservices ; JavaFX pour des interfaces graphiques de bureau ; la programmation concurrente (les Thread et l'ExecutorService) pour faire plusieurs choses en parallèle ; et GraalVM pour compiler ton application en exécutable natif ultra-rapide.

Glossaire

Package
Regroupement logique de classes liées, reflété par l'arborescence de dossiers (com.exemple.banque → com/exemple/banque/) ; évite les collisions de noms.
Visibilité
Niveau d'accès d'un membre : public (partout), protected (package + sous-classes), défaut (package), private (classe seule).
Outil de build
Maven ou Gradle : automatise la résolution des dépendances, la compilation, les tests et l'empaquetage.
Dépendance
Bibliothèque externe dont le projet a besoin ; déclarée dans pom.xml/build.gradle et téléchargée depuis le dépôt central.
JUnit
Bibliothèque de tests de référence ; une méthode @Test exécute du code et vérifie le résultat par des assertions.
Assertion
Vérification dans un test (assertEquals, assertTrue, assertThrows) ; le test échoue si la condition est fausse.
Javadoc
Documentation HTML générée à partir de commentaires /** … */ balisés (@param, @return).
Optional
Conteneur « valeur ou rien » renvoyé au lieu de null ; force l'appelant à traiter le cas vide et prévient le NullPointerException.

Récap et vérification

  • Un package range les classes ; la visibilité (public, private…) contrôle l'accès.
  • Maven et Gradle gèrent dépendances, compilation et tests, avec la structure src/main/java et src/test/java.
  • JUnit 5 teste ton code via @Test et des assertions comme assertEquals.
  • Javadoc génère la documentation à partir des commentaires /** ... */.
  • Bonnes pratiques : noms clairs, immuabilité, petites méthodes, Optional contre les null, pas de sur-ingénierie.
  • L'écosystème (Spring, Android, bibliothèques) s'ouvre via une simple dépendance.
