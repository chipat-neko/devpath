Concurrence moderne : CompletableFuture et threads virtuels

~38 min Avancé Leçon 15 (concurrence) requise

À la fin de cette leçon, tu sauras

  • composer des tâches asynchrones avec CompletableFuture ;
  • enchaîner (thenApply, thenCompose) et combiner (thenCombine) ;
  • gérer les erreurs (exceptionally, handle) sans bloquer ;
  • comprendre les threads virtuels (Java 21) et quand les utiliser.
Sommaire de la leçon

À la leçon 15, tu as vu les Thread et les ExecutorService : comment lancer du travail en parallèle. Reste une question : comment enchaîner des étapes asynchrones — « récupère l'utilisateur, puis ses commandes, puis calcule le total » — sans bloquer un thread à chaque attente, et sans sombrer dans un enfer de rappels imbriqués ? La réponse de Java tient en deux outils : CompletableFuture pour composer, et les threads virtuels (Java 21) pour changer d'échelle.

CompletableFuture : une valeur « à venir »

Un CompletableFuture<T> représente un résultat de type T qui arrivera plus tard. Au lieu d'attendre ce résultat en bloquant, on décrit ce qu'on veut en faire une fois disponible. On démarre une tâche avec supplyAsync, puis on greffe des transformations qui ne s'exécuteront qu'à l'arrivée.

Chaque thenApply renvoie un nouveau CompletableFuture : on empile les étapes comme un tuyau. join() (ou get()) force enfin l'attente — on le réserve au tout dernier moment, quand la valeur est indispensable.

thenApply, thenCompose, thenCombine

Trois façons d'enchaîner, à ne pas confondre :

  • thenApply : transformer la valeur avec une fonction ordinaire (T → U).
  • thenCompose : enchaîner une étape qui rend elle-même un futur (T → CompletableFuture<U>) — pour éviter un futur imbriqué dans un futur.
  • thenCombine : attendre deux futurs indépendants et fusionner leurs résultats.

Gérer les erreurs sans try/catch

Dans une chaîne asynchrone, une exception ne remonte pas par un try/catch classique : elle voyage dans le futur. On la traite avec exceptionally (fournir une valeur de repli) ou handle (voir à la fois le résultat et l'erreur).

Piège — join() trop tôt annule tout le bénéfice

Si tu appelles join() juste après supplyAsync, puis lances la deuxième tâche, tu es redevenu séquentiel : tu attends la première avant de démarrer la seconde. Le bon réflexe : d'abord déclarer tous les futurs (ils partent en parallèle), ensuite seulement les rejoindre. De même, une exception avalée sans exceptionally/handle reste tapie dans le futur : tu la découvriras — trop tard — au join().

Les threads virtuels (Java 21)

Un Thread classique (dit de plateforme) est mappé sur un thread du système d'exploitation : il coûte cher (environ 1 Mo de pile) et on ne peut en avoir que quelques milliers. Résultat : pour tenir des dizaines de milliers de connexions, on renonçait au code simple « un thread par requête » au profit d'un style asynchrone plus difficile à lire.

Les threads virtuels (projet Loom, stables en Java 21) renversent la donne : ils sont si légers qu'on peut en créer des millions. Quand un thread virtuel se bloque sur une entrée-sortie, la JVM le « démonte » et libère le thread porteur pour un autre. On écrit du code bloquant, simple et linéaire… qui passe à l'échelle comme de l'asynchrone.

Astuce — I/O ou calcul ? le bon outil

Distingue deux mondes. Pour des tâches d'entrée-sortie (appels réseau, requêtes en base, lecture de fichiers) qui passent leur temps à attendre : les threads virtuels brillent — un par tâche, code linéaire. Pour du calcul pur qui sature le processeur (traitement d'image, chiffrement) et n'attend jamais : reste sur un pool de threads de plateforme dimensionné au nombre de cœurs (ForkJoinPool/parallel streams). Un thread virtuel n'accélère pas le calcul : il excelle à attendre à grande échelle.

Cas réel — l'agrégateur qui appelait dix API

Un service devait, pour afficher une fiche produit, interroger dix API internes (stock, prix, avis, livraison…). En version séquentielle : dix appels de 150 ms bout à bout, soit 1,5 s de latence — inacceptable. Réécrit avec dix CompletableFuture lancés d'un coup et rassemblés par allOf(...).thenApply(...), le temps total est tombé à celui du plus lent, environ 200 ms. Plus tard, la migration du serveur vers les threads virtuels a permis de garder le code bloquant simple des endpoints tout en encaissant dix fois plus de connexions simultanées, sans réécrire la logique en style asynchrone.

Pour aller plus loin

CompletableFuture.allOf(...) attend un lot de futurs ; anyOf(...) rend la main dès le premier fini (utile pour un timeout concurrent). Attention à l'exécuteur : par défaut les *Async tournent sur le ForkJoinPool.commonPool() partagé ; pour de l'I/O, passe le tien. Côté Loom, évite le pinning : un bloc synchronized autour d'une opération bloquante épingle le thread virtuel à son porteur (préfère un ReentrantLock). Enfin, la concurrence structurée (StructuredTaskScope) traite un groupe de sous-tâches comme une unité : si l'une échoue, les autres sont annulées.

Glossaire

CompletableFuture
Objet représentant un résultat futur de type T ; on y greffe des étapes qui s'exécuteront à l'arrivée, sans bloquer.
supplyAsync
Démarre une tâche qui produit une valeur sur un autre thread et rend aussitôt un CompletableFuture.
thenApply / thenCompose
thenApply transforme la valeur avec une fonction ordinaire ; thenCompose enchaîne une étape elle-même asynchrone (sans futur imbriqué).
thenCombine
Attend deux futurs indépendants et fusionne leurs résultats : les deux tâches avancent en parallèle.
exceptionally / handle
Traitent une erreur survenue dans la chaîne : exceptionally fournit un repli ; handle reçoit à la fois le résultat et l'erreur.
join
Bloque jusqu'à ce que le futur soit prêt et rend sa valeur ; à réserver au dernier moment, une fois toutes les tâches lancées.
Thread de plateforme
Thread classique mappé 1:1 sur un thread du système : coûteux (~1 Mo), limité à quelques milliers.
Thread virtuel
Thread très léger géré par la JVM (Java 21) ; on peut en avoir des millions. Idéal pour l'I/O, il rend le code bloquant simple de nouveau viable.

Récap et vérification

  • CompletableFuture décrit un résultat à venir et enchaîne des étapes sans bloquer.
  • thenApply (transformer), thenCompose (enchaîner un futur), thenCombine (combiner deux futurs).
  • Les erreurs se traitent par exceptionally/handle ; join() se garde pour la fin.
  • Les threads virtuels (Java 21) rendent « un thread par tâche » viable pour l'I/O à grande échelle.
  • I/O → threads virtuels ; calcul pur → pool de threads de plateforme dimensionné aux cœurs.

Vérifie ta compréhension

  1. Avec thenCombine sur deux appels indépendants, à quoi correspond la durée d'attente totale ?
  2. Pourquoi ne pas appeler join() trop tôt ?
  3. Pour quel type de tâches les threads virtuels sont-ils faits ?
