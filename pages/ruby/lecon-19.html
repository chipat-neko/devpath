Module 6 · Ruby au quotidien — Leçon 19

JSON, le web et les APIs

~45 min Intermédiaire Hachages (leçon 5) utiles

À la fin de cette leçon, tu sauras

  • convertir entre JSON et structures Ruby (parse / to_json) ;
  • interroger une API web avec Net::HTTP et URI ;
  • naviguer dans une réponse imbriquée avec dig ;
  • gérer les erreurs réseau et de format avec rescue.
Sommaire de la leçon

Presque tous les services en ligne échangent des données au format JSON : la météo, une carte, un catalogue, un réseau social. Savoir lire ce format et interroger une API transforme tes scripts : ils ne sont plus enfermés dans ta machine, ils dialoguent avec le monde. Bonne nouvelle : Ruby fournit tout dans sa bibliothèque standard, sans rien installer.

JSON ↔ structures Ruby

Le JSON (JavaScript Object Notation) est du texte : des objets { }, des tableaux [ ], des chaînes, des nombres, des booléens. Le module json fait la traduction dans les deux sens : JSON.parse transforme un texte en hachage/tableau Ruby ; to_json fait l'inverse.

Interroger une API web

Une API REST expose des données à une adresse (URL). On lui envoie une requête HTTP et elle répond, le plus souvent, par du JSON. La bibliothèque standard net/http suffit : on enveloppe l'URL dans un objet URI, on récupère le corps de la réponse (une chaîne), puis on la parse.

Pour connaître le code de statut (200 OK, 404 introuvable, 500 erreur serveur), on utilise get_response qui renvoie un objet réponse complet plutôt que le seul corps.

Naviguer et sécuriser la lecture

Les réponses d'API sont souvent imbriquées. La méthode dig descend en toute sécurité dans une structure : si un maillon manque, elle renvoie nil au lieu de planter.

Un script complet et robuste

Le réseau échoue parfois : serveur injoignable, réponse invalide, coupure. Un script sérieux entoure ses appels d'un rescue pour ne pas s'effondrer sur la première erreur.

Choisis tes clés dès le parse

Décide une bonne fois si tu veux des clés chaînes ou symboles, et reste cohérent. symbolize_names: true donne des data[:nom] élégants, familiers si tu viens de Rails. Mais si les clés JSON sont dynamiques ou nombreuses, garder des chaînes évite de créer une multitude de symboles. Dans les deux cas, dig fonctionne à l'identique.

Ne fais jamais confiance au réseau

Deux réflexes vitaux : vérifier le code de statut avant de lire le corps (un 404 renvoie souvent une page d'erreur, pas ton JSON), et entourer d'un rescue les erreurs réseau (SocketError, délais) et de format (JSON::ParserError). Et surtout : n'utilise jamais eval pour lire du JSON — ce serait exécuter du code venu d'ailleurs. JSON.parse est sûr ; eval est une porte ouverte.

Cas réel : un tableau de bord bricolé en une soirée

Le trésorier d'un petit club voulait suivre le taux de change euro-dollar pour ses achats de matériel à l'étranger. Plutôt qu'un tableur mis à jour à la main, il a écrit un script Ruby de vingt lignes : un appel Net::HTTP.get vers une API de taux publique, un JSON.parse, un dig pour extraire le cours du jour, et un puts formaté. Programmé pour tourner chaque matin (via cron), il écrivait le résultat dans un fichier taux.csv. En quelques jours, il disposait d'un historique exploitable, sans aucun service payant. La leçon : dès qu'une donnée existe derrière une API, une poignée de lignes Ruby suffit à la capturer, l'archiver et la réutiliser.

Pour aller plus loin

Net::HTTP est verbeux pour les cas avancés (en-têtes, authentification, POST). Les gems Faraday et HTTParty offrent une interface plus douce ; Oj accélère l'analyse JSON sur de gros volumes. Pour tester du code qui appelle une API sans dépendre du réseau, la gem WebMock simule les réponses. Et pour envoyer des données, tu enverras un corps JSON avec un en-tête Content-Type: application/json dans une requête POST.

Glossaire

JSON
JavaScript Object Notation : format texte d'échange de données (objets, tableaux, chaînes, nombres, booléens).
Sérialiser
Convertir une structure en mémoire vers un format texte transportable (to_json) ; l'inverse est désérialiser (JSON.parse).
API REST
Service web exposant des données à des URL ; on l'interroge par des requêtes HTTP (GET, POST…) et il répond souvent en JSON.
URI
Objet représentant une adresse web ; Net::HTTP attend une URI, pas une simple chaîne.
Net::HTTP
Bibliothèque standard des requêtes HTTP ; get renvoie le corps, get_response l'objet réponse complet.
Code de statut
Nombre renvoyé par le serveur : 200 succès, 404 introuvable, 500 erreur serveur.
dig
Descend dans une structure imbriquée (Hash/Array) ; renvoie nil si un maillon manque, sans lever d'erreur.
rescue
Rattrape une exception (erreur réseau, JSON invalide) pour la traiter au lieu de laisser le programme s'arrêter.

Récap et vérification

  • JSON.parse transforme du texte en Hash/Array ; to_json fait l'inverse. symbolize_names: true donne des clés symboles.
  • On interroge une API en enveloppant l'URL dans URI puis via Net::HTTP.get (corps) ou get_response (statut + corps).
  • Vérifie le code de statut avant de lire le corps ; un 404 ne contient pas tes données.
  • dig lit en sûreté une structure imbriquée ; il renvoie nil plutôt que de planter.
  • Entoure les appels réseau d'un rescue (SocketError, JSON::ParserError) ; n'utilise jamais eval sur du JSON.

Vérifie ta compréhension

  1. Que renvoie JSON.parse('{"a": 1}'), et de quel type sont ses clés ?
  2. Pourquoi passer par URI(...) avant Net::HTTP.get ?
  3. Quel intérêt a dig par rapport à data["a"]["b"] ?
