Module 5 · Le web avec Rails — Leçon 16

Découvrir Rails : MVC et scaffolding

~44 min Intermédiaire Bases de Ruby requises

À la fin de cette leçon, tu sauras

  • comprendre l'architecture MVC de Rails ;
  • créer une application avec rails new ;
  • générer un CRUD complet par scaffolding ;
  • lire les routes, contrôleurs et migrations générés.
Sommaire de la leçon

Ruby on Rails est le framework qui a fait la célébrité de Ruby. Il fait tourner Shopify, GitHub, Basecamp et des milliers d'applications. Sa philosophie : la convention plutôt que la configuration — Rails devine ce que tu veux faire à partir de noms bien choisis, et te fait écrire très peu de code pour beaucoup de résultat. Après avoir appris le langage Ruby, voici sa destination naturelle : construire une vraie application web.

Cette leçon te fait créer une application et générer un CRUD complet en quelques commandes. La suivante (ActiveRecord et vues) entrera dans les détails.

L'architecture MVC

Rails organise le code en trois rôles — le patron MVC :

  • le Modèle (Model) : les données et les règles métier (une classe par table, via ActiveRecord) ;
  • la Vue (View) : l'affichage (des gabarits HTML) ;
  • le Contrôleur (Controller) : le chef d'orchestre, qui reçoit la requête, interroge le modèle et choisit la vue.

Une requête HTTP arrive, le routeur la dirige vers une action de contrôleur, qui prépare des données (via le modèle) et rend une vue. Cette séparation rend l'application claire et testable.

Créer une application

La commande rails new génère une application complète : structure de dossiers, configuration, base de données prête. Tout est là pour démarrer.

Le dossier généré suit une convention stricte : app/models, app/views, app/controllers, config/routes.rb, db/… Rails sait où trouver chaque chose parce que tout est à sa place attendue.

Le scaffolding : un CRUD en une commande

La démonstration de force de Rails : le scaffolding génère d'un coup le modèle, le contrôleur, les vues et les routes pour gérer une ressource (créer, lire, modifier, supprimer).

En deux commandes, tu as une interface web fonctionnelle : liste des articles, formulaire de création, page de détail, édition, suppression. Visite /articles et tout marche. C'est ce qui rend Rails si productif pour démarrer.

Erreur fréquente

Après un rails generate scaffold, on oublie souvent rails db:migrate : la page /articles renvoie alors une erreur du type « table “articles” n'existe pas ». Le scaffolding a bien écrit la migration, mais elle n'est pas encore appliquée à la base. Le réflexe : générer, puis migrer.

Les routes

Le fichier config/routes.rb associe les URL aux actions. Le scaffolding y a ajouté une ligne qui crée les sept routes REST d'une ressource.

La seule ligne resources :articles déclare les sept routes conventionnelles (lister, afficher, créer, modifier, supprimer). Encore une fois, la convention t'évite d'écrire chaque route à la main.

Le contrôleur

Le contrôleur généré contient une action par route. Chacune prépare des données et laisse Rails rendre la vue du même nom.

Les variables d'instance (@articles) passées dans l'action sont automatiquement visibles dans la vue. Et article_params illustre les strong parameters : une sécurité qui n'autorise que les champs explicitement permis — on ne fait jamais confiance aux données du formulaire en bloc.

Cas réel

Rails n'est pas né dans un laboratoire : David Heinemeier Hansson l'a extrait en 2004 de Basecamp, un logiciel de gestion de projet bien réel, avant de l'ouvrir au monde. La vidéo « construire un blog en 15 minutes », tournée d'une traite avec le scaffolding, a stupéfié les développeurs web de l'époque et lancé le framework. Aujourd'hui GitHub, Shopify, Airbnb à ses débuts et des milliers de startups reposent dessus. Ce que tu viens de faire en deux commandes — un CRUD complet en quelques secondes — est exactement ce qui a fait la réputation de Rails.

Astuce

La commande rails routes affiche toutes les routes de l'application : l'URL, le verbe HTTP, et l'action de contrôleur correspondante. C'est la carte de ton application : indispensable pour comprendre « quelle URL fait quoi ».

Pour aller plus loin

Le scaffolding est parfait pour démarrer et apprendre, mais en projet réel on génère plutôt les pièces séparément (rails g model, rails g controller) pour garder la main sur chaque partie. Rails offre énormément au-delà : validations, associations entre modèles, authentification, jobs en arrière-plan, e-mails, API… Tu as ici la fondation ; la prochaine leçon creuse le modèle (ActiveRecord) et les vues.

Glossaire

MVC
Modèle-Vue-Contrôleur : l'organisation du code en trois rôles — les données (modèle), l'affichage (vue) et l'orchestration des requêtes (contrôleur).
Convention over configuration
Principe fondateur de Rails : respecter des conventions de nommage (modèle Article → table articles → ArticlesController) connecte tout automatiquement, sans configuration.
Scaffolding
Génération automatique, en une commande, de toutes les pièces d'une ressource : migration, modèle, contrôleur, vues et route.
CRUD
Create, Read, Update, Delete : les quatre opérations de base sur une ressource — créer, lire, modifier, supprimer.
Migration
Classe Ruby versionnée décrivant un changement du schéma de la base ; rails db:migrate l'applique réellement.
resources
Ligne du fichier de routes qui déclare d'un coup les sept routes REST conventionnelles d'une ressource.
Action
Méthode publique d'un contrôleur associée à une route (index, show, create…) ; elle prépare les données et rend une vue.
Strong parameters
Mécanisme de sécurité (require / permit) n'autorisant que les champs explicitement listés à être affectés en masse depuis un formulaire.

Récap et vérification

  • MVC : Modèle (données), Vue (affichage), Contrôleur (chef d'orchestre) ; « convention plutôt que configuration ».
  • rails new crée l'app ; rails server la lance.
  • Le scaffolding (rails g scaffold) génère un CRUD complet ; rails db:migrate crée la table.
  • resources :articles crée les 7 routes REST ; les variables @… du contrôleur passent à la vue.

Exercice 3Défi

À quoi servent les strong parameters (params.require(...).permit(...)) ?

Voir une solution

Ils constituent une sécurité : ils n'autorisent que les champs explicitement permis à être affectés en masse à un modèle depuis les données d'un formulaire. Sans eux, un utilisateur malveillant pourrait soumettre des champs supplémentaires (par ex. admin: true) et les voir enregistrés. On ne fait jamais confiance aux paramètres d'une requête en bloc : on déclare précisément ceux qu'on accepte.
