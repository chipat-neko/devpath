La concurrence : threads, GVL et Ractor

~42 min Avancé Objets et erreurs requis

À la fin de cette leçon, tu sauras

  • lancer des threads et comprendre le rôle du GVL ;
  • distinguer une tâche I/O-bound d'une tâche CPU-bound ;
  • protéger un état partagé avec un Mutex et une Queue ;
  • savoir quand viser le vrai parallélisme avec un Ractor.
Sommaire de la leçon

Attendre une réponse réseau, lire dix fichiers, interroger trois APIs : souvent, un programme passe le plus clair de son temps à attendre. Pendant ces attentes, il pourrait faire autre chose. La concurrence consiste à structurer un programme pour qu'il progresse sur plusieurs tâches à la fois. Ruby offre plusieurs outils pour ça — mais avec une particularité qu'il faut comprendre avant tout : le GVL.

Les threads et le GVL

Un thread est un fil d'exécution au sein du programme. On en crée un avec Thread.new et on attend sa fin avec join. Mais dans l'interpréteur de référence (MRI/CRuby), un verrou global — le GVL (Global VM Lock, jadis « GIL ») — garantit qu'un seul thread exécute du code Ruby à la fois.

Le point clé : le GVL est relâché pendant les opérations d'entrée/sortie bloquantes (réseau, disque, sleep). Un thread qui attend le réseau laisse donc les autres avancer. C'est pourquoi les threads Ruby accélèrent bel et bien les tâches d'attente — mais pas le calcul pur.

I/O-bound contre CPU-bound

Une tâche est I/O-bound si son temps est dominé par des attentes (requête HTTP, base de données, lecture de fichier). Elle est CPU-bound si son temps est dominé par du calcul (hachage, compression, traitement d'image). Les threads MRI accélèrent la première catégorie, pas la seconde : pour du calcul pur, le GVL empêche deux threads de progresser en même temps.

Partager sans corrompre : Mutex et Queue

Dès que plusieurs threads touchent la même donnée, un danger apparaît : la condition de course (race condition). Même compteur += 1 n'est pas atomique : c'est lire, incrémenter, écrire. Deux threads peuvent lire la même valeur avant que l'un n'écrive, et une incrémentation est perdue. Un Mutex (mutual exclusion) sérialise l'accès : synchronize garantit qu'un seul thread est dans le bloc à la fois.

Mesure avant d'optimiser

Ne parallélise pas à l'aveugle. Chronomètre avec Benchmark.realtime une version séquentielle, puis une version à threads. Si la tâche est I/O-bound, tu verras un gain net ; si elle est CPU-bound en MRI, le temps ne bougera pas — c'est le signal qu'il faut des processus ou des Ractor, pas des threads.

Ractor : le vrai parallélisme

Pour exécuter du calcul Ruby réellement en parallèle sur plusieurs cœurs, Ruby 3 introduit les Ractor (Ruby actors). Chaque Ractor a son propre GVL et n'accède pas à la mémoire mutable des autres : ils communiquent par messages (send/receive). Cette isolation supprime par construction les conditions de course.

Les Ractor restent expérimentaux et imposent des contraintes fortes (les objets échangés doivent être immuables ou copiés). Pour la plupart des besoins courants — surtout I/O-bound — les threads suffisent ; réserve les Ractor au calcul lourd qu'on veut vraiment étaler sur plusieurs cœurs.

Le GVL n'est pas un bouclier

On lit parfois « le GVL rend Ruby thread-safe » : c'est faux. Le GVL protège les structures internes de l'interpréteur, pas tes données. Un tableau << x concurrent, un hash[k] = v partagé, un compteur += 1 : tous peuvent se corrompre sans Mutex. Ne partage jamais d'état mutable entre threads sans protection explicite.

Cas réel : agréger cinquante flux RSS

Un tableau de bord interne devait récupérer les cinquante flux RSS de l'équipe et les fusionner. En version séquentielle, chaque Net::HTTP.get attendait sa réponse avant de lancer le suivant : 38 secondes de rafraîchissement, l'essentiel passé à ne rien faire. En enveloppant chaque téléchargement dans un Thread.new et en collectant les résultats dans une Queue, le temps est tombé à 2,5 secondes : les cinquante attentes réseau se sont recouvertes. Aucun Ractor, aucun code savant — juste la bonne lecture « c'est de l'I/O, donc les threads vont aider ».

Pour aller plus loin

Trois pistes selon le besoin : les Fibers (coroutines coopératives, Fiber.new/resume) et le Fiber Scheduler de Ruby 3 sous-tendent la gem async pour des milliers de connexions I/O légères ; les processus (fork, ou la gem parallel) offrent un vrai parallélisme CPU au prix d'une mémoire non partagée ; et dans le monde web, les serveurs comme Puma combinent plusieurs processus (pour le CPU) et plusieurs threads par processus (pour l'I/O).

Antisèche

Glossaire

Thread
Fil d'exécution au sein d'un processus ; créé par Thread.new, attendu par join.
GVL
Global VM Lock : verrou de MRI garantissant qu'un seul thread exécute du bytecode Ruby à la fois ; relâché durant les I/O.
I/O-bound
Tâche dont le temps est dominé par l'attente (réseau, disque) ; accélérable par des threads.
CPU-bound
Tâche dont le temps est dominé par le calcul ; non accélérée par les threads en MRI.
Condition de course
Bug où le résultat dépend de l'entrelacement imprévisible de threads accédant à un même état.
Mutex
Mutual exclusion : verrou assurant qu'un seul thread entre dans une section critique (synchronize).
Queue
File thread-safe intégrée ; push d'un côté, pop (bloquant) de l'autre, sans mutex manuel.
Ractor
Acteur isolé de Ruby 3 sans mémoire mutable partagée ; permet un vrai parallélisme par messages.

Récap et vérification

  • Un thread (Thread.new + join) exécute un fil concurrent ; le GVL n'en laisse qu'un exécuter du Ruby à la fois.
  • Le GVL est relâché pendant les I/O : les threads accélèrent l'I/O-bound, pas le CPU-bound.
  • Tout état mutable partagé exige un Mutex ; une Queue est déjà sûre.
  • Pour du vrai parallélisme de calcul, vise les Ractor ou des processus.
  • Règle d'or : mesure (Benchmark) avant de conclure qu'une parallélisation aide.

Vérifie ta compréhension

  1. Pourquoi les threads accélèrent-ils une série de requêtes HTTP mais pas un gros calcul ?
  2. Le GVL protège-t-il compteur += 1 partagé entre threads ? Pourquoi ?
  3. Quand choisir un Ractor plutôt qu'un Thread ?

Exercices

Exercice 1Échauffement

Lance trois threads qui affichent chacun leur numéro, puis attends-les tous avant d'afficher "terminé".

Voir une solution

each(&:join) attend la fin de chaque thread : sans lui, le programme pourrait afficher "terminé" avant les threads.

Exercice 2Application

Mille threads incrémentent un compteur partagé. Protège l'accès avec un Mutex pour que le total final soit exactement 1000.

Voir une solution

Sans le synchronize, le résultat serait souvent inférieur à 1000 : c'est la condition de course en action.

Exercice 3Défi

Explique en une phrase pourquoi remplacer Thread.new par Ractor.new peut accélérer un calcul lourd mais compliquer le partage de données.

Voir une solution

Un Ractor possède son propre GVL, donc plusieurs Ractor calculent réellement en parallèle sur plusieurs cœurs (gain pour le CPU-bound) ; mais comme ils ne partagent pas de mémoire mutable, toute donnée doit être copiée ou immuable et échangée par messages (send/take), ce qui alourdit le code par rapport à des threads qui, eux, partagent la mémoire (au prix des conditions de course).
