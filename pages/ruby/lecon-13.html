Module 4 · Ruby en pratique — Leçon 13

Gems, Bundler et structure de projet

~45 min Intermédiaire Prérequis : leçon 12

À la fin de cette leçon, tu sauras

  • savoir installer une gem avec gem install et la charger avec require ;
  • savoir déclarer ses dépendances dans un Gemfile, lire une contrainte pessimiste ~> et expliquer le rôle de Gemfile.lock et de bundle exec ;
  • savoir organiser un projet Ruby idiomatique avec lib/, bin/, des tests et un README ;
  • savoir automatiser les tâches répétitives d'un projet avec un Rakefile.
Sommaire de la leçon

Jusqu'ici, tout ton code Ruby tenait dans un fichier ou deux, et tu n'utilisais que la bibliothèque standard. Mais la vraie force de Ruby, c'est aussi sa communauté : des dizaines de milliers de bibliothèques prêtes à l'emploi, qu'on appelle des gems. Faire une requête HTTP, analyser du HTML, colorer du texte dans le terminal… il existe presque toujours une gem pour ça.

Dans cette leçon, tu vas apprendre à installer des gems, à gérer proprement les dépendances d'un projet avec Bundler, à organiser tes fichiers comme le font les Rubyistes, et à automatiser les tâches répétitives avec Rake. C'est le passage du « script dans un coin » au projet digne de ce nom.

RubyGems : la bibliothèque mondiale de Ruby

Une gem est un paquet de code Ruby réutilisable : une bibliothèque, parfois accompagnée d'un exécutable. Toutes les gems publiques sont hébergées sur rubygems.org, le dépôt central de la communauté. L'outil gem, fourni avec Ruby, permet de les installer en une commande :

Bundler et le Gemfile : déclarer ses dépendances

Installer des gems à la main, ça va cinq minutes. Dès qu'un projet dépend de plusieurs gems, tu veux pouvoir dire « voici exactement ce dont mon projet a besoin » — et qu'un autre développeur (ou toi, dans six mois) retrouve le même environnement. C'est le rôle de Bundler, livré avec Ruby, et de son fichier Gemfile, placé à la racine du projet :

Un Gemfile minimal : la source des gems, puis une ligne par dépendance.

Le require: false sur la dernière ligne indique simplement que rubocop est un outil qu'on lance en ligne de commande : il n'a pas besoin d'être chargé dans le code du programme.

La contrainte "~> 0.23" s'appelle une contrainte pessimiste (pessimistic constraint). Elle se lit « au moins cette version, mais sans changer le chiffre de gauche ». Concrètement :

  • "~> 1.2" accepte toute version >= 1.2 et < 2.0 ;
  • "~> 1.2.3" accepte toute version >= 1.2.3 et < 1.3.0.

Pourquoi « pessimiste » ? Parce qu'elle suppose qu'un changement de version majeure risque de casser ton code. C'est lié au versionnage sémantique (semver), une convention suivie par la plupart des gems : une version MAJEURE.MINEURE.CORRECTIF où la majeure change quand l'API casse la compatibilité, la mineure quand on ajoute des fonctionnalités sans rien casser, et le correctif pour les corrections de bugs. ~> te laisse donc profiter des nouveautés et des correctifs, tout en te protégeant des ruptures.

Gemfile.lock et bundle exec : la reproductibilité

Après bundle install, Bundler crée un fichier Gemfile.lock. Là où le Gemfile exprime tes souhaits (« une version 0.23.x de httparty »), le lock enregistre les versions exactes qui ont été installées — y compris celles des dépendances de tes dépendances. Tu ne l'écris jamais à la main, mais tu dois le committer dans Git : c'est lui qui garantit que toute l'équipe, ton serveur et ton intégration continue utilisent rigoureusement les mêmes versions. Sans lui, « ça marche chez moi » redevient une loterie.

Cas réel

Une équipe avait mis Gemfile.lock dans le .gitignore, jugeant le fichier « généré, donc inutile à versionner ». Pendant des mois, tout allait bien. Puis une gem de traitement d'images publie une version mineure au comportement légèrement modifié. Le serveur de déploiement, qui relançait bundle install à chaque mise en ligne, installe cette nouveauté — alors que les développeurs gardaient l'ancienne version en cache local. Résultat : des miniatures déformées en production uniquement, introuvables en développement, et une soirée entière à comprendre pourquoi « le même code » se comportait différemment. Committer le lock aurait figé la version pour tout le monde et rendu ce bug impossible.

Dernière pièce du puzzle : bundle exec. Sur ta machine, plusieurs versions d'une même gem peuvent cohabiter (installées par différents projets). Préfixer une commande par bundle exec force Ruby à utiliser exactement les versions du Gemfile.lock du projet courant :

Une structure de projet idiomatique

Les projets Ruby suivent presque tous la même organisation. La respecter rend ton code immédiatement lisible pour n'importe quel Rubyiste — et pour les outils de l'écosystème :

La structure canonique : le code vit dans lib/, les exécutables dans bin/.

Le principe : lib/ contient toute la logique, bin/ ne contient que de minuscules scripts qui chargent lib/ et lancent le programme. Les tests vont dans spec/ (avec RSpec) ou test/ (avec Minitest), et le README.md explique à quoi sert le projet et comment l'utiliser.

Rake : automatiser les tâches du projet

Rake est l'outil d'automatisation de Ruby : tu décris des tâches dans un fichier Rakefile (écrit en Ruby !), puis tu les lances avec la commande rake. Idéal pour tester, nettoyer, générer… sans retaper les mêmes commandes :

desc documente la tâche, task la définit ; :default désigne celle lancée sans argument.

La commande rake -T liste toutes les tâches documentées par un desc — c'est la première chose à taper quand tu découvres un projet Ruby.

La commande gem build meteo.gemspec produit alors un fichier meteo-0.1.0.gem, prêt à être publié sur rubygems.org avec gem push. C'est tout : une gem n'a rien de magique, c'est ton code emballé avec une étiquette. Tu retrouves d'ailleurs le versionnage sémantique dans spec.version — à toi de le respecter pour tes utilisateurs.

Trois gems à connaître dès maintenant

Pour finir, trois gems que tu croiseras partout et qui valent le détour :

  • rubocop — le gardien du style. Il analyse ton code et signale ce qui s'écarte des conventions de la communauté (et peut corriger automatiquement avec rubocop -a).
  • pry — une console interactive surpuissante pour déboguer. Tu insères binding.pry dans ton code, et l'exécution s'arrête là, te laissant inspecter les variables en direct.
  • httparty — des requêtes HTTP simples et lisibles, comme tu l'as vu plus haut. Son slogan officiel : « Makes http fun again! » — tout un programme, très Ruby dans l'esprit.

Pièges fréquents

Piège fréquent

Oublier bundle exec : tu lances alors la version globale de la gem, pas celle du projet. Symptôme classique, l'erreur Gem::LoadError: You have already activated rake 13.0.6, but your Gemfile requires rake 13.2.1 — Bundler te suggère d'ailleurs lui-même d'ajouter bundle exec devant la commande.

Piège fréquent

Mettre Gemfile.lock dans le .gitignore d'une application : chaque machine installerait alors des versions potentiellement différentes, et les bugs « impossibles à reproduire » se multiplient. Committe-le toujours pour une application.

Piège fréquent

Confondre require et require_relative. require "rapport" cherche dans les gems installées et échoue avec LoadError: cannot load such file -- rapport. Pour tes propres fichiers, utilise require_relative "rapport" (chemin relatif au fichier courant, sans extension .rb).

Pour aller plus loin

Pour aller plus loin

La commande bundle gem mon_projet génère en une fois toute la structure d'une gem (lib/, gemspec, Rakefile, tests…) : une excellente façon d'étudier un squelette idiomatique. Explore aussi les groupes du Gemfile (group :development do … end) pour séparer les gems de développement de celles de production, et bundle update pour mettre à jour le lock en respectant tes contraintes. Enfin, le site Ruby Toolbox compare les gems par catégorie et par popularité.

Glossaire

Gem
Paquet de code Ruby réutilisable (bibliothèque, parfois avec un exécutable), publié sur rubygems.org et installable en une commande.
Bundler
Outil livré avec Ruby qui installe et fige les dépendances d'un projet à partir du Gemfile (commande bundle).
Gemfile
Fichier à la racine du projet listant les dépendances voulues et leurs contraintes de version.
Gemfile.lock
Fichier généré qui fige les versions exactes résolues, dépendances transitives comprises ; on le committe pour une application.
Contrainte pessimiste (~>)
Opérateur de version qui autorise la montée du dernier segment écrit mais verrouille celui d'avant, pour éviter les ruptures.
Semver
Versionnage sémantique MAJEURE.MINEURE.CORRECTIF : la majeure casse la compatibilité, la mineure ajoute, le correctif répare.
bundle exec
Préfixe qui force une commande à utiliser exactement les versions du Gemfile.lock du projet courant.
require_relative
Charge un fichier par chemin relatif au fichier courant (tes propres fichiers), là où require vise le load path.

Récap et vérification

  • Une gem est un paquet de code Ruby publié sur rubygems.org ; on l'installe avec gem install et on la charge avec require.
  • Le Gemfile déclare les dépendances d'un projet ; bundle install les installe et fige les versions exactes dans Gemfile.lock, qu'on committe.
  • La contrainte pessimiste ~> 1.2 autorise >= 1.2 et < 2.0, en s'appuyant sur le versionnage sémantique MAJEURE.MINEURE.CORRECTIF.
  • bundle exec garantit que la commande utilise les versions du lock du projet.
  • Structure idiomatique : code dans lib/, exécutables dans bin/, tests dans spec/ ou test/, plus README, Gemfile et Rakefile ; tes fichiers se chargent entre eux avec require_relative.
  • Rake automatise les tâches du projet : desc documente, task définit, rake -T liste.
