Méthodes : l'art du message

~45 min Intermédiaire Prérequis : leçon 7

À la fin de cette leçon, tu sauras

  • Savoir définir une méthode avec def et exploiter le retour implicite de la dernière expression ;
  • Savoir rendre tes appels lisibles avec les valeurs par défaut, les arguments nommés, *args et **options ;
  • Savoir appliquer les conventions ? et ! et choisir quand omettre les parenthèses ;
  • Savoir envoyer un message dynamiquement avec public_send et protéger tes détails internes avec private.
Sommaire de la leçon

Dans la plupart des langages, on dit qu'on « appelle une fonction ». En Ruby, le vocabulaire change, et ce n'est pas un caprice : on envoie un message à un objet. Quand tu écris "ruby".upcase, tu ne déclenches pas une procédure flottant dans le vide — tu demandes poliment à l'objet "ruby" s'il veut bien répondre au message upcase. C'est l'héritage direct de Smalltalk, et c'est le cœur du modèle objet de Ruby : tout est objet, et les objets se parlent.

Dans cette leçon, tu vas apprendre à définir tes propres méthodes, à profiter du retour implicite (un idiome central du langage), à rendre tes appels lisibles avec les arguments nommés, et à découvrir send, la porte d'entrée de la métaprogrammation. À la fin, tu écriras des méthodes que n'importe quel rubyiste lira avec plaisir.

Appeler une méthode, c'est envoyer un message

Une méthode se définit avec def et se termine par end. Pas d'accolades, pas de mot-clé function : juste un nom en snake_case et un corps indenté de deux espaces.

Regarde les deux dernières lignes : even? est un message envoyé à l'objet 5, length un message envoyé à la chaîne "ruby". Même saluer("Noah") est un message — envoyé implicitement à l'objet courant. Le point (.) est l'opérateur d'envoi de message : à gauche le destinataire, à droite le message. Cette image va éclairer tout le reste du cours.

Valeurs par défaut et arguments nommés

Un paramètre peut recevoir une valeur par défaut, utilisée si l'appelant ne fournit rien :

Mais dès qu'une méthode prend plusieurs paramètres du même type, les appels deviennent illisibles : que signifie creer_compte("noah", true, false) ? Mystère. Les arguments nommés (keyword arguments) règlent ça : on les déclare avec un deux-points, et l'appelant les nomme explicitement.

pseudo: sans valeur par défaut est obligatoire ; les autres sont optionnels. L'appel se lit comme une phrase : c'est exactement la lisibilité que Ruby cherche à offrir.

Cas réel

Dans une vraie base de code, on tombe vite sur des appels indéchiffrables comme User.create("noah", true, false, true). Que veulent dire ces trois booléens ? Impossible à deviner sans ouvrir la définition : c'est le boolean trap. La communauté Ruby a massivement basculé vers les arguments nommés — User.create(pseudo: "noah", admin: true, actif: false, newsletter: true) se relit sans effort six mois plus tard, et l'ordre des options n'a plus d'importance. Rails en a fait un pilier de son style : validates :email, presence: true, uniqueness: true.

Splat et double splat : accepter l'inconnu

Parfois tu ne sais pas combien d'arguments arriveront. Le splat *args ramasse les arguments positionnels dans un tableau, le double splat **options ramasse les arguments nommés dans un hash :

Dans moyenne, notes est un vrai tableau : tu peux lui envoyer sum, size, n'importe quel message de tableau. Dans construire_url, params est un hash dont on parcourt les paires.

Les conventions ? et ! : des noms qui parlent

Ruby autorise deux suffixes dans les noms de méthodes, et la communauté leur donne un sens précis :

  • methode? : un prédicat, qui répond par vrai ou faux. empty?, even?, include?…
  • methode! : une version « dangereuse » — le plus souvent parce qu'elle mute l'objet au lieu d'en retourner une copie.

Piège fréquent

Le ! ne signifie pas mécaniquement « mutation » : il signifie « attention, version plus risquée que la variante sans ! ». Beaucoup de méthodes mutantes n'ont pas de ! (push, clear…), et les variantes à ! comme upcase! retournent nil quand rien n'a changé — évite donc de chaîner dessus. Lis toujours la documentation au moindre doute.

Parenthèses : une affaire de style

En Ruby, les parenthèses d'appel sont optionnelles. La convention dominante : on les omet quand l'appel ressemble à une commande ou à un mot-clé de DSL, on les garde quand la méthode participe à un calcul ou retourne une valeur qu'on exploite.

Astuce

Pour la définition, la convention moderne garde les parenthèses dès qu'il y a des paramètres : def saluer(prenom) plutôt que def saluer prenom.

send et public_send : le message rendu explicite

Si appeler une méthode, c'est envoyer un message… alors on devrait pouvoir construire ce message dynamiquement, comme n'importe quelle donnée. C'est exactement ce que fait public_send : il prend le nom du message sous forme de symbole et l'envoie à l'objet.

La différence avec send ? send ignore les barrières de visibilité et peut invoquer une méthode privée — public_send les respecte. En pratique, préfère public_send : il ne te fera pas contourner une protection par accident. Tu viens d'entrevoir la métaprogrammation, cette capacité de Ruby à manipuler son propre code ; on y reviendra en fin de cours.

Méthodes privées et ambiguïté méthode / variable

Le mot-clé private marque les méthodes qui suivent comme des détails internes : l'extérieur ne peut pas leur envoyer de message avec un destinataire explicite. C'est ta façon de dire « ceci est ma cuisine interne, ne t'appuie pas dessus » — tu pourras la modifier sans casser le code des autres.

Dernier point subtil : comme l'appel sans parenthèses ressemble à une variable, comment Ruby tranche-t-il en cas d'ambiguïté ? Règle simple : si le parseur a vu une affectation à ce nom plus haut, c'est une variable locale ; sinon, c'est un envoi de message.

Pièges fréquents

Piège fréquent

puts retourne toujours nil. Si la dernière ligne de ta méthode est un puts, ta méthode retourne nil, pas le texte affiché. Sépare bien « produire une valeur » (retour implicite) et « afficher » (puts chez l'appelant).

Piège fréquent

Ne confonds pas def f(langue = "fr") (paramètre positionnel avec défaut, appelé f("en")) et def f(langue: "fr") (argument nommé, appelé f(langue: "en")). Mélanger les deux syntaxes à l'appel provoque une ArgumentError.

Piège fréquent

Avec send, le nom du message vient parfois de l'extérieur (saisie utilisateur, paramètre web). N'envoie jamais un message arbitraire non vérifié : utilise public_send et valide le nom contre une liste blanche de symboles autorisés.

Pour aller plus loin

Pour aller plus loin

Quand un objet reçoit un message auquel il ne sait pas répondre, Ruby invoque method_missing — une méthode que tu peux redéfinir pour fabriquer des réponses à la volée. C'est ainsi que certaines bibliothèques offrent des méthodes « magiques » comme find_by_email dans Rails. Tu peux aussi explorer obj.method(:nom), qui réifie une méthode en objet Method manipulable. La leçon sur la métaprogrammation t'ouvrira ces portes.

Antisèche

Glossaire

Message
Nom envoyé à un objet via le point (obj.message). En Ruby, « appeler une méthode » = « envoyer un message » : c'est l'objet qui décide comment répondre.
Retour implicite
La valeur de la dernière expression évaluée devient la valeur de retour de la méthode, sans écrire return.
Clause de garde
return … if … placé en tête de méthode pour sortir tôt sur un cas particulier et garder le reste du code sans imbrication.
Argument nommé
Paramètre déclaré avec un deux-points (x:) et fourni par son nom à l'appel (f(x: 5)) : appels lisibles, ordre libre.
Splat / double splat
*args ramasse les arguments positionnels dans un tableau ; **options ramasse les arguments nommés dans un hash.
Prédicat (?)
Convention de nommage d'une méthode qui répond par true ou false : even?, include?…
Méthode dangereuse (!)
Convention signalant une variante plus risquée que celle sans ! — souvent parce qu'elle mute l'objet sur place.
send / public_send
Envoient un message construit dynamiquement (un symbole). send ignore la visibilité ; public_send la respecte — à préférer.

Récap et vérification

  • Appeler une méthode = envoyer un message à un objet ; le . sépare destinataire et message.
  • La dernière expression évaluée est la valeur de retour ; return sert aux sorties anticipées.
  • Valeurs par défaut, arguments nommés (pseudo:), *args (tableau) et **options (hash) rendent les signatures flexibles et les appels lisibles.
  • ? annonce un prédicat booléen, ! une version dangereuse (souvent mutante).
  • Parenthèses omises pour le style « commande/DSL », gardées pour les calculs.
  • public_send(:message) envoie un message dynamiquement ; private cache la cuisine interne.

Vérifie ta compréhension

  1. Que retourne une méthode dont la dernière ligne est puts "ok", et pourquoi ?
  2. Quelle est la différence entre def f(x = 1) et def f(x: 1) au moment de l'appel ?
  3. Pourquoi préférer public_send à send quand le nom du message vient d'une donnée externe ?
