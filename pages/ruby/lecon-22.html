Projet : un carnet de contacts en ligne de commande

~40 min Intermédiaire Chaînes & JSON requis

À la fin de cette leçon, tu sauras

  • lire les arguments d'un programme avec ARGV ;
  • déclarer des options propres avec OptionParser ;
  • faire persister des données dans un fichier JSON ;
  • assembler un vrai outil en ligne de commande, de bout en bout.
Sommaire de la leçon

Pour clore ce cours, construisons un vrai outil : un carnet de contacts (répertoire) qui s'utilise dans le terminal. Il réunit plusieurs briques du cours — les chaînes et les expressions régulières (leçon 18) pour valider une adresse e-mail, le JSON (leçon 19) et les fichiers (leçon 12) pour conserver les données — auxquelles s'ajoutent deux outils standard de tout programme en ligne de commande : le tableau ARGV et la bibliothèque OptionParser. En une centaine de lignes, tu obtiens un script autonome, du genre qu'on garde vraiment sous la main.

Le cahier des charges

Notre outil gère quatre commandes : ajouter un contact, lister les contacts, en chercher un par son nom, et en supprimer un. Les contacts doivent survivre à la fermeture du terminal : on les enregistre dans un fichier contacts.json. À chaque exécution, le programme charge le fichier, agit selon la commande, puis le réécrit. C'est le cycle fondamental de tout petit outil sans base de données.

Lire les arguments : ARGV

Quand tu lances ruby contacts.rb ajouter "Alice Martin", Ruby range les mots qui suivent le nom du script dans un tableau global : ARGV. Le nom du script n'y figure pas (il est dans $PROGRAM_NAME). ARGV est un tableau ordinaire : on peut le parcourir, et surtout appeler shift pour en retirer le premier élément — pratique pour isoler la commande du reste.

abort écrit son message sur la sortie d'erreur et arrête le programme avec un code de sortie non nul : un terminal ou un script appelant sait alors que quelque chose a échoué. C'est le réflexe à avoir dès qu'un argument obligatoire manque.

Des options propres avec OptionParser

Les arguments positionnels suffisent pour un nom, mais dès qu'on veut des données facultatives et nommées — une adresse e-mail, un téléphone — mieux vaut des options (--email alice@exemple.fr). Les analyser à la main est fastidieux et fragile ; la bibliothèque standard OptionParser (dans optparse) le fait pour toi : tu déclares chaque option, et parse! les extrait de ARGV en ne laissant que les arguments positionnels.

Le bloc passé à on reçoit la valeur de l'option et la range dans le hachage options. Cadeau : OptionParser génère aussi une aide --help à partir de tes déclarations, et refuse les options inconnues. Tu écris quoi accepter, pas comment le lire.

Valider avant d'enregistrer

Un carnet plein d'e-mails malformés ne sert à rien. On réutilise l'expression régulière de la leçon 18 pour un contrôle de forme : email =~ /\A[^@\s]+@[^@\s]+\.[^@\s]+\z/. Les ancres \A et \z exigent que toute la chaîne corresponde, et [^@\s] interdit espace et arobase multiples. Ce n'est pas une validation parfaite (aucune regex ne l'est), mais elle attrape les fautes de frappe courantes avant qu'elles ne polluent le fichier.

Persister en JSON

Deux petites fonctions encapsulent le fichier. charger renvoie le tableau de contacts ; astuce clé du premier lancement : si le fichier n'existe pas encore, on ne veut pas d'erreur mais un tableau vide. On protège aussi la lecture contre un JSON corrompu avec un rescue (leçon 12).

JSON.parse transforme le texte du fichier en tableau de hachages Ruby ; JSON.pretty_generate fait l'inverse en indentant le résultat, pour un fichier lisible à l'œil. Comme les chaînes Ruby sont en UTF-8 (leçon 18), les accents restent lisibles dans le fichier : José s'écrit José, sans être échappé en José comme le font d'autres langages par défaut.

Toujours prévoir le premier lancement

Au tout premier appel, contacts.json n'existe pas. Sans le garde-fou File.exist?, File.read lèverait Errno::ENOENT (« fichier introuvable ») et l'outil s'arrêterait avant même d'avoir servi. La règle : un outil doit démarrer proprement à vide. Ici, on renvoie [] — un tableau vide, prêt à recevoir le premier contact.

Assembler le tout

Il ne reste qu'à brancher les morceaux : parser les options, lire la commande, charger, agir avec un case, sauver quand les données changent. Essaie d'abord d'assembler toi-même, puis compare avec la solution de référence.

Un carnet de contacts complet en ligne de commande, avec options OptionParser, validation d'e-mail par regex et persistance JSON.

Voir la solution complète

Tout est là : OptionParser pour les options, ARGV.shift pour la commande et le nom, JSON + File pour la persistance, une regex pour valider l'e-mail, et des codes de sortie (abort, exit 1) qui signalent les erreurs. Essaie : ruby contacts.rb ajouter "Alice" --email alice@exemple.fr, puis ruby contacts.rb lister.

Un cas réel : du pense-bête au petit outil d'équipe

Cas réel

Une petite association gérait ses bénévoles dans un tableur partagé, lent à ouvrir et pénible à filtrer depuis un téléphone. Un membre a écrit, un dimanche, un script Ruby exactement de ce moule : un fichier benevoles.json, des commandes ajouter / chercher, et une validation d'e-mail. D'abord un pense-bête personnel, le script a été versionné avec Git puis posé sur le serveur de l'association : chacun le lançait par SSH. Ses collègues ont ajouté une commande export qui produisait un CSV pour le publipostage, puis une option --tag pour classer les bénévoles par activité. La morale : la barre pour créer un outil utile est basse. Un tableau de hachages, un fichier JSON, quelques commandes lues dans ARGV — et Ruby vous donne en prime une syntaxe si lisible que le script reste modifiable par toute l'équipe.

Pour aller plus loin

Pour un outil à beaucoup de commandes, la gem Thor (celle qui propulse le générateur de Rails) offre de vraies sous-commandes avec aide intégrée, sans écrire le case à la main. Pour des interfaces plus riches — couleurs, tableaux, invites interactives — regarde la famille TTY (tty-prompt, tty-table). Et si le fichier JSON devient trop gros ou multi-utilisateur, c'est le signal qu'il faut passer à une vraie base : sqlite3 en Ruby est le pas suivant naturel.

Glossaire

Capstone
Projet de synthèse : il réunit et met en pratique plusieurs notions du cours dans une réalisation concrète.
ARGV
Tableau global contenant les arguments passés au script sur la ligne de commande (sans le nom du programme, qui est dans $PROGRAM_NAME).
OptionParser
Bibliothèque standard (require "optparse") qui déclare et analyse les options en ligne de commande, et génère l'aide --help.
parse!
Méthode d'OptionParser qui lit ARGV, en retire les options reconnues (rangées dans un hachage) et laisse les arguments positionnels.
Persistance
Conservation des données entre deux exécutions ; ici, un fichier JSON tient lieu de mémoire durable, sans base de données.
JSON.parse / pretty_generate
Convertissent respectivement un texte JSON en objets Ruby, et des objets Ruby en texte JSON indenté (leçon 19).
Code de sortie
Entier renvoyé par un programme en s'arrêtant : 0 = succès, ≠ 0 = erreur. abort sort avec un code non nul et un message sur stderr.
warn
Écrit un message sur la sortie d'erreur (stderr), sans arrêter le programme : idéal pour les diagnostics qui ne doivent pas polluer le résultat.

Récap et vérification

  • ARGV contient les arguments du script ; ARGV.shift les consomme un à un (la commande, puis le nom).
  • OptionParser déclare les options ; parse! les extrait de ARGV et remplit un hachage.
  • Un fichier JSON (File.read/write + JSON.parse/pretty_generate) suffit à persister l'état d'un petit outil.
  • On valide une saisie (regex e-mail) et on gère le premier lancement (File.exist? → []).
  • abort et exit 1 signalent une erreur par un code de sortie non nul.

  1. Que contient ARGV pour ruby contacts.rb chercher Alice ?
  2. Que fait parse! au tableau ARGV ?
  3. Pourquoi charger teste-t-il File.exist? avant de lire ?

Exercice 3Défi

Explique pourquoi on protège JSON.parse par un rescue JSON::ParserError plutôt que de laisser l'erreur remonter.

Voir une solution

Le fichier contacts.json peut être corrompu — édité à la main de travers, tronqué par un arrêt brutal, ou vidé. Sans rescue, JSON.parse lèverait JSON::ParserError et le programme s'arrêterait avec une trace brutale, avant même de comprendre la commande. En interceptant l'erreur, on choisit une dégradation maîtrisée : on avertit sur stderr (warn) et on repart d'un tableau vide, laissant l'utilisateur reconstruire son carnet plutôt que de buter sur une erreur incompréhensible. C'est la robustesse de la leçon 12 appliquée à un cas concret.

Mini-projet fil rouge — une liste de tâches

Pour clore ce cours, écrivons une liste de tâches. Elle réunit une classe avec attr_reader, un constructeur, des méthodes (dont to_s), un tableau, les blocs (each, count) et l'interpolation — un condensé de Ruby idiomatique.

Ce que tu vas construire

Une classe Tache (titre, faite) avec une méthode pour la terminer et un affichage [x]/[ ], un tableau de tâches, et le décompte des tâches restantes.

Étapes

La classe Tache

Définis une classe avec attr_reader :titre, :faite et un initialize qui met @faite à false.

Terminer une tâche

Ajoute une méthode terminer qui passe @faite à true.

Affichage lisible

Redéfinis to_s pour renvoyer "[x] titre" ou "[ ] titre" selon l'état (avec un ternaire).

Un tableau de tâches

Crée quelques Tache.new(...) dans un tableau et termines-en une avec .first.terminer.

Parcourir et compter

Affiche chaque tâche avec each { |t| puts t }, puis compte les restantes avec count { |t| !t.faite }.
