Module 2 · Collections et blocs — Leçon 06

Blocs, procs et lambdas

~45 min Débutant Prérequis : leçon 5

À la fin de cette leçon, tu sauras

  • savoir passer un bloc à une méthode avec { } ou do…end et transformer des collections avec map, select et reject ;
  • savoir écrire ta propre méthode qui reçoit un bloc grâce à yield, block_given? et &block ;
  • savoir distinguer Proc.new et les lambdas (->) sur l'arité et le comportement de return ;
  • savoir lire et utiliser la notation map(&:upcase) ainsi que sum et count avec un bloc.
Sommaire de la leçon

S'il fallait ne retenir qu'une seule idée de Ruby, ce serait celle-ci : les blocs. Un bloc, c'est un morceau de code que tu confies à une méthode, et qu'elle exécute quand elle le décide. C'est grâce aux blocs que Ruby se lit presque comme une phrase : « pour chaque nombre, affiche-le », « garde les notes au-dessus de 10 », « transforme chaque mot en majuscules ». Pas d'index à gérer, pas de boucle à écrire à la main.

Dans cette leçon, tu vas d'abord apprendre à utiliser les blocs avec les méthodes de collection, puis à écrire tes propres méthodes qui en acceptent un. Tu découvriras enfin les objets Proc et les lambdas, qui permettent de stocker un bloc dans une variable — et tu comprendras enfin ce que signifie le mystérieux map(&:upcase) que tu croiseras partout en Ruby.

Un bloc, c'est du code passé à une méthode

Reprenons la méthode each vue avec les tableaux. Ce qui suit l'appel, entre accolades, n'est pas un argument classique : c'est un bloc. La méthode each l'exécute une fois par élément, en lui passant l'élément courant via le paramètre entre barres verticales |n| (qu'on appelle les pipes).

Il existe une deuxième syntaxe, avec do…end, strictement équivalente. La convention de la communauté Ruby est limpide : accolades { } quand le bloc tient sur une ligne, do…end dès qu'il en prend plusieurs.

Note

Un bloc n'existe jamais seul : il accompagne toujours un appel de méthode. Écrire { |n| puts n } tout seul sur une ligne est une erreur de syntaxe. C'est la méthode qui décide quand, et combien de fois, le bloc s'exécute.

map, select, reject : transformer plutôt que boucler

map construit un nouveau tableau en appliquant le bloc à chaque élément. Plus d'index, plus de tableau vide à préparer, plus de compteur à incrémenter : tu décris la transformation, Ruby s'occupe de la mécanique. C'est exactement ça, le « bonheur du développeur » : le code dit quoi faire, pas comment boucler.

Deux cousines de map servent à filtrer : select garde les éléments pour lesquels le bloc renvoie vrai, reject fait l'inverse.

Écrire ta méthode qui accepte un bloc : yield

Le vrai déclic, c'est de passer de l'autre côté : écrire ta méthode qui reçoit un bloc. Le mot-clé yield (« céder la main ») exécute le bloc fourni à l'appel. Pas besoin de le déclarer dans les paramètres : tout appel de méthode peut transporter un bloc, silencieusement.

yield peut aussi passer des valeurs au bloc : ce sont elles qui arrivent entre les pipes. Et la valeur renvoyée par le bloc devient la valeur de l'expression yield. C'est exactement ainsi que each et map fonctionnent en interne.

Capturer un bloc avec &block

yield est invisible : rien dans la signature n'indique que la méthode attend un bloc. Pour rendre le bloc explicite et manipulable, on le capture avec un dernier paramètre préfixé de &. Le bloc est alors converti en objet Proc, que tu peux stocker, transmettre à une autre méthode, ou exécuter avec call.

Souviens-toi de la philosophie de Ruby : tout est objet. Le & matérialise le bloc — qui n'est pas un objet — en Proc — qui en est un. Retiens cette conversion, elle va resservir très vite dans l'autre sens.

Cas réel — le fichier qu'on oubliait de fermer

Dans beaucoup de langages, lire un fichier suit un rituel fragile : ouvrir, lire, puis penser à fermer — et si une exception surgit entre les deux, le fichier reste ouvert. Sur un serveur qui tourne des semaines, ces fuites finissent par épuiser les descripteurs du système (« Too many open files »), et l'application refuse toute nouvelle connexion. Ruby résout ça avec exactement le mécanisme de cette leçon : File.open("data.txt") { |f| f.read }. La méthode File.open reçoit un bloc, te passe le fichier ouvert via yield, exécute ton code, puis ferme le fichier quoi qu'il arrive — même si le bloc lève une erreur. Le motif « ouvrir / faire / refermer proprement » est encapsulé une fois pour toutes dans la méthode : c'est toute la puissance des blocs pour gérer une ressource sans jamais la laisser filer.

Proc.new et lambda : deux saveurs de code en boîte

Tu peux créer un Proc directement, sans passer par une méthode, et même le ranger dans une variable. Ruby en propose deux variantes : Proc.new et la lambda, qu'on écrit en Ruby moderne avec la flèche ->.

Première différence : l'arité, c'est-à-dire le nombre d'arguments exigés. La lambda est stricte, comme une méthode ; le proc est laxiste et complète avec nil ou ignore le surplus.

Deuxième différence, la plus importante : le comportement de return. Dans une lambda, return sort de la lambda seulement. Dans un proc, return sort de la méthode qui l'entoure — ce qui peut court-circuiter ton code sans prévenir.

Astuce

Règle pratique : quand tu veux une « mini-fonction anonyme » rangée dans une variable, choisis la lambda ->. Son arité stricte et son return sage en font le choix le plus prévisible. Proc.new sert surtout quand tu manipules des blocs capturés avec &block.

sum et count avec un bloc

Beaucoup de méthodes de collection acceptent un bloc optionnel qui change leur comportement. Deux exemples que tu utiliseras sans cesse : sum, qui peut transformer chaque élément avant d'additionner, et count, qui peut compter sous condition.

Remarque comme tout ce que tu as appris dans cette leçon converge ici : un bloc pour décrire la règle, &:length quand la règle se résume à un appel de méthode, et zéro boucle écrite à la main.

Pièges fréquents

Piège fréquent

map renvoie un nouveau tableau, il ne modifie pas l'original. Si tu écris prix.map { |p| p * 1.2 } sans rien assigner, le résultat part au vent et prix reste inchangé. Range le résultat dans une variable.

Piège fréquent

Un return dans un Proc.new sort de la méthode englobante — et s'il n'y en a pas (proc créé au niveau du fichier), Ruby lève LocalJumpError: unexpected return. Dans le doute, utilise une lambda, ou laisse simplement la dernière expression du bloc servir de valeur de retour, comme partout en Ruby.

Piège fréquent

Avec une méthode appelée sans parenthèses, { } et do…end ne se rattachent pas pareil : dans puts notes.select { |n| n > 10 }, le bloc va bien à select, mais avec do…end il irait à puts — qui l'ignore, et select sans bloc renvoie alors un Enumerator. Si un bloc semble « ne pas s'exécuter », vérifie à quelle méthode il est accroché, et ajoute des parenthèses au besoin.

Pour aller plus loin

Pour aller plus loin

Les blocs, procs et lambdas sont des fermetures (closures) : ils capturent les variables visibles à l'endroit où ils sont créés et les emportent avec eux. Explore aussi reduce (alias inject), qui condense une collection en une seule valeur, et la méthode method(:nom) qui convertit une méthode existante en objet appelable, à passer avec & exactement comme un symbole. Enfin, la documentation du module Enumerable liste des dizaines de méthodes à blocs : c'est la caverne d'Ali Baba de Ruby.

Antisèche

Glossaire

Bloc
Morceau de code passé à une méthode, écrit { } (une ligne) ou do…end (plusieurs). N'existe jamais seul : la méthode décide quand l'exécuter.
yield
Mot-clé qui exécute le bloc fourni à l'appel, et peut lui passer des valeurs. Lève LocalJumpError si aucun bloc n'a été donné.
block_given?
Prédicat qui indique si un bloc a été passé à la méthode : permet de le rendre optionnel avant d'appeler yield.
&block (capture)
Dernier paramètre préfixé de & qui matérialise le bloc en objet Proc — stockable, transmissible, appelable avec call.
Proc
Objet « code en boîte ». Arité souple (complète avec nil, ignore le surplus) ; un return y sort de la méthode englobante.
Lambda
Proc plus strict, créé avec ->(x) { } : arité vérifiée comme une méthode, et return qui ne quitte que la lambda.
Arité
Nombre d'arguments qu'un bloc, proc ou lambda attend. Point de divergence majeur entre proc (laxiste) et lambda (stricte).
Symbol#to_proc (&:sym)
Conversion d'un symbole en proc appelant la méthode homonyme : &:upcase équivaut au bloc { |x| x.upcase }.

Récap et vérification

  • Un bloc est un morceau de code passé à une méthode : { } sur une ligne, do…end sur plusieurs.
  • map transforme, select garde, reject écarte — sans boucle manuelle ni index.
  • Dans tes méthodes, yield exécute le bloc reçu, block_given? teste sa présence, &block le capture en objet Proc.
  • Lambda (->) : arité stricte, return local. Proc.new : arguments souples, return qui sort de la méthode englobante.
  • map(&:upcase) = & appelle :upcase.to_proc, qui produit l'équivalent de { |x| x.upcase }.
  • sum et count acceptent un bloc pour transformer avant d'additionner ou compter sous condition.

Vérifie ta compréhension

  1. Quelle est la différence de résultat entre notes.select { |n| n >= 10 } et notes.map { |n| n >= 10 } ?
  2. Que se passe-t-il si une méthode exécute yield alors qu'on l'a appelée sans bloc, et comment t'en protéger ?
  3. Pourquoi test_proc renvoie-t-il 10 alors que test_lambda atteint la fin de la méthode ?
  4. Réécris mots.map { |m| m.capitalize } avec la notation symbol-to-proc.
