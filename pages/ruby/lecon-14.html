Tester son Ruby

~50 min Intermédiaire Prérequis : leçon 13

À la fin de cette leçon, tu sauras

  • Savoir écrire une classe de tests Minitest avec assert_equal, refute, assert_raises et setup ;
  • Savoir lire et écrire des specs RSpec avec describe, context, it, expect et let ;
  • Savoir dérouler un cycle TDD complet — rouge, vert, refactor — sur un cas concret ;
  • Savoir isoler une dépendance avec Minitest::Mock ou instance_double.
Sommaire de la leçon

Tu sais maintenant écrire du Ruby qui fonctionne. Mais comment prouver qu'il fonctionne — aujourd'hui, et encore dans six mois, après vingt modifications ? La réponse de la communauté Ruby est unanime : les tests automatisés. Ruby est sans doute le langage où la culture du test est la plus forte, et ce n'est pas un hasard — un langage dynamique, sans compilateur pour vérifier tes types, a besoin d'un autre filet de sécurité.

Dans cette leçon, tu vas découvrir les deux grands outils de test de l'écosystème : Minitest, livré avec Ruby, et RSpec, le standard de facto en entreprise. Tu verras aussi le TDD en action, honnêtement, cycle par cycle.

Pourquoi tester ?

Un bon test rend trois services à la fois.

Un filet de sécurité. Quand tu modifies du code, tes tests te disent en quelques secondes si tu as cassé quelque chose ailleurs. Sans eux, chaque refactoring est un saut sans parachute.

Une documentation vivante. Un test décrit ce que le code doit faire, avec des exemples concrets. Contrairement à un commentaire, il ne peut pas mentir : s'il ment, il échoue.

Un outil de design. Écrire le test d'abord t'oblige à te demander « comment je veux utiliser ce code ? » avant de te demander comment l'implémenter. Un code difficile à tester est presque toujours un code mal conçu — le test est un détecteur de mauvais design.

Minitest : tester avec la bibliothèque standard

Minitest est inclus dans Ruby : rien à installer. Un test Minitest est une classe qui hérite de Minitest::Test, et chaque méthode dont le nom commence par test_ est un test. À l'intérieur, tu utilises des assertions : des méthodes qui vérifient un fait et font échouer le test s'il est faux.

Retiens les quatre assertions essentielles :

  • assert_equal attendu, obtenu — vérifie une égalité (l'attendu en premier !) ;
  • assert expression — vérifie que c'est vrai ;
  • refute expression — vérifie que c'est faux ;
  • assert_raises(Erreur) { ... } — vérifie que le bloc lève bien cette erreur.

La méthode setup est appelée avant chaque test : c'est là que tu prépares un état propre, pour que chaque test parte de zéro et reste indépendant des autres.

RSpec : le standard en entreprise

RSpec n'est pas dans la bibliothèque standard (gem install rspec), mais c'est lui que tu croiseras dans l'immense majorité des entreprises Ruby. Sa philosophie : un test doit se lire comme une spécification en langage presque naturel. Voici exactement les mêmes tests, réécrits en RSpec — compare :

Les correspondances sont directes : describe remplace la classe de test, it "..." remplace test_*, let et before remplacent setup, et expect(x).to eq(y) remplace assert_equal y, x. Le bloc context regroupe les tests qui partagent une situation (« après l'ajout d'un article »). Et remarque l'élégance de be_vide : RSpec le traduit automatiquement en appel à ta méthode vide?.

Avec --format documentation, la sortie EST la spécification de ta classe (l'ordre peut varier, RSpec mélange souvent les tests volontairement).

Note

Minitest ou RSpec ? Les deux sont excellents. Minitest est plus simple et plus rapide, RSpec plus expressif et plus répandu en entreprise (notamment dans le monde Rails). L'important est de tester — l'outil compte moins que l'habitude.

Le TDD en vrai : FizzBuzz piloté par les tests

Le TDD (Test-Driven Development) inverse l'ordre habituel : tu écris le test avant le code, puis tu suis un cycle en trois temps — rouge (le test échoue), vert (tu écris le minimum pour qu'il passe), refactor (tu nettoies sans rien casser). Les bonnes pratiques qui durent

  • Un comportement par test. Si ton test s'appelle test_ajout_et_total_et_vidage, découpe-le. Un test ciblé qui échoue te dit exactement où chercher.
  • Des noms parlants. test_un_prix_negatif_est_refuse vaut mille fois test_2. Le nom doit décrire le comportement attendu, pas l'implémentation.
  • Teste les bords. Le panier vide, le prix à zéro, la liste à un seul élément, la chaîne vide : les bugs vivent aux frontières, pas au milieu du cas nominal.
  • Des tests indépendants. Chaque test doit pouvoir tourner seul, dans n'importe quel ordre. C'est le rôle de setup et let : repartir d'un état neuf à chaque fois.

Astuce

Quand tu trouves un bug, écris d'abord un test qui le reproduit (rouge), puis corrige (vert). Le bug ne pourra plus jamais revenir sans déclencher d'alarme.

Cas réel

Sur une boutique en ligne, une remise « -10 % au-delà de 50 € » était calculée avec une comparaison stricte (> 50) au lieu de large (>= 50) : un panier de pile 50 € ne recevait pas la remise promise. Le bug est passé en production et a déclenché des réclamations clients. Après correction, l'équipe a ajouté un test dédié au cas limite : assert_equal 45.0, panier_de_50_euros.total. Six mois plus tard, un refactoring du calcul des remises a bien failli réintroduire la même erreur — mais cette fois, le test est passé au rouge avant même le déploiement. Le bug n'a jamais pu revenir. C'est précisément ça, un test de non-régression : la mémoire durable de chaque erreur déjà payée une fois.

Pièges fréquents

Piège fréquent

Dans assert_equal, l'ordre est attendu d'abord, obtenu ensuite : assert_equal 29.90, panier.total. Si tu inverses, le test fonctionne quand même… mais les messages d'erreur affichent « Expected » et « Actual » à l'envers, et tu chercheras le bug du mauvais côté.

Piège fréquent

En Minitest, une méthode de test qui ne commence pas par test_ est silencieusement ignorée — aucune erreur, le test ne tourne juste jamais. Si ta suite affiche moins de « runs » que prévu, vérifie les préfixes. Même piège en RSpec avec un it sans bloc do…end : il est marqué « pending » au lieu d'échouer.

Piège fréquent

Un test sans assertion passe toujours. Si tu écris le code d'abord et « oublies » le assert ou le expect, tu obtiens un faux sentiment de sécurité. D'où l'intérêt du rouge en TDD : voir le test échouer prouve qu'il vérifie réellement quelque chose.

Glossaire

Test automatisé
Bout de code qui exécute une partie du programme et vérifie automatiquement que le résultat est celui attendu.
Assertion
Vérification élémentaire d'un fait dans un test (assert_equal, expect(...).to) ; si elle est fausse, le test échoue.
Minitest
Framework de test livré avec Ruby : sobre et rapide, un test est une méthode test_… d'une classe Minitest::Test.
RSpec
Framework de test externe très répandu en entreprise ; ses tests (describe/it/expect) se lisent comme une spécification.
TDD
Test-Driven Development : écrire le test avant le code, en suivant le cycle rouge → vert → refactor.
Refactoring
Réécrire le code pour l'améliorer sans changer son comportement ; les tests verts garantissent que rien ne casse.
Double (mock/stub)
Faux objet qui remplace une vraie dépendance (email, API) pour isoler le code testé ; à utiliser avec parcimonie.
Test de non-régression
Test ajouté après un bug corrigé, qui échoue si le bug réapparaît : il fige durablement la correction.

Récap et vérification

  • Les tests sont à la fois un filet de sécurité, une documentation vivante et un outil de design.
  • Minitest (bibliothèque standard) : classe héritant de Minitest::Test, méthodes test_*, assertions assert_equal, assert, refute, assert_raises, préparation dans setup.
  • RSpec (standard en entreprise) : describe / context / it, expect(x).to eq(y), let et before pour la mise en place.
  • Le TDD suit le cycle rouge → vert → refactor : un test qui échoue, le code minimal pour le faire passer, puis un nettoyage sous protection.
  • Les doubles (Minitest::Mock, instance_double) isolent ton code de ses dépendances externes — à doser avec parcimonie.
  • Un comportement par test, des noms parlants, et toujours tester les cas limites.
