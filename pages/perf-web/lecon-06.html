Module 03 · Pratique — Leçon 06

Auditer & optimiser un site

~33 min Intermédiaire Tout le cours

À la fin de cette leçon, tu sauras

  • mener un audit Lighthouse performance + SEO ;
  • dérouler une checklist combinée ;
  • te fixer un budget de performance ;
  • prioriser le plus gros frein avant tout le reste.
Sommaire de la leçon

Il est temps de tout réunir sur un vrai site. La démarche tient en une boucle — mesurer, corriger le plus gros frein, re-mesurer — appliquée à la fois à la performance et au référencement. Faisons-en un réflexe d'ingénieur.

La démarche, en bref

On ne devine pas : on mesure (Lighthouse, en bridant mobile + réseau lent, et les données de terrain si disponibles), on identifie le plus gros problème, on le corrige, puis on re-mesure pour confirmer le gain. On répète sur le frein suivant, jusqu'à atteindre ses objectifs.

Cas réel : d'un score Lighthouse de 48 à 96

Une page d'accueil plafonnait à 48/100 en performance sur mobile bridé, avec un LCP à 4,2 s. La mesure désigne le coupable : une image héro en PNG de 2 Mo. Corrections, dans l'ordre du plus gros frein : image héro en AVIF redimensionnée et préchargée (LCP → 1,9 s), scripts passés en defer, cache long activé. Re-mesure : 96/100. Pas de refonte : juste la boucle mesurer → corriger → re-mesurer appliquée au bon frein.

La checklist combinée

Performance :

  • Images : format moderne (WebP/AVIF), bonne taille, dimensions réservées, lazy hors premier écran.
  • JavaScript : scripts en defer, moins de JS, pas de grosse librairie pour un détail.
  • Rendu : CSS critique léger, polices en font-display: swap.
  • Réseau : cache long + versionnage, compression (brotli), preconnect/preload utiles.
  • Vitals : LCP < 2,5 s, CLS < 0,1, INP < 200 ms.

SEO :

  • title et meta description uniques par page ; HTML sémantique.
  • robots.txt correct (pas de blocage involontaire) et sitemap.xml.
  • balise canonique contre les doublons ; données structurées fidèles au contenu.
  • site rapide et mobile-friendly (les deux se rejoignent).

Une seule base

Beaucoup de ces points se recoupent avec l'accessibilité : un HTML propre, un site rapide et clair sert performance, SEO et a11y. Tu n'optimises pas trois fois — tu soignes une fondation commune.

Les trois Core Web Vitals résument l'expérience perçue : chacun mesure une facette et vise une cible « bonne » sur mobile.

Le budget de performance

Pour ne pas laisser le site se dégrader avec le temps, fixe un budget : des seuils à ne pas dépasser (ex. « LCP < 2,5 s sur mobile bridé », « JS initial < 150 Ko »). On vérifie le budget régulièrement — idéalement automatiquement dans la CI. Un budget transforme un vœu en contrainte tenue.

Pour aller plus loin

La compétence durable n'est pas une liste d'astuces, mais le réflexe de mesure : observer, corriger le plus gros frein, re-mesurer. Les modules suivants approfondissent chaque levier — le chemin critique du rendu, les images et polices, le cache et le réseau, puis la mesure dans la durée (labo, terrain, budgets) — avant le projet final de diagnostic d'une page lente.

Glossaire

Lighthouse
Outil d'audit (performance, SEO, accessibilité…) intégré au navigateur ; à lancer en bridant mobile et réseau.
Audit
Mesure de l'état d'une page pour identifier les freins avant de corriger.
Budget de performance
Ensemble de seuils à ne pas dépasser (LCP, poids du JS, CLS…) pour éviter la dégradation dans le temps.
Données de terrain (RUM)
Mesures issues des vrais utilisateurs, par opposition au test en laboratoire d'un seul appareil.
Lighthouse CI
Exécution automatique de Lighthouse dans la chaîne d'intégration, pour vérifier le budget à chaque changement.
Boucle d'optimisation
Mesurer → identifier le plus gros frein → corriger → re-mesurer, en répétant.
Base commune
Un HTML propre et sémantique et un site rapide servent à la fois la performance, le SEO et l'accessibilité.
Core Web Vitals
Trois métriques d'expérience — LCP (chargement), CLS (stabilité visuelle), INP (réactivité) — chacune avec une cible à tenir sur mobile.

Récap et vérification

  • Boucle : mesurer → identifier → corriger → re-mesurer, perf et SEO ensemble.
  • Checklist : images/JS/cache/Vitals (perf) ; title/robots/sitemap/canonique/données structurées (SEO).
  • Fixe un budget de performance et vérifie-le régulièrement.
  • Une base commune (HTML propre, site rapide) sert perf, SEO et accessibilité.

Vérifie ta compréhension

  1. Quelle est la boucle d'optimisation ?
  2. Cite trois corrections de performance et deux de SEO.
  3. À quoi sert un budget de performance ?

Exercices

Exercice 1Échauffement

Classe ces corrections en « performance » ou « SEO » : (a) WebP + lazy ; (b) meta description ; (c) defer sur les scripts ; (d) canonique.

Voir une solution

Performance : (a) WebP + lazy, (c) defer sur les scripts. SEO : (b) meta description, (d) balise canonique. (Beaucoup de bonnes pratiques servent les deux, mais ces quatre-là sont chacune typées.)

Exercice 2Application

Tu as un LCP à 4 s causé par une grosse image héro en PNG. Donne deux corrections prioritaires.

Voir une solution

(1) Convertir l'image héro en WebP/AVIF et la servir à la bonne taille (compression + dimensions adaptées) — gros gain immédiat sur le LCP ; (2) la précharger (preload as="image") et surtout ne pas lui mettre loading="lazy". Bonus : réserver ses dimensions pour éviter aussi le CLS. On re-mesure ensuite pour confirmer le passage sous 2,5 s.

Exercice 3Application

Parmi les Core Web Vitals, lequel (sigle) mesure le temps d'affichage du plus gros élément et doit rester sous 2,5 s ?

Voir une solution

C'est le LCP (Largest Contentful Paint) : le moment où le principal contenu visible (souvent l'image héro ou un gros titre) est peint. Cible : < 2,5 s sur mobile bridé. Ses coupables habituels : image trop lourde, ressource critique bloquante, serveur lent.
