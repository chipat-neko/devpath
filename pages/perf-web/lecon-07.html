Le chemin critique du rendu

~36 min Avancé Leçon 06 requise

À la fin de cette leçon, tu sauras

  • décrire comment le navigateur passe du code aux pixels ;
  • repérer les ressources bloquantes (CSS, JS) ;
  • appliquer le CSS critique et différer le reste ;
  • raccourcir le chemin critique de rendu.
Sommaire de la leçon

Tu sais mesurer la vitesse (Web Vitals) et alléger les ressources. Reste à comprendre ce qui se passe entre le moment où le HTML arrive et celui où l'utilisateur voit quelque chose. Ce trajet a un nom : le chemin critique de rendu (Critical Rendering Path). Le connaître, c'est savoir exactement quoi optimiser pour afficher plus tôt.

Du code aux pixels

Pour peindre une page, le navigateur enchaîne plusieurs étapes. Il lit le HTML pour bâtir le DOM (l'arbre des éléments), lit le CSS pour bâtir le CSSOM (l'arbre des styles), les combine en un arbre de rendu (les éléments visibles avec leur style), calcule la position et la taille de chacun (mise en page, ou layout), puis peint les pixels et les compose en couches à l'écran.

Le CSS bloque le rendu

Le navigateur refuse de peindre une page à moitié stylée : il attend d'avoir tout le CSSOM avant le premier affichage. Le CSS est donc bloquant pour le rendu. Une grosse feuille de style, ou plusieurs feuilles chaînées, retardent d'autant le premier pixel — même si le HTML, lui, est prêt depuis longtemps.

Attention au FOUC… et à son contraire

Si l'on charge le CSS trop tard (ou en async mal maîtrisé), la page apparaît un instant sans style (le FOUC, flash of unstyled content). L'inverse — bloquer le rendu sur du CSS non essentiel — donne une page blanche trop longtemps. L'équilibre : charger tout de suite le strict nécessaire au premier écran, différer le reste.

Le JavaScript bloque l'analyse

Un <script> sans attribut interrompt la construction du DOM : le navigateur s'arrête, télécharge, exécute, puis reprend. Pire, comme un script peut lire les styles, il doit parfois attendre le CSSOM avant de s'exécuter. Résultat : un script mal placé retarde à la fois le DOM et le premier affichage. D'où le réflexe vu en leçon 03 : defer par défaut, async pour l'indépendant.

Raccourcir le chemin critique

Trois leviers, dans l'ordre :

  • Inliner le CSS critique : mettre directement dans le <head> le minimum de styles nécessaires au premier écran (above the fold), pour peindre sans attendre un fichier externe.
  • Différer le reste du CSS : charger les styles non critiques de façon non bloquante.
  • Réduire le nombre de ressources bloquantes : moins de feuilles, moins de scripts synchrones, moins d'allers-retours réseau.

L'astuce media="print"

Le motif media="print" onload="this.media='all'" est une ruse classique : le navigateur considère la feuille comme non bloquante (elle ne concerne que l'impression), la télécharge en arrière-plan, puis onload la rebascule sur all. Résultat : du CSS chargé sans retarder le premier affichage. Les outils comme Critical extraient automatiquement le CSS du premier écran.

Cas réel : une page vitrine bloquée par ses styles

Un site marchand chargeait cinq feuilles CSS externes dans le <head>, dont un gros framework de composants. Sur une connexion mobile, le premier pixel n'apparaissait qu'après 1,8 s — tout ce temps en page blanche, le HTML pourtant déjà reçu. En inlinant les ~8 Ko de CSS du premier écran et en différant le reste avec l'astuce media="print", le FCP est tombé sous 0,7 s. Aucun octet de CSS en moins : juste envoyé dans le bon ordre.

Mise en page et peinture : le coût d'après

Le chemin critique ne s'arrête pas au premier affichage. Chaque changement de style peut déclencher un nouveau reflow (recalcul de la mise en page) puis un repaint (nouvelle peinture). Modifier width, top ou font-size relance la mise en page ; animer transform ou opacity, en revanche, ne touche que la composition (sur le GPU) et reste fluide. C'est pourquoi on anime avec transform/opacity, jamais avec width/margin.

Pour aller plus loin

Deux techniques serveur raccourcissent encore le chemin : rel="preload" demande au navigateur d'aller chercher tôt une ressource clé (police, image LCP), et les 103 Early Hints laissent le serveur souffler les ressources critiques avant même la réponse HTML. Côté rendu, content-visibility: auto évite de mettre en page ce qui est hors écran.

Glossaire

Chemin critique de rendu
La suite d'étapes et de ressources (HTML + CSS, parfois JS) indispensables au premier affichage ; le raccourcir accélère le rendu perçu.
DOM
Document Object Model : l'arbre des éléments de la page, construit à partir du HTML.
CSSOM
CSS Object Model : l'arbre des styles, construit à partir du CSS ; le rendu attend qu'il soit complet.
Arbre de rendu
La combinaison du DOM et du CSSOM : les éléments visibles avec leur style, prêts pour la mise en page.
CSS critique
Le minimum de styles nécessaires au premier écran ; inliné dans le <head> pour peindre sans attendre un fichier externe.
Reflow (mise en page)
Recalcul de la position et de la taille des éléments ; coûteux, déclenché par les changements de géométrie (width, top…).
Repaint / composite
Nouvelle peinture des pixels (repaint), puis assemblage des couches (composite, sur le GPU) ; animer transform/opacity ne touche que la composition.
FOUC
Flash of Unstyled Content : bref instant où la page s'affiche sans style (CSS appliqué trop tard) ; on l'évite en servant tout de suite le CSS critique.

Récap et vérification

  • Le navigateur bâtit le DOM (HTML) et le CSSOM (CSS), les combine, met en page, peint et compose.
  • Le CSS bloque le rendu : on inline le critique et on diffère le reste.
  • Le JS bloque l'analyse : defer/async l'écartent du chemin.
  • Après coup, éviter les reflows : animer avec transform/opacity.

Vérifie ta compréhension

  1. Quelles deux structures le navigateur doit-il construire avant le premier affichage ?
  2. Pourquoi le CSS est-il dit « bloquant pour le rendu » ?
  3. Que fait l'astuce media="print" onload="this.media='all'" ?

Exercices

Exercice 1Échauffement

Une page a un HTML léger reçu en 100 ms, mais quatre feuilles CSS externes qui mettent chacune 300 ms à arriver, chaînées. Pourquoi le premier affichage tarde-t-il, alors que le HTML est prêt ?

Voir une solution

Parce que le CSS est bloquant pour le rendu : le navigateur ne peint rien tant que le CSSOM n'est pas complet, donc tant que les quatre feuilles ne sont pas toutes téléchargées et analysées. Le HTML a beau être prêt, l'affichage attend le CSS. Ici, quatre feuilles chaînées = quatre allers-retours : le premier pixel n'arrive qu'après la dernière. La solution : inliner le CSS critique du premier écran et différer (ou fusionner) le reste.

Exercice 2Application

Écris, dans un <head>, un bloc de CSS critique inline pour l'en-tête, puis charge reste.css de façon non bloquante.

Voir une solution

Les styles du premier écran s'appliquent tout de suite (inline), et reste.css se charge sans bloquer le rendu, puis s'applique via onload. On peut ajouter un <noscript><link rel="stylesheet" href="reste.css"></noscript> pour les rares clients sans JS.

Exercice 3Défi

Une animation de menu qui fait varier width et left saccade sur mobile. Explique pourquoi, et propose une correction fondée sur le pipeline de rendu.

Voir une solution

Animer width et left force le navigateur à refaire, à chaque image, la mise en page (reflow) puis la peinture (repaint) de la zone concernée — un travail lourd sur le thread principal, d'où les saccades sur un mobile modeste. La correction : animer avec transform (par exemple translateX() pour le déplacement, scaleX() pour la largeur) et éventuellement opacity. Ces propriétés ne déclenchent ni reflow ni repaint : elles sont traitées à l'étape de composition, sur le GPU, ce qui donne une animation fluide à 60 images/seconde. On peut aussi indiquer will-change: transform pour préparer la couche.

Exercice 4Au clavier

Au démarrage d'une connexion, le serveur n'envoie pas tout d'un coup : la fenêtre part à 14 Ko et double à chaque aller-retour. Écris allersRetours(kilooctets) qui compte les allers-retours nécessaires, puis affiche allersRetours(60).
