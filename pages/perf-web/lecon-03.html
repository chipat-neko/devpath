Module 01 · Performance — Leçon 03

JavaScript & rendu

~35 min Intermédiaire Leçon 02

À la fin de cette leçon, tu sauras

  • comprendre le coût du JavaScript ;
  • charger les scripts avec defer / async ;
  • raccourcir le chemin critique de rendu ;
  • réduire le JS et soigner les polices.
Sommaire de la leçon

Après les images, le second grand frein est le JavaScript. Non pas tant son téléchargement que son exécution : analyser et lancer du JS occupe le thread principal, celui-là même qui dessine la page et répond aux clics. Trop de JS, et la page est lente à afficher comme à réagir.

Le coût caché du JavaScript

Un octet d'image se contente d'être affiché ; un octet de JS doit être téléchargé, analysé, compilé puis exécuté. Sur un mobile modeste, ce travail peut bloquer l'affichage et dégrader l'INP (réactivité). D'où la règle d'or : le JS le plus rapide est celui qu'on n'envoie pas.

Charger les scripts sans bloquer

Un <script> classique bloque l'analyse du HTML le temps de se télécharger et s'exécuter. Deux attributs corrigent cela :

  • defer : télécharge en parallèle, exécute après le HTML, dans l'ordre. Le bon choix par défaut.
  • async : télécharge en parallèle, exécute dès que prêt (ordre non garanti). Pour des scripts indépendants (analytics).

defer par défaut

Place tes scripts dans le <head> avec defer : ils se téléchargent tôt mais n'exécutent qu'après le HTML, dans l'ordre. Réserve async aux scripts vraiment indépendants.

Le chemin critique de rendu

Pour afficher la page, le navigateur a besoin du HTML et du CSS : le CSS est bloquant pour le rendu (rien ne s'affiche tant qu'il n'est pas chargé). On raccourcit ce chemin critique en gardant un CSS initial léger, et en différant le CSS non essentiel.

Les polices web

Les polices personnalisées peuvent retarder l'affichage du texte ou provoquer un saut quand elles arrivent. font-display: swap affiche d'abord une police système, puis remplace — le texte est lisible tout de suite.

Envoyer moins de JavaScript

  • Code splitting : ne charger que le code de la page courante, pas toute l'application d'un coup.
  • Tree shaking : laisser l'outil de build retirer le code mort (fonctions jamais utilisées).
  • Bibliothèques : une grosse dépendance pour une petite fonction ? Souvent, quelques lignes de JS suffisent.

Cas réel : un tableau de bord qui gèle sur mobile

Une application chargeait 480 Ko de JavaScript d'un coup — dont une librairie de dates de 90 Ko utilisée pour un seul affichage. Sur un mobile modeste, le thread principal restait bloqué plusieurs secondes et l'INP virait au rouge. Deux corrections : code splitting par route (chaque page tombe à ~70 Ko) et remplacement de la librairie de dates par Intl.DateTimeFormat, natif et gratuit. Résultat : le premier écran s'affiche et réagit tout de suite, INP repassé au vert.

Pièges fréquents

  • Script bloquant dans le <head> sans defer. Retarde tout l'affichage.
  • Trop de JS d'un coup. Découpe (code splitting) et n'envoie que l'utile.
  • Polices sans font-display. Texte invisible ou saut à l'arrivée de la police.
  • Grosse librairie pour un détail. Pèse le coût ; parfois le natif suffit.

Pour aller plus loin

Pour les sites construits avec un framework, le rendu côté serveur (SSR) ou la génération statique (SSG) envoient du HTML déjà prêt, puis « hydratent » avec le JS. On affiche vite, et l'interactivité arrive ensuite. C'est un grand levier quand le JS devient incontournable.

Pour aller plus loin

Avant d'ajouter du JavaScript, demande-toi si le HTML/CSS ne suffit pas : un menu en <details>, un défilement en CSS… Moins de JS, c'est moins de poids, moins de bugs et une page plus réactive.

Glossaire

Thread principal
Le fil d'exécution unique où le navigateur analyse le JS, met en page et répond aux interactions ; le saturer rend la page lente à afficher et à réagir.
defer
Attribut de <script> : télécharge en parallèle, exécute après l'analyse du HTML, dans l'ordre. Le bon choix par défaut.
async
Attribut de <script> : télécharge en parallèle et exécute dès qu'il est prêt, sans garantie d'ordre. Pour les scripts indépendants.
Chemin critique de rendu
L'ensemble des ressources (HTML + CSS) nécessaires au premier affichage ; le CSS y est bloquant. On le raccourcit en allégeant le CSS initial.
font-display: swap
Règle CSS qui affiche d'abord une police système puis bascule sur la police web à son arrivée : pas de « texte invisible ».
Code splitting
Découper le JavaScript en morceaux chargés à la demande (par page / route) au lieu d'un seul gros paquet.
Tree shaking
Élimination automatique du code mort (fonctions jamais utilisées) par l'outil de build.
INP
Interaction to Next Paint : mesure la réactivité de la page aux interactions ; le JS lourd sur le thread principal le dégrade.

Récap et vérification

  • Le coût du JS, c'est surtout son exécution sur le thread principal (affichage + INP).
  • Charge les scripts en defer (par défaut), async pour les indépendants.
  • Garde le chemin critique court : CSS initial léger, reste différé.
  • Polices en font-display: swap ; envoie moins de JS (splitting, natif).

Vérifie ta compréhension

  1. Pourquoi le JS coûte-t-il plus qu'une image à poids égal ?
  2. Quelle différence entre defer et async ?
  3. Que fait font-display: swap ?

Exercice 3Défi

Une page importe une grosse bibliothèque de 90 Ko juste pour formater une date. Lighthouse signale un INP élevé. Comment raisonnes-tu ?

Voir une solution

Le problème : on paie le coût (téléchargement + exécution sur le thread principal) d'une grosse dépendance pour une fonction minime, ce qui pèse sur la réactivité (INP). Pistes, par ordre : (1) vérifier si une API native suffit (Intl.DateTimeFormat formate les dates sans dépendance) ; (2) sinon, importer seulement la partie utile (import ciblé + tree shaking) au lieu de toute la librairie ; (3) en dernier recours, différer ou charger à la demande ce code s'il n'est pas nécessaire au premier rendu. La règle : le meilleur JS est celui qu'on n'envoie pas.
