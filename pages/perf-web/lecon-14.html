Module 05 · Maîtriser — Leçon 14

Stratégies de rendu : CSR, SSR, SSG & hydratation

~38 min Avancé Leçon 03 requise

À la fin de cette leçon, tu sauras

  • dire où le HTML est fabriqué : navigateur, serveur ou build ;
  • opposer CSR, SSR et SSG et leurs effets sur les Web Vitals ;
  • expliquer le coût de l'hydratation sur l'interactivité ;
  • choisir une stratégie selon le type de site et savoir l'alléger.
Sommaire de la leçon

Une question décide d'une grande partie de la performance d'un site, avant même la moindre optimisation : où le HTML est-il fabriqué ? Dans le navigateur de l'utilisateur, sur le serveur à chaque visite, ou une fois pour toutes au moment de la publication ? Ce choix — la stratégie de rendu — pèse sur la vitesse d'affichage, l'interactivité et le référencement. Cette leçon est conceptuelle : pas de serveur à installer, juste les idées pour comprendre les compromis et parler le même langage que les frameworks modernes.

Trois endroits pour fabriquer le HTML

Le HTML qu'affiche le navigateur peut naître à trois moments : dans le navigateur à l'exécution (rendu client, CSR), sur le serveur à chaque requête (rendu serveur, SSR), ou au build, une fois avant la mise en ligne (rendu statique, SSG). Plus le HTML arrive prêt, plus le premier affichage est rapide — mais moins il est produit tard, moins il peut être personnalisé à la volée. Tout est là : un curseur entre vitesse d'affichage et fraîcheur/personnalisation.

Le rendu côté client (CSR)

En CSR, le serveur envoie une page presque vide et un gros fichier JavaScript ; c'est le navigateur qui, en l'exécutant, construit tout l'affichage. Avantage : après le premier chargement, la navigation interne est très fluide (pas de rechargement). Inconvénients pour la performance : un écran blanc tant que le JS n'est pas téléchargé et exécuté (mauvais LCP), et un référencement plus fragile (le contenu n'existe pas dans le HTML initial).

Rendu serveur (SSR) et statique (SSG)

Dans les deux cas, le navigateur reçoit un HTML déjà rempli : le contenu s'affiche vite (bon FCP/LCP) et les moteurs de recherche le lisent directement. La différence est le moment de fabrication. Le SSG génère les pages au build : idéal pour ce qui change peu (blog, documentation, page marketing) — c'est d'ailleurs exactement l'approche de ce site. Le SSR génère à chaque requête : nécessaire quand le contenu dépend de l'utilisateur ou change constamment (tableau de bord, page de compte, prix en direct), au prix d'un travail serveur à chaque visite.

Le coût caché : l'hydratation

Un HTML rendu au serveur s'affiche vite… mais il est d'abord inerte : les boutons sont visibles, pourtant rien ne réagit encore. Pour les rendre interactifs, le navigateur télécharge le JavaScript et rattache les écouteurs d'événements aux éléments déjà présents : c'est l'hydratation. Pendant ce laps de temps, la page semble prête mais ne répond pas — un piège classique pour l'INP : l'utilisateur clique, il ne se passe rien.

Alléger : moins de JavaScript à hydrater

Le fil rouge des approches modernes est simple : hydrater moins. Les îlots (islands) n'hydratent que les rares zones vraiment interactives (un panier, un carrousel) et laissent le reste en HTML statique. Le streaming SSR envoie le HTML par morceaux, dès qu'ils sont prêts, sans attendre toute la page. Les composants serveur (comme les React Server Components) exécutent une partie du code au serveur pour n'envoyer aucun JavaScript au client sur ces parties. Toutes visent la même cible : réduire le poids exécuté sur le fil principal — ce qu'on mesurait à la leçon 11.

Choisir selon le site

Il n'y a pas de « meilleure » stratégie dans l'absolu, seulement la bonne pour un besoin. Un contenu figé et public gagne au SSG ; un contenu personnalisé ou temps réel demande du SSR ; une application derrière authentification, où le SEO importe peu et la richesse d'interaction prime, peut assumer le CSR. Beaucoup de sites mélangent : SSG pour les pages publiques, SSR ou CSR pour l'espace connecté.

Le piège du « tout CSR » par défaut

Beaucoup de sites choisissent le CSR simplement parce que le framework le propose ainsi — sans en avoir besoin. Résultat : un blog qui affiche un écran blanc pendant deux secondes, le temps qu'un mégaoctet de JavaScript se télécharge, pour un contenu qui ne change jamais. Avant de charger du JavaScript pour construire une page, demande-toi si cette page a vraiment besoin d'être construite au client. Souvent, un simple HTML statique (SSG) est plus rapide, plus robuste et mieux référencé.

Cas réel : une page marketing en CSR

Une page d'accueil produit, entièrement en CSR, affichait un LCP à 4,2 s sur mobile : le visuel principal n'apparaissait qu'après le téléchargement et l'exécution du bundle. Comme le contenu était identique pour tous, l'équipe est passée en SSG : le HTML complet, image comprise, arrivait dès la première réponse. Le LCP est tombé à 1,3 s et la page est enfin devenue indexable proprement. Aucun contenu n'avait changé : seul le moment de fabrication du HTML.

Antisèche

Glossaire

CSR (Client-Side Rendering)
Le HTML est construit dans le navigateur par du JavaScript ; le serveur n'envoie qu'une coquille vide.
SSR (Server-Side Rendering)
Le serveur fabrique le HTML à chaque requête et l'envoie prêt à afficher.
SSG (Static Site Generation)
Les pages HTML sont générées une fois au build, avant la mise en ligne.
Hydratation
Étape où le JavaScript rattache les écouteurs d'événements à un HTML déjà rendu, pour le rendre interactif.
Îlots (islands)
Approche qui n'hydrate que les zones réellement interactives, en gardant le reste statique.
Streaming SSR
Envoi du HTML par morceaux au fur et à mesure qu'ils sont prêts, sans attendre toute la page.

Récap et vérification

  • Le HTML naît au build (SSG), au serveur (SSR) ou au navigateur (CSR).
  • Plus il arrive prêt, plus l'affichage et le SEO sont bons ; le CSR gagne en dynamisme mais retarde le premier rendu.
  • L'hydratation crée un délai « visible mais inerte » : un piège pour l'INP.
  • On choisit selon le site et on allège (îlots, streaming, moins de JS).

Vérifie ta compréhension

  1. Pourquoi une page en CSR affiche-t-elle souvent un écran blanc au début ?
  2. Qu'est-ce que l'hydratation, et pourquoi menace-t-elle l'INP ?
  3. Pour un blog qui change rarement, quelle stratégie et pourquoi ?

Exercices

Exercice 1Échauffement

Classe ces trois sigles du HTML « le plus prêt à l'affichage » au « moins prêt » : SSR, CSR, SSG. Justifie en une phrase.

Voir une solution

SSG > SSR > CSR. Le SSG livre un HTML fabriqué à l'avance, prêt immédiatement ; le SSR le fabrique à la requête (un court délai serveur, le TTFB, s'ajoute) ; le CSR n'envoie qu'une coquille vide et doit d'abord télécharger puis exécuter du JavaScript pour construire la page — c'est le plus tardif à l'affichage.

Exercice 2Application

Une page de documentation est en CSR : écran blanc d'une à deux secondes, et elle se référence mal. Quelle stratégie proposes-tu et quels gains attends-tu ?

Voir une solution

Passer en SSG : la documentation est un contenu stable, identique pour tous, sans besoin de personnalisation. Gains attendus : un LCP bien meilleur (le HTML complet, avec le texte, arrive dès la première réponse ; plus d'écran blanc en attendant le JavaScript), un SEO solide (le contenu est présent dans le HTML initial, directement lisible par les moteurs), et un hébergement plus simple et robuste (de simples fichiers). Si quelques éléments sont interactifs (recherche, menu), on peut les hydrater en îlots sans alourdir le reste.

Exercice 3Défi

Une application affiche vite son tableau de bord (rendu serveur), mais les utilisateurs se plaignent que « les boutons ne répondent pas pendant un instant après l'ouverture ». Explique la cause et propose deux pistes.

Voir une solution

La cause est le délai d'hydratation : le HTML rendu au serveur s'affiche vite, mais les boutons restent inertes tant que le JavaScript n'a pas fini de se télécharger et de rattacher ses écouteurs. Le clic tombe dans ce « trou », d'où l'impression d'une interface morte (mauvais INP). Deux pistes : (1) envoyer moins de JavaScript à hydrater — n'hydrater que les zones interactives (îlots), découper le bundle, déférer le non essentiel ; (2) prioriser l'hydratation des éléments visibles et souvent cliqués (hydratation à la demande, au premier survol/clic, ou au moment où l'élément entre à l'écran), pour que ce qui est sous les yeux réagisse en premier. On peut aussi utiliser le streaming pour livrer et activer la page par morceaux plutôt qu'en un bloc.
