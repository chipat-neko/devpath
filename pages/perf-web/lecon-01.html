Module 01 · Performance — Leçon 01

Les Web Vitals (LCP, CLS, INP)

~31 min Intermédiaire Bases HTML/CSS/HTTP

À la fin de cette leçon, tu sauras

  • expliquer pourquoi on mesure la performance ;
  • définir LCP, CLS et INP et leurs cibles ;
  • distinguer mesure de labo et de terrain ;
  • appliquer la démarche mesurer → corriger → re-mesurer.
Sommaire de la leçon

« Mon site est rapide » est une opinion ; 2,3 secondes pour le premier affichage est un fait. Pour optimiser, il faut d'abord mesurer — et avec les bons indicateurs. Google a popularisé un petit ensemble de mesures centrées sur l'expérience réelle : les Core Web Vitals.

Pourquoi mesurer ?

La performance n'est pas un caprice de développeur : un site lent fait fuir les visiteurs, baisse les conversions, et il est moins bien classé par les moteurs (les Web Vitals sont un signal de classement). Surtout, l'optimisation « au feeling » est trompeuse : on développe sur une machine puissante et un bon réseau, très loin du mobile d'un utilisateur réel.

Cas réel : la vitesse se compte en argent

Les grands sites mesurent l'impact au centime près. Amazon a estimé qu'+100 ms de latence lui coûtait environ 1 % de ventes ; en réduisant fortement ses temps d'attente, Pinterest a vu son trafic issu des moteurs de recherche grimper d'environ 15 %. À l'inverse, un chantier de refonte « au feeling », sans mesure, dépense des semaines sur un frein qui n'en était pas un. La mesure n'est pas de la bureaucratie : c'est ce qui dirige l'effort là où il rapporte.

Les trois Core Web Vitals

Trois indicateurs couvrent trois questions essentielles :

  • LCP — Largest Contentful Paint : « le contenu principal s'affiche-t-il vite ? ». C'est le temps d'apparition du plus gros élément visible (image héro, titre). Cible : < 2,5 s.
  • CLS — Cumulative Layout Shift : « la page est-elle stable ? ». Mesure les sauts de mise en page imprévus (un bouton qui bouge au moment où on clique). Cible : < 0,1.
  • INP — Interaction to Next Paint : « la page réagit-elle vite ? ». Mesure la latence entre une interaction et la réponse visible. Cible : < 200 ms.

Trois questions, trois mesures

LCP = ça s'affiche vite ? CLS = ça ne bouge pas ? INP = ça répond vite ? Garde cette grille en tête : chaque optimisation vise à améliorer l'une de ces trois sensations.

Mesurer : labo et terrain

Deux types de mesures, complémentaires :

  • Labo : en conditions simulées et reproductibles — Lighthouse (DevTools), idéal pour déboguer et comparer avant/après.
  • Terrain (RUM, Real User Monitoring) : les vraies mesures des vrais visiteurs, avec leurs appareils et réseaux. C'est ce qui compte pour le classement.

Teste comme un vrai utilisateur

Dans Lighthouse, active le bridage (mobile + réseau lent). Un site « instantané » sur ta fibre peut être pénible sur un mobile d'entrée de gamme en 4G — et c'est ce que vit une grande partie de tes visiteurs.

La démarche

L'optimisation est une boucle, pas un coup de baguette : (1) mesurer (Lighthouse + terrain), (2) identifier le plus gros frein, (3) corriger une chose, (4) re-mesurer pour vérifier le gain. On répète sur le frein suivant. On ne devine jamais.

Pièges fréquents

  • Optimiser au feeling. Sans mesure, on perd du temps sur le mauvais problème.
  • Tester seulement sur sa machine. Brider mobile + réseau lent change tout.
  • Oublier le CLS. Un site « rapide » mais instable reste désagréable.
  • Confondre labo et terrain. Lighthouse aide à déboguer ; le classement se base sur les données réelles.

Pour aller plus loin

Les Web Vitals évoluent : INP a remplacé l'ancien FID (First Input Delay) en 2024 pour mieux refléter la réactivité tout au long de la visite. L'esprit reste le même : des mesures simples, centrées sur le ressenti de l'utilisateur, plutôt qu'une foule de métriques techniques.

Pour aller plus loin

Fixe-toi un budget de performance (ex. « LCP < 2,5 s sur mobile bridé ») et vérifie-le régulièrement. Un budget transforme la performance d'un vague objectif en une contrainte claire qu'on ne laisse pas dériver.

Glossaire

Core Web Vitals
Petit ensemble de mesures centrées sur l'expérience réelle (LCP, CLS, INP), aussi utilisées comme signal de classement.
LCP (Largest Contentful Paint)
Temps d'apparition du plus gros élément visible (image héro, titre) ; cible < 2,5 s.
CLS (Cumulative Layout Shift)
Ampleur des sauts de mise en page imprévus pendant le chargement ; cible < 0,1.
INP (Interaction to Next Paint)
Latence entre une interaction et la réponse visible à l'écran ; cible < 200 ms. A remplacé le FID en 2024.
Labo (lab data)
Mesure en conditions simulées et reproductibles (ex. Lighthouse) : idéale pour déboguer et comparer avant/après.
Terrain (RUM)
Real User Monitoring : mesures des vrais visiteurs, avec leurs appareils et réseaux ; ce qui compte pour le classement.
Lighthouse
Outil d'audit intégré aux DevTools qui produit un rapport de performance (mesure de labo).
Budget de performance
Seuil que l'on s'impose (ex. « LCP < 2,5 s sur mobile bridé ») pour empêcher la performance de dériver.

Récap et vérification

  • On mesure avant d'optimiser : l'intuition trompe.
  • LCP (affichage < 2,5 s), CLS (stabilité < 0,1), INP (réactivité < 200 ms).
  • Mesure de labo (Lighthouse) pour déboguer, de terrain (RUM) pour le classement.
  • Boucle : mesurer → identifier → corriger → re-mesurer.

Vérifie ta compréhension

  1. Que mesure le LCP, et quelle est sa cible ?
  2. Comment éviter un mauvais CLS sur une image ?
  3. Quelle différence entre mesure de labo et de terrain ?

Exercices

Exercice 1Échauffement

Associe chaque Web Vital à la question qu'il répond : « ça s'affiche vite ? », « ça ne bouge pas ? », « ça répond vite ? ».

Voir une solution

LCP → « ça s'affiche vite ? » (chargement du contenu principal). CLS → « ça ne bouge pas ? » (stabilité visuelle). INP → « ça répond vite ? » (réactivité aux interactions).

Exercice 2Application

Ajoute les attributs qui réservent l'espace d'une image 1200×800 pour éviter le saut de mise en page.

Voir une solution

Le navigateur connaît le ratio et réserve la place avant même de charger l'image.

Exercice 3Défi

Sur ta machine, le site s'affiche « instantanément » et Lighthouse donne un bon LCP. Mais les données de terrain montrent un LCP de 4,5 s pour beaucoup d'utilisateurs. Comment l'expliques-tu, et que fais-tu ?

Voir une solution

Ta machine (CPU rapide, fibre) ne représente pas tes visiteurs réels (mobiles d'entrée de gamme, 4G, réseaux lents). Le test de labo non bridé est trop optimiste ; les données de terrain disent la vérité. Que faire : (1) re-tester dans Lighthouse en activant le bridage mobile + réseau lent pour reproduire le problème ; (2) identifier ce qui retarde le plus gros élément (image héro lourde, JS bloquant, polices, réponse serveur) ; (3) corriger ce frein (optimiser l'image, précharger, différer le JS…) ; (4) re-mesurer sur le terrain. La règle : on optimise pour l'utilisateur réel, pas pour sa propre machine.
