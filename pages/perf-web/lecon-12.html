Module 05 · Maîtriser — Leçon 12

Les Web Workers : libérer le fil principal

~36 min Avancé Leçon 11 requise

À la fin de cette leçon, tu sauras

  • expliquer ce qu'un Web Worker apporte à la fluidité ;
  • créer un worker et échanger avec lui par postMessage ;
  • distinguer la copie (structured clone) du transfert d'un ArrayBuffer ;
  • reconnaître ce qu'un worker ne peut pas faire, et quand il en vaut la peine.
Sommaire de la leçon

À la leçon précédente, on a appris à découper une tâche longue pour rendre la main. Mais parfois, un calcul est si lourd — analyser un gros fichier, traiter une image, filtrer des dizaines de milliers de lignes — que même découpé, il gêne l'interface. La vraie solution est alors de le sortir du fil principal. C'est le rôle des Web Workers : un second fil d'exécution, en parallèle, qui calcule pendant que le fil principal reste libre pour l'affichage et les clics.

Pourquoi un second fil

Le fil principal doit rester disponible pour l'utilisateur. Un worker est un fil séparé qui exécute son propre JavaScript en même temps, sans jamais bloquer l'interface. Il ne partage pas les variables de la page : les deux fils communiquent uniquement par messages. On confie au worker le calcul ; il renvoie le résultat ; le fil principal se contente de l'afficher.

Créer un worker et lui parler

Un worker vit dans son propre fichier. Sur la page, on le crée avec new Worker(), on lui envoie des données avec postMessage(), et on écoute sa réponse avec l'événement message. Dans le fichier du worker, on écoute pareillement les messages entrants et on répond avec postMessage().

Rien d'autre à installer : Worker fait partie du navigateur. Le worker a accès à un contexte réduit — self, fetch, les minuteurs, la plupart des API de calcul — mais pas à la page elle-même.

Échanger des données : copie ou transfert

Par défaut, les données passées à postMessage() sont copiées (mécanisme du structured clone) : le worker reçoit un double indépendant, il n'y a pas de mémoire partagée à protéger. C'est simple et sûr, mais copier un très gros objet a un coût proportionnel à sa taille. Pour les gros tampons binaires (image, son, données brutes), on peut transférer la propriété d'un ArrayBuffer au lieu de le copier : le transfert est quasi instantané, mais l'original devient inutilisable côté émetteur (il a « changé de main »).

Ce qu'un worker ne peut pas faire

Un worker n'a pas accès au DOM : pas de document, pas de window, aucune manipulation de la page. C'est voulu : si deux fils pouvaient modifier l'affichage en même temps, le rendu deviendrait incohérent. Le partage du travail est donc clair : le worker calcule et renvoie des données ; seul le fil principal touche à la page. Pour dessiner hors du fil principal, il existe un cas particulier, OffscreenCanvas, qui permet de confier un canvas à un worker — mais c'est l'exception qui confirme la règle.

Un worker n'est pas gratuit

Créer un worker et lui envoyer des messages a un coût fixe (démarrage du fil, sérialisation des données). Pour un petit calcul de quelques millisecondes, ce coût dépasse le gain : on ralentit au lieu d'accélérer. Le worker se justifie quand le calcul est vraiment lourd (dizaines de ms et plus) ou répété. En dessous, un simple découpage (leçon précédente) suffit.

Cas réel : un import de CSV qui gelait l'appli

Une application laissait l'utilisateur importer un fichier CSV de plusieurs Mo. L'analyse et la validation, faites sur le fil principal, gelaient l'interface pendant 3 à 4 secondes : barre de progression figée, boutons inertes. En déplaçant l'analyse dans un worker et en renvoyant l'avancement par messages, l'interface est restée fluide pendant tout l'import, avec une vraie progression animée. Le temps de calcul n'a pas changé ; c'est le fil principal, resté libre, qui a tout changé pour l'utilisateur.

Antisèche

Glossaire

Web Worker
Fil d'exécution JavaScript séparé, en parallèle du fil principal ; ne partage pas les variables de la page et n'a pas accès au DOM.
postMessage
Méthode d'envoi de données d'un fil à l'autre ; les données sont copiées (ou transférées) et reçues via l'événement message.
Structured clone
Mécanisme de copie en profondeur des données échangées ; sûr, mais son coût croît avec la taille.
Objet transférable
Donnée (comme un ArrayBuffer) dont on passe la propriété à l'autre fil sans copie ; l'original devient inutilisable.
ArrayBuffer
Tampon de données binaires brutes de taille fixe ; candidat idéal au transfert.
OffscreenCanvas
Canvas manipulable depuis un worker, pour dessiner sans occuper le fil principal.

Récap et vérification

  • Un worker est un second fil : il calcule en parallèle sans bloquer l'interface.
  • Les fils communiquent par messages (postMessage / message), pas par variables partagées.
  • Les données sont copiées par défaut ; on peut transférer un ArrayBuffer pour éviter la copie.
  • Pas de DOM dans un worker ; il se justifie pour un calcul lourd, pas pour un petit.

Vérifie ta compréhension

  1. Pourquoi un worker ne fige-t-il pas l'interface, même pour un très gros calcul ?
  2. Quelle différence entre copier et transférer un ArrayBuffer ?
  3. Pourquoi ne met-on pas un tout petit calcul dans un worker ?

Exercices

Exercice 1Échauffement

Vrai ou faux : « Depuis un worker, je peux mettre à jour directement le texte d'un bouton avec document.querySelector. » Justifie.

Voir une solution

Faux. Un worker n'a pas accès au DOM : ni document, ni window. Il ne peut donc pas modifier le bouton. La bonne démarche : le worker renvoie le nouveau texte par postMessage, et c'est le fil principal, dans son gestionnaire message, qui met à jour le DOM. Le worker calcule, la page affiche.

Exercice 2Application

Écris, côté page, le code qui crée un worker tri.worker.js, lui envoie un tableau data à trier, et affiche le résultat reçu via afficher().

Voir une solution

Et côté worker : self.onmessage = (e) => self.postMessage(e.data.sort((a,b) => a - b));. Le tri, même long, n'occupe que le fil du worker.

Exercice 3Défi

Tu déplaces un calcul de 8 ms (répété à chaque frappe) dans un worker, et… l'appli devient plus lente et saccadée. Explique pourquoi, et dis quand le worker aurait été le bon choix.

Voir une solution

Pour 8 ms de calcul, le coût fixe du worker (sérialiser le message à l'aller, le désérialiser au retour, franchir la frontière entre fils) dépasse le gain : à chaque frappe on paie ce surcoût, d'où la lenteur. Sous ce seuil, mieux vaut découper ou débattre (debounce) le calcul sur le fil principal. Le worker devient rentable quand le calcul est lourd (dizaines à centaines de ms), continu (traitement d'un flux) ou porté par un gros tampon qu'on peut transférer plutôt que copier — là, sortir le travail du fil principal paie largement son coût d'entrée.
