Mesurer dans la durée : labo, terrain & budgets

~38 min Avancé Leçon 09 requise

À la fin de cette leçon, tu sauras

  • distinguer la mesure en laboratoire et sur le terrain ;
  • lire les Core Web Vitals au 75e centile (CrUX, Search Console) ;
  • collecter du RUM sur tes vrais utilisateurs ;
  • fixer un budget et le tenir avec Lighthouse CI.
Sommaire de la leçon

On sait optimiser. Reste la question qui décide de tout : comment sait-on qu'on a vraiment amélioré les choses ? Un score Lighthouse à 98 sur ta machine ne prouve rien si tes visiteurs, eux, attendent. Il existe pour cela deux mesures complémentaires — le laboratoire et le terrain — et une manière de ne plus régresser une fois les gains obtenus.

Laboratoire ou terrain : deux mesures qui se complètent

La mesure de laboratoire (lab) reproduit un chargement dans des conditions fixes et contrôlées : un appareil simulé, un réseau bridé, une page rechargée à froid. C'est ce que fait Lighthouse. Reproductible, elle est parfaite pour déboguer et comparer un avant/après.

La mesure de terrain (field, ou RUM pour Real User Monitoring) provient des vrais utilisateurs : leurs appareils, leurs réseaux, leurs pays. Elle seule dit ce que vivent réellement les gens — mais on ne la voit qu'après la mise en ligne, et elle ne se « rejoue » pas à volonté.

Un bon score labo ne garantit pas un bon terrain

Lighthouse teste un appareil, une connexion. Tes utilisateurs, eux, sont sur mille configurations. Un 98/100 en labo peut coexister avec un terrain médiocre si ton public réel roule sur des mobiles d'entrée de gamme en 4G lente. Le labo oriente ; le terrain tranche.

Le terrain et le 75e centile

Sur le terrain, une seule visite ne veut rien dire : il faut une distribution. Google évalue les Core Web Vitals au 75e centile (p75) : la valeur sous laquelle se situent 75 % des visites. Autrement dit, « au moins trois visiteurs sur quatre ont une bonne expérience ». On préfère le p75 à la moyenne, car une moyenne flatteuse peut cacher une minorité qui souffre.

Où voit-on ces données de terrain sans rien installer ? Google agrège les mesures des utilisateurs de Chrome dans le CrUX (Chrome UX Report). On les consulte dans :

  • PageSpeed Insights : colle une URL, tu obtiens le terrain (CrUX) et un audit labo (Lighthouse) côte à côte.
  • Search Console → rapport « Signaux web essentiels » : l'état de tes URL (bonnes / à améliorer / mauvaises) sur mobile et ordinateur, dans le temps.

Ton propre RUM en quelques lignes

Le CrUX ne couvre que les pages assez visitées et n'inclut pas l'INP par élément. Pour du sur-mesure, la petite bibliothèque officielle web-vitals mesure LCP, CLS et INP chez tes vrais utilisateurs et t'envoie les valeurs. Tu vois alors tes centiles, segmentés par page, pays ou type d'appareil.

Ne plus régresser : le budget en CI

Obtenir un bon score est une chose ; le garder en est une autre. À chaque fonctionnalité, une image un peu lourde, une librairie « juste pour un détail », et le site s'alourdit sans qu'on le voie — la mort par mille coupures. La parade : un budget de performance vérifié automatiquement à chaque changement.

Lighthouse CI lance Lighthouse dans la chaîne d'intégration : à chaque pull request, il mesure et fait échouer le build si un seuil est franchi (LCP trop long, JS trop lourd…). La régression est bloquée avant d'atteindre les utilisateurs.

Cas réel : le paradoxe du « bon score, utilisateurs mécontents »

Une équipe affichait fièrement un Lighthouse à 95 sur son poste. Pourtant la Search Console classait ses pages « à améliorer » : le p75 du LCP dépassait 3,5 s sur le terrain. En posant un RUM (web-vitals), ils ont vu la vérité : leurs visiteurs, majoritairement sur mobile en 4G, subissaient une police web bloquante invisible sur une fibre de bureau. Un font-display: swap + un préchargement ciblé, et le p75 est repassé au vert. Sans le terrain, ils « optimisaient » une page déjà rapide… pour eux.

Pour aller plus loin

Au-delà de Lighthouse CI, on trouve WebPageTest (labo très détaillé, waterfall, multi-lieux), les budgets webpack/Vite (alerte au dépassement de poids d'un bundle) et les plateformes RUM (SpeedCurve, Sentry, ou ta propre collecte). L'idée reste la même : mesurer en continu et faire du seuil une règle, pas un vœu.

Glossaire

Données de laboratoire
Mesures prises dans des conditions fixes et contrôlées (appareil simulé, réseau bridé) ; reproductibles, idéales pour déboguer et comparer. Ex. : Lighthouse.
Données de terrain (RUM)
Real User Monitoring : mesures collectées chez les vrais utilisateurs, sur leurs appareils et réseaux ; seul reflet de l'expérience vécue.
CrUX
Chrome UX Report : base de données publique agrégeant les Core Web Vitals des utilisateurs de Chrome, source du terrain dans PageSpeed Insights et Search Console.
75e centile (p75)
Valeur sous laquelle se situent 75 % des visites ; seuil retenu par Google pour juger un Web Vital, plus honnête que la moyenne.
PageSpeed Insights
Outil web affichant côte à côte le terrain (CrUX) et un audit de laboratoire (Lighthouse) pour une URL.
Search Console
Console Google pour les propriétaires de site ; son rapport « Signaux web essentiels » suit l'état des URL dans le temps.
Lighthouse CI
Exécution automatique de Lighthouse dans la chaîne d'intégration ; fait échouer le build quand un budget est dépassé.
Budget de performance
Ensemble de seuils à ne pas dépasser (poids, temps, score) ; devient une contrainte tenue une fois vérifié automatiquement.

Récap et vérification

  • Le labo (Lighthouse) est reproductible : on l'utilise pour déboguer et comparer avant/après.
  • Le terrain (RUM, CrUX) dit ce que vivent les vrais utilisateurs : on le juge au p75.
  • On lit le terrain gratuitement via PageSpeed Insights et Search Console ; on l'affine avec web-vitals.
  • Un budget en CI (Lighthouse CI) empêche la régression de repartir vers les utilisateurs.

Vérifie ta compréhension

  1. Où consulter le terrain de ton site sans rien installer ?
  2. Pourquoi juge-t-on un Web Vital au p75 plutôt qu'à la moyenne ?
  3. Que fait Lighthouse CI quand un budget est dépassé ?

Exercices

Exercice 1Échauffement

Pour chacun de ces besoins, dis si tu utilises le labo ou le terrain : (a) comparer une page avant et après une optimisation ; (b) savoir si tes vrais visiteurs mobiles ont un bon LCP ; (c) déboguer pas à pas une image trop lourde.

Voir une solution

(a) Labo — on veut des conditions figées pour isoler l'effet de la seule optimisation. (b) Terrain — seul le RUM/CrUX (via Search Console ou web-vitals) dit ce que vivent les mobiles réels. (c) Labo — Lighthouse/WebPageTest donnent le détail reproductible (waterfall, éléments) pour déboguer. Règle : labo pour corriger et comparer, terrain pour vérifier le réel.

Exercice 2Application

Ta page a un LCP moyen de 2,1 s, mais un p75 à 3,4 s. Que t'apprend cet écart, et par où commencer ?

Voir une solution

La moyenne (2,1 s) est trompeuse : elle est tirée vers le bas par les visites rapides. Le p75 à 3,4 s montre qu'un quart des visites (au moins) est nettement au-dessus de la cible de 2,5 s — Google classera la page « à améliorer ». Il faut regarder qui est dans la traîne lente : segmenter le RUM par appareil, réseau ou pays. Souvent, c'est le mobile en réseau lent ; on cible alors l'image LCP (format/poids/préchargement) et les polices bloquantes. On re-mesure ensuite le p75, pas la moyenne.

Exercice 3Défi

Ton équipe corrige la perf tous les six mois, puis elle se dégrade à nouveau à chaque nouvelle fonctionnalité. Propose un dispositif pour que ça tienne dans la durée.

Voir une solution

Le problème n'est pas de corriger, c'est de ne plus régresser. Il faut institutionnaliser la mesure : 1) définir un budget chiffré (ex. score perf ≥ 0,9, LCP ≤ 2,5 s, JS initial ≤ 150 Ko) ; 2) le vérifier automatiquement à chaque pull request avec Lighthouse CI, qui fait échouer le build en cas de dépassement — la régression est arrêtée avant la mise en ligne ; 3) compléter par un budget de bundle (webpack/Vite) pour alerter dès qu'un import alourdit le JS ; 4) surveiller le terrain (Search Console, RUM) pour attraper ce que le labo ne voit pas. Le seuil devient une règle partagée, plus un effort ponctuel.

Exercice 4Au clavier

Un budget de performance ne sert que s'il rend un verdict chiffré. Écris verdict(ressources, budgetKo) qui rend tenu ou dépassé de N Ko, puis affiche le verdict pour { js: 420, css: 90, images: 610 } face à un budget de 1000 Ko.
