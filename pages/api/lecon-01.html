Module 1 · Les fondamentaux REST — Leçon 01

Qu'est-ce qu'une API REST

~30 min Débutant Bases du web utiles

À la fin de cette leçon, tu sauras

  • expliquer ce qu'est une API ;
  • décrire le modèle client/serveur sur HTTP ;
  • définir les principes REST (ressources, sans état) ;
  • lire une requête et une réponse simples.
Sommaire de la leçon

Une application mobile qui affiche la météo, un site qui montre tes commandes, un front JavaScript qui charge des données sans recharger la page : tous parlent à un serveur via une API. Une API REST est la façon la plus répandue de faire dialoguer deux programmes sur le web. La comprendre, c'est tenir le fil qui relie le front-end au back-end, les applis mobiles aux serveurs, et les services entre eux.

Ce cours est transversal et indépendant d'un langage : les principes valent que tu construises ton API en Node, Python, PHP, Java ou autre. On y parle conception et conventions, le savoir qui rend une API agréable à utiliser.

Une API, c'est quoi ?

API signifie Application Programming Interface : une interface par laquelle un programme en utilise un autre. Comme un menu de restaurant : tu n'as pas besoin de savoir comment la cuisine fonctionne ; tu lis le menu, tu commandes, on te sert. L'API est ce menu : elle liste ce que tu peux demander et sous quelle forme, en cachant les détails internes.

Une API web expose ces services par le réseau, en utilisant le protocole HTTP — le même qui sert à charger des pages. Au lieu de renvoyer du HTML pour un navigateur, elle renvoie des données (le plus souvent en JSON) pour un autre programme.

Cas réel

Quand une appli météo affiche la température, elle appelle en coulisse une API web et reçoit un JSON du genre {"ville":"Lyon","temp":21}. Elle ne connaît rien des serveurs, des bases de données ni des capteurs derrière : elle lit le « menu » (l'API) et affiche la réponse. GitHub, Google Maps, ta banque : presque toute appli moderne est un assemblage d'appels d'API.

Le modèle client/serveur

Toute API web repose sur un échange entre deux rôles : un client qui demande, un serveur qui répond. Le client envoie une requête ; le serveur renvoie une réponse. C'est un dialogue strict : une requête, une réponse.

Le client peut être n'importe quoi : un navigateur, une appli mobile, un autre serveur, ou un simple outil de test comme curl. Le serveur, lui, ne sait rien du client : il reçoit une requête, la traite, répond, et passe à la suivante.

Observe un vrai échange

Ouvre les outils de développement de ton navigateur (onglet Réseau) et navigue sur un site : tu verras défiler les requêtes et leurs réponses JSON. Ou en terminal : curl https://api.github.com/users/torvalds renvoie une vraie réponse d'API. Rien ne remplace le fait de voir le dialogue client/serveur en direct.

Les principes REST

REST (REpresentational State Transfer) est un style de conception d'API web, pas une technologie. Il repose sur quelques idées simples qui, ensemble, rendent une API prévisible :

  • tout est une ressource : un article, un utilisateur, une commande. Chaque ressource a une URL qui l'identifie (par ex. /articles/42).
  • on agit sur les ressources avec les verbes HTTP standards (lire, créer, modifier, supprimer) — la prochaine leçon les détaille.
  • le serveur renvoie une représentation de la ressource, généralement en JSON.
  • la communication est sans état (stateless) : chaque requête contient tout ce qu'il faut pour être traitée ; le serveur ne « se souvient » pas des requêtes précédentes.

Le caractère sans état est important : il signifie qu'on peut multiplier les serveurs (pour tenir la charge), n'importe lequel pouvant traiter n'importe quelle requête, puisque rien n'est gardé en mémoire entre deux appels. L'information nécessaire (qui es-tu, que veux-tu) voyage dans chaque requête.

« Sans état » ne veut pas dire « sans données »

Le serveur ne garde pas de contexte de conversation entre deux requêtes : il ne se souvient pas que tu viens d'appeler telle URL. Mais il a bien sûr une base de données persistante ! La nuance : l'état des données (les articles) vit dans la base ; l'état de la session (qui es-tu, où en es-tu) voyage dans chaque requête, pas dans la mémoire du serveur.

Ressource et représentation

Distinction subtile mais utile : la ressource est le concept (l'article n°42) ; la représentation est sa forme transmise (le JSON qui le décrit à un instant donné). La même ressource pourrait être représentée en JSON, en XML, ou autrement ; aujourd'hui, JSON domine très largement.

Ce bloc JSON est la représentation de la ressource « article 42 » renvoyée par le serveur. Le client la reçoit, la lit, l'affiche. C'est ce dialogue — URL pour désigner, verbe pour agir, JSON pour représenter — qui constitue le cœur de REST.

Pour aller plus loin

REST n'est pas la seule façon de faire dialoguer deux programmes. Tu croiseras aussi GraphQL (le client décrit précisément les données voulues en une requête), gRPC (binaire, très rapide, entre services) et les WebSockets (canal bidirectionnel temps réel). REST reste le point de départ : le plus répandu, le plus simple à lire, et celui dont les principes éclairent tous les autres.

Antisèche : le vocabulaire REST

Glossaire

API (Application Programming Interface)
Interface par laquelle un programme en utilise un autre. Une API web le fait par le réseau, via HTTP, en échangeant des données.
REST
REpresentational State Transfer : un style de conception d'API web (pas une technologie) fondé sur des ressources, des URL, les verbes HTTP et l'absence d'état.
Client / Serveur
Les deux rôles d'un échange : le client envoie une requête, le serveur renvoie une réponse. Le serveur ignore tout du client d'un appel à l'autre.
Requête / Réponse
L'aller-retour de base : une demande (verbe + URL + éventuel corps) suivie d'un résultat (statut + données).
Ressource
Le concept manipulé (un article, un utilisateur), identifié par une URL comme /articles/42.
Représentation
La forme concrète d'une ressource transmise sur le réseau, aujourd'hui presque toujours en JSON.
Sans état (stateless)
Propriété de REST : chaque requête contient tout ce qu'il faut pour être traitée ; le serveur ne mémorise pas les requêtes précédentes.
HTTP
Le protocole du web qui transporte requêtes et réponses ; le même qui charge les pages sert aux API.

Récap et vérification

  • Une API est une interface par laquelle un programme en utilise un autre ; une API web le fait via HTTP.
  • Modèle client/serveur : le client envoie une requête, le serveur renvoie une réponse.
  • REST : des ressources identifiées par des URL, manipulées par les verbes HTTP, représentées en JSON.
  • La communication est sans état : chaque requête se suffit à elle-même.

Vérifie ta compréhension

  1. Avec tes mots, qu'est-ce qu'une API ?
  2. Que signifie « sans état » pour une API REST ?
  3. Quelle différence entre une ressource et sa représentation ?

Exercices

Exercice 1Échauffement

Dans l'échange GET /articles → réponse JSON, identifie qui est le client et qui est le serveur.

Voir une solution

Le client est celui qui envoie la requête GET /articles (par ex. un front JavaScript, une appli mobile, ou curl). Le serveur est celui qui reçoit cette requête et renvoie la réponse (le statut 200 OK et le JSON des articles).

Exercice 2Application

Pourquoi le caractère « sans état » facilite-t-il la mise à l'échelle d'une API (ajouter des serveurs) ?

Voir une solution

Parce qu'aucune information n'est conservée sur un serveur particulier entre deux requêtes : chaque requête se suffit à elle-même. On peut donc placer plusieurs serveurs identiques derrière un répartiteur de charge ; n'importe lequel peut traiter n'importe quelle requête, sans avoir besoin de connaître l'historique. Si l'état était stocké côté serveur, il faudrait toujours renvoyer le client vers le « bon » serveur.

Exercice 3Défi

Écris la représentation JSON plausible d'une ressource « utilisateur » d'identifiant 7, avec un nom et un e-mail.

Voir une solution

C'est une représentation possible de la ressource « utilisateur 7 », telle que la renverrait GET /utilisateurs/7.
