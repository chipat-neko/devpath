Module 05 · API en pratique — Leçon 10

Documenter une API avec OpenAPI

~36 min Intermédiaire Leçon 05 recommandée

À la fin de cette leçon, tu sauras

  • expliquer ce qu'est un contrat OpenAPI (ex-Swagger) et à quoi il sert ;
  • lire et écrire la structure d'un document (info, paths, components) ;
  • en dériver une doc interactive, des clients et des serveurs générés ;
  • choisir entre les approches contract-first et code-first.
Sommaire de la leçon

Une API que personne ne sait utiliser ne vaut rien. Jusqu'ici tu as conçu des ressources, des URL et des réponses JSON ; encore faut-il les décrire aux développeurs qui vont les consommer — et, idéalement, aux machines. C'est le rôle d'OpenAPI : un format standard pour écrire le contrat d'une API REST, une fois, dans un fichier que lisent aussi bien les humains que les outils.

Un bon contrat OpenAPI n'est pas une corvée de fin de projet : c'est une source unique de vérité d'où découlent la documentation, des bibliothèques clientes, des squelettes de serveur et même des tests. Voyons comment.

Le contrat OpenAPI

OpenAPI (anciennement Swagger) est une spécification qui décrit une API REST dans un seul document, en YAML ou en JSON. Il énumère les chemins (les URL), les opérations (verbes HTTP), les paramètres, les corps de requête et les réponses possibles avec leurs schémas. Trois grandes sections structurent le fichier : info (métadonnées : titre, version), paths (les points d'entrée) et components (les schémas et objets réutilisables).

Note — Swagger, OpenAPI : le même objet

« Swagger » était le nom historique du format (et de ses outils). Depuis la version 3, la spécification s'appelle OpenAPI (3.0, puis 3.1 alignée sur JSON Schema), tandis que « Swagger » désigne désormais la famille d'outils (Swagger UI, Swagger Editor). Quand on dit « un fichier Swagger », on parle en général d'un document OpenAPI.

De la spec aux outils : un fichier, mille usages

La force d'OpenAPI, c'est que le contrat est exploitable par des machines. À partir du même openapi.yaml, on obtient gratuitement une documentation interactive (Swagger UI, Redoc, Scalar) où l'on peut essayer les requêtes depuis le navigateur, des bibliothèques clientes générées dans des dizaines de langages, des squelettes de serveur, et des outils de validation qui vérifient que les requêtes et réponses respectent le schéma.

Astuce — versionne la spec avec le code

Garde openapi.yaml dans le dépôt, à côté du code qu'il décrit. Chaque évolution de l'API passe alors par une modification visible du contrat, relue en pull request comme n'importe quel changement. Bonus : un outil de diff OpenAPI peut signaler automatiquement les changements cassants (un champ retiré, un type modifié) avant qu'ils n'atteignent les clients.

Contract-first ou code-first ?

Deux écoles cohabitent pour produire ce contrat. En contract-first, on écrit d'abord le openapi.yaml à la main, puis on en génère le squelette du serveur et les clients : l'API est conçue comme une interface, avant toute implémentation. En code-first, on écrit le code du serveur avec des annotations (ou des décorateurs), et un outil en extrait la spec. Le premier favorise la conception et le travail en parallèle des équipes ; le second colle au code et évite qu'il diverge de la doc.

Attention — une doc qui ment est pire que pas de doc

Le danger numéro un de la documentation, c'est la dérive : le code évolue, la spec reste figée, et les développeurs perdent confiance. La parade est d'automatiser : en code-first, régénérer la spec à chaque build ; en contract-first, valider en CI que l'implémentation respecte le contrat (tests de contrat, leçon à venir). Une spec vérifiée mécaniquement ne peut pas mentir longtemps.

Cas réel — les grandes API vivent de leur OpenAPI

Stripe, GitHub et Twilio publient publiquement la spécification OpenAPI de leur API. C'est ce qui leur permet d'offrir des SDK officiels dans une dizaine de langages (JavaScript, Python, Java, Go, Ruby…) tous générés à partir du même contrat, et de garder une documentation de référence toujours synchronisée. Quand GitHub ajoute un champ à une réponse, la spec change, et les SDK comme la doc suivent automatiquement. Sans ce contrat lisible par machine, maintenir à la main des dizaines de bibliothèques serait intenable.

Pour aller plus loin

Les components ne se limitent pas aux schemas : on y définit aussi des réponses, des paramètres et des schémas de sécurité (securitySchemes : Bearer JWT, OAuth2, clé d'API) réutilisables. Pour les API événementielles (WebSockets, files de messages), OpenAPI a un cousin, AsyncAPI, bâti sur les mêmes idées. Et comme OpenAPI 3.1 s'aligne sur JSON Schema, les mêmes schémas peuvent servir à valider des données bien au-delà des API.

Récap et vérification

  • OpenAPI (ex-Swagger) décrit une API REST dans un contrat YAML/JSON lisible par les humains et les machines.
  • Trois sections clés : info (métadonnées), paths (opérations et réponses), components (schémas réutilisables via $ref).
  • Du contrat dérivent doc interactive, SDK clients, squelettes serveur et validation — une seule source de vérité.
  • Contract-first (spec d'abord) ou code-first (spec extraite du code) : les deux marchent, à condition d'automatiser pour que la doc ne dérive pas.

Glossaire

OpenAPI
Spécification standard décrivant une API REST dans un document YAML ou JSON, exploitable par les humains et les outils.
Swagger
Nom historique du format, aujourd'hui réservé à la famille d'outils (Swagger UI, Swagger Editor) construits autour d'OpenAPI.
Contrat (d'API)
Description formelle de ce que l'API accepte et renvoie ; sert de référence partagée entre l'équipe serveur et les consommateurs.
paths
Section listant les chemins de l'API et, pour chacun, les opérations (verbes HTTP), paramètres, corps et réponses.
components
Section regroupant les éléments réutilisables (schémas, réponses, paramètres, schémas de sécurité) référencés par $ref.
Swagger UI
Interface web générée depuis un document OpenAPI, qui affiche la doc et permet d'essayer les requêtes depuis le navigateur.
Contract-first
Approche où l'on écrit d'abord le contrat OpenAPI, puis on en génère le serveur et les clients.
Code-first
Approche où l'on annote le code du serveur et où un outil en extrait automatiquement la spécification OpenAPI.
