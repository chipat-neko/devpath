Module 2 · Concevoir une API — Leçon 05

JSON, pagination, filtrage et versioning

~32 min Intermédiaire Leçon 04 requise

À la fin de cette leçon, tu sauras

  • structurer une réponse JSON claire ;
  • paginer une collection (limit/offset, curseur) ;
  • filtrer et trier via la query string ;
  • versionner une API.
Sommaire de la leçon

Renvoyer toute une table d'un coup en JSON brut marche pour dix éléments ; pas pour dix millions. Une vraie API doit aider le client à demander juste ce qu'il veut : une page de résultats, filtrés, triés. Et comme une API évolue, elle doit pouvoir changer sans casser les clients existants. Cette leçon couvre la mise en forme des données et ces mécanismes de collection : pagination, filtrage, et versioning.

Structurer le JSON

Une réponse JSON doit être prévisible. Pour un élément, on renvoie l'objet ; pour une collection, un tableau — souvent enveloppé dans un objet qui laisse de la place pour des métadonnées (total, pagination).

L'enveloppe { "data": [...], "meta": {...} } a un avantage : elle réserve un endroit pour les informations de pagination sans polluer les éléments. Quelle que soit ta convention, tiens-t'y partout : un client doit pouvoir compter sur une forme constante.

Paginer une collection

La pagination découpe une grande collection en pages. Deux approches dominent. La plus simple, limit/offset, se règle par la query string :

Simple, mais elle a une limite sur des données qui changent vite : si on insère des éléments entre deux pages, l'offset « glisse » et on peut voir un doublon ou rater un élément. La pagination par curseur corrige cela : au lieu d'un offset, le serveur renvoie un pointeur vers l'élément suivant.

Le curseur est un jeton opaque qui repère « où on en était » — stable même si des éléments sont ajoutés. Règle pratique : limit/offset pour des données stables et de petites tailles ; curseur pour de grands flux qui bougent (réseaux sociaux, journaux).

Filtrer et trier

La query string (la partie après le ?) sert aussi à filtrer et trier une collection, sans changer d'URL de ressource.

Ces paramètres se cumulent librement. Important : ils restent sur la même ressource /articles — on ne crée pas /articlesPublies ni /articlesTech. Le filtre est une vue de la collection, exprimée en query string ; l'URL de la ressource ne bouge pas.

Versionner l'API

Une API publique a des clients qui dépendent de sa forme. Si tu changes la structure d'une réponse, tu risques de tout casser chez eux. La version protège contre ça : on publie une nouvelle version sans toucher à l'ancienne.

La version dans le chemin (/v1/) est la plus courante car la plus visible. Le principe : les changements cassants (renommer un champ, en supprimer un) justifient une nouvelle version ; les ajouts compatibles (un nouveau champ optionnel) n'en demandent pas. Tu laisses ainsi le temps aux clients de migrer.

Cas réel

Stripe et GitHub incarnent ces choix. Stripe versionne par date (en-tête Stripe-Version: 2020-08-27) : chaque compte reste figé sur sa version tant qu'il ne migre pas, si bien qu'aucune évolution ne casse les intégrations en place. GitHub, lui, pagine par curseur sur ses gros flux (commits, notifications) via l'en-tête Link: <…?after=…>; rel="next" : impossible de rater ou de dupliquer un élément quand des milliers arrivent en continu. limit/offset, plus simple, reste réservé aux petites collections stables.

Toujours paginer par défaut

Ne renvoie jamais une collection complète sans limite : le jour où elle compte un million d'éléments, la requête écroule le serveur et le client. Impose une limite par défaut (ex. 20) et une limite maximale (ex. 100), même si le client ne demande pas de pagination. C'est une protection, pas une option.

Glossaire

Pagination
Découpage d'une grande collection en pages successives, pour ne jamais tout renvoyer d'un coup.
limit / offset
Pagination par position : limit = taille de page, offset = nombre d'éléments sautés. Simple, mais « glisse » si la collection change.
Curseur
Jeton opaque qui repère l'élément suivant ; stable même quand des éléments sont insérés. Adapté aux grands flux mouvants.
Query string
Partie de l'URL après le ?, faite de paires clé=valeur ; sert à filtrer, trier et paginer.
Tri
Ordonner la collection via la query string ; convention courante : - devant le champ = décroissant (?tri=-date).
Enveloppe
Objet { "data": […], "meta": {…} } qui entoure une collection pour réserver une place aux métadonnées (total, pagination).
Versioning
Publier une nouvelle version (/v2/) pour introduire un changement sans toucher à l'ancienne (/v1/).
Changement cassant
Modification qui brise les clients existants (renommer/supprimer un champ) ; impose une nouvelle version. Un ajout compatible, non.

Récap et vérification

  • Réponses JSON prévisibles : objet pour un élément, tableau (souvent enveloppé data/meta) pour une collection.
  • Pagination : limit/offset (simple) ou curseur (stable sur des flux qui bougent).
  • Filtrer/trier via la query string (?publie=true&tri=-date), sur la même ressource.
  • Versionner (/v1/) pour évoluer sans casser les clients existants.

Exercice 3Défi

Ton API renomme le champ titre en nom dans les réponses. Est-ce un changement cassant ? Comment le livrer sans briser les clients existants ?

Voir une solution

Oui, c'est un changement cassant : un client qui lit réponse.titre obtiendra undefined si le champ s'appelle désormais nom. Pour le livrer sans casse : publier une nouvelle version (/v2/articles) qui renvoie nom, tout en gardant /v1/articles qui renvoie encore titre. Les clients migrent vers /v2 à leur rythme ; on annonce ensuite une date de fin de support de /v1. (Un ajout de champ, à l'inverse, serait compatible et n'exigerait pas de nouvelle version.)
