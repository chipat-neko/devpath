Module 05 · API en pratique — Leçon 14

Projet fil rouge : une API de bout en bout

~40 min Intermédiaire Projet de synthèse

À la fin de cette leçon, tu sauras

  • assembler tout le cours en une API cohérente de bout en bout ;
  • dérouler la conception : ressources, verbes, statuts, pagination ;
  • ajouter les couches robustesse : authentification, erreurs Problem Details ;
  • documenter, notifier (webhook) et tester ton API.
Sommaire de la leçon

Nous voici au bout du cours. En treize leçons, tu as vu chaque brique séparément : le modèle client/serveur, les verbes et le CRUD, les codes de statut, la conception des URL, le JSON et la pagination, l'authentification, la sécurité, le passage à l'échelle, la documentation, la gestion des erreurs, les webhooks et les tests. Il est temps de tout assembler en une seule API cohérente. Ce projet fil rouge reprend l'API de tâches et l'étoffe, module après module, jusqu'à une API que tu pourrais réellement exposer.

Le cahier des charges

On veut une API REST qui gère des tâches : les lister (avec pagination), en créer, les modifier, les supprimer. Elle doit être authentifiée, renvoyer des erreurs standard, être documentée, notifier par webhook quand une tâche est terminée, et venir avec ses tests. Voici la vue d'ensemble des ressources et des points d'entrée.

Étape 1 — Concevoir les ressources et les URL

On part des noms (modules 01-02) : une collection /taches et ses éléments /taches/{id}. Des noms au pluriel, pas de verbe dans l'URL (le verbe, c'est la méthode HTTP), et une hiérarchie lisible.

Étape 2 — Le cycle CRUD et la pagination

Chaque verbe renvoie le bon statut (module 01) et, pour les listes, on pagine (module 02) plutôt que de renvoyer dix mille éléments d'un coup. Voici les requêtes type, en curl.

Un GET /taches ne renvoie jamais la collection entière : il en renvoie une page. La réponse est une enveloppe qui, en plus des éléments, indique le total et comment atteindre les autres pages.

Côté serveur, une requête traverse plusieurs couches avant de produire une réponse. Les visualiser aide à savoir où placer chaque responsabilité.

Étape 3 — Sécuriser et normaliser les erreurs

On protège toutes les routes par un jeton Bearer (modules 03-04) : sans jeton valide, 401 ; jeton valide mais sans droit, 403. Et on renvoie toutes les erreurs au format Problem Details (leçon 11), pour un client qui n'a qu'un format à gérer.

Astuce — un gestionnaire d'erreurs central

Ne bricole pas la réponse d'erreur dans chaque route. Centralise : une fonction unique attrape les exceptions (validation, ressource absente, droit refusé) et les traduit en problem+json. Le reste du code se contente de lever l'erreur métier ; la forme de la réponse reste garantie partout.

Étape 4 — Documenter et notifier

On décrit l'API en OpenAPI (leçon 10) : la spec sert de documentation interactive et de base aux tests de contrat. Et on émet un webhook (leçon 12) tache.terminee pour prévenir les services abonnés — signé, idempotent, avec accusé 2xx.

Cas réel — les mêmes briques dans une vraie API SaaS

Ce petit projet n'a rien d'un jouet : c'est l'ossature de la plupart des API de production. Un outil de gestion de projet (type Trello, Asana) expose exactement cela — des ressources CRUD paginées, un jeton d'accès, des erreurs standard, une spec OpenAPI publique, et des webhooks (card.updated, task.completed) pour intégrer Slack ou un CI. Change « tâche » en « facture », « réservation » ou « message » : le squelette est le même. Maîtriser ces sept briques, c'est savoir concevoir la quasi-totalité des API web.

Piège — n'attends pas l'accusé du webhook pour répondre

Le webhook part vers un service tiers que tu ne contrôles pas : s'il est lent ou injoignable, il ne doit pas bloquer la réponse à ton client. Émets l'événement dans une file d'attente, réponds tout de suite au client (le 200 du PUT), puis confie l'envoi — et ses réessais en cas d'échec — à un travailleur en arrière-plan. Un webhook synchrone, c'est la latence d'un inconnu greffée sur chacune de tes requêtes.

Étape 5 — Tester l'ensemble

On verrouille le contrat avec quelques tests d'intégration (leçon 13) : le chemin heureux et les refus.

Pour aller plus loin — et après ?

Ton API est conçue ; restent les étapes de vie : la versionner (/v1, leçon 05) pour évoluer sans casser les clients ; la déployer de façon reproductible (cours Docker) ; la surveiller (journaux, métriques, alertes — cours Observabilité) ; et documenter son cycle de vie (dépréciation annoncée, changelog). Une API n'est pas « finie » à la première mise en ligne : elle se maintient.

Récap du cours

  • Une API REST s'organise autour de ressources (URL) manipulées par des verbes HTTP, avec les bons codes de statut.
  • On la conçoit (URL, JSON, pagination, versioning), on la sécurise (auth, validation, erreurs standard), on la fait tenir à l'échelle (cache, rate limiting, au-delà de REST).
  • On la documente (OpenAPI), on la rend réactive (webhooks) et on la protège des régressions (tests de contrat en CI).
  • Le même squelette de sept briques se retrouve dans la quasi-totalité des API web de production.

Glossaire du cours

Ressource
Entité exposée par l'API et identifiée par une URL (ex. /taches/1) ; on la manipule via les verbes HTTP.
CRUD
Les quatre opérations de base — Créer, Lire, Mettre à jour, Supprimer — portées par POST, GET, PUT/PATCH, DELETE.
Code de statut
Nombre à trois chiffres résumant l'issue d'une requête : 2xx succès, 4xx erreur du client, 5xx erreur du serveur.
Pagination
Découpage d'une longue collection en pages successives, pour ne pas tout renvoyer d'un coup.
Jeton Bearer
Jeton d'accès envoyé dans l'en-tête Authorization pour authentifier chaque requête.
Problem Details
Format d'erreur standard (RFC 9457, application/problem+json) utilisé de façon cohérente pour toutes les erreurs.
OpenAPI
Spécification décrivant les routes, paramètres et schémas d'une API ; sert de documentation et de base aux tests de contrat.
Webhook
Notification HTTP émise par l'API vers une URL abonnée quand un événement survient, en remplacement du polling.

Exercices

Exercice 1Échauffement

Un client envoie DELETE /taches/1 et la suppression réussit. Quel code de statut HTTP renvoies-tu, sachant qu'il n'y a rien à retourner dans le corps de la réponse ?

Voir une solution

204 No Content : succès de la famille 2xx, sans corps de réponse.

Exercice 2Application

Après un POST /taches qui crée une ressource (réponse 201 Created), quel en-tête de réponse indique au client l'URL de la ressource fraîchement créée (par exemple /taches/42) ?

Voir une solution

L'en-tête Location : il pointe vers l'URL de la nouvelle ressource.

Exercice 3Application

Un client appelle GET /taches sans en-tête Authorization (aucun jeton). Toutes les routes de l'API exigent un jeton Bearer valide. Quel code de statut renvoies-tu ?

Voir une solution

401 Unauthorized : la requête n'est pas authentifiée. À ne pas confondre avec 403 Forbidden, qui répond à un client bien authentifié mais sans le droit d'accéder à la ressource.

Mini-projet fil rouge — l'API de tâches complète

Rassemble les cinq étapes en un seul jeu de requêtes. Essaie d'abord par toi-même de rédiger les appels et une réponse type, puis compare avec la solution de référence.

Ce que tu vas produire

Le parcours complet d'une tâche — création authentifiée, lecture paginée, mise à jour, notification par webhook et suppression — avec les bons verbes, statuts et formats.

Étapes

Créer

POST /taches avec jeton et corps JSON → 201 + Location.

Lister

GET /taches?page=1 → 200, collection paginée.

Terminer

PUT /taches/1 passe faite: true → 200, et émet le webhook.

Notifier

Un POST signé tache.terminee part vers l'abonné.

Supprimer

DELETE /taches/1 → 204, sans corps.

Voir une solution complète

Chaque étape mobilise une brique du cours : conception d'URL, verbe et statut justes, jeton d'authentification, pagination, format JSON avec liens, et webhook signé. C'est, en miniature, une API de production.
