Module 2 · Concevoir une API — Leçon 04

Concevoir des ressources et des URL

~34 min Intermédiaire Leçon 03 requise

À la fin de cette leçon, tu sauras

  • nommer des ressources avec des noms au pluriel ;
  • distinguer collection et élément ;
  • imbriquer des ressources liées ;
  • éviter les erreurs classiques (verbes dans l'URL).
Sommaire de la leçon

Une bonne API se reconnaît à ses URL : claires, régulières, devinables. Comme le verbe HTTP exprime déjà l'action (leçon 2), l'URL ne doit décrire que la ressource. Concevoir de bonnes URL, c'est offrir à ceux qui consommeront ton API une carte cohérente où ils se repèrent sans documentation. Cette leçon donne les conventions admises par toute la profession.

Des noms, pas des verbes

La règle d'or : une URL désigne une chose (un nom), jamais une action (un verbe). L'action est portée par le verbe HTTP. Mettre un verbe dans l'URL est l'erreur n°1 du débutant.

Pourquoi ? Parce que POST /createArticle répète l'idée de création déjà portée par POST, et multiplie les URL pour une même ressource. Avec des noms, une ressource = une URL, et les verbes HTTP couvrent toutes les actions. C'est plus court, plus régulier, plus prévisible.

Erreur n°1 du débutant

Mettre un verbe dans l'URL : /getArticles, /createUser, /deleteArticle/42. L'action est déjà portée par le verbe HTTP ; la répéter dans l'URL multiplie les chemins pour une même ressource et casse la régularité. Une URL nomme une chose, jamais une action.

Collections et éléments

Deux niveaux structurent une API REST : la collection (toutes les ressources d'un type) et l'élément (une ressource précise, identifiée). On utilise le pluriel pour les deux, l'élément ajoutant un identifiant.

Le pluriel (/articles, pas /article) se lit naturellement : /articles est « la liste des articles », /articles/42 est « l'article 42 dans cette liste ». Garde cette convention sur toute l'API : la régularité est ce qui la rend devinable.

Imbriquer des ressources liées

Quand une ressource appartient à une autre (les commentaires d'un article), on exprime ce lien par l'imbrication dans l'URL :

L'URL se lit comme un chemin : « dans l'article 42, les commentaires ». Mais ne va pas trop loin : au-delà de deux niveaux (/a/1/b/2/c/3), l'URL devient illisible. Passé un niveau d'imbrication, préfère une ressource à plat avec un filtre (vu en leçon 5) : /commentaires?article=42.

Cas réel

Les API que tout le monde cite en exemple — GitHub, Stripe — appliquent ces règles à la lettre : GET /repos/{proprio}/{repo}/issues, POST /v1/customers, GET /v1/customers/{id}/invoices. Des noms au pluriel, une imbrication mesurée, des identifiants clairs : c'est précisément ce qui rend leur documentation si facile à parcourir : on devine les URL avant même de les lire.

Les bonnes pratiques de nommage

  • Minuscules et tirets pour les noms composés : /articles-archives, pas /articlesArchives ni /articles_archives.
  • Cohérence : si c'est /articles, alors /utilisateurs et /commandes — toujours le pluriel.
  • Pas d'extension (.json) dans l'URL : le format se négocie par l'en-tête Accept.
  • Les actions hors CRUD (rares) peuvent faire exception : POST /articles/42/publier est toléré quand l'opération n'est pas un simple create/update.

Le test du « devine l'URL »

Une bonne API passe ce test : si je connais /articles/42, je devine sans documentation que /articles liste tout, que /utilisateurs/7 existe, et que DELETE /articles/42 supprime. La régularité est la documentation. Chaque exception (un singulier ici, un verbe là) casse cette prévisibilité et force à consulter le manuel.

Antisèche : concevoir ses URL

Glossaire

Ressource
La « chose » exposée par l'API (un article, un utilisateur), désignée par une URL faite de noms.
Collection
L'ensemble des ressources d'un type, au pluriel : /articles.
Élément
Une ressource précise de la collection, identifiée : /articles/42.
Identifiant
La valeur qui distingue un élément dans sa collection (souvent un nombre ou un code unique).
Imbrication
Exprimer l'appartenance d'une ressource à une autre dans l'URL : /articles/42/commentaires.
Query string (filtre)
Paramètres après le ? pour filtrer ou aplatir : /commentaires?article=42. Alternative à une imbrication profonde.
Endpoint (point d'accès)
La combinaison verbe + URL exposée par l'API, par ex. GET /articles/42.
Convention
Règle de nommage appliquée uniformément (pluriel, minuscules, tirets) qui rend l'API devinable sans documentation.

Récap et vérification

  • L'URL désigne une ressource (un nom), jamais une action : pas de verbe dans l'URL.
  • Collection au pluriel (/articles) ; élément avec identifiant (/articles/42).
  • L'imbrication (/articles/42/commentaires) exprime l'appartenance ; pas plus de deux niveaux.
  • Nommage : minuscules, tirets, pluriel cohérent, pas d'extension de format.

Vérifie ta compréhension

  1. Pourquoi POST /createArticle est-il une mauvaise URL ?
  2. Quelle URL pour lister les commandes de l'utilisateur 7 ?
  3. Quand vaut-il mieux un filtre (?article=42) qu'une imbrication ?

Exercices

Exercice 1Échauffement

Corrige ces URL mal conçues : GET /getUser/3 et POST /addProduct.

Voir une solution

On retire les verbes des URL : noms au pluriel, l'action vient du verbe HTTP.

Exercice 2Application

Donne les URL et verbes pour : lister les avis du produit 12, et ajouter un avis à ce produit.

Voir une solution
Exercice 3Défi

Conçois les URL d'un blog avec articles, leurs commentaires, et des catégories. Montre comment lire un article, ses commentaires, et tous les articles d'une catégorie (en évitant une imbrication trop profonde).

Voir une solution

Les commentaires, qui appartiennent à un article, sont imbriqués (un seul niveau). Pour « les articles d'une catégorie », on évite /categories/tech/articles et on préfère un filtre sur la collection d'articles : plus souple et plus lisible.
