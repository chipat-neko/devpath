Module 3 · Robustesse — Leçon 06

Authentification, sécurité et bonnes pratiques

~35 min Avancé Leçon 05 requise

À la fin de cette leçon, tu sauras

  • authentifier avec une clé ou un jeton (Bearer/JWT) ;
  • appliquer les protections de base (HTTPS, validation, débit) ;
  • renvoyer des erreurs exploitables et documenter (OpenAPI) ;
  • situer GraphQL face à REST.
Sommaire de la leçon

Une API exposée sur Internet est, par nature, accessible à tous — y compris à des acteurs malveillants. La rendre sûre et robuste n'est pas optionnel. Cette dernière leçon rassemble les protections essentielles : prouver l'identité du client (authentification), se prémunir des entrées hostiles, et bien communiquer les erreurs. On la garde au niveau des principes : leur mise en œuvre précise relève de chaque langage et framework.

Authentifier le client

La plupart des API exigent de savoir qui appelle. Le client joint une preuve d'identité dans l'en-tête Authorization de chaque requête (rappel : REST est sans état, donc l'identité voyage à chaque appel). Deux formes courantes :

Une clé d'API est un secret long attribué à un client : simple, adaptée aux intégrations serveur-à-serveur. Un JWT (JSON Web Token) est un jeton signé qui encode l'identité et expire : le serveur vérifie la signature sans interroger de base, ce qui colle bien au caractère sans état de REST. Dans les deux cas : sans preuve valide → 401 ; preuve valide mais droits insuffisants → 403 (leçon 3).

Jamais le secret dans l'URL

Passer sa clé en query string (?api_key=abc123) la fait apparaître dans les journaux du serveur, l'historique du navigateur et l'en-tête Referer envoyé aux sites tiers. Le secret voyage toujours dans l'en-tête Authorization, jamais dans le chemin ni les paramètres.

Les protections de base

Quelques mesures couvrent l'essentiel des risques courants :

  • HTTPS partout : sans chiffrement du transport, jetons et données circulent en clair. C'est non négociable pour une API en production.
  • Valider toutes les entrées : ne jamais faire confiance au corps, aux paramètres ni aux en-têtes reçus. On valide types, longueurs et formats avant tout traitement (renvoyer 400/422 sinon).
  • Limiter le débit (rate limiting) : plafonner le nombre de requêtes par client et par minute, pour résister aux abus et aux attaques par force brute. Le statut dédié est 429 Too Many Requests.
  • Principe du moindre privilège : chaque jeton n'a que les droits strictement nécessaires ; ne jamais exposer plus que ce qu'il faut.

Ces réflexes recoupent les bonnes pratiques de sécurité web générales (injections, contrôle d'accès, secrets) : une API n'échappe à aucune d'elles. La règle directrice : ne jamais faire confiance à l'entrée, et exposer le minimum.

Le CORS

Si un front-end JavaScript sur monsite.com appelle ton API sur api.exemple.com, le navigateur applique une règle de sécurité : la même origine. Pour autoriser cet appel inter-origines, l'API doit renvoyer des en-têtes CORS indiquant quelles origines ont le droit de l'appeler.

Point de vigilance : n'autorise Access-Control-Allow-Origin: * (toutes origines) que pour une API publique en lecture seule. Pour une API authentifiée, déclare l'origine exacte de ton front : sinon n'importe quel site pourrait appeler ton API depuis le navigateur d'un utilisateur connecté.

Erreurs claires et documentation

Une bonne API échoue proprement : un statut juste (leçon 3) et un corps d'erreur structuré et constant, qui aide le client à comprendre et corriger.

Ne renvoie jamais de message d'erreur technique brut (trace, requête SQL) : c'est une fuite d'information exploitable. Logue le détail côté serveur, renvoie un message générique au client. Enfin, documente ton API avec OpenAPI (anciennement Swagger) : une description standard, lisible par les humains et les outils, qui génère docs interactives et clients automatiquement.

Cas réel

Les grandes plateformes empilent ces protections. GitHub plafonne le débit (5 000 requêtes/heure par jeton, exposées dans les en-têtes X-RateLimit-Remaining et X-RateLimit-Reset) et révoque automatiquement toute clé repérée dans un dépôt public (secret scanning). Stripe refuse toute requête en HTTP clair et n'accepte les clés qu'en en-tête. Le jour où un secret fuite malgré tout, l'exposition est ainsi bornée (débit limité) et détectée (scan) au lieu de passer inaperçue.

Et GraphQL ?

GraphQL est une alternative à REST : au lieu de multiples URL, une seule, où le client décrit précisément les champs qu'il veut. Avantage : il évite de sur-charger ou sous-charger les réponses (le client demande exactement ce dont il a besoin). Inconvénients : mise en cache plus complexe, courbe d'apprentissage, et risque de requêtes coûteuses. REST reste le choix par défaut pour sa simplicité et son alignement avec HTTP ; GraphQL brille quand les besoins en données sont très variables (clients multiples, mobiles).

Glossaire

Authentification
Prouver l'identité de l'appelant ; la preuve voyage dans l'en-tête Authorization à chaque requête (REST est sans état).
Clé d'API
Secret long attribué à un client, adapté aux intégrations serveur-à-serveur.
JWT
JSON Web Token : jeton signé qui encode l'identité et expire ; vérifiable sans interroger de base.
HTTPS
HTTP chiffré (TLS) : rend illisibles jetons et données en transit. Non négociable en production.
Rate limiting
Limitation du débit : plafonner les requêtes par client et par minute ; dépassement → 429 Too Many Requests.
CORS
En-têtes qui autorisent (ou non) un front d'une autre origine à appeler l'API ; éviter * sur une API authentifiée.
OpenAPI
Format standard (ex-Swagger) décrivant une API ; génère documentation interactive et clients.
GraphQL
Alternative à REST : une seule URL où le client décrit les champs voulus ; brille quand les besoins en données varient.

Récap et vérification

  • Le client s'authentifie via Authorization: Bearer … : clé d'API ou JWT (signé, expirable, sans état).
  • Protections : HTTPS, valider toute entrée, limiter le débit (429), moindre privilège.
  • CORS : autoriser explicitement l'origine du front ; éviter * sur une API authentifiée.
  • Erreurs structurées (jamais de détail technique brut) ; documenter avec OpenAPI. GraphQL = alternative pour des besoins variables.

Vérifie ta compréhension

  1. Dans quel en-tête le client envoie-t-il sa preuve d'identité, et que renvoie-t-on sans elle ?
  2. Pourquoi éviter Access-Control-Allow-Origin: * sur une API authentifiée ?
  3. Pourquoi ne pas renvoyer un message d'erreur technique brut ?

Par exemple : 1) HTTPS partout (chiffrer le transport) ; 2) valider toutes les entrées (corps, paramètres, en-têtes) avant traitement ; 3) limiter le débit (rate limiting, 429) pour résister aux abus. Exercice 3Défi

Un client envoie un e-mail au format invalide lors d'une création. Décris la réponse idéale de l'API : statut et corps.

Voir une solution

On renvoie un statut 4xx précis (422 pour une validation échouée), avec un corps structuré qui nomme le champ fautif et le problème — assez pour que le client corrige, sans exposer de détail technique interne.
