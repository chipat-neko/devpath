Module 05 · API en pratique — Leçon 13

Tester une API

~36 min Intermédiaire Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • distinguer les niveaux de tests d'une API (unitaire, intégration, contrat, bout en bout) ;
  • écrire un test de route qui vérifie statut, corps et en-têtes ;
  • couvrir les cas d'erreur et pas seulement le « chemin heureux » ;
  • valider le contrat et automatiser la suite en intégration continue.
Sommaire de la leçon

Une API est un contrat entre des équipes qui, souvent, ne se parlent pas. Le jour où tu renommes un champ montant en total, ou renvoies 200 là où le client attendait 201, tu casses silencieusement tous ceux qui en dépendent — et tu ne le sauras qu'au support. Les tests automatisés sont le filet qui attrape ces régressions avant la mise en production. Cette leçon montre quoi tester dans une API et comment, du test d'une route jusqu'à l'automatisation en intégration continue.

Que tester, et à quel niveau ?

On teste par couches, des plus rapides et nombreuses aux plus lentes et rares. Les tests unitaires vérifient une fonction isolée (calcul d'un total, validation d'un e-mail), sans réseau. Les tests d'intégration lancent l'application et frappent une vraie route HTTP, base de test incluse. Les tests de contrat vérifient que les réponses respectent le schéma annoncé (leçon 10, OpenAPI). Enfin, les tests de bout en bout (E2E) parcourent un scénario complet à travers plusieurs services.

Un test de route, de bout en bout

Un test d'intégration d'API suit le patron Arrange / Act / Assert : on prépare l'état (données, authentification), on envoie une requête, puis on vérifie la réponse — statut, corps et en-têtes. Des outils comme supertest (Node), pytest + requests (Python) ou REST Assured (Java) démarrent l'app en mémoire et jouent de vraies requêtes HTTP.

Ne teste pas que le « chemin heureux »

La tentation est de ne tester que le cas idéal. Or une API passe son temps à refuser (leçon 11) : ces refus font partie du contrat et doivent être testés autant que les succès. Vérifie le 404 sur une ressource absente, le 401 sans jeton, le 403 sans droit, le 422 sur une entrée invalide — et que le corps d'erreur a la bonne forme.

Astuce — un cas de test par comportement observable

Pense en termes de comportements visibles du client, pas de lignes de code : « créer sans droit renvoie 403 », « paginer au-delà de la dernière page renvoie une liste vide, pas une erreur », « deux POST identiques avec une clé d'idempotence ne créent qu'une ressource ». Chaque comportement du contrat = un test. C'est aussi une documentation vivante : en lisant les tests, on apprend comment l'API réagit.

Tester le contrat, pas seulement un exemple

Vérifier rep.body.id === 1 teste une valeur, pas la forme générale des réponses. Le test de contrat valide chaque réponse contre le schéma déclaré (JSON Schema issu de ta spec OpenAPI). Ainsi, si un champ obligatoire disparaît ou change de type, le test échoue — même si l'exemple précis passait. C'est le rempart contre les breaking changes involontaires.

Isoler les dépendances, puis automatiser

Un test doit être rapide, déterministe et sans effet de bord dans le monde réel. On ne frappe donc pas les vraies dépendances externes (passerelle de paiement, service d'e-mail) : on les remplace par des doublures (mocks) ou on utilise leur bac à sable. Une fois la suite fiable, on l'exécute automatiquement à chaque push, en intégration continue : aucune fusion ne passe si un test casse.

Attention — ne fais pas dépendre tes tests d'un service tiers réel

Appeler la vraie API de paiement dans tes tests, c'est se condamner à des échecs intermittents (le réseau, la panne du tiers), à des coûts et parfois à de vrais débits. Pire, un test qui écrit dans une base partagée devient flaky et pollue les autres. Chaque test doit partir d'un état connu (base de test réinitialisée, dépendances simulées) pour être reproductible.

Cas réel — la collection Postman qui tourne en CI

Beaucoup d'équipes conçoivent leurs requêtes dans Postman pendant le développement, avec des tests attachés à chaque requête (pm.expect(...)). Ces collections ne restent pas des jouets manuels : exportées, elles sont rejouées en CI par Newman (le lanceur en ligne de commande de Postman). Une équipe avait ainsi une route GET /factures qui renvoyait un jour montant en centimes, le lendemain en euros, selon un refactor. Le test de contrat en CI a bloqué la fusion avant que le client de facturation ne facture cent fois trop cher. Le test a coûté cinq minutes à écrire ; le bug évité, bien davantage.

Pour aller plus loin

Le contract testing piloté par le consommateur (outil Pact) laisse le client déclarer ses attentes ; le serveur prouve qu'il les respecte, sans environnement partagé. Le fuzzing d'API (ex. schemathesis, qui génère des requêtes à partir de la spec OpenAPI) déniche des cas d'erreur oubliés. Enfin, les tests de charge (k6, Locust) ne vérifient pas la justesse mais la tenue en charge : latence et taux d'erreur sous un trafic réaliste.

Récap et vérification

  • On teste par couches : beaucoup d'unitaires rapides, un socle d'intégration (frapper la route), des tests de contrat, quelques E2E.
  • Un test de route suit Arrange / Act / Assert et vérifie statut + corps + en-têtes.
  • Couvre les cas d'erreur (401, 403, 404, 422) autant que le chemin heureux.
  • Valide le contrat contre le schéma OpenAPI, isole les dépendances externes, et automatise la suite en CI.

Glossaire

Test d'intégration
Test qui exerce une vraie route HTTP de l'application (avec sa base de test), et non une fonction isolée.
Test de contrat
Test qui vérifie que les requêtes et réponses respectent le schéma convenu (souvent OpenAPI), pour prévenir les changements cassants.
Arrange / Act / Assert
Structure d'un test en trois temps : préparer l'état, exécuter l'action, vérifier le résultat.
Assertion
Affirmation vérifiable dans un test (par ex. « le statut vaut 201 ») ; si elle est fausse, le test échoue.
Doublure (mock)
Objet ou service de remplacement simulant une dépendance externe, pour rendre le test rapide et déterministe.
supertest
Bibliothèque Node qui démarre l'application et joue de vraies requêtes HTTP contre ses routes.
Newman
Lanceur en ligne de commande de Postman, qui rejoue une collection de requêtes et ses tests en intégration continue.
Test flaky
Test au résultat instable (tantôt vert, tantôt rouge) sans changement de code, souvent dû à une dépendance réseau ou à un état partagé.

Vérifie ta compréhension

  2. Pourquoi tester les cas d'erreur (404, 401, 422) et pas seulement les succès ?
  3. En quoi un test de contrat diffère-t-il d'un test qui vérifie une valeur précise du corps ?
