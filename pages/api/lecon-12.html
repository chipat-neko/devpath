Module 05 · API en pratique — Leçon 12

Notifier avec les webhooks

~35 min Intermédiaire Leçon 08 recommandée

À la fin de cette leçon, tu sauras

  • expliquer ce qu'est un webhook et en quoi il inverse le polling ;
  • décrire le cycle de vie d'un événement : abonnement, envoi, accusé de réception ;
  • vérifier l'authenticité d'un webhook grâce à une signature HMAC ;
  • concevoir un endpoint récepteur fiable : réponse rapide, idempotence, rejeux.
Sommaire de la leçon

Jusqu'ici, c'est toujours le client qui interroge l'API : « donne-moi les commandes », « ce paiement est-il validé ? ». Mais comment réagir à un événement qui survient chez le serveur, à un moment imprévisible — un paiement accepté, un fichier fini d'encoder, un livreur qui bouge ? La réponse naïve consiste à redemander sans cesse (« c'est bon ? et maintenant ? et maintenant ? »). C'est le polling, et c'est du gaspillage. Les webhooks renversent la logique : le serveur rappelle le client dès que quelque chose arrive.

Le problème : savoir « quand »

En polling, le client répète une requête à intervalle régulier pour détecter un changement. Si l'événement est rare, l'écrasante majorité des appels renvoient « rien de neuf » : bande passante, quota et latence gaspillés. Trop espacé, le client réagit tard ; trop rapproché, il matraque l'API. Un webhook supprime le dilemme : zéro appel tant qu'il ne se passe rien, notification immédiate quand l'événement survient.

Note — « HTTP callback », « reverse API »

Un webhook n'est rien d'autre qu'une requête HTTP ordinaire (le plus souvent un POST avec un corps JSON) envoyée par le service source vers une URL que tu as fournie. On parle aussi de HTTP callback ou d'API « à l'envers » : cette fois, c'est ton application qui joue le rôle de serveur et reçoit la requête.

Le cycle de vie d'un événement

Un webhook suit toujours les mêmes étapes. D'abord un abonnement : tu déclares au service une URL de rappel (le endpoint) et les types d'événements qui t'intéressent (paiement.reussi, commande.expediee…). Ensuite, quand l'événement survient, le service construit un payload (les données de l'événement) et l'envoie en POST. Ton endpoint répond alors par un accusé de réception : un code 2xx signifie « reçu, je m'en occupe ».

Remarque les en-têtes : X-Event-Id identifie l'événement de façon unique (clé pour l'idempotence, voir plus bas), X-Event-Type évite de fouiller le corps pour router, et X-Signature prouve l'origine.

Sécuriser : vérifier la signature

Ton endpoint est une URL publique : n'importe qui peut lui envoyer un faux POST « paiement réussi » et déclencher une livraison gratuite. Il faut donc prouver que la requête vient bien du service attendu. La méthode standard est la signature HMAC : à l'abonnement, le service et toi partagez un secret. Pour chaque envoi, le service calcule une empreinte HMAC-SHA256 du corps avec ce secret et la place dans un en-tête. À la réception, tu recalcules la même empreinte : si elle correspond, le corps est authentique et intact.

Attention — signe le corps BRUT, et compare en temps constant

Calcule la signature sur les octets exacts reçus, avant tout parsing : si tu fais JSON.parse puis re-sérialises, l'ordre des clés ou les espaces peuvent changer et la signature ne collera plus. Beaucoup de frameworks exposent un raw body pour ça. Compare ensuite avec une fonction à temps constant (timingSafeEqual) et non ===, pour ne pas révéler la signature attendue caractère par caractère via le temps de réponse.

Fiabilité : livraison « au moins une fois »

Le réseau est faillible : un webhook peut se perdre, arriver en retard, ou être livré deux fois. Les services sérieux garantissent une livraison at-least-once (au moins une fois) : si ton endpoint ne répond pas 2xx, ils réessaient avec un délai croissant (backoff). Conséquence directe : ton traitement doit être idempotent — recevoir deux fois le même événement ne doit pas créditer deux fois le compte. La parade : mémoriser l'id de l'événement (X-Event-Id) et ignorer ceux déjà traités. Ne suppose pas non plus que les événements arrivent dans l'ordre.

Astuce — réponds vite, traite ensuite

Le service source impose souvent un délai court (2 à 10 s) pour l'accusé. Ne fais donc pas le travail lourd (envoi d'e-mail, appels externes) avant de répondre. Le bon réflexe : valider la signature, enregistrer l'événement dans une file, répondre immédiatement 202 Accepted, puis traiter en asynchrone. Tu accuses réception en quelques millisecondes et tu évites les rejeux dus aux dépassements de délai.

Cas réel — les webhooks de Stripe et de GitHub

Stripe (paiements) envoie un événement checkout.session.completed à ton serveur quand un client paie : c'est ce webhook, et non la page de retour, qui doit déclencher la livraison — car l'utilisateur peut fermer l'onglet avant la redirection. Stripe signe chaque envoi (en-tête Stripe-Signature), réessaie pendant des jours en cas d'échec, et fournit un catalogue d'événements rejouables. GitHub fait pareil pour l'intégration continue : à chaque git push, un webhook push prévient ton service de CI, qui lance les tests. Dans les deux cas, la doc insiste : vérifie la signature et rends le traitement idempotent.

Pour aller plus loin

Pour standardiser le format des événements entre services, regarde CloudEvents (spécification CNCF : champs id, source, type, time…). Pour l'abonnement automatique et le passage à l'échelle sur le Web ouvert, WebSub (ex-PubSubHubbub) formalise le trio publisher / hub / subscriber. Et pour tester en local sans exposer ta machine, des tunnels (type ngrok) ou les CLI des fournisseurs (stripe listen) relaient les webhooks vers localhost.

Récap et vérification

  • Un webhook inverse le polling : au lieu de redemander, le client s'abonne et le serveur le rappelle (POST) quand un événement survient.
  • Cycle : abonnement (URL + types d'événements) → POST du payload → accusé 2xx ; sans 2xx, le service réessaie.
  • Sécurité : signature HMAC sur le corps brut, secret partagé, comparaison à temps constant.
  • Fiabilité : livraison at-least-once → traitement idempotent (clé = id d'événement), réponse rapide (202) puis travail asynchrone.

Glossaire

Webhook
Requête HTTP (souvent POST JSON) envoyée par un service vers une URL fournie par le client, pour le notifier d'un événement. Aussi appelé HTTP callback.
Polling
Technique où le client interroge l'API à intervalle régulier pour détecter un changement, au prix de nombreux appels inutiles.
Endpoint de rappel
URL publique exposée par le récepteur, que le service source appelle pour livrer l'événement.
Payload
Corps de la requête webhook : les données décrivant l'événement (identifiant, type, date, détails).
Signature HMAC
Empreinte cryptographique du corps calculée avec un secret partagé, prouvant l'origine et l'intégrité du message.
Livraison at-least-once
Garantie qu'un événement est livré au moins une fois, quitte à l'être plusieurs fois en cas de rejeu.
Idempotence
Propriété d'un traitement dont l'exécution répétée avec la même entrée produit le même effet qu'une seule exécution.
Backoff
Stratégie de rejeu où le délai entre deux tentatives augmente progressivement, pour ne pas saturer un récepteur en difficulté.

Vérifie ta compréhension

  1. En une phrase, quelle est la différence entre polling et webhook ?
  2. Pourquoi faut-il calculer la signature sur le corps brut plutôt que sur le JSON re-sérialisé ?
  3. Un service garantit une livraison « au moins une fois ». Quelle propriété ton traitement doit-il avoir, et comment l'obtenir ?
