Module 05 · API en pratique — Leçon 11

Gérer les erreurs proprement

~35 min Intermédiaire Leçon 03 recommandée

À la fin de cette leçon, tu sauras

  • choisir le bon code de statut selon la nature de l'erreur (4xx client, 5xx serveur) ;
  • renvoyer un corps d'erreur standard avec Problem Details (application/problem+json) ;
  • détailler les erreurs de validation champ par champ ;
  • garantir la cohérence sans fuiter d'informations sensibles.
Sommaire de la leçon

Une API passe une bonne partie de son temps à dire non : donnée manquante, droit refusé, ressource introuvable, panne interne. La qualité d'une API se mesure autant à ses erreurs qu'à ses succès. Une erreur bien faite indique quoi a échoué, pourquoi, et si l'on peut réessayer — le tout dans un format prévisible, pour que chaque client sache le traiter sans deviner.

À l'inverse, des erreurs incohérentes (un coup du texte, un coup du HTML, un coup un 200 déguisé) rendent les clients fragiles et truffés de rustines. Cette leçon fixe deux règles : le bon code de statut, et le bon corps.

Choisir le bon code de statut

Le code de statut HTTP est le premier mot de la réponse. La grande partition, vue au module 01 : les 4xx disent « c'est toi, le client, qui as un problème » (inutile de réessayer à l'identique), les 5xx disent « c'est moi, le serveur, qui ai échoué » (souvent transitoire). Encore faut-il choisir le bon 4xx : ne pas tout écraser sous un vague 400.

Note — 401 vs 403, une confusion classique

401 Unauthorized signifie en réalité « non authentifié » : le serveur ne sait pas qui tu es (jeton absent ou invalide) — connecte-toi. 403 Forbidden signifie « authentifié mais pas autorisé » : on sait qui tu es, mais tu n'as pas le droit. Le nom « Unauthorized » du 401 est un abus de langage historique de la norme HTTP ; retiens le sens, pas le mot.

Un corps d'erreur standard : Problem Details

Le code de statut ne suffit pas : un 422 nu n'explique pas quel champ pose problème. Il faut un corps. Plutôt que d'inventer son format, on utilise le standard Problem Details (RFC 9457), un objet JSON servi avec le type de contenu application/problem+json. Il définit cinq champs conventionnels : type (une URI identifiant la catégorie d'erreur), title (résumé lisible), status (le code HTTP répété), detail (explication de ce cas précis) et instance (l'URI concernée). On peut y ajouter ses propres extensions.

Astuce — détaille la validation champ par champ

Pour un formulaire, renvoyer un seul message global oblige l'utilisateur à corriger à l'aveugle. Une extension errors qui liste chaque champ fautif et sa raison permet à l'interface d'afficher l'erreur sous le bon champ. Renvoie toutes les erreurs d'un coup plutôt qu'une par une : l'utilisateur corrige tout en une passe.

La cohérence : un seul format, partout

La vraie valeur d'un format d'erreur vient de sa constance : le même schéma pour toutes les erreurs de l'API, de la validation à la panne. En pratique, on centralise : un gestionnaire d'erreurs unique attrape les exceptions et les traduit en problem+json, au lieu de laisser chaque route bricoler sa réponse. Le client, lui, n'écrit qu'un code de traitement d'erreur.

Attention — ne jamais renvoyer 200 pour une erreur, ni fuiter la trace

Deux fautes graves. 1) Répondre 200 OK avec { "success": false } : les clients (et les caches, et les outils) croient à un succès. Le code de statut est le signal d'erreur — utilise-le. 2) En production, ne mets jamais de stack trace, de requête SQL ou de chemin de fichier dans detail : c'est une fuite d'information exploitable. Message clair côté client, détails techniques dans les logs côté serveur, reliés par un identifiant de corrélation.

Cas réel — le 200 qui masquait les pannes

Une équipe expose une API qui, par « simplicité », répond toujours 200 OK avec un corps { "ok": false, "message": "..." } en cas d'erreur. Conséquences en cascade : le monitoring (qui compte les 5xx) ne voit aucune panne et n'alerte jamais ; les caches et CDN mettent en cache des « erreurs » comme des succès ; les clients mobiles affichent des écrans vides sans comprendre pourquoi. La migration vers de vrais codes de statut + problem+json a fait réapparaître les incidents dans les tableaux de bord — et permis, enfin, de les corriger. Le bon code de statut n'est pas un détail : c'est ce qui rend une panne visible.

Pour aller plus loin

Ajoute un code d'erreur métier stable (ex. "code": "STOCK_INSUFFISANT") en extension : contrairement au title traduisible, il ne change jamais et les clients peuvent brancher dessus une logique fiable. Un identifiant de corrélation (traceId) relie l'erreur vue par le client à la trace complète côté serveur (leçon d'observabilité). Enfin, la RFC 9457 remplace la RFC 7807 (même format, précisions ajoutées) : les deux media types application/problem+json restent compatibles.

Récap et vérification

  • Le code de statut classe l'erreur : 4xx côté client (401 non authentifié, 403 interdit, 404 absent, 400/422 invalide, 409 conflit), 5xx côté serveur.
  • Problem Details (RFC 9457, application/problem+json) standardise le corps : type, title, status, detail, instance + extensions.
  • Détaille la validation champ par champ (extension errors) pour un affichage précis côté client.
  • Cohérence via un gestionnaire central ; jamais de 200 pour une erreur, jamais de stack trace exposée en prod.

Glossaire

Code de statut
Nombre à trois chiffres résumant l'issue d'une requête HTTP ; les 4xx désignent une erreur du client, les 5xx une erreur du serveur.
Problem Details
Format standard (RFC 9457) d'objet d'erreur JSON pour les API HTTP, servi avec le type application/problem+json.
application/problem+json
Type de contenu (media type) signalant que le corps de la réponse est un objet Problem Details.
type (Problem Details)
URI identifiant la catégorie d'erreur ; sert de clé stable et peut pointer vers une page de documentation.
422 Unprocessable Content
Code indiquant que la requête est syntaxiquement correcte mais viole une règle de validation ou de métier.
Erreur de validation
Rejet d'une entrée non conforme aux règles attendues (champ manquant, format ou valeur invalide).
Gestionnaire d'erreurs
Point unique du serveur qui intercepte les exceptions et les convertit en réponses d'erreur cohérentes.
Identifiant de corrélation
Jeton (ex. traceId) rattaché à une requête, permettant de relier l'erreur vue par le client aux journaux du serveur.
