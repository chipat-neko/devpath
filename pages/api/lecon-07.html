Module 04 · API à l'échelle — Leçon 07

Authentification avancée (OAuth2, JWT)

~32 min Intermédiaire Cours API (L01-06) conseillé

À la fin de cette leçon, tu sauras

  • distinguer authentification et autorisation ;
  • comparer clés d'API, JWT et sessions ;
  • expliquer le principe d'OAuth 2.0 ;
  • gérer les refresh tokens et leurs pièges.
Sommaire de la leçon

La leçon 6 a posé les bases de la sécurité d'une API. Ce module « à l'échelle » approfondit la pièce maîtresse : qui a le droit d'appeler ton API, et comment le prouver de façon robuste. On clarifie d'abord deux mots qu'on confond souvent.

Authentification vs autorisation

  • L'authentification répond à « qui es-tu ? » — prouver son identité.
  • L'autorisation répond à « as-tu le droit ? » — vérifier les permissions sur une ressource.

Une API doit faire les deux : identifier l'appelant, puis vérifier qu'il a le droit pour chaque action. S'authentifier ne donne pas tous les droits ; on contrôle l'autorisation à chaque requête sensible.

Trois façons de s'authentifier

  • Clé d'API : un secret unique passé à chaque requête. Simple, adapté aux services (machine à machine), mais peu adapté aux utilisateurs (pas de notion d'identité fine, révocation globale).
  • Session + cookie : l'état est gardé côté serveur. Classique pour le web « traditionnel », moins pour des API consommées par des clients variés.
  • Jeton (token) JWT : un jeton autoporteur envoyé à chaque requête, très répandu pour les API modernes.

Le JWT : un jeton autoporteur

Un JWT (JSON Web Token) contient lui-même les informations utiles (l'identité de l'utilisateur, une date d'expiration) sous forme de JSON encodé, et il est signé par le serveur. Le serveur peut alors vérifier la signature à chaque requête sans consulter de base : le jeton se suffit à lui-même.

Signé ≠ chiffré

Un JWT est signé (on détecte toute modification) mais son contenu est seulement encodé, pas chiffré : n'importe qui peut le lire. On n'y met donc jamais de données sensibles. Et il faut vérifier la signature côté serveur — ne jamais faire confiance à un jeton non vérifié.

OAuth 2.0 : déléguer l'accès

OAuth 2.0 n'est pas une méthode de connexion, mais un protocole de délégation : il permet à une application d'obtenir un accès limité à une API au nom d'un utilisateur, sans connaître son mot de passe. C'est ce qui se passe quand tu cliques sur « Se connecter avec… » : tu autorises une appli à accéder à certaines données d'un service, pour un périmètre (scope) donné.

L'access token obtenu est souvent un JWT ; il a une durée de vie courte et un périmètre limité : même volé, son pouvoir et sa durée sont restreints.

Cas réel

Le bouton « Se connecter avec Google » (ou GitHub, Apple…) omniprésent est du pur OAuth 2.0 : le site tiers ne voit jamais ton mot de passe, seulement un access token limité au périmètre que tu as accepté — souvent juste ton nom et ton e-mail. C'est aussi pourquoi, depuis ton compte Google, tu peux révoquer d'un clic l'accès d'une application à laquelle tu ne fais plus confiance : tu invalides son autorisation sans changer ton mot de passe ni affecter les autres applis.

Les refresh tokens

Si l'access token expire vite (c'est voulu : limiter les dégâts en cas de vol), comment éviter de redemander la connexion toutes les 15 minutes ? Grâce au refresh token : un jeton à longue durée, gardé en sécurité, qui sert uniquement à obtenir un nouvel access token quand l'ancien expire.

Le refresh token est précieux

Comme il permet de fabriquer de nouveaux access tokens, le refresh token doit être stocké en sécurité (jamais accessible au JavaScript de la page : idéalement un cookie HttpOnly) et révocable côté serveur. Sa fuite est plus grave que celle d'un access token court.

Antisèche : identité et accès

Glossaire

Authentification
Prouver « qui tu es » (identité).
Autorisation
Vérifier « si tu as le droit » sur une ressource ; contrôlée à chaque requête sensible.
JWT (JSON Web Token)
Jeton autoporteur : JSON encodé (en-tête.charge_utile.signature) et signé, vérifiable sans consulter de base.
Signature
Empreinte qui garantit l'intégrité d'un JWT (détecte toute modification) — mais pas sa confidentialité : signé ≠ chiffré.
OAuth 2.0
Protocole de délégation : une appli obtient un accès limité au nom d'un utilisateur, sans connaître son mot de passe.
Scope (périmètre)
L'étendue exacte des droits accordés à un jeton (ex. : lire les photos, en lecture seule).
Access token
Jeton à courte durée envoyé à chaque requête ; souvent un JWT à périmètre limité.
Refresh token
Jeton à longue durée, gardé en sécurité, servant uniquement à obtenir un nouvel access token.

Récap et vérification

  • Authentification = « qui es-tu ? » ; autorisation = « as-tu le droit ? » (vérifiée à chaque requête).
  • Clé d'API (services), session (web), JWT autoporteur (API modernes) — JWT signé mais lisible : pas de secret dedans.
  • OAuth 2.0 délègue un accès limité sans partager le mot de passe (« Se connecter avec… »).
  • Access token court + refresh token long (et bien protégé) = sécurité + confort.

Exercices

Exercice 1Échauffement

Pour chaque cas, choisis « clé d'API » ou « OAuth 2.0 » : (a) un service de paiement appelle ton API serveur à serveur ; (b) une application veut accéder, au nom d'un utilisateur, à ses photos sur un autre service.

Voir une solution

(a) un service appelant ton API serveur à serveur (machine à machine) → clé d'API : il n'y a pas d'utilisateur humain ni de délégation, juste deux services qui se font confiance via un secret partagé. La clé d'API est simple et adaptée à ce cas (on la garde secrète côté serveur, on peut la révoquer). (b) une application accédant aux photos d'un utilisateur hébergées sur un autre service, en son nom → OAuth 2.0 : c'est exactement le scénario de délégation pour lequel OAuth existe. L'utilisateur autorise l'appli à accéder à un périmètre précis (ses photos, en lecture seule par exemple) sur le service tiers, sans jamais donner son mot de passe à l'appli. L'appli obtient un access token limité. La règle : clé d'API pour l'authentification service↔service sans utilisateur ; OAuth 2.0 dès qu'il s'agit d'agir au nom d'un utilisateur sur un service tiers, avec consentement et périmètre.

Exercice 2Application

Un développeur stocke le numéro de carte bancaire de l'utilisateur dans la charge utile d'un JWT « parce que c'est pratique à relire ». Pourquoi est-ce une grave erreur ?

Voir une solution

C'est une faute de sécurité majeure car un JWT n'est pas chiffré : son contenu (l'en-tête et la charge utile) est seulement encodé en Base64, un format réversible et lisible par n'importe qui. Il suffit de copier le jeton (qui circule à chaque requête, et est souvent stocké côté client) et de le décoder — aucun outil spécial, aucune clé n'est nécessaire — pour lire en clair tout ce qu'il contient, y compris ce numéro de carte. La signature du JWT ne protège que l'intégrité (elle permet de détecter une modification du contenu), pas la confidentialité : signé ne veut pas dire secret. Conséquences : fuite de données sensibles à la moindre interception ou consultation du stockage local, violation des règles de protection des données (et, pour une carte bancaire, des normes type PCI-DSS), responsabilité juridique. La règle : on ne met dans un JWT que des informations non sensibles et utiles à l'autorisation — un identifiant d'utilisateur, un rôle, une date d'expiration —, jamais un mot de passe, un numéro de carte, un secret ou des données personnelles confidentielles. Les données sensibles restent côté serveur (en base, chiffrées si nécessaire) et ne sont récupérées qu'au besoin, via une requête authentifiée ; le JWT sert seulement à prouver qui fait la demande. « Pratique à relire » n'est jamais une raison de stocker un secret dans un conteneur lisible par tous.

Exercice 3Défi

Pourquoi utiliser un access token à courte durée plus un refresh token, plutôt qu'un seul jeton à très longue durée ? Quel compromis cela résout-il ?

Voir une solution

Le couple access token court + refresh token long résout un compromis fondamental entre sécurité et confort que ne peut pas régler un jeton unique. Le problème d'un seul jeton à très longue durée : il est utilisé à chaque requête, donc il circule beaucoup et risque d'être intercepté ou volé (depuis le stockage du client, un log, un réseau mal sécurisé…). S'il a une durée de vie longue, un attaquant qui le vole obtient un accès durable ; et comme un JWT est typiquement vérifié sans consulter de base, il est difficile à révoquer avant son expiration. À l'inverse, un jeton unique à courte durée serait sûr mais insupportable à l'usage : l'utilisateur devrait se reconnecter toutes les quelques minutes. La solution à deux jetons : l'access token est court (ex. 15 min) et c'est lui qui circule à chaque requête : s'il est volé, le pouvoir de l'attaquant expire vite, limitant fortement les dégâts. Le refresh token est long mais n'est presque jamais transmis : il sert uniquement, de temps en temps, à demander un nouvel access token quand l'ancien expire ; on le stocke en sécurité (idéalement un cookie HttpOnly inaccessible au JavaScript) et on le rend révocable côté serveur (on peut invalider la session en cas de vol détecté, de déconnexion, etc.). Le résultat : l'utilisateur reste connecté confortablement (le renouvellement est transparent), tout en minimisant la fenêtre d'exploitation d'un access token volé et en gardant la possibilité de couper l'accès via le refresh token. On a donc à la fois la sécurité (exposition courte du jeton de tous les jours, révocabilité) et le confort (pas de reconnexion permanente) — un équilibre qu'un jeton unique, court ou long, ne peut pas atteindre. C'est pourquoi ce schéma est devenu le standard des API et d'OAuth 2.0.
