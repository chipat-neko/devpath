Module 04 · API à l'échelle — Leçon 09

Au-delà de REST (GraphQL, gRPC, WebSockets)

~36 min Intermédiaire Leçon 08 conseillée

À la fin de cette leçon, tu sauras

  • situer les limites de REST ;
  • expliquer GraphQL, gRPC et WebSockets ;
  • comparer leurs forces et leurs cas d'usage ;
  • choisir le bon outil selon le besoin.
Sommaire de la leçon

REST est un excellent choix par défaut, et le restera pour la plupart des API. Mais il a des limites dans certains contextes, et d'autres approches y répondent. Comprendre ces alternatives — et surtout quand les choisir — fait partie du niveau confirmé.

Les limites de REST

  • Sur-récupération / sous-récupération : un endpoint renvoie un objet fixe. Le client reçoit parfois trop de champs (gaspillage), ou doit faire plusieurs requêtes pour assembler ce dont il a besoin.
  • Pas de temps réel : REST est un modèle requête → réponse. Le serveur ne peut pas pousser spontanément une information au client (notifications, mises à jour en direct).
  • Verbosité entre services : pour des communications internes très fréquentes (microservices), le texte JSON sur HTTP/1.1 peut être moins efficace que des formats binaires.

GraphQL : le client choisit les données

Avec GraphQL (qui a son propre cours), il n'y a souvent qu'un seul point d'entrée : le client envoie une requête décrivant exactement les champs voulus, et reçoit précisément cela — ni plus, ni moins. Cela règle la sur/sous-récupération.

Pas magique pour autant

GraphQL apporte de la flexibilité côté client, mais déplace de la complexité côté serveur (résolveurs, requêtes coûteuses à maîtriser, cache moins simple que le cache HTTP de REST). C'est un excellent choix quand les clients ont des besoins de données variés, pas une obligation.

Cas réel

GitHub a ouvert en 2016 une API GraphQL (v4) à côté de son API REST (v3). La raison : les intégrations — surtout mobiles — devaient enchaîner de nombreux appels REST pour composer un seul écran (un dépôt, ses issues, leurs auteurs, les labels…), en récupérant au passage des quantités de champs inutiles. Avec GraphQL, une seule requête décrit l'arbre de données voulu ; l'application devient plus rapide et plus sobre en données mobiles. GitHub n'a pas supprimé REST pour autant : les deux coexistent, chacun pour ses usages — l'illustration parfaite du « on choisit par besoin ».

gRPC : rapide entre services

gRPC est conçu pour la communication service à service très performante. Il s'appuie sur HTTP/2 et un format binaire compact (Protocol Buffers), avec un contrat fortement typé défini à l'avance. Résultat : rapide et économe, idéal entre microservices internes. En revanche, c'est moins pratique pour un usage direct depuis un navigateur, et moins « lisible » que JSON.

WebSockets : le temps réel bidirectionnel

Pour du temps réel (chat, notifications, cours de bourse, position en direct, collaboration), il faut que le serveur puisse pousser des données au client sans attendre une requête. Les WebSockets ouvrent un canal permanent et bidirectionnel : une fois la connexion établie, client et serveur s'envoient des messages dans les deux sens, à tout moment.

Un canal ouvert a un coût

Un WebSocket maintient une connexion vivante par client : cela consomme de la mémoire côté serveur, complique la montée en charge (répartir des connexions persistantes entre plusieurs serveurs est plus délicat que des requêtes indépendantes) et oblige à gérer les reconnexions. Pour un rafraîchissement occasionnel, un simple appel REST périodique suffit ; on réserve les WebSockets au vrai temps réel.

Pour aller plus loin

Le WebSocket n'est pas la seule voie du temps réel. Quand le serveur doit seulement pousser (sans réponse du client), les Server-Sent Events (SSE) offrent un flux unidirectionnel plus simple, bâti sur du HTTP ordinaire (idéal pour un fil d'actualité ou une barre de progression). Côté services, gRPC-Web permet d'appeler du gRPC depuis un navigateur, et tRPC apporte, en TypeScript, un typage de bout en bout sans schéma séparé.

Antisèche : REST et ses alternatives

Glossaire

GraphQL
Langage de requête pour API où le client décrit précisément les champs voulus ; un unique point d'entrée renvoie une réponse sur mesure, évitant la sur/sous-récupération.
Résolveur
Fonction côté serveur GraphQL qui sait produire la valeur d'un champ ; l'ensemble des résolveurs relie le schéma aux données réelles.
Sur-récupération (over-fetching)
Recevoir plus de champs que nécessaire parce que l'endpoint renvoie un objet fixe ; la sous-récupération, à l'inverse, oblige à multiplier les appels.
gRPC
Cadre d'appel de procédure à distance, binaire et fortement typé, bâti sur HTTP/2 ; taillé pour la communication rapide entre services internes.
Protocol Buffers
Format binaire compact et typé utilisé par gRPC ; le contrat .proto définit messages et services et génère le code des deux côtés.
HTTP/2
Version du protocole HTTP permettant le multiplexage (plusieurs échanges sur une même connexion) et un transport binaire ; socle de gRPC.
WebSocket
Canal réseau permanent et bidirectionnel entre client et serveur ; une fois ouvert, chacun envoie des messages à tout moment (temps réel).
Server-Sent Events (SSE)
Flux unidirectionnel du serveur vers le client sur HTTP ordinaire ; plus simple qu'un WebSocket quand seul le serveur doit pousser.

Récap et vérification

  • Limites de REST : sur/sous-récupération, pas de temps réel, verbosité entre services.
  • GraphQL : le client demande exactement les champs voulus (besoins de données variés).
  • gRPC : binaire sur HTTP/2, rapide entre microservices.
  • WebSockets : canal bidirectionnel permanent pour le temps réel. On choisit par besoin, on peut combiner.

Exercices

Exercice 1Échauffement

Pour chaque besoin, choisis l'approche la plus adaptée : (a) une API publique de gestion de tâches (CRUD) ; (b) une messagerie instantanée ; (c) deux microservices internes qui s'appellent des milliers de fois par seconde ; (d) une application mobile qui veut, pour chaque écran, juste les champs précis dont il a besoin.

Voir une solution

(a) une API publique CRUD → REST : simple, standard, universel, bien outillé (et le cache HTTP fonctionne) — le choix par défaut idéal. (b) une messagerie instantanée → WebSockets : il faut du temps réel bidirectionnel (recevoir les messages des autres sans recharger), ce que REST ne permet pas (pas de push). (c) deux microservices internes très sollicités → gRPC : binaire et rapide sur HTTP/2, parfait pour des appels internes fréquents où la performance prime et où la lisibilité publique n'importe pas. (d) une app mobile voulant des champs précis par écran → GraphQL : le client demande exactement ce dont il a besoin, évitant la sur-récupération (économie de bande passante, précieuse sur mobile) et les allers-retours multiples. On voit que le « bon » choix découle directement du besoin ; et une même plateforme pourrait très bien utiliser les quatre, chacun à sa place.

Exercice 2Application

Un développeur affirme : « REST est dépassé, il faut tout passer en GraphQL. » Que lui réponds-tu de façon nuancée ?

Voir une solution

Que c'est une simplification trompeuse. GraphQL n'est pas « mieux que REST » dans l'absolu : c'est un outil différent, avec ses propres compromis. Ce que GraphQL apporte vraiment : une grande flexibilité côté client (demander exactement les champs voulus, en une requête), précieuse quand des clients variés (web, mobile, partenaires) ont des besoins de données différents ou quand on veut éviter la multiplication d'endpoints. Mais ce qu'il coûte : il déplace la complexité côté serveur (écrire et optimiser les résolveurs, maîtriser les requêtes potentiellement coûteuses ou imbriquées qu'un client peut formuler, gérer la sécurité de requêtes arbitraires) ; le cache y est plus délicat que le cache HTTP simple et éprouvé de REST (Cache-Control, ETag, 304) ; et l'outillage/monitoring diffère. REST, de son côté, reste excellent pour la majorité des cas : CRUD standard, API publiques, simplicité, universalité, cache HTTP gratuit, immense écosystème. Il n'est pas « dépassé » : il est mûr et adapté à énormément de situations. La bonne posture : ne pas raisonner en « ancien vs moderne » (un travers — le cargo-cult de la nouveauté), mais en besoin. On choisit GraphQL si le problème qu'il résout (besoins de données hétérogènes, sur-récupération coûteuse) se pose réellement ; sinon, REST fait très bien le travail avec moins de complexité. Et « tout passer en GraphQL » impliquerait un coût de migration et d'apprentissage qui n'est justifié que si le bénéfice est réel. Conclusion : REST et GraphQL coexistent ; on évalue au cas par cas, voire on les combine. La maturité technique, c'est de choisir l'outil adapté au problème — pas d'adopter le dernier à la mode par principe.

Exercice 3Défi

Synthèse du module « API à l'échelle » : une équipe lance une API REST simple qui rencontre le succès, puis fait face à : (1) des pics de trafic qui saturent le serveur, (2) des doubles paiements lors de réessais, (3) une app mobile qui se plaint de trop de requêtes et de données inutiles, (4) un besoin de notifications en direct. Quels outils des leçons 7-8-9 réponds à chaque problème ?

Voir une solution

Chaque problème correspond à un mécanisme vu dans le module : (1) Pics de trafic qui saturent le serveur → plusieurs leviers de la leçon 8. D'abord le cache HTTP (Cache-Control, ETag/304) pour ne pas recalculer/retransmettre les données lues souvent et changeant peu — ça soulage massivement le serveur. Ensuite le rate limiting (429 + Retry-After) pour empêcher qu'un client (ou un bot) monopolise les ressources et garantir l'équité ; c'est aussi une protection contre les abus/DoS. (2) Doubles paiements lors de réessais → l'idempotence (leçon 8) : une clé d'idempotence sur la création de paiement garantit qu'un même ordre, rejoué (double clic, réessai réseau), ne débite qu'une fois ; côté client, un réessai discipliné (backoff exponentiel + jitter, et uniquement pour des opérations sûres) évite d'aggraver les choses. (3) App mobile : trop de requêtes et de données inutiles → c'est exactement la sur/sous-récupération de REST : GraphQL (leçon 9) laisse le mobile demander pile les champs voulus en une requête, économisant bande passante et allers-retours ; à défaut de migrer, on peut aussi améliorer la pagination (par curseur, leçon 8, plus stable) et proposer des champs/inclusions optionnels. (4) Notifications en direct → les WebSockets (leçon 9) : un canal bidirectionnel permanent permet au serveur de pousser les notifications instantanément, ce que le modèle requête→réponse de REST ne permet pas. En complément transversal : l'authentification avancée (leçon 7 — OAuth2/JWT, access token court + refresh token) sécurise tout cela proprement à mesure que l'API grandit et expose plus de fonctionnalités. Le fil rouge du module : passer d'« une API REST qui marche » à « une API qui tient à l'échelle » — performante (cache, pagination efficace), fiable (rate limiting, idempotence, réessais propres), sûre (auth robuste) et capable de dépasser REST là où c'est justifié (GraphQL pour la flexibilité, gRPC en interne, WebSockets pour le temps réel). On ne change pas tout d'un coup ni par mode : on applique le bon mécanisme au bon problème, au fur et à mesure que les besoins réels apparaissent.
