Migrations et évolution du schéma

~36 min Avancé Leçon 11 (DDL) recommandée

À la fin de cette leçon, tu sauras

  • versionner le schéma comme du code avec des migrations ordonnées et immuables ;
  • écrire une migration up (et sa down) et suivre l'état avec une table de versions ;
  • distinguer un changement rétro-compatible d'un changement cassant ;
  • déployer un renommage sans interruption grâce au patron expand/contract et au backfill.
Sommaire de la leçon

Le schéma n'est jamais figé : on ajoute une colonne, une table, un index. La question n'est pas comment écrire l'ALTER TABLE (leçon 11 l'a montré), mais comment propager ce changement partout de la même façon : sur ta machine, celle des coéquipiers, la base de test de la CI, et la production — sans oublier une étape ni casser l'application en vol. La réponse : traiter les changements de schéma comme du code versionné, appelé migrations.

Le problème : garder toutes les bases synchronisées

Appliquer un ALTER TABLE à la main dans un client SQL fonctionne… une fois, sur une base. Multiplie par cinq environnements et trois personnes : quelqu'un oublie, la CI diverge, la prod plante au prochain déploiement. Une migration est un fichier numéroté, rangé dans le dépôt Git à côté du code, qui décrit un changement. Un outil les applique dans l'ordre et note lesquels ont déjà tourné.

Une migration = un fichier ordonné et immuable

Chaque migration a une partie up (appliquer le changement) et, idéalement, une partie down (le défaire). Une fois qu'une migration a été appliquée ailleurs qu'en local — surtout en prod — elle est immuable : on ne la réécrit pas, on en crée une nouvelle.

Piège fréquent

Ne jamais modifier une migration déjà appliquée en production. Les autres bases l'ont déjà exécutée ; la corriger crée une divergence silencieuse (leur schéma ne correspondra plus au fichier). Une erreur se répare par une nouvelle migration qui vient après. Les migrations forment un historique, pas un brouillon.

Note — les outils, un par écosystème

Le principe est universel ; chaque monde a son outil : Flyway et Liquibase (Java), Alembic (Python/SQLAlchemy), Prisma Migrate et Knex (Node), les migrations Rails et Django. Tous font la même chose : un dossier de fichiers ordonnés + une table de suivi + une commande migrate. Apprends le concept une fois, tu les retrouves partout.

Rétro-compatible ou cassant ?

Un changement est rétro-compatible si l'ancienne version de l'application continue de fonctionner avec le nouveau schéma. C'est crucial : pendant un déploiement progressif, l'ancien et le nouveau code tournent en même temps quelques minutes. La migration passe avant le code ; l'ancien code doit survivre au nouveau schéma.

Le patron expand/contract

Comment renommer nom en nom_complet sans jamais couper le service ? On n'échange pas la colonne d'un coup. On élargit (expand), on migre, puis on resserre (contract), en plusieurs déploiements :

Astuce — backfill par lots

Un UPDATE qui touche des millions de lignes d'un coup verrouille longtemps et gonfle le journal de transactions. Découpe-le en tranches (par plage d'id, par exemple 10 000 lignes), avec une pause entre chaque. La production respire, et une interruption ne perd que le lot en cours.

Créer un index sans bloquer

Sur une grosse table, un CREATE INDEX classique verrouille les écritures le temps de la construction — parfois de longues minutes. PostgreSQL propose CREATE INDEX CONCURRENTLY, qui construit l'index sans bloquer les écritures (plus lent, mais transparent pour les utilisateurs).

Cas réel

Une équipe qui déploie plusieurs fois par jour voulait renommer email en email_pro. Version naïve : une migration RENAME COLUMN juste avant le déploiement. Résultat : pendant les 90 secondes où les anciens serveurs cohabitaient avec les nouveaux, l'ancien code cherchait email, disparu : vague de 500, alertes, rollback en catastrophe. Rejoué en expand/contract sur trois déploiements successifs — ajout + double écriture, backfill + bascule des lectures, suppression une semaine plus tard — le renommage est passé sans un seul incident. C'est le mode de fonctionnement standard des grandes plateformes en déploiement continu.

Pour aller plus loin

Deux styles de gestion : impératif (tu écris chaque migration, façon Flyway/Alembic) ou déclaratif (tu décris le schéma cible, l'outil calcule le diff, façon Prisma). Ajoute des vérifications : rejouer toutes les migrations sur une base vide en CI, tester la down, et bloquer les changements cassants par revue. Enfin, garde les migrations de schéma (DDL) séparées des migrations de données lourdes.

Antisèche

Glossaire

Migration
Fichier versionné et ordonné décrivant un changement de schéma, appliqué de façon reproductible sur toutes les bases.
up / down
Les deux sens d'une migration : up applique le changement, down le défait (retour arrière).
schema_migrations
Table de suivi où l'outil note les migrations déjà appliquées, pour ne jamais les rejouer.
Rétro-compatible
Se dit d'un changement de schéma avec lequel l'ancienne version du code continue de fonctionner.
Changement cassant
Modification (renommage, suppression, NOT NULL sans défaut) qui fait échouer l'ancienne version du code.
Expand/contract
Patron en trois temps (élargir, migrer, resserrer) pour transformer un schéma sans interruption de service.
Backfill
Remplissage des lignes existantes après l'ajout d'une colonne, idéalement par lots pour ne pas bloquer la base.
CREATE INDEX CONCURRENTLY
Variante PostgreSQL qui construit un index sans verrouiller les écritures de la table.

Récap et vérification

  • Une migration = un fichier ordonné, versionné dans Git, immuable une fois appliqué ailleurs ; la table de suivi évite de le rejouer.
  • Corriger une migration passée = en écrire une nouvelle, jamais réécrire l'ancienne.
  • Un changement rétro-compatible (ajout) laisse tourner l'ancien code ; un renommage/suppression d'un coup est cassant.
  • Le patron expand/contract (élargir, migrer, resserrer) renomme ou supprime sans coupure, en plusieurs déploiements.
  • Remplis les grosses tables par backfill en lots ; indexe-les avec CONCURRENTLY pour ne pas bloquer.

Vérifie ta compréhension

  1. Pourquoi ne faut-il jamais réécrire une migration déjà appliquée en production ?
  2. Pourquoi ADD COLUMN … DEFAULT est-il rétro-compatible mais RENAME COLUMN ne l'est pas ?
  3. Quelles sont les trois étapes du patron expand/contract pour renommer une colonne ?
