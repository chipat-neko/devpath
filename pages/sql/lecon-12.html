Module 04 · Manipuler et structurer — Leçon 12

Vues, transactions et intégrité

~33 min Intermédiaire Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • savoir créer et interroger une vue avec CREATE VIEW … AS SELECT
  • savoir grouper des opérations en transaction tout-ou-rien (BEGIN, COMMIT, ROLLBACK) et expliquer ACID
  • savoir protéger l'intégrité avec les contraintes et les actions ON DELETE CASCADE / RESTRICT / SET NULL ;
  • savoir gérer les droits d'accès avec GRANT et REVOKE.
Sommaire de la leçon

Jusqu'ici, tu as appris à lire et à modifier des données. Cette leçon change d'angle : il s'agit de rendre l'accès aux données plus simple (avec les vues) et plus fiable (avec les transactions et les contraintes). Ce sont les outils qui font la différence entre une base « jouet » et une base sur laquelle on peut compter, même quand plusieurs opérations s'enchaînent ou que plusieurs personnes travaillent en même temps.

On garde notre schéma habituel : une table clients, une table commandes (chaque commande appartient à un client via client_id) et une table produits. Tous les exemples tournent autour de ces tables.

Les vues : une requête enregistrée

Une vue (VIEW) est une requête SELECT à laquelle on donne un nom. Une fois créée, tu l'interroges comme si c'était une table : c'est une « table virtuelle ». L'intérêt : enfermer une requête compliquée derrière un nom simple, et la réutiliser partout sans la réécrire.

On enregistre une jointure clients ↔ commandes sous le nom commandes_clients.

Maintenant, plus besoin de réécrire la jointure. Tu lis la vue comme une table :

nomvillemontant
DupontLyon150
MartinParis240
NkonoNantes120

Une vue sert aussi à exposer un sous-ensemble : tu peux créer une vue qui ne montre que certaines colonnes (par exemple sans les données sensibles) et donner accès à la vue plutôt qu'à la table complète.

Note

Une vue ne stocke pas de données. À chaque fois que tu l'interroges, le moteur rejoue le SELECT sous-jacent sur les tables réelles. Les résultats reflètent donc toujours l'état actuel des données.

Les vues matérialisées (mention)

Il existe une variante, la vue matérialisée, qui elle stocke le résultat calculé. C'est utile quand la requête est lourde et qu'on accepte un résultat un peu moins frais en échange de la vitesse. Il faut alors la rafraîchir explicitement.

PostgreSQL propose MATERIALIZED VIEW. MySQL et SQLite ne l'ont pas en standard : on simule avec une table mise à jour à la main.

Les transactions : tout ou rien

Une transaction regroupe plusieurs opérations en un seul bloc indivisible. Soit tout réussit, soit rien n'est appliqué. On ouvre avec BEGIN (ou START TRANSACTION), on valide avec COMMIT, et on annule tout avec ROLLBACK.

Un virement : on retire 100 d'un compte, on les ajoute à l'autre. Le COMMIT rend les deux changements définitifs d'un coup.

Cas réel

Réserver un billet de train, c'est une transaction. En un seul bloc, le système doit décrémenter le nombre de places et enregistrer le paiement. Si le paiement échoue après que la place a été retenue, un ROLLBACK rend la place au stock : sinon un siège resterait « vendu » à personne. À l'inverse, deux clients ne peuvent pas acheter le dernier billet en même temps : l'isolation force l'un à attendre que l'autre ait validé (ou annulé). C'est exactement ce mécanisme qui évite les doubles réservations un soir de forte affluence.

Note

Selon l'outil, la première instruction démarre parfois une transaction automatiquement (mode « autocommit » désactivé). En SQLite et PostgreSQL, BEGIN est explicite ; MySQL accepte START TRANSACTION comme synonyme.

Les propriétés ACID

Les transactions reposent sur quatre garanties résumées par l'acronyme ACID. Voici l'idée, sans jargon, avec notre virement :

  • A — Atomicité : le bloc est indivisible. Les deux UPDATE du virement passent ensemble, ou aucun. Jamais 100 retirés sans les 100 ajoutés.
  • C — Cohérence : la base passe d'un état valide à un autre état valide. Les contraintes (clés, CHECK…) restent respectées après le COMMIT.
  • I — Isolation : deux transactions simultanées ne se marchent pas dessus. Chacune voit une image cohérente, comme si elle était seule.
  • D — Durabilité : une fois le COMMIT fait, le changement survit même à une coupure de courant juste après.

Isolation et anomalies (survol)

Quand plusieurs transactions tournent en même temps, des « anomalies » peuvent apparaître. La plus connue est la lecture sale (dirty read) : une transaction lit une donnée modifiée par une autre transaction qui n'a pas encore fait COMMIT… et qui finira peut-être par un ROLLBACK. On a alors lu quelque chose qui n'a jamais vraiment existé.

Pour s'en protéger, on choisit un niveau d'isolation. Du plus permissif au plus strict : READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE. Plus c'est strict, moins il y a d'anomalies, mais plus il y a de verrous et d'attente.

Le niveau par défaut varie : READ COMMITTED sous PostgreSQL, REPEATABLE READ sous MySQL/InnoDB. SQLite, lui, sérialise tout par conception.

L'intégrité par les contraintes

Au-delà des transactions, la base se protège avec des contraintes déclarées sur les colonnes : PRIMARY KEY, NOT NULL, UNIQUE, CHECK et surtout FOREIGN KEY, qui relie une commande à un client existant. Tu en as déjà croisé ; ici, on s'intéresse à ce qui se passe quand on supprime une ligne référencée.

Les trois comportements les plus utiles :

  • ON DELETE CASCADE : supprimer le client supprime aussi ses commandes.
  • ON DELETE RESTRICT : interdit de supprimer le client tant qu'il a des commandes (la suppression échoue).
  • ON DELETE SET NULL : garde les commandes mais met leur client_id à NULL (la colonne doit alors accepter NULL).

Note

Sous SQLite, les clés étrangères doivent être activées par session avec PRAGMA foreign_keys = ON;, sinon les actions référentielles sont ignorées.

Les droits : GRANT et REVOKE

Dernier pilier de la fiabilité : décider qui a le droit de faire quoi. On accorde un droit avec GRANT et on le retire avec REVOKE.

Astuce courante : donner SELECT sur une vue plutôt que sur la table, pour ne montrer qu'un sous-ensemble. SQLite, base mono-fichier, ne gère pas GRANT/REVOKE.

Pièges fréquents

Piège fréquent

Oublier le COMMIT. Tant que tu ne valides pas, tes modifications restent invisibles aux autres et seront perdues si la connexion se ferme. À l'inverse, un COMMIT rend tout définitif : vérifie avant.

Piège fréquent

Transactions trop longues. Une transaction ouverte pose des verrous ; si elle traîne, les autres attendent. Ouvre tard, valide tôt : garde le bloc BEGIN … COMMIT aussi court que possible.

Piège fréquent

Croire qu'une vue stocke des données. Une vue ordinaire rejoue sa requête à chaque appel. Si la requête sous-jacente est lente, lire la vue est lent aussi. Pour stocker, il faut une vue matérialisée.

Piège fréquent

ON DELETE CASCADE qui efface en chaîne. Supprimer un client peut effacer toutes ses commandes sans avertissement. Utilise CASCADE en connaissance de cause ; en cas de doute, préfère RESTRICT.

Glossaire

Vue (VIEW)
Requête SELECT nommée, interrogée comme une table virtuelle ; elle ne stocke pas de données et rejoue sa requête à chaque appel.
Vue matérialisée
Vue qui stocke son résultat calculé pour aller plus vite ; il faut la rafraîchir (REFRESH) pour la remettre à jour.
Transaction
Bloc d'opérations indivisible : soit tout est appliqué (COMMIT), soit rien (ROLLBACK).
COMMIT / ROLLBACK
Valide définitivement, respectivement annule, les écritures d'une transaction en cours.
ACID
Les quatre garanties d'une transaction : Atomicité (tout ou rien), Cohérence (états valides), Isolation (transactions indépendantes), Durabilité (survit aux pannes).
Niveau d'isolation
Réglage du compromis entre anomalies et verrous : de READ UNCOMMITTED (permissif) à SERIALIZABLE (strict).
Action référentielle
Comportement d'une clé étrangère à la suppression du parent : CASCADE, RESTRICT ou SET NULL.
GRANT / REVOKE
Commandes qui accordent, respectivement retirent, un droit d'accès (SELECT, INSERT…) à un utilisateur ou un rôle.

Récap et vérification

  • Une vue (CREATE VIEW) est une requête nommée, interrogée comme une table ; elle ne stocke rien (sauf si elle est matérialisée).
  • Une transaction (BEGIN … COMMIT / ROLLBACK) est un bloc tout-ou-rien.
  • ACID : Atomicité, Cohérence, Isolation, Durabilité — les garanties d'une transaction.
  • Les niveaux d'isolation arbitrent entre sécurité (moins d'anomalies) et performance (moins de verrous).
  • Les contraintes protègent l'intégrité ; ON DELETE CASCADE / RESTRICT / SET NULL décident du sort des lignes référencées.
  • GRANT et REVOKE gèrent les droits d'accès.

  1. Quelle est la différence entre COMMIT et ROLLBACK ?
  2. Une vue ordinaire stocke-t-elle ses données ? Que se passe-t-il quand tu l'interroges ?
  3. Que garantit la lettre « A » d'ACID, illustrée par un virement ?
  4. Si tu supprimes un client référencé par des commandes, que fait ON DELETE SET NULL ?
