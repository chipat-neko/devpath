Module 04 · Manipuler et structurer — Leçon 11

Créer et modifier des tables (DDL)

~33 min Intermédiaire Leçon 10 recommandée

À la fin de cette leçon, tu sauras

  • savoir créer une table avec CREATE TABLE, en déclarant colonnes et types ;
  • savoir poser des contraintes (PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE, DEFAULT, CHECK) ;
  • savoir faire évoluer une table avec ALTER TABLE et la supprimer proprement avec DROP TABLE ;
  • savoir à quoi sert un index et quand le créer avec CREATE INDEX.
Sommaire de la leçon

Jusqu'ici, tu as appris à lire des données déjà rangées dans des tables, avec SELECT … FROM. Mais d'où viennent ces tables ? Quelqu'un a d'abord dû les définir : décider quelles colonnes elles contiennent, de quel type, et quelles règles elles doivent respecter. C'est le rôle du DDL (Data Definition Language, « langage de définition des données »), la partie de SQL qui crée et modifie la structure de la base.

Dans cette leçon, tu vas construire le squelette d'une petite base de boutique : une table clients et une table commandes reliée à la première. Tu verras comment déclarer les colonnes, poser des garde-fous (les contraintes), numéroter automatiquement les lignes, faire évoluer une table existante, la supprimer proprement, et accélérer les recherches avec un index.

Note

Les commandes DDL modifient la base de façon durable : après un CREATE TABLE, la table existe vraiment. On les écrit en général une seule fois, au moment de mettre en place la base, puis on travaille au quotidien avec SELECT, INSERT, etc. Comme aucune base ne tourne dans cette page, les requêtes ci-dessous sont à lire et comprendre ; les petits tableaux montrent le résultat qu'elles produiraient sur une vraie base.

Créer une table avec CREATE TABLE

La commande CREATE TABLE donne un nom à la table, puis liste ses colonnes entre parenthèses. Chaque colonne s'écrit nom TYPE, et les colonnes sont séparées par des virgules. Le type indique quelle sorte de donnée la colonne peut contenir : du texte, un nombre entier, une date…

On déclare cinq colonnes. VARCHAR(100) = texte de longueur variable jusqu'à 100 caractères ; INTEGER = nombre entier ; DATE = une date du calendrier.

Voici les types les plus courants, suffisants pour débuter :

Note

Les noms de types varient un peu d'un moteur à l'autre. SQLite est très souple (il accepte presque n'importe quoi et range tout dans quelques catégories ; il n'a d'ailleurs pas de vrai type BOOLEAN et stocke 0 ou 1). PostgreSQL et MySQL sont plus stricts. INTEGER, VARCHAR, DATE et DECIMAL font partie du standard et marchent partout.

Les contraintes : poser des règles sur les colonnes

Une contrainte est une règle que la base fait respecter automatiquement. Si tu essaies d'insérer une ligne qui la viole, la base refuse l'opération. C'est ta première ligne de défense contre les données incohérentes. On les écrit juste après le type de la colonne.

  • PRIMARY KEY : identifie chaque ligne de façon unique (la « clé primaire »). Une seule par table.
  • NOT NULL : la colonne doit toujours avoir une valeur (interdit le vide).
  • UNIQUE : deux lignes ne peuvent pas partager la même valeur.
  • DEFAULT valeur : valeur appliquée automatiquement si on n'en fournit pas.
  • CHECK (condition) : impose une condition (ex. un prix positif).
  • REFERENCES : relie cette colonne à la clé d'une autre table (clé étrangère, voir plus bas).

Chaque client a un id unique et obligatoire, un nom obligatoire, un email obligatoire et jamais en double ; actif vaut TRUE par défaut, et inscrit_le prend la date du jour (CURRENT_DATE) si on ne précise rien.

L'auto-incrément : numéroter les lignes tout seul

La clé primaire est souvent un simple numéro qui s'incrémente : 1, 2, 3… Plutôt que de calculer toi-même le prochain numéro à chaque insertion, tu peux demander à la base de le faire. C'est l'auto-incrément. Malheureusement, c'est le point où les moteurs divergent le plus :

MoteurÉcriture typique
Standard ANSIid INTEGER GENERATED ALWAYS AS IDENTITY
PostgreSQLid SERIAL PRIMARY KEY (ou la forme IDENTITY)
SQLiteid INTEGER PRIMARY KEY AUTOINCREMENT
MySQLid INT AUTO_INCREMENT PRIMARY KEY

Avec SERIAL, tu n'indiques pas l'id à l'insertion : la base attribue 1 au premier client, 2 au suivant, etc.

Note

La forme GENERATED ALWAYS AS IDENTITY est celle du standard moderne, gérée par PostgreSQL et d'autres. Mais en pratique tu rencontreras très souvent SERIAL, AUTOINCREMENT ou AUTO_INCREMENT selon le moteur. À noter : en SQLite, une colonne déclarée INTEGER PRIMARY KEY s'auto-incrémente déjà toute seule ; le mot-clé AUTOINCREMENT n'y est qu'un raffinement rarement nécessaire. Vérifie toujours la documentation de ton moteur.

Relier deux tables : la clé étrangère

Une boutique a des clients et des commandes. Chaque commande appartient à un client. Pour exprimer ce lien, on ajoute dans commandes une colonne qui pointe vers la clé primaire de clients : c'est une clé étrangère (FOREIGN KEY … REFERENCES).

La ligne FOREIGN KEY (client_id) REFERENCES clients(id) garantit que tout client_id d'une commande correspond bien à un id existant dans clients. Impossible de créer une commande pour un client fantôme.

Une fois ces deux tables remplies, une lecture de commandes pourrait donner :

Les commandes 1 et 2 appartiennent au client 1, la 3 au client 2, etc. La clé étrangère est ce qui rend ce lien fiable et c'est elle qui permettra, plus tard, de joindre les deux tables.

Cas réel

Sur une vraie boutique en ligne, ces deux tables sont exactement celles qui portent le chiffre d'affaires. Un jour, une équipe voulait « faire le ménage » et supprimer un vieux compte client : la base a refusé le DELETE parce que des commandes de cet historique le référençaient encore. Frustrant sur le moment ? Non : c'est exactement le but. Sans cette clé étrangère, on se serait retrouvé avec des commandes orphelines pointant vers un client fantôme — impossible ensuite d'éditer une facture ou de calculer un total par client. La contrainte a protégé la comptabilité toute seule.

Faire évoluer une table : ALTER TABLE

Une base vit : un jour tu auras besoin d'une colonne en plus, ou tu voudras en renommer une. Pas besoin de tout recréer : ALTER TABLE modifie une table existante sans perdre ses données.

Quatre opérations courantes : ajouter, supprimer, renommer une colonne, et renommer la table.

Note

Modifier le type d'une colonne se fait avec une syntaxe variable : ALTER COLUMN … TYPE … en PostgreSQL, MODIFY COLUMN … en MySQL. SQLite, lui, est limité sur ALTER TABLE (il sait surtout ajouter, supprimer et renommer une colonne, pas changer son type ni ajouter une contrainte). Là encore, le standard pose les bases, mais chaque moteur a ses nuances.

Supprimer : DROP TABLE et TRUNCATE

Deux opérations bien différentes :

  • DROP TABLE supprime la table entière : sa structure et ses données. Elle n'existe plus.
  • TRUNCATE vide la table de toutes ses lignes mais garde la structure : la table reste là, prête à être remplie de nouveau.

IF EXISTS évite une erreur si la table n'existe pas : pratique dans un script qu'on rejoue plusieurs fois.

Piège fréquent

DROP TABLE et TRUNCATE sont irréversibles et ne demandent aucune confirmation. Il n'y a pas de corbeille. Sur une vraie base, réfléchis à deux fois et fais une sauvegarde avant. TRUNCATE n'est d'ailleurs pas géré par tous les moteurs (SQLite ne le connaît pas ; on y utilise DELETE FROM table).

Accélérer les recherches : les index

Quand une table grandit, retrouver une ligne peut devenir lent : sans aide, la base parcourt toutes les lignes une à une. Un index est comme l'index d'un livre : une structure qui permet de sauter directement à la bonne page. On le crée avec CREATE INDEX sur la ou les colonnes qu'on interroge souvent.

Si tu cherches souvent les commandes d'un client donné (WHERE client_id = …), cet index rend la recherche bien plus rapide.

Note

Bonne nouvelle : les colonnes PRIMARY KEY et UNIQUE sont déjà indexées automatiquement. Tu n'as donc à créer des index que pour les autres colonnes que tu filtres souvent, comme une clé étrangère. On approfondit la performance dans la leçon 14.

Pièges fréquents

Piège fréquent

Oublier la clé primaire. Une table sans PRIMARY KEY autorise les doublons et rend chaque ligne difficile à identifier. Donne presque toujours une clé primaire à tes tables, le plus souvent un id auto-incrémenté.

Piège fréquent

Choisir un type inadapté. Stocker un prix dans du VARCHAR empêche les calculs et fausse les comparaisons (en texte, '9' paraît « plus grand » que '100'). Pour de l'argent, utilise DECIMAL ; pour une date, DATE, pas du texte.

Piège fréquent

Supprimer une table encore référencée. Si commandes pointe vers clients par une clé étrangère, un DROP TABLE clients sera refusé tant que des commandes existent. Supprime d'abord la table « enfant » (commandes), ou retire la contrainte.

Piège fréquent

Multiplier les index inutiles. Un index accélère les lectures mais ralentit chaque écriture (la base doit aussi mettre l'index à jour) et occupe de l'espace. N'indexe que les colonnes vraiment interrogées souvent.

Pour aller plus loin

Pour aller plus loin

Dans les vrais projets, on ne tape pas ces commandes à la main : on les versionne dans des migrations, des fichiers numérotés qui décrivent chaque évolution du schéma, exactement comme on versionne du code. On découvre aussi des types avancés (JSON, UUID, ENUM), les index composites (sur plusieurs colonnes à la fois) et les contraintes différées, vérifiées seulement à la fin d'une transaction.

Antisèche : le DDL en un coup d'œil

Les commandes qui définissent et font évoluer la structure d'une base.

Glossaire

DDL
« Data Definition Language » : la partie de SQL qui crée et modifie la structure de la base (CREATE, ALTER, DROP), par opposition au DML qui manipule les données.
Contrainte
Règle que la base fait respecter automatiquement ; toute écriture qui la viole est rejetée (NOT NULL, UNIQUE, CHECK…).
Clé primaire (PRIMARY KEY)
Colonne (ou groupe) qui identifie chaque ligne de façon unique et non vide. Une seule par table.
Clé étrangère (FOREIGN KEY)
Colonne qui pointe vers la clé primaire d'une autre table ; garantit que la valeur référencée existe bien.
Intégrité référentielle
Garantie que les liens entre tables restent cohérents : pas de commande sans client réel, pas de suppression d'un client encore référencé.
Auto-incrément
Mécanisme qui attribue automatiquement le numéro suivant à la clé primaire (SERIAL, AUTOINCREMENT, AUTO_INCREMENT, GENERATED … AS IDENTITY).
Index
Structure annexe qui accélère la recherche sur une colonne, comme l'index d'un livre ; il ralentit un peu les écritures et occupe de l'espace.
Migration
Fichier versionné décrivant une évolution du schéma (ajout de colonne, nouvelle table…), rejoué dans l'ordre pour construire ou mettre à jour la base.

Récap et vérification

  • CREATE TABLE nom (colonne TYPE …) définit une table, ses colonnes et leurs types.
  • Les contraintes (PRIMARY KEY, FOREIGN KEY … REFERENCES, NOT NULL, UNIQUE, DEFAULT, CHECK) protègent la cohérence des données.
  • L'auto-incrément numérote les lignes : GENERATED … AS IDENTITY (standard), SERIAL (PostgreSQL), AUTOINCREMENT (SQLite), AUTO_INCREMENT (MySQL).
  • ALTER TABLE fait évoluer une table (ADD/DROP/RENAME COLUMN, contraintes) sans la recréer.
  • DROP TABLE IF EXISTS supprime tout ; TRUNCATE vide les lignes mais garde la structure.
  • CREATE INDEX accélère les recherches fréquentes, au prix d'écritures un peu plus lentes.
