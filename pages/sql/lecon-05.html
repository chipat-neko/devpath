Agréger : COUNT, SUM et GROUP BY

~34 min Intermédiaire Leçon 04 recommandée

À la fin de cette leçon, tu sauras

  • savoir utiliser les fonctions d'agrégation COUNT, SUM, AVG, MIN et MAX, et comprendre comment elles traitent les NULL ;
  • savoir regrouper des lignes avec GROUP BY et appliquer la règle : toute colonne non agrégée du SELECT doit être dans le GROUP BY ;
  • savoir distinguer WHERE (filtre les lignes) de HAVING (filtre les groupes) et connaître l'ordre logique FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY ;
  • savoir compter des valeurs uniques avec COUNT(DISTINCT colonne).
Sommaire de la leçon

Jusqu'ici, tu sais lire des colonnes ligne par ligne avec SELECT … FROM. Mais souvent, tu ne veux pas voir chaque ligne : tu veux un résumé. Combien de commandes ? Quel est le chiffre d'affaires total ? Le panier moyen par catégorie ? C'est le rôle des fonctions d'agrégation et de GROUP BY.

On travaille sur deux tables récurrentes : commandes (une ligne par commande) et produits. Voici un aperçu de commandes :

idclient_idmoiscategoriemontant
1102026-01livre30
2102026-01jeu50
3112026-02livre20
4112026-02jeu90
5122026-02livreNULL

La table commandes (extrait). La commande 5 a un montant inconnu (NULL).

Compter et résumer : les fonctions d'agrégation

Une fonction d'agrégation prend plusieurs lignes et renvoie une seule valeur. Les cinq à connaître : COUNT (compter), SUM (additionner), AVG (moyenne), MIN et MAX.

Sans GROUP BY, l'agrégat porte sur toute la table : tu obtiens une seule ligne de résumé.

nb_commandestotalpanier_moyenplus_petitplus_gros
519047.52090

Remarque le total : 30 + 50 + 20 + 90 = 190. La ligne 5 (NULL) n'a pas été additionnée : SUM, AVG, MIN et MAX ignorent les NULL. Du coup la moyenne est 190 / 4 = 47.5 (4 valeurs, pas 5).

COUNT(*) ou COUNT(colonne) ?

C'est une distinction qui surprend les débutants. COUNT(*) compte les lignes, quelles qu'elles soient. COUNT(colonne) compte seulement les lignes où cette colonne n'est pas NULL.

lignesmontants_connus
54

Il y a bien 5 lignes, mais seulement 4 ont un montant renseigné. La commande 5, dont le montant est NULL, est comptée par COUNT(*) mais pas par COUNT(montant).

Note

Un NULL, ce n'est pas zéro ni une chaîne vide : c'est « valeur inconnue / absente ». C'est pour ça que les agrégats le sautent. Pour traiter un NULL comme un zéro, on verra COALESCE(montant, 0) plus tard.

GROUP BY : un résumé par groupe

Le résumé global, c'est bien, mais souvent tu veux le détail par catégorie, par client, par mois… C'est exactement le rôle de GROUP BY : il regroupe les lignes qui partagent la même valeur, puis calcule l'agrégat pour chaque groupe.

Une ligne de résultat par valeur distincte de categorie.

categorienbtotal
livre350
jeu2140

Trois commandes sont des livres (ids 1, 3, 5), deux sont des jeux (ids 2, 4). Le total des livres est 30 + 20 = 50 : la commande 5 (montant à NULL) est comptée par COUNT(*) — d'où nb = 3 — mais ignorée par SUM, qui n'additionne donc que 2 montants.

La règle d'or du SELECT agrégé

Voici LA règle à graver : toute colonne du SELECT qui n'est pas dans une fonction d'agrégation doit figurer dans le GROUP BY. Sinon, la base ne sait pas quelle valeur afficher pour un groupe qui contient plusieurs lignes différentes.

Ici client_id n'est ni agrégé, ni dans le GROUP BY : un même groupe « livre » contient les clients 10, 11 et 12. Lequel afficher ? La requête est rejetée. La version correcte :

Piège fréquent

MySQL (en réglage par défaut historique, sans ONLY_FULL_GROUP_BY) acceptait ce genre de requête et renvoyait une valeur arbitraire pour la colonne fautive. PostgreSQL, SQLite récent et le SQL standard la refusent. Écris toujours la version stricte : elle est portable et sans surprise.

HAVING : filtrer les groupes

Tu sais déjà filtrer des lignes avec WHERE. Mais comment garder seulement les groupes dont le total dépasse un seuil ? WHERE ne peut pas, car il agit avant l'agrégation : à ce moment-là, le total n'existe pas encore. C'est le rôle de HAVING, qui filtre après le regroupement.

Seuls les groupes dont le total dépasse 60 sont conservés.

categorietotal
jeu140

Le groupe « livre » (total 50) est écarté ; « jeu » (140) reste. Note bien : dans HAVING, on peut utiliser un agrégat comme SUM(montant), ce qui est interdit dans WHERE.

On peut combiner les deux : WHERE élimine d'abord certaines lignes, puis GROUP BY regroupe ce qui reste, puis HAVING trie les groupes.

Cas réel

Un tableau de bord d'audience (type Google Analytics ou Matomo) repose entièrement sur cette mécanique. « Sessions par source de trafic » = COUNT(*) … GROUP BY source ; « ne montrer que les pays d'où viennent plus de 100 visites » = HAVING COUNT(*) > 100 ; « visiteurs uniques » = COUNT(DISTINCT visiteur_id). Le filtre de date en haut de page, lui, se traduit en WHERE jour BETWEEN … AND … — avant le regroupement, car il élimine des lignes, pas des groupes. Chaque graphique du dashboard n'est qu'une requête GROUP BY déguisée.

L'ordre logique d'une requête

Tu écris une requête dans un certain ordre, mais la base ne l'exécute pas dans cet ordre. Comprendre l'ordre logique explique pourquoi WHERE ne voit pas les alias d'agrégat et pourquoi HAVING existe :

  • 1. FROM — on choisit la table.
  • 2. WHERE — on filtre les lignes (pas encore d'agrégat).
  • 3. GROUP BY — on forme les groupes.
  • 4. HAVING — on filtre les groupes (les agrégats existent).
  • 5. SELECT — on calcule les colonnes et les alias.
  • 6. ORDER BY — on trie le résultat.
  • 7. LIMIT — on coupe à N lignes.

Comme SELECT passe après WHERE, le WHERE ne connaît pas encore l'alias total : voilà pourquoi un filtre sur un agrégat passe forcément par HAVING.

categorietotal
jeu140
livre50

Note

LIMIT est la forme de SQLite, PostgreSQL et MySQL. Le SQL standard écrit plutôt FETCH FIRST 5 ROWS ONLY, et SQL Server utilise TOP 5 (juste après SELECT). L'idée reste la même : couper le résultat à un nombre de lignes.

Astuce

Dans ORDER BY, tu PEUX réutiliser l'alias total car il passe après SELECT. C'est plus lisible que de réécrire SUM(montant). Certaines bases permettent même ORDER BY 2 (la 2e colonne), mais l'alias reste plus clair.

Compter les valeurs distinctes : COUNT(DISTINCT …)

Combien de clients différents ont commandé ? Pas le nombre de commandes, mais le nombre de clients uniques. DISTINCT à l'intérieur de COUNT élimine les doublons avant de compter.

nb_commandesnb_clients
53

Il y a 5 commandes mais seulement 3 clients distincts (10, 11, 12). COUNT(DISTINCT client_id) renvoie 3.

Pièges fréquents

Piège fréquent

Confondre WHERE et HAVING. WHERE filtre des lignes avant le regroupement et ne peut pas contenir d'agrégat. HAVING filtre des groupes après, et c'est là que vivent SUM(...), COUNT(*), etc. Règle simple : condition sur une colonne brute → WHERE ; condition sur un agrégat → HAVING.

Trois autres erreurs classiques :

  • Une colonne ni agrégée ni groupée dans le SELECT. En SQL standard, c'est rejeté. Ajoute-la au GROUP BY ou enveloppe-la dans un agrégat.
  • Oublier que COUNT(colonne) ignore les NULL. Si tu veux compter toutes les lignes, utilise COUNT(*).
  • Trier sur un agrégat « invisible ». Si tu écris ORDER BY total, pense à avoir nommé l'agrégat avec AS total dans le SELECT (ou réécris l'expression complète ORDER BY SUM(montant) DESC).

Pour aller plus loin

Pour aller plus loin

On peut grouper sur une expression, pas seulement une colonne : par exemple GROUP BY SUBSTR(mois, 1, 4) pour regrouper par année. Les extensions ROLLUP et CUBE (PostgreSQL, SQL Server ; non disponibles en SQLite) ajoutent des lignes de sous-totaux et de total général. Enfin, les fonctions de fenêtrage (OVER (...), leçon 13) calculent des agrégats sans réduire le nombre de lignes : tu gardes le détail ET tu vois le total à côté.

Glossaire

Fonction d'agrégation
Fonction qui condense plusieurs lignes en une seule valeur : COUNT, SUM, AVG, MIN, MAX.
GROUP BY
Clause qui regroupe les lignes partageant la même valeur, puis calcule l'agrégat pour chaque groupe.
WHERE
Filtre les lignes avant l'agrégation ; ne peut pas contenir de fonction d'agrégation.
HAVING
Filtre les groupes après le GROUP BY ; c'est là qu'on teste SUM(…), COUNT(*), etc.
COUNT(*) vs COUNT(colonne)
COUNT(*) compte les lignes ; COUNT(colonne) ne compte que les valeurs non NULL.
COUNT(DISTINCT)
Compte les valeurs distinctes d'une colonne, après élimination des doublons.
Ordre logique
Séquence d'exécution réelle d'une requête (FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY), distincte de l'ordre d'écriture : elle explique pourquoi WHERE ignore les alias et les agrégats.

Récap et vérification

  • Les fonctions d'agrégation (COUNT, SUM, AVG, MIN, MAX) résument plusieurs lignes en une valeur.
  • COUNT(*) compte les lignes ; COUNT(colonne) ignore les NULL ; SUM/AVG aussi.
  • GROUP BY calcule un agrégat par groupe ; toute colonne non agrégée du SELECT doit y figurer.
  • WHERE filtre les lignes (avant), HAVING filtre les groupes (après).
  • Ordre logique : FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
  • COUNT(DISTINCT colonne) compte les valeurs uniques.

Vérifie ta compréhension

  1. Quelle différence entre COUNT(*) et COUNT(montant) sur une table où certains montants sont NULL ?
  2. Tu veux les catégories dont le chiffre d'affaires dépasse 1000 €. Tu écris la condition dans WHERE ou dans HAVING ? Pourquoi ?
  3. Pourquoi SELECT client_id, SUM(montant) FROM commandes GROUP BY categorie est-elle refusée ?
