Module 06 · Logique stockée & données modernes — Leçon 15

Procédures, fonctions et triggers

~30 min Intermédiaire Cours SQL recommandé

À la fin de cette leçon, tu sauras

  • savoir écrire et appeler une fonction stockée qui renvoie une valeur dans un SELECT
  • savoir créer une procédure et l'invoquer avec CALL pour une action transactionnelle
  • savoir poser un trigger BEFORE/AFTER en utilisant NEW et OLD
  • savoir peser les avantages et les inconvénients de la logique stockée selon le SGBD .
Sommaire de la leçon

Jusqu'ici, tu as toujours écrit ta logique à côté de la base : ton application envoie des requêtes, récupère les résultats, puis décide quoi faire. Dans cette leçon, on déplace une partie de cette logique dans la base de données elle-même. Les FONCTIONS, les PROCÉDURES et les TRIGGERS permettent de stocker du code exécuté côté serveur, au plus près des données.

C'est puissant mais à double tranchant. La SYNTAXE de ce code procédural n'est pas standardisée : PostgreSQL utilise le langage PL/pgSQL, MySQL son propre dialecte procédural. On va voir les concepts communs, puis quand chaque variante diverge.

Pourquoi mettre de la logique dans la base ?

Déplacer du code côté serveur répond à trois besoins. L'intégrité : une règle métier appliquée par la base s'impose à toutes les applications qui s'y connectent, pas seulement à celle qui a pensé à la coder. La performance : la logique s'exécute là où vivent les données, sans aller-retour réseau pour chaque étape. La sécurité : tu peux donner le droit d'EXECUTE une procédure sans donner l'accès direct aux tables.

Le revers, c'est que ce code n'est pas en SQL standard. Une fonction écrite en PL/pgSQL ne tournera pas telle quelle sur MySQL. On signalera donc systématiquement le SGBD visé.

Note

Une FONCTION renvoie une valeur et s'utilise dans une requête. Une PROCÉDURE fait une action et s'appelle avec CALL. Un TRIGGER s'exécute tout seul quand une ligne change. Garde ces trois rôles en tête.

Les fonctions stockées

Une fonction stockée prend des paramètres, exécute du code, et RENVOIE une valeur. On l'appelle exactement comme une fonction intégrée (par exemple UPPER ou ROUND), à l'intérieur d'un SELECT. Voici une fonction PostgreSQL qui calcule le prix TTC à partir d'un prix HT et d'un taux.

Une fonction peut aussi renvoyer une table (plusieurs lignes), via RETURNS TABLE(...). On l'utilise alors dans un FROM comme une vue paramétrée.

Note

En MySQL, une fonction qui ne lit pas de tables doit être marquée DETERMINISTIC, et celle qui en lit, READS SQL DATA : CREATE FUNCTION prix_ttc(...) RETURNS DECIMAL(10,2) DETERMINISTIC RETURN ...;. Sans cette indication, MySQL refuse souvent la création.

Les procédures stockées

Une PROCÉDURE ne renvoie pas forcément de valeur : elle réalise une ACTION, souvent une suite d'écritures qui doivent réussir ou échouer ensemble. On l'appelle avec CALL. Exemple : transférer un montant d'un compte à un autre.

Appelée seule, la procédure s'exécute dans une transaction implicite : les deux UPDATE réussissent ou échouent ensemble.

Note

En PostgreSQL, une procédure peut aussi piloter explicitement COMMIT / ROLLBACK en son sein (ce qu'une fonction ne peut pas faire). En MySQL, la déclaration ressemble à CREATE PROCEDURE transferer(IN p_de INT, ...) et on encadre souvent le corps avec DELIMITER // pour que le client ne coupe pas sur le premier ; interne.

Les boucles (LOOP, WHILE, FOR) existent aussi, mais en pratique on les évite dès qu'une requête ensembliste fait le travail : un UPDATE sur 1000 lignes est bien plus rapide qu'une boucle qui traite ligne par ligne.

Les triggers : du code automatique

Un TRIGGER (déclencheur) est du code qui s'exécute AUTOMATIQUEMENT quand une ligne est insérée, modifiée ou supprimée. Tu déclares BEFORE ou AFTER un INSERT / UPDATE / DELETE, avec FOR EACH ROW pour agir sur chaque ligne touchée. Dans le corps, deux pseudo-tables sont disponibles : NEW (la ligne après modification) et OLD (la ligne avant). En PostgreSQL, le trigger appelle une fonction RETURNS TRIGGER.

Désormais chaque UPDATE sur articles remplit updated_at sans que l'application y pense.

Après un UPDATE articles SET titre = 'Nouveau' WHERE id = 7;, la colonne se met à jour seule :

idtitreupdated_at
7Nouveau2026-06-10 14:32:07

Note

En MySQL, on écrit le code directement dans le trigger : CREATE TRIGGER ... BEFORE UPDATE ON articles FOR EACH ROW SET NEW.updated_at = NOW(); sans fonction séparée. À noter aussi : PostgreSQL emploie EXECUTE FUNCTION (les anciennes versions acceptent encore EXECUTE PROCEDURE).

Les cas d'usage typiques : l'audit (journaliser qui modifie quoi dans une table d'historique), l'horodatage automatique d'un updated_at, la validation (refuser une écriture invalide), ou la dénormalisation (recalculer un total stocké). Pour un audit, un trigger AFTER INSERT peut écrire OLD et NEW dans une table journal.

Cas réel

Dans les applications de gestion (banque, RH, e-commerce), toute modification d'une ligne sensible est doublée d'une écriture dans une table d'historique par un trigger AFTER. Le jour où un client conteste une opération ou qu'un auditeur demande « qui a changé ce montant, et quand ? », la trace est déjà là : chaque UPDATE a laissé une ligne horodatée avec l'ancienne et la nouvelle valeur. Aucune application ne peut « oublier » de journaliser, puisque c'est la base qui s'en charge.

Avantages et inconvénients

Du côté positif : la règle est centralisée et garantie quelle que soit l'application, les opérations sensibles restent atomiques, et on réduit les allers-retours réseau. C'est idéal pour des invariants stricts (un updated_at toujours juste, un solde jamais négatif).

Du côté négatif : la logique devient cachée. Un développeur qui lit le code applicatif ne voit pas qu'un trigger modifie les données dans son dos. La portabilité souffre (changer de SGBD oblige à tout réécrire). Le débogage est plus difficile : pas de point d'arrêt facile, des messages d'erreur parfois obscurs. Enfin, ce code vit dans la base et non dans ton dépôt Git ; il faut un effort conscient pour le versionner.

Astuce

Range tes CREATE FUNCTION / CREATE TRIGGER dans des fichiers de migration suivis par Git. Ainsi la logique stockée est versionnée et revue comme le reste du code.

Pièges fréquents

Piège fréquent

Mettre trop de logique dans la base. Une règle métier complexe enfouie dans des triggers devient dure à tester, à versionner et à comprendre. Garde dans la base ce qui protège l'intégrité ; laisse les calculs métier riches à l'application.

Piège fréquent

Les triggers en cascade. Un trigger qui écrit dans une table équipée elle-même d'un trigger peut déclencher une chaîne d'effets imprévus, voire une boucle. Vérifie toujours ce qu'un trigger touche en aval.

Méfie-toi aussi des effets de bord cachés et du manque de portabilité : du PL/pgSQL ne se transpose pas automatiquement vers MySQL, et inversement.

Antisèche : la logique stockée

Glossaire

Fonction stockée
Bloc de code enregistré dans la base qui prend des paramètres et renvoie une valeur (ou une table) ; s'appelle dans un SELECT.
Procédure stockée
Bloc de code qui exécute une action (souvent des écritures groupées) sans forcément renvoyer de valeur ; s'invoque avec CALL.
Trigger (déclencheur)
Code lié à une table qui s'exécute automatiquement à chaque INSERT, UPDATE ou DELETE.
PL/pgSQL
Langage procédural de PostgreSQL (variables, IF, boucles) employé pour le corps des fonctions et procédures ; MySQL a son propre dialecte.
NEW / OLD
Pseudo-lignes d'un trigger : OLD est la ligne avant modification, NEW la ligne après.
BEFORE / AFTER
Moment d'exécution d'un trigger : BEFORE avant l'écriture (peut corriger NEW), AFTER après (idéal pour journaliser).
CALL
Instruction qui invoque une procédure ; contrairement à une fonction, une procédure ne s'insère pas dans un SELECT.
FOR EACH ROW
Clause d'un trigger indiquant qu'il s'exécute une fois par ligne touchée, et non une seule fois pour l'instruction entière.

Récap et vérification

  • Une FONCTION renvoie une valeur (ou une table) et s'appelle dans un SELECT.
  • Une PROCÉDURE exécute une action, s'appelle avec CALL, souvent dans une transaction.
  • Le corps offre variables (DECLARE), conditions (IF) et boucles ; privilégie l'ensembliste aux boucles.
  • Un TRIGGER s'exécute automatiquement BEFORE/AFTER une écriture, avec NEW et OLD.
  • Avantages : intégrité, performance, sécurité ; inconvénients : logique cachée, portabilité, débogage.
  • La SYNTAXE varie (PL/pgSQL vs MySQL) : précise toujours le SGBD.

  2. Dans un trigger BEFORE UPDATE, que contiennent NEW et OLD ?
