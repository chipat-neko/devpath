Module 03 · Combiner des tables — Leçon 07

Les jointures (JOIN)

~37 min Intermédiaire Leçon 06 recommandée

À la fin de cette leçon, tu sauras

  • savoir relier deux tables avec INNER JOIN … ON … grâce aux clés ;
  • savoir utiliser les alias de table pour lever les ambiguïtés et gagner en lisibilité ;
  • savoir distinguer INNER JOIN (correspondances) et LEFT JOIN (tout à gauche, NULL sinon) ;
  • savoir chaîner plusieurs JOIN et combiner une jointure avec WHERE et GROUP BY.
Sommaire de la leçon

Jusqu'ici, tu as toujours lu une seule table à la fois avec SELECT … FROM. Mais dans une vraie base, les données ne sont jamais entassées dans un seul grand tableau : elles sont éclatées en plusieurs tables reliées entre elles. Les noms des clients vivent dans une table clients, leurs achats dans une table commandes, et les deux sont reliées par une clé. Pour réafficher l'information complète, il faut les recombiner : c'est le rôle des jointures (JOIN).

Dans cette leçon, on travaille sur un petit schéma de boutique avec trois tables : clients, commandes et produits. Tu vas apprendre à les assembler avec INNER JOIN, à nommer tes tables avec des alias, à tout garder à gauche avec LEFT JOIN, à chaîner plusieurs tables, et à combiner une jointure avec un filtre et un regroupement. Tout reste en SQL standard, avec les variantes utiles signalées au passage.

Pourquoi les données sont éclatées

Regarde nos deux tables de départ. La table clients donne un identifiant id (sa clé primaire, unique pour chaque client), un nom et une ville :

1Alice DupontLyon
2Bruno MartinParis
3Chloé NguyenLille

La table commandes ne répète pas le nom du client : elle stocke seulement un client_id qui pointe vers le id de la table clients. Elle pointe de la même façon vers la table produits avec un produit_id. Ces deux colonnes sont des clés étrangères :

idclient_idproduit_idmontant
10111013.50
10211112.00
10321212.00

Stocker le nom du client une seule fois (dans clients) et le libellé du produit une seule fois (dans produits) évite de les recopier sur chaque commande, et les erreurs qui vont avec. L'inconvénient : pour afficher « Alice a commandé un Carnet », il faut rapprocher les tables en faisant correspondre commandes.client_id avec clients.id (et plus loin commandes.produit_id avec produits.id). C'est exactement ce que fait une jointure.

INNER JOIN … ON …

La jointure la plus courante est INNER JOIN. Tu pars d'une première table dans le FROM, tu ajoutes JOIN avec la seconde, puis ON indique quelle colonne correspond à quelle colonne.

La condition ON relie la clé étrangère (commandes.client_id) à la clé primaire (clients.id).

Le résultat rapproche chaque commande de son client. Comme le client 1 (Alice) a passé deux commandes, Alice apparaît sur deux lignes :

nommontant
Alice Dupont13.50
Alice Dupont12.00
Bruno Martin12.00

« INNER » signifie qu'on ne garde que les lignes qui correspondent dans les deux tables. Une commande sans client valide ou un client sans commande n'apparaît pas. C'est l'intersection des deux tables.

Note

Le mot INNER est facultatif : écrire simplement JOIN revient au même qu'INNER JOIN dans tous les SGBD (PostgreSQL, MySQL, SQLite). Beaucoup l'omettent. On le garde ici pour bien marquer la différence avec LEFT JOIN.

Les alias de table

Écrire commandes.client_id à chaque fois devient vite lourd. Tu peux donner un alias (un surnom court) à chaque table, juste après son nom dans le FROM et le JOIN, puis t'en servir partout.

Ici c désigne clients et co désigne commandes. Le résultat est identique à la requête précédente.

Les alias rendent la requête plus courte, mais ils servent surtout à lever les ambiguïtés. Les deux tables ont chacune une colonne id : si tu écris SELECT id tout seul, le moteur ne sait pas de quel id tu parles et renvoie une erreur. En préfixant par l'alias (c.id ou co.id), tu lèves le doute.

Astuce

Choisis des alias courts mais parlants : l'initiale ou les deux premières lettres de la table (c pour clients, co pour commandes, p pour produits). Dès qu'une requête joint deux tables ou plus, prends l'habitude de toujours préfixer tes colonnes : la requête reste lisible même si on ajoute une table plus tard.

LEFT JOIN : tout garder à gauche

Reprenons le problème autrement : et si tu voulais lister tous les clients, même ceux qui n'ont jamais commandé ? Avec INNER JOIN, Chloé (client 3) disparaît car elle n'a aucune commande. C'est là qu'intervient LEFT JOIN.

Un LEFT JOIN garde toutes les lignes de la table de gauche (celle du FROM), et y ajoute les correspondances de droite quand il y en a. Quand il n'y en a pas, les colonnes de droite valent NULL.

Tous les clients apparaissent ; ceux sans commande ont des NULL à droite.

nommontant
Alice Dupont13.50
Alice Dupont12.00
Bruno Martin12.00
Chloé NguyenNULL

Chloé apparaît bien, avec une case vide à droite : c'est le signe qu'elle n'a aucune commande. Retiens l'idée : gauche = la table du FROM, et LEFT JOIN ne perd jamais une de ses lignes.

Le RIGHT JOIN est le miroir : il garde toutes les lignes de la table de droite. En pratique on l'utilise rarement : il suffit d'inverser l'ordre des tables pour transformer un RIGHT JOIN en LEFT JOIN, plus naturel à lire de gauche à droite.

Note

SQLite ne connaissait pas RIGHT JOIN avant sa version 3.39 (2022) ; sur d'anciennes versions, il faut donc inverser les tables et utiliser LEFT JOIN. PostgreSQL et MySQL gèrent les deux depuis longtemps.

Lister les lignes sans correspondance

Le LEFT JOIN a une utilité très concrète : trouver ce qui manque. Pour lister uniquement les clients sans commande, on fait un LEFT JOIN, puis on garde seulement les lignes où la partie droite est restée vide, avec WHERE … IS NULL.

On teste co.id IS NULL : si l'identifiant de commande est vide, c'est qu'aucune commande n'a été rapprochée.

nomville
Chloé NguyenLille

Cette technique s'appelle une anti-jointure : on garde justement les lignes qui n'ont pas trouvé de partenaire à droite. On y revient dans « Pour aller plus loin ».

Cas réel

Sur une boutique en ligne, la page « Mes commandes » est exactement cette requête : un JOIN entre commandes et produits, filtré par le client_id de l'utilisateur connecté, affiche chaque achat avec son libellé et son prix. Côté marketing, c'est le LEFT JOIN … WHERE … IS NULL qui travaille : pour relancer les inscrits « dormants », on liste les clients qui n'ont aucune commande (une anti-jointure) ; pour repérer les invendus, on liste les produits jamais reliés à une commande. Et le tableau de bord « activité par client », où même les clients à zéro achat doivent apparaître, se construit avec un LEFT JOIN … GROUP BY … COUNT plutôt qu'un INNER JOIN qui les ferait disparaître.

Pièges fréquents

Piège fréquent

Oublier la condition ON (ou écrire FROM clients, commandes sans rien relier) produit un produit cartésien : chaque client est associé à chaque commande, ce qui explose le nombre de lignes (3 clients × 100 commandes = 300 lignes absurdes). Vérifie toujours qu'un ON relie bien tes tables.

Piège fréquent

Confondre INNER et LEFT. INNER JOIN ne garde que les lignes qui ont une correspondance des deux côtés ; LEFT JOIN garde toutes les lignes de gauche. Si un client « disparaît » de ton résultat, c'est souvent qu'un INNER JOIN l'a écarté faute de commande.

Piège fréquent

Colonnes homonymes ambiguës. Quand deux tables ont une colonne du même nom (ici id), écrire SELECT id ou ON client_id = id sans préfixe déclenche une erreur « colonne ambiguë ». Préfixe toujours par l'alias : c.id, co.id.

Piège fréquent

Mettre une condition sur la table de droite dans le WHERE d'un LEFT JOIN annule l'effet « LEFT ». Par exemple WHERE co.montant > 10 élimine les lignes NULL (les clients sans commande), et tu retombes sur un INNER JOIN déguisé. Si la condition doit s'appliquer seulement aux lignes correspondantes, place-la dans le ON : ON co.client_id = c.id AND co.montant > 10.

Pour aller plus loin

Pour aller plus loin

Tu peux explorer le FULL JOIN (garder les lignes non appariées des deux côtés à la fois) et les auto-jointures (joindre une table avec elle-même, par exemple pour relier un employé à son manager) : ce sera le sujet de la leçon suivante. Quand les deux tables partagent un nom de colonne identique, USING (client_id) raccourcit le ON. L'anti-jointure (LEFT JOIN … WHERE … IS NULL) sert à trouver tout ce qui manque. Enfin, côté performance, des index sur les colonnes de jointure accélèrent énormément les requêtes sur de grandes tables.

Glossaire

Jointure (JOIN)
Opération qui recombine deux tables en rapprochant leurs lignes selon une condition, pour réafficher une information éclatée.
INNER JOIN
Ne garde que les lignes ayant une correspondance des deux côtés (l'intersection) ; le mot INNER est facultatif.
LEFT JOIN
Garde toutes les lignes de la table de gauche (celle du FROM) et met NULL à droite quand il n'y a pas de correspondance.
Condition ON
Indique quelle colonne d'une table correspond à quelle colonne de l'autre : en général clé étrangère = clé primaire (co.client_id = c.id).
Alias de table
Surnom court donné à une table dans le FROM/JOIN (clients c) ; il raccourcit la requête et lève les ambiguïtés de colonnes.
Anti-jointure
Motif LEFT JOIN … WHERE … IS NULL qui isole les lignes de gauche sans partenaire à droite ; sert à trouver ce qui manque.
Produit cartésien
Résultat d'une jointure sans condition : chaque ligne d'une table est combinée à toutes celles de l'autre (N × M), presque toujours une erreur.

Récap et vérification

  • Les données d'une base sont éclatées en tables reliées par des clés ; les JOIN les recombinent.
  • INNER JOIN … ON … garde uniquement les lignes qui correspondent des deux côtés (l'intersection).
  • Les alias de table (FROM clients c) raccourcissent les requêtes et lèvent les ambiguïtés de colonnes.
  • LEFT JOIN garde toutes les lignes de gauche, avec des NULL à droite quand il n'y a pas de correspondance ; RIGHT JOIN est son miroir.
  • On chaîne plusieurs JOIN pour relier trois tables ou plus, et on combine librement avec WHERE, GROUP BY et ORDER BY.

Vérifie ta compréhension

  2. Que se passe-t-il si tu oublies la condition ON dans une jointure ?
  3. Pourquoi mettre WHERE co.montant > 10 sur un LEFT JOIN peut-il le transformer en INNER JOIN, et comment l'éviter ?
