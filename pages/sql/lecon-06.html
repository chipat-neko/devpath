Modéliser : tables, clés et relations

~33 min Intermédiaire Module 2 recommandé

À la fin de cette leçon, tu sauras

  • distinguer tables, lignes et colonnes typées dans le modèle relationnel
  • choisir le bon type de données (INTEGER, DECIMAL, VARCHAR, DATE)
  • reconnaître une PRIMARY KEY et une FOREIGN KEY, et la relation qu'elle crée ;
  • modéliser un petit schéma à plusieurs tables reliées sans dupliquer les données.
Sommaire de la leçon

Jusqu'ici tu sais lire des colonnes d'une table avec SELECT … FROM. Mais d'où viennent ces tables, et comment plusieurs tables se relient-elles pour décrire un vrai système de vente ? C'est le rôle de la modélisation : organiser les données en tables propres et les relier entre elles.

Dans cette leçon, tu vas comprendre le modèle relationnel de façon intuitive : ce qu'est une table, comment typer ses colonnes, et surtout comment une table en désigne une autre grâce aux clés. C'est la fondation qui rendra possibles les jointures du module suivant.

Le modèle relationnel : tables, lignes, colonnes

Une base de données relationnelle range tout dans des tables. Imagine un tableur, mais avec des règles strictes. Le vocabulaire officiel mérite d'être posé une fois pour toutes :

  • Une table (on dit aussi relation) décrit une seule catégorie de choses : les clients, les commandes, les produits.
  • Une ligne (un enregistrement) représente un élément concret : un client précis, une commande précise.
  • Une colonne (un attribut) décrit une propriété, et chaque colonne a un type : du texte, un nombre, une date…

Voici une table clients minuscule pour fixer les idées.

idnomville
1Camille RoyLyon
2Hugo MarinNantes
3Inès LopezLille

Une table = un nom au pluriel, des lignes pour les éléments, des colonnes typées pour les propriétés.

Note

Le mot « relationnel » ne vient pas des « relations entre tables » mais du terme mathématique relation, qui désigne… une table. Les liens entre tables, eux, s'appellent des associations. Dans la pratique, on parle quand même couramment de « relations » entre tables, et on fera pareil ici.

Les types de données

Chaque colonne stocke un genre précis de valeur. Annoncer le bon type permet à la base de vérifier les données, de les trier correctement et de calculer dessus. Les grandes familles standard :

  • Entiers : INTEGER (ou INT) pour des nombres sans virgule, comme un identifiant ou une quantité.
  • Décimaux : DECIMAL(8,2) ou NUMERIC(8,2) pour de l'argent et les valeurs exactes (ici 8 chiffres dont 2 après la virgule).
  • Texte : VARCHAR(100) pour une chaîne de longueur limitée, TEXT pour un texte libre plus long.
  • Dates et heures : DATE pour un jour, TIMESTAMP pour un instant précis (date + heure).
  • Booléens : BOOLEAN pour un vrai/faux (par exemple « commande payée »).

Note

Les noms varient selon le SGBD. PostgreSQL respecte bien la norme (BOOLEAN, NUMERIC, TIMESTAMP). MySQL traite BOOLEAN comme un petit entier (0/1) et propose DATETIME. SQLite est le plus souple : il regroupe tout en quelques familles (INTEGER, REAL, TEXT, BLOB) et n'a ni vrai BOOLEAN ni vrai type DATE (on stocke les dates en texte ISO comme '2026-06-09').

La clé primaire (PRIMARY KEY)

Comment être sûr de désigner une ligne précise, sans confusion possible ? Avec une clé primaire : une colonne (ou un groupe de colonnes) dont la valeur est unique et jamais vide pour chaque ligne. Dans clients, c'est la colonne id. Deux clients peuvent s'appeler « Hugo Marin », mais leurs id diffèrent.

On la déclare dans la définition de la table avec PRIMARY KEY.

La clé primaire garantit l'unicité ; NOT NULL impose qu'un nom soit toujours renseigné.

Astuce

Préfère une clé primaire « technique » sans signification métier : un simple id numérique qui s'incrémente. Évite d'utiliser un e-mail ou un nom comme clé : ça change, et le jour où ça change, tu casses toutes les références. Beaucoup de SGBD savent générer ces id automatiquement (SERIAL ou GENERATED ALWAYS AS IDENTITY en PostgreSQL, AUTO_INCREMENT en MySQL, AUTOINCREMENT en SQLite).

La clé étrangère (FOREIGN KEY) et les relations

Voici le cœur du sujet. Une clé étrangère est une colonne qui pointe vers la clé primaire d'une autre table. C'est elle qui crée la relation entre deux tables. Une commande appartient à un client : la table commandes contient donc une colonne client_id qui reprend l'id d'un client.

client_id est une clé étrangère : chaque commande désigne un client existant.

Regardons les données. La même valeur 1 apparaît dans plusieurs commandes : ce sont toutes les commandes de Camille Roy.

idclient_iddate_achatmontant
1012026-05-0259.90
1112026-05-18120.00
1222026-05-2034.50
1332026-06-0189.00

C'est une relation un-à-plusieurs : un client peut avoir plusieurs commandes, mais chaque commande appartient à un seul client. Le « plusieurs » se trouve toujours du côté qui porte la clé étrangère (ici commandes).

Et la relation plusieurs-à-plusieurs ? Une commande peut contenir plusieurs produits, et un produit peut figurer dans plusieurs commandes. Impossible à exprimer avec une seule clé étrangère : on crée une table de liaison qui porte deux clés étrangères.

Une table de liaison transforme un plusieurs-à-plusieurs en deux relations un-à-plusieurs.

commande_idproduit_idquantite
105002
105011
115003
135021

Note

Le SGBD doit connaître la table produits avant de pouvoir la référencer. En pratique, on crée d'abord les tables « pointées » (clients, produits), puis celles qui les référencent (commandes, lignes_commande).

La normalisation, en intuitif

Normaliser, c'est ranger les données pour ne jamais répéter la même information à deux endroits. Imagine qu'on range tout dans une seule grande table « commandes » qui recopie le nom et la ville du client à chaque ligne :

idclient_nomclient_villemontant
10Camille RoyLyon59.90
11Camille RoyLyon120.00
12Hugo MarinNantes34.50

Le problème saute aux yeux : « Camille Roy / Lyon » est répété. Si Camille déménage, il faut corriger toutes ses lignes — et on en oubliera forcément une, créant des données contradictoires. La solution est exactement ce qu'on a fait : le nom et la ville vivent une seule fois dans clients, et commandes ne garde qu'un client_id qui pointe dessus. Une info, un seul endroit.

Note

Tu verras au module suivant que les jointures (JOIN) servent justement à recoller ces tables séparées le temps d'une requête : on stocke sans redondance, et on rassemble seulement quand on lit.

Le schéma complet en un coup d'œil

Rassemblons les quatre tables et leurs liens. Voici un schéma texte des relations (la flèche se lit « pointe vers ») :

PK = clé primaire, FK = clé étrangère. lignes_commande relie commandes et produits.

En résumé des cardinalités : un client a plusieurs commandes (un-à-plusieurs) ; une commande et un produit sont reliés plusieurs-à-plusieurs via lignes_commande. La table produits, elle, se définit tout simplement :

Une table de référence classique : un identifiant, un libellé texte, un prix décimal.

idlibelleprix
500Carnet A54.90
501Stylo plume24.00
502Lampe de bureau39.00

Cas réel

Ce schéma à quatre tables est exactement celui de n'importe quelle boutique en ligne. La page « Mon compte » lit clients ; le catalogue lit produits ; « Mes commandes » lit commandes filtrée par client_id ; et le détail d'une commande (« 2× Carnet, 1× Stylo ») lit lignes_commande. Le prix d'un produit n'est stocké qu'une fois dans produits — sauf que les vrais sites recopient volontairement le prix dans lignes_commande au moment de l'achat : c'est une dénormalisation maîtrisée, pour figer le prix payé même si le catalogue change ensuite.

Pièges fréquents

Piège fréquent

Dupliquer au lieu de relier. Recopier le nom du client dans chaque commande semble pratique sur le moment, mais tu crées de la redondance ingérable. Stocke l'info une fois, puis référence-la par sa clé.

Piège fréquent

Oublier la clé primaire. Sans elle, rien ne garantit l'unicité : tu peux insérer deux lignes identiques et plus aucune clé étrangère ne peut viser une ligne précise. Donne une PRIMARY KEY à chaque table.

Piège fréquent

Plusieurs-à-plusieurs sans table de liaison. Mettre plusieurs produit_id dans une case de commandes (« 500,501,502 ») casse le modèle : on ne peut plus filtrer ni compter proprement. Crée une table de liaison.

Piège fréquent

Types mal choisis. Stocke un prix en VARCHAR ou une date en texte libre, et tu ne peux plus additionner ni trier correctement (en texte, '100' < '9' car la comparaison se fait caractère par caractère !). Choisis DECIMAL pour l'argent et DATE pour les dates.

Glossaire

Table (relation)
Ensemble de lignes de même structure décrivant une catégorie de choses : clients, produits.
Type de données
Nature d'une colonne (INTEGER, DECIMAL, VARCHAR, DATE…) ; il conditionne tri, calcul et validation.
Clé primaire (PRIMARY KEY)
Colonne(s) identifiant chaque ligne de façon unique et non nulle ; de préférence un id technique.
Clé étrangère (FOREIGN KEY)
Colonne qui pointe vers la clé primaire d'une autre table ; elle crée la relation et garantit que la ligne visée existe.
Relation un-à-plusieurs
Un élément d'un côté, plusieurs de l'autre ; la clé étrangère est portée par le côté « plusieurs ».
Table de liaison
Table intermédiaire à deux clés étrangères qui exprime un plusieurs-à-plusieurs (ex. lignes_commande).
Normalisation
Organisation des tables pour ne jamais répéter une même information ; évite les incohérences lors des mises à jour.

Récap et vérification

  • Le modèle relationnel range les données en tables (lignes = enregistrements, colonnes = attributs typés).
  • Chaque colonne a un type : INTEGER, DECIMAL, VARCHAR/TEXT, DATE/TIMESTAMP, BOOLEAN.
  • La PRIMARY KEY identifie chaque ligne de façon unique ; la FOREIGN KEY pointe vers la clé primaire d'une autre table et crée la relation.
  • Un-à-plusieurs = clé étrangère du côté « plusieurs » ; plusieurs-à-plusieurs = table de liaison.
  • Normaliser, c'est stocker chaque info une seule fois pour éviter la redondance.

Vérifie ta compréhension

  1. Dans la table produits, quelle colonne ferais-tu clé primaire, et pourquoi pas libelle ?
  2. La colonne client_id de commandes est une clé étrangère : vers quelle table et quelle colonne pointe-t-elle ?
  3. Pourquoi a-t-on besoin de lignes_commande plutôt que de lister les produits dans commandes ?
