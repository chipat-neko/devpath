Module 07 · SQL en production — Leçon 17

Optimiser les requêtes et les index

~36 min Avancé Cours SQL recommandé

À la fin de cette leçon, tu sauras

  • Savoir lire un plan d'exécution avec EXPLAIN et EXPLAIN ANALYZE et distinguer coût estimé et temps réel ;
  • Savoir choisir le bon type d'index (B-tree, GIN/GiST, composite, partiel, couvrant, sur expression) selon la requête ;
  • Savoir reconnaître quand un index n'aide pas et le coût d'une condition non sargable ;
  • Savoir appliquer une méthode d'optimisation fondée sur la mesure et éviter le piège N+1.
Sommaire de la leçon

Tu sais déjà écrire des requêtes correctes. La question maintenant n'est plus « est-ce que ça renvoie le bon résultat ? » mais « est-ce que ça le renvoie vite, sur une table de dix millions de lignes, sans saturer le serveur ? ». Une même requête peut s'exécuter en 2 ms ou en 8 s selon la façon dont la base décide de la lire. Cette décision, c'est le travail du planificateur, et ton levier principal pour l'orienter, c'est l'index.

Dans cette leçon, tu vas apprendre à lire ce que la base fait réellement (et non ce que tu crois qu'elle fait), à choisir des index pertinents plutôt qu'à en empiler au hasard, et à reconnaître les situations où un index ne sert à rien. Règle d'or annoncée tout de suite : on ne devine pas, on mesure avec EXPLAIN.

Le planificateur de requêtes

Le SQL est déclaratif : tu dis quoi tu veux, pas comment l'obtenir. Pour une même requête, il existe souvent plusieurs chemins d'exécution (parcourir toute la table, passer par un index, joindre dans un sens ou dans l'autre…). Le planificateur évalue ces chemins, estime le coût de chacun à partir des statistiques de la table, et choisit le moins cher. EXPLAIN te montre le plan choisi sans exécuter la requête ; EXPLAIN ANALYZE l'exécute vraiment et ajoute les temps mesurés.

Lecture du plan : Seq Scan = parcours séquentiel de toute la table. cost=0.00..2310.00 donne le coût de démarrage (0) et le coût total estimé (2310, en unités arbitraires : ce n'est pas une durée). rows=12000 est le nombre de lignes estimé en sortie, width=36 la taille moyenne d'une ligne en octets. La ligne actual time donne le temps réel (premier chiffre = avant la première ligne, second = avant la dernière), rows=11873 le nombre réel de lignes, et Rows Removed by Filter: 88127 révèle l'essentiel : la base a lu 100 000 lignes pour n'en garder que ~12 %. Execution Time est la durée totale. Quand l'estimé (rows=12000) colle au réel (rows=11873), les statistiques sont saines.

Note

Les coûts (cost) sont sans unité et sans dimension réelle : ils servent à comparer des plans entre eux, pas à prédire une durée. Pour du temps, il faut ANALYZE. Et pour voir les lectures disque, ajoute EXPLAIN (ANALYZE, BUFFERS).

Les scans et les jointures

Trois façons de lire une table reviennent sans cesse. Le Seq Scan lit toute la table de bout en bout : optimal quand tu veux une grosse fraction des lignes ou que la table est petite. L'Index Scan traverse un index pour trouver les lignes ciblées puis va chercher chaque ligne dans la table : gagnant quand le filtre est très sélectif. L'Index Only Scan répond sans toucher la table, parce que toutes les colonnes demandées sont déjà dans l'index : le plus rapide.

Pour les jointures, le planificateur choisit aussi un algorithme : Nested Loop (pour chaque ligne de la table externe, on cherche les correspondances : excellent si la table interne a un index et que le côté externe est petit), Hash Join (on construit une table de hachage de la plus petite relation : efficace sur de gros volumes sans tri), Merge Join (les deux côtés sont triés sur la clé puis fusionnés : idéal quand les données sont déjà triées ou indexées). Tu n'imposes pas l'algorithme : tu donnes des index et de bonnes statistiques, le planificateur tranche.

Les index en profondeur

Le B-tree est l'index par défaut et couvre la grande majorité des besoins : égalité (=), plages (<, <=, >, BETWEEN), tri (ORDER BY) et préfixe de chaîne (LIKE 'abc%'). Pour les cas spéciaux : hash (égalité stricte uniquement), GIN et GiST pour les types composites — JSONB, plein-texte (tsvector), tableaux, données géographiques. Au-delà du type, plusieurs formes d'index changent tout :

Index composite (plusieurs colonnes). L'ordre des colonnes est décisif : l'index est utilisable pour un filtre sur la première colonne, ou sur la première et la deuxième, mais pas sur la deuxième seule. Pense à un annuaire trié par nom puis prénom : chercher par prénom seul n'aide pas.

Index partiel (avec WHERE) : n'indexe qu'un sous-ensemble, donc plus petit et plus rapide à maintenir. Parfait pour une valeur rare souvent recherchée.

Index couvrant (INCLUDE) : ajoute des colonnes « en charge utile » pour permettre un Index Only Scan sans qu'elles servent au filtrage.

Index sur expression : indexe le résultat d'une fonction, indispensable quand tu filtres sur une transformation (voir section suivante).

Quand un index n'aide pas

Un index n'est pas magique. Il est ignoré dans plusieurs cas. Faible sélectivité : si un filtre garde 60 % des lignes, passer par l'index (lire l'index puis aller chercher chaque ligne) coûte plus cher qu'un Seq Scan ; le planificateur a raison de ne pas l'utiliser. Petite table : sur 200 lignes, tout tient en mémoire, le Seq Scan gagne toujours. Condition non sargable : si tu appliques une fonction à la colonne indexée, l'index B-tree sur la colonne brute devient inutilisable.

Le mot sargable (Search ARGument ABLE) désigne une condition que la base peut résoudre via un index. La règle : laisse la colonne nue d'un côté de la comparaison. Au lieu de transformer la colonne, transforme la valeur ou réécris la plage.

Enfin, tout index a un coût en écriture : chaque INSERT, UPDATE ou DELETE doit aussi mettre à jour les index, et chaque index occupe de l'espace disque. Dix index sur une table très écrite peuvent diviser le débit d'insertion par deux. Un index se justifie par les lectures qu'il accélère, pas par principe.

Les statistiques (ANALYZE)

Le planificateur estime les coûts à partir de statistiques sur la distribution des données : nombre de lignes, valeurs distinctes, valeurs les plus fréquentes, histogrammes. Si ces statistiques sont périmées (après un gros chargement, par exemple), il estime mal et peut choisir un Seq Scan là où un index serait dix fois plus rapide. La commande ANALYZE recalcule ces statistiques.

Note

PostgreSQL lance un autovacuum qui réanalyse en arrière-plan. Mais après un import massif ou la création d'une table, force un ANALYZE manuel avant de juger un plan : un écart énorme entre rows estimé et réel dans EXPLAIN ANALYZE est le symptôme typique de stats périmées.

Une méthode, pas des recettes

Optimiser, ce n'est pas connaître par cœur quel index poser : c'est une boucle. 1. Mesurer : identifie la requête lente (avec EXPLAIN ANALYZE, et en production avec pg_stat_statements). 2. Comprendre : lis le plan, repère le Seq Scan coûteux, le Rows Removed by Filter élevé, le tri qui déborde sur disque. 3. Indexer ce qui est filtré (WHERE), joint (JOIN ... ON) ou trié (ORDER BY), en pensant à la sélectivité. 4. Vérifier : relance EXPLAIN ANALYZE et confirme que le plan a changé et que le temps a baissé. Sans l'étape 4, tu ne sais pas si ton index sert vraiment — il arrive qu'il ne soit même pas utilisé.

Astuce

Ne sélectionne que les colonnes utiles. Un SELECT * empêche souvent l'Index Only Scan (il faut retourner des colonnes absentes de l'index) et transporte des octets pour rien. Liste explicitement tes colonnes : c'est gratuit et ça aide le planificateur.

Cas réel

Le tableau de bord d'une boutique affiche « les 20 dernières commandes du client ». Sur une table commandes de douze millions de lignes, la page rame : EXPLAIN ANALYZE montre un Seq Scan suivi d'un Sort qui déborde sur disque — près de 6 s. Le filtre porte sur client_id et le tri sur creee_le DESC : on pose l'index composite (client_id, creee_le DESC), on relance ANALYZE, et le même plan devient un Index Scan qui lit 20 lignes déjà triées : 3 ms. Deux mille fois plus rapide, pour un seul index dans le bon ordre — trouvé en lisant le plan, pas en devinant.

Le piège N+1

Celui-ci ne vient pas du SQL mais du code applicatif, et c'est l'un des plus coûteux. Tu récupères une liste de N éléments, puis tu fais une requête par élément pour charger ses détails : 1 requête pour la liste + N requêtes pour les détails. Avec 200 commandes, c'est 201 allers-retours réseau là où une seule jointure suffirait.

Chaque requête a un coût fixe (réseau, parsing, planification) indépendant de sa taille. Regrouper N petites requêtes en une seule jointure (ou un WHERE id = ANY(:ids)) supprime ce coût fixe multiplié. La plupart des ORM proposent un chargement « eager » (par exemple un join fetch) pour éviter le N+1 : encore faut-il l'activer.

Pièges fréquents

Piège fréquent

Indexer à l'aveugle. Ajouter un index « au cas où » a un coût réel : ralentissement des écritures et espace disque. Mesure d'abord, indexe ensuite, et supprime les index jamais utilisés (PostgreSQL expose pg_stat_user_indexes pour les repérer).

Piège fréquent

Mauvais ordre dans un index composite. (a, b) n'accélère pas un filtre sur b seul. Place en premier la colonne utilisée pour l'égalité, ensuite celle de la plage ou du tri. Un index inutile parce que mal ordonné est aussi coûteux qu'un index utile.

Piège fréquent

Conclure sans EXPLAIN. « Ça a l'air plus rapide » n'est pas une mesure : variations de cache, données chaudes, charge du serveur faussent l'impression. Le plan et l'Execution Time sont les seuls juges, idéalement sur un volume représentatif.

Pour aller plus loin

Pour aller plus loin

Quand l'indexation ne suffit plus : le partitionnement découpe une énorme table par plage ou liste pour ne scanner qu'une partition ; les vues matérialisées (leçon 19) figent un calcul lourd ; pg_stat_statements classe tes requêtes par temps cumulé en production ; les index BRIN sont minuscules et parfaits sur des données naturellement ordonnées (séries temporelles) ; le tuning du planificateur (work_mem, random_page_cost) affine ses choix ; et le pooling de connexions (PgBouncer) réduit le coût fixe d'ouverture, ce qui atténue même les effets d'un N+1 résiduel.

Antisèche : du symptôme à la piste

Glossaire

Planificateur (query planner)
Composant du SGBD qui, pour une requête, évalue plusieurs plans d'exécution, estime leur coût d'après les statistiques, et retient le moins cher.
EXPLAIN / EXPLAIN ANALYZE
EXPLAIN affiche le plan et les coûts estimés sans exécuter ; EXPLAIN ANALYZE exécute vraiment la requête et ajoute les temps et lignes réels.
Seq Scan / Index Scan
Seq Scan : parcours de toute la table. Index Scan : on cible les lignes via un index puis on les lit dans la table ; gagnant si le filtre est sélectif.
Index Only Scan
Réponse obtenue depuis le seul index, sans lire la table, parce qu'il contient déjà toutes les colonnes demandées : la lecture la plus rapide.
Sélectivité
Fraction des lignes qu'un filtre conserve. Haute (peu de lignes) = un index aide ; faible (beaucoup de lignes) = le Seq Scan l'emporte.
Sargable
Search ARGument ABLE : condition qu'un index peut résoudre. Elle exige la colonne nue d'un côté ; une fonction sur la colonne (lower, EXTRACT) la rend non sargable.
Index composite
Index sur plusieurs colonnes, trié d'abord par la première : utilisable pour un filtre sur la première colonne (ou la première et la deuxième), mais pas sur la deuxième seule.
Piège N+1
Anti-pattern applicatif : 1 requête pour une liste de N éléments, puis N requêtes pour leurs détails. Se corrige par une jointure ou un chargement eager.

Récap et vérification

  • Planificateur : choisit le plan le moins coûteux selon les statistiques ; EXPLAIN montre le plan estimé, EXPLAIN ANALYZE ajoute les temps réels.
  • Scans : Seq Scan (toute la table), Index Scan (filtre sélectif), Index Only Scan (réponse depuis l'index seul).
  • Index : B-tree par défaut ; composites (l'ordre compte), partiels (WHERE), couvrants (INCLUDE), sur expression ; GIN/GiST pour JSON, plein-texte, géo.
  • Inutile quand : faible sélectivité, petite table, condition non sargable. Et tout index coûte en écriture.
  • Statistiques : ANALYZE les met à jour ; périmées = mauvais plans.
  • Méthode : mesurer, indexer ce qui est filtré/joint/trié, vérifier avec EXPLAIN. Éviter le N+1 côté appli.

Vérifie ta compréhension

  1. Quelle est la différence entre le coût (cost) et le temps (actual time) dans un plan, et lequel exige ANALYZE ?
  2. Pourquoi WHERE lower(email) = 'a@x.fr' ignore-t-il un index B-tree posé sur email, et comment corriger ?
  3. Tu as l'index (client_id, creee_le). Accélère-t-il un filtre sur creee_le seul ? Pourquoi ?
