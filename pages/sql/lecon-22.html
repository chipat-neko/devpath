Concurrence, transactions et niveaux d'isolation

~38 min Avancé Leçon 12 (transactions) recommandée

À la fin de cette leçon, tu sauras

  • reconnaître les anomalies de concurrence (lecture sale, non répétable, fantômes, mise à jour perdue) ;
  • choisir le bon niveau d'isolation (READ COMMITTED, REPEATABLE READ, SERIALIZABLE) ;
  • comprendre le MVCC : pourquoi les lecteurs ne bloquent pas les écrivains ;
  • poser un verrou explicite avec SELECT … FOR UPDATE et éviter les interblocages.
Sommaire de la leçon

Une base sert des dizaines de clients en même temps. Deux caissiers encaissent le même compte, deux acheteurs visent le dernier billet : sans précaution, les mises à jour se marchent dessus et l'argent — ou le stock — se met à mentir. Les transactions (leçon 12) rendent un groupe d'opérations « tout ou rien ». Cette leçon règle la question suivante : quand plusieurs transactions tournent en parallèle, que voient-elles l'une de l'autre ? C'est le rôle des niveaux d'isolation.

Le problème : la mise à jour perdue

L'anomalie la plus coûteuse. Deux transactions lisent la même valeur, la modifient chacune de leur côté, puis l'écrivent. La seconde écriture écrase la première : une mise à jour est perdue, sans erreur, sans trace.

Astuce — laisse la base calculer

Le remède le plus simple : ne lis pas pour réécrire côté application. Fais l'opération atomique en une requête : UPDATE comptes SET solde = solde + 50 WHERE id = 7. La base lit et écrit sous un même verrou de ligne : aucune fenêtre pour une mise à jour perdue.

Les quatre anomalies

La norme SQL décrit ce que deux transactions concurrentes peuvent se faire subir :

  • Lecture sale (dirty read) : lire une donnée qu'une autre transaction a modifiée mais pas encore validée (elle peut annuler !).
  • Lecture non répétable (non-repeatable read) : relire la même ligne dans la transaction et obtenir une valeur différente, car une autre a validé entre-temps.
  • Lignes fantômes (phantom) : relancer la même requête filtrée et voir apparaître de nouvelles lignes insérées par une autre transaction.
  • Mise à jour perdue : le scénario ci-dessus.

Note — le défaut varie

Le niveau par défaut n'est pas le même partout : PostgreSQL et Oracle démarrent en READ COMMITTED, MySQL/InnoDB en REPEATABLE READ. READ UNCOMMITTED (qui autorise les lectures sales) existe dans la norme mais est à fuir ; PostgreSQL le traite comme READ COMMITTED.

MVCC : lire sans bloquer

Comment PostgreSQL laisse des dizaines de lecteurs travailler sans les faire attendre ? Grâce au MVCC (contrôle de concurrence multiversion). Chaque transaction voit un instantané cohérent de la base pris à son début : une écriture crée une nouvelle version de la ligne sans détruire l'ancienne. Résultat : les lecteurs ne bloquent pas les écrivains, et réciproquement. Seules deux écritures sur la même ligne s'attendent.

Piège fréquent

Le MVCC laisse des versions mortes derrière lui. Sans nettoyage, la table gonfle : c'est le rôle de l'autovacuum de PostgreSQL. Une transaction laissée ouverte des heures empêche ce nettoyage (les vieilles versions restent « peut-être vues ») et fait enfler la base. Ne laisse jamais une transaction ouverte inutilement.

Verrouiller explicitement : SELECT … FOR UPDATE

Parfois on doit lire une ligne puis décider avant d'écrire (vérifier un stock, réserver un siège). Pour empêcher qu'un autre la modifie entre-temps, on la verrouille dès la lecture avec FOR UPDATE : toute autre transaction qui veut la même ligne attend la fin de la nôtre.

Cas réel

Le dernier billet de concert. Deux fans cliquent « acheter » à la même milliseconde. Sans verrou, les deux transactions lisent statut = 'libre', les deux vendent : survente, un fan à la porte, un remboursement et un avis furieux. Avec SELECT … FOR UPDATE, la première transaction verrouille la ligne ; la seconde attend, relit statut = 'vendu' et repart bredouille proprement. Les billetteries et les systèmes de réservation (avions, hôtels) reposent entièrement sur ce mécanisme — souvent doublé d'une contrainte d'unicité comme garde-fou ultime.

Les interblocages (deadlocks)

Le verrouillage a un revers : deux transactions peuvent s'attendre mutuellement, chacune tenant ce que l'autre réclame. Personne n'avance : c'est un interblocage. Les bases le détectent et sacrifient une des transactions (elle reçoit une erreur de deadlock et doit réessayer).

Astuce — éviter les interblocages

Un remède presque magique : accéder toujours aux ressources dans le même ordre (par exemple par id croissant). Si toutes les transactions verrouillent A avant B, aucune ne peut tenir B en attendant A : le cycle devient impossible. Garde aussi les transactions courtes et prévois un réessai automatique sur erreur de deadlock.

Pour aller plus loin

Deux stratégies s'opposent : le verrouillage pessimiste (FOR UPDATE : je verrouille avant, au cas où) et le verrouillage optimiste (je lis une colonne version, et à l'écriture j'ajoute WHERE version = :lu ; si 0 ligne modifiée, quelqu'un est passé avant → je recommence). L'optimiste brille quand les collisions sont rares. Regarde aussi FOR UPDATE SKIP LOCKED, la clé des files d'attente (chaque worker prend une tâche libre sans attendre les autres).

Antisèche

Glossaire

Isolation
Le « I » d'ACID : degré auquel une transaction est protégée des effets des autres transactions concurrentes.
Lecture sale (dirty read)
Lire une modification non encore validée par une autre transaction ; celle-ci peut annuler, rendant la lecture fausse.
Lecture non répétable
Relire la même ligne dans une transaction et obtenir une valeur différente, car une autre a validé entre les deux lectures.
Ligne fantôme (phantom)
Nouvelle ligne apparaissant dans le résultat d'une requête filtrée relancée, insérée par une transaction concurrente.
Mise à jour perdue (lost update)
Deux transactions lisent puis réécrivent la même donnée ; la seconde écriture efface la première.
MVCC
Contrôle de concurrence multiversion : chaque écriture crée une version, chaque transaction lit un instantané ; lecteurs et écrivains ne se bloquent pas.
SELECT … FOR UPDATE
Verrou explicite posé dès la lecture : les autres transactions qui veulent la même ligne attendent (verrouillage pessimiste).
Interblocage (deadlock)
Cycle d'attente où des transactions se bloquent mutuellement ; la base en annule une, qu'il faut réessayer.

Récap et vérification

  • Une mise à jour perdue s'évite en rendant l'opération atomique (SET x = x + …) plutôt qu'en lisant puis réécrivant côté application.
  • Les niveaux d'isolation ferment les anomalies : READ COMMITTED < REPEATABLE READ < SERIALIZABLE, du plus permissif au plus strict.
  • Le MVCC fait que les lecteurs ne bloquent pas les écrivains ; seules deux écritures sur la même ligne s'attendent.
  • SELECT … FOR UPDATE verrouille une ligne pour « lire puis décider » sans course ; alternative : le verrou optimiste par colonne version.
  • Les interblocages s'évitent par un ordre de verrous constant, des transactions courtes et un réessai sur erreur.
