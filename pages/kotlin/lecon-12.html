Module 3 · L'objet à la Kotlin — Leçon 12

Extensions et scope functions

~45 min Avancé Prérequis : leçon 11

À la fin de cette leçon, tu sauras

  • écrire des fonctions et propriétés d'extension et comprendre leur résolution statique ;
  • choisir la bonne scope function (let, run, apply, also, with) selon le receveur et la valeur retournée ;
  • exploiter let pour la null-safety et apply pour la configuration d'objet ;
  • reconnaître pourquoi la stdlib Kotlin est largement bâtie sur les extensions.
Sommaire de la leçon

Tu as sûrement déjà pesté contre une classe que tu ne pouvais pas modifier : String, une classe d'une bibliothèque, un type généré… En Java, tu finis avec des StringUtils.machin(s) qui se lisent à l'envers. Kotlin renverse le problème avec deux outils qui, ensemble, donnent à ton code ce côté fluide et lisible : les fonctions d'extension et les scope functions. Les premières te laissent « ajouter » des méthodes à n'importe quel type ; les secondes te laissent travailler sur un objet dans un petit bloc dédié, sans variable temporaire.

C'est exactement l'esprit du cours : la sécurité d'un typage fort, sans la cérémonie. Rien ici n'est de la magie à l'exécution : tout est résolu à la compilation, donc l'auto-complétion et le compilateur restent tes alliés. Allons-y.

Une fonction d'extension, c'est quoi ?

Une fonction d'extension se déclare comme une fonction normale, mais on préfixe son nom par le type receveur suivi d'un point. À l'intérieur, this désigne l'instance sur laquelle on appelle la fonction.

On appelle "kotlin".crier() exactement comme une méthode de la classe String. Pourtant, on n'a pas touché à String : la classe reste fermée, intacte. C'est tout l'intérêt — on étend des types qu'on ne possède pas.

Résolution statique : ce n'est PAS du monkey-patching

Si tu viens de Ruby ou de JavaScript, méfie-toi du réflexe « on rouvre la classe ». En Ruby, rouvrir String modifie réellement la classe pour tout le programme. En Kotlin, rien n'est ajouté à la classe : le compilateur transforme l'appel en un simple appel de fonction statique, en passant le receveur en argument caché.

Deux conséquences concrètes. D'abord, l'extension est résolue selon le type statique, pas le type réel à l'exécution : pas de polymorphisme dynamique. Ensuite, une extension n'accède qu'aux membres publics du type — elle ne peut pas lire les champs privés, contrairement à une vraie méthode.

Note

Si une extension porte le même nom et la même signature qu'un vrai membre de la classe, c'est toujours le membre qui gagne. L'extension est ignorée silencieusement : tu ne peux pas « remplacer » une méthode existante par une extension.

Propriétés d'extension

On peut aussi ajouter des propriétés. Comme une extension ne stocke aucun état (pas de champ), une propriété d'extension n'a pas de champ de stockage : on doit fournir un get() (et éventuellement un set) qui calcule la valeur.

Portée et imports

Une extension n'est visible que si elle est dans la portée (in scope). Déclarée au niveau d'un fichier dans un autre package, il faut l'importer comme n'importe quelle fonction — c'est ce qui évite de polluer tout le projet, contrairement au monkey-patching global.

C'est précisément ainsi que la stdlib Kotlin est bâtie. CharSequence.first(), Iterable.map(), Iterable.filter(), Int.coerceIn()… des milliers de fonctions de la bibliothèque standard sont des extensions. C'est pour ça que les collections Java vues depuis Kotlin gagnent soudain map, filter, groupBy sans que les classes Java n'aient changé.

Les scope functions : le tableau mental

Les scope functions sont cinq fonctions de la stdlib qui exécutent un bloc dans le contexte d'un objet. Tout se joue sur deux axes : comment on désigne l'objet dans le bloc (this ou it), et ce que la fonction retourne (le résultat de la lambda, ou l'objet lui-même).

Retiens la règle simple : apply/also retournent l'objet (parfait pour chaîner et configurer) ; let/run/with retournent le résultat du bloc (parfait pour transformer). Et : it pour let/also, this pour run/apply/with.

apply : configurer un objet

let : le nullable et la transformation

C'est l'usage star : combiné à ?., le bloc let ne s'exécute que si la valeur est non-nulle, et it y est de type non-nullable.

also : l'effet de bord (souvent loguer)

also reçoit it et retourne l'objet : idéal pour glisser un log ou une vérification au milieu d'une chaîne sans casser le flux.

run et with : regrouper des appels sur un objet

Différence pratique entre run et with : run est une extension (objet.run { }, donc s'enchaîne avec ?. sur un nullable), tandis que with(objet) { } se lit mieux quand l'objet n'est pas nullable et qu'on veut juste « travailler avec » lui.

Pièges fréquents

Piège fréquent

Confondre la valeur retournée. apply et also retournent l'objet : val x = obj.apply { 42 } donne obj, pas 42. Si tu veux récupérer le résultat du bloc, c'est let, run ou with.

Piège fréquent

Ne pas imbriquer les scope functions. Un let { it.run { with(it2) { … } } } devient illisible et les it/this se télescopent. Si tu en imbriques deux, nomme explicitement le paramètre (.let { serveur -> … }) ou découpe en plusieurs étapes lisibles.

Piège fréquent

Croire qu'une extension peut « surcharger » une méthode existante ou voir l'état privé d'une classe. Non : un membre réel gagne toujours, et l'extension ne voit que le public. Pour de la vraie logique métier liée à l'état interne, écris une méthode dans la classe.

Pour aller plus loin

Pour aller plus loin

On peut écrire des extensions sur un type nullable (fun String?.ouVide() = this ?: ""), sur un type générique (fun <T> T.aussi(...)), et même des extensions locales à une classe (membres extensions). Regarde aussi takeIf/takeUnless, deux cousines des scope functions très pratiques pour les conditions.

Un cas réel

Cas réel — le style « idiomatique » d'Android repose là-dessus

Quand Google a poussé Kotlin sur Android, il a livré les KTX — des paquets qui ne sont que des fonctions d'extension. view.isVisible = true, bundleOf("id" to 42), prefs.edit { putString("clé", v) } : chacune enrobe une API Java verbeuse dans une extension lisible, sans toucher aux classes du framework. Le tandem avec les scope functions est partout : on configure une vue ou un builder avec apply { } (Paint().apply { color = RED; strokeWidth = 4f }), on garde le résultat nullable d'un findViewById ou d'un appel réseau avec ?.let { }, et on glisse un log au milieu d'une chaîne avec also { }. Même logique côté serveur : les builders d'OkHttp, de Ktor ou d'Exposed se lisent comme des blocs apply. Résultat : un code qui se lit de gauche à droite, dans l'ordre où on pense — exactement ce que ces deux outils cherchent à offrir.

Glossaire

Fonction d'extension
Fonction déclarée fun Type.nom() qui s'appelle comme une méthode du Type, sans modifier ni ouvrir la classe.
Propriété d'extension
Propriété ajoutée à un type ; faute de champ de stockage, elle doit fournir un get() (et parfois un set()) au lieu d'une valeur initiale.
Type receveur
Le type placé avant le point dans la déclaration (String dans String.crier()) ; à l'intérieur, this le désigne.
Résolution statique
Une extension est choisie selon le type déclaré de la variable, pas son type réel à l'exécution : aucun polymorphisme dynamique, accès au public seulement.
Scope function
Une des cinq fonctions de la stdlib (let, run, with, apply, also) qui exécute un bloc dans le contexte d'un objet.
this vs it
Deux façons de nommer l'objet dans le bloc : receveur implicite (this, pour run/apply/with) ou paramètre unique (it, pour let/also).
Monkey-patching
Le fait de modifier réellement une classe à l'exécution (Ruby, JS) ; ce que les extensions Kotlin ne font pas, puisqu'elles compilent en appels statiques.
Opérateur Elvis (?:)
Fournit une valeur de repli quand l'expression de gauche est null ; se marie souvent à ?.let { } pour gérer une branche « sinon ».

Récap et vérification

  • Une fonction d'extension préfixe le nom par Type. ; à l'intérieur, this est le receveur.
  • Résolution statique : appel compilé en fonction statique, selon le type déclaré, accès au public uniquement — ce n'est pas du monkey-patching.
  • Une propriété d'extension exige un get() (aucun champ de stockage).
  • Les extensions s'importent ; la stdlib Kotlin en est massivement constituée.
  • apply/also retournent l'objet (configurer, loguer) ; let/run/with retournent le bloc (transformer).
  • it pour let/also, this pour run/apply/with ; let brille avec ?..

Vérifie ta compréhension

  1. Pourquoi bestiole.nom() de l'exemple affiche-t-il « Animal » alors que l'objet réel est un Chien ?
  2. Tu veux créer un objet, régler trois propriétés et récupérer cet objet : quelle scope function ? Et si tu voulais plutôt récupérer le résultat d'un calcul sur l'objet ?
  3. Quelle scope function utilises-tu pour n'exécuter un bloc que si une variable nullable n'est pas nulle, et comment s'appelle la valeur non-nulle dans le bloc ?
