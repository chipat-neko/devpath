Tester son code Kotlin

~40 min Intermédiaire Coroutines (leçon 13) utiles

À la fin de cette leçon, tu sauras

  • écrire des tests avec JUnit 5 et kotlin.test ;
  • utiliser les assertions idiomatiques et le cycle de vie ;
  • tester qu'une exception est levée avec assertFailsWith ;
  • tester une coroutine avec runTest.
Sommaire de la leçon

Kotlin tourne sur la JVM : il hérite donc de tout l'outillage de test de Java, à commencer par JUnit 5. Mais Kotlin ajoute sa propre bibliothèque, kotlin.test, dont les assertions se lisent comme du Kotlin idiomatique, et un support dédié pour tester les coroutines. Cette leçon te donne le filet de sécurité indispensable à tout code amené à durer : des tests qu'une commande rejoue en une seconde.

Le premier test

Un test est une fonction annotée @Test qui exerce ton code et affirme un résultat. Avec kotlin.test, les assertions ont l'ordre naturel (obtenu, attendu) et des noms clairs.

La structure classique est AAA : Arrange (créer la calculatrice), Act (appeler additionner), Assert (assertEquals). On lance avec gradle test (ou en un clic dans l'IDE) : le rapport dit lesquels passent et lesquels échouent, avec un message « attendu 5, obtenu 4 ».

Le cycle de vie

Quand plusieurs tests partagent une préparation, on l'extrait dans une fonction @BeforeTest, exécutée avant chaque test. Chaque test repart ainsi d'un état neuf et indépendant.

lateinit var (vu au module 1) convient bien ici : la propriété est initialisée dans @BeforeTest, juste avant chaque test. L'indépendance est une règle d'or : l'ordre d'exécution ne doit jamais changer le résultat.

Tester les exceptions

Tester qu'une erreur est bien levée fait partie du contrat. assertFailsWith vérifie qu'un bloc lance l'exception attendue, et la renvoie pour l'inspecter.

Le code qui doit échouer est passé dans un lambda de fin (la syntaxe { … } après la fonction, typique de Kotlin) : assertFailsWith l'exécute, attrape l'exception et vérifie son type. Si rien n'est levé, le test échoue.

Tester une coroutine

Les fonctions suspend (module 4) ne peuvent s'appeler que depuis une coroutine. Pour les tester, on utilise runTest de kotlinx-coroutines-test : il fournit un contexte de coroutine et, bonus, saute les délais (delay) pour que les tests restent instantanés.

Remarque la forme fun … = runTest { … } : le test est l'appel à runTest. Tout ce qui est à l'intérieur peut appeler des fonctions suspend. Et comme runTest avance le temps virtuellement, un delay(1000) ne ralentit pas la suite de tests.

Astuce

Comme en Java, l'esprit TDD (rouge → vert → refactor) s'applique : écris le test d'abord, vois-le échouer, écris le code minimal pour le faire passer. Kotlin s'y prête bien grâce à des tests concis. Pour des assertions encore plus expressives, la bibliothèque Kotest propose un style resultat shouldBe 5.

Un cas réel

Cas réel — le filet qui permet de refactorer sans peur

Une équipe doit remanier le calcul des frais bancaires : du code central, touché par dix écrans. Sans tests, chaque modification est une roulette russe ; avec une suite de tests, la peur disparaît. Le scénario type : un développeur pousse un changement, la CI (intégration continue) lance gradlew test à chaque commit, un test retraitTropGrandLeveUneException passe au rouge — la régression est attrapée avant d'atteindre la production, pas par un client mécontent. Mieux : comme les appels réseau de l'app sont des fonctions suspend, la suite qui les couvre tournerait en minutes si chaque delay était réel ; grâce à runTest et son temps virtuel, des centaines de tests asynchrones s'exécutent en quelques secondes. C'est ce qui rend le cycle rouge → vert → refactor viable au quotidien : on modifie le code, on relance la suite, un feu vert confirme que rien n'a cassé. Les tests ne sont pas une corvée : ils sont ce qui autorise à changer le code sereinement.

Glossaire

@Test
Annotation marquant une fonction comme test : l'outil (JUnit) l'exécute et rapporte si ses assertions passent ou échouent.
Assertion
Vérification qui compare une valeur obtenue à une valeur attendue (assertEquals, assertTrue…) ; si elle échoue, le test rougit.
AAA (Arrange-Act-Assert)
Structure d'un test : préparer les données (Arrange), exécuter l'action testée (Act), vérifier le résultat (Assert).
@BeforeTest
Fonction exécutée avant chaque test pour recréer un état neuf, garantissant l'indépendance des tests vis-à-vis de leur ordre.
assertFailsWith
Assertion qui échoue si le bloc fourni ne lève pas l'exception attendue ; elle retourne l'exception capturée pour vérifier son message.
runTest
Constructeur de kotlinx-coroutines-test qui ouvre un scope de coroutine à temps virtuel : il permet d'appeler des fonctions suspend et saute les delay.
kotlin.test
Bibliothèque d'assertions idiomatiques et multiplateformes de Kotlin, posée par-dessus un moteur comme JUnit 5.
TDD
Test-Driven Development : écrire le test d'abord (rouge), le code minimal pour le faire passer (vert), puis nettoyer (refactor).

Récap et vérification

  • Kotlin teste avec JUnit 5 + kotlin.test ; une fonction @Test structurée en AAA.
  • Les assertions (assertEquals, assertTrue, assertFailsWith…) comparent attendu et obtenu.
  • @BeforeTest recrée un état neuf : les tests sont indépendants (souvent avec lateinit var).
  • assertFailsWith<T> { … } vérifie qu'une exception est levée et la renvoie.
  • runTest { … } teste les fonctions suspend et saute les delay.

Exercice 3Défi
