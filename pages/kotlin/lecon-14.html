Module 4 · Kotlin en pratique — Leçon 14

Interopérabilité Java et outillage

~44 min Intermédiaire Prérequis : leçon 13

À la fin de cette leçon, tu sauras

  • savoir appeler du code Java depuis Kotlin en gérant la nullabilité des types platform ;
  • savoir exposer du Kotlin à Java avec @JvmStatic et @JvmOverloads ;
  • savoir lire un build.gradle.kts minimal et lancer les tâches build, run, test ;
  • savoir mettre en place qualité (ktlint, detekt), tests (kotlin.test) et documentation KDoc.
Sommaire de la leçon

Le vrai superpouvoir de Kotlin, ce n'est pas une syntaxe plus courte que celle de Java : c'est de tourner sur la même JVM et de partager le même bytecode. Concrètement, une classe Kotlin et une classe Java peuvent vivre dans le même projet, se compiler ensemble et s'appeler l'une l'autre sans la moindre passerelle. C'est ce qui rend la migration possible classe par classe, et qui met tout l'écosystème Java (chaque bibliothèque Maven, chaque framework) à portée de main.

Dans cette leçon, on traverse la frontière dans les deux sens, puis on installe l'outillage qui transforme un fichier .kt isolé en projet sérieux : Gradle, contrôle de style, analyse statique, tests et documentation. Fil rouge habituel : la sécurité du typage fort, sans la cérémonie de Java.

Appeler Java depuis Kotlin

Aucune cérémonie : une classe Java s'importe et s'utilise comme une classe Kotlin. Le compilateur lit directement le .class ou le .jar.

Kotlin réinterprète même certaines API Java : un getter getName() devient accessible en obj.name, et setName(x) en obj.name = x. La JVM ne voit aucune différence ; toi, tu écris du Kotlin idiomatique.

Les types platform : la vigilance aux frontières

Java n'a pas de null-safety dans son système de types : n'importe quelle référence peut valoir null. Quand Kotlin reçoit une valeur de Java sans annotation, il ne peut pas trancher entre String et String?. Il l'appelle alors un type platform, noté String! dans les messages de l'IDE.

Piège fréquent

Un type platform désactive le filet de sécurité de Kotlin : aucun avertissement à la compilation, mais une NullPointerException possible à l'exécution. Aux frontières avec du Java non annoté, déclare explicitement le type en ? ou vérifie la valeur tout de suite.

La bonne nouvelle : si le code Java porte les annotations @Nullable / @NotNull (paquets jakarta.annotation, JetBrains, Android…), Kotlin les respecte et bascule le type en String? ou String non-null. Le platform type ne surgit que pour le Java « nu ».

Appeler Kotlin depuis Java

L'autre sens demande de connaître comment Kotlin se projette dans le bytecode. Un fichier Outils.kt contenant des fonctions de haut niveau est compilé dans une classe OutilsKt avec des méthodes static.

Deux annotations rendent l'API plus naturelle côté Java :

  • @JvmStatic génère une vraie méthode statique pour un membre d'object ou de companion object (sinon Java doit passer par .INSTANCE).
  • @JvmOverloads génère une surcharge par paramètre à valeur par défaut : Java n'a pas les arguments par défaut de Kotlin, cette annotation comble l'écart.

Qualité : style et analyse statique

Le style officiel Kotlin est documenté et outillé. Deux familles d'outils :

  • Formatage : ktlint (ou ktfmt) vérifie et corrige l'indentation, l'ordre des imports, les espaces — selon les Kotlin coding conventions.
  • Analyse statique : detekt repère les odeurs de code (fonctions trop longues, complexité, code mort) au-delà du simple style.

Astuce

Branche ktlint et detekt en plugins Gradle dès le début du projet, et fais-les tourner dans ta CI. Le style cesse d'être un sujet de revue de code : la machine tranche, tu te concentres sur la logique.

Documentation : KDoc et Dokka

KDoc est l'équivalent Kotlin de Javadoc : un commentaire /** … */ avant une déclaration, avec des balises @param, @return et la syntaxe Markdown.

L'outil Dokka (plugin Gradle officiel) transforme ces KDoc en site HTML de documentation d'API. Et pour les scripts ponctuels, Kotlin propose les fichiers .kts (Kotlin Script) : un script.kts s'exécute via kotlin script.kts sans projet ni main — pratique pour de l'automatisation rapide.

Pièges fréquents

  • Types platform ignorés. Recevoir un String! et le stocker tel quel propage un null silencieux. Annote côté Java ou type explicitement (: String?) à la frontière.
  • Oublier @JvmStatic / @JvmName. Sans elles, l'API vue depuis Java devient verbeuse (.INSTANCE, FichierKt). Pense Java quand tu exposes du Kotlin à du Java.
  • Mélanger build.gradle (Groovy) et build.gradle.kts. Les exemples du web sont souvent en Groovy ; la syntaxe du Kotlin DSL diffère (parenthèses, set(...)).
  • SAM et fonctions. Une interface Java à méthode unique s'appelle avec un lambda Kotlin, mais une interface Kotlin exige fun interface pour le même confort.

Un cas réel

Cas réel — migrer un backend Java vers Kotlin sans tout réécrire

Une équipe hérite d'une application Java de plusieurs centaines de milliers de lignes : la réécrire d'un bloc serait suicidaire. Grâce au bytecode partagé, elle procède classe par classe. Un nouveau service ? Écrit en Kotlin, il appelle sans friction les dépôts Java existants (les getX() deviennent obj.x). Une classe Java retouchée ? L'IDE la convertit en Kotlin en un clic, et le reste du code Java continue de l'appeler via MaClasseKt et les @JvmStatic ajoutés aux points d'entrée. Le vrai travail n'est pas la syntaxe : c'est de traquer les types platform aux frontières — chaque String! reçu d'une vieille API Java non annotée est un null en puissance. L'équipe annote donc le code Java stratégique (@Nullable/@NotNull) ou type explicitement en ? à la réception. C'est exactement le chemin qu'a suivi Android : d'un SDK 100 % Java à un écosystème où Kotlin est le langage recommandé, sans jamais casser l'existant.

Glossaire

Interopérabilité
Capacité de Kotlin et Java à cohabiter dans un même projet, à se compiler ensemble et à s'appeler mutuellement : ils partagent la même JVM et le même bytecode.
Type platform (T!)
Type d'une valeur venue de Java non annoté : Kotlin ignore si elle est nulle et te laisse choisir. Traité comme non-null par erreur, il provoque une NullPointerException à l'exécution.
@JvmStatic
Annotation qui génère une vraie méthode statique pour un membre d'object ou de companion object, évitant à Java de passer par .INSTANCE.
@JvmOverloads
Annotation qui crée, pour Java, une surcharge par paramètre à valeur par défaut ; comble l'absence d'arguments par défaut côté Java.
Gradle
Outil de build de l'écosystème JVM : il compile, teste, empaquette et gère les dépendances. Le wrapper ./gradlew fixe sa version par projet.
Kotlin DSL
Écriture du script de build en Kotlin (build.gradle.kts) plutôt qu'en Groovy : autocomplétion et vérification de types dans la configuration elle-même.
ktlint / detekt
Outils de qualité : ktlint formate selon les conventions officielles ; detekt détecte les odeurs de code (complexité, code mort) au-delà du style.
KDoc / Dokka
KDoc est le format de commentaire de documentation (/** … @param @return */) ; Dokka, le plugin Gradle qui le transforme en site HTML d'API.

Récap et vérification

  • Kotlin et Java partagent la JVM : appel direct dans les deux sens, migration classe par classe, écosystème Maven entier disponible.
  • Les types platform (String!) viennent du Java non annoté : vigilance null à la frontière ; les annotations @Nullable/@NotNull rétablissent la sécurité.
  • @JvmStatic et @JvmOverloads rendent l'API Kotlin naturelle vue de Java.
  • build.gradle.kts (Kotlin DSL) pilote build, run, test ; ktlint/detekt assurent la qualité, kotlin.test/JUnit 5 les tests, KDoc/Dokka la doc.
