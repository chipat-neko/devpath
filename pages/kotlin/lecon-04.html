Module 1 · Les bases de Kotlin — Leçon 04

Les fonctions

~45 min Débutant Prérequis : leçon 3

À la fin de cette leçon, tu sauras

  • savoir déclarer une fonction avec fun et choisir entre corps en bloc et corps en expression ;
  • savoir remplacer la surcharge à rallonge par des valeurs par défaut combinées aux arguments nommés ;
  • savoir utiliser vararg et l'opérateur spread * ;
  • savoir organiser son code en petites fonctions pures, top-level ou locales.
Sommaire de la leçon

Tu sais déjà déclarer des variables avec val et var, manipuler les types de base et piloter le flot d'exécution. Il est temps de donner une structure à tout ça : les fonctions. En Kotlin, elles sont au cœur du langage — à tel point qu'elles n'ont même pas besoin d'une classe pour exister.

Tu vas retrouver ici le fil conducteur du cours : toute la sécurité d'un typage fort, sans la cérémonie de Java. Une fonction Kotlin se déclare en une ligne quand c'est possible, accepte des valeurs par défaut, des arguments nommés, et t'encourage à découper ton code en petites unités pures et lisibles.

Déclarer une fonction : fun

Le mot-clé fun ouvre la déclaration, suivi du nom, des paramètres (chacun avec son type, après le nom, comme pour les variables), puis du type de retour après un deux-points :

Deux différences avec Java sautent aux yeux : le type vient après le nom (a: Int plutôt que int a), et le type de retour ferme la signature au lieu de l'ouvrir. Autre détail important : les paramètres d'une fonction Kotlin sont toujours des val — impossible de les réassigner dans le corps, et c'est une bonne chose pour la lisibilité.

Le corps en expression : une fonction = une valeur

Quand le corps se résume à une seule expression, Kotlin te permet de remplacer le bloc { return … } par un simple =. Le type de retour est alors inféré :

C'est l'application directe d'un principe que tu as déjà croisé avec if et when : Kotlin préfère les expressions (qui produisent une valeur) aux instructions. Une fonction courte est une valeur calculée, autant l'écrire comme telle.

Astuce

Pour une fonction publique d'une bibliothèque, les conventions officielles recommandent d'écrire le type de retour explicitement, même en corps d'expression : fun double(x: Int): Int = x * 2. Le lecteur (et le compilateur de tes utilisateurs) n'a pas à deviner.

Unit : le « void » qu'on n'écrit jamais

Une fonction qui ne renvoie rien d'utile renvoie en réalité Unit, l'équivalent du void de Java — à une nuance près : Unit est un vrai type, avec une unique valeur. En pratique, tu ne l'écris jamais, il est omis par convention :

Note

Pourquoi un type plutôt qu'un mot-clé void ? Parce qu'un vrai type se glisse partout où un type est attendu — dans un générique, par exemple. C'est un de ces choix discrets qui rendent Kotlin plus régulier que Java.

Valeurs par défaut et arguments nommés : l'idiome Kotlin

En Java, une fonction avec des options se décline en une cascade de surcharges, ou en pattern builder. Kotlin règle le problème à la racine : un paramètre peut porter une valeur par défaut, et l'appelant peut nommer les arguments qu'il fournit.

Remarque au passage qu'une valeur par défaut peut utiliser les paramètres précédents (email dérive de nom), et que la virgule finale après actif: Boolean = true, est autorisée — c'est même le style moderne, qui rend les diffs Git plus propres.

La combinaison des deux mécanismes est l'idiome Kotlin par excellence : sans arguments nommés, impossible de fournir admin sans fournir email d'abord ; avec eux, chaque appel ne dit que ce qui compte. Compare creerUtilisateur("Ada", "ada@exemple.fr", true, true) — quatre valeurs dont on devine mal le rôle — à creerUtilisateur(nom = "Ada", admin = true) : le second se lit comme une phrase. Adieu la surcharge à rallonge.

Fonctions top-level et fonctions locales

La surcharge existe quand même

Les valeurs par défaut couvrent la plupart des cas, mais la surcharge classique reste possible : plusieurs fonctions du même nom, différenciées par leurs types de paramètres. Elle garde son utilité quand les versions font des choses réellement différentes selon le type :

Règle de pouce : valeurs par défaut pour les variantes « même logique, options en plus », surcharge pour les variantes « logique différente selon le type ».

En pratique : un mini convertisseur d'unités

Assemblons tout ça avec les conventions officielles : noms en camelCase, verbes ou descriptions claires, et surtout des petites fonctions pures — qui dépendent uniquement de leurs paramètres et ne modifient rien à l'extérieur. Faciles à lire, à tester, à composer :

Chaque fonction fait une seule chose et la dit dans son nom. La conversion ne sait rien de l'affichage, l'affichage ne sait rien des kilomètres : tu peux recombiner ces briques à l'infini.

Pour aller plus loin

Pour aller plus loin

Les fonctions Kotlin réservent d'autres superpouvoirs que tu découvriras bientôt : les lambdas et fonctions d'ordre supérieur (une fonction passée en paramètre, type (Int) -> Int), les fonctions d'extension qui « ajoutent » des méthodes à des types existants, les fonctions infix (1 to "un") et inline. Côté coulisses JVM : une fonction top-level est compilée en méthode statique d'une classe ConversionsKt, et @JvmOverloads génère les surcharges Java correspondant à tes valeurs par défaut.

Un cas réel

Cas réel — pourquoi Jetpack Compose est agréable à écrire

Dans Jetpack Compose (la boîte à outils d'interface moderne d'Android), afficher un texte s'écrit Text("Bonjour", fontSize = 20.sp, color = Color.Red). Or cette fonction déclare une vingtaine de paramètres — police, alignement, interligne, nombre de lignes maximum… Sans valeurs par défaut, il faudrait tous les fournir à chaque appel, ou multiplier les surcharges par dizaines comme dans les anciennes API Java d'Android. Grâce aux arguments nommés et aux valeurs par défaut, chaque appel ne mentionne que ce qui sort de l'ordinaire et se lit comme une phrase. Ce seul mécanisme du langage explique une bonne part du confort de Compose — et de la plupart des bibliothèques Kotlin modernes.

Glossaire

fun
Mot-clé qui déclare une fonction : fun nom(params): TypeRetour, le type suivant toujours le nom.
Corps en expression
Fonction dont le corps est une seule expression après = ; le type de retour est inféré et il n'y a pas de return.
Unit
Type des fonctions qui ne renvoient rien d'utile (équivalent du void de Java), omis par convention.
Valeur par défaut
Valeur donnée à un paramètre (x: Int = 0) et utilisée quand l'appelant ne le fournit pas.
Argument nommé
À l'appel, on précise nom = valeur ; cela permet de sauter des paramètres à valeur par défaut et clarifie l'appel.
vararg
Marque un paramètre acceptant un nombre variable d'arguments ; il se comporte comme un tableau dans le corps.
Spread (*)
Opérateur qui « déballe » un tableau en arguments individuels pour alimenter un vararg : moyenne(*notes).
Fonction top-level / locale
Top-level : déclarée hors de toute classe. Locale : déclarée dans une autre fonction, et visible d'elle seule.

Récap et vérification

  • fun nom(param: Type): TypeRetour { … } ; les paramètres sont des val.
  • Corps en expression : fun double(x: Int) = x * 2, type de retour inféré (mais explicite-le sur tes API publiques).
  • Unit = le void de Java, toujours omis dans le code idiomatique.
  • Valeurs par défaut + arguments nommés = l'idiome qui remplace la surcharge à rallonge ; la surcharge reste là pour les logiques différentes par type.
  • vararg accepte un nombre variable d'arguments ; le spread * déballe un tableau à l'appel.
  • Les fonctions vivent où tu veux : top-level (sans classe, contrairement à Java) ou locales (dans une autre fonction).
  • Vise des petites fonctions pures, nommées en camelCase, qui font une seule chose.

Vérifie ta compréhension

  1. Quelle est la différence entre fun f(x: Int): Int { return x + 1 } et fun f(x: Int) = x + 1 ? Laquelle préfères-tu pour une API publique, et pourquoi ?
  2. Avec fun envoyer(dest: String, copie: String = "", urgent: Boolean = false), comment appelles-tu la fonction en ne précisant que dest et urgent ?
  3. Tu as un val mots = arrayOf("a", "b") et une fonction fun coller(vararg morceaux: String) : que dois-tu écrire pour lui passer le tableau, et pourquoi coller(mots) échoue-t-il ?
