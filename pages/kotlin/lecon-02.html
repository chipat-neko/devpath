Module 1 · Les bases de Kotlin — Leçon 02

Types, chaînes et null-safety

~45 min Débutant Prérequis : leçon 1

À la fin de cette leçon, tu sauras

  • savoir déclarer les types de base de Kotlin et convertir explicitement avec toLong(), toDouble() ou toIntOrNull() ;
  • savoir construire des chaînes avec les templates $nom et ${expr} et les raw strings """ ;
  • savoir lire un type nullable et distinguer String de String? ;
  • savoir manier ?., ?:, let et le smart cast pour éliminer les NullPointerException à la compilation.
Sommaire de la leçon

En Java, n'importe quelle variable de type objet peut valoir null — et rien dans le type ne te prévient. Le résultat, tu le connais peut-être : des NullPointerException qui explosent en production, à des kilomètres de l'endroit où le null est apparu. Tony Hoare, l'inventeur de la référence nulle en 1965, a lui-même qualifié son idée d'« erreur à un milliard de dollars ». Kotlin prend le problème à la racine : le type d'une variable dit explicitement si elle peut être nulle, et le compilateur refuse tout code qui ignorerait cette possibilité.

Dans cette leçon, on pose d'abord les types de base et la manière dont Kotlin gère les conversions, on découvre les templates de chaînes — un idiome que tu utiliseras dans chaque programme —, puis on plonge dans la null-safety : String?, ?., ?:, let et le smart cast. À la fin, tu sauras pourquoi les NPE sont, en Kotlin, des erreurs de compilation plutôt que des crashs nocturnes.

Tout est objet : les types de base

Kotlin propose les types numériques classiques — Int (32 bits), Long (64 bits), Double (flottant 64 bits), Float — ainsi que Boolean, Char et String. Contrairement à Java, il n'y a pas de dualité visible entre primitifs (int) et objets (Integer) : en Kotlin, tu manipules toujours des objets, avec des méthodes. Le compilateur se charge en coulisses d'utiliser des primitifs JVM quand c'est possible, pour la performance.

Et comme on l'a vu à la leçon précédente, l'inférence de type rend les annotations souvent superflues : val age = 32 suffit, le compilateur sait que c'est un Int. On annote quand ça clarifie l'intention, par exemple pour forcer un Long : val population = 8_000_000_000L (le suffixe L) ou val population: Long = 8_000_000_000.

Conversions : toujours explicites

En Java, un int se glisse silencieusement dans un long ou un double. Kotlin refuse toute conversion implicite, même « sans perte » : tu dois appeler une méthode de conversion. C'est un choix délibéré — chaque changement de type est visible dans le code, donc relisible.

Astuce

Pour convertir une saisie utilisateur, préfère toujours toIntOrNull() ou toDoubleOrNull() à toInt() : tu obtiens null au lieu d'une exception, et la null-safety de Kotlin (qu'on voit juste après) t'oblige à gérer ce cas proprement.

Templates de chaînes : adieu la concaténation

Là où Java enchaîne les + ("Bonjour " + nom + ", tu as " + age + " ans"), Kotlin interpole directement dans la chaîne. C'est l'idiome central de manipulation de texte : $variable pour une variable simple, ${expression} avec accolades pour tout le reste.

Les accolades sont obligatoires dès qu'il y a un appel de méthode ou une opération.

Raw strings et méthodes courantes

Pour du texte multiligne — JSON, SQL, ASCII art —, les raw strings délimitées par trois guillemets conservent les retours à la ligne et n'interprètent pas les \n. La méthode trimIndent() retire l'indentation commune, ce qui permet d'indenter le bloc avec ton code sans polluer le résultat.

String vs String? : le type dit si null est possible

Voici le cœur de la leçon. En Kotlin, String et String? sont deux types différents. Le premier garantit une valeur non nulle ; le second, avec son point d'interrogation, annonce que null est une valeur légitime. Cette distinction vaut pour tous les types : Int?, Boolean?, tes propres classes… Et le compilateur fait respecter le contrat des deux côtés.

Relis bien la seconde erreur : le compilateur t'interdit d'appeler .length sur un String? sans précaution. Là où Java aurait laissé passer et planté à l'exécution, Kotlin transforme la NPE potentielle en erreur de compilation. C'est exactement ça, « attraper le milliard de dollars » avant qu'il ne coûte quoi que ce soit.

Naviguer dans le nullable : ?. et ?: (elvis)

Deux opérateurs couvrent la majorité des situations. L'appel sûr ?. exécute l'appel si la valeur est non nulle, et renvoie null sinon — sans jamais planter. L'opérateur elvis ?: fournit une valeur de repli quand l'expression à sa gauche vaut null. (Penche la tête à gauche : ?: ressemble à la banane d'Elvis.)

Note

L'elvis accepte aussi return ou throw à droite : val nom = saisie ?: return sort de la fonction si la saisie est nulle. Après cette ligne, nom est garanti non nul — un idiome très courant en début de fonction.

Smart cast, let… et le dernier recours !!

Si tu vérifies explicitement qu'une valeur n'est pas nulle, le compilateur s'en souvient : à l'intérieur du if, la variable est « smart-castée » vers son type non nul, et tu l'utilises sans ?.. Autre idiome : let exécute un bloc uniquement si la valeur est non nulle, la valeur étant disponible sous le nom it. Reste enfin !!, l'assertion non-nulle : « je jure que ce n'est pas null, plante si je me trompe ». C'est littéralement réintroduire la NPE de Java — à éviter sauf cas très justifié.

Pièges fréquents

Piège fréquent

Saupoudrer !! pour « faire taire le compilateur » annule tout l'intérêt de la null-safety : chaque !! est une NPE en puissance. Quand tu es tenté d'en écrire un, demande-toi quel repli a du sens (?:), ou si un ?.let ou un smart cast n'exprime pas mieux l'intention.

Piège fréquent

Le smart cast ne fonctionne pas sur une propriété var d'une classe : entre ta vérification != null et l'usage, un autre code pourrait la remettre à null. Le compilateur refuse donc le cast. La parade idiomatique : copier dans un val local, ou utiliser ?.let { }.

Piège fréquent

"3.5".toInt() lève une NumberFormatException : la chaîne doit représenter un entier exact. Passe par toDoubleOrNull() puis toInt() si tu veux tronquer, et garde le réflexe des variantes OrNull pour toute donnée externe.

Pour aller plus loin

Pour aller plus loin

Quand Kotlin appelle du code Java, les types venus de Java sont des « platform types » (notés String! dans les messages du compilateur) : Kotlin ne sait pas s'ils peuvent être nuls, et te fait confiance. Les annotations @Nullable et @NotNull côté Java lèvent l'ambiguïté. Explore aussi requireNotNull() et checkNotNull(), qui valident une précondition avec un message d'erreur clair, et la fonction filterNotNull() sur les collections — tu la retrouveras au module sur les collections.

Un cas réel

Cas réel — la première cause de crash sur Android

Pendant des années, la NullPointerException a été l'une des toutes premières causes de plantage des applications Android — un déréférencement de null oublié quelque part dans des millions de lignes de Java. En rendant la nullabilité visible dans le type et vérifiée à la compilation, Kotlin déplace ces bugs de la production (crash chez l'utilisateur, à 3 h du matin) vers l'éditeur (souligné en rouge avant même de lancer l'appli). C'est l'un des arguments les plus cités par les équipes qui expliquent leur passage à Kotlin : moins de crashs liés au null, visibles dans les tableaux de bord de stabilité.

Glossaire

Type nullable
Type suffixé de ? (ex. String?) autorisant la valeur null, par opposition au type non-nul.
Null-safety
Système du compilateur qui transforme les NullPointerException potentielles en erreurs de compilation.
Appel sûr (?.)
Exécute l'appel si le récepteur est non nul, renvoie null sinon, sans planter.
Opérateur elvis (?:)
Fournit une valeur de repli quand l'expression de gauche vaut null.
Smart cast
Conversion automatique vers le type non-nul après une vérification if (x != null).
let
Fonction de portée qui exécute un bloc avec la valeur sous le nom it, utile après ?..
Assertion non-null (!!)
Affirme qu'une valeur n'est pas nulle ; lève une NPE si elle l'est — à éviter.
Raw string
Chaîne entre """ conservant les sauts de ligne, sans interpréter les échappements.

Récap et vérification

  • Tous les types sont des objets : Int, Long, Double, Boolean, Char, String — le compilateur optimise en primitifs JVM tout seul.
  • Aucune conversion implicite : toLong(), toDouble(), toIntOrNull()… chaque changement de type est explicite.
  • Les templates "$nom" et "${expr}" remplacent la concaténation ; les raw strings """ gèrent le multiligne avec trimIndent().
  • String? autorise null, String l'interdit — et le compilateur fait respecter le contrat.
  • ?. appelle sans planter, ?: fournit un repli, let exécute si non nul, le smart cast suit tes if (x != null) — et !! reste l'exception, pas la règle.

Vérifie ta compréhension

  1. Pourquoi val grand: Long = monInt ne compile-t-il pas, alors que l'équivalent Java fonctionne ?
  2. Quelle est la différence de comportement entre surnom?.length et surnom!!.length quand surnom vaut null ?
  3. Dans quel cas le smart cast après if (x != null) est-il refusé par le compilateur, et quelles sont les deux parades idiomatiques ?
