Module 6 · Kotlin avancé et écosystème — Leçon 20

Kotlin Multiplateforme : un code, toutes les cibles

~50 min Avancé Interop Java (leçon 14) et coroutines utiles

À la fin de cette leçon, tu sauras

  • comprendre un module de code partagé compilé vers plusieurs cibles ;
  • déclarer une API avec expect et la réaliser par plateforme avec actual ;
  • distinguer ce qui se partage (logique) de ce qui reste natif (interface) ;
  • situer l'écosystème (Compose Multiplatform, Ktor, SQLDelight).
Sommaire de la leçon

Écrire deux fois la même règle de calcul — une fois en Kotlin pour Android, une fois en Swift pour iPhone — c'est deux fois le travail, deux fois les bugs, et deux vérités qui divergent avec le temps. Kotlin Multiplateforme (souvent abrégé KMP) propose une autre voie : écrire la logique une seule fois, en Kotlin, et la faire compiler vers plusieurs cibles — la JVM (Android, serveur, bureau), le natif (iOS via LLVM) et le JavaScript (web). Cette leçon en explique le principe et le mécanisme central, expect/actual.

Un seul code, plusieurs cibles

Un projet KMP range son code par source set. Le dossier commonMain contient le code commun — du Kotlin pur, sans dépendance à une plateforme. À côté, des dossiers spécifiques (androidMain, iosMain, jsMain…) n'accueillent que ce qui a besoin des API d'une plateforme précise.

Le compilateur produit un artefact par cible : un .jar/.aar pour la JVM, un framework pour iOS, un paquet .js pour le web. Le même fichier commonMain voyage dans les trois.

expect / actual : une API commune, une réalisation par plateforme

Certaines choses n'existent que sur une plateforme donnée : le nom du système, l'accès au stockage local, un générateur d'UUID… Kotlin résout cela avec un couple de mots-clés. Dans commonMain, on déclare ce qu'on attend avec expect (sans corps). Dans chaque source set de plateforme, on fournit l'implémentation avec actual.

Le code commun appelle plateforme() sans jamais savoir qui répondra : c'est le compilateur qui, pour chaque cible, branche la bonne actual. La résolution est statique (à la compilation), pas dynamique : aucun coût à l'exécution, et une erreur claire si une plateforme oublie de fournir son actual.

Ce qui se partage, ce qui reste natif

La règle est simple : on partage la logique, on garde l'interface native. Modèles de données, appels réseau, accès à la base, validation, règles métier : tout cela descend dans commonMain. L'interface graphique, elle, reste écrite avec l'outil natif de chaque plateforme — Jetpack Compose côté Android, SwiftUI côté iOS — pour un rendu et des performances irréprochables.

Attention

KMP ne partage pas l'interface par défaut. Sans Compose Multiplatform, chaque plateforme écrit son écran séparément (Compose, SwiftUI…). Ne promets pas « une app pour toutes les plateformes en un clic » : la promesse réaliste de KMP, c'est de mutualiser la logique — souvent 40 à 70 % d'une application — pas forcément les pixels.

Astuce

Commence petit : extrais d'abord un module sans interface — par exemple la validation d'un formulaire ou le calcul d'un panier — et partage-le entre Android et iOS. Tu récoltes le bénéfice (une seule source de vérité, testée une fois) sans toucher aux écrans existants.

Un cas réel

Cas réel — l'application Cash App partage son cœur entre Android et iOS

Cash App (l'application de paiement de Block, ex-Square, utilisée par des dizaines de millions de personnes) a migré une grande partie de sa logique vers Kotlin Multiplateforme. Les modèles, les appels réseau, la logique de présentation (ce que l'écran doit afficher) vivent dans un module commun ; les écrans restent natifs — Compose sur Android, SwiftUI sur iOS. Le gain n'est pas cosmétique : une règle de paiement corrigée l'est une seule fois, et elle est identique sur les deux téléphones. Fini le scénario classique où le bug est réparé côté Android trois semaines avant iOS parce que deux équipes ont réécrit la même règle. D'autres l'emploient à grande échelle (Netflix pour son outil interne Prodicle, Philips, McDonald's) : le point commun est toujours le même — partager ce qui doit rester cohérent, garder natif ce qui doit rester rapide et intégré.

Pour aller plus loin

Pour aller plus loin

L'écosystème KMP repose sur des bibliothèques déjà multiplateformes : kotlinx.coroutines et kotlinx.serialization (vues aux leçons 13 et 19) fonctionnent dans commonMain, Ktor fait les appels réseau, SQLDelight gère la base de données, et Compose Multiplatform partage aussi l'interface (desktop, Android, iOS, web). Explore ensuite les classes expect (pas seulement les fonctions), les bibliothèques publiées pour toutes les cibles, et le pont Kotlin/Native ↔ Swift.

Glossaire

Kotlin Multiplateforme (KMP)
Technologie permettant d'écrire du code Kotlin une fois et de le compiler vers plusieurs plateformes (JVM, Native, JS).
Cible (target)
Plateforme visée par la compilation d'un module KMP : Android/JVM, iOS/Native, Web/JS, bureau…
Source set
Dossier de code associé à une (ou plusieurs) cible(s) : commonMain pour le partagé, androidMain, iosMain… pour le spécifique.
commonMain
Le source set commun : du Kotlin pur, sans dépendance à une plateforme, compilé vers toutes les cibles.
expect
Mot-clé déclarant, dans le commun, une API attendue sans corps — un contrat que chaque plateforme doit honorer.
actual
Mot-clé fournissant, dans un source set de plateforme, l'implémentation concrète d'une déclaration expect.
Compose Multiplatform
Boîte à outils d'interface qui étend Jetpack Compose à plusieurs plateformes, pour partager aussi l'UI.
Kotlin/Native
Compilateur produisant du binaire natif (via LLVM), notamment pour iOS, sans machine virtuelle.

Récap et vérification

  • Un projet KMP écrit sa logique dans commonMain et la compile vers plusieurs cibles.
  • Les dossiers androidMain, iosMain… n'accueillent que le code spécifique à une plateforme.
  • expect déclare une API dans le commun ; actual la réalise par plateforme, résolu à la compilation.
  • On partage la logique ; l'interface reste native (sauf Compose Multiplatform).

Vérifie ta compréhension

  1. Dans quel source set place-t-on le code partagé entre toutes les plateformes ?
  2. À quoi servent respectivement expect et actual ?
  3. Par défaut, l'interface graphique est-elle partagée entre Android et iOS ? Pourquoi ?

Exercices

Exercice 1Échauffement

Range ces trois éléments dans le bon source set : (a) une data class Produit, (b) l'accès au stockage local iOS, (c) une fonction de validation d'e-mail. Lesquels vont dans commonMain ?

Voir une solution

commonMain : (a) la data class Produit et (c) la validation d'e-mail — ce sont de la logique et des données pures, sans API de plateforme. iosMain : (b) l'accès au stockage local iOS, qui dépend d'une API propre à iOS (exposée au commun via un expect).

Exercice 2Application

Dans commonMain, déclare une fonction attendue uuid(): String (chaque plateforme a son générateur), puis écris son actual pour Android (renvoie java.util.UUID.randomUUID().toString()).

Voir une solution

Le code commun peut désormais appeler uuid() ; chaque cible fournira son implémentation.

Exercice 3Défi

Explique en une phrase pourquoi expect/actual ne coûte rien à l'exécution, contrairement à un choix fait dynamiquement avec un when sur le nom de la plateforme.

Voir une solution

Parce que la liaison est statique : le compilateur choisit la bonne actual pour chaque cible à la compilation, si bien que le binaire produit contient déjà la seule implémentation utile. Un when (plateforme) à l'exécution testerait la condition à chaque appel et embarquerait toutes les branches — un surcoût inutile ici.
