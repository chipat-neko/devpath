Module 4 · Kotlin en pratique — Leçon 15

Premiers pas vers Android

~50 min Intermédiaire Prérequis : leçon 14

À la fin de cette leçon, tu sauras

  • lire et comprendre une fonction @Composable simple (Text, Column, Row) en reliant la syntaxe aux trailing lambdas du cours ;
  • expliquer la recomposition et le rôle de remember { mutableStateOf(…) } pour gérer l'état d'une UI ;
  • situer la structure d'un projet Android (Activity, manifest, Gradle) et le rôle d'un ViewModel ;
  • connaître les autres débouchés de Kotlin (Ktor, Multiplatform, Compose Desktop) et bâtir un plan d'apprentissage.
Sommaire de la leçon

Depuis la leçon 1, tu as appris un langage : val par défaut, les expressions partout, la null-safety, les data class, les lambdas et les fonctions d'extension. Cette leçon répond à la question naturelle : concrètement, où va ce Kotlin que tu maîtrises maintenant ? La réponse principale s'appelle Android, mais ce n'est pas la seule.

Bonne nouvelle : tu n'as presque rien de nouveau à apprendre côté langage. Android moderne, c'est Kotlin + Jetpack Compose, et Compose repose entièrement sur des notions que tu connais déjà — surtout les trailing lambdas. Cette leçon est un panorama : tu vas lire du vrai code Compose sans même ouvrir Android Studio, et repartir avec un plan d'apprentissage clair.

Jetpack Compose : une UI déclarative

Pendant des années, on construisait les écrans Android en XML, puis on les « gonflait » et les manipulait en code. Compose renverse l'approche : tu décris l'interface en Kotlin, sous forme de fonctions. Une fonction d'UI s'appelle un composable et porte l'annotation @Composable.

Une fonction qui retourne Unit mais qui « émet » de l'UI : c'est tout. Pas de balise XML, pas de findViewById. Le nom commence par une majuscule par convention (comme un type), pour distinguer les composables des fonctions ordinaires.

Note

Text, Column, Button… sont eux-mêmes des composables fournis par Compose. Tu construis ton écran en appelant des composables depuis tes propres composables : c'est une composition, d'où le nom.

Empiler des éléments : Column et Row

Pour disposer plusieurs éléments, Compose offre des conteneurs. Column empile verticalement, Row aligne horizontalement. Et ici la magie du cours opère : leur dernier paramètre est une lambda, donc tu utilises la syntaxe du trailing lambda que tu connais — les accolades après l'appel.

Relis ce Column { … } : c'est exactement la même forme que list.forEach { … } ou repeat(3) { … } vus plus tôt. Le bloc entre accolades est le contenu du composable, décrit par d'autres appels de composables. Une UI Compose, c'est un arbre de fonctions imbriquées par des trailing lambdas.

L'état et la recomposition

Une UI déclarative décrit l'écran pour un état donné. Quand l'état change, Compose ré-exécute les composables concernés pour redessiner : c'est la recomposition. Tu ne mets jamais l'écran à jour à la main ; tu changes l'état, et l'UI suit.

Pour qu'une valeur déclenche la recomposition, on l'enveloppe dans un mutableStateOf(…). Et pour qu'elle survive aux recompositions successives (sinon elle serait recréée à chaque passage), on l'entoure de remember { … }.

Le by est la délégation de propriété : il te laisse lire et écrire clics comme un Int ordinaire, alors que la vraie valeur vit dans l'objet d'état. Sans by, tu écrirais clics.value. Note aussi onClick = { clics++ } : encore une lambda, passée comme argument cette fois.

Astuce

Une bonne pratique Compose est le state hoisting : faire « remonter » l'état hors du composable d'affichage. Le composable reçoit alors la valeur en paramètre et un callback (onClick) pour signaler les actions — ce qui le rend pur, testable et réutilisable.

À quoi ressemble un projet Android

Soyons honnêtes : un projet Android, c'est plus que des composables. Voici les pièces que tu rencontreras, en survol :

  • Activity : le point d'entrée d'un écran. Une MainActivity appelle setContent { … } et y place ton composable racine.
  • AndroidManifest.xml : la carte d'identité de l'app — nom, icône, activités déclarées, permissions demandées (caméra, internet…).
  • Gradle : l'outil de build. Le fichier build.gradle.kts (en Kotlin DSL, justement) liste tes dépendances et versions.
  • Émulateur : un téléphone virtuel fourni par Android Studio pour tester sans appareil physique.

Tu n'as pas besoin de tout comprendre aujourd'hui : Android Studio génère ce squelette pour toi. Retiens juste que setContent { } est la frontière entre le monde Android historique et le monde Compose.

Séparer l'UI et l'état : le ViewModel

Mettre toute la logique dans les composables devient vite ingérable, et l'état y serait perdu à chaque rotation d'écran. Android propose le ViewModel : une classe qui détient l'état et la logique métier, survit aux changements de configuration, et expose des données que l'UI observe.

L'idée à mémoriser : le composable affiche, le ViewModel décide. Cette séparation est un pilier de l'architecture Android moderne (souvent appelée MVVM).

Au-delà d'Android : Ktor, Multiplatform, Desktop

Deux autres horizons, à mentionner avec honnêteté :

  • Kotlin Multiplatform (KMP) : partager la logique métier (réseau, base de données, règles) entre Android et iOS, tout en gardant l'UI native de chaque plateforme. C'est mûr et utilisé en production par de grandes apps ; Compose Multiplatform (UI partagée jusqu'à iOS) est plus récent et progresse vite, mais vérifie l'état de l'écosystème avant de t'y engager pour un produit critique.
  • Compose Desktop : les mêmes composables que tu viens de lire, mais pour des applications de bureau Windows, macOS et Linux.

Note

Côté emploi, Kotlin est aujourd'hui le langage par défaut d'Android (recommandation officielle de Google), avec une forte demande mobile. Le serveur Kotlin/Ktor grandit, souvent en complément d'écosystèmes Java/Spring existants. KMP ouvre des postes « cross-platform ». Globalement, savoir Kotlin + Compose est un atout très recherché.

Pièges fréquents

Piège fréquent

Oublier remember autour de mutableStateOf. Un var x = mutableStateOf(0) nu est recréé à zéro à chaque recomposition : ton compteur semble « bloqué » à 0. Règle : dans un composable, c'est presque toujours remember { mutableStateOf(…) }.

Deux autres erreurs classiques : muter une variable ordinaire (un simple var clics = 0 sans état Compose) en espérant rafraîchir l'écran — Compose ne « voit » pas ce changement, donc rien ne bouge. Et lancer un travail long directement dans le corps d'un composable (appel réseau, boucle lourde) : comme un composable peut être ré-exécuté très souvent, on délègue ces tâches au ViewModel et aux coroutines.

Pour aller plus loin

Pour aller plus loin

Installe Android Studio (gratuit), puis suis les codelabs Google « Jetpack Compose » — des tutoriels pas-à-pas, du « Hello World » à une vraie app. Garde la doc officielle Kotlin et Android Developers ouverte : c'est la référence vivante, toujours à jour. Pour le serveur, le générateur de projet Ktor (start.ktor.io) te crée un squelette en deux clics.

Un cas réel

Cas réel — pourquoi les grandes apps sont passées à Compose

Pendant dix ans, une app Android, c'était des écrans en XML « gonflés » puis modifiés à la main via findViewById : verbeux, source de bugs (une vue oubliée, un état incohérent entre XML et code). Google a introduit Compose pour supprimer cette double source de vérité. Aujourd'hui le Play Store lui-même, de nombreux écrans de l'app Google, et des produits comme Twitter/X ou des pans d'apps bancaires sont écrits en Compose. Le gain concret n'est pas cosmétique : un composable qui applique le state hoisting (état remonté, reçu en paramètre) est prévisualisable dans Android Studio sans lancer l'app, et testable en isolation — on lui passe une valeur, on vérifie l'affichage. La séparation ViewModel décide / composable affiche permet en plus de survivre aux rotations d'écran sans perdre l'état, un problème historique d'Android que le XML gérait très mal. Moins de code, moins de bugs d'état, itération plus rapide : voilà pourquoi Compose est devenu le défaut.

Glossaire

Jetpack Compose
Boîte à outils moderne d'UI Android : on décrit l'interface en Kotlin sous forme de fonctions, au lieu de la déclarer en XML.
@Composable
Annotation d'une fonction qui « émet » de l'UI dans l'arbre de composition. Elle ne retourne rien ; appeler Text(…) ou Button(…) ajoute l'élément à l'écran.
Recomposition
Ré-exécution automatique, par Compose, des composables qui lisent un état modifié, afin de redessiner l'écran pour le nouvel état.
mutableStateOf
Crée une valeur observable : la modifier déclenche la recomposition des composables qui la lisent.
remember
Conserve une valeur (souvent un mutableStateOf) à travers les recompositions ; sans lui, l'état serait recréé à chaque passage.
State hoisting
Patron qui « remonte » l'état hors d'un composable : l'enfant reçoit la valeur en paramètre et un callback pour signaler les actions, ce qui le rend pur, prévisualisable et testable.
ViewModel
Classe qui détient l'état et la logique métier, survit aux changements de configuration (rotation) et expose des données observées par l'UI : le composable affiche, le ViewModel décide.
Ktor
Framework serveur (et client) HTTP de JetBrains, écrit en Kotlin avec le même style de trailing lambdas ; débouché « backend » de Kotlin, à côté d'Android.

Récap et vérification

Le module se referme : depuis la leçon 1 tu as construit la sécurité d'un typage fort sans la cérémonie de Java — et tu viens de voir que ces mêmes outils (lambdas, expressions, null-safety) sont exactement ce qui rend Compose lisible.

  • Une UI Compose est un arbre de fonctions @Composable, assemblées par des trailing lambdas (Column { … }, Button(onClick = …) { … }).
  • L'état réactif s'écrit remember { mutableStateOf(…) } ; le modifier déclenche la recomposition.
  • Un projet Android s'articule autour d'une Activity, du manifest, de Gradle et de l'émulateur ; le ViewModel sépare l'état de l'affichage.
  • Kotlin va au-delà : Ktor (serveur), Multiplatform (logique partagée iOS/Android) et Compose Desktop.

Vérifie ta compréhension

  1. Pourquoi une fonction @Composable qui ne retourne rien peut-elle quand même « créer » un bouton à l'écran ?
  2. Que se passe-t-il si tu écris mutableStateOf(0) sans remember dans un composable ? Pourquoi ?
  3. En une phrase, quel est le rôle du ViewModel par rapport au composable ?
