Module 3 · L'objet à la Kotlin — Leçon 09

Data classes, enums et sealed classes

~50 min Intermédiaire Prérequis : leçon 8

À la fin de cette leçon, tu sauras

  • savoir écrire une data class et exploiter equals, toString, copy et la destructuration générés ;
  • savoir définir une enum class avec propriétés et méthodes, et faire un when exhaustif dessus ;
  • savoir modéliser une hiérarchie fermée avec sealed class et laisser le compilateur t'imposer tous les cas ;
  • savoir créer un singleton avec object et regrouper constantes et fabriques dans un companion object.
Sommaire de la leçon

En Java, modéliser une donnée toute bête — un point, un utilisateur, un état — réclame une cérémonie pénible : un constructeur, des getters, equals, hashCode, toString, parfois un constructeur de copie. Vite cinquante lignes pour porter deux champs. Kotlin renverse la charge : tu décris ce que la donnée est, et le compilateur génère tout le reste. C'est exactement notre fil conducteur — la sécurité d'un typage fort, sans la cérémonie.

Dans cette leçon, tu vas assembler trois outils complémentaires : la data class pour les porteurs de données, l'enum class pour un ensemble fermé de valeurs, et la sealed class pour une hiérarchie fermée de variantes. En prime, object et companion object pour les singletons et l'équivalent du static de Java.

La data class : la donnée en une ligne

Une data class est une classe dont le rôle est de transporter des données. Tu déclares ses propriétés dans le constructeur primaire, et Kotlin génère pour toi equals, hashCode, toString, copy et les fonctions de destructuration.

L'équivalent Java de ce Point — constructeur, deux getters, equals, hashCode, toString — frôle la cinquantaine de lignes. Ici, une seule, et == compare déjà les valeurs (en Java, == compare les références ; c'est .equals() qui compare les valeurs). Kotlin inverse la convention : == appelle equals, et === compare l'identité.

Note

Seules les propriétés déclarées dans le constructeur primaire entrent dans equals, hashCode, toString et copy. Une propriété ajoutée dans le corps de la classe en est exclue.

copy et l'immutabilité pratique

Avec des val partout, comment « modifier » un point ? On ne le modifie pas : on en crée une nouvelle version. La fonction copy générée produit une copie en ne changeant que les champs nommés.

C'est l'immutabilité pratique : tes objets ne changent jamais sous tes pieds, mais produire une variante reste trivial. Tu profites de la sûreté du non-mutable sans la lourdeur de tout reconstruire à la main.

Piège fréquent

copy est une copie de surface. Si une propriété est une liste mutable ou un autre objet mutable, la copie pointe vers la même instance. Préfère des types immuables (List plutôt que MutableList) dans tes data classes.

La destructuration

Une data class fournit gratuitement des opérateurs component1(), component2()… qui permettent de la « déballer » en plusieurs variables d'un coup.

L'ordre des variables suit l'ordre des propriétés du constructeur, pas leur nom. Si tu n'as besoin que d'une partie, remplace les composantes inutiles par _ : val (x, _) = p.

Piège fréquent

La destructuration se fait par position, pas par nom. Si tu écris val (y, x) = p, tu intervertis silencieusement les valeurs sans la moindre erreur : y reçoit component1() (le x du point). Nomme tes variables avec soin.

L'enum class : un ensemble fermé de valeurs

Une enum class liste un nombre fixe et connu de valeurs. Chaque entrée est un singleton. Tu peux lui attacher des propriétés et même des méthodes.

Chaque entrée porte ici un paramètre degres, et oppose() est une vraie méthode partagée. ordinal donne l'index de l'entrée (à partir de 0), entries renvoie la liste de toutes les valeurs (préfère-la à l'ancien values(), qui recréait un tableau à chaque appel).

Note

entries est apparu en Kotlin 1.9 et est la forme recommandée aujourd'hui. Tu croiseras encore values() et valueOf("NORD") dans du code plus ancien : ils fonctionnent toujours, mais entries évite l'allocation d'un nouveau tableau à chaque appel.

Le when exhaustif sur enum

Le vrai bénéfice d'un ensemble fermé apparaît avec when : comme le compilateur connaît toutes les valeurs possibles, il peut vérifier que tu les traites toutes. Utilisé comme expression, le when n'a alors pas besoin de branche else.

Cette erreur de compilation est une alliée : ajoute une valeur à l'enum plus tard, et chaque when non couvert refusera de compiler tant que tu n'auras pas traité le nouveau cas. Le filet de sécurité est automatique.

La sealed class : une hiérarchie fermée

Une enum énumère des valeurs fixes. Une sealed class (ou sealed interface) énumère des types fixes : un ensemble fermé de sous-classes, toutes connues à la compilation, chacune pouvant porter ses propres données. C'est l'outil idéal pour le pattern « résultat ».

Comme toutes les sous-classes de Resultat sont déclarées au même endroit, le when sur is est lui aussi exhaustif : pas d'else. Et grâce au smart cast, dans la branche is Resultat.Succes, r est automatiquement vu comme un Succes : tu accèdes à r.donnees sans cast manuel. Le compilateur t'oblige à traiter chaque variante et te donne le bon type dans chacune.

Note

Le out dans Resultat<out T> rend le type covariant : un Resultat<Int> est alors acceptable là où un Resultat<Number> est attendu. C'est aussi ce qui autorise Echec à hériter de Resultat<Nothing> et à se glisser partout, puisque Nothing est sous-type de tout. Tu reverras la variance en détail dans la leçon sur les génériques ; retiens pour l'instant qu'elle fait fonctionner ce patron sans heurt.

Astuce

enum vs sealed : choisis l'enum quand chaque cas est une valeur unique sans données propres (les jours de la semaine). Choisis la sealed class quand chaque cas transporte des données différentes (un succès porte un résultat, un échec porte un message).

object et companion object

Le mot-clé object déclare un singleton : une seule instance, créée à la première utilisation, sans constructeur à appeler. Le companion object, lui, est un objet attaché à une classe : c'est là que tu ranges l'équivalent des membres static de Java — constantes et fabriques.

Le constructeur de Utilisateur est privé : on passe par la fabrique creer du companion (qui, lui, a accès au constructeur privé de la classe). C'est un patron courant pour contrôler la création des instances. Note que const val exige une valeur connue à la compilation (chaîne ou nombre).

Étude de cas : les états d'un téléchargement

Assemblons tout : modélisons les états par lesquels passe un téléchargement. Certains états n'ont pas de données (en attente), d'autres en portent (la progression, le fichier, l'erreur). C'est le terrain parfait pour une sealed class mêlant object et data class.

Un état sans donnée devient un object (inutile d'en créer plusieurs exemplaires), un état porteur devient une data class. Pour EnAttente, on compare par valeur (pas de is nécessaire) ; pour les autres, is déclenche le smart cast. Si demain tu ajoutes un état Annule, le when cessera de compiler tant que tu ne l'auras pas traité : ta logique d'affichage reste forcément à jour.

Pièges fréquents

Piège fréquent

Mettre une propriété mutable ou un type mutable dans une data class casse l'intérêt de equals/hashCode : deux objets « égaux » peuvent diverger après coup, et un objet utilisé comme clé de Map devient introuvable si son hash change. Garde tes data classes immuables.

Trois autres erreurs classiques : oublier le ; avant les membres d'une enum qui a des méthodes (Kotlin l'exige) ; ajouter une branche else inutile dans un when sur sealed/enum, ce qui désactive le contrôle d'exhaustivité (ajoute un cas plus tard, le compilateur ne te préviendra plus) ; et croire que copy clone en profondeur — il ne copie que la surface.

Pour aller plus loin

Pour aller plus loin

Explore les value classes (@JvmInline value class) pour typer fortement un identifiant sans surcoût, les data object (un object avec un toString lisible, pratique pour les états sans donnée d'une sealed class), et le fait que les sous-classes d'une sealed doivent vivre dans le même module et le même paquet. Côté Android, ce trio data/enum/sealed est la base de la modélisation d'état (UI state) avec Jetpack Compose.

Un cas réel

Cas réel — l'état d'un écran dans une appli Android

Dans une application mobile moderne (Jetpack Compose), un écran ne se décrit pas par une poignée de boolean dispersés (isLoading, hasError, isEmpty…) — combinaison qui autorise des états incohérents comme « en chargement et en erreur en même temps ». On modélise plutôt l'écran par une sealed class unique : sealed interface EtatEcran { object Chargement; data class Succes(val items: List<Article>); data class Erreur(val message: String); object Vide }. L'interface graphique fait alors un when exhaustif sur cet état : chaque cas dessine exactement un écran, et il est impossible d'en oublier un — le compilateur le refuse. Ajoute un état « hors ligne » plus tard ? Tous les when concernés cessent de compiler jusqu'à ce que tu le gères. Ce patron — data classes pour les données, sealed pour les variantes, enum pour les valeurs simples — est la colonne vertébrale de la modélisation d'état dans les applis Kotlin, côté Android comme côté serveur (Ktor).

Glossaire

data class
Classe porteuse de données pour laquelle Kotlin génère equals, hashCode, toString, copy et les componentN.
copy()
Fonction générée qui crée une copie de l'objet en ne remplaçant que les propriétés nommées ; copie de surface.
Destructuration
Déballage d'un objet en plusieurs variables par position : val (x, y) = point ; s'appuie sur component1(), component2()…
enum class
Ensemble fixe et connu de valeurs nommées, chacune un singleton ; peut porter propriétés et méthodes.
sealed class / interface
Hiérarchie fermée : toutes les sous-classes sont connues à la compilation, ce qui rend le when exhaustif.
when exhaustif
when couvrant tous les cas d'un ensemble fermé ; ne requiert pas d'else et signale à la compilation un cas oublié.
Smart cast
Conversion de type automatique après un test is : dans la branche is Succes, la variable est vue comme un Succes sans cast manuel.
object / companion object
object déclare un singleton ; companion object attache à une classe l'équivalent des membres static (constantes, fabriques).

Récap et vérification

  • data class : equals, hashCode, toString, copy et destructuration générés ; == compare les valeurs, === les références.
  • copy : crée une variante immuable en changeant les champs nommés (copie de surface).
  • enum class : ensemble fermé de valeurs, avec propriétés et méthodes ; entries liste tout ; when exhaustif sans else.
  • sealed class / interface : hiérarchie fermée de types ; le when sur is est exhaustif et le smart cast donne le bon type par branche.
  • object : singleton ; companion object : équivalent du static (constantes, fabriques).
