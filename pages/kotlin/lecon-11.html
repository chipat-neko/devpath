Module 3 · L'objet à la Kotlin — Leçon 11

Génériques, lazy et delegation

~50 min Avancé Prérequis : leçon 10

À la fin de cette leçon, tu sauras

  • écrire des fonctions et classes génériques avec contraintes (where T : Comparable<T>) ;
  • comprendre la variance out (producteur) et in (consommateur) sur des cas simples ;
  • utiliser reified avec inline, choisir entre lateinit et by lazy ;
  • déléguer une implémentation avec by pour écrire un décorateur sans boilerplate.
Sommaire de la leçon

Tu sais déjà manipuler des classes et des fonctions en Kotlin. Cette leçon ajoute les outils qui rendent ton code réutilisable sans tricher sur les types : les génériques (le même code pour List<Int> et List<String>), la variance (pourquoi une liste de chiens est aussi une liste d'animaux), et la délégation (by), qui te laisse réutiliser une implémentation existante sans recopier la moindre méthode.

C'est exactement le fil de ce cours : la sécurité d'un typage fort, mais sans la cérémonie. Là où Java te ferait écrire des dizaines de méthodes de délégation à la main, Kotlin t'offre un seul mot-clé.

Fonctions génériques

Un paramètre de type se déclare entre chevrons avant le nom de la fonction. Il représente « un type quelconque, mais le même partout ». Ici T est déduit à l'appel.

Le type de retour est T? : si la liste est vide, on renvoie null. Aucune duplication, aucun cast : le compilateur sait que premier(listOf(10)) rend un Int?.

Classes génériques

Une classe peut elle aussi être paramétrée. Le T déclaré après le nom est disponible partout dans le corps.

Contraintes de type

Par défaut, T peut être n'importe quoi — donc tu ne peux appeler dessus que les méthodes de Any?. Pour exiger plus, ajoute une borne supérieure. Pour une seule contrainte, on l'écrit après deux-points ; pour plusieurs, on utilise where.

Sans la contrainte Comparable<T>, l'opérateur >= ne compilerait pas : le compilateur n'aurait aucune garantie que T sache se comparer. (Pour une seule borne, tu pourrais aussi écrire fun <T : Comparable<T>> maximum(...) ; where devient indispensable dès qu'il y a deux contraintes.)

Variance : out (producteur)

Voici une vraie question : si Chien hérite d'Animal, est-ce qu'une List<Chien> est acceptable là où on attend une List<Animal> ? En Java, non par défaut. En Kotlin, oui pour List, parce que List est déclarée List<out E> : elle ne fait que produire des éléments (les renvoyer), jamais en accepter en entrée.

Comme List est déjà déclarée out dans la bibliothèque standard, une List<Chien> est une List<Animal> : tu n'as rien à écrire de spécial. Retiens l'idée : out = « ça sort uniquement », donc le sous-typage suit le sens naturel (Chien → Animal).

Variance : in (consommateur)

Le miroir : in marque un type qui ne fait que consommer des T (les recevoir en entrée). Une chose capable de manger n'importe quel Animal peut, à plus forte raison, manger des Chien. Le sous-typage s'inverse.

Astuce

Moyen mnémotechnique anglo-saxon : PECS — Producer Extends, Consumer Super. En Kotlin, traduis-le simplement : un producteur est out, un consommateur est in.

reified et inline

Sur la JVM, les types génériques sont effacés à l'exécution (type erasure) : T n'existe plus, donc T::class et valeur is T sont normalement interdits. La parade : une fonction inline recopie son corps sur le site d'appel, ce qui permet de marquer T comme reified — « concret » — et d'accéder à son type réel.

Règle pratique : reified n'est utilisable que sur un paramètre de type d'une fonction inline. C'est ce qui fait marcher des helpers de la bibliothèque standard comme filterIsInstance<String>().

lateinit : promettre d'initialiser plus tard

Une propriété non-nullable doit recevoir une valeur. Mais parfois cette valeur n'arrive qu'après la construction (injection de dépendance, setUp() de test, cycle de vie Android). lateinit var dit au compilateur « fais-moi confiance, je l'initialise avant le premier usage ».

Lire une lateinit avant de l'avoir affectée lève UninitializedPropertyAccessException. Le garde-fou ::nom.isInitialized permet de tester l'état sans risque.

by lazy : calculer une fois, à la demande

Quand la valeur existe dès le départ mais coûte cher à produire, utilise by lazy. Le bloc ne s'exécute qu'au premier accès, puis le résultat est mémorisé.

Différence clé avec lateinit : lazy est un val et tu fournis le calcul ; lateinit est un var que quelqu'un d'autre remplit.

Délégation de classe avec by

Voici le bijou. Tu veux une List qui journalise certains accès, mais sans réimplémenter les dizaines de méthodes de l'interface. La clause by délègue toute l'implémentation à un objet existant ; tu ne redéfinis que ce que tu veux changer.

C'est le patron Décorateur, sans le boilerplate : en Java il faudrait écrire à la main size(), isEmpty(), iterator(), contains()… Kotlin les génère pour toi à partir de by source.

Note

Au-delà des classes, Kotlin offre les propriétés déléguées. by lazy en est une. Delegates.observable en est une autre : elle exécute un callback à chaque modification — pratique pour réagir à un changement d'état.

Pièges fréquents

Piège fréquent

lateinit ne marche pas avec les types primitifs (Int, Boolean, etc.) ni avec les val. Pour un Int qui s'initialise tard, préfère by lazy ou un var nullable. Et n'oublie jamais le test ::prop.isInitialized si l'accès peut précéder l'affectation.

Trois autres écueils classiques :

  • Confondre lazy et lateinit : lazy = val que la classe calcule ; lateinit = var rempli de l'extérieur.
  • Vouloir T::class sans inline + reified : à cause de l'effacement de type, le compilateur refuse. Marque la fonction inline et le type reified.
  • Croire que tout générique est covariant : MutableList<Chien> n'est pas une MutableList<Animal> (on pourrait y insérer un chat !). Seuls les types out autorisent ce sous-typage.

Pour aller plus loin

Pour aller plus loin

Explore la variance au point d'usage (type projection, List<out Animal> dans une signature), le mode de synchronisation de lazy (LazyThreadSafetyMode.NONE pour gagner en perf quand un seul thread accède), et Delegates.vetoable pour refuser une affectation invalide. Côté écosystème, regarde comment Android s'appuie massivement sur lateinit et sur by viewModels().

Un cas réel

Cas réel — la bibliothèque standard et Android carburent à ces trois outils

Ces notions ne sont pas de la théorie : la bibliothèque standard de Kotlin est bâtie dessus. List<out E> et Map<K, out V> sont covariantes, si bien qu'une List<String> circule là où on attend une List<Any> sans le moindre cast ; filterIsInstance<String>() ne fonctionne que grâce à reified. Côté Android, by lazy repousse une initialisation coûteuse — ouvrir une base de données, parser une config — jusqu'au premier accès, tandis que by viewModels() et by activityViewModels() sont des propriétés déléguées qui relient en une ligne un ViewModel au cycle de vie d'un écran. Des bibliothèques comme Room ou Retrofit exposent des API génériques (Dao<T>, Call<T>) et composent leurs comportements par délégation — un intercepteur de journalisation décore un client HTTP exactement comme notre ListeLoggee décore une liste. Génériques, variance et délégation : les trois mêmes idées passent d'un helper de trois lignes à des frameworks utilisés par des millions d'applications.

Glossaire

Paramètre de type
Nom symbolique (souvent T, E, K) déclaré entre chevrons ; il représente « un type quelconque, mais le même partout » et est fixé à l'appel ou à l'instanciation.
Contrainte (borne supérieure)
Limite imposée à un paramètre de type via : Borne ou where ; elle débloque sur T les membres de la borne (ex. Comparable<T> autorise >=).
Variance
Règle disant si un sous-typage des éléments (Chien → Animal) se propage au type paramétré (List<Chien> → List<Animal>) et dans quel sens.
out (covariance)
Marque un type qui ne fait que produire des T ; le sous-typage suit celui des éléments. Sûr en lecture, d'où List<out E>.
in (contravariance)
Marque un type qui ne fait que consommer des T ; le sous-typage s'inverse. Un consommateur d'Animal peut servir de consommateur de Chien.
reified
Paramètre de type d'une fonction inline conservé à l'exécution ; il rend possibles valeur is T et T::class, normalement interdits par l'effacement de type.
lateinit
Modificateur d'un var non nul promettant une initialisation avant le premier usage ; l'accès prématuré lève UninitializedPropertyAccessException. Interdit sur les primitifs.
Propriété déléguée (by)
Propriété dont la lecture/écriture est confiée à un objet délégué (by lazy, Delegates.observable) ; appliqué à une classe entière, by réalise la délégation d'implémentation.

Récap et vérification

  • Génériques : fun <T> … et class Boite<T> pour un code réutilisable et typé.
  • Contraintes : where T : Comparable<T> débloque les opérations attendues sur T.
  • Variance : out = producteur (sous-typage naturel), in = consommateur (sous-typage inversé).
  • reified : type concret à l'exécution, possible uniquement avec inline.
  • lateinit (var rempli plus tard, isInitialized) vs by lazy (val calculé une fois).
  • Délégation : class X(s) : Iface by s = décorateur sans boilerplate ; Delegates.observable pour réagir aux changements.
