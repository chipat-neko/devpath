Module 6 · Kotlin avancé et écosystème — Leçon 18

Construire un DSL

~50 min Avancé Lambdas & extensions (leçons 6, 12) utiles

À la fin de cette leçon, tu sauras

  • comprendre la lambda avec receiver, cœur des DSL Kotlin ;
  • écrire un type-safe builder qui se lit comme de la configuration ;
  • imbriquer des blocs pour modéliser une structure ;
  • protéger les portées avec @DslMarker.
Sommaire de la leçon

Tu as sûrement déjà vu du Kotlin qui ne ressemble pas à du code « normal », mais à de la configuration lisible : un fichier build.gradle.kts, une route de serveur Ktor, un écran Jetpack Compose. Ce sont des DSL (Domain-Specific Languages, langages dédiés) : des mini-langages taillés pour un domaine, écrits… en Kotlin. Leur ingrédient secret est une seule idée : la lambda avec receiver. Cette leçon te la fait construire de tes mains.

La lambda avec receiver

Une lambda ordinaire a le type (A) -> B. Une lambda avec receiver a le type A.() -> B : à l'intérieur, this est une instance de A, et l'on accède à ses membres sans préfixe. Tu connais déjà une fonction qui l'utilise : apply (leçon 12).

La clé : dans le bloc, append(...) nu signifie this.append(...). C'est ce « this implicite » qui donne aux DSL leur allure déclarative : on écrit ce qu'on veut, pas la plomberie.

Un builder maison

Construisons un type-safe builder : une fonction fiche { } qui crée un objet et le remplit via un bloc. « Type-safe » parce que, contrairement à un fichier texte, l'éditeur vérifie tout et l'auto-complétion propose les bons champs.

Remarque Fiche().apply(bloc) : apply est une lambda avec receiver, donc il exécute notre bloc sur la nouvelle Fiche et la renvoie. Le résultat se lit comme une petite fiche déclarative, mais reste du Kotlin vérifié à la compilation.

Imbriquer les blocs

La vraie puissance vient de l'imbrication : un bloc qui contient d'autres blocs, pour décrire une arborescence (un menu et ses plats, une page et ses sections, un serveur et ses routes).

Chaque niveau a son receiver : dans menu { }, this est un Menu ; dans plat { }, this est un Plat. On obtient une structure claire qui ressemble à la donnée qu'elle décrit.

Protéger les portées : @DslMarker

Un piège guette les DSL imbriqués : à l'intérieur de plat { }, les deux receivers (le Plat courant et le Menu englobant) sont accessibles. On pourrait alors appeler plat(...) par erreur dans un plat. L'annotation @DslMarker corrige cela : elle interdit d'atteindre implicitement le receiver externe.

Astuce

Le trailing lambda (leçon 6) fait tout le charme visuel : quand le dernier paramètre est une lambda, on la sort des parenthèses. plat("Pizza") { prix = 9.5 } appelle en réalité plat("Pizza", { prix = 9.5 }). Sans cette règle, aucun DSL ne serait aussi lisible.

Un cas réel

Cas réel — les DSL que tu utilises déjà sans le savoir

Le mécanisme de cette leçon fait tourner des pans entiers de l'écosystème. Gradle (l'outil de build) lit un build.gradle.kts qui est exactement ce type de DSL : dependencies { implementation("…") } est un bloc avec receiver. Ktor, le serveur web, décrit ses routes ainsi : routing { get("/") { … } }. Jetpack Compose bâtit les interfaces Android avec Column { Text("Bonjour") }. La bibliothèque kotlinx.html génère du HTML typé : html { body { h1 { +"Titre" } } }. Dans tous ces cas, la même recette : une lambda avec receiver par niveau, l'imbrication pour la structure, et @DslMarker pour éviter les confusions de portée. Savoir en construire un — ne serait-ce qu'un petit générateur de configuration maison — te fait comprendre de l'intérieur les outils que tu emploies tous les jours, et t'ouvre la porte à des API élégantes pour tes propres bibliothèques.

Pour aller plus loin

Pour aller plus loin

Explore la fonction buildList { }/buildMap { } de la bibliothèque standard (des builders déjà tout prêts), l'opérateur unaryPlus (le +"texte" de kotlinx.html est une surcharge d'opérateur), et la combinaison d'un DSL avec des fonctions inline pour éviter tout coût à l'exécution. Étudier le code source de kotlinx.html ou d'un plugin Gradle est une excellente façon de voir des DSL de production.

Glossaire

DSL
Domain-Specific Language : un mini-langage taillé pour un domaine (build, HTML, UI). En Kotlin, il s'écrit en Kotlin et reste vérifié à la compilation.
Lambda avec receiver
Lambda de type A.() -> B dans laquelle this est une instance de A, accessible sans préfixe.
Receiver
L'objet joué par this à l'intérieur d'une lambda avec receiver ou d'une fonction d'extension.
Type-safe builder
Fonction qui construit un objet via un bloc de configuration, avec vérification de types et auto-complétion (contrairement à un fichier texte).
Trailing lambda
Règle syntaxique : si le dernier paramètre est une lambda, on peut l'écrire après les parenthèses — moteur visuel des DSL.
@DslMarker
Annotation posée sur une annotation-marqueur ; appliquée aux classes d'un DSL, elle masque les receivers externes dans les blocs imbriqués.
apply
Fonction de portée (leçon 12) qui exécute un bloc sur un objet (comme receiver) et renvoie cet objet : le raccourci parfait pour un builder.

Récap et vérification

  • Une lambda avec receiver (A.() -> Unit) fait de this une instance de A dans le bloc.
  • Un builder crée un objet, lui applique le bloc (souvent via apply), puis le renvoie.
  • L'imbrication de blocs, un receiver par niveau, décrit une arborescence lisible.
  • @DslMarker masque les receivers externes : chaque bloc ne voit que le sien.

  2. Pourquoi apply est-il pratique pour écrire un builder ?
