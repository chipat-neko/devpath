Module 1 · Les formats texte courants — Leçon 01

Pourquoi des formats de données

~30 min Débutant Aucun prérequis

À la fin de cette leçon, tu sauras

  • expliquer ce qu'est la sérialisation ;
  • comprendre l'échange de données entre programmes ;
  • distinguer formats texte et binaires ;
  • connaître les grands formats que tu vas étudier.
Sommaire de la leçon

Un programme manipule des données en mémoire sous forme d'objets, de tableaux, de structures. Mais dès qu'il faut sauvegarder ces données dans un fichier, les envoyer à un autre programme par le réseau, ou lire une configuration, il faut les transformer en une suite de caractères ou d'octets qui suit des règles précises : un format de données. Ce cours transversal couvre les formats que tu croises tous les jours : JSON, CSV, YAML, XML et leurs cousins.

Comprendre ces formats — leurs forces, leurs limites, comment les lire et les écrire — est une compétence universelle. Quel que soit ton langage, tu liras du JSON d'une API, un CSV exporté d'un tableur, ou un fichier de configuration en YAML.

La sérialisation

La sérialisation est l'opération qui transforme des données en mémoire en une représentation transmissible (texte ou octets). L'opération inverse, qui reconstruit les données à partir de cette représentation, s'appelle la désérialisation (ou parsing).

C'est le cœur du sujet : un format est une convention partagée qui permet à un programme d'écrire des données et à un autre — éventuellement écrit dans un langage différent, sur une autre machine — de les relire à l'identique. Sans format commun, deux programmes ne pourraient pas se comprendre.

L'échange entre programmes

Le besoin numéro un : faire communiquer des programmes. Un front-end JavaScript reçoit du JSON d'un serveur écrit en Python ; un tableur exporte un CSV qu'un script va analyser ; une application lit un fichier de configuration. Dans tous ces cas, un format neutre sert de langue commune.

L'avantage d'un format standard : il est indépendant du langage. Le JSON produit par du Java se lit en JavaScript, en Go, en Rust… parce que tous s'accordent sur les mêmes règles d'écriture. C'est pourquoi les API web (cours API REST) échangent presque toujours en JSON : c'est le plus petit dénominateur commun compris de tous.

Cas réel

Une API météo publique renvoie la prévision en JSON. Le même flux est consommé, sans concertation, par un site web (JavaScript), une application mobile (Kotlin/Swift) et un script d'analyse (Python). Aucun de ces clients ne connaît le langage du serveur, ni celui des autres : ils partagent seulement le format. Changer le serveur de langage (Ruby → Go, par exemple) ne casse rien, tant que le JSON produit garde la même forme. C'est tout l'intérêt d'un format neutre : il découple les programmes les uns des autres.

Texte ou binaire ?

Les formats se divisent en deux grandes catégories :

  • les formats texte (JSON, CSV, YAML, XML) : lisibles par un humain dans un éditeur, faciles à déboguer et à versionner. En contrepartie, plus volumineux et plus lents à analyser.
  • les formats binaires (Protocol Buffers, MessagePack, formats d'images…) : compacts et rapides à lire/écrire pour la machine, mais illisibles directement par un humain.

Le choix dépend du besoin : pour une configuration ou une API publique, on privilégie un format texte (lisibilité, débogage). Pour des échanges massifs et performants entre services, un format binaire peut être préférable. Ce cours se concentre sur les formats texte, les plus courants au quotidien.

Astuce

En cas de doute, commence par un format texte. Tu gagnes la lisibilité, un diff propre dans Git, et des outils qui savent déjà le lire. Ne passe au binaire que si un besoin réel l'exige (volume massif, latence critique, mesures à l'appui). Optimiser la compacité avant d'en avoir la preuve, c'est se compliquer le débogage sans bénéfice tangible.

Attention

Un format texte n'est « du texte » qu'à travers un encodage. Aujourd'hui, c'est presque toujours l'UTF-8 (qui gère les accents, les emojis, tous les alphabets). Enregistrer un fichier dans un autre encodage (Latin-1, Windows-1252…) puis le relire en UTF-8 transforme « é » en « Ã© » : le fameux mojibake. Règle d'or : tout en UTF-8, de l'écriture à la lecture.

Les formats du cours

Tu vas étudier les formats texte que tu rencontreras le plus :

Chacun a sa spécialité et ses compromis. Une grande partie du métier consiste à savoir lequel choisir selon le contexte — un sujet qu'on traitera en fin de cours. Mais d'abord, place au plus important d'entre eux : JSON.

Données ≠ programme

Un format de données décrit des données, pas des instructions. JSON, CSV ou YAML ne sont pas des langages de programmation : ils n'ont ni boucles, ni conditions, ni calculs. Ils ne font que décrire une structure d'information (des valeurs, des listes, des associations clé-valeur). C'est précisément cette simplicité qui les rend sûrs à échanger et faciles à analyser.

Pour aller plus loin

Les formats binaires ne sont pas réservés aux experts : Protocol Buffers (Google) et MessagePack sérialisent les mêmes données que JSON, mais en octets compacts, avec un schéma qui décrit les champs. On les croise dans les échanges internes à fort trafic (gRPC), les jeux en réseau, l'IoT. L'idée reste celle de ce chapitre — sérialiser puis désérialiser — seule la représentation change : illisible à l'œil, mais plus petite et plus rapide.

Glossaire

Format de données
Convention d'écriture qui décrit une structure d'information (valeurs, listes, clés-valeurs) pour la stocker ou l'échanger.
Sérialisation
Transformer des données en mémoire en une représentation transmissible (texte ou octets).
Désérialisation (parsing)
Opération inverse : reconstruire les données en mémoire à partir de leur représentation.
Format texte
Format lisible par un humain (JSON, CSV, YAML, XML) : facile à déboguer et à versionner, mais plus volumineux.
Format binaire
Format fait d'octets bruts (Protocol Buffers, MessagePack) : compact et rapide, mais illisible directement.
Encodage (UTF-8)
Règle qui associe des caractères à des octets ; UTF-8 est le standard universel pour le texte.
Interopérabilité
Capacité de programmes hétérogènes (langages, machines différents) à échanger grâce à un format commun.
JSON
Le format texte le plus répandu pour l'échange de données ; étudié dès la prochaine leçon.

Récap et vérification

  • La sérialisation transforme des données en mémoire en texte/octets transmissibles ; la désérialisation (parsing) fait l'inverse.
  • Un format est une convention partagée qui permet à des programmes (langages, machines différents) d'échanger.
  • Formats texte (lisibles, déboguables) vs binaires (compacts, rapides, illisibles).
  • Les grands formats texte : JSON, CSV, YAML, TOML, XML — chacun avec sa spécialité.

Exercices

Exercice 1Échauffement

Avec tes mots, explique la différence entre sérialiser et désérialiser.

Voir une solution

Sérialiser : transformer des données en mémoire (un objet, une liste) en une représentation transmissible/stockable (du texte comme JSON, ou des octets). Désérialiser (parser) : l'opération inverse, reconstruire les données en mémoire à partir de cette représentation. On sérialise pour envoyer/sauvegarder, on désérialise pour relire/utiliser.

Exercice 2Application

Pour chacun de ces besoins, dirais-tu plutôt format texte ou binaire ? (a) un fichier de configuration édité à la main ; (b) des millions d'échanges très rapides entre deux microservices internes.

Voir une solution

(a) texte : la lisibilité et l'édition facile priment sur la performance (ex. YAML, TOML). (b) binaire : la compacité et la vitesse comptent plus que la lisibilité humaine, et le volume est énorme (ex. Protocol Buffers, MessagePack). Le contexte décide.

Exercice 3Défi

Un développeur dit « je vais stocker ma config dans un fichier de code JavaScript exécutable, c'est plus puissant que du JSON ». Quels risques cela pose-t-il par rapport à un format de données pur ?

Voir une solution

Un format de données pur (JSON, YAML…) décrit seulement des données : pas de code à exécuter, donc pas de risque qu'il « fasse » quelque chose. Stocker la config dans du code exécutable introduit plusieurs risques : 1) sécurité — exécuter ce fichier peut lancer du code arbitraire (dangereux s'il vient d'une source non sûre) ; 2) portabilité — un autre langage ne pourra pas le lire (il faut un interpréteur JS) ; 3) outillage — on perd la validation, le diff propre et les outils standards qui comprennent les formats de données. La séparation données/programme est précisément ce qui rend les formats sûrs et universels.
