Module 2 · Configuration et documents — Leçon 04

YAML et TOML, la configuration lisible

~37 min Intermédiaire Leçon 02 (JSON) requise

À la fin de cette leçon, tu sauras

  • lire et écrire du YAML (indentation, listes, maps) ;
  • éviter les pièges de YAML ;
  • lire du TOML (sections explicites) ;
  • choisir entre YAML, TOML et JSON pour une config.
Sommaire de la leçon

JSON est parfait pour l'échange entre programmes, mais un peu lourd à écrire et lire à la main (accolades, guillemets partout). Pour les fichiers de configuration — qu'un humain édite —, on préfère souvent des formats plus légers visuellement : YAML et TOML. Tu les croises dans le DevOps, les conteneurs, l'intégration continue, et la config de nombreux outils.

YAML : la structure par l'indentation

YAML exprime la même chose que JSON (maps, listes, valeurs) mais avec une syntaxe épurée : pas d'accolades ni de crochets, la structure vient de l'indentation (comme en Python). Les paires sont clé: valeur, les listes commencent par un tiret.

Compare avec le même contenu en JSON (leçon 2) : YAML est nettement plus aéré. Les listes sont des lignes préfixées de - ; les maps (objets) sont des clé: valeur indentés sous leur parent. Et YAML autorise les commentaires (#), précieux dans une configuration.

Les pièges de YAML

La lisibilité de YAML a un revers : sa flexibilité crée des pièges. Deux sont célèbres.

Le plus connu est le « problème de la Norvège » : le code pays NO est lu comme le booléen false ! De même, yes/no/on/off deviennent des booléens, et des nombres perdent leurs zéros. La parade : mettre entre guillemets toute valeur qui doit rester du texte. La sensibilité à l'indentation est l'autre source d'erreurs : un éditeur qui montre les espaces aide beaucoup.

TOML : des sections explicites

TOML (Tom's Obvious, Minimal Language) vise la même lisibilité que YAML, mais sans son ambiguïté : la structure est explicite, par des sections entre crochets, et l'indentation n'a aucune importance. Il ressemble aux vieux fichiers .ini, en plus rigoureux.

TOML est moins ambigu que YAML : les types sont clairs (les chaînes sont toujours entre guillemets), les sections sont visibles, et l'indentation est libre. Il est très utilisé pour la configuration d'outils — par exemple Cargo.toml en Rust, pyproject.toml en Python. C'est un bon compromis entre lisibilité et rigueur.

YAML, TOML ou JSON pour une config ?

Les trois peuvent servir de configuration ; le choix dépend du contexte :

En résumé : JSON pour l'échange machine, YAML pour les configs riches et hiérarchiques (en restant vigilant), TOML pour les configs simples et sans surprise. Beaucoup d'outils acceptent d'ailleurs plusieurs de ces formats.

Tous expriment la même chose

JSON, YAML et TOML décrivent fondamentalement les mêmes structures : des valeurs, des listes, des maps imbriquées. On peut convertir l'un en l'autre. Ils ne diffèrent que par la syntaxe et les compromis (lisibilité, ambiguïté, commentaires). Comprendre cela te permet de passer de l'un à l'autre sans peine : ce sont des habits différents pour les mêmes données.

Cas réel

Le « problème de la Norvège » est si connu qu'il a un site dédié (noyaml.com) et qu'il a poussé la spécification YAML 1.2 à retirer les booléens yes/no/on/off. Mais beaucoup de bibliothèques lisent encore en YAML 1.1 par défaut : le piège reste bien vivant. Scénario typique en CI : une image épinglée à version: 1.20 (sans guillemets) est lue 1.2, et le pipeline déploie la mauvaise version sans erreur visible. Réflexe : guillemets sur tout code, version ou identifiant.

Attention

En YAML, l'indentation se fait en espaces, jamais en tabulations — une tabulation provoque une erreur d'analyse. Et comme un simple espace en trop ou en moins change la structure, active l'affichage des caractères invisibles dans ton éditeur et un linter YAML (yamllint). C'est le prix de la lisibilité : la mise en page est la sémantique.

Pour aller plus loin

YAML a des fonctions avancées : les ancres (&) et alias (*) pour réutiliser un bloc sans le recopier, et le séparateur --- pour mettre plusieurs documents dans un fichier (courant en Kubernetes). Détail élégant : tout JSON valide est aussi du YAML valide, car YAML est un sur-ensemble de JSON. TOML, lui, reste volontairement minimal — sa force est justement de n'avoir presque aucune surprise.

Glossaire

YAML
YAML Ain't Markup Language : format de configuration lisible où la structure vient de l'indentation.
TOML
Tom's Obvious, Minimal Language : format de configuration à sections explicites, peu ambigu.
Indentation significative
Principe (YAML, Python) où le décalage en espaces détermine l'imbrication ; les tabulations sont interdites.
Problème de la Norvège
Bug classique : le code pays NO non quoté est interprété comme le booléen false.
Table (TOML)
Section délimitée par [nom] qui regroupe des clés ; équivalent d'un objet/map.
Ancre / alias (YAML)
& définit un bloc réutilisable, * le réutilise ailleurs sans le recopier.
Linter
Outil qui vérifie la validité et le style d'un fichier (ex. yamllint) et signale les pièges d'indentation.

Récap et vérification

  • YAML : structure par indentation, listes en -, maps en clé: valeur, commentaires autorisés.
  • Pièges YAML : indentation sensible (pas de tabulations) et interprétations surprenantes (NO→false) : mettre des guillemets.
  • TOML : sections explicites [entre crochets], indentation libre, moins ambigu (Cargo.toml, pyproject.toml).
  • Choix : JSON (échange machine), YAML (config riche éditée à la main), TOML (config simple sans ambiguïté).

Exercice 2Application

Dans un YAML, tu veux stocker le code pays NO et la version 1.10 en gardant exactement ces textes. Écris les deux lignes correctement.

Voir une solution

Sans guillemets, NO deviendrait false et 1.10 deviendrait le nombre 1.1 (zéro final perdu). Les guillemets forcent l'interprétation comme texte.

Exercice 3Défi

Écris en TOML une configuration avec un titre (chaîne), un booléen debug, et une section [base_de_donnees] contenant un hôte et un port.

Voir une solution

Les clés de premier niveau viennent avant toute section ; la section [base_de_donnees] regroupe ses propres clés. L'indentation est libre (purement cosmétique en TOML).
