Module 4 · Formats de données : aller plus loin — Leçon 07

Valider en profondeur avec un schéma

~40 min Intermédiaire Leçon 06 requise

À la fin de cette leçon, tu sauras

  • contraindre les valeurs (pattern, enum, minimum) ;
  • valider des tableaux et des objets imbriqués ;
  • réutiliser un schéma avec $ref ;
  • combiner des règles avec oneOf, anyOf, allOf.
Sommaire de la leçon

À la leçon 6, tu as vu l'idée d'un schéma : décrire la forme attendue d'un document pour la valider à la frontière. Un schéma minimal (types et champs obligatoires) suffit rarement en pratique : on veut aussi imposer qu'un âge soit positif, qu'un e-mail ressemble à un e-mail, qu'un statut soit l'une de trois valeurs. Cette leçon approfondit JSON Schema, le standard le plus répandu, pour écrire des validations riches et fiables.

Un schéma, plus que des types

Un schéma JSON est lui-même un document JSON. Chaque mot-clé ajoute une contrainte. Les fondations que tu connais : type (le type attendu), properties (les champs d'un objet), required (les champs obligatoires). Un ajout très utile : additionalProperties: false, qui interdit tout champ non prévu — précieux pour détecter une faute de frappe dans une clé.

Sans additionalProperties: false, une clé mal orthographiée passerait silencieusement (le champ attendu resterait vide, le champ en trop serait ignoré). Le verrouiller transforme une erreur discrète en erreur visible : exactement ce qu'on veut d'un validateur.

Contraindre les valeurs

Le cœur de la richesse de JSON Schema : chaque type a ses mots-clés de contrainte. Pour un nombre : minimum, maximum. Pour une chaîne : minLength, maxLength, pattern (une expression régulière), et format (des formats nommés comme email ou date). Pour limiter à une liste de valeurs : enum.

Ces contraintes déplacent une grande part de tes vérifications « métier » dans le schéma, à un seul endroit, déclaratif et testable. Le code applicatif reçoit alors des données déjà propres.

Astuce

Préfère enum à un pattern quand la liste des valeurs est fermée et connue (un statut, un rôle, un type de compte). C'est plus lisible, l'erreur est plus claire (« doit valoir l'une de : actif, inactif, banni »), et beaucoup d'outils en tirent une autocomplétion.

Structurer : tableaux et imbrication

Les données réelles sont rarement plates. Pour un tableau, le mot-clé items décrit la forme de chaque élément. Pour un objet dans un objet, on imbrique simplement un schéma dans properties. La validation devient récursive : chaque niveau applique ses propres règles.

Ici, un panier sans aucune ligne (minItems: 1) ou dont une ligne a une quantité nulle est rejeté : la règle métier « une commande a au moins un article, en quantité positive » vit entièrement dans le schéma.

Composer et réutiliser

Quand la même forme revient (une adresse, un montant), on la définit une fois et on la référence avec $ref. Et pour exprimer « l'un OU l'autre », JSON Schema fournit trois combinateurs : allOf (toutes les règles), anyOf (au moins une), oneOf (exactement une).

Le $ref pointe vers un fragment du même document (#/$defs/adresse) — mais il peut aussi désigner un autre fichier de schéma. C'est ainsi qu'on bâtit des bibliothèques de schémas partagés entre projets, sans copier-coller.

Cas réel

Le fichier de workflow GitHub Actions (.github/workflows/ci.yml) est validé en direct dans ton éditeur par un JSON Schema publié — bien qu'il soit écrit en YAML ! Les outils convertissent le YAML en structure de données, puis appliquent le schéma. C'est pourquoi une clé mal orthographiée (jobs: écrit job:) se souligne en rouge avant même que tu ne pousses ton code. Des milliers de schémas publics sont recensés sur schemastore.org, pour package.json, Docker Compose, les configs d'outils…

Attention

oneOf exige qu'exactement une branche corresponde : si une donnée valide deux branches à la fois, elle est rejetée. C'est un piège fréquent quand les branches se recouvrent. Si tu veux dire « au moins une », utilise anyOf ; garde oneOf pour des cas réellement exclusifs (par exemple « soit un paiement par carte, soit par virement, jamais les deux »).

Pour aller plus loin

JSON Schema a plusieurs versions (appelées drafts : draft-07, 2019-09, 2020-12). On les déclare avec le mot-clé $schema. Les concepts vus ici sont stables d'une version à l'autre ; seuls quelques mots-clés avancés changent de nom (definitions est devenu $defs). Pour du XML, l'équivalent est XSD (leçon 5) ; côté code, des bibliothèques comme Zod (TypeScript) ou Pydantic (Python) offrent la même idée, intégrée au langage.

Antisèche

Glossaire

JSON Schema
Standard, écrit en JSON, pour décrire et valider la structure de données JSON ; l'équivalent de XSD pour XML.
Mot-clé
Une entrée d'un schéma qui exprime une contrainte (type, required, minimum…).
pattern
Contrainte qui impose qu'une chaîne corresponde à une expression régulière.
enum
Contrainte qui limite une valeur à une liste fermée et explicite.
format
Contrainte nommée pour des chaînes courantes (email, date, uri…), au support variable selon le validateur.
additionalProperties
Mot-clé qui, mis à false, interdit tout champ non déclaré dans properties.
$ref
Référence vers un autre schéma (fragment du même fichier ou fichier externe), pour réutiliser une définition sans la copier.
oneOf / anyOf / allOf
Combinateurs : exactement une règle vérifiée / au moins une / toutes.

Récap et vérification

  • Au-delà des types, un schéma contraint les valeurs : minimum, pattern, enum, format.
  • additionalProperties: false transforme une faute de frappe de clé en erreur visible.
  • On valide des tableaux (items, minItems) et des objets imbriqués, récursivement.
  • $ref réutilise une définition ; allOf/anyOf/oneOf combinent des règles.

Vérifie ta compréhension

  1. Que fait additionalProperties: false et pourquoi est-ce utile ?
  2. Quelle est la différence entre anyOf et oneOf ?
  3. À quoi sert $ref ?

Exercices

Exercice 1Échauffement

Écris la contrainte JSON Schema pour un champ note qui doit être un entier compris entre 0 et 20 inclus.

Voir une solution

Pour exclure une borne, il existe exclusiveMinimum/exclusiveMaximum ; ici, 0 et 20 sont autorisés, donc minimum/maximum conviennent.

Exercice 2Application

Décris un champ tags qui est un tableau d'au moins une chaîne, sans doublon.

Voir une solution

items décrit chaque élément, minItems impose au moins un tag, et uniqueItems interdit les répétitions.

Exercice 3Défi

Un moyen de paiement est soit une carte (champ numeroCarte), soit un virement (champ iban), jamais les deux. Quel combinateur utilises-tu, et pourquoi ?

Voir une solution

On utilise oneOf, car les deux cas sont mutuellement exclusifs : exactement une branche doit correspondre.

Avec anyOf, un objet contenant à la fois numeroCarte et iban passerait ; oneOf le rejette, car il valide alors deux branches.
