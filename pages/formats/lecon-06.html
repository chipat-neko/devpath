Choisir et valider un format

~37 min Intermédiaire Leçon 05 requise

À la fin de cette leçon, tu sauras

  • choisir un format selon le besoin ;
  • valider des données avec un schéma ;
  • gérer l'encodage (UTF-8) ;
  • situer les formats binaires et éviter les pièges.
Sommaire de la leçon

Tu connais maintenant les grands formats texte. Cette leçon prend de la hauteur : comment choisir le bon format pour un besoin donné, comment valider que des données reçues sont conformes, et quels pièges transversaux (encodage, types) guettent quel que soit le format. C'est la synthèse qui fait de toi un utilisateur averti des données. Le module suivant (leçons 7 à 11) pousse ensuite chacun de ces sujets en profondeur.

Choisir selon le besoin

Il n'y a pas de « meilleur format » dans l'absolu : il y a le format adapté au besoin. Une grille de décision simple :

Les bonnes questions à se poser : qui lit/écrit (humain ou machine ?), les données sont-elles plates ou hiérarchiques ? a-t-on besoin de validation stricte ? de performance ? Réponds à cela, et le format s'impose souvent de lui-même. Et n'oublie pas : tu peux convertir d'un format à l'autre — ils décrivent les mêmes structures.

Valider avec un schéma

Recevoir des données ne suffit pas : il faut vérifier qu'elles sont conformes à ce qu'on attend (les bons champs, les bons types). Comme pour la sécurité (ne jamais faire confiance à l'entrée), on valide. Un schéma décrit la structure attendue, et un validateur la vérifie automatiquement.

Chaque format a son outillage de validation : JSON Schema pour JSON, XSD pour XML (leçon 5), des bibliothèques de validation (Zod, Joi…) côté code. Valider à la frontière de ton système — quand des données entrent — t'épargne des bugs et des failles plus loin. C'est le pendant « données » de la validation des entrées vue en sécurité.

Astuce

Valide une seule fois, à l'entrée. Dès qu'une donnée franchit la frontière (formulaire, fichier importé, réponse d'API), passe-la au schéma ; ensuite, tout le code en aval peut la considérer comme fiable. Inutile de re-vérifier partout : un point de contrôle net vaut mieux que dix vérifications éparpillées.

Cas réel

Quand tu édites un package.json (npm) ou un fichier de config dans VS Code, l'autocomplétion et les soulignés rouges viennent d'un JSON Schema publié sur schemastore.org. L'éditeur reconnaît le fichier, télécharge le schéma correspondant et valide en direct : propriété inconnue, type erroné, champ obligatoire manquant. Le même mécanisme qui protège une API valide aussi ta config, sous tes yeux, pendant que tu tapes.

L'encodage : UTF-8 partout

Un piège transversal, indépendant du format : l'encodage de caractères. Un fichier texte est une suite d'octets ; l'encodage dit comment ces octets représentent des caractères. Si l'écriture et la lecture n'utilisent pas le même encodage, les accents et caractères spéciaux deviennent du charabia (du mojibake : « Café » qui s'affiche « CafÃ© »).

La règle d'or moderne : utilise UTF-8 partout. C'est l'encodage standard du web et de la quasi-totalité des formats (JSON impose même l'UTF-8). Déclare-le explicitement quand le format le permet (encoding="UTF-8" en XML), et configure tes outils pour lire/écrire en UTF-8. La plupart des problèmes d'accents « cassés » viennent d'un encodage incohérent entre deux bouts de la chaîne.

Cas réel

Exporte un CSV contenant des accents depuis un outil moderne (donc en UTF-8), puis double-clique dessus pour l'ouvrir dans Excel sous Windows : « Café » devient « CafÃ© ». Par défaut, Excel suppose l'encodage local (Windows-1252), pas UTF-8. Les parades classiques : ajouter un BOM UTF-8 en tête de fichier (Excel le reconnaît), ou passer par Données → À partir d'un fichier texte et choisir explicitement l'encodage. Une immense part des tickets « mes accents sont cassés » vient exactement de là.

Attention

Le BOM (Byte Order Mark), ces quelques octets invisibles en tête d'un fichier UTF-8, aide Excel mais peut gêner d'autres outils. Un programme qui lit la première ligne verra un caractère parasite (U+FEFF) collé devant le premier caractère : une clé JSON qui devrait être "nom" ne correspondra plus, car elle vaut en réalité « BOM + nom ». À utiliser en connaissance de cause : pratique pour un CSV destiné à Excel, à éviter pour du JSON destiné à des programmes.

Les formats binaires, en bref

Au-delà des formats texte, les formats binaires existent quand la performance et la compacité priment. Ils ne sont pas lisibles à l'œil, mais bien plus rapides et petits.

Tu n'en as pas besoin pour la plupart des projets, mais il est bon de savoir qu'ils existent : quand une API interne échange des millions de messages par seconde, ou qu'on stocke des téraoctets, le texte devient trop coûteux et le binaire s'impose. Le compromis lisibilité/performance (leçon 1) revient ici à grande échelle.

Pour aller plus loin

Tu sais désormais lire, écrire, choisir et valider les formats du quotidien. Pour approfondir : JSON Schema en détail pour des validations riches ; les API et la sérialisation dans ton langage (chaque cours de langage a son module fichiers/données) ; les formats binaires (Protobuf) si tu vises la performance ; et les bonnes pratiques de versionnement des formats (faire évoluer une structure sans casser les anciens lecteurs, comme le versioning d'API). Retiens l'essentiel : un format est un outil ; choisis-le selon le besoin, valide ce que tu reçois, et reste en UTF-8.

Antisèche

Glossaire

Sérialisation
Transformation d'une donnée en mémoire (objet) en une suite de caractères ou d'octets, transmissible et stockable ; la désérialisation fait l'inverse.
Schéma
Description formelle de la structure attendue d'un document (champs, types, contraintes), servant à valider automatiquement des données.
JSON Schema
Standard de schéma pour décrire et valider des données JSON (l'équivalent de XSD pour XML).
Validation
Vérification qu'une donnée reçue est conforme à un schéma ; on la place à la frontière du système, avant de traiter l'entrée.
Encodage
Règle de correspondance entre les caractères et les octets d'un fichier texte (UTF-8, Latin-1…).
UTF-8
Encodage universel du web, capable de représenter tous les caractères ; à privilégier partout (JSON l'impose).
Mojibake
Caractères illisibles obtenus quand un texte est écrit dans un encodage et lu dans un autre (ex. « Café » → « CafÃ© »).
Format binaire
Format non textuel (Protobuf, MessagePack…), compact et rapide pour la machine, au prix de la lisibilité humaine.

Récap et vérification

  • Choisir selon le besoin : humain/machine, plat/hiérarchique, validation, performance (JSON, CSV, YAML, TOML, XML, binaire).
  • Valider les données reçues avec un schéma (JSON Schema, XSD) : ne jamais faire confiance à l'entrée.
  • UTF-8 partout pour éviter le mojibake (accents cassés par un encodage incohérent).
  • Les formats binaires (Protobuf, MessagePack…) pour la performance et la compacité, au prix de la lisibilité.

Vérifie ta compréhension

  1. Quelles questions poses-tu pour choisir un format de données ?
  2. À quoi sert un schéma (JSON Schema, XSD) ?
  3. D'où vient le « mojibake » (accents cassés) et comment l'éviter ?

Exercices

Exercice 1Échauffement

Quel format choisirais-tu pour : (a) la réponse d'une API web ; (b) l'export d'une table de 10 000 lignes vers un tableur ; (c) le fichier de configuration d'un outil en ligne de commande ?

Voir une solution

(a) JSON (échange machine, natif sur le web) ; (b) CSV (données tabulaires, compatible tableurs) ; (c) TOML ou YAML (configuration lisible éditée à la main ; TOML si simple et sans ambiguïté, YAML si riche et hiérarchique).

Exercice 2Application

Écris un schéma JSON (JSON Schema) qui exige un objet avec une ville (chaîne) et un codePostal (chaîne) tous deux obligatoires.

Voir une solution

Note que codePostal est de type string (et non integer) : pour préserver un éventuel zéro initial ("01000"), on garde un texte.

Exercice 3Défi

Un fichier JSON exporté affiche « Genève » comme « GenÃ¨ve » quand on l'ouvre. Diagnostique le problème et donne la marche à suivre.

Voir une solution

Diagnostic : c'est du mojibake, dû à une incohérence d'encodage : le fichier a été écrit en UTF-8 mais est lu (ou réinterprété) dans un autre encodage (souvent Latin-1/Windows-1252). Le « è » encodé en UTF-8 (deux octets) est affiché comme deux caractères Latin-1 (Ã¨). Marche à suivre : 1) s'assurer que le fichier est bien écrit en UTF-8 (JSON l'exige) ; 2) configurer l'outil/l'éditeur qui le lit pour interpréter le fichier en UTF-8 (et non Latin-1) ; 3) vérifier toute la chaîne (export, transfert, lecture) pour qu'elle soit cohérente en UTF-8 de bout en bout. Le contenu n'est pas corrompu : c'est l'interprétation des octets qui est mauvaise.
