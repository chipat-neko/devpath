Module 2 · Configuration et documents — Leçon 05

XML et les documents structurés

~35 min Intermédiaire Leçon 02 (JSON) requise

À la fin de cette leçon, tu sauras

  • lire un document XML (balises, attributs, arbre) ;
  • distinguer élément et attribut ;
  • situer l'écosystème XML (schémas, XPath) ;
  • choisir entre XML et JSON.
Sommaire de la leçon

Avant le règne de JSON, le format d'échange dominant était XML (eXtensible Markup Language). Il reste très présent : documents bureautiques (un fichier .docx est du XML zippé), flux RSS, configurations Java/.NET, standards d'entreprise, services SOAP. Tu en croiseras forcément ; et comme tu connais déjà le HTML, sa syntaxe te sera familière.

La syntaxe à balises

XML organise l'information avec des balises (tags), comme le HTML. Chaque élément a une balise ouvrante et une balise fermante qui encadrent un contenu ; les éléments s'imbriquent pour former un arbre.

La première ligne (déclaration) précise la version et l'encodage. Ensuite, tout est élément : <nom>…</nom> encadre une valeur, <competences> contient d'autres éléments. Contrairement au HTML, les balises ne sont pas prédéfinies : tu inventes les tiennes (<personne>, <competence>) — c'est le « extensible » de XML.

Éléments et attributs

XML offre deux façons de porter une information : le contenu d'un élément, ou un attribut sur la balise ouvrante (comme en HTML). C'est une particularité par rapport à JSON, qui n'a que des paires clé-valeur.

Ici id et disponible sont des attributs de produit ; nom et prix sont des éléments ; devise est un attribut de prix. Cette double possibilité est puissante mais source de débats sans fin (« attribut ou élément ? ») — une complexité que JSON évite en ne proposant qu'une seule façon de faire.

L'écosystème XML

La grande force historique de XML est son écosystème de standards matures :

  • les schémas (XSD, DTD) : ils définissent la structure valide d'un document (quels éléments, quels types, quel ordre), et permettent de valider un document automatiquement.
  • XPath : un langage pour naviguer et sélectionner des parties d'un document XML (l'équivalent des sélecteurs CSS pour XML).
  • XSLT : un langage pour transformer un XML en un autre format (un autre XML, du HTML…).
  • les espaces de noms (namespaces) : pour mélanger des vocabulaires sans collision.

Cette richesse explique pourquoi XML reste le choix de domaines exigeants (édition, finance, administration) : la validation par schéma et les transformations standardisées sont précieuses pour des documents complexes et critiques. JSON a depuis comblé une partie de cet écart (avec JSON Schema, par exemple), mais l'écosystème XML reste plus mûr sur ces points.

XML ou JSON ?

Pour la plupart des échanges modernes, JSON l'emporte : plus léger, plus simple, intégré nativement aux langages web. XML garde l'avantage dans des cas précis :

On préfère XML quand : on a besoin de validation par schéma stricte, de documents mêlant texte et balisage (édition), de transformations standardisées, ou quand un système existant l'impose. On préfère JSON pour : les API web, la légèreté, l'intégration facile en JavaScript et les échanges courants. Connaître les deux te permet de lire l'existant et de choisir à bon escient.

HTML et XML, cousins

Tu connais déjà la syntaxe à balises grâce au HTML : c'est le même principe. Nuance : HTML a un vocabulaire fixe (les balises <p>, <div>… sont prédéfinies et tolérantes aux erreurs), tandis que XML te laisse inventer tes balises mais exige une syntaxe stricte (toute balise ouverte doit être fermée, sensible à la casse). Le XHTML fut d'ailleurs une version « XML stricte » du HTML.

Cas réel

Un fichier .docx (Word), .xlsx (Excel) ou .pptx (PowerPoint) est en réalité une archive ZIP de fichiers XML — c'est le standard Office Open XML. Renomme un .docx en .zip, ouvre-le : tu y trouves word/document.xml, le texte de ton document décrit en balises. Des milliards de documents bureautiques reposent ainsi, sans que personne ne le voie, sur XML. C'est pourquoi le connaître reste utile bien après le règne de JSON.

Attention

XML sait référencer des entités, et c'est une porte d'entrée pour deux attaques classiques : le billion laughs (une entité qui en référence d'autres en cascade, saturant la mémoire) et l'XXE (XML External Entity, qui peut lire des fichiers du serveur). Règle : en lisant du XML venu de l'extérieur, désactive le traitement des entités externes et des DTD dans ton analyseur. La plupart des bibliothèques ont une option « sûre » pour cela.

Pour aller plus loin

XML est une famille plus qu'un simple format d'échange : le SVG (images vectorielles) est du XML, les flux RSS/Atom (podcasts, actualités) aussi, tout comme les services web SOAP, le XHTML et les formats bureautiques. Là où JSON a gagné l'échange léger, XML garde le terrain des documents riches et des standards d'entreprise. Les deux mondes coexistent ; savoir lire l'un et l'autre est un atout durable.

Glossaire

XML
eXtensible Markup Language : format à balises, à vocabulaire libre, pour documents et données structurés.
Élément
Nœud formé d'une balise ouvrante, d'un contenu et d'une balise fermante ; les éléments s'imbriquent.
Attribut
Paire nom="valeur" placée sur la balise ouvrante d'un élément.
Schéma (XSD, DTD)
Description de la structure valide d'un document, permettant sa validation automatique.
XPath
Langage d'expressions pour naviguer dans un document XML et en sélectionner des parties.
XSLT
Langage de transformation d'un XML vers un autre format (XML, HTML, texte).
Espace de noms
Namespace : mécanisme pour mêler plusieurs vocabulaires sans collision de noms.
XXE
Faille d'entité externe : on la neutralise en désactivant DTD et entités externes à l'analyse.

Récap et vérification

  • XML organise l'information en balises imbriquées formant un arbre ; les balises sont libres (extensible).
  • Une info peut être un élément (contenu) ou un attribut (sur la balise) — JSON n'a qu'une façon de faire.
  • Écosystème mûr : schémas (validation), XPath (navigation), XSLT (transformation), espaces de noms.
  • Choix : JSON pour la plupart des échanges modernes ; XML pour validation stricte, documents, transformations, ou systèmes existants.

Exercice 3Défi

Un partenaire impose un échange en XML avec validation stricte par schéma. Ton équipe préfère JSON. Quels arguments objectifs peux-tu avancer de chaque côté ?

Voir une solution

Pour XML (côté partenaire) : la validation par schéma (XSD) garantit automatiquement que chaque document respecte une structure stricte — précieux pour des échanges critiques entre organisations ; l'écosystème (XPath, XSLT) est mûr ; et c'est peut-être un standard imposé dans son secteur. Pour JSON (côté équipe) : format plus léger et simple, intégration native en JavaScript et dans les API web, moins verbeux ; et JSON dispose désormais de JSON Schema pour la validation. Conclusion : le choix dépend du contexte. Si la validation stricte et l'interopérabilité avec des systèmes XML sont des exigences fortes, XML se justifie ; sinon, JSON est généralement plus simple. On peut aussi convertir entre les deux à la frontière du système.
