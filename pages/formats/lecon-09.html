Module 4 · Formats de données : aller plus loin — Leçon 09

Unicode et l'encodage, en profondeur

~40 min Intermédiaire Leçon 06 requise

À la fin de cette leçon, tu sauras

  • distinguer caractère, code point et octets ;
  • comparer UTF-8, UTF-16 et UTF-32 ;
  • reconnaître le BOM et l'échappement \uXXXX ;
  • comprendre la normalisation (NFC/NFD) et le cas des emojis.
Sommaire de la leçon

À la leçon 6, tu as retenu la règle d'or : UTF-8 partout. Cette leçon explique pourquoi ça marche, et ce qui se cache derrière les accents « cassés ». Comprendre la chaîne caractère → code point → octets t'évite une famille entière de bugs : tris qui échouent, longueurs fausses, mots de passe refusés, emojis coupés en deux.

Caractère, code point, octets

Trois niveaux à ne pas confondre. Un caractère est ce que tu vois (la lettre « é »). Unicode est un immense catalogue qui attribue à chaque caractère un numéro unique, le code point (pour « é », c'est U+00E9). Enfin, un encodage décide comment écrire ce numéro sous forme d'octets dans un fichier.

Cette séparation est la grande idée moderne : Unicode catalogue les caractères (plus de 150 000 : alphabets, idéogrammes, symboles, emojis), et un encodage comme UTF-8 les sérialise en octets. Le mojibake de la leçon 6, c'est exactement lire des octets avec le mauvais encodage : le catalogue est bon, la traduction en octets est mal relue.

UTF-8, UTF-16, UTF-32

Il existe plusieurs façons d'encoder les code points. UTF-32 utilise toujours 4 octets par caractère : simple mais volumineux. UTF-16 en utilise 2 (ou 4 pour les caractères rares). UTF-8 est à taille variable : 1 octet pour l'ASCII (a-z, chiffres), 2 pour les accents latins, 3-4 pour le reste. Son atout décisif : un fichier purement ASCII est identique en UTF-8, d'où sa compatibilité totale avec l'existant.

Sur le web, UTF-8 domine largement (plus de 98 % des pages) : compact pour les textes latins, compatible ASCII, sans ambiguïté d'ordre des octets. UTF-16 reste présent en interne dans certains langages (JavaScript, Java, C#) — d'où quelques pièges qu'on verra avec les emojis.

Cas réel

En JavaScript, "café".length vaut 4, mais "🎉".length vaut… 2 ! La raison : JS compte les unités UTF-16, et l'emoji 🎉 (hors du bloc de base) en occupe deux (une paire de substitution). Un champ « 140 caractères max » qui compte .length laissera donc passer moins d'emojis que prévu, et un slice maladroit peut couper un emoji en deux moitiés invalides. Pour compter de vrais caractères, on itère sur les code points ([...texte].length).

BOM et échappement

Deux détails reviennent souvent. Le BOM (Byte Order Mark) est une petite marque optionnelle (octets EF BB BF en UTF-8) placée en tête de fichier : elle aide certains outils (Excel) à reconnaître l'UTF-8, mais gêne les programmes qui la prennent pour un caractère réel. L'échappement \uXXXX permet, lui, d'écrire un caractère par son code point même dans un fichier ASCII : pratique pour les caractères invisibles ou incertains.

JSON accepte les deux écritures : le caractère directement (en UTF-8) ou son échappement \uXXXX. Les deux produisent la même chaîne une fois décodée ; l'échappement est juste une écriture de repli, sans ambiguïté d'encodage.

Normalisation : le même « é », deux façons

Piège subtil : « é » peut s'écrire de deux manières en Unicode. Soit un seul code point précomposé (U+00E9), soit deux code points : un « e » (U+0065) suivi d'un accent combinant (U+0301). À l'écran, les deux affichent « é » — mais octet pour octet, ce sont des chaînes différentes, qui échouent à une comparaison stricte.

La normalisation résout ce problème : elle réécrit le texte sous une forme canonique unique. NFC privilégie les caractères composés (le plus courant sur le web) ; NFD les décompose. La règle pratique : normalise en NFC avant de comparer, trier ou stocker — sinon deux textes visuellement identiques peuvent être jugés différents.

Attention

macOS stocke historiquement les noms de fichiers en NFD, alors que Linux et le web tendent vers NFC. Un fichier nommé « résumé.pdf » créé sur Mac peut voyager avec un « é » décomposé : un script qui cherche la chaîne « résumé » en NFC ne le trouvera pas. Beaucoup de bugs « le fichier existe pourtant ! » viennent exactement de là. La parade : normaliser les noms avant comparaison.

Astuce

La plupart des langages offrent une fonction de normalisation intégrée : "texte".normalize("NFC") en JavaScript, unicodedata.normalize("NFC", s) en Python. Applique-la à la frontière (comme la validation) : normalise ce qui entre, puis tout le reste du code manipule une forme unique. Un seul point de contrôle vaut mieux que des surprises éparpillées.

Emojis et caractères composés

Les emojis poussent tout cela à l'extrême. Certains sont un seul code point (🎉 = U+1F389). Mais beaucoup sont des séquences : le drapeau 🇫🇷 est deux code points (les lettres régionales F et R), et une famille 👨‍👩‍👧 combine plusieurs emojis reliés par un caractère invisible (le zero-width joiner). Compter, couper ou inverser une chaîne d'emojis « à la main » produit vite du charabia.

La bonne unité pour l'humain, c'est le graphème : ce qu'on perçoit comme « un caractère », même s'il est fait de plusieurs code points. Les bibliothèques modernes (segmenteurs de graphèmes) savent découper correctement ; à la main, on se trompe. Retiens surtout que « longueur d'une chaîne » est une question piégée dès qu'il y a des emojis ou des accents combinés.

Pour aller plus loin

Unicode définit aussi des règles de casse (majuscule/minuscule) parfois surprenantes : en turc, « i » majuscule n'est pas « I ». D'où le conseil, pour des comparaisons techniques (identifiants, clés), de rester en ASCII et d'éviter de dépendre de la casse locale. Pour aller plus loin : le case folding Unicode, les propriétés de caractères, et les algorithmes de segmentation de texte (UAX #29).

Antisèche

Glossaire

Unicode
Catalogue universel qui attribue un numéro unique (code point) à chaque caractère de (presque) toutes les écritures.
Code point
Le numéro Unicode d'un caractère, noté U+XXXX (ex. U+00E9 pour « é »), indépendant de l'encodage.
Encodage
Règle qui transforme les code points en octets (UTF-8, UTF-16, UTF-32, Latin-1…).
UTF-8
Encodage à taille variable (1 à 4 octets), compatible ASCII ; standard du web.
BOM
Byte Order Mark : marque optionnelle en tête de fichier signalant l'encodage ; utile à Excel, gênante ailleurs.
Normalisation (NFC/NFD)
Réécriture d'un texte sous une forme canonique unique, composée (NFC) ou décomposée (NFD).
Accent combinant
Code point qui se greffe sur le précédent (ex. U+0301) pour former un caractère accentué décomposé.
Graphème
Un « caractère perçu » par l'humain, éventuellement composé de plusieurs code points (emojis, accents combinés).

Récap et vérification

  • Trois niveaux : caractère (vu) → code point (numéro Unicode) → octets (encodage).
  • UTF-8 (taille variable, compatible ASCII) est le standard ; UTF-16/32 existent aussi.
  • Le BOM et l'échappement \uXXXX sont deux détails d'écriture à connaître.
  • Normaliser en NFC avant de comparer ; les emojis se comptent par graphème, pas par octet.

Vérifie ta compréhension

  1. Quelle est la différence entre un code point et des octets ?
  2. Pourquoi « é » peut-il donner "é" === "é" faux ?
  3. Pourquoi "🎉".length vaut 2 en JavaScript ?

Exercices

Exercice 1Échauffement

Range ces trois mots du plus général au plus concret : octets, caractère, code point.

Voir une solution

Caractère (ce que tu vois) → code point (le numéro Unicode attribué) → octets (l'écriture concrète dans un encodage). Unicode nomme, l'encodage écrit.

Exercice 2Application

Un JSON contient { "nom": "Ren\u00E9" }. Quelle chaîne obtient-on après décodage, et pourquoi ?

Voir une solution

On obtient { "nom": "René" }. \u00E9 est l'échappement du code point U+00E9 (« é »). JSON accepte le caractère directement ou son échappement \uXXXX : les deux donnent la même chaîne une fois décodée.

Exercice 3Défi

Une recherche d'utilisateur par nom « marché » échoue pour un enregistrement pourtant affiché « marché », créé depuis un Mac. Diagnostique et propose une correction.

Voir une solution

Diagnostic : problème de normalisation. Le nom stocké est sans doute en NFD (macOS), avec « é » décomposé en « e » + accent combinant, tandis que la recherche envoie « é » en NFC. Visuellement identiques, mais octets différents : la comparaison stricte échoue. Correction : normaliser les deux côtés (donnée stockée et terme recherché) en NFC avant comparaison — idéalement, normaliser à l'insertion pour que la base ne contienne qu'une seule forme.
