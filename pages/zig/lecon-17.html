Module 5 · Zig avancé — Leçon 17

La généricité et les interfaces

~52 min Avancé Prérequis : leçons 08 & 11

À la fin de cette leçon, tu sauras

  • écrire une fonction générique avec anytype ;
  • expliquer la monomorphisation à la compilation ;
  • fabriquer un conteneur générique avec une fonction qui renvoie un type ;
  • reconnaître le motif d'interface à l'exécution (pointeur + table de fonctions).
Sommaire de la leçon

Comment écrire max(a, b) une seule fois pour qu'elle marche sur des entiers et des flottants ? La plupart des langages ont un mot-clé pour ça (template en C++, <T> en Java, impl Trait en Rust). Zig, lui, n'a aucun mot-clé de généricité. Il n'en a pas besoin : puisque les types sont des valeurs manipulables à la compilation (leçons 08 et 11), la généricité découle de comptime. Cette leçon montre les deux formes utiles au quotidien : anytype pour les fonctions, les fonctions qui renvoient un type pour les conteneurs — puis le motif des vraies interfaces décidées à l'exécution.

Une fonction, tous les types : anytype

Le mot-clé anytype à la place d'un type de paramètre dit : « déduis le type à l'appel ». Le compilateur génère alors une version distincte de la fonction pour chaque type réellement utilisé. On récupère le type déduit avec la fonction intégrée @TypeOf.

Il n'y a qu'une ligne de source, mais le binaire final contient deux fonctions : une pour i32, une pour f64. C'est la monomorphisation — le contraire d'une fonction unique qui déciderait du type à l'exécution. Rien n'est deviné pendant que le programme tourne : tout est fixé à la compilation.

Le même principe que les template C++

La monomorphisation de Zig ressemble aux templates de C++ (une instance par type) et aux generics de Rust : le code est spécialisé par type, sans coût à l'exécution. À l'opposé, les génériques de Java sont « effacés » (une seule version, types perdus au runtime). Zig obtient le résultat des templates… sans langage de templates séparé : c'est du Zig ordinaire évalué à comptime.

Le « typage canard » à la compilation

Avec anytype, il n'y a aucun contrat écrit : la fonction accepte n'importe quel type… tant que le corps compile pour ce type. Si tu écris a.len, tout type possédant un champ len passe ; les autres provoquent une erreur de compilation (jamais un plantage à l'exécution). C'est le « si ça marche à la compilation, c'est bon », l'équivalent statique du duck typing.

Contraindre et documenter avec comptime

Puisque le contrat est implicite, rends-le explicite : vérifie tôt avec @TypeOf, @hasDecl(T, "…") ou @typeInfo, et lève un message clair avec @compileError("…"). Une contrainte vérifiée à comptime transforme un message d'erreur cryptique en une phrase que tu contrôles — un cadeau pour qui appellera ta fonction.

Fabriquer un conteneur générique

Pour un type générique (une pile de i32, une pile de chaînes…), on écrit une fonction qui prend un comptime T: type et renvoie un type : une véritable « usine à types ». Chaque appel Pile(i32), Pile([]const u8) produit une struct concrète, spécialisée.

Cas réel — std.ArrayList n'est rien d'autre que ça

Le conteneur le plus utilisé de Zig, std.ArrayList(T), est exactement ce motif : une fonction ArrayList(comptime T: type) type qui renvoie une struct enveloppant un slice []T, une longueur et une capacité. Quand tu écris std.ArrayList(u8) ou std.ArrayList(Produit), tu appelles une fonction qui fabrique le type sur mesure. Toute la bibliothèque standard (HashMap, BoundedArray, SinglyLinkedList…) repose sur cette même idée : pas de magie, juste des fonctions comptime qui renvoient des struct.

Les interfaces décidées à l'exécution

anytype et les conteneurs génériques résolvent tout à la compilation. Mais parfois on veut choisir le comportement pendant l'exécution : stocker des objets « de formes différentes » dans une même liste, changer d'implémentation selon la configuration… Zig n'a pas de mot-clé interface ni trait. Le motif idiomatique : une struct qui réunit un pointeur opaque vers les données (*anyopaque) et un pointeur vers une table de fonctions (la vtable).

Cas réel — std.mem.Allocator EST une interface

Depuis la leçon 06, tu passes un Allocator partout. Regarde sa définition : c'est exactement ce motif — un champ ptr: *anyopaque (l'allocateur concret : GPA, arène, page_allocator…) et un champ vtable pointant vers ses fonctions alloc, resize, free. Voilà pourquoi une même fonction accepte n'importe quel allocateur : elle ne voit qu'une interface, et l'implémentation réelle est choisie à l'exécution par l'appelant. std.io.Writer, std.Random : même recette. Tu utilisais des interfaces Zig sans le savoir depuis la leçon 6 !

Comptime ou exécution : comment choisir ?

La question à se poser est simple : connaît-on le type à la compilation ? Si oui — c'est le cas le plus fréquent — préfère anytype ou un conteneur générique : zéro coût à l'exécution, erreurs attrapées tôt. Si non — il faut mélanger des types dans une liste, ou brancher sur une config lue au démarrage — alors le motif d'interface (ptr + vtable) est la bonne réponse, au prix d'un appel indirect.

anytype n'est pas gratuit à l'échelle

Comme chaque type d'appel génère une copie de la fonction, abuser d'anytype sur de grosses fonctions gonfle le binaire (code bloat) — le même piège qu'avec les templates C++. Et sans contrainte explicite, une erreur d'usage produit un message parfois profond et opaque. Règle de sagesse : anytype pour les petites fonctions utilitaires et les conteneurs ; documente le contrat, ou vérifie-le à comptime.

Pour aller plus loin

Pour aller plus loin

Explore le module std.meta (introspection de types à comptime : std.meta.fields, @typeInfo) pour écrire des fonctions qui s'adaptent à la forme d'une struct — sérialisation, comparaison automatique… Compare le motif d'interface de Zig avec les traits de Rust (vérifiés par le compilateur) et l'héritage de C++ (vtable cachée par le langage). En Zig, la vtable est visible et explicite : c'est plus verbeux, mais il n'y a aucune machinerie cachée — fidèle à la devise du langage.

Glossaire

anytype
Type de paramètre déduit à l'appel ; le compilateur génère une version de la fonction par type utilisé.
monomorphisation
Génération d'une copie spécialisée du code générique pour chaque type concret, à la compilation ; aucun coût à l'exécution.
@TypeOf
Fonction intégrée qui renvoie le type d'une ou plusieurs expressions ; sert notamment à typer la valeur de retour.
@This()
Renvoie le type de la struct englobante ; indispensable pour référencer le type d'un conteneur générique de l'intérieur.
typage canard (duck typing) statique
Un type est accepté si le corps compile pour lui ; sinon, erreur de compilation (jamais un plantage au runtime).
conteneur générique
Type paramétré, obtenu par une fonction qui renvoie un type ; ex. std.ArrayList(T).
*anyopaque
Pointeur vers des données de type effacé ; brique du motif d'interface, on « récupère » le vrai type via @ptrCast.
vtable (table de fonctions)
Table de pointeurs de fonctions ; associée à ptr, elle réalise le polymorphisme à l'exécution (ex. std.mem.Allocator).

Récap et vérification

  • anytype = type déduit à l'appel ; le compilateur monomorphise (une version par type), zéro coût runtime.
  • Sans contrat écrit : « si ça compile, c'est bon » ; contrains à comptime (@hasDecl, @compileError) pour des messages clairs.
  • Un type générique = une fonction comptime T: type qui renvoie une struct (comme std.ArrayList).
  • Pour choisir à l'exécution : motif ptr: *anyopaque + vtable — c'est ce qu'est std.mem.Allocator.

Exercices

Exercice 1Échauffement

Écris une fonction générique identite qui renvoie son argument tel quel, quel que soit son type. Quel type de retour lui donner ?

Voir une solution

Le paramètre est anytype ; le type de retour est @TypeOf(x), c'est-à-dire exactement le type déduit à l'appel. C'est le squelette minimal d'une fonction générique en Zig.

Exercice 2Application

Complète cette usine à types : une Paire(T) qui contient deux valeurs de type T et une méthode egales disant si elles sont identiques.

Voir une solution

La fonction renvoie une struct paramétrée par T. À l'intérieur, @This() désigne le type courant (la Paire(T) concrète), ce qui permet d'écrire la méthode. Note que == ne marchera que pour des T comparables : c'est le typage canard statique : Paire de types non comparables provoquerait une erreur… de compilation.

Exercice 3Défi

On te donne une fonction trier(liste: anytype). Tu veux garantir qu'elle ne soit appelée qu'avec un slice, et sinon afficher un message clair à la compilation. Comment ?

Voir une solution

On inspecte le type à comptime avec @typeInfo ; s'il ne s'agit pas d'un slice, @compileError stoppe la compilation avec ton message (incluant le nom du type fautif via @typeName). Principe clé : anytype n'impose aucun contrat, mais tu peux en ajouter un explicite qui transforme une erreur obscure en une phrase que tu maîtrises. C'est la marque d'une API générique soignée.
