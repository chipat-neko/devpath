Module 5 · Zig avancé — Leçon 14

Les tests intégrés au langage

~50 min Avancé Prérequis : leçons 06 & 07

À la fin de cette leçon, tu sauras

  • écrire un bloc test à côté du code qu'il vérifie ;
  • lancer la suite avec zig test et zig build test ;
  • utiliser std.testing (expect, expectEqual, expectError…) ;
  • laisser std.testing.allocator détecter les fuites pour toi.
Sommaire de la leçon

Dans beaucoup de langages, écrire des tests demande d'installer une bibliothèque, d'adopter des conventions, de configurer un lanceur. En Zig, les tests font partie du langage : un mot-clé test, une commande zig test, et un allocateur spécial qui repère les fuites tout seul. Résultat : on teste pendant qu'on code, sans friction.

Un bloc test, dans le même fichier

Un test est un bloc nommé, écrit juste à côté de la fonction qu'il vérifie. Il ne part pas dans le programme final : il n'est compilé que lorsqu'on lance les tests.

On lance : zig test maths.zig. Zig compile uniquement les blocs test (et ce qu'ils utilisent), les exécute, et affiche All 1 tests passed. — ou le détail de l'échec.

Pourquoi try devant chaque vérification ?

std.testing.expect renvoie une erreur si la condition est fausse (le type d'erreur error.TestUnexpectedResult). Le try propage cette erreur, ce qui fait échouer le test. C'est la gestion d'erreurs de la leçon 7, réutilisée telle quelle : un test est juste une fonction qui peut renvoyer une erreur.

La boîte à outils std.testing

Quelques fonctions couvrent l'essentiel des vérifications. Toutes renvoient une erreur en cas d'échec, d'où le try :

Préfère expectEqual à expect(a == b)

Avec expect(a == b), un échec dit seulement « faux ». Avec expectEqual(a, b), Zig affiche les deux valeurs — tu vois immédiatement ce que tu as obtenu au lieu de l'attendu. Le diagnostic est bien plus rapide.

L'allocateur de test qui traque les fuites

C'est la fonctionnalité qui fait la différence. std.testing.allocator est un allocateur ordinaire… qui vérifie, à la fin du test, que tout ce qui a été alloué a bien été libéré. Une fuite ? Le test échoue et pointe l'allocation coupable.

Cas réel — la bibliothèque standard de Zig

Ouvre n'importe quel fichier de la bibliothèque standard de Zig (par exemple std/array_list.zig) : le code et ses blocs test sont dans le même fichier. Toute la stdlib se teste avec zig test, et l'allocateur de test garantit qu'aucune structure ne fuit. Les tests servent aussi de documentation exécutable : pour comprendre une fonction, on lit son test juste en dessous.

Regrouper les tests dans le build

Sur un vrai projet, on ne lance pas les fichiers un par un : build.zig (leçon 13) déclare une étape de test qui parcourt tout, et zig build test exécute l'ensemble.

Un test non référencé ne s'exécute pas

Zig n'exécute que les tests des fichiers atteints depuis le fichier racine testé (par les @import) ou déclarés dans build.zig. Un fichier jamais importé verra ses tests silencieusement ignorés. Vérifie que ta racine de test référence bien tous tes modules (souvent via un test { std.testing.refAllDecls(@This()); }).

Et après ?

Tu écris désormais des tests en même temps que ton code, avec détection de fuites offerte. Les leçons suivantes te donnent de quoi les rendre encore plus utiles : manier finement pointeurs et mémoire, puis tester du code concurrent.

Pour aller plus loin

Regarde std.testing.tmpDir (dossier temporaire jetable pour tester des E/S), std.testing.fuzz (entrées aléatoires), et errdefer combiné aux tests pour vérifier que le nettoyage a bien lieu sur le chemin d'erreur. Approfondis la démarche dans le cours Tests & qualité.

Glossaire

bloc test
Un bloc nommé, écrit dans un fichier source, exécuté par zig test et ignoré à la compilation normale.
zig test
La commande qui compile et exécute les blocs test d'un fichier (et de ses imports).
std.testing
Le module de la bibliothèque standard qui fournit les fonctions de vérification (expect, expectEqual…).
expect
Vérifie une condition booléenne ; renvoie une erreur (donc try) si elle est fausse.
expectError
Vérifie qu'une expression renvoie précisément l'erreur attendue.
std.testing.allocator
Un allocateur qui vérifie, en fin de test, que toute allocation a été libérée ; sinon le test échoue pour fuite.
fuite mémoire
De la mémoire allouée jamais libérée ; ici transformée en échec de test détectable tout de suite.
zig build test
Lance, via build.zig, toute la suite de tests du projet d'un coup.

Récap et vérification

  • Les tests sont dans le langage : un bloc test, la commande zig test, zéro dépendance.
  • Ils vivent à côté du code — et servent aussi de documentation exécutable.
  • std.testing fournit expect, expectEqual, expectError, expectEqualStrings…
  • std.testing.allocator transforme une fuite en test qui échoue.

Vérifie ta compréhension

  1. Pourquoi met-on try devant std.testing.expect ?
  2. Qu'apporte std.testing.allocator par rapport à un allocateur ordinaire ?
  3. Pourquoi préférer expectEqual à expect(a == b) ?

Exercices

Exercice 1Échauffement

Écris un bloc test qui vérifie qu'une fonction double(x: i32) i32 renvoie bien 10 pour l'entrée 5, en affichant les deux valeurs si ça casse.

Voir une solution

On utilise expectEqual (et non expect(double(5) == 10)) pour que Zig affiche l'attendu et l'obtenu en cas d'échec. Le @as(i32, 10) fixe le type de la valeur attendue pour qu'il corresponde à celui renvoyé.

Exercice 2Application

Ce test échoue avec un message de fuite mémoire. Pourquoi ? Corrige-le.

Voir une solution

La ArrayList a alloué de la mémoire (dans append) mais on ne l'a jamais libérée. À la fin du test, std.testing.allocator constate qu'un bloc reste vivant et signale la fuite. Correction : libérer la liste avec defer dès sa création.

C'est exactement l'intérêt de l'allocateur de test : il transforme un oubli de deinit en échec immédiat, au lieu d'une fuite invisible en production.

Exercice 3Défi

Tu veux vérifier qu'une fonction racine(x: f64) !f64 renvoie error.Negatif pour une entrée négative, et une valeur approchée de 3.0 pour 9.0. Écris les deux tests.

Voir une solution

Deux vérifications complémentaires : expectError confirme le chemin d'erreur (l'entrée invalide renvoie précisément error.Negatif), et expectApproxEqAbs gère le flottant avec une tolérance (on ne teste jamais l'égalité exacte de deux f64). Noter le try racine(9.0) : on déballe la valeur avant de la comparer.
