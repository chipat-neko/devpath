Module 3 · Zig en pratique — Leçon 08

comptime : la métaprogrammation

~55 min Avancé Prérequis : leçon 7

À la fin de cette leçon, tu sauras

  • exécuter du code à la compilation avec comptime ;
  • écrire des fonctions génériques via les types en paramètre ;
  • générer des types à la compilation ;
  • comprendre pourquoi Zig n'a pas besoin de macros.
Sommaire de la leçon

Voici la fonctionnalité la plus originale de Zig : comptime. L'idée est aussi simple que radicale : une partie du code peut s'exécuter à la compilation, pas à l'exécution. Du même langage, sans macros ni système de templates séparé. C'est ce qui donne à Zig sa généricité, sa métaprogrammation et une bonne part de sa puissance.

Calculer à la compilation

Le mot-clé comptime force l'évaluation d'une expression pendant la compilation. Le résultat est gravé dans le binaire ; aucun calcul à l'exécution.

Les types comme arguments

Rappelle-toi : en Zig, un type est une valeur. On peut donc passer un type en argument à une fonction — à condition que ce soit un argument comptime (connu à la compilation). C'est la base de la généricité.

La même fonction marche pour tout type : Zig compile une version spécialisée pour chaque T utilisé.

Raccourci : anytype

Quand tu n'as pas besoin de nommer le type, anytype laisse Zig le déduire à l'appel : fn maximum(a: anytype, b: anytype) accepte n'importe quel couple compatible, sans écrire comptime T: type. Plus court ; mais tu perds le nom T réutilisable dans la signature, si bien que comptime T: type reste préférable dès que le type doit reparaître ailleurs (type de retour, autre paramètre).

La généricité sans templates

Là où le C++ a un système de templates séparé et où Java a des génériques limités, Zig réutilise simplement comptime. Un conteneur générique est une fonction qui renvoie un type.

C'est exactement ainsi que ArrayList(i32) de la stdlib fonctionne : une fonction comptime qui fabrique un type.

Une fonction générique n'est vérifiée qu'à l'appel

Le corps d'une fonction comptime T: type n'est validé que lorsqu'on l'instancie avec un type concret. maximum(i32, …) compile ; mais maximum appelée avec un type qui ne supporte pas > (une struct, par exemple) n'échoue qu'à cet appel-là, jamais à la définition. Tant qu'un type n'est pas utilisé, une incompatibilité peut passer inaperçue : pense à couvrir chaque instanciation prévue par un test.

inline : dérouler à la compilation

inline for et inline while déroulent la boucle à la compilation : chaque itération devient du code distinct, ce qui permet par exemple de parcourir les champs d'un type.

Pourquoi pas de macros ?

Beaucoup de langages ont des macros — un mini-langage séparé pour générer du code (le préprocesseur C, les macros Rust…). Zig les évite : tout ce qu'on ferait avec une macro, on le fait avec comptime, dans le même langage. Un seul ensemble de règles à apprendre, et du code généré qu'on peut lire et déboguer normalement.

Cas réel — l'affichage formaté de la stdlib

Quand tu écris std.debug.print("{}", .{point}), comment Zig sait-il afficher un struct qu'il n'a jamais vu ? À la compilation, la fonction de formatage inspecte le type via @typeInfo, parcourt ses champs avec un inline for, puis génère le code d'affichage adapté, champ par champ. Aucune réflexion à l'exécution, aucune annotation : tout est résolu en comptime. C'est le même mécanisme qui alimente la sérialisation JSON de la bibliothèque standard.

Pièges fréquents

Piège fréquent

Vouloir passer un type calculé à l'exécution : un argument comptime T: type doit être connu à la compilation. Tu ne peux pas choisir un type selon une saisie utilisateur. Si tu as besoin de variabilité à l'exécution, c'est le rôle des unions étiquetées (leçon 5).

Pour aller plus loin

Pour aller plus loin

La réflexion via @typeInfo permet d'inspecter n'importe quel type à la compilation (ses champs, ses méthodes) et de générer du code en conséquence : c'est ainsi que Zig implémente l'affichage formaté, la sérialisation, etc., sans annotations ni génération de code externe.

Glossaire

comptime
Mot-clé qui force l'évaluation d'un code à la compilation ; le résultat est gravé dans le binaire, sans coût à l'exécution.
Métaprogrammation
Écrire du code qui produit ou manipule du code (ou des types) ; en Zig, elle se fait en comptime, dans le langage lui-même.
Généricité
Écrire une fonction ou un conteneur valable pour tout type ; obtenue en passant le type en argument comptime.
Type comme valeur
En Zig, un type est une valeur ordinaire : on peut le stocker, le passer en argument et le renvoyer.
anytype
Type de paramètre inféré à l'appel : la fonction accepte n'importe quel argument et Zig déduit son type. Plus concis que comptime T: type, mais sans nom de type réutilisable dans la signature.
inline for / while
Boucle déroulée à la compilation : chaque itération devient du code distinct (utile pour parcourir les champs d'un type).
@typeInfo
Fonction intégrée qui donne accès à la structure d'un type (champs, variantes, méthodes) pour de la réflexion à la compilation.
Macro
Langage séparé de génération de code (préprocesseur C, macros Rust…) ; Zig s'en passe grâce à comptime.

Récap et vérification

  • comptime exécute du code à la compilation ; le résultat est gravé dans le binaire.
  • Un type est une valeur : on le passe en argument comptime pour la généricité.
  • Un conteneur générique est une fonction qui renvoie un type (comme ArrayList).
  • Zig n'a pas de macros : comptime + @typeInfo font tout, dans le même langage.
