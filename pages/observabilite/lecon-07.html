OpenTelemetry : instrumenter avec un standard ouvert

~35 min Avancé Leçons 01 à 06 conseillées

À la fin de cette leçon, tu sauras

  • expliquer ce qu'est OpenTelemetry et le problème qu'il résout ;
  • distinguer API, SDK et Collector ;
  • comprendre le protocole OTLP et les exporters ;
  • décrire la propagation de contexte (traceparent).
Sommaire de la leçon

Dans les leçons précédentes, on a instrumenté logs, métriques et traces « à la main », chacun avec ses outils. Le problème : chaque bibliothèque, chaque langage, chaque fournisseur avait son format. Changer de backend (passer de Jaeger à un service cloud, par exemple) obligeait à ré-instrumenter tout le code. OpenTelemetry (souvent abrégé OTel) règle ce problème : un standard unique pour produire les trois signaux, indépendant de l'outil qui les stocke et les affiche.

Le problème que résout OpenTelemetry

OpenTelemetry est un projet de la CNCF (la fondation qui héberge aussi Kubernetes). Il naît de la fusion de deux projets concurrents, OpenTracing et OpenCensus, pour offrir un seul ensemble d'API, de SDK et de conventions. L'idée directrice : instrumenter une fois, envoyer n'importe où.

API, SDK, Collector : qui fait quoi

OpenTelemetry sépare volontairement trois responsabilités. Cette séparation est ce qui permet de découpler ton code de l'outillage.

  • L'API : l'ensemble des fonctions que ton code appelle (créer un span, incrémenter un compteur). Volontairement minimale et stable pour ne pas casser ton code quand l'implémentation évolue.
  • Le SDK : l'implémentation concrète de l'API. C'est lui qui décide de l'échantillonnage, groupe les données en lots, et les envoie via un exporter.
  • Le Collector : un binaire indépendant de l'application qui reçoit les données (receivers), les transforme (processors : filtrer, enrichir, échantillonner) et les envoie (exporters). Le déployer permet de centraliser la configuration hors du code.

Astuce — le Collector, pas obligatoire mais recommandé

Une application peut exporter directement vers un backend, sans Collector. Mais passer par le Collector isole l'app des détails du backend : on change de fournisseur, on ajoute un filtrage ou un échantillonnage en un seul endroit, sans redéployer les applications.

OTLP : le protocole commun

OTLP (OpenTelemetry Protocol) est le format de transport natif d'OTel. Les données voyagent en gRPC ou HTTP vers le Collector ou un backend. Son intérêt : un format unique pour les trois signaux, compris par un nombre croissant d'outils. Fini les convertisseurs entre chaque paire d'outils.

Auto-instrumentation : instrumenter sans (presque) coder

Écrire chaque span à la main serait fastidieux. OTel fournit des bibliothèques d'auto-instrumentation : elles s'accrochent aux frameworks courants (serveur HTTP, client de base de données, client HTTP sortant) et créent automatiquement des spans pour chaque requête. En Java ou Node.js, un simple agent à charger au démarrage suffit pour obtenir des traces sans modifier le code métier.

Cas réel — la stratégie d'adoption typique

Beaucoup d'équipes démarrent avec l'auto-instrumentation seule : en quelques minutes, elles voient déjà les requêtes HTTP entrantes, les appels sortants et les requêtes SQL, sans écrire une ligne. Puis elles ajoutent, ponctuellement, de l'instrumentation manuelle sur les parties métier qui comptent (« span validation du panier », « span calcul du prix »). Des acteurs comme Shopify ou eBay ont documenté cette bascule vers OpenTelemetry précisément pour ne plus dépendre du format d'un seul fournisseur et garder la liberté de changer d'outil.

La propagation de contexte : coudre les services

Pour qu'une trace suive une requête à travers plusieurs services (revoir la leçon 04), chaque service doit transmettre l'identifiant de trace au suivant. OpenTelemetry utilise le standard W3C Trace Context : un en-tête HTTP nommé traceparent voyage avec la requête.

Sans propagation, chaque service produirait des traces isolées impossibles à relier. Avec elle, on retrouve le fil — exactement le trace_id qui, en leçon 06, cousait les trois piliers.

Attention — la propagation se coupe facilement

Si un service oublie de transmettre l'en-tête traceparent (appel HTTP fait « à la main » sans instrumentation, passage par une file de messages non instrumentée…), la trace se brise en deux. On se retrouve avec deux demi-traces sans lien. L'auto-instrumentation gère ça pour les cas courants ; les chemins exotiques demandent d'y penser explicitement.

Antisèche — OpenTelemetry

Glossaire

OpenTelemetry (OTel)
Standard ouvert (CNCF) qui unifie la production de logs, métriques et traces, indépendamment du backend.
API OTel
L'ensemble stable de fonctions que le code appelle pour instrumenter, sans dépendre d'une implémentation.
SDK OTel
L'implémentation de l'API : échantillonnage, mise en lots, envoi via les exporters.
Collector
Service indépendant qui reçoit les signaux (receivers), les traite (processors) et les redistribue (exporters).
OTLP
OpenTelemetry Protocol : le format de transport natif (gRPC ou HTTP) des trois signaux.
Exporter
Composant qui envoie les données vers une destination donnée (Jaeger, Prometheus, un service cloud…).
Auto-instrumentation
Bibliothèques qui créent automatiquement des spans pour les frameworks courants, sans coder.
Propagation de contexte
Transmission du trace_id d'un service à l'autre via l'en-tête W3C traceparent.

Récap et vérification

  • OpenTelemetry unifie logs, métriques et traces : on instrumente une fois, on exporte n'importe où.
  • L'API (stable) est ce qu'appelle le code ; le SDK l'implémente ; le Collector reçoit et redistribue.
  • OTLP est le protocole commun ; les exporters choisissent la destination sans changer le code.
  • La propagation via traceparent relie les spans d'une requête à travers les services.

Exercices

Exercice 1Échauffement

Une équipe exporte ses traces directement depuis l'application vers Jaeger, sans Collector. On lui demande d'ajouter aussi un envoi vers un service cloud, et de masquer un champ sensible. Pourquoi introduire un Collector simplifie-t-il ces deux besoins ?

Voir une solution

Sans Collector, chaque changement de destination ou de traitement doit être fait dans le code de chaque application, puis redéployé. Avec un Collector, on configure ces besoins en un seul endroit, hors du code : (1) ajouter un second exporter (vers le service cloud) dans le pipeline du Collector fait partir les traces vers deux destinations à la fois, sans toucher aux applications ; (2) ajouter un processor qui masque ou supprime le champ sensible s'applique à tout le flux, quelle que soit l'app émettrice. Le Collector agit comme un point de passage central : les applications continuent d'émettre en OTLP sans rien savoir des backends ni des règles de filtrage. C'est exactement le découplage recherché — le code reste stable, l'exploitation évolue de son côté.

Exercice 2Application

Un microservice panier appelle un microservice paiement. Dans l'outil de traces, on ne voit jamais les deux services dans une même trace : toujours deux traces séparées. Quelle est la cause la plus probable, et comment la corriger ?

Voir une solution

La cause la plus probable est une rupture de propagation de contexte : le service panier n'inclut pas l'en-tête traceparent dans son appel HTTP vers paiement, ou le service paiement ne le lit pas pour rattacher son span. Résultat : paiement démarre une nouvelle trace avec un trace_id différent, au lieu de continuer celle du panier — d'où deux traces isolées. Corrections : (1) s'assurer que le client HTTP du panier est auto-instrumenté (ou injecter manuellement le contexte dans les en-têtes de la requête sortante) ; (2) s'assurer que le serveur HTTP du paiement est instrumenté pour extraire le traceparent entrant et créer son span comme enfant. Si un intermédiaire non instrumenté s'intercale (une file de messages, un proxy qui réécrit les en-têtes), il faut y propager le contexte explicitement. Une fois la chaîne rétablie, les deux services partagent le même trace_id et apparaissent dans une seule cascade, ce qui permet enfin de voir où le temps est passé de bout en bout.

Exercice 3Défi

Ta direction hésite à adopter OpenTelemetry : « on a déjà un outil qui marche, pourquoi ajouter une couche ? ». Construis un argumentaire en distinguant le court terme et le long terme.

Voir une solution

L'argument central est le découplage entre l'instrumentation (dans le code, coûteuse à écrire et à maintenir) et le backend (l'outil qui stocke et affiche). Court terme : OTel n'oblige pas à jeter l'outil actuel — on peut continuer à l'alimenter via un exporter. Le gain immédiat vient de l'auto-instrumentation : on obtient rapidement des traces et des métriques cohérentes sur les frameworks courants, avec des conventions partagées (mêmes noms d'attributs partout), ce qui facilite déjà la corrélation. Long terme : c'est là que se joue la vraie valeur. (1) Pas d'enfermement fournisseur : le jour où l'outil actuel devient trop cher, change de tarif ou ne convient plus, on change de backend en éditant la configuration du Collector, sans ré-instrumenter des dizaines de services — un travail qui, autrement, se compterait en mois. (2) Un seul standard à connaître pour toutes les équipes et tous les langages : on réduit la dette de formations et d'intégrations sur mesure. (3) Écosystème : OTel étant porté par la CNCF (comme Kubernetes), les nouveaux outils s'y branchent nativement ; on suit le mouvement plutôt que de le subir. Le risque de ne rien faire : rester prisonnier du format propriétaire d'un fournisseur, et payer très cher (en temps d'ingénierie) toute migration future. On peut donc proposer une adoption progressive et réversible : commencer par brancher OTel en parallèle de l'existant sur un ou deux services, mesurer, puis étendre. Le coût d'entrée est faible, l'option de sortie (changer d'outil sans douleur) a une grande valeur — c'est un investissement de flexibilité.
