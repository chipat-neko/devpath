Module 4 · Tests avancés — Leçon 07

Tests paramétrés et bons jeux de données

~40 min Intermédiaire Prérequis : leçon 02

À la fin de cette leçon, tu sauras

  • Remplacer des tests dupliqués par un test paramétré (test.each) ;
  • Choisir les cas qui comptent : classes d'équivalence et valeurs aux limites ;
  • Ne pas oublier les cas méchants (vide, nul, négatif, immense) ;
  • Fabriquer des données de test lisibles avec des fixtures et des factories.
Sommaire de la leçon

Tu sais écrire un test propre (leçon 2). Mais un même comportement doit souvent être vérifié sur beaucoup de valeurs : une fonction de calcul, une validation, un formatage… Copier-coller le même test dix fois est illisible et fragile. Cette leçon montre comment paramétrer un test, puis — plus important encore — comment choisir les valeurs qui débusquent vraiment les bugs. Car un test ne vaut que par la qualité de son jeu de données.

test.each : un tableau de cas

La plupart des frameworks (Jest, Vitest, JUnit avec @ParameterizedTest, pytest avec @pytest.mark.parametrize…) offrent un test paramétré : on donne un tableau de cas, et le framework génère un test par ligne. En JavaScript, c'est test.each.

Un seul bloc, une seule assertion, et pourtant trois tests distincts au rapport : chaque ligne du tableau devient un cas nommé (les %i sont remplacés par les valeurs). Ajouter un cas ? Une ligne dans le tableau. Chaque cas garde son propre verdict — si le deuxième échoue, les autres tournent quand même.

Astuce — des cas qui se lisent

Pour beaucoup de colonnes, un tableau d'objets est plus clair qu'un tableau de tableaux : test.each([{ age: 11, tarif: "réduit" }, …]) ("à $age ans, tarif $tarif", ({ age, tarif }) => …). Chaque valeur porte alors un nom dans le tableau, et le titre la reprend par ce nom, pas seulement par sa place : le rapport affiche « à 11 ans, tarif réduit ».

Choisir les cas : classes d'équivalence

Paramétrer, c'est facile ; bien choisir les valeurs, c'est le vrai métier. On ne peut pas tout tester (une fonction sur un entier a des milliards d'entrées). L'idée : regrouper les entrées en classes d'équivalence — des ensembles où le programme est censé se comporter pareil — et ne prendre qu'un représentant par classe. Si le code traite bien toute la classe de la même façon, un cas par classe suffit à la couvrir — c'est une hypothèse, que les valeurs aux limites viendront éprouver.

Exemple : une fonction tarif(age) qui applique un prix réduit aux enfants (moins de 12 ans) et aux seniors (65 ans et plus), plein tarif entre les deux. Trois comportements → trois classes.

Les valeurs aux limites : là où ça casse

L'un des bugs les plus répandus est le décalage d'une unité (« off-by-one ») : > écrit à la place de >=, une boucle qui s'arrête un cran trop tôt. Ces erreurs vivent exactement sur les frontières. La règle d'or : pour chaque limite, teste la valeur juste avant et la valeur juste après.

Cas réel — la réduction qui oubliait les 65 ans

Une billetterie appliquait la réduction senior avec age > 65. Résultat : les personnes de 65 ans pile payaient plein tarif — pile la première année où elles y avaient droit. Le bug a survécu des mois car les tests n'essayaient que 40 et 70 ans, jamais la borne. Un unique cas [65, "réduit"] l'aurait attrapé le premier jour. Les frontières ne sont pas un détail : c'est là que le code se trompe.

Ne pas oublier les cas « méchants »

Les jeux de données naïfs ne contiennent que du « gentil ». Or le réel envoie du vide, du nul, du négatif, de l'immense, des accents, des espaces. Passe mentalement cette checklist pour toute entrée :

Attention — un cas d'erreur EST un cas de test

« Que fait la fonction sur une entrée invalide ? » est une question de conception, pas un oubli. Décide (lève une erreur ? renvoie une valeur par défaut ?) puis écris le test qui verrouille cette décision. Un comportement non testé sur l'entrée invalide, c'est un comportement qui dérivera au premier refactor.

Fixtures et factories : des données lisibles

Quand un test a besoin d'un objet complexe (un utilisateur, une commande), le construire à la main encombre et cache l'intention. Une fixture est une donnée de départ réutilisable ; une factory est une fonction qui la fabrique, avec des valeurs par défaut sensées et la possibilité de surcharger juste ce qui compte pour le test.

Le lecteur voit immédiatement ce qui distingue chaque cas (actif: false), sans être noyé par les trois autres champs. Le test dit pourquoi, la factory dit comment.

Pièges fréquents

Piège fréquent

Mettre de la logique dans le tableau de cas (calculer l'attendu avec la même formule que le code testé). Le test se met alors à « prouver » que le code égale… le code. Écris toujours le résultat attendu en dur, calculé de tête ou à la main.

Piège fréquent

Le sur-paramétrage : cinquante lignes qui testent toutes la même classe d'équivalence. Ça gonfle le rapport sans rien couvrir de neuf. Vise la diversité des cas (une par classe + les bornes), pas le nombre.

Pour aller plus loin

Pour aller plus loin

Choisir les cas à la main a une limite : on ne pense qu'aux cas qu'on imagine. Le property-based testing (leçon 10) génère une centaine d'entrées aléatoires par défaut (davantage si on le demande) et vérifie une propriété générale (« trier puis re-trier ne change rien »), débusquant les cas auxquels personne n'avait songé. Côté objets volumineux, regarde aussi les snapshots, qui figent une sortie de référence.

Antisèche

Glossaire

Test paramétré
Un test unique rejoué sur plusieurs jeux de données ; chaque ligne devient un cas distinct au rapport.
test.each
Mécanisme JavaScript (Jest/Vitest) de test paramétré prenant un tableau de cas.
Classe d'équivalence
Ensemble d'entrées que le programme est censé traiter de façon identique ; si c'est bien le cas, un représentant suffit à la couvrir.
Valeur limite (borne)
Entrée située juste à la frontière entre deux classes, où nichent les erreurs de décalage.
Off-by-one
Erreur classique d'un cran (> au lieu de >=, boucle trop courte), révélée par les bornes.
Fixture
Donnée de test préparée à l'avance et réutilisable.
Factory
Fonction qui fabrique une donnée de test, avec des valeurs par défaut surchargeables.

Récap et vérification

  • Un test paramétré (test.each) supprime la duplication : un tableau de cas, un test par ligne, chacun jugé à part.
  • On choisit les valeurs par classes d'équivalence (un représentant par comportement) et surtout par valeurs aux limites (avant/après chaque frontière).
  • Les bugs de bornes (off-by-one) sont parmi les plus fréquents : teste toujours les frontières.
  • Complète avec les cas méchants (vide, null, négatif, immense) et verrouille le comportement sur entrée invalide.
  • Rends les données lisibles avec des fixtures et des factories ; garde le résultat attendu écrit en dur.

Vérifie ta compréhension

  1. Quel intérêt a test.each par rapport à trois tests copiés-collés ?
  2. Pour une limite « à partir de 18 ans », quelles deux valeurs testes-tu en priorité ?
  3. Pourquoi ne faut-il jamais calculer le résultat attendu avec la même formule que le code testé ?
