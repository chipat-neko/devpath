Module 3 · Qualité au-delà des tests — Leçon 06

Couverture, intégration continue et qualité du code

~37 min Intermédiaire Leçon 05 requise

À la fin de cette leçon, tu sauras

  • lire une couverture de code et connaître ses limites ;
  • comprendre le rôle de l'intégration continue (CI) ;
  • citer les autres garde-fous de qualité ;
  • assembler une posture qualité cohérente.
Sommaire de la leçon

Les tests sont la pièce maîtresse de la qualité, mais pas la seule. Cette dernière leçon élargit le cadre : comment mesurer ce qu'on teste (la couverture, et ses pièges), comment rejouer automatiquement les tests à chaque changement (l'intégration continue), et quels autres outils gardent un code sain. On passe des tests à une véritable posture qualité.

La couverture de code

La couverture (code coverage) mesure quel pourcentage du code est exécuté par les tests. Un outil instrumente le code et rapporte les lignes (ou branches) jamais atteintes. C'est utile pour repérer les angles morts : du code que personne ne teste.

La couverture indique où regarder : ici, paiement.js est sous-testé alors que c'est un module sensible. On l'utilise comme un radar, pas comme une note.

Les limites de la couverture

Piège majeur : une couverture élevée ne garantit pas de bons tests. Du code peut être exécuté sans être vérifié : un test qui appelle une fonction mais n'affirme rien augmente la couverture sans rien prouver.

De plus, viser 100 % à tout prix mène à des tests inutiles sur du code trivial, et à un faux sentiment de sécurité. La couverture est un indicateur, pas un objectif : 70 % de tests pertinents valent mieux que 100 % de tests creux. Surveille surtout la couverture des parties critiques (logique métier, sécurité, paiement), et méfie-toi du chiffre global pris seul.

L'intégration continue

Écrire des tests ne sert que si on les lance. L'intégration continue (Continuous Integration, CI) automatise ça : à chaque push de code, un serveur récupère le projet, installe les dépendances, et rejoue toute la suite de tests. Si un test échoue, l'équipe est alertée immédiatement — avant que le code cassé ne se propage.

L'effet est puissant : le code de la branche principale reste toujours vert, car rien n'y entre sans passer les tests. La CI transforme les tests d'une bonne intention individuelle en un garde-fou collectif et automatique. C'est le pont vers le déploiement continu (CD), qui livre automatiquement le code validé.

Les autres garde-fous

La qualité s'appuie sur plusieurs outils complémentaires, au-delà des tests :

  • le linter : il analyse le code sans l'exécuter pour repérer erreurs probables, mauvaises pratiques et code suspect (variable inutilisée, comparaison douteuse…).
  • le formateur (formatter) : il met le code en forme automatiquement (indentation, espaces), pour un style uniforme et des revues focalisées sur le fond, pas la forme.
  • la vérification de types (TypeScript, types statiques) : elle attrape des erreurs avant l'exécution, comme passer un texte là où un nombre est attendu.
  • la revue de code (code review) : un humain relit les changements ; elle attrape ce qu'aucun outil ne voit (logique, clarté, choix de conception) et diffuse la connaissance.

Ces garde-fous se cumulent avec les tests, chacun attrapant une classe de problèmes différente. Branchés dans la CI, ils s'appliquent automatiquement à chaque changement.

Pour aller plus loin

Tu as maintenant une vue d'ensemble de la qualité logicielle. Pour approfondir : les tests basés sur les propriétés (générer des centaines d'entrées aléatoires pour éprouver une invariante) ; le mutation testing (introduire des bugs pour vérifier que les tests les détectent — un vrai test de tes tests) ; les tests de contrat entre services ; et la mise en place concrète d'une CI/CD. Et applique les outils de ton langage : chaque cours de langage (Java, Rust, Kotlin…) montre son framework de test et son outillage.

Cas réel — quand la couverture devient une cible

Des équipes imposent un seuil de couverture obligatoire (souvent « 100 % ») pour bloquer toute fusion en dessous. L'intention est bonne, mais l'effet pervers est connu : sous pression, des développeurs écrivent des tests qui appellent le code sans rien affirmer, uniquement pour faire monter le chiffre. La couverture atteint 100 %… et ne prouve toujours rien. C'est une illustration de la loi de Goodhart : « quand une mesure devient un objectif, elle cesse d'être une bonne mesure ». Les équipes matures suivent plutôt la tendance de la couverture et surveillent surtout les modules critiques (paiement, sécurité), au lieu de brandir un chiffre global comme une note.

Antisèche

Glossaire

Couverture de code
Pourcentage du code exécuté par les tests ; repère les angles morts, ne prouve pas la justesse.
Couverture de branches
Part des embranchements (if/else) réellement empruntés par les tests, plus fine que la couverture de lignes.
Intégration continue (CI)
Automatisation qui rejoue tests et vérifications à chaque push, bloquant la fusion en cas d'échec.
Pipeline
Suite d'étapes automatisées (installer, linter, tester, mesurer) déclenchée par un changement.
Linter
Outil d'analyse statique qui repère erreurs probables et mauvaises pratiques sans exécuter le code.
Formateur
Outil qui met le code en forme automatiquement pour un style uniforme.
Revue de code
Relecture humaine des changements ; attrape ce qu'aucun outil ne voit et diffuse la connaissance.
Posture qualité
Ensemble de couches complémentaires (tests, couverture, outils, CI, revue) plutôt qu'un seul outil.

Récap et vérification

  • La couverture repère les angles morts, mais une couverture élevée ne garantit pas de bons tests (du code exécuté ≠ vérifié) ; c'est un indicateur, pas un objectif.
  • L'intégration continue rejoue les tests à chaque push : la branche principale reste toujours verte.
  • Autres garde-fous : linter, formateur, types, revue de code — cumulés, branchés dans la CI.
  • La qualité est une posture faite de couches complémentaires, pas d'un seul outil.

Vérifie ta compréhension

  1. Pourquoi une couverture de 100 % ne garantit-elle pas un code bien testé ?
  2. Que fait l'intégration continue à chaque push ?
  3. Cite deux garde-fous de qualité autres que les tests, et ce qu'ils attrapent.

Exercices

Exercice 1Échauffement

Vrai ou faux : « atteindre 100 % de couverture signifie que le code est sans bug ». Justifie.

Voir une solution

Faux. La couverture mesure quelles lignes sont exécutées par les tests, pas si elles sont correctement vérifiées. Un test sans assertion (ou avec une assertion faible) peut couvrir du code fautif sans le détecter. De plus, 100 % ne dit rien des cas non envisagés (entrées inattendues, combinaisons). C'est un indicateur d'angles morts, pas une garantie d'absence de bug.

Exercice 2Application

Une équipe a de bons tests mais oublie souvent de les lancer avant de fusionner. Quel mécanisme résout ce problème, et comment ?

Voir une solution

L'intégration continue (CI). Configurée sur le dépôt, elle rejoue automatiquement toute la suite de tests à chaque push, sans dépendre de la mémoire de chacun. On peut en plus bloquer la fusion tant que les tests ne passent pas : il devient alors impossible d'intégrer du code cassé. La discipline individuelle est remplacée par un garde-fou automatique et collectif.

Exercice 3Synthèse

Décris une « chaîne qualité » complète qui s'exécute à chaque modification de code, en combinant ce que tu as appris dans ce cours.

Voir une solution

Chaque couche attrape une classe de problèmes différente. Ensemble, dans la CI, elles gardent la branche principale toujours verte et le code sain — c'est la posture qualité visée par tout le cours.
