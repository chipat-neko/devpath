Module 4 · Tests avancés — Leçon 10

Tests basés sur les propriétés et mutation testing

~44 min Avancé Prérequis : leçons 02 et 06

À la fin de cette leçon, tu sauras

  • Écrire un test basé sur une propriété et laisser l'outil générer une centaine de cas, ou davantage ;
  • Reconnaître de bonnes propriétés (aller-retour, invariant, idempotence, oracle) ;
  • Comprendre le shrinking qui réduit un contre-exemple au plus simple ;
  • Éprouver la qualité de tes tests avec le mutation testing et lire un score de mutation.
Sommaire de la leçon

Jusqu'ici, tu choisissais toi-même les entrées de tes tests : « pour 25, j'attends true ». C'est précis, mais tu ne testes que les cas auxquels tu penses — et les bugs se cachent justement dans ceux que tu oublies. Deux techniques renversent la perspective : le test basé sur les propriétés laisse une machine générer les entrées à ta place, et le mutation testing teste… tes tests. Ce sont les outils qui séparent une suite « qui passe » d'une suite en laquelle on a vraiment confiance.

Des exemples choisis à la propriété

Un test classique affirme un lien entre une entrée et une sortie. Un test basé sur les propriétés (property-based testing, PBT) affirme une règle qui doit tenir pour toutes les entrées, puis laisse l'outil générer les cas aléatoires — une centaine par défaut avec fast-check, des centaines ou des milliers si on le lui demande — pour tenter de la mettre en défaut.

Reprenons l'idée d'idempotence : trier une liste déjà triée ne doit plus rien changer. Plutôt qu'un exemple, on affirme la règle pour n'importe quel tableau :

Une seule règle éprouve des entrées qu'on n'aurait jamais écrites à la main : tableau vide, tableau d'un seul élément, valeurs négatives, entiers énormes. C'est là que nichent les bugs. Les doublons, eux, sortent rarement d'un générateur par défaut, et les très grandes tailles jamais : il faut les lui demander.

Le shrinking : un contre-exemple minimal

Quand une propriété tombe, l'outil ne se contente pas de crier « ça casse pour [847, -12, 91, 847, 0, 6] ». Il réduit (shrink) automatiquement ce contre-exemple vers le plus petit qui échoue encore — souvent un tableau d'un ou deux éléments, comme [0, 0] ou [1]. Ce cas minimal pointe droit vers la cause.

Reconnaître de bonnes propriétés

La difficulté du PBT n'est pas l'outil, c'est de trouver la propriété. Quelques familles reviennent sans cesse :

  • Aller-retour (round-trip) : décoder(encoder(x)) === x. Sérialisation, compression, parsing.
  • Invariant : une propriété conservée. Trier ne change pas la longueur ni l'ensemble des éléments.
  • Idempotence : f(f(x)) === f(x). Trier, normaliser, dédupliquer.
  • Oracle : comparer à une implémentation lente mais évidemment correcte (une version naïve).
  • Métamorphique : une relation entre deux appels. trier(tab) et trier(mélange(tab)) donnent le même résultat.

Astuce — cherche des propriétés, pas des résultats

Quand tu bloques, demande : « qu'est-ce qui reste vrai quoi qu'il arrive ? » Souvent tu ne connais pas le résultat exact d'une entrée aléatoire, mais tu connais une relation qui doit tenir : la sortie a la bonne taille, elle est triée, l'aller-retour revient au départ. Le PBT complète tes tests par l'exemple, il ne les remplace pas.

Le mutation testing : tester ses tests

La couverture (leçon 6) dit quelles lignes s'exécutent, pas si elles sont vérifiées. Le mutation testing répond à la vraie question : « si j'introduis un bug, mes tests le remarquent-ils ? » L'outil crée des mutants — des copies du code avec une petite altération (>= devient >, + devient -) — puis relance la suite sur chacun.

Ce mutant survivant révèle exactement ce que la leçon 7 enseignait : il manque un test sur la valeur limite. Le mutation testing transforme cette intuition en mesure objective : le score de mutation (part de mutants tués) mesure la force de détection de ta suite, là où la couverture ne mesure que son étendue.

Attention — couverture élevée, tests faibles

Un module peut afficher 100 % de couverture et un score de mutation médiocre : le code est exécuté partout, mais des dizaines de mutants survivent faute d'assertions précises. C'est le meilleur argument contre la couverture prise comme note : elle ne voit pas les tests creux, le mutation testing si.

Cas réel — un bug endormi vingt ans dans la recherche dichotomique

En 2006, Joshua Bloch (Google, ex-Sun) révèle que presque toutes les recherches dichotomiques et tris fusion contiennent le même bug : le calcul du milieu (bas + haut) / 2 déborde la capacité d'un entier 32 bits quand le tableau dépasse ~1 milliard d'éléments. L'algorithme était publié — et prouvé correct — depuis vingt ans ; dans la bibliothèque de Java, le bug a dormi environ neuf ans. Aucun exemple écrit à la main n'utilisait un tableau assez grand — et un générateur par défaut non plus, avec ses tableaux de dix éléments au plus : une propriété ne vaut que par les entrées qu'on lui fait générer, et il aurait fallu lui demander exprès des index proches du maximum d'un entier. (En JavaScript, où les nombres ne sont pas des entiers 32 bits, ce calcul ne déborde pas.) Correctif en Java : bas + (haut - bas) / 2.

Pièges fréquents

Piège fréquent — la propriété tautologique

Réécrire le code sous test dans la propriété ne prouve rien : expect(trier(t)).toEqual(monTri(t)) où monTri est une copie du code teste juste que deux clones sont d'accord. Une bonne propriété exprime une vérité indépendante de l'implémentation (tri croissant, même longueur), pas une paraphrase.

Piège fréquent — les mutants équivalents

Certains mutants ne changent rien au comportement observable (dans une boucle for (i = 0; i < n; i++) où n est un entier positif, remplacer i < n par i != n) : aucun test ne peut les tuer, et c'est normal. Ils empêchent d'atteindre 100 % de score : vise une tendance élevée, pas le sans-faute absolu.

Pour aller plus loin

Pour aller plus loin

Le PBT existe dans tous les langages : QuickCheck (Haskell, l'ancêtre de 1999), fast-check (JS/TS), Hypothesis (Python), jqwik (Java). Côté mutants : Stryker (JS), PIT (Java), mutmut (Python). Étape suivante : le model-based testing, où l'outil génère non pas des entrées mais des séquences d'actions et les compare à un modèle simplifié du système — redoutable pour éprouver une machine à états.

Antisèche

Glossaire

Test basé sur les propriétés
Test affirmant une règle universelle ; l'outil génère les entrées (une centaine par défaut) pour la mettre en défaut.
Propriété
Énoncé vrai pour toute entrée valide (aller-retour, invariant, idempotence, oracle, métamorphique).
Générateur
Composant qui produit des entrées aléatoires d'un type donné (entiers, tableaux, objets).
Shrinking
Réduction automatique d'un contre-exemple vers le plus petit cas qui échoue encore.
Mutation testing
Technique introduisant des mutants dans le code pour vérifier que les tests les détectent.
Mutant
Version du code modifiée par une petite altération ; tué si un test échoue, survivant sinon.
Score de mutation
Part des mutants tués ; mesure la capacité de détection de la suite, complémentaire de la couverture.
Mutant équivalent
Mutant au comportement identique à l'original : aucun test ne peut le tuer.

Récap et vérification

  • Le property-based testing énonce une règle vraie pour toutes les entrées et laisse l'outil générer les cas — il éprouve ce qu'on n'aurait pas écrit.
  • Cherche des propriétés : aller-retour, invariant, idempotence, oracle, métamorphique.
  • Le shrinking réduit un contre-exemple au plus petit cas fautif : le diagnostic devient limpide.
  • Le mutation testing teste tes tests : un mutant survivant = un cas ou une assertion qui manque (sauf mutant équivalent) ; le score de mutation mesure la force de détection, là où la couverture ne mesure que l'étendue.

Vérifie ta compréhension

  1. En quoi une propriété diffère-t-elle d'un test par l'exemple ?
  2. À quoi sert le shrinking quand une propriété échoue ?
  3. Que signifie un mutant « survivant », et que révèle-t-il ?
