Les doublures de test : mocks, stubs et fakes

~37 min Avancé Leçon 04 requise

À la fin de cette leçon, tu sauras

  • expliquer pourquoi isoler le code testé ;
  • distinguer stub, mock et fake ;
  • simuler une dépendance (base, réseau, temps) ;
  • éviter le piège du sur-mocking.
Sommaire de la leçon

Un test unitaire doit être rapide et déterministe. Or beaucoup de code dépend de choses lentes ou imprévisibles : une base de données, un appel réseau, l'heure courante, un envoi d'e-mail. Tester avec ces vraies dépendances rendrait le test lent, fragile et parfois impossible. La solution : les doublures de test (test doubles), des objets de remplacement qui imitent une dépendance pour le temps du test.

Pourquoi isoler ?

Imagine un service d'inscription qui, après avoir créé l'utilisateur, envoie un e-mail de bienvenue. Tester réellement enverrait un vrai e-mail à chaque exécution — inacceptable. On veut tester la logique d'inscription sans déclencher l'envoi réel. La doublure remplace le service d'e-mail par un faux, le temps du test.

Remarque que la fonction reçoit serviceEmail en paramètre : c'est l'injection de dépendance. Elle rend le code testable, car on peut fournir une doublure à la place du vrai service. Un code difficile à doubler est souvent un code aux dépendances trop rigides : tester révèle, là encore, un défaut de conception.

Stub, mock, fake

« Doublure » est le terme générique. On distingue surtout trois variantes selon ce qu'elles font :

  • un stub : renvoie des réponses prédéfinies pour alimenter le test. « Quand on te demande l'utilisateur 7, réponds toujours ceci. »
  • un mock : une doublure qui sert à vérifier les interactions — qu'une méthode a bien été appelée, avec les bons arguments, le bon nombre de fois.
  • un fake : une vraie implémentation simplifiée, fonctionnelle mais légère — par exemple une « base de données » en mémoire (un simple tableau) au lieu de la vraie.

Le vocabulaire strict (celui de Gerard Meszaros, repris par Martin Fowler) distingue encore l'espion (spy) : une doublure qui enregistre les appels reçus, pour qu'on les vérifie après coup — c'est ce que fait emailMock ci-dessous. Le mock au sens strict, lui, est programmé d'avance avec les appels attendus. Beaucoup d'outils mêlent les deux mots : la documentation de Jest dit de ses « mock functions » qu'on les appelle aussi des « spies ». Dans cette leçon, « mock » désigne toute doublure qui sert à vérifier une interaction.

En pratique, on parle souvent de « mock » pour toute doublure, mais la nuance compte : un stub sert à fournir des entrées, un mock à vérifier un comportement de sortie (un appel attendu). Les bibliothèques de mocking de chaque langage (vues dans les cours de langage) automatisent leur création.

Simuler le temps et le hasard

Deux dépendances sournoises rendent un test non déterministe : l'horloge et l'aléatoire. Un test qui dépend de l'heure réelle ou d'un nombre tiré au hasard donnera des résultats différents à chaque exécution — ce qui viole le « R » de FIRST (reproductible).

Le principe général : rendre l'imprévisible injectable. Au lieu d'appeler directement l'horloge ou le générateur aléatoire, on les passe en paramètre (ou via une dépendance), pour qu'un test puisse fournir une valeur fixe. Beaucoup de frameworks offrent aussi des « fausses horloges » qui figent ou avancent le temps à volonté.

Le piège du sur-mocking

Les doublures sont utiles, mais on peut en abuser. Si un test mock tout, il finit par ne tester que ses propres mocks — pas le vrai code. Pire, il devient couplé aux détails d'implémentation : change la façon dont le code appelle ses dépendances, et le test casse alors que le comportement est correct.

Règle d'équilibre : ne double que ce qui est lent, externe ou imprévisible (base, réseau, temps, e-mail). Pour la logique pure, utilise les vrais objets : c'est plus simple et plus fiable. Et préfère vérifier des résultats (ce que le code produit) plutôt que des interactions internes (comment il s'y prend), quand c'est possible. Un fake (base en mémoire) est souvent préférable à une forêt de mocks.

Tester le comportement, pas l'implémentation

Le meilleur test résiste au refactoring : tu réorganises le code sans changer ce qu'il fait, et le test reste vert. Si tes tests cassent à chaque refactoring interne, c'est qu'ils testent le « comment » au lieu du « quoi ». Vise des tests qui décrivent un comportement observable : ils protègent vraiment, et te laissent libre d'améliorer le code dessous.

Cas réel — « préférez les fakes aux mocks »

Dans Software Engineering at Google (2020), le chapitre consacré aux doublures recommande d'abord d'utiliser l'implémentation réelle quand c'est possible, et sinon de privilégier les fakes — de vraies implémentations simplifiées, souvent fournies par l'équipe qui possède la dépendance — plutôt que de multiplier les mocks. La raison est exactement celle du sur-mocking : un test bardé de mocks se couple au comment du code et casse à chaque remaniement, alors qu'un test appuyé sur un fake vérifie le quoi et résiste aux changements internes. Beaucoup d'équipes ont fait ce chemin : parties de suites où chaque appel était mocké (fragiles, pénibles à maintenir), elles sont passées à des fakes partagés (une base en mémoire, un faux service de paiement) et ont retrouvé des tests stables qui survivent au refactoring.

Antisèche

Glossaire

Doublure de test (test double)
Objet de remplacement qui imite une dépendance le temps du test.
Stub
Doublure qui renvoie des réponses prédéfinies pour alimenter le test.
Mock
Doublure qui vérifie les interactions : méthode appelée, arguments, nombre d'appels.
Espion (spy)
Au sens strict, doublure qui enregistre les appels reçus pour qu'on les vérifie après coup ; souvent rangé sous « mock ».
Fake
Vraie implémentation simplifiée mais fonctionnelle (ex. base de données en mémoire).
Injection de dépendance
Passer une dépendance en paramètre plutôt que la créer en dur, pour pouvoir la doubler.
Déterministe
Qui produit toujours le même résultat pour les mêmes entrées (temps et hasard maîtrisés).
Sur-mocking
Abus de doublures qui couple le test à l'implémentation et le rend fragile.
Effet de bord
Action observable hors du calcul (envoyer un e-mail, écrire en base) qu'une doublure neutralise.

Récap et vérification

  • Les doublures remplacent une dépendance lente/imprévisible pour garder un test rapide et déterministe ; l'injection de dépendance les rend possibles.
  • Stub (réponses prédéfinies), mock (vérifie les interactions), fake (implémentation simplifiée réelle).
  • Rendre l'imprévisible injectable (temps, hasard) pour des tests reproductibles.
  • Éviter le sur-mocking : ne doubler que l'externe ; tester le comportement, pas l'implémentation.

Exercices

Exercice 1Échauffement

Identifie le type de doublure : (a) un objet qui renvoie toujours {id: 1, nom: "Lou"} ; (b) un objet qui enregistre les appels pour vérifier qu'une méthode a été appelée.

Voir une solution

(a) un stub (il fournit une réponse prédéfinie) ; (b) un mock (il vérifie une interaction : l'appel a-t-il eu lieu ?). Au sens strict, un objet qui enregistre les appels est un espion ; cette leçon le range sous « mock ».

Exercice 2Application

Rends cette fonction testable de façon déterministe : function codePromoDuJour() { return Math.random() < 0.5 ? "A" : "B"; }.

Voir une solution

En production, on appellera codePromoDuJour(Math.random()) ; en test, on passe une valeur fixe.

Exercice 3Défi

Un collègue mock chaque méthode interne d'une classe pour la tester, et ses tests cassent à chaque refactoring. Diagnostique et propose une meilleure approche.

Voir une solution

Diagnostic : c'est du sur-mocking ; les tests vérifient comment la classe s'y prend (appels internes) plutôt que ce qu'elle produit. Ils sont couplés à l'implémentation, donc cassent au moindre changement correct. Meilleure approche : ne doubler que les dépendances externes (base, réseau, temps), utiliser les vrais objets pour la logique interne, et écrire des assertions sur le résultat observable (ce que renvoie la classe, l'état final) plutôt que sur la liste des appels internes. Un fake (ex. base en mémoire) remplace avantageusement une forêt de mocks. Les tests résisteront alors au refactoring.
