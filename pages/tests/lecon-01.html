Module 1 · Les bases du test — Leçon 01

Pourquoi tester son code

~30 min Débutant Savoir programmer dans un langage

À la fin de cette leçon, tu sauras

  • expliquer la valeur d'un test automatisé ;
  • comprendre le coût croissant d'un bug ;
  • voir les tests comme un filet de sécurité ;
  • les considérer comme une documentation vivante.
Sommaire de la leçon

Tu sais écrire du code qui marche aujourd'hui. Mais un logiciel vit des mois ou des années : on le modifie, on le corrige, plusieurs personnes y touchent. Comment garantir qu'un changement n'a rien cassé ailleurs ? La réponse de l'industrie tout entière : des tests automatisés, du code qui vérifie ton code. Ce cours est transversal : les principes valent dans tous les langages ; les cours de langage (Java, Rust, Kotlin…) montrent comment les appliquer avec leurs outils.

Avant les techniques, comprenons pourquoi tester. Sans cette conviction, les tests semblent une corvée ; avec elle, ils deviennent un réflexe qui te fait gagner du temps et de la sérénité.

Tester, ça veut dire quoi ?

Tout le monde teste son code : on lance le programme, on regarde si la sortie est bonne. Le problème, c'est que ce test manuel est lent, fastidieux, et qu'on ne le refait jamais entièrement. Un test automatisé capture cette vérification dans du code rejouable : une fois écrit, il se relance en une fraction de seconde, autant de fois qu'on veut.

L'idée est universelle : un test appelle ton code avec des entrées connues et affirme (assert) le résultat attendu. S'il diffère, le test échoue avec un message. Multiplie ça par des centaines de cas, rejouables en une commande : tu obtiens un contrôle de santé instantané de toute l'application.

Erreur fréquente

« Ça compile, donc ça marche. » La compilation ne vérifie que la forme (types, syntaxe), jamais le comportement. De même, lancer l'application à la main une fois ne dit rien des dizaines d'autres cas, ni de ce qu'un futur changement cassera. Seul un test rejouable protège dans la durée.

Le coût croissant d'un bug

Un bug coûte d'autant plus cher qu'il est découvert tard. Trouvé pendant que tu écris le code : quelques minutes. Trouvé par un collègue en revue : une heure. Trouvé en production par un client : des heures de diagnostic, une correction en urgence, une réputation entamée, parfois des données perdues.

Les tests automatisés déplacent la détection vers la gauche de cette échelle : ils attrapent les régressions au moment où tu écris, là où elles coûtent le moins. C'est l'argument économique central : le temps passé à écrire des tests est très inférieur au temps qu'ils font économiser.

Cas réel — Ariane 5, vol 501 (1996)

Trente-sept secondes après le décollage, la fusée européenne Ariane 5 s'autodétruit. La cause : un morceau de code hérité d'Ariane 4, réutilisé sans être re-testé dans les conditions du nouveau lanceur. Une conversion d'un nombre 64 bits vers 16 bits déborde, le calculateur plante, et 370 millions de dollars partent en fumée. La leçon coûte cher : du code « qui marchait » ne marche plus dans un contexte différent — seul un test rejoué dans le nouveau contexte l'aurait révélé au sol.

Le filet de sécurité

Le bénéfice le plus ressenti au quotidien : les tests te donnent le courage de changer le code. Sans tests, toucher à un module qui marche fait peur — on ne sait pas ce qu'on risque de casser. Avec une bonne suite de tests, tu modifies, tu relances les tests, et tu vois immédiatement si quelque chose a cédé.

Ce filet de sécurité est ce qui rend possible le refactoring (améliorer la structure du code sans changer son comportement) et l'évolution sereine d'un projet. Une application sans tests devient, avec le temps, un code que personne n'ose plus toucher : il se fige et pourrit. Les tests gardent un projet vivant et modifiable.

Astuce — le test de non-régression

Quand tu corriges un bug, écris d'abord un test qui le reproduit (il échoue), puis corrige jusqu'à ce qu'il passe. Ce test reste dans la suite : si le bug tente de revenir un jour (après un autre changement), il sera attrapé aussitôt. C'est le meilleur retour sur investissement d'un test.

Une documentation vivante

Un bon test décrit un comportement attendu de façon exécutable. En lisant les tests d'une fonction, on comprend ce qu'elle est censée faire : ses cas normaux, ses cas limites, ses erreurs. C'est une documentation qui ne ment jamais — contrairement aux commentaires, elle ne peut pas devenir obsolète sans que la suite de tests échoue.

D'où l'importance de bien nommer ses tests (on y revient à la leçon 2) : un nom de test est une phrase qui décrit une règle métier. La suite de tests devient alors la spécification vivante du logiciel.

Tester n'est pas « tout tester »

L'objectif n'est pas de tester chaque ligne à 100 %, ni de viser une suite parfaite dès le départ. C'est de tester ce qui compte : la logique métier, les cas limites, les bugs déjà rencontrés (pour qu'ils ne reviennent pas). Un petit ensemble de tests pertinents vaut mieux qu'une montagne de tests triviaux. La qualité prime sur la quantité.

Pour aller plus loin

Ce cours te mènera vers la pyramide des tests (beaucoup de tests unitaires, moins d'intégration, encore moins de bout-en-bout), le schéma Arrange – Act – Assert (leçon 2), le TDD (écrire le test avant le code) et la notion de couverture (quelle part du code est exercée). Chaque cours de langage montre ensuite l'outil concret : JUnit, pytest, Jest, cargo test…

Antisèche

Glossaire

Test automatisé
Code qui exerce une partie du programme avec des entrées connues et affirme le résultat attendu, rejouable à volonté.
Assertion (assert)
Instruction qui vérifie qu'une condition est vraie ; si elle est fausse, le test échoue et le signale.
Régression
Comportement qui fonctionnait et qui casse à la suite d'un changement ailleurs dans le code.
Refactoring
Améliorer la structure interne du code sans changer son comportement observable ; rendu sûr par les tests.
Shift-left
Déplacer la détection des défauts au plus tôt dans le cycle (écriture, revue) où la correction coûte le moins.
Test de non-régression
Test ajouté pour reproduire un bug donné, afin qu'il soit détecté s'il réapparaît.
Documentation vivante
Description exécutable du comportement attendu : elle reste toujours à jour car elle échoue sinon.
Suite de tests
Ensemble des tests d'un projet, lancés ensemble pour donner un état de santé global.

Récap et vérification

  • Un test automatisé capture une vérification dans du code rejouable en une fraction de seconde.
  • Le coût d'un bug croît avec le temps : les tests le détectent tôt, là où il coûte le moins.
  • Les tests sont un filet de sécurité qui donne le courage de modifier et de refactoriser.
  • Ils forment une documentation vivante du comportement, qui ne peut pas devenir obsolète sans échouer.

Vérifie ta compréhension

  1. Quel avantage un test automatisé a-t-il sur un test manuel ?
  2. Pourquoi dit-on que les tests donnent « le courage de changer le code » ?
  3. En quoi les tests sont-ils une documentation qui ne ment pas ?

Exercices

Exercice 1Échauffement

Avec tes mots, explique ce que fait un test automatisé en deux temps (les deux verbes clés).

Voir une solution

Un test exerce le code (il l'appelle avec des entrées connues) puis affirme (assert) le résultat attendu. Si le résultat obtenu diffère de l'attendu, le test échoue et le signale. (On verra à la leçon 2 que s'y ajoute une phase de préparation — le schéma « Arrange, Act, Assert ».)

Exercice 2Application

Un bug de calcul de prix est découvert en production. Cite trois coûts qu'il engendre, et comment un test l'aurait évité.

Voir une solution

Coûts possibles : 1) le temps de diagnostic en urgence (retrouver la cause) ; 2) l'impact client (commandes mal facturées, perte de confiance) ; 3) la correction et le redéploiement en urgence, qui interrompt le travail prévu. Un test sur le calcul de prix (avec quelques cas, dont les cas limites) aurait échoué dès l'écriture du code fautif, attrapant le bug en quelques minutes au lieu de jours.

Exercice 3Défi

Propose trois noms de tests (sous forme de phrases) pour une fonction diviser(a, b), qui en décrivent le comportement attendu.

Voir une solution

Chaque nom est une phrase qui décrit une règle : un cas normal, un cas d'erreur, un cas limite. Ensemble, ils documentent le comportement de diviser.
