Module 1 · Les bases du test — Leçon 03

La pyramide des tests

~35 min Intermédiaire Leçon 02 requise

À la fin de cette leçon, tu sauras

  • distinguer tests unitaires, d'intégration et E2E ;
  • comprendre la pyramide des tests ;
  • arbitrer entre vitesse et confiance ;
  • reconnaître l'anti-pattern du cornet de glace.
Sommaire de la leçon

Tous les tests ne testent pas la même chose. Vérifier qu'une fonction calcule juste, vérifier que deux modules s'assemblent bien, ou vérifier qu'un utilisateur peut acheter un produit de bout en bout : ce sont trois niveaux différents, aux coûts et aux bénéfices différents. Savoir les distinguer et les doser est une compétence clé. La pyramide des tests est le modèle qui guide ce dosage.

Les trois niveaux

  • les tests unitaires : ils vérifient une petite unité isolée (une fonction, une classe), sans ses dépendances réelles. Très rapides (des milliers par seconde), ils localisent précisément un bug.
  • les tests d'intégration : ils vérifient que plusieurs pièces fonctionnent ensemble (le code et la base de données, deux services). Plus lents, ils attrapent les problèmes d'assemblage qu'un test unitaire ne voit pas.
  • les tests de bout en bout (E2E) : ils simulent un parcours utilisateur complet à travers toute l'application (cliquer, remplir un formulaire, valider). Les plus lents et les plus fragiles, mais aussi les plus proches de la réalité.

Aucun niveau ne remplace les autres : ils attrapent des types de bugs différents. Une logique fausse ? Un test unitaire. Un mauvais branchement à la base ? Un test d'intégration. Un bouton cassé dans le parcours d'achat ? Un test E2E.

La pyramide

La pyramide des tests recommande une proportion : beaucoup de tests unitaires à la base, moins de tests d'intégration au milieu, peu de tests E2E au sommet.

La logique : plus on descend, plus les tests sont rapides, stables et précis ; plus on monte, plus ils sont réalistes mais lents et fragiles. On veut donc une large base de tests unitaires (qu'on lance des centaines de fois par jour) et un petit sommet de tests E2E (qui couvrent les parcours critiques).

Le compromis vitesse / confiance

Chaque niveau arbitre entre deux qualités opposées :

Un test unitaire isole tellement le code qu'il peut passer alors que l'assemblage réel est cassé ; un test E2E vérifie le tout, mais il est lent et casse pour de mauvaises raisons (un délai réseau, un sélecteur qui change). La pyramide équilibre : on attrape la majorité des bugs vite et précisément (en bas), et on confirme les parcours essentiels en réaliste (en haut), sans payer le coût des E2E partout.

L'anti-pattern du cornet de glace

L'erreur fréquente est la pyramide inversée, surnommée le cornet de glace (ice-cream cone) : beaucoup de tests E2E (ou manuels) au sommet, peu de tests unitaires à la base.

Conséquences : la suite est lente (on ne la lance plus), fragile (elle casse sans vrai bug), et chère à maintenir. Quand un test E2E échoue, on ne sait pas où est le problème, car il traverse tout. Le remède : faire descendre la couverture vers la base — remplacer des E2E par des tests unitaires et d'intégration ciblés.

La pyramide est un guide, pas une loi

Les proportions exactes dépendent du projet : une bibliothèque de calcul sera presque tout en unitaires ; une application très visuelle aura davantage d'E2E. Retiens l'idée, pas les chiffres : privilégier les tests rapides et précis, réserver les tests lents et réalistes aux parcours qui comptent vraiment. La forme générale doit rester une pyramide, pas un cornet.

Cas réel — d'où vient la pyramide

Le modèle a été popularisé par Mike Cohn dans Succeeding with Agile (2009). La culture de test de Google en donne une proportion souvent citée : environ 70 % d'unitaires, 20 % d'intégration, 10 % d'E2E. Beaucoup d'équipes ont d'abord fait l'inverse : d'énormes suites Selenium de bout en bout qui prenaient des heures et cassaient sans vrai bug. Résultat, plus personne ne les lançait. En rééquilibrant vers la base — remplacer des E2E par des tests unitaires ciblés — ces suites sont repassées de plusieurs heures à quelques minutes, et la confiance est revenue.

Astuce — faire descendre un test

Face à un E2E lent ou fragile, pose-toi la question : « quel bug attrape-t-il vraiment, et un test plus bas ne le prendrait-il pas mieux ? » Souvent, une règle métier testée en E2E se teste en unitaire en une milliseconde. Garde l'E2E seulement pour vérifier que les pièces sont bien branchées sur les parcours critiques.

Antisèche

Glossaire

Test unitaire
Test d'une petite unité isolée (fonction, classe), sans ses dépendances réelles ; rapide et précis.
Test d'intégration
Test vérifiant que plusieurs composants fonctionnent ensemble (code + base de données, deux services…).
Test de bout en bout (E2E)
Test simulant un parcours utilisateur complet à travers toute l'application ; réaliste mais lent.
Pyramide des tests
Modèle de dosage : large base d'unitaires, moins d'intégration, peu d'E2E.
Cornet de glace
Anti-pattern : pyramide inversée avec trop d'E2E et trop peu d'unitaires ; suite lente et fragile.
Test double (mock, stub)
Fausse dépendance qui remplace un composant réel (base, réseau) pour isoler l'unité testée.
Test fragile (flaky)
Test qui échoue de façon intermittente sans vraie régression ; typique des E2E mal maîtrisés.

Récap et vérification

  • Unitaire (une unité isolée, rapide, précis), intégration (plusieurs pièces ensemble), E2E (parcours complet, réaliste).
  • La pyramide : beaucoup d'unitaires, moins d'intégration, peu d'E2E.
  • Compromis : en bas = rapide/précis ; en haut = réaliste mais lent/fragile.
  • Éviter le cornet de glace (pyramide inversée) : suite lente, fragile, difficile à diagnostiquer.

Vérifie ta compréhension

  1. Quelle différence entre un test unitaire et un test d'intégration ?
  2. Pourquoi la pyramide recommande-t-elle peu de tests E2E ?
  3. Qu'est-ce que l'anti-pattern du cornet de glace ?

Exercices

Exercice 1Échauffement

Classe ces tests par niveau (unitaire, intégration, E2E) : (a) « formaterDate renvoie le bon format », (b) « un visiteur s'inscrit puis se connecte via le site », (c) « le dépôt enregistre bien dans la base de test ».

Voir une solution

(a) unitaire (une fonction pure isolée) ; (b) E2E (parcours utilisateur complet à travers le site) ; (c) intégration (le code testé avec une vraie base).

Exercice 2Application

Une équipe a 5 tests unitaires et 60 tests E2E très lents. Quel problème, et que conseilles-tu ?

Voir une solution

C'est un cornet de glace : trop de tests E2E, presque pas d'unitaires. La suite est lente (on hésite à la lancer), fragile, et un échec n'indique pas où est le bug. Conseil : inverser la proportion — écrire beaucoup de tests unitaires sur la logique métier (rapides, précis), garder seulement une poignée d'E2E sur les parcours critiques (inscription, paiement), et déplacer le reste vers des tests d'intégration ou unitaires.

Exercice 3Défi

Pour une fonctionnalité « virement bancaire », propose un test à chaque niveau (unitaire, intégration, E2E).

Voir une solution

Chaque niveau couvre un risque différent : la logique (unitaire), la persistance atomique (intégration), le parcours réel (E2E). On en met beaucoup au niveau unitaire et un seul au niveau E2E.
