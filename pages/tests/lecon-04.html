Module 2 · Bien tester — Leçon 04

Le développement piloté par les tests (TDD)

~36 min Intermédiaire Leçon 03 requise

À la fin de cette leçon, tu sauras

  • expliquer le principe du TDD ;
  • dérouler le cycle rouge-vert-refactor ;
  • écrire le code minimal pour faire passer un test ;
  • juger quand le TDD aide… et quand il gêne.
Sommaire de la leçon

Jusqu'ici, on écrivait les tests après le code. Le développement piloté par les tests (Test-Driven Development, TDD) inverse l'ordre : on écrit le test d'abord, puis le code pour le satisfaire. Cette inversion, déroutante au début, a un effet profond : elle te fait concevoir ton code depuis son usage, et garantit qu'il est testé dès la première ligne.

Le cycle rouge-vert-refactor

Le TDD est une boucle de trois étapes, répétée pour chaque petit incrément de fonctionnalité :

  • Rouge : écris un test pour un comportement qui n'existe pas encore. Lance-le : il échoue (le code n'existe pas). C'est normal, et important : ça prouve que le test peut échouer.
  • Vert : écris le minimum de code pour faire passer le test. Pas plus. Le test passe : tu es au vert.
  • Refactor : maintenant que c'est vert, améliore la structure du code (et des tests) sans changer le comportement. Les tests te protègent pendant cette amélioration.

Chaque tour est court (souvent quelques minutes) et porte sur un petit comportement. On avance par minuscules pas vérifiés, plutôt que d'écrire beaucoup de code puis d'espérer qu'il marche.

Un exemple complet

Construisons une fonction estPair(n) en TDD. Rouge d'abord : le test avant le code.

Sur un exemple aussi simple, le bénéfice paraît mince. Il devient évident sur du code complexe : en avançant test par test, on ne se retrouve jamais avec une montagne de code non vérifié, et chaque cas limite est capturé au moment où on y pense.

Le code minimal, vraiment minimal

L'étape « vert » demande une discipline contre-intuitive : écrire juste assez pour passer le test, même si ça semble « trop simple ». Cette retenue évite d'écrire du code spéculatif (pour des cas qu'aucun test ne demande) qui pourrait être faux et non couvert.

Le principe est « YAGNI » (You Aren't Gonna Need It) : tu n'en auras pas besoin. On ajoute la complexité quand un test la réclame, pas avant. Le code reste ainsi entièrement justifié par des comportements vérifiés.

Quand le TDD aide (et quand il gêne)

Le TDD brille quand les règles sont claires et exprimables en tests : logique métier, algorithmes, transformations de données, correction de bugs (on écrit d'abord un test qui reproduit le bug). Il pousse à un code mieux découpé, car un code difficile à tester est souvent un code mal conçu — le test révèle le problème tôt.

Il aide moins quand on explore (prototype jetable, recherche d'une approche) ou quand le résultat est surtout visuel/subjectif (mise en page). Le TDD n'est pas une religion : c'est un outil puissant à sortir quand il convient. Même sans le pratiquer strictement, penser au test pendant qu'on code change déjà la conception en mieux.

Le test qui reproduit un bug

Un usage du TDD utile à tous, même sans le pratiquer au quotidien : face à un bug, écris d'abord un test qui le reproduit (il échoue, rouge), puis corrige le code jusqu'à ce qu'il passe (vert). Bénéfice double : tu confirmes que tu as bien compris et corrigé le bug, et le test reste pour empêcher qu'il réapparaisse (une régression). C'est l'un des réflexes les plus rentables du métier.

Cas réel — le test qui fige une correction

La pratique a été formalisée par Kent Beck dans Test-Driven Development: By Example (2002), au cœur de l'Extreme Programming. Son usage le plus répandu aujourd'hui, même dans des équipes qui ne font pas de TDD « pur », est la correction de bug guidée par un test : sur des projets comme le noyau Linux, les navigateurs ou les grandes bases de code, un correctif est presque toujours accompagné d'un test qui reproduit le bug (rouge), puis passe une fois le code corrigé (vert). Ce test reste ensuite dans la suite pour toujours : si un remaniement futur réintroduit le défaut, il redevient rouge immédiatement. C'est ainsi qu'un bug corrigé une fois ne revient presque jamais.

Antisèche

Glossaire

TDD (développement piloté par les tests)
Méthode où l'on écrit le test avant le code, par petits incréments vérifiés.
Rouge
Première étape : écrire un test qui échoue, prouvant qu'il vérifie un comportement encore absent.
Vert
Deuxième étape : écrire le minimum de code pour faire passer le test.
Refactor
Troisième étape : améliorer la structure du code sans changer son comportement, tests au vert.
Code minimal
Juste assez de code pour satisfaire le test courant, sans complexité spéculative.
YAGNI
« You Aren't Gonna Need It » : n'ajouter une fonctionnalité que lorsqu'un test la réclame.
Test de régression
Test qui reproduit un ancien bug pour empêcher qu'il ne réapparaisse.
Refactoring
Transformation du code interne à comportement constant, sécurisée par les tests.

Récap et vérification

  • Le TDD écrit le test avant le code : on conçoit depuis l'usage et on est testé dès le départ.
  • Cycle rouge (test qui échoue) → vert (code minimal) → refactor (améliorer, tests au vert).
  • Écrire le code minimal (principe YAGNI) : pas de complexité non réclamée par un test.
  • Le TDD aide sur la logique claire ; pour un bug, écrire d'abord un test qui le reproduit.

Vérifie ta compréhension

  1. Quelles sont les trois étapes du cycle TDD ?
  2. Pourquoi écrire d'abord un test qui échoue ?
  3. Que signifie écrire le « code minimal » à l'étape verte ?

Exercices

Exercice 1Échauffement

Dans quel ordre fais-tu ces trois actions en TDD : (a) refactorer, (b) écrire le code minimal, (c) écrire un test qui échoue ?

Voir une solution

Ordre : (c) écrire un test qui échoue (rouge), puis (b) écrire le code minimal qui le fait passer (vert), puis (a) refactorer en gardant les tests au vert. Puis on recommence pour le comportement suivant.

Exercice 2Application

Déroule un cycle TDD pour une fonction tripler(n) : écris le test (rouge), puis le code minimal (vert).

Voir une solution
Exercice 3Défi

Un bug est signalé : moyenne([]) plante au lieu de renvoyer 0. Décris la démarche TDD pour le corriger durablement.

Voir une solution

1) Rouge : écrire un test qui reproduit le bug : test("la moyenne d'une liste vide est 0", () => affirmerEgal(moyenne([]), 0)); — il échoue (le code plante). 2) Vert : corriger moyenne pour gérer le cas vide (par ex. if (liste.length === 0) return 0;) jusqu'à ce que le test passe. 3) Refactor si nécessaire, tests au vert. Le test reste dans la suite : si quelqu'un réintroduit le bug plus tard, il échouera aussitôt (anti-régression).
