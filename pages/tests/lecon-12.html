Module 5 · Tester au-delà du fonctionnel — Leçon 12

Les tests de contrat entre services

~40 min Avancé Prérequis : leçons 05, 09

À la fin de cette leçon, tu sauras

  • Nommer le risque du couplage entre deux services et son coût en E2E ;
  • Écrire un contrat piloté par le consommateur (consumer-driven) ;
  • Faire vérifier ce contrat par le producteur, chacun de son côté ;
  • Situer le test de contrat face au schéma et à l'E2E.
Sommaire de la leçon

À la leçon 9, on a vu que tester deux services ensemble (bout en bout) coûte cher : lent, fragile, difficile à monter. Pourtant, dès qu'une application se découpe en plusieurs services, une question devient vitale : quand le service B change son API, comment savoir avant la mise en production qu'il vient de casser le service A qui l'appelle ? Le test de contrat répond à ça sans jamais déployer les deux ensemble.

Le problème : le couplage entre services

Un consommateur (une appli web, un service A) appelle un producteur (une API, un service B). Chacun a sa suite de tests, tous verts. Un jour, l'équipe du producteur renomme un champ prix en montant : ses tests à lui restent verts, ceux du consommateur aussi (il utilise un faux serveur figé). Et pourtant, en production, le consommateur reçoit undefined et plante. Personne ne l'a vu venir : c'est le couplage caché.

Le contrat : les attentes du consommateur

L'idée fondatrice s'appelle consumer-driven contract : c'est le consommateur qui décrit ce dont il a besoin, interaction par interaction (« si j'appelle GET /produits/1, j'attends un objet avec un id et un montant »). Un outil comme Pact intercepte ces attentes pendant les tests du consommateur et en génère un fichier de contrat.

Le contrat, un fichier partagé

Le contrat généré est un simple fichier JSON : une liste d'interactions, chacune avec la requête attendue et la réponse promise. Ce fichier est l'artefact partagé entre les deux équipes.

Astuce — le broker, place d'échange des contrats

Plutôt que de s'envoyer ce fichier par courriel, les équipes le publient sur un broker (un dépôt central de contrats, comme le Pact Broker). Le consommateur y publie ses contrats ; le producteur les récupère pour se vérifier. Le broker sait aussi quelles versions sont compatibles entre elles : il peut répondre à « puis-je déployer ce producteur en production sans casser aucun consommateur ? ».

La vérification côté producteur

La seconde moitié — la plus importante — se joue chez le producteur. Il récupère le contrat et rejoue chaque interaction contre sa vraie API : pour chaque requête décrite, répond-il bien ce que le contrat promet ? Si un champ a disparu ou changé de type, la vérification échoue et le build du producteur passe au rouge.

Contrat, schéma ou E2E : lequel, quand ?

Un schéma (OpenAPI, JSON Schema) décrit la forme possible de l'API, mais pas ce que chaque consommateur utilise vraiment. Un test E2E (leçon 9) est réaliste mais lent et exige tout l'environnement. Le test de contrat se place entre les deux : rapide comme un test unitaire, mais ciblé sur les interactions réellement employées entre deux services. Les trois se complètent ; ils ne s'excluent pas.

Cas réel

Cas réel — le champ renommé un vendredi soir

Une équipe « paiement » renomme amount en amount_cents pour lever une ambiguïté de devise. Tous leurs tests passent ; ils déploient. Le week-end, l'appli mobile — un consommateur maintenu par une autre équipe — affiche des prix à zéro : elle lisait amount, désormais absent. Après l'incident, ils adoptent le contract testing : l'appli mobile publie un contrat exigeant amount. La fois suivante où quelqu'un veut renommer le champ, la vérification du producteur casse en intégration continue, avec un message clair : « le consommateur appli-mobile attend amount ». Le renommage se fait alors proprement, en versionnant le changement des deux côtés. Le couplage n'a pas disparu — il est devenu visible.

Pièges fréquents

Piège fréquent — croire que le contrat teste le producteur

Un contrat ne dit pas si le producteur est correct dans l'absolu : il dit seulement s'il respecte les attentes d'un consommateur donné. Un champ que personne ne consomme n'est pas dans le contrat, donc pas protégé. Le contract testing complète les tests du producteur, il ne les remplace pas.

Piège fréquent — vérifier le contrat d'un seul côté

Générer le contrat côté consommateur ne sert à rien si le producteur ne le rejoue jamais contre sa vraie API. C'est la vérification côté producteur qui attrape les ruptures. Sans elle, tu as un joli fichier JSON… et toujours la même surprise en production.

Pour aller plus loin

Pour aller plus loin

Le même principe s'applique aux messages asynchrones (files, événements) : le contrat décrit alors la forme du message publié, pas une paire requête/réponse. Côté outillage, le broker propose le fameux can-i-deploy qui bloque un déploiement risqué. Et pour les API publiques à mille consommateurs inconnus, on revient au schéma versionné + une politique de compatibilité : le contrat brille surtout entre services d'une même organisation.

Antisèche

Glossaire

Test de contrat
Test qui vérifie que deux services se comprennent, en confrontant chacun à un contrat partagé plutôt qu'en les déployant ensemble.
Consommateur
Service qui appelle une API ; dans l'approche consumer-driven, il décrit les interactions dont il a besoin.
Producteur
Service qui expose l'API ; il doit prouver qu'il respecte le contrat en le rejouant contre sa vraie implémentation.
Contrat
Ensemble d'interactions (requête attendue → réponse promise) servant de référence commune, souvent un fichier JSON.
Consumer-driven
Démarche où le contrat naît des attentes réelles du consommateur, pas d'une spécification descendante.
Vérification (producteur)
Étape où le producteur rejoue chaque interaction du contrat contre son API et échoue s'il ne la respecte plus.
Broker
Dépôt central où les contrats sont publiés, versionnés et partagés entre équipes (ex. Pact Broker).

Récap et vérification

  • Dès qu'une appli se découpe en services, un changement d'API peut casser un appelant sans faire rougir aucun test : c'est le couplage caché.
  • Le contrat capture les interactions attendues ; en consumer-driven, c'est le consommateur qui le définit.
  • La vérification côté producteur rejoue le contrat contre la vraie API : c'est elle qui attrape les ruptures.
  • Le broker partage les contrats et sait quelles versions sont compatibles.
  • Le test de contrat se place entre le schéma et l'E2E : rapide, mais ciblé sur les échanges réels.

Vérifie ta compréhension

  1. Pourquoi les tests unitaires de chaque service ne détectent-ils pas un couplage rompu ?
  2. Dans l'approche consumer-driven, qui écrit le contrat ?
  3. Quelle étape attrape réellement une rupture de contrat ?

Exercices

Exercice 1Échauffement

Une équipe dit : « On a des tests de contrat, donc plus besoin de tester notre API. » Où est l'erreur ?

Voir une solution

Un test de contrat vérifie seulement que le producteur respecte les attentes des consommateurs connus. Il ne juge ni la logique interne de l'API, ni les champs que personne ne consomme, ni les cas d'erreur non décrits. Il complète les tests unitaires et d'intégration du producteur (leçons 2, 5, 9) : il ne les remplace pas.

Exercice 2Application

Un consommateur a besoin, pour GET /clients/7, d'un objet contenant id et email. Décris en une phrase l'interaction que son contrat doit capturer, puis ce que le producteur devra prouver.

Voir une solution

Interaction : « quand j'envoie GET /clients/7, j'attends un statut 200 avec un corps possédant les champs id et email ». Vérification producteur : rejouer cette requête contre l'API réelle et confirmer que la réponse a bien le statut 200 et les deux champs, aux bons types. Si l'API renvoie courriel au lieu d'email, la vérification échoue et le build casse.
