Module 1 · Les bases du test — Leçon 02

Anatomie d'un bon test

~35 min Débutant Leçon 01 requise

À la fin de cette leçon, tu sauras

  • structurer un test en Arrange-Act-Assert ;
  • écrire des assertions claires ;
  • garantir l'indépendance des tests ;
  • nommer et cibler un test sur un seul comportement.
Sommaire de la leçon

Un test mal écrit est pire qu'aucun test : il donne une fausse confiance, casse sans raison, ou devient illisible. À l'inverse, un bon test est court, clair, et dit immédiatement ce qui ne va pas quand il échoue. Cette leçon donne les caractéristiques universelles d'un bon test — valables quel que soit le langage ou le framework.

La structure Arrange-Act-Assert

Presque tous les bons tests suivent le même squelette en trois temps, le motif AAA :

  • Arrange (préparer) : mettre en place le contexte — créer les objets, préparer les données.
  • Act (agir) : exécuter l'action qu'on veut tester, en une opération.
  • Assert (vérifier) : affirmer le résultat attendu.

Cette séparation rend le test lisible d'un coup d'œil : on voit le contexte, l'action, l'attendu. Garde l'Act réduit à une seule action : si tu testes plusieurs actions à la suite, c'est souvent le signe qu'il faudrait plusieurs tests.

Des assertions claires

L'assertion est le cœur du test : elle compare un résultat obtenu à un résultat attendu. Une bonne assertion est précise et, en cas d'échec, produit un message utile.

Chaque langage offre une famille d'assertions (égalité, vérité, contenu d'une collection, exception levée…). Choisis la plus spécifique : elle exprime mieux l'intention et donne un meilleur message d'échec. Un bon message d'échec te dit quoi a cassé sans relire le test.

Erreur fréquente

L'assertion « fourre-tout » affirmerVrai(resultat === attendu) gaspille l'information : en cas d'échec, la plupart des frameworks ne peuvent afficher que « faux », sans dire quelle valeur a été obtenue (pytest fait exception : il détaille un simple assert). Préfère en général l'assertion spécifique (affirmerEgal, affirmerContient, affirmerLeve…) : elle connaît l'attendu et l'obtenu, donc produit un message qui te dit tout de suite ce qui cloche.

L'indépendance des tests

Règle d'or : chaque test doit pouvoir s'exécuter seul et dans n'importe quel ordre, sans dépendre d'un autre. Un test qui suppose qu'un autre s'est exécuté avant est fragile : il casse dès qu'on réorganise ou qu'on lance un seul test.

La plupart des frameworks fournissent un crochet « avant chaque test » (beforeEach, @BeforeEach, setUp…) qui recrée un contexte propre. Évite tout état partagé mutable entre tests : c'est la première cause des tests « qui marchent ensemble mais pas seuls ».

Un test, un comportement

Un bon test vérifie une seule chose. S'il échoue, on sait exactement laquelle, sans deviner. Un test qui affirme dix choses différentes s'arrête à la première qui échoue et masque les suivantes ; pire, son nom ne peut plus décrire une règle claire.

Le nom du test est essentiel : c'est une phrase qui décrit la règle vérifiée. Un bon nom permet de comprendre l'échec rien qu'en lisant le rapport, sans ouvrir le code. « retirer plus que le stock lève une erreur » en dit plus que « test3 ».

Les qualités F.I.R.S.T.

On résume souvent les bons tests par l'acronyme FIRST : Fast (rapides, pour qu'on les lance souvent), Independent (indépendants), Repeatable (reproductibles — même résultat à chaque exécution), Self-validating (ils disent eux-mêmes s'ils passent, sans inspection manuelle), Timely (écrits au bon moment, idéalement avec le code). Un test qui s'écarte de FIRST est un test qu'on finira par ignorer.

Cas réel — les tests « flaky »

Chez Google, dont l'infrastructure exécute des millions de tests, les ingénieurs ont mesuré en 2016 qu'environ 1,5 % des exécutions de tests rendent un résultat flaky, et que près de 16 % des tests (plus d'un sur sept) sont instables à un degré ou à un autre : un tel test échoue parfois sans vraie régression (dépendance à l'horloge, au réseau, à l'ordre d'exécution ou à un autre test). Le vrai danger est humain : quand un rouge « peut être un faux », les équipes finissent par relancer à l'aveugle ou ignorer les échecs — et un vrai bug passe inaperçu. C'est tout le sens du R (Repeatable) et du I (Independent) de FIRST : un test doit rendre le même verdict à chaque exécution, sinon il ruine la confiance dans la suite entière.

Glossaire

AAA (Arrange-Act-Assert)
Structure en trois temps d'un test : préparer le contexte, exécuter l'action, affirmer le résultat.
Assertion
Vérification qui compare un résultat obtenu à un résultat attendu ; son échec fait échouer le test.
Crochet (beforeEach)
Fonction lancée automatiquement avant (ou après) chaque test pour préparer ou nettoyer le contexte.
Isolation / indépendance
Propriété d'un test exécutable seul et dans n'importe quel ordre, sans dépendre d'un autre.
État partagé mutable
Objet réutilisé entre plusieurs tests ; première cause des tests « qui marchent ensemble mais pas seuls ».
Test flaky
Test non déterministe qui passe ou échoue de façon aléatoire, sans vraie régression ; il détruit la confiance.
FIRST
Acronyme des qualités d'un bon test : Fast, Independent, Repeatable, Self-validating, Timely.
Nommage de test
Choix d'un nom-phrase décrivant la règle métier vérifiée, lisible directement dans le rapport d'échec.

Récap et vérification

  • Arrange-Act-Assert : préparer, agir (une seule action), vérifier.
  • Des assertions spécifiques donnent de meilleurs messages d'échec (attendu vs obtenu).
  • Indépendance : chaque test part d'un état neuf (crochet « avant chaque »), exécutable seul et dans tout ordre.
  • Un test = un comportement, avec un nom qui décrit la règle. Vise les qualités FIRST.

Vérifie ta compréhension

  1. Que désignent les trois temps du motif AAA ?
  2. Pourquoi l'indépendance des tests est-elle si importante ?
  3. Pourquoi viser « un test = un seul comportement » ?

Exercice 2Application

Ces deux tests partagent un objet : const c = new Compteur(); déclaré une fois en dehors. Pourquoi est-ce risqué, et comment corriger ?

Voir une solution

C'est un état partagé mutable : si le premier test incrémente c, le second ne part pas de zéro ; le résultat dépend alors de l'ordre d'exécution. Correction : recréer le compteur avant chaque test.

Exercice 3Défi

Un test s'appelle "test du panier" et contient cinq assertions sur des comportements différents. Explique les deux problèmes et propose une meilleure organisation.

Voir une solution

Problèmes : 1) si une assertion échoue, les suivantes ne s'exécutent pas ; on ne voit qu'un seul problème à la fois et on ignore les autres. 2) le nom "test du panier" ne décrit aucune règle : en cas d'échec, le rapport n'aide pas. Meilleure organisation : découper en plusieurs tests, un par comportement, chacun avec un nom-phrase : "un panier vide a un total de 0", "ajouter un article augmente le total", "appliquer un code promo réduit le total", etc. Chaque échec devient alors précis et auto-explicatif.
