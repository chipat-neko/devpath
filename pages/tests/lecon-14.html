Module 6 · Projet — Leçon 14

Projet — reprendre du code legacy sous filet de tests

~46 min Avancé Prérequis : l'ensemble du cours

À la fin de cette leçon, tu sauras

  • Reconnaître ce qu'est un code legacy et pourquoi il fait peur ;
  • Poser un filet avec des tests de caractérisation avant de toucher au code ;
  • Ouvrir des coutures (seams) pour rendre testable un code qui ne l'était pas ;
  • Assembler une suite de tests complète mobilisant tout le cours.
Sommaire de la leçon

Tu sais désormais écrire de bons tests, doser la pyramide, pratiquer le TDD, générer des cas et éprouver tes tests. Reste l'épreuve qui attend vraiment tout développeur : hériter d'un code sans tests, en production, que personne n'ose toucher. Cette dernière leçon rassemble tout le cours autour de ce défi, puis te fait assembler une suite de tests complète en fil rouge.

Qu'est-ce que le code legacy

La définition la plus utile vient de Michael Feathers : le code legacy, c'est du code sans tests. Peu importe son âge ou son élégance : sans filet, chaque modification est un pari. Le paradoxe est cruel : pour le modifier sans risque il faudrait des tests, mais pour le tester il faut souvent… le modifier. On dénoue ce nœud pas à pas.

Le dilemme du legacy

« Je ne peux pas refactorer sans tests, et je ne peux pas tester sans refactorer. » La sortie : poser d'abord un filet grossier autour du comportement existant (caractérisation), puis n'ouvrir que de petites coutures sûres pour rendre le code injectable.

Les tests de caractérisation

Un test de caractérisation ne vérifie pas ce que le code devrait faire, mais fige ce qu'il fait aujourd'hui — bugs compris. Son but n'est pas de juger : c'est un filet de sécurité. Tant qu'il reste vert, tu sais que tu n'as rien changé au comportement observable. S'il rougit après un refactor, tu as modifié quelque chose — volontairement ou non.

Ouvrir des coutures

Souvent le code résiste au test parce qu'il crée lui-même ses dépendances : il lit l'heure réelle, ouvre une vraie connexion, appelle un service distant. Une couture (seam, terme de Feathers) est un point où l'on peut changer le comportement sans éditer le code sur place. La couture la plus simple : transformer une dépendance dure en paramètre injectable — exactement la technique d'injection vue à la leçon 8.

Astuce — le golden master pour les grosses sorties

Quand la sortie est volumineuse (un rapport, un HTML, un gros JSON), n'écris pas l'assertion à la main : capture une fois la sortie de référence (le golden master) dans un fichier, puis compare chaque exécution à ce fichier. C'est l'approval testing : idéal pour figer d'un coup le comportement d'un code legacy tentaculaire.

Cas réel — la refonte qui n'osait pas commencer

Une équipe hérite d'un moteur de calcul de primes de 3 000 lignes, sans un seul test, écrit par quelqu'un parti depuis longtemps. Personne n'ose y toucher : un changement, et la paie de milliers de salariés dérape. Plutôt qu'une réécriture risquée, ils posent un golden master : ils rejouent 500 dossiers réels à travers le moteur et figent chaque sortie. Le filet devient vert. Ensuite seulement, ils refactorent par petits pas — extraire une fonction, injecter une dépendance — en surveillant le master à chaque étape. Six semaines plus tard, le moteur est modulaire et couvert ; aucune prime n'a bougé d'un centime. C'est la démarche exacte du livre de Feathers, Working Effectively with Legacy Code.

Pour aller plus loin — la méthode Mikado

Pour des refontes plus profondes, la méthode Mikado systématise l'approche par petits pas : tente le changement voulu ; note ce qui casse ; annule tout ; traite d'abord les prérequis ; recommence. On dessine ainsi un « graphe Mikado » des dépendances à régler dans l'ordre, sans jamais laisser le code cassé plus de quelques minutes. Le principe reste celui de cette leçon : on ne progresse que depuis un état vert.

Antisèche

Glossaire

Code legacy
Code dépourvu de tests : modifiable seulement au prix d'un risque, quelle que soit sa qualité apparente.
Test de caractérisation
Test qui capture le comportement existant tel quel (sans le juger) pour servir de filet avant refactor.
Couture (seam)
Endroit du code où l'on peut altérer le comportement sans en modifier le corps, pour le rendre testable.
Injection de dépendance
Fournir une dépendance de l'extérieur (paramètre) au lieu de la créer en dur : la couture la plus courante.
Golden master
Sortie de référence figée une fois, à laquelle on compare les exécutions suivantes (approval testing).
Refactor
Modifier la structure interne sans changer le comportement observable ; sûr uniquement sous filet de tests.
Approval testing
Technique du golden master : on valide une fois une sortie de référence, puis chaque exécution y est comparée automatiquement.
Méthode Mikado
Démarche de refonte par petits pas : on tente un changement, on note ce qui casse, on annule, puis on traite les prérequis d'abord — toujours depuis un état vert.

Récap et vérification

  • Le code legacy, c'est du code sans tests : on le rend sûr avant de le modifier.
  • Les tests de caractérisation figent le comportement actuel comme filet, sans juger de sa justesse.
  • Les coutures (souvent une simple injection) rendent testable un code qui créait ses dépendances.
  • Le golden master fige d'un coup une grosse sortie ; puis on refactore petit, toujours dans le vert.

Vérifie ta compréhension

  1. Selon Feathers, qu'est-ce qui définit un code legacy ?
  2. Que capture un test de caractérisation, et pourquoi ?
  3. Comment une couture par injection rend-elle estOuvert() testable ?

Exercices

Exercice 1Échauffement

On te confie une fonction score(joueur) de 200 lignes, sans aucun test, que tu dois modifier demain. Quelle est la toute première chose à écrire, et pourquoi ?

Voir une solution

Un test de caractérisation : appelle score avec une entrée réaliste, lis la sortie réelle et fige-la dans une assertion. Tu ne cherches pas encore à corriger quoi que ce soit — tu poses un filet. Ainsi, quand tu modifieras le code demain, tout écart de comportement fera rougir ce test immédiatement.

Exercice 2Application

Cette fonction est intestable car elle lit l'heure réelle. Ouvre une couture par injection sans changer son comportement par défaut : function salutation() { const h = new Date().getHours(); return h < 18 ? "Bonjour" : "Bonsoir"; }

Voir une solution
Exercice 3Défi

Un module génère un rapport HTML de 300 lignes. Comment le mettre sous filet sans écrire des dizaines d'assertions ? Nomme la technique et décris les deux étapes.

Voir une solution

Un golden master (approval testing). 1) On exécute le module une fois, on relit sa sortie et on l'enregistre telle quelle dans un fichier de référence (le master), après l'avoir inspectée. 2) Le test rejoue le module et compare la sortie au fichier : toute différence le fait rougir. On fige ainsi 300 lignes d'un coup, sans rédiger les assertions à la main ; c'est parfait pour un legacy volumineux avant refactor.

Mini-projet fil rouge — une suite de tests complète

Pour clore le cours, écrivons une suite de tests pour une fonction total — le genre de filet qu'on poserait justement autour d'un code existant. Elle réunit l'organisation describe/test, le beforeEach, le motif AAA (Arrange-Act-Assert), les assertions et la couverture des cas limites — un condensé de tout ce cours.

Ce que tu vas construire

Trois tests pour total(panier) : un panier vide, un cas nominal, et un cas limite (quantité nulle), avec un état réinitialisé avant chacun.

Étapes

Le bloc describe

Regroupe les tests de total dans un describe.

Réinitialiser

Avec beforeEach, remets le panier à vide avant chaque test (isolation).

Le cas de base

Un panier vide doit valoir 0 : expect(total(panier)).toBe(0).

Le cas nominal

Ajoute deux articles et vérifie la somme (motif Arrange-Act-Assert).

Le cas limite

Une quantité nulle ne doit rien ajouter.

ProjetFil rouge

Assemble les étapes en une suite complète. Essaie d'abord par toi-même, puis compare avec la solution de référence.
