Module 4 · Tests avancés — Leçon 09

Tests d'intégration et de bout en bout (E2E)

~42 min Intermédiaire Prérequis : leçon 03

À la fin de cette leçon, tu sauras

  • Distinguer test unitaire, d'intégration et de bout en bout ;
  • Écrire un test d'intégration avec un environnement jetable (base neuve) ;
  • Piloter l'app comme un utilisateur avec un test E2E et un Page Object ;
  • Décider où tester quoi — et où s'arrêter.
Sommaire de la leçon

Jusqu'ici, tu testais des unités isolées : une fonction, une classe, en remplaçant leurs voisines par des doublures (leçon 5). Mais un logiciel réel, c'est des unités qui collaborent, une base de données, un navigateur. Deux niveaux se posent au-dessus de l'unitaire : le test d'intégration (plusieurs pièces réelles ensemble) et le test de bout en bout (le système entier, vu comme un utilisateur). On revient à la pyramide de la leçon 3 pour les situer.

Rappel : la pyramide des tests

Chaque niveau a un compromis : plus on monte, plus le test couvre de choses d'un coup… mais plus il est lent, coûteux et fragile. D'où la forme de pyramide : beaucoup d'unitaires à la base, quelques tests d'intégration, très peu d'E2E au sommet.

Les tests d'intégration

Un test d'intégration fait travailler plusieurs modules réels ensemble — typiquement ton code de persistance avec une vraie base, au lieu d'un mock. On vérifie ce que les tests unitaires ne peuvent pas voir : la requête SQL est-elle correcte ? le schéma correspond-il ? la donnée relue est-elle bien celle écrite ?

Environnements jetables

La clé d'un test d'intégration fiable : une base neuve et jetable à chaque fois. En pratique, une base en mémoire (SQLite :memory:) ou un conteneur éphémère lancé pour la durée des tests (les testcontainers démarrent un vrai PostgreSQL dans Docker, puis le détruisent). Chaque test part d'un état connu : pas d'ordre imposé, pas de données qui traînent.

Les tests de bout en bout (E2E)

Un test E2E (end-to-end) pilote l'application entière, exactement comme un utilisateur : il ouvre une page dans un vrai navigateur, remplit des champs, clique, et vérifie ce qui s'affiche. Des outils comme Playwright ou Cypress automatisent ce navigateur.

Le Page Object : des E2E lisibles

Les tests E2E vieillissent mal : le moindre changement d'interface casse des dizaines de sélecteurs éparpillés. Le patron Page Object range les détails d'une page (ses sélecteurs, ses actions) dans un objet. Les tests parlent alors le langage du métier (« inscrire »), pas celui du HTML (« remplir #email »).

Astuce — vise des sélecteurs stables

Cible les éléments par leur rôle ou un attribut dédié (data-testid="valider") plutôt que par une classe CSS ou une position. Le style change souvent ; l'intention, rarement. Des sélecteurs stables sont le premier remède contre les E2E instables. Les blocs de cette page ciblent des identifiants (#email) pour rester courts ; dans un vrai projet, préfère page.getByRole("button", { name: "Créer mon compte" }).

Où s'arrêter

Un E2E couvre énormément mais coûte cher : lent (secondes par test), fragile, difficile à diagnostiquer quand il rougit. La sagesse : réserver l'E2E aux parcours critiques (connexion, paiement, inscription) et pousser tout le reste vers l'intégration et l'unitaire. Chaque règle métier fine se teste bien plus vite en unitaire.

Cas réel — la suite E2E de 40 minutes

Une équipe avait tout misé sur l'E2E : presque aucun test unitaire, des centaines de scénarios navigateur. La suite mettait 40 minutes, cassait au moindre ajustement de CSS, et « re-lancez, ça passera » était devenu un rituel. C'est la pyramide inversée (un « cornet de glace »). En redescendant la logique vers des unitaires rapides et en ne gardant qu'une poignée d'E2E sur les parcours clés, la suite est repassée à quelques minutes — et surtout, on lui a refait confiance.

Pièges fréquents

Piège fréquent

Vouloir tester chaque règle de gestion via l'interface. C'est lent et indirect : si le calcul d'une remise a dix cas, teste-les en unitaire (leçon 7) et garde un seul E2E qui prouve que « payer marche ».

Piège fréquent

Oublier de remettre l'environnement à zéro entre les tests d'intégration : un test crée un utilisateur, le suivant compte « 2 utilisateurs » et échoue au hasard selon l'ordre. Base neuve ou nettoyage systématique : l'isolation d'abord.

Pour aller plus loin

Pour aller plus loin

Entre l'intégration et l'E2E existe le test d'API : on appelle les routes HTTP du serveur sans navigateur — bien plus rapide, idéal pour le back. Entre services, les tests de contrat (Pact) vérifient que producteur et consommateur s'accordent sur le format des échanges, sans tout déployer. Et pour l'UI, la régression visuelle compare des captures d'écran pour repérer un décalage de pixels.

Antisèche

Glossaire

Test d'intégration
Test faisant collaborer plusieurs modules réels (souvent code + vraie base), sans doublure entre eux.
Test de bout en bout (E2E)
Test du système entier via l'interface réelle, rejouant un parcours utilisateur complet.
Environnement jetable
Base ou service neuf et éphémère (mémoire, conteneur) recréé pour garantir l'isolation.
Testcontainer
Vrai service (PostgreSQL, Redis…) démarré dans un conteneur le temps des tests, puis détruit.
Page Object
Objet encapsulant les sélecteurs et actions d'une page pour des tests E2E lisibles et robustes.
Sélecteur
Expression qui cible un élément de la page ; à préférer stable (rôle, data-testid).
Parcours critique
Scénario métier essentiel (connexion, paiement) justifiant un test E2E malgré son coût.
Pyramide inversée
Anti-patron où l'E2E domine : suite lente et fragile (« cornet de glace »).

Récap et vérification

  • Au-dessus de l'unitaire : l'intégration (plusieurs modules réels) et l'E2E (système entier, vu de l'utilisateur).
  • La pyramide guide l'effort : beaucoup d'unitaires, quelques intégrations, très peu d'E2E.
  • Un test d'intégration demande un environnement remis à zéro entre les tests (base neuve ou nettoyage systématique) pour rester isolé et reproductible.
  • Un test E2E pilote un vrai navigateur ; le Page Object et des sélecteurs stables le gardent lisible et robuste.
  • Réserve l'E2E aux parcours critiques ; teste la logique fine en unitaire. Fuis la pyramide inversée.

Vérifie ta compréhension

  1. Qu'est-ce qu'un test d'intégration vérifie qu'un test unitaire ne peut pas voir ?
  2. Dans un test E2E, pourquoi cibler un élément par son rôle ou un data-testid plutôt que par sa classe CSS ?
  3. À quoi sert un Page Object dans une suite E2E ?
