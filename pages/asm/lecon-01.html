Module 1 · La machine — Leçon 01

Découvrir l'assembleur

~45 min Avancé Prérequis : connaître un langage comme le C

À la fin de cette leçon, tu sauras

  • expliquer pourquoi apprendre l'assembleur (performance, débogage, sécurité, compilateurs) ;
  • décrire le modèle machine : CPU, mémoire, registres et le cycle fetch-decode-execute ;
  • passer du C au code machine et lire la sortie de gcc -S ;
  • écrire, assembler et lier un premier programme NASM qui renvoie un code de sortie via syscall.
Sommaire de la leçon

Tu écris du code depuis un moment. Tu déclares une variable, tu appelles une fonction, tu lances ton programme : ça marche. Mais entre ta ligne de C (ou de Python, ou de Rust) et l'instant où le processeur fait vraiment quelque chose, il y a une couche que tu n'as jamais vue. Cette couche, c'est l'assembleur : la traduction la plus proche du langage que la machine exécute physiquement.

Dans cette leçon, on ne va pas écrire une application. On va ouvrir le capot. Tu vas comprendre ce qu'est un processeur, à quoi servent les registres, comment ton code source devient des octets exécutables, et tu vas écrire ton tout premier programme en assembleur x86-64. Spoiler : il ne fera qu'une chose, renvoyer un nombre au système, mais tu comprendras chaque octet de ce qu'il fait.

Pourquoi apprendre l'assembleur en 2026

Personne n'écrit d'application web en assembleur. Alors pourquoi s'embêter ? Parce que l'assembleur n'est pas un langage de production, c'est une lunette. Une fois que tu sais lire l'assembleur, tu vois ce qui était invisible :

  • La performance. Pourquoi telle boucle est lente ? Pourquoi le compilateur a-t-il déroulé celle-ci mais pas celle-là ? L'assembleur te montre le travail réel du CPU.
  • Le débogage. Quand un programme plante avec un SIGSEGV et que tu n'as pas les sources, le désassemblage est tout ce qui te reste.
  • La sécurité. Les dépassements de tampon, le reverse engineering, l'analyse de malwares : tout se joue au niveau des instructions.
  • Les compilateurs. Comprendre ce que gcc -O2 produit, c'est cesser de croire à la magie et commencer à écrire du code que le compilateur aime.

Le fil conducteur de ce cours : comprendre la machine démystifie tous les langages. Une variable, un appel de fonction, un pointeur : ce sont des abstractions. En dessous, il n'y a que des octets en mémoire et des instructions qui les déplacent.

Cas réel

En janvier 2018, les failles Spectre et Meltdown ont fait trembler toute l'industrie : elles n'existaient qu'au niveau des instructions, dans la manière dont le CPU exécute spéculativement le code par avance. Impossible de les comprendre — et de les corriger — sans lire l'assembleur. Même chose côté défensif : quand un analyste décortique un logiciel malveillant livré sans code source, ou quand un ingénieur cherche pourquoi une boucle critique est deux fois trop lente, l'écran affiche… de l'assembleur désassemblé. C'est la langue commune à qui veut voir ce que la machine fait vraiment.

Le modèle : CPU, mémoire, registres

Réduis un ordinateur à l'essentiel et il reste trois choses.

Le CPU (le processeur) est l'ouvrier : il exécute des instructions, une par une, à grande vitesse. Il ne sait faire que des choses très simples : additionner deux nombres, comparer, déplacer une valeur, sauter à un autre endroit du programme.

La mémoire (la RAM) est un immense tableau d'octets numérotés. Chaque case a une adresse (un numéro). C'est là que vivent ton programme et tes données. Mais le CPU ne calcule pas directement dans la mémoire : elle est trop loin, trop lente.

Les registres sont les quelques cases ultra-rapides situées dans le CPU lui-même. En x86-64, il y en a 16 d'usage général, chacun de 64 bits (8 octets). Leurs noms : rax, rbx, rcx, rdx, rsi, rdi, rbp, rsp, et r8 à r15. Pour calculer, le CPU charge des valeurs depuis la mémoire vers les registres, travaille dans les registres, puis range le résultat.

Note

Chaque registre 64 bits a des « vues » plus petites : rax est le registre complet (64 bits), eax en est la moitié basse (32 bits), ax les 16 bits du bas, al les 8 bits du bas. Ce sont les mêmes bits physiques, regardés à différentes tailles.

Du code source au binaire

Quand tu écris du C, ton fichier .c n'est qu'un texte. Pour qu'il s'exécute, il traverse une chaîne :

  • Compilation : le compilateur traduit ton C en assembleur (du texte, encore, mais bien plus proche de la machine).
  • Assemblage : l'assembleur traduit cet assembleur en code machine (des octets bruts), rangé dans un fichier objet.
  • Édition de liens : le linker assemble les morceaux et produit l'exécutable final.

Tu viens de voir, en clair, la correspondance entre une ligne de C et une instruction machine.

Note

Pourquoi eax et pas rax alors que la fonction renvoie un int ? En x86-64, écrire dans un registre 32 bits comme eax remet automatiquement à zéro les 32 bits du haut de rax. Le compilateur en profite : une écriture 32 bits est plus compacte et nettoie le registre complet d'un coup.

x86-64, et deux syntaxes

x86-64 (aussi appelée AMD64 ou x64) est l'architecture de la quasi-totalité des PC et serveurs. « x86 » renvoie à la lignée historique des processeurs Intel ; « -64 » indique les registres et adresses de 64 bits.

Ton premier programme : sortir avec un code

Place nette : on écrit du vrai assembleur, à la main. Notre programme va simplement dire au système d'exploitation « termine-moi avec le code 42 ». Pour parler au noyau Linux, on utilise un appel système (syscall) : une demande de service au système. Celui qui nous intéresse s'appelle exit, et porte le numéro 60.

Décortiquons, ligne par ligne :

  • section .text déclare la zone où vit le code machine exécutable.
  • global _start expose le symbole _start. C'est le point d'entrée par défaut : l'endroit où l'exécution commence (l'équivalent du main, mais sans la bibliothèque C autour).
  • mov rax, 60 met le numéro du syscall dans rax. Le noyau lit toujours rax pour savoir quel service tu demandes.
  • mov rdi, 42 met le premier argument dans rdi. La convention Linux x86-64 passe les arguments d'un syscall dans rdi, rsi, rdx, r10, r8, r9, dans cet ordre.
  • syscall est l'instruction qui passe la main au noyau. Il lit rax et rdi, exécute exit(42), et le processus s'arrête.

L'équivalent C de ces six lignes tient en une : exit(42);. La différence, c'est qu'ici tu vois exactement comment l'argument et le numéro de service arrivent au noyau.

Astuce

Un code de sortie est un entier de 0 à 255. Par convention, 0 signifie « tout s'est bien passé » et toute autre valeur signale une erreur. C'est ce que teste un if program; then … dans un script shell.

Assembler, lier, exécuter

Trois commandes. On transforme le texte en fichier objet avec nasm, on lie avec ld, puis on lance.

-f elf64 indique à nasm de produire un objet au format ELF 64 bits, le format des exécutables Linux.

Le programme n'affiche rien : il ne fait que se terminer. La preuve qu'il a marché est dans echo $?, qui révèle le code de sortie : 42. La variable $? du shell contient toujours le code de retour de la dernière commande : tu viens de le fixer toi-même, registre par registre.

Le cycle fetch-decode-execute

Comment le CPU exécute-t-il tes instructions ? Il répète sans fin une boucle à trois temps :

  • Fetch (chercher) : le CPU lit en mémoire l'instruction pointée par un registre spécial, le compteur de programme (rip en x86-64).
  • Decode (décoder) : il interprète les octets pour savoir quelle opération faire et sur quels registres.
  • Execute (exécuter) : il réalise l'opération, met à jour les registres, et avance rip vers l'instruction suivante.

Quand tu as écrit mov rax, 60 puis mov rdi, 42, le CPU a fait deux tours de cette boucle : fetch mov rax, 60, decode, execute (rax vaut 60), rip avance ; puis fetch mov rdi, 42, et ainsi de suite. Des milliards de fois par seconde. Tout ce que fait un ordinateur, depuis le rendu de cette page jusqu'au calcul scientifique, n'est qu'une très longue suite de ces trois temps.

Pièges fréquents

Piège fréquent

Oublier global _start (ou mal l'orthographier) donne un avertissement du linker : ld: warning: cannot find entry symbol _start. Sans point d'entrée déclaré, ld ne sait pas où commencer.

Piège fréquent

Confondre le numéro du syscall (dans rax) et ses arguments (dans rdi, rsi…). Mettre 42 dans rax et 60 dans rdi appellerait un tout autre service que exit.

Piège fréquent

Un code de sortie est tronqué à 8 bits : il « boucle » modulo 256. exit(256) donne un $? de 0, et exit(257) donne 1. Reste entre 0 et 255 pour éviter les surprises.

Piège fréquent

Ne pas terminer par un exit et laisser l'exécution « tomber » après ta dernière instruction : le CPU continue sur les octets suivants (souvent des zéros) et le programme plante avec SIGSEGV. Contrairement à une fonction C, _start n'a pas d'appelant vers qui revenir : c'est à toi d'appeler exit.

Glossaire

Registre
Case mémoire ultra-rapide située dans le CPU ; x86-64 en compte 16 d'usage général, de 64 bits (rax, rdi…).
x86-64
Architecture 64 bits (aussi appelée AMD64 ou x64) de la quasi-totalité des PC et serveurs ; définit les registres, les instructions et leur encodage.
Code machine
Les octets bruts que le CPU exécute ; l'assembleur en est la représentation textuelle lisible, une instruction par ligne.
Appel système (syscall)
Demande de service au noyau (sortir, lire, écrire…) ; numéro dans rax, arguments dans rdi, rsi…, déclenché par syscall.
Syntaxe Intel
Convention d'écriture instruction destination, source (celle de NASM et de ce cours), là où la syntaxe AT&T inverse l'ordre et préfixe registres et immédiats.
Point d'entrée
Adresse où l'exécution commence ; par défaut le symbole _start, rendu visible au linker par global _start.
Fetch-decode-execute
Le cycle sans fin du CPU : chercher l'instruction pointée par rip, la décoder, l'exécuter, puis avancer.
Code de sortie
Entier de 0 à 255 qu'un programme rend en se terminant ; 0 = succès, lisible dans le shell via $?.

Récap et vérification

  • L'assembleur n'est pas un langage d'application : c'est une lunette sur la performance, le débogage, la sécurité et les compilateurs.
  • Le CPU travaille dans des registres rapides (16 registres 64 bits en x86-64) ; la mémoire stocke code et données ; le CPU fait la navette entre les deux.
  • Ton code traverse : compilation (texte assembleur) → assemblage (code machine) → édition de liens (exécutable).
  • On écrit en syntaxe Intel/NASM : instruction destination, source.
  • Un syscall Linux x86-64 : numéro dans rax, arguments dans rdi, rsi, rdx… ; on déclenche avec syscall.
  • Le CPU répète sans fin fetch → decode → execute.

Vérifie ta compréhension

  1. Pourquoi le CPU charge-t-il les données dans des registres au lieu de calculer directement en mémoire ?
  2. Dans mov rax, 60, lequel est la destination et lequel est la source ? Que vaut rax ensuite ?
  3. Pour un syscall, où place-t-on son numéro, et où place-t-on son premier argument ?
  4. Que ferait echo $? juste après un programme qui se termine par exit(256), et pourquoi ?
