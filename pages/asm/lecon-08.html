Module 3 · Données et lecture — Leçon 08

Lire le code du compilateur

~55 min Avancé Prérequis : leçon 7

À la fin de cette leçon, tu sauras

  • lire l'assembleur généré par gcc avec -S et le désassembler avec objdump -d ;
  • comparer -O0 et -O2 pour voir l'optimisation à l'œuvre (registres, code mort, boucle éliminée) ;
  • reconnaître les patterns classiques : if, boucle, appel de fonction et switch (table de saut) ;
  • utiliser cette lecture pour déboguer un crash et comprendre la performance d'un programme.
Sommaire de la leçon

Tu sais maintenant écrire de l'assembleur à la main. Mais la compétence la plus rentable au quotidien, ce n'est pas d'en écrire : c'est d'en lire. Chaque fois que tu compiles un programme C, Rust, Go ou C++, le compilateur produit de l'assembleur x86-64 — exactement le langage que tu connais désormais. Apprendre à le relire, c'est ouvrir le capot de toutes ces machines de haut niveau d'un seul coup.

Dans cette leçon, on prend de petites fonctions C, on demande au compilateur son assembleur, et on apprend à le déchiffrer. On verra surtout pourquoi le code change radicalement entre -O0 et -O2, et comment repérer du premier coup d'œil un if, une boucle, un appel ou un switch.

Demander son assembleur au compilateur

Deux façons d'obtenir l'assembleur d'un programme C. La première, avant assemblage, avec l'option -S de gcc : tu récupères un fichier .s en syntaxe AT&T (l'inverse de NASM : la destination est à droite, les registres sont préfixés par %). La seconde, après compilation, en désassemblant le binaire avec objdump.

Avec objdump -M intel -d tu obtiens la syntaxe Intel, beaucoup plus proche de NASM que tu connais.

Astuce

Le site Compiler Explorer (godbolt.org) fait tout ça dans le navigateur : tu écris du C à gauche, l'assembleur s'affiche à droite, et un code couleur relie chaque ligne C à ses instructions. C'est l'outil idéal pour expérimenter sans rien installer.

Lire une fonction simple en Intel

Reprenons carre en désassemblage Intel, non optimisé. Voici ce que produit le compilateur (commenté à droite).

Tu reconnais tout : l'argument x arrive dans edi (convention System V, premier argument entier), le résultat repart dans eax, et push rbp / mov rbp, rsp / pop rbp forment le prologue et l'épilogue classiques. Le compilateur range bêtement x sur la pile puis le relit : c'est ce que donne -O0, fidèle au code source ligne par ligne, sans aucune ruse.

-O0 contre -O2 : voir l'optimisation

Recompile la même fonction avec -O2. Le compilateur sait que la pile est inutile ici : x est déjà dans un registre, autant l'utiliser directement.

Trois instructions au lieu de sept. Plus aucun accès mémoire, plus de cadre de pile. C'est la première leçon de l'optimisation : garder les valeurs dans les registres et ne toucher la pile que si c'est indispensable.

Regardons un cas plus parlant avec une boucle.

En -O0, gcc traduit fidèlement : un compteur i sur la pile, un test, un saut, un incrément — la boucle telle que tu l'as écrite. En -O2, surprise : la boucle disparaît. Le compilateur reconnaît que tu additionnes 0 + 1 + … + (n-1) et remplace toute la boucle par la formule fermée n*(n-1)/2.

C'est l'élimination de boucle par reconnaissance d'une réduction : une boucle entière devient quatre instructions sans le moindre saut. Tu ne pourrais pas deviner ce code en lisant seulement le C — c'est précisément pour ça qu'on lit l'assembleur.

Note

Les autres optimisations courantes : le déroulage de boucle (traiter plusieurs itérations par tour pour réduire les sauts), l'inlining (recopier le corps d'une petite fonction au lieu de l'appeler), et l'élimination de code mort (supprimer tout calcul dont le résultat n'est jamais lu).

Reconnaître un if

Un if se lit toujours de la même façon : une comparaison (cmp) ou un test (test) suivi d'un saut conditionnel (je, jle, jns…) qui enjambe le bloc à ne pas exécuter. Le saut utilise la condition inverse de celle du C.

Le C dit « si x < 0 alors nie » ; l'assembleur dit « si x >= 0, saute par-dessus la négation ». C'est la même logique vue à l'envers. Dès que tu vois cmp ou test suivi d'un jquelque-chose, tu tiens un branchement.

Reconnaître un switch : la table de saut

Un switch sur des valeurs contiguës ne se compile pas en cascade de if : le compilateur construit une table de saut. Il range en mémoire les adresses des différents cas, puis saute directement à la bonne grâce à un indexage — un seul saut indirect au lieu de n comparaisons.

La signature d'un switch optimisé, c'est ce jmp vers [base + registre*8] : un saut calculé à partir d'une table d'adresses. En coût, c'est O(1) quel que soit le nombre de cas, alors qu'une chaîne de if serait en O(n).

Note

Dans un vrai binaire indépendant de la position (PIE, le défaut aujourd'hui), la table contient souvent des décalages relatifs plutôt que des adresses absolues, et gcc les additionne à une base avant de sauter. Le principe reste identique : un saut indexé par la valeur du switch.

Pourquoi le compilateur gagne (presque toujours)

En lisant ce code, une évidence s'impose : à -O2, le compilateur produit souvent mieux que ce que tu écrirais à la main. Il connaît par cœur les coûts de chaque instruction, alloue les registres de façon optimale sur des fonctions entières, déroule et vectorise sans se fatiguer, et n'oublie jamais un cas. Tu peux le battre sur un noyau critique très précis, mais sur du code ordinaire, lui faire confiance est le bon réflexe. Écris du C clair, laisse-le optimiser.

Là où ta lecture devient précieuse, c'est pour le débogage et la performance. Un crash dans du code optimisé donne une pile parfois incohérente et des variables « optimisées away » dans le débogueur : savoir lire l'asm permet de retrouver ce qui s'est réellement passé. Et quand un profil pointe une fonction chaude, regarder son assembleur révèle si le compilateur a bien vectorisé, ou s'il rate une optimisation parce que ton code l'en empêche (un pointeur potentiellement aliasé, par exemple).

Cas réel

En 2009, une faille du noyau Linux (CVE-2009-1897) est née d'une optimisation invisible. Le pilote tun déréférençait un pointeur, puis vérifiait if (!tun) juste après. Comme déréférencer un pointeur nul est un « comportement indéfini », gcc -O2 en a déduit que tun ne pouvait pas être nul et a purement supprimé le test de sécurité. Le trou était invisible dans le C : il n'apparaissait que dans l'assembleur produit, où le branchement avait disparu. C'est en relisant cet asm qu'on a compris le problème (corrigé en réordonnant le code et en compilant avec -fno-delete-null-pointer-checks). La morale de cette leçon en un cas : ce que le compilateur exécute n'est pas toujours ce que le source laisse croire.

Pièges fréquents

Piège fréquent

Lire l'assembleur de -O0 en pensant qu'il représente « le vrai code ». Le -O0 est volontairement naïf et lent (tout passe par la pile) : il sert à déboguer, pas à juger la performance. Pour comprendre ce qui tournera réellement en production, lis toujours la version optimisée (-O2 ou -O3).

Autre confusion classique : oublier que objdump -d sort de l'AT&T par défaut. Si l'ordre des opérandes te semble inversé et que les registres ont des %, ajoute -M intel. Enfin, attention aux suffixes de saut non signés : ja/jb (above/below) servent aux comparaisons non signées, jg/jl (greater/less) aux signées. Le compilateur choisit selon le type C, et confondre les deux change le sens du test.

Pour aller plus loin

Pour aller plus loin

Ouvre Compiler Explorer et compare un même code C entre gcc et clang, ou entre -O2 et -O3. Active l'option qui relie les lignes C à l'asm par couleur, et observe comment une simple boucle de copie devient une instruction SIMD (registres xmm/ymm) quand tu montes en niveau d'optimisation.

Antisèche

Glossaire

-O0 / -O2
Niveaux d'optimisation de gcc/clang : -O0 traduit le source fidèlement (lent, lisible, pour déboguer) ; -O2 optimise agressivement (registres, code mort supprimé, boucles fondues).
objdump
Désassembleur : reconstitue les instructions à partir des octets d'un binaire. objdump -d -M intel donne la syntaxe Intel.
Syntaxe AT&T vs Intel
Deux notations pour le même code : AT&T (défaut de gcc/objdump, destination à droite, registres en %) et Intel (destination à gauche, proche de NASM).
Table de saut (jump table)
Tableau d'adresses indexé par la valeur d'un switch ; un seul saut indirect jmp [base + i*8] remplace une cascade de comparaisons — coût O(1).
cmov
Déplacement conditionnel (conditional move) : choisit une valeur selon les drapeaux sans saut, évitant une rupture de flux (utile pour min/max).
Inlining
Optimisation qui recopie le corps d'une petite fonction à l'endroit de l'appel, supprimant le coût du call/ret.
Élimination de code mort
Suppression de tout calcul dont le résultat n'est jamais lu ; peut faire disparaître une boucle entière.
Auto-vectorisation
Transformation automatique d'une boucle en instructions SIMD (xmm/ymm) qui traitent plusieurs données à la fois.

Récap et vérification

  • gcc -S donne l'asm (AT&T), objdump -d désassemble un binaire ; ajoute -M intel pour la syntaxe que tu connais.
  • -O0 suit le source ligne par ligne (tout sur la pile) ; -O2 garde les valeurs en registres, élimine le code mort et peut faire disparaître des boucles entières.
  • Un if = cmp/test + saut conditionnel avec la condition inverse ; une boucle = un saut arrière ; un appel = call ; un switch dense = un jmp indirect via une table de saut.
  • Le compilateur optimise presque toujours mieux que toi ; lire son asm sert surtout à déboguer le code optimisé et à comprendre la performance.
