Module 4 · Assembleur en pratique — Leçon 13

Ce que fait l'optimiseur

~55 min Avancé Prérequis : leçons 8 & 11

À la fin de cette leçon, tu sauras

  • situer les niveaux -O0 → -O3, -Os et leurs compromis ;
  • reconnaître les transformations clés : inlining, déroulage, code mort ;
  • lire un saut remplacé par un cmov sans branche ;
  • repérer une boucle auto-vectorisée (SIMD) et ses pièges.
Sommaire de la leçon

À la leçon 8, tu as lu l'assembleur produit à -O0 : fidèle au source, mais naïf — chaque variable relue depuis la pile, chaque petit calcul refait. Passe à -O2 et le même code C devient méconnaissable : des fonctions entières disparaissent, des boucles se déplient, des if perdent leur saut. L'optimiseur n'est pas magique : il applique une poignée de transformations dont chacune a un but clair. Les reconnaître, c'est comprendre pourquoi ton code va (ou ne va pas) plus vite — et pourquoi déboguer du code optimisé est si déroutant.

Les niveaux d'optimisation

Le drapeau -O règle l'agressivité du compilateur. Plus il monte, plus il transforme — au prix de la lisibilité de l'asm, du temps de compilation, et parfois de la taille du code.

Trois transformations qui sautent aux yeux

Compile int carre(int x){ return x*x; } int f(){ return carre(3)+carre(4); } à -O2 et regarde : la fonction f se réduit à mov eax, 25 ; ret. Trois optimisations se sont enchaînées.

  • Inlining : le corps de carre est recopié à l'appel, supprimant le call/ret et son coût.
  • Propagation de constantes (constant folding) : 3*3 et 4*4 sont calculés à la compilation → 9 et 16.
  • Élimination du code mort : carre n'étant plus appelée, sa définition entière disparaît du binaire.

Astuce : comparer avant/après sans quitter le terminal

gcc -O0 -S -o - f.c puis gcc -O2 -S -o - f.c affichent l'asm sur la sortie standard : on compare d'un coup d'œil. Ajoute -fverbose-asm pour annoter chaque instruction du nom de variable correspondant. En ligne, Compiler Explorer (godbolt.org) colore la correspondance source ↔ asm en direct.

Sans branche : le cmov

Un if (a > b) m = a; else m = b; se traduit naïvement par un saut conditionnel. Mais un saut mal prédit par le processeur coûte cher (le pipeline se vide). Quand les deux branches sont courtes, l'optimiseur préfère calculer les deux et choisir avec un cmov (conditional move) : aucune branche, donc aucune mauvaise prédiction possible.

Déroulage et vectorisation

Sur une boucle qui somme un tableau, deux optimisations se combinent à -O3. Le déroulage (loop unrolling) traite plusieurs éléments par tour pour amortir le coût du test de boucle. L'auto-vectorisation va plus loin : elle utilise les registres SIMD (leçon 9) pour additionner 4, 8 ou 16 entiers en une seule instruction.

L'optimiseur exploite l'absence d'UB — attention

Une transformation n'est valide que si le comportement défini du programme est préservé. L'optimiseur suppose donc qu'il n'y a aucun comportement indéfini (UB). Écris if (x + 1 < x) pour détecter un débordement signé : comme le débordement int est un UB, le compilateur en déduit que le test est toujours faux et le supprime. Ton garde-fou disparaît. La leçon : à -O2/-O3, un UB latent qui « marchait » à -O0 peut casser silencieusement. Compile avec -fsanitize=undefined pour les débusquer.

Cas réel

Une boucle de traitement d'image (somme de luminance sur 4 millions de pixels) tournait en 12 ms à -O0. Le profil (leçon 11 + perf) montrait 90 % du temps dans la boucle. Simple passage à -O2 : 3 ms (les variables restent en registres, plus d'allers-retours pile). Puis -O3 -march=native : 0,8 ms — le compilateur a vectorisé avec AVX2, traitant 8 pixels par instruction. Gain total ×15 sans toucher une ligne de C, juste en laissant l'optimiseur faire son travail sur un code écrit « proprement » (accès contigus, pas de dépendance entre tours). La morale : écrire un code vectorisable (boucles simples, mémoire contiguë) vaut souvent mieux que d'écrire du SIMD à la main.

Pour aller plus loin

Pour aller plus loin

Au-delà des drapeaux : la LTO (Link-Time Optimization, -flto) permet d'inliner entre fichiers objets. La PGO (Profile-Guided Optimization) compile une première fois, mesure l'exécution réelle, puis recompile en optimisant les chemins chauds. Côté source, __builtin_expect (ou [[likely]]) guide la prédiction, restrict promet l'absence d'aliasing (débloque la vectorisation), et -march=native autorise les instructions de ton processeur (AVX-512…) — au prix de la portabilité du binaire.

Antisèche

Glossaire

Optimiseur
Partie du compilateur qui transforme le code pour le rendre plus rapide (ou plus petit) sans changer son comportement défini. Réglé par -O0…-O3, -Os.
Inlining
Recopie du corps d'une fonction à son point d'appel ; supprime le coût du call/ret et ouvre d'autres optimisations.
Propagation de constantes
Évaluation à la compilation des expressions dont les opérandes sont connues (constant folding) : 3*3 devient 9.
Élimination du code mort
Suppression du code qui ne peut jamais s'exécuter ou dont le résultat n'est jamais utilisé.
Déroulage de boucle
Traiter plusieurs itérations par tour pour amortir le coût du test et exposer du parallélisme.
cmov (sans branche)
Instruction de copie conditionnelle : transfère une valeur selon les drapeaux, sans saut — insensible à la prédiction de branchement.
Auto-vectorisation
Transformation d'une boucle scalaire en instructions SIMD qui traitent plusieurs éléments à la fois (-O3).
Comportement indéfini (UB)
Construction sans sémantique garantie (débordement signé, déréférencement nul…) ; l'optimiseur suppose son absence, ce qui peut supprimer un test qui en dépend.

Récap et vérification

  • -O0 pour déboguer, -O2 en production, -O3 quand la vectorisation aide (à mesurer), -Os pour la taille.
  • Trois transformations phares : inlining, propagation de constantes, élimination du code mort — souvent enchaînées.
  • Le cmov remplace un saut court par une copie conditionnelle ; l'auto-vectorisation utilise le SIMD (paddd, xmm).
  • L'optimiseur suppose l'absence d'UB : un débordement signé peut faire disparaître ton garde-fou. Teste avec -fsanitize=undefined.

Vérifie ta compréhension

  1. Pourquoi f() peut-elle se réduire à mov eax, 25 ; ret ?
  2. Quel avantage a un cmov sur un saut conditionnel ?
  3. Pourquoi un test de débordement signé peut-il disparaître à -O2 ?

Exercices

Exercice 1Échauffement

Tu veux comparer l'asm de calc.c à -O0 puis à -O2, sur la sortie standard, avec les variables annotées. Donne les deux commandes.

Voir une solution

-S s'arrête à l'assembleur, -o - écrit sur la sortie standard (pas de fichier), -fverbose-asm ajoute en commentaire le nom de variable de chaque opérande. Idéal pour voir, ligne à ligne, ce que l'optimiseur a changé.

Exercice 2Application

Dans l'asm d'une boucle à -O3, tu vois paddd xmm0, xmm1 et une avance de rax par pas de 16. Qu'a fait l'optimiseur, et pourquoi le pas est-il de 16 ?

Voir une solution

Il a auto-vectorisé la boucle : paddd (packed add doubleword) additionne 4 entiers de 32 bits en parallèle dans un registre SIMD 128 bits (xmm). Le pas de 16 octets = 4 éléments × 4 octets : la boucle traite 4 valeurs par tour au lieu d'une, avec un seul test de fin de boucle pour 4 éléments (déroulage implicite). C'est pourquoi -O3 -march=native peut donner des gains spectaculaires sur les boucles régulières et contiguës.

Exercice 3Défi

Un code de vérification int somme(int a, int b){ int s = a + b; if (s < a) return -1; /* débordement */ return s; } « marche » à -O0 mais le test semble ignoré à -O2. Explique et corrige.

Voir une solution

Le débordement d'un int signé est un comportement indéfini. L'optimiseur a le droit de supposer qu'il ne se produit jamais : il en déduit que a + b >= a toujours (pour b >= 0), donc que s < a est toujours faux, et supprime le test. Le garde-fou disparaît.

Corrections possibles : (a) tester avant l'opération avec des limites (if (a > INT_MAX - b) …), ou (b) utiliser les intrinsèques sûrs : __builtin_add_overflow(a, b, &s) renvoie vrai en cas de débordement, sans UB. On peut aussi passer en non signé (débordement défini, modulo 2ⁿ) selon le besoin. Toujours : gcc -fsanitize=undefined révèle ce genre de piège à l'exécution.
