Module 04 · Vue confirmé — Leçon 07

Composition API & composables

~30 min Intermédiaire Cours Vue (L01-06) conseillé

À la fin de cette leçon, tu sauras

  • utiliser la Composition API avec <script setup> ;
  • organiser la logique réactive (ref, computed) ;
  • extraire un composable réutilisable ;
  • éviter les pièges de réactivité.
Sommaire de la leçon

Tu connais les bases de Vue (réactivité, composants). Ce module « confirmé » va plus loin : la Composition API est la façon moderne d'organiser la logique d'un composant Vue 3, et elle débloque une fonctionnalité puissante : les composables, qui rendent la logique réutilisable.

Options API vs Composition API

L'Options API (historique) organise un composant par options : data, methods, computed… La logique d'une même fonctionnalité se retrouve éparpillée entre ces options. La Composition API regroupe au contraire la logique par fonctionnalité, dans une seule fonction de configuration : plus lisible quand un composant grossit, et surtout réutilisable.

script setup : la forme recommandée

<script setup> est le sucre syntaxique recommandé en Vue 3 : tout ce que tu déclares au niveau racine (variables, fonctions, imports) est automatiquement disponible dans le template. Moins de cérémonie, plus de clarté.

Rappel de réactivité (côté Composition)

  • ref : crée une référence réactive ; on lit/écrit sa valeur via .value dans le script (mais pas dans le template, où elle est dépaquetée).
  • computed : une valeur dérivée, recalculée automatiquement quand ses dépendances changent.
  • watch : réagir à un changement pour exécuter un effet (appel réseau, log…).

Le composable : extraire de la logique réutilisable

Un composable est simplement une fonction qui utilise la Composition API pour encapsuler une logique réactive, et qu'on peut réutiliser dans plusieurs composants. Par convention, son nom commence par use.

N'importe quel composant peut maintenant réutiliser cette logique en une ligne. C'est l'équivalent moderne et propre de la réutilisation, sans les limites des anciens « mixins ».

Un composable plus réaliste

Les composables brillent pour encapsuler une logique avec effets : récupérer des données, écouter un événement, gérer une minuterie… On expose un état (données, chargement, erreur) que le composant n'a plus qu'à afficher.

Le composant reste alors minimal : il appelle useFetch(...) et affiche enChargement, erreur ou donnees. La logique est testable isolément : c'est tout l'intérêt.

Cas réel — VueUse, des composables partagés entre projets

VueUse est une collection très populaire de plus de 200 composables prêts à l'emploi, utilisée dans d'innombrables applications Vue. Plutôt que de réécrire à chaque projet useFetch, useLocalStorage (persister un état), useDark (thème sombre), useMouse ou useDebouncedRef, on les importe. C'est la démonstration à grande échelle de l'intérêt du motif : une logique réactive bien encapsulée se partage entre composants et entre projets, exactement comme une fonction utilitaire.

Les pièges de réactivité

Ne pas perdre la réactivité

Oublier .value dans le script, ou déstructurer un objet reactive (qui « casse » le lien réactif) : deux erreurs classiques. Avec ref et des composables qui retournent les refs (sans les déstructurer en valeurs brutes), on garde la réactivité intacte.

Pour aller plus loin

Un composable peut aussi utiliser les hooks de cycle de vie (onMounted, onUnmounted) pour installer puis nettoyer ses effets — écouteur d'événement, minuterie, abonnement — afin d'éviter les fuites. watchEffect exécute immédiatement une fonction et re-suit tout seul les dépendances réactives qu'elle lit. La bibliothèque VueUse est une excellente source d'exemples bien écrits pour s'en inspirer.

Glossaire

Composition API
Manière d'organiser un composant Vue 3 en regroupant la logique par fonctionnalité, dans <script setup>.
script setup
Sucre syntaxique recommandé : variables, fonctions et imports du niveau racine sont automatiquement disponibles dans le template.
ref
Conteneur réactif pour une valeur ; on lit/écrit son contenu via .value dans le script (dépaqueté dans le template).
computed
Valeur dérivée d'un état réactif, recalculée automatiquement quand ses dépendances changent.
watch
Observe une source réactive pour exécuter un effet (appel réseau, journalisation…) à chaque changement.
Composable
Fonction (par convention useX) qui encapsule une logique réactive réutilisable et testable.
reactive
Rend un objet réactif via un proxy ; déstructurer ses propriétés casse la réactivité (utiliser toRefs).
Mixin
Ancien mécanisme de réutilisation de logique, remplacé par les composables, plus clairs et sans collisions de noms.

Récap et vérification

  • La Composition API (<script setup>) regroupe la logique par fonctionnalité.
  • ref (état, .value), computed (dérivé), watch (effet).
  • Un composable = une fonction useX qui encapsule une logique réactive réutilisable et testable.
  • Attention aux pièges de réactivité (.value oublié, déstructuration d'un reactive).

Exercices

Exercice 1Échauffement

Pourquoi nomme-t-on un composable useTimer plutôt que timer ? Qu'apporte cette convention ?

Voir une solution

La convention de préfixer par use (useTimer, useFetch, useCompteur…) est un signal partagé par la communauté Vue. Elle indique d'un coup d'œil que la fonction est un composable : c'est-à-dire qu'elle utilise la Composition API (elle peut contenir de l'état réactif ref, des computed, des watch, des hooks de cycle de vie) et qu'elle est destinée à être appelée dans le setup d'un composant. Avantages : 1) la lisibilité — quiconque lit le code reconnaît immédiatement la nature et l'usage de la fonction ; 2) la cohérence avec l'écosystème (les composables des bibliothèques suivent la même règle), ce qui facilite la collaboration ; 3) ça distingue les composables des fonctions utilitaires ordinaires (qui, elles, ne dépendent pas de la réactivité de Vue et peuvent être appelées n'importe où). Une fonction nommée simplement timer n'enverrait pas ce signal : on ne saurait pas qu'elle est « réactive » et liée au cycle de vie d'un composant. La convention use est donc une petite règle de nommage à fort rendement en clarté.

Exercice 2Application

Tu as la même logique de « suivi de la position de la souris » dupliquée dans trois composants. Comment la factoriser proprement avec la Composition API ?

Voir une solution

On extrait la logique dans un composable, par exemple useMouse(). Le composable contient l'état réactif (les coordonnées) et la logique d'écoute : il crée des ref x et y, ajoute un écouteur d'événement mousemove qui les met à jour, et — important — nettoie cet écouteur quand le composant est démonté (via le hook onUnmounted), pour éviter les fuites. Il retourne ensuite { x, y }. En pseudo-structure : « créer x et y en ref ; dans onMounted, attacher l'écouteur qui met à jour x/y ; dans onUnmounted, le retirer ; retourner { x, y } ». Chacun des trois composants n'a alors plus qu'à faire const { x, y } = useMouse() dans son <script setup> et à afficher les coordonnées. Bénéfices : la logique n'existe plus qu'à un seul endroit (fini la duplication et les corrections à reporter trois fois) ; elle est testable isolément ; chaque composable gère proprement son cycle de vie (mise en place + nettoyage), ce que des copies éparpillées risqueraient d'oublier ; et chaque composant qui l'utilise obtient sa propre instance d'état (les coordonnées ne sont pas partagées par accident entre composants, sauf si on le veut explicitement). C'est exactement le rôle des composables : transformer une logique répétée en une brique réutilisable, autonome et soignée.

Exercice 3Défi

Un développeur écrit const { compteur } = reactive({ compteur: 0 }) puis modifie compteur, mais le template ne se met pas à jour. Explique le problème et donne deux façons de le corriger.

Voir une solution

Le problème est un piège de réactivité classique lié à la déstructuration d'un objet reactive. Quand on fait reactive({ compteur: 0 }), Vue renvoie un proxy réactif : c'est l'accès à travers ce proxy (par ex. etat.compteur) qui est suivi. En déstructurant (const { compteur } = ...), on copie la valeur primitive 0 dans une variable locale compteur qui n'a plus aucun lien avec le proxy réactif. Modifier cette variable locale ne déclenche donc aucune mise à jour ; le template ne « voit » pas le changement. C'est une limite fondamentale : la réactivité de reactive ne survit pas à la déstructuration de ses propriétés primitives. Deux corrections : 1) Utiliser ref au lieu de reactive pour une valeur simple : const compteur = ref(0), puis modifier compteur.value++. Une ref est un conteneur réactif autonome ; on peut la passer et la retourner sans perdre la réactivité (c'est pourquoi les composables retournent des refs). 2) Ne pas déstructurer, ou utiliser toRefs : soit on garde l'objet et on accède via etat.compteur (le lien réactif est préservé), soit, si l'on veut déstructurer tout en gardant la réactivité, on enveloppe avec toRefs : const { compteur } = toRefs(etat). toRefs transforme chaque propriété en une ref liée à l'objet d'origine, de sorte que la déstructuration conserve le lien réactif (on accédera alors via compteur.value). Règle pratique à retenir : pour des valeurs simples ou que l'on doit retourner/passer, privilégier ref ; réserver reactive aux objets qu'on manipule sans les déstructurer ; et utiliser toRefs au moment de déstructurer un reactive. Ce piège est l'une des erreurs les plus fréquentes en Composition API, et le comprendre évite des heures de « pourquoi ça ne se met pas à jour ».
