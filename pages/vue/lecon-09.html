Module 04 · Vue confirmé — Leçon 09

État, performance & production

~37 min Intermédiaire Leçons 07-08 conseillées

À la fin de cette leçon, tu sauras

  • centraliser l'état avec Pinia ;
  • appliquer des optimisations de rendu et de chargement ;
  • produire un build de production (Vite) ;
  • situer le rendu côté serveur (SSR).
Sommaire de la leçon

Une application Vue qui grandit pose deux questions : où ranger l'état partagé par plusieurs composants, et comment rester rapide. Cette dernière leçon du module couvre la gestion d'état avec Pinia, quelques optimisations clés, et la mise en production.

Pinia : l'état centralisé

Quand un même état (l'utilisateur connecté, un panier, des filtres) est partagé par beaucoup de composants éloignés, le faire transiter par props ou provide/inject devient lourd. Pinia (la bibliothèque officielle) offre un magasin (store) centralisé : un endroit unique où vit l'état, avec des actions pour le modifier et des getters pour en dériver.

Quand sortir Pinia ?

Pas pour tout ! Pour de l'état local à un composant, un ref suffit. Pour des données transversales simples, provide/inject. Pinia s'impose quand l'état est partagé, modifié à plusieurs endroits et durable — alors sa structure (état/getters/actions) et ses outils de débogage deviennent précieux.

Optimiser le rendu

Vue est rapide par défaut, mais quelques réflexes aident sur les grosses interfaces :

  • Toujours une key stable dans v-for (un identifiant unique, pas l'index) : Vue suit ainsi correctement chaque élément lors des mises à jour.
  • Ne pas mettre v-if et v-for sur le même élément : en Vue 3, v-if est évalué avant v-for et ne voit donc pas la variable de boucle (c'était l'inverse en Vue 2) ; on filtre plutôt en amont (un computed).
  • v-once pour du contenu qui ne change jamais (rendu une seule fois), v-memo pour mémoriser des sous-arbres coûteux.
  • Éviter de recréer de gros objets à chaque rendu ; préférer des computed pour les valeurs dérivées.

Optimiser le chargement

Le plus gros levier de performance perçue est souvent de charger moins au démarrage. Deux techniques :

  • le lazy-loading des routes (avec Vue Router) : chaque page n'est téléchargée que lorsqu'on y va ;
  • les composants asynchrones (defineAsyncComponent, leçon 8) pour les morceaux lourds.

C'est exactement l'esprit du cours Performance web : découper et différer.

Cas réel — l'éditeur riche qu'on ne charge qu'au besoin

Imagine un tableau de bord dont une seule page contient un éditeur de texte riche (coloration, formatage) pesant à lui seul 300 Ko. Tout charger au démarrage ferait payer ce poids à tous les visiteurs, même ceux qui ne l'ouvrent jamais. En déclarant cette page en import dynamique, l'éditeur n'est téléchargé qu'au moment où l'utilisateur y accède : l'accueil s'affiche instantanément, et le gros morceau arrive seulement quand il sert. C'est le levier n°1 de performance perçue sur les applications réelles.

Le build de production (Vite)

En développement, on travaille avec un serveur instantané (Vite). Pour déployer, on génère un build de production optimisé : code minifié, découpé en morceaux (code splitting), arbre élagué (tree-shaking, on retire le code mort), prêt à servir comme fichiers statiques.

Tester sur le build, pas juste en dev

Le mode développement est plus permissif et plus lent que la production. On vérifie toujours le comportement et les performances sur le build de prod (preview) avant de déployer : certains soucis n'apparaissent que là.

Aperçu : le rendu côté serveur (SSR)

Par défaut, une application Vue est rendue dans le navigateur (le serveur n'envoie qu'une page presque vide + du JS). Pour un meilleur référencement et un premier affichage plus rapide, on peut faire du rendu côté serveur (SSR) : le serveur génère le HTML initial. Le framework Nuxt rend cela accessible. C'est un sujet à part entière ; retiens surtout pourquoi il existe (SEO, performance perçue), traité aussi en Performance & SEO.

Glossaire

Pinia
Bibliothèque officielle de gestion d'état : un store central réactif pour l'état partagé.
Store
Espace central regroupant un état, des getters (valeurs dérivées) et des actions (qui le modifient).
Getter
Valeur dérivée de l'état d'un store, recalculée automatiquement (équivalent d'un computed).
Action
Fonction d'un store qui modifie son état (ajouter, retirer, charger…).
key
Identifiant unique et stable donné à chaque élément d'un v-for pour que Vue suive correctement les éléments.
Lazy-loading
Charger une page ou un composant seulement au moment où il est nécessaire (import() dynamique).
Build de production
Version optimisée générée par Vite : code minifié, découpé (code splitting) et élagué (tree-shaking).
Tree-shaking
Élimination automatique du code jamais utilisé lors du build.
SSR
Rendu côté serveur : le serveur génère le HTML initial (meilleur SEO et premier affichage), facilité par Nuxt.

Récap et vérification

  • Pinia centralise l'état partagé (état / getters / actions) — quand l'état est partagé, modifié partout, durable.
  • Optimiser le rendu : key stable, pas de v-if+v-for mêlés, v-once/v-memo, computed.
  • Optimiser le chargement : lazy-loading des routes et composants asynchrones.
  • Build de prod (Vite) minifié/élagué ; SSR (Nuxt) pour SEO et premier affichage.

Exercices

Exercice 1Échauffement

Pour chaque cas, choisis « ref local », « provide/inject » ou « Pinia » : (a) l'ouverture d'un menu déroulant dans un composant ; (b) le thème clair/sombre lu un peu partout ; (c) le panier d'achat, modifié et lu depuis de nombreux écrans.

Voir une solution

(a) l'ouverture d'un menu déroulant → ref local : c'est un état purement interne au composant (ouvert/fermé), personne d'autre n'en a besoin ; un simple const ouvert = ref(false) suffit. (b) le thème clair/sombre lu un peu partout → provide/inject : c'est une donnée transversale et plutôt stable, « ambiante », dont beaucoup de composants ont besoin en lecture ; un ancêtre la fournit, les descendants l'injectent, sans prop drilling. (c) le panier d'achat → Pinia : c'est de l'état d'application partagé, modifié depuis de nombreux endroits (ajouter, retirer, vider) et lu ailleurs (badge du header, page panier, total) ; il mérite un store centralisé avec actions et getters, structuré et débogable. La règle : on monte en puissance selon le partage et la complexité — local→ref, transversal simple→provide/inject, partagé/modifié/durable→Pinia. On évite de sur-dimensionner (pas de Pinia pour un menu) comme de sous-dimensionner (pas de prop drilling pour un panier global).

Exercice 2Application

Une application Vue charge tout son code au démarrage et met plusieurs secondes à s'afficher. Quelles techniques de ce module appliques-tu pour accélérer le premier affichage ?

Voir une solution

Le problème est un bundle initial trop gros : l'utilisateur télécharge et exécute tout le code de l'application avant de voir quoi que ce soit. Les techniques : 1) Lazy-loading des routes — c'est le levier le plus efficace. Au lieu d'importer toutes les pages d'emblée, on les déclare avec un import dynamique (component: () => import('./pages/X.vue')) ; ainsi, seule la page d'accueil (et le code commun) est chargée au démarrage, et chaque autre page n'est téléchargée qu'au moment où l'utilisateur y navigue. Le bundle initial fond. 2) Composants asynchrones (defineAsyncComponent, leçon 8) — pour les morceaux lourds même au sein d'une page (un éditeur de texte riche, un gros graphique, une carte) qui ne sont pas visibles immédiatement : on les charge à la demande. 3) Vérifier le build de production — s'assurer qu'on teste bien le build optimisé (minifié, code-splitté, tree-shaké) et non le mode dev, plus lourd ; analyser la taille des morceaux pour repérer une dépendance énorme qu'on pourrait alléger ou charger paresseusement. 4) Optimisations de rendu en complément (key stables, éviter v-if+v-for, computed pour les dérivés) pour que, une fois le code arrivé, l'affichage soit fluide. 5) (Si le SEO ou le premier affichage est critique) envisager le SSR (Nuxt) : le serveur renvoie un HTML déjà rendu, l'utilisateur voit le contenu immédiatement pendant que le JS se charge. Démarche : d'abord mesurer (quel est le poids du bundle, quelle page/dépendance pèse le plus), puis appliquer le lazy-loading là où ça compte, et re-mesurer. Le principe directeur, commun avec la performance web : ne charger que le nécessaire, au bon moment. Découper et différer transforme « plusieurs secondes » en « affichage quasi immédiat » sans rien retirer aux fonctionnalités.

Exercice 3Défi

Synthèse du module « Vue confirmé » : un développeur connaît les bases de Vue mais écrit tout dans des composants énormes, sans réutilisation, avec de l'état dupliqué et un chargement lent. Quels outils des leçons 7-8-9 lui conseilles-tu, et pour quel problème chacun ?

Voir une solution

Chaque symptôme correspond à un outil vu dans le module : 1) « Composants énormes, logique mélangée » → la Composition API (leçon 7) : avec <script setup>, on regroupe la logique par fonctionnalité au lieu de l'éparpiller, ce qui rend un gros composant lisible et réorganisable. 2) « Pas de réutilisation, logique dupliquée » → les composables (leçon 7) : on extrait la logique réactive répétée (suivi de souris, fetch, minuterie…) dans des fonctions useX réutilisables et testables, factorisant le code partagé. 3) « Composants pas assez flexibles / props qui se multiplient » → les slots et scoped slots (leçon 8) : pour rendre les composants « contenants » génériques (le parent fournit le contenu) sans empiler les props. 4) « Une donnée passée à travers 5 niveaux de props » → provide/inject (leçon 8) pour les données transversales (thème, langue), éliminant le prop drilling. 5) « État dupliqué / désynchronisé entre écrans » → Pinia (leçon 9) : un store centralisé pour l'état partagé (panier, session), avec une seule source de vérité, des actions et des getters ; fini les copies incohérentes. 6) « Chargement lent au démarrage » → le lazy-loading des routes et les composants asynchrones (leçons 8-9) : ne charger chaque page/morceau lourd qu'à la demande, et soigner le build de production (leçon 9). 7) « Modale mal positionnée » (bonus, leçon 8) → Teleport. Le fil rouge du module : passer d'un Vue « qui marche » à un Vue structuré, réutilisable et performant. Aucun de ces outils n'est obligatoire pour de petits projets ; mais à mesure qu'une application grandit, ils répondent chacun à un problème concret d'organisation, de réutilisation, de partage d'état ou de performance. Le bon réflexe : reconnaître le symptôme, choisir l'outil adapté (sans sur-ingénierie), et garder le code au service de l'utilisateur — lisible pour l'équipe, rapide pour l'utilisateur final.
