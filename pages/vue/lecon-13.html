Module 5 · Construire une application — Leçon 13

Tester ses composants avec Vitest

~35 min Avancé Leçons 04 et 07 conseillées

À la fin de cette leçon, tu sauras

  • monter un composant dans un test avec mount ;
  • structurer un test selon le schéma Arrange / Act / Assert ;
  • simuler une interaction avec trigger et await ;
  • vérifier les props et les événements émis avec emitted.
Sommaire de la leçon

Un test automatisé, c'est un petit programme qui vérifie qu'un composant se comporte comme prévu. Il donne trois choses précieuses : la confiance de modifier sans tout casser (non-régression), une documentation vivante de ce que le composant est censé faire, et un filet qui rattrape les bugs avant l'utilisateur. Dans l'écosystème Vue, l'outil de référence est Vitest, épaulé par Vue Test Utils.

Vitest et Vue Test Utils

Vitest est le lanceur de tests : il exécute tes fichiers *.test.js, très rapidement, en partageant la configuration de Vite (aucun réglage à dupliquer). Vue Test Utils fournit la fonction mount, qui monte réellement un composant dans un DOM simulé et renvoie un wrapper pour l'inspecter et interagir avec lui. Le projet créé par npm create vue@latest propose de tout installer d'un coup.

Un premier test

Testons un composant Compteur qui incrémente un nombre au clic. Un test tient en trois temps que l'on retrouve partout : on prépare (Arrange), on agit (Act), on vérifie (Assert).

N'oublie pas le await devant trigger

Vue met à jour le DOM de façon asynchrone. Après un trigger, il faut await pour laisser le rendu se rafraîchir avant de vérifier ; sinon wrapper.text() renvoie encore l'ancienne valeur et le test échoue sans raison apparente. Règle simple : await devant chaque trigger.

Le wrapper et ses méthodes

mount renvoie un wrapper — une poignée sur le composant monté. Quelques méthodes couvrent l'essentiel des besoins.

Tester les props et les événements

Un composant se pilote par ses props (entrées) et communique par ses événements (sorties). On teste les deux : on passe des props au montage, et on vérifie ce qui a été émis avec emitted().

emitted('valider') renvoie un tableau des émissions de l'événement valider (une entrée par émission, avec ses arguments). C'est ainsi qu'on vérifie le « contrat de sortie » d'un composant sans connaître ses rouages internes.

Teste le comportement, pas l'implémentation

Un bon test vérifie ce que l'utilisateur voit et fait : « au clic, le compteur affiche 1 ». Il évite de fouiller les variables internes (wrapper.vm.n) ou de dépendre de la structure exacte du HTML. Ainsi tu peux refactoriser le composant sans réécrire les tests : seul un vrai changement de comportement doit les faire échouer.

Cas réel — le bouton qui émettait deux fois

Un composant <BoutonPaiement> déclenchait parfois deux paiements : un double-clic rapide émettait l'événement payer à deux reprises. Le bug était invisible en développement, mais coûteux en production. Un test tout simple — cliquer deux fois puis expect(wrapper.emitted('payer')).toHaveLength(1) — a d'abord échoué (révélant le défaut), puis réussi une fois la protection anti-double-clic ajoutée. Depuis, ce test garde la porte fermée : toute régression future le fera échouer aussitôt.

Pour aller plus loin — au-delà du test unitaire

Vue Testing Library encourage à sélectionner les éléments comme le ferait un utilisateur (par rôle, par texte), pour des tests encore plus proches de l'usage réel. Et pour vérifier un parcours complet dans un vrai navigateur (connexion, achat…), on passe aux tests de bout en bout avec Playwright ou Cypress. Test unitaire, d'intégration et e2e sont complémentaires — voir le cours Tests.

Antisèche — tester avec Vitest

Glossaire

Vitest
Lanceur de tests rapide qui partage la configuration de Vite ; exécute les fichiers de test et affiche les résultats.
Vue Test Utils
Bibliothèque officielle pour monter et inspecter des composants Vue dans un test (mount, wrapper).
mount
Fonction qui monte réellement un composant dans un DOM simulé et renvoie un wrapper.
Wrapper
Objet renvoyé par mount pour lire (text, find) et agir (trigger, emitted) sur le composant.
Arrange / Act / Assert
Structure d'un test : préparer, agir, puis vérifier le résultat attendu.
trigger
Simule un événement du DOM (clic, saisie…) ; à faire précéder de await pour laisser le rendu se rafraîchir.
emitted
Renvoie les événements émis par le composant ; sert à vérifier son « contrat de sortie ».
Non-régression
Garantie qu'un changement ne casse pas un comportement qui marchait ; les tests forment ce filet.

Récap et vérification

  • Vitest lance les tests ; Vue Test Utils (mount) monte le composant et renvoie un wrapper.
  • Structure Arrange / Act / Assert : mount → find().trigger() → expect().
  • await devant chaque trigger : le rendu de Vue est asynchrone.
  • On teste props (au montage) et événements (emitted), et surtout le comportement, pas l'implémentation.

Vérifie ta compréhension

  1. Que renvoie mount, et à quoi sert cet objet ?
  2. Pourquoi faut-il await devant trigger ?
  3. Comment vérifier qu'un composant a émis un événement ?

Exercices

Exercice 1Échauffement

Un composant Message affiche <p>Bonjour</p>. Écris un test qui vérifie que son rendu contient bien « Bonjour ».

Voir une solution

Pas d'interaction ici, donc pas de await : on monte (Arrange) et on vérifie directement le texte rendu (Assert).

Exercice 2Application

Un composant Salut reçoit une prop nom et affiche « Salut, {{ nom }} ! ». Écris un test qui lui passe le nom « Sofia » et vérifie le rendu.

Voir une solution

On passe les props via l'option { props: { ... } } de mount. Le test vérifie l'entrée du composant : la prop est-elle bien affichée ?

Exercice 3Défi

Un composant Interrupteur a un bouton qui émet l'événement bascule à chaque clic. Écris un test qui clique une fois et vérifie que l'événement a été émis exactement une fois. Attention au piège de l'asynchrone.

Voir une solution

Le piège : sans async / await, l'assertion s'exécuterait avant la mise à jour. On await le trigger, puis emitted('bascule') renvoie le tableau des émissions : toHaveLength(1) confirme qu'il y en a eu exactement une. On teste ainsi le contrat de sortie sans rien savoir de l'intérieur du composant.
