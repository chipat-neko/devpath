Module 4 · VB.NET approfondi — Leçon 13

Déboguer et fiabiliser son code

~52 min Avancé Prérequis : leçon 12

À la fin de cette leçon, tu sauras

  • activer Option Explicit et Option Strict ;
  • utiliser le débogueur (points d'arrêt, pas à pas, espions) ;
  • structurer la gestion d'erreurs avec Try/Catch/Finally ;
  • lever une exception avec Throw.
Sommaire de la leçon

Ton code fonctionne… la plupart du temps. Reste le plus difficile : le rendre fiable. Cela tient en trois gestes : détecter les erreurs le plus tôt possible, comprendre ce qui se passe quand ça coince, et réagir proprement à l'imprévu. Cette leçon réunit les trois outils correspondants en VB.NET : les options de compilation, le débogueur de Visual Studio, et la gestion structurée des exceptions.

Détecter tôt : Option Explicit et Option Strict

Par tolérance historique, VB.NET accepte des choses risquées : utiliser une variable jamais déclarée, ou convertir automatiquement un texte en nombre. Deux options rétablissent la rigueur et transforment des bugs d'exécution en erreurs de compilation, détectées avant même de lancer le programme.

  • Option Explicit On (actif par défaut) : oblige à déclarer chaque variable avec Dim. Une faute de frappe sur un nom devient une erreur, plus une variable fantôme silencieuse ;
  • Option Strict On (désactivé par défaut — à activer !) : interdit les conversions implicites qui peuvent perdre de l'information ou échouer. On doit alors convertir explicitement avec CInt, CStr, Integer.Parse…

Active Option Strict dès le début

On l'active par projet (Propriétés → Compiler → Option strict : On) ou fichier par fichier, en tête. Les quelques conversions à écrire explicitement te coûtent trois secondes ; elles t'épargnent des bugs sournois qui, sinon, n'apparaissent qu'à l'exécution.

Comprendre l'exécution : le débogueur

Quand un programme ne fait pas ce qu'on croit, inutile de deviner. Le débogueur de Visual Studio suspend l'exécution et laisse inspecter l'état réel du programme, ligne par ligne.

  • Point d'arrêt (breakpoint) : un clic dans la marge (ou F9) pose un point rouge ; l'exécution s'arrête sur cette ligne ;
  • Pas à pas : F10 exécute la ligne sans entrer dans les appels (pas à pas principal), F11 entre dans la procédure appelée (détaillé), Maj+F11 en ressort ;
  • Espions et variables locales : les fenêtres Variables locales et Espion affichent la valeur courante de chaque variable ; survoler une variable la montre aussi.

Le débogueur plutôt que le Console.WriteLine partout

Semer des Console.WriteLine pour tracer une valeur fonctionne, mais c'est lent et on oublie souvent d'en retirer dans le code livré. Un point d'arrêt ne laisse aucune trace et montre toutes les variables d'un coup. Réserve les traces aux problèmes qu'on ne peut pas reproduire au débogueur.

Réagir à l'imprévu : Try / Catch / Finally

Certaines erreurs ne dépendent pas de toi : fichier absent, réseau coupé, saisie invalide. On les appelle des exceptions. Plutôt que de laisser le programme planter, on les capture :

  • le bloc Try contient le code « à risque » ;
  • chaque Catch attrape un type précis d'exception ; l'ordre compte, du plus spécifique au plus général (un Catch ex As Exception placé en premier masquerait tous les autres) ;
  • Finally s'exécute toujours, avec ou sans erreur : c'est l'endroit du nettoyage (souvent remplacé par Using, vu à la leçon 12) ;
  • ex.Message contient le texte descriptif de l'erreur.

Parfois, c'est toi qui détectes une situation invalide et veux la signaler : on lève alors une exception avec Throw.

Cas réel : un import qui ne doit jamais tout casser

Cas réel — une ligne fautive ne doit pas faire tomber tout le rapport

Un outil de comptabilité importe chaque nuit un fichier CSV fourni par un partenaire. Une nuit, une ligne est mal formée (un montant écrit « N/A »). Sans gestion d'erreur, Integer.Parse lève une exception, le traitement s'interrompt, et le matin personne n'a de rapport. En entourant le traitement de chaque ligne d'un Try/Catch, les lignes valides sont importées, les fautives sont écrites dans un journal, et Finally referme proprement le fichier. Le lendemain, l'équipe a son rapport et la liste des lignes à corriger. La règle d'or : une exception attendue (donnée externe douteuse) se gère ; une exception inattendue (bug de logique) doit rester visible pour être corrigée.

Ne pas avaler les erreurs

Un Catch vide masque le vrai bug

Écrire un Catch qui ne fait rien fait taire l'erreur : le programme continue dans un état incohérent et le vrai problème devient introuvable. Ne capture que ce que tu sais traiter ; sinon laisse l'exception remonter. Et n'utilise jamais Try/Catch comme contrôle de flux normal : pour éviter un fichier absent, teste If File.Exists(chemin) plutôt que d'attraper l'exception après coup.

Pour aller plus loin

Pour aller plus loin — ses propres exceptions

Pour un besoin métier précis, on peut définir une classe qui hérite de Exception : Public Class SoldeInsuffisantException : Inherits Exception. On la lève avec Throw et on la capture spécifiquement — le code devient auto-documenté. Mais .NET fournit déjà des dizaines de types (ArgumentException, InvalidOperationException, IOException…) : réutilise-les avant d'en inventer.

Glossaire

Option Explicit
Option imposant la déclaration explicite (Dim) de toute variable ; évite les variables créées par une faute de frappe.
Option Strict
Option interdisant les conversions de type implicites risquées ; force les conversions explicites (CInt, Integer.Parse…).
Débogueur
Outil qui suspend l'exécution pour inspecter l'état du programme et avancer pas à pas.
Point d'arrêt
Breakpoint : marque posée sur une ligne où le débogueur suspend l'exécution.
Pas à pas
Exécution ligne par ligne (F10 principal, F11 détaillé) pour observer le déroulement.
Exception
Objet représentant une erreur survenue à l'exécution, qui interrompt le flux normal du programme.
Try / Catch / Finally
Structure qui capture les exceptions (Catch, par type) et garantit un nettoyage (Finally).
Throw
Instruction qui lève (déclenche) une exception pour signaler une situation invalide.

Récap et vérification

  • Option Explicit On (déclaration obligatoire) et Option Strict On (pas de conversion implicite risquée) attrapent des bugs dès la compilation.
  • Le débogueur (points d'arrêt, F10/F11, espions) montre l'état réel au lieu de deviner.
  • Try/Catch capture les exceptions par type, du plus précis au plus général ; Finally s'exécute toujours.
  • Throw lève une exception ; on ne capture que ce qu'on sait traiter, jamais un Catch vide.

Vérifie ta compréhension

  1. Que change Option Strict On pour les conversions de type ?
  2. À quoi sert un point d'arrêt ?
  3. Que fait l'instruction Throw ?
