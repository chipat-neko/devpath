Module 02 · Les services du quotidien — Leçon 05

HTTP, TLS & le web côté réseau

~32 min Intermédiaire Leçons 03 et 04 utiles

À la fin de cette leçon, tu sauras

  • situer HTTP dans la pile réseau (sur TCP) ;
  • expliquer ce qu'ajoute TLS (le « S » de HTTPS) ;
  • décrire la poignée de main TLS ;
  • distinguer HTTP/1.1, HTTP/2 et HTTP/3.
Sommaire de la leçon

On arrive au sommet de la pile : la couche application, celle qui donne un sens aux données. Pour le web, ce protocole est HTTP. Cette leçon le situe par rapport à tout ce qu'on a vu — IP, TCP, ports — et montre comment TLS vient le sécuriser.

HTTP, tout en haut de la pile

HTTP est le protocole du web : un échange requête → réponse entre un client (le navigateur) et un serveur. Mais HTTP ne s'occupe pas du transport : il s'appuie sur TCP (leçon 3), qui s'appuie sur IP (leçon 2). Chaque couche fait son travail.

Avant qu'une seule requête HTTP ne parte, il a donc fallu : résoudre le nom (DNS, leçon 4), ouvrir une connexion TCP (poignée de main), et — en HTTPS — négocier TLS.

TLS : le « S » de HTTPS

HTTP seul circule en clair : n'importe quel intermédiaire peut lire ou modifier les données. TLS (Transport Layer Security) s'insère entre TCP et HTTP et apporte trois garanties : confidentialité (chiffrement), intégrité (détection des altérations) et authenticité (on parle au bon serveur, prouvé par un certificat). HTTP + TLS = HTTPS.

Le cadenas, ce n'est pas « sûr »

Le cadenas du navigateur signifie « la connexion est chiffrée et le serveur a un certificat valide ». Il ne dit rien sur l'honnêteté du site lui-même : un site de phishing peut très bien être en HTTPS. TLS protège le transport, pas le contenu.

L'évolution du protocole

HTTP a évolué pour aller plus vite :

  • HTTP/1.1 : une requête à la fois par connexion (ou presque) — simple mais limité.
  • HTTP/2 : multiplexage — plusieurs échanges en parallèle sur une seule connexion TCP, en-têtes compressés.
  • HTTP/3 : repose sur QUIC, qui tourne sur UDP (pas TCP !) pour réduire la latence et mieux gérer les pertes, avec TLS intégré.

La boucle est bouclée

HTTP/3 sur UDP illustre joliment le cours : on a choisi UDP (rapide, leçon 3) et reconstruit par-dessus (dans QUIC) la fiabilité et le chiffrement nécessaires, plutôt que de subir certaines lourdeurs de TCP. Comprendre les couches, c'est comprendre pourquoi ces choix.

Cas réel — quand le web entier est passé au HTTPS

Longtemps, le HTTPS était réservé aux pages sensibles (paiement, connexion) car les certificats étaient payants et pénibles à installer. Tout a basculé vers 2015 : Let's Encrypt a rendu les certificats gratuits et automatiques, pendant que Chrome et Firefox commençaient à afficher « Non sécurisé » sur les pages en HTTP simple et réservaient HTTP/2 au HTTPS. En quelques années, la part des pages chargées en HTTPS est passée d'environ 30 % à plus de 90 %. Aujourd'hui, servir un site en clair est l'exception : le chiffrement du transport est devenu la norme par défaut.

Glossaire

HTTP
HyperText Transfer Protocol : le protocole applicatif du web, un échange requête → réponse.
HTTPS
HTTP transporté dans TLS : la même chose, mais chiffrée et authentifiée.
TLS
Transport Layer Security : la couche qui s'insère entre TCP et HTTP pour chiffrer et prouver l'identité du serveur.
Certificat
Preuve signée de l'identité d'un serveur, vérifiée par le client pendant la poignée de main TLS.
Poignée de main TLS
handshake : la négociation initiale (capacités, certificat, clé de session) avant l'échange chiffré.
Multiplexage
Faire circuler plusieurs échanges en parallèle sur une seule connexion (HTTP/2).
QUIC
Transport moderne bâti sur UDP, avec fiabilité par flux et TLS intégré : la base de HTTP/3.
Port 443
Le port standard de HTTPS (le port 80 étant celui du HTTP en clair).

Récap et vérification

  • HTTP est le protocole applicatif du web (requête/réponse), sur TCP (port 443 en HTTPS).
  • TLS s'insère entre TCP et HTTP : confidentialité, intégrité, authenticité (certificat) → HTTPS.
  • Le cadenas garantit la connexion, pas l'honnêteté du site.
  • Évolution : HTTP/1.1 → HTTP/2 (multiplexage) → HTTP/3 (QUIC sur UDP).

Vérifie ta compréhension

  1. Sur quoi s'appuie HTTP pour le transport ?
  2. Qu'ajoute TLS, et que ne garantit pas le cadenas ?
  3. Quelle particularité a HTTP/3 côté transport ?

Exercices

Exercice 1Échauffement

Range ces éléments du plus bas (réseau) au plus haut (application) : HTTP, IP, TCP, TLS.

Voir une solution

Du plus bas au plus haut : IP (couche Internet : adresses, routage) → TCP (couche transport : fiabilité, ports) → TLS (chiffrement, inséré au-dessus de TCP) → HTTP (couche application : le sens du message). Chacun s'appuie sur celui du dessous : HTTP voyage dans TLS, qui voyage dans TCP, qui voyage dans IP.

Exercice 2Application

« Mon site est en HTTPS, donc mes utilisateurs sont en sécurité. » Cette affirmation est-elle correcte ? Nuance.

Voir une solution

Partiellement seulement. HTTPS (HTTP + TLS) garantit que la communication entre le navigateur et le serveur est chiffrée (personne ne lit les données en transit), intègre (pas d'altération en chemin) et que le serveur est bien celui annoncé par son certificat. C'est nécessaire et indispensable. Mais HTTPS ne dit rien sur : la sécurité de l'application elle-même (injections, XSS, failles d'authentification — un site en HTTPS peut être vulnérable), l'honnêteté du site (un site de phishing obtient facilement un certificat valide et affiche le cadenas), ou la protection des données une fois arrivées sur le serveur. Le cadenas porte sur le transport, pas sur le contenu ni l'intention. La bonne formulation : « HTTPS protège les données en transit, c'est une couche nécessaire parmi d'autres ». La sécurité réelle combine HTTPS et une application sécurisée (cf. cours Sécurité applicative).

Exercice 3Défi

HTTP/3 a fait un choix surprenant : revenir à UDP, le transport « sans garantie ». Pourquoi est-ce pertinent, alors que le web a besoin de fiabilité ?

Voir une solution

Le paradoxe n'est qu'apparent. Le web a effectivement besoin de fiabilité, mais TCP impose des contraintes coûteuses en latence : une poignée de main avant tout échange, et surtout un blocage en tête de file (head-of-line blocking) — si un paquet est perdu, tout le flux TCP attend sa retransmission, même les données indépendantes prêtes à être livrées. Sur une connexion qui transporte de nombreux échanges en parallèle (comme une page web moderne), c'est pénalisant. HTTP/3 sur QUIC part d'UDP (rapide, sans ces contraintes) et reconstruit par-dessus, dans QUIC, exactement ce dont le web a besoin : fiabilité et ordre par flux indépendant (une perte ne bloque que son flux, pas les autres), établissement de connexion plus rapide (handshake combiné avec TLS), et meilleure gestion des changements de réseau (passer du Wi-Fi à la 4G sans tout recommencer). Autrement dit : plutôt que de subir les limites de TCP, on choisit la base minimale (UDP) et on y bâtit un transport sur mesure. C'est une belle illustration de la pensée « en couches » : comprendre ce que chaque couche garantit permet de recomposer les briques différemment pour de meilleures performances.
