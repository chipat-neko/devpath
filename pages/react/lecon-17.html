Robustesse : error boundaries, portals et tests

~35 min Intermédiaire Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire une error boundary (classe ou react-error-boundary) pour capter une erreur de rendu et afficher un repli, en sachant ce qu'elle ne capte pas ;
  • savoir projeter une UI ailleurs dans le DOM avec createPortal (modales, infobulles) tout en restant dans l'arbre React ;
  • savoir tester le comportement d'un composant et d'un hook avec React Testing Library (render, screen, getByRole, userEvent) et mocker un fetch ;
  • savoir déboguer avec les React DevTools et <StrictMode> sans masquer les signaux qu'ils révèlent.
Sommaire de la leçon

Une application qui « marche sur ta machine » n'est pas encore une application fiable. En production, une erreur dans un seul composant peut faire disparaître toute l'interface : l'utilisateur se retrouve devant un écran blanc, sans message ni recours. Et sans tests, chaque modification devient un pari. Cette leçon te donne les trois piliers de la robustesse : contenir les erreurs de rendu, projeter une UI ailleurs dans le DOM proprement, et vérifier le comportement automatiquement.

On verra les error boundaries, les portals, puis les tests avec React Testing Library (composant et hook), et enfin l'outillage de débogage. À chaque fois, le code est montré et son comportement décrit : React exige un build, rien ne s'exécute dans l'éditeur.

Les error boundaries

Par défaut, si un composant lève une exception pendant le rendu, React démonte tout l'arbre : page blanche. Une error boundary est un composant qui capte l'erreur d'un sous-arbre et affiche un repli (fallback) à la place, en gardant le reste de l'app vivant. Particularité historique : c'est l'un des rares cas où l'on écrit encore un composant de classe, car les hooks ne couvrent pas ce besoin.

On l'utilise comme une enveloppe : tout ce qui plante à l'intérieur déclenche le repli, le reste de la page est épargné. On peut en placer plusieurs, à différents niveaux de granularité.

En pratique, plutôt que réécrire cette classe, on utilise la bibliothèque react-error-boundary : elle fournit un composant prêt à l'emploi, un fallbackRender avec accès à l'erreur, et une fonction resetErrorBoundary pour réessayer.

Piège fréquent

Une error boundary ne capte pas tout. Elle ignore les erreurs des gestionnaires d'événements (un onClick qui plante) et le code asynchrone (un setTimeout, une promesse, un await dans un effet). Ces cas-là se gèrent avec un try/catch classique et un état d'erreur.

Cas réel

Une boutique en ligne déploie une refonte du panier. Un bug dans le bloc de recommandations — une propriété undefined lue pendant le rendu — fait planter tout l'arbre : au lieu d'un simple encart de suggestions manquant, c'est la page entière qui vire à l'écran blanc, panier compris, et les ventes s'effondrent avant la moindre alerte. Le correctif tient en deux temps : envelopper chaque zone secondaire (recommandations, avis, bannières) dans sa propre error boundary pour qu'une panne locale reste locale, et brancher componentDidCatch sur un outil de suivi (Sentry) pour être prévenu à la première occurrence plutôt que par la courbe du chiffre d'affaires.

Les portals

Parfois, un composant doit être rendu ailleurs dans le DOM que là où il est déclaré : une modale, une infobulle ou un menu déroulant ne doivent pas être coincés dans un parent qui a overflow: hidden ou un empilement (z-index) défavorable. Le portal résout ça : createPortal(enfant, conteneur) rend l'enfant dans un nœud DOM différent, tout en le gardant dans l'arbre React.

Le point conceptuel à retenir : les événements bouillonnent dans l'arbre React, pas dans l'arbre DOM. Même si la modale est physiquement à la fin du <body>, un clic en son sein remonte vers le composant parent qui l'a déclarée. Le contexte (useContext), lui aussi, traverse normalement : le portal change l'emplacement DOM, pas la position logique.

Note

Le conteneur cible (#modal-root) doit exister dans le HTML avant le rendu. On l'ajoute à côté du <div id="root"> dans index.html. Pense aussi à l'accessibilité : rôle dialog, gestion du focus et fermeture au clavier (touche Échap).

Tester comme un utilisateur

React Testing Library (RTL) repose sur une philosophie simple : tester le comportement, pas l'implémentation. On n'inspecte pas l'état interne ni les noms de fonctions ; on interroge le rendu comme le ferait un utilisateur — par rôle accessible, par texte, par libellé — et on simule de vraies interactions. Un test ainsi écrit survit à un refactor tant que le comportement visible ne change pas.

Le trio de base : render monte le composant, screen donne accès aux requêtes, et les getByRole / getByText retrouvent les éléments. Pour les interactions, userEvent simule clics et saisies de façon réaliste.

Préfère getByRole aux sélecteurs CSS : il échoue si le bouton n'est pas accessible, ce qui te pousse à écrire une UI correcte. Utilise findBy… (asynchrone) pour attendre un élément qui apparaît après un chargement, et queryBy… (qui renvoie null) pour vérifier une absence.

Tester un hook et mocker le réseau

Un hook personnalisé ne s'appelle pas hors d'un composant. Pour le tester en isolation, RTL fournit renderHook, qui le monte dans un composant minimal et expose son result.current. Toute mise à jour d'état se fait dans act pour que React applique le rendu.

Pour un composant qui fait un fetch, on ne contacte pas le vrai réseau : on le mocke afin que le test soit rapide et déterministe. On remplace fetch par une fonction simulée renvoyant une réponse contrôlée, puis on attend l'affichage avec findBy….

Astuce

Mocker fetch à la main devient vite fragile. MSW (Mock Service Worker) intercepte les requêtes au niveau réseau : ton composant utilise le vrai fetch, et tu décris les réponses dans des handlers réutilisables entre tous tes tests.

Déboguer : DevTools et StrictMode

Deux outils accompagnent ton développement quotidien. Les React DevTools (extension de navigateur) affichent l'arbre des composants, leurs props, leur état, et un Profiler pour repérer les rendus coûteux. Et <StrictMode> est un composant qui n'affiche rien mais active, en développement uniquement, des vérifications supplémentaires.

Ce double rendu n'est pas un bug : c'est un révélateur. Si ton composant se comporte mal quand il est rendu deux fois, c'est qu'il cache un effet de bord pendant le rendu, ou un effet sans nettoyage. StrictMode te le montre tôt, en local, plutôt qu'en production.

Pièges fréquents

Le premier réflexe à corriger : une error boundary ne peut pas s'écrire en composant fonction. Il n'existe pas (encore) de hook équivalent à getDerivedStateFromError ; il faut une classe, ou la bibliothèque react-error-boundary. Tenter un try/catch autour du JSX dans une fonction n'attrape rien : l'erreur de rendu survient plus tard, lors du commit.

Piège fréquent

Croire qu'une error boundary rattrape une promesse rejetée ou une erreur dans un onClick : faux. Ces erreurs asynchrones et événementielles échappent au mécanisme ; gère-les avec try/catch et un état d'erreur que tu affiches toi-même.

Côté tests, l'erreur classique est de tester l'implémentation au lieu du comportement : vérifier qu'une variable d'état vaut telle valeur, ou cibler par classe CSS. Le test casse au moindre refactor sans qu'aucun bug réel n'existe. Interroge toujours ce que l'utilisateur perçoit : un texte, un rôle, un libellé.

Enfin, ne retire jamais <StrictMode> pour faire taire un avertissement ou un double rendu gênant. Ce n'est pas le bruit : c'est le signal. Le supprimer masque un vrai problème qui réapparaîtra en production, plus difficile à diagnostiquer.

Pour aller plus loin

Les exemples de test ci-dessus tournent avec un lanceur de tests : Vitest (intégré naturellement à Vite) ou Jest. Ils fournissent test, expect, les mocks et le rapport de couverture.

Pour aller plus loin

Au-delà des tests unitaires : Playwright pour les tests end-to-end (piloter un vrai navigateur sur ton app complète), MSW pour simuler le réseau de façon réaliste, et TypeScript pour typer props, état et hooks — beaucoup de bugs deviennent alors impossibles dès l'écriture du code.

Antisèche

Glossaire

Error boundary
Composant (classe ou react-error-boundary) qui capte une erreur de rendu d'un sous-arbre et affiche un repli, en gardant le reste de l'application vivant.
getDerivedStateFromError
Méthode statique appelée quand un enfant lève au rendu ; elle renvoie le nouvel état qui fait basculer sur le repli.
componentDidCatch
Méthode de cycle de vie où l'on journalise l'erreur et sa pile de composants (console ou outil de suivi).
Portal
Rendu d'un enfant dans un autre nœud du DOM via createPortal, tout en le gardant à sa place dans l'arbre React (propagation des événements, contexte).
React Testing Library
Bibliothèque qui pousse à tester le comportement visible (rôles, textes) plutôt que l'implémentation interne.
getByRole
Requête RTL qui retrouve un élément par son rôle accessible (bouton, titre…) ; elle échoue si l'UI n'est pas accessible.
renderHook
Monte un hook isolé dans un composant minimal et expose result.current ; les mises à jour d'état se font dans act.
StrictMode
Composant de développement qui monte, démonte et rend chaque composant deux fois pour révéler les effets de bord impurs ; sans effet en production.

Récap et vérification

  • Une error boundary (classe avec getDerivedStateFromError / componentDidCatch, ou react-error-boundary) capte les erreurs de rendu d'un sous-arbre et affiche un repli ; elle ignore l'asynchrone et les événements.
  • createPortal(enfant, conteneur) rend un enfant ailleurs dans le DOM (modales, infobulles) tout en le gardant dans l'arbre React : les événements y bouillonnent selon l'arbre React.
  • Avec React Testing Library, on teste le comportement : render, screen, getByRole / getByText, userEvent et expect.
  • renderHook teste un hook isolé ; on mocke fetch (ou MSW) pour des tests rapides et déterministes.
  • Les React DevTools et <StrictMode> (double rendu en dev) révèlent les bugs tôt : ce sont des signaux, pas du bruit.

Vérifie ta compréhension

  1. Pourquoi une error boundary doit-elle être une classe (ou react-error-boundary), et quelles erreurs ne capte-t-elle jamais ?
  2. Un clic dans une modale rendue par portal : vers quel parent l'événement remonte-t-il, celui du DOM ou celui de l'arbre React ?
  3. Que signifie « tester le comportement, pas l'implémentation », et pourquoi getByRole y aide-t-il ?
