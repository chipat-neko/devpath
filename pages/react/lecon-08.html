Les formulaires contrôlés

~35 min Intermédiaire Leçon 07 recommandée

À la fin de cette leçon, tu sauras

  • lier un champ de saisie à l'état avec value et onChange (composant contrôlé) ;
  • gérer plusieurs champs (texte, checkbox, radio, select) avec un état objet et un handler générique ;
  • traiter la soumission d'un formulaire avec onSubmit et preventDefault, puis réinitialiser l'état ;
  • ajouter une validation simple et afficher des messages d'erreur.
Sommaire de la leçon

Tu sais maintenant lire et modifier l'état d'un composant. Les formulaires sont l'endroit où ce savoir devient vraiment concret : chaque champ de saisie est une donnée que l'utilisateur fait varier, et que ton composant doit suivre. En React, la bonne pratique consiste à faire de l'état la source de vérité de chaque champ. On appelle ça un composant contrôlé.

Dans cette leçon, tu vas relier un champ à l'état, gérer plusieurs types de champs (texte, case à cocher, boutons radio, menu déroulant), regrouper tout ça dans un seul état objet, puis traiter la soumission et valider la saisie. À la fin, tu sauras construire un petit formulaire complet et fiable.

Le champ contrôlé : value + onChange

Un champ HTML, laissé à lui-même, garde sa propre valeur dans le DOM. React préfère que ce soit l'état qui décide de la valeur affichée. Le principe tient en deux attributs :

  • value={texte} : la valeur affichée vient de l'état ;
  • onChange : à chaque frappe, on met l'état à jour avec la nouvelle valeur.

La boucle est la suivante : tu tapes une lettre → onChange se déclenche → setTexte met l'état à jour → le composant se re-rend → value affiche le nouvel état. L'utilisateur a l'impression de taper normalement, mais en réalité c'est React qui réaffiche le champ à chaque frappe. Comme l'état contient toujours la vérité, tu peux l'afficher ailleurs, le transformer, le valider : il est à ta disposition.

Note

« Source de vérité » veut dire : la valeur officielle du champ vit dans l'état React, pas dans le DOM. Le champ visible n'est qu'un reflet de cet état.

Les différents types de champs

Tous les champs suivent la même logique (état + handler), mais l'attribut à contrôler change selon le type. Voici les cas courants.

Le <textarea> se contrôle comme un input texte, avec value : en React, on ne met pas le texte entre les balises, on le passe en value.

La case à cocher n'a pas de texte : son état est un booléen, et on contrôle checked (pas value). On lit e.target.checked.

Les boutons radio partagent un même état : chaque bouton est checked quand l'état vaut sa valeur. Le <select>, lui, se contrôle par value posé sur le select (et non sur les <option>).

Plusieurs champs avec un état objet

Un useState par champ devient vite lourd. Pour un vrai formulaire, regroupe les champs dans un seul état objet, et écris un handler générique qui sait quel champ mettre à jour grâce à l'attribut name du champ.

Deux points clés ici. D'abord, name="nom" sur l'input doit correspondre à la clé nom de l'objet : c'est ce qui permet à [name]: value (une clé calculée) de cibler le bon champ. Ensuite, on ne mute jamais l'objet : on en crée une copie avec ...prev puis on remplace une seule clé. React détecte le changement parce que c'est un nouvel objet.

Astuce

Pour qu'une case à cocher passe par le même handler, lis la bonne propriété selon le type. Au début du handler, calcule : const champ = e.target.type === "checkbox" ? e.target.checked : e.target.value; puis fais setForm((prev) => ({ ...prev, [e.target.name]: champ })).

La soumission du formulaire

Pour traiter l'envoi, on écoute onSubmit sur le <form>, pas un onClick sur le bouton. Première chose à faire dans le handler : e.preventDefault(), qui empêche le navigateur de recharger la page (comportement HTML par défaut). Ensuite, tu lis l'état, tu fais ton traitement, et tu peux réinitialiser.

Comme les champs sont contrôlés, réinitialiser le formulaire revient simplement à remettre l'état à sa valeur de départ : les champs se vident automatiquement, puisqu'ils reflètent l'état.

Valider et afficher les erreurs

La validation est un calcul sur l'état. À la soumission, tu vérifies les champs, tu construis un objet d'erreurs, et tu n'envoies que s'il est vide. Les messages s'affichent ensuite avec un rendu conditionnel.

Le motif {erreurs.email && <p>…</p>} n'affiche le paragraphe que si une erreur existe pour ce champ. La fonction valider reçoit les valeurs et renvoie un objet d'erreurs : la séparer du handler la rend testable et réutilisable.

Et les champs non contrôlés ?

Il existe une autre approche : les composants non contrôlés, où l'on laisse le DOM stocker la valeur et où on la lit au dernier moment avec une référence (useRef). C'est plus court pour un formulaire très simple, mais on perd l'accès continu à la valeur (validation en direct, désactivation conditionnelle du bouton…). On y reviendra dans la leçon 12.

Pour des formulaires riches (beaucoup de champs, validation poussée), des bibliothèques comme React Hook Form ou Formik automatisent l'état, la validation et les erreurs. Le contrôlé « à la main » que tu viens d'apprendre reste la base : ces outils en sont une couche au-dessus.

Pièges fréquents

Piège fréquent

Mettre value sans onChange : le champ devient en lecture seule (impossible de taper), et React affiche un avertissement en console. Un champ contrôlé a toujours les deux. Si tu veux vraiment une valeur initiale modifiable sans la suivre, utilise defaultValue (non contrôlé) à la place.

  • Une case à cocher via value au lieu de checked. Une checkbox se contrôle avec checked={booléen} et se lit via e.target.checked. Avec value, la case ne reflètera pas l'état.
  • Muter l'état objet. Écrire form.nom = "x"; setForm(form) ne déclenche pas de re-rendu : c'est le même objet. Crée toujours une copie : setForm((prev) => ({ ...prev, nom: "x" })).
  • Oublier name sur un champ. Le handler générique s'appuie sur e.target.name pour savoir quelle clé mettre à jour. Sans name, [name] vaut undefined et tu corromps l'objet.
  • Oublier e.preventDefault(). Sans lui, la soumission recharge la page et tu perds l'état ; ton handler semble « ne rien faire ».

Pour aller plus loin

Pour aller plus loin

Explore les formulaires non contrôlés avec useRef (leçon 12), puis React Hook Form ou Formik pour gérer état, validation et erreurs à grande échelle. Côté validation, des schémas comme Zod ou Yup décrivent les règles de façon déclarative. Et n'oublie jamais l'accessibilité : chaque champ mérite un <label htmlFor> associé, et un message d'erreur doit être relié au champ (par exemple via aria-describedby).

Cas réel

Sur un formulaire d'inscription réel, deux besoins reviennent toujours : garder le bouton « Créer mon compte » désactivé tant que la saisie est invalide, et afficher les erreurs sous chaque champ en direct. Les deux découlent gratuitement du champ contrôlé : comme l'état contient la vérité, on écrit disabled={!estValide} et les messages se recalculent à chaque frappe. Le piège inverse est tout aussi courant : poser value={x} en oubliant onChange rend le champ impossible à modifier — l'utilisateur tape et rien ne s'affiche — et React le signale en console. Un champ contrôlé a toujours les deux.

Antisèche

Glossaire

Composant contrôlé
Champ dont la valeur affichée vient de l'état React (via value/checked) et se met à jour par onChange.
Composant non contrôlé
Champ dont la valeur vit dans le DOM (defaultValue), lue au dernier moment avec une référence (useRef).
Source de vérité
Endroit qui détient la valeur officielle du champ : l'état React pour un champ contrôlé, le DOM pour un non contrôlé.
value / checked
Attributs contrôlés : value pour le texte et le select, checked (booléen) pour checkbox et radio.
Handler générique
Fonction unique branchée sur plusieurs champs, qui met à jour le bon grâce à e.target.name.
Clé calculée [name]
Syntaxe { [name]: value } qui utilise la valeur de name comme nom de propriété : cible dynamiquement le champ à modifier.
Validation
Calcul sur l'état qui produit un objet d'erreurs ; on n'envoie que s'il est vide, et on affiche les messages par rendu conditionnel.
useRef
Hook renvoyant une référence persistante (ref.current) ; sert à lire un champ non contrôlé sans re-rendu à chaque frappe (leçon 12).

Récap et vérification

  • Un champ contrôlé tire sa valeur de l'état (value / checked) et la met à jour à chaque frappe (onChange) : l'état est la source de vérité.
  • La case à cocher se contrôle par checked et se lit via e.target.checked ; le <select> par value sur le select.
  • Plusieurs champs : un état objet + un handler générique qui s'appuie sur e.target.name et recopie l'objet (...prev).
  • La soumission écoute onSubmit, commence par preventDefault(), lit l'état, valide, puis réinitialise.

Vérifie ta compréhension

  1. Que se passe-t-il si tu mets value sur un input sans onChange ?
  2. Pourquoi écrit-on setForm((prev) => ({ ...prev, [name]: value })) plutôt que de modifier form directement ?
  3. Quel attribut contrôle une case à cocher, et quelle propriété lit-on dans le handler ?
