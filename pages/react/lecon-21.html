Module 07 · React avec TypeScript — Leçon 21

React avec TypeScript

~40 min Intermédiaire Notions de TypeScript utiles

À la fin de cette leçon, tu sauras

  • démarrer un projet React typé et nommer tes fichiers .tsx ;
  • typer un composant, ses props et ses hooks ;
  • typer un Context et un hook personnalisé ;
  • mesurer ce que le typage t'évite comme bugs.
Sommaire de la leçon

Tout ce cours t'a montré React en JSX ; en entreprise, on l'écrit presque toujours en TypeScript. Le gain est énorme : l'éditeur connaît tes composants, refuse une prop oubliée, et t'évite la classe de bugs la plus fréquente en React — passer la mauvaise donnée au mauvais composant. Cette leçon montre, côté React, comment tirer parti de TypeScript dans une vraie application. Elle complète la leçon « TypeScript avec React » du cours TypeScript : ici, l'accent est sur la pratique React.

Démarrer un projet typé

Les outils modernes proposent un modèle TypeScript clé en main. Les fichiers de composants prennent l'extension .tsx (TSX = JSX + types).

Aucune configuration manuelle : le typage est actif d'emblée, et l'éditeur signale les erreurs au fil de la frappe.

Un composant typé, de bout en bout

Un composant typé déclare la forme de ses props. L'erreur la plus fréquente (oublier ou mal nommer une prop) devient impossible.

L'éditeur autocomplète titre, badge, children et signale toute incohérence : c'est un filet de sécurité permanent à mesure que l'application grandit.

Cas réel

Une équipe renomme la prop d'un composant très utilisé : onClose devient onDismiss. En JavaScript, les dizaines d'appels qui passent encore onClose ne provoquent aucune erreur : la prop est simplement ignorée, et le bouton « fermer » cesse silencieusement de fonctionner un peu partout — un bug découvert en production. Le même renommage en TypeScript colore en rouge chaque appel resté sur l'ancien nom : le compilateur dresse la liste exacte des fichiers à corriger, et le refactor se termine en confiance en quelques minutes.

Hooks et événements en pratique

Dans un composant réel, l'état et les événements bénéficient directement du typage. useState infère le plus souvent ; pour un événement, on utilise le type React adéquat.

TypeScript garantit ici que e.target.value est une chaîne, et que setNom n'accepte qu'une chaîne. Les erreurs de type sur l'état (passer un nombre là où on attend une chaîne) sont attrapées immédiatement.

Astuce — laisser inférer, ou annoter ?

Règle simple : laisse useState inférer quand la valeur initiale est représentative (useState("") → string, useState(0) → number). Annote quand elle ne l'est pas : useState(null) serait bloqué sur le type null — écris useState<User | null>(null). Même réflexe pour un tableau vide : useState<Tache[]>([]), sinon TypeScript déduit never[] et refusera le premier ajout.

Typer un Context et un hook personnalisé

Pour partager un état (thème, utilisateur connecté), le Context se type pour éviter le piège du « contexte utilisé hors de son fournisseur ».

En typant le contexte ThemeCtx | null et en vérifiant dans le hook, on transforme un bug d'exécution courant (un undefined inattendu) en une erreur explicite et localisée. C'est un patron très répandu.

Typage à l'intérieur, validation à la frontière

Un piège classique : croire que « projet TypeScript » veut dire « données sûres ». Le typage vérifie ce que toi tu écris ; il ne sait rien de ce qui entre depuis l'extérieur — une réponse d'API, un localStorage, une variable d'URL. Un const data = await res.json() a le type any (ou unknown) : TypeScript te croit sur parole. Le bon modèle mental : le typage protège l'intérieur de l'app, la validation protège son entrée.

Piège fréquent

Typer le composant mais oublier que les données externes (réponses d'API affichées dans React) ne sont pas vérifiées par les types. Un const data = await res.json() reste non fiable, même dans un projet TS. Valide ces données à la frontière (avec Zod, voir le cours TypeScript) avant de les passer à tes composants. Le typage protège l'intérieur de ton app ; la validation protège son entrée.

Pour aller plus loin

L'écosystème React est entièrement typé : React Router, TanStack Query, les bibliothèques de formulaires… exposent des types riches qui guident leur usage. Tu n'as presque jamais à écrire any. Pour approfondir le typage lui-même (génériques, types utilitaires, types conditionnels), c'est le cours TypeScript qui prend le relais. Ensemble, React et TypeScript forment la combinaison la plus demandée du développement front — et la plus agréable une fois prise en main.

Glossaire

.tsx
Extension d'un fichier de composant React typé : TSX = JSX + annotations de types.
Props typées
Forme des propriétés d'un composant, déclarée par un type (ou une interface) et vérifiée à chaque appel : une prop oubliée ou mal typée devient une erreur de compilation.
React.ReactNode
Type du contenu qu'un composant peut afficher (les children) : éléments JSX, chaînes, nombres, listes, null…
ChangeEvent
Type d'un événement de saisie React, paramétré par l'élément concerné (HTMLInputElement) ; il donne un e.target.value correctement typé.
useState<T>
Forme annotée du hook d'état, utile quand la valeur initiale ne suffit pas à inférer le type (null, union, tableau vide).
Context typé
createContext<T | null>(null) associé à un hook qui lève une erreur si le contexte est null : un usage hors du Provider devient une erreur claire et localisée.
unknown
Type d'une donnée dont on ne sait rien encore (ex. réponse d'API) ; il force à vérifier avant tout usage, contrairement à any.
any
Type « passe-partout » qui désactive toute vérification ; à éviter, en particulier sur les données venues de l'extérieur.

Récap et vérification

  • Démarrer typé (--template react-ts) ; composants en .tsx.
  • Typer les props évite l'erreur n°1 (mauvaise donnée au mauvais composant) ; children = React.ReactNode.
  • Hooks et événements typés (useState<T>, React.ChangeEvent<…>) ; Context typé + hook qui vérifie le non-null.
  • Le typage protège l'intérieur ; valider les données externes à la frontière reste nécessaire.

Exercice 3Défi

Pourquoi typer un Context en MonType | null puis vérifier dans un hook personnalisé ?

Voir une solution

Parce qu'un composant peut tenter d'utiliser le contexte en dehors de son fournisseur : dans ce cas useContext renvoie la valeur par défaut (null). En typant le contexte MonType | null et en lançant une erreur explicite dans le hook personnalisé si la valeur est null, on transforme un bug d'exécution silencieux (un undefined inattendu plus loin) en un message clair et localisé — et, après la vérification, TypeScript sait que la valeur est garantie non-null et typée.
