Gérer les événements

~33 min Intermédiaire Leçon 06 recommandée

À la fin de cette leçon, tu sauras

  • attacher un gestionnaire d'événement en JSX (onClick, onChange, onSubmit) en lui passant une fonction, pas son appel ;
  • lire l'objet événement (e.target.value) et appeler e.preventDefault() pour bloquer le rechargement d'un formulaire ;
  • passer des arguments à un handler via une fonction fléchée onClick={() => faire(id)} ;
  • remonter un événement au composant parent grâce à une prop fonction.
Sommaire de la leçon

Une interface n'est vivante que si elle réagit : un clic incrémente un compteur, une frappe filtre une liste, une soumission envoie un formulaire. Tu sais déjà gérer des événements en JavaScript vanilla avec addEventListener. En React, le principe est le même, mais tu n'attaches plus les écouteurs à la main : tu les déclares directement dans le JSX, et React s'occupe du branchement.

Dans cette leçon, tu vas brancher des boutons et un champ de saisie sur l'état du composant, lire l'objet événement, empêcher le comportement par défaut d'un formulaire, et faire communiquer un enfant vers son parent. On part du connu (un écouteur DOM) vers l'idiome React.

Les gestionnaires d'événements en JSX

Pour réagir à une action, tu passes une fonction à un attribut comme onClick, onChange ou onSubmit. Ces attributs s'écrivent en camelCase (rappelle-toi des règles de JSX), et ils reçoivent la fonction entre accolades.

Le point décisif : onClick={direBonjour} passe la fonction elle-même, pour que React l'appelle plus tard, au moment du clic. Si tu écris onClick={direBonjour()} avec des parenthèses, tu appelles la fonction tout de suite, pendant le rendu, et tu passes à onClick sa valeur de retour (souvent undefined). On revient sur ce piège plus bas — c'est l'erreur numéro un.

Définir le handler dans le composant

Le plus souvent, le handler vit dans le composant, car il a besoin de lire et de modifier l'état. Voici un compteur qui s'incrémente à chaque clic.

Le handler incrementer appelle setCount, qui demande à React de re-rendre le composant avec la nouvelle valeur. Tu décris le résultat (Cliqué {count} fois) ; React s'occupe de mettre le DOM à jour. La forme fonctionnelle setCount((c) => c + 1) part toujours de la valeur la plus récente ; on peut aussi écrire le handler en fonction fléchée inline quand il est court : onClick={() => setCount((c) => c + 1)}.

Passer des arguments à un handler

Souvent, tu veux transmettre une donnée au handler — par exemple l'id de l'élément cliqué. Tu ne peux pas écrire onClick={supprimer(id)} : ce serait un appel immédiat. La solution idiomatique est d'envelopper l'appel dans une fonction fléchée.

La fonction fléchée () => supprimer(t.id) est une nouvelle fonction que React appellera au clic. C'est elle qui appelle supprimer(t.id), au bon moment, avec le bon argument. Note au passage la prop key={t.id} sur chaque <li> : une clé stable, indispensable dans une liste.

L'objet événement

React passe automatiquement un objet événement à ton handler — on le nomme par convention e (ou event). Il porte des informations utiles : e.target (l'élément concerné), e.target.value (la valeur d'un champ), e.key (la touche pressée)… et des méthodes comme e.preventDefault().

Le cas le plus courant est un champ de saisie : à chaque frappe, onChange se déclenche, et on lit e.target.value pour mettre l'état à jour.

L'autre usage clé est e.preventDefault(), qui annule le comportement par défaut du navigateur. Sur un formulaire, ce comportement est de recharger la page : en React (application monopage), on ne veut presque jamais ça.

On met onSubmit sur le <form> (pas onClick sur le bouton) : ainsi la touche Entrée dans le champ déclenche aussi l'envoi, ce qui est meilleur pour l'accessibilité.

Les événements synthétiques de React

L'objet e que tu reçois n'est pas tout à fait l'événement natif du DOM : c'est un événement synthétique (SyntheticEvent), une enveloppe que React place par-dessus. Son intérêt : une API identique et cohérente dans tous les navigateurs. Tu utilises e.target, e.preventDefault() ou e.stopPropagation() de la même façon partout, sans te soucier des différences entre Chrome, Firefox ou Safari.

Note

Si tu as vraiment besoin de l'événement natif, il reste accessible via e.nativeEvent. En pratique, l'API synthétique couvre la quasi-totalité des cas : e.target.value, e.key, e.preventDefault()…

Remonter un événement au parent

Les données descendent du parent vers l'enfant via les props. Pour faire l'inverse — qu'un enfant signale quelque chose à son parent — on passe une fonction en prop. L'enfant se contente de l'appeler ; c'est le parent qui décide quoi en faire. Ce motif s'appelle souvent un callback, et on nomme la prop onQuelqueChose par convention.

Le parent passe sa fonction ajouter via la prop onAjouter. L'enfant, lui, ignore tout de l'état : il appelle onAjouter("Nouvelle tâche") au clic. Cette séparation rend BoutonAjout réutilisable n'importe où. Remarque aussi setTaches((liste) => [...liste, texte]) : on construit un nouveau tableau plutôt que de modifier l'ancien — l'état reste immuable.

Éviter de recréer des handlers coûteux

Une fonction fléchée inline comme () => supprimer(t.id) est recréée à chaque rendu. Dans l'immense majorité des cas, c'est parfaitement acceptable : ne complique pas ton code pour ça. Mais quand un handler est passé à un composant enfant optimisé (mémoïsé), cette nouvelle fonction à chaque rendu peut casser l'optimisation et provoquer des rendus inutiles.

Le hook useCallback conserve la même référence de fonction d'un rendu à l'autre. Retiens juste l'idée pour l'instant : on l'étudiera en détail à la leçon 13. Tant que tu n'as pas mesuré un problème de performance, écris tes handlers simplement.

Pièges fréquents

Piège fréquent

Écrire onClick={faire()} au lieu de onClick={faire}. Avec les parenthèses, la fonction est appelée pendant le rendu (et à chaque re-rendu), pas au clic. Passe la fonction, ou enveloppe l'appel : onClick={() => faire()}.

  • Oublier e.preventDefault() sur un onSubmit. Sans lui, le navigateur recharge la page et tu « perds » ton application. Mets-le en première ligne du handler de soumission.
  • Muter l'état dans un handler. taches.push(x) modifie le tableau existant : React ne voit pas le changement et ne re-rend pas. Crée une nouvelle valeur : setTaches([...taches, x]).
  • Mal passer les arguments. onClick={supprimer(id)} appelle supprimer tout de suite. Il faut une fonction fléchée : onClick={() => supprimer(id)}.
  • Confondre la valeur et l'événement. Dans onChange, le handler reçoit l'événement e, pas directement la valeur. Lis e.target.value.

Pour aller plus loin

Pour aller plus loin

Sous le capot, React utilise une forme de délégation d'événements : il pose ses écouteurs à la racine et les redistribue, plutôt que d'attacher un écouteur par élément. Au-delà de onClick et onChange, explore les événements clavier (onKeyDown avec e.key) et focus (onFocus, onBlur) : ils sont essentiels pour l'accessibilité, afin que tout soit pilotable au clavier. Et pour stabiliser des handlers passés en props, garde useCallback en tête (leçon 13).

Cas réel

Grand classique en revue de code : une liste où chaque ligne porte <button onClick={supprimer(item.id)}>. Au lieu d'attendre le clic, supprimer est appelée pour chaque ligne pendant le rendu : les éléments « disparaissent tout seuls » au chargement, et comme chaque suppression relance un rendu, on frôle la boucle infinie. Correctif : envelopper l'appel, onClick={() => supprimer(item.id)}. Côté formulaire, le pendant est un onSubmit sans e.preventDefault() : la page se recharge, l'application « s'efface », et le handler semble ne rien faire alors qu'il s'exécute bel et bien.

Glossaire

Gestionnaire d'événement
Fonction (handler) exécutée en réaction à une action de l'utilisateur (clic, frappe, soumission).
onClick / onChange / onSubmit
Attributs JSX en camelCase auxquels on passe un gestionnaire ; ils remplacent addEventListener.
Objet événement (e)
Objet passé au handler qui décrit l'événement : e.target, e.target.value, e.key, et des méthodes.
Événement synthétique
Enveloppe (SyntheticEvent) que React place sur l'événement natif pour offrir une API identique dans tous les navigateurs ; le natif reste sous e.nativeEvent.
e.preventDefault()
Annule le comportement par défaut du navigateur, par exemple le rechargement de la page à la soumission d'un formulaire.
Fonction fléchée en ligne
() => faire(x) : nouvelle fonction créée pour appeler le handler au clic avec un argument, sans l'exécuter au rendu.
Callback (prop fonction)
Fonction passée par le parent en prop (nommée onXxx) que l'enfant appelle pour remonter un événement.
useCallback
Hook qui conserve la même référence de fonction entre les rendus ; utile quand un handler est passé à un enfant mémoïsé (leçon 13).

Récap et vérification

  • Un gestionnaire reçoit une fonction : onClick={faire}, jamais onClick={faire()}.
  • Pour passer un argument, enveloppe l'appel dans une fonction fléchée : onClick={() => faire(id)}.
  • Le handler reçoit l'objet événement e : e.target.value lit un champ, e.preventDefault() bloque le rechargement d'un formulaire.
  • Les événements de React sont synthétiques : une API cohérente entre navigateurs.
  • Un enfant remonte un événement au parent en appelant une prop fonction ; l'état se met à jour de façon immuable.
