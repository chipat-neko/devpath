Module 06 · React en production — Leçon 20

Les frameworks et le rendu (Next.js, RSC)

~35 min Avancé Leçon 19 recommandée

À la fin de cette leçon, tu sauras

  • comparer les modes de rendu CSR, SSR, SSG et ISR et choisir le bon pour un cas donné ;
  • expliquer ce qu'apporte un framework comme Next.js (App Router) par rapport à React + Vite ;
  • distinguer un Server Component d'un Client Component ('use client') et savoir où s'exécute chacun ;
  • situer le déploiement, TypeScript et l'accessibilité dans une appli React de production.
Sommaire de la leçon

Jusqu'ici, tu as construit des interfaces React qui vivent entièrement dans le navigateur : tu sers un index.html quasi vide, un gros fichier JavaScript prend le relais, et c'est React qui peint l'écran. C'est une Single Page Application (SPA), et c'est parfait pour un tableau de bord ou un outil interne. Mais dès qu'il s'agit de référencement, de premier chargement rapide ou de données sensibles, ce modèle montre ses limites.

Cette leçon prend de la hauteur : elle décrit les modes de rendu, les frameworks (Next.js, React Router/Remix) et la grande nouveauté de React moderne, les React Server Components. Comme tout cela exige un serveur et un build complet, on ne lance rien ici : on lit le code et on décrit le comportement.

Les limites d'une SPA pure

Une SPA React + Vite renvoie au navigateur une page presque vide, du genre <div id="root"></div>. Tout le contenu est ensuite généré côté client par JavaScript. Trois problèmes apparaissent à l'échelle.

  • SEO : un moteur de recherche qui ne lit pas le HTML final voit une page vide. Le référencement et le partage sur les réseaux (aperçu, titre, image) en pâtissent.
  • Performance du premier chargement : l'utilisateur attend le téléchargement puis l'exécution d'un gros bundle avant de voir quoi que ce soit. Sur mobile ou réseau lent, l'écran reste blanc.
  • Tout-côté-client : la moindre donnée passe par un appel fetch depuis le navigateur, ce qui expose les clés d'API et multiplie les allers-retours réseau.

La réponse à ces limites tient en un mot : rendre une partie de l'application sur le serveur.

Les modes de rendu : CSR, SSR, SSG, ISR

Il existe plusieurs moments où l'on peut transformer tes composants en HTML. Chacun a son compromis entre fraîcheur des données, vitesse et charge serveur.

Le réflexe : contenu très dynamique et personnalisé (panier, espace connecté) penche vers le SSR ; contenu stable (page « À propos », documentation) penche vers le SSG ; un blog ou un catalogue qui change quelques fois par jour est l'exemple type de l'ISR.

Note

L'hydratation est l'étape où React « rattache » son code interactif au HTML déjà rendu par le serveur. Le visiteur voit le contenu tout de suite, puis l'interactivité (clics, état) s'active quand le JavaScript est chargé.

Les frameworks : Next.js et React Router

React, seul, ne sait faire qu'une chose : transformer des composants en interface. Il ne gère ni le routage serveur, ni la génération de pages, ni le bundling optimisé. C'est le rôle d'un framework bâti sur React. Les deux références aujourd'hui sont Next.js (avec son App Router) et React Router (qui a absorbé Remix).

Leur première idée commune : le routage par fichiers. Plus besoin de déclarer un arbre de <Routes> à la main : l'arborescence de dossiers est la table des routes.

Au-delà du routage, un framework apporte : le rendu serveur (SSR/SSG/ISR clé en main), le chargement de données intégré au rendu, le découpage automatique du bundle par route, et une foule d'optimisations (images, polices, cache). Tu écris du React ; le framework s'occupe de l'infrastructure autour.

Les React Server Components (RSC)

C'est le changement le plus profond de React moderne. Un Server Component s'exécute sur le serveur, jamais dans le navigateur. Conséquences directes : il peut accéder aux données directement (base de données, fichiers, clés secrètes) et il n'envoie aucun JavaScript au client. Par défaut, dans l'App Router de Next.js, tous les composants sont des Server Components.

Mais un Server Component ne peut pas être interactif : pas de useState, pas de useEffect, pas de onClick. Dès qu'il faut de l'interactivité, on passe à un Client Component, signalé par la directive 'use client' tout en haut du fichier.

Le bon modèle mental : Server Components pour la structure et les données, Client Components pour les îlots interactifs. Un Server Component peut importer et afficher un Client Component, le combinant librement.

Deux mécanismes complètent le tableau. Le streaming avec <Suspense> permet d'envoyer la page par morceaux : l'en-tête s'affiche immédiatement pendant qu'une liste lente continue de charger.

Enfin, les Server Actions permettent d'écrire une fonction qui s'exécute sur le serveur, appelée directement depuis un formulaire, sans créer d'API REST à la main.

Cas réel

Un média en ligne était une SPA React + Vite : rapide à développer, mais quasi invisible sur Google. Les articles n'apparaissaient pas dans les résultats de recherche (HTML initial vide), et le partage sur les réseaux affichait un aperçu sans titre ni image. La migration vers Next.js a réglé les deux d'un coup : les pages d'articles passent en SSG/ISR (HTML complet généré au build, régénéré à chaque publication), le référencement décolle et les cartes de partage (Open Graph) se remplissent enfin. Les rares îlots interactifs — bouton « j'aime », commentaires — restent des Client Components ; tout le reste ne coûte aucun JavaScript au navigateur.

Le déploiement

Une SPA Vite se déploie comme un dossier de fichiers statiques sur n'importe quel hébergeur. Une appli avec rendu serveur a besoin, en plus, d'un serveur qui exécute du code à chaque requête. Des plateformes comme Vercel (créateur de Next.js) ou Netlify automatisent tout : tu connectes ton dépôt Git, et chaque push déclenche un build et un déploiement.

Ces plateformes exécutent aussi des edge functions : du code déployé au plus près de l'utilisateur (dans des centaines de localisations) pour un temps de réponse minimal.

React + TypeScript et accessibilité

En production, on type quasi systématiquement ses composants avec TypeScript (vu dans le cours dédié). Typer les props attrape une erreur dès l'écriture, pas en plein navigateur. Les hooks se typent aussi : useState<number>(0) contraint l'état.

L'accessibilité n'est pas une option : utilise les bonnes balises (<button> pour cliquer, <nav>, <main>), associe chaque champ à son <label> via htmlFor, et n'ajoute des attributs aria-* que lorsque le HTML natif ne suffit pas. Une appli rendue côté serveur a justement l'avantage de produire un HTML sémantique complet, lisible par les lecteurs d'écran.

Par où continuer

L'écosystème React bouge vite. Pour rester à jour : suis la documentation officielle de React et celle de Next.js, qui font autorité sur les RSC ; surveille les release notes à chaque version majeure ; et construis de petits projets réels, c'est ce qui ancre le mieux ces notions. Le bon réflexe de veille, c'est d'essayer une idée nouvelle sur un projet jetable avant de l'introduire en production.

Pièges fréquents

Piège fréquent

Tout rendre côté client. Une SPA pure pénalise le SEO et le premier affichage. Si ton site doit être trouvé sur Google ou s'afficher vite, le rendu serveur n'est pas un luxe.

Piège fréquent

Mettre 'use client' partout. Tu perds tout l'intérêt des Server Components (zéro JS, accès direct aux données). Garde les composants en Server par défaut, et n'isole en Client que les vrais îlots interactifs.

Piège fréquent

Appeler un hook client dans un Server Component. Un useState ou un onClick dans un composant sans 'use client' provoque une erreur. Et ne confonds pas SSR (à chaque requête) avec SSG (une fois au build) : ce sont deux fraîcheurs de données différentes. Enfin, n'ignore jamais l'accessibilité, et résiste à la sur-ingénierie : pour un petit outil interne, une SPA Vite suffit largement.

Glossaire

SPA
Single Page Application : le serveur renvoie un HTML quasi vide et le JavaScript peint tout dans le navigateur.
CSR
Client-Side Rendering : le HTML est construit côté client ; simple et interactif, mais pénalisant pour le référencement et le premier affichage.
SSR
Server-Side Rendering : le serveur génère le HTML à chaque requête, puis le client l'hydrate ; données fraîches, bon référencement.
SSG
Static Site Generation : le HTML est produit une fois au build ; ultra-rapide à servir, mais figé jusqu'au prochain build.
ISR
Incremental Static Regeneration : du SSG régénéré périodiquement en arrière-plan ; rapide tout en restant assez frais.
Server Component
Composant exécuté sur le serveur (données directes, secrets, zéro JS envoyé) ; sans état ni gestionnaires d'événements.
Client Component
Composant marqué 'use client', exécuté dans le navigateur ; il porte l'interactivité (état, effets, clics).
Hydratation
Étape où React rattache son code interactif au HTML déjà rendu par le serveur.

Récap et vérification

  • Une SPA pure coince sur le SEO, le premier affichage et l'exposition des données.
  • CSR = client ; SSR = serveur à chaque requête ; SSG = au build ; ISR = statique régénéré périodiquement.
  • Un framework (Next.js, React Router) ajoute routage par fichiers, rendu serveur, chargement de données et bundling.
  • Les Server Components tournent sur le serveur (données directes, zéro JS) ; 'use client' bascule en Client Component pour l'interactivité.
  • Le streaming (Suspense) et les Server Actions complètent le modèle ; le déploiement passe par Vercel/Netlify.
