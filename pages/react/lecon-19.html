Module 06 · React en production — Leçon 19

Les données serveur et React moderne

~37 min Avancé Leçon 18 recommandée

À la fin de cette leçon, tu sauras

  • comprendre pourquoi fetch dans useEffect ne suffit pas (races, cache, refetch) et ce qu'apporte une bibliothèque de data fetching
  • savoir décrire le cache et la revalidation stale-while-revalidate de TanStack Query : clés, mutations, invalidation, optimistic update
  • utiliser les nouveautés React 19 : use(), les Actions avec useActionState, useOptimistic et useFormStatus
  • séparer l'état serveur de l'état client et situer les Server Components dans cette évolution.
Sommaire de la leçon

Tu sais déjà aller chercher des données avec fetch dans un useEffect, gérer un état de chargement et une erreur. Ça marche pour un cas isolé, mais dès qu'une application grandit, ce schéma maison montre ses limites : le même code de chargement se répète partout, rien n'est mis en cache, et les requêtes concurrentes se télescopent. Les données serveur ne sont pas un état comme les autres : elles vivent ailleurs, peuvent changer sans toi, et doivent être synchronisées, pas seulement « stockées ».

Dans cette leçon, on remplace le fetch artisanal par des outils pensés pour l'état serveur (TanStack Query, SWR), on découvre <Suspense> pour le chargement déclaratif, et on plonge dans les nouveautés de React 19 : le hook use(), les Actions de formulaire et l'UI optimiste. On termine en situant les Server Components, qui font le pont vers la leçon suivante.

Le problème du fetch dans useEffect

Reprenons le schéma classique : un effet qui déclenche un fetch et écrit le résultat dans un état. Il fonctionne, mais il accumule des défauts dès qu'on s'en sert sérieusement.

Les ennuis sont structurels. Une race condition : si id passe de 1 à 2, la réponse de 1 peut arriver après celle de 2 et écraser le bon résultat. Aucun cache : deux composants qui demandent le même utilisateur font deux requêtes, et revenir sur une page recharge tout. Aucune revalidation : si la donnée change côté serveur, ton écran reste périmé. Et tu réécris ce trio loading/error/data partout. Gérer la course manuellement demande un drapeau de nettoyage, comme ci-dessous, et ce n'est que le premier des problèmes.

Les bibliothèques de data fetching

TanStack Query (anciennement React Query) et SWR résolvent tout ça d'un coup. Leur idée centrale : l'état serveur mérite un cache dédié, indexé par une clé de requête. Tu décris quoi charger et comment, la bibliothèque gère le reste : déduplication, mises en cache, revalidation, retry automatique.

Le modèle s'appelle stale-while-revalidate : la donnée en cache est affichée immédiatement (même périmée), pendant qu'une requête fraîche part en arrière-plan ; l'écran se met à jour quand elle revient. L'utilisateur ne voit presque jamais un écran de chargement vide.

Pour écrire côté serveur, on utilise une mutation, puis on invalide les clés concernées pour forcer leur revalidation.

On peut aller plus loin avec une mise à jour optimiste : on modifie le cache avant la réponse serveur pour que l'UI réagisse instantanément, et on annule (rollback) si la requête échoue. TanStack Query expose onMutate et onError exactement pour ça. Enfin, le retry automatique relance une requête échouée quelques fois avant d'abandonner. Tout cela explique pourquoi ces bibliothèques remplacent le fetch maison : tu écris la logique métier, pas la plomberie.

Astuce

Choisis tes clés comme des chemins : ["user", id], ["posts", { page }]. Invalider ["user"] touche toutes les sous-clés. Une bonne convention de clés rend le cache prévisible.

Suspense pour les données

<Suspense> déplace l'état de chargement hors du composant : au lieu d'écrire un if (isPending) dans chaque composant, tu déclares un fallback autour d'une zone, et React l'affiche tant que les données ne sont pas prêtes. Le composant enfant, lui, écrit son rendu comme si la donnée était déjà là.

Le rendu du chargement devient déclaratif : la frontière du fallback décrit où un spinner peut apparaître, pas quand. Important : <Suspense> gère le chargement, pas les erreurs. Il faut l'associer à une error boundary (vue à la leçon 17) qui attrape l'échec du chargement.

Le hook use() de React 19

React 19 introduit use(), qui consomme une promesse (ou un contexte) directement dans le rendu. Si la promesse n'est pas résolue, le composant suspend et déclenche le fallback du <Suspense> parent. C'est la pièce qui rend Suspense naturel pour les données.

Note

Ne crée pas la promesse dans le composant qui appelle use() : à chaque rendu tu en obtiendrais une nouvelle, et le composant suspendrait à l'infini. La promesse vient d'un cache ou d'un framework. En pratique, on laisse TanStack Query ou un framework gérer cette plomberie.

Les Actions et useActionState

Pour les formulaires, React 19 introduit les Actions : une fonction asynchrone passée à <form action={...}>. useActionState l'enrobe et te donne l'état retourné, une action à brancher, et un booléen isPending automatique — fini le useState de chargement à la main.

Dans un composant enfant du formulaire, useFormStatus lit l'état de soumission du <form> parent sans prop à faire descendre — pratique pour un bouton réutilisable.

useOptimistic pour une UI instantanée

useOptimistic affiche un résultat provisoire pendant qu'une action s'exécute, puis se cale sur l'état réel quand elle se termine. Il doit être déclenché depuis une action (ou une transition) ; tant que cette action est en cours, l'état optimiste est rendu, et dès qu'elle se termine React revient à l'état réel — donc en cas d'échec, le rollback est géré pour toi sans code dédié.

Note

Le setter ajouterOptimiste doit être appelé dans une action ou un startTransition. Comme une fonction passée à <form action={...}> est déjà enveloppée dans une transition, l'appel y est valide ; hors de ce contexte, l'état optimiste n'apparaîtrait que brièvement.

Cas réel

Une messagerie web souffrait d'un double défaut : à chaque ouverture d'une conversation, la liste des messages était re-fetchée depuis zéro (écran de chargement à chaque clic), et l'envoi d'un message attendait l'aller-retour serveur avant de l'afficher — impression de lenteur permanente. La bascule vers TanStack Query a supprimé les rechargements inutiles (cache par clé ["conversation", id], stale-while-revalidate), et useOptimistic fait apparaître le message envoyé instantanément, marqué « envoi… », avec rollback automatique si le serveur refuse. Ressenti : une application qui répond au doigt, alors que le réseau, lui, n'a pas changé.

Le rapport avec les Server Components

Tout ce qu'on vient de voir prépare le terrain des Server Components, qui s'exécutent côté serveur et peuvent charger leurs données avant d'envoyer le HTML — souvent sans useEffect ni même de bibliothèque côté client. Avec eux, un composant peut être async et faire son await fetch(...) directement.

L'idée à retenir : use(), <Suspense> et les Actions ne sont pas que des gadgets côté client, ce sont les briques d'un modèle où serveur et client collaborent. TanStack Query reste pleinement pertinent pour l'état serveur côté client ; les Server Components couvrent surtout le chargement initial.

Bonnes pratiques

Quelques principes pour ne pas se tromper. Sépare l'état serveur de l'état client : l'URL d'un utilisateur, sa liste de messages, c'est de l'état serveur (cache, revalidation) ; un menu ouvert ou un champ en cours de saisie, c'est de l'état client (useState). Les mélanger crée des bugs de synchronisation. Gère toujours chargement et erreur, idéalement via <Suspense> et une error boundary. Enfin, ne sur-fetch pas : règle staleTime pour éviter les requêtes inutiles, et ne recharge pas une donnée déjà fraîche en cache.

Pièges fréquents

Piège fréquent

Utiliser fetch dans useEffect pour tout, et réinventer un cache à la main. Au-delà d'un cas trivial, tu reconstruis mal ce que TanStack Query fait bien. Autres erreurs classiques : ne pas gérer les races (réponses dans le désordre) ; déclencher un refetch en boucle en mettant un objet recréé à chaque rendu dans les dépendances de l'effet ; mettre un <Suspense> sans error boundary (un échec de chargement casse l'app) ; faire une mise à jour optimiste sans rollback (l'UI ment quand la requête échoue) ; et mélanger état serveur et état client dans le même useState.

Glossaire

État serveur
Données appartenant au backend : à synchroniser (cache, revalidation), pas seulement à stocker.
Race condition
Deux requêtes concurrentes dont les réponses arrivent dans le désordre ; la plus lente peut écraser la bonne si rien ne la neutralise.
Clé de requête
Identité d'une donnée dans le cache (ex. ["user", id]) : deux composants qui la partagent ne déclenchent qu'une requête.
stale-while-revalidate
Stratégie qui affiche la donnée en cache (même périmée) tout de suite, puis la revalide en arrière-plan.
Invalidation
Marquer une clé comme périmée après une écriture pour forcer sa revalidation (invalidateQueries).
use()
Hook React 19 qui consomme une promesse (ou un contexte) dans le rendu ; suspend tant qu'elle n'est pas résolue.
Action
Fonction asynchrone passée à <form action={…}> ; useActionState l'enrobe et fournit isPending.
Mise à jour optimiste
Afficher le résultat attendu avant la réponse serveur (useOptimistic), avec retour à l'état réel en cas d'échec.

Récap et vérification

  • Le fetch dans useEffect souffre de races, d'absence de cache et de refetch non maîtrisés ; il ne passe pas à l'échelle.
  • TanStack Query / SWR apportent cache par clé, revalidation stale-while-revalidate, mutations + invalidation, optimistic update et retry.
  • <Suspense> rend le chargement déclaratif via un fallback ; il s'associe à une error boundary pour les échecs.
  • React 19 ajoute use() (consommer une promesse/un contexte), les Actions + useActionState, useFormStatus et useOptimistic.
  • Sépare état serveur et état client ; les Server Components prolongent ce modèle côté serveur.
