useRef et useContext

~35 min Avancé Module 3 recommandé

À la fin de cette leçon, tu sauras

  • utiliser useRef pour référencer un nœud du DOM (donner le focus, mesurer) via ref et .current ;
  • stocker une valeur mutable persistante (id de minuteur, valeur précédente) sans déclencher de re-rendu, et distinguer ref et state ;
  • partager des données transverses (thème, utilisateur connecté) avec createContext, un Provider et useContext pour éviter le prop drilling ;
  • reconnaître quand le contexte est adapté et anticiper ses limites de re-rendu.
Sommaire de la leçon

Tu sais maintenant gérer l'état avec useState et les effets avec useEffect. Mais l'état n'est pas le seul outil : parfois tu veux garder une valeur entre les rendus sans que l'interface se redessine, ou accéder directement à un élément du DOM. Et parfois tu veux partager une donnée à travers toute l'application sans la faire transiter de composant en composant. Deux hooks répondent à ces besoins : useRef et useContext.

Ce sont des outils du quotidien. useRef te donne une « boîte » mutable et discrète ; useContext te donne un canal de diffusion pour les données globales. On les prend l'un après l'autre, avec des exemples concrets.

useRef : une boîte mutable qui persiste

useRef crée un objet stable, le même à chaque rendu, avec une unique propriété : .current. Tu peux y écrire et y lire ce que tu veux. Sa particularité : modifier .current ne déclenche aucun re-rendu. C'est exactement l'inverse de l'état. On écrit dans .current depuis un gestionnaire d'événement ou un effet, jamais pendant le rendu.

On distingue deux usages bien distincts : (1) pointer vers un nœud du DOM, et (2) mémoriser une valeur mutable hors de l'état. Voyons-les séparément.

Référencer un nœud du DOM

L'usage le plus courant : obtenir une référence vers un véritable élément du DOM pour agir dessus impérativement — lui donner le focus, le faire défiler, le mesurer. La recette tient en trois temps : créer une ref, l'attacher avec l'attribut ref, puis lire .current.

Après le montage, React remplit champ.current avec le nœud DOM réel. Tu peux alors appeler les méthodes natives du DOM (focus(), scrollIntoView(), select()…). Avant le montage, et si l'élément est retiré, .current vaut null — d'où l'initialisation à null.

Astuce

Pour donner le focus dès l'affichage (et non au clic), combine la ref avec un useEffect au montage : useEffect(() => { champ.current.focus(); }, []);. L'effet s'exécute après que React a relié la ref au DOM.

Stocker une valeur mutable sans re-rendu

Deuxième usage : garder une valeur entre les rendus quand cette valeur ne concerne pas l'affichage. Cas typiques : l'identifiant renvoyé par setInterval (pour pouvoir l'annuler plus tard) ou la valeur précédente d'une prop. Une variable locale serait réinitialisée à chaque rendu ; une ref, elle, survit.

Ici, secondes est de l'état (il s'affiche, donc il doit rendre l'UI), tandis que idMinuteur est une ref (un détail technique invisible). Si on avait stocké l'id dans useState, chaque mise à jour de cet id aurait inutilement re-rendu le composant.

ref ou state ? La bonne question

La règle de décision tient en une phrase : est-ce que ce changement doit redessiner l'interface ? Si oui, c'est de l'état (useState). Si non, c'est une ref (useRef).

Autre différence pratique : l'état se met à jour de façon asynchrone (la nouvelle valeur apparaît au rendu suivant), alors qu'une ref se modifie immédiatement et de manière synchrone. C'est précisément ce qui rend la ref adaptée aux valeurs qu'on lit ou écrit en dehors du cycle de rendu, dans des gestionnaires d'événements ou des effets.

Note

Une ref n'est pas une faille pour contourner l'état. Quand l'affichage dépend d'une donnée, passe par useState : c'est ce qui garantit que l'UI reste le reflet fidèle de tes données.

useContext : partager sans prop drilling

Quand une donnée (le thème, l'utilisateur connecté, la langue) doit être lue par beaucoup de composants à des profondeurs variées, la passer en props de parent en enfant devient pénible : c'est le prop drilling. Des composants intermédiaires reçoivent et retransmettent une prop qui ne les concerne pas.

Le contexte résout ça : il crée un canal de diffusion. Un Provider fournit une value en haut de l'arbre, et n'importe quel descendant la lit avec useContext, sans intermédiaire. La recette : createContext pour créer le contexte, un Provider pour le fournir, useContext pour le consommer.

Quand le contexte est adapté (et ses limites)

Le contexte brille pour les données transverses et rarement modifiées : thème, utilisateur authentifié, langue, préférences. Ce sont des informations dont beaucoup d'écrans ont besoin mais qui changent peu souvent.

Sa limite tient au re-rendu : chaque fois que la value du Provider change, tous les composants qui consomment ce contexte se re-rendent. Si tu places dans un même contexte une donnée qui change à chaque frappe au clavier, tu provoques une cascade de re-rendus dans toute l'application. Le contexte n'est donc pas un substitut universel à l'état local ni à un passage de props ponctuel.

En séparant les contextes selon ce qui change ensemble, tu limites les re-rendus aux seuls composants réellement concernés.

Pièges fréquents

Piège fréquent

Utiliser useRef là où il faut un état. Si tu modifies ref.current en espérant voir l'écran changer, rien ne se passe : aucun re-rendu n'est déclenché. Pour une valeur affichée, c'est useState.

  • Lire ou écrire ref.current pendant le rendu. Au premier rendu d'un nœud DOM, la ref vaut encore null (React ne l'a pas reliée). Manipule-la dans un gestionnaire d'événement ou un useEffect, jamais dans le corps du composant pendant le rendu.
  • Oublier le Provider. Sans Provider au-dessus, useContext renvoie la valeur par défaut passée à createContext. Si cette valeur est mal choisie (par exemple null), tu obtiens une erreur surprenante. Choisis une valeur par défaut sensée, et n'oublie pas d'envelopper l'arbre.
  • Tout mettre dans un seul contexte. Un contexte fourre-tout re-rend tous ses consommateurs au moindre changement. Découpe par domaine et par fréquence de mise à jour.
  • Muter l'objet d'une ref pour de l'état dérivé affiché. Une ref n'avertit pas React ; l'écran reste figé jusqu'au prochain re-rendu provoqué par autre chose.

Pour aller plus loin

Pour aller plus loin

Pour exposer une ref depuis un composant enfant vers son parent, regarde forwardRef et useImperativeHandle (en React 19, ref devient même une prop ordinaire). Côté contexte, explore l'imbrication de plusieurs Providers, l'optimisation des re-rendus (mémoïsation de la value), et les bibliothèques de gestion d'état (Zustand, Redux Toolkit) lorsque le contexte montre ses limites sur des données très changeantes.

Cas réel

Deux besoins très concrets d'une vraie application illustrent ces hooks. D'abord l'autofocus : à l'ouverture d'une fenêtre modale ou d'un formulaire de connexion, on place le curseur dans le premier champ pour que l'utilisateur tape sans cliquer — c'est un useRef sur l'input, appelé dans un useEffect au montage. Ensuite l'utilisateur connecté : son nom, son avatar et ses droits sont nécessaires dans le header, le menu, la page de profil, partout. On les met dans un AuthContext fourni en haut de l'application ; chaque écran les lit par useContext sans qu'on ait à les faire descendre en props sur dix niveaux. La plupart des applications React ont ainsi un ThemeContext et un AuthContext proches de la racine.

Antisèche

Glossaire

useRef
Hook renvoyant un objet stable { current } qui persiste entre les rendus ; modifier .current ne déclenche pas de re-rendu.
.current
Unique propriété d'une ref : contient la valeur mémorisée ou, pour une ref de DOM, le nœud réel après le montage.
Attribut ref
Attribut posé sur un élément JSX (ref={maRef}) qui relie le nœud DOM à la ref une fois l'élément monté.
ref vs state
Règle de choix : si le changement doit redessiner l'UI → useState ; sinon (valeur technique invisible) → useRef.
createContext
Crée un contexte avec une valeur par défaut ; renvoie un objet portant .Provider et lisible par useContext.
Provider
Composant <Ctx.Provider value={…}> qui diffuse une valeur à tous ses descendants.
useContext
Hook qui lit la value du Provider le plus proche ; le composant se re-rend quand cette valeur change.
Prop drilling
Transmission d'une prop à travers des niveaux qui ne l'utilisent pas ; ce que le contexte permet d'éviter.

Récap et vérification

  • useRef crée une boîte { current } stable entre les rendus ; écrire dans .current ne re-rend pas.
  • Usage 1 — référencer un nœud du DOM : ref={maRef} sur l'élément, puis maRef.current pour agir (focus, mesure).
  • Usage 2 — mémoriser une valeur mutable invisible (id de minuteur, valeur précédente) sans déclencher de rendu.
  • Choix ref vs state : si le changement doit redessiner l'UI, c'est de l'état ; sinon, une ref.
  • useContext + createContext + Provider partagent des données transverses sans prop drilling ; attention aux re-rendus quand la value change.

Vérifie ta compréhension

  1. Pourquoi modifier ref.current ne met-il pas l'interface à jour, contrairement à un setState ?
  2. Dans quel ordre relie-t-on une ref à un <input>, et où peut-on lire .current sans risque ?
  3. Que renvoie useContext si aucun Provider n'enveloppe le composant ?
