Module 04 · Hooks avancés & application — Leçon 14

Organiser une application & bonnes pratiques

~35 min Avancé Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • structurer un projet React avec Vite (dossiers components/, hooks/, point d'entrée) et la règle « un composant = un fichier » ;
  • découper une interface en composants présentation vs conteneur et placer l'état au bon endroit (colocation) ;
  • appliquer les bonnes pratiques React (clés stables, état minimal et dérivé, accessibilité, nommage) et éviter les rendus inutiles ;
  • situer l'écosystème (routage, state management, data fetching, tests, TypeScript) et choisir tes prochaines pistes d'apprentissage.
Sommaire de la leçon

Tu connais désormais les composants, les props, l'état, les événements, les listes et les hooks. Il reste une compétence décisive : assembler tout ça en une vraie application, organisée et maintenable. Cette leçon fait la synthèse du cours et te donne les réflexes d'architecture qui distinguent un code de débutant d'un code de production.

On va voir comment démarrer un projet moderne, comment découper l'interface, où ranger l'état, comment naviguer entre des pages, puis une checklist de bonnes pratiques, quelques leviers de performance et un tour d'horizon de l'écosystème. À la fin, tu sauras vers quoi continuer.

La structure d'un projet

En production, on n'écrit pas React dans un seul fichier : on s'appuie sur un outil de build moderne comme Vite. Il transpile le JSX, fournit un serveur de développement rapide avec rechargement à chaud, et génère un bundle optimisé pour la mise en ligne. On crée un projet d'une commande :

L'arborescence typique sépare clairement les responsabilités. Un principe simple guide tout : un composant = un fichier, nommé comme le composant.

Le point d'entrée (main.jsx) ne fait qu'une chose : attacher le composant racine au DOM. Tout le reste est de la composition à partir de là.

Note

Cette arborescence n'est pas imposée par React : c'est une convention. L'essentiel est la cohérence : un nouvel arrivant doit deviner où trouver un composant ou un hook sans poser de question.

Découper l'UI en composants

Un bon composant est petit, fait une seule chose et porte un nom qui le décrit. Quand un composant dépasse une centaine de lignes ou mélange plusieurs préoccupations, c'est le signal qu'il faut le scinder.

Une distinction utile : les composants de présentation (comment ça s'affiche, ils reçoivent tout par props) et les composants conteneurs (où vit l'état et la logique). Le conteneur orchestre, la présentation se contente d'afficher :

Où placer l'état ? Règle d'or : la colocation. Garde chaque état au plus près de l'endroit où il sert. Si un seul composant en a besoin, il reste local. Si plusieurs frères doivent le partager, fais-le remonter vers leur parent commun le plus proche — pas plus haut. Un état placé trop haut alourdit inutilement tout l'arbre.

Le routage côté client

Une application réelle a plusieurs « pages » : accueil, détail, profil… Plutôt que de recharger le navigateur à chaque fois, on fait du routage côté client : la bibliothèque React Router change le composant affiché selon l'URL, sans rechargement, ce qui donne des transitions instantanées.

L'idée à retenir : une URL correspond à un composant. Tu déclares la correspondance une fois, React Router se charge d'afficher le bon élément selon l'adresse courante. On ne détaille pas tout ici ; c'est une vue d'ensemble pour savoir que ça existe.

Les bonnes pratiques

Quelques principes reviennent dans tout code React solide. D'abord, les clés stables sur les listes : une key doit identifier la donnée (un id), jamais l'index du tableau si la liste peut changer d'ordre.

Ensuite, l'état minimal et dérivé calculé : ne stocke dans l'état que ce qui ne peut pas être recalculé. Tout ce qui découle d'un autre état se calcule au rendu, sans useState ni useEffect supplémentaire.

Enfin, des handlers propres (nommés handleClick, onToggle…), l'accessibilité de base (vrais <button> pour les actions, <label> liés aux champs, attributs aria-* quand nécessaire) et un nommage explicite : composants en PascalCase, hooks préfixés par use.

La performance

React est rapide par défaut. La première règle de performance est donc : mesure avant d'optimiser, avec le React DevTools Profiler. La plupart des applications n'ont besoin d'aucune optimisation manuelle.

Quand un rendu coûteux se répète inutilement, trois outils existent. memo évite de re-rendre un composant dont les props n'ont pas changé ; useMemo mémorise un calcul lourd ; useCallback stabilise une fonction passée en prop.

Pour les grosses applications, le découpage de code (code splitting) charge une partie de l'interface seulement quand on en a besoin. lazy et <Suspense> permettent de charger un composant à la demande tout en affichant un repli pendant le chargement :

Astuce

N'enrobe pas tout de memo/useMemo « au cas où ». La mémoïsation a un coût et complique le code. Ne l'ajoute que lorsque le Profiler montre un vrai problème.

L'écosystème

React reste volontairement une bibliothèque centrée sur l'UI. Autour, un écosystème mûr couvre le reste des besoins d'une application :

  • State management : pour un état partagé largement, le Context de React suffit souvent ; au-delà, des outils comme Zustand ou Redux Toolkit structurent un état global.
  • Data fetching : TanStack Query (React Query) gère le chargement, le cache et la resynchronisation des données serveur, en évitant des useEffect fragiles.
  • Tests : React Testing Library teste les composants comme un utilisateur les utilise (ce qui s'affiche, pas les détails internes).
  • TypeScript : typer les props et l'état attrape des erreurs avant l'exécution et documente le code.

Tu n'as pas besoin de tout adopter d'un coup. Chaque outil répond à un problème précis : ajoute-le quand ce problème se présente vraiment, pas avant.

Et après

Félicitations : tu maîtrises maintenant React moderne — composants fonction, props, état, événements, listes et hooks, plus les réflexes d'architecture pour assembler une vraie application. C'est une base solide et recherchée.

Pour continuer, choisis selon tes projets : approfondis React Router pour des applications multi-pages, adopte un gestionnaire d'état ou TanStack Query quand l'état grandit, ajoute TypeScript pour fiabiliser ton code, explore Next.js pour le rendu serveur et le routage par fichiers, et installe une habitude de tests avec React Testing Library. Le meilleur apprentissage reste de construire : lance un projet qui te tient à cœur, et fais-le grandir.

Checklist de bonnes pratiques

Note

Garde cette liste sous la main quand tu relis ton code : elle résume l'essentiel d'un projet React sain.

  • Composants en PascalCase, un par fichier, petits et focalisés sur une seule responsabilité.
  • Hooks appelés au sommet du composant, jamais dans une condition ou une boucle ; hooks personnalisés préfixés par use.
  • État immuable : jamais de mutation directe, toujours une nouvelle copie ({ ...obj }, [...arr]).
  • Clés stables sur les listes (un id), pas l'index si l'ordre peut changer.
  • État minimal : ce qui peut être dérivé se calcule au rendu, pas dans un useState.
  • Colocation : l'état vit au plus près de son usage ; on ne le fait remonter qu'en cas de partage.
  • Accessibilité : vrais <button>, <label> liés aux champs, alternatives textuelles.
  • Effets justifiés : useEffect seulement pour la synchronisation externe, avec un tableau de dépendances correct.
  • Mesure avant optimisation : profile d'abord, mémoïse ensuite, et seulement si nécessaire.

Pour aller plus loin

Pour aller plus loin

Au-delà des applications « côté client », des frameworks comme Next.js ou Remix ajoutent le rendu côté serveur, le routage par fichiers et les React Server Components : des composants qui s'exécutent sur le serveur pour réduire le JavaScript envoyé au navigateur. C'est la direction que prend React 19 pour les applications les plus exigeantes.

Cas réel

Sur un tableau de bord d'entreprise, l'équipe part d'un composant Dashboard de 600 lignes qui mêle appels réseau, filtres, tri et affichage. Le refactor suit exactement cette leçon : on extrait un conteneur DashboardData (état + useFetch), des composants de présentation (KpiCard, Chart, Table) qui ne reçoivent que des props, un hook useFilters partagé, et on isole le graphique lourd derrière lazy. Résultat concret : le bundle initial repasse sous les 200 Ko, chaque composant se teste seul, et un nouvel arrivant retrouve n'importe quelle pièce en quelques secondes. Ce sont ces réflexes — pas de nouvelles API — qui distinguent un code maintenable d'un code qui fait peur.

Glossaire

Vite
Outil de build moderne : serveur de dev rapide, rechargement à chaud, bundle optimisé pour la production.
Composant conteneur
Composant qui détient l'état et la logique et passe les données à ses enfants ; il orchestre.
Composant de présentation
Composant qui reçoit tout par props et se contente d'afficher, sans état propre ; facile à tester et réutiliser.
Colocation
Placer chaque état au plus près de son usage ; ne le faire remonter au parent commun que s'il est partagé.
État dérivé
Valeur calculée à partir d'un autre état pendant le rendu (un total, un filtrage) : à ne pas stocker dans un useState.
memo
Enveloppe un composant pour éviter son re-rendu tant que ses props n'ont pas changé.
Code splitting
Découper le bundle pour ne télécharger le code d'une partie de l'UI qu'au moment où on en a besoin (lazy + <Suspense>).
React Router
Bibliothèque de routage côté client : associe une URL à un composant sans recharger la page.

Récap et vérification

  • Un projet moderne s'amorce avec Vite ; on range les composants, hooks et pages dans des dossiers dédiés, à raison d'un composant par fichier.
  • On découpe l'UI en composants petits et réutilisables (présentation vs conteneur), et on place l'état au plus près de son usage (colocation).
  • React Router gère la navigation entre pages sans recharger : une URL ↔ un composant.
  • Les bonnes pratiques (clés stables, état minimal et dérivé, accessibilité, nommage) priment ; on optimise la performance seulement après mesure.
  • L'écosystème (state management, data fetching, tests, TypeScript, Next.js) s'adopte au besoin.

  2. Pourquoi vaut-il mieux dériver une valeur au rendu plutôt que la stocker dans un useState ?
