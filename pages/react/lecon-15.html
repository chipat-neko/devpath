Le routage avec React Router

~35 min Intermédiaire Cours React recommandé

À la fin de cette leçon, tu sauras

  • savoir configurer le routage d'une SPA avec createBrowserRouter et <RouterProvider> (ou <BrowserRouter>) ;
  • savoir naviguer sans rechargement avec <Link>, <NavLink> et useNavigate ;
  • savoir lire les paramètres d'URL avec useParams et les paramètres de requête avec useSearchParams ;
  • savoir composer des routes imbriquées avec <Outlet> et prévoir une route 404.
Sommaire de la leçon

Jusqu'ici tes composants vivaient dans une seule « page ». Mais une vraie application a plusieurs vues : un accueil, une liste, une fiche de détail, une page « à propos ». En React, on ne change pas de fichier HTML pour passer de l'une à l'autre : on fait du routage côté client. C'est le rôle de React Router, la bibliothèque de référence pour relier l'URL affichée dans la barre d'adresse à l'arbre de composants rendu à l'écran.

Cette leçon part du principe que tu maîtrises déjà les composants fonction, useState et les hooks. On ne réexplique pas le rendu : on ajoute une couche, la navigation. Le code montré suppose le paquet react-router-dom installé ; il ne s'exécute pas dans l'éditeur du site (React demande un build), donc lis-le comme une description du comportement attendu.

Le problème : une seule page HTML, plusieurs vues

Une application React est une SPA (single-page application) : le serveur n'envoie qu'un fichier index.html et un bundle JavaScript. Si tu écris un lien <a href> classique, le navigateur recharge toute la page : il redemande le HTML, recharge le bundle, et ton état React est perdu. L'expérience devient lente et clignotante.

Le routage côté client résout cela : une bibliothèque intercepte la navigation, met à jour l'URL via l'API History du navigateur, et rend une vue différente sans recharger. L'utilisateur a l'impression de changer de page ; en réalité, React remplace seulement les composants affichés.

Note

« Sans recharger » ne veut pas dire « sans changer d'URL ». L'URL change bien (et reste partageable, et le bouton « retour » fonctionne) ; c'est seulement le rechargement complet du document qui est évité.

Configurer le routeur

L'approche moderne de React Router (v6.4+, jusqu'à la v7) s'appuie sur createBrowserRouter, qui décrit les routes sous forme de données, puis <RouterProvider> qui les branche sur l'application. Chaque route associe un path à un element (le composant à rendre).

Quand l'URL vaut /, React rend <Accueil /> ; quand elle vaut /a-propos, il rend <APropos />. Aucun rechargement.

Il existe aussi la forme historique en JSX, avec <BrowserRouter> qui englobe un bloc <Routes> contenant des <Route>. Elle reste valable et tu la croiseras souvent.

Même résultat ; createBrowserRouter est privilégié car il débloque les data routers (loaders/actions, abordés plus bas).

Naviguer : Link, NavLink, useNavigate

Pour proposer un lien, on n'utilise jamais <a href> entre deux vues de l'app : on utilise <Link>. En interne, <Link> rend bien une balise <a> accessible, mais intercepte le clic pour naviguer côté client, sans rechargement.

L'attribut s'appelle to, pas href. Le clic change l'URL et la vue, sans recharger le document.

Quand tu veux marquer le lien actif (celui de la page courante), utilise <NavLink> : il fournit un booléen isActive que tu exploites pour la classe CSS.

className reçoit une fonction : React Router lui passe { isActive } et tu renvoies la chaîne de classes adaptée. (Pour to="/", pense à l'option end afin que le lien ne reste pas « actif » sur toutes les sous-routes.)

Parfois la navigation ne vient pas d'un clic sur un lien mais d'une action : après l'envoi d'un formulaire, après une connexion réussie. Le hook useNavigate te donne une fonction pour naviguer par code.

naviguer(-1) revient en arrière, comme le bouton « précédent » ; { replace: true } remplace l'entrée d'historique au lieu d'en ajouter une — pratique après un login, pour que « retour » ne ramène pas au formulaire.

Les paramètres d'URL : useParams et useSearchParams

Une fiche de détail a une URL dynamique : /users/42, /users/77… On déclare un segment variable avec un deux-points dans le path, puis on le lit avec useParams.

Le nom de la clé (id) correspond exactement au nom déclaré après le deux-points (:id).

Pour les paramètres de requête (la partie après ?, comme /recherche?q=react&page=2), on utilise useSearchParams, qui fonctionne comme un useState dédié à la query string.

Taper dans le champ met à jour l'URL (?q=…) : la recherche devient partageable et survit à un rechargement.

Routes imbriquées et <Outlet>

Souvent, plusieurs vues partagent une même enveloppe : un en-tête, un menu, un pied de page. Plutôt que de répéter ce layout dans chaque composant, on imbrique les routes : une route parente rend la coquille commune, et l'emplacement où afficher la route enfant est marqué par <Outlet>.

L'en-tête et le pied restent affichés ; seul le contenu de <Outlet /> change selon l'URL. index: true désigne la route enfant par défaut du parent.

La route 404 et un mot sur les data routers

Que se passe-t-il si l'utilisateur tape une URL inexistante ? Sans rien prévoir, l'écran reste vide. On ajoute une route « attrape-tout » avec path: "*", placée comme enfant du layout, qui correspond à tout ce qui n'a pas déjà matché.

Le segment * a la priorité la plus faible : React Router choisit toujours la route la plus spécifique d'abord, donc * ne capture que ce qui reste.

Avec createBrowserRouter, chaque route peut aussi déclarer un loader (charger les données avant d'afficher la vue, plutôt que dans un useEffect après le rendu) et une action (traiter l'envoi d'un formulaire). On parle de data router. C'est puissant pour éviter les écrans de chargement en cascade, mais ce n'est pas indispensable pour démarrer : retiens d'abord Link, useParams et Outlet.

Le lien avec l'API History

Tu te souviens de l'API History du navigateur (cours HTML avancé) : history.pushState et history.replaceState changent l'URL et l'historique sans recharger, et l'événement popstate détecte le bouton « retour ». React Router est exactement une couche au-dessus de cette API : <Link> appelle pushState pour toi, et useNavigate(-1) revient en arrière comme un popstate. Tu n'as donc pas à manipuler window.history à la main : la bibliothèque le fait, et garde React synchronisé avec l'URL.

Pièges fréquents

Piège fréquent

Utiliser <a href="/a-propos"> au lieu de <Link to="/a-propos"> : le navigateur recharge toute l'application, perd l'état React et annule l'intérêt de la SPA. Entre deux vues internes, c'est toujours <Link> ou <NavLink>. Le <a> brut reste réservé aux liens externes.

Piège fréquent

Oublier <Outlet /> dans un layout : la coquille s'affiche, mais les routes enfants restent invisibles, car React ne sait pas où les insérer. Si tes pages « disparaissent » sous un layout, vérifie d'abord la présence de l'Outlet.

Piège fréquent

Croire que l'ordre source des routes fixe la priorité, et oublier la 404. Depuis la v6, React Router classe les routes par spécificité (la plus précise gagne), pas par ordre d'écriture ; tu n'as donc pas à ranger path: "*" en dernier « à la main ». En revanche, si tu ne déclares pas de path: "*", les URL inconnues n'affichent rien. Prévois toujours une page « introuvable ».

Pour aller plus loin

Pour aller plus loin

Quatre prolongements naturels : les data routers (loaders/actions) pour charger les données au niveau de la route ; le code splitting par route avec React.lazy et <Suspense>, pour ne télécharger le code d'une page qu'au moment où on y va ; les routes protégées, où un composant garde vérifie l'authentification et redirige avec <Navigate> si l'utilisateur n'est pas connecté ; et enfin Next.js, un framework qui propose un routage par fichiers (l'arborescence des dossiers définit les URL) et le rendu côté serveur.

Cas réel

Sur une boutique en ligne, chaque fiche produit vit à une URL partageable comme /produits/casque-audio-42 : on la copie dans un message, on la met en favori, un moteur de recherche l'indexe. La fiche lit son identifiant avec useParams, tandis que les filtres du catalogue (/catalogue?tri=prix&page=2) passent par useSearchParams — si bien qu'un rechargement, ou un lien envoyé à un ami, rouvre exactement la même sélection. Après un paiement réussi, useNavigate("/merci", { replace: true }) évite qu'un clic sur « retour » ne repasse par le formulaire de paiement. C'est ce trio — Link, paramètres d'URL, navigation par code — qui donne à une SPA le confort d'un vrai site multi-pages.

Antisèche

Glossaire

SPA
Single-page application : une seule page HTML et un bundle JS ; les vues changent côté client sans rechargement du document.
Routage côté client
Afficher une vue différente selon l'URL en manipulant l'historique du navigateur, sans redemander le document au serveur.
createBrowserRouter
Décrit les routes sous forme de données (path → element) et débloque les data routers (loaders/actions) ; branché par <RouterProvider>.
<Link> / <NavLink>
Rendent un <a> accessible mais interceptent le clic pour naviguer sans recharger ; NavLink expose isActive pour styliser le lien courant.
useNavigate
Hook renvoyant une fonction pour naviguer par code (après un envoi de formulaire, un login) ; { replace: true } remplace l'entrée d'historique.
useParams
Lit les segments dynamiques du chemin (:id) ; les valeurs renvoyées sont toujours des chaînes.
useSearchParams
Lit et écrit la chaîne de requête (après ?), à la manière d'un useState dédié à l'URL.
<Outlet>
Emplacement, dans une route parente, où React Router insère la route enfant active ; permet un layout partagé.

Récap et vérification

  • Une SPA n'a qu'une page HTML ; le routage côté client affiche des vues différentes selon l'URL, sans recharger.
  • On configure avec createBrowserRouter + <RouterProvider> (ou <BrowserRouter> / <Routes> / <Route>).
  • On navigue avec <Link>, on marque l'actif avec <NavLink>, et on redirige par code avec useNavigate — jamais avec <a href> en interne.
  • useParams lit les segments dynamiques (:id) ; useSearchParams lit et écrit la query string.
  • <Outlet> rend la route enfant dans un layout partagé ; path: "*" gère la 404.

Vérifie ta compréhension

  1. Pourquoi un <a href> interne casse-t-il l'intérêt d'une SPA, là où <Link> ne le fait pas ?
  2. Que se passe-t-il si un layout n'inclut pas <Outlet />, et pourquoi ?
  3. Quelle est la différence entre useParams et useSearchParams, et pour quelle forme d'URL chacun ?
