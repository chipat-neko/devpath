Stockage & bases gérées

~35 min Intermédiaire Leçon 02

À la fin de cette leçon, tu sauras

  • distinguer stockage objet, bloc et fichier ;
  • tirer parti du stockage objet ;
  • choisir une base gérée (SQL ou NoSQL) ;
  • éviter les pièges de coûts du stockage.
Sommaire de la leçon

Une application doit ranger des données : des fichiers (images, documents) et des données structurées (utilisateurs, commandes). Le cloud propose, pour chaque besoin, un service géré qui s'occupe de la durabilité, des sauvegardes et de la mise à l'échelle. Encore faut-il choisir le bon.

Trois familles de stockage

  • Stockage objet : pour des fichiers (images, vidéos, sauvegardes), à très grande échelle, accessibles par API/URL. Le plus courant dans le cloud.
  • Stockage bloc : un disque attaché à une machine virtuelle (comme un disque dur), pour le système et les bases auto-gérées.
  • Stockage fichier : un partage réseau monté par plusieurs machines (comme un lecteur réseau).

Le bon outil pour le bon usage

Pour les fichiers téléversés d'une application (photos, PDF), c'est presque toujours le stockage objet : durable, peu cher, infiniment extensible, servi via URL (souvent derrière un CDN). On ne stocke pas ça « sur le disque du serveur ».

Le stockage objet en pratique

On range les fichiers dans des conteneurs (souvent appelés buckets), chaque fichier ayant une clé (son chemin). Le service garantit une très grande durabilité (copies multiples) et propose des classes de stockage : standard pour l'accès fréquent, « archive » bien moins cher pour ce qu'on consulte rarement.

Les bases de données gérées

Plutôt que d'installer et d'exploiter une base soi-même (sauvegardes, mises à jour, réplication…), on prend une base gérée : le fournisseur s'occupe de tout cela. On choisit selon le besoin :

  • Relationnelle (SQL) gérée : données structurées et reliées, transactions, requêtes riches (revoir le cours SQL).
  • NoSQL gérée : flexibilité du schéma, montée en charge horizontale, accès par clé très rapide (revoir le cours NoSQL).

Géré = moins d'exploitation

Une base gérée t'évite les sauvegardes manuelles, les mises à jour de version, la configuration de la réplication. Tu gagnes en sérénité ; en échange, tu as moins de contrôle fin et tu dépends du fournisseur. Pour une petite équipe, c'est presque toujours le bon choix.

Cache et messages (en bref)

Deux services gérés très utiles complètent souvent l'ensemble : un cache en mémoire (type Redis) pour accélérer les lectures fréquentes, et une file de messages pour faire communiquer des composants de façon asynchrone (envoyer un e-mail « plus tard », traiter en arrière-plan).

Un cas concret

Cas réel

Longtemps, faire sortir ses données d'un cloud coûtait cher — assez pour dissuader de partir chez un concurrent. Ces frais de sortie (egress) sont devenus un sujet de concurrence et de réglementation : en 2024, dans le sillage du Data Act européen, les grands fournisseurs (AWS, Google Cloud, Azure) ont annoncé la gratuité du transfert sortant pour les clients qui migrent vers un autre hébergeur. La morale pour l'architecte : le coût de sortie fait partie du choix d'un service — pense « réversibilité » dès le départ, pas seulement au prix affiché du Go stocké.

Pièges fréquents

  • Stocker les fichiers sur le disque du serveur. Ils disparaissent si l'instance est recréée ; utilise le stockage objet.
  • Choisir SQL ou NoSQL par mode. Choisis selon la forme des données et les requêtes, pas la hype.
  • Oublier les frais de sortie (egress). Transférer des données hors du cloud est souvent facturé — parfois la surprise de la facture.
  • Mauvaise classe de stockage. Payer le tarif « accès fréquent » pour des archives consultées une fois par an.

Pour aller plus loin

La sauvegarde et la réplication sont des fonctions à activer et à tester : une sauvegarde qu'on n'a jamais restaurée n'est pas une sauvegarde. Les services gérés facilitent ces tâches, mais c'est à toi de définir la fréquence et la rétention adaptées à tes données.

Pour aller plus loin

Le coût du stockage a trois composantes souvent : l'espace occupé, le nombre de requêtes, et le transfert sortant. Lis bien la tarification : un stockage « pas cher au Go » peut coûter cher si on y accède énormément.

Glossaire

Stockage objet
Service qui range des fichiers dans des conteneurs (buckets), chacun repéré par une clé, servi par URL ; durable et extensible à l'infini.
Bucket
Conteneur de stockage objet dans lequel on dépose les fichiers ; chaque fichier y possède une clé qui fait office de chemin.
Stockage bloc
Disque virtuel attaché à une seule machine (comme un disque dur), pour le système et les bases auto-gérées.
Stockage fichier
Partage réseau monté par plusieurs machines à la fois, à la manière d'un lecteur réseau.
Base gérée
Base de données dont le fournisseur assure les sauvegardes, les mises à jour et la réplication : moins d'exploitation, en échange de moins de contrôle fin.
Classe de stockage
Niveau tarifaire d'un fichier objet (« standard » pour l'accès fréquent, « archive » bien moins cher pour ce qu'on consulte rarement).
Transfert sortant (egress)
Sortie de données hors du cloud, souvent facturée ; source classique de mauvaise surprise sur la facture.
Durabilité
Garantie qu'un fichier ne sera pas perdu, obtenue en conservant plusieurs copies réparties.

Récap et vérification

  • Stockage objet (fichiers, le plus courant), bloc (disque de VM), fichier (partage réseau).
  • Le stockage objet est durable, extensible, servi par URL ; pense aux classes (archive).
  • Bases gérées : SQL pour le relationnel/transactionnel, NoSQL pour la flexibilité/échelle ; choisis selon les données.
  • Surveille les coûts : espace, requêtes, et surtout transfert sortant.

Vérifie ta compréhension

  1. Quel stockage pour les images téléversées par les utilisateurs ?
  2. Qu'apporte une base de données gérée ?
  3. Quel coût est souvent une mauvaise surprise ?

Exercices

Exercice 1Échauffement

Associe : (a) images téléversées ; (b) données d'utilisateurs reliées entre elles avec transactions ; (c) disque système d'une VM. → stockage objet / base relationnelle gérée / stockage bloc.

Voir une solution

(a) stockage objet ; (b) base relationnelle (SQL) gérée ; (c) stockage bloc (le disque attaché à la machine).

Exercice 2Application

Tu stockes de vieux journaux d'activité (logs) que tu ne consultes presque jamais. Comment réduire leur coût de stockage ?

Voir une solution

Les placer dans une classe de stockage « archive » (bien moins chère au Go que le standard), puisqu'ils sont rarement consultés. On accepte en échange un accès plus lent et un éventuel coût de récupération. On peut aussi définir une règle de cycle de vie qui déplace automatiquement les fichiers vers l'archive après X jours, voire les supprime au-delà de la durée de rétention nécessaire.

Exercice 3Défi

Une application stocke les photos de profil sur le disque local de son serveur cloud. Tout marche en test. Pourquoi est-ce un problème en production, et quelle est la bonne architecture ?

Voir une solution

Problèmes : (1) le disque local est éphémère — si l'instance est recréée (mise à jour, panne, mise à l'échelle), les photos disparaissent ; (2) avec plusieurs instances derrière un équilibreur, chacune n'aurait que ses fichiers (incohérence) ; (3) ça ne s'étend pas et n'est pas servi efficacement. Bonne architecture : envoyer les fichiers dans un stockage objet (durable, partagé par toutes les instances), les servir via URL (idéalement derrière un CDN), et ne garder en base que la référence (le chemin) du fichier. Le serveur applicatif redevient ainsi sans état, donc remplaçable et scalable.
