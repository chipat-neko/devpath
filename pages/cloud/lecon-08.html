Le réseau cloud (VPC)

~34 min Intermédiaire Leçon 07

À la fin de cette leçon, tu sauras

  • ce qu'est un réseau privé virtuel (VPC) et une plage CIDR ;
  • distinguer sous-réseau public et privé, passerelle Internet et NAT ;
  • répartir le trafic avec un équilibreur de charge ;
  • suivre le chemin d'une requête jusqu'à ta base de données.
Sommaire de la leçon

Derrière chaque déploiement cloud se cache un réseau : le squelette invisible qui relie tes machines, ta base et le monde extérieur. La leçon 06 a posé la sécurité réseau ; ici, on structure. Comprendre le VPC, c'est cesser de subir la topologie par défaut et décider, sciemment, qui parle à qui.

Le VPC : ton réseau privé dans le cloud

Un VPC (Virtual Private Cloud) est un réseau isolé, rien qu'à toi, dans une région. Tu lui donnes une plage d'adresses privées en notation CIDR — par exemple 10.0.0.0/16, soit 65 536 adresses de 10.0.0.0 à 10.0.255.255. Tout ce que tu déploies (machines, bases) reçoit une adresse dans cette plage et reste, par défaut, invisible depuis Internet.

Sous-réseaux publics et privés

On découpe le VPC en sous-réseaux, plus petits (10.0.1.0/24 = 256 adresses). La différence tient à une seule chose : la table de routage.

  • Un sous-réseau public a une route vers une passerelle Internet : ses ressources peuvent recevoir et émettre du trafic public. On y met ce qui doit être joignable (équilibreur, serveur web).
  • Un sous-réseau privé n'a pas cette route : il est injoignable depuis Internet. Pour qu'il puisse tout de même sortir (télécharger une mise à jour) sans être exposé, on passe par une passerelle NAT placée dans le public. On y met la base, les files, les traitements.

Public ne veut pas dire « sans protection »

Un sous-réseau « public » autorise seulement une route vers Internet. Ce qui décide réellement de qui peut se connecter, ce sont les groupes de sécurité (leçon 06) : on peut avoir une machine dans le public mais n'ouvrir que le port 443 depuis l'équilibreur.

L'équilibreur de charge

Un seul serveur, c'est un point unique de défaillance et un plafond de capacité. L'équilibreur de charge (load balancer) place une porte d'entrée unique devant plusieurs instances identiques, et répartit les requêtes entre elles. Il surveille leur santé (health checks) : une instance qui ne répond plus est retirée de la rotation, sans coupure visible.

Le DNS : des noms plutôt que des adresses

Personne ne tape une adresse IP. Le DNS (Domain Name System) traduit un nom lisible (mon-site.fr) en l'adresse de ton équilibreur. Chez un fournisseur cloud, un service de DNS géré héberge ta zone et ses enregistrements (un A ou un CNAME qui pointe vers l'équilibreur), souvent avec bascule automatique si une région tombe.

Le chemin complet d'une requête

Assemblons tout : du navigateur jusqu'à la base, une requête traverse chaque brique dans l'ordre.

Un cas concret

Cas réel

L'architecture « équilibreur en façade, application dans un sous-réseau public, base dans un sous-réseau privé » est le patron par défaut de presque toutes les applications web sérieuses — des trois grands fournisseurs (AWS, Azure, GCP) aux PaaS comme Heroku qui le cachent pour toi. Quand un site tient un pic de trafic un soir de vente flash, c'est l'équilibreur qui étale la charge sur des instances ajoutées à la volée (leçon 05), pendant que la base privée reste inatteignable de l'extérieur. Le jour où une instance plante à 3 h du matin, le health check la sort du circuit et personne ne s'en aperçoit : c'est ce maillage réseau, invisible, qui rend le service « toujours debout ».

Pièges fréquents

  • Plages CIDR qui se chevauchent. Si deux VPC que tu veux relier (appairage) partagent la même plage, le routage devient impossible. Planifie tes plages en amont.
  • Base dans le sous-réseau public. Par facilité, on l'expose « juste pour tester »… et on oublie. La base va dans le privé.
  • Un seul sous-réseau, une seule zone. Répartis tes sous-réseaux sur plusieurs zones de disponibilité (leçon 02) pour survivre à la panne d'une zone.
  • Passerelle NAT oubliée. Sans elle, une instance privée ne peut même pas télécharger ses mises à jour.

Pour aller plus loin

Pour aller plus loin

Au-delà des bases : l'appairage de VPC (peering) et les passerelles de transit relient plusieurs réseaux ; les points de terminaison privés (private endpoints) atteignent un service géré (stockage, base) sans passer par Internet du tout ; un VPN ou une liaison dédiée raccordent ton réseau d'entreprise au VPC. Et pour ne pas cliquer tout cela à la main, on décrit le réseau en Infrastructure as Code (cours IaC / Terraform) — reproductible et versionné.

Glossaire

VPC
Virtual Private Cloud : réseau privé isolé, propre à toi, dans une région du fournisseur.
CIDR
Notation d'une plage d'adresses IP (ex. 10.0.0.0/16) ; le nombre après la barre indique combien d'adresses.
Sous-réseau (subnet)
Subdivision d'un VPC avec sa propre plage ; public ou privé selon sa table de routage.
Table de routage
Ensemble de règles qui déterminent la destination du trafic d'un sous-réseau.
Passerelle Internet
Composant qui permet à un sous-réseau public d'échanger du trafic avec Internet.
Passerelle NAT
Permet à un sous-réseau privé d'initier des connexions sortantes sans être joignable depuis Internet.
Équilibreur de charge
Point d'entrée unique qui répartit les requêtes sur plusieurs instances et surveille leur santé.
DNS
Domain Name System : traduit un nom de domaine en adresse IP via des enregistrements (A, CNAME).

Récap et vérification

  • Un VPC est ton réseau privé isolé, défini par une plage CIDR ; on le découpe en sous-réseaux.
  • Public = route vers une passerelle Internet ; privé = isolé, sortie via NAT.
  • L'équilibreur de charge répartit le trafic sur des instances saines ; le DNS donne un nom.
  • Patron type : équilibreur → app (public) → base (privé), chaque brique n'exposant que le nécessaire.

Vérifie ta compréhension

  1. Qu'est-ce qui rend un sous-réseau « public » ?
  2. Pourquoi deux VPC destinés à être reliés ne doivent-ils pas partager la même plage CIDR ?
  3. À quoi sert un health check sur l'équilibreur ?

Exercices

Exercice 1Échauffement

On te donne un VPC en 10.0.0.0/16. Quel type de sous-réseau choisis-tu pour un serveur web joignable par le public, et lequel pour sa base ?

Voir une solution

Le serveur web va dans un sous-réseau public (route vers la passerelle Internet), par exemple 10.0.1.0/24, derrière l'équilibreur. La base va dans un sous-réseau privé, par exemple 10.0.2.0/24, sans route Internet : seule l'application peut la joindre. Bonus : dupliquer ce découpage sur une deuxième zone de disponibilité.

Exercice 2Application

Une instance dans un sous-réseau privé doit télécharger une mise à jour depuis Internet. Comment le permettre sans l'exposer ?

Voir une solution

Via une passerelle NAT placée dans un sous-réseau public : la table de routage du sous-réseau privé envoie le trafic sortant vers la NAT, qui le relaie vers Internet. Les connexions sortantes passent, mais aucune connexion entrante depuis Internet n'est possible : l'instance reste invisible.

Exercice 3Défi

Décris, dans l'ordre, le chemin d'une requête depuis un navigateur jusqu'à la base de données.

Voir une solution

1) Le navigateur interroge le DNS, qui traduit mon-site.fr en l'adresse de l'équilibreur. 2) La requête arrive à l'équilibreur, qui la dirige vers une instance saine de l'application, dans le sous-réseau public. 3) L'application traite la requête et interroge la base de données, dans le sous-réseau privé, via une connexion interne autorisée par le groupe de sécurité. 4) La réponse remonte le même chemin. À aucun moment la base n'a été joignable depuis Internet.
