Consommer une API web

~37 min Avancé Leçon 12 recommandée

À la fin de cette leçon, tu sauras

  • appeler une API web en GET avec file_get_contents et un contexte de flux ;
  • utiliser cURL pour un contrôle complet (en-têtes, POST, timeout) ;
  • employer Guzzle, le client HTTP moderne, pour plus de confort ;
  • décoder le JSON, réagir aux codes de statut et garder ta clé d'API hors du code.
Sommaire de la leçon

À la leçon 12, tu as appris à construire une API REST en JSON. Cette leçon fait l'inverse : consommer l'API de quelqu'un d'autre depuis ton code PHP — une météo, un taux de change, un service de paiement, l'API de ton propre micro-service. Ton script devient un client HTTP : il envoie une requête, reçoit une réponse (souvent du JSON) et la transforme en tableau PHP. On verra les trois façons de faire, de la plus simple à la plus robuste. On reste en PHP 8.3.

Le plus simple : file_get_contents + contexte

Tu connais déjà file_get_contents pour lire un fichier. Comme les flux unifient fichiers et réseau (vu à la leçon 19), la même fonction lit aussi une URL https://…. Pour une simple requête GET, cela suffit. Pour aller au-delà (méthode POST, en-têtes, timeout), on lui passe un contexte de flux créé avec stream_context_create.

C'est parfait pour un script rapide. Deux limites : en cas d'erreur HTTP (404, 500…), file_get_contents renvoie false et déclenche un warning peu pratique ; et récupérer le code de statut exact demande de fouiller la variable magique $http_response_header. Pour un vrai contrôle, on passe à cURL.

json_decode : pense au true

Sans second argument, json_decode($json) renvoie un objet ($data->temperature). Avec true, tu obtiens un tableau associatif ($data['temperature']) — souvent plus pratique. Vérifie toujours le résultat : un JSON invalide renvoie null. Depuis PHP 7.3, json_decode($json, true, 512, JSON_THROW_ON_ERROR) lève une exception au lieu de renvoyer null en silence.

Le contrôle complet : cURL

cURL est la bibliothèque de référence pour les requêtes HTTP, disponible partout sans installation. Son style est verbeux mais explicite : on ouvre une session (curl_init), on la configure option par option (curl_setopt), on l'exécute (curl_exec), puis on la ferme (curl_close).

Plus long, mais tu maîtrises tout : méthode, corps, en-têtes, délai, et surtout le code de statut obtenu via curl_getinfo. C'est le choix par défaut quand tu ne veux pas ajouter de dépendance.

Le confort moderne : Guzzle

Dans un vrai projet (avec Composer, vu à la leçon 11), on utilise rarement cURL à la main : on installe Guzzle, le client HTTP le plus répandu de l'écosystème PHP. Il enveloppe cURL dans une API lisible, lève des exceptions sur les erreurs et décode le JSON pour toi.

Guzzle gère les redirections, les tentatives, l'asynchrone, et suit le standard PSR-18 (interface commune des clients HTTP). Pour du code de production, c'est l'option recommandée ; cURL reste précieux pour un petit script sans dépendance.

Toujours un timeout, jamais de clé dans le code

Deux fautes classiques : (1) appeler une API sans timeout. Le jour où le service tiers est lent, chaque visiteur de ton site attend 30 secondes, tes processus PHP s'accumulent, et ton site tombe à cause de l'API d'un autre. (2) écrire la clé d'API en dur ('Bearer sk_live_9f3...'). Elle finit dans Git, publiée, volée. Range-la dans une variable d'environnement (getenv('API_CLE'), fichier .env non versionné) — comme pour un mot de passe de base de données.

Lire et réagir au code de statut

Une réponse HTTP commence toujours par un code de statut à trois chiffres qui résume ce qui s'est passé. Le premier chiffre donne la famille. Un client sérieux ne suppose jamais que tout s'est bien passé : il vérifie le code avant de décoder le corps.

Le code 429 et la limitation de débit

Beaucoup d'API limitent le nombre d'appels (rate limiting) et répondent 429 Too Many Requests au-delà. Elles renseignent souvent un en-tête Retry-After indiquant combien de secondes patienter. Respecte-le : enchaîner les requêtes malgré un 429 ne fait qu'aggraver le blocage, parfois jusqu'au bannissement de ta clé.

Un cas réel : l'API lente qui a fait tomber tout le site

Cas réel

Un site de e-commerce affichait sur chaque fiche produit un bloc « livraison estimée » calculé par l'appel d'une API de transporteur, en file_get_contents sans timeout. Pendant des mois, tout allait bien. Un soir, le transporteur a eu un incident : son API répondait en 40 secondes au lieu de 200 millisecondes. Résultat : chaque visiteur restait bloqué 40 secondes sur une fiche produit, les processus PHP-FPM se sont tous retrouvés occupés à attendre, et tout le site — accueil, panier, paiement compris — est devenu inaccessible. Une panne chez un prestataire avait mis à genoux un site pourtant sain. Le correctif : un timeout de 3 secondes, un try/catch qui affiche « estimation indisponible » en cas d'échec, et un petit cache pour ne pas rappeler l'API à chaque affichage. La leçon : un appel réseau peut toujours être lent ou échouer ; traite-le comme tel, et ne laisse jamais la santé de ton site dépendre de la ponctualité d'un tiers.

Antisèche

Glossaire

Client HTTP
Programme qui envoie des requêtes à un serveur et lit ses réponses. Ici, ton script PHP joue ce rôle vis-à-vis d'une API.
API web
Service accessible par HTTP qui expose des données/actions, généralement en JSON. On la consomme en envoyant des requêtes à ses endpoints (URL).
cURL
Bibliothèque HTTP native de PHP : curl_init/curl_setopt/curl_exec/curl_close. Verbeuse mais complète et sans dépendance.
Contexte de flux
Objet de configuration (stream_context_create) qui ajoute méthode, en-têtes et timeout à un appel file_get_contents sur une URL.
Guzzle
Client HTTP populaire installé via Composer ; API lisible, exceptions sur erreur, conforme au standard PSR-18.
Code de statut
Nombre à trois chiffres résumant la réponse : 2xx succès, 3xx redirection, 4xx erreur du client, 5xx erreur du serveur.
Timeout
Délai maximal d'attente d'une réponse. Indispensable : sans lui, un service lent peut bloquer tout ton site.
Clé d'API (jeton)
Secret d'authentification envoyé dans l'en-tête Authorization. À stocker en variable d'environnement, jamais dans le code versionné.

Récap et vérification

  • GET simple : file_get_contents($url) ; en-têtes/POST/timeout via un contexte de flux.
  • cURL = contrôle complet : init/setopt/exec/close, sans oublier CURLOPT_RETURNTRANSFER.
  • Guzzle (Composer) = confort et exceptions : le choix par défaut en production.
  • Toujours : json_decode(..., true), vérifier le code de statut, poser un timeout.
  • La clé d'API vit dans une variable d'environnement, jamais dans le code.

Vérifie ta compréhension

  1. Pourquoi un appel d'API sans timeout est-il dangereux ?
  2. Quelle option cURL faut-il pour récupérer la réponse au lieu de l'afficher ?
  3. Faut-il réessayer automatiquement après un code 4xx ? Et après un 5xx ?

Exercice 3Défi

Explique pourquoi il ne faut pas réessayer « en boucle » après un code 429, et ce qu'il faut regarder pour savoir combien de temps patienter.

Voir une solution

Un 429 Too Many Requests signifie que tu as dépassé la limite de débit (rate limit) de l'API. Réessayer immédiatement, en boucle, ne fait qu'empirer les choses : tu continues de dépasser le quota, et certaines API finissent par bannir ta clé. La réponse contient très souvent un en-tête Retry-After indiquant le nombre de secondes (ou une date) à attendre avant le prochain appel. La bonne stratégie : lire Retry-After, patienter ce délai (ou appliquer un backoff exponentiel : 1 s, 2 s, 4 s…), et espacer durablement tes requêtes pour rester sous la limite.
