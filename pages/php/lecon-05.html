Module 02 · PHP pour le web — Leçon 05

Formulaires et données HTTP

~30 min Débutant Leçon 4 recommandée

À la fin de cette leçon, tu sauras

  • Comprendre la différence entre les méthodes HTTP GET et POST et savoir quand utiliser chacune ;
  • Lire en sécurité les données envoyées par un formulaire avec $_POST et l'opérateur ?? ;
  • Construire le pattern « même fichier qui affiche le formulaire et le traite » en vérifiant $_SERVER['REQUEST_METHOD'] ;
  • Valider les entrées et les réafficher sans danger avec htmlspecialchars().
Sommaire de la leçon

Jusqu'ici, ton script PHP générait du HTML tout seul, dans son coin. Mais le vrai intérêt du web, c'est l'échange : l'internaute remplit un champ, clique sur un bouton, et le serveur réagit. C'est exactement ce qu'on apprend ici. Recevoir des données envoyées par le navigateur, c'est le cœur battant du PHP côté serveur.

Souviens-toi : PHP s'exécute sur le serveur. Le navigateur envoie une requête (avec, par exemple, le contenu d'un formulaire), PHP la lit, fabrique du HTML en réponse, et renvoie ce HTML au navigateur. À aucun moment le PHP ne tourne dans la page : il a déjà fini son travail avant que tu voies le résultat.

Rappel HTTP : GET et POST

Quand ton navigateur demande une page, il utilise une méthode HTTP. Les deux que tu croiseras sans cesse sont GET et POST.

  • GET : les données voyagent dans l'URL, après un ?. Exemple : recherche.php?ville=Lyon&page=2. Visible, partageable, mis en favori. Idéal pour demander quelque chose (une recherche, un filtre) sans rien modifier.
  • POST : les données voyagent dans le corps de la requête, pas dans l'URL. Invisibles dans la barre d'adresse, pas mises en cache. Idéal pour envoyer quelque chose qui change l'état du serveur (créer un compte, poster un message, envoyer un mot de passe).

Règle simple : si l'action lit des données, GET. Si elle écrit ou envoie de l'info sensible, POST.

Note

POST n'est pas « chiffré » : les données du corps restent lisibles si la connexion n'est pas en HTTPS. POST cache juste les données de l'URL et de l'historique ; c'est HTTPS qui les protège réellement pendant le transport.

Un formulaire HTML qui envoie au serveur

Côté navigateur, c'est le HTML qui décide où et comment partent les données, grâce à la balise <form>. Deux attributs comptent : method (la méthode HTTP) et action (le fichier PHP qui reçoit).

Chaque <input> a un attribut name : c'est la clé sous laquelle PHP retrouvera la valeur. Ici, ce que l'internaute tape arrivera côté serveur sous le nom prenom. Retiens bien : c'est name qui compte pour PHP, pas id (ce dernier sert au CSS, au JavaScript et à relier le <label> au champ).

Les superglobales : $_GET, $_POST, $_SERVER

Quand la requête arrive, PHP range automatiquement les données reçues dans des tableaux spéciaux appelés superglobales. « Super » parce qu'elles sont accessibles partout, sans rien importer.

  • $_GET : les données envoyées par la méthode GET (l'URL).
  • $_POST : les données envoyées par la méthode POST (un formulaire method="post").
  • $_REQUEST : un mélange de GET et POST. Pratique en apparence, mais flou : tu ne sais plus d'où vient la donnée. Évite-le, préfère le tableau précis.
  • $_SERVER : des infos sur la requête elle-même (méthode utilisée, adresse, etc.).

Note

La clé dans $_POST correspond exactement à l'attribut name de l'<input>. Si tu écris name="email", tu liras $_POST['email'].

Lire une valeur en toute sécurité

Premier réflexe de débutant : écrire $_POST['prenom'] directement. Problème : si la clé n'existe pas (première visite, formulaire pas encore envoyé), PHP affiche un avertissement « Undefined array key ». La parade moderne est l'opérateur de coalescence ?? : « prends cette valeur, ou bien celle-ci si elle n'existe pas ».

L'expression $_SERVER['REQUEST_METHOD'] === 'POST' vaut true uniquement quand la page a été atteinte par un envoi de formulaire POST. C'est la clé du pattern qui suit.

Le même fichier affiche le formulaire ET le traite

Pas besoin de deux fichiers. Le plus courant en PHP : un seul fichier qui, à la première visite (GET), montre le formulaire vide, et qui, après l'envoi (POST), traite les données.

Valider et ne jamais faire confiance aux entrées

Une règle d'or, gravée dans le marbre : ne fais JAMAIS confiance à ce qui vient du navigateur. L'internaute peut envoyer n'importe quoi : champ vide, texte de 10 000 caractères, code malveillant. Ton travail : valider. Voici une validation basique (champ obligatoire, format d'e-mail).

filter_var(..., FILTER_VALIDATE_EMAIL) renvoie l'e-mail s'il a un format correct, ou false sinon. On accumule les messages dans un tableau $erreurs pour tous les afficher d'un coup. La validation côté serveur est obligatoire : même si tu ajoutes required dans le HTML, on peut contourner le navigateur (avec un outil qui envoie la requête directement).

Réafficher proprement : htmlspecialchars

Imagine que tu réaffiches le prénom saisi sans précaution, et qu'un visiteur tape <script>...</script>. Le navigateur l'exécuterait : c'est la faille XSS (injection de code dans la page). La parade : htmlspecialchars(), qui transforme les caractères dangereux (<, >, &, guillemets) en entités inoffensives.

La règle : toute donnée venue de l'utilisateur passe par htmlspecialchars() avant d'être affichée dans la page. Aucune exception.

Astuce

Tu peux créer un petit raccourci : function e(string $t): string { return htmlspecialchars($t); }, puis écrire <?= e($prenom) ?>. Plus court, plus dur à oublier.

Pièges fréquents

Piège fréquent

Faire confiance aux données reçues. Jamais. Une entrée non validée et non échappée est une porte ouverte. Toujours valider (côté serveur) et toujours échapper à l'affichage avec htmlspecialchars().

  • Afficher sans htmlspecialchars → faille XSS. Échappe systématiquement.
  • Oublier de vérifier la méthode → le code de traitement s'exécute même à la première visite. Entoure-le d'un if ($_SERVER['REQUEST_METHOD'] === 'POST').
  • Lire $_POST['x'] inexistant → avertissement « Undefined array key ». Utilise toujours $_POST['x'] ?? ''.
  • Confondre name et id → PHP lit la clé d'après name. Un id sans name n'envoie rien au serveur.

Un cas réel : le commentaire qui volait les sessions

Cas réel

Un site associatif affichait les commentaires de ses visiteurs. Le code se contentait de echo $_POST['message']; pour les réafficher. Un jour, un visiteur a posté non pas du texte, mais <script>…</script>. Ce script, stocké puis renvoyé à chaque visiteur de la page, s'exécutait dans leur navigateur : il lisait leur cookie de session et l'envoyait à l'attaquant, qui pouvait alors se faire passer pour eux. C'est une faille XSS stockée, parmi les plus répandues du web. La cause n'avait rien d'exotique : une donnée utilisateur affichée sans échappement. La parade tient en une fonction : echo htmlspecialchars($message) à l'affichage — et, en complément, l'attribut httponly sur le cookie de session pour le rendre illisible par JavaScript. Règle d'or : toute donnée venue du navigateur est échappée avant d'être réinsérée dans la page.

Glossaire

Méthode HTTP
Verbe d'une requête : GET (demander, données dans l'URL) ou POST (envoyer / modifier, données dans le corps).
Superglobale
Tableau spécial accessible partout sans import : $_GET, $_POST, $_SERVER, $_COOKIE, $_SESSION…
$_POST
Superglobale contenant les champs d'un formulaire envoyé en POST ; la clé correspond exactement à l'attribut name de l'<input>.
Validation
Vérification que les données reçues respectent les règles attendues (obligatoire, format, longueur) ; toujours côté serveur, car le contrôle du navigateur est contournable.
Échappement
Transformation des caractères spéciaux en entités avant l'affichage, avec htmlspecialchars() ; empêche le HTML/JS injecté de s'exécuter.
XSS
Cross-Site Scripting : injection de code dans une page à cause d'une donnée affichée sans échappement ; parade = htmlspecialchars() à la sortie.
REQUEST_METHOD
Clé de $_SERVER indiquant la méthode utilisée ; === 'POST' permet de ne traiter le formulaire qu'après un envoi.
name vs id
name est la clé transmise au serveur (lue dans $_POST) ; id ne sert qu'au client (CSS, JavaScript, <label>) et n'arrive pas à PHP.

Récap et vérification

  • GET pour demander (données dans l'URL), POST pour envoyer ou modifier (données dans le corps).
  • Les données arrivent dans les superglobales $_GET, $_POST, $_SERVER.
  • Lis en sécurité avec $_POST['cle'] ?? '' et vérifie $_SERVER['REQUEST_METHOD'] === 'POST'.
  • Un seul fichier peut afficher le formulaire et le traiter.
  • Toujours valider côté serveur et échapper l'affichage avec htmlspecialchars().
