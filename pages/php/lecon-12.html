Construire une API REST en JSON

~30 min Intermédiaire Cours PHP recommandé

À la fin de cette leçon, tu sauras

  • savoir structurer une API REST (ressources, verbes HTTP, codes de statut) et lire une requête JSON avec php://input ;
  • savoir répondre en JSON proprement avec json_encode, http_response_code() et le bon Content-Type ;
  • savoir écrire un routeur minimal sans framework et brancher un CRUD sur PDO en requêtes préparées ;
  • savoir gérer le CORS, un jeton Bearer et consommer une API tierce avec cURL.
Sommaire de la leçon

Jusqu'ici, ton PHP renvoyait du HTML : le serveur fabriquait une page, le navigateur l'affichait. Une API REST change de logique : au lieu de pages, elle expose des ressources (articles, utilisateurs, commandes) qu'un client — un front JavaScript, une appli mobile, un autre serveur — manipule en échangeant du JSON. Pas de <form>, pas de gabarit : juste des données structurées et des codes de statut HTTP clairs.

Dans cette leçon, tu construis une API complète à la main, sans framework, pour comprendre ce que les frameworks automatisent : lire une requête, router selon le verbe et l'URL, répondre en JSON, brancher un CRUD sur PDO, gérer le CORS et l'authentification, et enfin consommer une API tierce. Tu réutilises tout ce que tu connais (PDO, requêtes préparées, namespaces), mais côté machine plutôt que côté page.

Le principe REST

REST repose sur trois piliers. D'abord les ressources, identifiées par une URL : /articles désigne la collection, /articles/42 un élément précis. Ensuite les verbes HTTP, qui disent quoi en faire : GET lit, POST crée, PUT (ou PATCH) modifie, DELETE supprime. Enfin les codes de statut, qui annoncent le résultat sans que le client ait à deviner.

Note

Le code de statut fait partie du contrat. Un client bien écrit teste response.status avant de lire le corps : un 404 n'a pas besoin d'être parsé, un 201 signale qu'une création a réussi. Ne réponds jamais 200 pour tout.

Lire la requête entrante

Trois informations te suffisent pour traiter une requête : la méthode, le chemin et le corps. Les données de formulaire classiques arrivent dans $_POST, mais une API JSON reçoit un corps brut : tu le lis avec file_get_contents('php://input') puis tu le décodes.

Piège fréquent

En PHP 8.3, tu peux remplacer le test json_last_error() par le flag JSON_THROW_ON_ERROR : json_decode($raw, true, 512, JSON_THROW_ON_ERROR) lèvera une JsonException que tu attrapes dans un try/catch. Plus propre que de vérifier null à la main.

Répondre en JSON

Une réponse JSON correcte, c'est trois choses : le bon en-tête Content-Type, le bon code de statut, et un corps encodé avec json_encode. Centralise-la dans une petite fonction pour ne jamais l'oublier.

Astuce

Le type de retour never (PHP 8.1+) indique que la fonction ne rend jamais la main (elle finit par exit). C'est de la documentation utile pour ton IDE et pour l'analyse statique : tout code après l'appel est mort.

Le routeur est le cœur de l'API : il regarde le verbe et l'URL, puis appelle la bonne fonction. En réel, on redirige toutes les requêtes vers un seul index.php (le « front controller ») via la config du serveur. Voici une version compacte qui gère /articles et /articles/{id}.

CORS et authentification par jeton

Si ton API est appelée par un front hébergé sur un autre domaine (ou un autre port), le navigateur bloque la réponse tant que tu n'envoies pas les en-têtes CORS. Et pour protéger les routes, le schéma le plus courant est le jeton Bearer envoyé dans l'en-tête Authorization.

Piège fréquent

Ne mets Access-Control-Allow-Origin: * en production que pour une API publique en lecture seule. Pour une API authentifiée, indique l'origine exacte de ton front, sinon n'importe quel site pourra appeler ton API depuis le navigateur d'un utilisateur connecté.

Consommer une API tierce avec cURL

Ton API a aussi le droit d'être cliente : récupérer une météo, un taux de change, un service de paiement. L'extension cURL de PHP fait ça. Tu prépares une session, tu fixes les options, tu exécutes, tu décodes.

Pièges fréquents

  • Oublier le Content-Type : sans application/json, beaucoup de clients refusent de parser ta réponse. Centralise dans jsonResponse().
  • Mauvais code de statut : répondre 200 pour une création au lieu de 201, ou 200 avec un message d'erreur dans le corps. Le statut doit dire la vérité.
  • Ne pas valider le JSON reçu : json_decode renvoie null sur un corps invalide ou vide. Vérifie avec json_last_error() ou JSON_THROW_ON_ERROR avant d'utiliser les données.
  • Injection SQL : un id ou un champ vient toujours du client. Requêtes préparées, sans exception.
  • Exposer les erreurs détaillées : ne renvoie jamais $e->getMessage() brut au client. Logue le détail côté serveur, renvoie un message générique avec un 500.
  • Oublier le CORS : si ton front ne reçoit rien alors que curl marche, c'est presque toujours un en-tête CORS ou un préflight OPTIONS non géré.

Pour aller plus loin

Pour aller plus loin

En production, on s'appuie sur des frameworks API (Slim pour du léger, Symfony ou Laravel pour du complet) qui gèrent routing, validation et sérialisation. Documente ton API avec OpenAPI/Swagger, authentifie avec des JWT signés, ajoute pagination et filtrage sur les collections, et couvre le tout par des tests d'API (PHPUnit + client HTTP). Explore aussi GraphQL quand le client a besoin de choisir précisément les champs renvoyés.

Un cas réel : l'API qui répondait toujours 200

Cas réel

Une API de catalogue renvoyait toujours le statut 200, même pour une ressource absente : elle mettait {"error":"introuvable"} dans le corps, mais avec un 200 OK. Côté client, l'appli mobile se fiait — à raison — au statut : un 200 signifiait « données valides », donc elle affichait une fiche vide et, pire, son cache HTTP stockait ces réponses d'erreur comme du contenu légitime. Le jour où un produit très consulté a été retiré, des milliers d'appareils ont affiché une page produit blanche mise en cache, impossible à rafraîchir avant expiration. Le correctif a tenu en quelques lignes : renvoyer les vrais codes — 404 pour l'absence, 400 pour une requête malformée. Aussitôt, caches et CDN ont cessé de conserver les erreurs, et le client a pu réagir correctement. La morale : le code de statut n'est pas décoratif ; c'est un contrat que tous les intermédiaires (navigateur, cache, CDN, client) respectent à ta place — à condition que tu dises la vérité.

Glossaire

REST
Style d'API où l'on manipule des ressources identifiées par une URL, via les verbes HTTP, en échangeant surtout du JSON.
Ressource
Entité exposée par l'API (article, produit…) : /articles est la collection, /articles/42 un élément précis.
Verbe HTTP
L'action demandée : GET lit, POST crée, PUT/PATCH modifie, DELETE supprime.
Code de statut
Nombre qui annonce le résultat : 2xx succès (200, 201, 204), 4xx faute du client (400, 401, 404), 5xx erreur serveur.
php://input
Flux du corps brut de la requête ; à lire pour un corps JSON, car $_POST ne se remplit que pour les formulaires.
Front controller
Fichier unique (index.php) qui reçoit toutes les requêtes et les aiguille vers la bonne fonction selon verbe + URL.
CORS
Mécanisme qui autorise un front d'un autre domaine à appeler l'API ; activé par les en-têtes Access-Control-Allow-*, avec un préflight OPTIONS préalable.
Jeton Bearer
Jeton d'authentification envoyé dans l'en-tête Authorization: Bearer … pour prouver l'identité de l'appelant sur les routes protégées.

Récap et vérification

  • Une API REST expose des ressources manipulées par des verbes HTTP, avec des codes de statut qui disent le résultat.
  • On lit le corps JSON avec file_get_contents('php://input') + json_decode, et on le valide systématiquement.
  • On répond avec Content-Type: application/json, http_response_code() et json_encode (flags JSON_UNESCAPED_UNICODE).
  • Un routeur match (true) dispatche verbe + URL vers des fonctions branchées sur PDO en requêtes préparées.
  • Le CORS ouvre l'API à un front séparé ; le jeton Bearer protège les routes.

Vérifie ta compréhension

  1. Quel code de statut renvoies-tu après une création réussie ? Et après une suppression sans corps ?
  2. Pourquoi lit-on php://input plutôt que $_POST pour une API JSON ?
  3. À quoi sert la requête OPTIONS dans le mécanisme CORS, et comment y réponds-tu ?
