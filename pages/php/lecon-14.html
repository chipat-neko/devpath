Module 04 · PHP en profondeur — Leçon 14

Performance, tests et déploiement

~35 min Intermédiaire Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • savoir optimiser une application PHP avec OPcache, le préchargement et la mise en cache, en évitant les requêtes N+1 ;
  • savoir écrire et lancer des tests avec PHPUnit (assertions, data providers, mocks) ;
  • savoir appliquer les normes PSR et l'analyse statique (PHPStan, PHP_CodeSniffer) ;
  • savoir configurer et déployer en production (.env, php.ini, Composer, PHP-FPM, Docker, CI/CD).
Sommaire de la leçon

Tu sais désormais écrire des classes, gérer des sessions, parler à une base via PDO et installer des dépendances avec Composer. Mais entre « ça marche sur ma machine » et « ça tourne en production sous charge sans planter », il reste un fossé. Cette leçon le comble : tu vas apprendre à rendre ton code rapide, fiable (grâce aux tests et à l'analyse statique) et déployable proprement.

L'idée centrale : une application de production se pilote avec des outils, pas à l'instinct. OPcache pour la vitesse, PHPUnit pour la confiance, PHPStan pour la rigueur, des variables d'environnement pour la configuration, et un pipeline pour livrer. On passe en revue chacun de ces leviers avec du code et des configurations commentés.

La performance : OPcache et préchargement

À chaque requête, PHP lit tes fichiers .php, les compile en opcodes (bytecode), puis les exécute. Sans cache, cette compilation est refaite à chaque appel. OPcache garde le bytecode compilé en mémoire : la compilation n'a lieu qu'une fois. C'est le gain le plus rentable que tu puisses activer, souvent un facteur 2 à 3 sur le temps de réponse.

En production, validate_timestamps=0 dit à PHP de ne jamais revérifier si les fichiers ont changé : il faut alors recharger PHP-FPM à chaque déploiement.

Le préchargement (preloading) va plus loin : au démarrage du serveur, un script charge en mémoire les classes utilisées partout (le framework, tes entités). Elles deviennent disponibles sans aucun chargement par requête.

Éviter les requêtes N+1

Le piège de performance le plus courant avec une base de données : tu charges une liste de N éléments, puis tu fais une requête par élément pour récupérer une relation. Résultat : 1 requête + N requêtes = N+1 allers-retours vers la base.

Pour les données calculées ou lentes à obtenir, ajoute une couche de cache. APCu stocke en mémoire locale du serveur (simple, mono-machine) ; Redis est un cache externe partagé entre plusieurs serveurs.

Note

Avant d'optimiser, profile. Xdebug génère des traces de profilage exploitables avec un outil comme KCachegrind ; Blackfire mesure finement le temps et la mémoire par fonction, en local comme en production. On optimise ce qu'on mesure, jamais ce qu'on suppose.

Les tests avec PHPUnit

Tester, c'est écrire du code qui vérifie automatiquement que ton code fait ce qu'il doit. Le gain : tu refactorises sans peur, tu attrapes les régressions avant tes utilisateurs. PHPUnit est le standard de fait. Un test est une méthode d'une classe qui étend TestCase et utilise des assertions.

Quand ton code dépend d'un service externe (une base, une API), tu ne veux pas le solliciter dans un test unitaire. Tu fournis un mock : un faux objet au comportement programmé.

Tes tests ont besoin de l'autoload. On déclare un namespace de test dans composer.json sous autoload-dev, puis on lance la suite.

Les normes PSR et l'analyse statique

Les PSR (PHP Standard Recommendations) uniformisent l'écosystème. PSR-4 relie un namespace à un dossier (tu l'utilises déjà via Composer) ; PSR-12 fixe le style : indentation, accolades, espaces. Suivre PSR-12 rend ton code lisible par n'importe quel développeur PHP.

Deux familles d'outils gardent la qualité. PHP_CodeSniffer (commande phpcs) vérifie le style et peut le corriger automatiquement (phpcbf). PHPStan et Psalm font de l'analyse statique : ils lisent ton code sans l'exécuter et détectent les bugs de typage, les variables jamais définies, les méthodes inexistantes.

Astuce

Monte le niveau PHPStan progressivement. Pars du niveau actuel de ton code, corrige tout, puis incrémente. Atteindre le niveau 9 sur un projet existant d'un coup est décourageant ; le faire palier par palier est réaliste.

La configuration par environnement

Ton code doit être identique en dev et en prod ; seules les valeurs changent (mot de passe de base, clé d'API, mode debug). On les place dans des variables d'environnement, souvent chargées depuis un fichier .env en développement via une bibliothèque comme vlucas/phpdotenv.

La règle d'or : tu versionnes un .env.example sans valeurs, jamais le .env réel. Les secrets restent hors du dépôt Git.

Le déploiement : Composer, PHP-FPM, Docker, CI/CD

En production, on n'installe pas les dépendances de développement (PHPUnit, PHPStan) et on optimise l'autoload pour qu'il n'ait plus à deviner où sont les classes.

Le serveur de prod typique combine PHP-FPM (le processus qui exécute PHP) et Nginx (qui sert les fichiers statiques et transmet les requêtes PHP à FPM). Docker emballe tout — PHP, ses extensions, la config — dans une image reproductible.

Enfin, la CI/CD (intégration et déploiement continus) automatise tout : à chaque git push, un pipeline lance les tests, l'analyse statique et le contrôle de style. Si tout est vert, il construit l'image et déploie.

La sécurité en production

La mise en prod ajoute des exigences de sécurité. Sers tout en HTTPS (chiffrement du trafic). Ajoute des en-têtes de sécurité. Et configure les cookies de session pour qu'ils ne fuient pas.

Pièges fréquents

Piège fréquent

OPcache désactivé en prod. C'est l'erreur de performance numéro un : ton application recompile chaque fichier à chaque requête et tourne 2 à 3 fois plus lentement. Vérifie avec opcache_get_status() que opcache.enable=1 est bien actif.

Piège fréquent

Afficher les erreurs détaillées en prod. Un message d'erreur PHP révèle des chemins, des noms de tables, parfois des identifiants : c'est une faille. En production, display_errors=0 et log_errors=1. Idem pour les secrets : ne versionne jamais ton .env, et ne déploie jamais avec les dépendances de dev (--no-dev obligatoire).

Pour aller plus loin

Pour aller plus loin

Pousse PHPStan ou Psalm au niveau maximal et ajoute des tests d'intégration (qui touchent une vraie base de test). Profile en conditions réelles avec Blackfire. Côté architecture, explore l'architecture hexagonale pour découpler ton domaine de l'infrastructure. En exploitation, branche un outil de monitoring d'erreurs comme Sentry et muscle tes pipelines CI/CD (déploiement automatique, environnements de pré-prod). C'est aussi le moment d'apprendre un framework (Symfony, Laravel) : ils intègrent nativement tout ce que tu viens de voir.

Un cas réel : le site lent à cause d'un réglage oublié

Cas réel

Une boutique en ligne se plaignait de pages « qui rament » en production, alors que tout était instantané en local. Pendant deux jours, l'équipe a soupçonné la base : index ajoutés, requêtes relues, cache tenté — sans effet notable. Un développeur a fini par appeler opcache_get_status() sur le serveur : la fonction renvoyait false. OPcache n'était tout simplement pas activé dans le php.ini de prod : à chaque requête, le serveur recompilait l'intégralité du code avant de l'exécuter. Une ligne — opcache.enable=1 — et un rechargement de PHP-FPM plus tard, le temps de réponse moyen est tombé de 900 ms à 300 ms, sans toucher une seule ligne de code applicatif. La leçon : avant de réécrire quoi que ce soit, vérifie la configuration. Le levier de performance le plus rentable est parfois un simple réglage oublié — et on ne le trouve qu'en mesurant, pas en devinant.

Antisèche

Glossaire

OPcache
Cache d'opcodes intégré à PHP : garde le bytecode compilé en mémoire pour ne pas recompiler à chaque requête (gain × 2 à × 3).
Opcode (bytecode)
Forme intermédiaire compilée de ton code .php, exécutée par le moteur : c'est ce qu'OPcache met en cache.
Requête N+1
1 requête pour une liste + 1 requête par élément pour sa relation ; explosion du nombre d'allers-retours, résolue par une jointure (eager loading).
PHPUnit
Framework de test standard en PHP : des classes étendant TestCase vérifient le code via des assertions.
Data provider
Mécanisme PHPUnit qui rejoue le même test avec plusieurs jeux de données, sans dupliquer la méthode.
Mock
Faux objet au comportement programmé, qui remplace une dépendance réelle (base, API) pour tester une unité en isolation.
Analyse statique
Outils (PHPStan, Psalm) qui lisent le code sans l'exécuter et détectent bugs de typage, méthodes ou variables inexistantes.
PHP-FPM
Gestionnaire de processus qui exécute PHP côté serveur ; un serveur web (Nginx) lui transmet les requêtes dynamiques.

Récap et vérification

  • Performance : active OPcache et le préchargement, élimine les requêtes N+1, mets en cache (APCu/Redis), profile avec Xdebug ou Blackfire.
  • Tests : PHPUnit avec assertions, data providers et mocks te donnent la confiance pour refactoriser.
  • Qualité : PSR-4/PSR-12, PHP_CodeSniffer pour le style, PHPStan/Psalm pour l'analyse statique.
  • Configuration : variables d'environnement et .env hors du dépôt ; display_errors=0 et log_errors=1 en prod.
  • Déploiement : composer install --no-dev --optimize-autoloader, PHP-FPM + Nginx, Docker, CI/CD.
  • Sécurité : HTTPS, en-têtes durcis, cookies de session secure/httponly/samesite.

Vérifie ta compréhension

  1. Pourquoi OPcache accélère-t-il PHP, et que change validate_timestamps=0 en production ?
  2. Qu'est-ce qu'une requête N+1 et comment l'éliminer ?
  3. À quoi sert un data provider dans PHPUnit, et en quoi diffère-t-il d'un mock ?
  4. Cite trois réglages à changer entre php.ini de dev et de prod, et explique pourquoi.
