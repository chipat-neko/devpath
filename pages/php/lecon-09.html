Module 03 · PHP moderne — Leçon 09

POO avancée et organisation

~28 min Intermédiaire Leçon 8 recommandée

À la fin de cette leçon, tu sauras

  • Réutiliser du code avec l'héritage (extends, parent::), les classes abstraites et les traits ;
  • Définir des contrats avec les interfaces (interface, implements) et choisir entre interface et classe abstraite ;
  • Organiser un projet en namespaces (namespace, use) et comprendre l'autoloading PSR-4 ;
  • Gérer les erreurs proprement avec les exceptions (try/catch/finally, throw) et en créer des personnalisées.
Sommaire de la leçon

Tu sais déjà créer une classe avec ses propriétés et ses méthodes. C'est une bonne base, mais un vrai projet, c'est rarement une seule classe : c'est dix, cinquante, parfois des centaines de classes qui doivent coopérer sans se marcher dessus. Dans cette leçon, tu vas apprendre à structurer tout ça : partager du code entre classes, définir des contrats clairs, ranger ton code dans des dossiers logiques et gérer les erreurs sans que tout s'écroule.

Rappel important : tout ce code s'exécute sur le serveur (via php -S ou Apache). PHP lit tes classes, fabrique des objets, puis produit du texte ou du HTML qu'il envoie au navigateur. Les « sorties » que tu verras en commentaire sont ce que PHP affiche côté serveur ; rien ne s'exécute dans l'éditeur du site.

L'héritage : réutiliser et spécialiser

L'héritage permet à une classe (la classe fille) de récupérer les propriétés et méthodes d'une autre (la classe parente) avec le mot-clé extends. La fille peut redéfinir une méthode du parent, et appeler la version d'origine avec parent::.

Ici Chien hérite du constructeur d'Animal (grâce à la constructor promotion : protected string $nom crée directement la propriété). protected rend $nom accessible dans la classe et ses filles, mais pas de l'extérieur.

Les classes abstraites : un squelette à compléter

Une classe abstract ne peut pas être instanciée directement : elle sert de modèle. Elle peut contenir des méthodes normales et des méthodes abstract (sans corps) que chaque fille doit implémenter.

Le mot-clé abstract devant aire() oblige chaque fille à fournir sa propre version : Cercle calcule l'aire d'un disque, un futur Carre calculerait autre chose. La méthode concrète decrire(), elle, est écrite une seule fois et profite à toutes.

Les interfaces : des contrats

Une interface ne contient que des signatures de méthodes, sans code : c'est une promesse. Une classe qui implements une interface s'engage à fournir toutes ses méthodes. Gros avantage : une classe peut implémenter plusieurs interfaces (alors qu'elle ne peut hériter que d'une seule classe).

Dans comparer(self $autre), le type self veut dire « un objet de la même classe » : ici, un autre Produit. L'opérateur <=> (le « spaceship ») renvoie -1, 0 ou 1 selon que la gauche est inférieure, égale ou supérieure à la droite. Surtout, tu peux maintenant écrire une fonction qui accepte n'importe quel objet Exportable, sans savoir s'il s'agit d'un Produit ou d'autre chose : c'est tout l'intérêt d'un contrat.

Les traits : partager des méthodes sans héritage

Parfois deux classes sans lien de parenté ont besoin du même code. Plutôt que de copier-coller, on utilise un trait : un bloc de méthodes qu'on « injecte » dans une classe avec use.

Un trait n'est pas une classe : on ne peut pas l'instancier. C'est juste du code prêt à être réutilisé. Article et Commentaire obtiennent tous les deux la méthode horodater() sans partager de parent commun.

Note

Si deux traits utilisés par la même classe définissent une méthode du même nom, PHP refuse de deviner et lève une erreur. Tu choisis alors la bonne avec insteadof, par exemple use A, B { A::saluer insteadof B; } pour garder la version de A.

Les namespaces : ranger et éviter les collisions

Quand un projet grandit, deux classes peuvent porter le même nom (par exemple un User à toi et un User d'une bibliothèque externe). Le namespace agit comme un « nom de famille » qui les distingue. On l'importe avec use.

La convention : le namespace reflète l'organisation des dossiers. App\Models\User vit dans src/Models/User.php. L'antislash initial (comme dans \App\Models\User) signifie « à partir de la racine », utile quand un nom est ambigu.

Note

Le séparateur de namespace est l'antislash \, à ne pas confondre avec le slash / des chemins de fichiers ou avec l'opérateur d'accès objet ->.

L'autoloading : charger les classes automatiquement

Sans aide, tu devrais écrire un require pour chaque fichier de classe : ingérable sur un gros projet. L'autoloading charge le bon fichier dès que tu utilises une classe. La norme PSR-4 définit une correspondance entre namespace et chemin : à un préfixe (ex. App\) correspond un dossier (ex. src/).

Avec cette config, App\Models\User est cherché dans src/Models/User.php : le préfixe App\ devient src/, le reste suit l'arborescence. C'est l'outil Composer qui génère ce fichier vendor/autoload.php ; on le verra en détail dans la leçon suivante.

Les exceptions : gérer les erreurs proprement

Quand quelque chose tourne mal (fichier absent, division impossible, donnée invalide), on lance une exception avec throw, et on la rattrape avec try/catch. Le bloc finally s'exécute toujours, qu'il y ait eu erreur ou non.

Note que la deuxième ligne du try n'affiche jamais son résultat : dès que throw se déclenche, PHP saute directement au catch. Le finally, lui, passe dans tous les cas : parfait pour fermer un fichier ou une connexion.

Les exceptions forment une hiérarchie : la plupart héritent de la classe Exception. Tu peux créer la tienne en l'étendant, ce qui te permet de la rattraper de façon ciblée.

Astuce

Tu peux enchaîner plusieurs catch du plus précis au plus général. Place catch (SoldeInsuffisantException $e) avant catch (Exception $e), sinon le bloc général attrapera tout en premier.

Pièges fréquents

Piège fréquent

L'héritage abusif. On est tenté de tout faire avec extends, mais des chaînes d'héritage profondes deviennent rigides et fragiles. Demande-toi : est-ce vraiment un « est un » (un Chien est un Animal) ? Si tu veux juste partager un comportement, préfère une interface (contrat) ou la composition (un objet en utilise un autre).

Piège fréquent

Mauvais mapping PSR-4 → « Class not found ». Si Composer ne trouve pas ta classe, vérifie : le namespace en haut du fichier correspond-il au chemin ? Le nom du fichier est-il exactement celui de la classe, casse comprise (User.php et non user.php) ? Après modification de composer.json, régénère l'autoload avec composer dump-autoload.

Piège fréquent

Interface vs classe abstraite. Une interface dit quoi faire (uniquement des signatures, implémentable plusieurs fois). Une classe abstraite peut aussi dire comment (méthodes concrètes, propriétés partagées), mais on n'en hérite qu'une seule. Choisis l'interface dès que plusieurs familles d'objets sans parent commun doivent respecter le même contrat.

Pour aller plus loin

Un cas réel : ajouter PayPal sans tout casser

Cas réel

Une boutique en ligne avait codé les paiements en appelant directement une classe StripePaiement un peu partout : dans le panier, dans les remboursements, dans les abonnements. Le jour où la direction a voulu proposer PayPal en plus, il a fallu ouvrir des dizaines de fichiers et ajouter des if partout — chantier long et risqué. La refonte a introduit une interface PaiementInterface avec une seule méthode payer(int $centimes): Recu. Désormais le code métier ne dépend plus que du contrat, jamais d'un prestataire précis. Ajouter PaypalPaiement puis, plus tard, ApplePayPaiement revient à écrire une classe qui implements PaiementInterface, sans toucher au reste. C'est la démonstration concrète du principe : on programme contre une interface, pas contre une implémentation. L'héritage aurait échoué ici (Stripe et PayPal n'ont aucun parent commun naturel) ; l'interface, elle, colle parfaitement.

Glossaire

Héritage
Mécanisme par lequel une classe fille récupère les membres d'une classe parente via extends (un seul parent possible) ; parent:: rappelle la version d'origine.
Classe abstraite
Classe abstract non instanciable, qui mêle méthodes concrètes partagées et méthodes abstract que chaque fille doit implémenter.
Interface
Contrat listant des signatures de méthodes sans code ; une classe peut en implements plusieurs à la fois.
Trait
Bloc de méthodes réutilisable, injecté dans une classe avec use, sans lien d'héritage ; réutilisation « horizontale ».
Namespace
« Nom de famille » qui range les classes et évite les collisions de noms ; le séparateur est l'antislash \.
Autoloading (PSR-4)
Chargement automatique du fichier d'une classe selon une correspondance namespace → dossier ; généré par Composer.
Exception
Objet signalant une erreur, lancé avec throw et rattrapé avec try/catch ; finally s'exécute toujours.
Composition
Alternative à l'héritage où un objet en utilise un autre plutôt que d'en hériter ; souvent plus souple qu'une hiérarchie profonde.

Récap et vérification

  • Héritage : extends pour spécialiser, parent:: pour réutiliser la méthode du parent.
  • Classe abstraite : un squelette non instanciable, avec méthodes concrètes et abstract.
  • Interface : un contrat (implements), plusieurs possibles par classe.
  • Trait : du code partagé via use, sans lien d'héritage.
  • Namespace : range les classes et évite les collisions ; use pour importer.
  • Autoloading PSR-4 : Composer charge le bon fichier automatiquement.
  • Exceptions : throw / try / catch / finally, et tes propres classes d'exception.

Vérifie ta compréhension

  1. Quelle est la différence entre implements et extends, et combien de chacun une classe peut-elle avoir ?
  2. Dans quel cas choisirais-tu un trait plutôt qu'une classe parente ?
  3. Si Composer renvoie « Class not found » alors que le fichier existe, quelles deux causes vérifies-tu en premier ?
