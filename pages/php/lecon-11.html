Module 03 · PHP moderne — Leçon 11

Composer, frameworks et aller plus loin

~32 min Intermédiaire Leçon 10 recommandée

À la fin de cette leçon, tu sauras

  • Comprendre le rôle de Composer, du fichier composer.json, du dossier vendor/ et de l'autoload PSR-4 ;
  • Savoir ce qu'apportent les frameworks (Laravel, Symfony) et le pattern MVC ;
  • Connaître les moteurs de template (Twig, Blade) et l'intérêt des tests avec PHPUnit ;
  • Adopter de bonnes pratiques de déploiement : ne pas versionner les secrets ni le dossier vendor/.
Sommaire de la leçon

Jusqu'ici tu as écrit ton code PHP à la main, ligne par ligne. Mais aucun développeur professionnel ne part de zéro : il s'appuie sur des bibliothèques écrites par d'autres et sur des frameworks qui structurent toute l'application. Dans cette leçon, tu vas découvrir l'écosystème qui rend PHP moderne agréable à utiliser : l'outil composer, le dépôt Packagist, les normes PSR, les frameworks comme Laravel et Symfony, les moteurs de template, les tests et enfin le déploiement.

L'objectif n'est pas de tout maîtriser aujourd'hui, mais de te donner la carte du territoire pour savoir où chercher et par où continuer. Rappel essentiel : tout ce code s'exécute sur un serveur (via php -S ou Apache), jamais dans le navigateur.

Composer : le gestionnaire de dépendances

Composer est l'outil qui télécharge et organise les bibliothèques dont ton projet a besoin. Tu déclares tes besoins dans un fichier composer.json, et Composer s'occupe d'aller chercher les bonnes versions. Voici à quoi ressemble un composer.json de départ.

Pour ajouter une dépendance, tu n'édites même pas le fichier à la main : tu lances une commande, et Composer met à jour composer.json tout seul.

Composer télécharge les paquets dans un dossier vendor/ et génère un fichier composer.lock qui fige les versions exactes installées.

Le dossier vendor/ contient tout le code téléchargé. Tu ne le modifies jamais à la main, et tu ne le versionnes pas dans Git : n'importe qui peut le reconstruire avec composer install à partir de composer.lock.

L'autoload PSR-4 : charger ses classes automatiquement

Avant Composer, il fallait écrire un require pour chaque fichier de classe. C'était vite ingérable. L'autoload PSR-4 résout ça : tu associes un préfixe d'espace de noms à un dossier, et PHP charge le bon fichier automatiquement dès que tu utilises une classe.

Dans le composer.json ci-dessus, la règle "App\\": "src/" dit : « toute classe dans l'espace de noms App se trouve dans le dossier src/ ». Une classe App\Article vivra donc dans src/Article.php.

Une seule ligne suffit ensuite pour activer tout le mécanisme dans ton point d'entrée. Le fichier vendor/autoload.php est généré par Composer.

Note

Si tu ajoutes une nouvelle règle d'autoload dans composer.json, pense à lancer composer dump-autoload pour que Composer régénère sa table de correspondance.

Packagist : le dépôt des paquets

Packagist (packagist.org) est le grand annuaire public où sont publiés les paquets PHP. Quand tu fais composer require monolog/monolog, Composer va chercher ce paquet sur Packagist. Chaque nom suit la forme éditeur/projet.

Quelques paquets très utilisés que tu croiseras vite :

  • monolog/monolog — écrire des journaux (logs) proprement.
  • guzzlehttp/guzzle — faire des requêtes HTTP vers d'autres serveurs ou API.
  • phpunit/phpunit — écrire des tests automatisés.
  • vlucas/phpdotenv — charger des variables d'environnement depuis un fichier .env.

Astuce

Avant d'écrire toi-même un module compliqué (envoi d'e-mails, génération de PDF, calcul de dates), cherche sur Packagist : il existe presque toujours un paquet testé par des milliers de personnes.

Les normes PSR : un langage commun

Les PSR (PHP Standard Recommendations) sont des conventions partagées par toute la communauté pour que le code reste cohérent d'un projet à l'autre. Deux comptent particulièrement pour débuter :

  • PSR-4 — la règle d'autoload qu'on vient de voir : un espace de noms correspond à une arborescence de dossiers.
  • PSR-12 — le style d'écriture du code : indentation, accolades, espaces. Tout le monde écrit de la même façon, donc le code reste lisible en équipe.

Tu n'as pas à retenir PSR-12 par cœur : des outils vérifient et corrigent le style pour toi, par exemple php-cs-fixer ou phpcs.

Les frameworks : ne pas réinventer la roue

Un framework est une grosse structure prête à l'emploi qui te fournit tout ce dont une application web a besoin : le routage (associer une URL à une action), un ORM (manipuler la base de données via des objets plutôt que du SQL brut), des protections de sécurité intégrées, et un système de templates.

Les deux grands en PHP :

  • Laravel — le plus populaire, très agréable pour débuter, avec une excellente documentation.
  • Symfony — très robuste et modulaire, largement utilisé en entreprise (Laravel lui-même réutilise des composants Symfony).

La plupart des frameworks suivent le pattern MVC (Modèle - Vue - Contrôleur) : le Modèle gère les données, la Vue gère l'affichage HTML, et le Contrôleur fait le lien entre les deux. Voici l'idée d'un contrôleur Laravel (juste pour visualiser).

Remarque comme on ne touche ni au SQL, ni au routage, ni à l'échappement : le framework s'en charge.

Les moteurs de template : séparer logique et affichage

Mélanger du PHP et du HTML dans un même fichier devient vite illisible. Un moteur de template sépare clairement la logique (préparer les données) de l'affichage (produire le HTML). Les deux plus connus sont Twig (Symfony) et Blade (Laravel).

Gros avantage : l'échappement automatique. Toute variable affichée est échappée par défaut, ce qui te protège des failles XSS sans y penser.

En Twig, {{ ... }} affiche une valeur (échappée), et {# ... #} est un commentaire.

Les tests : vérifier que ça marche, automatiquement

Un test est un petit bout de code qui vérifie qu'une autre partie de ton code se comporte comme prévu. L'outil standard en PHP est PHPUnit. Quand tu modifies ton code plus tard, tu relances les tests : s'ils passent toujours, tu n'as rien cassé.

Le déploiement : mettre en ligne sans tout casser

Déployer, c'est faire tourner ton code sur un vrai serveur accessible au public. Deux règles d'or : ne jamais mettre les identifiants en dur dans le code, et ne jamais versionner les secrets.

On range les valeurs sensibles (mot de passe de la base, clés d'API) dans un fichier .env qui reste sur le serveur et n'est pas committé dans Git. Le code les lit ensuite via les variables d'environnement.

Note

Le paquet vlucas/phpdotenv lit ton fichier .env au démarrage et rend ses valeurs disponibles. On les récupère ensuite avec getenv('...') ou via le tableau $_ENV['...']. Les frameworks comme Laravel et Symfony intègrent ce mécanisme d'office.

Pour finir, ton fichier .gitignore doit au minimum exclure le dossier vendor/ et le fichier .env.

Pièges fréquents

Piège fréquent

Versionner vendor/ ou les secrets. Le dossier vendor/ est lourd et reconstructible : mets-le dans .gitignore et utilise composer install. Un fichier .env committé par erreur expose tes mots de passe à quiconque a accès au dépôt.

Piège fréquent

Réinventer ce qu'un framework offre déjà (routage, ORM, échappement) ou ignorer les normes PSR : tu obtiens du code plus fragile et illisible en équipe. Et ne pas écrire de tests, c'est avancer les yeux fermés : la moindre modification peut casser quelque chose sans que tu le saches.

Pour aller plus loin

Pour aller plus loin

Choisis un framework et suis son tutoriel officiel : Laravel ou Symfony. Explore ensuite Twig pour les templates, PHPUnit pour les tests, la création d'API REST, le déploiement avec Docker et l'intégration continue (CI/CD), et approfondis l'architecture MVC.

Un cas réel : « ça marche chez moi »

Cas réel

Une petite équipe déployait son site en copiant les fichiers par FTP, dossier vendor/ compris. Un développeur avait installé en local une version plus récente d'une bibliothèque, mais n'a envoyé au serveur que « les fichiers modifiés ». Résultat : un vendor/ incohérent en production — une classe attendue par le nouveau code manquait. Un vendredi soir, le site est tombé sur une Fatal error: Class not found, invisible en local puisque « ça marchait chez lui ». Le correctif : arrêter de transférer vendor/, le mettre au .gitignore, versionner composer.lock, et déployer en lançant composer install sur le serveur. Depuis, chaque environnement reconstruit exactement les mêmes versions à partir du .lock : le fameux « ça marche chez moi » est devenu « ça marche partout pareil ». La leçon : le code tiers ne se recopie pas à la main, il se reconstruit à l'identique depuis un fichier de verrouillage.

Antisèche

Glossaire

Composer
Gestionnaire de dépendances de PHP : il télécharge et met à jour les bibliothèques déclarées, et génère l'autoload.
composer.json
Fichier où tu déclares le nom du projet, ses dépendances (require) et les règles d'autoload ; versionné dans Git.
composer.lock
Fichier généré qui fige les versions exactes installées ; garantit le même code partout via composer install.
vendor/
Dossier du code tiers téléchargé par Composer ; reconstructible, donc jamais versionné (mis au .gitignore).
Autoload PSR-4
Convention qui associe un préfixe d'espace de noms à un dossier ; PHP charge la classe automatiquement, sans require.
Packagist
Annuaire public des paquets PHP (packagist.org) où Composer va chercher les bibliothèques, nommées éditeur/projet.
Framework
Structure prête à l'emploi (Laravel, Symfony) fournissant routage, ORM, sécurité et templates, souvent organisée en MVC.
Moteur de template
Outil (Twig, Blade) qui sépare logique et affichage et échappe automatiquement les variables (protection XSS).

Récap et vérification

  • Composer gère les dépendances via composer.json et les installe dans vendor/.
  • L'autoload PSR-4 charge tes classes automatiquement à partir d'un espace de noms.
  • Packagist est le dépôt public des paquets ; les PSR sont les conventions communes.
  • Les frameworks (Laravel, Symfony) fournissent routage, ORM, sécurité et templates, souvent en MVC.
  • Les templates (Twig, Blade) séparent logique et affichage avec échappement automatique ; PHPUnit teste le code.
  • Au déploiement, on garde les secrets hors de Git via les variables d'environnement.

Vérifie ta compréhension

  1. À quoi sert le dossier vendor/, et pourquoi ne pas le versionner dans Git ?
  2. Que fait la règle d'autoload "App\\": "src/" dans composer.json ?
  3. Cite deux avantages d'utiliser un framework plutôt que tout écrire à la main.
  4. Où ranges-tu le mot de passe de ta base de données, et pourquoi pas dans le code ?
