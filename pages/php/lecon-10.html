Bases de données avec PDO

~35 min Intermédiaire Leçon 9 recommandée

À la fin de cette leçon, tu sauras

  • savoir te connecter à une base de données avec PDO et activer le mode d'erreur ERRMODE_EXCEPTION ;
  • savoir écrire des requêtes préparées avec des paramètres pour te protéger de l'injection SQL ;
  • savoir réaliser un CRUD complet (INSERT, SELECT, UPDATE, DELETE) et récupérer les résultats avec fetch / fetchAll ;
  • savoir utiliser lastInsertId, compter les lignes affectées et regrouper des écritures dans une transaction.
Sommaire de la leçon

Jusqu'ici, tes données vivaient dans des variables PHP : dès que le script se termine, tout disparaît. Pour qu'un site retienne ses utilisateurs, ses produits ou ses messages, il faut les persister dans une base de données. PHP se connecte à des bases comme MySQL, MariaDB ou SQLite, et l'outil moderne pour le faire s'appelle PDO.

Dans cette leçon, tu vas connecter PHP à une base, lire et écrire des lignes, et surtout le faire en toute sécurité. Comme toujours, ce code tourne sur le serveur (avec php -S ou Apache) : tu ne cliques sur aucun bouton d'aperçu, tu exécutes ton script et tu observes la sortie.

Pourquoi une base de données

Une base de données stocke des informations de façon durable, organisée en tables (lignes et colonnes), un peu comme un tableur très puissant. Quand un visiteur crée un compte, tu enregistres son nom et son mot de passe haché dans une table ; au prochain passage, tu les relis.

PHP ne stocke rien lui-même : il parle à un serveur de base de données. Les plus courants sont MySQL et MariaDB. Pour apprendre sans rien installer de lourd, SQLite est parfait : la base est un simple fichier sur le disque.

Note

Le langage pour interroger une base s'appelle le SQL. PDO sert à envoyer ces requêtes SQL depuis PHP. Le cours SQL t'apprend à écrire les requêtes ; ici on voit comment les exécuter proprement.

Se connecter avec PDO

PDO (PHP Data Objects) est une interface unifiée : le même code fonctionne avec MySQL, SQLite ou PostgreSQL, on change juste la chaîne de connexion (le DSN). On crée un objet PDO avec new PDO($dsn, $user, $pass).

Tout de suite après, on configure le mode d'erreur sur ERRMODE_EXCEPTION : ainsi, la moindre erreur SQL lèvera une exception au lieu de passer inaperçue. C'est indispensable.

Pour SQLite, le DSN est encore plus simple : new PDO('sqlite:boutique.db'), sans utilisateur ni mot de passe.

Les requêtes préparées : ta défense n°1

Voici le point le plus important de toute la leçon. Ne mets JAMAIS une donnée venue de l'utilisateur directement dans une chaîne SQL. Si tu fais '... WHERE id = ' . $_GET['id'], un visiteur malveillant peut injecter du SQL et lire ou détruire ta base : c'est l'injection SQL.

La parade : une requête préparée. Tu écris la requête avec des emplacements (des paramètres), puis tu envoies les valeurs séparément. PDO les insère de façon sûre. On utilise soit des paramètres positionnels ?, soit des paramètres nommés :id.

Piège fréquent

Concaténer une entrée dans le SQL est la faille de sécurité la plus classique du web. Règle simple : dès qu'une valeur varie, elle passe par un paramètre (? ou :nom), jamais par concaténation.

Récupérer les résultats

Après un SELECT, tu lis les lignes renvoyées. fetch() donne une ligne (ou false s'il n'y en a plus), fetchAll() donne toutes les lignes d'un coup. Avec le mode FETCH_ASSOC (activé plus haut), chaque ligne est un tableau associatif où les clés sont les noms de colonnes.

Astuce

Les requêtes préparées protègent l'entrée (le SQL) ; htmlspecialchars protège la sortie (le HTML). Ce sont deux protections différentes, et il te faut les deux. Au passage, une base renvoie souvent les nombres sous forme de chaîne : caste en (float) avant un calcul ou un formatage.

lastInsertId et lignes affectées

Après un INSERT, tu as souvent besoin de l'identifiant généré (par exemple pour créer la fiche d'un utilisateur tout juste inscrit). C'est le rôle de $pdo->lastInsertId(). Après un UPDATE ou un DELETE, $stmt->rowCount() te dit combien de lignes ont été touchées.

Les transactions

Parfois, plusieurs écritures forment un tout indivisible : débiter un compte ET créditer un autre. Si la seconde échoue, il ne faut surtout pas garder la première. Une transaction regroupe ces opérations : soit tout réussit (commit), soit on annule tout (rollBack).

Grâce à ERRMODE_EXCEPTION, toute erreur SQL saute directement dans le catch, qui déclenche le rollBack.

Pièges fréquents

  • Concaténer une entrée dans le SQL. C'est l'injection SQL. Toute valeur variable passe par un paramètre ? ou :nom.
  • Identifiants en clair dans le code. Mot de passe de base écrit en dur, puis poussé sur Git : catastrophe. Lis-les depuis des variables d'environnement (getenv).
  • Oublier ERRMODE_EXCEPTION. Sans lui, une requête qui échoue renvoie false en silence et tu cherches le bug pendant des heures.
  • Ne pas gérer l'échec de connexion. Entoure le new PDO(...) d'un try/catch pour afficher un message propre, pas une trace technique.
  • Mélanger PDO et l'ancienne extension mysql_*. Les fonctions mysql_query sont supprimées de PHP moderne. Reste sur PDO partout.

Pour aller plus loin

Pour aller plus loin

Sur de gros projets, on remplace souvent le SQL manuel par un ORM (Doctrine, ou Eloquent dans Laravel) qui mappe tes tables sur des objets PHP. Les migrations versionnent la structure de la base. Pour les requêtes avancées, retourne au cours SQL. Et pour des applications propres, on injecte l'objet $pdo dans les classes qui en ont besoin plutôt que de le recréer partout (injection de dépendances).

Un cas réel : les places fantômes

Cas réel

Une billetterie enregistrait chaque réservation en deux écritures : d'abord décrémenter le stock de places (UPDATE evenements SET places = places - 1), puis insérer la commande (INSERT INTO commandes …). Tant que le trafic restait faible, tout allait bien. Un soir de mise en vente très demandée, la base a saturé et la seconde requête a échoué sur des dizaines de réservations : le stock était bien décompté, mais aucune commande ne correspondait. Résultat : des places « fantômes », bloquées et invendables, un inventaire faux, et un service client débordé. Le correctif tenait en trois lignes : envelopper les deux écritures dans beginTransaction() / commit(), avec rollBack() dans le catch. Depuis, une réservation est soit complète, soit inexistante — jamais à moitié. La leçon : dès que deux écritures n'ont de sens qu'ensemble, elles doivent vivre dans une transaction, sinon la première panne fabrique des incohérences durables.

Antisèche

Glossaire

PDO (PHP Data Objects)
Interface objet unifiée pour accéder aux bases de données ; le même code marche pour MySQL, SQLite ou PostgreSQL, en changeant seulement le DSN.
DSN
Chaîne de connexion décrivant la base à joindre ; ex. mysql:host=localhost;dbname=boutique ou sqlite:app.db.
Requête préparée
Requête où les valeurs sont fournies séparément via des paramètres ; PDO les insère sans risque d'injection SQL.
Paramètre lié
Emplacement dans la requête — positionnel ? ou nommé :id — rempli par execute(), jamais concaténé.
fetch / fetchAll
fetch() renvoie une ligne (ou false) ; fetchAll() renvoie toutes les lignes dans un tableau.
CRUD
Les quatre opérations de base sur des données : Create (INSERT), Read (SELECT), Update (UPDATE), Delete (DELETE).
Transaction
Groupe d'écritures « tout ou rien » : commit valide l'ensemble, rollBack annule tout en cas d'erreur.
ERRMODE_EXCEPTION
Mode qui fait lever une PDOException à la moindre erreur SQL, au lieu d'un échec silencieux ; à toujours activer.

Récap et vérification

  • Une base de données persiste les données ; PHP s'y connecte via PDO.
  • On crée la connexion avec new PDO($dsn, $user, $pass) et on active ERRMODE_EXCEPTION.
  • Les requêtes préparées (prepare + execute avec des paramètres) protègent de l'injection SQL.
  • On lit avec fetch / fetchAll (mode FETCH_ASSOC), et on échappe la sortie avec htmlspecialchars.
  • Le CRUD (INSERT / SELECT / UPDATE / DELETE) suit toujours le même schéma ; lastInsertId et rowCount complètent les écritures.
  • Les transactions (beginTransaction / commit / rollBack) garantissent que plusieurs écritures forment un tout indivisible.
