Module 02 · Construire — Leçon 04

Structurer les sorties (JSON, tool use)

~37 min Intermédiaire Leçon 03

À la fin de cette leçon, tu sauras

  • obtenir une réponse en JSON conforme à un schéma ;
  • valider la sortie avant de l'utiliser ;
  • expliquer le tool use (function calling) ;
  • dérouler le cycle appel d'outil → exécution → réponse.
Sommaire de la leçon

Un texte libre est agréable à lire, mais difficile à traiter par programme. Dès qu'un LLM alimente une application, on veut des sorties structurées et prévisibles : du JSON conforme à un schéma, ou des appels d'outils que ton code exécute.

Demander du JSON

La première étape : exiger le format, donner le schéma attendu, et ne demander que le JSON (pas de texte autour). On baisse aussi la température pour la fiabilité.

Le mode structuré

Demander « gentiment » du JSON ne suffit pas toujours : le modèle peut ajouter une phrase ou se tromper de forme. Beaucoup d'API offrent un mode JSON ou des sorties structurées qui garantissent une réponse conforme à un schéma fourni. Quand c'est disponible, utilise-le plutôt que d'espérer.

Toujours valider

Même en mode structuré, valide la sortie côté code (avec un schéma : JSON Schema, Pydantic, Zod…). Un LLM reste probabiliste : ne fais jamais confiance aveuglément à sa sortie avant de l'avoir vérifiée.

Le tool use (function calling)

Plus puissant encore : on déclare des outils (des fonctions, avec leur schéma d'arguments). Le modèle ne les exécute pas ; il demande leur appel en renvoyant le nom de l'outil et des arguments structurés. Ton code exécute la fonction, puis renvoie le résultat au modèle, qui formule la réponse finale.

Le cycle d'un outil

1) tu envoies la question + la liste d'outils ; 2) le modèle répond « appelle get_weather(ville:"Lyon") » ; 3) ton code exécute la vraie fonction ; 4) tu renvoies le résultat au modèle ; 5) il rédige la réponse finale pour l'utilisateur.

Pourquoi c'est essentiel

Le tool use relie le LLM au monde réel : interroger une base, appeler une API, faire un calcul exact, déclencher une action. Le modèle décide quoi appeler et avec quels arguments ; ton code garde le contrôle de l'exécution (et donc de la sécurité). C'est la brique des agents, à la leçon suivante.

Cas réel

Un assistant de service e-commerce ne doit jamais inventer le statut d'une commande. On lui donne un outil chercher_commande(numero) branché sur la vraie base. À « où en est ma commande 4821 ? », le modèle demande l'appel chercher_commande(4821) ; le code lit la base et renvoie « expédiée, livraison mardi » ; le modèle formule la réponse. On obtient la fluidité du langage et l'exactitude des données : zéro hallucination sur un fait vérifiable.

Pièges fréquents

  • Faire confiance sans valider. Parse et vérifie toujours le JSON ; gère l'échec.
  • Compter sur la politesse. Préfère un mode JSON/structuré garanti quand il existe.
  • Exécuter aveuglément un appel d'outil. Vérifie les arguments et les droits avant d'agir.
  • Température trop haute. Pour des sorties structurées, reste bas.

Pour aller plus loin

On décrit les outils et les schémas avec JSON Schema, un standard. Des bibliothèques (Pydantic en Python, Zod en TypeScript) génèrent ce schéma à partir de tes types et valident la réponse en une étape — pratique et sûr.

Pour aller plus loin

Donne des descriptions claires à chaque outil et à chaque paramètre : le modèle s'en sert pour décider quand et comment appeler. Un bon descriptif d'outil, c'est comme un bon prompt.

Antisèche

Glossaire

JSON
Format de données structuré et universel (JavaScript Object Notation). Le format de choix quand une sortie de LLM sera traitée par programme.
JSON Schema
Standard pour décrire la forme attendue d'un JSON (types, champs requis). Sert à cadrer une sortie et à décrire les paramètres d'un outil.
Mode structuré (mode JSON)
Option d'API qui garantit une réponse conforme à un schéma, au lieu d'espérer que le modèle obéisse. À préférer quand il existe.
Tool use (function calling)
Mécanisme où le modèle demande l'appel d'une fonction (nom + arguments structurés). Il ne l'exécute pas : ton code le fait.
Argument / paramètre d'outil
Les entrées d'un outil, décrites par un schéma. Le modèle les remplit ; tu les vérifies avant d'agir.
Validation
Étape où l'on parse puis contrôle la sortie contre un schéma avant de l'utiliser. Indispensable, même en mode structuré.
Pydantic / Zod
Bibliothèques (Python / TypeScript) qui génèrent un schéma à partir de tes types et valident la réponse en une étape.
Agent
Programme où le LLM enchaîne raisonnement et appels d'outils pour atteindre un but. Le tool use en est la brique de base (leçon 5).

Récap et vérification

  • Pour traiter la réponse par programme, exige du JSON conforme à un schéma.
  • Utilise le mode structuré quand il existe, et valide toujours côté code.
  • Le tool use laisse le modèle demander l'appel d'une fonction ; ton code l'exécute.
  • Cycle : question + outils → appel demandé → exécution → résultat renvoyé → réponse finale.

Vérifie ta compréhension

  1. Pourquoi valider la sortie même en mode JSON ?
  2. Qui exécute la fonction lors d'un tool use ?
  3. À quoi sert le tool use ?

Exercice 3Défi

On demande à un LLM de calculer « 1893 × 4127 ». Pourquoi vaut-il mieux passer par un outil, et comment l'organiser ?

Voir une solution

Un LLM ne calcule pas de façon fiable : il prédit un résultat plausible, souvent faux sur de gros nombres. On déclare un outil multiply(a, b) ; le modèle, face à la question, demande l'appel multiply(1893, 4127) ; ton code exécute la vraie multiplication et renvoie 7812411 ; le modèle l'intègre dans sa réponse. On obtient l'exactitude du code avec la souplesse du langage naturel.
