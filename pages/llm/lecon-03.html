Appeler une API de LLM

~35 min Intermédiaire Leçon 02

À la fin de cette leçon, tu sauras

  • structurer une conversation en messages (system/user/assistant) ;
  • envoyer une requête authentifiée à une API de LLM ;
  • lire la réponse et l'usage en tokens ;
  • protéger ta clé d'API.
Sommaire de la leçon

Passons à la pratique : appeler un LLM depuis ton code. La plupart des fournisseurs exposent une API HTTP très semblable — on envoie une liste de messages, on reçoit une réponse. Voyons la mécanique.

Le format conversationnel

Une requête de chat est une liste de messages, chacun avec un rôle : system (cadrage), user (l'utilisateur), assistant (les réponses précédentes du modèle). Pour une conversation, on renvoie tout l'historique à chaque appel — le modèle est sans mémoire entre deux requêtes.

Le modèle n'a pas de mémoire

Entre deux appels, l'API ne « retient » rien. Pour poursuivre une conversation, c'est à toi de renvoyer l'historique (system + tous les échanges). D'où l'importance de gérer le contexte (et son coût en tokens).

Lire la réponse

La réponse contient le message généré et, en général, un objet usage qui détaille les tokens consommés (entrée + sortie) — utile pour suivre le coût.

Protéger ta clé d'API

Une clé d'API est un secret : elle engage ton compte et ta facturation. Ne l'écris jamais en dur dans le code ni dans le dépôt Git. Range-la dans une variable d'environnement (souvent via un fichier .env ignoré par Git), et lis-la au lancement.

Jamais de clé côté navigateur

N'appelle pas l'API directement depuis le front-end : la clé serait visible par tous. Passe par un petit serveur (back-end) qui détient la clé et relaie les appels. C'est aussi là qu'on met les garde-fous (quotas, validation).

Cas réel

Des développeurs poussent parfois une clé d'API par mégarde dans un dépôt public sur GitHub. Des robots scannent GitHub en continu : une clé exposée peut être récupérée et exploitée en quelques minutes, générant une facture salée. Parades : clés en variables d'environnement, .env dans le .gitignore, et rotation immédiate de toute clé ayant fuité.

Quelques paramètres utiles

  • temperature : l'aléatoire (vu en leçon 1).
  • max_tokens : la longueur maximale de la réponse (et un garde-fou de coût).
  • stream : recevoir la réponse au fil de l'eau, token par token, pour un affichage progressif.

Pièges fréquents

  • Croire que l'API a une mémoire. Renvoie l'historique à chaque appel.
  • Exposer la clé. Variable d'environnement, jamais en dur, jamais dans le navigateur.
  • Ignorer l'usage. Surveille les tokens pour maîtriser le coût.
  • Oublier les erreurs. Gère les limites de débit (429) et les pannes : réessais, délais.

Pour aller plus loin

La plupart des fournisseurs offrent un SDK officiel (Python, JavaScript…) qui simplifie l'authentification, le streaming et les erreurs. Les API se ressemblent assez pour qu'on passe de l'une à l'autre sans tout réécrire — mais vérifie toujours la documentation de ta version.

Pour aller plus loin

Pense au coût et à la latence dès le départ : un prompt plus court, un modèle plus petit pour les tâches simples, un cache des réponses fréquentes… autant de leviers concrets une fois l'app en production.

Glossaire

Message
Un élément de la conversation : un objet { role, content }. La requête en est une liste, renvoyée entière à chaque appel.
Rôle (system / user / assistant)
Qui parle : le cadrage (system), l'utilisateur (user), ou les réponses passées du modèle (assistant).
Clé d'API
Secret qui authentifie tes appels et engage ta facturation. Jamais en dur dans le code, jamais côté navigateur.
Variable d'environnement
Valeur fournie au programme par son environnement (souvent via un fichier .env ignoré par Git). Endroit standard pour ranger un secret.
Bearer
Schéma d'autorisation HTTP : on envoie l'en-tête Authorization: Bearer <clé> pour prouver son identité.
usage
Objet de la réponse détaillant les tokens consommés (entrée, sortie, total). Base du suivi de coût.
Streaming
Recevoir la réponse token par token au fil de la génération (paramètre stream), pour un affichage progressif.
Back-end (proxy)
Serveur intermédiaire qui détient la clé et relaie les appels au LLM ; il porte aussi quotas, validation et journalisation.

Récap et vérification

  • Une requête chat = une liste de messages (system/user/assistant) ; l'API est sans mémoire.
  • On envoie un POST authentifié par une clé (en-tête Authorization).
  • La réponse contient le message et un objet usage (tokens).
  • Protège la clé : variable d'environnement, côté serveur, jamais dans le navigateur.

Vérifie ta compréhension

  1. Pourquoi faut-il renvoyer l'historique à chaque appel ?
  2. Où range-t-on la clé d'API, et pas où ?
  3. Que contient l'objet usage ?

Exercice 3Défi

Une application web appelle directement l'API du LLM depuis le JavaScript du navigateur, avec la clé dans le code. Quels sont les deux problèmes majeurs, et quelle architecture corrige cela ?

Voir une solution

Problèmes : (1) la clé est exposée à tout visiteur (il suffit d'ouvrir les outils du navigateur) — n'importe qui peut l'utiliser à tes frais ; (2) aucun garde-fou possible (quotas, validation, filtrage). Correction : introduire un back-end qui détient la clé en variable d'environnement ; le navigateur appelle ton serveur, qui valide la demande puis relaie l'appel au LLM. La clé ne quitte jamais le serveur.
