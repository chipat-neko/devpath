Patterns d'architecture : MVC, MVVM, Repository

~35 min Intermédiaire Leçon 09 requise

À la fin de cette leçon, tu sauras

  • séparer interface, logique et données avec MVC ;
  • comprendre ce qu'ajoute la liaison de données de MVVM ;
  • isoler la persistance derrière un Repository ;
  • reconnaître ces architectures dans les frameworks du marché.
Sommaire de la leçon

Les patterns vus jusqu'ici opèrent à l'échelle de quelques classes. Les patterns d'architecture, eux, organisent une application entière : comment répartir les responsabilités entre l'interface, la logique et les données ? En voici trois incontournables, ceux qui reviennent dans presque toutes les offres d'emploi.

MVC — Modèle, Vue, Contrôleur

Le pattern MVC répartit une application en trois rôles : le Modèle (les données et les règles métier), la Vue (l'affichage) et le Contrôleur (qui reçoit les actions de l'utilisateur, met à jour le modèle, puis choisit la vue à présenter). Le but : découpler l'interface de la logique. La vue ignore les règles métier ; le modèle ignore comment il est affiché.

MVVM — quand la liaison de données entre en jeu

Le MVVM (Modèle – Vue – Vue-Modèle) est né des interfaces à liaison de données (data binding). Le Vue-Modèle expose l'état et les commandes que la vue consomme ; une liaison synchronise automatiquement la vue et le vue-modèle dans les deux sens. Plus besoin d'écrire à la main le code qui rafraîchit l'affichage : la vue devient déclarative (« affiche cette valeur ») et le vue-modèle ne connaît même pas la vue.

Une famille, mille variantes

MVC a de nombreux cousins : MVP (Model-View-Presenter), MVVM, le MTV de Django (même idée, autres noms). Ne te crispe pas sur les frontières exactes — elles varient d'un framework à l'autre. Retiens l'invariant : séparer la présentation de la logique et des données, pour qu'un changement d'écran ne touche pas les règles métier.

Repository — abstraire l'accès aux données

Le Repository (dépôt) place une couche entre la logique métier et la source de données (base SQL, API, fichier). Le métier manipule ce qui ressemble à une collection d'objets en mémoire — depot.parId(1), depot.enregistrer(u) — sans savoir d'où ils viennent. On peut alors changer de source (SQL → API) sans toucher au métier, et tester avec un dépôt en mémoire.

Gare au « contrôleur obèse »

L'erreur la plus fréquente en MVC est le fat controller : on entasse la logique métier dans le contrôleur (ou pire, dans la vue). Le contrôleur ne doit qu'orchestrer : recevoir l'action, déléguer au modèle, choisir la vue. Les règles métier vivent dans le modèle ; l'accès aux données, dans le Repository.

Le Repository rend les tests triviaux

Avec un DepotMemoire, tu testes toute ta logique métier sans base de données : pas d'installation, pas de nettoyage entre tests, exécution instantanée. C'est le mariage direct avec la leçon 09 (injection) et le cours Tests & qualité.

Cas réel : le vocabulaire commun du marché

Ces trois patterns sont partout : Ruby on Rails, Django et Laravel structurent le web serveur en MVC ; Angular et Vue.js appliquent MVVM avec leur liaison de données ; et le Repository est au cœur de Spring Data (Java), d'Entity Framework (.NET) et de Doctrine (PHP), qui génèrent parfois les dépôts pour toi. Les connaître, c'est parler la langue de n'importe quelle équipe.

Pour aller plus loin

Ces patterns se prolongent dans des architectures complètes : la Clean Architecture et l'architecture hexagonale (ports et adaptateurs) poussent l'idée à son terme — un cœur métier pur, entouré d'adaptateurs (UI, base, API) branchés par injection. Le Repository y est un « port » ; MVC/MVVM y organisent l'adaptateur d'interface.

Glossaire

Pattern d'architecture
Modèle d'organisation d'une application entière, réglant la répartition des responsabilités entre couches.
MVC
Modèle-Vue-Contrôleur : sépare les données et règles (modèle), l'affichage (vue) et l'orchestration des actions (contrôleur).
Modèle
Couche des données et des règles métier ; elle ignore comment elle est affichée.
Vue
Couche d'affichage ; elle présente l'état sans connaître les règles métier.
Contrôleur
Couche qui reçoit les actions de l'utilisateur, met à jour le modèle et choisit la vue ; il orchestre, sans porter la logique.
MVVM
Modèle-Vue-Vue-Modèle : variante où une liaison de données synchronise automatiquement la vue et un vue-modèle.
Liaison de données (data binding)
Synchronisation automatique, souvent bidirectionnelle, entre l'interface et l'état ; supprime le code de rafraîchissement manuel.
Repository (dépôt)
Couche qui présente les données comme une collection en mémoire, masquant la source réelle (base, API, fichier) où elles sont conservées durablement (persistance).

Récap et vérification

  • MVC sépare affichage (vue), orchestration (contrôleur) et données + règles (modèle).
  • MVVM ajoute une liaison de données qui synchronise vue et vue-modèle automatiquement.
  • Le Repository masque la source de données : le métier manipule une « collection » et devient testable.
  • Invariant commun : séparer la présentation de la logique et des données ; éviter le contrôleur obèse.

Exercices

Exercice 1Échauffement

Dans une application MVC, on te dit qu'un développeur a écrit le calcul du prix TTC directement dans la vue (le gabarit HTML). Quel principe est violé, et où ce calcul devrait-il être ?

Voir une solution

La séparation des responsabilités est violée : la vue doit seulement afficher, pas calculer. Le calcul du prix TTC est une règle métier : il doit vivre dans le Modèle (ou un service métier). La vue se contente ensuite d'afficher la valeur déjà calculée. Sinon, la même règle risque d'être dupliquée dans chaque gabarit.

Exercice 2Application

Écris un DepotProduitsMemoire avec parId(id) et enregistrer(p), puis un Catalogue qui reçoit ce dépôt par injection et expose ajouter(p).

Voir une solution

Le Catalogue ignore que le dépôt est en mémoire : en production, on lui injecterait un DepotProduitsSQL respectant le même contrat.

Exercice 3Défi

Explique, avec le compteur du cours, la différence de flux entre MVC et MVVM lorsqu'on clique sur « + ».

Voir une solution

En MVC : le clic déclenche le contrôleur, qui appelle modele.incrementer() puis demande explicitement à la vue de se rafraîchir avec la nouvelle valeur — c'est le contrôleur qui pousse la mise à jour. En MVVM : le bouton est lié à une commande du vue-modèle qui incrémente une propriété observable ; la liaison de données met alors la vue à jour automatiquement, sans qu'aucun code n'ait à appeler « rafraîchis l'affichage ». Le vue-modèle ne connaît même pas la vue : il ne fait qu'exposer un état, et la liaison s'occupe du reste.
