Module 3 · Comportement — Leçon 06

Bien utiliser les patterns

~33 min Avancé Leçon 05 requise

À la fin de cette leçon, tu sauras

  • éviter la sur-ingénierie ;
  • reconnaître quelques anti-patterns ;
  • faire émerger un pattern par le refactoring ;
  • décider quand un pattern aide… et quand il nuit.
Sommaire de la leçon

Connaître les patterns crée une tentation : les appliquer partout pour montrer qu'on les maîtrise. C'est une erreur fréquente et coûteuse. Un pattern mal placé ajoute de la complexité au lieu d'en retirer. Cette leçon est aussi importante que les précédentes : elle t'apprend à utiliser les patterns avec discernement — y compris à ne pas les utiliser.

Le piège de la sur-ingénierie

La sur-ingénierie (over-engineering) consiste à rendre un code plus compliqué que le problème ne l'exige. Appliquer une fabrique, une stratégie et un observateur pour afficher « Bonjour », c'est noyer une solution triviale sous des couches d'abstraction qui n'apportent rien.

Chaque pattern a un coût : plus de classes, plus d'indirection, plus à comprendre pour le prochain développeur. Ce coût n'est justifié que si le pattern résout un vrai problème présent (variation, couplage, complexité). En son absence, le code le plus simple qui marche est le meilleur.

Les anti-patterns

Un anti-pattern est une « solution » couramment employée mais contre-productive. Les reconnaître évite de répéter des erreurs connues :

  • God Object (objet-dieu) : une classe qui fait tout, sait tout, et que personne n'ose toucher. Viole la responsabilité unique ; à découper.
  • Spaghetti code : un flux de contrôle si emmêlé qu'on ne peut plus le suivre. Symptôme d'une absence de structure.
  • Golden Hammer (marteau d'or) : « quand on a un marteau, tout ressemble à un clou » — appliquer son pattern (ou son outil) préféré à tous les problèmes.
  • Copier-coller : dupliquer du code au lieu de le factoriser ; chaque bug doit alors être corrigé à dix endroits.

Le point commun : ces anti-patterns semblent rapides à court terme, mais creusent une dette technique qui ralentit tout le projet ensuite. Les patterns bien employés sont, à l'inverse, des investissements qui paient sur la durée.

Faire émerger les patterns

La meilleure façon d'utiliser un pattern n'est souvent pas de le décider à l'avance, mais de le laisser émerger par le refactoring. On écrit d'abord la solution la plus simple ; quand un besoin réel apparaît (le code se répète, une variation se multiplie), on refactore vers le pattern qui le résout.

Cette approche évite la sur-ingénierie : le pattern n'apparaît que lorsqu'il gagne sa place. C'est le pont avec le cours Tests & qualité : une bonne suite de tests te donne le filet de sécurité pour refactorer vers un pattern sans crainte de casser le comportement.

La bonne question à se poser

Avant d'introduire un pattern, pose-toi : « quel problème concret cela résout-il, ici, maintenant ? » Si tu peux nommer le problème (ce switch grossit à chaque type → Strategy ; cette lib a une interface incompatible → Adapter), le pattern est justifié. Si la seule réponse est « c'est plus propre » ou « au cas où », abstiens-toi.

Pour aller plus loin

Tu as les bases pour reconnaître et appliquer les patterns essentiels. Pour approfondir : le livre du Gang of Four et l'excellent site Refactoring Guru (patterns illustrés) ; les patterns spécifiques à un domaine (architecture MVC/MVVM, patterns d'entreprise, patterns de concurrence) ; et surtout, la pratique du refactoring, qui est l'art de faire évoluer un code vers de meilleures structures. Retiens l'essentiel : les patterns sont un moyen au service de la simplicité et de la clarté, jamais une fin en soi.

Cas réel : quand l'abstraction devient une blague

La communauté des développeurs se moque volontiers de la sur-ingénierie : le dépôt FizzBuzzEnterpriseEdition réimplémente le minuscule exercice « FizzBuzz » avec des dizaines de fabriques, stratégies et interfaces — des milliers de lignes pour afficher des nombres. Même dans du vrai code, des classes au nom de AbstractSingletonProxyFactoryBean ont fini par exister. La leçon : une abstraction qui ne résout aucun problème présent n'est pas « professionnelle », elle est juste coûteuse.

La règle de trois

Un repère simple contre l'abstraction prématurée : duplique une fois, hésite deux fois, factorise à la troisième. Deux morceaux de code qui se ressemblent ne justifient pas encore une abstraction — ils divergent souvent ensuite. Attends la troisième occurrence : le motif est alors réel, stable, et le pattern gagne sa place sans que tu devines l'avenir.

Glossaire

Sur-ingénierie (over-engineering)
Rendre un code plus compliqué que le problème ne l'exige ; empiler des abstractions qui n'apportent rien.
Anti-pattern
« Solution » répandue mais contre-productive, qu'il vaut mieux reconnaître pour l'éviter.
God Object (objet-dieu)
Classe qui concentre trop de responsabilités ; fragile, intestable, à découper selon la responsabilité unique.
Spaghetti code
Code au flux de contrôle si emmêlé qu'on ne peut plus le suivre ; symptôme d'une absence de structure.
Golden Hammer (marteau d'or)
Réflexe d'appliquer son outil ou pattern préféré à tous les problèmes, qu'il convienne ou non.
Dette technique
Coût futur accumulé par des raccourcis de conception : chaque compromis se paie en lenteur et en bugs plus tard.
Refactoring
Améliorer la structure interne d'un code sans changer son comportement ; c'est ainsi qu'un pattern émerge.
YAGNI
You Aren't Gonna Need It : n'ajoute pas une capacité « au cas où » ; attends le besoin réel.

Récap et vérification

  • La sur-ingénierie applique des patterns là où le problème ne le demande pas : chaque pattern a un coût.
  • Les anti-patterns (God Object, spaghetti, golden hammer, copier-coller) sont des erreurs connues à éviter.
  • Laisser un pattern émerger par le refactoring, quand un besoin réel apparaît, plutôt que le forcer d'avance.
  • Critère : nommer le problème concret que le pattern résout ici et maintenant ; sinon, s'abstenir (YAGNI).

Vérifie ta compréhension

  1. Qu'est-ce que la sur-ingénierie, et pourquoi l'éviter ?
  2. Cite un anti-pattern et explique son problème.
  3. Quelle question se poser avant d'introduire un pattern ?

Exercices

Exercice 1Échauffement

Un développeur ajoute une Factory, un Singleton et une Strategy pour un script de 20 lignes qui lit un fichier. Quel est le problème ?

Voir une solution

C'est de la sur-ingénierie : ces patterns ajoutent des classes, de l'indirection et de la complexité sans résoudre aucun problème réel du script. Pour 20 lignes qui lisent un fichier, une simple fonction suffit. On n'introduit un pattern que lorsqu'un besoin concret le justifie.

Exercice 2Application

Une classe GestionTout gère les utilisateurs, les commandes, les paiements, les e-mails et les logs. Nomme l'anti-pattern et propose une direction.

Voir une solution

C'est un God Object (objet-dieu) : une classe qui fait tout, viole la responsabilité unique, et devient impossible à tester ou modifier sans risque. Direction : la découper en classes à responsabilité unique — ServiceUtilisateur, ServiceCommande, ServicePaiement, ServiceEmail, Journal — chacune cohérente et testable indépendamment.

Exercice 3Défi

Tu as un if/else qui choisit entre deux modes de calcul. Faut-il déjà introduire le pattern Strategy ? Sous quelle condition le ferais-tu ?

Voir une solution

Pas forcément. Pour deux cas simples, un if/else est parfaitement lisible ; introduire Strategy maintenant serait de la sur-ingénierie. On laisse émerger le pattern : si le nombre de modes se multiplie (quatre, cinq variantes), si chaque mode devient complexe, ou si l'on doit en ajouter régulièrement sans rouvrir le code existant, alors Strategy gagne sa place et on refactore vers lui — idéalement protégé par des tests. Le critère est le besoin réel et présent, pas l'anticipation.

Exercice 4Application

Complète l'acronyme qui résume la règle « n'ajoute pas une capacité au cas où, attends le besoin réel » : Y….

Voir une solution

YAGNI — You Aren't Gonna Need It (« tu n'en auras pas besoin »). C'est le garde-fou contre l'abstraction prématurée : on n'introduit une structure (dont un pattern) que lorsqu'un besoin réel et présent la justifie, jamais par anticipation.

Exercice 5Au clavier

Un patron n'est justifié que si son effet se mesure. Écris memoiser(fn), un décorateur qui garde les résultats déjà calculés, décore une fonction qui compte ses propres appels, appelle-la avec 2, 3, 2, 3, 2, puis affiche le JSON de [resultats, appelsReels].
