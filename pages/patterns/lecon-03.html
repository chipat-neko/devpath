Patterns de création

~38 min Intermédiaire Leçon 02 requise

À la fin de cette leçon, tu sauras

  • déléguer l'instanciation avec Factory Method ;
  • garantir une instance unique avec Singleton (et ses pièges) ;
  • construire un objet complexe avec Builder ;
  • reconnaître quand chacun s'applique.
Sommaire de la leçon

Les patterns de création répondent à une même question : « comment instancier des objets sans coupler le code au type concret ? » Créer un objet avec new MaClasse() partout fige la dépendance à cette classe précise. Les patterns de création introduisent une indirection qui rend l'instanciation plus souple. On en voit trois parmi les plus utiles.

Factory Method

Le pattern Factory Method (fabrique) délègue la création d'objets à une méthode dédiée, plutôt que d'appeler new directement. Le code appelant demande « un produit » sans savoir quelle classe concrète sera instanciée.

Avantage : la logique de choix vit en un seul endroit (respect du principe ouvert/fermé — ajouter un transport ne modifie que la fabrique), et le code client dépend d'une abstraction (un transport) plutôt que d'une classe précise. C'est l'un des patterns les plus répandus.

Singleton

Le Singleton garantit qu'une classe n'a qu'une seule instance, accessible globalement. On l'utilise pour une ressource unique : une configuration, un pool de connexions, un journal (logger).

Attention : le Singleton est controversé. Il introduit un état global qui complique les tests (difficile à remplacer par un fake) et masque les dépendances (une classe utilise le Singleton sans l'annoncer dans ses paramètres). Beaucoup d'experts préfèrent l'injection de dépendance : créer une seule instance au démarrage et la passer aux objets qui en ont besoin. Utilise le Singleton avec parcimonie, en connaissant ses coûts.

Builder

Le Builder (monteur) sert à construire un objet complexe pas à pas, surtout quand il a de nombreux paramètres optionnels. Il évite les constructeurs à rallonge où l'on ne sait plus ce que signifie chaque argument.

Le Builder rend la construction lisible (chaque étape porte un nom) et flexible (on ne fournit que les options voulues). Le construire() final assemble et renvoie l'objet. C'est précieux pour des objets de configuration riches.

Piège fréquent

Tu écris ton premier Builder et la chaîne casse net, sur un TypeError dès le deuxième maillon. La cause est presque toujours la même : une méthode d'étape qui oublie son return this. Sans lui, l'étape renvoie undefined, et l'appel suivant s'applique à cet undefined au lieu du monteur. Retiens la règle : chaque étape renvoie le monteur, et seul construire() renvoie l'objet fini.

Les patterns évoluent avec les langages

Certains patterns de création sont en partie intégrés aux langages modernes : les arguments nommés ou par défaut réduisent le besoin de Builder ; les modules réduisent celui de Singleton. Les comprendre reste utile — pour les reconnaître dans les bibliothèques et pour saisir quel problème ils résolvent — mais vérifie toujours si ton langage offre déjà une solution plus simple.

Cas réel : tu as déjà croisé ces trois patterns

Ils sont partout dans les outils du quotidien. document.createElement("div") est une Factory Method : tu demandes un élément par son nom sans instancier la classe DOM concrète. Les constructeurs de requêtes comme knex('users').where(...).orderBy(...) (SQL) sont des Builders — on assemble la requête par étapes chaînées. Et le journal partagé d'une application (un seul logger pour tout le programme) est le cas d'usage typique du Singleton.

Reconnaître un pattern à sa signature

Un chaînage qui se termine par un .build()/.construire() trahit un Builder. Une méthode statique getInstance()/obtenir() qui renvoie toujours le même objet, un Singleton. Une fonction create…() qui renvoie des types variés selon un paramètre, une Factory. Le nom des méthodes est souvent le meilleur indice.

Glossaire

Pattern de création
Famille de patrons qui contrôlent la fabrication des objets pour découpler le code du type concret instancié.
Factory Method (fabrique)
Déléguer l'instanciation à une méthode dédiée ; le client demande « un produit » sans connaître sa classe concrète.
Singleton
Pattern garantissant une seule instance d'une classe, accessible globalement ; controversé à cause de son état global.
Builder (monteur)
Construire un objet complexe par étapes nommées, souvent via un chaînage fluide, avant un construire() final.
État global
Donnée accessible et modifiable de partout ; source de couplage caché et de tests fragiles (reproché au Singleton).
Chaînage fluide (fluent)
Style où chaque méthode renvoie l'objet lui-même, permettant d'enchaîner les appels : a.x().y().z().
Instanciation
Action de créer un objet à partir d'une classe (le new) ; c'est ce que les patterns de création encadrent.

Récap et vérification

  • Factory Method : déléguer l'instanciation à une méthode ; le client dépend d'une abstraction, la décision est centralisée.
  • Singleton : une instance unique accessible globalement ; controversé (état global, tests difficiles) — préférer souvent l'injection.
  • Builder : construire un objet complexe pas à pas, lisible et flexible.
  • Vérifie toujours si le langage offre déjà une solution plus simple.

Exercice 3Défi

On te demande de remplacer un Singleton Config par de l'injection de dépendance pour faciliter les tests. Explique la démarche.

Voir une solution

Au lieu que chaque classe appelle Config.obtenir() en interne (couplage à l'état global), on crée une seule instance de Config au démarrage de l'application, puis on la passe en paramètre (constructeur ou argument) aux objets qui en ont besoin. Exemple : new Service(config) au lieu de Config.obtenir() dans le service. Bénéfices : en test, on fournit une fausse config (un fake) sans état global persistant ; et chaque classe annonce sa dépendance dans sa signature, au lieu de la masquer. On garde l'avantage « une seule instance » sans les inconvénients du Singleton.

Exercice 4Au clavier

Un singleton ne se prouve pas par l'intention : il se prouve en COMPTANT les constructions. Écris Config avec une méthode statique instance() qui ne construit qu'une seule fois, et un compteur Config.construites. Appelle instance() trois fois, puis affiche le JSON de [a === b, a === c, Config.construites].
