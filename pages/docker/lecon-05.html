Module 2 · Applications réelles — Leçon 05

Orchestrer avec Docker Compose

~40 min Intermédiaire Leçon 04 requise

À la fin de cette leçon, tu sauras

  • décrire plusieurs services dans un compose.yaml ;
  • déclarer build, ports, volumes, variables ;
  • exprimer une dépendance entre services ;
  • tout lancer avec docker compose up.
Sommaire de la leçon

À la leçon précédente, relier une app à une base demandait plusieurs commandes docker run, un réseau créé à la main, des options à ne pas oublier. Pour une vraie application — souvent plusieurs services (web, base, cache…) — ça devient vite ingérable. Docker Compose résout ça : on décrit toute l'application dans un seul fichier, et une commande lance le tout. C'est l'outil que tu utiliseras au quotidien en développement.

Un fichier, toute l'application

Compose lit un fichier compose.yaml (anciennement docker-compose.yml) écrit en YAML. Chaque service y décrit un conteneur. Voici une application web + base de données complète :

Tout ce que tu faisais en plusieurs docker run est là, déclaré clairement : deux services (api et bdd), leurs ports, variables, volumes et dépendances. Le fichier est la documentation de ton infrastructure.

Anatomie d'un service

Chaque service combine les notions des leçons précédentes :

  • build: . ou image: ... : soit construire depuis un Dockerfile local, soit utiliser une image toute prête.
  • ports : la publication -p (hôte:conteneur), en liste.
  • environment : les variables d'environnement (mots de passe, URL…).
  • volumes : la persistance des données, comme -v.
  • depends_on : l'ordre de démarrage entre services.

Avantage majeur, automatique : Compose crée un réseau commun à tous les services du fichier. L'api joint donc la base par son nom de service bdd (vu dans DATABASE_URL), sans aucune configuration réseau manuelle. La leçon 4 expliquait le mécanisme ; Compose te l'offre gratuitement.

Lancer et piloter

Une poignée de commandes pilote toute l'application :

docker compose up -d lit le fichier, construit les images, crée le réseau et les volumes, et démarre les services dans le bon ordre — le tout en une commande. docker compose down défait proprement l'ensemble. Attention : down -v efface aussi les volumes (donc les données) ; à manier avec prudence.

Reconstruire et cibler un service

Après avoir modifié ton code, docker compose up -d --build reconstruit les images avant de redémarrer. Tu peux aussi n'agir que sur un service : docker compose up -d api ne (re)démarre que l'api, et docker compose logs -f api ne suit que ses journaux — pratique quand une seule brique pose problème.

depends_on ne suffit pas toujours

depends_on garantit l'ordre de démarrage, mais pas que le service soit prêt : une base de données peut être démarrée sans encore accepter les connexions. Pour une vraie robustesse, ajoute un healthcheck (Compose peut attendre qu'un service soit « sain ») ou une logique de reconnexion dans l'application. Ne suppose jamais qu'un service dépendant est instantanément opérationnel.

L'indentation YAML

Le YAML est sensible à l'indentation (avec des espaces, jamais de tabulations). Une erreur d'alignement change la structure et provoque une erreur. Les niveaux s'emboîtent : services > le nom du service > ses clés (build, ports…) > leurs valeurs. Les listes commencent par un tiret -. Si Compose refuse ton fichier, vérifie d'abord l'indentation : c'est la cause n°1.

Cas réel : l'arrivée d'un nouveau développeur

Avant Compose, intégrer une recrue prenait une demi-journée : installer PostgreSQL et Redis sur sa machine, créer la base, régler dix variables d'environnement, lancer les migrations… avec l'inévitable « ça marche pas chez moi » dû à une version différente. Depuis qu'un compose.yaml décrit toute la pile, l'intégration tient en deux commandes : git clone puis docker compose up. Chacun obtient exactement le même environnement, et le fichier versionné évolue avec le projet.

Glossaire

Docker Compose
Outil qui décrit et lance une application multi-conteneurs à partir d'un seul fichier compose.yaml.
Service
Un conteneur décrit dans Compose (son image ou son build, ses ports, variables, volumes…). Un fichier en compte souvent plusieurs.
compose.yaml
Fichier (anciennement docker-compose.yml) où toute l'application est déclarée en YAML.
YAML
Format texte structuré par l'indentation (espaces, jamais de tabulation) ; les listes commencent par un tiret.
Indentation
Décalage en espaces qui définit l'emboîtement des blocs ; une erreur d'alignement change la structure et casse le fichier.
depends_on
Déclare qu'un service démarre après un autre ; garantit l'ordre, pas que le service soit prêt.
Healthcheck
Test périodique qui indique si un service est réellement « sain » ; permet d'attendre qu'une dépendance soit prête, pas seulement démarrée.
Réseau par défaut
Réseau que Compose crée automatiquement : chaque service y est joignable par son nom, sans configuration.

Récap et vérification

  • Docker Compose décrit une application multi-services dans un seul compose.yaml.
  • Un service combine build/image, ports, environment, volumes, depends_on.
  • Compose crée un réseau commun : les services se joignent par leur nom.
  • docker compose up -d lance tout ; down défait (down -v efface aussi les volumes).

Vérifie ta compréhension

  1. Quel avantage principal Compose offre-t-il par rapport à des docker run séparés ?
  2. Comment, dans un compose.yaml, l'api joint-elle le service bdd ?
  3. Que fait docker compose down -v de plus que down ?
