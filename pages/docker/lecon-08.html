Module 4 · Docker au quotidien — Leçon 08

Développer dans des conteneurs

~40 min Intermédiaire Leçon 07 requise

À la fin de cette leçon, tu sauras

  • monter ton code dans un conteneur avec un bind mount ;
  • obtenir un rechargement à chaud en développement ;
  • configurer tout ça dans Compose (watch, .env) ;
  • distinguer un usage dev d'un usage production.
Sommaire de la leçon

Reconstruire une image à chaque console.log ajouté ? Impensable au quotidien. En développement, on modifie le code des dizaines de fois par heure : il faut que le conteneur voie ces changements immédiatement, sans repasser par docker build. Tout tient en deux idées : monter le code source de ta machine dans le conteneur, et laisser un outil recharger l'application à chaque sauvegarde. Le conteneur devient alors un environnement de dev partagé et jetable — sans installer Node, Python ou PostgreSQL sur ta propre machine.

Le problème : reconstruire tue le rythme

Souviens-toi : une image est une photo figée du code au moment du build. Si tu modifies une ligne, l'image ne change pas ; il faudrait la reconstruire puis relancer le conteneur pour voir l'effet. Quelques secondes à chaque fois ? Multiplié par cent modifications par jour, c'est le rythme du développement qui s'effondre. Il nous faut un lien vivant entre le code sur le disque et le conteneur.

Monter son code : le bind mount

Un bind mount relie un dossier précis de ta machine à un dossier du conteneur. On l'active avec la même option -v que les volumes, mais en donnant un chemin à gauche :

Désormais, /app dans le conteneur est ton dossier de travail : chaque fichier que tu enregistres dans l'éditeur est vu instantanément à l'intérieur. Attention à ne pas confondre avec le volume nommé de la leçon 4 : celui-ci est géré par Docker pour persister des données (une base, par exemple), il est opaque et rangé hors de ton dossier. Le bind mount, lui, expose un dossier bien réel de ton disque — parfait pour le code en cours d'écriture.

Recharger à chaud

Le bind mount rend les fichiers visibles ; encore faut-il que l'application redémarre pour prendre en compte le nouveau code. C'est le rôle d'un outil de surveillance (watcher) que tu connais peut-être déjà : nodemon pour Node, le serveur de dev de Vite, flask --debug, uvicorn --reload… Il observe les fichiers montés et relance le process à chaque changement. Bind mount plus watcher, c'est la boucle « éditer → sauver → voir » en quelques secondes.

Avec Compose : bind mounts et watch

En pratique, on décrit tout ça dans compose.yaml. La façon classique : un bind mount déclaré dans volumes. La façon moderne : la section develop: avec watch:, qui synchronise les fichiers (ou reconstruit) automatiquement.

Lancé avec docker compose watch, Compose surveille les chemins déclarés : une modification dans ./src est synchronisée à chaud, tandis qu'un changement de package.json déclenche une reconstruction. Tu obtiens un environnement de dev complet (app + base + cache) qui se met à jour tout seul.

La configuration : variables et .env

Une application a besoin de configuration : URL de base de données, clés, mode debug. On ne la code pas en dur : on la passe par des variables d'environnement. Compose lit automatiquement un fichier .env placé à côté du compose.yaml et substitue les ${VARIABLES} :

Séparer la configuration du code permet de changer un port ou un mot de passe sans toucher aux fichiers versionnés ; le .env, lui, reste hors du dépôt (via .gitignore).

Protéger node_modules du bind mount

Piège classique : en montant tout ton dossier (./:/app), tu écrases le node_modules installé dans l'image par celui — souvent absent ou incompatible — de ton hôte. La parade : ajouter un volume anonyme qui préserve le dossier du conteneur, - /app/node_modules. Déclaré après le bind mount, il « protège » ce sous-dossier et laisse les dépendances de l'image intactes.

Le bind mount, c'est pour le dev — pas la prod

En production, une image doit être autonome : elle contient son code, on la déploie telle quelle. Un bind mount la rendrait dépendante d'un dossier présent sur le serveur — fragile et non reproductible. Réserve les bind mounts au développement ; pour la prod, le code est COPYé dans l'image au build (leçon 6). Beaucoup d'équipes ont deux fichiers : compose.yaml (base) et compose.override.yaml (surcouche dev avec les bind mounts).

Cas réel : le même environnement pour toute l'équipe

Sur un projet réel, chaque développeur avait « sa » version de Node, « sa » base locale, « ses » variables : les bugs « ça marche chez moi » pullulaient. En passant le dev dans Compose — bind mount du code, base PostgreSQL en service, .env d'exemple versionné — l'intégration est devenue : git clone, cp .env.example .env, docker compose watch. Trois lignes, et chacun code dans exactement le même environnement que la production, quelle que soit sa machine. Les incidents d'environnement ont quasiment disparu.

Pour aller plus loin : les Dev Containers

VS Code pousse l'idée plus loin avec les Dev Containers : un fichier .devcontainer/devcontainer.json décrit l'image, les extensions et les réglages de l'éditeur. Ouvre le projet, et VS Code s'exécute à l'intérieur du conteneur : terminal, débogueur, IntelliSense, tout tourne dans l'environnement conteneurisé. GitHub Codespaces s'appuie sur le même format pour offrir un poste de dev complet dans le navigateur.

Antisèche

Glossaire

Bind mount
Montage d'un dossier précis de l'hôte dans le conteneur (-v ./src:/app) : les fichiers y sont partagés en direct, idéal pour le code en dev.
Volume nommé
Stockage géré par Docker, hors de ton dossier, pour persister des données (opaque) ; à ne pas confondre avec le bind mount.
Rechargement à chaud
Redémarrage automatique de l'application quand le code change ; assuré par un watcher (nodemon, Vite…).
Watcher
Outil qui surveille les fichiers et relance le process à chaque modification.
docker compose watch
Commande qui synchronise (sync) ou reconstruit (rebuild) selon la section develop.watch du compose.yaml.
.env
Fichier de variables lu automatiquement par Compose pour substituer les ${VARIABLES} ; gardé hors du dépôt.
Variable d'environnement
Valeur de configuration passée au conteneur (port, mot de passe, mode) ; sépare la config du code.
Dev Container
Environnement de développement décrit par devcontainer.json, dans lequel l'éditeur s'exécute directement.

Récap et vérification

  • Un bind mount (-v ./src:/app) rend ton code visible dans le conteneur, sans reconstruire.
  • Un watcher (nodemon, Vite…) recharge l'app à chaque sauvegarde : boucle de dev rapide.
  • Compose automatise via develop.watch (docker compose watch) et lit la config depuis .env.
  • Le bind mount est réservé au dev ; en prod, le code est inclus dans l'image (autonome).

Vérifie ta compréhension

  1. Comment voir ses modifications de code dans un conteneur sans docker build ?
  2. Le bind mount suffit-il à recharger l'application ?
  3. Pourquoi ajouter - /app/node_modules quand on monte tout son dossier ?

Exercices

Exercice 1Échauffement

Écris une commande docker run qui lance node:20 en montant le dossier courant sur /app et en s'y plaçant, puis exécute npm run dev.

Voir une solution

-v "$(pwd):/app" monte le dossier courant, -w /app définit le répertoire de travail, et la commande finale démarre le serveur de dev.

Exercice 2Application

Dans un compose.yaml, ajoute à un service web un bind mount du dossier courant vers /app, et fais lire le port depuis une variable ${APP_PORT}.

Voir une solution

Le bind mount partage le code ; ${APP_PORT} est lu depuis le fichier .env voisin. On sépare ainsi la config du code.

Exercice 3Défi

Ton bind mount ./:/app écrase le node_modules installé dans l'image. Comment le préserver tout en gardant le partage du code ?

Voir une solution

Le volume anonyme /app/node_modules, déclaré après le bind mount, « masque » ce sous-dossier : Docker y garde les dépendances installées dans l'image au lieu de les faire écraser par le dossier de l'hôte.
