Module 4 · Docker au quotidien — Leçon 07

Publier ses images : registres et tags

~35 min Intermédiaire Leçon 06 requise

À la fin de cette leçon, tu sauras

  • expliquer ce qu'est un registre et lire un nom d'image ;
  • te connecter avec docker login et pousser une image ;
  • étiqueter avec docker tag et tirer ailleurs ;
  • choisir des tags de version plutôt que latest.
Sommaire de la leçon

Jusqu'ici, tes images vivaient sur ta seule machine : tu les construisais avec docker build, tu les lançais avec docker run. Mais une image ne prend toute sa valeur que si on peut la partager : avec un serveur de production, un collègue, une chaîne d'intégration continue. C'est le rôle d'un registre — un entrepôt d'images où l'on pousse (push) ce qu'on a construit et d'où l'on tire (pull) ce dont on a besoin. Tu t'en sers déjà sans le savoir : chaque FROM node:20 va chercher une image sur un registre public.

Qu'est-ce qu'un registre ?

Un registre stocke et distribue des images, rangées en dépôts (un dépôt = une image et toutes ses versions). Le registre par défaut est Docker Hub (docker.io) : c'est là que Docker va chercher nginx ou postgres. Il en existe d'autres : GitHub Container Registry (ghcr.io), ou les registres des fournisseurs cloud (AWS ECR, Google Artifact Registry, Azure ACR). Un dépôt peut être public (tout le monde peut tirer) ou privé (connexion obligatoire).

L'anatomie d'un nom d'image

Un nom complet d'image suit toujours la même structure : registre/espace-de-noms/dépôt:tag. Quand tu écris simplement nginx, Docker complète les parties manquantes : cela devient docker.io/library/nginx:latest. Les images officielles vivent dans l'espace library ; les tiennes, sous ton nom de compte.

Se connecter et pousser une image

Pour publier dans un dépôt (surtout privé), il faut d'abord s'authentifier une fois avec docker login. On étiquette ensuite l'image locale avec le nom complet du dépôt distant, puis on la pousse.

docker tag ne copie rien : il ajoute simplement un second nom (un alias) à une image déjà présente. C'est ce nom complet — avec le registre et l'espace de noms — qui indique à push où envoyer l'image. Sans lui, Docker tenterait de pousser vers Docker Hub sous ton compte par défaut.

Plusieurs tags pour une même image

Une image peut porter plusieurs noms à la fois. Au build, docker build -t monapp:1.2.0 -t monapp:latest . crée les deux étiquettes d'un coup ; il suffit ensuite de push chacune. Pratique pour publier à la fois une version précise (1.2.0) et un alias mouvant (latest) qui pointe vers la dernière.

Tirer et lancer ailleurs

Sur une autre machine — le serveur de production, par exemple — on récupère l'image d'une commande, puis on la lance :

docker run tire l'image tout seul si elle n'est pas déjà là : le pull explicite sert surtout à pré-télécharger ou à mettre à jour. Le même nom complet garantit que production et développement parlent exactement de la même image.

Des tags qui veulent dire quelque chose

Un tag est une étiquette lisible (1.2.0, latest, stable) posée sur une image. Rien n'empêche de déplacer un tag : republier latest le fait pointer vers une autre image. C'est pratique, mais dangereux en production, car latest ne dit jamais quelle version tourne vraiment. Pour une identité immuable, chaque image possède aussi un digest — une empreinte sha256 calculée sur son contenu : monapp@sha256:9f2c… désigne toujours le même octet près.

latest n'est pas « la dernière version »

Contrairement à ce que le nom suggère, latest n'a aucune magie : c'est un tag par défaut comme un autre, qui vaut ce qu'on a poussé dessus en dernier. Déployer monapp:latest en production, c'est accepter que le contenu change sous tes pieds sans que la commande ne bouge — impossible de savoir ce qui tourne, ni de revenir en arrière proprement. En production, épingle toujours une version explicite.

Cas réel : revenir en arrière en une commande

Une équipe déploie monapp:2.4.0 ; en quelques minutes, les erreurs explosent : une régression est passée. Comme chaque version est étiquetée et conservée dans le registre, le retour arrière tient en une ligne : docker pull monapp:2.3.0 puis relance. Le service repart sur la version précédente le temps de corriger. Si l'équipe avait déployé latest, il aurait fallu deviner quelle image se cachait derrière — et l'ancienne aurait peut-être déjà été écrasée. Des tags de version, c'est un bouton « annuler » pour la production.

Pour aller plus loin

Un registre ne s'arrête pas au push. On peut signer ses images (Docker Content Trust, cosign) pour prouver leur origine ; héberger son propre registre privé avec l'image officielle registry:2 ; ou gérer des images multi-architectures (amd64 + arm64) qui tirent la bonne variante selon la machine. Autant de sujets que tu croiseras dès que la publication devient sérieuse.

Glossaire

Registre
Serveur qui stocke et distribue des images ; on y push puis on pull. Par défaut : Docker Hub (docker.io).
Dépôt
Emplacement d'une image donnée et de toutes ses versions dans un registre (ex. noah/monapp).
Docker Hub
Registre public par défaut (docker.io) d'où proviennent les images officielles comme nginx.
GHCR
GitHub Container Registry (ghcr.io) : registre lié aux dépôts GitHub, pratique pour la CI.
Tag
Étiquette lisible posée sur une image (1.2.0, latest) ; déplaçable vers une autre image.
latest
Tag par défaut, sans magie : il vaut la dernière image poussée dessus, à éviter en production.
Digest
Empreinte sha256 calculée sur le contenu : identité immuable d'une image (@sha256:…).
docker tag
Ajoute un alias (un nom) à une image existante ; ne duplique pas les données.

Récap et vérification

  • Un registre stocke et distribue les images : on push ce qu'on construit, on pull ce qu'on déploie.
  • Un nom d'image se lit registre/espace/dépôt:tag ; les parties omises ont des valeurs par défaut.
  • docker tag ajoute un nom (alias) ; docker login authentifie ; push/pull échangent avec le registre.
  • En production, préfère un tag de version (voire un digest) à latest : traçable et réversible.

Exercices

Exercice 1Échauffement

Décompose le nom d'image docker.io/library/postgres:16 : quel est le registre, l'espace de noms, le dépôt et le tag ?

Voir une solution

Registre : docker.io (Docker Hub). Espace de noms : library (les images officielles). Dépôt : postgres. Tag : 16. Écrire simplement postgres:16 revient au même : Docker complète le registre et l'espace library.

Exercice 2Application

Tu as une image locale nommée monsite. Écris les commandes pour la publier sur GitHub Container Registry sous ghcr.io/noah/monsite en version 1.0.0.

Voir une solution

Connexion, puis on donne à l'image locale le nom complet du dépôt distant, puis on pousse cette version.

Exercice 3Défi

Tu veux publier la même image sous deux étiquettes : la version précise 2.1.0 et l'alias latest. Montre comment les créer au build puis les pousser.

Voir une solution

Les deux étiquettes pointent vers la même image : 2.1.0 restera figée, tandis que latest sera déplacé au prochain build. On garde ainsi une version traçable et un alias pratique.
