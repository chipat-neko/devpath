Module 1 · Les conteneurs — Leçon 01

Pourquoi Docker : les conteneurs

~30 min Débutant Bases de la ligne de commande utiles

À la fin de cette leçon, tu sauras

  • expliquer le problème que résout Docker ;
  • distinguer un conteneur d'une machine virtuelle ;
  • définir image, conteneur et registre ;
  • situer Docker dans le flux de développement moderne.
Sommaire de la leçon

« Ça marche sur ma machine ! » — la phrase la plus frustrante du développement. Un projet tourne chez toi, mais plante chez un collègue ou en production, parce que les versions de langage, de bibliothèques ou du système diffèrent. Docker répond exactement à ce problème : il emballe une application avec tout son environnement dans un conteneur qui s'exécute à l'identique partout. C'est devenu un outil incontournable du développement et du déploiement modernes.

Ce cours part de zéro. Tu n'as pas besoin de connaître l'administration système : juste un terminal et de la curiosité. À la fin, tu sauras conteneuriser une application et orchestrer plusieurs services.

Le problème : la reproductibilité

Une application moderne dépend d'une pile entière : une version précise du langage (Node 20, Python 3.12…), des bibliothèques, des variables d'environnement, parfois une base de données. Installer tout ça « à la main » sur chaque machine est long, fragile, et source de différences invisibles. Multiplie par le nombre de développeurs et de serveurs : le casse-tête explose.

L'idée de Docker : décrire cet environnement une fois, dans un fichier, et le rejouer à l'identique partout. Plus de « chez moi ça marche » : si ça marche dans le conteneur, ça marche partout où le conteneur tourne.

Conteneur ou machine virtuelle ?

On compare souvent Docker aux machines virtuelles (VM). Les deux isolent une application, mais à un niveau très différent. Une VM embarque un système d'exploitation complet au-dessus de l'hôte : lourd (plusieurs Go), lent à démarrer (minutes). Un conteneur, lui, partage le noyau du système hôte et n'embarque que l'application et ses dépendances : léger (quelques Mo à centaines de Mo), démarrage en une fraction de seconde.

Conséquence pratique : on peut lancer des dizaines de conteneurs sur une machine ordinaire, là où quelques VM la saturent. La contrepartie : les conteneurs partagent le noyau de l'hôte (Linux), donc l'isolation est un peu moins étanche qu'une VM — un compromis presque toujours gagnant pour le développement et le déploiement d'applications.

Les trois notions clés

Tout Docker tient autour de trois mots qu'il faut bien distinguer :

  • une image : un modèle en lecture seule contenant l'application et son environnement. C'est le « plan », figé et partageable (par ex. l'image officielle node:20).
  • un conteneur : une instance en cours d'exécution d'une image. On peut en lancer plusieurs depuis la même image, comme plusieurs objets depuis une même classe.
  • un registre (registry) : un dépôt d'images partagées. Le Docker Hub est le registre public où l'on récupère des milliers d'images officielles (bases de données, langages, serveurs web).

La relation image → conteneur est la même qu'entre une classe et un objet en programmation, ou entre une recette et un plat : l'image est le modèle figé, le conteneur est l'exécution vivante. Cette distinction est la clé de tout le reste du cours.

Ne confonds pas image et conteneur

C'est l'erreur de débutant la plus fréquente. On ne « modifie pas une image » : elle est figée. On lance un conteneur à partir d'elle, on le manipule, et à sa suppression tout ce qui n'a pas été explicitement conservé disparaît. Pour changer le modèle, on reconstruit une nouvelle image.

Installer Docker

Pour pratiquer, installe Docker Desktop (Windows, macOS) ou le moteur Docker (Linux), depuis le site officiel docker.com. Vérifie l'installation avec docker --version. Tout le reste du cours suppose Docker disponible dans ton terminal.

Où Docker s'insère

Docker accompagne tout le cycle de vie d'un projet. En développement, il te donne en une commande une base de données ou un service identique à celui de la production, sans rien installer durablement. En intégration continue, les tests s'exécutent dans un conteneur propre et reproductible. En déploiement, la même image validée part en production. Et il est la brique de base des orchestrateurs comme Kubernetes qui gèrent des conteneurs à grande échelle.

Cas réel : le premier jour d'un nouveau développeur

Avant Docker, intégrer un nouveau venu prenait souvent une à deux journées : installer la bonne version du langage, la base de données, régler les variables d'environnement, déboguer les écarts avec sa machine. Aujourd'hui, beaucoup d'équipes livrent un fichier compose.yaml : le nouveau clone le dépôt, tape docker compose up, et toute la pile (application + base + cache) démarre à l'identique en quelques minutes. L'environnement de développement devient une donnée versionnée dans le dépôt, au même titre que le code.

Pars des images officielles

Sur le Docker Hub, privilégie les images officielles (badge « Docker Official Image ») ou vérifiées : node, python, postgres, nginx… Elles sont maintenues, corrigées côté sécurité, et documentées. Épingle toujours une version précise (python:3.12) plutôt que latest, dont le contenu change dans le temps et casse la reproductibilité.

Glossaire

Docker
Plateforme qui emballe une application et son environnement dans un conteneur exécutable à l'identique partout.
Conteneur
Instance en exécution d'une image, isolée mais partageant le noyau de l'hôte ; légère et rapide à démarrer.
Image
Modèle figé en lecture seule décrivant une application et ses dépendances ; on en lance des conteneurs.
Registre
Dépôt d'images partagées d'où l'on télécharge (pull) et où l'on publie (push) des images.
Docker Hub
Le registre public de référence, riche en images officielles (langages, bases de données, serveurs web).
Machine virtuelle
Isolation par un OS invité complet au-dessus de l'hôte : plus étanche mais lourde et lente à démarrer.
Noyau (kernel)
Cœur du système d'exploitation, partagé par les conteneurs de l'hôte : la clé de leur légèreté.
Docker Desktop
Application (Windows, macOS) qui fournit le moteur Docker et une interface graphique pour pratiquer en local.

Récap et vérification

  • Docker résout la reproductibilité : emballer une app avec son environnement pour qu'elle tourne à l'identique partout.
  • Un conteneur partage le noyau de l'hôte (léger, rapide) ; une VM embarque un OS complet (lourd, isolé).
  • Image = modèle figé en lecture seule ; conteneur = instance en exécution ; registre = dépôt d'images (Docker Hub).
  • Image → conteneur, c'est comme classe → objet.

Exercices

Exercice 1Échauffement

Avec tes mots, explique la différence entre une image et un conteneur.

Voir une solution

L'image est un modèle figé, en lecture seule, qui décrit une application et tout son environnement ; elle ne « tourne » pas. Le conteneur est une instance vivante lancée à partir d'une image : c'est l'application qui s'exécute réellement. D'une même image, on peut démarrer plusieurs conteneurs indépendants.

Exercice 2Application

Un collègue dit « le projet plante chez moi alors qu'il marche chez toi ». En quoi Docker aiderait ?

Voir une solution

En conteneurisant le projet, on fige une bonne fois la version du langage, les bibliothèques et la configuration dans une image. Le collègue lance le même conteneur : il obtient exactement le même environnement que toi, supprimant les différences invisibles (version, dépendance manquante…) qui causaient le plantage.

Exercice 3Défi

Pourquoi peut-on lancer beaucoup plus de conteneurs que de machines virtuelles sur une même machine ?

Voir une solution

Parce qu'un conteneur ne duplique pas le système d'exploitation : il partage le noyau de l'hôte et n'embarque que l'application et ses dépendances (quelques Mo). Une VM, elle, embarque un OS complet (plusieurs Go) par instance : la mémoire et le CPU sont vite saturés. La légèreté des conteneurs permet d'en empiler des dizaines là où quelques VM suffisent à remplir la machine.
