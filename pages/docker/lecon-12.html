Builds modernes : BuildKit, cache et multi-plateforme

~42 min Avancé Leçon 06 requise

À la fin de cette leçon, tu sauras

  • ce qu'est BuildKit et pourquoi il accélère les builds ;
  • garder un cache entre les builds avec RUN --mount=type=cache ;
  • injecter un secret sans qu'il reste dans l'image (--mount=type=secret) ;
  • construire une image pour plusieurs architectures avec docker buildx.
Sommaire de la leçon

Tu sais déjà rendre une image légère avec le multi-stage (leçon 6) et rapide grâce au cache des couches (leçon 3). Ces techniques reposent toutes sur le moteur de build de Docker. Depuis quelques années, ce moteur a changé — il s'appelle BuildKit — et il débloque des capacités que l'ancien ne permettait pas : un cache qui survit aux invalidations, des secrets propres, et des images qui tournent sur plusieurs processeurs.

Pourquoi le multi-stage allège autant l'image

La raison profonde : seule la dernière étape devient l'image finale ; tout ce qui vit dans les étapes précédentes est jeté. On compile donc dans une étape riche (compilateur, node_modules de dev, en-têtes C, ~1 Go d'outillage), puis on COPY --from=build uniquement l'artefact — le binaire ou le dist/ — dans une base minuscule (alpine, distroless). L'image passe couramment de plusieurs centaines de Mo à quelques dizaines. Bonus non négligeable : moins de logiciels embarqués, c'est aussi une surface d'attaque réduite en production.

BuildKit : le moteur de build moderne

Historiquement, docker build construisait les couches strictement de haut en bas, une par une. BuildKit, le moteur par défaut des versions récentes de Docker, est plus malin : il lit tout le Dockerfile, construit un graphe des dépendances, et exécute en parallèle les étapes indépendantes. Dans un build multi-stage, deux étapes qui ne s'attendent pas se construisent en même temps.

Concrètement, tu n'as rien à installer : un docker build récent utilise déjà BuildKit. La commande docker buildx en est l'interface étendue, qui donne accès aux options avancées de cette leçon.

Un signe visible : la sortie de build de BuildKit affiche des étapes numérotées [+] Building avec leur durée, au lieu de l'ancien flot linéaire. C'est le même Dockerfile ; seul le moteur qui l'exécute a changé.

Un cache qui persiste : RUN --mount=type=cache

Le cache des couches a une limite : dès qu'une couche est invalidée, tout ce qu'elle contenait est perdu. Si tu modifies package.json, la couche npm ci se rejoue et retélécharge tous les paquets, même ceux qui n'ont pas changé. BuildKit offre un autre cache : un dossier monté le temps du RUN, qui survit d'un build à l'autre.

La ligne # syntax=docker/dockerfile:1 en tête active la syntaxe étendue de BuildKit. Le --mount=type=cache,target=/root/.npm monte le cache de npm dans l'étape : même quand la couche est invalidée et que npm ci se rejoue, il réutilise les paquets déjà téléchargés au lieu de tout reprendre. Le même principe s'applique à pip (~/.cache/pip), apt, Go, Maven…

L'ordre des instructions qui ruine le cache

Le cache monté accélère un RUN qui se rejoue ; mais le vrai levier reste de ne pas le rejouer du tout. Pour cela, l'ordre du Dockerfile est décisif : une couche n'est réutilisée que si toutes celles d'avant sont intactes. Un COPY . . placé avant le RUN npm ci invalide l'installation à chaque modification de code — même une virgule dans un commentaire relance tout. La règle : copie d'abord le seul package*.json, installe, puis copie le reste. Ce qui change souvent (le code) doit venir après ce qui change rarement (les dépendances).

.dockerignore : le complément indispensable de COPY . .

Avant tout build, Docker envoie le contexte (le dossier courant) au moteur. Sans filtre, un COPY . . embarque aussi node_modules, .git, les logs et les fichiers locaux : contexte plus lourd, build plus lent, et surtout cache brisé — le moindre fichier local qui change invalide la couche. Un .dockerignore, calqué sur le .gitignore, les exclut : node_modules, .git, *.log, .env. Bonus sécurité : c'est aussi ce qui évite de copier par mégarde un .env plein de secrets dans l'image.

Des secrets qui ne laissent pas de trace

À la leçon 6, on a vu qu'un secret copié dans une couche y reste à jamais, récupérable avec docker history. Mais certains builds ont besoin d'un secret : un jeton pour télécharger un paquet privé, par exemple. BuildKit résout ça avec --mount=type=secret : le secret est monté le temps d'un RUN, puis disparaît sans jamais entrer dans une couche.

Le fichier npm_token.txt ne fait pas partie du contexte copié : BuildKit le rend disponible sous /run/secrets/ uniquement pendant le RUN concerné. Après le build, docker history ne montre rien : le secret n'est dans aucune couche. C'est la bonne réponse à un besoin réel, sans compromis de sécurité.

Une image, plusieurs architectures

Ton Mac récent a un processeur ARM (Apple Silicon) ; beaucoup de serveurs sont en x86-64 (amd64), et des serveurs ARM se répandent aussi. Une image construite pour une architecture ne tourne pas sur l'autre. docker buildx construit une image multi-plateforme en une commande : elle regroupe plusieurs variantes sous un seul tag, et Docker tire automatiquement la bonne selon la machine.

Le résultat poussé sur le registre est un manifeste qui liste les deux variantes. Sur un serveur amd64, docker pull monorg/monapp:1.0.0 récupère la variante amd64 ; sur une machine ARM, la variante arm64 — même tag, image adaptée. Pour bâtir une architecture différente de la tienne, BuildKit l'émule (via QEMU) : c'est plus lent, mais une seule commande suffit.

Cas réel : l'image qui refuse de démarrer en production

Une équipe développe sur des MacBook ARM : docker build produit — sans le dire — une image arm64. Poussée telle quelle et déployée sur un serveur cloud x86-64, elle échoue au démarrage avec un obscur exec format error. Le correctif n'est pas de « reconstruire sur le serveur », mais de publier une image multi-plateforme : docker buildx build --platform linux/amd64,linux/arm64 … --push. Le même tag fonctionne alors partout, poste de dev comme serveur. Depuis la généralisation des puces ARM, c'est devenu un réflexe de publication.

Le cache de build dans la CI

Sur ta machine, le cache est là d'un build à l'autre. Dans un pipeline d'intégration continue, chaque exécution repart souvent d'un environnement neuf : pas de cache, donc des builds lents. BuildKit sait exporter et réimporter le cache (--cache-to / --cache-from, par exemple vers un registre), pour retrouver la rapidité même en CI. C'est l'un des grands intérêts de BuildKit côté automatisation — un pont naturel vers le cours CI/CD.

Antisèche

Glossaire

BuildKit
Moteur de build par défaut de Docker : parallélise les étapes indépendantes et débloque cache monté, secrets et multi-plateforme.
buildx
Interface étendue de docker build donnant accès aux fonctions avancées de BuildKit.
Cache monté
Dossier monté le temps d'un RUN (--mount=type=cache) qui survit d'un build à l'autre, contrairement au cache des couches.
Secret de build
Valeur montée pendant un RUN (--mount=type=secret) puis effacée : elle n'entre dans aucune couche.
Multi-plateforme
Image construite pour plusieurs architectures (amd64, arm64…) et réunie sous un seul tag via un manifeste.
Manifeste
Index qui liste les variantes d'une image ; Docker en tire automatiquement celle qui correspond à la machine.
--platform
Option de buildx précisant les architectures cibles, ex. linux/amd64,linux/arm64.

Récap et vérification

  • BuildKit est déjà le moteur par défaut : il parallélise les étapes indépendantes ; buildx ouvre ses options.
  • RUN --mount=type=cache garde un cache (npm, pip…) entre les builds, même quand la couche est invalidée.
  • RUN --mount=type=secret injecte un secret sans qu'il reste dans une couche.
  • buildx build --platform amd64,arm64 publie une image qui tourne sur plusieurs architectures.

  2. Comment passer un jeton au build sans qu'il se retrouve dans docker history ?

Exercices

Exercice 1Échauffement

Vrai ou faux : pour utiliser BuildKit, il faut installer un outil séparé et changer toutes ses commandes. Justifie.

Voir une solution

Faux. BuildKit est le moteur par défaut des versions récentes de Docker : un simple docker build l'utilise déjà. docker buildx n'est qu'une interface étendue pour ses options avancées (cache monté, secrets, multi-plateforme). Sur une très vieille installation, on peut le forcer avec DOCKER_BUILDKIT=1.

Exercice 2Application

Ajoute à un Dockerfile Python un cache persistant pour pip (dossier /root/.cache/pip) lors du RUN pip install.

Voir une solution

La ligne # syntax active la syntaxe étendue ; le cache de pip persiste entre les builds, si bien qu'un changement de requirements.txt ne retélécharge que les paquets nouveaux.

Exercice 3Défi

Un collègue passe un jeton d'API au build avec --build-arg TOKEN=… et s'étonne qu'on puisse le retrouver dans l'image. Explique le problème et propose la bonne méthode.

Voir une solution

La valeur d'un ARG reste inscrite dans l'historique de l'image : docker history (ou l'extraction de l'image) la révèle. Il faut utiliser un secret de build : RUN --mount=type=secret,id=token … côté Dockerfile, et docker build --secret id=token,src=./token.txt côté commande. Le secret n'est alors monté que le temps du RUN (sous /run/secrets/) et n'entre dans aucune couche.
