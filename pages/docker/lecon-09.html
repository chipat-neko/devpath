Module 4 · Docker au quotidien — Leçon 09

Observer et déboguer ses conteneurs

~40 min Intermédiaire Leçon 08 requise

À la fin de cette leçon, tu sauras

  • lire les journaux d'un conteneur (docker logs) ;
  • entrer dedans avec docker exec et l'inspecter ;
  • mesurer ses ressources et vérifier sa santé ;
  • configurer le redémarrage automatique.
Sommaire de la leçon

Ton application tourne dans un conteneur… mais que fait-elle vraiment ? Un conteneur peut sembler une boîte noire : pas d'écran, pas de fenêtre. En réalité, Docker fournit une petite trousse de diagnostic pour regarder à l'intérieur : lire ce que l'application écrit, ouvrir un terminal dedans, inspecter sa configuration, mesurer sa consommation, et surveiller sa santé. Ces réflexes te feront gagner des heures le jour où « ça ne marche pas ».

Lire les journaux : docker logs

Premier réflexe devant un problème : regarder les logs. Un conteneur capture tout ce que le process écrit sur la sortie standard (stdout) et la sortie d'erreur (stderr).

Bonne pratique héritée du monde conteneur : une application écrit ses logs sur stdout (pas dans un fichier interne). Docker les collecte, et un orchestrateur pourra les centraliser. Si docker logs reste vide alors que l'app plante, c'est souvent qu'elle écrit dans un fichier au lieu de la sortie standard.

Entrer dans un conteneur : docker exec

Parfois, lire les logs ne suffit pas : on veut ouvrir un terminal à l'intérieur pour vérifier un fichier, tester une connexion, lister des variables. C'est le rôle de docker exec :

Ne confonds pas exec et run : docker exec lance une commande dans un conteneur déjà en cours, alors que docker run crée un nouveau conteneur à partir d'une image. Pour aller inspecter le conteneur qui pose problème, c'est bien exec qu'il te faut.

L'état, la config, les ressources

Trois commandes complètent le tableau :

  • docker ps : la liste des conteneurs actifs, leur statut et leurs ports publiés (docker ps -a montre aussi ceux qui sont arrêtés).
  • docker inspect : toute la configuration d'un conteneur en JSON (adresse IP, montages, variables, réseau…). Un --format cible une valeur précise.
  • docker stats : la consommation CPU et mémoire en temps réel, conteneur par conteneur.

Le redémarrage automatique : restart policies

Que se passe-t-il si un conteneur plante ou si la machine redémarre ? Par défaut, il reste arrêté. Une politique de redémarrage le relance automatiquement :

Les valeurs : no (jamais, défaut), on-failure (seulement en cas d'erreur), always (toujours), unless-stopped (toujours, sauf arrêt manuel). En production, unless-stopped est un choix courant : le service se relève seul après un plantage ou un reboot.

Cas réel : le conteneur qui redémarre en boucle

En production, un service apparaît sans cesse en Restarting dans docker ps. La trousse de diagnostic livre le coupable en trois commandes : docker logs montre un OOMKilled — le conteneur dépasse sa limite mémoire et le noyau le tue ; docker stats confirme une mémoire au plafond ; docker inspect révèle une limite (--memory) trop basse pour la charge. Diagnostic : fuite mémoire côté app ou limite mal calibrée. Sans ces outils, on redémarrerait à l'aveugle ; avec eux, la cause saute aux yeux en deux minutes.

Tester la connexion entre services depuis l'intérieur

Un service n'arrive pas à joindre la base ? Entre dans son conteneur et teste depuis là où le problème se pose : docker compose exec web sh, puis ping bdd ou wget -qO- http://bdd:5432. Tu vérifies ainsi le DNS interne de Compose (joindre un service par son nom) et le réseau, sans quitter le contexte réel du conteneur.

Ce que tu modifies via exec est éphémère

docker exec est parfait pour observer, mais tout ce que tu changes à la main dans un conteneur (installer un paquet, éditer un fichier) disparaît à sa recréation : un conteneur est jetable. Une fois la cause comprise, la correction durable se fait dans le Dockerfile ou le compose.yaml, puis on reconstruit. L'exec diagnostique ; le fichier corrige.

Pour aller plus loin

À plusieurs conteneurs, on ne lit plus les logs un par un : on les centralise (pilotes de logs Docker, pile ELK/Loki) et on collecte des métriques (Prometheus + Grafana) pour visualiser CPU, mémoire et santé dans le temps. C'est le domaine de l'observabilité, indispensable dès qu'un système grandit — et cœur des orchestrateurs comme Kubernetes.

Antisèche

Glossaire

docker logs
Affiche ce que le conteneur écrit sur stdout/stderr ; -f suit en direct, --tail limite.
stdout / stderr
Sorties standard et d'erreur du process ; une app conteneurisée y écrit ses logs pour que Docker les collecte.
docker exec
Lance une commande (souvent un shell) dans un conteneur en cours ; à distinguer de run qui en crée un nouveau.
docker inspect
Renvoie toute la configuration d'un conteneur en JSON ; --format extrait une valeur précise.
docker stats
Affiche la consommation CPU et mémoire des conteneurs en temps réel.
Healthcheck
Test périodique de bon fonctionnement ; fait passer le conteneur en healthy ou unhealthy.
Restart policy
Règle de redémarrage automatique : no, on-failure, always, unless-stopped.
OOMKilled
État d'un conteneur tué par le noyau pour dépassement de sa limite mémoire (Out Of Memory).

Récap et vérification

  • docker logs -f montre ce que l'app écrit ; premier réflexe de débogage.
  • docker exec -it … sh ouvre un shell dans le conteneur qui tourne (≠ run).
  • ps, inspect, stats donnent état, configuration et ressources.
  • Un healthcheck dit si le service va bien ; une restart policy le relance seul.

Vérifie ta compréhension

  1. Quelle commande pour lire, en direct, ce qu'écrit un conteneur ?
  2. Que devient un paquet installé à la main via docker exec ?
  3. À quoi sert une politique de redémarrage ?

Exercices

Exercice 1Échauffement

Un conteneur nommé api semble bloqué. Donne deux commandes pour : (1) suivre ses journaux en direct, (2) ouvrir un shell à l'intérieur.

Voir une solution

Les logs révèlent souvent l'erreur ; si besoin, l'exec permet d'inspecter fichiers, variables et connexions depuis l'intérieur.

Exercice 2Application

Dans un compose.yaml, configure le service web pour qu'il redémarre automatiquement, sauf si on l'a arrêté manuellement.

Voir une solution

unless-stopped relance le conteneur après un plantage ou un reboot, mais respecte un docker compose stop volontaire.

Exercice 3Défi

Ajoute à un Dockerfile un HEALTHCHECK qui interroge http://localhost:8080/health toutes les 30 secondes et échoue après 3 essais.

Voir une solution

Docker appelle l'URL toutes les 30 s ; si la commande échoue 3 fois de suite, le conteneur passe unhealthy, ce qu'on voit dans docker ps et qu'un orchestrateur peut exploiter.
