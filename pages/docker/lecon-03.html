Module 1 · Les conteneurs — Leçon 03

Écrire un Dockerfile

~40 min Intermédiaire Leçon 02 requise

À la fin de cette leçon, tu sauras

  • écrire un Dockerfile pour conteneuriser une app ;
  • employer FROM, WORKDIR, COPY, RUN, CMD ;
  • construire l'image avec docker build ;
  • comprendre le cache des couches et l'ordre des instructions.
Sommaire de la leçon

Jusqu'ici, tu as utilisé des images existantes (nginx, ubuntu). Pour conteneuriser ton application, tu vas construire ta propre image. La recette s'écrit dans un fichier nommé Dockerfile : une suite d'instructions, lues de haut en bas, qui décrivent comment assembler l'image. C'est le cœur de Docker : une fois ce Dockerfile écrit, n'importe qui reconstruit la même image, à l'identique.

Les instructions essentielles

  • FROM : l'image de base dont on hérite. Toujours la première instruction. On part presque toujours d'une image officielle (un langage, un OS minimal).
  • WORKDIR : le répertoire de travail pour les instructions suivantes (et au lancement). Évite les cd répétés.
  • COPY source dest : copie des fichiers de ta machine vers l'image.
  • RUN : exécute une commande pendant la construction (installer des paquets, compiler). Son résultat est figé dans l'image.
  • EXPOSE : documente le port utilisé (informatif ; la publication réelle se fait avec -p au run).
  • CMD : la commande par défaut exécutée quand le conteneur démarre. Une seule par image.

Distinction cruciale : RUN agit à la construction (une fois, pour bâtir l'image) ; CMD agit à l'exécution (à chaque démarrage de conteneur). Confondre les deux est l'erreur classique du débutant.

Le cache des couches

Chaque instruction du Dockerfile crée une couche (layer) empilée sur la précédente. Docker met en cache chaque couche : si rien n'a changé pour une instruction, il réutilise la couche au lieu de la rejouer. C'est ce qui rend les reconstructions ultra-rapides — à condition d'ordonner intelligemment.

L'ordre compte : dès qu'une couche change, toutes celles qui suivent sont recalculées. En copiant package.json et en installant les dépendances avant de copier le code, on garde l'étape coûteuse (npm install) en cache tant que les dépendances ne bougent pas. Modifier une ligne de code ne relance alors pas toute l'installation.

Cas réel : un build de CI qui passe de 8 min à 40 s

Une équipe reconstruit son image à chaque commit dans son pipeline. Le Dockerfile faisait COPY . . avant RUN npm install : la moindre modification de code invalidait la couche des dépendances, et l'installation complète se rejouait — 8 minutes à chaque fois. En remontant COPY package.json + RUN npm install avant le COPY . ., l'installation reste en cache tant que les dépendances ne changent pas : les builds tombent à moins d'une minute. Un simple réordonnancement, un pipeline dix fois plus rapide.

Le fichier .dockerignore

Comme .gitignore, un fichier .dockerignore exclut des fichiers du contexte de construction : node_modules, .git, fichiers temporaires. Cela accélère le build et allège l'image. Mets-y systématiquement node_modules et .git — inutile (et nuisible) de les copier dans l'image.

Pour aller plus loin : ENV, ARG et le multi-stage

Un Dockerfile réel utilise vite d'autres instructions : ENV (variables d'environnement dans l'image), ARG (variables disponibles seulement à la construction), ENTRYPOINT (programme fixe complété par CMD). Et pour des images de production légères, le build multi-étapes (plusieurs FROM) compile dans une image jetable puis ne copie que le résultat : c'est l'objet de la dernière leçon du cours.

Glossaire

Dockerfile
Fichier texte décrivant, instruction par instruction, comment construire une image reproductible.
Image de base (FROM)
Image existante dont on hérite ; point de départ obligatoire de tout Dockerfile.
Couche (layer)
Résultat figé d'une instruction, empilé sur les précédentes ; l'image est la pile de ses couches.
Cache des couches
Réutilisation d'une couche inchangée pour éviter de la reconstruire ; une couche modifiée invalide toutes celles au-dessus.
Contexte de construction
Dossier (le « . » de build) d'où Docker peut lire le Dockerfile et copier des fichiers.
Tag (-t)
Nom (et version) donné à une image pour la retrouver et la lancer, ex. mon-app:1.0.
RUN vs CMD
RUN s'exécute à la construction ; CMD au démarrage du conteneur.
.dockerignore
Liste de fichiers à exclure du contexte (ex. node_modules, .git) : build plus rapide, image plus légère.

Récap et vérification

  • Un Dockerfile décrit, instruction par instruction, comment bâtir une image.
  • FROM (base), WORKDIR, COPY, RUN (à la construction), EXPOSE (doc), CMD (au démarrage).
  • docker build -t nom . construit l'image depuis le contexte courant.
  • Chaque instruction = une couche mise en cache : copier les dépendances avant le code accélère les rebuilds.

Vérifie ta compréhension

  1. Quelle différence entre RUN et CMD ?
  2. Pourquoi copier package.json et installer les dépendances avant de copier le code ?
  3. Que désigne le . dans docker build -t app . ?

Exercices

Exercice 1Échauffement

Quelle instruction place-t-on toujours en première ligne d'un Dockerfile, et à quoi sert-elle ?

Voir une solution

FROM : elle déclare l'image de base dont on hérite (par ex. FROM node:20-alpine). Toute image part d'une autre ; FROM est donc obligatoirement la première instruction.

Voir une solution

build -t monapi . crée l'image depuis le Dockerfile du dossier courant ; run -d -p 8000:8000 la lance en arrière-plan en publiant le port (en supposant que l'app écoute sur 8000).
