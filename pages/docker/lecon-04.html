Module 2 · Applications réelles — Leçon 04

Volumes, réseaux et ports

~40 min Intermédiaire Leçon 03 requise

À la fin de cette leçon, tu sauras

  • persister des données avec un volume ;
  • utiliser un bind mount pour le développement ;
  • publier un port (-p) vers l'extérieur ;
  • relier des conteneurs par un réseau Docker.
Sommaire de la leçon

Un conteneur isolé qui ne garde rien et ne parle à personne a peu d'intérêt. Une vraie application doit conserver des données (une base ne peut pas tout perdre à chaque redémarrage) et communiquer (le serveur web parle à la base, et le navigateur parle au serveur web). Cette leçon couvre les deux : les volumes pour la persistance, et les ports et réseaux pour la communication.

Le problème : des conteneurs jetables

Rappelle-toi : le système de fichiers d'un conteneur est éphémère. Supprime le conteneur, et tout ce qu'il a écrit disparaît. Pour une base de données conteneurisée, ce serait catastrophique. La solution : stocker les données en dehors du conteneur, dans un volume géré par Docker, qui survit aux suppressions et redémarrages.

Les volumes nommés

Un volume nommé est un espace de stockage géré par Docker, indépendant du cycle de vie des conteneurs. On le branche sur un dossier du conteneur avec -v.

La syntaxe -v nom:chemin relie un volume à un dossier dans le conteneur. Tout ce que l'application écrit à ce chemin va en réalité dans le volume : il persiste tant que tu ne le supprimes pas explicitement (docker volume rm). C'est la façon de conserver des données en production.

Le bind mount : pour développer

Une variante, le bind mount, relie un dossier de ta machine à un dossier du conteneur. Très pratique en développement : tu édites ton code sur ta machine, et le conteneur voit les changements en direct.

Différence avec un volume nommé : le bind mount pointe vers un chemin précis de l'hôte ($(pwd) = dossier courant), tandis qu'un volume nommé est géré par Docker dans un espace dédié. Règle générale : bind mount pour développer (voir son code en direct), volume nommé pour les données de production (bases, fichiers persistants).

Piège fréquent

Un bind mount recouvre le dossier visé. Avec -v "$(pwd)":/app, le /app/node_modules installé par le RUN npm install de l'image se retrouve caché derrière ton dossier de travail : le conteneur s'arrête aussitôt sur un « module introuvable » que seul docker logs révèle, alors que l'image, elle, est correcte. La parade : ajouter -v /app/node_modules au lancement, pour remonter par-dessus ce chemin précis le dossier de l'image.

Cas réel : la base de données effacée par mégarde

Une équipe lance sa base Postgres en conteneur pour la préproduction, sans volume. Tout fonctionne des semaines : le conteneur tourne, les données s'accumulent. Puis une mise à jour de routine fait docker rm -f bdd pour recréer le conteneur avec une nouvelle image… et toutes les données disparaissent, car elles vivaient dans le système de fichiers éphémère du conteneur. La règle qui aurait tout sauvé : toute base conteneurisée monte ses données sur un volume nommé dès le premier jour.

Publier un port

Un conteneur est isolé du réseau : par défaut, on ne peut pas l'atteindre depuis l'hôte. La publication de port (-p, déjà croisée) ouvre une porte de la machine vers le conteneur.

Lis toujours -p dans l'ordre hôte:conteneur. Le port de gauche est celui que tu tapes dans le navigateur (sur ta machine) ; celui de droite est le port sur lequel l'application écoute dans le conteneur. Les deux n'ont pas besoin d'être identiques.

Les réseaux : conteneurs qui se parlent

Quand plusieurs conteneurs doivent communiquer (un serveur web et sa base), on les place sur un réseau Docker commun. Sur un réseau, chaque conteneur peut joindre les autres par leur nom, sans connaître d'adresse IP.

C'est le point clé : sur un même réseau Docker, le nom du conteneur (bdd) sert de nom d'hôte. L'application se connecte à bdd:5432 comme à un serveur normal. On n'a plus à gérer d'adresses IP fragiles : Docker fait la résolution. (La prochaine leçon, Docker Compose, automatisera tout ce câblage.)

Monter un dossier en lecture seule

Un bind mount peut être en lecture seule en ajoutant :ro : -v "$(pwd)/config":/etc/app:ro. Le conteneur lit la configuration mais ne peut pas la modifier — utile pour injecter des fichiers de config ou des certificats sans risquer qu'un conteneur les altère.

Publier vs réseau interne

Ne confonds pas les deux modes de communication. -p ouvre un conteneur vers l'extérieur (ton navigateur, Internet). Un réseau Docker fait communiquer les conteneurs entre eux, en interne. Une base de données ne devrait pas être publiée avec -p vers l'extérieur : seuls les autres conteneurs (via le réseau) ont besoin de l'atteindre. Moins on expose, plus c'est sûr.

Glossaire

Volume nommé
Espace de stockage géré par Docker, indépendant des conteneurs ; la façon de persister des données de production.
Bind mount
Montage d'un dossier précis de l'hôte dans le conteneur ; idéal en développement pour voir son code en direct.
Persistance
Conservation des données au-delà de la vie d'un conteneur, grâce à un volume.
Éphémère
Se dit du système de fichiers propre au conteneur : tout ce qui n'est pas dans un volume disparaît à sa suppression.
Publication de port (-p)
Ouverture d'un port du conteneur vers l'hôte, au format hôte:conteneur : la porte vers l'extérieur.
Réseau Docker
Réseau virtuel commun sur lequel les conteneurs communiquent entre eux, en interne.
Résolution par nom
Sur un réseau Docker, le nom d'un conteneur sert de nom d'hôte ; plus besoin de gérer d'adresses IP.
:ro
Suffixe rendant un montage en lecture seule : le conteneur lit mais ne peut pas modifier.

Récap et vérification

  • Le système de fichiers d'un conteneur est éphémère : pour persister, on utilise un volume (-v nom:chemin).
  • Bind mount (-v /chemin/hôte:/chemin) pour développer (code en direct) ; volume nommé pour les données de production.
  • -p hôte:conteneur publie un port vers l'extérieur.
  • Un réseau Docker fait communiquer les conteneurs entre eux par leur nom, sans IP.

Exercice 2Application

En développement, tu veux que ton image mon-app voie ton code en direct (dossier courant monté dans /app) et publie le port 3000. Écris la commande.

Voir une solution

Le bind mount "$(pwd)":/app reflète tes modifications dans le conteneur ; -p 3000:3000 publie le port.

Exercice 3Défi

Une base de données ne doit être jointe que par l'API, pas exposée à Internet. Comment relies-tu les deux conteneurs sans publier le port de la base ?

Voir une solution

On place les deux conteneurs sur le même réseau : l'API atteint la base par son nom bdd. On ne met -p que sur l'API : la base reste invisible de l'extérieur, ce qui est plus sûr.
