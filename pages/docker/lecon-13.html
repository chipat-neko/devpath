Composer une pile complète : réseaux, profils et montée en charge

~40 min Avancé Leçon 05 requise

À la fin de cette leçon, tu sauras

  • décrire une pile de plusieurs services (proxy, api, base, cache) ;
  • cloisonner les services avec plusieurs réseaux ;
  • paramétrer avec des variables et activer des services à la carte (profils) ;
  • monter en charge avec --scale et adapter dev/prod par des fichiers d'override.
Sommaire de la leçon

La leçon 5 t'a montré Compose avec deux services : une api et sa base. Une vraie application en aligne souvent plus — un reverse-proxy en façade, l'api, une base, un cache. Cette leçon franchit ce pas : décrire une pile réaliste, la cloisonner pour la sécurité, la paramétrer, et la faire monter en charge — le tout dans un seul fichier versionné.

Une pile de plusieurs services

Voici une pile à quatre services. Chacun reste un bloc simple (comme en leçon 5), mais ils coopèrent : le proxy reçoit le trafic et le passe à l'api, qui parle à la base et au cache. La configuration nginx du proxy (un fichier monté, avec une ligne proxy_pass http://api:3000;) n'est pas montrée ici : sans elle, nginx ne sert que sa page d'accueil et ne relaie rien.

Comme en leçon 5, Compose crée un réseau commun et chaque service joint les autres par leur nom : l'api atteint la base à l'adresse db et le cache à cache (visible dans DATABASE_URL et REDIS_URL). Un seul port est publié — celui du proxy ; le reste dialogue en interne.

Comment « par leur nom » fonctionne vraiment

Ce n'est pas de la magie : sur le réseau que Compose a créé, le moteur Docker fournit un serveur DNS interne (à l'adresse 127.0.0.11 dans chaque conteneur) qui résout le nom d'un service vers son IP sur le réseau partagé. D'où une conséquence pratique : on écrit db, jamais une IP en dur — l'adresse change à chaque redémarrage, mais le nom, lui, est stable. Un service ne résout que les noms des services avec lesquels il partage un réseau ; le nom d'un service d'un autre réseau ne se résout tout simplement pas.

Isoler avec plusieurs réseaux

Par défaut, tous les services partagent un réseau : le proxy pourrait parler directement à la base. Ce n'est pas souhaitable — le proxy n'a aucune raison de toucher aux données. On cloisonne en déclarant plusieurs réseaux et en rattachant chaque service à ceux dont il a besoin.

Résultat : le proxy et la base ne sont sur aucun réseau commun ; le proxy ne peut donc pas atteindre la base, même s'il était compromis. Seule l'api, présente sur les deux réseaux, fait le pont. C'est le principe de segmentation : réduire ce que chaque composant peut joindre.

Attendre un service vraiment prêt

La leçon 5 le rappelait : depends_on seul garantit l'ordre de démarrage, pas que le service soit prêt. Ici, l'api utilise depends_on: { db: { condition: service_healthy } } : elle attend que le healthcheck de la base la déclare saine (le pg_isready répond) avant de démarrer. C'est le mécanisme employé dans le projet final ; sans lui, l'api tenterait de se connecter à une base encore en train d'ouvrir ses ports.

Variables et profils

Coder secret ou postgres:16 en dur dans le fichier le fige. Compose sait interpoler des variables écrites ${...}, lues depuis l'environnement ou un fichier .env placé à côté du compose.yaml.

${PG_VERSION:-16} utilise 16 si la variable n'est pas définie ; ${DB_PASSWORD:?…} refuse de démarrer si elle manque — pratique pour rendre un secret obligatoire. Ces variables-là paramètrent le fichier Compose ; à ne pas confondre avec le bloc environment, qui passe des variables dans le conteneur (leçon 8).

Autre besoin courant : n'activer certains services que dans certains cas. Les profils le permettent : un service marqué d'un profiles ne démarre avec la pile que si ce profil est demandé.

La pile de production reste minimale ; les outils de confort (interface de base, générateur de données de test) vivent derrière un profil et ne partent jamais en production par accident.

Les profils se cumulent — et fixent une bonne habitude

Un service peut lister plusieurs profils (profiles: [dev, debug]) : il démarre si l'un d'eux est demandé. On active plusieurs profils en répétant l'option (--profile dev --profile debug) ou via la variable COMPOSE_PROFILES=dev,debug, pratique dans un .env. Subtilité utile : si un service sans profil déclare un depends_on vers un service à profil, Compose refuse le projet (« depends on undefined service ») tant que ce profil n'est pas activé : une dépendance requise ne peut pas rester absente. À l'inverse, viser nommément un service à profil (docker compose up adminer) le démarre sans activer son profil. Le réflexe à prendre : mettre tout ce qui n'est pas indispensable en production (interface de base, seed de données, mailer de test) derrière un profil, pour qu'un simple docker compose up ne lance jamais que le strict nécessaire.

Monter en charge et adapter dev/prod

Compose peut lancer plusieurs instances d'un même service. Si l'api est sans état (elle ne stocke rien localement), --scale en démarre plusieurs répliques, que le proxy répartit.

Un détail compte : un service qu'on met à l'échelle ne doit pas publier un port fixe vers l'hôte (deux instances ne peuvent pas prendre le même port). C'est le proxy qui expose un port unique et distribue vers les répliques par leur nom de service.

Enfin, le même projet a des besoins différents en dev et en prod. Plutôt que deux fichiers rivaux, Compose fusionne plusieurs fichiers. Un compose.override.yaml présent à côté du fichier principal est appliqué automatiquement — idéal pour les réglages de dev (monter le code en bind mount, exposer des ports de debug) ; en production, on choisit explicitement les fichiers.

Arrêter la pile sans perdre les données

Une pile a un cycle de vie : docker compose stop suspend les conteneurs, docker compose down les supprime. L'arrêt se fait dans l'ordre inverse des depends_on : ce qui dépend de la base s'arrête avant elle. Le point sensible est ailleurs : que deviennent les données de la base entre deux down ?

Le piège du down -v qui efface la base

docker compose down supprime conteneurs et réseaux mais conserve les volumes nommés (ici pgdata) : relancer un up retrouve les données. En revanche, docker compose down -v supprime aussi les volumes — la base repart vide, sans confirmation. Le -v est parfait pour repartir propre en développement, mais sur des données qui comptent c'est irréversible. Autre confusion fréquente : down arrête la pile et la démonte ; pour juste la mettre en pause, c'est stop (les conteneurs et leurs données restent, un start les relance).

Compose n'est pas un orchestrateur de production à grande échelle

--scale répartit des répliques sur une seule machine, sans redémarrage automatique en cas de panne matérielle ni déploiement progressif. Pour de la haute disponibilité sur plusieurs serveurs — mise à l'échelle automatique, auto-réparation, montées de version sans coupure — on passe à un orchestrateur comme Kubernetes (cours dédié). Compose reste roi en développement et pour les déploiements simples ; il ne remplace pas Kubernetes en production exigeante.

Cas réel

Dans une pile Compose, les services se joignent par leur nom : le service web atteint la base via l'hôte db, sans connaître son adresse IP, grâce au DNS interne que Docker fournit sur les réseaux créés par Compose. C'est ce qui permet, avec docker compose up --scale web=3, de lancer trois instances derrière un reverse-proxy sans changer une ligne de configuration applicative : le nom de service est résolu vers les conteneurs disponibles.

Antisèche

Glossaire

Pile (stack)
L'ensemble des services conteneurisés d'une application (proxy, api, base, cache…), décrits dans un même fichier Compose.
Reverse-proxy
Service en façade qui reçoit le trafic externe et le distribue aux services internes ; souvent le seul à publier un port.
Segmentation réseau
Rattacher chaque service aux seuls réseaux nécessaires pour limiter ce qu'il peut joindre.
service_healthy
Condition de depends_on qui fait attendre qu'une dépendance soit réellement saine (via son healthcheck).
Interpolation ${...}
Substitution d'une variable dans le fichier Compose ; :- donne un défaut, :? rend la variable obligatoire.
Profil
Étiquette (profiles) qui rend un service optionnel : il ne démarre avec la pile que si ce profil est activé (--profile ou COMPOSE_PROFILES) ; on peut aussi le lancer en le visant par son nom.
Override
Fichier Compose supplémentaire fusionné avec le principal pour adapter la pile (dev/prod).

Récap et vérification

  • Une pile réelle aligne plusieurs services qui se joignent par leur nom sur le réseau commun.
  • Plusieurs réseaux cloisonnent : chaque service ne voit que ceux auxquels il est rattaché.
  • Les variables ${...} paramètrent le fichier ; les profils activent des services à la carte.
  • --scale lance des répliques sur une machine ; les overrides adaptent dev et prod. Au-delà : Kubernetes.

Vérifie ta compréhension

  1. Pourquoi mettre la base et le proxy sur des réseaux différents ?
  2. Quelle différence entre ${VAR:-x} et ${VAR:?x} ?
  3. Que permet un profil, et pourquoi est-ce utile pour la production ?

Exercices

Exercice 1Échauffement

Dans la pile à quatre services, combien de ports sont publiés vers l'hôte, et lequel ? Pourquoi la base n'en publie-t-elle aucun ?

Voir une solution

Un seul port est publié : le 80 du proxy. L'api, la base et le cache dialoguent uniquement en interne sur le réseau Compose, joints par leur nom (api, db, cache). Publier le port de la base l'exposerait inutilement au monde : on ne publie que ce qui doit être atteint de l'extérieur.

Exercice 2Application

Rends la version de Redis paramétrable, avec 7 par défaut, via une variable REDIS_VERSION.

Voir une solution

Sans variable définie, Compose lit redis:7-alpine ; en posant REDIS_VERSION=8 dans le .env ou l'environnement, on bascule sur redis:8-alpine sans toucher au fichier.

Exercice 3Défi

On veut trois répliques de l'api derrière le proxy. Quel réglage faut-il retirer du service api pour que ça fonctionne, et pourquoi ?

Voir une solution

Il faut que l'api ne publie aucun port fixe vers l'hôte (pas de ports: ["3000:3000"]) : trois instances ne peuvent pas réserver le même port de l'hôte. C'est le proxy qui expose le port unique (80) et répartit les requêtes vers api, résolu vers les trois répliques. On lance ensuite docker compose up -d --scale api=3.
