Configurer l'image : ENTRYPOINT, CMD, ARG et ENV

~40 min Avancé Leçon 03 requise

À la fin de cette leçon, tu sauras

  • choisir entre CMD et ENTRYPOINT pour démarrer un conteneur ;
  • combiner ENTRYPOINT + CMD (programme fixe, arguments par défaut) ;
  • distinguer la forme exec de la forme shell et son effet sur les signaux ;
  • configurer une image avec ARG (au build) et ENV (à l'exécution).
Sommaire de la leçon

À la leçon 3, tu as écrit un Dockerfile avec FROM, WORKDIR, COPY, RUN et CMD. Ces cinq instructions suffisent à conteneuriser, mais elles laissent deux questions ouvertes : comment le conteneur démarre exactement, et comment le configurer sans réécrire le Dockerfile. C'est le rôle de ENTRYPOINT, ARG et ENV — les instructions qui séparent une image « qui marche » d'une image paramétrable et propre à arrêter.

CMD et ENTRYPOINT : deux façons de démarrer

Les deux définissent ce qui s'exécute au lancement, mais avec une différence décisive : ce qui se passe quand on ajoute une commande derrière docker run.

  • CMD donne une commande par défaut, entièrement remplaçable. docker run image autrechose ignore le CMD et lance autrechose.
  • ENTRYPOINT fixe le programme : docker run image quelquechose ajoute quelquechose comme arguments, sans remplacer le programme.

Retiens l'image mentale : CMD est un brouillon qu'on écrase ; ENTRYPOINT est un préfixe qu'on complète. Un conteneur outil qu'on relance avec des arguments variables (un client de base de données, un convertisseur) veut un ENTRYPOINT ; une application au comportement unique se contente d'un CMD.

ENTRYPOINT + CMD : le programme et ses arguments par défaut

Le vrai intérêt vient de leur combinaison. Quand une image déclare les deux, ENTRYPOINT est le programme et CMD fournit ses arguments par défaut — que l'utilisateur peut remplacer sans toucher au programme.

On obtient une image qui a un comportement par défaut sensé tout en restant paramétrable. C'est le motif standard des images officielles : postgres, nginx ou node l'utilisent pour te laisser passer tes propres options.

Forme exec ou forme shell

Chaque instruction de démarrage s'écrit de deux manières, et le choix a des conséquences réelles sur l'arrêt du conteneur.

  • Forme exec (un tableau JSON) : CMD ["node", "server.js"]. Le programme devient directement le processus principal (PID 1) du conteneur.
  • Forme shell (une simple chaîne) : CMD node server.js. Docker lance en réalité /bin/sh -c "node server.js" : c'est le shell qui est PID 1, et ton programme devient son enfant.

Pourquoi est-ce important ? Quand tu fais docker stop, Docker envoie le signal SIGTERM au PID 1 pour un arrêt propre. En forme shell, ce signal va au shell, qui ne le transmet pas à ton programme : après 10 secondes d'attente, Docker tue tout brutalement (SIGKILL). L'application n'a pas pu fermer ses connexions ni finir ses écritures. La forme exec évite ce piège : ton programme reçoit directement SIGTERM.

Le problème du « PID 1 »

Un processus PID 1 a une responsabilité spéciale sous Linux : adopter et « récolter » les processus zombies, et gérer les signaux par défaut différemment. Un programme qui n'est pas prévu pour ça (Node, Python) peut mal se comporter en PID 1. La parade simple : docker run --init (ou init: true en Compose) insère un mini-init qui fait ce travail et relaie proprement les signaux. Utile dès qu'une application lance des sous-processus.

ARG et ENV : configurer au build et à l'exécution

Deux instructions injectent des valeurs sans réécrire le Dockerfile, mais à des moments différents :

  • ARG : une variable disponible seulement pendant la construction. On lui donne une valeur avec --build-arg. Elle n'existe plus dans le conteneur en marche.
  • ENV : une variable inscrite dans l'image, présente à la construction et à l'exécution (l'application peut la lire). On la surcharge au lancement avec -e ou --env-file.

Règle de sécurité qui découle directement de cette distinction : un secret ne se passe jamais par ARG. La valeur d'un --build-arg reste inscrite dans l'historique de l'image (docker history) et fuite. Les mots de passe et clés passent par ENV au lancement, ou mieux par des secrets de build (leçon 12).

Cas réel : un ENTRYPOINT qui prépare le terrain

Beaucoup d'images officielles utilisent un petit script comme ENTRYPOINT (souvent nommé docker-entrypoint.sh) qui fait un travail d'initialisation — attendre la base de données, appliquer des migrations, générer un fichier de configuration à partir des variables ENV — puis lance le programme réel avec exec "$@". Le exec est essentiel : il remplace le shell par le programme, qui redevient PID 1 et reçoit donc les signaux. C'est exactement le lien entre les deux moitiés de cette leçon : ENTRYPOINT pour orchestrer le démarrage, exec pour préserver l'arrêt propre.

Pour aller plus loin : LABEL et USER

Deux instructions complètent la configuration : LABEL ajoute des métadonnées à l'image (auteur, version, source — utile aux registres et aux scanners), et USER choisit l'utilisateur d'exécution. On a vu à la leçon 6 pourquoi passer en utilisateur non-root ; place le USER après les RUN qui ont besoin des droits, juste avant l'ENTRYPOINT/CMD.

Antisèche

Glossaire

CMD
Commande par défaut d'un conteneur, entièrement remplacée par tout argument passé à docker run.
ENTRYPOINT
Programme fixe lancé au démarrage ; les arguments du run s'y ajoutent au lieu de le remplacer.
Forme exec
Écriture en tableau JSON (["node","x"]) : le programme devient PID 1 et reçoit directement les signaux.
Forme shell
Écriture en chaîne (node x), exécutée via /bin/sh -c : le shell est PID 1 et transmet mal les signaux.
PID 1
Le processus principal du conteneur ; c'est lui que vise SIGTERM lors d'un docker stop.
ARG
Variable disponible seulement pendant la construction ; valeur donnée par --build-arg, absente du conteneur en marche.
ENV
Variable inscrite dans l'image, lisible à l'exécution ; surchargée au lancement par -e ou --env-file.
--init
Option qui insère un mini-init comme PID 1 pour gérer signaux et zombies quand le programme ne le fait pas.

Récap et vérification

  • CMD = commande par défaut remplaçable ; ENTRYPOINT = programme fixe que les arguments complètent.
  • Ensemble : ENTRYPOINT le programme, CMD ses arguments par défaut.
  • Forme exec (tableau JSON) pour que le programme soit PID 1 et s'arrête proprement sur SIGTERM.
  • ARG configure le build (jamais de secret) ; ENV configure l'exécution.

Vérifie ta compréhension

  1. Que fait docker run image bash si l'image déclare CMD ? Et si elle déclare ENTRYPOINT ?
  2. Pourquoi préférer la forme exec pour un serveur qui doit s'arrêter proprement ?
  3. Une variable déclarée avec ARG est-elle lisible par l'application une fois le conteneur lancé ?

Exercices

Exercice 1Échauffement

Une image déclare ENTRYPOINT ["echo"]. Que produit docker run img bonjour tout le monde ? Et si l'image avait déclaré CMD ["echo"] à la place ?

Voir une solution

Avec ENTRYPOINT ["echo"] : les mots sont ajoutés en arguments, donc la sortie est bonjour tout le monde. Avec CMD ["echo"] : l'argument du run remplace le CMD, Docker tente donc d'exécuter la commande bonjour (qui n'existe pas) — erreur. C'est toute la différence entre « compléter » et « remplacer ».

Exercice 2Application

Écris les deux dernières lignes d'un Dockerfile pour une image qui lance toujours python app.py, avec --workers 4 comme valeur par défaut que l'utilisateur peut remplacer.

Voir une solution

docker run img lance python app.py --workers 4 ; docker run img --workers 8 lance python app.py --workers 8 (le CMD par défaut est remplacé, l'ENTRYPOINT reste).

Exercice 3Défi

On veut choisir la version de Node au moment du build et fixer NODE_ENV pour l'exécution. Quelle instruction pour chacun, et pourquoi ne pas inverser ?

Voir une solution

La version de base est un paramètre de construction → ARG NODE_VERSION=20 (utilisé dans FROM node:${NODE_VERSION}-alpine), fixé par --build-arg. NODE_ENV doit être lu par l'application au run → ENV NODE_ENV=production. Inverser ne marcherait pas : un ARG n'existe plus dans le conteneur (l'app ne pourrait pas le lire), et un ENV ne peut pas paramétrer la ligne FROM avant que l'image n'existe.
