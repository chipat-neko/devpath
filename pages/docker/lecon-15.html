Module 6 · Projet — Leçon 15

Projet : conteneuriser une application de bout en bout

~42 min Avancé Tout le cours

À la fin de cette leçon, tu sauras

  • relier toutes les briques du cours en un projet réel ;
  • conteneuriser une app + sa base avec Compose ;
  • rendre le service robuste (healthcheck, restart) et sûr ;
  • publier une image traçable pour un déploiement reproductible.
Sommaire de la leçon

Au début de ce cours, Docker était un mot mystérieux. Tu sais maintenant écrire un Dockerfile, gérer volumes et réseaux, orchestrer avec Compose, optimiser une image, la publier, la déboguer, la sécuriser, la configurer (ENTRYPOINT, ARG, ENV) et la construire pour plusieurs plateformes. Ce projet de synthèse les fait converger : prendre une application, la conteneuriser de bout en bout, et la mener jusqu'à un déploiement reproductible. C'est exactement le chemin d'un vrai projet.

La démarche, du code à la production

Conteneuriser sérieusement suit toujours le même fil : on emballe l'application dans une image, on publie une image identifiée, puis on la déploie à l'identique, en laissant Compose lancer les services qui vont ensemble. Chaque étape mobilise une leçon du cours.

Un Compose prêt pour la production

Le cœur du projet est un compose.yaml qui réunit ce qu'on a appris : deux services reliés par un réseau implicite, un volume nommé pour persister les données, un healthcheck et un depends_on conditionné à la santé, une politique de redémarrage, et quelques options de durcissement.

Ce seul fichier condense presque tout le cours : réseau et ports (leçon 4), Compose et dépendances (leçon 5), image versionnée (leçon 7), santé et redémarrage (leçon 9), durcissement (leçon 10). Un docker compose up -d et la pile démarre à l'identique sur n'importe quelle machine.

Cas réel : la fin du « ça marche sur ma machine »

Avant Docker, l'intégration d'un nouvel arrivant se comptait en jours : installer la bonne version du langage, la base, les dépendances système, régler les écarts entre son poste et le serveur… et le fameux « chez moi ça marche » au moindre décalage. Avec un compose.yaml versionné, la commande devient git clone puis docker compose up : en quelques minutes, tout le monde — et le serveur de production — fait tourner exactement le même environnement. Le gain n'est pas que technique : c'est la reproductibilité qui supprime une classe entière de bugs « impossibles à reproduire ».

Construire une fois, déployer partout

La bonne pratique : construire l'image une seule fois, l'étiqueter (1.0.0), la scanner, puis déployer ce même artefact en test, en pré-production et en production. On ne reconstruit pas à chaque environnement (ce serait une image différente à chaque fois) ; seule la configuration (variables, secrets) change d'un environnement à l'autre. C'est le principe du Twelve-Factor App : la config vit dans l'environnement, pas dans l'image.

Pour aller plus loin

La suite naturelle de ce cours : l'intégration continue (le cours CI/CD) automatise build → scan → tag → push à chaque validation ; l'orchestration avec Kubernetes (cours dédié) gère la mise à l'échelle, l'auto-réparation et les déploiements progressifs sur des grappes de serveurs. L'image reste la brique de base : celle que tu sais construire ici est exactement celle que déploieront ces outils.

L'image, construite en deux temps

Le compose.yaml orchestre, mais chaque image mérite d'être légère. Le projet final s'appuie sur un Dockerfile multi-stage : une première étape compile avec tous les outils, une seconde ne garde que le résultat. C'est ce qui sépare une image d'un giga-octet d'une image de cent cinquante méga-octets.

Glossaire

Capstone
Projet de synthèse qui mobilise l'ensemble des notions du cours sur un cas concret et complet.
Pile (stack)
Ensemble des services conteneurisés qui composent une application (ici : app + base), décrits ensemble dans un fichier Compose.
Reproductibilité
Propriété d'obtenir le même environnement partout ; objectif central de la conteneurisation.
Artefact
Le livrable produit par le build : ici l'image étiquetée, construite une fois et déployée telle quelle.
depends_on / service_healthy
Fait attendre un service qu'une dépendance soit non seulement lancée, mais réellement saine (via son healthcheck).
Volume nommé
Stockage géré par Docker, indépendant du cycle de vie des conteneurs : les données survivent aux recréations.
Twelve-Factor
Ensemble de bonnes pratiques pour les applications ; ici : la configuration vit dans l'environnement, pas dans l'image.
Multi-stage (build multi-étapes)
Dockerfile en plusieurs étapes FROM : une étape compile avec les outils, l'étape finale ne récupère (COPY --from) que l'artefact. Résultat : une image bien plus légère et sûre.

Récap et vérification

  • La démarche : emballer (Dockerfile) → publier (tag + registre) → déployer (Compose, robustesse, sécurité).
  • Un compose.yaml versionné décrit toute la pile : services, réseau, volume, healthcheck, restart.
  • On construit l'image une fois, on l'étiquette, on la scanne ; seule la config change entre environnements.
  • Résultat : un déploiement reproductible — la fin du « ça marche sur ma machine ».

Exercices

Exercice 1Échauffement

Cite, dans l'ordre, les trois grandes étapes pour mener une application du code jusqu'à la production avec Docker.

Voir une solution

1) Emballer l'application dans une image (Dockerfile, multi-stage). 2) Publier une image étiquetée sur un registre (scan, tag, push). 3) Déployer à l'identique (pull + up), en laissant Compose lancer les services qui vont ensemble (app + base, réseau, volume), avec healthcheck, restart et durcissement.

Exercice 2Application

Ajoute à un service db (PostgreSQL) un healthcheck qui le déclare sain quand la base répond, et fais attendre le service app que db soit sain.

Voir une solution

pg_isready renvoie un succès quand PostgreSQL accepte les connexions ; condition: service_healthy retient app tant que ce n'est pas le cas.

Exercice 3Défi

Explique pourquoi on met image: monorg/monapp:1.0.0 plutôt que latest dans le Compose de production, et ce que ça change lors d'un retour arrière.

Voir une solution

Un tag de version fige ce qui tourne : on sait exactement quelle version est déployée, et le déploiement est traçable. latest est ambigu (il change dans le temps) et masque le contenu réel. Pour un retour arrière, il suffit de repointer sur le tag précédent (:0.9.0) et de relancer : l'image exacte est toujours dans le registre. Avec latest, on ne saurait pas vers quoi revenir.

Mini-projet fil rouge — conteneuriser une application

Pour clore ce cours, conteneurisons une application Node avec sa base de données. Il réunit un Dockerfile multi-étapes (image légère, utilisateur non-root) et un Compose reliant l'app et PostgreSQL (réseau, volumes, dépendances) — l'essentiel de Docker réuni.

Ce que tu vas construire

Un Dockerfile qui compile puis n'embarque que le nécessaire, et un fichier Compose qui lance l'application avec une base PostgreSQL persistante.

Étapes

L'étape de build

Pars de node:20-alpine AS build, copie les package*.json, fais npm ci puis npm run build.

L'image finale

Repars d'une image propre, installe seulement les dépendances de production (--omit=dev), puis copie le résultat avec COPY --from=build : le code, qui change le plus souvent, vient en dernier pour garder le cache.

Sécuriser

Passe en USER node, expose le port et définis le CMD.

Le Compose

Déclare deux services (app, db) avec un mappage de ports, un healthcheck sur db et un depends_on conditionné à sa santé (service_healthy).

Persister

Ajoute un volume nommé pour les données PostgreSQL.

ProjetFil rouge

Assemble les deux fichiers. Essaie d'abord par toi-même, puis compare avec la solution de référence.
