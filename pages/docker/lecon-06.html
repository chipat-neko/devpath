Module 3 · En production — Leçon 06

Images optimisées et bonnes pratiques

~40 min Avancé Leçon 05 requise

À la fin de cette leçon, tu sauras

  • alléger une image avec un build multi-stage ;
  • choisir une image de base minimale ;
  • renforcer la sécurité (non-root, .dockerignore) ;
  • préparer une image pour le déploiement.
Sommaire de la leçon

Tu sais conteneuriser et orchestrer. Reste à faire des images dignes de la production : légères (pour démarrer vite et coûter moins), sûres (pour limiter les risques), et reproductibles. Cette leçon de synthèse rassemble les bonnes pratiques qui séparent une image « qui marche » d'une image professionnelle.

Le poids, ça compte

Une image lourde se télécharge lentement, occupe le disque et la mémoire, et augmente la surface d'attaque. Première règle : partir d'une base minimale. Les variantes -slim et surtout alpine (une distribution Linux de quelques Mo) réduisent drastiquement la taille.

Alpine est le choix par défaut pour beaucoup d'images de production. Attention toutefois : Alpine utilise une bibliothèque C différente (musl), ce qui peut poser problème à de rares dépendances natives ; teste avant d'adopter.

Le build multi-stage

La technique la plus puissante : le multi-stage. Beaucoup d'applications ont besoin d'outils de construction (compilateurs, dépendances de build) qui sont inutiles à l'exécution. Le multi-stage construit dans une étape, puis ne copie que le résultat dans une image finale minuscule.

Le COPY --from=build récupère un fichier de l'étape précédente. Résultat : l'image finale ne contient que les fichiers compilés et un serveur léger — pas les centaines de Mo d'outils de build. C'est la différence entre une image de 1 Go et une de 30 Mo, pour le même service.

La sécurité de base

Quelques réflexes réduisent fortement les risques :

  • Ne pas tourner en root : par défaut, un conteneur s'exécute en root. Crée et utilise un utilisateur sans privilèges avec USER.
  • Épingler les versions : FROM node:20.11-alpine plutôt que node:latest, pour des builds reproductibles.
  • Pas de secrets dans l'image : mots de passe et clés passent par des variables d'environnement ou des secrets, jamais codés en dur dans le Dockerfile.
  • .dockerignore : exclure .git, node_modules, .env du contexte.

Le passage en utilisateur non-root est l'une des protections au meilleur rapport effort/bénéfice : si une faille de l'application est exploitée, l'attaquant n'a pas les droits root dans le conteneur, ce qui limite les dégâts.

Cas réel : le secret resté dans une couche

Une image est faite de couches empilées, chacune figée. Un développeur copie un fichier .env contenant une clé d'API, puis le supprime dans une instruction suivante : le fichier disparaît de l'image finale… mais reste présent dans la couche où il a été ajouté. N'importe qui peut le récupérer avec docker history ou en extrayant l'image (docker save). Des milliers de clés ont ainsi fuité dans des images publiques. La règle : un secret ne doit jamais entrer dans une couche — on passe par des variables d'environnement au lancement ou des secrets de build, et on exclut .env via .dockerignore.

L'ordre des instructions accélère les builds

Docker met chaque instruction en cache et rejoue tout ce qui suit un changement. En copiant d'abord package*.json et en installant les dépendances avant de copier le reste du code (COPY . .), l'installation — l'étape la plus lente — n'est refaite que si les dépendances changent. Modifier une ligne de code ne réinstalle plus tout : les builds passent de plusieurs minutes à quelques secondes.

Pour aller plus loin

Tu maîtrises maintenant l'essentiel de Docker. La suite naturelle : les healthchecks pour la robustesse ; l'analyse de vulnérabilités des images (docker scout, Trivy) ; et surtout l'orchestration à grande échelle avec Kubernetes, qui gère des centaines de conteneurs sur des grappes de serveurs (mise à l'échelle, auto-réparation, déploiements progressifs). Docker est la brique ; Kubernetes est le chef d'orchestre.

Antisèche

Glossaire

Image de base
Point de départ d'un Dockerfile (FROM) ; son poids conditionne celui de l'image finale.
Alpine
Distribution Linux minuscule (quelques Mo) souvent choisie comme base ; utilise la bibliothèque C musl, à tester avec les dépendances natives.
Build multi-stage
Dockerfile à plusieurs FROM : on construit dans une étape, puis on ne copie que le résultat dans une image finale minimale.
Étape (stage)
Une phase d'un build multi-stage, nommée avec AS ; on y pioche des fichiers avec COPY --from=….
Couche (layer)
Chaque instruction du Dockerfile crée une couche figée ; elle est mise en cache et reste inspectable — d'où le danger d'y laisser un secret.
.dockerignore
Fichier listant ce qui est exclu du contexte de build (node_modules, .git, .env) : build plus léger et plus sûr.
Utilisateur non-root (USER)
Bascule le conteneur sur un compte sans privilèges : limite les dégâts si l'application est compromise.
Registre
Serveur qui stocke et distribue les images (Docker Hub, registre cloud…) ; on y push puis on pull en production.

Récap et vérification

  • Partir d'une base minimale (-slim, alpine) allège l'image.
  • Le multi-stage (FROM … AS build + COPY --from=build) ne garde que le résultat, pas les outils de build.
  • Sécurité : utilisateur non-root (USER), versions épinglées, pas de secrets en dur, .dockerignore.
  • Déploiement : tag de version, push sur un registre, pull + run en production (souvent via CI/CD).

Exercices

Exercice 1Échauffement

Cite deux façons de réduire la taille d'une image Docker.

Voir une solution

1) Partir d'une image de base minimale (-slim ou alpine) au lieu de l'image complète. 2) Utiliser un build multi-stage pour ne garder que le résultat de la construction, sans les outils de build. (Bonus : un .dockerignore qui exclut node_modules, .git, etc.)

Exercice 2Application

Ajoute à un Dockerfile les instructions qui créent un utilisateur non privilégié app et basculent dessus (base Alpine).

Voir une solution

On crée un groupe et un utilisateur système, puis USER app fait que tout ce qui suit (et le conteneur au démarrage) s'exécute sans les droits root.

Exercice 3Défi

Écris un Dockerfile multi-stage pour une app web statique : une étape node:20 qui fait npm run build (sortie dans dist/), puis une image finale nginx:alpine qui sert ce dist/.

Voir une solution

L'étape build compile l'application ; l'image finale ne contient que le dist/ servi par nginx — ni Node, ni dépendances, ni code source.
