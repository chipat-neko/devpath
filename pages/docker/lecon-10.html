Module 4 · Docker au quotidien — Leçon 10

Renforcer la sécurité : images et chaîne d'approvisionnement

~38 min Avancé Leçon 09 requise

À la fin de cette leçon, tu sauras

  • réduire la surface d'attaque d'une image (distroless) ;
  • scanner les vulnérabilités connues (docker scout, Trivy) ;
  • durcir l'exécution (--read-only, --cap-drop) ;
  • protéger les secrets au build et sécuriser la chaîne.
Sommaire de la leçon

La leçon 6 a posé les réflexes de base : image minimale, utilisateur non-root, pas de secret codé en dur, .dockerignore. C'est le socle. Mais une image de production affronte un monde hostile : des failles connues dans ses dépendances, des images publiques piégées, un conteneur qui, s'il est compromis, ne doit pas devenir un tremplin. Cette leçon va plus loin : réduire encore la surface, scanner, durcir, protéger les secrets, et sécuriser toute la chaîne d'approvisionnement — de l'image d'origine jusqu'à ce qui tourne en production.

Moins d'image, moins de surface d'attaque

Chaque paquet présent dans une image est une porte potentielle : une faille dans le shell, dans curl, dans une bibliothèque système peut être exploitée. Le principe est simple : ce qui n'est pas là ne peut pas être attaqué. Au-delà d'Alpine (vu en leçon 6), deux options poussent la logique à l'extrême :

  • les images distroless (Google) : le strict nécessaire pour faire tourner l'app (le runtime), sans gestionnaire de paquets ni shell ;
  • FROM scratch : une image vide, pour un binaire statique (courant en Go, Rust) qui n'a besoin de rien d'autre.

Sans shell, un attaquant qui parvient à exécuter du code ne peut même pas ouvrir de terminal ni installer d'outils : beaucoup de techniques d'intrusion tombent à plat.

Scanner les vulnérabilités connues

Même une image soignée peut embarquer une faille répertoriée (une CVE, identifiant public d'une vulnérabilité) dans sa base ou une dépendance. Un scanner compare le contenu de l'image à des bases de données de vulnérabilités et liste les problèmes, classés par gravité :

Le geste qui corrige le plus de failles d'un coup : mettre à jour l'image de base et reconstruire. Beaucoup de CVE viennent du système sous-jacent, pas de ton code ; une base récente les efface. On rescanne ensuite pour vérifier, et on intègre le scan à la CI pour bloquer toute image trop vulnérable avant qu'elle n'atteigne la production.

Durcir l'exécution du conteneur

Par défaut, un conteneur est plus permissif qu'il ne devrait : il tourne en root (vu en leçon 6), avec un jeu de capabilities (privilèges Linux fins) et un système de fichiers modifiable. On réduit ces pouvoirs au lancement :

La même chose se déclare en Compose (read_only: true, cap_drop: [ALL], security_opt). L'idée directrice est le moindre privilège : on part de « rien » et on ajoute uniquement ce dont l'application a strictement besoin. Un rootfs en lecture seule empêche un intrus d'y déposer un binaire malveillant.

Un secret dans ARG ou ENV reste visible

Passer une clé via ARG CLE=… ou ENV CLE=… la fige dans une couche : elle ressort avec docker history ou en extrayant l'image. Pour un secret nécessaire uniquement pendant le build (jeton privé, clé de dépôt), utilise le montage de secret de BuildKit : RUN --mount=type=secret,id=npmtoken …. Le secret est disponible le temps de la commande, puis n'entre dans aucune couche. Pour un secret d'exécution, on l'injecte au lancement (variable, secret d'orchestrateur), jamais dans l'image.

Sécuriser la chaîne d'approvisionnement

D'où vient l'image de départ ? Peux-tu prouver que celle qui tourne en production est bien celle que tu as construite ? C'est la question de la chaîne d'approvisionnement logicielle (supply chain). Quatre pratiques la solidifient :

  • Partir d'images de confiance : les Docker Official Images et les éditeurs vérifiés, pas la première image publique venue.
  • Épingler par digest : FROM node:20-alpine@sha256:abc… fige le contenu exact (un tag peut être redéployé sur une autre image ; le digest, jamais).
  • Signer les images : cosign (projet Sigstore) ou Docker Content Trust attachent une signature vérifiable ; la production n'exécute que ce qui est signé.
  • Produire un SBOM : l'inventaire (Software Bill of Materials) de tous les composants de l'image, pour savoir en une requête si une nouvelle CVE te concerne.

Cas réel : les images piégées de Docker Hub

Des chercheurs en sécurité ont découvert sur le Docker Hub public une série d'images (autour du compte docker123321) qui, sous des noms anodins, embarquaient un mineur de cryptomonnaie (Monero). Tirées et lancées des millions de fois, elles ont détourné la puissance de calcul de qui les exécutait, pour un gain estimé à plusieurs dizaines de milliers de dollars. La leçon : docker pull exécute du code écrit par un inconnu. On part d'images officielles ou d'éditeurs vérifiés, on épingle par digest, on scanne, et en environnement sensible on n'exécute que des images signées.

Pas de shell = pas de terminal pour l'intrus

Une image distroless ou scratch n'a pas de sh. Concrètement, une faille de type « exécution de commande » ne trouve rien à lancer : ni shell, ni curl, ni gestionnaire de paquets pour télécharger un outil. Contrepartie : tu ne peux plus faire docker exec … sh pour déboguer (leçon 9). On garde alors une variante :debug pour le développement, et l'image nue pour la production.

Pour aller plus loin

Sigstore/cosign a rendu la signature accessible sans gérer de clés à la main (signature « sans clé » adossée à une identité). Côté provenance, le cadre SLSA décrit des niveaux de garantie sur comment un artefact a été produit. Dans un cluster Kubernetes, un admission controller (Kyverno, OPA/Gatekeeper) peut refuser tout déploiement d'image non signée ou trop vulnérable : la politique de sécurité devient automatique. Outils à connaître : trivy et grype (scan), syft (SBOM), cosign (signature).

Antisèche

Glossaire

CVE
Common Vulnerabilities and Exposures : identifiant public d'une faille de sécurité répertoriée (ex. CVE-2021-44228).
Scan de vulnérabilités
Analyse d'une image comparant ses composants à des bases de CVE ; outils : docker scout, Trivy, Grype.
Distroless
Image ne contenant que le runtime de l'application, sans shell ni gestionnaire de paquets : surface d'attaque minimale.
Capability
Privilège Linux fin (accès réseau, montage…) ; --cap-drop ALL les retire tous, on n'en rajoute que le strict nécessaire.
Rootfs en lecture seule
Système de fichiers du conteneur monté en lecture seule (--read-only) : empêche d'y écrire un binaire malveillant.
Secret de build (BuildKit)
RUN --mount=type=secret : rend un secret disponible pendant une commande de build sans le figer dans une couche.
Digest
Empreinte sha256 du contenu exact d'une image ; épingler par digest garantit l'immuabilité, là où un tag peut bouger.
Signature d'image
Preuve cryptographique d'origine et d'intégrité (cosign, Docker Content Trust) ; vérifiée avant l'exécution.
SBOM
Software Bill of Materials : inventaire des composants d'une image, pour tracer rapidement l'impact d'une nouvelle faille.

Récap et vérification

  • Moins de contenu = moins de surface : distroless/scratch retirent shell et outils.
  • Scanner (docker scout, Trivy) puis mettre à jour la base efface la plupart des CVE ; à automatiser en CI.
  • Durcir l'exécution : non-root, --cap-drop ALL, --read-only, no-new-privileges (moindre privilège).
  • Secrets via BuildKit (build) ou injection au lancement, jamais dans une couche ; sécuriser la chaîne : digest, signature, SBOM.

Exercice 2Application

Écris la commande docker run qui lance monapp en utilisateur non-root (UID 1000), système de fichiers en lecture seule, et sans aucune capability Linux.

Voir une solution

C'est le principe du moindre privilège : on retire tout, puis on ne rajoute (--cap-add, --tmpfs) que ce dont l'application a réellement besoin.
