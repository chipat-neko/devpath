Module 5 · Aller plus loin — Leçon 14

Gérer l'espace et le stockage

~38 min Avancé Leçon 02 requise

À la fin de cette leçon, tu sauras

  • voir où part l'espace disque avec docker system df ;
  • reconnaître images dangling, conteneurs arrêtés et volumes orphelins ;
  • nettoyer avec prune sans effacer tes données ;
  • inspecter le poids couche par couche avec docker history.
Sommaire de la leçon

Après quelques semaines d'usage, Docker occupe étonnamment vite plusieurs gigaoctets : images empilées, conteneurs oubliés, volumes de bases éphémères, cache de build. Un jour, le disque est plein et un docker build échoue faute d'espace. Cette leçon t'apprend à voir où va cet espace et à le récupérer — sans jamais supprimer par mégarde des données qui comptent.

Où passe l'espace disque

Docker range ce qu'il stocke en quatre catégories : les images, les conteneurs, les volumes et le cache de build. Une seule commande dresse le bilan :

La colonne RECLAIMABLE (« récupérable ») est la plus parlante : c'est l'espace que tu peux libérer sans toucher à ce qui sert. Ici, près de 4 Go dorment. La différence TOTAL − ACTIVE donne ce qui n'est plus référencé par rien.

Cas réel : les logs qui remplissent le disque en silence

Un poste échappe à docker system df : les journaux. Par défaut, Docker écrit tout ce qu'un conteneur envoie sur sa sortie dans un fichier *-json.log qui grossit sans aucune limite. Un serveur bavard qui tourne des mois peut ainsi engloutir des dizaines de gigaoctets — invisibles dans le df, mais bien réels sur le disque. La parade est de plafonner la rotation dès le départ, par conteneur (--log-opt max-size=10m --log-opt max-file=3) ou globalement dans /etc/docker/daemon.json. Sans cette limite, aucun prune ne réglera le problème : il ne touche pas aux logs d'un conteneur vivant.

Images dangling et anciennes versions

Chaque fois que tu reconstruis une image sous le même nom, l'ancienne version perd son tag mais reste sur le disque, affichée <none> dans docker images : c'est une image dangling (« qui pend »). Ajoute les anciennes versions taguées (monapp:0.9, :0.8…) qu'on ne lance plus, et les gigaoctets s'accumulent.

docker image prune (sans option) est sûr : il ne retire que les <none>, jamais une image taguée. Le -a va bien plus loin : il supprime toute image qu'aucun conteneur n'utilise actuellement — y compris des images taguées que tu comptais réutiliser. À réserver à un vrai grand ménage.

Conteneurs arrêtés et volumes orphelins

Un conteneur qui s'arrête ne disparaît pas : il reste, avec sa couche d'écriture, visible par docker ps -a. Lancer beaucoup de conteneurs jetables (tests, essais) en laisse des dizaines. De même, un volume dont plus aucun conteneur ne se sert devient orphelin.

Supprimer un conteneur arrêté est sans danger : ses données utiles, si l'application est bien faite, vivent dans un volume, pas dans le conteneur (leçon 4). En revanche, docker volume prune touche au stockage : un volume « non utilisé » aujourd'hui peut contenir la base d'un projet simplement arrêté. À manier en regardant d'abord la liste.

Le prune qui a effacé la base de données

Le piège classique : un développeur veut « faire de la place » et lance docker system prune -a --volumes en fin de journée. Le --volumes supprime tous les volumes non attachés à un conteneur en marche : la base de développement, dont le conteneur était simplement arrêté, part avec. Les données sont perdues. La règle : --volumes ne se tape jamais par réflexe. Vérifie d'abord docker volume ls, et garde tes données importantes dans des volumes nommés que tu sais identifier.

Piège : les volumes anonymes qui s'accumulent

Un volume peut être nommé (docker run -v pgdata:/var/lib/postgresql/data) ou anonyme : Docker en crée un tout seul, au nom illisible fait de 64 caractères, dès qu'un conteneur déclare un VOLUME dans son image ou qu'on écrit -v /chemin sans nom. À chaque run, un nouveau volume anonyme naît ; l'ancien devient orphelin mais reste sur le disque. Relance dix fois un conteneur Postgres « pour tester » et tu te retrouves avec dix volumes anonymes, impossibles à distinguer. La leçon : nomme toujours les volumes qui comptent — un volume nommé est réutilisé et identifiable, un volume anonyme se perd dans la masse.

Retiens l'échelle : system prune seul est sûr (il ne touche ni les images que tu utilises, ni les volumes) ; -a ajoute les images non utilisées ; --volumes ajoute les données. Chaque cran demande plus de vigilance. Docker demande d'ailleurs confirmation avant d'agir — lis ce qu'il annonce.

Pour aller plus loin : le cache de build a sa propre comptabilité

Sous BuildKit (le moteur par défaut), le cache de build n'est pas un simple tas d'images : c'est un magasin à part, souvent le premier poste à gonfler quand on itère sur un Dockerfile. Deux commandes le maîtrisent finement. docker system df -v (mode verbeux) détaille chaque entrée — bien plus que le total agrégé du df ordinaire — et montre laquelle pèse. Et plutôt que de tout vider, on peut nettoyer par âge avec un filtre : docker builder prune --filter until=168h ne supprime que les entrées de plus d'une semaine, préservant le cache récent qui accélère encore tes builds. Utile pour un ménage régulier sans repartir de zéro à chaque fois.

Inspecter le poids couche par couche

Quand une image est trop lourde, docker history montre le poids couche par couche et désigne le coupable : une dépendance oubliée, un fichier volumineux copié par erreur, un cache de paquets non nettoyé.

On lit d'un coup d'œil que npm ci pèse 180 Mo : c'est là qu'un multi-stage (leçon 6) ou un --omit=dev ferait fondre l'image. docker history est aussi l'outil qui révèle un secret resté dans une couche : si tu y vois un COPY .env, c'est le signal d'alarme vu à la leçon 6.

Prévenir plutôt que nettoyer

Le meilleur nettoyage est celui qu'on n'a pas à faire. Deux réflexes limitent l'accumulation : docker run --rm supprime le conteneur automatiquement à sa fin (idéal pour les commandes jetables), et un bon .dockerignore (leçon 3) évite de gonfler le contexte et les images. Pour le reste, un docker system prune périodique suffit à garder un environnement sain.

Antisèche

Glossaire

docker system df
Affiche l'espace occupé par les images, conteneurs, volumes et cache, avec la part récupérable.
Image dangling
Image sans tag (<none>), typiquement une version remplacée par un rebuild ; se supprime sans risque.
Conteneur arrêté
Conteneur qui a fini de tourner mais reste sur le disque (visible avec docker ps -a) tant qu'on ne le supprime pas.
Volume orphelin
Volume qu'aucun conteneur n'utilise ; il peut malgré tout contenir des données précieuses.
prune
Famille de commandes qui suppriment les objets inutilisés ; -a et --volumes élargissent (et risquent) la coupe.
RECLAIMABLE
Colonne de system df indiquant l'espace libérable sans casser ce qui sert.
docker history
Liste les couches d'une image et leur taille ; révèle une couche trop lourde ou un secret oublié.

Récap et vérification

  • docker system df montre où part l'espace : images, conteneurs, volumes, cache de build.
  • Les images <none> (dangling), conteneurs arrêtés et cache se nettoient sans risque.
  • system prune est sûr ; -a retire les images non utilisées ; --volumes efface des données.
  • docker history révèle la couche trop lourde — ou le secret resté dans l'image.

Exercices

Exercice 1Échauffement

Dans la sortie de docker images, tu vois plusieurs lignes marquées <none>. Qu'est-ce que c'est, et quelle commande les enlève sans toucher au reste ?

Voir une solution

Ce sont des images dangling : d'anciennes versions qui ont perdu leur tag lors d'un rebuild, mais restent sur le disque. docker image prune (sans -a) les supprime toutes, et uniquement elles : aucune image taguée n'est touchée.

Exercice 2Application

Un collègue veut « tout nettoyer » et s'apprête à taper docker system prune -a --volumes. Que lui conseilles-tu de vérifier d'abord, et pourquoi ?

Voir une solution

De regarder d'abord docker volume ls (et docker ps -a). Le --volumes efface les volumes non rattachés à un conteneur en marche : la base d'un projet simplement arrêté partirait avec ses données. Pour un ménage courant, docker system prune seul suffit et ne touche pas aux volumes.

Exercice 3Défi

Une image pèse 1,2 Go alors qu'elle ne sert qu'un petit site statique. Quelle commande utilises-tu pour comprendre, et vers quelle technique du cours te tourneras-tu ?

Voir une solution

docker history monimage montre la taille de chaque couche. On y repère typiquement une base trop lourde ou des outils de build (compilateur, node_modules) restés dans l'image. La parade : un build multi-stage (leçon 6) qui ne copie que le résultat compilé dans une image finale minimale, plus une base -alpine. On passe souvent du gigaoctet à quelques dizaines de Mo.
