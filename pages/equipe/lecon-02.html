Module 1 · Entrer dans le code des autres — Leçon 02

Lire le code des autres

~33 min Débutant Prérequis : la leçon 1

À la fin de cette leçon, tu sauras

  • aborder un code inconnu sans chercher à tout comprendre — seulement « assez pour la tâche » ;
  • trouver un point d'entrée et remonter le fil, à partir d'un symptôme observé ou du démarrage du programme ;
  • suivre une donnée à la trace à travers les couches, lire les tests comme une spécification exécutable ;
  • interroger l'historique (git log, git blame) pour retrouver le pourquoi, et poser une bonne question quand chercher seul ne suffit plus.
Sommaire de la leçon

Deuxième semaine de Sam dans l'équipe, et déjà une vraie mission : un bug. Depuis hier, les e-mails de confirmation d'adhésion ne partent plus dans Repère. Une association crée un compte, valide son adhésion… et ne reçoit rien. Inès a assigné le ticket à Sam : « Bon premier vrai bug, prends ton temps. » Sam ouvre le dépôt. Des dizaines de dossiers, des milliers de lignes, écrites par Karim, Léa, Théo — des gens, pas Sam. Nulle part un fichier envoi_des_mails.py qui dirait par où commencer.

C'est l'angoisse de la page blanche, en négatif : non pas une page vide à remplir, mais une masse pleine à comprendre. Par où entrer ? Ici commence une compétence dont personne ne parle quand on apprend à programmer, et qui occupe pourtant l'essentiel d'une journée de développeur en équipe : lire le code des autres. Ce n'est pas « écrire, mais à l'envers ». C'est une activité distincte, avec ses propres réflexes — et ce sont eux que cette leçon va outiller, à travers le bug de Sam.

Lire n'est pas écrire

Le premier réflexe, quand on découvre un gros code, c'est de vouloir le comprendre en entier avant d'y toucher. C'est un piège, et c'est épuisant : un projet réel ne tient pas dans une tête. La bonne question n'est jamais « comment marche tout ça ? » mais « qu'est-ce que j'ai besoin de comprendre pour ma tâche ? ». Sam n'a pas à maîtriser Repère ; Sam a un e-mail qui ne part pas, et un chemin précis à éclairer là-dedans.

Ces deux lectures ne se font pas au même moment ni au même prix. Le survol est rapide et bon marché : on parcourt l'arborescence des dossiers, on repère les grands blocs (le front, l'API, la base, l'envoi des mails), on se fait une carte grossière. La plongée est lente et coûteuse : on suit chaque ligne d'une fonction, on tient dans sa tête ce que valent les variables. La compétence, c'est de survoler beaucoup et plonger peu — réserver l'effort de la plongée à la seule zone qui décide de la tâche.

« Assez pour la tâche », pas « tout »

Un développeur expérimenté ne connaît pas « tout » le code sur lequel il travaille — souvent, il en ignore de vastes pans. Ce qu'il sait faire, c'est découper sa tâche jusqu'à un morceau qu'il peut comprendre isolément, et faire confiance au reste sans l'ouvrir. Viser la compréhension totale d'un gros projet n'est pas de la rigueur : c'est une manière de ne jamais commencer.

Trouver le point d'entrée

Un code inconnu n'a pas de « début » évident ; il faut s'en donner un. Ce point de départ d'où l'on commence à tirer le fil s'appelle le point d'entrée. Il y en a deux grandes familles, et Sam peut choisir l'une ou l'autre selon ce qu'il a sous la main.

La première consiste à partir de ce qu'on observe. Sam voit un symptôme : pas d'e-mail. Il tient aussi un indice précis — le message affiché à l'écran après l'inscription (« Votre demande a bien été enregistrée »), une ligne dans les journaux (envoi email : file pleine), le libellé d'un bouton. Chacun de ces fragments est une chaîne de caractères qui existe quelque part dans le code. La chercher (avec l'outil de recherche de l'éditeur) mène droit à l'endroit qui la produit : de là, on remonte le fil, couche après couche.

La seconde consiste à partir du point d'entrée du programme lui-même : le main, le fichier de démarrage, ou — pour une application web comme Repère — la table des routes qui associe chaque URL à un bout de code. L'adhésion se valide via un formulaire qui envoie une requête à l'URL /adhesions ? Alors la route /adhesions pointe vers la fonction qui traite l'inscription. On part du haut et on descend.

Astuce : une chaîne de texte est un fil à tirer

Le raccourci le plus rentable pour entrer dans un code inconnu : recopie un bout de texte visible (un message d'erreur, un libellé de bouton, un mot du journal) et cherche-le dans tout le projet. Le texte affiché est presque toujours écrit en clair dans le code, à un seul endroit. Tu passes de « je ne sais pas par où commencer » à « me voici exactement à la bonne ligne » en une recherche.

Suivre une donnée à la trace

Une fois le point d'entrée trouvé, la meilleure boussole dans un code qu'on ne connaît pas est de choisir une donnée et de la suivre. Sam ne cherche pas à comprendre toute l'inscription : il suit un seul objet, l'e-mail de confirmation, de l'endroit où il naît jusqu'à celui où il devrait partir. C'est le fil d'Ariane : tant qu'on tient la donnée des yeux, on ne se perd pas dans les branches qui ne la concernent pas.

Concrètement, on repère la fonction qui fabrique l'e-mail, puis on lit seulement les endroits où cet objet est passé à la suivante. Voici, dans Repère, la fonction sur laquelle Sam finit par tomber en suivant le fil. Il ne la lit pas pour tout comprendre ; il la lit pour répondre à une seule question : « l'e-mail arrive-t-il bien dans la file ? »

Sam relit lentement. Le message est bien construit (première étape : d'accord). Puis un if file_envoi.est_pleine() tout neuf : si la file est pleine, on écrit une ligne dans le journal et on return — sans ajouter le message. Or le journal disait justement file pleine. Le fil est retrouvé : l'e-mail est préparé, mais un garde-fou récent le laisse tomber quand la file est saturée. Sam n'a pas eu à comprendre Repère en entier ; il a suivi une donnée jusqu'à l'endroit où elle se perd.

Piège fréquent

Lire le code « dans le vide », sans jamais lancer le programme. On peut passer une heure à raisonner sur ce que devrait faire une fonction, quand deux minutes d'exécution (un point d'arrêt, un message affiché, un test lancé) montreraient ce qu'elle fait vraiment. La lecture statique et l'observation dynamique se complètent : la seconde tranche les hypothèses que la première multiplie.

Lire les tests d'abord

Il existe un endroit du code écrit exprès pour expliquer comment on l'utilise : les tests. Un test montre noir sur blanc comment on appelle une fonction — avec quelles entrées — et ce qu'on attend en retour. C'est une spécification exécutable : contrairement à un commentaire, il ne peut pas mentir sans que la machine s'en aperçoive, puisqu'il tourne. Avant d'ouvrir envoyer_confirmation, Sam aurait pu chercher test_envoi_confirmation : le test lui aurait offert un exemple d'usage prêt à lire, et la liste des cas que le code est censé gérer.

Astuce : le test est le mode d'emploi

Pour comprendre faire_un_truc, cherche d'abord test_faire_un_truc. Le test te donne gratuitement : un exemple d'appel qui compile, les entrées typiques, le résultat attendu, et souvent les cas limites auxquels tu n'aurais pas pensé. Lire le test avant le code, c'est lire la notice avant de démonter l'appareil.

Ici, le test raconte une histoire lisible sans même connaître Repère : on prépare une adhésion, on appelle la fonction, on vérifie que la file contient bien un message ensuite. Et un détail saute aux yeux : il n'existe aucun test pour le cas « file pleine ». Le garde-fou a été ajouté sans filet — ce que Sam notera pour la suite.

Note

Les tests sont une porte d'entrée, pas une garantie. Un chemin non testé — comme le cas « file pleine » ici — est justement celui où les bugs se cachent. Lire les tests t'apprend donc deux choses : ce que le code promet de faire (les cas couverts) et, en creux, ce sur quoi personne ne veille (les cas absents). Les deux sont précieux quand on chasse un bug. On revient sur l'écriture des tests dans le cours Les tests.

Interroger l'historique : git log et git blame

Sam a trouvé la ligne fautive. Mais une question demeure : pourquoi ce garde-fou existe-t-il ? Le supprimer bêtement rétablirait peut-être les e-mails… tout en réintroduisant le problème que ce code visait à régler. Le code dit le quoi (ce qui se passe) ; il ne dit presque jamais le pourquoi (la raison qui a mené là). Ce pourquoi, il est ailleurs : dans l'historique du dépôt.

Deux commandes suffisent pour l'essentiel. git log déroule l'histoire des changements ; git blame attribue chaque ligne d'un fichier au commit qui l'a écrite. À partir de là, on remonte au message de ce commit — et donc à la raison. On peut même demander à Git de retrouver tous les commits qui ont touché à un motif précis (ici, la file d'envoi), avec l'option -S.

Sam lance git blame sur la ligne du garde-fou. Le commit s'appelle a3f9c1, signé Karim, trois semaines plus tôt. Son message : « Protéger l'envoi quand la file sature (incident du 14) — sans ce garde-fou, le serveur tombait. » Tout s'éclaire : le garde-fou n'est pas une erreur, c'est un pansement posé un jour d'incident. Le vrai bug n'est pas qu'il existe, mais qu'il abandonne silencieusement les e-mails au lieu de les réessayer plus tard. Sans l'historique, Sam aurait « réparé » en cassant autre chose. (Toutes ces commandes sont détaillées dans le cours Git ; ici, on s'en sert comme d'un outil de lecture.)

Pour aller plus loin

L'historique ne vaut que ce que valent les messages de commit. Un « fix » laconique n'apprend rien ; un message qui dit pourquoi (l'incident, la contrainte, l'alternative écartée) est un cadeau au lecteur futur — souvent toi. C'est tout le sujet de la leçon 7, « Écrire un bon message de commit » : quand on a lu du code des autres, on comprend enfin pourquoi ces messages comptent tant.

Poser une bonne question

Lire seul a des limites, et savoir quand s'arrêter de chercher fait partie de la compétence. La règle de bon sens dans l'équipe de Repère : on cherche seul un temps raisonnable — assez pour comprendre le terrain — puis on demande, avant de s'enliser une demi-journée sur ce qu'un collègue expliquerait en deux minutes. Chercher d'abord n'est pas de la fierté : c'est ce qui rend la question utile quand on la pose.

Car toutes les questions ne se valent pas. « Comment marche l'envoi des mails ? » oblige le collègue à tout reprendre depuis zéro ; c'est une demande de cours, pas d'aide. À l'inverse, une question qui montre le chemin déjà parcouru — ce qu'on a lu, ce qu'on croit, et le point précis de doute — se répond d'un mot et prouve qu'on a fait sa part. Comparons ce que Sam pourrait demander à Léa.

Sam pose la seconde. Léa répond en une phrase : le worker qui vide la file est planté depuis jeudi ; la file déborde ; le garde-fou fait donc son office… un peu trop bien. Le vrai correctif n'est même pas dans le fichier que Sam lisait. Mais sans l'avoir lu, sans avoir suivi la donnée et interrogé l'historique, Sam n'aurait pas pu poser cette question-là. Bien lire le code des autres, c'est aussi ce qui permet, le moment venu, de bien leur parler.

Une bonne question tient en quatre morceaux

Le contexte (quel symptôme, quel objectif), le chemin (ce que tu as déjà lu ou essayé), l'hypothèse (ce que tu crois qu'il se passe) et le point de doute (la seule chose que tu n'arrives pas à trancher). Une question ainsi cadrée respecte le temps de l'autre, et te fait avancer même lorsque la réponse est « non » — car elle infirme une hypothèse précise.

Pièges fréquents

Piège fréquent

Vouloir tout comprendre avant de commencer. Devant un gros code, on se dit « je lirai tout, puis je m'attaquerai au bug ». On n'y arrive jamais : le projet est trop grand, on se décourage, on n'a rien corrigé. La lecture efficace est ciblée : on part de la tâche, on éclaire le chemin qu'elle exige, et on laisse le reste dans l'ombre — pour l'instant.

  • Lire sans jamais exécuter — raisonner sur ce que le code « devrait » faire alors qu'un point d'arrêt ou un test montrerait ce qu'il fait vraiment. L'observation tranche ce que la lecture suppose.
  • Ignorer les tests et l'historique — se priver des deux sources qui expliquent le code : le test dit comment on l'appelle, le commit dit pourquoi il est là. Sans elles, on relit dix fois la même ligne sans comprendre son sens.
  • Retirer un code « bizarre » qu'on ne comprend pas — une ligne étrange cache souvent une raison invisible (un incident passé, un cas limite). On l'interroge (git blame) avant de la supprimer ; on ne la juge pas sur sa seule apparence.

Cas réel

Cas réel

Sur un vieux service de facturation, un développeur reprend un module qu'il ne connaît pas et tombe sur une ligne absurde : un montant est arrondi puis multiplié par 1.0, ce qui ne sert visiblement à rien. Convaincu d'avoir trouvé une scorie, il la supprime, tout passe au vert, il livre. Trois jours plus tard, la comptabilité signale des écarts d'un centime sur des milliers de factures. Ce * 1.0 forçait en réalité un type décimal qui changeait la règle d'arrondi ; un git blame l'aurait mené à un commit intitulé « corrige l'arrondi des centimes — ne pas retirer ». La leçon n'est pas « ne touche à rien » : c'est qu'un code qu'on ne comprend pas n'est pas forcément un code inutile. Avant de retirer l'étrange, on lui demande son histoire.

Antisèche

Glossaire

Point d'entrée
Endroit d'où l'on commence à lire un code inconnu : soit un symptôme observé (message, journal), soit le démarrage du programme (le main, une route).
Lecture en survol
Lecture large et rapide qui donne la forme du projet (dossiers, couches, grands blocs), sans entrer dans le détail des fonctions.
Lecture en profondeur
Lecture lente et détaillée d'une portion précise (souvent une fonction), ligne à ligne ; réservée à la zone qui décide de la tâche.
Suivre une donnée / trace
Stratégie consistant à choisir un objet (ici l'e-mail) et à le suivre de couche en couche, pour ne lire que le chemin qui le concerne.
git blame
Commande Git qui indique, pour chaque ligne d'un fichier, le commit, l'auteur et la date qui l'ont introduite ; sert à remonter à la raison d'une ligne.
git log
Commande Git qui déroule l'historique des commits d'un dépôt ou d'un fichier ; avec -S "motif", retrouve les commits touchant un motif donné.
Spécification exécutable
Un test vu comme une description du comportement attendu qui, contrairement à un commentaire, tourne : il montre comment appeler le code et ce qu'il doit renvoyer.
Charge cognitive
Quantité d'informations qu'on doit tenir en tête en même temps pour comprendre du code ; la lire de façon ciblée sert à la maintenir supportable.
Question bien posée
Demande qui montre le chemin déjà parcouru — contexte, ce qu'on a lu, hypothèse, point précis de doute — et se répond vite, au lieu d'exiger un cours.

Récap et vérification

  • Lire n'est pas écrire : on ne cherche pas à tout comprendre, mais « assez pour la tâche » ; on survole beaucoup et on plonge peu, sur la seule zone utile.
  • On se donne un point d'entrée : remonter depuis un symptôme observé (recopier un texte et le chercher) ou descendre depuis la route ; puis suivre une donnée à la trace de couche en couche.
  • Les tests sont une spécification exécutable (le mode d'emploi) ; l'historique (git log, git blame) donne le pourquoi qu'un code ne dit jamais.
  • Chercher seul a des limites : une bonne question (contexte + chemin + hypothèse + point de doute) respecte le temps de l'autre et fait avancer, même quand la réponse est « non ».

Vérifie ta compréhension

  1. Pourquoi vouloir « tout comprendre » d'un gros code avant d'y toucher est-il un mauvais point de départ ? Que vise-t-on à la place ?
  2. Tu vois à l'écran le message « Paiement refusé » sans savoir d'où il vient. Décris une manière rapide de trouver le code qui le produit.
  3. Sur une ligne de code étrange que tu n'oses pas supprimer, quelle commande Git te mène à la raison de sa présence, et par quels intermédiaires ?
