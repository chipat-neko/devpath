Module 3 · Communiquer autour du code — Leçon 09

Documenter ce qui compte

~35 min Intermédiaire Prérequis : le module 2

À la fin de cette leçon, tu sauras

  • documenter le pourquoi (l'intention, la contrainte, le piège évité) et laisser le code dire le quoi ;
  • situer les niveaux de documentation — README, doc d'API, ADR, runbook — et le besoin auquel chacun répond ;
  • reconnaître ce qu'il ne faut pas documenter, pour ne pas écrire une doc qui se périmera ;
  • comprendre pourquoi une doc qui ment est pire que pas de doc, et comment la garder près du code ;
  • écrire un ADR court pour tracer une décision structurante qu'on te redemandera un jour.
Sommaire de la leçon

Sam corrige un bug dans Repère et tombe sur une ligne qui n'a aucun sens : juste avant d'envoyer une requête à un service externe, le code attend deux secondes — un sleep(2) sec, planté là. Pourquoi ? Rien ne l'explique. Sam remonte le fichier, cherche un commentaire : rien. Ou, presque pire, quelques lignes plus haut, un commentaire qui annonce fièrement // on envoie la requête juste au-dessus de la ligne qui envoie la requête. Il décrit ce que le code fait déjà, mot pour mot, et ne dit rien de ce qui intrigue vraiment. Sam est seul face à une intention perdue.

C'est le drame ordinaire de la documentation : on en écrit trop là où le code se suffit, et pas assez là où il faudrait. Documenter, ce n'est pas tout écrire ; c'est capturer précisément ce que le code ne peut pas dire de lui-même — l'intention derrière un choix, la contrainte qui l'a imposé, le piège qu'il évite. Cette leçon trie : quoi documenter, à quel niveau, et surtout quoi ne pas documenter pour ne pas se retrouver avec une doc qui ment.

Documenter le pourquoi, pas le quoi

Le code est déjà la description exacte de ce qu'il fait. Il dit le quoi mieux que n'importe quelle phrase : il est exécuté, il ne peut pas mentir sur son comportement. Ce que le code ne dit jamais, c'est le pourquoi : pourquoi cette valeur-là et pas une autre, pourquoi cet ordre bizarre, pourquoi ce détour qui semble inutile. Un commentaire, une ligne de doc, ne valent leur place que s'ils portent cette part invisible.

Le premier commentaire — incrémente i — est du bruit. Il répète ce que i = i + 1 hurle déjà ; il alourdit la lecture et, pire, il devra être maintenu pour rien. Le second explique la contrainte (la limite du service distant), la conséquence évitée (les erreurs 429) et donne même une trace (le ticket). Sam, en lisant ça, comprend en cinq secondes ce qui lui aurait coûté une demi-heure d'enquête — et sait qu'il ne doit surtout pas « nettoyer » cette ligne.

Le test du « pourquoi »

Avant d'écrire un commentaire, demande-toi : est-ce que le code le dit déjà ? Si oui, supprime le commentaire — il ne fait que du bruit. S'il ajoute une information que le lecteur ne peut pas déduire (une raison, un lien vers un ticket, un piège), garde-le. Le bon réflexe est de commencer chaque commentaire mentalement par « parce que… », « attention… » ou « sinon… ».

Il y a un cas particulier utile : parfois le meilleur commentaire n'existe pas, parce qu'un bon nom l'a rendu superflu. Une constante DELAI_ANTI_SATURATION_S = 2 se passe presque de commentaire ; le nom porte déjà l'intention. On y reviendra : la première documentation d'un code, c'est le code lui-même, bien nommé.

Les niveaux de documentation

« La doc » n'est pas une chose unique. C'est un empilement de documents qui répondent chacun à un besoin et à un public différents. Les mélanger — mettre un guide de démarrage dans un commentaire de fonction, ou noyer une décision d'architecture dans le README — est une source de confusion. Quatre niveaux reviennent partout :

  • le README — pour démarrer : installer, lancer, contribuer. C'est la porte d'entrée du projet (on l'a vu au premier jour de Sam, leçon 3). Public : quelqu'un qui arrive.
  • la doc d'API / des interfaces — pour utiliser un module sans lire son code : que fait cette fonction, qu'attend-elle, que renvoie-t-elle, que se passe-t-il en cas d'erreur. Public : celui qui appelle ton code.
  • les ADR (architecture decision records) — pour comprendre pourquoi telle décision structurante a été prise. Public : celui qui, plus tard, se demande « pourquoi diable a-t-on fait ça ? ».
  • les runbooks — pour savoir quoi faire quand X casse en production : la marche à suivre, étape par étape, quand tel service tombe. Public : celui qui est de garde, souvent en pleine nuit (on y reviendra au module 4).

Écris pour le lecteur, pas pour toi

Le fil de tout le cours revient ici : chaque document vise un lecteur précis dans une situation précise. Le runbook s'adresse à quelqu'un de stressé, en pleine nuit : il doit être une suite d'actions, pas un essai. La doc d'API s'adresse à quelqu'un de pressé qui veut juste appeler la fonction : elle doit tenir en un coup d'œil. Écrire « de la doc » dans le vide ne mène à rien ; écrire pour telle personne qui cherche telle chose, oui.

Quoi NE PAS documenter

Le réflexe « plus de doc, c'est mieux » est un piège. Chaque phrase écrite est une phrase à maintenir : dès que le code change, toute doc qui décrivait ce code devient potentiellement fausse. Or personne ne relit systématiquement la doc quand il modifie une ligne. La doc redondante avec le code n'est donc pas neutre : elle est une dette qui se transforme en mensonge à la première évolution.

Trois choses qu'il vaut mieux ne pas documenter, ou documenter autrement :

  • Ce que le code dit déjà. Paraphraser une ligne (// boucle sur les tickets au-dessus d'un for qui boucle sur les tickets) n'ajoute rien et devra suivre chaque renommage. Préfère un bon nom : il ne se périme pas, car il est le code.
  • Les détails d'implémentation volatils. Documenter dans le README que « la fonction utilise une boucle imbriquée » fige un choix qui changera ; le lendemain d'un refactor, c'est faux. Documente le contrat (ce que ça garantit), pas la mécanique interne du jour.
  • L'évident et le trivial. Un getter qui renvoie un champ n'a pas besoin d'un paragraphe. Réserve les mots pour ce qui surprend : le cas limite, la contrainte externe, la décision contre-intuitive.

Piège fréquent

Confondre « beaucoup de doc » et « bien documenté ». Une documentation de trois cents pages que personne n'ouvre ne vaut rien de plus qu'une page blanche — en réalité, elle vaut moins, car elle donne l'illusion trompeuse que « c'est documenté ». Le but n'est pas de couvrir, c'est d'être utile et vrai. Une seule page à jour bat un manuel périmé.

La doc qui ment est pire que pas de doc

Voici le point le plus important de la leçon. Une absence de doc est un manque : on le sait, on va lire le code, on demande à un collègue. Une doc fausse, elle, est un piège : on lui fait confiance, on agit dessus, et on se trompe. Pire encore, elle contamine : dès qu'on découvre une ligne de doc périmée, on cesse de croire toute la doc. La confiance est binaire — une doc à qui on ne peut plus se fier ne sert plus à personne, même dans ses parties encore justes.

D'où vient une doc qui ment ? Presque toujours de la distance. Quand la doc vit loin du code — un wiki séparé, un document oublié, une page qu'on ne voit pas en modifiant le fichier —, elle n'évolue pas avec lui. Le code avance, la doc reste. Un an plus tard, ils décrivent deux réalités différentes, et c'est le lecteur qui paie la différence.

La parade tient en deux principes. D'abord, garder la doc le plus près possible du code qu'elle décrit : un commentaire dans le fichier, une doc d'API générée depuis le code, un README dans le dossier concerné — plutôt qu'un wiki lointain. Ensuite, la faire évoluer avec le code : modifier la doc dans la même modification que le code, et la relire en revue comme on relit le code (le module 2 t'a appris ce réflexe). Une PR qui change un comportement mais laisse la doc décrire l'ancien devrait être bloquée exactement comme un test cassé.

Note

« Près du code » ne veut pas dire « tout en commentaire ». Cela veut dire : au plus proche endroit où le lecteur concerné le trouvera, et où l'auteur pensera à le mettre à jour. Le contrat d'une fonction va dans sa doc d'API ; la raison d'un choix va en commentaire à côté ; une décision d'architecture va dans un ADR versionné avec le code, pas dans un wiki que plus personne n'ouvre. La bonne distance, c'est celle qui fait que la doc bouge quand le code bouge.

Les ADR : tracer une décision

Certaines décisions ne se voient pas dans le code : pourquoi telle base de données plutôt qu'une autre, pourquoi ce format d'échange, pourquoi avoir renoncé à telle bibliothèque. Le code montre le résultat du choix, jamais les options écartées ni la raison. Six mois plus tard, quelqu'un — souvent l'auteur lui-même — se demande « pourquoi diable a-t-on fait ça ? », est tenté de tout changer, et rejoue un débat déjà tranché faute d'en connaître les termes.

L'ADR (architecture decision record) répond exactement à ce besoin : un court document, un par décision structurante, écrit au moment du choix. On n'y revient pas pour rediscuter — on y revient pour comprendre. Il tient sur une page et suit toujours la même trame : le contexte, la décision, les conséquences.

Remarque la vertu de ce document : il rend le sleep(2) de Sam immédiatement compréhensible, il dit ce qu'on a écarté et pourquoi (donc évite de reproposer une file d'attente déjà jugée trop lourde), et il pose la condition qui justifierait d'y revenir. Un ADR n'est pas de la bureaucratie : c'est la mémoire des décisions d'une équipe, celle qui empêche de tourner en rond. Pour la forme même du document (Markdown, titres, listes), le cours Markdown donne tout ce qu'il faut ; pour le fond des décisions d'architecture, le cours Architecture creuse ce qui mérite un ADR.

Pour aller plus loin

Les ADR se rangent en général dans un dossier docs/adr/ du dépôt, numérotés (0001-…, 0002-…), versionnés avec le code — donc relus en revue et jamais perdus. Une décision peut être marquée « remplacée par l'ADR N » plutôt que supprimée : on garde la trace de l'évolution du raisonnement. Le format Markdown, léger et lisible en clair, en fait le support idéal ; voir le cours Markdown pour la syntaxe, et Architecture pour distinguer une vraie décision structurante d'un simple détail.

Pièges fréquents

Piège fréquent

Commenter le quoi au lieu du pourquoi. C'est le réflexe le plus courant : on annote une ligne en la paraphrasant (// on ouvre le fichier). Ce commentaire n'apprend rien, alourdit la lecture, et devra être maintenu pour rien. Si tu ne sais pas quoi mettre comme « pourquoi », c'est peut-être qu'il n'y a rien à dire : laisse le code parler seul.

  • Laisser mourir la doc loin du code — un wiki séparé qu'on ne rouvre jamais en modifiant le code se périme sans que personne s'en aperçoive, jusqu'à ce qu'il mente.
  • Tout documenter, et donc ne rien maintenir — plus la doc est volumineuse, moins elle est tenue à jour ; une doc massive se transforme vite en champ de mines de fausses informations.
  • Rédiger une documentation exhaustive que personne ne lit — couvrir chaque fonction en dix lignes rassure l'auteur mais noie l'essentiel ; le lecteur pressé ne trouve plus le seul paragraphe qui comptait.

Cas réel

Cas réel

Théo doit intervenir sur Repère un soir : un flux d'export semble bloqué. Il ouvre le wiki interne, trouve une page « Procédure d'export » détaillée, la suit à la lettre — et relance un service qui, depuis un refactor de six mois plus tôt, n'existe plus sous ce nom. La page décrivait l'ancienne architecture ; personne ne l'avait touchée depuis. Théo perd quarante minutes à cause d'une doc qui ment, là où une absence de doc l'aurait envoyé lire le code tout de suite. Le lendemain, l'équipe tire deux leçons : la procédure part du wiki vers un runbook versionné dans le dépôt, à côté du code d'export ; et toute PR qui touche ce flux doit mettre à jour le runbook, relu en revue. Depuis, il suit le code — parce qu'il vit avec lui.

Antisèche

Glossaire

Documentation
Tout écrit qui accompagne le code pour aider un lecteur — commentaire, README, doc d'API, ADR, runbook. Sa valeur tient à ce qu'elle capture ce que le code ne dit pas de lui-même.
Commentaire du « pourquoi »
Commentaire qui explique l'intention, la contrainte ou le piège derrière une ligne, plutôt que de répéter ce qu'elle fait déjà ; le seul type de commentaire qui mérite sa place.
README
Document d'entrée d'un projet : comment l'installer, le lancer, y contribuer. Il s'adresse à quelqu'un qui découvre le projet et veut démarrer vite.
ADR (architecture decision record)
Court document, un par décision structurante, qui trace le contexte, le choix retenu et ses conséquences ; on le consulte pour comprendre une décision passée, pas pour la rediscuter.
Runbook
Marche à suivre opérationnelle décrivant, étape par étape, quoi faire quand un incident précis survient en production ; destinée à la personne de garde, souvent sous pression.
Doc d'API
Description du contrat d'un module ou d'une fonction — ce qu'il attend, renvoie, garantit — permettant de l'utiliser sans lire son implémentation.
Doc périmée
Documentation devenue fausse parce que le code a changé sans elle ; plus dangereuse qu'une absence de doc, car on lui fait confiance et elle ruine la confiance dans le reste.
Source de vérité
L'endroit unique qui fait autorité sur une information ; pour le comportement d'un programme, c'est le code : toute doc qui le contredit a tort par définition.

Récap et vérification

  • Documenter, c'est écrire le pourquoi (intention, contrainte, piège évité), pas le quoi que le code dit déjà. Un commentaire qui paraphrase le code est du bruit à maintenir.
  • La doc s'étage par besoin et par public : README (démarrer), doc d'API (utiliser), ADR (comprendre une décision), runbook (agir en incident). Le code bien nommé en est le socle.
  • Il ne faut pas tout documenter : la doc redondante avec le code se périme et ment ; mieux vaut peu de doc, ciblée et vraie, qu'un manuel exhaustif ignoré.
  • Une doc qui ment est pire que pas de doc ; on la garde près du code, on la fait évoluer avec lui et on la relit en revue. L'ADR trace les décisions structurantes qu'on nous redemandera.

Vérifie ta compréhension

  1. Sam trouve sleep(2) sans explication. Quel commentaire serait utile, et pourquoi ? Qu'est-ce qui distingue le « pourquoi » du « quoi » ?
  2. On veut expliquer pourquoi l'équipe a choisi une base plutôt qu'une autre. Quel niveau de documentation est fait pour ça, et quelles rubriques contient-il ?
  3. Pourquoi dit-on qu'une doc périmée est pire que pas de doc du tout ? Donne un moyen concret d'éviter qu'elle se périme.
