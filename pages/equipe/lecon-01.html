Module 1 · Entrer dans le code des autres — Leçon 01

Coder à plusieurs change tout

~28 min Débutant Prérequis : savoir coder seul un petit programme et avoir déjà utilisé Git (commit, branche)

À la fin de cette leçon, tu sauras

  • expliquer pourquoi le code est lu bien plus souvent qu'il n'est écrit, et ce que ça change à ta façon d'écrire ;
  • reconnaître que le vrai coût d'une équipe n'est pas technique mais tient à la coordination entre les personnes ;
  • situer les trois dimensions du travail collectif — le code, le processus, les gens — que ce cours va parcourir ;
  • te repérer dans le fil rouge du cours : Repère et l'équipe qui le développe, que l'on suivra jusqu'au bout.
Sommaire de la leçon

C'est le premier jour de Sam dans l'équipe. Sam sait coder : des projets personnels solides, de bons réflexes, un langage bien en main. Pourtant, en clonant le dépôt de Repère — l'application que l'équipe développe — une sensation étrange s'installe. Le code marche, mais il a été écrit par d'autres ; il y a des conventions non dites, un historique, des choix dont personne n'explique la raison sur le moment. Coder n'est soudain plus un dialogue entre soi et la machine. C'est devenu une activité entre humains.

C'est le sujet de tout ce cours. Tu sais déjà écrire du code ; tu vas apprendre à le faire avec d'autres — lire le leur, faire relire le tien, communiquer autour, tenir un projet dans la durée. Aucune de ces compétences n'est enseignée quand on apprend un langage, et pourtant ce sont elles qui décident du sort d'un projet réel. Commençons par le renversement qui change tout le reste.

Le code est lu bien plus qu'il n'est écrit

Quand tu programmes seul, tu écris du code puis tu passes à autre chose. En équipe, ce même code va être lu des dizaines de fois : par la personne qui le relit avant de le fusionner, par celle qui corrigera un bug dedans six mois plus tard, par le nouveau venu qui essaie de comprendre le projet — et par toi-même, qui ne te souviendras plus de rien. On estime couramment qu'une ligne de code est lue dix fois pour une fois qu'elle est écrite. Ce rapport a une conséquence directe : le lecteur, pas l'auteur, est le vrai destinataire du code.

Concrètement, cela déplace le curseur de ce qu'est du « bon » code. Le trait d'esprit compact qui t'a fait gagner deux minutes en l'écrivant en fera perdre dix à chacun de ses lecteurs. À l'inverse, un nom de variable explicite, une fonction découpée, un commentaire qui explique pourquoi ce choix bizarre était nécessaire : voilà des cadeaux au futur. Écrire pour le lecteur n'est pas de la politesse, c'est de l'efficacité collective.

Le prochain lecteur, c'est souvent toi

On imagine le lecteur comme un collègue abstrait. En réalité, la personne qui rouvrira ce fichier dans six mois, sans plus aucun souvenir du contexte, ce sera très probablement toi. Écrire pour « les autres », c'est aussi écrire pour ton toi futur — celui qui te remerciera, ou te maudira.

Le vrai coût, c'est la coordination

On croit souvent qu'ajouter une personne à un projet le fait avancer plus vite, mécaniquement. Mais deux développeurs ne travaillent pas deux fois plus vite qu'un seul : ils doivent se mettre d'accord. Qui fait quoi ? Où passe la frontière entre nos deux bouts de code ? Est-ce que ta modification casse la mienne ? Ce temps de coordination est invisible sur un planning, mais c'est lui qui coûte le plus cher — et il croît étonnamment vite avec la taille de l'équipe.

Ce constat porte un nom célèbre : la loi de Brooks, « ajouter des gens à un projet en retard le retarde davantage ». Non parce que les nouveaux venus sont mauvais, mais parce qu'il faut les intégrer, leur expliquer, se synchroniser — pendant que le reste continue. La bonne nouvelle : la coordination n'est pas une fatalité. Tout ce cours consiste à la rendre moins chère, par des pratiques simples — une revue claire, un bon message de commit, une convention automatisée — qui remplacent d'interminables allers-retours par des habitudes partagées.

Piège fréquent

Croire que « plus de bras = plus vite ». Sur une tâche déjà bien lancée, un renfort mal intégré ralentit tout le monde le temps de sa mise au courant. La vitesse d'une équipe ne se mesure pas au nombre de personnes, mais à la fluidité avec laquelle elles se coordonnent. C'est cette fluidité que les bonnes pratiques achètent.

Programmer devient une activité sociale

Passer en équipe ne rajoute pas seulement des réunions : cela transforme la nature du métier. À côté du code (ce qu'on écrit), apparaissent le processus (comment on travaille ensemble : branches, revues, livraisons) et les gens (comment on se parle, se relit, se fait confiance). Un projet peut mourir alors que le code est excellent, simplement parce que le processus grince ou que les gens ne se parlent plus. Ces trois dimensions se tiennent.

C'est aussi ce qui rend ces compétences difficiles à apprendre seul : on ne peut pas « s'entraîner à la revue de code » dans son coin. Mais on peut comprendre ce qui marche et pourquoi, reconnaître les situations quand elles arrivent, et éviter les erreurs classiques. C'est exactement ce que les leçons suivantes vont faire, situation par situation : lire le code d'autrui, faire et recevoir une revue, écrire un commit et une demande de fusion, estimer, nommer la dette, gérer un incident.

Astuce

Chaque fois qu'une décision technique te paraît « évidente », demande-toi : évidente pour qui ? Ce qui va de soi pour l'auteur ne l'est presque jamais pour le lecteur qui découvre. Rendre l'implicite explicite — dans le code, le commit, la doc — est le geste de base du travail en équipe.

Ce qui change, concrètement

Voici le renversement, poste par poste. Rien de tout cela n'est difficile ; c'est simplement différent, et rester en mode « solo » dans une équipe est la source la plus fréquente de friction.

  • Le nom des choses — seul, tmp2 suffit ; en équipe, un nom doit se comprendre sans toi à côté pour l'expliquer.
  • Les décisions — seul, tu tranches et tu oublies ; en équipe, tu traces le pourquoi (commit, doc) parce qu'on te le redemandera.
  • Le rythme — seul, tu fusionnes quand tu veux ; en équipe, ton travail passe par une revue et s'insère dans celui des autres.
  • Les erreurs — seul, un bug te concerne ; en équipe, une panne concerne tout le monde, et se gère ensemble, sans chercher de coupable.

Repère, notre fil rouge

Pour rester concret, on suivra tout le cours la même petite équipe, autour du même produit : Repère, une application web qui aide des associations à suivre leurs demandes (adhésions, dons, bénévolat) sous forme de tickets. Rien de spectaculaire : quelques milliers d'utilisateurs, un back-end, un front, une base de données. Juste assez réel pour tomber en panne un vendredi soir, accumuler de la dette, et exiger mille petits choix quotidiens.

Fais connaissance avec l'équipe — tu la recroiseras à chaque leçon :

  • Inès — la responsable technique. Elle arbitre, porte la vision, protège le temps de l'équipe.
  • Léa — développeuse expérimentée, gardienne de la lisibilité ; c'est souvent elle qui relit.
  • Karim — au back-end, pragmatique et souvent pressé ; il livre vite, parfois au prix d'un raccourci.
  • Sam — la nouvelle recrue, dont tu partages le regard neuf tout au long du cours.
  • Théo — celui qui met en production et se retrouve en première ligne les soirs d'incident.

Note

Personne dans cette équipe n'est un héros ni un cancre. Karim n'est pas « le mauvais » parce qu'il prend des raccourcis, Léa n'est pas « la donneuse de leçons » parce qu'elle relit. Ce sont des gens normaux qui essaient de bien faire, avec des contraintes réelles. Le travail en équipe, c'est composer avec ça — pas rêver de collègues parfaits.

La carte du cours

Ce cours suit un arc simple, celui que Sam va vivre : entrer dans le code des autres, apprendre à relire et se faire relire, communiquer autour du code, puis tenir le projet dans la durée, jusqu'à l'incident et son lendemain. Quatre modules, une progression.

Pour aller plus loin

Ce cours parle de la pratique collective ; il suppose que tu maîtrises déjà les outils qu'elle mobilise. Trois cours en sont les compagnons naturels : Git pour les branches et l'historique, les tests pour la confiance dans le code relu, et l'architecture pour les décisions qu'on documente et la dette qu'on gère. On y renverra sans les réexpliquer.

Pièges fréquents

Piège fréquent

Rester en « mode solo » dans une équipe. Coder dans son coin, fusionner sans prévenir, ne pas expliquer ses choix, prendre une revue comme une agression : ce sont des réflexes de travail solitaire qui, transposés en équipe, créent des frictions permanentes. Le premier pas n'est pas technique, c'est de réaliser que les règles ont changé.

  • Écrire pour épater plutôt que pour être compris — le code le plus malin est rarement le plus utile en équipe ; le plus clair, presque toujours.
  • Confondre activité et avancement — beaucoup de commits ou de messages ne veut pas dire qu'on progresse ; ce qui compte, c'est ce qui est relu, fusionné, compris.
  • Attendre l'équipe parfaite — elle n'existe pas ; la compétence, c'est de bien travailler avec des collègues réels, pressés et faillibles, toi compris.

Cas réel

Cas réel

Un développeur brillant rejoint une petite équipe et livre, seul, une fonctionnalité entière en une nuit : du code dense, astucieux, qui marche. Trois mois plus tard, il part. Personne d'autre n'ose toucher à son module : illisible, non documenté, sans test, chaque modification y déclenche des bugs. L'équipe finit par le réécrire entièrement — plus lentement, mais compréhensible par tous. La leçon n'est pas que ce développeur était mauvais : c'est qu'un code que personne d'autre ne peut reprendre est, pour une équipe, un passif, quelle que soit son élégance. La valeur d'un code se mesure aussi à la facilité avec laquelle les autres peuvent le faire vivre.

Antisèche

Glossaire

Ratio lecture/écriture
Constat qu'une ligne de code est lue bien plus souvent (environ dix fois) qu'elle n'est écrite ; il justifie d'optimiser le code pour le lecteur.
Écrire pour le lecteur
Principe consistant à privilégier la clarté (noms, structure, « pourquoi ») pour celui qui lira, plutôt que la commodité de celui qui écrit.
Coût de coordination
Temps et effort dépensés à se synchroniser dans une équipe (qui fait quoi, éviter les conflits) ; souvent le coût dominant d'un projet collectif.
Canaux de communication
Les liens deux à deux entre membres d'une équipe ; leur nombre croît en n(n−1)/2, bien plus vite que la taille de l'équipe.
Loi de Brooks
Observation selon laquelle ajouter des personnes à un projet logiciel en retard tend, à court terme, à le retarder encore, à cause du temps d'intégration.
Processus
La manière dont une équipe organise son travail : branches, revues, intégration, livraison — l'une des trois dimensions du travail collectif.
Fil rouge
Cas concret suivi tout au long d'un cours ; ici, l'équipe et l'application Repère, qui servent d'exemple récurrent.
Passif (code)
Code qui, malgré sa qualité apparente, coûte plus qu'il ne rapporte à l'équipe parce que personne d'autre ne peut le comprendre ni le faire évoluer.
Rendre explicite
Formuler ouvertement ce qui était implicite (une intention, une contrainte, une décision) pour que le lecteur n'ait pas à le deviner.

Récap et vérification

  • Le code est lu bien plus qu'écrit : en équipe, on écrit d'abord pour le lecteur — clarté, noms, « pourquoi » — pas pour la commodité de l'auteur.
  • Le vrai coût d'une équipe est la coordination ; les canaux de communication explosent avec la taille, d'où la loi de Brooks. Les bonnes pratiques la rendent moins chère.
  • Programmer devient social : le code, le processus et les gens sont inséparables ; un projet peut mourir par n'importe laquelle des trois dimensions.
  • Le fil rouge Repère et son équipe (Inès, Léa, Karim, Sam, Théo) servent de terrain jusqu'au projet final, qui traverse les quatre modules.

Vérifie ta compréhension

  1. Pourquoi dit-on que « le lecteur est le vrai destinataire du code » ? Donne une conséquence concrète sur ta façon d'écrire.
  2. Une équipe passe de 3 à 6 personnes. Le travail avance-t-il forcément deux fois plus vite ? Explique avec l'idée de coût de coordination.
  3. Cite les trois dimensions du travail en équipe et un exemple de projet qui échoue par l'une d'elles alors que le code est bon.

Exercices

Exercice 1Échauffement

On te donne cette fonction, écrite « pour soi » : def f(l): return [x for x in l if x[1] > 0]. Sans changer ce qu'elle fait, propose deux améliorations qui la rendent lisible pour l'équipe, et explique en une phrase pourquoi chacune aide le lecteur.

Exercice 2Application

L'équipe de Repère (5 personnes) et une équipe concurrente (10 personnes) démarrent la même fonctionnalité. Calcule le nombre de canaux de communication de chacune (formule : n(n−1)/2), puis explique pourquoi la plus grande équipe n'ira pas forcément deux fois plus vite.

Voir une solution
Exercice 3Défi

Un collègue affirme : « Le seul truc qui compte, c'est que le code marche. Le reste — revues, doc, messages de commit — c'est de la bureaucratie. » Rédige une réponse courte (trois arguments) qui montre pourquoi, en équipe, « ça marche » ne suffit pas, sans tomber dans le sermon.
