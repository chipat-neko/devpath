Module 3 · Communiquer autour du code — Leçon 07

Écrire un bon message de commit

~32 min Intermédiaire Prérequis : le module 2 (la revue de code)

À la fin de cette leçon, tu sauras

  • expliquer pourquoi un message de commit doit dire le pourquoi et le contexte, quand le diff montre déjà le quoi ;
  • rédiger un message bien formé : une ligne de sujet courte à l'impératif, une ligne vide, un corps qui explique ;
  • découper ton travail en commits atomiques — un commit = un changement cohérent — pour un historique qui se relit ;
  • voir l'historique comme une documentation qui fait vivre git log, git blame et git bisect, et adopter une convention partagée.
Sommaire de la leçon

Il est tard, Karim finit de corriger un bug agaçant dans Repère : un formulaire d'adhésion qui plantait quand le nom du bénévole contenait une apostrophe. Trois lignes changées, le test repasse au vert. Reste à valider. Karim tape git commit -m "fix", pousse sa branche, referme son ordinateur. Le bug est corrigé, tout le monde est content. Six mois plus tard, en cherchant l'origine d'une régression, Léa remonte l'historique et tombe sur ce commit : « fix ». Fix quoi ? Elle ouvre le diff, voit trois lignes obscures sur l'échappement d'une chaîne, et n'a aucune idée de ce que ce commit corrigeait, ni pourquoi c'était fait ainsi. Le savoir était dans la tête de Karim ce soir-là ; il n'en reste rien.

C'est le sujet de cette leçon. Un message de commit n'est pas une formalité administrative pour « valider » : c'est un message que tu écris à la personne qui, plus tard, tentera de comprendre ce que tu as fait et pourquoi — un collègue, ou toi-même. Comme pour le code (voir la leçon 1), le lecteur est le vrai destinataire. On ne réexplique pas Git ici — pour les branches et l'historique, va voir le cours Git — on parle de ce qu'on écrit dedans.

Le pourquoi, pas le quoi

Commence par un constat qui change tout : le diff d'un commit dit déjà, exactement et sans ambiguïté, ce qui a changé. Chaque ligne ajoutée, chaque ligne retirée y figure. Répéter ce quoi dans le message (« modifie la fonction X, ajoute une ligne Y ») est un doublon inutile : le lecteur n'a qu'à regarder le code. Ce que le diff ne dira jamais, en revanche, c'est pourquoi tu as fait ce changement. Quel problème résolvais-tu ? Dans quelle situation se manifestait-il ? Pourquoi cette solution-là et pas une autre ? Ce contexte n'existe nulle part dans le code — s'il n'est pas dans le message, il est perdu.

La bonne formule tient en une phrase : un message utile dit « corrige X qui plantait quand Y, parce que Z ». Reprends le commit de Karim. « fix » ne dit rien. « Corrige le plantage du formulaire d'adhésion quand le nom contient une apostrophe » dit le quoi utilement (le symptôme, pas les lignes) et commence à dire le pourquoi. En ajoutant un corps — « l'apostrophe cassait la requête d'insertion ; on échappe désormais la chaîne côté serveur plutôt que de filtrer le caractère, pour ne pas mutiler les vrais noms » — on lègue à Léa tout ce qui lui manquait. Le savoir de ce soir-là est sauvé.

Le « quoi » vit dans le code, le « pourquoi » nulle part

C'est la règle qui décide de tout le reste. On peut toujours reconstituer ce qui a changé en lisant le diff ; on ne peut jamais reconstituer pourquoi à partir du code seul. Le message de commit est le seul endroit où ce « pourquoi » est enregistré au moment précis où tu le connais encore. Écris ce que le lecteur ne pourra pas deviner.

L'anatomie d'un bon message

Un message de commit a une forme, aussi standard qu'une lettre. Elle n'a rien d'arbitraire : chaque partie sert un outil ou un lecteur précis. Trois éléments : une ligne de sujet, une ligne vide, puis un corps facultatif.

  • La ligne de sujet est courte — vise ≈ 50 caractères, ne dépasse pas 72. C'est le titre du commit : ce qu'affichent git log --oneline, l'interface de revue, la liste des commits. Rédige-la à l'impératif présent (« Corrige », « Ajoute », « Supprime »), sans point final. L'impératif décrit ce que le commit fait au code quand on l'applique — c'est aussi la forme qu'emploie Git lui-même (« Merge », « Revert »).
  • La ligne vide qui suit n'est pas décorative : c'est elle qui permet à Git de distinguer le sujet du corps. Sans elle, tout est aplati en une seule masse et --oneline te renvoie un pavé.
  • Le corps explique le pourquoi et le contexte, en phrases, sur plusieurs lignes si besoin. Il est facultatif : un changement trivial (corriger une faute dans un libellé) s'en passe. Un choix non évident, lui, le mérite toujours.

Voici le contraste, côte à côte. Le même changement, mais deux legs très différents pour l'équipe.

Le test de l'impératif

Pour savoir si ta ligne de sujet est à la bonne forme, glisse-la après « Ce commit va… » : « Ce commit va… corriger le plantage » se dit bien ; « Ce commit va… corrigé le plantage » non. C'est un petit réflexe qui aligne tout l'historique sur la même forme, agréable à lire en liste.

Des commits atomiques

Un bon message ne sauve pas un mauvais découpage. Si un seul commit mélange trois choses sans rapport — une correction de bug, une nouvelle fonctionnalité et un grand renommage de variables — aucun message ne pourra le résumer honnêtement ; au mieux, une liste à puces qui trahit le problème. La qualité du message commence donc avant de l'écrire, au moment de décider ce que le commit contient. Un commit devrait être atomique : un seul changement cohérent, qui a un sens à lui tout seul.

Les bénéfices sont très concrets. Un commit atomique se relit plus vite en revue (voir le module 2) : le relecteur juge un seul sujet à la fois. Il se révoque proprement : si l'export CSV pose problème, on annule ce seul commit sans emporter la correction du bug. Il rend l'historique fouillable : quand on cherchera plus tard « quand l'export CSV est-il arrivé ? », il y a un commit, un seul, qui répond. Le fourre-tout, lui, noie tout : on ne sait plus quelle ligne appartient à quelle intention.

Atomique, pas minuscule

« Atomique » ne veut pas dire « le plus petit possible » : un commit d'une seule ligne par ci, un autre par là, hache l'histoire aussi mal qu'un fourre-tout. La bonne unité est le changement cohérent : tout ce qui va ensemble pour accomplir une intention (le correctif et son test, par exemple), et rien qui relève d'une autre. Un commit = une idée qu'on peut nommer en une ligne.

L'historique comme documentation

Mis bout à bout, des commits bien écrits forment quelque chose de précieux : une documentation vivante du projet, gratuite, toujours à jour, qui raconte pourquoi le code est devenu ce qu'il est. Un git log --oneline sur une belle branche se lit comme un sommaire : on suit l'histoire d'une fonctionnalité, décision après décision. Un git log rempli de « fix », « wip », « encore », « ça marche » ne raconte rien : l'information est là (dans les diff) mais illisible.

Deux outils de Git s'appuient directement sur la qualité de tes commits, et deviennent presque inutiles sans elle. git blame répond à « qui a écrit cette ligne, et dans quel commit ? » — mais retrouver le commit ne sert qu'à lire son message ; si ce message est « fix », blame t'a mené à une impasse. git bisect, lui, cherche par dichotomie le commit qui a introduit un bug : il te dépose sur un commit précis. Si ce commit est atomique et bien décrit, tu comprends immédiatement ce qu'il faisait ; s'il est un fourre-tout de 600 lignes intitulé « wip », tu as trouvé le coupable sans savoir de quoi il est coupable.

Piège fréquent

Croire que l'historique est jetable. « De toute façon, personne ne relit les vieux commits. » Faux : personne ne les relit pour le plaisir, mais dès qu'un bug apparaît ou qu'une décision est remise en cause, on plonge dans blame et bisect — et c'est précisément ce jour-là que la qualité des messages compte le plus. On écrit l'historique pour le mauvais jour, pas pour le bon.

Une convention partagée

Jusqu'ici, on a parlé de messages individuels. En équipe, un cran de plus aide énormément : se mettre d'accord sur un format commun. Le plus répandu préfixe le sujet par un type : type: sujet. Les types usuels sont peu nombreux et parlants : feat (nouvelle fonctionnalité), fix (correction de bug), docs (documentation), refactor (réorganisation sans changement de comportement), test (ajout ou correction de tests), chore (tâches d'outillage, dépendances). Ce petit préfixe, lu en tête de chaque ligne, dit d'un coup d'œil la nature du changement.

Cette convention porte un nom : les Conventional Commits. Elle ajoute deux raffinements utiles : une portée entre parenthèses pour situer le changement (feat(adhesion):), et un moyen de signaler un changement cassant — un ! avant le deux-points, ou un paragraphe BREAKING CHANGE: dans le corps. Au-delà du confort de lecture, un format régulier se traite par machine : on peut générer un changelog automatiquement (regrouper les feat et les fix de la version), et la CI peut refuser un message hors format ou en déduire le prochain numéro de version. La convention transforme un texte libre en donnée exploitable.

Pour aller plus loin

Une convention ne vaut que si elle est partagée et légère. Inès l'a écrite en cinq lignes dans le CONTRIBUTING.md de Repère, et l'équipe a branché une petite vérification automatique côté CI : le format n'est plus un débat, c'est un acquis — exactement l'esprit de la leçon 6 sur le style. Le but n'est pas la pureté formelle, c'est de ne plus discuter de la forme pour se concentrer sur le fond : le pourquoi.

Pièges fréquents

Piège fréquent

Le message « fix » (ou « wip », « update », « . »). C'est le réflexe du soir, quand « valider » ressemble à une corvée. Le problème n'apparaît pas ce jour-là — il apparaît six mois plus tard, chez quelqu'un d'autre, qui paie ton économie de trente secondes par une demi-heure d'enquête. Un sujet vide n'est pas plus rapide : il déplace simplement le coût, plus loin, sur un autre.

  • Décrire le quoi au lieu du pourquoi — « change la ligne 42 » est un doublon du diff ; ce que le lecteur veut, c'est la raison.
  • Le sujet fleuve — une ligne de sujet de 150 caractères est tronquée partout (--oneline, interfaces de revue) et illisible. Ce qui déborde va dans le corps.
  • Coller la ligne vide au corps, ou l'oublier — sans la ligne vide après le sujet, Git ne sait plus où finit le titre ; tout l'outillage s'en trouve perturbé.
  • Le commit fourre-tout — mélanger correctif, fonctionnalité et refactorisation rend le message malhonnête et la revue pénible. Découpe d'abord, décris ensuite.

Cas réel

Cas réel

Une équipe traque une régression : depuis une semaine, certains paiements sont enregistrés au double du montant. Personne ne sait quel changement l'a introduite. Théo lance git bisect ; en quelques essais, Git désigne un commit précis. Son message ? « maj ». Le diff ? 480 lignes, mêlant un vrai correctif, un renommage massif et un changement d'unité (des euros passés en centimes). Impossible de savoir laquelle de ces trois choses a cassé les paiements sans tout relire, ligne à ligne, pendant deux heures. Le coupable était trouvé ; comprendre son crime a coûté une après-midi. Si ce travail avait été trois commits atomiques — « fix: … », « refactor: renomme … », « refactor: passe les montants en centimes » — bisect aurait pointé directement le changement d'unité, message à l'appui. Le découpage et le message n'étaient pas de la coquetterie : ils valaient une après-midi d'équipe.

Antisèche

Glossaire

Message de commit
Texte attaché à un commit qui explique le changement ; son rôle premier est de dire le pourquoi et le contexte, que le diff ne montre pas.
Ligne de sujet
Première ligne du message, courte (≈ 50, max 72 caractères) et à l'impératif ; sert de titre au commit dans git log --oneline et les interfaces de revue.
Corps du message
Partie facultative, après une ligne vide, qui développe en phrases le pourquoi, le contexte et les solutions écartées ; requise pour un choix non trivial.
Commit atomique
Commit qui contient un seul changement cohérent, ayant un sens à lui seul ; il se relit, se révoque et se retrouve indépendamment des autres.
Historique (log)
Suite ordonnée des commits d'un projet ; consulté avec git log, il fait office de documentation vivante quand les messages sont soignés.
git blame
Commande qui, ligne par ligne, indique le dernier commit (donc l'auteur et le message) l'ayant modifiée ; utile surtout si ce message explique le pourquoi.
git bisect
Commande qui trouve par dichotomie le commit ayant introduit un bug ; son résultat n'est exploitable que si le commit désigné est atomique et bien décrit.
Conventional Commits
Convention de format des messages sous la forme type(portée): sujet (feat, fix, docs…), avec signalement des changements cassants ; permet changelog et vérifications automatiques.

Récap et vérification

  • Le message dit le pourquoi, pas le quoi : le diff montre déjà ce qui a changé ; le contexte et la raison n'existent que si tu les écris. La bonne forme : « corrige X qui plantait quand Y, parce que Z ».
  • Un message bien formé a une ligne de sujet courte à l'impératif (≈ 50, max 72), une ligne vide, puis un corps qui explique — ce dernier facultatif mais précieux dès qu'un choix n'est pas évident.
  • Un commit doit être atomique : un seul changement cohérent. On ne mélange pas correctif, fonctionnalité et refactorisation, sinon aucun message honnête n'est possible et la revue devient pénible.
  • L'historique est une documentation : git log raconte le projet, git blame et git bisect ne valent que par de bons commits. Une convention partagée (type: sujet, Conventional Commits) facilite la lecture, le changelog et la CI.

Vérifie ta compréhension

  1. Pourquoi dit-on qu'un message de commit doit expliquer le pourquoi plutôt que le quoi ? Où le quoi se trouve-t-il déjà ?
  2. Cite les trois parties d'un message bien formé et donne, pour la ligne de sujet, sa longueur visée et sa forme grammaticale.
  3. En quoi un commit fourre-tout gêne-t-il git bisect ? Qu'apporte un découpage atomique dans ce cas ?
