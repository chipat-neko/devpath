Travailler à plusieurs sur du code

Tu sais coder. Mais coder avec d'autres ne s'apprend pas en apprenant un langage : le code se lit bien plus qu'il ne s'écrit, le vrai coût devient la coordination, et mille petits gestes décident du sort d'un projet — lire le code des autres, faire et recevoir une revue, écrire un message de commit et une demande de fusion, documenter ce qui compte, estimer sans se mentir, nommer la dette technique, gérer un incident et en faire l'après sans chercher de coupable. Ce cours enseigne cette face humaine du métier, sur un fil rouge concret : Repère et la petite équipe qui le développe.

Bien s'équiper

Les extensions VS Code pour travailler en équipe

Ce cours parle de pratiques, pas d'un langage : aucun outil payant n'est requis. Mais quelques extensions de VS Code (Ctrl+Shift+X) rendent le travail collectif nettement plus fluide :

À installer pour collaborer sereinement

  • GitLens — voir qui a écrit chaque ligne et pourquoi (blame en ligne, historique, comparaison) : l'outil clé pour lire le code des autres.
  • EditorConfig for VS Code — appliquer automatiquement le style partagé du dépôt, quel que soit l'éditeur de chacun.
  • Prettier et ESLint (ou l'équivalent de ton langage) — formateur et linter : retirer le style du débat.
  • GitHub Pull Requests and Issues — ouvrir, relire et commenter des demandes de fusion sans quitter l'éditeur.
  • Code Spell Checker — éviter les fautes dans le code, les commits et la doc que toute l'équipe va lire.

Pour qui ?

Ce cours vise les développeurs qui savent déjà coder seuls et rejoignent — ou animent — une équipe : stage, premier poste, projet open-source, collectif. Il suppose des bases de Git (commits, branches) et des tests, sans les réexpliquer : il porte sur la pratique collective autour du code, pas sur un langage. Rien à installer d'obligatoire ; tout est illustré par des situations réelles.

Ce que tu vas apprendre

Coder avec d'autres, pas seulement à côté d'eux

À la fin du cours, tu sauras

  • entrer dans un code inconnu : lire celui des autres, suivre une donnée, interroger l'historique, et être intégré (ou intégrer) sans douleur ;
  • faire une revue utile et en recevoir une sans la prendre mal, puis automatiser le style pour ne plus jamais en débattre ;
  • communiquer autour du code : un message de commit qui raconte, une demande de fusion qu'on a envie de relire, une doc juste, une estimation honnête ;
  • tenir le projet dans la durée : nommer et traiter la dette technique, gérer un incident et en faire l'après sans chercher de coupable.

Pour qui, et pourquoi

On apprend à coder seul ; on travaille presque toujours à plusieurs. Or les compétences qui décident du sort d'un projet réel — lire le code des collègues, se relire les uns les autres, communiquer clairement, tenir la distance — ne sont enseignées nulle part quand on découvre un langage. Ce cours comble ce trou, sans moralisme : il montre ce qui marche et pourquoi, à partir de situations que tu croiseras vraiment. On y suppose que tu sais déjà écrire du code et te servir de Git ; on t'apprend à en faire une activité collective.

Chaque leçon est autonome, illustrée par des schémas dessinés et des exemples concrets. Le fil rouge : Repère, une petite application web qui aide des associations à suivre leurs demandes, et l'équipe qui la développe — Inès (responsable technique), Léa (revue et lisibilité), Karim (back-end, pragmatique), Sam (la nouvelle recrue, dont tu partages le regard neuf) et Théo (mises en production et incidents). Des gens normaux qui essaient de bien faire : exactement ceux avec qui tu travailleras.

Récapitulatif

À retenir & glossaire

Les points clés du cours, puis les termes essentiels à connaître.

À retenir

  • Le code est lu bien plus qu'écrit : en équipe, on écrit d'abord pour le lecteur, et le vrai coût est la coordination.
  • Lire le code des autres est une compétence : point d'entrée, suivi d'une donnée, tests, git blame — sans chercher à tout comprendre.
  • Une revue utile regarde la correction et la conception, pas le style ; on la reçoit en dissociant soi de son code.
  • Le style s'automatise (linter, formateur, CI) : on cesse d'en débattre pour ne discuter que du fond.
  • Un message de commit dit le pourquoi ; une demande de fusion petite et décrite se relit vite.
  • On documente ce qui compte (le pourquoi, les décisions, les runbooks) et on estime en assumant l'incertitude.
  • La dette technique se nomme, se rend visible et se budgète ; on choisit quand rembourser et quand vivre avec.
  • Un incident se gère à froid (endiguer d'abord) ; l'après sans coupable blâme le système, pas la personne.
Revue de code
Relecture du code d'un collègue avant de le fusionner : on y cherche les bugs et les problèmes de conception, on y explique le pourquoi, on commente le code et non la personne.
Demande de fusion
Proposition d'intégrer une branche dans le code commun (aussi pull request ou merge request) ; petite, titrée et décrite, elle se relit vite.
Message de commit
Texte qui accompagne un enregistrement Git : un sujet court et un corps qui explique le pourquoi ; ensemble, ils font de l'historique une documentation.
Linter / formateur
Outils qui vérifient (linter) et imposent (formateur) automatiquement le style et certaines règles : ils retirent la mise en forme du débat humain.
Intégration (onboarding)
Ensemble de ce qui permet à un nouveau venu de devenir productif vite : README qui marche, binôme, premier ticket cadré, doc d'accueil.
Dette technique
Coût futur des raccourcis pris aujourd'hui ; comme une dette financière, elle a un principal et des intérêts qu'on paie tant qu'on ne la rembourse pas.
ADR (décision d'architecture)
Court document qui trace une décision structurante : contexte, options, choix retenu, conséquences ; il répond plus tard au « pourquoi avoir fait ça ? ».
Runbook
Marche à suivre documentée pour réagir à une situation connue (une panne, une opération sensible) : quoi vérifier, quoi faire, dans quel ordre.
Incident
Événement qui dégrade le service en production ; on le gère par étapes (endiguer, comprendre, réparer) et à plusieurs, pas seul.
Post-mortem sans coupable
Analyse d'un incident (blameless) qui cherche les causes dans le système plutôt qu'une personne à blâmer, et débouche sur des actions concrètes.
Coût de coordination
Temps passé à se synchroniser dans une équipe ; souvent le coût dominant, il croît plus vite que le nombre de personnes.
