Module 14 · CSS, encore plus loin — Leçon 42

Le CSS à l'échelle et l'avenir

~30 min Avancé Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • savoir remplacer un préprocesseur par les variables natives, calc(), color-mix() et le nesting ;
  • savoir construire une architecture de design tokens hiérarchisée (primitives, sémantiques, composant) et la thématiser ;
  • savoir exposer une API de composant via des custom properties surchargeables et typées avec @property ;
  • savoir faire de la veille (Baseline, fonctionnalités à venir) et adopter une feature avec un repli sûr.
Sommaire de la leçon

Tu as parcouru les frontières du CSS moderne : cascade en couches, sélecteurs relationnels, espaces colorimétriques perceptuels, requêtes de conteneur, animations pilotées par le défilement. Reste une question d'ingénieur : comment fait-on tenir tout ça dans un projet de plusieurs dizaines de milliers de lignes, à plusieurs mains, sans que la feuille de style ne pourrisse ? Cette leçon n'introduit pas de nouvelle syntaxe : elle assemble ce que tu connais en une architecture, et te prépare à la veille.

L'idée directrice : le navigateur fait aujourd'hui presque tout ce pour quoi on chargeait Sass il y a dix ans. On va voir pourquoi le préprocesseur devient optionnel, comment structurer des design tokens, comment transformer un composant en API publique, et comment garder la cascade sous contrôle à l'échelle.

Le CSS moderne remplace le préprocesseur

Sass apportait quatre choses majeures : les variables, le nesting, la modularité (partials/imports), et des fonctions de calcul/couleur. Le CSS natif couvre désormais les quatre. La différence cruciale : les variables Sass sont résolues à la compilation (statiques), les custom properties CSS sont live dans le DOM — elles cascadent, héritent, et changent à l'exécution. C'est strictement plus puissant.

La même carte qu'avec Sass, mais zéro étape de compilation, et --brand reste surchargeable à chaud.

Note

Ce qui manque encore en natif : les boucles (@each), les mixins paramétrés, et l'autoprefixing. En pratique on n'en a presque plus besoin ; quand si, un PostCSS minimal (autoprefixer + un plugin de fallback) suffit, sans la lourdeur d'un préprocesseur complet.

Les design tokens : une hiérarchie de variables

Une erreur classique consiste à déclarer --blue: #2563eb et à l'utiliser partout. Le jour où le bleu doit devenir violet selon le contexte, tu es coincé. La solution éprouvée des design systems : trois niveaux. Les primitives (la palette brute, sans signification), les sémantiques (le rôle : surface, texte, accent), et les tokens de composant (spécifiques à un widget). Chaque niveau ne référence que le niveau au-dessus.

Changer la marque revient à modifier une primitive ; tous les niveaux suivants se mettent à jour seuls.

Le thème devient alors trivial : on ne touche qu'au niveau sémantique, jamais aux primitives ni aux composants.

Un même composant, deux thèmes, zéro duplication de règle.

Cas réel

Tous les design systems industriels reposent sur cette hiérarchie : GitHub Primer, Shopify Polaris, Material Design 3 et Adobe Spectrum exposent une palette de base (primitives), une couche de rôles (« alias »/sémantiques) et des tokens de composant. C'est précisément ce découpage qui leur permet de livrer un thème clair, un thème sombre et des variantes de marque sans réécrire un seul composant — exactement comme le bouton de thème de ce site, qui ne bascule que des tokens sémantiques sous [data-theme].

La custom property comme API de composant

Un composant bien conçu expose un contrat : des variables que l'extérieur peut surcharger, sans connaître son implémentation interne. C'est l'équivalent CSS des props. La technique : déclarer une variable avec une valeur de repli via la syntaxe var(--x, défaut), et laisser le parent la redéfinir.

--stack-gap est l'unique point d'entrée public ; le reste est encapsulé.

Pour une API robuste, type les variables avec @property (déjà vu) : tu garantis la valeur de repli si l'extérieur passe une valeur invalide, et tu rends la variable animable. C'est ce qui transforme une convention fragile en contrat solide.

Au survol, l'anneau s'anime ; une valeur incorrecte retomberait sur 0px au lieu de tout casser.

Le scoping à l'échelle : conventions et @scope

À grande échelle, le risque numéro un est la fuite : une règle qui mord sur un composant voisin. Deux outils complémentaires. D'abord la convention de nommage : BEM reste une valeur sûre (.card, .card__title, .card--featured) car il rend la portée lisible et garde la spécificité plate. Ensuite @scope (déjà vu), qui borne réellement la portée dans l'arbre, y compris une limite basse pour ne pas déborder sur des sous-composants.

La limite basse to (.media .media) empêche la règle de fuir sur le bloc imbriqué.

Astuce

En équipe, réserve @scope aux composants vraiment sujets aux fuites (cartes de contenu riche, widgets imbricables). Pour le reste, une bonne convention BEM + le nesting suffisent et restent plus lisibles dans les code reviews. Garde aussi en tête que @scope introduit une notion de proximité dans l'arbre dans la cascade : à spécificité égale, la règle déclarée dans le scope le plus proche l'emporte.

La cascade maîtrisée avec @layer

À l'échelle, le vrai problème de la cascade n'est pas la spécificité d'une règle isolée mais l'ordre de bataille entre des couches qui ne devraient pas se concurrencer : reset, librairie tierce, composants, utilitaires, surcharges. @layer (déjà vu) résout ça architecturalement : tu déclares l'ordre une fois, et la spécificité interne à chaque couche ne peut plus déborder sur une couche prioritaire.

.bg-danger (une seule classe) l'emporte sur .btn.btn--primary (deux classes) parce que sa couche passe après. La spécificité ne décide plus, l'architecture si.

Houdini et la colocation

Pour les cas que le CSS standard ne couvre pas encore, Houdini ouvre des portes. La Properties & Values API, c'est @property que tu connais déjà. La Paint API va plus loin : tu enregistres un worklet JS qui peint un fond procédural utilisable comme une image. C'est puissant mais encore inégalement supporté (absent de Firefox et de Safari côté Paint) : réserve-le à de l'amélioration progressive.

Le background-color sert de repli : si paint() n'est pas compris, la déclaration background-image est ignorée et la couleur tient.

Côté organisation des fichiers, la tendance moderne est la colocation : ranger le CSS d'un composant à côté de son markup (les CSS Modules en bundler, ou simplement un fichier .css par composant). Combinée aux @layer et aux tokens globaux, elle te donne le meilleur des deux mondes : portée locale claire, design system partagé.

La veille : ce qui arrive et comment suivre

Le CSS bouge vite. Quelques chantiers à surveiller : la fonction inline if() (conditions dans une valeur, déjà dans Chrome), sibling-index()/sibling-count() (indexer un élément dans sa fratrie sans JS), le masonry natif (en cours de spécification, syntaxe encore débattue entre display: masonry et une extension de grid), et les container style queries qui réagissent à la valeur d'une custom property du conteneur.

Support : les style queries sur custom properties sont largement disponibles (Chrome, Edge, Safari 18+) ; if() est récent (Chrome 137+) — prévois toujours un repli, ici la première déclaration padding.

Note

Baseline est devenu la référence pour décider. Une feature « Baseline Widely available » est sûre dans tous les navigateurs majeurs depuis 30 mois ; « Newly available » signifie « tout récent, prévois un repli ». Le statut est affiché directement sur MDN et caniuse.

Pièges fréquents

Piège fréquent

Sortir Sass par réflexe pour un simple calcul ou une teinte. Avec calc() et color-mix(), le préprocesseur n'apporte souvent qu'une étape de build et des variables moins puissantes (statiques). Demande-toi d'abord si le natif suffit — c'est presque toujours oui.

Piège fréquent

Des tokens plats et incohérents : utiliser --blue-500 directement dans un bouton court-circuite la hiérarchie. Quand le thème change, le bouton ne suit pas. Un composant ne référence jamais une primitive directement ; il passe toujours par un token sémantique.

Piège fréquent

Surcharger une variable au mauvais niveau : redéfinir --color-accent sur .btn au lieu de --btn-bg contamine tout le sous-arbre du bouton (icônes, liens internes qui héritent de l'accent). Surcharge le token le plus spécifique qui résout ton besoin, pas un token global.

Piège fréquent

Adopter une feature non Baseline sans repli. Attention aussi à @supports : pour tester un sélecteur récent, c'est @supports selector(...), pas un test de propriété. Et beaucoup de features de valeur (comme if() ou paint()) reposent sur le mécanisme naturel « déclaration invalide ignorée » : place toujours la déclaration de repli avant celle qui utilise la nouveauté.

Pour aller plus loin

Pour aller plus loin

Explore Open Props (une bibliothèque de tokens prête à l'emploi en custom properties pures), le format de tokens du W3C Design Tokens Community Group (échange entre Figma et le code), les container style queries avancées, l'API Houdini Paint, et un pipeline PostCSS minimal (autoprefixer seul). Pour la veille : suis Baseline sur MDN, caniuse, et le blog du CSS Working Group.

Antisèche : le CSS moderne à l'échelle

Glossaire

Design token
Variable nommée qui capture une décision de design (couleur, espacement, rayon…) pour la réutiliser et la thématiser de façon cohérente.
Primitive
Token de plus bas niveau : une valeur brute de la palette (ex. --blue-500), sans rôle d'usage, jamais utilisée directement dans un composant.
Token sémantique
Token qui nomme un rôle (--color-accent, --color-surface) et pointe vers une primitive ; c'est le seul niveau que le thème modifie.
Custom property
Variable CSS (--x) résolue dans le navigateur : elle cascade, hérite et change au runtime, contrairement à une variable Sass figée à la compilation.
@property
Règle qui type une custom property (syntax), fixe sa valeur initiale (repli garanti si l'entrée est invalide) et la rend animable.
@layer
Mécanisme de couches de cascade : l'ordre de déclaration des couches prime sur la spécificité des sélecteurs qu'elles contiennent.
@scope
Règle qui borne la portée d'un ensemble de styles à un sous-arbre du DOM, avec une éventuelle limite basse (to (…)) pour ne pas déborder.
Baseline
Référentiel d'interopérabilité indiquant si une fonctionnalité web est « Widely » (sûre partout) ou « Newly » (récente, à replier) dans les navigateurs majeurs.

Récap et vérification

  • Le CSS natif (variables live, calc(), color-mix(), nesting, @layer) rend le préprocesseur optionnel dans la plupart des projets.
  • Les design tokens se hiérarchisent en trois niveaux : primitives → sémantiques → composant ; le thème ne touche qu'au sémantique.
  • Une custom property avec repli est l'API publique d'un composant ; @property la type, la sécurise et la rend animable.
  • @scope et BEM bornent la portée ; @layer décide l'ordre de cascade indépendamment de la spécificité.
  • La veille passe par Baseline : adopter tôt, mais toujours avec un repli quand la feature est « Newly available ».

Vérifie ta compréhension

  1. Pourquoi une custom property CSS est-elle strictement plus puissante qu'une variable Sass ? Donne un cas où la différence est décisive.
  2. Dans une architecture à trois niveaux, pourquoi un composant ne doit-il jamais référencer une primitive ? Que casse-t-on sinon ?
  3. Tu as .btn.btn--primary dans la couche components et .bg-danger (une seule classe) dans utilities déclarée après. Laquelle gagne, et pourquoi la spécificité n'a-t-elle pas le dernier mot ?
