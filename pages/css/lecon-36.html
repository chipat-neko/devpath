Module 12 · Architecture, accessibilité & performance — Leçon 36

Propriétés logiques, préférences & robustesse

~28 min Avancé Leçon 10 recommandée

À la fin de cette leçon, tu sauras

  • écrire un CSS internationalisé avec les propriétés logiques (margin-inline, padding-block, inset, border-start-start-radius) qui suivent la direction et le mode d'écriture ;
  • adapter ton interface aux préférences système via prefers-color-scheme + color-scheme, prefers-reduced-motion et prefers-contrast ;
  • respecter le mode forced-colors sans casser l'accessibilité, et harmoniser les contrôles natifs avec accent-color ;
  • construire une amélioration progressive propre avec les feature queries @supports, y compris selector().
Sommaire de la leçon

Tu maîtrises déjà la mise en page moderne. Reste un terrain où beaucoup de code « propre » se fissure : un site lu en arabe (RTL), un utilisateur en mode sombre forcé par l'OS, quelqu'un qui a activé « réduire les animations » ou le mode contraste élevé de Windows. Un CSS robuste n'impose pas gauche et droite : il raisonne en termes de flux et il écoute les préférences de la machine.

Cette leçon assemble quatre piliers d'un CSS résilient : les propriétés logiques (i18n), les media features de préférence, le mode forced-colors, et les feature queries @supports pour une amélioration progressive sans casse.

Propriétés logiques : penser en flux, pas en gauche/droite

Les propriétés physiques (margin-left, top, border-top-left-radius) sont figées dans l'espace de l'écran. Les propriétés logiques sont relatives au flux du texte : deux axes, inline (le sens de lecture) et block (l'empilement des lignes), avec les côtés start et end. En français, inline-start = gauche ; en arabe, inline-start bascule à droite — automatiquement.

margin-inline accepte une ou deux valeurs (start puis end). inset: 0 remplace les quatre offsets d'un positionnement absolu et est déjà direction-neutre.

writing-mode et direction : le rappel i18n

Deux propriétés redéfinissent ces axes. direction (ou l'attribut HTML dir) inverse l'axe inline pour les langues RTL. writing-mode: vertical-rl fait carrément basculer l'axe block à l'horizontale (textes verticaux CJK, libellés tournés). Avec des propriétés logiques, ton composant suit ces changements sans une seule règle en plus.

Note

Préfère piloter la direction via l'attribut HTML dir="rtl" (correct sémantiquement et pour les lecteurs d'écran) plutôt que direction en CSS. Le CSS, lui, reste neutre grâce aux propriétés logiques.

Démo : la même boîte en LTR et en RTL

L'exemple ci-dessous n'utilise que des propriétés logiques. La deuxième boîte porte dir="rtl" : la marge de début, le rayon d'angle et l'alignement basculent tout seuls. Aucune règle [dir="rtl"] n'a été écrite.

Clique « 👁 Aperçu » : la boîte RTL est l'image miroir de la première, sans CSS dédié. Ajoute writing-mode: vertical-rl; à .carte pour voir l'axe block basculer.

Cas réel

Une équipe produit ouvre son application au marché du Golfe et doit livrer une version arabe (RTL) en deux semaines. Le CSS d'origine, truffé de margin-left, padding-right et text-align: left, aurait exigé une feuille [dir="rtl"] miroir à maintenir en double. L'équipe migre plutôt vers les propriétés logiques : un simple <html dir="rtl"> retourne alors toute l'interface — marges, arrondis, alignements — sans une seule règle propre au RTL. La bascule qui menaçait de durer des jours devient l'affaire d'un attribut.

Media features de préférence : écouter l'utilisateur

Le navigateur expose les réglages système via des media queries. La plus courante, prefers-color-scheme, se couple à la propriété color-scheme qui indique au navigateur de teinter aussi les UI natives (champs, barres de défilement).

Dans les DevTools (onglet Rendering → « Emulate CSS media feature »), bascule prefers-color-scheme et prefers-reduced-motion pour voir le panneau et l'animation réagir.

Astuce

Pour les animations, inverse la logique : anime par défaut, puis désactive dans @media (prefers-reduced-motion: reduce). Tu obtiens un repli sûr même si une transition t'échappe. Et teste tout ça en direct via « 👁 Aperçu » puis l'émulation des DevTools.

Il existe aussi prefers-reduced-transparency (remplacer les fonds translucides par de l'opaque). Traite-la comme une amélioration : la base reste utilisable sans elle.

forced-colors : ne pas casser le mode contraste élevé

En mode contraste forcé (Windows High Contrast), le système remplace tes couleurs par une palette restreinte définie par l'utilisateur, via des mots-clés système (Canvas, CanvasText, ButtonText, Highlight…). C'est une bonne chose : tu ne dois ni le combattre, ni y forcer tes propres couleurs.

forced-color-adjust: none rétablit tes couleurs sur un élément précis (un logo, un graphique). À utiliser avec parcimonie : tu reprends alors la responsabilité du contraste.

accent-color et color-scheme : des contrôles natifs cohérents

Plutôt que de réécrire des cases à cocher de zéro (fragile, peu accessible), accent-color teinte les contrôles natifs (checkbox, radio, range, progress) avec ta couleur de marque, tout en gardant l'accessibilité et le comportement natifs.

« 👁 Aperçu » : les contrôles natifs prennent ta couleur violette. Change accent-color et observe la cohérence sur toute la famille de champs.

@supports : amélioration progressive sans casse

Les feature queries testent si le navigateur comprend une déclaration ou un sélecteur, et n'appliquent l'amélioration que dans ce cas. La règle d'or : écris d'abord la base qui marche partout, puis enrichis dans un @supports.

Note la différence : @supports (propriété: valeur) pour une déclaration, @supports selector(...) pour un sélecteur comme :has().

Pièges fréquents

Piège fréquent

Coder en left/right. Un margin-right ou un text-align: left casse silencieusement en RTL : la marge reste du mauvais côté. Par défaut, raisonne en inline/block et start/end ; ne garde le physique que pour ce qui est vraiment lié à l'écran (une ombre portée décorative, par exemple).

  • Ignorer prefers-reduced-motion. Une animation non désactivée peut provoquer des malaises (mouvement vestibulaire). Désactive ou réduis systématiquement le mouvement dans @media (prefers-reduced-motion: reduce).
  • Écraser les couleurs système en forced-colors. Forcer tes background/color (ou abuser de forced-color-adjust: none) rend ton UI illisible pour ceux qui en ont le plus besoin. Laisse faire le système ; ajoute des outline avec les mots-clés système si un état devient invisible.
  • @supports mal parenthésé. Il faut des parenthèses autour de chaque test : @supports (display: grid), pas @supports display: grid. Et selector() pour un sélecteur, jamais @supports (:has(*)).
  • Oublier color-scheme. Sans elle, tes champs et barres de défilement restent en thème clair même quand ton fond est sombre — d'où des champs blancs aveuglants.

Pour aller plus loin

Pour aller plus loin

Approfondis le RTL complet (icônes directionnelles à retourner, nombres, ponctuation bidi), les modes d'écriture verticaux (writing-mode, text-orientation) pour le japonais/chinois, et adopte l'amélioration progressive comme philosophie : une base solide, des couches d'enrichissement testées par @supports et les media features. Entraîne-toi à émuler toutes ces préférences dans les DevTools (panneau Rendering) pour valider chaque état sans changer tes réglages système.

Antisèche : logique, préférences & robustesse

Glossaire

Propriété logique
Propriété relative au flux du texte (axes inline et block, côtés start/end) plutôt qu'aux côtés physiques de l'écran ; elle suit dir et writing-mode.
Axe inline / axe block
L'axe inline est le sens de lecture (horizontal en français) ; l'axe block est celui de l'empilement des lignes (vertical). Ils basculent avec writing-mode.
prefers-color-scheme
Media feature qui expose la préférence de thème (clair ou sombre) réglée dans le système d'exploitation.
color-scheme
Propriété qui déclare les thèmes gérés (light dark) pour que le navigateur rende aussi les UI natives (champs, barres de défilement) dans la bonne palette.
forced-colors
Mode (contraste élevé de Windows) où le système remplace les couleurs par une palette utilisateur restreinte, exposée via des mots-clés système (Canvas, ButtonText, Highlight…).
accent-color
Propriété qui teinte les contrôles de formulaire natifs (case, bouton radio, curseur) avec une couleur de marque, sans perdre l'accessibilité native.
Feature query (@supports)
Règle conditionnelle qui teste si le navigateur comprend une déclaration (@supports (display: grid)) ou un sélecteur (@supports selector(:has(*))).
Amélioration progressive
Stratégie consistant à écrire d'abord une base universelle, puis à ajouter des enrichissements conditionnés par @supports ou des media features — sans jamais casser l'expérience de base.

Récap et vérification

  • Les propriétés logiques (margin-inline, padding-block, inset, border-start-start-radius, valeurs start/end) suivent la direction et le mode d'écriture.
  • prefers-color-scheme + color-scheme gèrent le thème clair/sombre, UI natives comprises.
  • Désactive le mouvement dans prefers-reduced-motion: reduce ; renforce le contraste dans prefers-contrast: more.
  • En forced-colors: active, utilise les couleurs système ; réserve forced-color-adjust: none aux cas précis.
  • accent-color harmonise les contrôles natifs ; @supports (…) et @supports selector(…) enrichissent par-dessus une base universelle.

Vérifie ta compréhension

  1. Quelle propriété logique remplaces-tu pour que margin-left: 1rem suive le sens de lecture en RTL ?
  2. Pourquoi coupler prefers-color-scheme avec color-scheme plutôt que de changer seulement background ?
  3. Quelle est la différence d'écriture entre tester une propriété et tester un sélecteur en @supports ?
