Clean architecture & hexagonale

~34 min Intermédiaire Leçon 04

À la fin de cette leçon, tu sauras

  • énoncer la règle de dépendance ;
  • situer les cercles de la clean architecture ;
  • expliquer l'hexagonale (ports & adaptateurs) ;
  • en peser les bénéfices et les coûts.
Sommaire de la leçon

Clean architecture et architecture hexagonale visent la même idée, sous deux images différentes : protéger le métier en faisant pointer toutes les dépendances vers lui, et reléguer la base, l'interface et les frameworks au rang de détails interchangeables.

La règle de dépendance

Le principe unique à retenir : les dépendances pointent vers l'intérieur, vers le métier. Le cœur (les règles) ne connaît rien de la base, du web ou du framework. Ce sont eux qui connaissent le métier, via des abstractions (l'inversion de dépendance de la leçon 3, appliquée à grande échelle).

Les cercles de la clean architecture

  • Entités : les objets et règles du métier les plus stables (au centre).
  • Cas d'usage : ce que l'application fait (orchestration des règles pour une action précise).
  • Adaptateurs : traduisent entre le métier et le monde extérieur (contrôleurs, présentateurs, dépôts).
  • Frameworks & détails : la base, le web, l'UI — le plus extérieur, le plus remplaçable.

L'architecture hexagonale (ports & adaptateurs)

Même idée, autre vocabulaire : le métier est au centre d'un hexagone. Il communique avec l'extérieur par des ports (des interfaces qu'il définit) ; des adaptateurs (du code technique) branchent le monde réel sur ces ports. On distingue les ports entrants (qui pilotent le métier : une API, un test) et sortants (que le métier pilote : une base, un service d'e-mail).

La même idée, deux dessins

Clean = cercles concentriques ; hexagonale = un centre et des ports/adaptateurs. Dans les deux cas : le métier au centre, les détails à la périphérie, les dépendances qui pointent vers le centre. Si tu retiens ça, tu as l'essentiel.

Pourquoi ? Les bénéfices

  • Testabilité : on teste le métier sans base ni web (on branche de faux adaptateurs).
  • Remplaçabilité : changer de base ou d'interface ne touche que des adaptateurs, pas le cœur.
  • Clarté : on sait où vit chaque chose ; le métier est lisible, isolé du bruit technique.
  • Décisions retardées : on peut choisir la base, le framework… plus tard.

Le coût : ne pas en faire trop

Cette structure a un coût : plus d'interfaces, plus d'indirection, plus de fichiers. Pour une petite application, l'appliquer dogmatiquement serait de la sur-ingénierie. On en prend la dose adaptée : isoler le métier vaut surtout quand il est riche et durable.

L'abstraction a un prix

Chaque interface ajoutée « pour isoler » a un coût de lecture et de maintenance. Mets-en là où le métier est précieux et susceptible de survivre aux technologies ; pas partout par principe.

Cas réel

Une équipe devait migrer sa persistance de MongoDB vers PostgreSQL (besoin de vraies transactions et de requêtes relationnelles). Parce que le métier ne dépendait que d'un port DepotCommandes (une interface), la bascule s'est résumée à écrire un nouvel adaptateur SQL et à changer une ligne de câblage : pas une seule règle métier modifiée, et les tests (branchés sur un faux dépôt en mémoire) sont restés verts du début à la fin. Le contre-exemple est classique : quand le code d'accès aux données est éparpillé dans les règles, la même migration devient un chantier à haut risque qui touche des dizaines de fichiers.

Pièges fréquents

  • Appliquer le dogme partout. Une appli CRUD simple n'a pas besoin de quatre couches d'abstraction.
  • Inverser le sens des dépendances. Le métier ne doit jamais dépendre de la base ou du framework.
  • Confondre adaptateur et métier. Un contrôleur traduit ; il ne contient pas de règles.
  • Abstraire ce qui ne variera jamais. Une interface pour une seule implémentation figée est inutile.

Pour aller plus loin

Ces styles s'appuient directement sur le couplage/cohésion et l'inversion de dépendance (leçon 3), et utilisent des design patterns concrets (Repository pour la persistance, Adapter pour les ports…). Ce ne sont pas des concepts exotiques, mais l'application disciplinée des principes vus jusqu'ici.

Pour aller plus loin

Test décisif : « puis-je écrire un cas d'usage métier et le tester sans démarrer de base ni de serveur web ? ». Si oui, ton métier est bien isolé au centre — c'est tout l'objectif.

Antisèche : isoler le métier

Glossaire

Règle de dépendance
Principe unique de la clean architecture : les dépendances pointent vers l'intérieur, vers le métier ; le cœur ignore la base, le web et le framework.
Entités
Objets et règles métier les plus stables, au centre des cercles.
Cas d'usage
Ce que l'application fait : l'orchestration des règles métier pour une action précise.
Adaptateur
Code technique qui traduit entre le métier et le monde extérieur (contrôleur, dépôt, client d'API…).
Port
Interface définie par le métier (hexagonale). Entrant s'il pilote le métier, sortant si le métier le pilote.
Adaptateur entrant / sortant
Entrant : il déclenche le métier (API, test). Sortant : le métier l'appelle (base, e-mail).
Architecture hexagonale
« Ports & adaptateurs » : le métier au centre, relié à l'extérieur par des ports qu'implémentent des adaptateurs.
Sur-ingénierie
Ajouter plus de structure (couches, interfaces) que le problème n'en demande ; à éviter sur un métier pauvre.

Récap et vérification

  • La règle de dépendance : tout pointe vers le métier (au centre) ; les détails sont à la périphérie.
  • Clean (cercles : entités, cas d'usage, adaptateurs, frameworks) et hexagonale (ports & adaptateurs) = même idée.
  • Bénéfices : testabilité, remplaçabilité, clarté, décisions retardées.
  • Coût : plus d'abstraction ; à doser, pas à appliquer dogmatiquement.

Vérifie ta compréhension

  1. Dans quel sens pointent les dépendances ?
  2. Que sont les « ports » et les « adaptateurs » ?
  3. Quel est le coût de ces architectures ?

Exercices

Exercice 1Échauffement

Dans une architecture hexagonale, range : (a) la règle « un panier vide ne peut pas être validé » ; (b) le code qui écrit en base ; (c) un contrôleur HTTP. → métier (centre) / adaptateur sortant / adaptateur entrant.

Voir une solution

(a) Métier (centre) — une règle du domaine ; (b) adaptateur sortant — il implémente un port de persistance que le métier pilote ; (c) adaptateur entrant — il pilote le métier via un port entrant (il traduit la requête HTTP en appel de cas d'usage).

Exercice 2Application

Pourquoi cette architecture permet-elle de tester le métier sans base de données ?

Voir une solution

Parce que le métier dépend d'un port (une interface), pas d'une base concrète. En test, on branche un adaptateur factice (un faux dépôt en mémoire) sur ce port. Le métier ne voit aucune différence : il appelle toujours la même interface. On vérifie ainsi les règles sans démarrer de base ni de serveur — rapide et fiable.

Exercice 3Défi

Un développeur applique la clean architecture « par le livre » sur une petite application de liste de tâches : entités, cas d'usage, ports, adaptateurs, 4 couches d'interfaces… Le code en devient énorme. Qu'en penses-tu ?

Voir une solution

C'est de la sur-ingénierie : appliquer le dogme complet à une appli simple (essentiellement du CRUD) ajoute beaucoup d'indirection (interfaces, couches, fichiers) pour un métier pauvre qui ne le justifie pas. Le coût de lecture/maintenance dépasse le bénéfice. La bonne approche est de prendre la dose adaptée : garder les principes (séparer le métier, dépendances vers l'intérieur) mais avec peu de couches — par exemple une simple séparation présentation / métier / données, et n'introduire un port + adaptateur que là où une variation est réellement attendue (ex. plusieurs sources de données). L'architecture sert le besoin ; elle ne s'applique pas « parce que c'est dans le livre ». Ces styles brillent quand le métier est riche et durable, pas sur une todo-list.
