Domain-Driven Design (léger)

~33 min Intermédiaire Leçon 05

À la fin de cette leçon, tu sauras

  • expliquer l'idée du Domain-Driven Design ;
  • utiliser un langage ubiquitaire ;
  • découper en contextes délimités ;
  • juger quand le DDD vaut le coût.
Sommaire de la leçon

Le Domain-Driven Design (DDD) part d'une idée simple : pour bien concevoir un logiciel complexe, il faut d'abord comprendre le métier qu'il sert, et faire de ce métier le centre de la conception. C'est une approche riche ; on en voit ici l'essentiel, utile à tous.

Le métier au centre

Le DDD remet le domaine (le métier : la banque, la logistique, la santé…) au cœur du logiciel. La structure du code reflète le métier et ses règles, plutôt que les technologies. C'est le prolongement naturel de la clean architecture (leçon 5) : un métier riche, isolé, qu'on modélise sérieusement.

Le langage ubiquitaire

Pilier du DDD : le langage ubiquitaire. Développeurs et experts métier partagent le même vocabulaire, et ce vocabulaire se retrouve dans le code. Si l'expert dit « affréter une cargaison », le code parle d'affreter() et de Cargaison — pas de processData(). Le code devient une conversation lisible par tous.

Les mots comptent

Quand le code et les experts métier emploient les mêmes mots, les malentendus s'effondrent : moins de traductions, moins de bugs de compréhension. Le langage ubiquitaire est le bénéfice le plus accessible du DDD — applicable même sans tout le reste.

Les contextes délimités

Dans un grand système, le même mot peut avoir des sens différents selon le sous-domaine : un « client » n'est pas la même chose pour la facturation et pour le support. Le DDD répond par les contextes délimités (bounded contexts) : on découpe le domaine en zones cohérentes, chacune avec son modèle et son langage propres, reliées par des contrats explicites.

De bonnes frontières

Les contextes délimités donnent les frontières qui manquaient pour découper proprement — et, le cas échéant, en faire des microservices (leçon 4). On découpe par sens métier, pas par hasard technique.

Quelques briques (en bref)

Le DDD propose un vocabulaire de modélisation à l'intérieur d'un contexte :

  • Entité : un objet avec une identité qui dure (un Compte, une Commande).
  • Objet-valeur : défini par ses valeurs, sans identité (une Adresse, un Montant).
  • Agrégat : un groupe d'objets traité comme un tout cohérent, avec une racine qui garde les règles.
  • Service de domaine : une opération métier qui n'appartient naturellement à aucun objet.

Quand le DDD vaut le coût

Le DDD complet est exigeant : il demande du temps avec les experts métier et de la discipline de modélisation. Il brille sur les domaines complexes et durables (assurance, finance, logistique). Pour une application simple (du CRUD), il serait disproportionné — mais son langage ubiquitaire, lui, est presque toujours bénéfique.

Cas réel

Dans une plateforme SaaS, une seule classe User — héritée des débuts — servait à tout : authentification, facturation, préférences, permissions d'équipe, historique de support. Chaque nouvelle fonctionnalité y ajoutait des champs ; au bout de quelques années, l'objet comptait des dizaines d'attributs à moitié utilisés, et le moindre changement risquait de casser un module sans rapport. La refonte a consisté à reconnaître des contextes délimités : un Compte pour l'authentification, un Payeur pour la facturation, un Membre pour les équipes — chacun avec son modèle, reliés par un simple identifiant. Le mot « utilisateur » n'a pas disparu ; il a simplement cessé d'être le même objet partout.

Pièges fréquents

  • DDD complet sur du CRUD. Sur-ingénierie : un domaine pauvre ne le justifie pas.
  • Négliger le langage. Un DDD sans vocabulaire partagé rate son objectif premier.
  • Un seul modèle pour tout. Forcer un « client » universel crée des conflits ; sépare les contextes.
  • Le faire seul. Sans les experts métier, on modélise des hypothèses, pas le domaine réel.

Pour aller plus loin

On distingue le DDD stratégique (les grandes frontières : sous-domaines, contextes délimités, leurs relations) du DDD tactique (les briques de modélisation : entités, agrégats…). Commence par le stratégique et le langage : ce sont eux qui rapportent le plus, et le plus tôt.

Pour aller plus loin

Même sans « faire du DDD », adopte deux réflexes : parler le langage du métier dans le code, et repérer les frontières où les concepts changent de sens. Ce sont les bénéfices les plus rentables, applicables dès aujourd'hui.

Antisèche : le vocabulaire du DDD

Glossaire

Domain-Driven Design (DDD)
Approche de conception qui place le métier (le domaine) au centre et fait refléter par le code sa structure et ses règles.
Domaine
Le métier que sert le logiciel (banque, logistique, santé…) et l'ensemble de ses règles.
Langage ubiquitaire
Vocabulaire commun aux développeurs et aux experts métier, employé tel quel dans le code ; le bénéfice le plus accessible du DDD.
Contexte délimité (bounded context)
Zone cohérente du domaine avec son propre modèle et son propre langage ; répond au fait qu'un même mot change de sens selon le sous-domaine.
Entité
Objet doté d'une identité qui persiste dans le temps (un Compte, une Commande).
Objet-valeur
Objet défini uniquement par ses valeurs, sans identité propre (une Adresse, un Montant).
Agrégat
Groupe d'objets traité comme un tout cohérent, avec une racine qui garantit les règles.
DDD stratégique / tactique
Stratégique : les grandes frontières (sous-domaines, contextes). Tactique : les briques de modélisation (entités, agrégats…). On commence par le stratégique.

Récap et vérification

  • Le DDD met le domaine (métier) au centre de la conception.
  • Le langage ubiquitaire : un vocabulaire partagé métier/dev, présent dans le code.
  • Les contextes délimités découpent le domaine en zones cohérentes (de bonnes frontières).
  • Le DDD complet vaut pour les domaines complexes ; le langage, lui, profite à tous.

Vérifie ta compréhension

  1. Qu'est-ce que le langage ubiquitaire ?
  2. À quoi servent les contextes délimités ?
  3. Quand le DDD complet est-il justifié ?

Exercices

Exercice 1Échauffement

Réécris ce nom de méthode technique en langage métier : updateRecordStatus(id, 2) pour une commande qu'on expédie.

Voir une solution

Par exemple commande.expedier() (ou marquerCommeExpediee()). Le nom dit l'intention métier (« expédier une commande ») plutôt qu'une opération technique opaque (« mettre le statut à 2 »). C'est le langage ubiquitaire appliqué : le code se lit comme le métier se parle.

Exercice 2Application

Dans une plateforme e-commerce, le mot « produit » signifie des choses différentes pour le catalogue, le stock et la facturation. Comment le DDD aborde-t-il cela ?

Voir une solution

Par des contextes délimités : on ne force pas un modèle « produit » unique. Le catalogue a son produit (titre, description, photos), le stock le sien (référence, quantité, emplacement), la facturation le sien (libellé, prix, TVA). Chaque contexte a son modèle et son langage, et ils communiquent par des contrats explicites (un identifiant partagé, un événement). On évite ainsi un modèle géant qui essaierait de satisfaire tout le monde et ne satisferait personne.

Exercice 3Défi

Une équipe veut « faire du DDD » sur une petite application de gestion de contacts (ajouter/lister/modifier/supprimer). Bonne idée ? Que retiendrais-tu quand même ?

Voir une solution

Le DDD complet (agrégats, services de domaine, contextes multiples, modélisation poussée) serait disproportionné : le domaine est pauvre (du CRUD), il n'y a quasi pas de règles métier complexes — la sur-ingénierie coûterait sans rien apporter. Ce qu'on retient quand même : le langage ubiquitaire (nommer les choses comme le métier les nomme : Contact, fusionnerDoublons()…) et une séparation simple présentation / métier / données. Ces réflexes peu coûteux améliorent toujours la clarté. On garde le DDD lourd pour le jour où le domaine deviendra réellement complexe.
