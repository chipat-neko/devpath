Architecture logicielle

Savoir coder une fonction, c'est une chose ; structurer une application qui reste compréhensible et modifiable à mesure qu'elle grandit, c'en est une autre. L'architecture logicielle est l'art d'organiser le code en parties claires, faiblement couplées, qui résistent au changement. Ce cours te donne les principes (couches, couplage, cohésion) et les styles (monolithe, microservices, clean, hexagonale, DDD) pour décider en connaissance de cause.

Bien s'équiper

Les extensions VS Code pour l'architecture

L'architecture se dessine autant qu'elle se code. Ouvre le panneau Extensions de VS Code (Ctrl+Shift+X) :

À installer pour ce cours

  • Draw.io Integration — dessiner des diagrammes d'architecture dans l'éditeur.
  • PlantUML — décrire des diagrammes en texte (versionnables avec le code).
  • Markdown All in One — documenter les décisions d'architecture (ADR).
  • Dependency Cruiser (ou équivalent) — visualiser les dépendances entre modules.

Prérequis

Avoir déjà construit une vraie application (back-end, front, ou les deux) aide énormément : on parle d'organiser du code réel. Le cours Design patterns est un excellent compagnon, et des notions d'API rendent les exemples très concrets.

Ce que tu vas apprendre

Objectifs du cours

À la fin du cours, tu sauras

  • dire ce qu'est une architecture et pourquoi elle compte ;
  • organiser le code en couches aux responsabilités claires ;
  • raisonner en couplage, cohésion et dépendances ;
  • peser monolithe et microservices ;
  • comprendre la clean architecture et l'hexagonale ;
  • aborder le Domain-Driven Design et concevoir une architecture.

Pour qui, et pourquoi

Ce cours est pour toi si tes projets grossissent et deviennent durs à modifier, et que tu veux des repères pour les structurer. L'architecture n'est pas une affaire de gros systèmes : dès qu'un code dépasse quelques fichiers, des choix d'organisation s'imposent — autant les faire en connaissance de cause.

Le fil conducteur est le compromis : il n'existe pas d'architecture « parfaite », seulement des choix adaptés (ou non) à un contexte. On apprend à raisonner les trade-offs, pas à appliquer des recettes.

Astuce

La meilleure architecture est souvent la plus simple qui répond au besoin actuel, tout en restant facile à faire évoluer. Méfie-toi de la complexité ajoutée « au cas où » : elle coûte tout de suite, et sert rarement.

Récapitulatif

À retenir & glossaire

Les points clés du cours, puis les termes essentiels à connaître.

À retenir

  • Une architecture organise le code en parties claires pour résister au changement.
  • On vise un faible couplage et une forte cohésion.
  • Les couches séparent les responsabilités ; les dépendances pointent vers le cœur métier.
  • Monolithe ou microservices : un compromis, pas une mode.
  • Clean/hexagonale isolent le domaine des détails techniques.
Architecture logicielle
L'organisation d'ensemble d'un système : ses parties, leurs rôles et leurs relations.
Couche
Un niveau de responsabilité (présentation, métier, données…) qui ne communique qu'avec ses voisins.
Séparation des responsabilités
Chaque partie a un rôle clair et unique, ce qui rend le code modifiable isolément.
Couplage
Le degré de dépendance entre deux parties ; on le veut faible.
Cohésion
Le degré d'unité interne d'une partie (ses éléments vont ensemble) ; on la veut forte.
Monolithe
Une application déployée en un seul bloc.
Microservices
Une application découpée en services indépendants, déployés séparément.
Clean architecture
Un style où les dépendances pointent vers le cœur métier, isolé des détails techniques.
Architecture hexagonale
Le métier au centre, relié à l'extérieur par des « ports » et « adaptateurs ».
Domain-Driven Design
Une approche centrée sur le métier et son langage, pour structurer les systèmes complexes.
Compromis (trade-off)
Tout choix d'architecture a des avantages et des coûts ; il n'y a pas de solution parfaite.
