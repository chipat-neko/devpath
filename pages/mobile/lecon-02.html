Module 1 · Le terrain du mobile — Leçon 02

Natif ou multiplateforme : choisir son approche

~31 min Débutant Prérequis : les cinq contraintes du mobile (leçon 1)

À la fin de cette leçon, tu sauras

  • distinguer les trois grandes familles — natif, multiplateforme, web/PWA — et ce que chacune donne et coûte ;
  • démonter le mythe « un seul code partout » et repérer la part de code qui reste spécifique à chaque plateforme ;
  • appliquer une grille de critères honnête (équipe, budget, performance, API, look natif, durée de vie) ;
  • justifier le choix retenu pour Carnet — et pourquoi ce cours reste utile quel que soit ce choix.
Sommaire de la leçon

À la leçon 1, on a posé les cinq contraintes du mobile : interruptions, ressources comptées, écran tactile, réseau capricieux, sandbox et magasin. Ces contraintes sont les mêmes quel que soit le chemin technique choisi. Reste pourtant une décision à prendre avant d'écrire la première ligne : par quelle voie construire l'app ? Écrire deux applications séparées, une par plateforme ? En écrire une seule qui tourne partout ? Emballer un site web ?

Cette leçon donne une grille de décision, pas un verdict. On va voir les trois grandes familles — natif, multiplateforme, web/PWA —, casser le mythe tenace du « un seul code partout », poser les critères qui font vraiment pencher la balance, puis appliquer tout cela à Carnet. Le fil directeur : il n'existe pas de bonne réponse absolue, seulement un bon choix pour un contexte donné.

Trois familles, trois compromis

On peut construire une app mobile de trois grandes façons. Chacune place le curseur ailleurs entre contrôle (accès fin à la machine, look parfait) et coût de production (temps, argent, taille d'équipe).

  • Natif. On écrit une app par plateforme, avec ses outils officiels : SwiftUI (en Swift) pour iOS, Jetpack Compose (en Kotlin) pour Android. Cela fait deux bases de code distinctes. On obtient le meilleur look, la meilleure performance, l'accès immédiat aux dernières API — au prix d'un double travail.
  • Multiplateforme. On écrit une seule base de code qui produit l'app iOS et Android. C'est le domaine de Flutter (en Dart) et de React Native. On divise l'effort par presque deux, au prix d'une couche intermédiaire entre le code et la plateforme.
  • Web / PWA. On construit un site web — une Progressive Web App — que l'utilisateur peut « installer » depuis son navigateur. Une seule technologie, un déploiement instantané, aucun magasin obligatoire ; mais un accès aux capacités natives (caméra fine, arrière-plan, notifications riches) plus limité et variable selon les navigateurs.

Natif ne veut pas dire « meilleur »

Le mot natif impressionne, mais il ne signifie pas « supérieur » : il signifie « écrit avec les outils propres à une plateforme, pour elle seule ». C'est un compromis, pas un label de qualité. Une app Flutter soignée bat une app native bâclée. La vraie question n'est jamais « quelle est la meilleure techno ? » mais « quel compromis sert mon projet ? ».

Le mythe du « un seul code partout »

Le multiplateforme se vend souvent par une promesse séduisante : « écris une fois, tourne partout ». La promesse est en grande partie tenue — mais en grande partie seulement. Le partage est réel pour le gros de l'app : la logique métier, la structure des écrans, l'état, les appels réseau. Il s'arrête là où la plateforme redevient singulière.

  • Les réglages fins de plateforme. Configurer les permissions dans les fichiers iOS et Android, gérer les icônes, l'écran de lancement, les entrées système : cela reste du travail spécifique, fichier par fichier.
  • Le look exact de chaque système. Un bouton, un sélecteur de date, une barre de navigation n'ont pas la même allure sur iOS et sur Android. Le multiplateforme propose un rendu cohérent, mais coller au dernier détail de chaque plateforme demande des ajustements.
  • Les dernières API système. Quand Apple ou Google sort une nouveauté (un widget d'un nouveau genre, un capteur inédit), le framework multiplateforme met du temps à l'exposer ; en attendant, il faut écrire un pont de code natif.

Piège fréquent

Promettre « zéro code spécifique ». C'est le mensonge commercial classique du multiplateforme. En vérité, il faudra toujours : configurer les deux plateformes, tester sur les deux (un vrai iPhone et un vrai Android), et parfois écrire un petit pont natif. Choisir le multiplateforme fait fondre la part spécifique, il ne la supprime pas. Budgète-la.

Une base de code, ou deux ?

La différence la plus concrète entre natif et multiplateforme tient en un chiffre : le nombre de bases de code à écrire, tester et maintenir dans la durée. Ce n'est pas qu'une affaire de premier développement : chaque correction de bug, chaque nouvelle fonctionnalité se paie une fois en multiplateforme, et deux fois en natif.

Astuce

Pour estimer le vrai coût, pense en années, pas en semaines. Le premier lancement n'est qu'un début : une app vit, reçoit des correctifs, gagne des fonctionnalités. Multiplie mentalement chaque tâche par le nombre de bases de code, sur toute la durée du projet. C'est souvent là que le multiplateforme gagne pour une petite équipe — et là que le natif se justifie pour une grande équipe qui a les moyens de deux spécialistes.

La grille de critères

Aucun de ces trois choix n'est « le bon » dans l'absolu. Le bon choix dépend de ton contexte. Voici les critères qui font réellement pencher la balance ; passe-les en revue avant de décider.

  • Taille et compétences de l'équipe. Une personne, ou une petite équipe qui connaît déjà le web ? Le multiplateforme évite d'embaucher deux spécialistes. Une grande équipe avec des experts iOS et Android ? Le natif devient tenable.
  • Budget et délais. Serrés ? Une seule base de code livre iOS et Android plus vite et moins cher. Confortables ? Le double coût du natif redevient acceptable.
  • Besoin de performance extrême. Un jeu 3D, du calcul lourd, un traitement d'image en temps réel ? Le natif garde l'avantage. Une app de formulaires, de listes et d'écrans ? Le multiplateforme suffit largement.
  • Accès aux dernières API natives. L'app doit-elle exploiter une nouveauté iOS le jour de sa sortie ? Le natif y accède en premier. Sinon, le multiplateforme rattrape vite.
  • Importance du look natif exact. Chaque plateforme doit-elle avoir précisément ses composants système ? Le natif l'offre nativement. Un look propre et cohérent suffit ? Le multiplateforme convient.
  • Durée de vie du projet. Un projet qui vivra dix ans amortit un investissement natif ; un projet court ou expérimental privilégie la vitesse du multiplateforme ou du web.

Le choix se révise

Un choix d'approche n'est pas gravé pour l'éternité. Beaucoup d'équipes commencent en multiplateforme pour valider vite une idée, puis réécrivent en natif la partie qui l'exige — ou l'inverse : une app native se dote plus tard d'une couche partagée. L'important est de choisir en connaissance de cause, pas de chercher un choix « définitif ». Un mauvais choix assumé et documenté vaut mieux qu'un bon choix subi.

Le choix pour Carnet

Appliquons la grille à notre fil rouge, Carnet — le journal de balades qui note une photo, un lieu et du texte, même hors-ligne. Passons ses besoins au filtre des critères :

  • Équipe : petite. Une ou deux personnes. Écrire et maintenir deux bases de code natives serait lourd. → penche vers le multiplateforme.
  • Budget : serré. On veut iOS et Android sans doubler le coût. → penche vers le multiplateforme.
  • Besoins matériels : caméra et GPS. Ce sont des capacités banales, accessibles partout, y compris en Flutter. → aucun obstacle au multiplateforme.
  • Performance : ordinaire. Des écrans, une liste, une carte. Pas de jeu 3D, pas de calcul lourd. → le multiplateforme suffit.
  • Look : cohérent suffit. Carnet n'a pas besoin de copier au pixel près chaque composant système ; un rendu propre et lisible convient.

La conclusion est nette : pour Carnet, Flutter est un choix raisonnable. Une base de code, iOS et Android livrés ensemble, la caméra et le GPS accessibles, un coût maîtrisé. Ce cours l'illustrera d'ailleurs dans les trois écosystèmes — mais le choix « par défaut » de Carnet, si l'on devait livrer demain avec deux développeurs, serait le multiplateforme.

Et si le contexte changeait ?

Renversons un critère pour voir le choix basculer. Imagine que Carnet doive absolument exploiter une nouveauté iOS le jour de sa sortie — mettons un tout nouveau capteur de profondeur exposé par une API fraîche. Là, le natif reprend l'avantage : il accède à cette API en premier, sans attendre que Flutter la relaie. Un seul critère qui bascule, et la balance penche de l'autre côté. C'est bien la preuve qu'il n'y a pas de réponse absolue : le bon choix dépend du contexte.

Pour aller plus loin

Chaque écosystème a son cours dédié si tu veux approfondir le langage lui-même : Swift (avec SwiftUI) pour iOS, Kotlin (avec Jetpack Compose) pour Android, Dart & Flutter pour le multiplateforme. Le présent cours reste au-dessus de ce choix : il enseigne les principes de l'application — cycle de vie, navigation, hors-ligne, permissions, publication — qui te serviront quelle que soit l'approche retenue.

Cas réel

Cas réel

Une jeune pousse veut lancer une app de covoiturage local avec deux développeurs et six mois devant elle. Recruter un spécialiste iOS et un spécialiste Android est hors budget ; livrer sur une seule plateforme priverait la moitié des utilisateurs. Elle choisit Flutter : une base de code, iOS et Android en même temps, deux développeurs suffisent. L'arbitrage est assumé : le sélecteur de date et quelques animations ne collent pas au pixel près au look 100 % natif de chaque système. Compromis accepté : mieux vaut deux apps « très proches du natif » livrées à temps qu'une seule app parfaite. — Le calcul inverse existe aussi : une banque reste, elle, sur du natif. Elle a les moyens de deux équipes, exige les dernières API de sécurité biométrique le jour de leur sortie, et veut le look exact de chaque plateforme pour inspirer confiance. Même grille de critères, contexte opposé, décision opposée — et les deux ont raison.

Pièges fréquents

Piège fréquent

Choisir par mode, pas par contexte. « Tout le monde fait du natif, donc natif » ; « Flutter est à la mode, donc Flutter ». C'est mettre la charrue avant les bœufs. La bonne démarche part du projet : équipe, budget, besoins, durée de vie ; puis on lit la grille ; ensuite seulement on nomme une techno. Une décision qui ne peut pas se justifier par un critère est une décision qui n'a pas été prise.

  • Croire « natif = toujours mieux » — c'est un compromis, pas un gage de qualité ; une app multiplateforme soignée bat une app native négligée.
  • Croire « un seul code = zéro spécifique » — la part spécifique fond mais ne disparaît pas ; il faut la budgéter et tester sur les deux plateformes.
  • Oublier la durée de vie — juger sur le seul premier lancement ; c'est la maintenance sur des années qui révèle le vrai coût d'une ou deux bases de code.

Antisèche

Glossaire

Application native
App écrite avec les outils officiels d'une plateforme (SwiftUI pour iOS, Jetpack Compose pour Android) et compilée pour elle seule ; deux plateformes = deux bases de code.
Multiplateforme
Approche (Flutter, React Native) où une seule base de code produit l'app iOS et Android, via une couche intermédiaire.
PWA (Progressive Web App)
Site web « installable » depuis le navigateur : un déploiement instantané, mais un accès aux capacités natives plus limité et variable.
Base de code
L'ensemble du code source d'une app : ce qu'il faut écrire, tester et maintenir. Le natif en demande deux ; le multiplateforme, une seule.
Pont (bridge)
Petit morceau de code natif écrit pour donner à une app multiplateforme l'accès à une API système que le framework n'expose pas encore.
Look natif
L'apparence et le comportement propres à chaque plateforme (boutons, sélecteurs, barres) ; le natif l'offre exactement, le multiplateforme s'en approche.
Flutter
Framework multiplateforme de Google, en Dart, où tout est un widget ; une base de code pour iOS et Android.
React Native
Framework multiplateforme de Meta, en JavaScript ; autre grande voie du « une base, deux apps », proche de React sur le web.

Récap et vérification

  • Trois familles : natif (deux bases de code, contrôle et look maximaux), multiplateforme (une base partagée, coût réduit), web/PWA (un site installable, accès natif limité).
  • Le « un seul code partout » est un mythe partiel : réglages fins, look exact et dernières API restent spécifiques à chaque plateforme.
  • La grille de critères (équipe, budget, performance, API, look, durée de vie) montre qu'il n'y a pas de bonne réponse absolue, seulement un bon choix pour un contexte.
  • Pour Carnet — petite équipe, budget serré, caméra/GPS banals, perf ordinaire — Flutter est raisonnable ; mais une nouveauté iOS « le jour J » ferait repencher vers le natif.
  • Ce cours reste utile quel que soit le choix : il enseigne les principes de l'application, communs aux trois écosystèmes.

Exercices

Exercice 1Échauffement

Pour chacune de ces affirmations, dis si elle est vraie ou fausse, et corrige en une ligne si elle est fausse : (a) « natif » veut dire « meilleure qualité garantie » ; (b) une app Flutter n'a aucun code spécifique à iOS ou Android ; (c) le natif demande deux bases de code pour couvrir iOS et Android ; (d) une PWA accède aux capacités natives aussi complètement qu'une app native.
