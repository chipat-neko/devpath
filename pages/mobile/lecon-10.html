Module 3 · L'app dans le monde réel — Leçon 10

Parler au réseau : appeler une API sans figer l'écran

~36 min Intermédiaire Prérequis : l'état et la source de vérité unique (leçon 6)

À la fin de cette leçon, tu sauras

  • faire une requête HTTP (GET/POST) et décoder une réponse JSON vers un modèle typé ;
  • expliquer pourquoi un appel réseau ne doit jamais tourner sur le fil principal, et comment l'asynchronisme l'évite ;
  • gérer le triptyque chargement / succès / erreur et le relier à l'état de la leçon 6 ;
  • rendre un appel robuste — timeout, codes 4xx/5xx, absence totale de réseau ;
  • appliquer tout cela à Carnet dans les trois écosystèmes — SwiftUI, Compose, Flutter.
Sommaire de la leçon

Jusqu'ici, Carnet vivait replié sur lui-même : on saisissait une observation, on la rangeait sur l'appareil, on la relisait. Aucun autre ordinateur n'était concerné. Mais une vraie application finit toujours par parler à un serveur : pour envoyer ses données ailleurs, pour en recevoir de fraîches. Dans Carnet, on voudra synchroniser une balade vers le nuage et récupérer la météo du lieu observé. C'est le sujet de cette leçon : l'appel réseau.

Le réseau introduit une difficulté que le stockage local ignorait : il est lent et incertain. Une lecture sur disque prend une milliseconde ; une requête vers un serveur peut prendre une seconde, dix secondes, ou ne jamais répondre. Programmer le réseau comme on programme une lecture locale — en attendant tranquillement la réponse sur place — fige l'écran. Toute la leçon tourne autour d'une règle : ne jamais bloquer le fil principal. On verra l'appel HTTP et le décodage JSON, l'asynchronisme qui garde l'interface vivante, le patron chargement / succès / erreur, la robustesse, et l'application à Carnet.

Un appel HTTP, une réponse JSON

Parler à une API, c'est envoyer une requête HTTP à une adresse et lire la réponse. Deux verbes suffisent pour l'essentiel : GET pour lire une ressource (la météo d'un lieu), POST pour créer ou envoyer quelque chose (une observation à synchroniser). Le serveur répond avec un code de statut (200 « tout va bien », 404 « introuvable », 500 « erreur serveur ») et, le plus souvent, un corps en JSON — un format texte que toutes les plateformes savent lire.

JSON, le langage commun

Le JSON n'est pas propre au mobile : c'est le format d'échange dominant du web, et les deux bouts de la ligne — l'app et le serveur — s'accordent dessus. Côté serveur, on définit un contrat (quels champs, quels types) ; côté app, on écrit un modèle qui colle à ce contrat. Si tu veux comprendre l'autre extrémité — comment une API est conçue, ses routes et ses réponses — le cours API et le cours HTTP sont les compagnons directs de cette leçon.

Ne jamais bloquer le fil principal

Voici le cœur de la leçon. Une application mobile possède un fil principal (aussi dit fil de l'UI) qui a une seule mission : dessiner l'écran et réagir aux gestes, plusieurs dizaines de fois par seconde. Tant qu'il est libre, l'interface est fluide. Mais si on lui confie une tâche lente et bloquante — attendre une réponse réseau —, il ne peut plus rien redessiner pendant tout ce temps : l'écran gèle. Boutons inertes, défilement collé, spinner immobile. Après quelques secondes, l'utilisateur croit l'app plantée et la ferme.

La solution s'appelle l'asynchronisme : on lance l'appel réseau sur un fil d'arrière-plan, le fil principal reste libre de continuer à dessiner, et quand la réponse arrive, le résultat revient sur le fil principal pour mettre l'écran à jour. On n'attend plus « les bras croisés » : on demande, on rend la main, on est rappelé plus tard.

Piège fréquent

Croire que « asynchrone » veut dire « on peut toucher l'écran depuis n'importe où ». Non : on peut attendre partout, mais toute modification de l'interface doit se faire sur le fil principal. C'est justement ce que garantissent await (SwiftUI, Flutter) et le retour de withContext (Kotlin) : la suite du code reprend sur le bon fil. Mettre à jour une vue depuis un fil d'arrière-plan provoque des plantages ou des affichages incohérents.

Les trois états d'un appel

Un appel réseau n'est pas un simple « j'ai les données ». Entre le moment où on le lance et celui où on connaît le résultat, l'écran doit montrer quelque chose. Et le résultat peut être un succès… ou un échec. D'où le patron le plus important de la leçon, à retenir par cœur : un appel traverse les états idle → loading → (success | error).

  • idle (au repos) : rien n'est encore demandé. L'écran affiche son contenu normal, ou un bouton « charger ».
  • loading (chargement) : l'appel est parti. On affiche un indicateur d'activité (un spinner) pour dire « ça travaille », et on désactive le bouton pour éviter les doubles envois.
  • success (succès) : la réponse est là, décodée. On affiche les données.
  • error (erreur) : quelque chose a échoué. On affiche un message clair et un bouton « réessayer » — jamais un écran vide ni un spinner qui tourne sans fin.

Ce patron n'est rien d'autre qu'un état, exactement au sens de la leçon 6 : une seule variable qui décrit l'écran, et dont l'interface est le reflet. On change l'état (passer à loading, puis à success ou error), et l'écran suit.

Astuce

Modélise l'état avec un type fermé (une enum Swift à valeurs associées, une sealed interface Kotlin, une classe scellée Dart). Le compilateur t'oblige alors à traiter les quatre cas : tu ne peux plus « oublier » l'erreur ou le chargement. C'est le meilleur garde-fou contre le spinner qui tourne à l'infini : l'oubli devient une erreur de compilation, pas un bug découvert par l'utilisateur.

Robustesse : le réseau ment, doute de tout

Un appel qui marche sur le Wi-Fi du bureau n'est pas un appel fiable. Le réseau réel est hostile : il est lent, il coupe, le serveur a des humeurs. Rendre un appel robuste, c'est prévoir tout ce qui peut mal tourner.

  • Le timeout. Ne jamais attendre l'infini. On fixe une limite (par exemple 15 secondes) : passé ce délai, l'appel échoue proprement et bascule en error. Sans timeout, un serveur muet fige l'app dans un loading éternel.
  • Les codes d'erreur HTTP. Un statut 2xx est un succès. Un 4xx dit « ta requête est fautive » (401 non autorisé, 404 introuvable) : réessayer à l'identique ne sert à rien. Un 5xx dit « le serveur a échoué » : réessayer plus tard peut marcher. On ne traite pas ces familles de la même façon.
  • Pas de réseau du tout. Mode avion, tunnel, forêt : la requête ne part même pas. On l'attrape et on annonce le hors-ligne — sujet entier de la leçon 11, où le stockage local prend le relais.
  • Ne pas faire aveuglément confiance aux données reçues. Un champ peut manquer, avoir un type inattendu, une valeur absurde. Le décodage doit échouer proprement (et tomber en error) plutôt que planter : une réponse malformée ne doit jamais faire tomber l'app.

Cas réel

Cas réel

Une application de transport soignée affichait, à chaque ouverture, les prochains passages en temps réel — récupérés par un appel réseau. Le développeur avait fait cet appel directement sur le fil principal, parce que « sur le Wi-Fi du bureau, c'était instantané ». Sur le terrain, en 4G faible dans une gare bondée, l'appel prenait 3 à 6 secondes : pendant tout ce temps, l'écran de démarrage gelait, aucun bouton ne répondait. Les évaluations tombaient : « l'app plante à l'ouverture », « écran figé ». Elle ne plantait pas : elle attendait, sur le mauvais fil. Le correctif a tenu en trois gestes : passer l'appel en asynchrone (hors du fil principal), afficher un spinner pendant le chargement, et prévoir un état erreur avec « réessayer » plus un timeout de 15 s. Même serveur, même réseau : l'app est passée de « plantée » à « fluide », juste en ne bloquant plus l'écran.

Carnet parle au réseau

Appliquons tout au fil rouge. Carnet a deux besoins réseau, un dans chaque sens :

  • Synchroniser (POST) : envoyer une observation locale vers le serveur, pour la retrouver sur un autre appareil ou en sauvegarde.
  • Récupérer la météo (GET) : interroger l'API météo avec la position de la balade, pour l'afficher à côté de l'observation.

Pour aller plus loin

Un vrai appel réseau porte souvent plus que l'URL : des en-têtes (un jeton d'authentification, le type de contenu), une gestion des certificats (HTTPS), parfois de la pagination pour les longues listes. Tout cela relève de l'API elle-même : le cours API détaille la conception des routes et de l'authentification, et le cours HTTP explique en profondeur les méthodes, les codes de statut et les en-têtes que cette leçon n'a qu'effleurés. Pièges fréquents

Piège fréquent

Oublier l'état « erreur ». On code le chargement, on code le succès, et l'on « verra plus tard » pour l'échec. Résultat : dès qu'il n'y a plus de réseau — c'est-à-dire souvent —, l'utilisateur voit un spinner qui tourne à l'infini, ou un écran vide sans explication. L'état erreur n'est pas un bonus : c'est la moitié du travail, car sur mobile l'échec est un cas normal, pas exceptionnel.

  • Appeler sur le fil principal — « ça marche sur mon Wi-Fi » : l'écran gèlera dès que le réseau faiblira, et l'utilisateur croira l'app plantée.
  • Ne pas mettre de timeout — un serveur muet laisse l'app coincée en loading pour toujours ; toujours plafonner l'attente.
  • Faire confiance au JSON reçu — supposer que tous les champs sont là et bien typés ; une réponse malformée doit tomber en erreur, pas faire planter l'app.
  • Traiter 4xx et 5xx pareil — réessayer en boucle une requête que le serveur refuse (401, 404) ne la fera jamais passer ; seul un 5xx justifie une nouvelle tentative plus tard.

Antisèche

Glossaire

Requête HTTP
Message envoyé à un serveur pour lire ou modifier une ressource ; ses verbes courants sont GET (lire) et POST (envoyer).
JSON
Format texte d'échange de données (accolades, paires clé/valeur) ; le langage commun entre l'application et le serveur.
Décodage (désérialisation)
Transformer un texte JSON reçu en un objet typé du langage (un Meteo, une Observation) aux champs manipulables directement.
Fil principal (fil de l'UI)
Le fil qui dessine l'écran et traite les gestes ; s'il est occupé par une tâche lente, l'interface gèle.
Asynchronisme
Lancer une tâche lente sans attendre sur place : le fil principal reste libre, et le résultat revient plus tard (async/await, coroutines, Future).
Coroutine
En Kotlin, une fonction qui peut se mettre en pause (suspend) sans bloquer ; withContext(Dispatchers.IO) déporte le travail hors du fil principal.
Timeout
Délai maximal accordé à un appel ; passé cette limite, l'appel échoue proprement au lieu d'attendre indéfiniment.
Code de statut HTTP
Nombre renvoyé par le serveur résumant l'issue : 2xx succès, 4xx requête fautive, 5xx erreur serveur.

Récap et vérification

  • Un appel réseau est une requête HTTP (GET pour lire, POST pour envoyer) ; la réponse JSON doit être décodée vers un modèle typé avant usage.
  • Le réseau est lent et incertain : on ne l'appelle jamais sur le fil principal. L'asynchronisme (async/await, coroutines, Future) garde l'interface fluide pendant l'attente.
  • Tout appel traverse les états idle → loading → (success | error) : spinner, données, ou message d'erreur avec « réessayer ». C'est un état au sens de la leçon 6.
  • La robustesse impose un timeout, la distinction des codes 4xx/5xx, la gestion de l'absence de réseau, et la méfiance envers les données reçues.
  • Dans Carnet, on synchronise une observation (POST) et on récupère la météo (GET), avec spinner et erreur, dans les trois écosystèmes.
