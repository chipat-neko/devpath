Module 4 · OCaml en profondeur — Leçon 13

Un projet complet : interpréteur

~50 min Avancé Prérequis : leçon 12

À la fin de cette leçon, tu sauras

  • modéliser un langage par un type variant (AST) ;
  • évaluer par pattern matching ;
  • gérer les erreurs avec result ;
  • assembler un programme OCaml de bout en bout.
Sommaire de la leçon

Tu as parcouru tout OCaml : l'inférence de types, les variants et le pattern matching, les modules et foncteurs, les types avancés, la concurrence. Il est temps de tout assembler dans un vrai projet. On va construire un mini-interpréteur d'expressions arithmétiques — un programme qui lit, comprend et évalue du code. C'est l'exercice emblématique d'OCaml, le langage des compilateurs : tu verras pourquoi variants et pattern matching y sont si parfaitement adaptés.

Le plan : de l'expression au résultat

Un interpréteur transforme une expression en une valeur. On le décompose en deux temps :

  1. représenter l'expression par une structure de données (l'arbre de syntaxe, ou AST) ;
  2. l'évaluer en parcourant cet arbre.

OCaml excelle ici : l'AST est un variant, et l'évaluation un pattern matching. Le code suit la structure du problème.

Modéliser l'AST avec un variant

Notre langage : des nombres, et les quatre opérations. On le décrit par un type expr récursif.

Le type est récursif : une Add contient deux expr, qui peuvent elles-mêmes être des additions, etc. C'est exactement la forme d'un arbre — d'où le nom « arbre de syntaxe ».

Évaluer par pattern matching

L'évaluateur parcourt l'arbre récursivement : un cas par constructeur. La structure du match épouse celle du type.

Remarque l'élégance : chaque cas est trivial, et le compilateur vérifie que tous les constructeurs sont traités. Si tu ajoutes un cas Puissance au type sans l'évaluer, OCaml t'avertit que le match est incomplet. La sûreté est gratuite.

Gérer les erreurs avec result

Une division par zéro doit être gérée proprement. Plutôt qu'une exception, on utilise le type result (Ok / Error) pour rendre l'échec visible dans le type.

Le type de retour devient (float, string) result : l'appelant ne peut pas ignorer l'erreur, car il doit faire un match sur Ok/Error. C'est le style fonctionnel de gestion d'erreurs : pas d'exception cachée, tout est explicite.

Étendre le langage

La beauté de cette architecture : pour ajouter une fonctionnalité (des variables, des conditions, des fonctions), on ajoute un constructeur au type expr et un cas à eval. Le compilateur guide : il signale chaque endroit à compléter. C'est ainsi qu'on bâtit, par étapes, un vrai langage de programmation — et c'est exactement ce que font les compilateurs écrits en OCaml.

Cas réel — ce patron est partout

AST + eval n'est pas qu'un exercice : c'est le squelette de la calculatrice de ton téléphone, des moteurs de règles métier, des formules d'un tableur, et bien sûr des compilateurs. Le premier compilateur de Rust a démarré exactement ainsi, en OCaml. Le même couple « variant récursif + pattern matching » structure des programmes de milliers de lignes — parce qu'il fait épouser au code la forme du problème.

Astuce — un interpréteur se teste très bien

Comme eval transforme une entrée en une sortie sans état, il se prête idéalement aux tests : let%test "2+3" = eval (Add (Nombre 2., Nombre 3.)) = 5.. Écris quelques cas connus dès le début : à chaque nouveau constructeur, ils attrapent aussitôt les régressions.

Pièges fréquents

Piège fréquent

Ignorer l'avertissement « pattern matching non exhaustif ». Quand OCaml signale qu'un match ne couvre pas tous les cas, ce n'est pas du zèle : c'est un bug en puissance (un cas oublié qui plantera à l'exécution). Traite ces avertissements comme des erreurs. À l'inverse, évite le joker _ -> … attrape-tout sur un type que tu fais évoluer : il masquerait justement les cas oubliés. Liste les constructeurs explicitement, et laisse le compilateur veiller.

Pour aller plus loin

Pour aller plus loin

Tu as construit la moitié arrière d'un compilateur (l'évaluation). La moitié avant — l'analyse (transformer du texte « (2 + 3) * 4 » en AST) — se fait avec un lexer et un parser : OCaml dispose d'excellents outils pour cela (ocamllex, menhir). Combine les deux et tu as un interpréteur complet, du texte au résultat. C'est l'aboutissement naturel de ce cours : OCaml est le langage pour écrire des langages. Félicitations, tu as fait le tour d'OCaml !

Glossaire

Interpréteur
Programme qui lit, comprend et évalue du code, produisant directement un résultat (sans passer par un exécutable).
AST (arbre de syntaxe abstraite)
Représentation arborescente d'un programme ; en OCaml, un variant récursif où chaque nœud est un constructeur et chaque feuille une valeur.
Variant récursif
Type somme dont des constructeurs contiennent le type lui-même (Add of expr * expr) : la structure même d'un arbre.
Évaluation
Parcours de l'AST — typiquement par pattern matching récursif — qui calcule la valeur de l'expression.
Exhaustivité
Garantie du compilateur que tous les cas d'un match sont traités ; un cas oublié devient un avertissement, pas un bug d'exécution.
result
Type Ok / Error qui rend l'échec explicite dans la signature : l'appelant est forcé de le gérer, sans exception cachée.
Lexer / Parser
Outils d'analyse (en OCaml : ocamllex et menhir) qui transforment le texte source en AST, en amont de l'évaluation.

Récap et vérification

  • Un interpréteur : représenter l'expression par un AST (variant récursif), puis l'évaluer (pattern matching).
  • Le match épouse la structure du type ; le compilateur vérifie l'exhaustivité.
  • Gérer les erreurs avec result (Ok/Error) : l'échec est dans le type, donc incontournable.
  • Étendre le langage = ajouter un constructeur + un cas ; le compilateur guide les modifications.

Vérifie ta compréhension

  1. Quelles sont les deux étapes d'un interpréteur ?
  2. Que vérifie le compilateur sur un match ?
  3. Pourquoi utiliser result plutôt qu'une exception ?

Exercice 3Défi

Pourquoi cette architecture (AST + eval) rend-elle l'ajout d'une fonctionnalité au langage simple et sûr ?

Voir une solution

Parce qu'ajouter une fonctionnalité revient à ajouter un constructeur au type expr et un cas à eval. Et comme le compilateur vérifie l'exhaustivité du pattern matching, il signale automatiquement tous les endroits où il faut traiter le nouveau cas. On ne peut pas oublier un endroit : le compilateur guide la modification de bout en bout, ce qui rend l'extension à la fois simple et sûre.
