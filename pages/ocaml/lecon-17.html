Module 5 · OCaml, encore plus loin — Leçon 17

Gérer les erreurs : result et let*

~55 min Avancé Prérequis : leçon 06

À la fin de cette leçon, tu sauras

  • modéliser un échec avec message grâce au type result ;
  • chaîner des étapes faillibles sans escalier de match ;
  • définir et utiliser l'opérateur let* (Result.bind) ;
  • choisir entre result et exceptions.
Sommaire de la leçon

La leçon 06 a montré option pour dire « valeur présente ou absente ». Mais l'absence ne dit pas pourquoi ça a échoué. Pour cela, OCaml a result : un succès qui transporte une valeur, ou un échec qui transporte un message. Le vrai sujet de cette leçon : comment enchaîner plusieurs opérations faillibles sans sombrer dans un escalier de match imbriqués — grâce aux opérateurs de liaison d'OCaml.

Le type result

result est un variant à deux cas, prédéfini dans la bibliothèque standard :

Astuce — option ou result ?

Prends option quand l'absence se suffit à elle-même (« pas trouvé », point). Prends result quand il faut expliquer l'échec (message, code, donnée fautive). En pratique, result gagne dès qu'un humain devra un jour lire pourquoi l'opération a raté.

La solution : bind et l'opérateur let*

La régularité saute aux yeux : à chaque étage, « si Error, on propage ; si Ok x, on continue avec x ». Cette opération porte un nom : bind (Result.bind). Depuis OCaml 4.08, on peut lui donner une syntaxe agréable, l'opérateur de liaison let* :

Chaque let* x = e in suite se lit : « calcule e ; si c'est Error, renvoie-le tout de suite ; sinon nomme la valeur x et poursuis ». Le résultat est un court-circuit automatique.

Astuce — unifier le type d'erreur

let* n'enchaîne deux result que si leurs Error ont le même type. Si parse échoue avec une string et lire_fichier avec une exception, le compilateur refuse. Result.map_error convertit l'un vers l'autre : lire_fichier f |> Result.map_error Printexc.to_string ramène tout à des messages string.

Pour aller plus loin — let+ et and+

À côté de let* (le bind), OCaml réserve aussi la syntaxe let+ (un map : transformer la valeur finale sans réenchaîner) et and+ (combiner plusieurs résultats indépendants à la fois) : comme let*, ils ne sont pas fournis tout faits, c'est à toi de les définir (let ( let+ ) = Result.map). Le même mécanisme d'opérateurs de liaison sert d'ailleurs pour option et pour les promesses Lwt (leçon 12) : une fois le réflexe acquis, il se transpose partout.

Attention — result ou exception ?

OCaml a aussi les exceptions (raise, try … with). La ligne de partage : result pour les erreurs attendues et prévues par le domaine (validation d'un formulaire, analyse d'un fichier, entrée utilisateur) — elles font partie du contrat de la fonction, et le type result force l'appelant à les traiter. Les exceptions pour l'exceptionnel : bug de programmation, invariant rompu, ressource système défaillante. Le piège classique : tout passer en exceptions « parce que c'est plus court », puis oublier un try et planter en production. Avec result, l'oubli devient une erreur de compilation.

Cas réel — la programmation « sur rails »

Ce style porte un nom imagé : le « railway oriented programming ». Imagine deux rails, « succès » et « échec » : tant que tout va bien, le train roule sur le rail du succès ; à la première panne, un aiguillage le bascule sur le rail de l'échec, où il file jusqu'au bout sans repasser par les étapes suivantes. C'est exactement ce que fait let* … = …. Les grandes bases OCaml (à commencer par Jane Street, avec sa bibliothèque Core et l'extension ppx_let qui offre let%bind) reposent massivement sur ce schéma pour un traitement d'erreurs explicite, typé et sans null. La robustesse ne vient pas d'un effort de discipline : elle est inscrite dans les types.

Antisèche — result et le chaînage

Glossaire

result
Variant Ok of 'a | Error of 'b représentant un succès porteur de valeur ou un échec porteur d'information.
Ok / Error
Les deux constructeurs de result : réussite et échec.
bind
Enchaînement « si Ok x, continuer avec x ; si Error, propager ».
Opérateur de liaison (let*)
Syntaxe (OCaml 4.08+) donnant à bind l'allure d'un let.
Court-circuit
Arrêt de la chaîne dès la première Error, sans exécuter la suite.
Exception
Mécanisme d'erreur hors du type de retour (raise / try … with), pour l'exceptionnel.
Railway oriented programming
Image du chaînage result : un rail « succès » et un rail « échec ».
Result.map_error
Transforme le contenu d'un Error sans toucher au Ok ; sert à unifier deux types d'erreur pour pouvoir les enchaîner avec let*.

Récap et vérification

  • result (Ok/Error) modélise un échec avec message, là où option dit seulement l'absence.
  • Enchaîner des étapes faillibles à la main produit un escalier de match répétitif.
  • Result.bind, exposé par l'opérateur let*, aplatit le chaînage et court-circuite au premier Error.
  • result pour les erreurs attendues (le type force à les traiter) ; exceptions pour l'exceptionnel.

Vérifie ta compréhension

  1. Qu'apporte result de plus qu'option ?
  2. Que fait let* x = e in suite quand e vaut Error msg ?
  3. Dans quels cas préférer une exception à un result ?

Exercices

Exercice 1Échauffement

Écris parse_positif : string -> (int, string) result qui convertit une chaîne en entier et échoue avec un message clair si ce n'est pas un nombre ou s'il est négatif.

Voir une solution

On s'appuie sur int_of_string_opt (variante sûre qui renvoie None au lieu de lever une exception). Le when ajoute la garde « négatif ». Chaque cas d'échec fabrique un Error avec un message explicite : c'est tout l'intérêt de result sur option.

Exercice 2Application

Avec let*, enchaîne : analyser deux chaînes en entiers positifs, puis les diviser (en refusant le diviseur nul). Toute la chaîne doit renvoyer un (int, string) result.

Voir une solution

Les deux let* déballent successivement a puis b. Si parse_positif sa échoue, b n'est jamais calculé et l'erreur ressort directement : c'est le court-circuit. Le code se lit comme la version « heureuse » (parse, parse, divise), la gestion d'erreur étant prise en charge par bind en coulisses.

Exercice 3Défi

Un collègue enveloppe tout dans des exceptions « parce que c'est plus court », y compris la validation des entrées utilisateur. Explique les risques, et dis quand result est un meilleur choix — et quand l'exception reste légitime.

Voir une solution

Les risques du tout-exception : une exception est invisible dans le type de retour. Rien, à la lecture d'une signature string -> int, ne signale qu'elle peut échouer : l'appelant ne sait pas qu'il doit l'attraper. Un try … with oublié, et le programme plante en production sur une entrée pourtant banale (un champ vide, une virgule au lieu d'un point). Les erreurs deviennent aussi difficiles à composer : collecter plusieurs messages de validation force à jongler avec le flot de contrôle exceptionnel.

Où result gagne : pour toute erreur attendue et faisant partie du contrat — validation de formulaire, parsing de fichier de config, requête réseau qui peut légitimement échouer. Le type (_, string) result documente l'échec et force l'appelant à le traiter ; l'oubli devient une erreur de compilation, pas un crash à 3h du matin. En prime, let* rend le chaînage aussi lisible qu'avec des exceptions.

Où l'exception reste légitime : pour l'exceptionnel au sens propre — un invariant interne rompu (assert false), un bug de programmation, une ressource système qui lâche. Là, on veut souvent que ça remonte bruyamment plutôt que de polluer chaque signature avec un cas d'erreur qui « ne devrait jamais arriver ». Le bon découpage : erreurs de domaine → result ; défaillances imprévues → exceptions. Et si l'on interfabrique les deux mondes, le pont try Ok (f x) with e -> Error e convertit une API à exceptions en API à result.
