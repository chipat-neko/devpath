Module 5 · OCaml, encore plus loin — Leçon 14

La programmation orientée objet

~50 min Avancé Prérequis : leçon 08

À la fin de cette leçon, tu sauras

  • écrire des objets et des classes (état, méthodes) ;
  • comprendre le sous-typage structural propre à OCaml ;
  • utiliser l'héritage et self ;
  • savoir quand préférer les modules aux objets.
Sommaire de la leçon

Le nom complet d'OCaml est Objective Caml : le « O » signale un système objet à part entière. Surprise : c'est la partie du langage la moins utilisée au quotidien — les OCamliens préfèrent les modules, les variants et le pattern matching. Mais les objets d'OCaml ont une propriété rare et élégante : le sous-typage structural. Cette leçon te fait découvrir ce « O », ses forces réelles, et surtout quand le sortir de la boîte à outils.

Astuce — le dièse, pas le point

OCaml appelle une méthode avec # (objet#methode), pas avec un point comme la plupart des langages. Le point est déjà pris : il sert à l'accès aux champs de records (p.nom) et aux membres de modules (List.map). Le # évite toute ambiguïté.

Le sous-typage structural

Voici la vraie originalité d'OCaml. Dans la plupart des langages objets, un type « est un sous-type » d'un autre parce qu'on l'a déclaré (héritage nominal : class Chien extends Animal). En OCaml, le sous-typage est structural : un objet est compatible avec un type dès qu'il en possède la structure — les bonnes méthodes, avec les bons types — sans aucune déclaration de parenté.

La coercition :>

OCaml n'insère pas automatiquement les conversions de sous-typage : on les rend explicites avec l'opérateur de coercition (objet :> type). C'est un peu verbeux, mais cela garde l'inférence de types prévisible : le compilateur ne « devine » jamais un sur-type à ta place.

Attention — objet et type d'objet ne se mélangent pas au hasard

Les types d'objets peuvent devenir verbeux et les messages d'erreur impressionnants (OCaml liste toute la structure attendue). Deux objets de structures différentes ne sont pas interchangeables, même s'ils « se ressemblent ». En cas de doute, annote explicitement le type d'objet attendu : le compilateur t'aidera bien plus vite.

Objets ou modules ? Quand choisir

La question pratique. OCaml offre deux mécanismes d'abstraction : les modules/foncteurs et les objets. Le réflexe idiomatique : modules par défaut, objets quand le sous-typage structural ou le dispatch tardif rend vraiment service.

Cas réel — où les objets d'OCaml brillent

Deux mondes concrets emploient vraiment le « O ». 1) js_of_ocaml (compiler OCaml vers JavaScript, chez des entreprises comme Ahrefs) : comme les valeurs du navigateur (document, un bouton, une requête) sont des objets, les représenter par des objets OCaml au sous-typage structural tombe juste. 2) Les bibliothèques d'interface graphique comme LablGTK : un widget « bouton » partage la structure d'un widget « générique » sans qu'on doive tout déclarer. À l'inverse, une grande partie de l'écosystème (dont une bonne part de Jane Street) écrit énormément d'OCaml sans presque jamais d'objets : modules et variants suffisent. Le « O » est un outil de niche, précieux quand la niche se présente.

Antisèche — les objets d'OCaml

Glossaire

Objet
Valeur réunissant un état (champs val) et un comportement (méthodes method).
Classe
Patron décrivant l'état et les méthodes d'objets ; on l'instancie avec new.
Méthode
Fonction attachée à un objet, appelée par objet#methode.
Sous-typage structural
Compatibilité de types fondée sur la structure (les méthodes présentes), pas sur une parenté déclarée.
Type d'objet
Description d'un objet par ses méthodes, ex. < aire : float >.
Coercition (:>)
Conversion explicite d'un objet vers un sur-type structural.
Héritage (inherit)
Réutilisation de l'état et des méthodes d'une classe par une autre.
self
Référence de l'objet à lui-même, pour appeler ses propres méthodes.

Récap et vérification

  • OCaml a un vrai système objet (le « O ») : object/class, val/method, new, appel par #.
  • Sa signature : le sous-typage structural — compatible par la forme, vérifié à la compilation.
  • Les conversions de sous-typage sont explicites (:>) ; l'héritage se fait avec inherit et self.
  • Réflexe idiomatique : modules par défaut, objets pour la niche (collections hétérogènes, js_of_ocaml, GUI).

Exercices

Exercice 1Échauffement

Écris une classe pile (pile d'entiers) avec un état interne et trois méthodes : push (empiler), pop (dépiler, renvoie un int option) et taille.

Voir une solution

L'état items est un champ mutable (une liste). push ajoute en tête avec :: ; pop filtre par pattern matching et renvoie une option pour gérer proprement la pile vide (pas d'exception, pas de null — fidèle à l'esprit OCaml de la leçon 6). On appelle chaque méthode avec #.

Exercice 2Application

On veut additionner l'aire d'une liste de formes hétérogènes (des cercles et des carrés). Explique pourquoi le sous-typage structural résout élégamment ce problème, et écris le type de la liste.

Voir une solution

Le problème : une list OCaml est homogène — tous ses éléments ont le même type. Or un cercle et un carre sont deux classes différentes. Comment les mettre dans une même liste ? Le sous-typage structural donne la réponse : puisque les deux classes possèdent une méthode aire : float, elles sont toutes deux compatibles avec le type d'objet < aire : float >, « tout objet qui sait donner son aire ». Il suffit de coercer chaque élément vers ce type commun :

Pourquoi c'est élégant : on n'a eu aucune hiérarchie à déclarer d'avance (pas de classe Forme mère à faire hériter par cercle et carre). Chaque classe est écrite indépendamment ; leur point commun — « avoir une méthode aire » — suffit à les réunir, et le compilateur vérifie statiquement que c'est bien le cas. C'est exactement le genre de situation (collection hétérogène « qui sait faire X ») où l'objet bat le variant : avec un variant, ajouter une nouvelle forme obligerait à modifier tous les match existants ; ici, une nouvelle classe avec une méthode aire s'insère sans rien changer au reste.

Exercice 3Défi

Un développeur venu de Java veut tout modéliser en OCaml avec des classes et de l'héritage. Quand est-ce une bonne idée, quand vaut-il mieux l'en dissuader, et que proposer à la place ?

Voir une solution

Il faut le freiner… avec nuance. Traduire mécaniquement les réflexes objets de Java en OCaml produit souvent du code lourd, verbeux et peu idiomatique, qui passe à côté des forces du langage. Quand les objets sont justifiés : (1) une collection hétérogène d'éléments « qui savent faire X », réunis par leur structure (le cas des formes ci-dessus) ; (2) un besoin de dispatch ouvert — pouvoir ajouter de nouvelles variantes sans modifier le code existant ; (3) l'interfaçage avec un monde objet, typiquement js_of_ocaml (le DOM du navigateur) ou une bibliothèque GUI comme LablGTK. Dans ces cas, le sous-typage structural d'OCaml est même plus élégant que l'héritage nominal de Java. Quand les en dissuader : pour la majorité du code — organiser des fonctions, définir un type de données avec un nombre fixe de cas, abstraire une structure. Là, l'objet est un mauvais choix par défaut. Ce qu'on propose à la place : (a) un module pour regrouper un type et ses opérations (l'équivalent OCaml d'une « classe utilitaire » ou d'un service) ; (b) un type variant + pattern matching quand l'ensemble des cas est connu et fixe (là où Java tenterait une hiérarchie de sous-classes) ; (c) un foncteur quand il faut paramétrer un module par un autre (l'équivalent d'une forme de généricité/injection de dépendance). Le message : en OCaml, l'abstraction par défaut, ce sont les modules et les variants ; l'objet est un outil spécialisé, excellent dans sa niche, contre-productif ailleurs. Bien programmer OCaml, ce n'est pas « faire de l'objet autrement », c'est souvent ne pas en faire du tout.
