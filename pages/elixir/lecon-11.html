Module 3 · Concurrence et OTP — Leçon 11

Mix, tests et écosystème

~50 min Avancé Prérequis : leçon 10

À la fin de cette leçon, tu sauras

  • créer et structurer un projet avec mix new, gérer ses dépendances Hex et lancer ses tâches ;
  • écrire des tests avec ExUnit (assert, setup) et transformer les exemples de doc en doctests ;
  • outiller son code avec mix format, Credo et la documentation ExDoc ;
  • comprendre le rôle de Telemetry et des releases pour l'observabilité et le déploiement.
Sommaire de la leçon

Jusqu'ici, tu as lancé du code dans iex ou via de petits fichiers .exs. C'est parfait pour explorer, mais un vrai système Elixir — résilient, concurrent, déployé en production — vit dans un projet Mix. Mix, c'est l'outil tout-en-un fourni avec Elixir : il crée la structure, compile, gère les dépendances, lance les tests, formate le code et prépare le déploiement. Un seul exécutable pour toute la vie du projet.

Dans cette leçon, on construit un petit projet de bout en bout. Tu vas voir que l'écosystème Elixir est étonnamment cohérent : tout est intégré, conventionnel, et pensé pour que tu passes ton temps sur la logique métier plutôt que sur la plomberie.

Créer un projet avec mix new

Tout commence par une commande. mix new génère un squelette de projet prêt à compiler, tester et publier.

La structure standard d'un projet Elixir, créée en une commande.

Tu obtiens deux dossiers clés : lib/ contient ton code source, test/ contient tes tests. Le cœur du projet est le fichier mix.exs, le manifeste qui décrit ton application.

Tout est du code Elixir normal : project/0 renvoie une liste de mots-clés décrivant le projet. Rien de magique, juste des fonctions qui retournent des données — fidèle à l'esprit du langage.

Les dépendances et Hex

Hex est le gestionnaire de paquets de l'écosystème BEAM (partagé avec Erlang). Pour ajouter une dépendance, tu l'ajoutes dans la liste deps sous forme de tuple {:nom, "contrainte"}.

La contrainte ~> 1.4 signifie « au moins 1.4, mais strictement inférieur à 2.0 » : tu récupères les corrections de bugs sans casser la compatibilité. L'option only: [:dev, :test] limite Credo aux environnements de développement et de test — inutile de l'embarquer en production.

Mix télécharge les dépendances et écrit un fichier mix.lock qui fige les versions exactes.

Le fichier mix.lock garantit que toute ton équipe — et la CI — utilise exactement les mêmes versions. Versionne-le toujours dans Git.

Compiler et exécuter

Mix compile à la demande, mais tu peux forcer une compilation et lancer du code directement. Le squelette généré te fournit déjà une fonction hello/0 qui renvoie :world.

Mais le plus pratique au quotidien, c'est iex -S mix : il démarre une session interactive avec ton projet déjà chargé. Tu peux appeler tes propres modules, tester une fonction, inspecter un résultat.

Dans cette session, deux commandes te feront gagner un temps fou : recompile() recharge ton code après une modification sans quitter iex, et h affiche la documentation d'une fonction directement dans le terminal.

Doctests : la doc qui se teste elle-même

As-tu remarqué la ligne doctest Portefeuille ? Elle dit à ExUnit d'exécuter tous les exemples iex> écrits dans tes blocs @doc et de vérifier que la sortie réelle correspond. Tes exemples de documentation deviennent des tests gratuits.

Astuce

Le doctest garantit que ta documentation ne ment jamais : si tu changes le comportement d'une fonction sans mettre l'exemple à jour, mix test échoue. La doc reste vraie pour toujours.

Cas réel

La documentation officielle d'Elixir — et de milliers de bibliothèques publiées sur HexDocs — est truffée d'exemples iex>. Ces exemples ne sont pas décoratifs : ils tournent comme doctests dans l'intégration continue du projet. Quand tu copies un exemple depuis la doc de Enum ou de String, tu as la garantie qu'il fonctionne vraiment, parce qu'un exemple devenu faux ferait échouer la CI avant la publication. C'est l'une des raisons de l'excellente réputation de la documentation Elixir.

Quand un test a besoin d'un état de départ commun, setup prépare le terrain avant chaque test et passe les données via le contexte.

Le %{operations: ops} dans la signature du test est un pattern matching sur le contexte renvoyé par setup — tu retrouves le pipe et le filtrage par motifs partout, jusque dans les tests.

Formater, analyser, documenter

Trois outils façonnent un code propre et lisible. D'abord le formateur intégré : mix format réécrit tout ton code selon un style canonique. Fini les débats sur les espaces et l'indentation.

Ensuite Credo, l'analyseur statique qu'on a ajouté plus haut : il repère les complexités inutiles, les incohérences et les mauvaises odeurs de code.

Enfin ExDoc transforme tes @moduledoc et @doc en un site HTML élégant et navigable. C'est le même outil qui génère la documentation officielle d'Elixir. (Il s'ajoute lui aussi comme dépendance only: :dev.)

La documentation publiée sur HexDocs vient directement de tes commentaires @doc.

Observabilité et déploiement

Deux briques de l'écosystème méritent d'être connues, même si on ne fait que les survoler ici.

Telemetry est la bibliothèque standard d'instrumentation. Une fonction émet un événement (durée d'une requête, taille d'une file) et des gestionnaires s'y abonnent pour mesurer, journaliser ou exporter vers un tableau de bord. C'est le socle de l'observabilité dans tout l'écosystème (Phoenix, Ecto, Oban l'utilisent).

Pour le déploiement, Mix sait construire une release : un paquet autonome contenant ton code compilé, ses dépendances et la machine virtuelle BEAM. Tu peux le copier sur un serveur qui n'a même pas Elixir installé.

La release démarre la supervision OTP, gère l'arrêt propre et permet la mise à jour à chaud — l'aboutissement naturel des notions de concurrence et de résilience vues dans ce module.

Pièges fréquents

Piège fréquent

Les fichiers de test se nomment en .exs (script), pas .ex. Un test écrit dans un .ex serait compilé dans la release et ignoré par mix test. De même, les modules de test doivent finir par Test et le fichier par _test.exs pour être découverts automatiquement.

Autre erreur classique : oublier la ligne doctest MonModule dans le fichier de test. Sans elle, tes jolis exemples iex> ne sont jamais exécutés — ils ne servent alors que de décor. Et attention à l'indentation des exemples : un doctest exige exactement quatre espaces devant le iex> dans le bloc @doc, sinon il n'est pas reconnu.

Pour aller plus loin

Pour aller plus loin

Crée tes propres tâches Mix dans lib/mix/tasks/ : un module Mix.Tasks.MaTache avec use Mix.Task et une fonction run/1 devient appelable via mix ma_tache. Explore aussi mix test --cover pour la couverture, les tests async: true qui tournent en parallèle (la concurrence d'Elixir au service de tests rapides !), et ExUnit.CaptureLog pour vérifier les journaux.

Glossaire

Mix
Outil tout-en-un livré avec Elixir : création de projet, compilation, dépendances, tests, formatage et déploiement.
Hex
Gestionnaire de paquets de l'écosystème BEAM (partagé avec Erlang), d'où proviennent les dépendances déclarées.
mix.exs
Manifeste du projet : du code Elixir qui décrit l'application, la version requise et la liste des dépendances.
mix.lock
Fichier généré qui fige les versions exactes installées ; à versionner dans Git pour des builds reproductibles.
ExUnit
Framework de test intégré à Elixir : fournit assert, refute et setup, sans dépendance à ajouter.
doctest
Mécanisme qui exécute comme tests les exemples iex> écrits dans les @doc, garantissant une documentation exacte.
setup
Bloc exécuté avant chaque test ; il prépare un contexte commun, transmis à la fonction de test par pattern matching.
Release
Paquet autonome (mix release) réunissant code compilé, dépendances et machine virtuelle BEAM, déployable sans installer Elixir.

Récap et vérification

  • mix new crée la structure lib/, test/ et le manifeste mix.exs.
  • Les dépendances se déclarent dans deps et se récupèrent via Hex avec mix deps.get ; mix.lock fige les versions.
  • iex -S mix ouvre une session avec le projet chargé ; recompile() et h y sont précieux.
  • ExUnit (intégré) fournit assert, refute, setup et les doctests qui testent les exemples de la doc.
  • mix format, Credo et ExDoc garantissent un code propre et documenté ; Telemetry et les releases adressent l'observabilité et le déploiement.
