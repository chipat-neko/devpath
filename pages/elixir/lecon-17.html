Module 4 · Elixir : aller plus loin — Leçon 17

Projet de synthèse : un service d'inventaire

~55 min Avancé Leçon 16 requise

À la fin de cette leçon, tu sauras

  • relire tout le cours comme une pile de briques qui s'emboîtent ;
  • écrire un inventaire complet en script (listes, maps, Enum, pipe) ;
  • le transformer en service à état avec un GenServer ;
  • valider les entrées par pattern matching et gardes, renvoyer :ok/:error.
Sommaire de la leçon

Voici la dernière étape du parcours. Plutôt qu'une notion neuve, cette leçon assemble ce que tu as appris : on part d'un petit inventaire écrit en script, puis on le fait grandir en un service concurrent — un processus qui garde son état, valide ce qu'on lui envoie et répond aux messages. Chaque brique du cours y trouve sa place.

Le cours, vu comme une pile

Les seize leçons précédentes forment quatre couches qui s'empilent. Rien de magique dans une application Elixir : ce sont ces briques, mises bout à bout.

Échauffement : l'inventaire en script

On commence par le fil rouge du cours : un inventaire écrit d'une traite. Il réunit les listes et les maps, une fonction anonyme, Enum (each, map, sum), l'opérateur pipe |> et l'interpolation — un condensé d'Elixir.

Ce que tu vas construire

Une liste de produits (des maps), une fonction valeur, l'affichage de chaque ligne, puis le total calculé via un pipeline map → sum.

Étapes

Les produits

Crée une liste de maps %{nom: ..., prix: ..., quantite: ...}.

La fonction valeur

Définis une fonction anonyme valeur = fn p -> p.prix * p.quantite end.

Afficher

Parcours avec Enum.each et affiche chaque ligne avec l'interpolation "#{...}" (appel valeur.(p)).

Le total par pipeline

Enchaîne produits |> Enum.map(valeur) |> Enum.sum().

Le résultat

Affiche le total avec IO.puts.

Étape 1Fil rouge

Assemble les cinq étapes en un programme complet. Essaie d'abord par toi-même, puis compare avec la solution de référence.

Voir une solution complète

Le projet : un service d'inventaire concurrent

Le script est correct, mais il vit et meurt en une exécution. Dans une vraie application (un serveur web, un jeu, une caisse), l'inventaire doit persister entre les requêtes, être interrogé et modifié de partout, sans que deux modifications se marchent dessus. C'est exactement le rôle d'un GenServer (leçon 9) : un processus qui détient un état et le fait évoluer, un message à la fois.

Cahier des charges

  • Stocker des produits typés par une struct (leçon 13).
  • ajouter/1 valide le produit et l'ajoute ; refuse un prix ou une quantité négatifs.
  • valeur_totale/0 renvoie la somme des prix × quantite.
  • Séparer nettement l'API publique (ce que le client appelle) des callbacks (ce que le serveur exécute).

Tout le cours est là : le pattern matching distingue les messages ({:ajouter, p} vs :valeur_totale) ; les gardes (when prix >= 0) valident sans un seul if ; le pipe enchaîne le calcul du total ; le tuple :ok/:error (leçon 7) transporte l'issue ; et l'état immuable est remplacé, jamais muté — Map.put renvoie une nouvelle map que le GenServer conserve.

Cas réel : le panier d'une boutique en ligne

Sur un site de vente, chaque panier client est souvent… un GenServer. Il garde les articles en mémoire (rapide, isolé), valide les quantités à chaque ajout et survit aux requêtes HTTP successives. Quand l'utilisateur passe commande, l'état est écrit en base via un changeset Ecto (leçon 16). Un superviseur (leçon 10) redémarre le processus s'il plante — sans emporter les autres paniers. C'est le patron exact que tu viens d'écrire, à peine étoffé : state isolé, messages, validation, tolérance aux pannes.

Sépare toujours l'API des callbacks

La convention OTP est nette : le client n'appelle jamais handle_call directement, il passe par Inventaire.ajouter/1. Cette façade rend le module agréable à utiliser (des noms métier, pas de tuples de messages) et te laisse changer l'implémentation interne sans toucher au code appelant. C'est de l'encapsulation, version fonctionnelle.

Ne mets pas de calcul lourd dans le serveur

Un GenServer traite ses messages un par un : c'est ce qui protège l'état, mais aussi ce qui peut créer un goulot d'étranglement. Un handle_call qui prendrait dix secondes bloque tous les autres clients pendant ce temps. Fais le gros du travail avant l'appel (dans le client) ou délègue-le à une Task (leçon 14) ; garde les callbacks courts.

Pour aller plus loin

Trois extensions naturelles : (1) placer l'Inventaire sous un superviseur dans l'arbre OTP d'un projet Mix ; (2) remplacer la validation maison par un changeset Ecto pour des messages d'erreur riches ; (3) exposer retirer/2 et lister/0 pour un vrai CRUD. Chaque ajout réutilise une leçon du cours : c'est le signe que les fondations tiennent.

Antisèche

Glossaire

Capstone
Projet de synthèse final qui assemble les notions du cours dans une réalisation unique et cohérente.
Struct
Map à clés fixes attachée à un module (%Produit{}) ; @enforce_keys impose les champs requis.
GenServer
Processus générique qui détient un état et le fait évoluer message par message, via handle_call/handle_cast.
API publique
Fonctions du module que le client appelle (ajouter/1) ; elles masquent les messages bruts envoyés au processus.
Callback
Fonction exécutée dans le processus (init, handle_call) en réponse à un message ; renvoie le nouvel état.
État (state)
La valeur immuable conservée par le GenServer entre deux messages ; remplacée, jamais mutée.
Garde (guard)
Condition (when …) attachée à une clause de fonction, qui affine le filtrage sans if.
Immuabilité
Principe selon lequel une donnée n'est jamais modifiée sur place : on produit une nouvelle valeur (ici Map.put).

Récap et vérification

  • Une application Elixir n'est que les quatre couches du cours assemblées : bases, fonctionnel, OTP, aller plus loin.
  • Un GenServer transforme un script jetable en service à état, isolé et interrogeable par messages.
  • On sépare l'API publique des callbacks ; la validation se fait par pattern matching + gardes, l'issue par un tuple :ok/:error.
  • L'état est immuable : chaque message renvoie une nouvelle valeur que le processus conserve.

Vérifie ta compréhension

  1. Pourquoi passer par Inventaire.ajouter/1 plutôt que d'appeler handle_call ?
  2. Qu'est-ce qui empêche deux ajouter simultanés de corrompre l'état ?
  3. Où, dans le code, la garde when prix >= 0 agit-elle ?

Exercices

Exercice 1Échauffement

Ajoute une fonction publique lister/0 qui renvoie la liste des produits stockés. Indique la fonction d'API et le handle_call correspondant.

Voir une solution

Map.values/1 renvoie les structs ; l'état n'est pas modifié, on le retourne tel quel dans le tuple :reply.

Exercice 2Application

Étends valider/1 pour refuser aussi un nom vide (chaîne ""), en renvoyant {:error, :nom_manquant}.

Voir une solution

L'ordre compte : la clause du nom vide vient en premier, sinon la clause avec gardes l'attraperait d'abord. Elixir essaie les clauses de haut en bas.

Exercice 3Défi

Ajoute retirer/1 qui enlève un produit par son nom. Que se passe-t-il si le nom n'existe pas ? Choisis un comportement et justifie-le.

Voir une solution

Map.delete/2 est idempotent : retirer un nom absent renvoie simplement la même map, sans erreur. On choisit donc de toujours répondre :ok — l'appelant n'a pas à savoir si l'article existait. C'est souvent le comportement le plus simple à consommer côté client.
