Module 3 · Concurrence et OTP — Leçon 12

Vers Phoenix et le temps réel

~50 min Avancé Prérequis : leçon 11

À la fin de cette leçon, tu sauras

  • situer le rôle de Phoenix (routeur, contrôleurs, templates HEEx) dans l'écosystème Elixir ;
  • comprendre Ecto (schemas, changesets, requêtes composables) et son lien avec le |> ;
  • expliquer le principe de LiveView : un état qui vit côté serveur dans un processus, des UI temps réel sans JavaScript ;
  • savoir où Elixir brille (temps réel, messagerie, IoT, fintech) et tracer ton plan d'apprentissage pour la suite.
Sommaire de la leçon

Tu as parcouru un long chemin. Tu connais l'immutabilité, le pattern matching, le pipe |>, les processus légers, les GenServer, les superviseurs et la philosophie let it crash. Tu tiens entre les mains une boîte à outils redoutable pour bâtir des systèmes concurrents et résilients. Mais une question reste : concrètement, on construit quoi avec ça ? Cette leçon finale ouvre les portes. Elle survole l'écosystème vers lequel mène naturellement Elixir, avec en figure de proue Phoenix, le framework web, et son joyau : LiveView.

Considère cette leçon comme une carte, pas comme un manuel exhaustif. Le but n'est pas que tu saches coder une application Phoenix complète à la fin — c'est l'affaire d'un cours entier — mais que tu comprennes pourquoi ces outils existent, comment ils s'appuient sur tout ce que tu as appris, et où ils brillent. Tu repartiras avec un plan d'apprentissage clair.

Phoenix, le framework web

Phoenix est à Elixir ce que Rails est à Ruby ou Django à Python : le framework web de référence. Sauf qu'il tourne sur la BEAM, la machine virtuelle Erlang. Résultat : il encaisse des dizaines de milliers de connexions simultanées sur une seule machine, chaque requête étant traitée dans son propre processus léger, isolé des autres. Si une requête plante, les autres ne s'en aperçoivent même pas — c'est le let it crash appliqué au web.

Phoenix suit le patron MVC (Modèle-Vue-Contrôleur), que tu as peut-être déjà croisé ailleurs : le routeur aiguille une URL vers une fonction, le contrôleur orchestre la logique, la vue/template produit le HTML. Tu crées un projet en une commande.

Génération et lancement d'une application Phoenix. mix est l'outil de build d'Elixir, déjà ton compagnon depuis le module 2.

Le routeur

Le routeur déclare quelle URL mène à quel contrôleur. C'est un simple module Elixir, lisible comme une table des matières du site. Remarque que ce n'est rien d'autre que des appels de macros — du code Elixir ordinaire.

Le routeur lie une méthode HTTP + un chemin à une fonction du contrôleur.

Contrôleurs et templates HEEx

Un contrôleur reçoit la requête (la conn, pour connection) et les paramètres, prépare des données, puis rend un template. Tout repose, encore une fois, sur le pattern matching et l'immutabilité : la conn est une structure que chaque fonction transforme et renvoie, souvent au fil d'un pipe.

Le pattern matching extrait id directement dans la signature de la fonction.

Le template, lui, est écrit en HEEx (HTML+EEx) : du HTML auquel on injecte de l'Elixir avec {...} pour les valeurs et <%= ... %> pour les blocs. HEEx vérifie ton HTML à la compilation — une balise mal fermée devient une erreur de compilation, pas un bug en production.

@produit est la donnée passée par le contrôleur. La condition @produit.stock > 0 s'écrit dans un bloc <%= ... %>.

Ecto, la couche base de données

La plupart des applications parlent à une base de données. En Elixir, c'est le rôle d'Ecto. Ecto repose sur trois piliers qui mettent en valeur tout ce que tu as appris : les schemas (la forme des données), les changesets (la validation et le filtrage des modifications) et les requêtes composables (construites au pipe).

Le changeset est un pipe : chaque étape ajoute une validation. Pur Elixir idiomatique.

Les requêtes aussi se composent au pipe. Tu construis un morceau de requête, tu le passes à la fonction suivante qui en ajoute un autre — et rien n'est exécuté tant que tu n'appelles pas le Repo.

Une requête est une donnée que tu construis progressivement, puis que Repo.all/1 exécute.

Note

Le fait qu'une requête Ecto soit une simple donnée que l'on transforme au pipe n'est pas un hasard : c'est l'immutabilité et la composition de fonctions, vues dès le module 1, appliquées au monde des bases de données.

LiveView, le temps réel sans JavaScript

Voici le joyau de l'écosystème. Avec Phoenix LiveView, tu construis des interfaces interactives temps réel — compteurs, formulaires validés en direct, tableaux de bord, jeux — sans écrire une ligne de JavaScript. Comment ? L'idée est lumineuse une fois qu'on la saisit.

Chaque page LiveView ouverte par un utilisateur est un processus Elixir vivant côté serveur (oui, exactement le processus léger du module 3 !). Ce processus détient l'état de la page (les assigns). Quand l'utilisateur clique, le navigateur envoie un petit message via WebSocket ; le processus met à jour son état ; Phoenix calcule uniquement le diff HTML qui a changé et l'envoie au navigateur, qui l'applique. L'utilisateur a l'impression d'une SPA réactive ; toi, tu n'as écrit que de l'Elixir.

Comme un GenServer du module 3 : un état (assigns), des messages (handle_event), une réponse. Le HTML se met à jour tout seul. &(&1 + 1) est la fonction anonyme courte qui incrémente.

Si tu trouves que mount, render et handle_event ressemblent furieusement à init, l'état et handle_call d'un GenServer, c'est parfaitement normal : LiveView est un processus à état qui répond à des messages. Tu connais déjà le concept.

Channels et PubSub

Pour le temps réel multi-utilisateur — un chat, des notifications, un flux d'événements — Phoenix offre les channels (des WebSockets organisés par sujet) et le PubSub (publish/subscribe). Le principe : un processus publie un message sur un sujet, et tous les processus abonnés à ce sujet le reçoivent — qu'ils soient sur la même machine ou répartis sur un cluster.

Diffusion d'un message à tous les abonnés d'un sujet. La réception passe par handle_info/2, vu avec les processus.

Couplés à LiveView, channels et PubSub rendent le temps réel collaboratif presque trivial : un utilisateur envoie un message, le serveur le diffuse, et les pages LiveView de tous les autres se mettent à jour instantanément.

Où Elixir brille (et qui l'utilise)

Elixir et la BEAM excellent partout où il faut gérer énormément de connexions simultanées et persistantes, du temps réel et de la résilience : messagerie, chat, notifications push, jeux en ligne, IoT (des millions de capteurs connectés), fintech (transactions concurrentes fiables), streaming, télécoms. Erlang, l'ancêtre, a été créé chez Ericsson pour les centraux téléphoniques : neuf 9 de disponibilité, soit quelques secondes d'arrêt par an.

Côté noms : Discord gère des millions d'utilisateurs simultanés sur Elixir ; WhatsApp a longtemps tourné sur Erlang avec une poignée d'ingénieurs pour des centaines de millions d'utilisateurs ; Pinterest, Heroku et de nombreuses fintechs ou plateformes IoT s'appuient sur l'écosystème. Le marché de l'emploi est de niche mais bien payé et fidèle : la communauté est petite, soudée, et les développeurs Elixir sont recherchés là où la fiabilité temps réel n'est pas négociable.

Cas réel

En 2017, Discord a raconté comment il a fait tenir 5 millions d'utilisateurs simultanés sur Elixir. L'idée est exactement celle de ce cours : chaque salon est un processus, et la présence en direct (« qui est en ligne ») s'appuie sur PubSub réparti sur un cluster de nœuds BEAM interconnectés. Là où le même problème aurait exigé ailleurs une armada de serveurs et de caches, une petite équipe l'a tenu grâce au modèle acteur. À l'autre bout du spectre, WhatsApp servait environ 450 millions d'utilisateurs avec une cinquantaine d'ingénieurs sur Erlang — le cousin d'Elixir sur la même BEAM.

Pièges fréquents

Piège fréquent

Croire que LiveView envoie « toute la page » à chaque clic. Non : Phoenix calcule un diff minimal et n'envoie que ce qui change réellement, ce qui rend la chose étonnamment légère sur le réseau. L'état, lui, reste côté serveur dans le processus.

Piège fréquent

Vouloir mettre toute ta logique métier dans le contrôleur ou la LiveView. Idiomatiquement, Phoenix te pousse à isoler la logique dans des contextes (des modules métier comme Catalogue ou Comptes). Le web n'est qu'une porte d'entrée vers ton cœur applicatif.

Pour aller plus loin

Pour aller plus loin

La meilleure prochaine étape est le tutoriel officiel Phoenix (hexdocs.pm/phoenix) et le livre Programming Phoenix LiveView. Construis un petit projet : un blog, un chat, ou un compteur partagé en temps réel. Tu verras alors tout l'écosystème — processus, supervision, pipe, pattern matching — converger dans une vraie application.

Glossaire

Phoenix
Framework web de référence d'Elixir, tournant sur la BEAM ; encaisse des dizaines de milliers de connexions simultanées.
BEAM
Machine virtuelle d'Erlang sur laquelle s'exécute Elixir ; elle apporte processus légers, isolation et tolérance aux pannes.
HEEx
Langage de templates de Phoenix (HTML+EEx) : du HTML vérifié à la compilation où l'on injecte de l'Elixir avec {…}.
Ecto
Couche d'accès aux bases de données : schemas (forme des données), changesets (validation) et requêtes composables au pipe.
changeset
Pipeline de validation et de filtrage des modifications avant écriture en base : cast puis des validate_*.
Repo
Point d'entrée qui exécute réellement les requêtes Ecto contre la base (Repo.all/1, Repo.insert/1…).
LiveView
UI temps réel sans JavaScript : l'état vit dans un processus serveur (les assigns) et seul le diff HTML est envoyé au navigateur.
PubSub
Mécanisme publish/subscribe : un processus publie sur un sujet, tous les abonnés le reçoivent — même sur un cluster.

Récap et vérification

Tu refermes le cours « Elixir : la concurrence sereine ». Reprenons le fil depuis le début : tu es parti des valeurs immuables et du pattern matching (module 1), tu as enchaîné les transformations avec le pipe |>, tu as modélisé tes données avec les structs et tu as apprivoisé l'erreur explicite ({:ok, _} / {:error, _}, module 2). Puis tu as découvert le cœur d'Elixir : les processus légers, les GenServer, les superviseurs et le let it crash (module 3). Cette dernière leçon t'a montré où tout cela mène en pratique.

  • Phoenix est le framework web d'Elixir : routeur, contrôleurs, templates HEEx vérifiés à la compilation, le tout sur la BEAM.
  • Ecto gère la base de données avec schemas, changesets et requêtes composables — toujours au pipe.
  • LiveView offre des UI temps réel sans JavaScript : l'état vit dans un processus côté serveur, seul le diff HTML est envoyé.
  • Channels et PubSub portent le temps réel multi-utilisateur (chat, notifications).
  • Elixir brille en temps réel, messagerie, IoT et fintech — Discord et WhatsApp en sont les vitrines.

Vérifie ta compréhension

  1. Dans le patron MVC de Phoenix, quel composant aiguille une URL vers une fonction, et lequel produit le HTML ?
  2. Pourquoi dit-on qu'une requête Ecto est « composable », et quel opérateur incarne cette composition ?
  3. En une phrase : où vit l'état d'une page LiveView, et qu'est-ce qui est envoyé au navigateur à chaque interaction ?
