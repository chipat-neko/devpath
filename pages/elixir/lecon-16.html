Module 4 · Elixir : aller plus loin — Leçon 16

Ecto : penser ses données

~50 min Avancé Leçon 15 requise

À la fin de cette leçon, tu sauras

  • situer les quatre briques d'Ecto : Repo, Schema, Changeset, Query ;
  • déclarer un schéma qui relie une table à une struct ;
  • caster et valider des données avec un changeset ;
  • écrire une requête composable et sûre.
Sommaire de la leçon

Une application finit toujours par persister des données et par recevoir des entrées non fiables (un formulaire web, une API). Dans l'écosystème Elixir, l'outil de référence est Ecto. Attention : ce n'est pas un ORM à la Active Record. Ecto reste fidèle à l'esprit fonctionnel — des données qu'on transforme par des fonctions, avec une frontière nette entre le calcul pur et l'effet de bord (la base). Cette leçon est conceptuelle : on lit du code Ecto pour en comprendre la structure, sans base à brancher.

Les quatre briques d'Ecto

Ecto se comprend comme quatre responsabilités distinctes :

  • Repo — le portail unique vers la base : toute lecture/écriture passe par lui (Repo.insert, Repo.all). C'est là, et seulement là, que vivent les effets de bord.
  • Schema — le pont entre une table et une struct Elixir (leçon 13).
  • Changeset — le cœur d'Ecto : il caste, valide et accumule les erreurs sur des données brutes.
  • Query — un langage de requêtes composable et sûr, compilé vers du SQL.

Le schéma : d'une table à une struct

Un schéma décrit les colonnes d'une table et génère la struct correspondante :

use Ecto.Schema — souviens-toi de la leçon 15 : use injecte des macros. schema … do field … end est un petit DSL qui, à la compilation, fabrique la struct %Utilisateur{} et déclare le type de chaque champ. timestamps() ajoute inserted_at et updated_at automatiquement.

Le changeset : caster et valider

Les données qui arrivent du web sont des maps de chaînes, potentiellement incomplètes ou malveillantes. Un changeset les fait passer par un pipeline : cast ne garde que les champs autorisés (et les convertit au bon type), puis les fonctions validate_* vérifient les règles en accumulant les erreurs — sans jamais lever d'exception.

Note que "30" (chaîne) devient 30 (entier) : c'est cast qui convertit selon le type déclaré dans le schéma. Le changeset renvoyé porte valid? et la liste des errors. Rien n'est écrit en base tant que tu n'appelles pas le Repo.

Cas réel : un formulaire d'inscription

Un visiteur remplit « email + mot de passe ». Le contrôleur construit un changeset à partir des params. Si valid? est faux (email vide, mot de passe trop court), Phoenix réaffiche le même formulaire en surlignant les champs fautifs — car le changeset porte déjà les messages d'erreur, champ par champ. S'il est valide, Repo.insert(changeset) crée le compte. Le même objet sert à valider et à piloter l'affichage des erreurs : c'est ce qui rend les formulaires Elixir aussi robustes, sans code de validation dupliqué entre le client et le serveur.

Les requêtes : composables et sûres

Ecto fournit un langage de requêtes qui ressemble au SQL mais reste de l'Elixir vérifié à la compilation :

Chaque where affine la requête sans muter la précédente : on compose. Surtout, les valeurs sont toujours paramétrées : Ecto ne concatène jamais tes données dans le SQL, ce qui neutralise par construction les injections SQL. La requête n'est qu'une description tant que le Repo ne l'exécute pas.

Ecto n'est pas un ORM

Pas de « magie » cachée : rien ne part en base tant que tu n'appelles pas explicitement le Repo, et les associations ne se chargent pas toutes seules. Pour obtenir les articles d'un utilisateur, tu écris Repo.preload(user, :articles) — le chargement est explicite. Cette absence de lazy loading évite les fameuses requêtes N+1 surprises : en Ecto, ce qui touche la base est toujours visible dans le code.

Valider sans base de données

Comme un changeset est une valeur pure, tu peux tester toute ta logique de validation sans démarrer de base : assert %Ecto.Changeset{valid?: false} = Utilisateur.changeset(%Utilisateur{}, %{}). Les tests des règles métier sont ainsi rapides et isolés ; on réserve la base aux quelques tests qui vérifient réellement l'écriture. C'est un des grands conforts de la séparation pur/effet.

Pour aller plus loin

Les migrations (mix ecto.gen.migration) versionnent le schéma de la base. Ecto.Multi regroupe plusieurs opérations dans une transaction tout-ou-rien. Les embedded schemas et Ecto.Changeset s'utilisent même sans base — par exemple pour valider un formulaire de contact ou une requête d'API. Enfin, les associations (has_many, belongs_to) et Repo.preload modélisent les relations entre schémas.

Antisèche

Glossaire

Ecto
Boîte à outils de données d'Elixir : schémas, changesets, requêtes et accès à la base, dans un style fonctionnel.
Repo
Portail unique vers la base ; seul endroit où se produisent les effets de bord (insert, all, …).
Schema
Description d'une table qui génère une struct et déclare le type de chaque champ.
Changeset
Valeur qui caste, valide et accumule les erreurs sur des données brutes ; porte valid? et errors.
cast
Ne garde que les champs autorisés d'une map de paramètres et les convertit au type déclaré.
Validation
Règles (validate_required, validate_format, …) qui ajoutent des erreurs au changeset sans lever d'exception.
Query
Description composable d'une requête, paramétrée (donc protégée des injections SQL), exécutée par le Repo.
Migration
Script versionné qui fait évoluer le schéma de la base (créer une table, ajouter une colonne).

Récap et vérification

  • Ecto s'articule en quatre briques : Repo (effet de bord), Schema, Changeset, Query (pures).
  • Le schéma relie une table à une struct ; le changeset caste, valide et porte les erreurs.
  • Les requêtes sont composables et paramétrées : sûres contre l'injection SQL ; rien ne s'exécute avant le Repo.
  • Ecto n'est pas un ORM : pas de chargement implicite, la logique de données reste pure et testable.

Vérifie ta compréhension

  1. Quel est le seul composant d'Ecto qui touche la base ?
  2. Que fait cast avec %{"age" => "25"} ?
  3. Pourquoi les requêtes Ecto résistent-elles aux injections SQL ?

Exercices

Exercice 1Échauffement

Déclare un schéma Article pour la table "articles" avec un champ titre (chaîne) et un champ vues (entier).

Voir une solution

use Ecto.Schema apporte le DSL ; chaque field déclare une colonne et son type. timestamps() ajoute la date de création et de mise à jour.

Exercice 2Application

Écris une fonction changeset/2 pour Article qui accepte titre et vues, rend titre obligatoire, et exige vues ≥ 0.

Voir une solution

Le pipe enchaîne cast (filtre + convertit) puis les validations. Chaque erreur s'accumule ; le changeset final porte valid? et la liste des errors.

Exercice 3Défi

Écris une requête qui renvoie les titres des articles ayant plus de 100 vues, puis explique où et quand elle touche la base.

Voir une solution

La requete n'est qu'une donnée décrivant l'intention : on peut la composer, la passer à des fonctions, la logger. Elle ne déclenche aucun SQL tant que Repo.all ne l'exécute pas — la frontière pur/effet, encore.
