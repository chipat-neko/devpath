Module 02 · POO et RAII — Leçon 06

Héritage et polymorphisme

~35 min Avancé Leçon 5 recommandée

À la fin de cette leçon, tu sauras

  • savoir spécialiser une classe par héritage public et appeler des membres hérités ;
  • savoir déclarer des méthodes virtual, les redéfinir avec override et exploiter la liaison dynamique ;
  • savoir manipuler des objets de façon polymorphe via une classe abstraite et un std::unique_ptr de base ;
  • savoir éviter les pièges du destructeur non virtuel et du slicing.
Sommaire de la leçon

Jusqu'ici, tu as construit des classes isolées, chacune gardant ses invariants grâce au RAII. L'étape suivante consiste à relier des classes entre elles : un Cercle et un Carre sont tous deux des Forme, et tu aimerais les traiter uniformément (calculer leur aire, les dessiner) sans connaître leur type exact. C'est le rôle de l'héritage et du polymorphisme.

Dans cette leçon, tu vas voir comment dériver une classe, comment la liaison dynamique choisit la bonne méthode à l'exécution, comment définir une interface abstraite, et surtout quels pièges (destructeur non virtuel, slicing) transforment un programme correct en fuite mémoire ou en comportement indéfini.

L'héritage public

Écrire class Chien : public Animal signifie « un Chien est un Animal ». La classe dérivée hérite des membres public et protected de la base, mais pas l'accès à ses membres private (elle ne peut pas y toucher directement). Tu utilises protected précisément pour exposer un membre aux dérivés sans l'ouvrir au monde extérieur.

Le constructeur du dérivé doit initialiser sa base via la liste d'initialisation (: Animal(std::move(n))) : la partie « Animal » de l'objet existe avant que le corps de Chien ne s'exécute.

Note

L'héritage private et protected existe mais reste rare. Réserve public à la relation « est-un ». Si tu veux seulement réutiliser du code, préfère la composition (un membre) à l'héritage.

Fonctions virtuelles et liaison dynamique

Par défaut, l'appel d'une méthode est résolu selon le type statique (celui écrit dans le code). Pour qu'il dépende du type réel de l'objet, déclare la méthode virtual dans la base et redéfinis-la avec override dans le dérivé. Le compilateur installe alors une table de pointeurs de fonctions (la vtable) et choisit la bonne implémentation à l'exécution : c'est la liaison dynamique.

Sans virtual, f.aire() appellerait Forme::aire() et afficherait 0, car f a pour type statique const Forme&. C'est la distinction clé entre liaison statique et dynamique.

Le polymorphisme en pratique

Le polymorphisme, c'est manipuler un Forme& ou un pointeur de base qui « pointe vers » un dérivé. La même ligne de code produit un comportement différent selon le type réel. En C++ moderne, on stocke ces objets via des smart pointers (std::unique_ptr<Forme>) plutôt que des pointeurs nus.

Le conteneur ne connaît que des Forme, pourtant chaque f->aire() route vers la bonne implémentation. Lorsqu'un unique_ptr est détruit (fin de portée du vecteur), il appelle delete sur le pointeur de base — d'où l'importance du destructeur virtuel.

Classes abstraites et interfaces

Une fonction virtuelle pure (= 0) n'a pas d'implémentation imposée et rend la classe abstraite : on ne peut plus l'instancier, seulement en dériver. Une classe composée uniquement de méthodes virtuelles pures forme une interface : un contrat que les dérivés doivent honorer.

Astuce

Nomme tes interfaces par une capacité plutôt que par un objet : Dessinable, Comparable, Serializable. Le code client dépend alors d'un comportement, pas d'une implémentation concrète.

Le destructeur virtuel

Voici la règle la plus importante de cette leçon : si une classe a au moins une méthode virtuelle (donc destinée à être une base polymorphe), son destructeur doit être virtual. Sinon, détruire un dérivé via un pointeur de base est un comportement indéfini : en pratique, seul le destructeur de la base s'exécute et la partie dérivée n'est jamais libérée — une fuite.

Ajoute virtual ~Base() = default; et la sortie devient ~Derive puis ~Base, dans le bon ordre. Toutes les classes de base de cette leçon le déclarent déjà.

Cas réel

Toutes les bibliothèques d'interface graphique en C++ (Qt, wxWidgets…) reposent sur cette leçon. Un QWidget est une base polymorphe : un bouton, une case à cocher, un curseur en dérivent et redéfinissent paintEvent() avec override. La boucle de rendu parcourt un std::vector de pointeurs de base et appelle la méthode de dessin sur chacun ; la liaison dynamique route vers le bon rendu sans que la boucle connaisse le type concret. Et si le destructeur de QWidget n'était pas virtual, détruire un bouton via un QWidget* ne libérerait jamais ses ressources propres (icône, libellé) : exactement la fuite décrite ci-dessus. C'est pourquoi toute classe de base destinée à être dérivée déclare un destructeur virtuel.

override et final

override ne change pas le comportement, mais demande au compilateur de vérifier que la méthode redéfinit bien une virtuelle de la base. Une signature qui diffère (un const oublié, un mauvais type) déclenche alors une erreur au lieu de créer silencieusement une méthode indépendante. final interdit toute redéfinition ultérieure (ou empêche d'hériter d'une classe).

Le slicing (découpage)

Le polymorphisme exige une indirection (référence ou pointeur). Si tu copies un dérivé par valeur dans une variable de type base, seule la partie « base » est copiée : le dérivé est tronqué. C'est le slicing, une source d'erreurs discrètes.

Retiens la règle : on manipule les hiérarchies polymorphes par référence ou par unique_ptr, jamais par valeur. Passer un Forme par valeur en paramètre découpe l'argument de la même manière.

Pièges fréquents

Piège fréquent

Oublier virtual. Sans elle, aucune liaison dynamique : un Forme& appelle toujours la version de la base. Le programme compile, mais le polymorphisme ne fonctionne pas.

Piège fréquent

Destructeur non virtuel sur une base polymorphe : delete via un pointeur de base est un comportement indéfini (le dérivé n'est pas détruit, fuite). Slicing : copier un dérivé par valeur dans une base le tronque. Override manquant : une faute de signature crée une méthode parallèle au lieu de redéfinir, sans avertissement.

Piège fréquent

Hériter par réflexe. L'héritage couple fortement dérivé et base. Si la relation n'est pas un « est-un » durable, préfère la composition. « Hériter pour réutiliser du code » est presque toujours un mauvais signe.

Pour aller plus loin

L'héritage multiple et les bases virtuelles (pour résoudre le « diamant ») ; les interfaces pures à la place de l'héritage d'implémentation ; le pattern Strategy, qui injecte un comportement via une interface plutôt que par dérivation ; et std::variant + std::visit, une alternative fermée et sans vtable au polymorphisme quand l'ensemble des types est connu à la compilation.

Glossaire

Héritage public
Relation « est-un » : le dérivé réutilise les membres public et protected de la base et peut en ajouter.
Fonction virtuelle
Méthode déclarée virtual : son appel est résolu selon le type réel de l'objet (liaison dynamique).
Liaison dynamique
Choix de l'implémentation à l'exécution, via la vtable, d'après le type concret ; par opposition à la liaison statique (au type écrit).
vtable
Table de pointeurs de fonctions installée par le compilateur pour router chaque appel virtuel vers la bonne redéfinition.
Classe abstraite
Classe possédant au moins une fonction virtuelle pure (= 0) : non instanciable, seulement dérivable.
override / final
override fait vérifier qu'on redéfinit bien une virtuelle ; final interdit toute redéfinition ou dérivation ultérieure.
Destructeur virtuel
Destructeur virtual d'une base polymorphe ; sans lui, détruire un dérivé via un pointeur de base est un comportement indéfini (fuite).
Slicing
Découpe d'un objet dérivé copié par valeur dans une base : seule la partie base subsiste, le polymorphisme est perdu.

Récap et vérification

  • class D : public B exprime « D est un B » ; le dérivé hérite des membres public/protected.
  • virtual + override activent la liaison dynamique : la méthode dépend du type réel via la vtable.
  • Une virtuelle pure (= 0) rend la classe abstraite et définit une interface.
  • Une base polymorphe doit avoir un destructeur virtuel.
  • On manipule les hiérarchies par référence ou unique_ptr ; copier par valeur provoque le slicing.

Vérifie ta compréhension

  1. Pourquoi f.aire() sur une const Forme& peut-il appeler Cercle::aire() alors que le type écrit est Forme ?
  2. Que se passe-t-il exactement si tu détruis un Derive via un unique_ptr<Base> dont Base n'a pas de destructeur virtuel ?
  3. Pourquoi Forme f = unCercle; affiche-t-il une aire de 0 ? Comment l'éviter ?
