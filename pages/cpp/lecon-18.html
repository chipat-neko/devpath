Tester en C++ : assertions et Catch2

~37 min Intermédiaire Bases de C++ requises

À la fin de cette leçon, tu sauras

  • utiliser assert() pour les invariants et comprendre ses limites ;
  • écrire des tests avec Catch2 (TEST_CASE, REQUIRE) ;
  • vérifier une exception et factoriser avec les SECTION ;
  • brancher les tests sur CMake/CTest.
Sommaire de la leçon

Le C++ te donne un contrôle total sur la machine — et donc mille façons de te tromper : dépassement de tableau, pointeur invalide, logique subtile. Le compilateur en attrape une partie ; les tests automatisés attrapent le reste. Contrairement à Rust ou Java, le C++ n'a pas de framework de test dans sa bibliothèque standard : on part d'assert() pour les invariants, puis on adopte un framework. Catch2, distribué en un seul en-tête, est l'un des plus simples et des plus répandus.

assert() : le garde-fou minimal

La macro assert() de <cassert> vérifie une condition à l'exécution : si elle est fausse, le programme s'arrête en affichant le fichier et la ligne. C'est l'outil des invariants — des choses qui doivent toujours être vraies.

Deux limites importantes : assert() est désactivé en compilation optimisée (si la macro NDEBUG est définie, l'assertion disparaît), et il arrête tout au premier échec. Parfait pour documenter un invariant pendant le développement ; insuffisant pour une suite de tests qui doit tous les exécuter et faire un rapport.

Catch2 : le premier test

Avec Catch2, un test est un bloc TEST_CASE et une vérification s'écrit REQUIRE. Pas de main à écrire : le framework le fournit.

On compile en liant Catch2, puis on lance l'exécutable : il affiche All tests passed (1 assertion in 1 test case). La grande force de Catch2 : en cas d'échec, il décompose l'expression et montre les valeurs réelles — REQUIRE( calc.additionner(2, 3) == 5 ) affiche with expansion: 4 == 5. Tu vois l'écart sans message à écrire.

REQUIRE et CHECK

Catch2 propose deux niveaux d'assertion. REQUIRE arrête le test en cours s'il échoue (la suite n'a plus de sens) ; CHECK signale l'échec mais continue, pour rapporter plusieurs problèmes d'un coup.

Règle simple : CHECK pour des vérifications indépendantes qu'on veut toutes voir ; REQUIRE quand la suite du test dépend de la condition (un pointeur non nul avant de le déréférencer, par exemple).

Vérifier une exception

Quand une fonction doit lever une exception sur une entrée invalide, on le teste avec REQUIRE_THROWS_AS, qui vérifie le type levé.

Si diviser(10, 0) ne lève rien — ou lève un autre type — le test échoue. Tester les chemins d'erreur est aussi important que tester les cas nominaux : un code robuste échoue proprement.

Les SECTION : préparation partagée sans duplication

Plutôt qu'un setUp global, Catch2 utilise les SECTION : le code avant les sections est réexécuté pour chaque section, garantissant un état neuf, sans duplication.

Chaque SECTION repart d'une pile fraîche à deux éléments : les sections sont indépendantes, exactement comme le @BeforeEach des autres langages, mais l'état partagé est écrit une seule fois.

Brancher sur CMake/CTest

En projet, on récupère Catch2 via le gestionnaire de paquets (vcpkg, Conan) ou FetchContent de CMake, puis on enregistre l'exécutable de test avec add_test(...) (ou catch_discover_tests). La commande ctest lance alors toute la suite et fait le rapport — c'est ce que rejoue ta chaîne d'intégration continue à chaque commit.

Cas réel — SQLite

SQLite, la base de données embarquée la plus déployée au monde (dans ton navigateur, ton téléphone, des avions), revendique un ratio d'environ 600 fois plus de code de test que de code source : des millions de lignes de tests, une couverture à 100 % des branches, plus du fuzzing continu. C'est ce filet de sécurité colossal qui autorise ses mainteneurs à refactorer sans crainte un logiciel critique. La morale : la confiance dans un code n'est pas une impression, c'est une suite de tests qu'on relance à chaque changement.

Pour aller plus loin

Pour aller plus loin

GoogleTest (gtest) est l'autre grand framework, avec GoogleMock pour simuler des dépendances. Pour la qualité : les sanitizers (-fsanitize=address,undefined) débusquent les bugs mémoire pendant les tests, la couverture se mesure avec gcov/llvm-cov, et le fuzzing (libFuzzer) génère des entrées hostiles automatiquement. Des tests rapides + sanitizers, c'est le filet de sécurité standard du C++ moderne.

Antisèche

Glossaire

Invariant
Condition qui doit toujours être vraie en un point du code ; documentée par assert() pendant le développement.
assert()
Macro de <cassert> qui stoppe le programme si sa condition est fausse ; désactivée quand NDEBUG est défini (build optimisé).
NDEBUG
Macro qui, définie, retire toutes les assert() ; c'est pourquoi une assertion ne remplace pas un test.
TEST_CASE
Bloc de test Catch2 ; le framework fournit le main et agrège les résultats de tous les cas.
REQUIRE / CHECK
REQUIRE arrête le test au premier échec (assertion fatale) ; CHECK signale mais poursuit (non fatale), pour relever plusieurs problèmes.
SECTION
Variante d'un test qui rejoue le code de mise en place commun ; chaque section part d'un état neuf, comme un @BeforeEach sans duplication.
Test de non-régression
Test ajouté après un bug pour garantir qu'il ne réapparaîtra pas ; conservé dans la suite et rejoué en continu.
CTest
Lanceur de tests de CMake : ctest exécute toute la suite enregistrée et produit le rapport, typiquement en intégration continue.

Récap et vérification

  • assert() documente un invariant mais s'arrête au premier échec et disparaît avec NDEBUG.
  • Catch2 : TEST_CASE + REQUIRE ; l'expression échouée affiche les valeurs réelles.
  • REQUIRE arrête le test ; CHECK signale et continue.
  • REQUIRE_THROWS_AS / REQUIRE_NOTHROW testent les chemins d'erreur.
  • Les SECTION rejouent la préparation pour chaque cas : tests indépendants ; ctest lance la suite.

Vérifie ta compréhension

  1. Cite deux limites d'assert() par rapport à un framework de test.
  2. Quelle différence entre REQUIRE et CHECK ?
  3. Comment les SECTION garantissent-elles l'indépendance des tests ?

Exercice 3Défi

Avec des SECTION, teste un std::vector<int> initialisé à {1, 2, 3} : une section vérifie qu'après push_back(4) la taille vaut 4, une autre qu'après clear() il est vide — chaque section partant du vecteur d'origine.

Voir une solution

Le vecteur {1, 2, 3} est reconstruit avant chaque section : la seconde ne voit pas le push_back de la première. C'est l'indépendance garantie par Catch2.
