Module 04 · C++ moderne — Leçon 14

Organiser un projet et aller plus loin

~33 min Avancé Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • séparer une classe en interface .hpp et implémentation .cpp avec #pragma once ;
  • écrire un CMakeLists.txt minimal et comprendre la place des gestionnaires de dépendances ;
  • mettre en place un test automatisé et appliquer les bonnes pratiques modernes (RAII, règle de zéro, const par défaut) ;
  • situer l'écosystème C++ (Boost, Qt, concurrence) pour choisir où aller ensuite.
Sommaire de la leçon

Tu sais désormais écrire des classes, gérer la mémoire avec des smart pointers, manipuler la STL et exploiter le déplacement. Il manque une dernière pièce, et non la moindre : passer d'un fichier main.cpp qui grossit à un vrai projet organisé, compilable d'une commande, testé et maintenable. C'est ce qui distingue un exercice d'un logiciel.

Cette leçon clôt le parcours. On va voir comment découper le code en en-têtes et implémentations, comment CMake orchestre la compilation, comment écrire des tests, quelles bonnes pratiques tenir, et où s'ouvre l'écosystème C++ une fois ces bases acquises. Le code de cette leçon se compile avec g++ ou clang++ et s'exécute en natif : garde un terminal ouvert à côté pour le reproduire.

Découper : en-têtes et implémentation

En C++, on sépare l'interface (ce qu'une classe offre) de l'implémentation (comment elle le fait). L'interface va dans un fichier .hpp, l'implémentation dans un .cpp. Chaque .cpp se compile indépendamment en un fichier objet, puis l'éditeur de liens assemble le tout. Avantage : modifier un seul .cpp ne recompile que lui, pas tout le projet.

Note

#pragma once évite qu'un en-tête inclus deux fois (directement et via un autre en-tête) ne déclare la classe en double. C'est l'équivalent moderne et concis des anciennes gardes #ifndef / #define / #endif, supporté par tous les compilateurs courants.

CMake : construire le projet

Compiler à la main avec g++ a.cpp b.cpp -o prog devient vite ingérable. CMake est l'outil de build de référence : tu décris ton projet dans un CMakeLists.txt, et CMake génère les commandes adaptées à ta plateforme (Makefiles, Ninja, projets Visual Studio…).

Pour les dépendances externes, ne copie pas les sources à la main : utilise un gestionnaire. vcpkg (Microsoft) et Conan téléchargent, compilent et exposent les bibliothèques à CMake. Tu déclares fmt ou boost, l'outil s'occupe du reste, de façon reproductible d'une machine à l'autre.

Les modules C++20 (survol)

Les modules sont l'alternative moderne aux en-têtes. Au lieu d'inclure du texte avec #include (recopié à chaque fois, lent à compiler), un module est compilé une fois et importé. Cela réduit les temps de compilation et supprime les fuites de macros entre fichiers.

Note

Le support des modules par les compilateurs et CMake progresse mais reste inégal en 2026. Pour un projet réel aujourd'hui, le couple .hpp/.cpp demeure le choix sûr ; garde les modules en tête pour les nouveaux projets ciblant des outils récents.

Les bonnes pratiques modernes

Le C++ moderne tient en quelques principes. Les respecter te fait écrire du code sûr et lisible :

  • RAII partout : une ressource (mémoire, fichier, verrou) est détenue par un objet qui la libère dans son destructeur. Plus de fuite oubliée.
  • Règle de zéro : si tes membres gèrent déjà leurs ressources (std::vector, std::unique_ptr…), n'écris ni destructeur, ni constructeur de copie/déplacement. Le compilateur génère le bon comportement.
  • const par défaut : marque const tout ce qui ne change pas. L'intention est claire et le compilateur t'aide.
  • Préfère la STL : std::vector, std::string, les algorithmes (std::sort, std::find) avant toute réimplémentation.
  • Évite les pointeurs nus possesseurs : pas de new/delete manuels ; std::unique_ptr et std::make_unique.

Ces idiomes sont codifiés dans les C++ Core Guidelines, maintenues par Bjarne Stroustrup (le créateur du langage) et Herb Sutter. C'est la référence pour trancher un doute de style ou de sécurité.

L'écosystème et la suite

Avec ces bases, tout l'écosystème C++ s'ouvre à toi. Quelques directions selon tes envies :

  • Qt : applications de bureau multiplateformes avec interface graphique.
  • Unreal Engine : moteur de jeu AAA scripté en C++.
  • Boost : vaste collection de bibliothèques, antichambre de la future norme.
  • Calcul et finance : là où la performance brute est non négociable, le C++ domine.
  • Concurrence : la STL fournit std::thread, std::async et std::mutex pour exploiter plusieurs cœurs.

Astuce

Avant d'écrire des std::thread à la main, regarde std::async et, en C++17/20, les algorithmes parallèles (std::execution::par). La concurrence est puissante mais piégeuse : commence par les abstractions de haut niveau.

Cas réel

Chromium, le socle de Chrome et Edge, compte des dizaines de milliers de fichiers C++. Une compilation complète depuis zéro se mesure en heures sur une machine ordinaire — d'où l'usage de la compilation distribuée (Goma/Reclient) sur des fermes de serveurs. Ce qui sauve le quotidien des développeurs, c'est précisément la compilation séparée : modifier un seul .cpp ne recompile que lui. Mais gare à l'effet de levier des en-têtes : toucher un .hpp inclus par des milliers de fichiers déclenche une recompilation en cascade géante. Les équipes traquent donc les inclusions inutiles (outil include-what-you-use) et misent sur les modules C++20 pour couper court à ce recopiage de texte. Le découpage interface/implémentation que tu viens d'apprendre n'est pas cosmétique : à grande échelle, c'est du temps de build — donc de l'argent.

Pièges fréquents

Piège fréquent

Tout mettre dans les en-têtes. Définir les fonctions dans le .hpp les recompile dans chaque .cpp qui l'inclut : temps de compilation qui explose. Garde l'interface dans le .hpp et l'implémentation dans le .cpp (les templates, eux, doivent rester visibles dans l'en-tête).

Piège fréquent

Gérer les dépendances à la main (copier les sources, bricoler les chemins) rend le projet impossible à reconstruire ailleurs. Et ne pas tester transforme chaque modification en pari. Un gestionnaire (vcpkg/Conan) plus une suite de tests, dès le début, t'épargnent des heures.

Piège fréquent

Écrire du C++ « à la C ». Tableaux bruts, new/delete, pointeurs nus possesseurs, char* au lieu de std::string : tout cela contourne les protections du langage. Les idiomes modernes (RAII, STL, smart pointers) ne sont pas du folklore, ils éliminent des classes entières de bugs.

Pour aller plus loin

Pour aller plus loin

Explore les modules C++20/23 pour accélérer la compilation ; la concurrence avancée (atomics, coroutines) ; les sanitizers (-fsanitize=address,undefined) qui débusquent les fuites et comportements indéfinis à l'exécution ; l'écosystème (Boost, Qt, Unreal) ; et, comme boussole permanente, les C++ Core Guidelines.

Antisèche

Glossaire

En-tête (.hpp)
Fichier d'interface déclarant ce qu'offre une classe ou un module ; inclus par les .cpp qui l'utilisent, protégé par #pragma once.
Unité de compilation
Un .cpp avec tout ce qu'il inclut : l'unité que le compilateur traduit indépendamment en un fichier objet .o.
Éditeur de liens
Linker : assemble les fichiers objets en un exécutable (ou une bibliothèque) en résolvant les symboles référencés entre eux.
#pragma once
Garde d'inclusion moderne : garantit qu'un en-tête n'est traité qu'une fois par unité, évitant les redéfinitions.
CMake
Outil de build de référence : le CMakeLists.txt décrit le projet et CMake génère les commandes adaptées à la plateforme (Make, Ninja, Visual Studio).
Gestionnaire de dépendances
Outil (vcpkg, Conan) qui télécharge, compile et expose les bibliothèques externes de façon reproductible, sans copier les sources à la main.
Module (C++20)
Alternative aux en-têtes : une unité compilée une fois puis importée ; compilation plus rapide, pas de fuite de macros.
Règle de définition unique (ODR)
One Definition Rule : une entité ne doit être définie qu'une seule fois dans tout le programme ; d'où interface dans le .hpp, définition dans le .cpp.

Récap et vérification

  • L'interface va dans un .hpp (avec #pragma once), l'implémentation dans un .cpp : compilation séparée, builds plus rapides.
  • CMake décrit le projet et génère le build ; vcpkg/Conan gèrent les dépendances de façon reproductible.
  • Les modules C++20 remplacent peu à peu les en-têtes, mais le support reste inégal.
  • Les tests (Catch2, GoogleTest) protègent contre les régressions ; intègre-les via CTest.
  • Bonnes pratiques : RAII, règle de zéro, const par défaut, STL d'abord, pas de pointeurs nus, et les Core Guidelines comme référence.

Vérifie ta compréhension

  1. Pourquoi place-t-on l'implémentation d'une méthode dans le .cpp plutôt que dans le .hpp ?
  2. À quoi sert #pragma once, et quel problème évite-t-il ?
  3. Qu'est-ce que la « règle de zéro » et quand s'applique-t-elle ?
  4. Cite deux raisons d'écrire des tests automatisés dès le début d'un projet.
