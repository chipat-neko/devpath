Module 03 · La bibliothèque standard — Leçon 09

Templates et généricité

~34 min Avancé Leçon 8 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire un template de fonction et comprendre la déduction de type à l'instanciation ;
  • savoir concevoir une classe générique (ex. une Pile<T>) avec plusieurs paramètres ;
  • comprendre que le code est instancié par type à la compilation et pourquoi tout vit dans les en-têtes ;
  • savoir contraindre un template avec un concept (C++20) pour obtenir des erreurs claires.
Sommaire de la leçon

Tu as sans doute déjà eu envie d'écrire une fonction max une seule fois, et qu'elle marche aussi bien pour des int que pour des double ou des std::string. En C, la réponse était souvent les macros ou la duplication. En C++ moderne, la réponse s'appelle les templates : un mécanisme qui génère du code spécialisé pour chaque type, à la compilation, sans surcoût à l'exécution.

Dans cette leçon, tu pars du problème concret (éviter la duplication), tu construis des fonctions puis des classes génériques, tu comprends ce qui se passe vraiment quand le compilateur « instancie » un template, et tu termines avec les concepts de C++20 qui transforment les erreurs cryptiques en messages lisibles.

Le problème : écrire la même fonction trois fois

Imagine une fonction qui renvoie le plus grand de deux arguments. Sans généricité, tu finis par dupliquer le corps pour chaque type.

Trois corps strictement identiques, à la signature près. Si tu corriges une logique, tu dois la corriger partout. C'est exactement ce que les templates suppriment.

Les templates de fonction

Un template de fonction est un patron paramétré par un ou plusieurs types. Le mot-clé typename (ou class, équivalent ici) introduit un paramètre de type T.

Le compilateur déduit T à partir des arguments : maximum(3, 7) génère une version où T = int. On parle d'instanciation. Tu peux aussi imposer le type entre chevrons : maximum<std::string>(...), utile quand la déduction est ambiguë ou impossible (ici, sans le forçage, T serait déduit comme const char* et comparerait des adresses).

Note

Le nom maximum évite la collision avec std::max (de <algorithm>), qui fait déjà exactement cela. Dans du vrai code, préfère std::max : la STL est elle-même un immense ensemble de templates éprouvés.

Les templates de classe : une pile générique

On paramètre aussi des classes entières. Voici une pile (Pile<T>) qui stocke n'importe quel type, en s'appuyant sur std::vector pour la gestion mémoire (RAII : aucun new/delete manuel).

Contrairement aux fonctions, le type d'une classe template ne se déduit pas toujours : tu écris explicitement Pile<std::string>. Chaque combinaison (Pile<int>, Pile<std::string>...) produit une classe distincte à la compilation.

Plusieurs paramètres de type

Un template peut prendre plusieurs paramètres. C'est ce que fait std::pair<K, V>. Reconstruisons une paire minimale pour voir le mécanisme.

Ici K et V sont indépendants. Le compilateur déduit les deux depuis l'argument passé à afficher. C'est exactement le modèle d'une entrée de std::map<K, V>.

Les paramètres non-type (survol)

Un template peut aussi être paramétré par une valeur connue à la compilation, pas seulement par un type. Le cas classique : une taille fixe. La taille d'un std::array étant de type std::size_t, on déclare le paramètre non-type avec ce même type pour que la déduction réussisse.

N est figé à la compilation : somme connaît la taille sans la recevoir à l'exécution. C'est le principe derrière std::array<T, N>, dont la taille fait partie du type.

Note

Attention au type du paramètre non-type : si tu écrivais template <typename T, int N>, la déduction de N depuis std::array<int, 3> échouerait, car la taille y est un std::size_t, pas un int. Fais correspondre les types.

Comment ça marche : du code généré par type

Un template n'est pas du code compilé une fois pour toutes. C'est une recette. À chaque type utilisé, le compilateur fabrique une version concrète. maximum(3,7) et maximum(2.5,1.5) produisent deux fonctions différentes dans le binaire.

Conséquence pratique majeure : le compilateur a besoin de voir la définition complète du template au point d'utilisation. On met donc tout (déclaration et corps) dans l'en-tête (.hpp), pas dans un .cpp séparé.

Compilation standard d'un programme à templates : aucune option spéciale, tout est résolu à la compilation.

Piège fréquent

Si tu mets la définition d'un template dans un .cpp à part, la compilation passe mais l'édition de liens échoue : undefined reference to .... Le compilateur n'a jamais instancié le template car il ne l'a pas vu là où il était utilisé. Solution : tout dans l'en-tête.

Les concepts (C++20) : contraindre un template

Un template non contraint accepte tout type… jusqu'à ce qu'une opération échoue, et le message d'erreur déroule alors des pages de jargon interne. Les concepts (C++20) posent une condition d'entrée claire.

Si tu décommentes doubler(3.14), le message devient explicite plutôt que cryptique :

Tu peux écrire tes propres concepts, mais la bibliothèque <concepts> en fournit déjà beaucoup : std::integral, std::floating_point, std::copyable, etc. Une contrainte = une intention documentée et des erreurs à la frontière du template.

Astuce

Syntaxe abrégée très lisible : auto doubler(std::integral auto x). Le auto contraint joue le rôle d'un paramètre template implicite, contraint par le concept placé devant.

Cas réel

Toute la bibliothèque standard est un gigantesque jeu de templates : std::vector<T>, std::map<K, V>, std::sort fonctionnent pour tes types sans que leurs auteurs les connaissent. Le revers historique : passer à std::sort un type qui ne sait pas se comparer déroulait autrefois des centaines de lignes d'erreurs pointant au fond de l'implémentation — la terreur du débutant C++. C'est précisément ce que les concepts de C++20 ont corrigé : les algorithmes de <ranges> annoncent leurs exigences (std::sortable, std::totally_ordered…) et une violation s'arrête net sur une ligne lisible. Le même mécanisme qui rend la STL générique rend désormais ses erreurs compréhensibles.

Antisèche

Glossaire

Template
Patron de code paramétré par un ou plusieurs types (ou valeurs) ; le compilateur en génère des versions concrètes à la demande.
Instanciation
Génération, à la compilation, d'une version concrète du template pour un type donné (ex. maximum<int>).
Paramètre de type
Le T introduit par typename (ou class) ; il représente un type quelconque fourni à l'instanciation.
Déduction de type
Mécanisme par lequel le compilateur devine les paramètres du template à partir des arguments d'appel, sans les écrire entre chevrons.
Paramètre non-type
Paramètre de template qui est une valeur connue à la compilation (ex. std::size_t N), et non un type.
Concept (C++20)
Contrainte nommée sur un paramètre de template (std::integral…) ; elle documente l'intention et produit des erreurs claires à la frontière.
Type dépendant
Type qui dépend d'un paramètre de template (T::value_type) ; il doit être précédé de typename.
En-tête (header-only)
Fichier .hpp contenant déclaration et corps du template, car le compilateur doit voir la définition au point d'utilisation.

Pièges fréquents

  • Croire qu'un template est compilé une seule fois. Il est instancié pour chaque type. Beaucoup de types utilisés = plus de code généré (et un binaire plus gros).
  • Séparer déclaration et définition dans un .cpp. Erreurs de lien (undefined reference). Garde tout dans l'en-tête.
  • Subir des messages d'erreur cryptiques. Avant C++20, une mauvaise utilisation déroulait des centaines de lignes. Avec les concepts, l'erreur s'arrête net à la contrainte.
  • Sur-généraliser. Un template qui prétend marcher pour « tout » sans contrainte est fragile. Contrains avec un concept ce que le type doit réellement savoir faire.
  • Oublier typename pour les types dépendants. Dans un template, T::value_type est ambigu pour le compilateur : il faut écrire typename T::value_type pour dire que c'est un type.

Piège fréquent

Type dépendant non annoncé : T::iterator it; dans un template ne compile pas. Écris typename T::iterator it;. Sans typename, le compilateur suppose que T::iterator est une valeur, pas un type.

Pour aller plus loin

Explore les concepts en détail et la syntaxe requires ; la spécialisation de template (un comportement sur-mesure pour un type précis) ; les variadic templates (template <typename... Args>) pour un nombre variable de paramètres ; et constexpr pour exécuter du code à la compilation. Et garde en tête que toute la STL (std::vector, std::map, std::sort) est faite de templates : la lire, c'est apprendre la généricité.

Récap et vérification

  • Un template de fonction (template <typename T>) génère une version par type, avec déduction automatique de T.
  • Un template de classe paramètre une classe entière (ex. Pile<T>) ; le type s'indique en général explicitement.
  • On peut avoir plusieurs paramètres (<typename K, typename V>) et des paramètres non-type (<std::size_t N>).
  • Le code est instancié à la compilation : tout le template vit dans l'en-tête.
  • Les concepts (C++20) contraignent un template et produisent des erreurs claires.
