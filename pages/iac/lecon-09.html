Module 04 · IaC en production — Leçon 09

Le cycle de vie et les dépendances

~35 min Intermédiaire Leçons 02 et 03 conseillées

À la fin de cette leçon, tu sauras

  • comprendre les dépendances implicites et le graphe ;
  • forcer un ordre avec depends_on ;
  • piloter le cycle de vie (create_before_destroy, prevent_destroy, ignore_changes) ;
  • lire l'existant avec un data source et importer une ressource.
Sommaire de la leçon

Terraform décide seul de l'ordre de création des ressources et gère leur cycle de vie. La plupart du temps, c'est parfait. Mais il arrive qu'on doive guider ce comportement : imposer un ordre, éviter une coupure, protéger une base de données. Cette leçon donne ces leviers de contrôle fin.

Les dépendances implicites

Quand une ressource référence une autre (par exemple subnet_id = aws_subnet.principal.id), Terraform en déduit qu'il faut créer le sous-réseau avant l'instance. Il construit ainsi un graphe de dépendances et en tire l'ordre : création dans le sens des flèches, destruction en sens inverse. Tu n'as rien à déclarer : la référence suffit.

depends_on : la dépendance explicite

Parfois, une ressource dépend d'une autre sans la référencer directement (un effet de bord, un droit qui doit exister avant). Le méta-argument depends_on force alors l'ordre :

À n'utiliser que lorsqu'aucune référence naturelle n'existe : abuser de depends_on alourdit le graphe. La dépendance implicite (par référence) reste toujours préférable.

Le bloc lifecycle

Le bloc lifecycle ajuste la manière dont Terraform crée, remplace ou détruit une ressource. Trois options clés :

  • create_before_destroy — pour un remplacement, crée la nouvelle ressource avant de supprimer l'ancienne : évite la coupure.
  • prevent_destroy — bloque tout apply qui détruirait la ressource : filet de sécurité pour une base de données.
  • ignore_changes — ignore les modifications d'un champ (souvent géré ailleurs), pour éviter des allers-retours.

Les data sources : lire l'existant

Un data source (source de données) lit une information sans la gérer : la dernière image système officielle, une zone DNS déjà créée, un secret existant. On récupère des valeurs pour ses ressources, sans prendre possession de l'objet lu.

Piège fréquent

Ce data source relit la dernière image Ubuntu à chaque plan. Le jour où une nouvelle version est publiée, l'identifiant change ; or l'attribut ami ne se modifie pas sur place, donc Terraform propose de détruire puis recréer ton instance alors que tu n'as pas touché au code. Épingle une image précise pour ce qui doit rester stable, ou ajoute lifecycle { ignore_changes = [ami] }.

prevent_destroy sur tout ce qui a un état

Sur une base de données, un stockage d'objets, un volume : prevent_destroy = true transforme une destruction accidentelle en erreur au plan, avant tout dégât. Un simple renommage de ressource ou un changement de champ « forçant le remplacement » peut sinon déclencher un destroy silencieux. Le garde-fou coûte une ligne ; sa valeur se mesure le jour où il bloque la mauvaise commande.

Cas réel — le champ que Terraform voulait « remettre à zéro »

Une équipe gère un groupe de serveurs dont le nombre d'instances est piloté par l'autoscaling du cloud : il monte à 6 aux heures de pointe, redescend à 2 la nuit. Le code Terraform, lui, déclare desired_capacity = 2. Résultat : chaque plan voit « 6 au lieu de 2 » et veut réduire le parc en pleine journée. La solution n'est pas de bagarrer avec l'autoscaler, mais de dire à Terraform de ne pas surveiller ce champ : lifecycle { ignore_changes = [desired_capacity] }. Terraform crée le groupe, puis laisse l'autoscaling gérer la taille. Chacun son rôle : l'IaC pose la structure, l'autoscaler ajuste le vivant.

Data source plutôt que valeur codée en dur

Tu as besoin de l'identifiant de la dernière image Ubuntu, ou de l'ID d'un réseau existant ? Ne le colle pas en dur : un data source le lit à chaque plan, donc la valeur reste juste même si elle change côté cloud. Le code devient portable (il marche dans une autre région/compte) et ne pourrit pas avec le temps.

Pour aller plus loin

Quand on réorganise du code (renommer une ressource, la sortir dans un module), Terraform croit par défaut qu'il faut détruire l'ancienne et créer la nouvelle. Le bloc moved lui dit « c'est la même ressource, elle a juste changé d'adresse », ce qui évite toute recréation. Avec import, ignore_changes et moved, on adapte le code au réel sans jamais casser l'infrastructure existante.

Glossaire

Dépendance implicite
Ordre déduit automatiquement quand une ressource référence une autre (a.id) ; forme préférée.
Graphe de dépendances
Représentation des liens entre ressources d'où Terraform tire l'ordre de création (et l'inverse pour la destruction).
depends_on
Méta-argument imposant une dépendance explicite quand aucune référence directe n'existe.
Bloc lifecycle
Bloc qui ajuste création, remplacement et destruction d'une ressource.
create_before_destroy
Option qui crée la nouvelle ressource avant de détruire l'ancienne lors d'un remplacement : évite la coupure.
prevent_destroy
Option qui fait échouer tout plan qui détruirait la ressource : garde-fou pour les données.
ignore_changes
Option qui demande d'ignorer les modifications d'un champ (souvent géré hors Terraform).
Data source
Bloc data qui lit une information existante sans la gérer ; relu à chaque plan.
Import
Opération qui adopte dans le state une ressource déjà existante, sans la recréer.

Récap et vérification

  • Terraform déduit l'ordre des références (dépendances implicites) ; depends_on force un ordre sans référence.
  • lifecycle pilote le remplacement : create_before_destroy (sans coupure), prevent_destroy (garde-fou), ignore_changes (champ externe).
  • Un data source lit l'existant sans le gérer ; l'import adopte une ressource créée à la main.
  • On adapte le code au réel sans recréer l'infrastructure.

Exercices

Exercice 1Échauffement

Tu crées une instance à partir d'un sous-réseau : subnet_id = aws_subnet.principal.id. Faut-il ajouter un depends_on pour que le sous-réseau soit créé avant ?

Voir une solution

Non. En écrivant aws_subnet.principal.id, tu crées déjà une dépendance implicite : Terraform sait qu'il doit créer le sous-réseau avant l'instance, puisque l'instance a besoin de son identifiant. Ajouter depends_on = [aws_subnet.principal] serait redondant. On réserve depends_on aux cas où il n'existe aucune référence directe alors qu'un ordre est quand même nécessaire (par exemple un droit d'accès qui doit exister avant qu'une instance ne l'utilise, sans être référencé dans ses arguments).

Exercice 2Application

Une base de données de production ne doit jamais être détruite par mégarde via Terraform. Comment le garantir ?

Voir une solution

Avec prevent_destroy = true, tout plan/apply qui aboutirait à détruire cette base échoue avec une erreur explicite, avant tout dégât. C'est un garde-fou contre les destructions accidentelles — par exemple si quelqu'un change un champ qui « force le remplacement », ou supprime le bloc par erreur. Pour détruire volontairement la ressource, il faudra retirer consciemment cette ligne : la protection oblige à un geste délibéré. On la met systématiquement sur tout ce qui porte des données (bases, volumes, stockages).

Exercice 3Défi

Un bucket S3 a été créé à la main il y a des mois, et contient des données. Tu veux désormais le gérer avec Terraform, sans le recréer (ce qui perdrait son contenu). Décris la démarche.

Voir une solution

La clé est l'import — on ajoute la ressource existante au state sans la recréer. Démarche : 1. Écrire le bloc resource "aws_s3_bucket" "logs" { bucket = "nom-exact-du-bucket" } décrivant le bucket tel qu'il existe. 2. Déclarer l'import, soit avec un bloc dans le code : import { to = aws_s3_bucket.logs, id = "nom-exact-du-bucket" }, soit avec la commande terraform import aws_s3_bucket.logs nom-exact-du-bucket. 3. Lancer terraform plan : Terraform lit le bucket réel, l'associe à la ressource et compare avec le code. 4. Ajuster le code jusqu'à ce que le plan n'annonce plus aucun changement (le code décrit alors fidèlement la réalité). À partir de là, le bucket est adopté : Terraform le gère normalement, et son contenu n'a jamais été touché. C'est la façon propre de faire entrer une ressource « historique » dans l'IaC.
