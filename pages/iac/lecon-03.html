Module 01 · Les bases — Leçon 03

Variables, state, plan/apply

~35 min Intermédiaire Leçon 02

À la fin de cette leçon, tu sauras

  • paramétrer avec des variables et exposer des outputs ;
  • expliquer le rôle du state ;
  • stocker le state à distance et le verrouiller ;
  • maîtriser plan / apply / destroy et les secrets.
Sommaire de la leçon

Une configuration codée en dur n'est pas réutilisable. Les variables la paramètrent, les outputs en exposent les résultats, et le state est la mémoire qui relie ton code à la réalité. Trois notions au cœur de Terraform.

Les variables

Une variable d'entrée paramètre la configuration (région, taille, nom…). On la déclare, puis on l'utilise avec var.nom. Les valeurs viennent d'un fichier .tfvars, de la ligne de commande ou de l'environnement.

Les outputs

Un output expose une valeur calculée après l'apply (l'adresse IP créée, l'URL d'un service…), utile pour l'afficher ou la transmettre à un autre module.

Le state : la mémoire de Terraform

Comment Terraform sait-il ce qui existe déjà ? Grâce au state (fichier terraform.tfstate) : il y mémorise la correspondance entre ton code et les ressources réelles (leurs identifiants). Au prochain plan, il compare code ↔ state ↔ réalité pour calculer les changements.

Le state est précieux — et sensible

Perdre le state, c'est perdre le lien avec ton infrastructure (Terraform voudrait tout recréer). Et il peut contenir des valeurs sensibles (mots de passe générés). On ne le commit jamais en clair dans Git ; on le protège.

Le state distant

En équipe, on stocke le state à distance (un stockage objet partagé, par ex.) plutôt qu'en local. Deux bénéfices : tout le monde travaille sur le même état, et un verrou empêche deux personnes d'appliquer en même temps (ce qui corromprait le state).

Cas réel — le verrou qui évite la corruption

Deux ingénieurs d'astreinte réagissent au même incident et lancent chacun terraform apply à quelques secondes d'intervalle. Avec un state local, les deux auraient écrit par-dessus le même état : corruption et ressources fantômes. Grâce au state distant, le second apply est refusé net (« Error: state locked ») : un seul passe, l'autre attend. Le verrouillage transforme une course dangereuse en simple file d'attente.

Le cycle plan / apply / destroy

Piège fréquent

Tu lis attentivement le plan, puis tu lances apply : Terraform ne rejoue pas le plan que tu viens de lire, il en recalcule un. Entre les deux, un collègue a pu appliquer un changement, ou un data source renvoyer une autre valeur — et en CI, avec -auto-approve, personne ne relit rien. Pour appliquer exactement ce que tu as validé, enregistre le plan : terraform plan -out=tfplan, puis terraform apply tfplan.

destroy : puissant et dangereux

terraform destroy supprime tout ce que la configuration gère. Génial pour nettoyer un environnement de test ; catastrophique lancé par erreur en production. Vérifie toujours sur quel environnement tu es.

Gérer les secrets

Les valeurs sensibles (mots de passe, clés) ne se mettent pas en dur dans le code. On les passe par des variables marquées sensibles, fournies via l'environnement ou un gestionnaire de secrets, et on protège le state (qui peut les contenir) par le chiffrement et des accès restreints.

Pièges fréquents

  • Commiter le state en clair. Il contient des secrets et l'image de ton infra : protège-le, ne le versionne pas en clair.
  • Travailler en local à plusieurs. Deux states divergent ; utilise un state distant verrouillé.
  • Éditer le state à la main. Risque de corruption ; passe par les commandes prévues.
  • Lancer destroy sans vérifier l'environnement. Toujours s'assurer de ne pas être en production.

Pour aller plus loin

Pour découper une grande infrastructure, on sépare les states par périmètre (réseau, applications, données) afin de limiter le « rayon de souffle » d'un changement et de paralléliser les équipes. Un grand state unique devient vite lent et risqué.

Pour aller plus loin

Beaucoup d'équipes n'autorisent l'apply que depuis le pipeline CI/CD, jamais depuis un poste. Le state est distant, le pipeline est la seule porte : traçabilité et sécurité maximales.

Glossaire

Variable d'entrée
Paramètre de la configuration (région, taille, nom…) déclaré par variable et utilisé avec var.nom ; ses valeurs viennent d'un .tfvars, de la CLI ou de l'environnement.
Output
Valeur calculée exposée après l'apply (adresse IP, URL…), pour l'afficher ou la transmettre à un autre module.
State
Fichier (terraform.tfstate) qui mémorise la correspondance entre le code et les ressources réelles (leurs identifiants) ; base de calcul de chaque plan.
State distant
State stocké sur un support partagé plutôt qu'en local, pour que toute l'équipe travaille sur le même état.
Verrou (lock)
Mécanisme qui empêche deux apply simultanés d'écrire dans le state en même temps et de le corrompre.
destroy
Commande qui supprime toutes les ressources gérées par la configuration : utile pour nettoyer un environnement de test, dangereuse en production.
Variable sensible
Variable marquée comme secrète ; sa valeur n'est pas affichée et provient de l'environnement ou d'un gestionnaire de secrets.
Rayon de souffle
Étendue des ressources qu'un changement peut impacter ; on le limite en découpant l'infra en plusieurs states.

Récap et vérification

  • Les variables (var.nom) paramètrent ; les outputs exposent les résultats.
  • Le state mémorise le lien code ↔ réalité ; il est précieux et sensible.
  • Stocke le state à distance et verrouillé pour le travail en équipe.
  • plan (aperçu) → apply → destroy ; protège les secrets et le state.

Vérifie ta compréhension

  1. À quoi sert le fichier de state ?
  2. Pourquoi un state distant verrouillé en équipe ?
  3. Pourquoi ne pas commiter le state en clair ?

Exercice 3Défi

Deux personnes d'une équipe travaillent sur la même infra avec un state local, chacune sur sa machine. Quels problèmes vont survenir, et quelle est la bonne pratique ?

Voir une solution

Problèmes : chacune a son propre state local, donc deux visions divergentes de l'infrastructure. Quand l'une applique un changement, l'autre ne le voit pas dans son state ; au prochain apply, elle pourrait recréer ou détruire des ressources qu'elle « croit » absentes/présentes. Sans verrou, des apply simultanés peuvent en plus corrompre l'état. Bonne pratique : un state distant partagé (stockage objet ou backend dédié) avec verrouillage — tout le monde lit/écrit le même état, et un seul apply s'exécute à la fois. Idéalement, n'autoriser l'apply que depuis le pipeline CI/CD, pour la traçabilité.
