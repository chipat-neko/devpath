Module 01 · Les bases — Leçon 01

Pourquoi l'Infrastructure as Code

~31 min Intermédiaire Bases de cloud utiles

À la fin de cette leçon, tu sauras

  • expliquer les limites de la configuration manuelle ;
  • citer les avantages de l'IaC ;
  • distinguer déclaratif et impératif ;
  • définir l'idempotence et situer Terraform.
Sommaire de la leçon

Créer un serveur en cliquant dans une console, ça marche… une fois. Mais comment le recréer à l'identique ? Comment savoir qui a changé quoi, et quand ? Comment monter un environnement de test jumeau de la production ? L'Infrastructure as Code répond à tout cela : on décrit l'infrastructure dans du code.

Les limites du « cliquer dans la console »

Configurer à la main (parfois appelé ClickOps) pose de vrais problèmes :

  • Non reproductible : refaire la même chose ailleurs est long et source d'erreurs.
  • Pas d'historique : impossible de savoir qui a modifié quoi, ni de revenir en arrière.
  • Dérive de configuration : avec le temps, chaque environnement diverge (« ça marche en test, pas en prod »).
  • Pas de revue : un changement risqué passe sans relecture d'un collègue.

L'idée de l'Infrastructure as Code

Avec l'IaC, l'infrastructure est décrite dans des fichiers texte, versionnés comme du code applicatif. Un outil lit ces fichiers et fait en sorte que la réalité y corresponde. On gagne d'un coup :

  • Reproductibilité : recréer un environnement complet en une commande.
  • Versionnage (Git) : historique, retour arrière, branches.
  • Revue de code : on relit un changement d'infra comme un changement de code.
  • Documentation vivante : le code est la description à jour de l'infra.
  • Automatisation : l'IaC s'intègre au pipeline CI/CD.

Déclaratif, pas impératif

Terraform est déclaratif : tu décris l'état voulu (« je veux ce serveur, ce réseau, cette base »), et l'outil calcule lui-même les actions pour y arriver (créer, modifier, supprimer). C'est l'inverse d'un script impératif qui enchaîne des commandes pas à pas. Tu dis quoi, pas comment.

L'idempotence

Conséquence clé : l'idempotence. Réappliquer la même configuration quand tout est déjà conforme ne change rien. Tu peux relancer sans crainte ; l'outil ne touche que ce qui diffère de l'état voulu. Fini les scripts qu'on n'ose pas rejouer.

Décrire la cible, pas les étapes

Comme pour Kubernetes (l'« état désiré »), l'IaC raisonne par convergence vers la cible. Tu maintiens une description à jour ; l'outil se charge des différences. C'est plus sûr et plus simple à raisonner.

Gare à la dérive

Modifier une ressource « à la main » dans la console après coup crée une dérive (drift) : le réel ne correspond plus au code. Au prochain apply, Terraform voudra annuler ton changement pour revenir à l'état décrit. La règle : tout changement passe par le code.

Terraform parmi d'autres

Terraform est l'un des outils d'IaC les plus répandus, et il est indépendant du fournisseur (un même outil pour plusieurs clouds, via des providers). Il en existe d'autres (Pulumi, ou les outils natifs d'un cloud) ; les principes de cette leçon valent pour tous. On apprendra Terraform comme support concret.

Cas réel — la règle de pare-feu « en urgence »

Pendant un incident, un ingénieur ouvre un port dans la console du cloud pour rétablir le service — vite fait, sans toucher au code. Trois semaines plus tard, un collègue lance un apply sans rapport : le plan prévoit de refermer ce port (absent du code), et l'incident ressurgit. Deux parades : reporter le changement dans le code aussitôt, ou l'importer dans le state. Le code doit rester la seule source de vérité.

Pièges fréquents

  • Modifier à la main après coup. Cela crée une dérive (drift) entre le code et la réalité : on perd le bénéfice de l'IaC.
  • Confondre déclaratif et script. On décrit la cible ; on ne programme pas chaque étape.
  • Ne pas versionner. De l'IaC hors Git, c'est se priver de l'historique et de la revue.
  • Croire que c'est réservé au cloud. L'IaC s'applique aussi au réseau, au DNS, aux services managés…

Pour aller plus loin

On distingue parfois deux familles : le provisionnement (créer l'infrastructure — Terraform) et la configuration (installer/régler le logiciel sur des machines — Ansible, etc.). Les deux sont complémentaires ; ce cours se concentre sur le provisionnement déclaratif.

Pour aller plus loin

Le test ultime de l'IaC : pouvoir tout détruire et tout recréer à partir du code (et d'une sauvegarde des données). Si tu en es capable sereinement, ton infrastructure est vraiment « as code ».

Glossaire

Infrastructure as Code (IaC)
Décrire l'infrastructure (serveurs, réseaux, bases) dans des fichiers texte versionnés, qu'un outil applique pour faire correspondre la réalité à la description.
Déclaratif
Style où l'on décrit l'état voulu ; l'outil calcule seul les actions pour l'atteindre. On dit « quoi », pas « comment ».
Impératif
Style où l'on énumère les commandes à exécuter, dans l'ordre. Rejouer suppose un état de départ précis.
Idempotence
Propriété d'une opération qu'on peut réappliquer sans effet supplémentaire : si l'état est déjà conforme, rien ne change.
Dérive (drift)
Écart entre l'infrastructure réelle et ce que décrit le code, typiquement après une modification manuelle dans la console.
Terraform
Outil d'IaC déclaratif et indépendant du fournisseur, édité par HashiCorp, configuré dans le langage HCL.
Provider
Plugin qui permet à Terraform de piloter une plateforme (un cloud, un DNS…) via son API ; interchangeable, il rend l'outil multi-fournisseurs.
Provisionnement
Création de l'infrastructure elle-même (Terraform), à distinguer de la configuration du logiciel sur les machines (Ansible…).

Récap et vérification

  • La config manuelle est non reproductible, sans historique, sujette à la dérive.
  • L'IaC décrit l'infra en code versionné : reproductible, relisible, automatisable.
  • Terraform est déclaratif (on décrit la cible) et idempotent (réappliquer ne change rien d'inutile).
  • Terraform est un outil parmi d'autres ; les principes sont universels.

Vérifie ta compréhension

  1. Cite deux limites de la configuration manuelle.
  2. Que signifie « déclaratif » ?
  3. Qu'est-ce que l'idempotence ?

Exercices

Exercice 1Échauffement

Cite trois bénéfices concrets d'avoir son infrastructure « en code » dans un dépôt Git.

Voir une solution

(1) Historique : on voit qui a changé quoi et quand, et on peut revenir en arrière ; (2) revue de code : un changement d'infra est relu avant d'être appliqué ; (3) reproductibilité : on recrée un environnement identique à partir du code. Bonus : la documentation est toujours à jour (le code est la description).

Exercice 2Application

Explique avec tes mots pourquoi un script impératif (« crée ceci, puis cela ») est plus fragile à rejouer qu'une configuration déclarative.

Voir une solution

Un script impératif suppose un état de départ précis : si on le rejoue alors que certaines ressources existent déjà, il peut échouer (« existe déjà ») ou créer des doublons. Une configuration déclarative décrit la cible : l'outil compare avec l'existant et n'applique que les différences. Réappliquer est donc sûr (idempotent), quel que soit l'état de départ.

Exercice 3Défi

Une équipe gère son infra en IaC, mais quelqu'un modifie une ressource « vite fait » dans la console du fournisseur. Quel problème cela crée-t-il, et comment l'éviter ?

Voir une solution

Cela crée une dérive de configuration (drift) : la réalité ne correspond plus au code. Au prochain apply, Terraform voudra annuler le changement manuel (pour revenir à l'état décrit), ou bien on ne saura plus quelle est la vraie source de vérité — et le bénéfice de l'IaC (reproductibilité, historique) s'effrite. Comment l'éviter : (1) règle d'équipe « tout changement passe par le code », pas par la console ; (2) restreindre les droits (IAM) pour empêcher les modifications manuelles en production ; (3) appliquer via un pipeline CI/CD (la seule voie d'apply) ; (4) détecter la dérive régulièrement (un plan qui montrerait des écarts non voulus). La source de vérité doit rester le code.
