Le state à distance et le travail en équipe

~34 min Intermédiaire Leçons 03 et 05 conseillées

À la fin de cette leçon, tu sauras

  • expliquer pourquoi le state local ne tient pas en équipe ;
  • configurer un backend distant (S3, GCS, Terraform Cloud) ;
  • comprendre le verrouillage (locking) ;
  • lire des sorties d'un autre state et protéger les secrets.
Sommaire de la leçon

Le state (leçon 03) est la mémoire de Terraform : la carte entre ton code et les ressources réelles. Tant que tu travailles seul, il vit tranquillement dans un fichier terraform.tfstate sur ton disque. Dès qu'une équipe touche à la même infrastructure, ce fichier local devient un problème. Cette leçon montre comment le partager en sécurité.

Pourquoi le state local ne tient pas en équipe

Imagine deux collègues qui modifient la même infra. Chacun a sa copie du state sur son poste. Alice applique un changement : son state local est à jour, pas celui de Bob. Bob applique à son tour : à partir d'un state périmé, il croit devoir recréer des ressources qui existent déjà. Les states divergent, l'infrastructure part en vrille — et si un poste tombe en panne, le state (donc la carte de l'infra) est perdu.

Le backend distant

Un backend indique où Terraform stocke son state. Par défaut, c'est le backend local (un fichier). En équipe, on déclare un backend distant : un stockage d'objets (AWS S3, Google Cloud Storage, Azure Blob) ou une plateforme dédiée (Terraform Cloud). Le state y est central, chiffré et sauvegardé.

La clé key range chaque state dans un « dossier » logique : on isole ainsi prod de dev, et le réseau de la base de données. Après avoir écrit ce bloc, terraform init propose de migrer le state local vers le backend.

Qui crée le backend lui-même ?

Petit casse-tête : le bucket S3 (et la table de verrous) qui hébergent le state doivent exister avant qu'on y stocke quoi que ce soit. On ne peut pas ranger le state de ce bucket… dans ce bucket qui n'existe pas encore. La solution courante : un petit projet « bootstrap » qui crée ces ressources avec un state local (une fois pour toutes), ou une création manuelle. Ensuite seulement, tout le reste bascule sur le backend distant.

Le verrouillage (locking)

Que se passe-t-il si Alice et Bob lancent apply en même temps ? Sans protection, ils écriraient le state simultanément et le corrompraient. Le verrouillage l'empêche : avant d'écrire, Terraform pose un verrou ; le second doit attendre que le premier ait fini.

Lire les sorties d'un autre state

On découpe souvent une grande infra en plusieurs states (réseau, base de données, application) pour limiter le rayon d'action de chaque changement. La source de données terraform_remote_state permet à un state de lire les sorties (leçon 03) d'un autre : par exemple, l'application récupère l'identifiant du réseau produit par le state « réseau ».

Le state contient des secrets en clair

Un mot de passe généré, une clé d'accès, une chaîne de connexion : tout cela peut apparaître en clair dans le state. Deux règles absolues : ne jamais committer le state dans Git, et n'utiliser qu'un backend chiffré (au repos) dont l'accès est restreint aux personnes autorisées. Le state se traite comme un coffre-fort, pas comme un fichier de config anodin.

Cas réel — un state versionné par erreur

C'est une bévue classique : un fichier terraform.tfstate qui atterrit dans un dépôt Git, parfois public. Comme le state contient des identifiants et des clés en clair, l'incident revient à publier des secrets d'infrastructure : des robots scannent GitHub en continu pour exactement cela. La parade est double et connue : mettre *.tfstate* dans le .gitignore dès le premier commit, et déplacer le state vers un backend distant chiffré à accès restreint. Beaucoup d'équipes n'y pensent qu'après la première frayeur ; autant le faire d'emblée.

Migrer un state existant sans le perdre

Tu passes d'un state local à un backend distant ? Ajoute le bloc backend, puis lance terraform init : Terraform détecte le changement et propose de copier le state existant vers le nouveau backend (« Do you want to copy existing state? »). Réponds yes. Le state est migré sans recréer une seule ressource : c'est un simple déménagement de la mémoire.

Pour aller plus loin

Terraform Cloud (et ses équivalents comme Spacelift ou Scalr) va plus loin qu'un simple stockage : state distant chiffré et verrouillé, mais aussi exécution des plan/apply à distance, historique des versions du state, variables sensibles chiffrées et contrôle d'accès par équipe. Pour un usage sérieux en entreprise, c'est souvent le pas suivant après le backend S3/GCS « fait maison ».

Antisèche

Glossaire

Backend
Configuration qui indique où Terraform stocke son state : local (un fichier) par défaut, ou distant (S3, GCS, Terraform Cloud…).
State distant
State stocké sur un service partagé plutôt que sur un poste : une source de vérité unique pour toute l'équipe, sauvegardée et chiffrée.
Verrouillage (locking)
Mécanisme qui empêche deux apply d'écrire le state en même temps : le second attend la libération du verrou.
Clé de state (key)
Chemin logique qui range un state donné dans le backend ; sert à séparer environnements et périmètres.
terraform_remote_state
Source de données qui lit les sorties d'un autre state, pour partager des valeurs entre configurations.
Migration de state
Déplacement du state d'un backend vers un autre ; terraform init copie l'existant sans recréer les ressources.
Chiffrement au repos
Chiffrement des données stockées (ici le state) ; indispensable car le state peut contenir des secrets en clair.
Rayon d'impact (blast radius)
Étendue des ressources qu'un seul changement peut affecter ; on découpe l'infra en états séparés pour le réduire.

Récap et vérification

  • Le state local ne tient pas en équipe : copies divergentes, risque de perte.
  • Un backend distant (S3, GCS, Terraform Cloud) offre une source de vérité partagée, chiffrée, sauvegardée.
  • Le verrouillage évite deux apply concurrents ; la clé key isole les states.
  • terraform_remote_state partage des sorties ; le state contient des secrets à protéger (jamais dans Git).

Vérifie ta compréhension

  1. Pourquoi un state local pose-t-il problème à plusieurs ?
  2. À quoi sert le verrouillage ?
  3. Que fait terraform init quand on ajoute un backend distant ?

Exercices

Exercice 1Échauffement

Écris le bloc terraform { backend … } pour stocker le state d'un environnement de production dans un bucket S3 nommé infra-tfstate, région eu-west-3, avec chiffrement.

Voir une solution

La clé key range ce state dans un « dossier » prod/ du bucket, ce qui permettra d'y ranger d'autres states (dev, périmètres) sans collision. encrypt = true demande le chiffrement au repos.

Exercice 2Application

Bob voit ce message quand il lance apply : « Error acquiring the state lock ». Que se passe-t-il, et que doit-il faire ?

Voir une solution

Le verrou du state est déjà pris : quelqu'un d'autre (ou un pipeline) est en train de faire un apply sur le même state, ou un apply précédent ne s'est pas terminé proprement. La bonne réaction est d'attendre que l'opération en cours se termine, puis de relancer : le verrou sera libéré automatiquement. Il ne faut pas forcer le déverrouillage (terraform force-unlock) à la légère : on ne le fait que si l'on est certain qu'aucune opération n'est réellement en cours (par exemple après un pipeline qui a planté), car forcer pendant une écriture réelle corromprait le state. C'est justement le rôle du verrou : garantir qu'un seul apply écrit à la fois.

Exercice 3Défi

Une équipe gère le réseau et l'application dans deux states séparés. L'application a besoin de l'identifiant du sous-réseau créé par le state « réseau ». Comment relier proprement les deux sans copier-coller l'identifiant à la main ?

Voir une solution

Deux ingrédients. 1. Côté « réseau », exposer l'identifiant en sortie (leçon 03) : output "subnet_id" { value = aws_subnet.principal.id }. Cette sortie est enregistrée dans le state « réseau ». 2. Côté « application », lire ce state avec la source terraform_remote_state pointant vers le backend et la key du réseau, puis utiliser data.terraform_remote_state.reseau.outputs.subnet_id là où on a besoin de l'identifiant. Résultat : si le réseau change son sous-réseau, l'application lira automatiquement la nouvelle valeur au prochain plan, sans qu'on recopie quoi que ce soit. On a couplé les deux states par leurs sorties, proprement et de façon reproductible. C'est le motif standard pour découper une grande infrastructure en states indépendants tout en les faisant communiquer.
