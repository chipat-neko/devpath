Modules & réutilisation

~33 min Intermédiaire Leçon 03

À la fin de cette leçon, tu sauras

  • repérer la duplication à factoriser ;
  • créer un module paramétré ;
  • l'appeler et lire ses outputs ;
  • composer plusieurs modules.
Sommaire de la leçon

Quand on déploie plusieurs fois le même ensemble de ressources (un serveur + son réseau + ses règles), le copier-coller s'installe — et avec lui les divergences et les erreurs. Les modules apportent à l'IaC ce que les fonctions apportent au code : la réutilisation.

Le problème de la duplication

Imaginons trois environnements, chacun avec un serveur web, un réseau et une base. Sans factorisation, c'est trois fois le même bloc de code, à maintenir en parallèle : modifier la taille des serveurs partout, sans en oublier un, devient pénible et risqué. La règle DRY (« Don't Repeat Yourself ») s'applique aussi à l'infrastructure.

Qu'est-ce qu'un module ?

Un module est simplement un dossier de configuration Terraform, paramétré par des variables (ses entrées) et exposant des outputs (ses sorties). Tout dossier est déjà un module (le « module racine ») ; on en crée d'autres, réutilisables, qu'on appelle depuis le racine.

Comme une fonction

Un module a des entrées (variables), un corps (les ressources) et des sorties (outputs). On l'appelle plusieurs fois avec des arguments différents — exactement comme une fonction. Modifier le module corrige tous ses usages d'un coup.

Une interface minimale

Un bon module expose peu de variables, bien nommées, et cache le reste. Plus l'interface est petite et stable, plus le module est facile à réutiliser sans tout casser à chaque évolution. Vise « une chose, bien faite ».

D'où viennent les modules ?

  • Locaux : un dossier de ton dépôt (./modules/...), le plus simple pour commencer.
  • Partagés : un dépôt Git ou un registre de modules, pour réutiliser entre projets/équipes — en épinglant une version.

Épingle la version d'un module partagé

Un module tiré d'un registre ou d'un dépôt Git évolue. Sans version épinglée (version = "1.4.0"), une mise à jour surprise peut changer ton plan — voire casser ton infra — sans que tu l'aies décidé. On met à jour volontairement.

Cas réel — réutiliser un module éprouvé

Le Terraform Registry public héberge des modules maintenus, comme le module VPC AWS officiel utilisé par des milliers d'équipes. Plutôt que réécrire (et déboguer) un réseau complet — sous-réseaux, tables de routage, passerelles — on appelle un module éprouvé en épinglant sa version. Même réflexe que d'installer une bibliothèque au lieu de la recoder : on réutilise le travail testé de la communauté.

Composer

On compose les modules : un module « réseau », un module « serveur » qui prend l'id du réseau, un module « base »… La configuration racine devient un assemblage lisible de briques, chacune testable et réutilisable séparément.

Pièges fréquents

  • Copier-coller au lieu de factoriser. Trois fois le même bloc ? C'est un module qui se cache.
  • Modules trop gros ou trop génériques. Un bon module fait une chose claire, avec peu d'entrées bien pensées.
  • Ne pas épingler la version d'un module partagé. Une mise à jour surprise peut casser ton infra.
  • Tout mettre dans le module racine. Sans découpage, le code devient un mur illisible.

Pour aller plus loin

Les boucles (count, for_each) permettent de créer plusieurs instances d'une ressource ou d'un module à partir d'une liste (trois serveurs identiques, un par zone…). Couplées aux modules, elles rendent la configuration à la fois concise et expressive.

Pour aller plus loin

Un bon module se documente (un court README : ce qu'il fait, ses variables, ses outputs) et se versionne. Traité comme un petit produit réutilisable, il devient un atout pour toute l'équipe.

Glossaire

Module
Dossier de configuration Terraform réutilisable, paramétré par des variables (entrées) et exposant des outputs (sorties) : l'équivalent d'une fonction.
Module racine
Le dossier depuis lequel on lance Terraform ; c'est lui qui appelle les autres modules.
source
Attribut d'un bloc module qui indique où trouver le module : un chemin local (./modules/…), un dépôt Git ou un registre.
DRY
« Don't Repeat Yourself » : éviter de dupliquer ; toute logique répétée devient une brique unique (ici, un module).
Composition
Assembler plusieurs modules en passant la sortie de l'un (ex. l'id du réseau) en entrée d'un autre.
Registre de modules
Catalogue de modules versionnés et partagés (public comme le Terraform Registry, ou privé) qu'on réutilise entre projets.
for_each
Mécanisme qui crée plusieurs instances d'une ressource ou d'un module à partir d'une liste ou d'une map.
Interface (d'un module)
L'ensemble de ses variables d'entrée et de ses outputs ; on la garde petite et stable pour ne pas casser les usages.

Récap et vérification

  • Les modules factorisent l'infrastructure (DRY) : un dossier paramétré, comme une fonction.
  • Entrées = variables, sorties = outputs ; on appelle avec un bloc module.
  • Modules locaux (dossier) ou partagés (registre, version épinglée).
  • On compose des briques claires plutôt qu'un gros bloc unique.

Exercice 2Application

Tu as trois serveurs identiques décrits par copier-coller, ne différant que par leur nom. Comment améliorer ?

Voir une solution

Extraire un module « serveur » (avec une variable nom et les attributs communs), puis l'appeler trois fois avec des noms différents. Mieux encore : utiliser for_each sur une liste de noms pour créer les trois instances en une seule déclaration. Ainsi, toute modification commune (taille, image, règles) se fait à un seul endroit — le module — et s'applique aux trois.

Exercice 3Défi

Une équipe veut partager un module « réseau standard » entre cinq projets différents. Quelles bonnes pratiques mets-tu en place ?

Voir une solution

(1) Placer le module dans un dépôt dédié (ou un registre de modules), pas dupliqué dans chaque projet ; (2) le versionner (tags sémantiques) et, dans chaque projet, épingler une version précise pour des déploiements reproductibles — on met à jour volontairement ; (3) le documenter (README : rôle, variables d'entrée, outputs) ; (4) garder une interface claire et stable (peu de variables, bien nommées) pour ne pas casser les projets consommateurs à chaque évolution ; (5) idéalement, le tester. Le module devient un petit produit réutilisable, maintenu une fois pour tous.
