Module 03 · Pratique — Leçon 06

Capstone — décrire une infra complète

~40 min Intermédiaire Tout le cours

À la fin de cette leçon, tu sauras

  • assembler providers, ressources et modules ;
  • paramétrer par variables et exposer des outputs ;
  • structurer pour plusieurs environnements ;
  • décliner une même infra proprement d'un environnement à l'autre.
Sommaire de la leçon

Étape charnière : assembler les briques en une infrastructure complète, propre et réutilisable. On décrit un réseau, un serveur web, une base — paramétrés, factorisés en modules, déclinables par environnement. C'est la synthèse des trois premiers modules.

La structure d'un projet

Un projet Terraform soigné sépare les responsabilités : une configuration racine qui assemble, des modules réutilisables, des variables par environnement.

Assembler les modules

La configuration racine devient un assemblage lisible : le réseau, puis le serveur qui s'y rattache, paramétrés par des variables.

Nomme tes ressources par environnement

Un nom qui inclut l'environnement (web-${var.env}) évite les collisions et rend chaque ressource identifiable d'un coup d'œil (web-dev, web-prod). Petit détail, grand confort en exploitation.

Trois façons de gérer les environnements

Ici, on décline par fichiers de valeurs (dev.tfvars, prod.tfvars) sur un même code — simple et explicite. Deux autres approches existent : les workspaces Terraform (un même dossier, plusieurs states nommés) et un dossier par environnement (isolation maximale, au prix de duplication). Le bon choix dépend du besoin d'isolation : plus les environnements divergent, plus on sépare.

Et après ?

Tu sais décrire une infrastructure en code, la factoriser en modules et la décliner par environnement. Les leçons suivantes de ce cours approfondissent la vie d'une infra en équipe et en production : le state à distance et le travail collaboratif (leçon 07), les boucles count/for_each (leçon 08), le cycle de vie et les dépendances (leçon 09), la sécurité et les secrets (leçon 10), avant un projet de synthèse complet (leçon 11).

Pour aller plus loin

La compétence durable n'est pas la syntaxe d'un outil, mais le réflexe : décrire l'infra en code versionné, raisonner en état désiré, lire le plan, factoriser. Ces principes valent pour Terraform comme pour tout autre outil d'IaC.

Cas réel — le main.tf de 2000 lignes

Une équipe plateforme gérait toute son infra dans un unique fichier et un seul state. Le moindre changement replanifiait des centaines de ressources ; un jour, un renommage maladroit a détruit des ressources sans rapport, faute de relire un plan devenu illisible. La sortie de crise : découper en modules par domaine (réseau, calcul, données), avec des states séparés. Résultat : des plans courts et lisibles, un rayon d'impact réduit, et l'arrivée d'un nouveau venu qui comprend l'infra module par module. La structure n'est pas cosmétique : c'est ce qui rend une infra en code sûre à faire évoluer.

Renommer une ressource = la détruire puis la recréer

Terraform suit chaque ressource par son adresse dans le state. Renommer un bloc (ou le déplacer d'un module à l'autre) fait croire à l'outil que l'ancienne a disparu (destroy) et qu'une nouvelle apparaît (create) — exactement le drame du cas réel ci-dessus. La parade : un bloc moved { } (ou terraform state mv) qui dit « c'est la même, elle a juste changé de nom ». Et toujours lire le plan : un destroy inattendu s'y voit.

Glossaire

Configuration racine
Le dossier depuis lequel on lance Terraform ; il assemble les modules, déclare les variables et expose les outputs.
Module
Dossier de configuration réutilisable, paramétré par des variables (entrées) et exposant des outputs (sorties) : l'équivalent d'une fonction.
Output
Valeur exposée par une configuration ou un module (une IP, une URL) ; se lit depuis la racine via module.<nom>.<sortie>.
Variable
Entrée d'une configuration ou d'un module ; c'est elle qu'on fait varier d'un environnement à l'autre.
Composition
Assembler plusieurs modules en passant la sortie de l'un (ex. l'id du réseau) en entrée d'un autre.
Idempotence
Réappliquer la même configuration ne change rien si l'état est déjà conforme : on peut relancer apply sans crainte.
État désiré
La cible décrite dans le code ; l'outil calcule les actions nécessaires pour amener le réel jusqu'à elle (approche déclarative).
Arborescence
Organisation des fichiers d'un projet Terraform : une racine (main/variables/outputs), un dossier modules/ et des fichiers *.tfvars par environnement.

Récap et vérification

  • Un projet propre = racine qui assemble + modules réutilisables + variables par environnement.
  • On relie les modules par leurs outputs (ex. l'id du réseau passé au serveur).
  • Même code, valeurs différentes par environnement ; plan avant apply.
  • Déclaratif, idempotent, secrets hors code, state protégé.
