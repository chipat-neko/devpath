Module 02 · Structurer — Leçon 05

Environnements & bonnes pratiques

~35 min Intermédiaire Leçon 04

À la fin de cette leçon, tu sauras

  • gérer plusieurs environnements à partir du même code ;
  • comparer les stratégies de séparation ;
  • appliquer les bonnes pratiques Terraform ;
  • intégrer l'IaC dans un pipeline CI/CD.
Sommaire de la leçon

On veut souvent plusieurs environnements — développement, pré-production, production — qui se ressemblent, mais avec des tailles et des budgets différents. L'IaC excelle ici : un même code, paramétré par environnement, garantit qu'ils restent cohérents.

Le besoin : des jumeaux paramétrés

L'idéal est que la pré-production soit un jumeau de la production, en plus petit : même structure, valeurs différentes (tailles réduites, moins de répliques). Ainsi, ce qu'on teste en pré-prod reflète vraiment la prod. Le pire est d'avoir des environnements qui ont divergé à force de bricolages manuels.

Les stratégies de séparation

Trois approches courantes pour gérer les environnements :

  • Variables par environnement : un même code, un fichier .tfvars par environnement (dev.tfvars, prod.tfvars). Simple et explicite.
  • Dossiers par environnement : un dossier dev/, prod/, chacun appelant les mêmes modules avec ses valeurs. Très lisible, states bien séparés.
  • Workspaces : plusieurs states pour une même config. Pratique pour des cas simples, mais à éviter si les environnements diffèrent beaucoup.

Du code partagé, des valeurs séparées

Le principe commun à toutes les stratégies : le même code (et les mêmes modules) pour tous les environnements, seules les variables changent. C'est ce qui garantit la cohérence — et c'est tout l'intérêt de l'IaC.

Les bonnes pratiques

  • Versionner tout le code dans Git ; jamais le state en clair ni les secrets.
  • State distant verrouillé, séparé par environnement.
  • terraform fmt et terraform validate systématiques (idéalement automatiques).
  • Toujours lire le plan avant apply, surtout les destructions.
  • Modules pour factoriser ; versions épinglées (providers et modules).
  • Secrets hors du code (variables sensibles, gestionnaire de secrets).
  • Revue de code des changements d'infra, comme pour l'applicatif.

Le state n'est pas un fichier anodin

Le state peut contenir des valeurs sensibles en clair (mots de passe générés, clés). Ne le commite jamais dans Git : garde-le dans un backend distant chiffré et verrouillé, séparé par environnement.

L'IaC dans le pipeline CI/CD

La maturité consiste à n'appliquer l'infra que depuis le pipeline (revoir le cours CI/CD), jamais depuis un poste. Un schéma classique : à chaque proposition de changement, le pipeline lance plan et l'affiche pour revue ; une fois approuvé et fusionné, il lance apply. Traçabilité, sécurité et cohérence maximales.

Cas réel — l'opération manuelle qui a coûté cher

En janvier 2017, un ingénieur de GitLab.com, en pleine nuit et sous pression pendant un incident, tape une commande de suppression directement sur le mauvais serveur de base de données de production : ~300 Go effacés, puis cinq méthodes de sauvegarde découvertes défaillantes. Six heures de données perdues. La leçon retenue et partagée publiquement : on n'opère pas à la main en production. L'IaC pilotée par un pipeline (plan revu, apply automatisé et tracé) supprime exactement ce type de manœuvre risquée.

Le plan en revue, l'apply automatisé

Afficher le plan dans la revue de code rend le changement d'infrastructure visible et discutable avant d'être appliqué. C'est le pendant infra de la revue de code applicative.

Pièges fréquents

  • Environnements divergents. Si dev et prod ont des codes différents, on ne teste pas vraiment la prod ; partage le code, sépare les variables.
  • Appliquer depuis son poste en prod. Pas de traçabilité, risque d'erreur ; passe par la CI.
  • Oublier fmt/validate. Le code dérive en qualité ; automatise-les.
  • Un seul state géant. Lent et risqué ; sépare par environnement et par périmètre.

Pour aller plus loin

Des outils dédiés (Terragrunt, ou les fonctions des plateformes CI) aident à gérer proprement de nombreux environnements et états sans copier-coller. Mais commence simple : code partagé + fichiers de variables par environnement couvre déjà la grande majorité des besoins.

Pour aller plus loin

La politique en code (policy as code) permet de vérifier automatiquement qu'un plan respecte des règles (« pas de stockage public », « chiffrement obligatoire ») avant l'apply. La sécurité devient un test, pas une relecture manuelle.

Glossaire

Environnement
Instance complète de l'infrastructure dédiée à un usage : développement, pré-production (test) ou production (les vrais utilisateurs).
Pré-production (staging)
Jumeau réduit de la production servant à valider un changement avant de le déployer : fidèle seulement s'il partage le même code.
.tfvars
Fichier de valeurs de variables, un par environnement (dev.tfvars, prod.tfvars), passé avec -var-file.
Workspace
Mécanisme Terraform qui associe plusieurs states à une même configuration ; pratique pour des cas simples, à éviter si les environnements divergent beaucoup.
Dérive (drift)
Écart entre l'infrastructure réelle et le code, dû à des modifications manuelles ; un plan la révèle, un apply la corrige.
Pipeline CI/CD
Chaîne automatisée qui, à chaque changement, lance fmt/validate/plan, affiche le plan en revue, puis apply après fusion.
Policy as code
Règles de conformité écrites en code (« pas de stockage public », « chiffrement obligatoire ») vérifiées automatiquement sur le plan avant l'apply.
Revue de plan
Lecture du plan par un pair avant application, comme une revue de code : rend le changement d'infra visible et discutable.

Récap et vérification

  • Plusieurs environnements = même code, valeurs différentes (par variables/dossiers/workspaces).
  • Bonnes pratiques : versionner, state distant verrouillé, fmt/validate, lire le plan, modules, secrets hors code, revue.
  • Maturité : appliquer l'infra depuis le pipeline CI/CD, plan en revue, apply automatisé.
  • Garde les environnements cohérents ; sépare les states.

Vérifie ta compréhension

  1. Quel principe commun aux stratégies d'environnements ?
  2. Pourquoi appliquer depuis la CI plutôt que son poste ?
  3. Cite trois bonnes pratiques Terraform.

Exercices

Exercice 1Échauffement

Comment appliques-tu la même configuration avec les valeurs de production rangées dans prod.tfvars ?

Voir une solution

Le code et les modules sont partagés ; seules les valeurs du fichier de variables changent d'un environnement à l'autre.

Exercice 2Application

Pourquoi une pré-production qui aurait « divergé » de la production (réglages modifiés à la main) est-elle un problème ?

Voir une solution

Parce qu'elle ne reflète plus la production : ce qu'on y teste ne garantit plus rien pour la prod (« ça marchait en pré-prod… »). Les bugs liés à la configuration passent inaperçus. L'IaC évite cela en gardant un code partagé : la pré-prod est un jumeau paramétré, recréable à l'identique, qui ne dérive pas.

Exercice 3Défi

Décris un flux CI/CD simple pour appliquer des changements d'infrastructure Terraform en toute sécurité.

Voir une solution

Un flux classique : (1) un développeur ouvre une proposition de changement (pull request) modifiant le code Terraform ; (2) la CI lance automatiquement terraform fmt -check, validate puis plan, et affiche le plan dans la PR ; (3) un collègue revoit le code et le plan (notamment les destructions) ; (4) après approbation et fusion sur la branche principale, la CI lance terraform apply sur l'environnement cible, en utilisant le state distant verrouillé et des identifiants gérés par le pipeline ; (5) éventuellement, un déploiement manuel approuvé (gate) pour la production. Avantages : chaque changement est tracé, revu, appliqué de façon unique et reproductible — personne n'applique « à la main » en prod.
