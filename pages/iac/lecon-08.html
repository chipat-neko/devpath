Module 04 · IaC en production — Leçon 08

Boucles et conditions : count, for_each et dynamic

~36 min Intermédiaire Leçons 02 à 04 conseillées

À la fin de cette leçon, tu sauras

  • créer plusieurs ressources avec count et for_each ;
  • choisir entre les deux et éviter le décalage d'indices ;
  • transformer des données avec les expressions et les conditions ;
  • générer des blocs répétés avec dynamic.
Sommaire de la leçon

Copier-coller un bloc de ressource pour créer trois serveurs presque identiques, c'est du code qui dérive vite. Terraform propose des méta-arguments — count et for_each — pour créer plusieurs ressources à partir d'un seul bloc, plus des expressions pour calculer les valeurs. C'est ce qui fait passer un code d'infra de « bricolage » à « industriel ».

count : répéter par un nombre

Le méta-argument count crée N copies d'une ressource. À l'intérieur, count.index donne le numéro (0, 1, 2…), utile pour différencier chaque copie.

Terraform crée aws_instance.web[0], [1] et [2]. On les référence par leur indice. count sert aussi d'interrupteur : count = var.actif ? 1 : 0 crée la ressource… ou pas.

for_each : répéter par une collection

for_each crée une ressource par élément d'un ensemble ou d'une map. À l'intérieur, each.key et each.value donnent la clé et la valeur courantes. Les instances sont alors identifiées par une clé nommée, pas par un numéro.

Ici Terraform crée aws_instance.web["web"], ["api"], ["db"]. Chaque instance porte une clé stable qui ne dépend pas de l'ordre.

Piège fréquent

Premier réflexe en découvrant for_each : lui passer une liste, comme ["web", "api"]. Terraform refuse : il attend une map ou un ensemble de chaînes, car ses clés doivent être uniques et connues dès le plan. Convertis avec for_each = toset(var.noms), ou passe directement une map quand tu veux choisir toi-même les clés.

count ou for_each ?

La règle pratique : for_each dès que les éléments ont une identité (un nom, un rôle). Réserve count aux cas « N copies vraiment identiques » ou à l'interrupteur 0/1. La raison est dans le schéma ci-dessus : count indexe par position, donc supprimer un élément au milieu recrée inutilement les suivants ; for_each indexe par clé, donc les autres restent intacts.

Le piège du décalage d'indices

Avec count, une liste ["web", "api", "db"] crée [0], [1], [2]. Si tu retires "api", "db" passe de l'indice [2] à [1] : Terraform voit un changement d'identité et veut détruire puis recréer une ressource pourtant inchangée. Sur une base de données, c'est une catastrophe. for_each avec des clés nommées évite complètement ce piège.

Les expressions : for et conditions

Une expression for transforme une collection en une autre, comme une compréhension de liste. Une expression conditionnelle condition ? a : b choisit une valeur. Elles calculent les valeurs que count/for_each et les ressources consomment.

dynamic : générer des blocs répétés

Certaines ressources contiennent des blocs imbriqués répétés (règles de pare-feu, volumes…). Plutôt que de les écrire à la main, dynamic les génère à partir d'une collection.

Cas réel — cinq serveurs copiés-collés

Un motif que l'on croise souvent en revue de code : cinq blocs resource "aws_instance" quasi identiques, différant par un nom et une taille, empilés à la main. Ajouter un environnement ? On recopie un sixième bloc et on prie pour n'avoir rien oublié. La refonte tient en une idée : décrire les serveurs dans une map ({ web = "t3.micro", api = "t3.small", … }) et un seul bloc for_each. Le code fond de 80 lignes à 8, ajouter un serveur devient une ligne de map, et les clés nommées évitent les recréations accidentelles. La donnée est séparée de la logique : c'est exactement l'esprit de l'IaC.

Dans le doute, for_each

Neuf fois sur dix, ce que tu crées « en plusieurs exemplaires » a une identité : un nom d'environnement, un rôle, une zone. Choisis alors for_each et des clés parlantes. Garde count pour deux cas seulement : N copies réellement interchangeables, ou l'interrupteur count = var.actif ? 1 : 0.

Pour aller plus loin

for_each ne s'applique pas qu'aux ressources : on peut le poser sur un module (leçon 04) pour instancier tout un ensemble de ressources par clé — par exemple un module « compte applicatif » décliné par équipe. Combiné aux expressions for et aux fonctions (merge, toset, lookup), on décrit des infrastructures entières de façon compacte et pilotée par les données.

Glossaire

Méta-argument
Argument spécial accepté par (presque) toutes les ressources : count, for_each, depends_on, provider, lifecycle.
count
Crée N instances d'une ressource à partir d'un nombre ; les instances sont indexées par position ([0], [1]…).
count.index
Numéro (0, 1, 2…) de l'instance courante dans une ressource utilisant count.
for_each
Crée une instance par élément d'un ensemble ou d'une map ; les instances sont identifiées par une clé nommée stable.
each.key / each.value
Clé et valeur de l'élément courant dans une ressource utilisant for_each.
Expression for
Construit une nouvelle collection à partir d'une autre : [for x in liste : expression].
Expression conditionnelle
Choix ternaire condition ? valeur_si_vrai : valeur_si_faux.
Bloc dynamic
Génère des blocs imbriqués répétés à partir d'une collection, via for_each et content.

Récap et vérification

  • count crée N copies indexées par position ; for_each une par élément, indexée par clé nommée.
  • Préfère for_each dès qu'il y a une identité : on évite le décalage d'indices et les recréations.
  • Les expressions (for, condition) calculent les valeurs consommées par les ressources.
  • dynamic génère des blocs imbriqués répétés sans copier-coller.

Exercices

Exercice 1Échauffement

Crée trois buckets S3 nommés d'après une liste d'environnements ["dev", "staging", "prod"], avec for_each.

Voir une solution

toset(...) transforme la liste en ensemble, ce qu'attend for_each. Chaque bucket est identifié par une clé stable (["dev"], ["staging"], ["prod"]) : retirer un environnement plus tard ne touchera pas les autres.

Exercice 2Application

Une ressource utilise count = length(var.noms) avec var.noms = ["web", "api", "db"]. Un collègue retire "api" du milieu de la liste. Pourquoi le plan montre-t-il des recréations, et comment l'éviter ?

Voir une solution

Avec count, les instances sont [0]="web", [1]="api", [2]="db". En retirant "api", la liste devient ["web", "db"] : "db" passe de l'indice [2] à [1]. Terraform associe les ressources par indice : il voit que [1] était "api" et est maintenant "db", donc il veut modifier/recréer [1], et supprimer [2]. Résultat : une ressource inchangée ("db") est recréée pour rien. La correction est de passer à for_each = toset(var.noms) : les instances deviennent ["web"], ["api"], ["db"]. Retirer "api" ne fait que supprimer ["api"] ; ["web"] et ["db"] restent intacts, car leur clé n'a pas bougé. C'est la raison numéro un de préférer for_each pour tout ce qui a une identité.

Exercice 3Défi

Tu veux ouvrir un nombre variable de ports sur un groupe de sécurité, selon une variable var.ports (liste). Écris la règle avec dynamic et explique l'intérêt par rapport à des blocs écrits à la main.

Voir une solution

Le bloc dynamic "ingress" génère un bloc ingress par port présent dans var.ports. L'intérêt : le nombre de règles n'est plus figé dans le code. Ajouter un port, c'est ajouter une valeur à la variable — pas copier un bloc. Le même module sert alors à des cas qui ouvrent 1, 3 ou 10 ports, sans duplication ni risque d'oublier un champ dans l'une des copies. On a séparé la donnée (quels ports) de la logique (comment créer une règle), ce qui rend le code réutilisable et lisible.
