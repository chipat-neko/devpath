Terraform : providers & ressources

~35 min Intermédiaire Leçon 01

À la fin de cette leçon, tu sauras

  • lire la structure d'un fichier HCL ;
  • configurer un provider ;
  • déclarer des ressources et les relier ;
  • dérouler le workflow init / plan / apply.
Sommaire de la leçon

Entrons dans le concret. Une configuration Terraform est un ensemble de fichiers .tf écrits en HCL, composés de blocs. Trois blocs suffisent pour démarrer : la configuration de Terraform, le provider, et les ressources.

La forme d'un bloc

Le HCL s'organise en blocs type "étiquettes" { … } contenant des paires clé = valeur. C'est lisible et déclaratif :

Le bloc terraform déclare les providers nécessaires (et leur version) ; le bloc provider les configure (région, identifiants…).

Le provider

Un provider est le plugin qui permet à Terraform de piloter une plateforme : un cloud, un service DNS, une base… C'est lui qui « sait parler » à l'API du fournisseur. Terraform est indépendant du fournisseur justement grâce à ces providers interchangeables.

Épingle la version du provider

Sans contrainte de version, un init peut récupérer une nouvelle version majeure du provider qui change des comportements par défaut : ton prochain plan propose alors des changements que tu n'as pas demandés. Fige la version (version = "~> 1.0") et commite le fichier de verrouillage .terraform.lock.hcl.

Les ressources

Une ressource déclare un élément d'infrastructure : son type (défini par le provider), un nom local, et ses attributs.

Les dépendances se déduisent toutes seules

En référant cloud_network.principal.id dans le serveur, tu crées une dépendance implicite : Terraform comprend qu'il doit créer le réseau avant le serveur. Tu n'ordonnes rien : il construit le graphe de dépendances à partir des références.

Cas réel — l'ordre qui posait problème

Avant Terraform, une équipe créait son infra avec un script maison qui lançait le serveur puis le réseau. De temps en temps, la création du serveur échouait : le réseau n'existait pas encore (une course). En passant au déclaratif, l'ordre se déduit des références : le réseau d'abord, le serveur ensuite — et les ressources indépendantes se créent en parallèle, donc plus vite. Le graphe supprime toute une classe de bugs d'orchestration.

Lire l'existant : les data sources

Parfois, on a besoin d'informations sur des ressources existantes (une image système, un réseau déjà créé) sans les gérer soi-même. Un bloc data les lit pour les utiliser dans sa configuration, sans les modifier.

Le workflow : init, plan, apply

Trois commandes rythment le travail :

Toujours lire le plan

plan est ton filet de sécurité : il liste exactement ce que apply ferait. Relis-le avant d'appliquer — surtout les lignes de destruction (un changement anodin peut entraîner la recréation d'une ressource).

Pièges fréquents

  • Oublier init. Sans lui, les providers ne sont pas installés ; rien ne marche.
  • Appliquer sans lire le plan. On peut détruire par mégarde ; le plan prévient.
  • Ordonner les ressources à la main. Inutile : les références suffisent à déduire l'ordre.
  • Fixer une version de provider trop floue. Épingle la version (~>) pour éviter les surprises de mise à jour.

Pour aller plus loin

terraform fmt formate ton code (indentation, alignement) et terraform validate vérifie sa cohérence avant même le plan. Deux commandes à lancer souvent — idéalement automatiquement — pour garder une base propre.

Pour aller plus loin

Le graphe de dépendances que Terraform construit lui permet aussi de paralléliser les créations indépendantes. Tu écris une description ; il optimise l'exécution.

Glossaire

HCL
HashiCorp Configuration Language, le langage déclaratif de Terraform, organisé en blocs type "étiquettes" { … }.
Bloc
Unité de base d'un fichier .tf : un type, des étiquettes qui le nomment, et un corps de paires clé = valeur.
Provider
Plugin qui traduit les déclarations Terraform en appels d'API d'une plateforme ; on le déclare dans terraform {} et le configure dans provider {}.
Ressource
Élément d'infrastructure géré par Terraform, déclaré par resource "type" "nom" { … }.
Data source
Bloc data qui lit des informations sur une ressource existante sans la gérer ni la modifier.
Dépendance implicite
Lien déduit quand une ressource référence un attribut d'une autre : Terraform en tire l'ordre de création.
Graphe de dépendances
Représentation des liens entre ressources que Terraform construit pour ordonner et paralléliser les opérations.
Workflow init / plan / apply
Les trois temps du travail : préparer le dossier, prévisualiser les changements, puis les appliquer.

Récap et vérification

  • Un fichier .tf est fait de blocs HCL : terraform, provider, resource.
  • Le provider permet de piloter une plateforme ; il rend Terraform indépendant du fournisseur.
  • Une ressource a un type, un nom et des attributs ; les références créent les dépendances.
  • Workflow : init → plan (aperçu) → apply ; lis toujours le plan.

Exercice 2Application

Dans quel ordre Terraform créera-t-il un réseau et un serveur si le serveur référence l'id du réseau ? Pourquoi ?

Voir une solution

D'abord le réseau, puis le serveur. En référençant cloud_network.principal.id dans le serveur, on crée une dépendance implicite : Terraform sait que le réseau doit exister (et avoir un id) avant de pouvoir créer le serveur. Il déduit cet ordre du graphe de dépendances, sans qu'on l'ordonne explicitement.

Exercice 3Défi

Tu lances terraform apply et le plan annonce, en plus de la modification voulue, la destruction puis recréation d'une base de données. Que fais-tu ?

Voir une solution

On n'applique pas tel quel : recréer une base détruirait ses données. C'est le rôle du plan d'avoir révélé ce replace. Démarche : (1) comprendre pourquoi — un attribut « forçant la recréation » (force-new) a changé (ex. on a modifié une propriété immuable comme la région ou le moteur) ; (2) chercher une alternative qui ne force pas la recréation (modifier autrement, ou faire la migration en deux temps) ; (3) si la recréation est inévitable, prévoir une sauvegarde/restauration des données et une fenêtre de maintenance ; éventuellement utiliser des mécanismes de protection (empêcher la destruction accidentelle). La règle : tout plan qui détruit une ressource avec état (base, volume) mérite un examen attentif avant apply.
