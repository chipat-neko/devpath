Module 04 · IaC en production — Leçon 10

Sécurité, secrets et conformité

~36 min Avancé Leçons 03 et 07 conseillées

À la fin de cette leçon, tu sauras

  • masquer une valeur avec sensitive et connaître ses limites ;
  • sortir les secrets du code vers un gestionnaire de secrets ;
  • appliquer le moindre privilège aux identifiants du provider ;
  • vérifier automatiquement avec la policy as code et les scanners.
Sommaire de la leçon

Décrire l'infrastructure en code apporte un immense confort — mais aussi une surface de risque nouvelle : un mot de passe oublié dans un fichier, un identifiant tout-puissant, une règle de sécurité qu'on croyait appliquée. Cette leçon rassemble les réflexes qui font qu'une infra en code reste sûre : cacher ce qui doit l'être, garder les secrets hors du dépôt, restreindre les droits, et vérifier automatiquement avant tout apply.

sensitive : masquer une valeur… à l'affichage

L'attribut sensitive = true demande à Terraform de ne pas afficher une valeur dans le plan, la sortie CLI ou les logs. À la place, on lit (sensitive value). C'est utile pour un mot de passe généré, une clé, un jeton exposé en output :

Les secrets ne vivent pas dans le code

La règle d'or : aucun secret en clair dans un fichier versionné. Un mot de passe collé dans un .tf committé sur Git y reste pour toujours dans l'historique, même après suppression. La bonne approche : stocker le secret dans un gestionnaire de secrets (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault…) et le lire au moment du besoin via un data source.

Le state contient les secrets en clair

Même en lisant un secret depuis un coffre, sa valeur finit écrite en clair dans le fichier d'état. C'est pourquoi le state (vu en leçon 07) doit vivre dans un backend chiffré (chiffrement au repos), à accès restreint, et jamais dans Git. Traite ton state comme un secret à part entière.

Le moindre privilège pour les identifiants

Terraform agit avec les droits que tu lui donnes. La tentation est d'utiliser un compte « administrateur de tout », parce que « ça marche à coup sûr ». Mais si ces identifiants fuitent — dans un log de CI, un poste compromis — l'attaquant hérite des mêmes pouvoirs. Le moindre privilège consiste à n'accorder que les droits strictement nécessaires :

  • un rôle par projet / par environnement, limité à ses ressources ;
  • des identifiants temporaires (OIDC en CI, rôle assumé) plutôt que des clés longues durée ;
  • rotation régulière et révocation immédiate en cas de doute.

Vérifier automatiquement : policy as code

Comment garantir qu'aucune configuration ne viole une règle (« pas de stockage public », « chiffrement obligatoire », « tags imposés ») ? En écrivant ces règles… en code. La policy as code évalue le plan avant l'apply et le bloque s'il enfreint une politique. Deux moteurs répandus : Sentinel (HashiCorp, intégré à Terraform Cloud) et OPA/Conftest (Open Policy Agent, ouvert, langage Rego).

Scanner le code : tfsec, checkov

Avant même d'écrire ses propres politiques, on peut lancer un scanner de sécurité qui connaît des centaines de mauvaises configurations classiques : chiffrement manquant, port ouvert au monde entier, journaux désactivés… Les plus connus sont tfsec, checkov et trivy. Marque sensitive dès la variable

Dès qu'une variable porte un secret (mot de passe, clé, jeton), ajoute-lui sensitive = true. Sa valeur se propage : si un output l'expose sans le marquer, Terraform refuse le plan plutôt que d'afficher un secret. Mieux vaut cette erreur nette qu'un mot de passe étalé dans les logs de la CI.

Cas réel — la clé oubliée dans un dépôt

En 2016, des attaquants ont trouvé des identifiants d'accès au cloud dans un dépôt de code privé d'Uber. Ces clés donnaient accès à un stockage contenant les données personnelles de 57 millions d'utilisateurs et chauffeurs. La fuite n'était pas un exploit sophistiqué : juste un secret rangé au mauvais endroit, avec des droits trop larges. Les trois parades de cette leçon l'auraient évitée : secrets hors du code (dans un coffre), moindre privilège (des clés limitées à ce stockage précis), et secret scanning qui alerte dès qu'une clé apparaît dans un commit.

Pour aller plus loin

La sécurité de l'IaC touche aussi la chaîne d'approvisionnement : épingle la version de tes providers et modules, et fais confiance au fichier .terraform.lock.hcl (les empreintes vérifiées). Un module public modifié en amont ne doit pas pouvoir changer ton infra sans que tu le décides. Ajoute à cela la détection de drift (écart entre le code et le réel) et tu couvres l'essentiel : qui peut agir, avec quoi, et à quelles conditions.

Antisèche

Glossaire

sensitive
Attribut qui empêche l'affichage d'une valeur dans le plan, la CLI et les logs ; la valeur reste en clair dans le state.
Gestionnaire de secrets
Service (Vault, AWS Secrets Manager, Azure Key Vault) qui stocke les secrets et les distribue à la demande ; lu via un data source.
Moindre privilège
Principe consistant à n'accorder à un identifiant que les droits strictement nécessaires à sa tâche.
Policy as code
Règles de conformité écrites en code et évaluées automatiquement sur le plan, qui bloquent un apply non conforme.
Sentinel
Moteur de politiques de HashiCorp, intégré à Terraform Cloud/Enterprise.
OPA / Rego
Open Policy Agent : moteur de politiques ouvert et son langage de règles, Rego (utilisable via Conftest).
Scanner IaC
Outil d'analyse statique (tfsec, checkov, trivy) qui repère les mauvaises configurations dans le code Terraform.
Secret scanning
Détection automatique de secrets (clés, mots de passe) apparaissant dans les commits d'un dépôt.

Récap et vérification

  • sensitive masque l'affichage d'une valeur, mais elle reste en clair dans le state (à chiffrer et restreindre).
  • Les secrets vivent dans un coffre ; le code n'en contient qu'une référence, jamais la valeur.
  • On applique le moindre privilège aux identifiants du provider (rôles limités, temporaires, tournés).
  • On vérifie automatiquement : policy as code (Sentinel/OPA) et scanners (tfsec/checkov) en CI, avant l'apply.

Vérifie ta compréhension

  1. Que protège sensitive, et que ne protège-t-il pas ?
  2. Où doit vivre un mot de passe de base de données ?
  3. À quel moment la policy as code bloque-t-elle une configuration ?

Exercices

Exercice 1Échauffement

Tu exposes en output le mot de passe généré d'une base. Écris l'output pour que Terraform ne l'affiche pas en clair.

Voir une solution

Sans sensitive = true, Terraform refuse même le plan quand la valeur provient d'un champ sensible : il ne veut pas étaler un secret dans la sortie. Avec l'attribut, la CLI affiche (sensitive value). Attention : la valeur reste lisible dans le state — d'où l'importance d'un backend chiffré.

Exercice 2Application

Une base a besoin d'un mot de passe. Un collègue propose de l'écrire directement dans main.tf « juste pour le prototype ». Explique le risque et propose une meilleure approche.

Voir une solution

Le risque : un secret committé, même sur un dépôt privé, reste à vie dans l'historique Git — un simple retrait ultérieur ne l'efface pas. Il peut fuiter via un fork, un accès élargi, un poste compromis. « Le prototype » devient trop souvent la prod.

Le code décrit où trouver le secret, jamais le secret. En dépannage rapide, on peut aussi passer par une variable d'environnement TF_VAR_db_password — hors dépôt — plutôt qu'une valeur en dur.

Exercice 3Défi

Ton équipe veut garantir qu'aucun bucket de stockage public ne sera jamais déployé, sans avoir à le vérifier à la main à chaque revue. Comment mettre en place cette barrière ?

1. Un scanner (tfsec ou checkov) connaît déjà la règle « bucket public » et la signale : un job de CI qui échoue sur une alerte HIGH bloque la fusion.
