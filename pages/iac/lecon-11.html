Module 05 · Projet — Leçon 11

Projet — une infrastructure modulaire de bout en bout

~42 min Avancé Tout le cours

À la fin de cette leçon, tu sauras

  • assembler un module réutilisable paramétré par variables ;
  • déployer plusieurs environnements avec for_each ;
  • brancher un backend distant et protéger le state ;
  • réaliser ton mini-projet fil rouge de bout en bout.
Sommaire de la leçon

Voici le projet de synthèse : réunir tout le cours en une infrastructure propre, réutilisable et sûre. On construit un module de service web paramétré, on le décline sur plusieurs environnements avec for_each, on protège son state dans un backend distant, et on soigne le cycle de vie. C'est la démonstration que les briques des modules 01 à 04 s'emboîtent en un tout cohérent.

Le cahier des charges

On veut un service web (un serveur rattaché à un réseau) décliné sur plusieurs environnements — dev, staging, prod — avec ces exigences :

  • un module unique décrit le service, paramétré par des variables ;
  • les environnements sont produits par for_each (pas de copier-coller) ;
  • le state vit dans un backend distant verrouillé ;
  • la base de prod est protégée (prevent_destroy) et le mot de passe hors du code.

Structurer le projet

Une racine qui assemble, un module réutilisable, un backend distant, des valeurs par environnement :

Un module de service, décliné par for_each

La racine appelle un seul module service, mais autant de fois qu'il y a d'environnements, grâce à for_each : chaque clé (dev, staging, prod) devient une instance nommée, sans décalage d'indices.

Nomme tes ressources par environnement

Un nom qui inclut l'environnement (web-${each.key}) évite les collisions et rend chaque ressource identifiable d'un coup d'œil (web-dev, web-prod). Petit détail, grand confort en exploitation.

Livrer sans casser

Le cycle sûr, vu tout au long du cours : on écrit le code, on lance un plan qui lit le state distant, on relit le plan (surtout les destructions), on fait relire en revue, puis on apply — le verrou garantissant qu'un seul apply modifie le state à la fois.

Mini-projet fil rouge — ton infrastructure en code

À toi de jouer ! Décris (en HCL, sans cloud réel requis) une petite infrastructure complète, modularisée, déclinée par environnement via for_each et protégée. L'objectif est la structure et la cohérence, pas un déploiement effectif.

Ce que tu vas construire

Une configuration Terraform : un module service (réseau + serveur), instancié pour dev/staging/prod avec for_each, un backend distant verrouillé, un output des URLs par environnement, la prod protégée (prevent_destroy) et le mot de passe hors du code. Le tout déclaratif, idempotent, sans secret en dur.

Étapes

1. Le module

Un module service (réseau + serveur), avec variables d'entrée (nom, taille) et outputs (url).

2. La racine + for_each

Une map d'environnements passée à for_each ; nommage par each.key ; outputs des URLs.

3. State & protection

Un backend distant chiffré et verrouillé ; prevent_destroy sur la prod ; secret lu, pas codé en dur.

Mini-projetCapstone

Écris ta configuration. Quand tu as essayé, déplie une solution de référence.

Voir une solution de référence

Résultat : un seul code décrit trois environnements. Ajouter preprod = une ligne dans la map, sans toucher aux autres instances (force de for_each). Le state part dans le backend distant ; on lance plan puis apply.

Et après ?

Tu sais décrire une infrastructure en code, la factoriser en modules, la décliner par environnement, protéger son state et sa sécurité. Les suites naturelles : brancher l'apply au pipeline CI/CD, généraliser la policy as code (leçon 10), tester les modules, et orchestrer plusieurs configurations. L'IaC est la 4ᵉ étape du parcours DevOps : conteneur → cluster → CI/CD → infrastructure en code.

Pour aller plus loin

La compétence durable n'est pas la syntaxe d'un outil, mais le réflexe : décrire l'infra en code versionné, raisonner en état désiré, lire le plan, factoriser, protéger le state et les secrets. Ces principes valent pour Terraform comme pour OpenTofu, Pulumi ou tout autre outil d'IaC.

Cas réel — reconstruire à l'identique

Le 28 février 2017, une panne majeure de la région AWS us-east-1 (service S3) a paralysé des pans entiers du web. La leçon retenue par beaucoup d'équipes : une infrastructure décrite en code se recrée ailleurs. Le même module, appliqué avec d'autres valeurs (nouvelle région, tailles adaptées), rebâtit un environnement équivalent en minutes — là où une infra montée à la main aurait demandé des jours et beaucoup de mémoire humaine.

Antisèche

Glossaire

Configuration racine
Le dossier depuis lequel on lance Terraform ; il assemble les modules, déclare les variables et expose les outputs.
Module
Dossier de configuration réutilisable, paramétré par des variables (entrées) et exposant des outputs (sorties) : l'équivalent d'une fonction.
for_each
Méta-argument qui instancie une ressource ou un module une fois par clé d'une map/set ; instances stables, identifiées par each.key.
Backend distant
Stockage partagé du state (S3, GCS, Terraform Cloud), souvent chiffré et verrouillé, pour le travail en équipe.
Verrouillage (lock)
Mécanisme qui empêche deux apply simultanés de modifier le même state : le second attend son tour.
Composition
Assembler plusieurs modules en passant la sortie de l'un en entrée d'un autre, depuis la racine.
Idempotence
Réappliquer la même configuration ne change rien si l'état est déjà conforme : on peut relancer apply sans crainte.
Capstone
Projet de synthèse en fin de cours qui réunit toutes les notions : ici, un service web modulaire, décliné par environnement et protégé.

Récap et vérification

  • Un projet propre = racine qui assemble + module réutilisable + variables par environnement.
  • for_each décline un module sur N environnements sans copier-coller ni décalage d'indices.
  • Le state vit dans un backend distant chiffré et verrouillé ; la prod est protégée.
  • Déclaratif, idempotent, secrets hors code ; plan avant apply.

Vérifie ta compréhension

  1. Pourquoi for_each plutôt que count pour des environnements ?
  2. Qu'est-ce qui change entre dev et prod ?
  3. Quelle est la compétence IaC la plus durable ?

Exercices

Exercice 1Échauffement

Dans la racine, appelle le module ./modules/service pour deux environnements (dev, prod) avec for_each, en nommant chaque serveur d'après l'environnement.

Voir une solution

La map { dev = "small", prod = "large" } produit deux instances : service["dev"] et service["prod"]. On lit chaque clé avec each.key (le nom) et sa valeur avec each.value (la taille).

Exercice 2Application

Expose en output l'URL de chaque environnement, sous forme d'une map { dev = "…", prod = "…" }.

Voir une solution

Avec for_each, module.service devient une map indexée par clé. Une expression for (leçon 08) parcourt module.service et bâtit { dev = url_dev, prod = url_prod }. On obtient d'un coup toutes les URLs, sans les lister à la main.

Exercice 3Défi

On veut que seule la prod soit protégée par prevent_destroy, pas dev ni staging. Or prevent_destroy n'accepte pas une variable directement. Propose une approche.

Voir une solution

C'est un piège classique : prevent_destroy doit être une valeur littérale (connue avant le plan), on ne peut pas y mettre var.env == "prod". Deux stratégies :

1. Séparer la ressource sensible. On sort la base dans un module dédié, appelé seulement pour la prod (via for_each filtré ou un module distinct), où prevent_destroy = true est écrit en dur.

2. S'appuyer sur les droits. En complément, on retire à l'identifiant CI le droit de supprimer la base de prod (moindre privilège, leçon 10) : même un code fautif ne peut pas la détruire.

La bonne réponse mélange souvent les deux : un garde-fou dans le code (prevent_destroy) et un garde-fou dans les permissions. La défense en profondeur ne repose jamais sur une seule ligne.
