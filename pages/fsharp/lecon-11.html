Les computation expressions

~55 min Avancé Prérequis : leçons 6-7

À la fin de cette leçon, tu sauras

  • comprendre le problème que résolvent les computation expressions ;
  • générer des séquences avec seq { } et yield ;
  • écrire de l'asynchrone linéaire avec async { } et let! ;
  • lire une expression result et le rôle de let! et return.
Sommaire de la leçon

Certains calculs portent un contexte : une valeur peut être absente (option), asynchrone (async), multiple (seq) ou faillible (Result). Les enchaîner à la main devient vite illisible : imbrications, vérifications répétées à chaque étape. Les computation expressions — les blocs xxx { } — masquent cette plomberie : on écrit un code linéaire, et le bloc s'occupe du contexte.

Le problème : la pyramide

Enchaîner trois étapes qui renvoient chacune un option produit une « pyramide » de match : chaque étape doit vérifier si la précédente a réussi.

La logique utile (calculer) se noie dans la plomberie (vérifier Some/None). C'est exactement ce que les computation expressions suppriment.

seq { } : générer des séquences

Le bloc seq { } construit une séquence paresseuse. yield émet un élément ; on peut mêler boucles, conditions et yield librement.

async { } : l'asynchrone linéaire

Le bloc async { } décrit un calcul asynchrone. La clé est let! : il attend le résultat d'une opération asynchrone sans bloquer le thread, puis poursuit. On lit le tout comme du code séquentiel.

let! et return : la mécanique

Dans un bloc de computation, deux mots-clés font tout le travail. let! x = e déballe la valeur de son contexte (il attend l'async, extrait le Some, prend la branche Ok…). return v remballe une valeur dans ce même contexte. Reprenons l'exemple de la pyramide, avec un bloc result :

Cas réel

L'async { } de F# est arrivé en 2007, cinq ans avant le async/await de C# (2012) qu'il a directement inspiré : la même idée d'écrire l'asynchrone en ligne droite. Aujourd'hui, les serveurs web F# (Giraffe, Saturn) et les pipelines de données reposent massivement sur ces blocs. Le bloc result, lui, vient de la bibliothèque FsToolkit.ErrorHandling et sert à chaîner des validations métier : on lit une règle de gestion sans une seule vérification manuelle de Ok/Error.

D'où viennent ces blocs ?

Chaque bloc xxx { } est piloté par un objet builder qui définit ce que signifient let! (méthode Bind), return (Return), yield (Yield)… Le compilateur traduit le bloc en appels à ces méthodes. seq et async sont fournis par F# ; result/option viennent de bibliothèques ; et tu peux définir ton propre builder.

Pièges fréquents

Piège fréquent

Un async { } ne démarre pas tout seul : c'est une description de calcul, « froide ». Tant qu'on ne le lance pas (Async.RunSynchronously, Async.Start, ou un let! depuis un autre async), rien ne se passe. C'est une différence avec les Task de .NET, qui démarrent immédiatement. Et rappelle-toi : let! n'a de sens qu'à l'intérieur d'un bloc de computation.

Pour aller plus loin

Pour aller plus loin

Il existe d'autres mots-clés : yield! aplatit une sous-séquence, do! attend un calcul sans valeur de retour, use! déballe puis libère une ressource, et match! déballe avant de filtrer. Le bloc task { } sert à interopérer avec les Task de .NET (pour appeler des bibliothèques C# asynchrones). Enfin, définir son propre builder permet de créer un mini-langage adapté à un domaine.

Antisèche

Glossaire

Computation expression
Bloc xxx { } qui masque la plomberie d'un contexte (absence, asynchronisme, séquence, erreur) pour écrire un code linéaire.
let! (bind)
Déballe la valeur portée par le contexte : attend l'async, extrait le Some, prend la branche Ok. Traduit en appel à Bind.
return
Remballe une valeur ordinaire dans le contexte du bloc (par ex. dans un async ou un Ok).
seq
Bloc produisant une séquence paresseuse ; les éléments sont calculés à la demande via yield.
async
Bloc décrivant un calcul asynchrone « froid » : il faut le lancer explicitement pour qu'il s'exécute.
yield
Émet un élément dans une séquence ; yield! insère les éléments d'une sous-séquence.
Builder
Objet définissant le sens de let!, return, yield (méthodes Bind, Return, Yield). C'est lui qui donne vie à un bloc xxx { }.

Récap et vérification

  • Les computation expressions suppriment la plomberie d'un contexte : on écrit du code linéaire.
  • seq { } génère des séquences paresseuses avec yield.
  • async { } + let! donnent un asynchrone lisible, sans imbrication de rappels.
  • let! déballe la valeur du contexte, return la remballe ; un builder définit ce sens.
