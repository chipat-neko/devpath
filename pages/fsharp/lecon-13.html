Module 4 · Aller plus loin en F# — Leçon 13

Structurer et tester un projet F#

~50 min Avancé Prérequis : leçon 9

À la fin de cette leçon, tu sauras

  • créer et lancer un projet avec dotnet ;
  • comprendre la règle de l'ordre des fichiers en F# ;
  • organiser le code en modules et namespaces ;
  • écrire un test et découvrir les tests de propriétés.
Sommaire de la leçon

Passer d'un script d'apprentissage à un vrai projet demande trois choses : savoir comment dotnet gère un projet (le fichier .fsproj), connaître la règle d'or de F# — l'ordre des fichiers compte — et organiser le code en modules et namespaces. On termine par les tests, dont les remarquables tests de propriétés.

Du script au projet

Un fichier .fsx est un script, exécuté directement par dotnet fsi (l'interpréteur interactif). Un .fsproj est un projet compilé, avec dépendances et point d'entrée. On en crée un en une commande :

La règle d'or : l'ordre des fichiers

En F#, la compilation se fait strictement de haut en bas, et les fichiers sont compilés dans l'ordre listé par le .fsproj. Conséquence : une définition doit apparaître avant son utilisation. On ne peut pas appeler quelque chose défini « plus loin ».

Cette contrainte paraît sévère, mais c'est un atout : elle rend les dépendances cycliques impossibles. On lit un projet F# du haut vers le bas comme une démonstration : chaque brique s'appuie sur les précédentes.

Modules et namespaces

Un module regroupe des définitions (fonctions, types, valeurs) ; on y accède par Module.fonction. Un namespace regroupe des modules et des types à travers plusieurs fichiers — mais il ne peut pas contenir de valeurs directement.

Écrire des tests

Un projet de test référence le projet principal. F# peut utiliser xUnit ou NUnit, mais possède aussi Expecto, une bibliothèque pensée pour lui, où les tests sont… de simples valeurs.

Les tests de propriétés (FsCheck)

Plutôt que d'écrire des exemples un par un, on énonce une propriété qui doit tenir pour toutes les entrées ; FsCheck génère alors des centaines de cas aléatoires pour tenter de la mettre en défaut.

Si une propriété échoue, FsCheck réduit le contre-exemple à sa plus petite forme (par ex. la liste [0]), ce qui pointe droit vers le bug.

Cas réel

FsCheck est le portage .NET de QuickCheck, l'outil né en Haskell qui a popularisé les tests de propriétés. En finance et dans l'outillage, on l'emploie pour des propriétés dites de « round-trip » : décoder (encoder x) = x pour un sérialiseur ou un parseur. Ce type de test débusque des cas limites — chaîne vide, caractères Unicode, très grands nombres — qu'une poignée d'exemples écrits à la main laisse passer. Un seul énoncé remplace des dizaines de cas de test.

Pièges fréquents

Piège fréquent

Réordonner les fichiers du .fsproj « par ordre alphabétique » casse la compilation : un fichier qui en utilise un autre doit venir après lui. L'ordre est intentionnel, respecte-le. Autre piège : écrire un let x = 3 directement sous un namespace — interdit, car un namespace n'accueille que des modules et des types. Mets la valeur dans un module.

Pour aller plus loin

Pour aller plus loin

La CLI dotnet couvre tout le cycle : build, run, test, pack (publier un paquet NuGet). Une solution (.sln) regroupe plusieurs projets (app + tests + bibliothèque). Dans un script .fsx, #r "nuget: FsCheck" charge une dépendance et #load "Fichier.fs" inclut un fichier — pratique pour prototyper avant de créer un vrai projet.

Glossaire

.fsproj
Fichier de projet F# (XML) : il liste les fichiers source (dans l'ordre de compilation) et les dépendances.
.fsx / dotnet fsi
Un script F# et l'interpréteur interactif qui l'exécute ; idéal pour prototyper sans créer de projet.
Ordre des fichiers
Règle F# : la compilation va de haut en bas et suit l'ordre du .fsproj ; une définition précède toujours son usage, ce qui interdit les cycles.
module
Regroupe des définitions (fonctions, types, valeurs), accessibles par Module.nom.
namespace
Regroupe des modules et types à travers plusieurs fichiers ; ne contient pas de valeurs directement.
dotnet test
Commande qui compile et exécute la suite de tests d'un projet.
Test de propriété
Test qui énonce une règle valable pour toutes les entrées ; un outil (FsCheck) l'éprouve sur de nombreux cas aléatoires et réduit tout contre-exemple.
Expecto
Bibliothèque de test pensée pour F#, où les tests sont de simples valeurs composables.

Récap et vérification

  • dotnet new/run/test et dotnet fsi pour les scripts.
  • La règle d'or : l'ordre des fichiers du .fsproj compte ; pas de cycles.
  • module regroupe des fonctions ; namespace chapeaute des modules.
  • Les tests de propriétés (FsCheck) éprouvent une règle sur des centaines de cas.
