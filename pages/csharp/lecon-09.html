Exceptions et gestion d'erreurs

~33 min Intermédiaire Leçon 8 recommandée

À la fin de cette leçon, tu sauras

  • savoir utiliser try/catch/finally et attraper des types d'exceptions précis du plus spécifique au plus général ;
  • savoir lever une exception avec throw et la re-lever sans perdre la pile (throw; et non throw e;) ;
  • savoir libérer des ressources automatiquement avec using et l'interface IDisposable ;
  • savoir créer ses propres exceptions et appliquer les bonnes pratiques (ne pas avaler, préférer TryParse).
Sommaire de la leçon

Un programme rencontre forcément des situations anormales : un fichier introuvable, une saisie qui n'est pas un nombre, une division par zéro, une connexion réseau qui tombe. En C#, ces situations se signalent avec des exceptions. Une exception n'est pas un simple code d'erreur que tu pourrais oublier de vérifier : c'est un objet qui interrompt le flux normal du programme et remonte la pile d'appels jusqu'à ce que quelqu'un la prenne en charge.

Bien gérer les exceptions, c'est écrire un code qui ne plante pas brutalement face à l'imprévu, qui libère ses ressources et qui donne des messages utiles. Dans cette leçon, tu apprends à attraper, lever, filtrer et créer des exceptions, et à utiliser using pour ne jamais oublier de fermer un fichier.

Une exception interrompt le flux

Quand une instruction échoue, le runtime .NET crée un objet exception et arrête l'exécution à cet endroit. Si rien ne l'attrape, l'exception remonte toute la pile d'appels (la suite des méthodes qui se sont appelées) et le programme s'arrête en affichant le type, le message et la trace de pile.

Trois informations à retenir dans ce message : le type (IndexOutOfRangeException) te dit quoi, le message te dit pourquoi, et la pile (at ... line 2) te dit où. Ces trois éléments sont ta première source d'information pour déboguer.

try / catch / finally

Pour reprendre la main sur une exception, on entoure le code risqué d'un bloc try et on traite le problème dans un catch. Le bloc finally, optionnel, s'exécute toujours, qu'il y ait eu une exception ou non.

On peut enchaîner plusieurs catch pour réagir différemment selon le type. L'ordre compte : il faut aller du plus spécifique au plus général, car le premier catch compatible gagne. Mettre catch (Exception) en premier masquerait tous les autres ; le compilateur signale d'ailleurs les catch rendus inaccessibles.

Le filtre when permet d'affiner : le catch ne s'active que si la condition est vraie. C'est plus lisible que de tester à l'intérieur du bloc, et l'exception continue son chemin si la condition est fausse.

La hiérarchie des exceptions

Toutes les exceptions héritent de la classe Exception. C'est cette hiérarchie qui rend possible le « du plus spécifique au plus général » : un catch (Exception) attrape tout, parce que tout en descend. Voici les types que tu croiseras le plus :

  • ArgumentException et ses dérivés ArgumentNullException, ArgumentOutOfRangeException : un argument reçu est invalide.
  • InvalidOperationException : l'objet est dans un état où l'opération n'a pas de sens (ex. lire une file vide).
  • NullReferenceException : accès à un membre sur une référence null (à éviter, pas à attraper).
  • FormatException, OverflowException : conversion ou calcul impossibles.
  • IOException, FileNotFoundException : problèmes d'entrée/sortie et de fichiers.

Note

La NullReferenceException n'est presque jamais à attraper mais à éviter : elle révèle un oubli de vérification. Les nullable reference types (le ? et l'opérateur !) t'aident à repérer ces cas dès la compilation.

Lever une exception avec throw

Tu lèves toi-même une exception avec throw quand une règle de ton code est violée. Mieux vaut un type précis avec un message clair qu'un retour silencieux que l'appelant pourrait ignorer.

Un point subtil mais essentiel : quand tu re-lèves une exception attrapée, écris throw; seul, et jamais throw e;. La version throw e; réinitialise la pile d'appels à la ligne courante, et tu perds l'endroit d'origine du problème.

using et IDisposable : libérer les ressources

Certains objets détiennent des ressources externes (un fichier ouvert, une connexion, un socket) qu'il faut libérer explicitement. Ces objets implémentent l'interface IDisposable et exposent une méthode Dispose(). Le bloc using garantit que Dispose() est appelé même si une exception survient — c'est un finally automatique.

Depuis C# 8, le using declaration évite l'indentation : pas d'accolades, la ressource est libérée à la fin du bloc englobant (souvent la méthode).

Astuce

Dès que tu vois un type avec une méthode Dispose() (fichiers, connexions de base de données, flux réseau), prends le réflexe du using. Tu n'oublieras plus jamais de fermer une ressource, et le code reste correct même quand une exception interrompt le traitement.

Créer ses propres exceptions

Pour des erreurs métier spécifiques à ton domaine, crée une classe qui hérite de Exception. Cela permet à l'appelant de l'attraper précisément, sans la confondre avec une erreur technique. La convention veut que le nom finisse par Exception.

Bonnes pratiques

Quelques règles transforment une gestion d'erreurs fragile en code robuste :

  • Ne pas avaler une exception : un catch vide cache le bug au lieu de le résoudre. Au minimum, journalise-la.
  • Messages utiles : explique ce qui a échoué et avec quelles valeurs, pas juste « erreur ».
  • Pas de flux normal par exception : lever et attraper coûte cher et brouille la logique. Une exception est pour l'exceptionnel.
  • Préférer TryParse quand l'échec est attendu (saisie utilisateur) : elle renvoie un booléen au lieu de lever.

Un cas réel : l'exception qui a détruit une fusée

Cas réel

Le 4 juin 1996, le vol inaugural de la fusée Ariane 5 s'est autodétruit une quarantaine de secondes après le décollage. La cause : un logiciel de navigation réutilisé d'Ariane 4 a tenté de convertir une vitesse horizontale (un flottant 64 bits) en entier 16 bits. La valeur, bien plus grande sur Ariane 5, a provoqué un dépassement — l'équivalent d'une OverflowException. Or cette conversion n'était pas protégée : l'exception non gérée a arrêté le calculateur de bord, la fusée a dévié puis s'est détruite. Coût : environ 370 millions de dollars. La morale de cette leçon en une image : une exception ignorée ne disparaît pas, elle ressurgit plus loin — ici, littéralement.

Pièges fréquents

Piège fréquent

Un catch (Exception) au corps vide « avale » l'erreur : le programme continue comme si de rien n'était, mais le vrai problème reste invisible et resurgira plus loin, plus difficile à diagnostiquer. Si tu ne sais pas quoi faire d'une exception, ne l'attrape pas.

Piège fréquent

Écrire throw e; pour re-lever écrase la trace de pile : tu verras la ligne du catch au lieu de l'origine réelle du bug. Utilise toujours throw; seul. De même, oublier le using sur un fichier laisse la ressource ouverte si une exception survient avant le Close() manuel.

Glossaire

Exception
Objet signalant une situation anormale ; elle interrompt le flux et remonte la pile jusqu'à un catch.
Pile d'appels (stack trace)
Suite des méthodes appelées menant au point d'erreur ; affichée avec le type et le message pour localiser le bug.
try / catch / finally
try entoure le code risqué, catch traite un type d'exception, finally s'exécute toujours.
throw; vs throw e;
throw; re-lève l'exception courante en gardant sa pile d'origine ; throw e; la réinitialise et masque l'origine.
Filtre when
Condition attachée à un catch : le bloc ne s'active que si elle est vraie, sinon l'exception poursuit sa route.
IDisposable / using
Interface exposant Dispose() pour libérer une ressource ; using l'appelle automatiquement, même en cas d'exception.
Exception personnalisée
Classe héritant de Exception pour une erreur métier précise, attrapable spécifiquement (nom en …Exception).
TryParse
Méthode qui tente une conversion et renvoie un bool au lieu de lever : idéale quand l'échec est attendu (saisie).

Récap et vérification

  • Une exception interrompt le flux et remonte la pile : retiens son type, son message et sa trace.
  • try/catch/finally : attrape du plus spécifique au plus général, affine avec when, et le finally s'exécute toujours.
  • throw lève une exception ; throw; la re-lève sans perdre la pile (jamais throw e;).
  • using et IDisposable libèrent automatiquement les ressources, même en cas d'exception.
  • Crée des exceptions métier en héritant de Exception ; n'avale rien, préfère TryParse pour les saisies.

Vérifie ta compréhension

  1. Pourquoi faut-il placer les catch du plus spécifique au plus général, et que se passe-t-il si catch (Exception) arrive en premier ?
  2. Quelle est la différence concrète entre throw; et throw e; dans un bloc catch ?
  3. Que garantit le bloc using qu'un simple appel manuel à Dispose() ne garantit pas ?
