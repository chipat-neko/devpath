Module 06 · C# en pratique : le web — Leçon 18

Données avec Entity Framework Core

~40 min Intermédiaire Leçon 17 (ASP.NET) recommandée

À la fin de cette leçon, tu sauras

  • définir un DbContext et des modèles (entités) ;
  • créer et appliquer des migrations ;
  • écrire des requêtes LINQ traduites en SQL ;
  • brancher EF Core sur une API ASP.NET.
Sommaire de la leçon

Une API qui garde ses données dans une List en mémoire les perd au redémarrage. Pour les persister, on branche une base de données — et en .NET, on le fait avec Entity Framework Core (EF Core), l'ORM officiel. Tu écris des classes C# et des requêtes LINQ que tu connais déjà ; EF Core les traduit en SQL et gère la base. C'est l'aboutissement naturel de la leçon précédente : une vraie API qui stocke ses données.

Installer EF Core

EF Core s'ajoute via des paquets NuGet. Pour apprendre, le fournisseur SQLite (une base dans un simple fichier) est idéal : zéro installation de serveur.

Le modèle et le DbContext

Deux pièces : une entité (une classe = une table) et un DbContext (la session avec la base, qui expose les tables sous forme de DbSet).

EF Core déduit beaucoup par convention : une propriété Id devient la clé primaire, le DbSet<Produit> nommé Produits devient la table. Tu décris ton modèle en C# ; la structure SQL en découle.

Les migrations

À partir de tes classes, EF Core génère le SQL qui crée et fait évoluer la base : ce sont les migrations, versionnées dans ton dépôt.

Chaque changement du modèle (ajouter une propriété, une entité) se traduit par une nouvelle migration : l'historique du schéma vit dans Git, et la base se recrée à l'identique partout. Fini le SQL appliqué à la main.

Des requêtes en LINQ

Le grand confort : on interroge la base avec LINQ (vu au module collections), pas avec des chaînes SQL. EF Core traduit ta requête LINQ en SQL et te renvoie des objets C# typés.

Point clé : SaveChangesAsync() est ce qui écrit en base. EF Core suit les changements de tes objets et les applique d'un coup, dans une transaction. Les versions asynchrones (...Async) s'intègrent parfaitement à l'API de la leçon 17.

Brancher EF Core sur l'API

On enregistre le DbContext dans l'injection de dépendances, et les endpoints le reçoivent automatiquement — exactement comme n'importe quel service.

Tu as maintenant une API complète et persistante : ASP.NET pour le web, EF Core pour les données, le tout typé et asynchrone. C'est l'architecture standard d'un service .NET en production.

Piège fréquent

Oublier SaveChangesAsync() après une modification : Add, Remove ou un changement de propriété ne touchent que les objets en mémoire tant que tu n'as pas sauvegardé ; rien n'est écrit en base. Autre piège classique, le N+1 : charger une liste puis accéder à une relation dans une boucle déclenche une requête par élément. Utilise Include(...) pour charger les relations en une fois, et surveille le SQL généré (EF peut le journaliser).

Pour aller plus loin

En production, on passe de SQLite à SQL Server ou PostgreSQL en changeant simplement le fournisseur et la chaîne de connexion : ton code LINQ ne bouge pas. EF Core gère aussi les relations (un-à-plusieurs, plusieurs-à-plusieurs), le chargement différé, les transactions explicites et les requêtes SQL brutes (FromSql) pour les cas pointus. Comme pour tout ORM, ta connaissance du SQL reste précieuse pour comprendre ce qu'EF génère et l'optimiser.

Un cas réel : la migration oubliée en production

Cas réel

Une équipe développait avec une base SQLite locale, recréée à volonté : en dev, tout roulait. Mais personne n'avait branché dotnet ef database update dans le pipeline de déploiement. Un jour, une migration ajoute une colonne Stock à Produit. En dev, aucun souci. En production, la nouvelle version du code interroge une colonne qui n'existe pas encore : chaque appel /produits renvoie une erreur 500 — SqliteException: no such column: Stock. La base de prod était restée au schéma d'avant : le code avait avancé, pas le schéma. Correctif immédiat : appliquer la migration. Correctif durable : ajouter dotnet ef database update (ou context.Database.Migrate() au démarrage) au pipeline, pour que schéma et code progressent toujours ensemble. Les migrations ne servent à rien si on oublie de les appliquer là où ça compte.

Glossaire

ORM
Mapping objet-relationnel : une couche (ici EF Core) qui fait correspondre des objets C# à des tables SQL, et traduit tes opérations en requêtes.
Entité
Classe C# dont chaque instance correspond à une ligne d'une table ; ses propriétés deviennent les colonnes (une propriété Id = clé primaire par convention).
DbContext
Objet représentant la session avec la base : il expose les tables sous forme de DbSet et pilote la lecture, l'écriture et le suivi des changements.
DbSet<T>
Propriété du contexte représentant une table (une collection d'entités) sur laquelle on écrit ses requêtes LINQ.
Migration
Fichier généré à partir du modèle, décrivant une évolution du schéma ; versionné dans Git et appliqué à la base par database update.
Suivi des modifications (change tracking)
Mécanisme par lequel EF Core mémorise l'état de chaque objet chargé (Added, Modified, Deleted) pour n'écrire que le nécessaire au SaveChanges.
SaveChangesAsync()
Méthode qui applique réellement en base, dans une transaction, tous les changements suivis ; sans elle, Add/Remove/modifications restent en mémoire.
Problème N+1
Anti-pattern où charger une liste puis accéder à une relation dans une boucle déclenche une requête par élément ; Include(...) charge tout en une fois.

Récap et vérification

  • EF Core : une entité = une table, un DbContext = la session (avec des DbSet).
  • Les migrations (dotnet ef migrations add / database update) versionnent le schéma.
  • On interroge en LINQ (traduit en SQL) ; SaveChangesAsync() écrit réellement en base.
  • Le DbContext s'injecte dans les endpoints : API ASP.NET + EF Core = service persistant complet.
