Génériques et collections

~35 min Intermédiaire Leçon 9 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire des classes et méthodes génériques avec un paramètre de type comme <T> ;
  • savoir poser une contrainte avec where T : IComparable<T> ;
  • savoir utiliser les collections clés du framework : List<T>, Dictionary<TKey, TValue>, HashSet<T> ;
  • savoir reconnaître IEnumerable<T> et choisir la collection adaptée à ton besoin.
Sommaire de la leçon

Tu as sûrement déjà croisé des types comme List<int> ou Dictionary<string, int> sans forcément savoir ce que signifient ces chevrons. Ce sont des génériques (en anglais generics) : un mécanisme qui permet d'écrire du code typé et réutilisable. Plutôt qu'une classe pour les listes de chaînes, une autre pour les listes d'entiers, etc., tu écris une classe paramétrée par un type.

Dans cette leçon, on part du problème que les génériques résolvent, puis on construit progressivement : classes et méthodes génériques, contraintes, et surtout les collections du framework System.Collections.Generic que tu utiliseras tous les jours. On finit par IEnumerable<T>, l'abstraction qui fait fonctionner foreach et LINQ.

Le problème : du code non typé avec object

Avant les génériques, pour écrire une structure « universelle », on stockait tout dans le type de base object, l'ancêtre commun de tous les types. On pouvait y mettre n'importe quoi, mais à la lecture il fallait caster (convertir) à la main, et rien n'empêchait de se tromper.

Le compilateur ne voit aucune erreur : le bug n'explose qu'à l'exécution.

C'est exactement ce qu'on veut éviter : une erreur de type devrait être détectée par le compilateur, pas par tes utilisateurs en production. Les génériques déplacent ces erreurs de l'exécution vers la compilation, et évitent au passage les casts.

Classes et méthodes génériques

Une classe générique déclare un paramètre de type entre chevrons, juste après son nom. Par convention on le nomme T (pour type), ou TKey/TValue quand il y en a plusieurs. Ce T est un « trou » qu'on remplira à l'usage.

Le compilateur garantit que Boite<string> ne contiendra que des string.

C'est exactement le mécanisme de List<T> ou Dictionary<TKey, TValue> : une seule définition, instanciée avec des types différents. Remarque la méthode générique Premier<T> : le type est déduit de l'argument, tu n'as pas besoin de l'écrire à l'appel.

Note

Contrairement à Java, les génériques C# fonctionnent aussi avec les types valeur : List<int> est parfaitement valide et performant (pas de « boxing »). Les => de l'exemple sont des membres en corps d'expression : une façon courte d'écrire une méthode d'une seule ligne.

Les contraintes : encadrer T avec where

Parfois, T ne doit pas être n'importe quel type : on veut pouvoir appeler certaines méthodes dessus. Une contrainte, introduite par le mot-clé where, restreint les types acceptés. La plus utile en pratique est where T : IComparable<T>, qui garantit qu'on peut comparer deux T.

Sans la contrainte, v.CompareTo(...) ne compilerait pas : un T quelconque n'a pas cette méthode.

Il existe d'autres contraintes utiles : where T : class (T doit être un type référence), where T : struct (un type valeur), where T : new() (T a un constructeur sans argument, ce qui autorise new T()). On peut même les combiner.

La collection reine : List<T>

List<T> est une liste à taille variable, la collection que tu utiliseras le plus. On y ajoute avec Add, on accède par indexeur liste[i], on connaît sa taille avec Count, et on la parcourt avec foreach.

Une List<T> grandit toute seule : pas besoin de prévoir sa taille comme un tableau.

Note bien : sur une List<T> on lit le nombre d'éléments avec Count, alors qu'un tableau (int[]) utilise Length. C'est une confusion classique sur laquelle on revient dans les pièges.

Associer des clés à des valeurs : Dictionary<TKey, TValue>

Un Dictionary<TKey, TValue> stocke des paires clé → valeur et offre un accès quasi instantané par la clé. Attention : lire une clé absente avec l'indexeur lève une KeyNotFoundException. La bonne pratique est TryGetValue, ou ContainsKey avant de lire.

TryGetValue renvoie un booléen et place la valeur dans la variable out : aucun risque d'exception.

Note

Un Dictionary n'a pas d'ordre garanti par contrat : ne te repose jamais sur l'ordre des paires lors d'un foreach. Si l'ordre d'insertion compte, conserve les clés à part (par exemple dans une List<TKey>).

Unicité et files : HashSet, Queue, Stack

Le framework offre d'autres collections génériques selon ton besoin. HashSet<T> garantit l'unicité : un même élément ne peut y figurer qu'une fois. Queue<T> est une file premier entré, premier sorti (FIFO), Stack<T> une pile dernier entré, premier sorti (LIFO).

HashSet ignore les doublons ; Queue et Stack imposent l'ordre de sortie.

IEnumerable<T> : tout ce qu'on peut parcourir

Toutes ces collections ont un point commun : elles implémentent IEnumerable<T>, l'interface qui signifie « une séquence qu'on peut parcourir élément par élément ». C'est elle qui rend foreach possible, et c'est sur elle que repose LINQ (la leçon suivante). En typant un paramètre par IEnumerable<T>, ta méthode accepte n'importe quelle séquence : liste, tableau, ensemble…

Une seule méthode, trois types d'entrée : l'abstraction IEnumerable<T> les unifie.

Choisir la bonne collection et l'initialiser

Le bon réflexe est de choisir la collection selon ton besoin d'accès : liste ordonnée et indexée → List<T> ; recherche par clé → Dictionary<TKey, TValue> ; garantir l'unicité → HashSet<T> ; traiter dans l'ordre d'arrivée → Queue<T> ou Stack<T>. Les initialiseurs de collection permettent de remplir tout ça en une expression, sans appeler Add ligne par ligne.

Plus court et plus lisible qu'une série d'appels à Add.

Un cas réel : la bonne collection change tout

Cas réel

Une équipe devait dédupliquer un fichier de plusieurs millions d'adresses e-mail. La première version testait chaque adresse avec liste.Contains(email) dans une boucle : or List<T>.Contains reparcourt toute la liste à chaque appel (coût proportionnel à sa taille). Résultat : un traitement qui grimpait à plusieurs heures et semblait figé. En remplaçant la List par un HashSet<string> — dont le test d'appartenance est quasi instantané grâce au hachage — le même travail est tombé à quelques secondes. Choisir la bonne collection n'est pas un détail : c'est parfois la différence entre une nuit de calcul et un clin d'œil.

Pièges fréquents

Piège fréquent

Utiliser les vieilles collections non génériques comme ArrayList ou Hashtable (espace System.Collections). Elles stockent des object et ramènent les casts et les InvalidCastException du début de leçon. Utilise toujours List<T> et Dictionary<TKey, TValue>.

Piège fréquent

Lire une clé absente d'un Dictionary avec l'indexeur (dico["x"]) : cela lève une KeyNotFoundException. Préfère TryGetValue ou teste avec ContainsKey avant de lire.

Piège fréquent

Modifier une collection (ajouter ou retirer) pendant qu'on la parcourt avec foreach lève une InvalidOperationException. Parcours une copie, ou utilise une boucle for à rebours. Et ne confonds pas List.Count (collections) avec Array.Length (tableaux) : ce sont deux noms différents pour la même idée.

Pour aller plus loin

Pour aller plus loin

LINQ (leçon suivante) ajoute des opérations puissantes — Where, Select, GroupBy — sur tout IEnumerable<T>. Explore aussi IReadOnlyList<T> pour exposer une collection sans permettre sa modification, les collections concurrentes (ConcurrentDictionary) pour le multithread, et yield return pour produire une séquence paresseusement. La question de la complexité (combien coûte un accès, un ajout) est traitée dans le cours Algorithmique.

Glossaire

Générique
Code paramétré par un type : une seule définition réutilisable pour int, string… avec vérification à la compilation.
Paramètre de type (T)
« Trou » de type déclaré entre chevrons après le nom (Boite<T>) ; rempli à l'usage (Boite<string>).
Contrainte (where)
Restriction sur T (class, struct, new(), une interface…) autorisant certaines opérations dessus.
List<T>
Liste ordonnée à taille variable ; accès par indice, nombre d'éléments via Count (pas Length).
Dictionary<TKey, TValue>
Association clé → valeur à accès rapide ; lire une clé absente lève, d'où TryGetValue.
HashSet<T>
Ensemble sans doublon ; Add renvoie false si l'élément existe déjà, test d'appartenance quasi instantané.
IEnumerable<T>
Interface « séquence qu'on peut parcourir » ; socle de foreach et de LINQ, commune à toutes les collections.
Initialiseur de collection
Remplissage entre accolades à la création (new List<int> { 1, 2, 3 }) ; évite une série d'appels à Add.

Récap et vérification

  • Les génériques (<T>) apportent un typage vérifié à la compilation et suppriment les casts.
  • Une contrainte where T : IComparable<T> autorise à appeler des méthodes sur T.
  • List<T> : liste indexée (Add, liste[i], Count) ; Dictionary<TKey, TValue> : clé → valeur (TryGetValue).
  • HashSet<T> garantit l'unicité ; Queue (FIFO) et Stack (LIFO) imposent l'ordre.
  • IEnumerable<T> est l'abstraction commune « une séquence à parcourir » : base de foreach et de LINQ.

Vérifie ta compréhension

  1. Pourquoi une List<string> évite-t-elle l'InvalidCastException qu'on risquait avec une boîte à object ?
  2. Tu veux lire une valeur dans un Dictionary sans risquer d'exception si la clé est absente : quelle méthode utilises-tu ?
  3. Quelle collection choisis-tu pour t'assurer qu'aucune valeur n'apparaît deux fois, et pourquoi ?
