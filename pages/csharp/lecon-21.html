Sécurité du null : types références nullables

~32 min Avancé Leçon 08 recommandée

À la fin de cette leçon, tu sauras

  • Comprendre d'où vient la NullReferenceException et pourquoi elle a coûté si cher ;
  • Activer le contexte nullable et distinguer string (non-null) de string? ;
  • Utiliser les opérateurs ?., ??, ??= et l'opérateur « pardon » ! à bon escient ;
  • Suivre l'analyse de flux du compilateur et migrer un code existant vers le nullable.
Sommaire de la leçon

Il existe une erreur que tout développeur C# a rencontrée : System.NullReferenceException: Object reference not set to an instance of an object. On croit tenir un objet ; en réalité la variable vaut null, et déréférencer null fait planter le programme à l'exécution. Son inventeur, Tony Hoare, a appelé le null son « erreur à un milliard de dollars », tant les bugs, plantages et failles qu'il a causés se chiffrent en fortune.

Depuis C# 8, le langage propose une parade : les types références nullables (nullable reference types). L'idée est de rendre le null visible dans le type — donc vérifiable par le compilateur avant l'exécution. Cette leçon montre comment activer cette sécurité, l'exploiter avec les bons opérateurs, et migrer du code existant sans tout casser.

Le problème du null

Historiquement, en C#, n'importe quel type référence (string, une classe, un tableau) pouvait valoir null, sans que rien ne l'indique. Le type string mentait : il promettait une chaîne mais pouvait cacher un null. Le bug ne se révélait qu'au moment fatal du déréférencement.

Le compilateur ne voyait rien : le crash arrivait chez l'utilisateur. L'objectif du contexte nullable est de transformer ce plantage d'exécution en un simple avertissement de compilation, corrigé une bonne fois pendant l'écriture.

Activer le contexte nullable

Dans les projets .NET récents (.NET 6 et suivants), le contexte est activé par défaut dans le fichier .csproj. On peut aussi le piloter fichier par fichier avec une directive.

Une fois le contexte actif, string signifie « chaîne garantie non nulle » et string? signifie « chaîne peut-être nulle ». Le point d'interrogation fait partie du type, exactement comme int? pour les types valeur.

Les opérateurs du null

Quatre opérateurs rendent le code concis face au null. L'accès conditionnel ?. court-circuite : si la partie gauche est null, toute l'expression vaut null au lieu de planter. La coalescence ?? fournit une valeur de repli. Sa variante ??= affecte seulement si la variable est null.

Le compilateur suit le flux

Le plus puissant : le compilateur pratique une analyse de flux. Il connaît à chaque ligne l'état d'une variable — peut-être null ou sûrement non null — et met à jour cet état au fil des tests. Après un if qui écarte le null, la variable est « rétrécie » (narrowing) en non-null : plus d'avertissement, sans opérateur.

Astuce

Le retour anticipé (if (x is null) return;, ou une exception) en début de méthode est le style le plus lisible : on écarte les cas nuls d'entrée, et tout le reste de la méthode travaille sur des valeurs garanties. ArgumentNullException.ThrowIfNull(x) (.NET 6+) fait cette garde en une ligne et informe le compilateur que x est non-null ensuite.

L'opérateur « pardon » et ses dangers

Parfois tu sais qu'une valeur n'est pas null alors que le compilateur en doute encore. L'opérateur null-forgiving ! (dit « pardon ») fait taire l'avertissement : valeur! affirme « fais-moi confiance, ce n'est pas null ». C'est une promesse, pas une vérification : si tu te trompes, la NullReferenceException revient à l'exécution.

Piège fréquent

L'opérateur ! ne corrige rien : il désactive le filet de sécurité à cet endroit précis. Chaque ! est une dette : tu affirmes au compilateur quelque chose qu'il ne peut plus vérifier pour toi. Réserve-le aux cas où tu as une garantie hors du champ de vision du compilateur (un framework qui initialise un champ par réflexion, par exemple), et documente pourquoi. Le semer partout revient à revenir à l'ère d'avant le nullable.

Champs, propriétés et initialisation

Un champ non-nullable doit recevoir une valeur avant la fin du constructeur, sinon le compilateur avertit (CS8618). Plusieurs réponses selon le cas : initialiser à la déclaration, marquer required (C# 11, oblige l'appelant à fournir la valeur), ou accepter honnêtement le null avec ?.

Pour aller plus loin

Explore les attributs d'annotation nullable pour décrire des contrats subtils : [NotNullWhen(true)] (sur un bool Try… qui garantit une sortie non-null quand il renvoie true), [MemberNotNull] (une méthode d'init qui remplit des champs), [MaybeNull]/[NotNull]. Ils permettent à ton API de guider l'analyse de flux chez ceux qui l'appellent, exactement comme le fait string.IsNullOrEmpty.

Un cas réel : 60 avertissements, zéro crash de plus

Cas réel

Une équipe maintenait une API dont le journal d'erreurs était dominé par une seule ligne : NullReferenceException, plusieurs fois par jour, à des endroits toujours différents. Plutôt que de courir après chaque crash, elle a activé <Nullable>enable</Nullable> sur le projet. Résultat immédiat : une soixantaine d'avertissements à la compilation — autant de null non gérés que le compilateur venait de rendre visibles. Ils les ont traités un par un : certains étaient de vrais bugs (une réponse d'API optionnelle jamais vérifiée), d'autres de fausses alertes corrigées par un ? honnête ou une garde. En deux jours, la migration a fait disparaître la classe entière de crashs du journal de production. La leçon : le nullable ne demande pas de tout réécrire, il révèle des dettes déjà présentes — et déplace le crash de l'utilisateur vers le compilateur.

Glossaire

NullReferenceException
Exception levée à l'exécution quand on déréférence une variable valant null ; le bug historique que le contexte nullable vise à prévenir.
Contexte nullable
Mode (activé par <Nullable>enable ou #nullable enable) où les types référence sont non-nullables par défaut et le null devient visible dans le type.
string vs string?
Sans ?, une valeur est promise (usage direct) ; avec ?, le null est possible et doit être vérifié avant déréférencement.
Accès conditionnel ?.
Court-circuite l'expression et renvoie null si la partie gauche est null, au lieu de lever une exception.
Coalescence ?? / ??=
?? fournit une valeur de repli quand l'opérande est null ; ??= n'affecte que si la variable vaut null.
Analyse de flux (null-state)
Suivi par le compilateur de l'état peut-être null / non null d'une variable ligne à ligne ; une garde rétrécit le type (narrowing).
Opérateur pardon !
Supprime un avertissement nullable sans vérifier à l'exécution : une promesse au compilateur, à réserver aux garanties hors de sa portée.
required
Modificateur (C# 11) qui oblige l'appelant à initialiser un membre à la création de l'objet : garantit un champ non-null sans constructeur.

Récap et vérification

  • La NullReferenceException vient d'un null caché dans un type référence ; le contexte nullable la transforme en avertissement de compilation.
  • Activé (<Nullable>enable), string est non-null et string? peut l'être : le ? fait partie du type.
  • ?. court-circuite sur null, ??/??= fournissent un repli ; combine-les pour un code concis et sûr.
  • Le compilateur suit le flux : une garde (is null / is not null) rétrécit le type et supprime l'avertissement sans opérateur.
  • L'opérateur ! fait taire mais ne vérifie pas : à réserver aux garanties hors de portée du compilateur.
  • required et l'initialisation à la déclaration évitent les champs non-null non initialisés (CS8618).
