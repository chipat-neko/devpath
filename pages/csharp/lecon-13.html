Module 04 · C# moderne — Leçon 13

Organiser un projet et aller plus loin

~32 min Intermédiaire Leçon 12 recommandée

À la fin de cette leçon, tu sauras

  • organiser ton code en namespace et un type par fichier, au sein d'une solution .sln et de projets .csproj ;
  • ajouter une bibliothèque avec dotnet add package et écrire un test xUnit lancé par dotnet test ;
  • comprendre l'injection de dépendances intégrée et appliquer les bonnes pratiques (nullable, async, record) ;
  • te repérer dans l'écosystème .NET (ASP.NET Core, EF Core, Blazor, MAUI) pour choisir ta suite.
Sommaire de la leçon

Tu sais maintenant écrire des classes, des méthodes, manipuler des collections et gérer des erreurs en C#. Mais un vrai logiciel, ce n'est pas un seul fichier de 2000 lignes : c'est du code organisé, testé, qui s'appuie sur des bibliothèques existantes plutôt que de tout réinventer. Cette dernière leçon du module te montre comment passer du « script qui marche » au « projet maintenable ».

On va structurer un projet .NET (namespaces, solutions, projets), ajouter des dépendances avec NuGet, écrire un premier test, découvrir l'injection de dépendances intégrée, puis faire le tour de l'écosystème pour savoir où aller ensuite. Pas besoin de tout retenir : l'objectif est de te donner la carte.

Organiser : namespaces, fichiers et projets

Un namespace regroupe des types qui vont ensemble et évite les collisions de noms. La convention moderne est le file-scoped namespace : une seule ligne, sans accolades qui décalent tout le fichier vers la droite. Et la règle d'or : un type public par fichier, le fichier portant le nom du type.

Au-dessus des fichiers, on a deux niveaux d'organisation. Un projet (.csproj) produit un exécutable ou une bibliothèque. Une solution (.sln) regroupe plusieurs projets (par exemple l'application + ses tests). On crée tout ça en ligne de commande.

On crée une solution, un projet console, puis on rattache le projet à la solution.

Le fichier .csproj

Le .csproj décrit ton projet : version de .NET ciblée, options du compilateur et dépendances. En C# moderne il est très court. Voici un projet minimal avec le nullable activé.

TargetFramework dit « je compile pour .NET 8 ». ImplicitUsings ajoute automatiquement les using les plus courants. Nullable active la vérification des références nullables : le compilateur t'avertit quand un null risque de provoquer un plantage. Garde-le toujours activé.

Note

Le .csproj est du XML, c'est pourquoi les chevrons apparaissent ici échappés. Tu n'as presque jamais à l'éditer à la main : les commandes dotnet le modifient pour toi.

NuGet : ajouter des bibliothèques

NuGet est le gestionnaire de paquets de .NET, l'équivalent de npm pour JavaScript ou pip pour Python. Plutôt que de coder toi-même un client HTTP, un parseur JSON avancé ou un logger, tu installes une bibliothèque éprouvée en une commande.

La commande ajoute une ligne dans ton .csproj (une balise PackageReference avec le nom et la version). N'importe qui clonant ton dépôt n'a qu'à lancer dotnet restore pour retrouver exactement les mêmes paquets. C'est tout l'intérêt : les dépendances sont déclarées, pas copiées-collées à la main.

Les tests : prouver que ton code marche

Un test automatique est un bout de code qui vérifie qu'une méthode renvoie ce qu'on attend. Tu l'écris une fois, tu le relances à chaque modification : si tu casses quelque chose, le test échoue immédiatement. Les frameworks les plus courants sont xUnit et NUnit. On part sur xUnit, le plus répandu aujourd'hui.

On crée un projet de tests, on lui fait référencer le projet à tester, puis on l'ajoute à la solution. Un test xUnit est une méthode marquée [Fact] ; on y appelle la méthode et on vérifie le résultat avec Assert.

Le patron Arrange / Act / Assert structure presque tous les tests : préparer, agir, vérifier. On lance toute la suite avec une seule commande.

Astuce

Un test qui échoue n'est pas une mauvaise nouvelle : c'est un bug attrapé avant qu'il n'atteigne tes utilisateurs. Écris un test dès qu'un comportement compte vraiment.

L'injection de dépendances

Quand une classe a besoin d'une autre (par exemple un service qui a besoin d'un logger), une mauvaise idée est de la créer elle-même avec new : elle devient impossible à tester et à remplacer. L'injection de dépendances (DI) renverse ça : la classe reçoit ce dont elle a besoin par son constructeur, et un « conteneur » se charge de fournir les bons objets. .NET en fournit un officiellement, dans le paquet Microsoft.Extensions.DependencyInjection : déjà présent dans les projets ASP.NET Core, à ajouter avec dotnet add package Microsoft.Extensions.DependencyInjection dans une application console.

Tu enregistres une fois la correspondance « interface → implémentation », et tout le reste se câble seul. Pour tester ServiceCommande, tu lui passes un faux INotificateur : c'est exactement ce que permet la DI.

Note

Dans un fichier qui utilise les top-level statements, les instructions de premier niveau doivent toujours précéder les déclarations de class/interface : l'inverse ne compile pas. C'est pour ça que le code de câblage est tout en haut, et les types juste en dessous.

Les bonnes pratiques

Voici les réflexes qui font la différence entre du code jetable et du code de production. Ils reprennent tout ce que tu as vu dans le module.

  • Nullable activé : laisse le compilateur traquer les null avant qu'ils ne plantent à l'exécution.
  • async pour l'I/O : lecture de fichier, appel réseau, base de données → async/await, jamais de blocage du thread.
  • Immutabilité : un record ou des propriétés en lecture seule rendent un objet plus sûr et plus simple à raisonner.
  • Propriétés plutôt que champs publics : exposer { get; private set; } garde le contrôle sur les modifications.
  • Gestion d'erreur cohérente : des exceptions claires, attrapées au bon niveau, pas avalées en silence.
  • Conventions de nommage : PascalCase pour types, méthodes et propriétés ; camelCase pour les variables locales.

La virgule décimale ci-dessus (49,90) dépend de la culture de ta machine : en français elle s'affiche avec une virgule, en anglais avec un point. Le record te donne gratuitement ce joli affichage et la comparaison par valeur.

L'écosystème et la suite

C# n'est pas qu'un langage console : c'est la porte d'entrée d'une plateforme énorme. Selon ce que tu veux construire, voici où regarder.

  • ASP.NET Core : sites web et API REST. Le point de départ pour le développement back-end.
  • Entity Framework Core : l'ORM officiel pour parler à une base de données avec des objets C# plutôt que du SQL brut.
  • Blazor : des interfaces web interactives écrites en C# au lieu de JavaScript.
  • .NET MAUI : applications mobiles (Android, iOS) et bureau à partir d'un seul code.
  • Unity : le moteur de jeux vidéo le plus populaire, scripté en C#.

Tout ce que tu as appris (types, collections, LINQ, async, records, DI) se retrouve dans chacun de ces mondes. Tu n'apprends pas un nouvel outil de zéro : tu réutilises le même C#.

Pièges fréquents

Piège fréquent

Tout entasser dans un seul fichier et un seul namespace géant. Au-delà de quelques classes, on ne s'y retrouve plus. Un type = un fichier, des namespaces qui suivent les dossiers : ton code reste navigable.

Piège fréquent

Réinventer ce que le framework offre déjà : gérer ses dépendances « à la main » au lieu de NuGet, recoder un conteneur DI, ignorer les avertissements nullable du compilateur. Un avertissement n'est pas du bruit : c'est un bug en puissance. Et ne pas écrire de tests, c'est s'interdire de modifier son code sereinement.

Pour aller plus loin

Pour aller plus loin

Construis une petite API avec ASP.NET Core, branche-la à une base avec Entity Framework Core, et explore l'injection de dépendances en détail (durées de vie Singleton, Scoped, Transient). Mets en place un pipeline CI/CD qui lance dotnet test à chaque commit. Côté interfaces, regarde Blazor, MAUI ou Unity selon ce qui t'attire.

Un cas réel : le fichier unique qui coûtait cher

Cas réel

Une petite équipe maintenait un utilitaire de facturation dans un unique Program.cs de 2 400 lignes, sans le moindre test. Tant qu'une seule personne y touchait, ça tenait. Le jour où un nouveau venu a « nettoyé » le calcul de TVA, un arrondi a discrètement changé : les factures étaient fausses de quelques centimes — invisible à l'œil, mais l'écart s'accumulait sur des milliers de lignes. Le bug est resté trois semaines en production. La réponse n'a pas été d'écrire plus de code, mais de le structurer : un projet Facturation.Core pour la logique, un projet Facturation.Tests avec quelques [Fact] couvrant les cas de TVA, et un dotnet test lancé à chaque commit. Le mois suivant, une modification similaire a fait passer un test au rouge en dix secondes — le bug n'a jamais atteint un client.

Glossaire

Namespace
Espace de noms qui regroupe des types apparentés et évite les collisions ; version moderne file-scoped (namespace X;) qui vaut pour tout le fichier.
Solution (.sln)
Fichier conteneur qui regroupe plusieurs projets liés (application, bibliothèque, tests) pour les ouvrir et les compiler ensemble.
Projet (.csproj)
Unité de compilation en XML : cible .NET, options du compilateur et dépendances ; produit un exécutable ou une bibliothèque.
NuGet
Gestionnaire de paquets de .NET (l'équivalent de npm ou pip) ; dotnet add package déclare la dépendance dans le .csproj.
xUnit
Framework de tests le plus répandu en .NET ; une méthode marquée [Fact] est un test, exécuté par dotnet test.
Arrange / Act / Assert
Structure canonique d'un test : préparer le contexte, exécuter l'action, puis vérifier le résultat attendu.
Injection de dépendances (DI)
Principe où une classe reçoit ses collaborateurs (par le constructeur) au lieu de les créer avec new ; découple et facilite les tests.
Conteneur DI
Composant (intégré à .NET via ServiceCollection/ServiceProvider) qui enregistre les correspondances interface → implémentation et fournit les objets câblés.

Récap et vérification

  • Un namespace (file-scoped) regroupe les types ; règle : un type public par fichier.
  • Une solution .sln regroupe des projets .csproj (application, bibliothèque, tests).
  • NuGet (dotnet add package) déclare les dépendances dans le .csproj.
  • Les tests xUnit ([Fact] + Assert, lancés par dotnet test) sécurisent les modifications.
  • L'injection de dépendances intégrée fournit les services par constructeur.
  • Bonnes pratiques : nullable, async pour l'I/O, records, propriétés, conventions de nommage.
  • L'écosystème (ASP.NET Core, EF Core, Blazor, MAUI, Unity) réutilise le même C#.
