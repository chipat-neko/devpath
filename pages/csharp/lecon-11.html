Module 03 · Robustesse et collections — Leçon 11

LINQ, délégués et lambdas

~32 min Avancé Leçon 10 recommandée

À la fin de cette leçon, tu sauras

  • savoir distinguer et utiliser les délégués Func<...>, Action<...> et Predicate<T> ;
  • savoir écrire des lambdas (x => ...) et comprendre la capture de variables ;
  • savoir construire un pipeline LINQ avec Where, Select, OrderBy, GroupBy, FirstOrDefault, Any, Sum ;
  • savoir éviter le piège de l'évaluation paresseuse en matérialisant avec ToList().
Sommaire de la leçon

Tu as une liste de données et tu veux la filtrer, la transformer, la trier ou la regrouper. En C, tu écrirais une boucle for à chaque fois. En C# moderne, tu décris ce que tu veux obtenir avec LINQ (Language Integrated Query), et le langage s'occupe de la mécanique. C'est sans doute la fonctionnalité la plus aimée de C#, et elle repose sur trois briques que tu vas découvrir dans l'ordre : les délégués, les lambdas, puis LINQ lui-même.

On part du plus simple (qu'est-ce qu'un délégué ?) pour arriver à des pipelines élégants comme nombres.Where(x => x > 0).Select(x => x * 2).ToList(). Chaque section a un exemple complet avec sa sortie console en commentaire.

Les délégués : un type qui pointe vers une méthode

Une variable int contient un nombre. Un délégué, lui, contient une méthode : c'est une référence à du code que tu peux stocker, passer en argument et appeler plus tard. Plutôt que de définir tes propres types de délégués, tu utiliseras presque toujours les deux familles fournies par .NET :

  • Func<..., TResult> : une méthode qui retourne une valeur. Le dernier paramètre générique est le type de retour ;
  • Action<...> : une méthode qui ne retourne rien (void) ;
  • Predicate<T> : un cas particulier qui prend un T et retourne un bool (équivalent à Func<T, bool>).

Remarque que addition est une variable, mais on l'appelle comme une méthode : addition(3, 4). C'est tout l'intérêt d'un délégué : du comportement qu'on manipule comme une donnée. On peut donc le ranger dans une variable, le passer à une autre méthode, ou le retourner.

Les lambdas : écrire la méthode sur place

Dans l'exemple précédent, n => n % 2 == 0 est une lambda : une petite méthode anonyme écrite directement là où on en a besoin. La syntaxe se lit « paramètres => corps ». À gauche de la flèche, les paramètres ; à droite, soit une expression (sa valeur est retournée), soit un bloc { ... }.

Une lambda peut capturer les variables locales qui l'entourent : elle « se souvient » de leur valeur même après la fin de la portée où elle a été créée. Ici la lambda capture taux :

Note

Le compilateur déduit souvent les types des paramètres d'une lambda d'après le délégué cible. Quand tu écris nombres.Where(x => x > 0), il sait déjà que x est un int : pas besoin de le préciser.

LINQ : interroger n'importe quelle séquence

LINQ ajoute une cinquantaine de méthodes à tout ce qui est IEnumerable<T> : listes, tableaux, Dictionary, résultats d'autres requêtes… Ces méthodes prennent des lambdas en argument, et c'est là que tout ce qui précède se rejoint. Tu enchaînes les opérations pour former un pipeline qui se lit de gauche à droite.

Le même résultat s'écrit aussi en syntaxe requête, plus proche du SQL. Le compilateur la traduit exactement vers la syntaxe méthode ci-dessus — c'est une question de goût, sauf pour les regroupements et jointures où la syntaxe requête est parfois plus lisible.

Les opérateurs LINQ à connaître

Tu couvriras l'immense majorité de tes besoins avec une poignée d'opérateurs. Voici les essentiels, groupés par usage :

  • Filtrer / projeter : Where (garder selon une condition), Select (transformer chaque élément) ;
  • Ordonner : OrderBy, OrderByDescending, puis ThenBy pour un second critère ;
  • Choisir un élément : First, FirstOrDefault, Single, Last ;
  • Tester : Any (au moins un ?), All (tous ?), Contains ;
  • Agréger : Count, Sum, Average, Min, Max ;
  • Regrouper et matérialiser : GroupBy, ToList, ToArray, ToDictionary.

FirstOrDefault et les valeurs par défaut

Quand tu cherches un élément précis, deux familles s'opposent. First / Single lèvent une exception si rien ne correspond. Leurs variantes ...OrDefault retournent la valeur par défaut du type (null pour un objet, 0 pour un int) au lieu de planter.

Règle pratique : utilise FirstOrDefault par défaut et teste le résultat. Réserve First aux cas où l'absence serait un vrai bug que tu veux voir exploser tout de suite.

Astuce

Pour un type référence (par exemple un string ou un objet), FirstOrDefault renvoie null quand rien ne correspond. Teste donc if (resultat is null) avant d'utiliser la valeur, sinon tu risques une NullReferenceException plus loin.

L'évaluation paresseuse (deferred execution)

Voici le concept qui surprend tout le monde : une requête LINQ ne s'exécute pas au moment où tu l'écris. Tant que tu ne la parcours pas (foreach, ToList, Count…), elle ne fait que décrire le travail. C'est l'évaluation paresseuse.

Le filtre tourne deux fois : une fois par énumération. Si la requête est coûteuse (accès réseau, calcul lourd) ou si la source change entre deux parcours, c'est un problème. La solution est de matérialiser le résultat une seule fois avec ToList() ou ToArray() : tu obtiens une collection concrète que tu peux parcourir autant que tu veux sans relancer la requête.

Les méthodes d'extension : la magie sous LINQ

Pourquoi peux-tu écrire nombres.Where(...) alors qu'un tableau n'a pas de méthode Where ? Grâce aux méthodes d'extension : des méthodes statiques qui s'appellent comme si elles appartenaient au type. LINQ n'est « que » un gros paquet de méthodes d'extension sur IEnumerable<T>. Tu peux en écrire toi-même — le mot-clé est this sur le premier paramètre.

Tu n'as pas besoin d'en écrire pour utiliser LINQ, mais comprendre le mécanisme démystifie totalement la syntaxe en pipeline : ce ne sont que des appels de méthodes chaînés, chacun renvoyant un IEnumerable<T> sur lequel le suivant s'applique.

Un cas réel : la requête exécutée deux fois

Cas réel

Sur un tableau de bord d'administration, une méthode renvoyait un IEnumerable<Commande> issu d'Entity Framework (donc traduit en SQL, exécuté à l'énumération). La page affichait d'abord le total avec commandes.Count(), puis parcourait la même variable dans un foreach pour la liste. À cause de l'évaluation paresseuse, la requête SQL partait deux fois vers la base à chaque affichage ; sous charge, la base saturait et la page devenait lente. Le correctif tenait en un mot : var liste = commandes.ToList(); une seule fois, puis lire liste.Count et parcourir liste en mémoire. Une requête au lieu de deux.

Pièges fréquents

Piège fréquent

Énumérer plusieurs fois une requête coûteuse. À cause de l'évaluation paresseuse, appeler .Count() puis foreach sur la même requête relance tout le pipeline. Matérialise une fois avec ToList() et travaille ensuite sur la liste.

  • First sur une séquence vide lève une exception. Préfère FirstOrDefault et teste le résultat (null ou valeur par défaut) avant de l'utiliser.
  • Les effets de bord dans une lambda. Une lambda Where ou Select devrait juste calculer et ne rien modifier d'extérieur. Combinée à l'évaluation paresseuse, elle peut s'exécuter zéro, une ou plusieurs fois — un effet de bord y devient imprévisible.
  • LINQ ne modifie jamais la source. nombres.Where(...) ne retire rien de nombres : il renvoie une nouvelle séquence. La liste d'origine reste intacte.
  • Capturer une variable de boucle. En C# moderne, une lambda capturée dans un foreach capture une nouvelle copie de la variable à chaque tour, ce qui est généralement ce que tu veux. Reste vigilant avec une boucle for classique : la lambda y capture la même variable d'indice, qui vaudra sa valeur finale au moment de l'appel.

Pour aller plus loin

Pour aller plus loin

Ce que tu viens de voir est LINQ to Objects (sur des collections en mémoire). Il existe aussi LINQ to SQL / Entity Framework : là, la requête n'est pas exécutée par C# mais traduite en SQL et envoyée à une base de données. C'est rendu possible par IQueryable<T> et les arbres d'expression (la lambda est analysée comme une structure de données, pas compilée en code). Approfondis aussi l'évaluation paresseuse avec yield return, et les performances de LINQ (chaque opérateur a un coût ; une boucle manuelle reste parfois plus rapide dans un chemin critique).

Antisèche

Glossaire

Délégué
Type qui référence une méthode : on le stocke, le passe en argument et l'appelle plus tard comme une fonction.
Func / Action / Predicate
Délégués prêts à l'emploi : Func retourne une valeur, Action non, Predicate<T> renvoie un bool.
Lambda
Méthode anonyme écrite sur place, forme paramètres => corps ; passée en argument aux opérateurs LINQ.
Capture (fermeture)
Une lambda « se souvient » des variables locales environnantes ; elle capture la variable, pas une copie de sa valeur.
LINQ
Language Integrated Query : opérateurs (Where, Select…) applicables à tout IEnumerable<T>, en syntaxe méthode ou requête.
Pipeline
Chaîne d'opérateurs LINQ lue de gauche à droite ; chaque étape renvoie une séquence transmise à la suivante.
Évaluation paresseuse
La requête ne s'exécute qu'au moment du parcours (foreach, ToList…) ; chaque énumération la relance.
Méthode d'extension
Méthode statique appelable comme un membre du type (mot-clé this sur le 1er paramètre) ; base technique de LINQ.

Récap et vérification

  • Un délégué est un type qui référence une méthode ; Func<...> retourne, Action<...> ne retourne rien, Predicate<T> retourne un bool.
  • Une lambda x => ... est une méthode anonyme écrite sur place ; elle peut capturer les variables environnantes.
  • LINQ s'applique à tout IEnumerable<T> via deux syntaxes équivalentes : méthode (pipeline) et requête (from ... where ... select).
  • Opérateurs clés : Where, Select, OrderBy, GroupBy, First/FirstOrDefault, Any/All, Count/Sum, ToList.
  • L'évaluation paresseuse fait que la requête s'exécute à chaque parcours ; ToList() la matérialise une fois.
  • LINQ repose sur les méthodes d'extension et ne modifie jamais la source.

Vérifie ta compréhension

  1. Quelle est la différence entre Func<int, bool> et Action<int> ?
  2. Pourquoi FirstOrDefault est-il souvent plus sûr que First, et que retourne-t-il quand rien ne correspond ?
  3. Tu écris une requête LINQ coûteuse puis tu la parcours deux fois. Que se passe-t-il, et comment l'éviter ?
