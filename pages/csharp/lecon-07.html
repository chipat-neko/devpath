Module 02 · POO en C# — Leçon 07

Interfaces et structures

~32 min Intermédiaire Leçon 6 recommandée

À la fin de cette leçon, tu sauras

  • Savoir définir et implémenter une interface, y compris plusieurs sur une même classe ;
  • Savoir utiliser les interfaces du framework comme IComparable et IDisposable ;
  • Savoir créer une structure (type valeur) et un readonly struct immuable ;
  • Savoir distinguer la sémantique valeur (struct) de la sémantique référence (class).
Sommaire de la leçon

Jusqu'ici tu as vu les classes : des moules qui décrivent des objets avec leur état et leur comportement. Dans cette leçon, on ajoute deux outils essentiels de la POO en C#. D'abord les interfaces : un contrat qui dit « voici ce qu'un type doit savoir faire », sans dire comment. Ensuite les structures (struct) : des types valeur, copiés au lieu d'être partagés, parfaits pour de petits objets immuables comme un point.

Ces deux notions paraissent indépendantes, mais elles répondent à la même question de conception : quel est le bon type pour modéliser mon idée ? On termine par LA distinction à intégrer une fois pour toutes : valeur contre référence.

Une interface, c'est un contrat

Une interface liste des membres (méthodes, propriétés) que tout type qui la signe doit fournir. Elle ne contient ni champ ni état : c'est une promesse de comportement, pas une donnée. Par convention C#, le nom commence par un I majuscule.

L'intérêt majeur : une classe ne peut hériter que d'une seule classe de base, mais elle peut implémenter plusieurs interfaces. C'est la façon C# de combiner des capacités sans héritage multiple.

Note

Une interface décrit le « quoi ». Une classe abstraite décrit aussi le « quoi » mais peut porter de l'état et du code partagé, et on n'en hérite qu'une seule. On y revient dans les pièges.

Implémenter une interface et le polymorphisme

Pour signer le contrat, on écrit : IPayable après le nom de la classe, puis on fournit chaque membre. Plusieurs classes différentes peuvent implémenter la même interface chacune à sa manière : c'est le polymorphisme par interface.

La boucle ne connaît que le contrat IPayable. Demain, tu ajoutes une classe Amende qui implémente IPayable et la boucle fonctionne sans rien changer. C'est exactement ce qu'on cherche : du code ouvert à l'extension.

Les interfaces du framework

.NET fournit des interfaces standard que tes types peuvent signer pour s'intégrer à l'écosystème. Trois incontournables :

  • IComparable<T> : « je sais me comparer », donc Array.Sort et List<T>.Sort savent te trier.
  • IEnumerable<T> : « on peut me parcourir avec foreach ».
  • IDisposable : « je détiens une ressource à libérer » (fichier, connexion). On l'utilise avec using.

À la sortie du bloc using (même en cas d'erreur), C# appelle Dispose() pour toi. C'est le mécanisme propre de libération des ressources.

Cas réel

Le duo IDisposable + using gère les ressources rares du système : fichiers ouverts, connexions à une base de données, sockets réseau. Une connexion SQL non refermée reste comptée dans le pool ; empile quelques milliers de requêtes qui « oublient » de fermer, et l'application épuise le pool puis se fige sur « Timeout expired ». En écrivant using var conn = new SqlConnection(...);, C# appelle Dispose() à la sortie du bloc même en cas d'exception : la connexion retourne au pool à coup sûr. C'est le mécanisme derrière StreamReader, HttpClient ou le DbContext d'Entity Framework.

Les membres par défaut dans une interface

Depuis C# 8, une interface peut fournir une implémentation par défaut. Les types existants n'ont alors rien à réécrire : pratique pour faire évoluer un contrat sans casser le code déjà en place.

À utiliser avec parcimonie : une interface reste avant tout un contrat. Les implémentations par défaut servent surtout à l'évolution d'API publiques, et ne sont accessibles qu'à travers le type interface (pas via la variable de type Personne).

Les structures : des types valeur

Une structure (struct) ressemble à une classe, mais c'est un type valeur : quand tu l'affectes ou la passes en argument, elle est copiée (sa donnée est en général sur la pile, pas dans le tas). On les préfère aux classes pour de petits objets, idéalement immuables, comme un point, une couleur ou un montant.

Le mot-clé readonly devant struct garantit qu'aucun champ ne change après construction : c'est le style recommandé.

class vs struct : valeur ou référence

Voici LE point à comprendre. Une variable de type classe contient une référence (un renvoi) vers un objet partagé : deux variables peuvent pointer le même objet. Une variable de type struct contient la valeur elle-même : l'affectation en fait une copie indépendante.

Pour la démonstration uniquement, on rend ici les deux types mutables (champs publics modifiables) ; dans du vrai code, on garderait la struct readonly et immuable.

Retiens la phrase : struct = copie, class = partage. Une fois ce réflexe acquis, l'essentiel des surprises disparaît.

Les records struct (survol)

Tu as peut-être croisé les records (types pensés pour la donnée, avec égalité par valeur et ToString auto). Il existe une variante valeur : record struct. Elle combine la sémantique de copie d'une struct et le confort d'écriture d'un record.

On creuse les records dans la leçon suivante : garde simplement en tête qu'un record struct est souvent le moyen le plus court d'écrire un petit type valeur immuable.

Pièges fréquents

Piège fréquent

Confondre interface et classe abstraite. L'interface est un contrat sans état (pas de champ), et un type peut en signer plusieurs. La classe abstraite porte de l'état et du code partagé, mais on n'en hérite qu'une seule. Choisis l'interface pour une capacité, la classe abstraite pour une base commune.

Piège fréquent

Muter une struct rangée dans une collection. maListe[0].X = 5; modifie une copie renvoyée par l'indexeur, pas l'élément stocké : ça ne compile même pas pour une List<T> (erreur « Cannot modify the return value »). C'est pourquoi on fait ses structs readonly et immuables : on remplace l'élément entier plutôt que de le muter.

Piège fréquent

Une grosse struct coûte cher. Comme une struct est copiée à chaque passage, un type valeur avec beaucoup de champs se recopie sans cesse. Règle simple : garde les structs petites (quelques champs). Au-delà, une class est généralement le bon choix.

Dernier oubli classique : déclarer : IPayable mais ne pas écrire la méthode du contrat. Le compilateur refuse : 'Facture' does not implement interface member 'IPayable.CalculerMontantDu()'. Implémenter chaque membre n'est pas optionnel.

Pour aller plus loin

Pour aller plus loin

Le couple IDisposable + using mérite d'être creusé (forme courte using var f = ...; sans accolades). IEnumerable<T> ouvre la porte à yield return pour produire des séquences à la volée. Et programmer contre des interfaces est la base de l'injection de dépendances, omniprésente en .NET : on dépend du contrat, pas de l'implémentation concrète. Les records font l'objet de la leçon suivante.

Antisèche

Glossaire

Interface
Contrat listant des membres qu'un type doit fournir, sans état ni implémentation (sauf membres par défaut) ; nommée I….
Implémenter
Signer une interface (: IPayable) et écrire chacun de ses membres ; obligatoire, sinon le code ne compile pas.
Polymorphisme par interface
Manipuler des objets via leur contrat commun sans connaître leur type concret ; on ajoute des types sans toucher au code existant.
Type valeur (struct)
Contient directement sa donnée ; l'affectation et le passage en argument la copient. À garder petite et readonly.
Type référence (class)
La variable contient un renvoi vers un objet partagé ; deux variables peuvent désigner la même instance.
readonly struct
Structure dont aucun champ ne change après construction ; on « modifie » en renvoyant une nouvelle valeur.
IDisposable
Contrat d'une seule méthode Dispose() pour libérer une ressource ; s'emploie avec using, qui l'appelle automatiquement.
Membre par défaut
Implémentation fournie directement dans l'interface (C# 8+) ; sert surtout à faire évoluer un contrat sans casser le code en place.

Récap et vérification

  • Une interface est un contrat sans état ; on la nomme I... et une classe peut en signer plusieurs.
  • Le polymorphisme par interface permet de manipuler des objets via leur contrat, sans connaître le type concret.
  • Le framework fournit IComparable<T> (tri), IEnumerable<T> (foreach), IDisposable (using).
  • Depuis C# 8, une interface peut offrir des membres par défaut.
  • Une struct est un type valeur (copié) ; on la veut petite et readonly. Une class est un type référence (partagé).
  • Mantra : struct = copie, class = partage.

Vérifie ta compréhension

  1. Pourquoi une classe peut-elle implémenter plusieurs interfaces mais n'hériter que d'une seule classe ?
  2. Que se passe-t-il quand on affecte une struct à une autre variable, puis qu'on modifie la seconde ? Et avec une class ?
  3. Quelle interface signes-tu pour qu'un type soit triable par Array.Sort, et quelle interface va de pair avec using ?
