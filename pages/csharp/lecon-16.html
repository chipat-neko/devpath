Module 05 · C# en profondeur — Leçon 16

Performance, mémoire et écosystème

~35 min Avancé Leçon 15 recommandée

À la fin de cette leçon, tu sauras

  • Comprendre le modèle mémoire (struct vs class, pile vs tas, boxing) et savoir l'éviter ;
  • Réduire les allocations avec Span<T>, stackalloc, ArrayPool et ValueTask ;
  • Mesurer correctement avec BenchmarkDotNet et lire les diagnostics dotnet-counters/dotnet-trace ;
  • Connaître JIT vs Native AOT et situer l'écosystème .NET (ASP.NET Core, EF Core, Blazor).
Sommaire de la leçon

Tu sais écrire du C# correct : classes, records, LINQ, async/await. La question de cette leçon est différente : comment écrire du C# rapide, et surtout comment savoir qu'il est rapide. La performance en .NET ne se devine pas ; elle se mesure. On va donc descendre d'un cran sous le langage : comment la mémoire est organisée, ce que fait le ramasse-miettes, comment éviter les allocations inutiles, et avec quels outils on chiffre tout ça.

Le fil rouge tient en une phrase : mesure d'abord, optimise ensuite. La moitié de cette leçon te donne les bons réflexes ; l'autre moitié te donne les instruments pour ne jamais optimiser à l'aveugle. On termine par une carte de l'écosystème pour savoir où aller après ce cours.

Le modèle mémoire : pile, tas et boxing

En .NET, un type est soit valeur (struct, enum, types primitifs comme int) soit référence (class, record class, tableaux, chaînes). Un type valeur contient directement ses données ; un type référence contient un pointeur vers un objet alloué sur le tas géré (managed heap). Les variables locales et les arguments vivent sur la pile (stack), rapide et libérée automatiquement à la sortie de la méthode. Le tas, lui, est nettoyé par le ramasse-miettes.

Le piège classique est le boxing : quand tu ranges une valeur dans un object (ou une interface non générique), le runtime alloue une boîte sur le tas pour y copier la valeur. C'est invisible dans le code mais bien réel à l'exécution.

Une List<int> stocke les int tels quels, sans boîte : c'est l'une des raisons d'être des génériques. Évite ArrayList, Hashtable et tout passage d'un struct en object dans une boucle chaude.

Note

Un struct n'est pas « toujours sur la pile ». Un struct champ d'une class vit sur le tas avec son objet conteneur ; un struct capturé par une lambda ou dans un async peut être déplacé. La règle juste : les types valeur sont copiés par valeur, les types référence partagent une référence.

Le garbage collector : générations et IDisposable

Le GC de .NET est générationnel. Les objets fraîchement alloués naissent en gén 0 ; ceux qui survivent à une collecte passent en gén 1, puis gén 2 (objets longue durée). L'idée : la plupart des objets meurent jeunes, donc collecter souvent la gén 0 (rapide) et rarement la gén 2 (coûteux) est efficace. Les gros objets (≥ 85 Ko) vont sur le LOH (Large Object Heap), traité comme la gén 2.

Deux modes : le GC workstation (par défaut côté client, latence faible) et le GC serveur (un tas et un thread par cœur, débit maximal ; activé par défaut sous ASP.NET Core). Le Background GC collecte la gén 2 en parallèle pour limiter les pauses.

Le GC gère la mémoire managée, pas les ressources externes (fichiers, sockets, handles). Pour celles-là, le contrat est IDisposable + using, qui appelle Dispose() de façon déterministe.

La finalisation (un finaliseur ~Type()) est un filet de sécurité : elle s'exécute sur un thread dédié, à un moment non déterministe, et retarde la libération d'un cycle de GC. Préfère toujours using ; ne garde un finaliseur que pour des ressources non managées, et appelle GC.SuppressFinalize dans Dispose.

Réduire les allocations : Span, stackalloc, ArrayPool

Span<T> est une vue (pointeur + longueur) sur une zone mémoire contiguë : un tableau, une portion de tableau, ou de la mémoire de pile. C'est un ref struct : il ne peut pas être stocké sur le tas ni capturé dans un async, ce qui garantit sa sûreté. Il permet de découper et parcourir sans copier ni allouer.

Réserve stackalloc aux petites tailles (quelques centaines d'octets) : la pile est limitée et un stackalloc dans une boucle peut la saturer (StackOverflowException). Pour les gros tampons réutilisés, ArrayPool<T> évite de marteler le GC.

Astuce

.NET 9 ajoute un Split sans allocation directement sur les ReadOnlySpan<char> (énumération de Range). En .NET 8, ce raccourci n'existe pas encore : on découpe à la main avec IndexOf et des sous-tranches, comme ci-dessus. Vérifie toujours la version de la cible avant d'utiliser une API « récente ».

Côté types, deux outils complètent le tableau. Un readonly struct garantit l'immuabilité et évite des copies défensives. Et ValueTask (ou ValueTask<T>) remplace Task quand une méthode async retourne souvent de façon synchrone (cache déjà rempli, par exemple) : pas d'allocation de Task dans le cas rapide.

Piège fréquent

Un ValueTask ne doit être attendu (await) qu'une seule fois, et jamais en parallèle. Si tu dois le consommer plusieurs fois ou le stocker, convertis-le d'abord avec .AsTask(). En cas de doute, reste sur Task : ValueTask est une optimisation ciblée, pas un remplaçant systématique.

Mesurer : BenchmarkDotNet

Mesurer « à la main » avec Stopwatch dans une boucle est presque toujours faux : le JIT n'est pas encore chaud, le GC se déclenche au hasard, le compilateur élimine du code mort, et la variance n'est pas chiffrée. Le standard de l'industrie est BenchmarkDotNet : il gère l'échauffement, lance plusieurs itérations, isole chaque cas dans son processus et te donne moyenne, écart-type et allocations.

On benchmarke toujours en configuration Release, optimisations activées.

La compilation : JIT vs Native AOT

Par défaut, .NET compile en IL (Intermediate Language), puis le JIT (Just-In-Time) traduit l'IL en code machine au premier appel de chaque méthode. Avantage : optimisations adaptées à la machine et à l'exécution réelle (le tiered compilation recompile à chaud le code souvent appelé). Inconvénient : un coût de démarrage.

Plusieurs leviers existent. ReadyToRun (R2R) pré-compile une partie en code natif dans l'assembly pour démarrer plus vite. Native AOT va au bout : il produit un exécutable natif autonome, sans JIT ni IL, avec un démarrage quasi instantané et une empreinte mémoire réduite — idéal pour des outils CLI, des microservices, des fonctions cloud.

Piège fréquent

Native AOT et le trimming sont incompatibles avec la réflexion dynamique non annotée et la génération de code à l'exécution. Une lib qui sérialise par réflexion peut casser silencieusement. Vérifie la compatibilité (avertissements IL2026/IL3050 à la compilation), privilégie les source generators (par ex. System.Text.Json en mode source-generated) et teste l'exécutable publié.

L'écosystème : où aller ensuite

.NET dépasse largement la console. Selon ton objectif, voici les briques principales construites sur les fondations que tu connais :

  • ASP.NET Core — serveurs web et APIs. Les minimal APIs permettent un endpoint en quelques lignes.
  • EF Core — ORM : tu manipules des objets, il génère le SQL et suit les modifications.
  • gRPC — RPC binaire performant entre services (contrats .proto).
  • Blazor — UI web en C# (WebAssembly ou serveur), sans écrire de JavaScript.
  • .NET MAUI — applications de bureau et mobiles multiplateformes depuis une base commune.
  • Azure et le cloud — hébergement, fonctions serverless, conteneurs ; .NET y est un citoyen de première classe.

Bonnes pratiques de performance

Quelques principes durables, par ordre d'importance :

  • Mesure avant d'optimiser. L'intuition se trompe ; un profileur ou BenchmarkDotNet dit la vérité. Optimise le point chaud réel, pas celui que tu imagines.
  • Choisis la bonne structure de données. Un Dictionary<K,V> au lieu d'une recherche linéaire change la complexité, pas seulement la constante.
  • Async pour l'I/O, pas pour le CPU. async/await libère un thread pendant une attente réseau ou disque ; il ne rend pas un calcul plus rapide.
  • Évite d'allouer dans les boucles chaudes. Sors les allocations constantes de la boucle, réutilise des tampons, préfère Span et ArrayPool aux copies.
  • N'optimise pas ce qui n'est pas un goulot. Un code 1000x plus rapide qui représente 0,1 % du temps ne change rien.

Astuce

Avant d'optimiser un bout de code, écris le benchmark baseline. Tu obtiens un chiffre de départ et une preuve, après coup, que ton changement a vraiment amélioré les choses — ou non. Sans mesure avant/après, tu ne fais que croire avoir accéléré.

Pièges fréquents

  • Optimiser sans mesurer. Le réflexe coupable n°1. Profile d'abord, sinon tu complexifies du code pour rien.
  • Boxing involontaire. Un struct rangé dans un object, une interface non générique, ou string.Format("{0}", monStruct) alloue une boîte. Reste générique.
  • Micro-benchmark naïf. Stopwatch + boucle = mesure fausse (JIT froid, GC, code éliminé). Utilise BenchmarkDotNet, en Release.
  • Allouer dans une boucle chaude. Une new List<...>() ou une concaténation += par itération sature la gén 0 et déclenche des GC à répétition.
  • Oublier using. Un IDisposable non libéré garde fichiers/connexions ouverts jusqu'à une finalisation aléatoire — fuite de ressources et bugs intermittents.
  • AOT sans vérifier la compatibilité. Réflexion dynamique et trimming font mauvais ménage : l'appli compile mais plante à l'exécution. Lis les avertissements IL**** et teste le binaire publié.

Un cas réel : le += qui saturait le ramasse-miettes

Cas réel

Un endpoint d'export générait un rapport CSV en concaténant les lignes avec rapport += ligne dans une boucle sur 50 000 enregistrements. En développement, avec quelques dizaines de lignes, personne ne voyait rien. En production, sous charge, le serveur passait près de 40 % de son temps CPU dans le ramasse-miettes et la latence explosait par à-coups. Plutôt que de deviner, l'équipe a isolé la méthode dans un BenchmarkDotNet avec [MemoryDiagnoser] : la version += allouait des centaines de mégaoctets (chaque += recrée toute la chaîne — un comportement quadratique). Le passage à un StringBuilder a divisé les allocations par ~100 et fait disparaître les pics de GC. La leçon : le coupable n'était pas un CPU « lent », mais les allocations — et seule la mesure l'a prouvé.

Antisèche

Glossaire

Type valeur / type référence
Un type valeur (struct, int) contient ses données et se copie ; un type référence (class) est partagé via un pointeur vers un objet du tas.
Pile / tas
La pile (stack) porte les variables locales, rapide et libérée à la sortie de la méthode ; le tas (heap) stocke les objets, nettoyé par le GC.
Boxing
Emballage d'une valeur dans un object (ou interface non générique) : une allocation sur le tas, invisible dans le code mais coûteuse en boucle chaude.
GC générationnel
Ramasse-miettes qui trie les objets par âge (gén 0/1/2 + LOH) : collecte souvent les jeunes (rapide), rarement les vieux (coûteux).
IDisposable / using
Contrat de libération déterministe des ressources externes (fichiers, connexions) ; using appelle Dispose() même en cas d'exception.
Span<T> / stackalloc
Vue contiguë sans copie / tampon alloué sur la pile : suppriment des allocations dans les chemins sensibles à la performance.
BenchmarkDotNet
Outil standard de micro-benchmark : gère l'échauffement, répète et isole les mesures, et rapporte temps et allocations (en Release).
JIT / Native AOT
Le JIT compile l'IL en code machine à l'exécution (souple) ; Native AOT produit un binaire natif à l'avance (démarrage éclair, réflexion limitée).

Récap et vérification

  • Types valeur (copiés) vs référence (partagés) ; pile rapide, tas géré par le GC ; le boxing alloue — reste générique.
  • Le GC est générationnel (gén 0/1/2, LOH), en mode workstation ou serveur ; using/IDisposable libèrent les ressources externes de façon déterministe.
  • Span<T>, stackalloc, ArrayPool, readonly struct et ValueTask réduisent les allocations dans les chemins chauds.
  • BenchmarkDotNet (en Release) est l'outil de mesure ; dotnet-counters/dotnet-trace diagnostiquent un processus vivant.
  • JIT par défaut, Native AOT/trimming/R2R pour le démarrage et la taille (attention à la réflexion).
  • L'écosystème : ASP.NET Core, EF Core, gRPC, Blazor, MAUI, Azure.
