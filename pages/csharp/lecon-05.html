Module 02 · POO en C# — Leçon 05

Classes, objets et propriétés

~34 min Intermédiaire Leçon 4 recommandée

À la fin de cette leçon, tu sauras

  • déclarer une classe, l'instancier avec new et choisir les bons modificateurs d'accès (public, private…) ;
  • écrire un constructeur (y compris surchargé et chaîné) et utiliser this ;
  • définir des propriétés : auto-propriétés, lecture seule avec init, expression-bodied et validation dans le set ;
  • comprendre l'encapsulation, les membres static et l'initialiseur d'objet.
Sommaire de la leçon

Jusqu'ici tu manipulais des types fournis par .NET : int, string, List<T>. Avec une classe, tu crées tes propres types, taillés pour ton domaine : un compte bancaire, un joueur, une commande. Une classe est un moule ; chaque objet créé à partir de ce moule est une instance qui porte ses propres données.

C# a une fonctionnalité phare pour exposer ces données proprement : les propriétés. Elles ressemblent à des champs publics côté utilisateur, mais cachent du code (validation, calcul, lecture seule). Cette leçon part de la classe nue, passe par le constructeur, puis installe les propriétés comme outil par défaut. Tout le code se compile avec dotnet ; les sorties console sont montrées en commentaire.

Classe, objet et modificateurs d'accès

Une classe regroupe des champs (les données) et des méthodes (les comportements). On crée un objet avec new. Chaque membre porte un modificateur d'accès qui dit qui peut le voir : public (tout le monde), private (la classe seule, c'est le défaut), protected (la classe et ses dérivées) et internal (le même assembly/projet).

Le champ _valeur est private : on ne peut le modifier qu'à travers les méthodes publiques. C'est le premier pas vers l'encapsulation.

Note

Convention C# : les types, méthodes et propriétés sont en PascalCase (Compteur, Incrementer) ; les variables locales et paramètres en camelCase (compteur) ; les champs privés sont souvent préfixés d'un underscore (_valeur).

Le constructeur, this, surcharge et chaînage

Le constructeur est une méthode spéciale, sans type de retour, qui porte le nom de la classe. Il s'exécute au moment du new et sert à mettre l'objet dans un état valide dès sa naissance. Le mot-clé this désigne l'instance courante : il sert à lever une ambiguïté quand un paramètre porte le même nom qu'un champ.

Tu peux fournir plusieurs constructeurs (surcharge) tant que leurs paramètres diffèrent. Pour éviter de répéter du code, un constructeur peut en appeler un autre via : this(...) (chaînage).

new Joueur("Lina") passe par : this(nom, 100) : une seule logique d'initialisation, réutilisée par les deux constructeurs.

Les propriétés : la signature de C#

Une propriété ressemble à un champ vue de l'extérieur (objet.Nom), mais cache deux accesseurs : get (lire) et set (écrire, avec le mot-clé value qui représente la valeur affectée). La forme complète permet d'ajouter de la logique :

{ get; set; } est une auto-propriété : le champ caché est créé automatiquement. init (au lieu de set) n'autorise l'écriture qu'au moment de la création.

Lecture seule, init et validation dans le set

Tout l'intérêt de passer par un set manuel, c'est d'y placer de la validation : rejeter une valeur invalide avant qu'elle ne corrompe l'objet. Et init permet une propriété immuable après construction tout en restant assignable dans un initialiseur d'objet.

Le set garde l'invariant « prix >= 0 » : impossible de mettre l'objet dans un état incohérent depuis l'extérieur.

Pourquoi des propriétés plutôt que des champs publics ?

On pourrait écrire public decimal Prix; et en finir. Mauvaise idée. Un champ public est une porte ouverte : n'importe qui écrit n'importe quoi, sans contrôle. Le jour où tu veux ajouter une validation ou un log, tu dois transformer le champ en propriété : cela change la nature du membre et peut casser du code qui en dépend (réflexion, sérialisation, héritage).

Une propriété, elle, offre l'encapsulation sans cérémonie : même syntaxe d'usage qu'un champ (objet.Prix = 10), mais tu gardes la main sur la lecture et l'écriture. Commencer en auto-propriété puis « ouvrir » le set pour valider ne change rien pour les appelants.

Astuce

Règle simple : en C#, on n'expose jamais un champ public. On expose une propriété. Garde les champs private et laisse les propriétés être la façade de l'objet.

Cas réel

Toute l'interface graphique de .NET repose sur les propriétés. En WPF et MAUI, le data binding relie un champ de saisie à une propriété d'objet : quand l'utilisateur tape, la propriété se met à jour, et quand la propriété change, l'écran se redessine. Ce mécanisme (via l'interface INotifyPropertyChanged) s'accroche au set d'une propriété — un simple champ public n'a pas de set où se brancher et resterait invisible pour l'interface. Voilà une raison très concrète pour laquelle, en C#, on expose toujours des propriétés.

Les membres static : appartenir à la classe, pas à l'objet

Un membre static appartient à la classe elle-même, pas à une instance. Il est partagé par tous les objets et s'appelle via le nom de la classe (Classe.Membre), sans new. Utile pour un compteur global, une constante, ou une fabrique.

Total est unique et incrémenté à chaque construction ; Id et Nom diffèrent d'un objet à l'autre. Le set de Total est private : lisible partout, modifiable seulement de l'intérieur.

Une classe complète : Compte

Réunissons tout : champ privé, constructeur, propriété en lecture seule, validation, et méthodes qui maintiennent l'invariant « solde >= 0 ».

Le Solde ne peut changer que via Deposer/Retirer, qui vérifient les règles : l'objet protège ses propres invariants. Voilà l'encapsulation en action.

Pièges fréquents

Piège fréquent

Exposer un champ public (public decimal Prix;) au lieu d'une propriété. Tu perds tout contrôle, et le transformer plus tard en propriété est un changement de surface qui peut casser sérialisation, réflexion et héritage. Mets toujours une propriété.

Piège fréquent

Oublier la validation dans le set « parce que ça marche pour l'instant ». Une auto-propriété { get; set; } accepte tout, y compris un prix négatif. Si la valeur a des règles, ouvre le set et vérifie value.

Piège fréquent

Confondre static et instance. Un membre static n'appartient à aucun objet : tu ne peux pas y lire un champ d'instance, et tous les objets partagent la même valeur. Inversement, un compteur censé être propre à chaque objet ne doit pas être static, sinon toutes les instances se le partagent par erreur.

Piège fréquent

init vs set : init rend la propriété immuable après construction (assignable seulement dans le constructeur ou l'initialiseur d'objet). Si tu choisis init puis tentes obj.Nom = "x" plus tard, c'est une erreur de compilation. Et une propriété de type référence non initialisée vaut null : l'utiliser provoque une NullReferenceException. Donne une valeur par défaut (= "") ou exige-la au constructeur.

Pour aller plus loin

Pour aller plus loin

Quand un type ne sert qu'à transporter des données immuables, les records (leçon 8) génèrent pour toi propriétés init, égalité par valeur et affichage. Les propriétés calculées (comme Fahrenheit) évitent de stocker ce qu'on peut dériver. Les indexeurs permettent d'écrire obj[i] sur tes propres types, et les constructeurs primaires condensent l'initialisation. Tout cela repose sur les briques de cette leçon.

Glossaire

Classe
Moule décrivant les champs et méthodes d'un type ; ne contient pas de données concrètes tant qu'on n'a pas créé d'objet.
Objet / instance
Exemplaire concret créé à partir d'une classe avec new ; porte ses propres valeurs de champs.
Champ
Variable membre qui stocke l'état d'un objet ; on le garde private et on l'expose via une propriété.
Propriété
Membre d'apparence « champ » (obj.Nom) cachant deux accesseurs get (lire) et set (écrire) ; point de contrôle idéal pour valider.
Auto-propriété
{ get; set; } : le champ de stockage est généré par le compilateur ; on « ouvre » le set plus tard si une règle apparaît, sans changer l'usage.
init
Accesseur d'écriture autorisé uniquement à la construction (constructeur ou initialiseur d'objet) ; rend la propriété immuable ensuite.
Encapsulation
Cacher l'état interne (private) et n'exposer qu'une façade contrôlée ; l'objet protège lui-même ses invariants.
static
Membre appartenant à la classe et non à un objet ; partagé par toutes les instances et appelé via Classe.Membre.

Récap et vérification

  • Une classe est un moule ; new crée un objet (instance) avec ses propres données.
  • Les modificateurs d'accès contrôlent la visibilité : private par défaut, public pour exposer.
  • Le constructeur initialise l'objet ; this désigne l'instance ; on peut surcharger et chaîner avec : this(...).
  • Les propriétés (get/set) remplacent les champs publics : auto-propriété { get; set; }, lecture seule { get; init; }, expression-bodied, validation dans le set.
  • On n'expose jamais un champ public : la propriété donne l'encapsulation sans changer la syntaxe d'usage.
  • Un membre static appartient à la classe ; l'initialiseur d'objet new T { ... } affecte les propriétés après le new.

Vérifie ta compréhension

  1. Quelle différence concrète y a-t-il entre une auto-propriété { get; set; } et une propriété { get; init; } ?
  2. Pourquoi préfère-t-on une propriété à un champ public, alors que l'usage obj.Prix = 10 a l'air identique ?
  3. Dans la classe Utilisateur, pourquoi Total est-il static mais Id non ? Que vaudrait Id du deuxième objet créé ?
