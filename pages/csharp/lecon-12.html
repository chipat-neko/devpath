L'asynchrone avec async/await

~35 min Avancé Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • comprendre pourquoi une opération longue bloque un thread et ce que async/await résolvent ;
  • écrire une méthode async qui retourne Task ou Task<T> et l'await sans bloquer ;
  • paralléliser plusieurs opérations avec Task.WhenAll et appeler une API avec HttpClient ;
  • reconnaître et éviter les pièges classiques : .Result/.Wait(), async void et le await oublié.
Sommaire de la leçon

Une application passe une bonne partie de son temps à attendre : une réponse réseau, une lecture de fichier, une requête en base de données. Pendant cette attente, le code « classique » bloque le thread (le fil d'exécution) qui patiente sans rien faire. En interface graphique, c'est l'application qui gèle ; sur un serveur, c'est un thread immobilisé qui ne peut plus servir d'autres requêtes. L'asynchrone résout ce gaspillage : au lieu d'attendre bêtement, le thread est libéré et reprend son travail quand le résultat arrive.

En C# moderne, ce mécanisme tient en deux mots-clés, async et await, et un type, Task. Cette leçon part de tes acquis sur les méthodes et les exceptions pour t'amener à écrire du code réactif, non bloquant, et à éviter les quelques pièges qui font la réputation de l'asynchrone.

Le problème : attendre, c'est bloquer

Imagine une méthode qui télécharge une page web et qui attend la réponse de façon bloquante. Tant que la réponse n'est pas arrivée, la ligne suivante ne s'exécute pas : le thread est immobilisé. S'il s'agit du thread d'interface, l'utilisateur voit l'application figée ; aucun clic, aucun défilement ne répond.

Pendant l'attente réseau (parfois plusieurs secondes), le thread ne fait rien d'autre. C'est ce gaspillage que l'asynchrone élimine — et on verra que ce .Result est lui-même un piège à bannir.

Le coût n'est pas le calcul (le processeur ne travaille pas), c'est l'attente. L'idée de l'asynchrone : pendant cette attente, rendre le thread à qui en a besoin.

Task et Task<T> : une promesse de résultat

Une Task représente une opération qui s'achèvera plus tard. Vois-la comme un ticket : tu le reçois immédiatement, et il te donnera le résultat quand ce sera prêt. Deux variantes :

  • Task : une opération qui se termine mais ne renvoie aucune valeur (l'équivalent asynchrone de void).
  • Task<T> : une opération qui se terminera en produisant une valeur de type T (un Task<string> promet une string).

Appeler la méthode démarre le travail et rend la Task immédiatement. C'est await qui en extrait la valeur, le moment venu.

async et await : attendre sans bloquer

Le mot-clé async sur une méthode autorise l'emploi d'await à l'intérieur ; il transforme la méthode pour qu'elle puisse se suspendre et reprendre plus tard. Le mot-clé await, lui, dit : « attends que cette Task finisse, mais libère le thread pendant ce temps ». Quand le résultat arrive, l'exécution reprend juste après le await.

La différence cruciale avec un blocage : pendant les 2 secondes, le thread n'est pas immobilisé ; il peut traiter d'autres travaux. Seul le flux de cette méthode est mis en pause.

Note

En .NET 8, le fichier Program.cs en top-level statements peut utiliser await directement au plus haut niveau : le compilateur génère pour toi une méthode Main marquée async. Pratique pour écrire du code asynchrone sans cérémonie.

Un cas réel : appeler une API avec HttpClient

L'exemple type d'opération asynchrone est l'appel réseau. La classe HttpClient expose des méthodes ...Async qui rendent des Task. On les await pour récupérer la réponse sans bloquer.

Compare avec la version bloquante du début : ici, pas de .Result, on await. Pendant l'aller-retour réseau, le thread reste disponible.

Piège fréquent

Ne crée pas un new HttpClient() à chaque appel (surtout dans un using répété) : tu risques d'épuiser les sockets du système. Réutilise une instance partagée, ou mieux, IHttpClientFactory dans une application ASP.NET.

Les bonnes pratiques : « async all the way »

Trois règles te mettent à l'abri de la plupart des ennuis :

  • Async jusqu'en haut (async all the way) : si une méthode await quelque chose, son appelante doit elle aussi être async et await le résultat. On ne mélange pas asynchrone et blocage.
  • Retourne Task ou Task<T>, jamais async void (sauf pour un gestionnaire d'événement). Une Task peut être attendue et porte ses exceptions ; un void asynchrone, non.
  • Nomme tes méthodes asynchrones avec le suffixe Async (ChargerAsync, EnregistrerAsync). C'est une convention .NET qui signale d'un coup d'œil qu'il faut await.

Chaque maillon est async et await le suivant : la chaîne ne se « casse » jamais par un blocage. C'est ça, async all the way.

Exécuter en parallèle avec Task.WhenAll

Quand plusieurs opérations sont indépendantes, les attendre l'une après l'autre est un gâchis : trois appels d'une seconde prennent trois secondes alors qu'ils pourraient se chevaucher. Task.WhenAll lance tout en même temps et attend que tout soit fini.

La clé : on démarre les tâches avant le moindre await (elles tournent alors en même temps), puis un seul Task.WhenAll attend toute la grappe. Task.WhenAll sur des Task<T> renvoie un tableau de résultats.

Astuce

Pour réagir à la première tâche terminée plutôt qu'à toutes, il existe Task.WhenAny. Utile pour un délai d'expiration : course entre ton opération et un Task.Delay.

Pièges fréquents

Le danger numéro un est de bloquer sur de l'asynchrone avec .Result ou .Wait(). Dans certains contextes (interface graphique, ancien ASP.NET), cela provoque un deadlock : le thread attend la Task, mais la Task a besoin de ce même thread pour finir. Tout se fige. La règle est simple : une fois async, toujours await, jamais .Result ni .Wait().

Piège fréquent

async void ne s'utilise que pour un gestionnaire d'événement (bouton cliqué, par ex.). Partout ailleurs, retourne Task : un async void ne peut pas être await, et une exception qu'il lève n'est pas attrapable proprement — elle peut faire planter le processus.

Trois autres pièges classiques :

  • Oublier await : ChargerNomAsync(1); sans await démarre la tâche mais ne l'attend pas. Le code continue comme si c'était fini, et une éventuelle exception part en silence (fire and forget involontaire). Le compilateur t'avertit (warning CS4014) : écoute-le.
  • Ne pas gérer les exceptions d'une Task : une opération asynchrone peut échouer. L'exception est « stockée » dans la Task et relancée au moment du await. Donc enveloppe ton await d'un try/catch si l'échec est possible.
  • Faire du séquentiel là où Task.WhenAll paralléliserait : enchaîner des await indépendants additionne les temps d'attente. Démarre les tâches puis attends-les ensemble.

Le try entoure le await : c'est là que l'exception de la tâche est relancée, donc là qu'on la capture.

Un cas réel : le await oublié

Cas réel

Une application de saisie enregistrait les fiches clients via EnregistrerAsync(fiche)… mais l'appel avait été écrit sans await. La méthode rendait aussitôt sa Task, le code continuait, et l'interface affichait « Enregistré ✓ » avant même que l'écriture soit finie. Tant que le réseau répondait vite, personne ne voyait rien. Mais dès que la base ralentissait ou renvoyait une erreur, l'exception partait dans le vide (un fire and forget involontaire) : la fiche n'était pas sauvegardée, sans le moindre message. Invisible en test, le bug provoquait des pertes de données en production. Le compilateur l'avait pourtant signalé par l'avertissement CS4014 : appliquer « async all the way » et écouter les avertissements aurait suffi à l'éviter.

Pour aller plus loin

L'asynchrone en C# va bien plus loin que async/await. Voici les directions naturelles une fois ces bases acquises :

Pour aller plus loin

Le CancellationToken permet d'annuler une opération en cours (un appel qui traîne, un utilisateur qui quitte). IAsyncEnumerable<T> avec await foreach consomme un flux asynchrone élément par élément (idéal pour de la pagination). ValueTask évite une allocation quand le résultat est souvent déjà disponible. Et pour du calcul intensif (pas de l'attente, du CPU), regarde la programmation parallèle : Parallel.For, PLINQ, ou les channels (System.Threading.Channels) pour des échanges producteur/consommateur.

Antisèche

Glossaire

Asynchrone
Manière de gérer l'attente (réseau, fichier, base) sans immobiliser un thread ; il est rendu puis repris au retour du résultat.
Thread
Fil d'exécution qui déroule le code ; le bloquer sur une attente le gaspille et peut figer l'interface ou saturer un serveur.
Task / Task<T>
Promesse d'un travail qui s'achèvera plus tard : Task sans valeur, Task<T> produira un T.
async
Modificateur autorisant await dans une méthode ; celle-ci peut alors se suspendre puis reprendre.
await
Attend la fin d'une Task en libérant le thread ; à la reprise, l'exception éventuelle de la tâche est relancée là.
Task.WhenAll
Attend un ensemble de tâches lancées ensemble ; le total tend vers la plus longue au lieu de la somme.
Deadlock (interblocage)
Blocage circulaire : le thread attend la Task et la Task attend le thread ; provoqué par .Result/.Wait().
Async all the way
Principe : rester asynchrone de bout en bout (chaque appelant async et await), sans jamais bloquer au milieu.

Récap et vérification

  • Une opération longue d'I/O (réseau, fichier, base) gaspille un thread si on l'attend de façon bloquante ; l'asynchrone libère ce thread.
  • Task = opération sans valeur de retour ; Task<T> = opération qui produira un T.
  • async autorise await dans une méthode ; await suspend le flux sans bloquer le thread, puis reprend avec le résultat.
  • Bonnes pratiques : async all the way, retourner Task (pas async void), suffixe Async.
  • Task.WhenAll exécute des tâches indépendantes en parallèle et attend l'ensemble.
  • Pièges : .Result/.Wait() (deadlock), await oublié, exceptions non gérées, séquentiel inutile.

Vérifie ta compréhension

  2. Que fait await au thread courant pendant l'attente, et en quoi est-ce différent de .Result ?
  3. Tu dois charger trois ressources indépendantes qui prennent chacune une seconde. Comment t'y prends-tu pour que le total soit d'environ une seconde et non trois ?

Voir une solution

.Result bloque le thread courant jusqu'à ce que la Task soit terminée. Mais dans certains contextes (interface graphique, ancien ASP.NET), la suite de la méthode asynchrone — le code après le await — doit s'exécuter sur ce même thread pour finir. Or ce thread est bloqué à attendre : la Task ne peut jamais se compléter, et le thread ne se débloque jamais. C'est un deadlock. La correction : ne jamais bloquer, await à la place (et rendre l'appelante async).
