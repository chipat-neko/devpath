Module 02 · POO en C# — Leçon 06

Héritage et polymorphisme

~34 min Intermédiaire Leçon 5 recommandée

À la fin de cette leçon, tu sauras

  • savoir spécialiser une classe par héritage (class Chien : Animal) et appeler le constructeur de base avec : base(...) ;
  • savoir déclarer des méthodes virtual, les redéfinir avec override et exploiter la liaison dynamique de façon polymorphe ;
  • savoir définir une classe abstract et redéfinir correctement ToString, Equals et GetHashCode de object ;
  • savoir distinguer override du masquage par new et réagir au type réel d'un objet par pattern matching.
Sommaire de la leçon

Tu sais maintenant créer des classes avec des champs, des propriétés et des méthodes. L'étape suivante consiste à relier tes classes entre elles. Un Chien et un Chat sont tous deux des Animal : ils partagent un nom, savent se présenter, mais émettent un cri différent. Plutôt que de tout réécrire, tu vas hériter du comportement commun et seulement spécialiser ce qui change.

Dans cette leçon, tu vas voir comment dériver une classe avec :, comment la liaison dynamique choisit la bonne méthode à l'exécution grâce à virtual/override, comment définir un contrat avec une classe abstract, et comment object (la racine de tous les types) te fournit ToString, Equals et GetHashCode. On terminera sur le pattern matching par type, très idiomatique en C# moderne.

L'héritage : class Chien : Animal

En C#, on dérive une classe avec deux-points : class Chien : Animal signifie « un Chien est un Animal ». La classe dérivée hérite des membres public et protected de la base, mais pas de ses membres private. On utilise protected précisément pour exposer un membre aux dérivés sans l'ouvrir à tout le monde.

Le constructeur du dérivé appelle celui de la base avec : base(...) : la « partie Animal » de l'objet doit exister avant le corps du constructeur de Chien.

Note

En C#, une classe ne peut hériter que d'une seule classe de base (pas d'héritage multiple). Pour combiner plusieurs « contrats », on utilise des interfaces (leçon suivante). Réserve l'héritage à une vraie relation « est-un » durable.

virtual et override : la liaison dynamique

Par défaut, une méthode n'est pas redéfinissable. Pour qu'un dérivé puisse changer son comportement et que C# choisisse la bonne version selon le type réel de l'objet, déclare la méthode virtual dans la base et redéfinis-la avec override dans le dérivé. C'est la liaison dynamique : l'appel est résolu à l'exécution, pas à la compilation.

La variable a a pour type statique Animal, mais son type réel est Chien : a.Cri() appelle donc Chien.Cri(). Sans virtual/override, l'appel serait figé sur Animal.Cri().

Le mot-clé sealed verrouille : public sealed override string Cri() empêche un dérivé ultérieur de redéfinir à nouveau la méthode, et public sealed class empêche carrément d'hériter de la classe.

Le polymorphisme en pratique

Le polymorphisme, c'est manipuler une variable de type base qui référence en réalité un dérivé. La même ligne de code produit un comportement différent selon le type réel. C'est ce qui te permet de stocker des animaux variés dans une seule liste et de tous les traiter uniformément.

La liste ne connaît que des Animal, pourtant chaque a.Cri() route vers la bonne implémentation. Tu peux ajouter un nouveau type d'animal sans toucher à cette boucle : c'est la grande force du polymorphisme.

Classes et méthodes abstract

Parfois, la classe de base n'a pas de comportement par défaut sensé. Quel serait le cri d'un « animal » générique ? Une méthode abstraite (abstract) déclare une signature sans corps et oblige chaque dérivé à la fournir. Une classe qui contient au moins une méthode abstraite doit être abstract : on ne peut plus l'instancier directement, seulement en dériver.

Note

Le format :F2 utilise la culture courante du système pour le séparateur décimal : une virgule en France (12,57), un point en culture anglaise ou invariante (12.57). Les sorties commentées de cette leçon supposent une machine configurée en français. Pour un résultat reproductible, passe explicitement System.Globalization.CultureInfo.InvariantCulture.

Astuce

Une classe abstract peut mélanger des méthodes abstraites (contrat) et des méthodes concrètes partagées (comportement par défaut hérité). C'est la différence avec une interface, qui décrit surtout un contrat. Utilise abstract quand les dérivés partagent du code et de l'état communs.

Cas réel

La classe Stream de .NET est abstract : elle définit un contrat de lecture/écriture d'octets sans dire d'où ils viennent. Ses dérivées le réalisent chacune à leur façon : FileStream (un fichier), MemoryStream (la mémoire), NetworkStream (le réseau), GZipStream (des octets compressés). Résultat : une méthode qui accepte un Stream — comme source.CopyTo(destination) — fonctionne sans modification avec un fichier, un flux réseau ou de la mémoire. C'est le polymorphisme de cette leçon à l'échelle de tout le framework : on programme contre la base abstraite, et chaque source branche son override.

La classe object : ToString, Equals, GetHashCode

En C#, tout type dérive implicitement de object. Tu hérites donc partout de trois méthodes virtuelles utiles : ToString() (représentation texte), Equals(object?) (égalité) et GetHashCode() (clé de hachage). Par défaut, ToString() renvoie le nom du type et Equals compare les références. Redéfinis-les pour donner un sens métier.

Astuce

Si tu veux justement une égalité « par valeur » sans écrire tout cela, utilise un record : public record Point(int X, int Y); génère pour toi ToString, Equals et GetHashCode cohérents. Garde la redéfinition manuelle pour les vraies classes mutables.

new vs override : le masquage à éviter

Si tu déclares dans le dérivé une méthode du même nom qu'une méthode de la base sans override, le compilateur t'avertit et te suggère new. Le mot-clé new masque la méthode de base au lieu de la redéfinir : il n'y a alors pas de liaison dynamique. Le comportement dépend du type statique de la variable, ce qui surprend presque toujours.

Le même objet répond « Base » ou « Derive » selon le type de la variable : c'est le piège du masquage. Dans la grande majorité des cas, tu voulais override (et donc une base virtual). Réserve new aux rares situations où tu veux délibérément deux méthodes distinctes.

Le pattern matching par type

Pour réagir au type réel d'un objet, le C# moderne offre l'opérateur is (avec capture de variable) et la switch expression. C'est plus sûr et plus lisible qu'une cascade de if avec des casts. Voici notre hiérarchie Forme traitée par pattern matching.

Le motif _ est le cas « par défaut ». La switch expression t'encourage à couvrir tous les cas : pratique quand ta hiérarchie évolue. Note que le polymorphisme classique (méthode virtual) reste souvent préférable quand le comportement « appartient » à la classe ; le pattern matching brille pour la logique externe à la hiérarchie.

Pièges fréquents

Piège fréquent

Oublier virtual/override. Sans eux, aucune liaison dynamique : une variable Animal appelle toujours la version de la base. Le programme compile, mais le polymorphisme ne fonctionne pas. Masquer avec new par accident a le même symptôme : le compilateur t'avertit, ne l'ignore pas.

Piège fréquent

Redéfinir Equals sans GetHashCode. Deux objets « égaux » doivent avoir le même hash, sinon ils se comportent mal dans un Dictionary<TKey, TValue> ou un HashSet<T>. Redéfinis toujours les deux ensemble, avec HashCode.Combine(...).

Piège fréquent

Hériter par réflexe et appeler une méthode virtual dans un constructeur. L'héritage couple fortement dérivé et base : si la relation n'est pas un « est-un » durable, préfère la composition (un champ). Et lors de la construction d'un objet, appeler une méthode virtuelle exécute la version du dérivé alors que ses champs ne sont pas encore initialisés : source de bugs subtils.

Pour aller plus loin

Pour aller plus loin

Les interfaces (leçon suivante) décrivent un contrat sans état et permettent d'« hériter » de plusieurs comportements. La composition remplace avantageusement l'héritage abusif (« a-un » plutôt que « est-un »). Les méthodes d'extension ajoutent des fonctions à un type sans le modifier. Enfin, le pattern matching avancé (motifs de propriétés, de positions, motifs relationnels et and/or) rend les switch très expressifs.

Glossaire

Héritage
Relation « est-un » où une classe dérivée réutilise et spécialise une classe de base ; en C#, une seule classe de base à la fois.
Classe de base / dérivée
La base fournit les membres communs ; la dérivée (: Base) les hérite (public/protected) et en ajoute.
virtual / override
Marquent une méthode redéfinissable dans la base et sa redéfinition dans le dérivé ; ensemble, ils activent la liaison dynamique.
Liaison dynamique
Choix de la méthode à l'exécution selon le type réel de l'objet, pas selon le type déclaré de la variable.
Polymorphisme
Manipuler des objets variés à travers un type commun (base ou interface), chacun réagissant à sa manière au même appel.
abstract
Méthode sans corps (contrat) et classe non instanciable ; oblige chaque dérivé à fournir l'implémentation.
sealed
Verrou : empêche d'hériter d'une classe ou de redéfinir à nouveau une méthode.
Masquage (new)
Déclarer un membre de même nom sans override : il cache celui de la base sans liaison dynamique ; à réserver aux cas rares.

Récap et vérification

  • class D : B exprime « D est un B » ; le dérivé hérite des membres public/protected et appelle la base via : base(...).
  • virtual + override activent la liaison dynamique : la méthode dépend du type réel ; sealed verrouille la redéfinition ou l'héritage.
  • Une classe abstract ne s'instancie pas ; ses méthodes abstract sont des contrats que les dérivés doivent honorer.
  • object est la racine : redéfinis ToString pour l'affichage, et Equals avec GetHashCode pour l'égalité par valeur.
  • new masque (à éviter par erreur) ; le pattern matching (is, switch) réagit au type réel d'un objet.

  3. Tu redéfinis Equals sur une classe Point. Que dois-tu redéfinir aussi, et pourquoi est-ce indispensable pour un HashSet<Point> ?
