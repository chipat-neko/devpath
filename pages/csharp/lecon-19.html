Tester son code avec xUnit et Moq

~34 min Intermédiaire Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • Écrire des tests unitaires avec xUnit ([Fact], Assert) et les lancer avec dotnet test ;
  • Paramétrer un test avec [Theory] et [InlineData] pour couvrir plusieurs cas d'un coup ;
  • Vérifier qu'une méthode lève bien une exception avec Assert.Throws ;
  • Isoler la classe testée de ses dépendances avec des doublures (Moq) et l'injection de dépendances.
Sommaire de la leçon

Tu sais écrire des classes, gérer des exceptions, organiser un projet. Reste une question : comment savoir que ton code fait vraiment ce qu'il prétend, et qu'il continuera à le faire après chaque modification ? La réponse tient en un mot : les tests automatisés. Un test est un petit programme qui exécute ton code avec des entrées connues et vérifie le résultat. Une fois écrit, il tourne en une fraction de seconde, autant de fois qu'on veut, et se plaint dès qu'une régression se glisse.

Dans l'écosystème .NET, le framework de test le plus répandu est xUnit (les alternatives NUnit et MSTest sont très proches). On l'exécute avec la commande dotnet test. Cette leçon te montre le cycle complet : un premier test, des tests paramétrés, la vérification d'exceptions, puis l'isolation des dépendances avec la bibliothèque Moq.

Un premier test : [Fact] et Assert

Un projet de test est un projet .NET à part, qui référence le projet à tester. On le crée en une commande :

Une méthode de test porte l'attribut [Fact] (un fait, toujours vrai). À l'intérieur, on suit le schéma AAA : Arrange (préparer les données), Act (appeler la méthode testée), Assert (vérifier le résultat).

Le nom du test se lit comme une phrase : MéthodeTestée_Situation_RésultatAttendu. Quand un test échoue, ce nom apparaît dans le rapport : un bon nom explique le bug sans même ouvrir le code.

xUnit fournit une famille d'assertions : Assert.Equal, Assert.True/Assert.False, Assert.Null/Assert.NotNull, Assert.Contains, Assert.Empty, etc. Choisis la plus précise : Assert.Equal(5, x) donne un meilleur message d'échec que Assert.True(x == 5).

Astuce

Pour comparer des nombres à virgule flottante, n'utilise jamais l'égalité stricte : les arrondis binaires la font échouer. xUnit propose Assert.Equal(attendu, réel, precision) où precision est le nombre de décimales significatives — par exemple Assert.Equal(0.3, a + b, 3).

Plusieurs cas d'un coup : [Theory] et [InlineData]

Recopier un test pour changer juste les entrées serait fastidieux. Un test paramétré factorise : on marque la méthode [Theory] (au lieu de [Fact]), on ajoute des paramètres, et chaque [InlineData(...)] fournit un jeu de valeurs. xUnit exécute une fois par ligne et les compte comme des tests distincts.

C'est l'occasion de couvrir les cas limites : zéro, négatifs, valeurs extrêmes, chaîne vide. Quand une source de données devient trop riche pour des [InlineData], on passe à [MemberData] ou [ClassData], qui pointent vers une méthode ou une classe fournissant les jeux d'essai.

Note

Chaque test doit être indépendant : xUnit crée une nouvelle instance de la classe de test pour chaque méthode, et ne garantit aucun ordre d'exécution. Ne partage jamais d'état mutable entre tests via un champ statique : un test qui dépend d'un autre finit par échouer « au hasard ».

Tester les erreurs : Assert.Throws

Un code robuste lève des exceptions dans les cas invalides (tu l'as vu à la leçon 9). Ce comportement se teste aussi : Assert.Throws<T> vérifie que le bloc lève bien l'exception attendue — et échoue s'il n'en lève aucune, ou une autre.

Tester le « chemin malheureux » est aussi important que le chemin nominal : c'est souvent là que se cachent les bugs de production.

Isoler avec des doublures : Moq

Un test unitaire doit vérifier une seule unité de code. Problème : une classe dépend souvent d'autres choses — une base de données, une API HTTP, une horloge, un service d'e-mail. Faire appel aux vraies dépendances rendrait le test lent, fragile (le réseau tombe) et non déterministe (la date change). La solution : remplacer ces dépendances par des doublures (test doubles) sous notre contrôle.

Pour que ce remplacement soit possible, la classe testée doit dépendre d'une interface, pas d'une classe concrète. C'est le principe d'inversion des dépendances vu à la leçon 7 : on programme contre un contrat.

La bibliothèque Moq fabrique une doublure d'interface à la volée. On la programme avec Setup(...).Returns(...) : « quand on t'appelle ainsi, réponds cela ». On récupère l'objet réel via .Object.

On distingue deux usages d'une doublure. Un stub fournit des données en entrée (le tarif ci-dessus) : on l'interroge via le résultat. Un mock surveille une interaction sortante (un e-mail envoyé, une ligne écrite) : on le vérifie avec Verify.

Piège fréquent

Ne sur-mocke pas. Si tu vérifies chaque appel interne avec des Verify, ton test épouse l'implémentation plutôt que le comportement : le moindre refactoring le casse alors que le résultat est correct. Règle simple : teste ce que fait le code (sa sortie), pas comment il le fait. Préfère un Assert sur le résultat à un Verify sur les rouages.

La pyramide des tests

Tous les tests ne se valent pas. Les tests unitaires (une classe isolée, avec doublures) sont rapides et nombreux : ils forment la base. Au-dessus, les tests d'intégration vérifient que plusieurs pièces s'assemblent (vraie base de test, vrai fichier) : plus lents, moins nombreux. Au sommet, quelques tests de bout en bout (E2E) traversent toute l'application. Cette forme — beaucoup en bas, peu en haut — est la pyramide des tests.

Pour aller plus loin

Explore FluentAssertions (assertions lisibles : total.Should().Be(10)), la couverture de code avec coverlet (dotnet test --collect:"XPlat Code Coverage"), et l'intégration continue : faire tourner dotnet test à chaque push pour bloquer une régression avant la fusion. Pour les tests d'API ASP.NET Core, regarde WebApplicationFactory (tests d'intégration en mémoire).

Un cas réel : le bug qui revenait tous les six mois

Cas réel

Sur une application de facturation, un calcul de TVA arrondissait 0,015 € à 0,01 € au lieu de 0,02 € (arrondi « banquier » mal choisi). Le bug était corrigé… puis réintroduit deux fois par des refactorings successifs, car rien ne le figeait. La troisième fois, le développeur a d'abord écrit un [Theory] reproduisant précisément le cas ([InlineData(0.015, 0.02)]), l'a vu passer au rouge, puis a corrigé. Ce test de non-régression est resté dans la suite : depuis, toute tentative de casser à nouveau l'arrondi fait échouer dotnet test en CI, avant même la revue. Le test ne coûte que quelques lignes ; le bug, lui, coûtait un correctif tous les six mois.

Antisèche

Glossaire

Test unitaire
Petit programme automatisé qui exécute une unité de code isolée avec des entrées connues et vérifie le résultat attendu.
xUnit
Framework de test répandu en .NET ; on y marque les tests avec [Fact]/[Theory] et on les lance avec dotnet test.
Schéma AAA
Arrange, Act, Assert : préparer le contexte, exécuter l'action testée, vérifier le résultat. Un seul comportement par test.
[Fact] / [Theory]
Un [Fact] teste un cas unique ; un [Theory] paramétré exécute une fois par [InlineData(...)].
Assertion
Vérification qui fait réussir ou échouer le test : Assert.Equal, Assert.Throws, Assert.True…
Doublure (test double)
Objet qui remplace une vraie dépendance pendant le test : stub (fournit des données) ou mock (surveille une interaction).
Moq
Bibliothèque qui fabrique des doublures d'interface : Setup().Returns() programme les réponses, Verify() vérifie les appels.
Test de non-régression
Test ajouté pour figer la correction d'un bug : il échoue si le bug réapparaît, empêchant sa réintroduction.

Récap et vérification

  • Un projet de test dotnet new xunit référence le projet à tester ; dotnet test compile et lance tout.
  • [Fact] pour un cas ; [Theory] + [InlineData] pour couvrir plusieurs entrées, cas limites compris.
  • Le schéma AAA et un nom parlant rendent chaque échec immédiatement compréhensible.
  • Assert.Throws<T> teste le chemin d'erreur autant que le chemin nominal.
  • Dépendre d'interfaces permet d'injecter des doublures (Moq) : tests rapides, déterministes, isolés.
  • La pyramide : beaucoup d'unitaires, quelques tests d'intégration, peu de bout en bout.

Vérifie ta compréhension

  2. Pourquoi la classe testée doit-elle dépendre d'une interface pour qu'on puisse la tester avec Moq ?
  3. Quelle est la différence entre un stub et un mock ?
  4. Qu'est-ce qu'un test de non-régression, et pourquoi l'écrire avant de corriger le bug ?
