Module 06 · C# en pratique : le web — Leçon 17

Une API web avec ASP.NET Core

~40 min Intermédiaire Async (leçon 12) recommandé

À la fin de cette leçon, tu sauras

  • créer une API web avec ASP.NET Core Minimal API ;
  • définir des endpoints et le routage ;
  • renvoyer du JSON et les bons codes de statut ;
  • utiliser l'injection de dépendances intégrée.
Sommaire de la leçon

C# n'est pas qu'un langage : c'est la porte d'entrée de la plateforme .NET, et son débouché numéro un est le web côté serveur avec ASP.NET Core. Des millions d'API d'entreprise tournent dessus, réputées pour leurs performances et leur robustesse. Cette leçon te fait construire ta première API web : des points d'accès qui répondent à des requêtes HTTP en JSON. On utilise l'approche moderne Minimal API, concise et idéale pour apprendre.

Créer le projet

L'outil dotnet génère un projet d'API prêt à tourner en une commande.

Le point d'entrée est Program.cs : en C# moderne, plus besoin de classe ni de Main explicite — le fichier est le programme.

Le premier endpoint

Une Minimal API associe une route (un chemin d'URL) à une fonction qui produit la réponse. MapGet répond aux requêtes GET.

Le segment {nom} dans la route est un paramètre : ASP.NET l'injecte automatiquement dans l'argument nom de la fonction, déjà converti au bon type. Pas de code de parsing à écrire.

Renvoyer du JSON

Renvoyer un objet C# le sérialise automatiquement en JSON. C'est le cœur d'une API REST.

Le record (vu au module POO) est parfait pour un DTO : immuable et concis. ASP.NET convertit l'objet en JSON sans configuration.

Les codes de statut avec Results

Une bonne API renvoie le code HTTP adéquat : 200 (OK), 201 (créé), 404 (introuvable), 400 (requête invalide). La classe Results les produit proprement.

Remarque MapPost avec un paramètre Produit p : ASP.NET désérialise automatiquement le corps JSON de la requête en objet C#. Le routage, la conversion des types et la sérialisation sont gérés pour toi.

L'injection de dépendances

ASP.NET intègre un système d'injection de dépendances : on enregistre des services, et le framework les fournit automatiquement aux endpoints qui les demandent. C'est la clé d'un code testable et organisé.

On ne crée jamais Horloge à la main dans l'endpoint : on déclare en avoir besoin (le paramètre IHorloge), et le conteneur le fournit. Cela découple le code et facilite les tests (on injecte une fausse horloge en test).

Erreur fréquente

La liaison de modèle (model binding) a des règles à connaître : les types simples (int, string, Guid…) sont lus depuis la route ou la query string ; un type complexe (Produit) est lu depuis le corps JSON, et il ne peut y en avoir qu'un seul par requête. Attendre deux objets dans le corps, ou un objet depuis la query, échoue silencieusement (paramètre à null). Pense aussi à valider les données reçues avant de les utiliser : une API ne fait jamais confiance à son client.

Astuce

Ajoute Swagger / OpenAPI à ton projet (builder.Services.AddEndpointsApiExplorer() + le paquet Swashbuckle) : tu obtiens une page web interactive qui documente et teste tous tes endpoints automatiquement. Précieux pour explorer une API en développement.

Pour aller plus loin

Les Minimal API conviennent aux services petits et moyens. Pour de grosses applications, ASP.NET propose aussi les contrôleurs (classes regroupant des endpoints), le filtrage, la validation par attributs, l'authentification (JWT), et bien plus. Et pour persister les données — au lieu de notre List en mémoire — on branche une vraie base via Entity Framework Core, l'ORM de .NET : c'est l'objet de la prochaine leçon.

Un cas réel : l'API qui renvoyait toujours 200

Cas réel

Une équipe livrait le back-end d'une application mobile. Par « simplicité », chaque endpoint renvoyait 200 OK, même en cas d'échec : l'erreur était glissée dans le corps JSON sous la forme { "erreur": "produit introuvable" }. Trois problèmes ont surgi en production. D'abord, la supervision comptait zéro erreur (tout était 200) alors que des requêtes échouaient en masse : les alertes ne se déclenchaient jamais. Ensuite, le client mobile devait disséquer chaque corps pour deviner si l'appel avait réussi, au lieu de tester un simple code de statut ; le code était truffé de cas particuliers. Enfin, les caches et proxys (CDN) mettaient en cache des « succès » qui étaient en réalité des erreurs. La correction a tenu en quelques Results.NotFound(), Results.BadRequest() et Results.Created(...) bien placés : la supervision a retrouvé la vue, le client mobile s'est simplifié, et l'infrastructure a pu faire son travail. La leçon : le code de statut fait partie du contrat de l'API, ce n'est pas un détail cosmétique.

Antisèche

Glossaire

Endpoint
Point d'accès de l'API : une association entre une route (verbe HTTP + chemin) et la fonction qui produit la réponse, déclarée avec MapGet, MapPost…
Routage
Mécanisme qui compare l'URL demandée aux routes déclarées et dirige la requête vers le bon endpoint, en extrayant au passage les paramètres de route.
Minimal API
Style d'API d'ASP.NET Core où un endpoint tient en une ligne (route + lambda), sans classe contrôleur ; idéal pour les services petits et moyens.
Liaison de modèle (model binding)
Remplissage automatique des arguments d'un endpoint : types simples depuis la route ou la query, type complexe (un seul) depuis le corps JSON.
Sérialisation / désérialisation JSON
Conversion d'un objet C# en texte JSON pour la réponse (sérialisation) et l'inverse pour lire le corps d'une requête (désérialisation) : automatique en ASP.NET.
Code de statut HTTP
Nombre à trois chiffres résumant l'issue de la requête : 2xx succès, 4xx erreur du client, 5xx erreur du serveur. Produit proprement par Results.
Injection de dépendances (DI)
Le framework fournit aux endpoints les services qu'ils déclarent en paramètre, après les avoir enregistrés (AddSingleton…) : code découplé et testable.
DTO / record
Objet de transfert de données qui décrit la forme échangée avec le client ; un record immuable et concis y est parfaitement adapté.

Récap et vérification

  • ASP.NET Core (Minimal API) : dotnet new web, endpoints via MapGet/MapPost.
  • Les paramètres de route ({nom}) et le corps JSON sont injectés et convertis automatiquement.
  • Renvoyer un objet → JSON ; Results.Ok/NotFound/Created pour les codes de statut.
  • L'injection de dépendances (AddSingleton + paramètre) découple et facilite les tests.
