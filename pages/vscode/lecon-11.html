Module 6 · Projet — Leçon 11

Projet : configurer un dépôt VS Code de A à Z

~40 min Avancé Leçons 01 à 10 conseillées

À la fin de cette leçon, tu sauras

  • réunir la configuration d'un projet dans le dossier .vscode/ ;
  • choisir quel fichier fait quoi (réglages, extensions, snippets, tâches, débogage) ;
  • rendre un dépôt prêt à l'emploi pour toute une équipe ;
  • mobiliser l'ensemble du cours sur un cas concret.
Sommaire de la leçon

Tu as fait le tour de VS Code : l'interface, l'édition, la recherche, le terminal et Git, les extensions, le débogage, les multi-curseurs, les snippets, les tâches et le développement à distance. Cette dernière leçon rassemble tout en un seul endroit : le dossier .vscode/ à la racine d'un projet. Versionné avec le code, il transforme un simple dépôt en environnement de travail cohérent : chaque personne qui l'ouvre obtient les mêmes réglages, les mêmes extensions conseillées et les mêmes raccourcis de tâches, sans rien configurer à la main.

Le dossier .vscode/, carte du projet

Souviens-toi de la leçon 05 : VS Code distingue les réglages Utilisateur (valables sur ta machine, tous projets confondus) des réglages Espace de travail (propres à ce projet). Ces derniers vivent dans un dossier .vscode/, à la racine, que l'on ajoute au dépôt Git. Cinq fichiers y suffisent à décrire un environnement complet ; chacun a été vu dans une leçon du cours.

1. Les réglages partagés — settings.json

C'est le cœur de la configuration : le formatage à l'enregistrement, le formateur par défaut, la taille de tabulation, les fichiers à masquer. Comme il est versionné, toute l'équipe applique les mêmes règles — fini les diffs pollués par des styles de code divergents.

Utilisateur ou Espace de travail ?

Un réglage placé dans .vscode/settings.json ne concerne que ce projet et prime sur ton réglage Utilisateur. Mets ici ce qui doit être identique pour tous (formatage, exclusions) ; garde tes préférences personnelles (thème, police) dans tes réglages Utilisateur, qui ne sont pas versionnés.

2. Les extensions conseillées — extensions.json

Ce fichier ne force rien : il recommande. À l'ouverture du projet, VS Code affiche une notification « Ce dépôt recommande des extensions » et propose de les installer en un clic. Idéal pour que chacun ait Prettier, ESLint ou l'extension du langage utilisé.

3. Les snippets du projet — projet.code-snippets

En leçon 08, tu as créé des snippets. Rangés dans .vscode/, ils deviennent des raccourcis propres au projet, partagés avec l'équipe : un préfixe suivi de Tab insère un fragment de code, avec des zones d'insertion $1, $2.

4. Les tâches — tasks.json

Une tâche transforme une commande du terminal en entrée de la palette (Terminal → Exécuter la tâche…). Plus besoin de retenir la ligne exacte : on lance Construire ou Tester d'un raccourci, et VS Code capture même les erreurs pour les afficher dans le panneau Problèmes.

5. Le débogage — launch.json

Enfin, launch.json (leçon 06) enregistre comment lancer le débogueur avec F5. Chaque configuration devient un choix dans la vue Exécuter et déboguer — de quoi partager un débogage prêt à l'emploi, sans que personne n'ait à le paramétrer.

Cas réel — le nouveau venu opérationnel en cinq minutes

Une développeuse rejoint une équipe. Sur l'ancien projet, sa première journée passait à installer des extensions au hasard, deviner le formateur attendu et copier des commandes depuis un README poussiéreux. Sur le nouveau, elle clone le dépôt, l'ouvre dans VS Code : une notification lui propose d'installer les extensions recommandées, le formatage s'aligne tout seul à l'enregistrement, la palette liste déjà « Tester » et « Construire », et F5 lance le débogueur. En cinq minutes, elle code dans les mêmes conditions que ses collègues. Ce confort tient à un seul dossier versionné : .vscode/.

Jamais de secrets dans .vscode/

Le dossier est versionné : tout ce qui s'y trouve part sur le dépôt distant. N'y écris jamais de mot de passe, de clé d'API ni de jeton. Pour les valeurs sensibles, utilise un fichier .env ignoré par Git, et référence-les via des variables d'environnement.

Pour aller plus loin — devcontainer.json

Un cran au-dessus des réglages : le fichier .devcontainer/devcontainer.json (leçon 10) décrit un conteneur de développement complet — version de l'outillage, dépendances, extensions — pour que l'environnement soit identique partout, y compris dans un Codespace exécuté dans le navigateur. C'est la config .vscode/ poussée jusqu'à la machine elle-même.

Commence petit

Pas besoin des cinq fichiers d'emblée. Le plus rentable est settings.json (formatage cohérent) et extensions.json (outillage commun). Ajoute tasks.json et launch.json le jour où une commande ou un débogage se répète. Un bon .vscode/ grandit avec le projet.

Antisèche — le dossier .vscode/ en un coup d'œil

Glossaire

Espace de travail (workspace)
Le projet ouvert dans VS Code ; ses réglages propres vivent dans .vscode/ et priment sur les réglages Utilisateur.
Dossier .vscode/
Dossier à la racine du dépôt regroupant la configuration VS Code du projet, versionnée avec le code.
settings.json (de projet)
Réglages partagés de l'espace de travail : formatage, formateur, tabulation, fichiers masqués.
extensions.json
Liste d'extensions recommandées ; VS Code propose de les installer à l'ouverture du projet.
Fichier .code-snippets
Snippets propres au projet : un préfixe + Tab insère un fragment avec zones $1, $2.
tasks.json
Déclare des commandes (build, test) exécutables depuis Exécuter la tâche ou la palette.
launch.json
Décrit une ou plusieurs configurations de débogage lancées avec F5.
devcontainer.json
Décrit un conteneur de développement reproductible (outillage, dépendances, extensions), y compris pour les Codespaces.

Récap et vérification

  • Le dossier .vscode/, versionné, rend un dépôt prêt à l'emploi pour toute l'équipe.
  • settings.json partage les réglages ; extensions.json recommande l'outillage ; les *.code-snippets partagent des fragments.
  • tasks.json range les commandes ; launch.json partage le débogage.
  • On n'y met jamais de secret ; pour aller plus loin, devcontainer.json fige l'environnement entier.

Vérifie ta compréhension

  1. Pourquoi place-t-on .vscode/ sous contrôle de version ?
  2. Quelle différence entre extensions.json et l'installation manuelle d'une extension ?
  3. Pourquoi ne faut-il jamais écrire une clé d'API dans .vscode/settings.json ?

Exercices

Exercice 1Échauffement

Tu démarres un petit projet web en équipe. Quels réglages mettrais-tu dans .vscode/settings.json pour que tout le monde formate le code de la même façon ?

Voir une solution

Au minimum : "editor.formatOnSave": true (formater à chaque enregistrement), "editor.defaultFormatter" pointant vers le formateur commun (par ex. Prettier, "esbenp.prettier-vscode"), et une "editor.tabSize" décidée ensemble (2 ou 4). On peut ajouter "files.exclude" pour masquer node_modules. Comme le fichier est versionné, chaque membre applique ces règles dès qu'il ouvre le projet : les diffs Git ne sont plus pollués par des différences de style.

Exercice 2Application

Écris un .vscode/extensions.json qui recommande Prettier et ESLint. Que verra une personne qui ouvre le projet pour la première fois ?

Voir une solution

À l'ouverture, VS Code repère ce fichier et affiche une notification du type « Ce dépôt recommande des extensions ». Un clic sur « Installer » ajoute Prettier et ESLint. Rien n'est imposé : la personne reste libre de refuser, mais l'outillage attendu est mis en avant sans qu'elle ait à deviner lequel installer.

Exercice 3Défi

Un collègue dit : « Versionner .vscode/, c'est imposer mes réglages aux autres, ça ne me plaît pas. » Que lui réponds-tu ? Distingue ce qui doit être partagé de ce qui reste personnel.

Voir une solution

On partage seulement ce qui doit être identique pour tous parce que ça touche le code commun : le formatage (pour des diffs propres), les exclusions, l'outillage recommandé (extensions.json qui propose sans forcer), les tâches et le débogage du projet. Ces choix relèvent de l'équipe, pas du goût individuel. À l'inverse, tout ce qui est personnel — thème clair/sombre, police, taille de l'éditeur, raccourcis perso — reste dans les réglages Utilisateur, qui ne sont pas versionnés et priment localement là où ils ne cassent rien. Bien séparé, .vscode/ n'impose pas un goût : il garantit une base technique commune tout en laissant chacun libre de son confort.

Mini-projet fil rouge — le dossier .vscode/ complet

Pour clore le cours, construis le dossier .vscode/ complet d'un petit projet Node.js, en réunissant tout ce que tu as appris : réglages partagés, extensions conseillées, un snippet de projet, une tâche de test et une configuration de débogage.

Ce que tu vas construire

Cinq fichiers dans .vscode/ : settings.json (formatage), extensions.json (Prettier + ESLint), projet.code-snippets (un en-tête), tasks.json (tâche « Tester ») et launch.json (débogage Node). De quoi rendre le dépôt utilisable dès le clone.

Étapes

Les réglages

Dans settings.json, active editor.formatOnSave, choisis le formateur et fixe editor.tabSize.

Les extensions

Dans extensions.json, recommande Prettier et ESLint via recommendations.

Un snippet

Dans projet.code-snippets, crée un préfixe licence qui insère un en-tête, avec une zone $1.

Une tâche

Dans tasks.json, déclare une tâche shell npm test du groupe test.

Le débogage

Dans launch.json, ajoute une config Node qui lance index.js, puis versionne le tout.

ProjetFil rouge

Écris les cinq fichiers. Essaie d'abord par toi-même, puis compare avec la solution de référence.

Voir une solution complète

Place ces cinq fichiers dans .vscode/ à la racine, commite-les : n'importe qui clonant le dépôt obtient le formatage, les extensions proposées, le snippet, la tâche « Tester » et le débogage F5 — sans configuration manuelle.
