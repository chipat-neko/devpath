Module 5 · Automatiser et étendre — Leçon 09

Automatiser avec les tâches (tasks.json)

~36 min Avancé Leçons 04 et 06 conseillées

À la fin de cette leçon, tu sauras

  • lancer une commande sans quitter l'éditeur avec une tâche ;
  • écrire un tasks.json (label, type, command, group) ;
  • déclencher la tâche de build avec Ctrl+Shift+B ;
  • rendre les erreurs cliquables avec un problemMatcher et enchaîner des tâches.
Sommaire de la leçon

En leçon 04, tu as découvert le terminal intégré pour taper des commandes. Mais retaper npm run build, npm test ou un long script à chaque fois est fastidieux et source d'erreurs. Les tâches (tasks) enregistrent ces commandes dans le projet : tu les lances d'un raccourci ou depuis la palette, et VS Code peut même relire leur sortie pour transformer les erreurs en liens cliquables. C'est le premier pas vers l'automatisation.

Lancer une tâche

Ouvre la palette (Ctrl+Shift+P) et tape « Exécuter la tâche » (Run Task), ou passe par le menu Terminal → Exécuter la tâche…. VS Code liste les tâches qu'il détecte automatiquement — notamment les scripts de ton package.json (npm) — plus celles que tu as définies. Choisis-en une : elle s'exécute dans un terminal intégré dédié.

Définir une tâche : tasks.json

Pour tes propres commandes, crée le fichier via la palette : « Tâches : Configurer une tâche » → « Créer tasks.json à partir d'un modèle » → « Others ». VS Code écrit .vscode/tasks.json. Voici une tâche minimale :

Les clés à connaître :

  • label : le nom affiché dans la liste des tâches ;
  • type : shell (la commande passe par un shell, pratique pour les enchaînements) ou process (exécutable lancé directement) ;
  • command (et éventuellement args) : la commande à exécuter ;
  • group : build ou test — sert à désigner la tâche par défaut de chaque catégorie.

Pas besoin de tout écrire

Si ton projet a un package.json, VS Code propose déjà tes scripts npm comme tâches, sans tasks.json. Tu n'écris un tasks.json que pour ajouter des commandes maison, choisir la tâche de build par défaut, ou brancher un problemMatcher.

Rendre les erreurs cliquables : le problemMatcher

Voici la vraie valeur ajoutée. Un problemMatcher apprend à VS Code à relire la sortie de la commande pour y repérer les erreurs (fichier, ligne, message) et les afficher dans le panneau Problèmes — chaque entrée devient un lien qui ouvre le fichier à la bonne ligne. Cas réel — la vérification avant chaque commit

Sur un projet d'équipe, on veut que rien ne parte sur le dépôt sans passer le typage, le linter et les tests. Plutôt que de retenir trois commandes, le mainteneur écrit trois tâches (tsc, eslint, test), chacune avec son problemMatcher, puis une tâche composée « Tout vérifier » en dependsOrder: "sequence". Il la met en build par défaut. Désormais, avant de committer, chacun fait Ctrl+Shift+B : les trois vérifications s'enchaînent, et la moindre erreur s'affiche cliquable dans Problèmes. Le fichier tasks.json étant versionné dans .vscode/, toute l'équipe partage exactement le même geste. Résultat : bien moins de builds cassés sur le dépôt commun.

Les tâches ne remplacent pas la CI

Une tâche automatise ton poste : elle est pratique mais dépend de ta machine. Elle ne remplace pas l'intégration continue (CI), qui rejoue ces vérifications sur un serveur neutre pour tout le monde. Vois les tâches comme le premier filet, en local ; la CI reste le garde-fou partagé (cours Git).

Glossaire

Tâche (task)
Commande enregistrée dans le projet, lançable depuis l'éditeur sans la retaper.
tasks.json
Fichier .vscode/ décrivant les tâches du projet.
label
Nom affiché d'une tâche dans la liste « Exécuter la tâche ».
group (build / test)
Catégorie d'une tâche ; avec isDefault, elle devient la tâche par défaut lancée au raccourci.
problemMatcher
Règle qui relit la sortie d'une commande pour en extraire des erreurs cliquables (panneau Problèmes).
Panneau Problèmes
Vue listant erreurs et avertissements, chacun ouvrant le fichier à la bonne ligne.
dependsOn
Liste des tâches préalables ; dependsOrder: "sequence" impose l'ordre.

Récap et vérification

  • Une tâche rejoue une commande (build, test, lint) sans quitter l'éditeur ; les scripts npm sont détectés d'office.
  • On les définit dans .vscode/tasks.json : label, type, command, group.
  • La tâche de build par défaut se lance avec Ctrl+Shift+B.
  • Un problemMatcher rend les erreurs cliquables ; dependsOn enchaîne plusieurs tâches. Les tâches ne remplacent pas la CI.

Vérifie ta compréhension

  1. Où définit-on ses propres tâches, et avec quelles clés minimales ?
  2. À quoi sert un problemMatcher ?
  3. Comment lancer trois vérifications à la suite d'un seul geste ?
