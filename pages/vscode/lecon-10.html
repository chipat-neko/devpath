Module 5 · Automatiser et étendre — Leçon 10

Développer à distance : SSH, WSL et conteneurs

~37 min Avancé Leçons 04 et 05 conseillées

À la fin de cette leçon, tu sauras

  • expliquer le principe du développement à distance ;
  • distinguer SSH, WSL, conteneurs et Codespaces ;
  • comprendre l'architecture interface locale / serveur distant ;
  • lire un devcontainer.json pour un environnement reproductible.
Sommaire de la leçon

Jusqu'ici, ton code vivait sur ta machine. Mais souvent il vit ailleurs : sur un serveur Linux distant, dans le sous-système Linux de Windows (WSL), dans un conteneur Docker, ou dans le nuage. Le développement à distance de VS Code résout élégamment ce cas : tu gardes ton interface locale, fluide et familière, pendant que le code et son exécution restent là où ils doivent être. C'est l'une des fonctions qui ont fait le succès de l'éditeur.

Le principe : l'interface ici, le code là-bas

L'astuce, c'est que VS Code se coupe en deux. La partie interface (fenêtre, menus, éditeur) tourne sur ta machine ; une partie serveur (VS Code Server) s'installe automatiquement sur la machine distante et y exécute le vrai travail : fichiers, terminal, extensions de langage, débogueur. Les deux dialoguent via une connexion sécurisée. Tu édites comme en local, mais tout se passe réellement à distance.

Quatre scénarios, une même logique

Une famille d'extensions officielles (le pack Remote Development) couvre quatre cibles. La logique est toujours la même ; seule la « machine distante » change :

  • Remote - SSH : le code est sur un serveur auquel tu te connectes en SSH (une machine de production, un poste puissant, un cloud) ;
  • WSL : sous Windows, tu édites dans le sous-système Linux (WSL) pour bénéficier d'outils Linux tout en restant sous Windows ;
  • Dev Containers : le code s'exécute dans un conteneur Docker décrivant précisément l'environnement (versions, dépendances) ;
  • GitHub Codespaces : l'environnement complet vit dans le nuage ; tu t'y connectes depuis VS Code ou même un navigateur.

L'indicateur vert, en bas à gauche

Le petit bouton coloré tout en bas à gauche de la fenêtre (l'indicateur distant) montre où tu es connecté : « SSH : serveur », « WSL », « Dev Container »… Clique dessus pour ouvrir un dossier distant, changer de cible, ou revenir en local. C'est ton repère : il évite de croire qu'on édite en local alors qu'on est à distance.

Les conteneurs de dev : devcontainer.json

Le cas des Dev Containers mérite un focus, car il répond à un vrai fléau : « ça marche sur ma machine ». Un fichier .devcontainer/devcontainer.json décrit l'environnement complet — image de base, outils, extensions à installer, commande d'initialisation. VS Code construit le conteneur et s'y connecte : chacun obtient exactement le même environnement.

  • image : l'image Docker de départ (ici Node 20) ;
  • customizations.vscode.extensions : les extensions installées automatiquement dans le conteneur ;
  • postCreateCommand : la commande jouée après la création (installer les dépendances).

Cas réel — un nouveau venu productif en dix minutes

Une équipe accueille une développeuse. Autrefois : une demi-journée à installer la bonne version de Node, une base de données locale, les bons outils, en suivant un README souvent périmé — et malgré tout, des différences subtiles avec les postes des collègues. Depuis que le projet contient un .devcontainer/devcontainer.json, elle clone le dépôt, ouvre le dossier, clique sur « Rouvrir dans le conteneur ». VS Code construit l'environnement décrit, installe les extensions listées, joue npm install… et en dix minutes elle code dans un environnement identique à celui de toute l'équipe. Le fameux « ça marche chez moi » disparaît : l'environnement est versionné avec le code.

Où s'installent les extensions ?

À distance, VS Code distingue les extensions de l'interface (thèmes, raccourcis — côté local) et celles qui touchent au code (langages, linters, débogueurs — côté distant). Si une extension de langage « ne fait rien » en session distante, c'est souvent qu'elle est installée en local seulement : installe-la dans la cible distante (le panneau Extensions montre les deux emplacements).

Glossaire

Développement à distance
Éditer avec une interface locale un code qui vit et s'exécute sur une autre machine.
VS Code Server
Partie serveur installée automatiquement côté distant ; y tournent fichiers, terminal et extensions.
SSH
Protocole de connexion sécurisée à une machine distante ; base de l'extension Remote - SSH.
WSL
Windows Subsystem for Linux : un Linux intégré à Windows, éditable via l'extension WSL.
Dev Container
Conteneur Docker servant d'environnement de développement, décrit par devcontainer.json.
devcontainer.json
Fichier décrivant l'environnement reproductible : image, extensions, commandes d'init.
Codespaces
Environnement de développement complet hébergé dans le nuage par GitHub.
Indicateur distant
Bouton en bas à gauche montrant la cible de connexion (SSH, WSL, conteneur…).

Récap et vérification

  • Le développement à distance garde l'interface en local et exécute le code sur une machine distante (via VS Code Server).
  • Quatre cibles : SSH (serveur), WSL (Linux sous Windows), Dev Containers (Docker), Codespaces (nuage).
  • devcontainer.json décrit un environnement reproductible (image, extensions, postCreateCommand) — fin du « ça marche chez moi ».
  • Les extensions de langage s'installent côté distant ; l'indicateur en bas à gauche rappelle où tu es.

Vérifie ta compréhension

  1. Qu'est-ce qui reste local et qu'est-ce qui part à distance ?
  2. Cite les quatre cibles du développement à distance.
  3. Quel problème le devcontainer.json résout-il ?

Exercices

Exercice 1Échauffement

Explique, en une phrase, ce qui reste sur ta machine et ce qui part à distance quand tu ouvres un dossier via Remote - SSH.

Voir une solution

Reste local : l'interface de VS Code — la fenêtre, l'éditeur, le thème, tes raccourcis. Part à distance : tout le reste — les fichiers du projet, le terminal, les extensions de langage, le débogueur et l'exécution du code — pris en charge par VS Code Server installé automatiquement sur le serveur. Tu édites en local, le travail réel se fait sur la machine distante.

Exercice 2Application

Un collègue sous Windows veut utiliser des outils Linux (bash, make…) sans machine virtuelle lourde ni dépôt distant. Quelle cible lui conseilles-tu ?

Voir une solution

WSL (Windows Subsystem for Linux). Avec l'extension WSL, VS Code ouvre le projet dans la distribution Linux intégrée à Windows : il dispose alors de tous les outils Linux (bash, make, gcc…), avec l'interface Windows habituelle et de bonnes performances. Pas de serveur distant ni de VM classique à gérer : le « distant » est simplement le Linux local de WSL. L'indicateur en bas à gauche affichera « WSL ».

Exercice 3Défi

Ton équipe passe une demi-journée à configurer chaque nouveau poste, avec des écarts de versions d'un développeur à l'autre. Quelle solution proposes-tu, et que mettrais-tu dedans ?

Voir une solution

Ajouter un Dev Container au dépôt : un fichier .devcontainer/devcontainer.json versionné avec le code. J'y mettrais : l'image de base figeant la bonne version du langage (ex. Node 20), la liste des extensions VS Code utiles au projet (formateur, linter), et un postCreateCommand installant les dépendances (npm install). Chaque personne n'a plus qu'à « Rouvrir dans le conteneur » : elle obtient un environnement identique en quelques minutes, sans écart de version. L'environnement devient reproductible et partagé, exactement comme le code — et il évolue avec lui dans Git.
