Le cache HTTP

~34 min Intermédiaire Leçons 03 à 05 conseillées

À la fin de cette leçon, tu sauras

  • expliquer à quoi sert le cache et où il vit ;
  • lire les directives de Cache-Control ;
  • comprendre la revalidation par ETag et le 304 ;
  • distinguer cache privé et partagé, et le cache-busting.
Sommaire de la leçon

Une page web tire des dizaines de fichiers : HTML, CSS, images, polices, scripts. Les re-télécharger à chaque visite serait lent et coûteux. Le cache HTTP permet de garder une copie locale d'une ressource et de la réutiliser sans redemander au serveur — ou en le redemandant juste assez pour vérifier qu'elle n'a pas changé. C'est l'un des plus gros leviers de performance du web, et il tient dans quelques en-têtes (leçon 05).

Garder une copie plutôt que tout redemander

Un cache est une mémoire de ressources déjà reçues. Ton navigateur en possède un (sur le disque et en mémoire) ; il existe aussi des caches partagés sur le chemin : un proxy d'entreprise, un CDN (réseau de serveurs répartis proches des visiteurs). Face à une ressource, le cache se pose deux questions : ma copie est-elle encore fraîche ? et si elle est périmée, a-t-elle vraiment changé ?

Cache-Control : l'en-tête maître

C'est le serveur qui décide de la politique de cache, en ajoutant l'en-tête Cache-Control à sa réponse. Ses directives principales :

  • max-age=SECONDES : durée pendant laquelle la copie est considérée fraîche (ex. max-age=3600 = 1 h).
  • no-cache : on peut stocker la copie, mais il faut revalider auprès du serveur avant chaque usage.
  • no-store : ne rien garder (pour des données sensibles : page de compte bancaire…).
  • private : seul le navigateur de l'utilisateur peut cacher ; public : les caches partagés (CDN, proxy) aussi.
  • immutable : promet que le contenu ne changera pas ; le navigateur ne revalide même pas pendant la durée.

Ici le serveur dit : « ce fichier est public, valable un an (31 536 000 s) et ne changera pas ». Un tel réglage ne convient qu'à une ressource dont le nom change quand le contenu change (on y revient plus bas).

Frais ou périmé : la revalidation

Tant que la copie est fraîche (dans la fenêtre max-age), le navigateur la sert directement : aucune requête. Une fois périmée (stale), il ne la jette pas pour autant : il fait une requête conditionnelle pour demander « a-t-elle changé ? ».

Le mécanisme repose sur l'ETag (entity tag), une empreinte de la ressource fournie par le serveur. Le navigateur la renvoie dans If-None-Match. Si le serveur constate que l'empreinte est inchangée, il répond 304 Not Modified sans corps : le navigateur réutilise sa copie. Sinon, il renvoie 200 avec le nouveau contenu.

Cache privé, cache partagé, et le rôle de Vary

La directive private réserve la copie au navigateur d'un seul utilisateur (utile pour une réponse personnalisée). Avec public, un cache partagé comme un CDN peut garder une copie et la servir à tous les visiteurs : c'est ce qui rend les gros sites rapides partout dans le monde.

Mais un cache partagé doit être prudent : si une réponse dépend d'un en-tête de la requête (la langue, l'encodage accepté…), servir la même copie à tout le monde serait faux. L'en-tête Vary le lui dit : Vary: Accept-Encoding signifie « garde une copie distincte par valeur d'Accept-Encoding » (leçon 09).

Le piège : comment mettre à jour un fichier caché un an ?

Si app.css est caché un an et que tu corriges un bug, comment forcer les visiteurs à recharger ? On ne modifie pas le cache : on change l'URL. C'est le cache-busting : on nomme le fichier d'après une empreinte de son contenu, app.9f2a.css. Un contenu modifié donne un nouveau nom : app.b3d1.css, donc une nouvelle ressource, re-téléchargée. Les fichiers versionnés ainsi peuvent porter max-age=31536000, immutable sans risque.

Le HTML, lui, référence ces noms : on le cache peu (ou en no-cache) pour qu'il pointe toujours vers les dernières versions.

Frais (fresh) vs périmé (stale)

Une copie est fraîche tant qu'on est dans sa fenêtre max-age : elle est servie sans contacter le serveur. Passé ce délai, elle devient périmée : elle n'est pas supprimée, mais doit être revalidée (requête conditionnelle) avant d'être réutilisée. « Périmé » ne veut donc pas dire « jeté », juste « à revérifier ».

Observe le cache dans l'onglet Réseau

Ouvre F12 → Réseau et recharge la page. Dans la colonne Taille, tu verras (from disk cache) ou (from memory cache) pour les HIT, et un poids réel pour les MISS ; les revalidations apparaissent en 304. La case « Désactiver le cache » force tout à retélécharger : pratique en développement, pour ne pas travailler sur d'anciennes versions.

no-cache n'est pas no-store

Piège classique : no-cache autorise le stockage — il impose juste une revalidation à chaque usage. Pour interdire réellement toute conservation (données bancaires, informations personnelles), c'est no-store qu'il faut. Autre erreur : marquer public une réponse personnalisée ; un CDN pourrait alors servir les données d'un utilisateur à un autre.

Cas réel

La deuxième visite quasi gratuite. Les frameworks web modernes (comme Vite ou webpack) génèrent des fichiers au nom « empreinté » : main.9f2a1c.js, vendor.b3d1e0.css. Le serveur les sert avec Cache-Control: public, max-age=31536000, immutable. Résultat : lors d'une première visite, le navigateur télécharge tout ; aux visites suivantes, il ne récupère que le petit HTML et éventuellement quelques 304 — parfois plus de 90 % des octets sont servis depuis le cache. Quand une mise à jour sort, seuls les fichiers modifiés changent de nom et sont re-téléchargés ; le reste demeure en cache. Ce couple « URL empreintée + cache très long » est le socle de la performance des sites d'aujourd'hui.

Pour aller plus loin

La directive stale-while-revalidate autorise à servir immédiatement une copie périmée tout en la revalidant en arrière-plan : rapidité et fraîcheur. L'en-tête Age indique depuis combien de temps une réponse dort dans un cache partagé. Enfin, un Service Worker (JavaScript) permet un cache programmable côté client : c'est la base des applications web hors-ligne (PWA), au-delà de ce que gèrent seuls les en-têtes HTTP.

Antisèche

Glossaire

Cache
Mémoire de ressources déjà reçues, réutilisées pour éviter de retélécharger ; privé (navigateur) ou partagé (proxy, CDN).
Cache-Control
En-tête de réponse qui définit la politique de cache via des directives (max-age, no-store, private…).
Fraîcheur (fresh/stale)
Une copie est fraîche dans sa fenêtre max-age (servie sans réseau), puis périmée (à revalider).
Revalidation
Requête conditionnelle qui demande au serveur si une copie périmée a changé, sans forcément la retélécharger.
ETag
Empreinte d'une ressource fournie par le serveur ; renvoyée par le client dans If-None-Match pour revalider.
304 Not Modified
Réponse sans corps signifiant « rien n'a changé » : le client réutilise sa copie en cache.
Vary
En-tête disant sur quels en-têtes de requête dépend la réponse, pour qu'un cache partagé garde les bonnes variantes.
Cache-busting
Technique consistant à changer l'URL (nom empreinté) quand le contenu change, pour contourner un cache de longue durée.

Récap et vérification

  • Le cache garde des copies pour éviter de retélécharger ; il vit dans le navigateur (privé) ou sur le chemin (partagé, CDN).
  • Cache-Control pilote tout : max-age (fraîcheur), no-cache (revalider), no-store (rien garder), private/public.
  • Périmé n'est pas jeté : on revalide avec l'ETag et If-None-Match ; si inchangé, 304 sans corps.
  • Pour mettre à jour un fichier caché longtemps : le cache-busting (nom empreinté).

Exercices

Exercice 1Échauffement

Tu recharges une page et, dans l'onglet Réseau, une image affiche (from disk cache) tandis qu'une autre affiche 304. Quelle différence entre les deux ?

Voir une solution

(from disk cache) signifie que la copie était encore fraîche (dans son max-age) : le navigateur l'a servie sans aucune requête réseau. Le 304, lui, signifie que la copie était périmée : le navigateur a fait une requête conditionnelle (avec If-None-Match), le serveur a confirmé que rien n'avait changé et a répondu 304 Not Modified sans corps. Dans les deux cas, le fichier n'est pas retéléchargé ; mais le premier ne coûte rien, le second coûte un aller-retour.

Exercice 2Application

Un développeur met Cache-Control: no-cache sur les réponses d'un tableau de bord qui affiche des données bancaires, pensant « ne jamais mettre en cache ». Où est l'erreur, et que faut-il écrire ?

Voir une solution

no-cache ne veut pas dire « ne pas cacher » : la réponse est stockée, elle est simplement revalidée avant chaque usage. Une copie des données bancaires peut donc rester sur le disque, ou dans un cache partagé. Pour des données sensibles, il faut Cache-Control: no-store (ne rien conserver), idéalement complété par private. La règle : no-store pour « rien garder », no-cache seulement pour « garder mais toujours revérifier ».

Exercice 3Défi

Tu déploies un site avec app.css servi en max-age=31536000 (un an). Deux jours plus tard, tu corriges une couleur dans le CSS. Les visiteurs voient-ils le changement ? Décris la bonne stratégie de cache pour le HTML et pour le CSS.

Voir une solution

Non : tant que leur copie de app.css est fraîche (un an !), les visiteurs la servent depuis le cache sans contacter le serveur : ils ne verront jamais ta correction. Le fichier étant caché sous ce nom, on ne peut pas le « rafraîchir » à distance. La bonne stratégie : cache-busting. On nomme le CSS d'après une empreinte de son contenu — app.9f2a.css — et on le sert en max-age=31536000, immutable. Quand tu modifies le fichier, son empreinte change : app.b3d1.css ; c'est une nouvelle URL, donc retéléchargée. Le HTML, qui référence ce nom, doit lui être caché très peu (par exemple no-cache) pour toujours pointer vers la dernière version des fichiers. Ainsi : HTML frais et léger + assets versionnés cachés très longtemps = mises à jour instantanées et performance maximale.
