Les URL et le DNS

~26 min Débutant Leçon 01 conseillée

À la fin de cette leçon, tu sauras

  • décortiquer une URL partie par partie ;
  • expliquer le rôle du DNS ;
  • dire ce qu'est un port ;
  • suivre la résolution d'un nom de domaine.
Sommaire de la leçon

Avant qu'une requête puisse partir (leçon 03), il faut savoir où l'envoyer. Cette information est entièrement contenue dans l'URL que tu tapes. Et comme cette URL contient un nom plutôt qu'une adresse numérique, une traduction s'opère en coulisses : le DNS. Décortiquons les deux.

L'anatomie d'une URL

Une URL (Uniform Resource Locator) est l'adresse complète d'une ressource sur le web. Elle se découpe en plusieurs parties :

  • le schéma (https) : le protocole à utiliser (http ou https).
  • l'hôte (boutique.exemple.com) : le nom de domaine du serveur. boutique est un sous-domaine, exemple le domaine, .com l'extension (TLD).
  • le port (443) : la « porte » sur le serveur (voir plus bas). Presque toujours omis car implicite.
  • le chemin (/produits/42) : quelle ressource précise on demande sur ce serveur.
  • la chaîne de requête (?couleur=bleu) : des paramètres, sous forme clé=valeur séparés par &.
  • le fragment (#avis) : un repère dans la page (une ancre). Il n'est pas envoyé au serveur ; le navigateur s'en sert pour faire défiler.

Savoir lire une URL, c'est déjà comprendre où va une requête et ce qu'elle transporte. Le chemin et la requête sont les deux parties que tu manipuleras le plus.

Les ports

Une même machine héberge souvent plusieurs services (un serveur web, une base de données, une messagerie…). Le port est un numéro qui dit « à quel service de cette machine » s'adresser : comme un numéro d'appartement après l'adresse de l'immeuble (l'IP). Quelques ports standard :

Comme 80 et 443 sont les ports par défaut du web, on ne les écrit pas dans l'URL : https://exemple.com sous-entend :443. On ne précise un port que s'il est inhabituel, par exemple localhost:3000 en développement.

Le DNS : du nom à l'adresse

Le serveur, lui, n'est joignable que par son adresse IP (leçon 01). Or l'URL contient un nom (exemple.com). Le DNS (Domain Name System) est l'annuaire mondial qui fait la traduction : il convertit un nom de domaine en adresse IP. C'est comme chercher un nom dans un répertoire pour obtenir un numéro de téléphone.

Interroge le DNS toi-même

Dans un terminal (cours Bash), la commande nslookup exemple.com (ou dig exemple.com) affiche l'adresse IP derrière un nom de domaine. Essaie avec quelques sites : tu verras la traduction nom → IP que ton navigateur fait silencieusement à chaque visite.

Cas réel

Le 21 octobre 2016, une grande partie du web (Twitter, Spotify, Reddit, GitHub, Netflix…) est devenue inaccessible pendant des heures. Les serveurs de ces sites fonctionnaient pourtant. La cible était Dyn, un gros fournisseur de DNS : submergé par une attaque, il ne répondait plus à la question « quelle est l'IP de… ? ». Sans traduction nom → IP, les navigateurs ne pouvaient plus joindre des sites dont l'adresse existait pourtant toujours. Un annuaire en panne suffit à rendre le web injoignable : le DNS est un maillon aussi discret que critique.

Attention au cache

Après un changement d'IP (nouvel hébergeur, migration), la propagation DNS n'est pas instantanée : tant que le TTL des anciennes réponses n'a pas expiré dans les caches, une partie des visiteurs est encore envoyée vers l'ancien serveur. Bon réflexe : abaisser le TTL à l'avance, avant une migration prévue, pour que les caches se rafraîchissent plus vite le jour J.

Pour aller plus loin

On peut choisir son résolveur : des résolveurs publics comme 1.1.1.1 (Cloudflare) ou 8.8.8.8 (Google) remplacent parfois avantageusement celui du fournisseur d'accès. Le DNS classique circule en clair ; DoH (DNS over HTTPS) et DoT (DNS over TLS) le chiffrent pour que les noms consultés restent privés.

Glossaire

URL
Uniform Resource Locator : l'adresse complète d'une ressource sur le web, découpée en schéma, hôte, port, chemin, requête et fragment.
Schéma
Le protocole en tête d'URL (http, https) qui indique comment communiquer avec le serveur.
Hôte (domaine)
Le nom du serveur dans l'URL (boutique.exemple.com) : sous-domaine, domaine et extension (TLD).
Port
Numéro qui désigne le service visé sur la machine : 80 pour HTTP, 443 pour HTTPS (implicites), 3000 en développement.
Chemin / Requête / Fragment
Le chemin (/produits/42) désigne la ressource ; la requête (?clé=valeur) ajoute des paramètres ; le fragment (#ancre) reste dans le navigateur.
DNS
Domain Name System : l'annuaire mondial qui traduit un nom de domaine en adresse IP.
Résolveur
Le serveur DNS (souvent celui du fournisseur d'accès) qui mène la résolution pour le navigateur et met les réponses en cache.
TTL
Time To Live : durée pendant laquelle une réponse DNS reste en cache avant d'être redemandée ; il gouverne la vitesse de propagation d'un changement.

Récap et vérification

  • Une URL se découpe en schéma, hôte, port, chemin, requête (?clé=valeur) et fragment (#ancre, non envoyé au serveur).
  • Le port désigne le service visé sur la machine : 80 pour HTTP, 443 pour HTTPS (implicites).
  • Le DNS traduit un nom de domaine en adresse IP, via une cascade de serveurs.
  • Les résolutions sont mises en cache (TTL) pour accélérer les visites suivantes.

Exercices

Exercice 1Échauffement

Découpe l'URL https://api.meteo.fr/villes/paris?jours=5 en ses parties.

Voir une solution

Schéma : https. Hôte : api.meteo.fr (sous-domaine api, domaine meteo, TLD .fr). Port : implicite (443). Chemin : /villes/paris. Requête : ?jours=5 (un paramètre jours valant 5). Pas de fragment.

Exercice 2Application

Tu lances un site en développement sur ta machine, accessible à http://localhost:3000. Explique chaque partie, et pourquoi le port est écrit ici alors qu'il ne l'est pas pour un site public.

Voir une solution

http est le schéma (non chiffré, acceptable en local). localhost est un nom spécial qui désigne ta propre machine (IP 127.0.0.1). :3000 est le port : le serveur de développement écoute sur le port 3000, qui n'est pas un port web par défaut. Comme 3000 n'est pas implicite (contrairement à 80/443), il faut l'écrire : sans lui, le navigateur tenterait le port 80 et ne trouverait rien. Pour un site public en HTTPS, le port 443 est sous-entendu, donc invisible.

Exercice 3Défi

Tu changes l'hébergeur de ton site : l'adresse IP du serveur change, mais le nom de domaine reste le même. Pendant quelques heures, certains visiteurs voient l'ancien site, d'autres le nouveau. Explique pourquoi avec le DNS.

Voir une solution

Le nom de domaine n'a pas changé, mais l'enregistrement DNS qui l'associe à une IP, oui : il pointe désormais vers le nouveau serveur. Le problème vient du cache DNS : les anciennes réponses (nom → ancienne IP) restent mémorisées par les navigateurs, systèmes et résolveurs des fournisseurs d'accès pendant la durée du TTL. Tant que ce cache n'a pas expiré, ces visiteurs continuent d'être envoyés vers l'ancienne IP, donc l'ancien site ; les autres, dont le cache a expiré (ou qui n'avaient pas l'entrée), refont une résolution et obtiennent la nouvelle IP. C'est la propagation DNS : elle prend le temps du TTL. Pour limiter la gêne, on abaisse le TTL avant une migration prévue, afin que les caches se rafraîchissent plus vite.
