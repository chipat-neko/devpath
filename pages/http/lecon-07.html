Module 3 · Web moderne et sécurité — Leçon 07

CORS et l'évolution du protocole

~30 min Intermédiaire Leçons 03 à 06 conseillées

À la fin de cette leçon, tu sauras

  • définir une origine et la politique de même origine ;
  • expliquer le rôle de CORS et du préflight ;
  • situer HTTP/1.1, HTTP/2 et HTTP/3 ;
  • récapituler les bonnes pratiques du web.
Sommaire de la leçon

Deux sujets de plus, incontournables du web moderne. D'abord CORS, ce mécanisme que tout développeur web finit par rencontrer (souvent via un message d'erreur dans la console !). Ensuite, un panorama de l'évolution du protocole — HTTP/1.1, HTTP/2, HTTP/3 — pour comprendre comment le web est devenu plus rapide sans changer ses messages.

L'origine et la politique de même origine

Une origine est le triplet schéma + hôte + port. Deux URL ont la même origine seulement si ces trois éléments sont identiques :

Par sécurité, les navigateurs appliquent la politique de même origine : par défaut, un script chargé par une page ne peut lire la réponse d'une requête vers une autre origine. Sans cette règle, un site malveillant pourrait, depuis ton navigateur déjà connecté, lire les données de ta banque ou de ta messagerie. C'est une protection fondamentale du web.

CORS : autoriser le cross-origin

Mais il est légitime qu'une page de site.com appelle une API sur api.site.com ou un service tiers. CORS (Cross-Origin Resource Sharing) est le mécanisme par lequel le serveur autorise explicitement certaines origines à lire ses réponses, via des en-têtes :

L'en-tête Access-Control-Allow-Origin dit au navigateur « j'autorise https://site.com à lire cette réponse ». Sans cet en-tête, le navigateur bloque la lecture côté page (et affiche l'erreur CORS bien connue) — même si le serveur, lui, a bien répondu. Point clé : CORS est une décision du serveur, appliquée par le navigateur ; ce n'est pas une erreur de ton code, mais une autorisation manquante côté serveur.

Le préflight

Pour les requêtes « non simples » (méthode PUT/DELETE, en-têtes personnalisés, certains Content-Type…), le navigateur envoie d'abord une requête de vérification préalable (préflight) avec la méthode OPTIONS :

Si la réponse autorise la méthode et l'origine, le navigateur envoie ensuite la vraie requête ; sinon, il l'annule. Ce OPTIONS est envoyé automatiquement par le navigateur : tu n'as pas à l'écrire, mais le voir dans l'onglet Réseau explique pourquoi une requête « part en double ».

L'évolution du protocole

HTTP a gagné en vitesse au fil des versions, sans changer ses messages (mêmes méthodes, en-têtes, codes) :

L'idée directrice : réduire les attentes. En HTTP/1.1, les nombreuses ressources d'une page (leçon 01) se gênaient ; HTTP/2 les fait voyager en parallèle ; HTTP/3 supprime des blocages réseau hérités de TCP. Pour toi qui écris des requêtes, rien ne change dans leur forme : ce sont les mêmes GET, en-têtes et statuts ; seul le transport s'optimise, comme HTTPS l'avait fait pour la sécurité.

Le fil rouge du cours

Remarque la constante : les messages HTTP ne changent pas. HTTPS ajoute un tunnel chiffré (leçon 06), HTTP/2 et HTTP/3 accélèrent le transport — mais la requête, ses en-têtes, son code de statut restent ce que tu as appris. Comprendre ce socle, c'est comprendre le web d'hier comme celui de demain. Pour la suite : le cours API REST applique tout cela à l'échange de données, et le cours Sécurité approfondit les failles côté application.

Cas réel

« Mon code marche, mais le navigateur bloque tout ! » C'est l'erreur qui fait perdre des heures à chaque développeur débutant. Sa page appelle une API sur un autre domaine, la console affiche blocked by CORS policy, et il modifie son JavaScript dans tous les sens… en vain. La clé : CORS n'est pas un bug de ton code. Le serveur a bien répondu — tu le vois dans l'onglet Réseau, statut 200 — mais comme sa réponse ne contient pas l'en-tête Access-Control-Allow-Origin autorisant ton origine, le navigateur refuse de laisser ta page lire le résultat. La correction est côté serveur, jamais dans la page. Comprendre qui décide (le serveur) et qui applique (le navigateur) fait gagner ces heures-là.

Lis le message d'erreur en entier

La console du navigateur ne dit pas seulement « CORS » : elle précise pourquoi — en-tête Access-Control-Allow-Origin absent, méthode non autorisée, préflight échoué… Cette ligne indique exactement quel en-tête configurer côté serveur. En développement local, un proxy (ou l'option adéquate du serveur de dev) évite aussi les soucis d'origine.

Access-Control-Allow-Origin: * n'est pas une baguette magique

L'astérisque autorise toutes les origines : pratique pour une API publique en lecture, risqué pour une API privée. Surtout, il est incompatible avec l'envoi de cookies d'authentification : pour une API authentifiée, il faut nommer explicitement les origines de confiance, pas mettre *. Ouvrir en grand pour « faire taire l'erreur » crée un trou de sécurité.

Pour aller plus loin

HTTP/3 repose sur QUIC, un transport bâti sur UDP plutôt que TCP : il supprime le « blocage en tête de file » de TCP et survit mieux aux changements de réseau (passer du Wi-Fi à la 4G sans rompre la connexion). Côté sécurité, les en-têtes Content Security Policy (CSP) et Permissions-Policy prolongent l'idée de CORS : le serveur déclare ce que la page a le droit de faire. Le fil reste le même — le serveur décide, le navigateur applique.

Antisèche

Glossaire

Origine
Triplet schéma + hôte + port ; deux URL sont de même origine seulement si les trois coïncident. Le chemin n'entre pas en compte.
Politique de même origine (SOP)
Règle de sécurité du navigateur : par défaut, un script ne peut pas lire la réponse d'une requête vers une autre origine.
CORS
Cross-Origin Resource Sharing : mécanisme par lequel le serveur autorise explicitement certaines origines à lire ses réponses.
Access-Control-Allow-Origin
En-tête de réponse par lequel le serveur nomme l'origine (ou *) autorisée à lire le résultat.
Préflight
Requête OPTIONS envoyée automatiquement par le navigateur avant une requête « non simple », pour vérifier la permission.
Multiplexage
Faire voyager plusieurs échanges en parallèle sur une seule connexion (apport majeur d'HTTP/2).
HTTP/2
Version binaire d'HTTP introduisant le multiplexage ; mêmes méthodes, en-têtes et codes qu'HTTP/1.1.
HTTP/3 (QUIC)
Version transportée par QUIC, au-dessus d'UDP : plus rapide et plus résistante aux pertes et aux changements de réseau.

Récap et vérification

  • Une origine = schéma + hôte + port ; la politique de même origine bloque par défaut la lecture cross-origin (sécurité).
  • CORS est l'autorisation, décidée par le serveur (en-tête Access-Control-Allow-Origin) et appliquée par le navigateur.
  • Le préflight (OPTIONS automatique) vérifie la permission avant une requête non simple.
  • HTTP/1.1 → 2 → 3 accélèrent le transport (multiplexage, QUIC) sans changer la forme des messages.

Exercices

Exercice 1Échauffement

La page https://app.exemple.com appelle https://api.exemple.com/data. Est-ce la même origine ? Qu'implique la réponse ?

Voir une solution

Non : l'hôte diffère (app.exemple.com vs api.exemple.com, deux sous-domaines distincts), donc ce sont deux origines différentes — même si le domaine racine est le même. Conséquence : la requête est cross-origin ; pour que la page puisse lire la réponse, le serveur d'API doit renvoyer un en-tête Access-Control-Allow-Origin: https://app.exemple.com (ou l'autoriser autrement). Sans cela, le navigateur bloquera la lecture avec une erreur CORS.

Exercice 2Application

Dans l'onglet Réseau, tu vois qu'avant ta requête DELETE, le navigateur a envoyé une requête OPTIONS vers la même URL. Que s'est-il passé, et qui l'a déclenchée ?

Voir une solution

C'est le préflight CORS. Comme DELETE est une méthode « non simple », le navigateur a automatiquement envoyé une requête OPTIONS au serveur pour lui demander « autorises-tu un DELETE depuis cette origine ? ». Le serveur répond avec Access-Control-Allow-Methods et Access-Control-Allow-Origin ; si la méthode et l'origine sont autorisées, le navigateur envoie ensuite la vraie requête DELETE. Tu n'as pas écrit ce OPTIONS : c'est le navigateur qui le gère, d'où l'impression d'une requête « en double ».

Exercice 3Défi

On entend : « CORS, c'est pénible, ça bloque mes requêtes pour rien ». Explique pourquoi cette protection existe, et pourquoi la désactiver dans le navigateur serait une mauvaise idée.

Voir une solution

CORS découle de la politique de même origine, qui protège l'utilisateur. Imagine : tu es connecté à ta banque dans un onglet. Dans un autre onglet, tu ouvres un site malveillant. Sans la politique de même origine, le JavaScript de ce site pourrait, depuis ton navigateur déjà authentifié (tes cookies de session étant envoyés, leçon 05), faire une requête vers l'API de ta banque et lire la réponse — donc tes comptes. La politique de même origine empêche par défaut cette lecture cross-origin ; CORS est le moyen contrôlé par lequel un serveur autorise explicitement les origines de confiance. Ce n'est donc pas un caprice : c'est ce qui empêche n'importe quel site de piller tes sessions ouvertes. Désactiver cette sécurité dans le navigateur (ce que certains tutoriels suggèrent à tort) reviendrait à exposer toutes tes sessions à n'importe quel site visité : dangereux. La bonne solution est toujours de configurer correctement CORS côté serveur (autoriser les origines légitimes), jamais d'affaiblir le navigateur. Une erreur CORS n'est pas un obstacle à contourner, c'est une autorisation à accorder, au bon endroit.
