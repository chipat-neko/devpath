Module 1 · Le web, comment ça marche — Leçon 03

La requête et la réponse HTTP

~28 min Débutant Leçon 01 conseillée

À la fin de cette leçon, tu sauras

  • décrire la structure d'une requête HTTP ;
  • décrire la structure d'une réponse HTTP ;
  • distinguer ligne de départ, en-têtes et corps ;
  • expliquer pourquoi HTTP est sans état.
Sommaire de la leçon

Le cœur du web tient en deux messages : une requête envoyée par le client, une réponse renvoyée par le serveur. Bonne nouvelle : ces messages sont du texte, lisible par un humain, et toujours bâtis sur le même plan. Une fois ce plan en tête, HTTP n'a plus de mystère.

La structure d'une requête

Une requête HTTP comporte trois parties : une ligne de requête, des en-têtes, et un corps facultatif :

  • la ligne de requête (GET /produits/42 HTTP/1.1) : la méthode (l'action voulue, ici « récupérer »), le chemin de la ressource, et la version du protocole.
  • les en-têtes (les lignes Clé: valeur) : des métadonnées sur la requête — le domaine visé (Host), le logiciel client (User-Agent), les formats acceptés (Accept)…
  • une ligne vide, puis un corps optionnel : les données envoyées (pour un GET, il n'y en a pas ; pour un envoi de formulaire, si).

La structure d'une réponse

La réponse suit le même plan, avec une ligne de statut au lieu de la ligne de requête :

  • la ligne de statut (HTTP/1.1 200 OK) : la version, un code de statut (200 = succès, leçon 04) et un court libellé.
  • les en-têtes : des métadonnées sur la réponse — le type du contenu (Content-Type), sa taille (Content-Length)…
  • une ligne vide, puis le corps : le contenu demandé (ici le code HTML de la page).

Requête et réponse partagent donc la même architecture : une ligne de départ, des en-têtes, une ligne vide, un corps. C'est ce qui rend HTTP simple à apprendre — et à observer.

HTTP est sans état

Point essentiel : HTTP est sans état (stateless). Chaque échange requête/réponse est indépendant : le serveur ne se « souvient » pas de la requête précédente. Deux requêtes du même visiteur sont, par défaut, deux inconnues l'une pour l'autre.

Cela pose une question : comment un site sait-il alors que tu es connecté d'une page à l'autre ? La réponse tient dans des informations réenvoyées à chaque requête — typiquement des cookies (leçon 05). L'absence d'état est en réalité une force : elle rend le web simple et permet à un serveur de répondre à des millions de requêtes sans garder un fil de discussion ouvert avec chacun.

Lien avec les API

Tout ce que tu apprends ici vaut aussi pour les API web (cours API REST) : une API échange exactement les mêmes requêtes et réponses HTTP, mais avec un corps en JSON (cours Formats de données) plutôt qu'en HTML. Le protocole est le même ; seul le contenu du corps change.

Cas réel

« Ça marche chez moi, pas en prod. » Un classique du débogage web se règle dans l'onglet Réseau. Une requête d'API renvoie une erreur illisible côté JavaScript ? En lisant la réponse brute, on découvre parfois un Content-Type: text/html au lieu de application/json : le serveur a renvoyé une page d'erreur HTML, pas du JSON. Les en-têtes et le corps racontent toute l'histoire. Parce que HTTP est textuel, la panne est visible à l'œil nu — au lieu de deviner, on lit.

Attention à l'en-tête Host

En HTTP/1.1, l'en-tête Host est obligatoire. Un même serveur (une même IP) héberge souvent plusieurs sites — c'est le virtual hosting — et c'est Host qui indique lequel on veut. Une requête sans Host reçoit une erreur 400 : le serveur ne sait pas à quel site elle s'adresse.

Pour aller plus loin

HTTP/1.1 est textuel, donc lisible. Mais HTTP/2 et HTTP/3 (leçon 07) transportent les mêmes informations sous forme binaire et compressée, pour aller plus vite. Les concepts — méthode, chemin, en-têtes, statut, corps — restent identiques ; seul l'emballage change. Ce que tu apprends ici vaut pour toutes les versions du protocole.

Glossaire

Requête HTTP
Message envoyé par le client : une ligne de requête (méthode + chemin + version), des en-têtes, une ligne vide, un corps optionnel.
Réponse HTTP
Message renvoyé par le serveur : une ligne de statut (version + code + libellé), des en-têtes, une ligne vide, un corps.
Ligne de requête / de statut
La première ligne du message. Requête : GET /page HTTP/1.1. Réponse : HTTP/1.1 200 OK.
En-tête
Ligne Clé: valeur portant des métadonnées (domaine, type de contenu, taille…) sur la requête ou la réponse.
Corps (body)
Le contenu transporté après la ligne vide : données d'un formulaire côté requête, HTML ou JSON côté réponse.
Méthode
L'action demandée en tête de requête (GET, POST…) ; détaillée à la leçon 04.
Sans état (stateless)
Propriété de HTTP : chaque échange est indépendant, le serveur ne mémorise pas les requêtes précédentes.
curl
Outil en ligne de commande qui envoie une requête HTTP et affiche la réponse brute ; curl -v montre tout l'échange.

Récap et vérification

  • Une requête = ligne de requête (méthode + chemin + version) · en-têtes · ligne vide · corps optionnel.
  • Une réponse = ligne de statut (version + code + libellé) · en-têtes · ligne vide · corps.
  • HTTP est textuel : observable dans l'onglet Réseau ou avec curl.
  • HTTP est sans état : chaque échange est indépendant ; l'état (connexion…) se maintient via des cookies réenvoyés.

  1. Quelles sont les trois parties d'une requête HTTP ?
  2. Qu'est-ce qui distingue la première ligne d'une requête de celle d'une réponse ?
  3. Que signifie « HTTP est sans état » ?

Exercices

Exercice 1Échauffement

Dans la ligne GET /articles?tag=web HTTP/1.1, identifie la méthode, le chemin (avec sa requête) et la version.

Voir une solution

Méthode : GET (récupérer une ressource). Chemin + requête : /articles?tag=web (la ressource /articles avec le paramètre tag=web). Version : HTTP/1.1. C'est la ligne de requête, première ligne du message.

Exercice 2Application

Lance curl -I https://exemple.com (ou regarde une réponse dans l'onglet Réseau). Quelles informations la ligne de statut et les en-têtes Content-Type / Content-Length te donnent-ils ?

Voir une solution

La ligne de statut (ex. HTTP/1.1 200 OK) indique que la requête a réussi : la ressource a été trouvée et renvoyée. Content-Type précise le format du corps (ex. text/html; charset=utf-8) : le navigateur sait ainsi qu'il doit interpréter le contenu comme du HTML encodé en UTF-8. Content-Length donne la taille du corps en octets : utile pour savoir combien de données suivent. Ensemble, ils décrivent la réponse avant même d'en lire le corps.

Exercice 3Défi

Un site affiche « Bonjour, Alice » sur toutes ses pages après connexion. Pourtant HTTP est sans état. Explique comment c'est possible, et ce qui se passerait sans ce mécanisme.

Voir une solution

Comme HTTP est sans état, le serveur ne se souvient pas, à la requête de la page suivante, qu'Alice s'est connectée juste avant. Pour combler ce vide, lors de la connexion le serveur renvoie un cookie (par exemple un identifiant de session) que le navigateur réenvoie automatiquement à chaque requête suivante vers ce site (leçon 05). À chaque page, le serveur lit ce cookie, retrouve la session d'Alice et personnalise la réponse (« Bonjour, Alice »). Sans ce mécanisme, chaque requête serait anonyme : Alice devrait se reconnecter à chaque page, puisque le serveur n'aurait aucun moyen de relier une requête à la précédente. Le cookie est donc le fil qui recrée une « mémoire » par-dessus un protocole qui n'en a pas.
