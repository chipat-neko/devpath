Module 5 · Projet — Leçon 12

Projet — un échange HTTP de bout en bout

~40 min Avancé Tout le cours conseillé

À la fin de cette leçon, tu sauras

  • reconstituer le voyage complet d'une requête, du DNS au rendu ;
  • lire et concevoir un échange HTTP réaliste, ligne par ligne ;
  • relier chaque en-tête au bon rôle (session, cache, négociation, sécurité) ;
  • mobiliser le cours entier sur un cas concret.
Sommaire de la leçon

Voici la dernière étape : un projet de synthèse. Pas de nouvelle notion, mais l'occasion d'assembler tout ce que le cours a construit. Tu vas suivre le voyage entier d'une requête, puis concevoir toi-même un échange HTTP complet — celui d'un navigateur qui se connecte à un espace personnel. Si tu sais lire et écrire cet échange, tu as compris le web.

Le voyage complet, d'un coup d'œil

Depuis la leçon 01, chaque leçon a éclairé une étape du même trajet. Les voici réunies : de l'URL que tu saisis jusqu'au document affiché, un seul dialogue requête-réponse.

Cinq modules, un seul édifice

Le cours s'est construit comme un bâtiment : chaque module repose sur le précédent. Ce projet est le toit — il ne tient que parce que tout le reste est là.

Concevoir l'échange, brique par brique

Passons à la pratique. On veut décrire l'échange réel entre un navigateur et le serveur d'un site, quand l'utilisateur ouvre sa page de compte. Une requête, une réponse ; chaque ligne a un rôle appris dans le cours.

Écrit en clair, ce même échange donne :

Prends chaque ligne et demande-toi : d'où vient-elle ? Host route vers le bon site ; Accept-Encoding propose la compression ; Cache-Control: no-store interdit de mettre en cache une page personnelle ; HttpOnly protège le cookie du JavaScript. Rien n'est décoratif : chaque en-tête décide quelque chose.

La ligne vide n'est pas un détail

Entre les en-têtes et le corps, il y a toujours une ligne vide : c'est elle qui sépare les métadonnées du contenu. Le serveur (comme le navigateur) lit les en-têtes ligne par ligne jusqu'à cette ligne vide, puis considère tout le reste comme le corps. Un oubli de cette séparation est une cause classique de message HTTP « cassé ».

Vérifie ce projet en vrai

Ouvre l'onglet Réseau (F12, leçon 11) sur n'importe quel site où tu es connecté, clique la requête du document principal et compare : tu retrouveras Host, Cookie, la ligne de statut, Content-Type, souvent Content-Encoding. Le projet de cette leçon n'est pas théorique : c'est exactement ce que ton navigateur échange à chaque page.

Une page personnelle ne se met pas en cache

Sur la page de compte, Cache-Control: no-store est volontaire : mettre en cache un contenu propre à un utilisateur (son nom, son solde) risquerait de le montrer à quelqu'un d'autre via un cache partagé, ou de le laisser sur un poste public. La règle : on met en cache le public et stable (leçon 08), jamais le privé. Choisir le bon en-tête de cache est une décision de sécurité autant que de performance.

Cas réel

Une page de connexion qui « ne se souvient de rien ». Un développeur signale que son site déconnecte l'utilisateur à chaque page : il faut se reconnecter sans arrêt. Plutôt que de deviner, il applique la démarche du cours : onglet Réseau, il regarde la réponse du formulaire de connexion. Le Set-Cookie est bien là (leçon 05)… mais sans attribut Secure, et le site est servi en HTTP sur une page et en HTTPS sur une autre (leçon 06). Résultat : selon le schéma, le navigateur n'envoie pas toujours le cookie, et la session paraît perdue. La correction tient en deux décisions vues dans le cours : forcer HTTPS partout et marquer le cookie Secure; HttpOnly; SameSite. Un bug « incompréhensible » redevient limpide dès qu'on lit l'échange au lieu de le subir.

Pour aller plus loin

Ce socle se prolonge dans trois directions. Les API REST reprennent exactement ces messages, avec un corps en JSON plutôt qu'en HTML. La Sécurité web approfondit cookies, HTTPS, CORS et les attaques associées (CSRF, XSS). Et le fonctionnement d'Internet sous HTTP — TCP/IP, DNS, routage — se creuse dans le cours Réseaux. Le protocole que tu maîtrises est la porte d'entrée de tout le reste.

Antisèche

Glossaire

Échange HTTP
Un couple requête / réponse complet entre un client et un serveur : c'est l'unité de base du web.
Ligne de requête
Première ligne d'une requête : méthode, chemin et version (GET /compte HTTP/1.1).
Ligne de statut
Première ligne d'une réponse : version, code de statut et texte (HTTP/1.1 200 OK).
En-tête
Métadonnée Nom: valeur qui précise la requête ou la réponse (session, type, cache, sécurité).
Corps (body)
Contenu transporté après la ligne vide : HTML, JSON, image… absent d'un simple GET.
Sans état (stateless)
Propriété d'HTTP : chaque requête est indépendante ; la continuité se recrée via les cookies.
Négociation de contenu
Mécanisme par lequel client (Accept) et serveur (Content-Type) s'accordent sur le format.
Fil rouge du cours
Idée constante : la forme des messages HTTP ne change pas ; seuls le transport et la sécurité évoluent.

Récap et vérification

  • Une requête part après le DNS (L. 02) et la connexion TCP/TLS (L. 06) ; la réponse revient avec un statut et un corps.
  • Chaque en-tête a un rôle précis : session (L. 05), négociation (L. 09), cache (L. 08), authentification (L. 10).
  • La ligne vide sépare toujours les en-têtes du corps.
  • Le fil rouge : les messages ne changent pas ; on les lit dans l'onglet Réseau (L. 11) pour tout déboguer.

Vérifie ta compréhension

  1. Cite les deux étapes qui précèdent l'envoi de la requête.
  2. Quel en-tête maintient la session, et lequel prouve l'identité ?
  3. Pourquoi une page de compte porte-t-elle Cache-Control: no-store ?

Exercices

Exercice 1Échauffement

Dans la requête du projet, associe chaque en-tête à son rôle : Host, Accept, Cookie, Authorization.

Voir une solution

Host: exemple.fr indique quel site est visé sur le serveur (un même serveur héberge souvent plusieurs domaines) — leçon 03. Accept: text/html annonce le format souhaité par le client : c'est la négociation de contenu, à laquelle le serveur répond par Content-Type — leçon 09. Cookie: session=abc123 renvoie le cookie de session posé précédemment, pour que le serveur reconnaisse l'utilisateur — leçon 05. Authorization: Bearer eyJ… transporte un jeton qui prouve l'identité pour accéder à une ressource protégée — leçon 10. Chaque en-tête vient donc d'une leçon précise : aucun n'est là par hasard.

Exercice 2Application

Le serveur répond 304 Not Modified au lieu de 200 OK, avec un corps vide. Qu'est-ce que cela veut dire, et pourquoi est-ce une bonne nouvelle ?

Voir une solution

Le 304 signifie « non modifié » : la ressource demandée n'a pas changé depuis la version que le navigateur a déjà en cache (leçon 08). Le client avait envoyé un en-tête de revalidation — If-None-Match avec l'ETag reçu la fois précédente (ou If-Modified-Since). Le serveur compare, constate que rien n'a bougé, et répond 304 sans le corps. C'est une bonne nouvelle : le navigateur réutilise sa copie locale, on économise la bande passante et le temps de téléchargement tout en garantissant que le contenu est à jour. Un 304 dans l'onglet Réseau n'est donc pas une erreur : c'est le cache qui fait bien son travail.

Exercice 3Défi

On te dit : « les pages de mon site s'affichent, mais les appels à mon API échouent en 401 une fois connecté ». Propose une démarche de diagnostic complète, en mobilisant le cours.

Voir une solution

1. Lire le statut (L. 04, 11). Le 401 dit « non authentifié » : le serveur ne reconnaît pas la requête comme provenant d'un utilisateur identifié. C'est donc un problème d'authentification (L. 10), pas de réseau ni de code applicatif au hasard. 2. Ouvrir l'onglet Réseau (L. 11) et cliquer la requête d'API. 3. Inspecter les en-têtes de requête. Deux pistes selon le mécanisme : si l'API attend un cookie de session (L. 05), le Cookie est-il envoyé ? Il ne l'est pas si l'API est sur une autre origine (L. 07) et que la requête n'active pas l'envoi des identifiants, ou si le cookie manque d'un attribut (SameSite, Secure, L. 06). Si l'API attend un jeton, l'en-tête Authorization: Bearer … est-il présent et non expiré ? 4. Vérifier l'origine (L. 07). Front et API sur des domaines différents ? Regarder s'il y a une erreur CORS associée et si le serveur autorise l'origine avec les identifiants. 5. Rejouer avec curl (L. 11) « Copier comme cURL », ajouter/corriger l'en-tête d'authentification, et confirmer que la requête passe alors en 200. Conclusion : le diagnostic croise authentification, cookies, origine et HTTPS — c'est-à-dire quatre leçons du cours réunies. La page blanche du départ est devenue une cause identifiée et une correction ciblée.

Mini-projet fil rouge — un échange HTTP complet

Pour clore ce cours, réunis toi-même les pièces. Tu vas rédiger un échange HTTP complet pour l'ouverture d'un espace personnel : la ligne de requête (méthode, chemin, version), les en-têtes de requête (dont la négociation et le cookie de session), la ligne de statut, les en-têtes de réponse (dont Set-Cookie marqué HttpOnly/Secure et un en-tête de cache) et le corps — toute l'anatomie d'HTTP, d'un bloc.

Ce que tu vas construire

La requête d'un navigateur déjà connecté qui demande sa page de compte, puis la réponse du serveur : statut 200, en-têtes de type et de cache, cookie de session sécurisé, et le HTML renvoyé.

Étapes

La ligne de requête

GET /compte HTTP/1.1 : méthode, chemin, version (leçon 03).

Les en-têtes de requête

Host, Accept (négociation, leçon 09) et Cookie (session, leçon 05).

La ligne de statut

La réponse commence par HTTP/1.1 200 OK (leçon 04).

Les en-têtes de réponse

Content-Type, un Cache-Control adapté (leçon 08) et un Set-Cookie marqué HttpOnly et Secure (leçons 05-06).

Le corps

Après une ligne vide, le document HTML personnalisé.

ProjetFil rouge

Rédige la requête et la réponse complètes. Essaie d'abord par toi-même, puis compare avec la solution de référence.

Voir une solution complète

Compare ligne à ligne avec le cours : la ligne de requête et la ligne de statut encadrent l'échange ; Accept/Accept-Encoding négocient le format et la compression ; Cookie identifie la session ; Cache-Control: no-store protège une page privée ; Set-Cookie renouvelle un cookie sécurisé ; et après la ligne vide, le corps HTML. Tu viens de réécrire, de mémoire, tout le cours en un seul échange.
