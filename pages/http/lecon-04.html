Méthodes et codes de statut

~28 min Débutant Leçon 03 conseillée

À la fin de cette leçon, tu sauras

  • choisir la bonne méthode (GET, POST, PUT, DELETE…) ;
  • distinguer sûr et idempotent ;
  • lire un code de statut par sa famille ;
  • reconnaître les codes les plus courants.
Sommaire de la leçon

La méthode dit quelle action on veut faire ; le code de statut dit comment ça s'est passé. Ce sont les deux mots-clés du dialogue HTTP. Bien les connaître, c'est savoir formuler une requête juste et interpréter une réponse d'un coup d'œil.

Les méthodes HTTP

Chaque requête commence par une méthode (un « verbe ») qui exprime l'intention :

GET et POST couvrent l'essentiel d'un site classique : lire des pages, soumettre des formulaires. Les autres (PUT, PATCH, DELETE) sont surtout employées par les API (cours API REST) pour manipuler des données.

Sûr et idempotent

Deux propriétés aident à raisonner sur les méthodes :

  • une méthode est sûre si elle ne modifie rien sur le serveur : elle ne fait que lire. GET et HEAD sont sûres.
  • une méthode est idempotente si l'exécuter plusieurs fois donne le même résultat qu'une seule. GET, PUT et DELETE le sont ; POST ne l'est pas.

L'exemple parlant : DELETE /article/42 répété laisse l'article supprimé (idempotent), tandis que POST /commandes répété crée plusieurs commandes. C'est pourquoi les navigateurs préviennent « voulez-vous renvoyer les données du formulaire ? » avant de rejouer un POST : l'opération n'est pas anodine à répéter.

401 ou 403 ?

Deux codes souvent confondus. 401 Unauthorized veut dire « je ne sais pas qui tu es » : il faut t'authentifier (te connecter). 403 Forbidden veut dire « je sais qui tu es, mais tu n'as pas le droit » : l'authentification a réussi, mais l'autorisation manque. Authentification = qui tu es ; autorisation = ce que tu peux faire.

Cas réel

301 ou 302 : un choix qui compte pour le référencement. Quand un site déménage une page, choisir 301 (permanent) ou 302 (temporaire) n'a rien d'anodin : les moteurs de recherche ne transfèrent le référencement de l'ancienne URL vers la nouvelle que sur un 301. Poser un 302 par erreur lors d'une refonte, et le trafic Google s'effondre : l'ancienne adresse garde tout le crédit, la nouvelle repart de zéro. Le bon code de statut a des conséquences bien réelles.

Ne modifie jamais avec un GET

GET est sûre par contrat : navigateurs, robots d'indexation et préchargeurs la déclenchent librement, sans te demander. Un lien <a href="/supprimer?id=42"> peut donc être suivi tout seul par le crawler de Google… et vider ta base. C'est une mésaventure classique. Toute action qui change l'état (supprimer, payer, valider) doit passer par POST, PUT, PATCH ou DELETE, jamais par un simple lien.

Pour aller plus loin

Comme POST n'est pas idempotent, les API de paiement (Stripe…) proposent une clé d'idempotence : un identifiant unique envoyé avec la requête. Si le réseau coupe et que le client réessaie, le serveur reconnaît la clé et ne débite qu'une seule fois. On rend ainsi une opération non idempotente sûre à rejouer — indispensable dès qu'il y a de l'argent en jeu.

Glossaire

Méthode (verbe)
L'action demandée en tête de requête : GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS.
GET / POST
GET récupère une ressource (sans corps) ; POST envoie des données pour créer ou soumettre (avec corps).
Méthode sûre
Méthode qui ne modifie rien sur le serveur (lecture seule) : GET, HEAD.
Idempotente
Méthode dont la répétition donne le même résultat qu'un seul appel : GET, PUT, DELETE ; POST ne l'est pas.
Code de statut
Nombre à trois chiffres en tête de réponse ; son premier chiffre indique la famille (1xx à 5xx).
4xx / 5xx
4xx : erreur côté client (requête fautive). 5xx : erreur côté serveur (défaillance).
401 vs 403
401 : non authentifié (connecte-toi). 403 : authentifié mais accès interdit.
CRUD
Les quatre opérations de base — Créer, Lire, Mettre à jour, Supprimer — que les méthodes HTTP incarnent dans une API REST.

Récap et vérification

  • La méthode exprime l'action : GET (lire), POST (créer/envoyer), PUT/PATCH (modifier), DELETE (supprimer)…
  • Sûre = ne modifie rien (GET) ; idempotente = répétable sans effet supplémentaire (GET, PUT, DELETE ; pas POST).
  • Le code de statut se lit par famille : 2xx succès, 3xx redirection, 4xx erreur client, 5xx erreur serveur.
  • Codes clés : 200, 201, 301/302, 304, 400, 401, 403, 404, 500, 503.

Vérifie ta compréhension

  1. Quelle méthode pour lire une page ? Pour soumettre un formulaire qui crée une commande ?
  2. Que signifie qu'une méthode est « idempotente » ?
  3. Tu reçois un code 404, puis un 500 : de quel côté est le problème dans chaque cas ?

Exercices

Exercice 1Échauffement

Associe chaque intention à sa méthode : (a) afficher un profil, (b) supprimer un message, (c) créer un compte.

Voir une solution

(a) afficher un profil → GET (lecture). (b) supprimer un message → DELETE. (c) créer un compte → POST (envoi de données pour créer une ressource). GET est sûre et idempotente ; DELETE est idempotente ; POST ne l'est pas (recréer deux fois = deux comptes).

Exercice 2Application

Tu cliques un lien et l'URL finale n'est pas celle du départ ; l'onglet Réseau montre d'abord un 301 puis un 200. Que s'est-il passé ?

Voir une solution

La première requête a reçu une réponse 301 Moved Permanently : la ressource a changé d'adresse de façon définitive. La réponse contient un en-tête Location indiquant la nouvelle URL ; le navigateur suit automatiquement cette redirection en envoyant une seconde requête vers la nouvelle adresse, qui répond 200 OK. D'où la séquence 301 → 200 et l'URL finale différente. Les redirections 301 servent par exemple à passer un site en HTTPS ou à réorganiser des URL sans casser les anciens liens.

Exercice 3Défi

Une page de paiement affiche parfois un 409 Conflict ou un 429 Too Many Requests. Sans les avoir mémorisés, comment peux-tu déjà déduire le sens général de ces codes, et qu'impliquent-ils ?

Voir une solution

Les deux commencent par 4  : ce sont des erreurs côté client (la requête, telle qu'envoyée, pose problème — ce n'est pas une panne serveur). Sans connaître le détail, on sait donc déjà qu'il faut corriger la demande, pas attendre une réparation du serveur. Pour le détail : 409 Conflict signale un conflit avec l'état actuel (par exemple deux tentatives de modifier la même ressource en même temps, ou une commande déjà validée). 429 Too Many Requests signale que tu as envoyé trop de requêtes dans un court laps de temps : le serveur te demande de ralentir (souvent via un en-tête Retry-After indiquant combien de temps patienter). La famille du code suffit à orienter la réaction : 4xx → revoir/espacer la requête ; 5xx → réessayer plus tard, le souci est côté serveur.
