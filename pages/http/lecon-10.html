Module 4 · HTTP en pratique — Leçon 10

L'authentification HTTP

~36 min Avancé Leçons 05 et 06 conseillées

À la fin de cette leçon, tu sauras

  • distinguer authentification et autorisation ;
  • interpréter 401, 403 et WWW-Authenticate ;
  • utiliser l'en-tête Authorization (Basic, Bearer) ;
  • comparer cookie de session et jeton.
Sommaire de la leçon

HTTP est un protocole sans état (leçon 05) : chaque requête arrive seule, sans mémoire de la précédente. Alors comment un serveur sait-il qui fait une requête, et s'il a le droit d'accéder à une ressource protégée ? Il faut que le client prouve son identité à chaque requête. C'est le rôle de l'authentification HTTP, portée par quelques en-têtes et deux codes de statut à bien distinguer.

Authentification n'est pas autorisation

Deux notions voisines mais différentes :

  • l'authentification répond à « qui es-tu ? » — prouver son identité ;
  • l'autorisation répond à « as-tu le droit ? » — vérifier les permissions.

HTTP leur associe deux statuts (leçon 04) qu'on confond souvent : 401 Unauthorized signifie en réalité « non authentifié » (le serveur ne sait pas qui tu es), tandis que 403 Forbidden signifie « je sais qui tu es, mais c'est interdit ».

L'en-tête Authorization et le défi 401

Pour s'authentifier, le client place ses preuves dans l'en-tête de requête Authorization. Le format le plus simple est le schéma Basic : l'identifiant et le mot de passe, joints par :, sont encodés en base64. Le déroulé typique : une première requête sans identifiants reçoit un 401 assorti de WWW-Authenticate: Basic (le « défi ») ; le client renvoie alors la requête avec l'en-tête Authorization.

Jetons (Bearer), clés d'API et JWT

Envoyer identifiant et mot de passe à chaque requête est rarement souhaitable. Le web moderne préfère les jetons (tokens) : après une connexion réussie, le serveur remet au client un jeton, que celui-ci présente ensuite via Authorization: Bearer <jeton> (bearer = « au porteur » : quiconque le détient est traité comme authentifié — d'où l'importance de le protéger).

  • Une clé d'API est un jeton simple, souvent statique, identifiant une application (dans Authorization ou un en-tête maison comme X-API-Key).
  • Un JWT (JSON Web Token) est un jeton auto-porteur : il contient des informations (identité, expiration) et une signature qui permet au serveur de vérifier qu'il n'a pas été falsifié, sans rien stocker de son côté.

Deux styles : cookie de session vs jeton

Il existe deux grandes manières de « se souvenir » d'un utilisateur connecté :

base64 n'est pas du chiffrement

C'est l'erreur de débutant la plus fréquente ici. La base64 est un simple encodage réversible, conçu pour transporter des octets en texte ; elle ne cache rien. Authorization: Basic dXNlcjpwYXNz se décode en user:pass en une seconde. C'est pourquoi toute authentification (Basic, Bearer, cookies, formulaires) doit passer par HTTPS — sans quoi les identifiants circulent en clair sur le réseau.

Tester une API protégée

Avec l'extension REST Client ou curl, tu ajoutes toi-même l'en-tête : curl -H "Authorization: Bearer eyJ..." https://api.exemple.fr/moi. Sans lui, tu récoltes un 401 ; avec un jeton valide, un 200 ; avec un jeton valide mais des droits insuffisants, un 403. Lire ces trois codes te dit immédiatement où est le problème : identité manquante, identité refusée, ou droits insuffisants.

Cas réel

Des clés secrètes publiées par erreur. Chaque année, des dizaines de milliers de clés d'API et de jetons se retrouvent, par mégarde, publiés dans des dépôts de code publics sur GitHub : un fichier de configuration commité, un jeton codé en dur « pour tester ». Des robots scrutent en permanence ces dépôts : une clé peut être exploitée en quelques minutes, parfois pour lancer des serveurs coûteux sur le compte cloud de la victime. Les hébergeurs (comme AWS ou GitHub) ont mis en place une détection automatique de secrets qui alerte et révoque, mais la règle d'or reste : un secret ne se met jamais dans le code ni dans une URL — on le stocke dans une variable d'environnement ou un coffre, et on le fait tourner (renouveler) régulièrement.

Pour aller plus loin

OAuth 2.0 est le cadre qui régit « Se connecter avec Google/GitHub » : il délivre des jetons d'accès sans jamais révéler ton mot de passe au site tiers. Ces jetons ont une durée de vie courte, complétée par un refresh token pour en obtenir de nouveaux. Pour les cookies de session, deux attributs sont essentiels (leçon 05) : HttpOnly (inaccessible au JavaScript, contre le vol par script) et Secure (envoyé uniquement en HTTPS). Le choix session/jeton, lui, dépend du contexte : rien n'est « meilleur » dans l'absolu.

Glossaire

Authentification
Prouver son identité au serveur (« qui es-tu ? »).
Autorisation
Vérifier qu'une identité connue a le droit d'accéder à une ressource (« as-tu le droit ? »).
401 Unauthorized
Statut « non authentifié » : le serveur ne sait pas qui tu es ; accompagné de WWW-Authenticate.
403 Forbidden
Statut « interdit » : l'identité est connue mais l'accès est refusé ; se ré-authentifier n'y change rien.
Authorization
En-tête de requête qui porte les preuves d'identité (schéma Basic ou Bearer).
Basic
Schéma envoyant identifiant:mot de passe encodé en base64 ; non chiffré, à n'utiliser que sur HTTPS.
Bearer / jeton
Schéma présentant un jeton « au porteur » ; une clé d'API ou un JWT signé en sont des formes.
JWT
JSON Web Token : jeton auto-porteur contenant des informations et une signature vérifiable sans stockage serveur.

Récap et vérification

  • Authentification = « qui es-tu » ; autorisation = « as-tu le droit ». Deux choses distinctes.
  • 401 = non authentifié (avec WWW-Authenticate) ; 403 = identifié mais interdit.
  • Les preuves voyagent dans Authorization : Basic (base64, HTTPS requis) ou Bearer (jeton, clé d'API, JWT).
  • Deux styles : cookie de session (état serveur) ou jeton auto-porteur (stateless).

Exercices

Exercice 1Échauffement

Tu appelles une API sans en-tête Authorization et reçois 401. Tu ajoutes un jeton valide : cette fois, 403. Que s'est-il passé ?

Voir une solution

Le premier appel échoue en 401 parce qu'aucune identité n'est fournie : le serveur ne sait pas qui tu es (authentification manquante). En ajoutant un jeton valide, tu es désormais authentifié — mais tu obtiens 403 : ton identité est reconnue, seulement elle n'a pas le droit d'accéder à cette ressource (autorisation refusée). Concrètement, ton compte est peut-être un utilisateur normal alors que la ressource est réservée aux administrateurs. Renvoyer d'autres identifiants ne servirait à rien : il faudrait des droits supplémentaires. Passer de 401 à 403 confirme donc que l'authentification, elle, fonctionne.

Exercice 2Application

Un collègue déclare : « notre login Basic est sûr, le mot de passe est encodé en base64 ». En HTTP (sans S). Que lui réponds-tu ?

Voir une solution

Que la base64 n'apporte aucune sécurité : c'est un encodage réversible, pas un chiffrement. Authorization: Basic dXNlcjpwYXNz se décode instantanément en user:pass. En HTTP nu, cet en-tête circule en clair sur le réseau : quiconque écoute (Wi-Fi public, routeur, leçon 06) lit directement l'identifiant et le mot de passe. La base64 sert seulement à transporter proprement des octets en texte, pas à les cacher. La correction indispensable : passer le site en HTTPS, qui chiffre tout le transport — en-tête Authorization compris. Sans HTTPS, aucune méthode d'authentification (Basic, Bearer, cookie, formulaire) n'est à l'abri de l'interception.

Exercice 3Défi

On te demande de choisir entre cookie de session et jeton (JWT) pour une nouvelle application. Explique le compromis principal et un critère de décision concret.

Voir une solution

Le cœur du compromis est : où vit l'état ? Avec un cookie de session, le serveur conserve la vraie session de son côté ; le cookie n'est qu'un identifiant. Avantage : on peut révoquer une session instantanément (on la supprime côté serveur) et le navigateur envoie le cookie automatiquement (avec HttpOnly/Secure, c'est robuste). Inconvénient : le serveur doit stocker et retrouver chaque session, ce qui se complique quand on répartit la charge sur plusieurs serveurs. Avec un JWT, le jeton est auto-porteur et signé : n'importe quel serveur peut le vérifier sans rien stocker (idéal pour des API réparties et des applications mobiles). Inconvénient : un JWT valide est difficile à révoquer avant son expiration (il faut des listes de révocation ou des durées de vie très courtes + refresh token), et il faut le stocker prudemment côté client. Critère concret : une application web classique mono-serveur avec besoin de déconnexion immédiate penchera vers la session ; une API sans état, distribuée sur plusieurs serveurs ou consommée par des applis mobiles, penchera vers le jeton. Dans les deux cas, HTTPS est non négociable.
