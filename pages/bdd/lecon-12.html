Lire un plan d'exécution

~40 min Avancé Prérequis : les index (leçon 11)

À la fin de cette leçon, tu sauras

  • expliquer qu'un optimiseur choisit un plan d'exécution plutôt que d'exécuter ta requête « au pied de la lettre » ;
  • lire les opérations d'un plan simple : parcours séquentiel, parcours d'index, et les grandes jointures ;
  • interpréter le coût estimé et le nombre de lignes, et distinguer EXPLAIN (estimé) de EXPLAIN ANALYZE (mesuré) ;
  • appliquer la boucle observer → agir → vérifier pour confirmer qu'un index sert vraiment, sur une requête de Rideau.
Sommaire de la leçon

À la leçon précédente, tu as posé un index et vu la requête accélérer. Mais une question reste en suspens : comment savoir que l'index sert ? La requête est peut-être devenue rapide pour une autre raison — le cache, une table plus petite, la chance. Deviner la performance ne suffit pas : il faut la lire. C'est exactement ce que fait le plan d'exécution, la feuille de route que le moteur suit pour répondre à ta requête. Apprendre à la lire, c'est passer du « j'espère que c'est plus rapide » au « je vois que l'index est utilisé ».

Cette leçon ne cherche pas l'exhaustivité — les plans réels de PostgreSQL ou d'autres moteurs sont touffus. On vise l'essentiel : reconnaître les deux ou trois opérations qui reviennent tout le temps, comprendre les nombres qui les accompagnent, et surtout maîtriser une boucle — observer le plan, agir sur le schéma, vérifier que le plan a changé. Avec ça, tu ne subis plus la lenteur : tu la diagnostiques.

Le moteur n'exécute pas ta requête « au pied de la lettre »

Quand tu écris SELECT * FROM billet WHERE representation_id = 42, tu décris un résultat voulu, pas une marche à suivre. Tu ne dis pas « parcours les lignes une par une » ni « utilise l'index ». SQL est un langage déclaratif : tu déclares le quoi, et le moteur décide du comment. Ce « comment » est confié à un composant précis : l'optimiseur (ou planificateur).

L'optimiseur regarde ta requête, connaît les tables et leurs index, consulte des statistiques sur les données (combien de lignes, quelles valeurs), et parmi plusieurs façons possibles d'obtenir le résultat, il en choisit une : c'est le plan d'exécution. Dans quel ordre lire les tables, avec ou sans index, comment assembler les jointures — tout cela, c'est lui qui tranche, à chaque exécution.

La commande qui révèle ce plan s'appelle EXPLAIN. On la place devant la requête. Le moteur ne renvoie pas les lignes du résultat : il renvoie sa feuille de route.

Un langage qui décrit, pas qui ordonne

C'est la grande différence entre SQL et un langage impératif. En Python, tu écris la boucle ; en SQL, tu décris l'ensemble voulu et le moteur invente la boucle. Cette liberté a un prix : tu ne contrôles pas directement comment la requête s'exécute. EXPLAIN est le seul moyen de voir ce que l'optimiseur a décidé à ta place.

Les opérations d'un plan simple

Un plan est un empilement d'opérations : chacune produit des lignes qu'elle passe à celle du dessus. Sur des requêtes simples, deux d'entre elles suffisent à comprendre 90 % des cas.

Le parcours séquentiel (Seq Scan)

Un parcours séquentiel — Seq Scan en PostgreSQL, full table scan ailleurs — signifie : lire la table en entier, ligne par ligne, et garder celles qui satisfont le WHERE. C'est le comportement par défaut quand aucun index n'aide. Sur une petite table de dix lignes, c'est parfaitement normal : aussi vite lu que trouvé. Sur une grosse table filtrée par un critère très sélectif — « les billets de cette représentation » parmi cent mille — c'est un signal d'alarme : le moteur lit tout pour n'en garder qu'une poignée.

Le parcours d'index (Index Scan)

Un parcours d'index — Index Scan, Index Seek — signifie : utiliser un index pour aller droit aux lignes qui correspondent, sans lire le reste. C'est le signe visible qu'un index sert. Là où le parcours séquentiel lisait cent mille lignes, l'index en désigne directement les quelques dizaines utiles. Voir Index Scan sur une requête filtrée, c'est voir l'index faire son travail.

Les jointures, en survol

Dès que la requête relie deux tables, le plan montre une jointure, et l'optimiseur choisit comment l'exécuter. Trois grandes méthodes reviennent ; il n'est pas nécessaire de les maîtriser à fond, juste de reconnaître leurs noms :

  • Jointure par boucle imbriquée (nested loop) : pour chaque ligne de la première table, chercher les lignes correspondantes de la seconde — idéalement via un index. Excellente quand la première table renvoie peu de lignes.
  • Jointure par hachage (hash join) : construire une table de hachage sur la plus petite des deux tables, puis la sonder pour chaque ligne de l'autre. Efficace pour joindre deux grands ensembles sans index utile.
  • Jointure par fusion (merge join) : trier les deux côtés puis les parcourir en parallèle comme une fermeture éclair. Adaptée quand les données sont déjà triées sur la clé de jointure.

Retiens surtout ceci : le nom de la jointure n'est presque jamais le problème. L'optimiseur choisit en général la bonne ; ce qui est lent, c'est presque toujours un parcours séquentiel caché dans la jointure, sur une table qui aurait mérité un index.

Ne mémorise pas tout le vocabulaire

Chaque moteur a ses noms : PostgreSQL dit Seq Scan et Index Scan, SQL Server dit Table Scan et Index Seek, MySQL affiche une colonne type avec ALL (tout lire) ou ref (via index). Les mots changent, l'idée non : lit-on toute la table, ou vise-t-on les lignes utiles ? C'est la seule question qui compte au début.

Lire les nombres : coût estimé et lignes estimées

Chaque opération du plan porte deux nombres qu'il faut savoir interpréter. Voici à quoi ressemble le plan de notre requête, avant tout index, en version pédagogique simplifiée :

Décryptons :

  • cost=0.00..1780.00 — le coût estimé. Deux nombres : le coût pour renvoyer la première ligne (0.00) et le coût total (1780.00). C'est une unité abstraite, pas des millisecondes : elle mélange lectures de disque et travail processeur selon une formule interne. Elle ne sert qu'à comparer deux plans entre eux — « 1780, c'est beaucoup plus que 8 » — jamais à prédire une durée en secondes.
  • rows=47 — le nombre de lignes estimé que l'opération va produire. Ici, l'optimiseur parie que 47 billets correspondent à la représentation 42.
  • width=32 — la taille moyenne d'une ligne en octets. On l'ignore le plus souvent.

Le mot important est estimé. L'optimiseur n'a pas compté les lignes : il les a devinées à partir des statistiques de la table — des résumés (nombre total de lignes, valeurs les plus fréquentes, dispersion) que le moteur tient à jour et rafraîchit périodiquement. Un plan repose sur ces estimations ; si elles sont fausses (statistiques périmées), l'optimiseur peut choisir un mauvais plan.

Piège fréquent

Lire le coût comme des millisecondes. Voir cost=1780 ne veut pas dire « 1780 ms ». Le coût est une unité sans dimension, propre au moteur, faite pour classer les plans, pas pour chronométrer. Si tu veux un vrai temps, il te faut EXPLAIN ANALYZE (ci-dessous), qui exécute réellement la requête et rapporte des millisecondes mesurées.

EXPLAIN (estimé) contre EXPLAIN ANALYZE (mesuré)

Il y a une différence capitale entre les deux commandes :

  • EXPLAIN n'exécute pas la requête. Il montre le plan prévu et les nombres estimés. Instantané, sans effet de bord — parfait pour inspecter une requête sans la lancer.
  • EXPLAIN ANALYZE exécute vraiment la requête, puis compare le prévu au réalisé : à côté de cost (estimé) apparaissent le actual time (temps réel en ms) et le nombre de lignes réellement produites. C'est l'outil pour mesurer, et pour repérer les écarts entre estimation et réalité.

Quand rows=47 (estimé) mais actual rows=52 000 (mesuré), l'optimiseur s'est lourdement trompé : ses statistiques sont à revoir. Ce genre d'écart est l'une des causes les plus fréquentes de plans catastrophiques.

Astuce

EXPLAIN ANALYZE exécute la requête pour de vrai. Sur un SELECT, c'est sans danger ; mais sur un UPDATE ou un DELETE, il modifie les données. Pour analyser une écriture sans l'appliquer, entoure-la d'une transaction que tu annules : BEGIN; EXPLAIN ANALYZE UPDATE …; ROLLBACK;. Le plan est mesuré, mais rien n'est écrit.

La boucle : observer → agir → vérifier

Voici la démarche qui transforme EXPLAIN en outil de travail. Elle tient en trois temps, et elle se répète.

Rideau : le plan des « billets d'une représentation », avant et après

Appliquons la boucle à une requête très banale de Rideau — afficher tous les billets vendus pour une représentation donnée, par exemple pour préparer le plan de salle du soir :

Étape 1 — observer. Sans index sur representation_id, le plan est un parcours séquentiel : le moteur lit toute la table pour ne garder qu'une quarantaine de lignes.

Étape 2 — agir. Le filtre porte sur representation_id : on pose exactement l'index qui manque (voir la leçon sur les index pour le choix de la colonne).

Étape 3 — vérifier. On relance exactement le même EXPLAIN. Le plan a changé de nature : Index Scan a remplacé Seq Scan, et le coût total s'est effondré.

La preuve est faite, et elle est lue, pas devinée : l'opération est passée de Seq Scan à Index Scan, la condition apparaît en Index Cond (le moteur l'applique via l'index, pas après coup en Filter), et le coût total chute de 1780 à 8,4. C'est ça, confirmer qu'un index sert : le plan le montre noir sur blanc.

Astuce — Filter ou Index Cond ?

Un détail qui distingue le débutant du praticien : quand la condition apparaît sous Filter, le moteur a d'abord lu des lignes puis a écarté celles qui ne correspondaient pas ; sous Index Cond, il a utilisé l'index pour ne lire que les bonnes. Voir sa condition passer de Filter à Index Cond après un CREATE INDEX, c'est la signature d'un index qui a pris le relais.

Lire un plan avec jointure, de bas en haut

Les plans à plusieurs opérations se lisent du plus profond vers le plus haut : chaque opération produit des lignes que sa parente au-dessus consomme. C'est un arbre, dessiné à l'envers. Prenons une requête qui relie billets et clients : « qui a acheté des billets pour la représentation 42 ? »

Remarque comme le plan raconte l'exécution : le côté qui renvoie peu de lignes (les 47 billets) sert de « pilote », et pour chacune de ces lignes, le moteur va chercher un client par sa clé primaire — d'où le choix de la boucle imbriquée. Si l'index sur billet manquait, cette feuille redeviendrait un Seq Scan lisant 90 000 lignes, et toute la jointure ralentirait : le coupable serait la feuille, pas la jointure.

Pourquoi c'est décisif : on lit la performance, on ne la devine pas

Tout l'intérêt tient dans une phrase : un index créé mais non utilisé par le plan ne sert à rien. On peut poser un index parfaitement, et le voir ignoré par l'optimiseur. Sans EXPLAIN, on croirait la requête optimisée alors qu'elle continue de tout lire. Les raisons d'un index ignoré sont classiques :

  • La mauvaise colonne. L'index est sur representation_id, mais la requête filtre sur place_id. L'index ne peut pas aider un filtre qui ne le concerne pas.
  • Une fonction appliquée à la colonne. WHERE lower(email) = 'chloe@…' demande de calculer lower(email) sur chaque ligne : l'index sur email devient inutilisable. On dit que la condition n'est pas sargable.
  • Une faible sélectivité. Si la requête ramène la moitié de la table, l'optimiseur juge — souvent à raison — qu'un parcours séquentiel est plus rapide qu'un aller-retour par l'index pour la moitié des lignes. Il ignore alors l'index volontairement. Ce n'est pas un bug.

Piège — la condition non sargable

Sargable (de l'anglais Search ARGument ABLE) qualifie une condition qu'un index peut exploiter directement. Envelopper la colonne dans une fonction la rend non sargable : WHERE lower(email) = 'x', WHERE annee(debut) = 2026 ou WHERE prix_paye + 2 = 30 forcent un calcul par ligne et neutralisent l'index. La règle : garde la colonne nue d'un côté du signe (WHERE debut >= '2026-01-01' plutôt que WHERE annee(debut) = 2026), et l'index redevient utilisable.

Pour aller plus loin

Certains moteurs offrent un index fonctionnel qui indexe le résultat d'une expression : CREATE INDEX ON client (lower(email)) rend alors WHERE lower(email) = … à nouveau sargable. C'est la réponse propre quand on doit filtrer sur une transformation : tu la mets en pratique dans l'exercice 3 de cette leçon.

Pièges fréquents

Piège fréquent

Optimiser une requête rare. On tombe sur un gros Seq Scan, on s'excite, on pose un index… pour une requête lancée une fois par mois par un rapport de nuit. Pendant ce temps, la requête jouée mille fois par heure reste lente. On optimise ce qui coûte, c'est-à-dire ce qui est lent et fréquent — jamais un plan effrayant sur une requête sans importance.

  • Croire qu'un Seq Scan est toujours mauvais. Sur une petite table, ou quand la requête ramène une grande part des lignes, lire toute la table est le meilleur plan. Le Seq Scan n'est un problème que sur une grosse table avec un filtre sélectif.
  • Se fier au coût estimé comme à une vérité. C'est une estimation fondée sur des statistiques qui peuvent être périmées. En cas de doute, passe à EXPLAIN ANALYZE pour comparer l'estimé au mesuré : un grand écart trahit des statistiques à rafraîchir.
  • Ajouter un index sans re-EXPLAIN. Poser l'index et supposer que le problème est réglé, c'est sauter l'étape la plus importante. Tant que le plan n'a pas montré le passage en Index Scan, tu ne sais rien.

Cas réel

Cas réel

Une petite billetterie se plaint que la page « plan de salle » met plusieurs secondes à charger le soir d'un concert complet. Le développeur avait pourtant créé un index — sur place_id. Un EXPLAIN de la vraie requête révèle un Seq Scan franc : la page filtrait par representation_id, pas par place_id. L'index existait, il était sain, mais il portait sur la mauvaise colonne : l'optimiseur ne pouvait pas s'en servir. Un index sur representation_id, un re-EXPLAIN pour confirmer le passage en Index Scan, et la page repasse sous les 50 ms. Le correctif a pris deux minutes ; le diagnostic, lui, aurait été impossible sans lire le plan.

Glossaire

Plan d'exécution
La suite d'opérations que le moteur décide de suivre pour répondre à une requête : quelles tables lire, dans quel ordre, avec ou sans index, comment joindre.
Optimiseur (planificateur)
Le composant du moteur qui, à partir de la requête, des index et des statistiques, choisit le plan d'exécution parmi plusieurs candidats.
EXPLAIN
Commande placée devant une requête pour afficher son plan prévu et ses nombres estimés, sans exécuter la requête.
EXPLAIN ANALYZE
Variante qui exécute réellement la requête et rapporte, en plus de l'estimé, le temps mesuré et le nombre de lignes réellement produites.
Parcours séquentiel
Opération (Seq Scan, full table scan) qui lit la table entière ligne par ligne ; normale sans filtre sélectif, coûteuse sur une grosse table filtrée.
Parcours d'index
Opération (Index Scan, Index Seek) qui utilise un index pour atteindre directement les lignes voulues ; le signe visible qu'un index sert.
Coût estimé
Nombre sans dimension attaché à chaque opération, servant à comparer les plans entre eux ; ce ne sont pas des millisecondes.
Statistiques
Résumés que le moteur tient à jour sur les données d'une table (nombre de lignes, valeurs fréquentes, dispersion) ; l'optimiseur s'en sert pour estimer et choisir un plan.
Sargable
Se dit d'une condition WHERE qu'un index peut exploiter directement ; appliquer une fonction à la colonne la rend non sargable et neutralise l'index.
Jointure par boucle imbriquée
Méthode de jointure (nested loop) qui, pour chaque ligne d'un côté, cherche les lignes correspondantes de l'autre — idéale quand un côté renvoie peu de lignes.
Jointure par hachage
Méthode de jointure (hash join) qui construit une table de hachage sur le plus petit ensemble puis la sonde ; efficace pour joindre deux grands ensembles sans index utile.

Récap et vérification

  • SQL est déclaratif : tu décris le résultat, l'optimiseur choisit le plan d'exécution. EXPLAIN ouvre une fenêtre sur ce plan sans l'exécuter ; EXPLAIN ANALYZE l'exécute et le mesure.
  • Deux opérations suffisent au début : le parcours séquentiel (lit tout — alarmant sur grosse table filtrée) et le parcours d'index (vise les lignes utiles — la preuve qu'un index sert). Les jointures se lisent de bas en haut.
  • Le coût est une unité abstraite pour comparer les plans, pas des millisecondes ; les lignes sont estimées à partir des statistiques, qui peuvent être périmées.
  • La méthode, c'est la boucle observer → agir → vérifier : repérer un Seq Scan sur un WHERE sélectif, poser l'index, re-EXPLAIN pour confirmer l'Index Scan. Un index non utilisé par le plan (mauvaise colonne, condition non sargable, faible sélectivité) ne sert à rien.
