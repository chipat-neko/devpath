Faire évoluer un schéma : les migrations

~38 min Avancé Prérequis : un schéma en place (tout le cours)

À la fin de cette leçon, tu sauras

  • définir une migration comme un changement de schéma versionné, rejouable et idéalement réversible ;
  • écrire les opérations ALTER TABLE du quotidien : ajouter une colonne, une table, une contrainte, un index ;
  • éviter le piège central : ajouter une colonne NOT NULL sans DEFAULT sur une table pleine, et le contourner en trois temps ;
  • appliquer le motif expand / contract pour migrer sans interruption, en gardant l'ancienne et la nouvelle version du code compatibles le temps de la bascule.
Sommaire de la leçon

Depuis la première leçon, on a dessiné le schéma de Rideau comme s'il était gravé une fois pour toutes : des tables, des clés, des contraintes, posées sur une feuille blanche. Mais une base qui vit ne reste jamais sur sa feuille blanche. Six mois après l'ouverture, la salle veut vendre des abonnements ; l'année suivante, une carte de fidélité ; un soir de tempête, il faut un statut de représentation « annulée » qui n'existait pas. À chaque fois, le schéma doit changer. Et là est tout l'enjeu de cette leçon : modifier une base vide est trivial — on efface, on réécrit ; modifier une base pleine, en service, avec des dizaines de milliers de billets déjà vendus et une application qui tourne, ne l'est pas du tout.

La réponse professionnelle à ce problème porte un nom : la migration. Ce n'est pas « se connecter à la prod et taper un ALTER TABLE à la main un vendredi soir ». C'est un changement décrit par un script, versionné, rejouable à l'identique sur toutes les copies de la base, et pensé pour ne ni perdre de données ni casser l'application. On va voir ce qu'est une migration, comment on la rédige, le piège qui fait échouer les débutants, et surtout la technique qui permet de faire évoluer un schéma pendant que l'application sert des clients, sans coupure.

Un schéma n'est jamais figé

Reprenons le schéma propre de Rideau, celui qu'on a construit tout au long du cours : client, commande, billet, representation, tarif… Il est correct. Il est normalisé. Et pourtant, il est déjà en retard sur le besoin, parce que le besoin, lui, avance. Voici trois demandes réelles qui vont tomber sur la table :

  • la salle lance des abonnements (un client paie une formule annuelle qui donne droit à N spectacles) : il faut une nouvelle table abonnement et un lien vers client ;
  • une représentation peut être annulée (intempéries, artiste malade) : il faut une colonne statut sur representation, qui n'était pas prévue ;
  • on s'aperçoit que client.nom mélange nom et prénom dans un seul champ : il faut le scinder en nom + prenom.

Chacune de ces demandes est un changement de schéma. Sur une base vide, tu réécrirais le CREATE TABLE et ce serait fini. Mais la base de Rideau n'est pas vide : elle contient l'historique de deux saisons. On ne peut pas « réécrire le CREATE TABLE » sans jeter ces données. Il faut transformer ce qui existe, en douceur.

La conception ne s'arrête pas au lancement

On a beaucoup insisté : le schéma est un mur porteur. Vrai — mais un mur porteur, on le renforce, on perce une ouverture, on ajoute un étage, au fil de la vie du bâtiment. La conception ne se termine pas le jour de la mise en production ; elle continue, à chaque évolution. Bien concevoir, c'est aussi bien faire évoluer.

La migration : un changement versionné

Une migration est un changement de schéma décrit par un script — le plus souvent un fichier de SQL — et rangé dans le dépôt de code avec un numéro : 001_creer_schema.sql, 002_ajouter_statut_representation.sql, 003_creer_table_abonnement.sql… Ce numéro n'est pas décoratif. Il fixe un ordre : les migrations se rejouent toujours dans la même séquence, de la première à la dernière. Une petite table technique (souvent nommée schema_migrations) mémorise, dans chaque base, celles qui y ont déjà été appliquées ; on ne rejoue jamais deux fois la même.

Pourquoi tant de rigueur ? Parce qu'une application vit sur plusieurs bases : celle du développeur sur son portable, celle de test (l'intégration continue), celle de production. Si le schéma se construit par des ALTER TABLE tapés à la main, ces trois bases divergent aussitôt : un oubli ici, une faute de frappe là, et « ça marche sur ma machine » devient « ça plante en prod ». Rejouer exactement la même suite de migrations sur les trois garantit qu'elles aboutissent au même schéma, au caractère près.

Un corollaire important : puisqu'une migration est un fichier numéroté dans le dépôt, c'est du code. Elle est versionnée avec git, relue en revue de code, testée avant d'atteindre la prod, et son historique raconte l'évolution du schéma comme les commits racontent celle du code. Le schéma cesse d'être un objet vivant et opaque sur un serveur : il devient une conséquence traçable de fichiers que toute l'équipe partage.

Astuce

Une migration ne se contente pas de dire comment aller en avant (la partie up : appliquer le changement) ; on lui associe idéalement le chemin retour (down : le défaire). Prendre l'habitude d'écrire les deux au moment où l'on rédige la migration — pendant qu'on a le contexte en tête — vaut bien mieux que de chercher à improviser un retour arrière en catastrophe, la prod à l'arrêt.

Les opérations ALTER TABLE

L'outil de base d'une migration relationnelle, c'est ALTER TABLE : la commande qui modifie une table existante sans la détruire. À côté de CREATE TABLE (créer une table neuve) et de DROP TABLE (la supprimer), ALTER couvre presque tous les changements du quotidien. En voici le répertoire, appliqué à Rideau.

Créer une table entière est un simple CREATE TABLE dans une migration : c'est ainsi qu'on ajoutera abonnement plus loin. Retiens surtout la dernière ligne, en commentaire : DROP COLUMN est destructif. Il ne réorganise pas les données, il les efface. Ce détail va nous occuper au moment de parler de réversibilité.

Note

La syntaxe exacte d'ALTER TABLE varie légèrement d'un moteur à l'autre — SQLite, par exemple, ne sait pas tout faire d'un seul coup et oblige parfois à recréer la table. On reste ici sur les formes les plus répandues (celles de PostgreSQL, largement standard) ; l'important n'est pas la ponctuation d'un dialecte, c'est de reconnaître les cinq opérations : ajouter/renommer/supprimer une colonne, ajouter une contrainte, ajouter un index.

Le piège central : NOT NULL sans DEFAULT

Voici l'erreur qui coûte le plus de nuits blanches, et elle tient en une ligne apparemment anodine. On veut rendre representation.statut obligatoire. Réflexe naturel : l'ajouter en NOT NULL. Sur une base vide, ça passe. Sur la base de Rideau, pleine de représentations déjà enregistrées, ça échoue :

La logique est implacable. NOT NULL promet : « aucune ligne de cette colonne n'est vide ». Or les 400 lignes déjà là n'ont, par définition, aucune valeur pour une colonne qui vient de naître. La base se retrouve devant une promesse qu'elle ne peut pas tenir, et — c'est une bonne chose — elle refuse plutôt que de mentir. Il y a deux façons propres de s'en sortir.

Quand aucun défaut universel n'a de sens (la valeur dépend de chaque ligne, ou doit être calculée), on procède en trois étapes, dans trois instructions — voire trois migrations distinctes :

Piège fréquent

« Ça a marché en développement. » Sur la base du développeur, souvent quasi vide, ADD COLUMN ... NOT NULL passe sans broncher — il n'y a aucune ligne existante à remplir. Puis la même migration atteint la prod et ses centaines de milliers de lignes, et elle plante. Une migration ne doit jamais être validée sur une base vide : teste-la sur une copie réaliste de la prod, avec de vraies données, sinon le piège ne se révèle qu'au pire moment.

Migrer sans coupure : expand / contract

Jusqu'ici, on a supposé qu'on pouvait appliquer la migration « tranquillement ». Mais Rideau vend des billets en continu : on ne veut pas éteindre le site pendant la migration, et surtout, pendant un déploiement, deux versions du code coexistent quelques minutes — l'ancienne encore en train de servir des requêtes, la nouvelle qui démarre. Si la migration casse ce que lit l'ancienne version, on provoque des erreurs en plein service. La parade porte un nom imagé : expand / contract, « élargir puis resserrer ».

L'idée : ne jamais passer directement de l'ancien schéma au nouveau. On élargit d'abord (les deux formes cohabitent), on bascule tranquillement, puis on resserre. En trois temps :

  1. Expand (élargir) — ajouter le nouveau (colonne, table) sans toucher à l'ancien. Le schéma sait maintenant faire les deux. L'ancienne version du code, qui ignore le nouveau, continue de fonctionner : on n'a rien retiré.
  2. Migrer + double écriture — recopier les données de l'ancien vers le nouveau, et faire écrire la nouvelle version du code dans les deux le temps de la transition. Pendant cette phase, ancien et nouveau restent cohérents, quelle que soit la version qui écrit.
  3. Contract (resserrer) — une fois que plus personne ne lit ni n'écrit l'ancien (toutes les instances tournent en nouvelle version), le supprimer. Le schéma est enfin dans sa forme cible.

Le même motif s'applique pour remplacer une colonne par une autre, changer un type, ou scinder un champ comme ici. La discipline commune : ajouter d'abord, migrer ensuite, supprimer en dernier, avec une phase intermédiaire où les deux formes coexistent. C'est plus long qu'un ALTER TABLE brutal — mais c'est le prix d'un service qui ne s'arrête jamais.

Compatibilité ascendante et descendante

Pendant la bascule, la base doit accepter à la fois l'ancienne et la nouvelle version du code. On dit qu'un changement est compatible ascendant (backward compatible) quand le code déjà en place continue de fonctionner après la migration. C'est exactement ce que garantit la phase expand : comme on n'a rien retiré, l'ancien code ne trouve jamais un mur à la place de ce qu'il attendait. La règle d'or : on déploie d'abord un schéma élargi, on retire l'ancien seulement quand plus aucun code ne s'en sert.

Réversibilité, et ses limites

On l'a dit : une bonne migration prévoit son chemin retour (le rollback). Si 002 ajoute une colonne, son retour la supprime ; si 003 crée une table, son retour la drop. Pouvoir revenir en arrière est précieux quand une migration se révèle mauvaise juste après la mise en production.

Mais toutes les migrations ne sont pas réversibles « pour de vrai ». Supprimer une colonne détruit ses données : le rollback peut bien recréer la colonne, il ne ressuscite pas ce qu'elle contenait. Le chemin retour existe sur le papier (la structure revient), mais l'information, elle, est perdue. C'est la nuance essentielle : réversible en structure n'est pas réversible en données. Une migration destructrice est, en pratique, un aller simple.

Piège fréquent

Croire que le rollback est un filet de sécurité universel. Il l'est pour les ajouts récents. Il ne l'est pas pour les suppressions : une fois la colonne droppée, ses données ont disparu, rollback ou pas. La vraie sécurité contre une migration destructrice n'est pas le chemin retour : c'est la sauvegarde prise avant, et le fait d'avoir testé la migration sur une copie. Le rollback range les meubles ; il ne rembobine pas le temps.

Trois évolutions de Rideau, de bout en bout

Rassemblons tout sur nos trois demandes réelles. Chacune illustre un cas de figure différent.

Ajouter la table abonnement (+ une clé étrangère)

Le plus simple : on crée une table neuve, reliée à client par une clé étrangère. Rien d'existant n'est touché, donc aucun risque pour le service : c'est une pure phase expand.

Ajouter representation.statut (avec DEFAULT)

Une colonne obligatoire sur une table pleine : on a vu le piège : un DEFAULT sensé le désamorce en une ligne, et l'on scelle les valeurs permises par un CHECK.

Pour aller plus loin

Sur de très grosses tables, même un ALTER TABLE anodin peut poser un verrou et ralentir le service le temps de réécrire des millions de lignes ; les moteurs et les outils modernes savent le faire « en ligne », sans blocage, mais c'est un métier en soi. De même, remplir des millions de lignes (le backfill du temps 2) se fait par lots, pas d'un seul UPDATE massif. On touche là aux frontières entre conception et exploitation : le motif reste le même (expand → migrer → contract), seule l'échelle change les précautions.

Pièges fréquents

Piège fréquent

La migration « à la main » en production. Se connecter à la prod, taper quelques ALTER TABLE, refermer : c'est rapide… et irreproductible. Le changement n'existe dans aucun fichier, la base de test ne l'a pas, le prochain déploiement le contredit, et personne ne sait plus dans quel état est réellement la prod. Une évolution de schéma qui n'est pas un script versionné et rejoué partout est une dette qu'on paiera au pire moment.

  • Migration destructrice non testée — lancer directement en prod un DROP ou un UPDATE massif sans l'avoir essayé sur une copie ni pris de sauvegarde. Le SQL réussit… et efface plus que prévu. Toujours : sauvegarde d'abord, essai sur une copie réaliste, puis prod.
  • NOT NULL sans DEFAULT sur table pleine — le grand classique : la migration échoue au contact des lignes existantes. Fournir un DEFAULT sensé, ou procéder en trois temps (ajouter vide → remplir → resserrer).
  • Renommer ou supprimer d'un coup une colonne encore lue par le code en prod — casse net l'ancienne version pendant le déploiement. Passer par expand/contract : on ne retire l'ancien qu'une fois que plus rien ne s'en sert.
  • Oublier le chemin retour — écrire seulement le up et découvrir, migration ratée, qu'on n'a aucun down préparé. Rédiger les deux au même moment (en sachant qu'un down après suppression ne rend pas les données).

Cas réel

Cas réel

Une boutique en ligne voulait rendre obligatoire un nouveau champ pays sur la table des adresses. Un développeur ajoute, un mercredi midi, ADD COLUMN pays TEXT NOT NULL : parfait sur sa machine (base de dev quasi vide), la revue passe. Le soir, le déploiement en production heurte les 800 000 adresses déjà enregistrées, sans valeur pour pays : la migration échoue, le déploiement s'interrompt à moitié, et le site tombe une quinzaine de minutes le temps de comprendre. Le correctif tenait en deux mots : soit un DEFAULT 'FR', soit la version en trois temps. Personne n'avait fait de faute de SQL : la migration n'avait simplement jamais rencontré de vraies données avant la prod. Depuis, chez eux, toute migration passe par une copie récente de la production avant d'être validée.

Antisèche

Glossaire

Migration
Changement de schéma décrit par un script, versionné et rejouable, appliqué à une base existante sans perdre de données ; idéalement réversible.
ALTER TABLE
Commande SQL qui modifie une table existante : ajouter, renommer ou supprimer une colonne, ajouter une contrainte, etc., sans recréer la table.
Migration versionnée
Migration rangée dans le dépôt avec un numéro fixant son ordre ; rejouée dans la même séquence, elle produit partout le même schéma.
Rollback (chemin retour)
Opération qui défait une migration (partie down) ; ramène la structure précédente, mais ne restitue pas les données déjà supprimées.
Réversibilité
Capacité d'une migration à être annulée. Réversible en structure n'implique pas réversible en données : une suppression est de fait irréversible.
Expand / contract
Motif de migration sans coupure : élargir (ajouter le nouveau sans retirer l'ancien), migrer les données, puis resserrer (retirer l'ancien une fois inutilisé).
Compatibilité ascendante
Propriété d'un changement qui n'empêche pas le code déjà en place de fonctionner ; garantie par la phase expand, qui ne retire rien.
Double écriture
Pendant une transition, faire écrire l'application à la fois dans l'ancien et le nouveau champ, pour les garder cohérents quelle que soit la version.
DEFAULT
Valeur appliquée automatiquement à une colonne quand rien n'est fourni ; à l'ajout d'une colonne, elle remplit aussi les lignes existantes.
Schéma évolutif
Schéma pensé pour changer dans le temps, par migrations successives, plutôt que figé une fois pour toutes au lancement.

Récap et vérification

  • Un schéma vit : modifier une base vide est trivial, modifier une base pleine et en service ne l'est pas. La réponse est la migration — un changement versionné, rejouable, idéalement réversible, rangé dans le dépôt comme du code.
  • Rejouer la même suite numérotée sur dev, test et prod donne partout le même schéma : fin du « ça marche sur ma machine ». L'outil de base est ALTER TABLE (ajouter/renommer/supprimer une colonne, une contrainte, un index).
  • Le piège central : ADD COLUMN ... NOT NULL sans DEFAULT échoue sur une table pleine. On le règle par un DEFAULT sensé, ou en trois temps (ajouter vide → remplir → SET NOT NULL).
  • Pour migrer sans coupure : expand / contract — ajouter le nouveau sans retirer l'ancien, migrer en écrivant dans les deux, puis retirer l'ancien quand plus rien ne s'en sert. C'est la compatibilité ascendante qui protège les deux versions du code pendant la bascule.
  • La réversibilité a des limites : un DROP COLUMN rend la structure mais pas les données. Le vrai filet est la sauvegarde et l'essai sur une copie réaliste, jamais le seul rollback.

Vérifie ta compréhension

  1. On ajoute ALTER TABLE representation ADD COLUMN statut TEXT NOT NULL; sur une table qui contient déjà 400 lignes, et la migration échoue. Pourquoi ? Donne deux façons de corriger.
  2. En quoi le motif expand / contract permet-il de scinder client.nom en nom+prenom sans jamais casser l'application en production ? Cite les trois étapes.
  3. Une migration a supprimé une colonne pleine par erreur. Son rollback recrée la colonne. Les données sont-elles récupérées ? Explique, et dis ce qui aurait vraiment protégé.
