Tester et fiabiliser son code

~52 min Avancé Prérequis : leçon 09

À la fin de cette leçon, tu sauras

  • écrire des tests avec @test, @test_throws et la comparaison ≈ ;
  • les organiser avec @testset et un fichier test/runtests.jl ;
  • mesurer honnêtement une performance avec @btime (BenchmarkTools) ;
  • débusquer l'instabilité de type avec @code_warntype.
Sommaire de la leçon

Un code de calcul scientifique n'a de valeur que si on peut lui faire confiance. Un test transforme une intuition (« ça a l'air de marcher ») en une vérification automatique qui se rejoue à volonté. Julia intègre tout le nécessaire dans sa bibliothèque standard : pas de dépendance à installer pour commencer.

Le module Test : @test

On charge Test, puis @test vérifie qu'une expression est vraie. En cas d'échec, Julia affiche ce qui a échoué et les valeurs en cause :

Ne teste jamais deux flottants avec ==

0.1 + 0.2 == 0.3 vaut false en arithmétique flottante ! Utilise ≈ (la fonction isapprox), qui admet une petite tolérance. Pour la régler : ≈(a, b; atol=1e-8). C'est le piège numérique n°1 dans les tests scientifiques.

Grouper avec @testset

Empiler des @test devient vite illisible. @testset les regroupe sous un nom, compte les réussites et les échecs, et n'interrompt pas la suite au premier problème : on voit tous les échecs d'un coup.

Organiser les tests d'un package

Par convention, les tests d'un projet vivent dans test/runtests.jl. La commande ] test (ou Pkg.test()) crée un environnement propre et exécute ce fichier. C'est ce que déclenche l'intégration continue à chaque modification.

Cas réel — le filet de sécurité d'un package scientifique

Les grands paquets Julia comme DataFrames.jl ou DifferentialEquations.jl comptent des milliers de @test. À chaque proposition de modification (pull request), un serveur exécute ] test sur plusieurs versions de Julia et plusieurs systèmes d'exploitation. Si un seul test passe au rouge, la fusion est bloquée. Ce filet permet à des centaines de contributeurs de faire évoluer un code numérique délicat sans casser, sans le savoir, le calcul d'un utilisateur à l'autre bout du monde. Écrire le test en même temps que la fonction, c'est se garantir que le comportement d'aujourd'hui survivra aux réécritures de demain.

Mesurer honnêtement : BenchmarkTools

Envie de savoir si une fonction est rapide ? @time te ment au premier appel : il inclut le temps de compilation. Le paquet BenchmarkTools résout cela en exécutant la fonction de nombreuses fois et en gardant le meilleur temps.

Traquer l'instabilité de type

Souviens-toi de la leçon 08 : la performance de Julia repose sur la stabilité de type. @code_warntype révèle en rouge les endroits où le compilateur ne connaît pas le type — souvent un Any ou un Union qui ruine la vitesse.

Rouge = à corriger, en priorité

Dans la sortie de @code_warntype, le bleu est bon signe (type concret connu), le rouge est un drapeau : un type abstrait force Julia à décider à l'exécution. Corriger ces points — souvent en rendant une fonction type-stable — est le levier de performance le plus rentable, bien avant de sortir le parallélisme.

Pour aller plus loin

Pour déboguer, Julia offre @show x (affiche x = valeur), le système de journalisation (@info, @warn, @error, filtrables par niveau) et le paquet Debugger.jl pour avancer pas à pas. Côté couverture, ] test --coverage indique quelles lignes tes tests exécutent réellement ; Aqua.jl, lui, vérifie l'hygiène générale d'un package (dépendances, ambiguïtés de méthodes).

Glossaire

Test unitaire
Vérification automatique qu'un petit morceau de code produit le résultat attendu.
@test
Macro du module Test qui réussit si son expression vaut true, échoue sinon.
@testset
Regroupe des tests sous un nom, compte réussites et échecs sans s'arrêter au premier.
≈ (isapprox)
Égalité approchée pour les nombres à virgule, avec une tolérance.
@test_throws
Réussit si l'expression lève bien l'erreur du type attendu.
Benchmark
Mesure de performance fiable ; @btime exclut le temps de compilation.
Instabilité de type
Situation où le type de retour d'une fonction n'est pas déterminé : elle ralentit le code.
Intégration continue (CI)
Serveur qui rejoue automatiquement la suite de tests à chaque modification.

Récap et vérification

  • @test vérifie une condition ; pour les flottants, on compare avec ≈, jamais ==.
  • @testset groupe les tests et totalise les résultats ; la suite vit dans test/runtests.jl.
  • @btime (BenchmarkTools) mesure sans le temps de compilation, contrairement à @time.
  • @code_warntype révèle l'instabilité de type (rouge) — le premier ennemi de la performance.

Vérifie ta compréhension

  1. Pourquoi comparer deux flottants avec ≈ plutôt que == ?
  2. Qu'apporte @btime par rapport à @time ?
  3. Que signale une couleur rouge dans @code_warntype ?

Exercices

Exercice 1Échauffement

Écris une fonction somme_carres(n) qui calcule 1² + 2² + … + n², puis un test vérifiant que somme_carres(3) == 14.

Voir une solution

On teste un cas normal et des cas limites (1 et 0). Le init = 0 n'est pas un détail : pour n = 0, l'intervalle 1:0 est vide, et sum sur un générateur vide lève une erreur au lieu de renvoyer 0 — il ne sait pas quel zéro produire. La valeur initiale le lui dit, et c'est justement le cas limite que le test vérifie. Plus les cas couverts sont variés, plus le test protège des régressions.

Exercice 2Application

Regroupe dans un @testset nommé « racine » deux vérifications : sqrt(4.0) ≈ 2.0, et le fait que sqrt(-1.0) lève une DomainError.

Voir une solution

Le premier test utilise ≈ (flottant) ; le second, @test_throws, réussit précisément parce que l'erreur attendue survient. Tester les erreurs est aussi important que tester les succès.

Exercice 3Défi

La fonction note(x) = x >= 10 ? "reçu" : 0 est instable. Diagnostique-la avec @code_warntype, puis corrige-la.

Voir une solution

Mélanger String et Int en sortie force un Union que Julia doit lever à l'exécution. En renvoyant toujours le même type, la fonction redevient type-stable et le compilateur peut l'optimiser pleinement.
