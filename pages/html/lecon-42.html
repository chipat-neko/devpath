Service Workers et l'offline avancé

~36 min Avancé Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • comprendre le contexte d'exécution d'un Service Worker et son cycle de vie (install, activate, contrôle des clients) ;
  • intercepter les requêtes via l'événement fetch et répondre depuis la Cache API ;
  • choisir la bonne stratégie de cache (cache-first, network-first, stale-while-revalidate) selon le type de ressource ;
  • implémenter un mode offline robuste avec page de repli et versionnement propre du cache.
Sommaire de la leçon

Tu as fini les 14 leçons : tu connais déjà le manifeste, l'installation d'une PWA et les métadonnées. Ici on attaque la pièce qui fait qu'une application fonctionne vraiment hors ligne : le Service Worker. Ce n'est pas une couche cosmétique, c'est un proxy réseau programmable qui s'interpose entre ta page et le réseau, capable de répondre à une requête même quand la connexion est morte.

On va parcourir le contexte d'exécution particulier de ce worker, son cycle de vie souvent mal compris, l'interception via fetch, les stratégies de cache que tu choisiras au cas par cas, et le mode offline. On survolera le Background Sync et les Push notifications, puis on finira sur l'outillage et les pièges qui transforment un SW en cauchemar de production.

Le Service Worker : un proxy réseau en arrière-plan

Un Service Worker est un script qui tourne dans un contexte séparé de la page, sans accès au DOM, sans window, sans document. Il vit dans un worker dédié, peut être tué par le navigateur quand il est inactif et réveillé sur événement. Son super-pouvoir : il s'enregistre comme intermédiaire pour toutes les requêtes réseau d'une portée (scope) donnée.

Deux contraintes non négociables : HTTPS obligatoire (sauf localhost pour le développement), parce qu'un proxy capable de réécrire le réseau serait une arme entre les mains d'un attaquant MITM ; et un script servi depuis ta propre origine. L'enregistrement se fait depuis la page.

Note

Le scope est borné par l'emplacement du fichier : un sw.js servi depuis /assets/sw.js ne peut contrôler que /assets/. Place-le à la racine pour couvrir toute l'origine, ou envoie l'en-tête Service-Worker-Allowed pour élargir.

Le cycle de vie : install, activate, contrôle des clients

Le cycle de vie est la source numéro un de bugs. Après register, le navigateur télécharge le script puis déclenche install (idéal pour précharger le cache), puis activate (idéal pour nettoyer les vieux caches). Mais subtilité majeure : par défaut, un nouveau SW reste en état waiting tant que des onglets pilotés par l'ancien sont ouverts. L'utilisateur ne voit donc pas ta nouvelle version avant d'avoir fermé tous les onglets.

self.skipWaiting() saute l'état d'attente ; self.clients.claim() permet au SW fraîchement activé de contrôler immédiatement les onglets déjà chargés. Ensemble, ils donnent une mise à jour quasi instantanée — mais attention, un client peut alors basculer d'une version à l'autre en cours de session, ce qui exige que ton cache reste cohérent.

Piège fréquent

Appeler skipWaiting() aveuglément peut casser un onglet en plein usage : du JS chargé par l'ancienne version demande soudain des assets servis par la nouvelle. Le pattern propre consiste à attendre un signal explicite de l'utilisateur (« Recharger pour mettre à jour ») via postMessage avant de basculer.

L'interception réseau : l'événement fetch et la Cache API

Le cœur du SW est l'écouteur fetch : il reçoit chaque requête sortante de la page et décide quoi renvoyer. Tu peux répondre depuis le réseau, depuis la Cache API, ou fabriquer une Response de toutes pièces. La Cache API (caches.open, cache.match, cache.put) est un magasin clé/valeur où la clé est une Request et la valeur une Response.

Piège fréquent

Le corps d'une Response est un flux à lecture unique. Si tu la mets en cache et la renvoies, tu dois clone() avant, sinon le second consommateur reçoit un corps déjà vidé (TypeError: body stream already read). Note aussi que cache.put rejette si le statut n'est pas 2xx (une réponse opaque de type cors a le statut 0) : entoure-le d'un garde si tu mets en cache des ressources tierces.

Les stratégies de cache : laquelle pour quoi

Il n'existe pas une stratégie universelle ; le choix dépend du type de ressource. Voici les quatre patrons classiques :

  • Cache-first : on sert le cache, on ne touche le réseau qu'en cas d'absence. Parfait pour le statique versionné (polices, images, JS hashé) — rapide et fiable.
  • Network-first : on tente le réseau, on retombe sur le cache si échec. Pour les données qui doivent être fraîches (API, fil d'actualité) mais tolèrent une version cachée hors ligne.
  • Stale-while-revalidate : on renvoie le cache immédiatement et on rafraîchit en arrière-plan pour la prochaine fois. Excellent compromis vitesse/fraîcheur (avatars, listes semi-statiques).
  • Cache-then-network : variante côté page — on affiche le cache puis on remplace par le réseau quand il arrive.

Note

Dans staleWhileRevalidate, la promesse maj tourne en arrière-plan même quand tu renvoies enCache. Pour garantir que le navigateur ne tue pas le SW avant la fin du rafraîchissement, enrobe-la dans event.waitUntil(maj) au niveau de l'écouteur fetch.

Le mode offline : page de repli

Quand le réseau ET le cache échouent pour une navigation, ne laisse pas le navigateur afficher son dinosaure. Précharge une page /offline.html à l'install et sers-la en dernier recours pour les requêtes de navigation (celles dont request.mode === 'navigate').

Cas réel

Twitter Lite a été l'un des cas d'école : en précachant son app-shell (l'ossature de l'interface) dans un Service Worker et en servant les données en network-first, la PWA restait consultable dans le métro, l'avion ou sur une 2G capricieuse — et rechargeait instantanément puisque la coquille venait du cache, pas du réseau. Même logique chez Spotify, Starbucks ou la météo de nombreux sites : le contenu déjà vu reste lisible hors ligne, une page de repli s'affiche pour le reste, et l'utilisateur ne tombe jamais sur le dinosaure du navigateur. C'est exactement l'assemblage de cette leçon : précache à l'install, interception fetch, stratégie adaptée, page /offline.html en dernier recours.

Background Sync et Push notifications (survol)

Deux API prolongent le SW au-delà de la session de la page. Le Background Sync permet de différer une action (envoyer un message, poster un formulaire) jusqu'au retour de la connectivité : la page enregistre un tag, le navigateur réveille le SW via l'événement sync dès que le réseau revient, même si l'onglet est fermé.

Les Push notifications reposent sur le protocole Web Push (abonnement via pushManager.subscribe avec une clé VAPID) et exigent un consentement explicite de l'utilisateur. On ne fait que les survoler ici : chacune mérite sa propre leçon.

Outils et débogage : Workbox et DevTools

Écrire un SW à la main est formateur, mais en production tu utiliseras souvent Workbox (de Google) : il fournit des stratégies prêtes à l'emploi, la génération de manifeste de précache avec hachage automatique, et la gestion de l'expiration. Côté débogage, l'onglet Application > Service Workers des DevTools est indispensable.

Génération automatique d'un Service Worker avec précache versionné via Workbox.

Astuce

Coche Update on reload dans DevTools > Application pendant le développement : le SW persiste agressivement, et sans cette option tu testeras pendant des heures une version déjà remplacée dans ton éditeur. Coche aussi Bypass for network pour ignorer temporairement le SW.

Pièges fréquents

  • Oublier HTTPS : l'enregistrement échoue silencieusement hors localhost. Vérifie la console.
  • Cache trop agressif : du HTML mis en cache-first sans versionnement bloque les utilisateurs sur une vieille version pour toujours. Le HTML va plutôt en network-first.
  • Ne pas nettoyer dans activate : les anciens caches s'accumulent et gonflent le stockage. Filtre sur le nom de version.
  • Casser les requêtes non gérées : si ton fetch ne return pas pour les méthodes/origines non prévues, tu risques d'avaler des requêtes (POST, analytics). Laisse passer ce que tu ne gères pas.
  • Précharger trop : un addAll géant à l'install ralentit la première activation et gaspille le quota. De plus, addAll est atomique — une seule URL en 404 fait échouer toute l'install. Précharge l'app-shell, pas tout le site.

Glossaire

Service Worker
Script exécuté dans un contexte séparé (sans DOM ni window), servi en HTTPS, qui agit en proxy réseau programmable pour son scope. Réveillé sur événement, tuable quand il est inactif.
scope (portée)
Zone d'URL contrôlée par un SW, bornée par l'emplacement de son fichier. Un sw.js à la racine couvre toute l'origine ; l'en-tête Service-Worker-Allowed peut l'élargir.
Cycle de vie (install / activate)
install précharge le cache ; activate nettoie les anciennes versions. Entre les deux, un nouveau SW reste en waiting tant que d'anciens onglets sont pilotés.
skipWaiting / clients.claim
skipWaiting() active le nouveau SW sans attendre la fermeture des onglets ; clients.claim() lui fait prendre le contrôle des pages déjà chargées. À utiliser avec prudence.
Cache API
Magasin clé/valeur où la clé est une Request et la valeur une Response (caches.open, match, put). Le corps d'une Response se lit une seule fois : clone() avant de le consommer deux fois.
app-shell
Ossature minimale de l'interface (HTML/CSS/JS de base) préchargée à l'install pour un affichage instantané et hors ligne, avant que les données ne se chargent.
Stratégie de cache
Politique choisie par ressource : cache-first (statique versionné), network-first (données fraîches), stale-while-revalidate (compromis vitesse/fraîcheur).
Workbox
Bibliothèque de Google qui génère un SW avec précache haché, stratégies prêtes à l'emploi et gestion de l'expiration, à la place d'un sw.js écrit à la main.

Récap et vérification

  • Le Service Worker est un proxy réseau en arrière-plan, sans DOM, sur HTTPS uniquement.
  • Cycle de vie : install (précache), activate (nettoyage), avec skipWaiting / clients.claim pour accélérer la prise de contrôle.
  • L'événement fetch intercepte les requêtes ; la Cache API les stocke (penser à clone()).
  • Stratégies : cache-first pour le statique versionné, network-first pour les données fraîches, stale-while-revalidate pour le compromis.
  • Mode offline : page de repli préchargée, servie sur échec d'une navigation.
  • Toujours versionner le cache et nettoyer les anciens pour ne pas piéger les utilisateurs.
