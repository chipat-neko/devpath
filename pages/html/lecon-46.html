Declarative Shadow DOM et le rendu serveur

~36 min Avancé Web Components (module 02) recommandés

À la fin de cette leçon, tu sauras

  • expliquer pourquoi un Shadow DOM créé en JavaScript (attachShadow) pose problème au rendu serveur ;
  • écrire un Declarative Shadow DOM avec <template shadowrootmode="open"> ;
  • sérialiser un shadow root avec getHTML() et le reparser avec setHTMLUnsafe() ;
  • distinguer le rendu (le HTML est déjà là) de l'hydratation (on rebranche le comportement).
Sommaire de la leçon

Au module 02, tu as créé des Web Components dont le contenu interne (le shadow tree) était construit en JavaScript, avec this.attachShadow({ mode: 'open' }) puis shadowRoot.innerHTML = …. Tant que ce script n'a pas tourné, le composant est un trou vide dans la page. Sur une connexion lente, ou si le JavaScript échoue, l'utilisateur ne voit rien.

Pour un site rendu côté serveur (SSR), c'est rédhibitoire : mauvais référencement (les robots lisent le HTML, pas le résultat du JS), mauvais LCP, et un désagréable clignotement au chargement. La réponse de la plateforme s'appelle le Declarative Shadow DOM (DSD) : écrire le shadow tree directement en HTML, pour qu'il soit rendu avant la moindre ligne de JavaScript.

Le problème : un Shadow DOM qui n'existe qu'en JavaScript

Un custom element impératif attache son ombre dans son constructeur ou son connectedCallback. Le serveur, lui, ne peut envoyer que du HTML : il n'exécute pas ton JavaScript de composant. Résultat, le HTML livré ne contient aucune trace du contenu interne. Le rendu attend le réseau, le téléchargement puis l'exécution du script.

La solution : <template shadowrootmode>

Le Declarative Shadow DOM repose sur un <template> spécial. Quand le parseur HTML rencontre un <template shadowrootmode="open"> comme enfant direct d'un élément, il ne le range pas dans un fragment inerte : il attache aussitôt un shadow root à l'élément parent et y déplace le contenu. Aucun JavaScript n'est requis — c'est le parseur qui fait le travail.

À l'ouverture de cette page — même avec JavaScript désactivé — le navigateur affiche la carte stylée, nom en gras compris. Le <style> placé dans le template reste encapsulé dans l'ombre, exactement comme un Shadow DOM impératif.

Astuce

shadowrootmode accepte "open" ou "closed", exactement comme le mode de attachShadow(). En open, le shadow root reste accessible via element.shadowRoot — indispensable pour l'hydratation. Réserve closed aux rares cas où tu veux vraiment verrouiller l'accès.

Hydrater : rebrancher le comportement

Le HTML déclaratif donne le rendu, pas le comportement. Un bouton dessiné ne réagit pas tant qu'aucun écouteur n'est posé. L'hydratation, c'est l'étape où l'on définit le custom element : dans son connectedCallback, il détecte que son shadowRoot existe déjà (rendu par le serveur) et se contente d'attacher les écouteurs, sans reconstruire le DOM.

Sérialiser et reparser un shadow root

Deux pièges historiques : element.innerHTML ne voit pas le contenu de l'ombre (il ne renvoie que le light DOM), et il ne parse pas le DSD à l'affectation. La plateforme fournit donc des API dédiées :

  • Sérialiser (ombre → chaîne HTML) : element.getHTML({ serializableShadowRoots: true }), à condition que le template ait été marqué shadowrootserializable.
  • Parser (chaîne → ombre) : element.setHTMLUnsafe(html), qui interprète les <template shadowrootmode> — là où innerHTML = … les ignorerait.

Piège fréquent

Le suffixe Unsafe de setHTMLUnsafe() n'est pas décoratif : cette méthode n'assainit rien. Elle exécute le HTML fourni comme n'importe quel innerHTML. Si la chaîne vient d'une source non fiable, assainis-la d'abord (DOMPurify, Sanitizer API) — le pendant « sûr », setHTML(), filtre le contenu mais retire aussi les scripts et certaines structures.

Cas réel

Les bibliothèques de composants qui visent le rendu serveur — Lit (avec @lit-labs/ssr), Shoelace / Web Awesome — s'appuient sur le Declarative Shadow DOM pour livrer des composants stylés dès la première image. Un site e-commerce y gagne un LCP plus bas et des fiches produit indexables : le robot de Google lit le prix et le titre dans le HTML, sans exécuter la moindre ligne de JavaScript. Avant le DSD (standardisé en 2023-2024, disponible dans tous les navigateurs à jour), rendre des Web Components côté serveur relevait du bricolage.

Pour aller plus loin

Creuse la notion d'hydratation progressive (n'hydrater un composant que lorsqu'il devient visible, via IntersectionObserver — cf. leçon 15), les Constructable Stylesheets (adoptedStyleSheets) pour partager une feuille de style entre plusieurs ombres, et la façon dont les frameworks (Astro, Enhance, Lit SSR) génèrent ce HTML déclaratif à partir de tes composants.

Antisèche

Glossaire

Declarative Shadow DOM (DSD)
Manière d'écrire un shadow tree directement en HTML, via <template shadowrootmode>, sans passer par attachShadow() en JavaScript.
shadowrootmode
Attribut du <template> qui indique au parseur d'attacher un shadow root ("open" ou "closed") à l'élément parent.
rendu serveur (SSR)
Server-Side Rendering : le serveur envoie un HTML déjà construit, affichable sans exécuter de JavaScript. Bon pour le SEO et le premier affichage.
hydratation
Étape où le JavaScript rebranche l'interactivité (écouteurs, état) sur un DOM déjà rendu, sans le reconstruire.
light DOM
Le contenu ordinaire d'un élément (ses enfants hors template), projeté dans les <slot> du shadow tree.
setHTMLUnsafe()
Méthode qui parse une chaîne HTML en interprétant le DSD, sans assainissement — à réserver aux sources de confiance.
encapsulation
Isolation du style et de la structure interne d'un composant : un <style> placé dans l'ombre ne fuit pas vers la page, déclarative ou non.

Récap et vérification

  • Un Shadow DOM créé en JavaScript est absent du HTML serveur : le composant reste vide jusqu'à l'exécution du script.
  • Le Declarative Shadow DOM l'écrit en HTML via <template shadowrootmode="open"> : le parseur attache l'ombre, sans JavaScript.
  • Le HTML donne le rendu ; l'hydratation ajoute ensuite le comportement — on teste this.shadowRoot pour ne pas reconstruire.
  • innerHTML ignore l'ombre : on sérialise avec getHTML({serializableShadowRoots:true}) et on reparse avec setHTMLUnsafe() (ou setHTML(), assaini).

Vérifie ta compréhension

  1. Pourquoi un custom element qui fait attachShadow() dans son constructeur ne s'affiche-t-il pas dans un rendu serveur ?
  2. Quel attribut, sur quel élément, déclenche l'attachement d'un shadow root par le parseur HTML ?
  3. Que doit vérifier connectedCallback avant de (re)construire l'ombre, et pourquoi ?
