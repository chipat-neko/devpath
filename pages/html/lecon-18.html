Module 07 · HTML appliqué — Leçon 18

Formulaires avancés et expérience utilisateur

~35 min Intermédiaire Cours HTML recommandé

À la fin de cette leçon, tu sauras

  • savoir choisir le bon type d'<input> pour activer clavier mobile et validation natifs ;
  • savoir mettre en place une validation native poussée avec required, pattern, min/max et messages personnalisés ;
  • savoir rendre un formulaire accessible avec <label>, autocomplete et aria-describedby ;
  • savoir enrichir l'UX avec <datalist>, <output> et inputmode.
Sommaire de la leçon

Tu connais déjà les bases des formulaires : <form>, <input>, <label>, <button>. Maintenant, on va aller au bout de ce que le HTML natif sait faire : des claviers adaptés sur mobile, une validation qui fonctionne sans une ligne de JavaScript, des suggestions, des calculs, et surtout des formulaires que tout le monde peut remplir, y compris au lecteur d'écran.

L'idée directrice de cette leçon : laisse le navigateur travailler pour toi. Plus tu décris précisément la nature de chaque champ, plus le navigateur t'offre gratuitement le bon clavier, la bonne validation et la bonne autocomplétion. Les exemples ci-dessous sont des blocs HTML que tu peux reprendre tels quels dans ton propre fichier.

Choisir le bon type d'input

Le piège numéro un, c'est de tout mettre en type="text". Chaque type spécialisé déclenche un clavier adapté sur mobile et une validation de format automatique. Voici les plus utiles :

Chaque type apporte un comportement gratuit : email et url vérifient le format, number ajoute des flèches +/−, range affiche un curseur, date/time ouvrent un sélecteur natif, color une pipette.

Sur smartphone, l'effet est spectaculaire : type="email" affiche un clavier avec le @ visible, type="tel" un pavé numérique, type="url" une touche « .com ». Il existe aussi datetime-local (date + heure dans le fuseau local), month (mois/année) et week (semaine ISO). Pour les fichiers :

accept="image/*" filtre les fichiers proposés, multiple autorise plusieurs sélections.

Note

Même quand l'apparence varie selon le navigateur, la valeur transmise est normalisée : une date arrive toujours au format AAAA-MM-JJ côté serveur, peu importe l'affichage local.

La validation native poussée

Le navigateur peut bloquer l'envoi d'un formulaire invalide et afficher un message, sans JavaScript. Les attributs clés : required (obligatoire), pattern (une expression régulière), min/max/step (bornes numériques ou de date), minlength/maxlength (longueur de texte).

Si tu tapes « ABC » dans le code postal, le navigateur refuse l'envoi et affiche un message reprenant le title : « 5 chiffres, ex. 75001 ».

L'attribut title personnalise l'indice montré quand le pattern n'est pas respecté. Sans title, le navigateur affiche un message générique du type « Veuillez respecter le format demandé » — bien moins utile.

Ces états sont aussi exposés au CSS via les pseudo-classes :valid et :invalid. Tu peux donc styliser un champ en rouge dès qu'il est invalide (le CSS est vu dans un autre cours, mais le lien se fait ici : c'est le HTML qui déclenche ces états).

Piège fréquent

La validation native reste une commodité : elle se contourne facilement. Tu dois toujours revalider côté serveur. Le HTML améliore l'expérience, il ne sécurise pas.

L'autocomplétion, un cadeau pour l'utilisateur

L'attribut autocomplete indique au navigateur la nature d'un champ, ce qui lui permet de proposer les valeurs déjà enregistrées (nom, e-mail, adresse, numéro de carte). C'est un gain de temps énorme et un vrai atout d'accessibilité : certaines extensions et gestionnaires de mots de passe en dépendent.

Les valeurs sont normalisées : given-name, family-name, email, tel, street-address, postal-code, cc-number, cc-exp, new-password, current-password…

Tu peux désactiver l'autocomplétion sur un champ sensible avec autocomplete="off", mais utilise-le avec parcimonie : dans la grande majorité des cas, l'autocomplétion aide l'utilisateur.

Cas réel

Sur une page de paiement e-commerce, un champ carte balisé autocomplete="cc-number" + inputmode="numeric" laisse le téléphone proposer la carte déjà enregistrée (ou scannée) et sort le pavé chiffré. À l'inverse, un type="text" nu oblige à tout retaper au mauvais clavier : c'est exactement le moment où l'acheteur abandonne. Quelques attributs bien placés font baisser le taux d'abandon au paiement.

datalist, output et les regroupements

<datalist> ajoute des suggestions à un champ texte tout en laissant l'utilisateur libre de taper autre chose. On le relie à l'input via l'attribut list, qui pointe vers l'id du <datalist>.

L'utilisateur voit des propositions, mais peut saisir une valeur libre : c'est la différence avec un <select>, qui impose un choix fermé.

<output> affiche un résultat calculé. Associé à un curseur (type="range"), il rend la valeur lisible. Le calcul dynamique demande une touche de JavaScript, mais l'élément sémantique, lui, est du HTML pur et est annoncé comme une zone de résultat aux technologies d'assistance.

<output> est une région « live » : sa mise à jour est signalée au lecteur d'écran.

Enfin, <fieldset> regroupe des champs liés et <legend> leur donne un titre commun — indispensable pour les groupes de cases à cocher ou de boutons radio, dont aucun n'a de <label> de groupe sinon.

Au lecteur d'écran, chaque option est annoncée avec le contexte du groupe : « Mode de livraison, Standard, bouton radio ».

Note

Le placeholder n'est pas un label : il disparaît dès qu'on tape, son contraste est faible, et il n'est pas toujours lu. Garde-le pour un exemple de saisie (« ex. 75001 »), jamais comme seule étiquette.

Rendre le formulaire accessible

Un formulaire accessible repose sur quelques règles simples. Chaque champ a un <label> associé : soit en enveloppant l'input, soit via for qui pointe vers l'id de l'input. Les textes d'aide et les messages d'erreur sont reliés au champ par aria-describedby, qui pointe vers l'id de l'élément d'aide.

Le lecteur d'écran annonce « Mot de passe, requis » puis lit l'aide reliée par aria-describedby : « 8 caractères minimum ».

Pense aussi à l'ordre de tabulation : il suit l'ordre du HTML, donc place tes champs dans un ordre logique plutôt que de bricoler avec tabindex. Un ordre source propre = une navigation au clavier correcte sans effort.

Les bonnes pratiques UX

Au-delà du code, quelques principes rendent un formulaire agréable :

  • Un champ par ligne : c'est plus lisible et plus rapide à remplir que des champs côte à côte.
  • Des messages clairs : dis quoi corriger et comment (« 5 chiffres ») plutôt que « champ invalide ».
  • Ne désactive jamais le collage sur un champ : c'est hostile, surtout pour les mots de passe.
  • Utilise inputmode pour affiner le clavier mobile sans changer le type : inputmode="numeric", "decimal", "email", "tel".

On garde type="text" (pas de flèches +/− indésirables) mais inputmode="numeric" sort le pavé chiffré sur mobile : le meilleur des deux.

Piège fréquent

Évite de désactiver le bouton d'envoi tant que le formulaire est invalide. L'utilisateur ne comprend pas pourquoi rien ne se passe. Laisse-le cliquer : la validation native lui indiquera précisément quoi corriger.

Astuce

Remplis tout ton formulaire au clavier seul : Tab pour passer de champ en champ, Espace/Entrée pour cocher et envoyer, les flèches pour les boutons radio. Si tu y arrives sans souris, ton formulaire est déjà accessible à une grande partie des utilisateurs — et l'ordre de tabulation reflète bien l'ordre du HTML.

Le lien avec JavaScript

Tout ce qu'on a vu fonctionne sans JavaScript. Mais quand tu en auras besoin (validation sur mesure, message au moment de la frappe), le HTML expose une Constraint Validation API. Chaque champ possède des propriétés et méthodes : checkValidity(), setCustomValidity(), l'objet validity… Tu n'as rien à écrire ici, mais retiens que tes attributs HTML (required, pattern…) alimentent directement cette API.

Le commentaire montre l'idée : ce sont tes attributs HTML qui remplissent l'objet validity. Bien déclarer le HTML, c'est déjà 90 % du travail de validation.

Pièges fréquents

  • Tout en type="text" : tu perds clavier mobile adapté et validation de format. Choisis le type le plus précis.
  • Le placeholder à la place du <label> : champ inaccessible et étiquette qui disparaît dès la saisie.
  • required sans message clair : ajoute un title ou une aide via aria-describedby.
  • Bouton d'envoi désactivé : préfère laisser la validation native s'exprimer.
  • Oublier autocomplete : tu prives l'utilisateur d'un remplissage instantané et fiable.
  • Champs non associés à un <label> : vérifie que chaque for correspond bien à un id existant.

Pour aller plus loin

Pour aller plus loin

La Constraint Validation API (validation sur mesure en JavaScript) et les Web Components de formulaire sont abordés dans le cours HTML avancé, tout comme l'accessibilité experte (ARIA poussé). Côté méthode, explore le design de formulaires : regroupement logique, formulaires en plusieurs étapes, et gestion fine des erreurs. La règle d'or reste : commence toujours par le HTML natif, n'ajoute du JavaScript que pour ce qu'il ne sait pas faire.

Glossaire

type (d'input)
Attribut qui change le comportement d'un <input> : clavier mobile, contrôle affiché et validation de format.
Validation native
Contrôles effectués par le navigateur (via required, pattern, min/max…) sans aucun JavaScript.
pattern
Expression régulière que la saisie doit respecter ; l'attribut title fournit le message d'aide affiché en cas d'erreur.
autocomplete
Indique la nature d'un champ (nom, e-mail, carte…) pour que le navigateur propose les valeurs enregistrées.
inputmode
Affine le clavier virtuel (numeric, decimal, tel…) sans changer le type du champ.
<datalist>
Liste de suggestions reliée à un champ par list ; l'utilisateur peut choisir une option ou saisir autre chose.
<fieldset> / <legend>
Regroupe des champs liés et leur donne un titre commun ; essentiel pour les groupes de radios et de cases.
aria-describedby
Relie un champ à l'id d'un texte d'aide ou d'erreur, lu par les technologies d'assistance après le libellé.

Récap et vérification

  • Choisis le type d'<input> le plus précis : clavier mobile et validation gratuits.
  • Valide en natif avec required, pattern, min/max/step, minlength/maxlength et un title explicite.
  • Ajoute autocomplete avec les valeurs standard pour un remplissage rapide et accessible.
  • Enrichis avec <datalist> (suggestions), <output> (résultat) et <fieldset>/<legend> (groupes).
  • Rends accessible : un <label> par champ, aria-describedby pour l'aide, un ordre source logique.
  • Soigne l'UX : un champ par ligne, messages clairs, collage autorisé, inputmode pertinent.
