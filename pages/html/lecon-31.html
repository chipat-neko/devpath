Module 10 · Web Components — Leçon 31

Le Shadow DOM

~32 min Avancé Leçon 05 recommandée

À la fin de cette leçon, tu sauras

  • savoir attacher un arbre shadow à un custom element avec attachShadow et y isoler un <style> local ;
  • savoir projeter le light DOM fourni par l'utilisateur grâce à <slot> ;
  • savoir styler le composant avec :host, ::slotted() et exposer des points de personnalisation via part et ::part() ;
  • savoir choisir entre les modes open et closed sans casser l'accessibilité.
Sommaire de la leçon

Tu sais déjà déclarer un custom element et réagir à son cycle de vie. Reste un problème de taille : tant que ton composant écrit dans le DOM de la page, ses styles et sa structure se mélangent à tout le reste. Une règle CSS globale repeint ton bouton interne ; ton propre <style> déborde sur la page. Le Shadow DOM règle ça : il crée un arbre encapsulé, isolé du document, où ta structure et ton CSS vivent en vase clos.

Dans cette leçon, tu vas attacher un shadow root, y placer un style qui ne fuit pas, projeter le contenu de l'utilisateur avec <slot>, puis ouvrir des points de personnalisation propres avec ::part.

Le problème : des styles qui fuient

Sans Shadow DOM, tout ce que ton composant injecte atterrit dans le DOM « clair » (le light DOM) de la page. Conséquence : un sélecteur global comme button { background: red } repeint tes boutons internes, et inversement un <style> que tu injectes peut casser la mise en page hôte. Plus le projet grandit, plus ces collisions deviennent ingérables. L'isolation n'est pas un confort, c'est ce qui rend un composant réellement réutilisable d'un projet à l'autre.

Le Shadow DOM établit une frontière : les sélecteurs du document ne traversent pas vers l'intérieur, et le CSS interne ne traverse pas vers l'extérieur. Cette frontière a des conséquences directes sur la façon de styler, qu'on détaille plus bas.

Attacher un shadow root

Dans le constructeur (ou connectedCallback) de ton custom element, appelle this.attachShadow({ mode: "open" }). Tu obtiens un ShadowRoot, racine d'un sous-arbre encapsulé. Tu y écris du HTML et un <style> qui ne concernera que ce sous-arbre.

Le <style> ne touche que le <p> du shadow, jamais les <p> de la page.

Projeter le contenu avec <slot>

Un composant encapsulé doit pouvoir afficher le contenu que l'utilisateur place entre ses balises. C'est le rôle de <slot> : c'est une « fenêtre » dans le shadow où le light DOM fourni est projeté. Sans name, le slot reçoit tout le contenu par défaut ; avec name="titre", il ne reçoit que les enfants portant slot="titre". Un <slot> peut contenir un contenu de repli affiché si l'utilisateur ne fournit rien.

Note

Le contenu projeté reste dans le light DOM : il appartient toujours à la page, qui peut le styler avec ses propres règles globales. Le slot ne fait que l'afficher à un endroit du shadow ; il ne le déplace pas dans l'arbre.

Styler par-delà la frontière

Comme le CSS global ne traverse plus, le shadow expose des sélecteurs dédiés :

  • :host cible le composant lui-même (l'élément <carte-info>), depuis l'intérieur du shadow.
  • :host(.actif) cible l'hôte seulement s'il correspond au sélecteur passé (classe, attribut, état…).
  • ::slotted(strong) cible le contenu projeté via un slot ; attention, il ne sélectionne que les nœuds projetés de premier niveau, pas leurs descendants.
  • part="..." sur un élément interne, combiné à ::part(...) côté page, expose un point de style public et contrôlé.

:host et ::slotted vivent dans le shadow ; ::part est la seule porte de style ouverte depuis l'extérieur.

open vs closed

Avec mode: "open", element.shadowRoot renvoie le shadow root : pratique pour les tests, le débogage et l'interopérabilité. Avec mode: "closed", element.shadowRoot vaut null et seul le code qui détient la référence retournée par attachShadow peut y accéder. Ce n'est pas une vraie barrière de sécurité (le code interne peut toujours fuiter la référence) et ça complique l'outillage. Préfère open par défaut ; ne ferme que si tu as une raison concrète.

Cas réel

Le Shadow DOM n'est pas réservé à tes composants : le navigateur s'en sert déjà pour ses contrôles natifs. Un <video controls>, un <input type="range"> ou un <input type="date"> cachent tout leur habillage (boutons, curseur, calendrier) dans un shadow root interne — c'est pour cela qu'on les stylise via des pseudo-éléments dédiés comme ::-webkit-slider-thumb, et non avec un sélecteur ordinaire. Côté industrie, les design systems livrés en Web Components (l'élément <clipboard-copy> de GitHub, Salesforce Lightning, Adobe Spectrum, les composants bâtis avec Lit) reposent sur cette encapsulation pour que leur CSS ne casse jamais, quelle que soit la feuille de style de la page qui les héberge.

Pièges fréquents

Piège fréquent

Croire que ton CSS global va styler l'intérieur du shadow. Il ne traverse pas. Pour intervenir depuis la page, passe par ::part() ou par des propriétés personnalisées (les variables CSS, elles, héritent à travers la frontière). En interne, utilise :host et :host(...).

  • Choisir closed par réflexe. Tu perds le débogage et l'interop sans gagner de sécurité réelle. Reste sur open sauf besoin précis.
  • Oublier le <slot>. Si aucun slot n'est présent dans le shadow, le contenu fourni par l'utilisateur n'est tout simplement pas affiché. Le composant paraît vide.
  • Négliger l'accessibilité. Le contenu reste exposé à l'arbre d'accessibilité, mais une relation ARIA par id (comme aria-labelledby) ne franchit pas la frontière : garde les éléments liés du même côté, et place les rôles et libellés dans le shadow.

Pour aller plus loin

Pour aller plus loin

Thèmes via ::part pour exposer une API de style stable. Custom States (ElementInternals.states + :state()) pour des états internes ciblables en CSS. Declarative Shadow DOM (<template shadowrootmode="open"> placé comme premier enfant de l'hôte) pour rendre le shadow côté serveur sans JS. Constructable stylesheets (adoptedStyleSheets) pour partager une même feuille entre plusieurs shadow roots sans dupliquer le <style>.

Antisèche : l'API du Shadow DOM

Glossaire

Shadow DOM
Arbre DOM encapsulé attaché à un élément : sa structure et son <style> sont isolés du reste du document.
Light DOM
Le DOM « clair » ordinaire de la page, y compris le contenu placé entre les balises d'un composant ; il reste stylable par la page.
Shadow root
Racine du sous-arbre encapsulé, renvoyée par attachShadow ; on y écrit le HTML et le CSS internes du composant.
attachShadow
Méthode qui crée et attache le shadow root ; prend une option { mode } valant "open" ou "closed".
Frontière (boundary)
Limite qui empêche les sélecteurs du document d'entrer et le CSS interne de sortir ; seules les variables CSS et ::part() la franchissent.
<slot>
Emplacement du shadow où le light DOM fourni est projeté. Un slot nommé capte les slot="…" correspondants ; le slot sans nom capte le reste.
:host / ::slotted()
Depuis l'intérieur du shadow : :host cible l'élément hôte, ::slotted() cible le contenu projeté (au premier niveau).
part / ::part()
Un élément interne marqué part="x" devient stylable depuis la page via ::part(x) : la seule porte de style ouverte vers l'extérieur.

Récap et vérification

  • attachShadow({ mode }) crée un arbre encapsulé où HTML et <style> sont isolés du document.
  • <slot> projette le light DOM ; sans slot, le contenu fourni n'apparaît pas.
  • On style depuis l'intérieur avec :host, :host(...) et ::slotted(...).
  • part + ::part(...) ouvrent un point de style public depuis la page ; les variables CSS traversent aussi.
  • open par défaut ; closed n'est pas une sécurité.

  3. Quel mécanisme exposerais-tu pour laisser la page personnaliser la couleur d'un badge interne, sans casser l'encapsulation ?
