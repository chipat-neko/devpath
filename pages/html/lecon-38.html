Module 14 · Interactions & sécurité — Leçon 38

Glisser-déposer et l'API History

~34 min Avancé Cours HTML avancé recommandé

À la fin de cette leçon, tu sauras

  • savoir rendre un élément déplaçable et gérer les événements dragstart, dragover et drop en pensant au preventDefault obligatoire ;
  • savoir transporter des données et lire des fichiers déposés via l'objet dataTransfer ;
  • savoir prévoir une alternative clavier à un glisser-déposer inaccessible ;
  • savoir modifier l'URL sans recharger avec history.pushState et réagir à popstate.
Sommaire de la leçon

Deux API de la plateforme web te permettent de construire des interactions que les développeurs croient souvent réservées aux frameworks : déplacer des éléments à la souris, et changer l'URL sans recharger la page. Le glisser-déposer natif (Drag and Drop) et l'API History sont disponibles dans tous les navigateurs depuis longtemps, mais elles ont chacune leurs pièges — un preventDefault oublié ou un state mal sérialisé suffit à tout casser.

Dans cette leçon, tu vas câbler une zone de dépôt complète, gérer le dépôt de fichiers pour un upload, puis construire une mini-navigation « single page » qui respecte le bouton Précédent. On insiste aussi sur l'accessibilité, trop souvent négligée avec le glisser-déposer.

Rendre un élément déplaçable

Un élément devient déplaçable avec l'attribut draggable="true". Côté source (l'élément qu'on saisit), deux événements t'intéressent : dragstart (au début du glissement, pour stocker ce qu'on transporte) et dragend (à la fin, qu'il y ait eu dépôt ou non, pour nettoyer).

La source déclare ce qu'elle transporte dans dragstart et se nettoie dans dragend.

La cible : autoriser le dépôt

Côté cible (la zone d'accueil), le navigateur refuse le dépôt par défaut. Pour l'autoriser, tu dois appeler e.preventDefault() dans dragover — c'est la règle la plus contre-intuitive de cette API. Les autres événements utiles sont dragenter et dragleave (pour le surlignage de la zone) et drop (le dépôt effectif).

Clique sur « 👁 Aperçu » pour glisser le jeton dans la boîte. Sans le preventDefault de dragover, rien ne se passerait au dépôt.

Note

L'événement drop ne se déclenche que sur une cible qui a « accepté » le survol via preventDefault dans dragover. C'est pour ça qu'on l'appelle sur les deux événements.

L'objet dataTransfer

e.dataTransfer est le porteur des données pendant tout le glissement. Tu y écris avec setData(type, valeur) et tu lis avec getData(type). Le type est un type MIME : text/plain, text/html, text/uri-list, ou un type applicatif comme application/json. Tu peux stocker plusieurs représentations de la même donnée.

Deux propriétés contrôlent le curseur et l'intention : effectAllowed (côté source, ce qui est permis : "copy", "move", "copyMove"…) et dropEffect (côté cible, l'effet retenu, qui change l'icône affichée). Attention : getData ne renvoie une valeur que dans drop ; pendant dragover, pour des raisons de sécurité, seuls les types sont lisibles, pas les données.

Un type applicatif pour les données structurées, un text/plain en repli pour les autres cibles (autre champ, autre appli).

Glisser des fichiers depuis le système

Le cas le plus utile en pratique : déposer des fichiers depuis l'explorateur pour les uploader. Ici la source est le système d'exploitation, pas un élément de ta page. Les fichiers arrivent dans e.dataTransfer.files, une FileList que tu parcours comme un tableau.

Chaque File expose name, size et type. Pour lire son contenu, on passe par l'API File (voir « Pour aller plus loin »).

Astuce

Double aussi le dépôt par un <input type="file"> caché : le même flux de traitement marche pour les deux, et l'input reste pleinement accessible au clavier.

L'accessibilité du glisser-déposer

Le glisser-déposer natif est inaccessible au clavier : sans souris ni écran tactile, on ne peut tout simplement pas l'utiliser. C'est une exclusion réelle. La règle : ne jamais faire d'une action un glisser-déposer exclusif. Prévois toujours un chemin alternatif — boutons « Monter / Descendre », menu de réaffectation, ou champ de saisie.

Le glisser-déposer reste un raccourci pour la souris ; les boutons garantissent que tout le monde peut réordonner.

Cas réel

Un tableau kanban (Trello, les projets GitHub, un back-office de gestion) repose entièrement sur le glisser-déposer : on saisit une carte, dragstart mémorise son identifiant, et le drop sur une colonne déclenche la réaffectation. Mais les équipes sérieuses n'en font jamais le seul moyen d'action : un menu « Déplacer vers… » ou des raccourcis clavier offrent le même résultat. Sans cette alternative, une personne au clavier ou au lecteur d'écran ne pourrait tout simplement pas déplacer ses cartes — une barrière d'accessibilité que la réglementation impose de plus en plus de lever.

L'API History : changer l'URL sans recharger

Passons à l'API History. Elle te permet de modifier la barre d'adresse et la pile de navigation sans recharger la page — la base de toute application « single page ». Deux méthodes :

  • history.pushState(state, "", url) : ajoute une entrée à l'historique (un nouveau bouton Précédent possible).
  • history.replaceState(state, "", url) : remplace l'entrée courante sans en créer une nouvelle.

Le premier argument est un objet d'état sérialisable, le deuxième (le titre) est ignoré par les navigateurs — passe une chaîne vide —, le troisième est l'URL (même origine obligatoire). Pour réagir aux boutons Précédent / Suivant, écoute l'événement popstate sur window.

Le state rangé dans pushState revient dans e.state lors du popstate : tu reconstruis la vue sans relire l'URL.

Piège fréquent

pushState ne déclenche pas popstate. Seule la navigation de l'utilisateur (Précédent / Suivant, ou history.back()) le fait. Après un pushState, appelle toi-même ta fonction de rendu — sinon la vue et l'URL se désynchronisent.

Note

Dans l'aperçu, le rendu se fait dans une iframe isolée : pushState peut y être bloqué par la politique d'origine et lever une SecurityError, et l'URL affichée n'est pas celle de la barre d'adresse. Pour tester réellement l'API History, exécute la démo dans une page servie à part. Les démos de glisser-déposer interne (jeton vers zone), elles, fonctionnent dans l'aperçu ; le dépôt de fichiers depuis l'OS, non.

back, forward, go et l'état sérialisable

Tu peux piloter l'historique par programme : history.back() (équivaut au bouton Précédent), history.forward(), et history.go(n) où n est un décalage relatif (go(-2) recule de deux entrées, go(0) recharge la page). Ces appels, eux, déclenchent popstate (de façon asynchrone).

Surtout : l'objet state doit être sérialisable par l'algorithme de clonage structuré. Il est stocké sur disque par le navigateur. Tu peux y mettre objets, tableaux, nombres, chaînes, Date, Map, Set… mais pas de fonctions, de nœuds DOM, ni de références circulaires non gérées. Une autre limite, souvent oubliée : la taille du state est plafonnée (de l'ordre du méga-octet) — n'y range pas des données volumineuses.

Range dans le state juste de quoi reconstruire la vue (un identifiant, un type), pas des objets vivants ni de gros volumes.

Cas réel

Ouvre Gmail, Twitter/X ou GitHub et navigue dans l'interface : l'URL change (/mail/0/inbox, /ton-profil) mais la page ne « clignote » jamais — aucun rechargement complet. C'est pushState à l'œuvre : chaque écran pousse une entrée d'historique, si bien que le bouton Précédent te ramène à la vue précédente et qu'un lien copié-collé rouvre le bon écran. Le jour où un site casse ton bouton Précédent, c'est presque toujours une API History mal gérée.

Le lien avec le routage côté client

Ce que tu viens de coder à la main — intercepter les clics, pousser une entrée, réagir à popstate — c'est exactement ce que fait un routeur client. React Router, Vue Router ou le routeur de la plupart des frameworks s'appuient sur cette même API History. Comprendre pushState et popstate te donne le modèle mental sous-jacent : un routeur n'est qu'une couche qui associe des URL à des composants au-dessus de ces primitives.

Note

Le routage par pushState utilise de « vraies » URL (/produit/42). Pour que le rechargement direct fonctionne, le serveur doit renvoyer ton index.html sur ces chemins (réécriture côté serveur), sinon tu obtiens un 404. C'est la différence avec le routage par fragment (#/produit/42), qui ne touche jamais le serveur.

Pièges fréquents

  • Oublier preventDefault dans dragover : sans lui, l'événement drop ne se déclenche jamais. C'est l'erreur n°1 du glisser-déposer.
  • Vouloir lire getData dans dragover : pour la sécurité, les données ne sont lisibles que dans drop ; pendant le survol, seuls les types le sont.
  • Un glisser-déposer sans alternative clavier : tu exclus les personnes qui n'utilisent pas de souris. Prévois toujours des boutons ou un menu.
  • Croire que pushState déclenche popstate : non. Appelle ta fonction de rendu manuellement après chaque pushState.
  • Un state non sérialisable : fonctions, nœuds DOM ou références circulaires lèvent une DataCloneError.
  • Casser le bouton Précédent : si tu fais un pushState à chaque interaction triviale, l'utilisateur doit cliquer dix fois sur Précédent pour sortir. Réserve pushState aux vraies navigations ; utilise replaceState pour les mises à jour mineures (un filtre, un onglet).

Pour aller plus loin

Pour aller plus loin

L'API File (FileReader, ou file.text() / file.arrayBuffer()) lit le contenu des fichiers déposés. Les bibliothèques de DnD accessibles (par ex. les solutions basées sur @dnd-kit) gèrent le clavier pour toi. L'API Navigation, plus récente, vise à remplacer l'API History avec un modèle plus cohérent (événement navigate, interception centralisée). Et côté frameworks, le routage côté client formalise tout ce que tu as vu ici.

Glossaire

draggable
Attribut booléen qui rend un élément déplaçable à la souris ; il active les événements dragstart, dragover, drop…
dragover + preventDefault
La cible doit annuler le comportement par défaut pendant dragover pour être autorisée à recevoir ; sans cela, drop ne se déclenche jamais.
dataTransfer
Objet porteur des données pendant le glissement : setData/getData par type MIME, et .files (une FileList) pour les fichiers venus du système.
effectAllowed / dropEffect
Opérations que la source autorise (copy, move…) et effet retenu par la cible, qui change l'icône du curseur.
API History
Ensemble pushState/replaceState qui modifie l'URL et la pile de navigation sans recharger la page.
popstate
Événement émis uniquement par la navigation arrière/avant (ou back()/go()), jamais par pushState.
state
Objet sérialisable (clonage structuré) rangé dans une entrée d'historique : ni fonction, ni nœud DOM, ni gros volume.
routage côté client
Couche (React Router, Vue Router…) qui associe des URL à des vues au-dessus de l'API History.

Récap et vérification

  • Un élément se rend déplaçable avec draggable="true" ; la source écoute dragstart / dragend.
  • La cible doit appeler preventDefault dans dragover pour que drop se déclenche.
  • dataTransfer transporte les données (setData / getData + type MIME, lisibles seulement dans drop) et expose les fichiers système dans .files.
  • Le glisser-déposer doit toujours avoir une alternative clavier.
  • pushState / replaceState changent l'URL sans recharger ; popstate ne réagit qu'à la navigation utilisateur ; le state doit être sérialisable.

Vérifie ta compréhension

  1. Pourquoi le dépôt ne fonctionne-t-il pas si tu oublies preventDefault dans dragover ?
  2. Quelle est la différence entre effectAllowed et dropEffect ?
  3. Après un history.pushState, l'événement popstate se déclenche-t-il ? Que dois-tu faire en conséquence ?
