Module 15 · La plateforme web en profondeur — Leçon 41

Les API modernes du navigateur

~34 min Avancé Leçon 15 recommandée

À la fin de cette leçon, tu sauras

  • savoir animer des changements d'état et de page avec la View Transitions API (document.startViewTransition) et un repli propre ;
  • savoir intercepter les navigations d'une SPA avec la Navigation API, successeur de History ;
  • savoir utiliser Web Share, Clipboard et File System Access en gérant permissions, HTTPS et geste utilisateur ;
  • savoir détecter une fonctionnalité ('share' in navigator) et organiser une dégradation gracieuse.
Sommaire de la leçon

Tu as parcouru les quatorze leçons du cours : tu sais désormais composer un <dialog>, écrire un Web Component, baliser en ARIA, structurer en schema.org, déclarer une PWA, optimiser le chargement, gérer le glisser-déposer et l'historique, verrouiller en CSP/SRI. Cette leçon de compléments rassemble une autre famille : les API JavaScript récentes qui effacent la frontière entre une page web et une application native — transitions fluides, navigation interceptée, partage système, presse-papiers, accès au système de fichiers.

Le fil rouge n'est pas seulement « comment appeler l'API », mais « comment l'appeler sans casser sur un navigateur qui ne la connaît pas, sans HTTPS, ou quand l'utilisateur refuse une permission ». La détection de fonctionnalité et la dégradation gracieuse sont ici la compétence centrale : une API moderne mal gardée transforme une amélioration en page blanche.

View Transitions : animer un changement d'état

La View Transitions API capture un instantané de l'écran avant et après une mutation du DOM, puis interpole entre les deux. Tu encapsules ta mise à jour dans un callback passé à document.startViewTransition : le navigateur fige l'ancien rendu, exécute ton callback, prend le nouveau rendu, et anime le passage (un cross-fade par défaut).

Pour personnaliser, tu cibles les pseudo-éléments générés en CSS : ::view-transition-old(root) et ::view-transition-new(root) reçoivent les deux instantanés, et view-transition-name sur un élément lui donne sa propre transition indépendante (utile pour faire « voler » une vignette vers sa version agrandie). Côté MPA (navigation entre deux documents), tu actives la transition par une règle @view-transition { navigation: auto; } dans la feuille de style — aucun JS requis, mais les deux pages doivent être de même origine.

Note

Le callback de startViewTransition peut être async et renvoyer une promesse : le navigateur attend sa résolution (par exemple un fetch de fragment) avant de capturer le nouvel état. Garde-le court, sinon l'écran reste figé pendant l'attente.

Navigation API : le successeur de History

Tu connais history.pushState et l'événement popstate. La Navigation API les remplace par un objet navigation central et un seul événement navigate qui intercepte toutes les navigations same-origin : clic sur un lien, soumission de formulaire, retour arrière. Tu n'as plus à intercepter les clics à la main pour bâtir un routeur SPA.

event.intercept remplace tout le bricolage pushState + gestion manuelle du retour : l'entrée d'historique est créée pour toi, l'état de chargement est exposé via navigation.transition, et tu peux scroller au bon endroit. Pour une navigation déclenchée par code, navigation.navigate('/page') renvoie un objet avec committed et finished, deux promesses qui te disent où en est la transition.

Web Share : partager comme une app native

navigator.share ouvre la feuille de partage du système (Messages, Mail, réseaux sociaux installés) avec un objet contenant title, text, url et même des files. C'est asynchrone, ça exige un geste utilisateur (un clic), et ça rejette si l'utilisateur annule.

Le pendant Web Share Target se déclare côté PWA dans le manifeste (clé share_target) : ton application installée apparaît alors dans la feuille de partage des autres apps et reçoit les données partagées sur une URL que tu traites. C'est ce qui fait qu'une PWA se comporte comme une cible de partage de premier rang.

Clipboard : lire et écrire le presse-papiers

L'API asynchrone navigator.clipboard remplace l'antique document.execCommand('copy'). L'écriture (writeText) est généralement permise depuis un geste utilisateur ; la lecture (readText) déclenche une demande de permission explicite, car lire le presse-papiers est sensible. Tout est asynchrone et soumis à un contexte sécurisé (HTTPS ou localhost).

Pour des données riches (image, HTML), tu utilises navigator.clipboard.write avec un tableau de ClipboardItem portant des Blob typés. La lecture suit le même modèle via read() et l'inspection des types de chaque item.

File System Access : ouvrir et enregistrer en local

Cette API donne au web un accès direct aux fichiers de l'utilisateur, derrière un sélecteur natif. showOpenFilePicker renvoie des handles (poignées) persistables ; tu lis le contenu, et avec un handle obtenu via showSaveFilePicker tu écris en place via un writable — un vrai « Enregistrer sous… ». Chaque appel exige un geste utilisateur, et l'écriture demande une permission distincte de la lecture.

Piège fréquent

Un handle conservé en IndexedDB survit au rechargement, mais la permission, elle, n'est pas garantie de survivre : à la reprise, appelle handle.queryPermission(...) puis handle.requestPermission(...) avant de relire ou réécrire, sinon tu reçois une NotAllowedError.

Cas réel

Les éditeurs web modernes — VS Code for the Web (vscode.dev), Excalidraw, Photopea — reposent sur File System Access. Quand tu ouvres un fichier local, le modifies et fais Ctrl+S, l'écriture retombe dans ton fichier d'origine, sans détour par le dossier « Téléchargements ». Avant cette API, un éditeur web ne savait que re-télécharger un nouveau fichier à chaque sauvegarde : tu accumulais dessin.png, dessin (1).png, dessin (2).png… Ces apps détectent l'API : présente (Chrome, Edge), elles offrent le vrai « Enregistrer » ; absente (Firefox, Safari), elles replient sur <input type="file"> pour ouvrir et un lien de téléchargement pour sauver. Une seule base de code, deux niveaux d'expérience.

Le reste de l'arsenal, en survol

Plusieurs API suivent le même contrat (geste utilisateur, contexte sécurisé, permission) et méritent une détection avant emploi :

  • Geolocation : navigator.geolocation.getCurrentPosition, avec callback de succès et d'erreur (permission refusée, position indisponible).
  • Notifications : Notification.requestPermission() puis new Notification(...) ; côté PWA, via le ServiceWorkerRegistration.
  • Web Speech : synthèse vocale (speechSynthesis.speak) et reconnaissance (SpeechRecognition, encore préfixée selon les navigateurs).
  • Badging : navigator.setAppBadge(n) pour afficher un compteur sur l'icône d'une PWA installée.
  • Réseau / batterie : navigator.connection (type, saveData) et navigator.getBattery() — au support et à la confidentialité variables, à n'utiliser qu'en amélioration.

Détection et dégradation gracieuse

La règle vaut pour tout ce qui précède : teste la présence avant l'appel, et prévois toujours un chemin de repli. Selon le cas, on teste une propriété sur navigator ou window ('share' in navigator), une méthode (document.startViewTransition), ou la pré-validation dédiée (navigator.canShare(data)).

Astuce

Pense en « amélioration progressive » : l'expérience de base fonctionne sans aucune de ces API, puis chaque détection positive ajoute une couche. Un thème change sans animation si View Transitions manque ; un lien se copie si Web Share manque. L'utilisateur n'a jamais d'écran cassé.

Pièges fréquents

Ces API échouent rarement par hasard : c'est presque toujours un contexte d'exécution mal anticipé.

  • Appeler sans détecter. navigator.share(...) sur un navigateur qui l'ignore lève une TypeError et casse le script entier. Garde chaque appel derrière un if.
  • Oublier HTTPS et le geste utilisateur. Clipboard, File System Access, Web Share exigent un contexte sécurisé et un déclenchement depuis un clic. Appelées au chargement ou en HTTP simple, elles rejettent avec NotAllowedError.
  • Ne pas gérer le refus. Une permission refusée ou une annulation (AbortError) n'est pas un bug : enveloppe d'un try/catch et distingue l'annulation volontaire de la vraie erreur.
  • View Transitions sans repli. Si startViewTransition est absent, ta mutation DOM doit quand même s'exécuter — sinon l'état ne change pas du tout.
  • Supposer un support universel. Navigation API et File System Access ne sont pas partout. Vérifie caniuse et le statut Baseline avant de t'appuyer dessus en production.

Pour aller plus loin

Pour aller plus loin

Suis le statut de chaque API via caniuse et l'indicateur Baseline (largement disponible / nouvellement disponible). Pour tester une API non encore stabilisée en production, regarde les origin trials de Chrome. L'ensemble de l'effort qui rapproche le web du natif s'appelle le Project Fugu ; il alimente les PWA avancées (badging, raccourcis, partage cible) et la famille des capteurs (orientation, mouvement, lumière). Ce sont d'excellents points d'entrée pour ta veille.

Glossaire

View Transitions API
Anime un changement d'état via document.startViewTransition(callback) : le navigateur capture l'écran avant et après le callback, puis interpole (cross-fade par défaut). Personnalisable en CSS avec ::view-transition-*.
Navigation API
Successeur de History : un objet navigation et un événement navigate unique interceptent toutes les navigations same-origin. event.intercept remplace le bricolage pushState/popstate.
Web Share (navigator.share)
Ouvre la feuille de partage native du système avec title, text, url, files. Exige un geste utilisateur ; canShare pré-valide les données.
Clipboard API
Accès asynchrone au presse-papiers via navigator.clipboard : writeText/readText (texte) et write/read (données riches). La lecture demande une permission explicite.
File System Access
Ouvre et enregistre de vrais fichiers locaux via showOpenFilePicker/showSaveFilePicker. Renvoie des handles (poignées) persistables ; l'écriture demande une permission distincte de la lecture.
Contexte sécurisé
Page servie en HTTPS (ou localhost). Prérequis de la plupart de ces API ; hors de lui, l'objet est souvent absent ou l'appel rejette.
Geste utilisateur (activation)
Déclenchement depuis une interaction réelle (clic, appui). Web Share, Clipboard et File System Access refusent d'agir sans lui, pour empêcher les abus silencieux.
Détection de fonctionnalité
Tester la présence d'une API ('share' in navigator, 'startViewTransition' in document) avant de l'appeler, puis brancher une dégradation gracieuse si elle manque.

Récap et vérification

  • View Transitions : document.startViewTransition(callback) anime un changement d'état ; CSS via ::view-transition-* et view-transition-name ; MPA via @view-transition.
  • Navigation API : un seul événement navigate + event.intercept remplacent pushState/popstate pour une SPA propre.
  • Web Share : navigator.share ouvre la feuille système ; canShare pré-valide ; Web Share Target fait d'une PWA une cible.
  • Clipboard : writeText/readText asynchrones, HTTPS et permission requis.
  • File System Access : showOpenFilePicker/showSaveFilePicker, handles persistables, permission lecture vs écriture.
  • Détection : 'x' in navigator ou window, puis dégradation gracieuse systématique.

Vérifie ta compréhension

  1. Pourquoi le callback passé à startViewTransition doit-il contenir la mutation du DOM, et non être appelé avant ?
  2. Quel avantage event.intercept de la Navigation API apporte-t-il par rapport à un routeur bâti sur pushState + popstate ?
  3. Cite deux conditions d'exécution communes à Clipboard, Web Share et File System Access, et l'erreur typique quand elles manquent.
