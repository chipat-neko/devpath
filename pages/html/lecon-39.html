Module 14 · Interactions & sécurité — Leçon 39

Sécurité côté client (CSP, SRI, sandbox)

~35 min Avancé Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire une CSP en liste blanche (script-src 'self', nonces) pour bloquer le XSS et le JS inline ;
  • savoir sécuriser une dépendance de CDN avec integrity et crossorigin (SRI) ;
  • savoir isoler du contenu tiers avec iframe sandbox et sécuriser target="_blank" via rel="noopener" ;
  • savoir reconnaître les en-têtes utiles (nosniff, frame-ancestors) et échapper les données utilisateur.
Sommaire de la leçon

Tu sais désormais construire des interfaces riches : dialogues, popovers, Web Components, PWA. Mais une plateforme web moderne s'adresse à de vrais utilisateurs, donc à de vrais attaquants. Le HTML et quelques en-têtes HTTP te donnent une première ligne de défense déclarative, vérifiée par le navigateur lui-même : pas de bibliothèque, pas de runtime à qui faire confiance, juste des règles que le moteur applique avant d'exécuter quoi que ce soit.

Cette leçon couvre les mécanismes que tu peux activer côté client : la CSP pour brider l'exécution de code, le SRI pour garantir l'intégrité de tes dépendances, l'iframe sandbox pour cloisonner du contenu tiers, et les bonnes pratiques sur les liens, les en-têtes et l'injection de données. L'objectif n'est pas la paranoïa, mais la défense en profondeur : chaque couche réduit la surface d'attaque.

Les menaces côté client

Trois familles dominent. Le XSS (cross-site scripting) injecte du JavaScript dans ta page : l'attaquant fait exécuter son code dans le contexte de ta victime (vol de cookies, de jetons, actions à son insu). Le clickjacking charge ton site dans une <iframe> invisible sur un site pirate pour détourner les clics. Enfin, les dépendances compromises : un script chargé depuis un CDN qui se fait pirater, et c'est tout ton trafic qui exécute du code malveillant.

Note

Les protections côté client ne remplacent jamais la validation côté serveur. Elles la complètent : même si une faille passe le serveur, la CSP peut empêcher le script injecté de s'exécuter.

La CSP : une liste blanche des sources

La Content-Security-Policy déclare au navigateur quelles ressources il a le droit de charger et d'exécuter. C'est une liste blanche par directive : script-src pour le JS, style-src pour le CSS, img-src pour les images, default-src comme repli. Tout ce qui n'est pas autorisé est bloqué, y compris le JavaScript injecté par un XSS et le JS inline (<script>…</script> ou onclick=).

On la sert idéalement via un en-tête HTTP, mais une <meta http-equiv> dans le <head> fonctionne aussi pour les pages statiques.

Ici, scripts et ressources ne peuvent venir que de ton propre domaine ('self'). Le JS inline et le JS distant non listé sont refusés.

Pour autoriser un script inline précis sans ouvrir la porte à tous, tu lui attribues un nonce aléatoire (régénéré à chaque réponse, côté serveur) :

'strict-dynamic' propage la confiance : un script déjà noncé peut charger d'autres scripts par le DOM, sans avoir à lister chaque domaine. Attention : en présence de 'strict-dynamic', les allowlists d'hôtes et 'self' sont ignorées ; seuls les nonces et hashes comptent.

Piège fréquent

Ajouter 'unsafe-inline' à script-src annule l'essentiel de la protection : tout JS injecté redevient exécutable. Si tu en as besoin « temporairement », c'est que ta CSP ne te protège plus du XSS.

Le SRI : garantir l'intégrité d'un CDN

Charger jQuery ou une police depuis un CDN, c'est pratique mais risqué : si le CDN est compromis, le fichier servi change sous tes pieds. Le Subresource Integrity ajoute un attribut integrity contenant le hash attendu du fichier. Le navigateur calcule le hash de ce qu'il reçoit ; s'il diffère, il refuse d'exécuter la ressource.

Le hash est encodé en base64, préfixé par l'algorithme (sha384 recommandé). On l'obtient à la génération du build ou via l'outil du CDN.

Astuce

Pour calculer un hash toi-même : openssl dgst -sha384 -binary fichier.js | openssl base64 -A, puis préfixe le résultat par sha384-. Recalcule-le à chaque mise à jour de version, sinon le navigateur bloquera la nouvelle ressource.

Piège fréquent

integrity sans crossorigin ne fonctionne pas pour une ressource cross-origin : le navigateur a besoin du CORS pour lire le contenu et le vérifier. Sans crossorigin="anonymous", la requête se fait sans CORS et la ressource est bloquée.

Cas réel

En juin 2024, le domaine polyfill.io — un script chargé par plus de 100 000 sites depuis un CDN « de confiance » — a changé de propriétaire et s'est mis à injecter du code malveillant qui redirigeait les visiteurs mobiles vers des sites de paris. Même logique côté paiement avec les attaques Magecart, qui greffent un « skimmer » de cartes bancaires sur un script tiers (l'affaire British Airways, en 2018, a touché 380 000 transactions). Dans les deux cas, un simple integrity (SRI) aurait figé le contenu attendu : dès que le fichier servi changeait, le navigateur l'aurait refusé au lieu de l'exécuter.

L'iframe sandbox : isoler le contenu tiers

Quand tu intègres du contenu que tu ne contrôles pas (pub, widget, aperçu utilisateur), l'attribut sandbox sur l'<iframe> coupe par défaut TOUTES les capacités dangereuses : scripts, formulaires, popups, navigation du parent. Tu réactives ensuite à la carte avec des jetons allow-*.

Sans allow-same-origin, le contenu est traité comme une origine opaque : il ne peut pas lire tes cookies ni ton localStorage.

Piège fréquent

Combiner allow-scripts ET allow-same-origin sur du contenu non fiable est dangereux : le script s'exécute alors avec ton origine et peut retirer lui-même l'attribut sandbox de son propre iframe, donc s'échapper. Ne réunis ces deux jetons que si tu contrôles totalement la source.

Les liens : tabnabbing et referrer

Un lien target="_blank" ouvre un onglet qui, sans précaution, garde une référence window.opener vers ta page : la page ouverte peut alors faire opener.location = 'https://phishing.example' et remplacer ton onglet par une copie piégée. C'est le tabnabbing.

noopener coupe l'accès à window.opener ; noreferrer n'envoie pas l'en-tête Referer. Tu peux aussi régler finement la fuite d'URL avec referrerpolicy="no-referrer" ou strict-origin-when-cross-origin.

Note

Les navigateurs modernes appliquent noopener implicitement pour target="_blank", mais l'écrire reste la bonne habitude : tu ne contrôles pas la version du navigateur de tes visiteurs, et l'intention reste explicite dans ton code.

HTTPS et en-têtes utiles

Tout ce qui précède suppose du HTTPS : sans chiffrement, un intermédiaire réécrit ta page et ta CSP. Côté en-têtes HTTP, deux réflexes : X-Content-Type-Options: nosniff empêche le navigateur de « deviner » le type d'un fichier (un .txt uploadé qui serait exécuté comme JS), et le contrôle du framing contre le clickjacking.

frame-ancestors (directive CSP) remplace l'ancien X-Frame-Options et dit qui a le droit de t'inclure dans une iframe : 'self' bloque le clickjacking depuis un autre domaine.

Échapper les données utilisateur

La CSP est un filet de sécurité, pas une excuse pour injecter n'importe quoi. La règle d'or reste : quand tu insères une donnée venue de l'utilisateur, utilise textContent (qui traite tout comme du texte) plutôt que innerHTML (qui interprète le HTML, donc les balises <script> et les attributs on*).

Clique sur « 👁 Aperçu » : avec textContent, même une valeur comme <b>x</b> s'affiche littéralement au lieu d'être interprétée.

Piège fréquent

Construire du HTML par concaténation puis l'affecter à innerHTML est la source numéro un de XSS. Si tu dois vraiment générer du HTML, passe par createElement + textContent, ou un système d'échappement éprouvé.

Pièges fréquents

  • 'unsafe-inline' dans script-src annule la protection anti-XSS : préfère les nonces ou les hashes.
  • integrity sans crossorigin sur une ressource d'un autre domaine : la vérification ne s'applique pas et la ressource est bloquée.
  • target="_blank" sans rel="noopener" : porte ouverte au tabnabbing.
  • innerHTML avec des données utilisateur : injection de balises et d'attributs on*.
  • sandbox="allow-scripts allow-same-origin" sur du contenu non fiable : le sandbox peut se neutraliser lui-même.

Pour aller plus loin

Pour aller plus loin

Approfondis les nonces CSP générés côté serveur, les Trusted Types (qui interdisent au runtime l'affectation de chaînes brutes aux puits dangereux comme innerHTML), Permissions-Policy pour restreindre l'accès aux API (caméra, géoloc), les rapports CSP (report-to / Reporting API) pour détecter les violations en production, et l'audit des dépendances (npm audit, lockfiles, SCA) pour repérer les paquets vulnérables.

Glossaire

XSS (cross-site scripting)
Injection de JavaScript dans une page pour l'exécuter dans le contexte de la victime (vol de cookies ou de jetons, actions à son insu). Principale menace que vise la CSP.
CSP (Content-Security-Policy)
Liste blanche déclarative, servie en en-tête HTTP ou en <meta>, qui indique au navigateur quelles sources il peut charger et exécuter, directive par directive (script-src, img-src…).
nonce
Jeton aléatoire régénéré à chaque réponse, placé dans la CSP et sur un <script> précis, pour autoriser cet inline-là sans ouvrir 'unsafe-inline'.
SRI (Subresource Integrity)
Attribut integrity contenant l'empreinte attendue d'un fichier ; le navigateur recalcule le hash reçu et bloque la ressource s'il diffère. À coupler avec crossorigin.
sandbox
Attribut d'<iframe> qui coupe par défaut toutes les capacités du contenu intégré ; on les rouvre une par une avec des jetons allow-*.
tabnabbing
Détournement d'onglet : une page ouverte via target="_blank" se sert de window.opener pour remplacer ton onglet par une copie piégée. Contré par rel="noopener".
clickjacking
Ton site est chargé dans une iframe invisible sur un site pirate pour détourner les clics ; bloqué par frame-ancestors (CSP) ou X-Frame-Options.
nosniff
En-tête X-Content-Type-Options: nosniff qui interdit au navigateur de « deviner » le type d'un fichier au lieu de suivre son Content-Type.

Récap et vérification

  • La CSP est une liste blanche déclarative qui bloque le JS injecté et inline ; évite 'unsafe-inline', utilise 'self' et les nonces.
  • Le SRI (integrity + crossorigin) garantit qu'un fichier de CDN n'a pas été altéré.
  • L'iframe sandbox isole le contenu tiers ; ne combine pas allow-scripts et allow-same-origin sur du non fiable.
  • Sur les liens externes : rel="noopener noreferrer" contre le tabnabbing.
  • HTTPS, nosniff et frame-ancestors complètent la défense ; échappe toujours les données utilisateur avec textContent.
