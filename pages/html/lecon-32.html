Module 11 · Accessibilité experte — Leçon 32

Les patterns ARIA

~34 min Avancé Module 2 recommandé

À la fin de cette leçon, tu sauras

  • savoir appliquer la règle d'or d'ARIA (HTML natif d'abord, ARIA seulement en dernier recours) ;
  • savoir choisir les bons rôles, états (aria-expanded, aria-selected) et propriétés (aria-controls, aria-labelledby) ;
  • savoir baliser les patterns onglets, accordéon et modale avec ARIA ;
  • savoir décrire le comportement clavier attendu pour chaque pattern.
Sommaire de la leçon

Tu sais déjà écrire du HTML sémantique. Mais certains composants d'interface n'ont pas d'équivalent natif : onglets, accordéons, menus déroulants riches. Pour ces cas, le W3C définit des patterns ARIA — des combinaisons normalisées de rôles, d'états et de comportements clavier qui permettent à un lecteur d'écran de comprendre et d'annoncer correctement ton composant.

Le piège, c'est qu'ARIA est trompeusement simple à écrire et redoutablement facile à mal employer. Cette leçon te donne la règle d'or, le vocabulaire ARIA, puis trois patterns de référence (onglets, accordéon, modale) avec le clavier attendu pour chacun.

La règle d'or : le HTML natif d'abord

La première règle d'ARIA, c'est de ne pas utiliser ARIA. Si un élément HTML natif fait le travail, utilise-le : <button>, <a href>, <input type="checkbox">, <details>, <dialog>. Ils apportent gratuitement le rôle, l'état, le focus et le clavier.

Le point crucial à intégrer : ARIA ne change PAS le comportement. Ajouter role="button" sur une <div> ne la rend ni focusable, ni activable au clavier. ARIA ne modifie que ce qu'annonce le lecteur d'écran. Le focus (tabindex), les touches (Entrée, Espace, flèches) et la gestion d'état : c'est à toi de les coder en JavaScript.

Le natif te donne tout ; la div « button » te laisse tout faire à la main.

Astuce

Plusieurs exemples de cette leçon embarquent un <script> : clique sur « 👁 Aperçu » pour les voir vivre (changer d'onglet, ouvrir la modale) et tester le clavier directement dans l'iframe.

Note

ARIA s'utilise quand aucun élément natif n'existe pour le pattern voulu (onglets, par exemple), ou pour enrichir un widget existant avec un état dynamique (aria-expanded). Jamais pour « réparer » ce que le natif fait déjà mieux.

Rôles, états et propriétés

Le vocabulaire ARIA se range en trois familles. Le rôle dit ce qu'est l'élément : role="tab", role="dialog", role="tablist". Les états décrivent une condition dynamique, qui change pendant l'interaction : aria-expanded, aria-selected, aria-checked. Les propriétés décrivent des relations plus stables : aria-controls (quel élément ce widget pilote), aria-labelledby (quel élément sert d'étiquette).

aria-labelledby réutilise un texte déjà visible plutôt que de dupliquer le libellé.

Le pattern onglets (tabs)

Les onglets n'ont pas d'équivalent natif : c'est le cas d'usage type d'ARIA. La structure : un conteneur role="tablist" qui contient des role="tab" ; chaque onglet porte aria-selected et aria-controls vers son panneau ; chaque panneau porte role="tabpanel" et aria-labelledby vers son onglet.

Un seul onglet est tabbable (tabindex="0") ; les flèches naviguent entre eux. C'est le pattern « tabindex roving ».

Astuce

Sur l'aperçu de ce bloc, tu peux changer d'onglet à la souris, mais aussi cliquer un onglet puis utiliser les flèches gauche/droite. C'est exactement ce qu'un utilisateur de lecteur d'écran attend.

Le pattern accordéon

Un accordéon, c'est une suite de sections dépliables. Deux approches. La plus simple : <details>/<summary> natifs, qui gèrent l'état et le clavier seuls. L'approche ARIA, utile quand tu veux un contrôle total du style et du comportement : un <button aria-expanded> par en-tête, qui pilote la région via aria-controls.

Tant que tu n'as pas besoin de personnaliser le comportement, <details> est le meilleur choix.

Note

Place le <button> d'en-tête à l'intérieur d'un titre (<h3>) pour conserver la structure de titres : les lecteurs d'écran permettent de naviguer de titre en titre, et l'accordéon reste repérable dans le plan du document. La région, elle, est étiquetée par son bouton via aria-labelledby pour ne pas rester un repère anonyme.

Le pattern modale (dialog)

Pour une boîte de dialogue, préfère l'élément natif <dialog> (vu en leçon 2) : showModal() gère le rôle dialog, le mode modal, le piégeage du focus et la touche Échap. Tu n'utilises role="dialog" + aria-modal="true" que si tu ne peux pas employer <dialog>.

aria-labelledby pointe vers le titre : le lecteur d'écran annonce « Confirmer la suppression, dialogue » à l'ouverture.

Le clavier attendu, pattern par pattern

ARIA promet un comportement ; c'est ton JavaScript qui doit le tenir. Voici les attentes minimales :

  • Onglets : Tab entre dans la liste sur l'onglet actif puis en sort vers le panneau ; ←/→ changent d'onglet ; Entrée/Espace activent (si la sélection n'est pas automatique).
  • Accordéon : Tab entre/sort de chaque en-tête ; Entrée/Espace déplient/replient. (Le natif <details> le fait seul.)
  • Modale : Tab reste piégé à l'intérieur ; Échap ferme ; le focus revient sur l'élément déclencheur à la fermeture.

Cas réel

Ces patterns ne sont pas académiques : les bibliothèques de composants sérieuses (Radix UI, React Aria, Headless UI, le JS de Bootstrap) implémentent exactement les recettes de l'APG — rôles, états et clavier — pour t'éviter de les recoder. Et l'accessibilité est une obligation, pas une option : en France, le RGAA impose ces comportements clavier aux services publics et aux grandes entreprises ; aux États-Unis, une chaîne comme Domino's Pizza a perdu en justice (2019) parce que son site restait inutilisable au lecteur d'écran. Un widget « joli mais role sans clavier » échoue à tout audit.

Pièges fréquents

Piège fréquent

Mettre les rôles ARIA sans le comportement clavier. Un role="tablist" qui ne répond pas aux flèches est cassé pour l'utilisateur clavier : le lecteur d'écran annonce « onglet » mais rien ne se passe. Le rôle est une promesse ; tu dois la tenir en JS.

Piège fréquent

Les rôles redondants (role="button" sur un <button>, role="navigation" sur un <nav>) sont du bruit inutile. Et aria-label sur un élément qui a déjà du texte visible écrase ce texte pour le lecteur d'écran : tu désynchronises ce que l'utilisateur voit de ce qu'il entend. Enfin, réinventer une <div>-checkbox au lieu d'un <input> natif, c'est se créer des bugs gratuits.

Pour aller plus loin

Pour aller plus loin

La référence absolue est le WAI-ARIA Authoring Practices Guide (APG) : il donne, pour chaque pattern, la structure exacte et le clavier attendu, avec des exemples testables. Ne devine jamais un pattern ARIA : copie celui de l'APG. Pense aussi à tester au lecteur d'écran (NVDA, VoiceOver) — c'est le seul vrai test. Et la leçon suivante traite le focus management, indispensable pour des modales et menus vraiment utilisables.

Antisèche : rôles, états et clavier

Glossaire

ARIA
Accessible Rich Internet Applications : un jeu d'attributs qui décrit le rôle, l'état et les relations d'un composant aux technologies d'assistance.
Règle d'or
« Ne pas utiliser ARIA » : préférer un élément HTML natif chaque fois qu'il existe, car il apporte rôle, focus et clavier gratuitement.
Rôle
Ce qu'est un élément pour l'assistance (role="tab", role="dialog") ; il ne change pas le comportement, seulement l'annonce.
État vs propriété
Un état change pendant l'interaction (aria-expanded) ; une propriété décrit une relation stable (aria-controls, aria-labelledby).
aria-controls / aria-labelledby
Relient deux éléments par leur id : le premier désigne l'élément piloté, le second l'élément qui sert d'étiquette.
Tabindex roving
Technique où un seul élément d'un groupe porte tabindex="0" (les autres -1) : Tab n'y fait qu'un arrêt, les flèches déplacent le focus.
APG
WAI-ARIA Authoring Practices Guide : la référence qui donne, pour chaque pattern, la structure et le clavier exacts à copier.
Nom accessible
Le libellé qu'une technologie d'assistance annonce pour un élément ; aria-label le fixe mais écrase tout texte visible.

Récap et vérification

  • HTML natif d'abord ; ARIA uniquement quand aucun élément adapté n'existe.
  • ARIA ne change que l'annonce ; le focus et le clavier sont à ta charge en JS.
  • Onglets : tablist > tab (aria-selected, aria-controls) + tabpanel (aria-labelledby), navigation aux flèches.
  • Accordéon : <details> natif, ou <button aria-expanded> + aria-controls (région étiquetée par aria-labelledby).
  • Modale : <dialog> + showModal() ; sinon role="dialog" + aria-modal="true".

  2. Quels attributs relient un role="tab" à son role="tabpanel", dans les deux sens ?
