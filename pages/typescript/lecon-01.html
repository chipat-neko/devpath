Module 01 · Démarrer avec TypeScript — Leçon 01

Pourquoi TypeScript ?

~26 min Intermédiaire Cours JavaScript recommandé

À la fin de cette leçon, tu sauras

  • expliquer quel problème TypeScript résout par rapport à JavaScript ;
  • comprendre que TS est un sur-ensemble de JS et que tsc efface les types à la compilation ;
  • installer TypeScript, générer un tsconfig.json et compiler un fichier avec strict ;
  • distinguer une erreur de type (compilation) d'une erreur d'exécution.
Sommaire de la leçon

Tu écris du JavaScript moderne sans problème : fonctions, objets, async, modules. Mais tu as sûrement déjà vu une appli planter parce qu'on a passé une chaîne là où on attendait un nombre, ou parce qu'on a lu une propriété qui n'existait pas. En JavaScript, ce genre de faute ne se voit qu'au moment où le code tourne — parfois chez l'utilisateur, en production.

TypeScript répond exactement à ça : il ajoute au JavaScript un typage statique, vérifié avant l'exécution, directement dans ton éditeur. Dans cette leçon, on regarde le problème qu'il résout, comment il s'installe et se compile, et pourquoi tes types disparaissent du code final.

Le problème : les erreurs de type explosent à l'exécution

En JavaScript, rien ne t'empêche d'appeler une fonction n'importe comment. L'erreur n'arrive qu'au runtime, souvent trop tard.

Ces bugs ne se révèlent qu'en lançant le programme : parfois un NaN silencieux qui contamine un calcul, parfois un plantage net. TypeScript, lui, te les signale pendant que tu écris, avant même de lancer quoi que ce soit.

Cas réel

En analysant après coup des centaines de bugs corrigés en production, les équipes d'Airbnb ont estimé qu'environ 38 % d'entre eux auraient été évités par TypeScript : c'étaient des erreurs de type (propriété absente, valeur undefined, mauvais argument) que le compilateur aurait soulignées avant la mise en ligne. C'est ce genre de constat qui a poussé de grands projets — de Slack à VS Code lui-même — à basculer vers TypeScript.

TypeScript est un sur-ensemble de JavaScript

Bonne nouvelle : tu connais déjà presque tout TypeScript. Tout JavaScript valide est du TypeScript valide. Tu peux renommer un fichier .js en .ts et il fonctionne. On ajoute ensuite des types, progressivement, là où ça aide.

Le : number après le paramètre et après les parenthèses, c'est l'apport de TypeScript : on déclare que ce paramètre est un nombre, et que la fonction renvoie un nombre.

La compilation : tsc transforme le .ts en .js

Un navigateur ou Node.js ne sait pas lire un fichier .ts directement. Il faut le compiler (on dit aussi « transpiler ») en JavaScript avec l'outil tsc (TypeScript Compiler). Point crucial : pendant cette étape, les types sont effacés. On appelle ça le type erasure.

Les annotations : number servaient uniquement à la vérification. Une fois le contrôle passé, elles n'ont plus de raison d'être dans le code qui s'exécute.

Installer et lancer TypeScript

On installe TypeScript en dépendance de développement, puis on l'appelle avec npx.

Les trois commandes que tu utiliseras le plus au démarrage d'un projet.

npx tsc prix.ts compile un fichier isolé. En pratique, on configure plutôt le projet via tsconfig.json, et npx tsc seul compile alors tout le projet selon cette configuration.

Le tsconfig.json et l'option strict

npx tsc --init crée un fichier tsconfig.json qui pilote le compilateur. L'option la plus importante à connaître dès le début est strict.

strict: true active un ensemble de vérifications sévères : valeurs null/undefined traquées, paramètres jamais laissés avec un type implicite douteux, etc. C'est le mode recommandé : il attrape bien plus de bugs. Toutes les leçons de ce cours supposent strict activé.

Note

Sans strict, TypeScript reste permissif et laisse passer des cas dangereux. Active-le dès le premier jour : tu prendras les bons réflexes tout de suite plutôt que de devoir corriger plus tard.

L'inférence : TypeScript devine souvent le type

Tu n'as pas à tout annoter. TypeScript infère (déduit) le type à partir de la valeur que tu écris. Annoter devient utile surtout sur les paramètres de fonction, que le compilateur ne peut pas deviner seul.

La règle pratique : laisse l'inférence faire son travail quand elle suffit, et annote explicitement quand ça clarifie ton intention (notamment les paramètres et les valeurs de retour des fonctions publiques).

Où TypeScript « tourne »

TypeScript intervient à plusieurs endroits, mais jamais à l'exécution finale (qui, elle, exécute du JavaScript) :

  • L'éditeur (VS Code) te souligne les erreurs en temps réel et propose l'autocomplétion intelligente (IntelliSense).
  • Le build : tsc vérifie le projet et produit le JavaScript livré.
  • Les outils modernes (Vite, ts-node, Deno, Bun) savent gérer le TypeScript directement, ce qui simplifie le démarrage.

Astuce

Même sans rien compiler, ouvrir un fichier .ts dans VS Code te donne déjà la vérification de types et l'autocomplétion. C'est souvent là que tu verras tes erreurs en premier.

Pièges fréquents

Piège fréquent

Croire que les types existent à l'exécution. Ils sont effacés par tsc. Tu ne peux donc pas tester un type comme une valeur : il n'existe pas de if (x === number). À l'exécution, il n'y a que du JavaScript (et ses propres tests comme typeof x === "number").

Piège fréquent

Penser que TS te protège des données externes. Une réponse fetch ou un JSON.parse arrivent en any : TS te croit sur parole. Si tu annonces que c'est un number, il ne vérifie pas la donnée réelle. Pour ça, il faut une validation à l'exécution (on verra ça plus tard).

Piège fréquent

Confondre une erreur de type (détectée par tsc, à la compilation) et une erreur d'exécution (le programme plante en tournant). Tout l'intérêt de TS est de transformer le plus possible des secondes en premières.

Pour aller plus loin

Pour aller plus loin

Le mode strict regroupe plusieurs options que tu pourras explorer une à une. Le TypeScript Playground en ligne te permet d'essayer du code et de voir le JS produit sans rien installer. ts-node, Deno et Bun exécutent du TypeScript directement, et l'IntelliSense de ton éditeur s'appuie sur les types pour t'autocompléter.

Antisèche

Glossaire

Typage statique
Vérification des types avant l'exécution (à la compilation), par opposition au typage dynamique de JavaScript qui ne se manifeste qu'au runtime.
Sur-ensemble
Langage qui en contient entièrement un autre : tout JavaScript valide est un TypeScript valide, TS n'ajoutant qu'une couche de types.
tsc
TypeScript Compiler : l'outil qui vérifie les types puis transforme (transpile) le .ts en .js.
Transpilation
Traduction d'un langage vers un autre de même niveau (ici TS → JS), à distinguer d'une compilation vers du code machine.
Type erasure
Effacement des annotations de type lors de la compilation : elles ne servent qu'au contrôle et n'existent pas dans le JavaScript exécuté.
Inférence
Capacité du compilateur à déduire seul le type d'une valeur (let n = 3 → number), ce qui évite d'annoter l'évident.
tsconfig.json
Fichier de configuration qui pilote le compilateur (cible, modules, options de rigueur) pour tout le projet.
strict
Option regroupant les vérifications les plus sévères (dont le suivi de null/undefined) ; recommandée dès le départ.

Récap et vérification

  • TypeScript ajoute un typage statique vérifié avant l'exécution : les erreurs de type se voient dans l'éditeur.
  • TS est un sur-ensemble de JS : tout JS valide est du TS valide ; on ajoute les types progressivement.
  • tsc compile le .ts en .js et efface les types (type erasure) : ils n'existent pas à l'exécution.
  • On installe avec npm install -D typescript, on configure avec npx tsc --init, et on active strict: true.
  • L'inférence devine souvent le type : on n'annote pas tout, surtout pas ce qui est évident.

  2. Que deviennent les annotations de type une fois le fichier compilé en JavaScript ?
  3. Pourquoi peut-on dire que « tout JavaScript valide est déjà du TypeScript » ?
