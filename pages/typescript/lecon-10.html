Module 03 · TypeScript en pratique — Leçon 10

TypeScript au quotidien

~35 min Intermédiaire Leçon 9 recommandée

À la fin de cette leçon, tu sauras

  • savoir migrer un projet JS vers TS progressivement avec allowJs puis le mode strict ;
  • savoir valider des données externes (fetch/JSON) à la frontière au lieu de faire confiance à un as ;
  • savoir lire et corriger les erreurs fréquentes du compilateur (« not assignable », « possibly undefined ») ;
  • savoir mettre en place l'outillage (ESLint, tsc --noEmit en CI) et éviter les pièges du quotidien.
Sommaire de la leçon

Tu connais maintenant les briques de TypeScript : les types de base, les unions, les interfaces, les génériques. Mais entre « je sais annoter une fonction » et « j'utilise TS sereinement sur un vrai projet », il reste un fossé. Cette leçon le comble : comment migrer du JavaScript existant, comment empêcher TS de te mentir sur des données réseau, comment lire les erreurs du compilateur sans paniquer, et quel outillage installer pour que le typage te protège vraiment.

Le fil rouge : TypeScript n'a de valeur que s'il reflète la réalité. Un type qui ment est pire qu'une absence de type, car il te donne une fausse confiance. Tout l'enjeu du quotidien, c'est de garder l'écart entre « ce que TS croit » et « ce qui se passe à l'exécution » aussi proche de zéro que possible.

Migrer un projet JS vers TS, progressivement

Bonne nouvelle : tu n'as pas à tout réécrire d'un coup. TypeScript est conçu pour cohabiter avec du JavaScript. La stratégie gagnante est incrémentale.

Première étape : installer TS et générer une configuration, en autorisant les fichiers .js à coexister.

Ensuite, tu renommes un fichier à la fois de .js en .ts, tu corriges les erreurs qui apparaissent, et tu passes au suivant. À la fin, tu actives "strict": true et tu nettoies les dernières alertes. Viser strict dès le départ sur une grosse base existante te noie sous des centaines d'erreurs : le progressif gagne.

Astuce

Active "checkJs": true sur quelques fichiers .js stratégiques avant même de les renommer : TS lit alors les commentaires JSDoc et t'indique les premiers problèmes. C'est une mise en jambe sans changer l'extension.

Préférer l'inférence, fuir any

Le réflexe de débutant, c'est de tout annoter. Or TypeScript infère souvent mieux que toi. Annote ce qui éclaire (les frontières : paramètres de fonction, retours publics, formes de données) et laisse l'inférence faire le reste.

L'autre réflexe à combattre : any. Il désactive tout contrôle de type sur la valeur, et la contamination se propage. Active noImplicitAny (inclus dans strict) pour que TS refuse les any implicites.

Quand tu ignores la forme d'une valeur, préfère unknown à any : il force un contrôle explicite avant usage. Le bug avec any est sournois car il ne crie pas : il renvoie undefined en silence et casse plus loin.

Modéliser les données par des types et des unions

Un bon projet TS commence par décrire ses données. Les unions discriminées rendent les états impossibles… impossibles à écrire.

Le compilateur affine (narrowing) le type dans chaque branche du switch : tu n'accèdes jamais à donnees dans la branche « erreur ». La forme des données guide le code.

Données externes : le danger du as non vérifié

Voici le piège le plus coûteux du quotidien. Un fetch renvoie du JSON dont TS ne connaît rien : à l'exécution, c'est any déguisé. La tentation est de plaquer un type avec as.

Le as ne vérifie rien : il force TS à te croire. Sur des données réseau, c'est une bombe à retardement. La solution : valider à la frontière, là où la donnée entre dans ton programme, avec un type guard qui contrôle vraiment la forme.

Le prédicat v is Utilisateur indique à TS : « si cette fonction renvoie true, alors la valeur a bien cette forme ». Désormais le type reflète la réalité, parce qu'on l'a vérifiée. Pour des schémas plus gros, une bibliothèque comme zod génère ces contrôles (et le type) pour toi — voir « Pour aller plus loin ».

Cas réel

Bug d'application mobile devenu un cas d'école : l'API renvoyait le prix tantôt en nombre (19.9), tantôt en chaîne ("19.9") selon la route. Le code faisait const p = data as Produit puis p.prix.toFixed(2) — qui explose sur une chaîne. Comme le build passait (le as ne vérifie rien), le crash n'est apparu qu'en production, sur certains écrans seulement. Correctif : un schéma de validation à la frontière qui normalise le prix en number dès l'entrée. Règle d'équipe depuis : aucune donnée réseau n'entre sans être validée.

TS avec React et avec Node

Sur le terrain, TS sert surtout aux frontières de tes outils. Côté React (revois le cours React), tu types les props et l'état : l'éditeur t'autocomplète et signale un prop manquant ou mal typé.

Côté Node (revois le cours Node.js), tu types les entrées/sorties d'une route d'API : le corps de la requête validé, la réponse renvoyée. Même principe qu'au-dessus — on valide ce qui vient du client avant de s'en servir.

Note

Pour Node, installe les types de la plateforme : npm i -D @types/node. Beaucoup de bibliothèques JS sans types intégrés ont un paquet @types/… correspondant publié par la communauté.

Lire les erreurs fréquentes du compilateur

Les messages de tsc font peur au début, mais ils suivent des schémas. Apprends à lire les deux plus courants.

« not assignable » se lit de gauche à droite : la valeur fournie, puis le type attendu. « possibly undefined » signale une valeur qui peut manquer : ajoute une vérification ou une valeur par défaut. Ne contourne pas l'erreur — elle pointe un vrai cas que ton code ignorait.

Outillage : strict, ESLint et la CI

Trois réglages transforment TS d'aide ponctuelle en filet de sécurité permanent.

  • Mode strict : "strict": true dans tsconfig.json. C'est lui qui active noImplicitAny, les contrôles de null/undefined, et l'essentiel de la valeur de TS.
  • ESLint + TS : typescript-eslint ajoute des règles spécifiques (interdire any, signaler les promesses non attendues) en complément du compilateur.
  • tsc --noEmit en CI : tu fais vérifier les types à chaque push, sans produire de build. Une erreur de type bloque la fusion.

Cette commande type-vérifie tout le projet sans générer de fichiers : idéale dans une pipeline.

Pourquoi l'effort en vaut la peine

Sur un vrai projet, TS rembourse vite son coût. Refactors sûrs : renomme un champ, le compilateur liste tous les endroits à corriger. Autocomplétion : ton éditeur connaît la forme exacte des objets. Documentation vivante : les types décrivent les intentions et ne se désynchronisent jamais du code, contrairement à un commentaire. Plus le projet grandit et plus l'équipe est nombreuse, plus ce filet devient précieux.

Pièges fréquents

Piège fréquent

Tout typer en any « pour avancer ». Chaque any est une dette : il éteint le typage autour de lui et reviendra sous forme de bug en production. Préfère unknown et un contrôle, ou prends le temps de modéliser.

Piège fréquent

Faire confiance à un as sur des données réseau. as ne vérifie rien à l'exécution : il affirme un type sans le prouver. Valide toujours à la frontière (type guard ou zod) avant d'utiliser une réponse JSON.

Piège fréquent

Désactiver strict ou masquer une erreur avec // @ts-ignore. Tu ne corriges rien : tu caches le symptôme. Lis l'erreur, comprends-la, traite la cause. Si tu dois vraiment ignorer, // @ts-expect-error avec un commentaire est moins risqué (il s'efface si l'erreur disparaît).

Antisèche

Glossaire

Migration incrémentale
Passage progressif de JS à TS, fichier par fichier (allowJs), en durcissant la config jusqu'à strict.
Inférence
Capacité du compilateur à déduire un type sans annotation ; on n'annote que les frontières (paramètres, retours, formes de données).
unknown
Type « valeur inconnue » qui, contrairement à any, force un contrôle explicite avant tout usage.
Type guard
Fonction à prédicat v is T qui prouve la forme d'une valeur à l'exécution et l'affine pour le compilateur.
Assertion (as)
Affirmation de type non vérifiée : TypeScript te croit sans contrôler ; dangereuse sur des données externes.
Union discriminée
Union d'objets distingués par un champ commun (statut), qui rend les états invalides impossibles à écrire.
Narrowing (affinement)
Réduction automatique d'un type par le compilateur dans une branche (if, switch, typeof, type guard).
Validation à la frontière
Contrôle des données au point où elles entrent dans le programme (réseau, formulaire, fichier), avant de les typer.

Récap et vérification

  • Migre du JS au TS fichier par fichier avec allowJs, puis active strict à la fin.
  • Préfère l'inférence, fuis any (active noImplicitAny), utilise unknown + contrôle quand la forme est inconnue.
  • Modélise les données avec des unions discriminées pour rendre les états invalides impossibles.
  • Valide à la frontière les données externes (type guard ou zod) au lieu de plaquer un as.
  • Lis les erreurs : « not assignable » (valeur → type attendu), « possibly undefined » (gère le cas absent).
  • Outille : strict, ESLint TS, et tsc --noEmit en CI.

Vérifie ta compréhension

  1. Pourquoi un as Utilisateur sur une réponse fetch ne te protège-t-il pas, alors qu'un type guard, oui ?
  2. Que change concrètement "strict": true, et pourquoi l'activer à la fin d'une migration plutôt qu'au début ?
  3. Tu lis « Object is possibly 'undefined' » sur le résultat d'un .find(). Quelle est la cause, et comment la corriger proprement ?
