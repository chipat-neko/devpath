Module 03 · TypeScript en pratique — Leçon 09

Modules, déclarations et configuration

~35 min Intermédiaire Leçon 8 recommandée

À la fin de cette leçon, tu sauras

  • savoir exporter et importer valeurs et types, et utiliser import type pour les types effacés à la compilation ;
  • savoir lire et régler un tsconfig.json (strict, target, module, outDir) ;
  • savoir écrire un fichier de déclaration .d.ts minimal et installer les types d'une lib via @types/* ;
  • savoir pourquoi un bundler ne vérifie pas les types et utiliser tsc --noEmit comme garde-fou.
Sommaire de la leçon

Jusqu'ici tu as écrit du TypeScript dans des fichiers isolés. Mais un vrai projet, c'est plusieurs fichiers qui se parlent, des bibliothèques installées via npm, et une configuration qui décide à quel point le compilateur est sévère. Cette leçon montre comment organiser ce tout : comment partager du code et des types entre fichiers, comment régler tsconfig.json, comment décrire du JavaScript existant, et comment TypeScript s'insère dans une chaîne d'outils moderne.

Tu connais déjà les modules ES en JavaScript (export / import). En TypeScript, le mécanisme est le même — mais il transporte aussi des types, qui disparaissent à la compilation. C'est de là que partent la plupart des subtilités. Commençons par là.

Exporter et importer : valeurs ET types

En TypeScript, un module peut exporter des valeurs (fonctions, constantes, classes) et des types (interfaces, alias). La syntaxe est identique à celle de JavaScript ; un type s'exporte exactement comme une valeur.

Une seule ligne d'import peut mélanger une valeur (greet) et un type (User).

Remarque le mot-clé type devant User dans l'import : il dit au compilateur que User n'est qu'un type. Voyons pourquoi c'est utile.

import type : un type effacé à la compilation

Les types n'existent qu'au moment de la vérification : une fois compilé en JavaScript, il n'en reste rien. Pour rendre cela explicite, TypeScript propose import type, qui n'importe que des types. À la compilation, cet import disparaît entièrement.

import type garantit zéro impact à l'exécution : aucun module n'est chargé pour ce seul type.

Astuce

Tu peux aussi écrire le préfixe par membre : import { greet, type User } from "./user". Pratique quand tu mélanges valeurs et types dans le même import. L'option verbatimModuleSyntax du tsconfig oblige même à marquer explicitement chaque import de type, ce qui évite toute ambiguïté.

Les fichiers de déclaration .d.ts

Imagine que tu utilises un petit fichier JavaScript écrit il y a longtemps, sans types. TypeScript ne sait pas ce qu'il contient. Un fichier de déclaration .d.ts sert à décrire les types d'un code existant, sans le réécrire. Il ne contient que des signatures, pas d'implémentation — d'où le mot-clé declare.

Un .d.ts du même nom, dans le même dossier, fournit les types ; declare signale « le code existe ailleurs, voici juste sa forme ».

Désormais, importer distance donne de l'autocomplétion et la vérification des arguments, alors que le code exécuté reste le JavaScript d'origine.

Les types des bibliothèques : @types/*

Beaucoup de paquets npm modernes livrent leurs propres types (un .d.ts est inclus) : tu installes, ça marche. Mais certaines libs JavaScript anciennes n'en ont pas. La communauté maintient alors des paquets de types séparés sous le préfixe @types/, hébergés sur le dépôt DefinitelyTyped.

Si l'import d'une lib provoque « could not find a declaration file », cherche un paquet @types/<nom>.

Note

Les @types/* vont dans devDependencies : ce sont des types, ils n'existent qu'au développement et disparaissent du bundle final. Pas besoin de les expédier en production.

Typer process.env et les imports non-code

Côté Node, process.env.MA_VAR est typé string | undefined : TypeScript ne sait pas si la variable est définie. C'est volontairement prudent — à toi de gérer le cas absent.

Pour les imports qui ne sont pas du code (une image, du CSS, du JSON via un bundler), TypeScript a besoin d'une déclaration de module pour ne pas se plaindre. C'est un autre usage de .d.ts.

Sans cette déclaration, import logo from "./logo.svg" déclenche une erreur de type.

declare global et augmentation de modules (survol)

Parfois tu dois ajouter un type à quelque chose qui existe déjà : une propriété globale, ou un champ supplémentaire sur un type fourni par une lib. C'est l'augmentation de module. À connaître de loin, à utiliser avec parcimonie.

L'augmentation étend des types existants ; garde-la pour les cas où tu ne peux pas faire autrement.

La chaîne d'outils : tsc vs bundlers

Point crucial, souvent mal compris. tsc fait deux choses : il vérifie les types et il compile en JavaScript. Les bundlers modernes (Vite, esbuild, swc) sont rapides parce qu'ils ne font que transpiler : ils retirent les types et produisent du JS, sans vérifier. Un code plein d'erreurs de types peut donc se construire sans broncher.

tsc --noEmit vérifie l'ensemble du projet sans écrire de JS : la commande idéale en intégration continue (CI).

La bonne pratique : laisser le bundler produire le code rapidement en développement, et lancer tsc --noEmit en CI (ou en script lint:types) pour bloquer toute erreur de type avant la fusion.

Cas réel

La mésaventure est un classique d'équipe : le site se construit et se déploie sans broncher (le bundler ne vérifie pas les types), mais un champ renommé nom → name a laissé un u.nom oublié ailleurs. En production : écran blanc. Depuis, l'étape tsc --noEmit tourne en intégration continue à chaque Pull Request : impossible de fusionner tant qu'un type ne colle pas. Leçon retenue : le typage ne protège vraiment que branché à la CI ; sinon ce n'est qu'une aide d'éditeur qu'on peut ignorer.

Pièges fréquents

Piège fréquent

Importer une lib JavaScript sans ses types : « Could not find a declaration file for module 'x' ». Solution : installer @types/x s'il existe, sinon écrire un .d.ts minimal pour la décrire.

Piège fréquent

Croire que « ça build, donc les types sont bons ». Le bundler transpile, il ne vérifie pas. Sans tsc --noEmit, des erreurs de type passent en production. Et n'oublie pas : un tsconfig avec strict: false laisse passer les null et bien d'autres bugs — garde strict: true.

Glossaire

Module ES
Fichier qui expose (export) et consomme (import) des valeurs et des types ; l'unité d'organisation d'un projet moderne.
import type
Import réservé aux types ; entièrement supprimé à la compilation, sans chargement de module à l'exécution.
tsconfig.json
Fichier de configuration du compilateur à la racine du projet (strict, target, module, outDir…).
strict
Réglage qui active en bloc les vérifications sévères, dont strictNullChecks et noImplicitAny ; le plus important à laisser à true.
Fichier de déclaration (.d.ts)
Fichier ne contenant que des signatures (via declare) pour décrire les types d'un code existant ou d'imports non-code.
@types · DefinitelyTyped
Dépôt communautaire de paquets de types (@types/lodash…) pour les bibliothèques JavaScript qui n'embarquent pas les leurs.
Transpilation
Traduction du TS en JS en retirant les types sans les vérifier ; ce que font les bundlers rapides (Vite, esbuild).
tsc --noEmit
Commande qui type-vérifie tout le projet sans écrire de fichier ; le garde-fou à lancer en intégration continue.

Récap et vérification

  • Les modules ES transportent valeurs et types ; import type n'importe qu'un type, effacé à la compilation.
  • tsconfig.json pilote le compilateur : strict, target, module, outDir, rootDir.
  • Un .d.ts décrit (via declare) les types d'un code JS ou d'imports non-code, sans implémentation.
  • Les libs non typées se complètent avec @types/* (DefinitelyTyped) ; beaucoup livrent déjà leurs types.
  • Les bundlers transpilent sans vérifier : tsc --noEmit reste le garde-fou des types, idéal en CI.

Vérifie ta compréhension

  1. Quelle différence concrète, dans le JavaScript généré, entre import { User } et import type { User } ?

  3. Tu lances vite build sans erreur, mais ton code a un bug de type. Pourquoi, et quelle commande l'aurait détecté ?
