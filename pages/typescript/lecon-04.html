Module 02 · Le système de types — Leçon 04

Unions, littéraux et affinage (narrowing)

~36 min Intermédiaire Leçon 3 recommandée

À la fin de cette leçon, tu sauras

  • déclarer des types union (string | number) et des types littéraux précis ;
  • affiner un type avec les gardes typeof, instanceof, in et le test de vérité ;
  • modéliser des données avec une union discriminée et la parcourir dans un switch ;
  • écrire un type guard personnalisé et garantir l'exhaustivité avec never.
Sommaire de la leçon

En JavaScript, une variable accueille n'importe quoi : une fonction peut recevoir un identifiant tantôt sous forme de number, tantôt sous forme de string, et tu gères ça à coups de typeof. TypeScript ne t'oblige pas à abandonner cette souplesse : il te demande juste de la décrire. C'est exactement le rôle des unions.

Dans cette leçon, tu vas apprendre à dire « cette valeur est l'un OU l'autre », à réduire l'ensemble des possibles à une liste précise, puis à laisser le compilateur restreindre le type au fil de ton code. C'est ce mécanisme — le narrowing — qui rend le typage agréable plutôt que pénible.

Les unions : l'une OU l'autre

Une union combine plusieurs types avec une barre verticale |. La valeur appartient alors à l'un d'entre eux, sans qu'on sache lequel à l'avance. Conséquence directe : tant que tu n'as pas tranché, TypeScript n'autorise que ce qui fonctionne pour tous les membres.

Sur une union, seuls les membres communs à tous les types sont accessibles sans précaution.

Les types littéraux : un ensemble fini de valeurs

Un type peut être une valeur précise, pas seulement string. "haut" est un type qui n'accepte que la chaîne "haut". Combinés en union, les littéraux décrivent un ensemble fermé de possibilités.

Un type littéral verrouille les valeurs autorisées dès l'écriture du code.

Astuce

Une union de littéraux remplace avantageusement un enum dans la plupart des cas : elle est plus légère, n'ajoute aucun code à l'exécution et se manipule comme de simples chaînes.

Le narrowing : restreindre selon le contexte

Le narrowing (affinage) est le cœur du sujet : à l'intérieur d'un if ou d'un switch, TypeScript déduit un type plus précis que celui déclaré. Tu écris du JavaScript ordinaire, et le compilateur suit ton raisonnement de branche en branche.

Le test typeof réduit l'union dans chaque branche ; ce qui reste après le return est aussi affiné.

Plusieurs gardes existent selon ce que tu testes :

Quatre gardes : typeof, instanceof, le test de vérité et in.

Note

Le test de vérité écarte aussi "" et 0, pas seulement null et undefined. Pour ne filtrer que le « vide » sans rejeter la chaîne vide ou zéro, compare explicitement : if (nom != null).

Les unions discriminées

Voici le pattern le plus important pour modéliser des données. Chaque variante partage un champ commun — un discriminant — dont la valeur est un littéral différent. TypeScript s'en sert pour distinguer les cas automatiquement.

Le champ type littéral aiguille le compilateur dans chaque case.

Sans le discriminant, TS ne saurait pas quelle propriété est disponible. Avec lui, accéder à forme.rayon hors du bon case devient une erreur — exactement la protection recherchée.

Cas réel

L'état d'un chargement de données (appel réseau) se modélise idéalement en union discriminée : { statut: "chargement" } | { statut: "succes"; donnees: Article[] } | { statut: "erreur"; message: string }. Impossible alors de lire donnees tant qu'on n'a pas vérifié statut === "succes" : le compilateur interdit d'afficher un contenu qui n'existe pas encore. Ce modèle remplace le trio fragile de booléens isLoading / hasError / data, qui laisse passer des états incohérents (chargement et erreur en même temps). Bonus : ajouter plus tard une variante "annule" et oublier de la traiter déclenche l'erreur never — le compilateur te rappelle chaque écran à mettre à jour.

Les type guards personnalisés

Quand un test ne se résume pas à typeof ou in, tu peux écrire ta propre garde : une fonction dont le type de retour est un prédicat x is Type. TypeScript la croit sur parole et affine en conséquence.

Le retour x is string transmet l'affinage au-delà de la fonction.

Note

Un type guard est une promesse. TypeScript ne vérifie pas que ta logique correspond vraiment au prédicat : si tu annonces x is string mais testes autre chose, le compilateur te fera confiance à tort. À toi d'être honnête.

never et la vérification d'exhaustivité

Le type never représente « une valeur qui ne peut pas exister ». Dans le default d'un switch sur une union discriminée, il sert de filet : si tu ajoutes une variante sans traiter son cas, le code ne compile plus.

Affecter la valeur restante à never transforme un oubli en erreur de compilation.

Pièges fréquents

Piège fréquent

Accéder à une propriété propre à une variante avant d'avoir discriminé : sur une Forme non affinée, forme.rayon échoue car Carre n'a pas de rayon. Discrimine d'abord (if/switch), accède ensuite.

Trois autres erreurs reviennent souvent :

  • Oublier un cas dans un switch. Sans le garde-fou never, l'oubli passe inaperçu. Ajoute systématiquement le default exhaustif.
  • Un type guard qui ment. Si le prédicat annonce x is string mais que la logique teste autre chose, TS affine faux et le bug surgit à l'exécution.
  • Confondre union et intersection. A | B signifie « A OU B » (moins de propriétés garanties) ; A & B signifie « A ET B » (toutes les propriétés des deux). L'union restreint, l'intersection cumule.

Glossaire

Union (|)
Type « l'un OU l'autre » : A | B. Seules les opérations communes à tous les membres sont accessibles avant affinage.
Type littéral
Type limité à une valeur précise ("haut", 42, true) plutôt qu'à tout un type comme string.
Narrowing (affinage)
Réduction, par le compilateur, d'un type large à un type plus précis à l'intérieur d'une branche de code.
Union discriminée
Union de formes qui partagent un champ commun à valeur littérale (le discriminant), permettant de les distinguer sûrement.
Discriminant
Le champ littéral commun (souvent nommé type ou kind) sur lequel on aiguille un switch.
Type guard
Test (intégré ou personnalisé) qui affine un type dans une branche ; un guard perso a un retour x is T.
Prédicat de type
La signature de retour x is T d'un type guard : elle transmet l'affinage au code appelant.
never
Type « valeur impossible ». Affecter le cas restant à never force à traiter toutes les variantes (exhaustivité).

Récap et vérification

  • Une union A | B dit « l'un ou l'autre » ; seuls les membres communs sont accessibles directement.
  • Les types littéraux verrouillent un ensemble fini de valeurs précises, souvent mieux qu'un enum.
  • Le narrowing affine le type via typeof, instanceof, le test de vérité et in.
  • Une union discriminée (champ type littéral) se parcourt sûrement dans un switch.
  • Un type guard x is Type propage l'affinage ; never garantit l'exhaustivité.

Vérifie ta compréhension

  1. Sur une valeur de type string | number, pourquoi .toUpperCase() est-il refusé tant qu'on n'a pas affiné ?
  2. Quel garde utilises-tu pour distinguer une instance de classe d'un autre type ?
  3. À quoi sert d'assigner la variable restante à never dans le default d'un switch ?
