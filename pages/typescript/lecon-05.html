Module 02 · Le système de types — Leçon 05

Typer les fonctions

~35 min Intermédiaire Leçon 4 recommandée

À la fin de cette leçon, tu sauras

  • savoir annoter les paramètres et le type de retour d'une fonction, y compris les fonctions fléchées ;
  • savoir décrire le type d'une fonction comme valeur et gérer les paramètres optionnels, par défaut et rest ;
  • savoir utiliser void, unknown et never en position de retour ;
  • savoir écrire des surcharges et typer le paramètre this.
Sommaire de la leçon

En JavaScript, une fonction accepte n'importe quoi : tu peux appeler aire("cercle") sans broncher, et le bug n'apparaît qu'à l'exécution. TypeScript te laisse écrire un contrat sur chaque fonction : voici les types que j'accepte en entrée, voici ce que je rends en sortie. Le compilateur vérifie ce contrat avant même que le code tourne.

Dans cette leçon, tu vas apprendre à annoter une fonction de bout en bout : ses paramètres, son retour, et même la fonction elle-même vue comme une valeur. On part de ce que tu connais déjà en JS et on ajoute juste ce qu'il faut de typage.

Paramètres et type de retour

La syntaxe de base ajoute un type après chaque paramètre (nom: type) et un type après les parenthèses, pour le retour.

Le type de retour : number est vérifié : si tu écrivais return "rond", le compilateur refuserait.

La même chose marche pour une fonction fléchée. On annote les paramètres, et le retour soit explicitement, soit en laissant l'inférence faire.

Astuce

Laisse TypeScript inférer le retour quand c'est évident, mais annote-le explicitement sur les fonctions exportées d'une bibliothèque : ça documente l'intention et fige le contrat.

Le type d'une fonction comme valeur

En JS, une fonction est une valeur : on la passe en argument (callback), on la stocke dans une variable. En TypeScript, cette valeur a un type de fonction, qu'on écrit avec une flèche.

Une fois la variable typée Operation, tu n'as plus besoin d'annoter a et b : ils sont déduits du contrat. C'est le typage contextuel. Et un callback qui prend moins de paramètres que prévu est accepté — comme en JS, où rien ne t'oblige à lire tous les arguments.

Optionnels, valeurs par défaut et rest

Trois besoins courants en JS ont chacun leur syntaxe typée.

Piège fréquent

Un paramètre optionnel x?: number peut être omis à l'appel. Une union x: number | undefined autorise la valeur undefined, mais l'argument reste obligatoire : tu dois écrire fn(undefined) explicitement. Ce n'est pas la même chose.

void en retour et le cas des callbacks

Une fonction qui ne renvoie rien d'utile a le type de retour void. C'est le cas de console.log ou d'un gestionnaire d'événement.

Subtilité utile : quand void décrit le retour d'un callback, il signifie « je vais ignorer ce que tu renvoies », pas « tu dois renvoyer undefined ». C'est ce qui permet de passer arr.push à forEach sans erreur.

Cas réel

Dès que tu utilises une bibliothèque, ce sont ses fichiers de déclaration (.d.ts) qui typent les fonctions que tu lui passes. bouton.addEventListener("click", gerer) attend un gerer: (e: MouseEvent) => void : écris (e: number) et l'erreur tombe aussitôt ; et comme le retour est void, tu peux passer une fonction qui renvoie quelque chose sans souci. Idem pour [3, 1, 2].sort(comparer), où comparer doit être (a: number, b: number) => number. Ces signatures précises — fournies par TypeScript (la lib DOM) ou par les paquets @types/* — transforment un mauvais callback en erreur de compilation plutôt qu'en bug d'exécution.

Piège fréquent

Ne sois pas trop strict sur le retour d'un callback. Si tu écris (n: number) => undefined au lieu de => void, tu refuses tous les callbacks qui renvoient autre chose, alors que tu comptais juste ignorer leur résultat.

Les surcharges (overloads)

Parfois une fonction se comporte différemment selon le type des arguments. Tu peux déclarer plusieurs signatures au-dessus d'une seule implémentation : ce sont les surcharges.

Le retour est précis pour chaque cas : a est string, b est number[] — pas l'union floue.

Piège fréquent

Ordonne les surcharges de la plus spécifique à la plus large. TypeScript retient la première signature qui correspond ; une signature trop générale placée en tête masquerait les suivantes.

Typer this

Dans une fonction classique, this dépend de la façon dont la fonction est appelée. TypeScript te laisse déclarer un paramètre this fictif en première position : il n'existe pas à l'exécution, il sert juste à vérifier le contexte.

unknown et never en retour

Deux types spéciaux apparaissent parfois en position de retour. unknown dit « je rends quelque chose, mais tu devras vérifier son type avant de l'utiliser ». never dit « cette fonction ne rend jamais la main normalement » (elle lance une erreur ou boucle indéfiniment).

Pour aller plus loin

Les fonctions génériques (leçon 6) permettent de typer une fonction qui marche pour plusieurs types tout en gardant un lien précis entrée/sortie, par ex. identite<T>(x: T): T — bien plus fin que unknown.

Les fonctions génériques (teaser)

Si tu écris une fonction qui doit renvoyer exactement le type qu'on lui donne, ni unknown ni une surcharge ne suffisent : il te faut une variable de type. C'est l'objet de la prochaine leçon.

Pièges fréquents

  • Oublier le type de retour sur une API publique. L'inférence peut renvoyer un type plus large ou plus étroit que prévu ; annoter explicitement protège tes appelants d'un changement silencieux.
  • Confondre x?: T et x: T | undefined. Le premier rend l'argument facultatif, le second le garde obligatoire.
  • Mal ordonner les surcharges. Du plus spécifique au plus large, sinon une signature large « avale » les cas précis.
  • Annoter un callback avec un retour trop strict. Préfère => void quand tu ignores le résultat, plutôt que => undefined.

Pour aller plus loin

Pour aller plus loin

TypeScript fournit des utilitaires qui extraient le type des fonctions : Parameters<T> donne le tuple des paramètres, ReturnType<T> donne le type de retour. Avec Operation ci-dessus, ReturnType<Operation> vaut number. Tu croiseras aussi les assertions de fonction (asserts x is T) et les fonctions d'ordre supérieur lourdement typées dans les bibliothèques.

Antisèche

Glossaire

Annotation de type
Le : type ajouté à un paramètre ou après les parenthèses pour fixer ce que la fonction accepte et renvoie.
Type de retour
Type de la valeur rendue par la fonction, placé après les parenthèses ; souvent inférable, à annoter sur une API publique.
Inférence
Déduction automatique d'un type par le compilateur (ici, le retour ou les paramètres d'un callback contextuel).
Paramètre optionnel
Paramètre marqué ?, qui peut être omis à l'appel — à distinguer d'un paramètre T | undefined obligatoire.
Paramètre rest
Écriture ...xs: T[] captant un nombre variable d'arguments dans un tableau typé.
Type de fonction
Type-valeur écrit avec une flèche (a: T) => R ; idéal pour typer un callback.
void
Retour « sans valeur utile ». En position de callback, il signifie « le résultat sera ignoré », pas « renvoie undefined ».
Surcharge (overload)
Plusieurs signatures publiques au-dessus d'une implémentation, pour un retour précis selon les arguments ; ordre du plus spécifique au plus large.

Récap et vérification

  • On annote chaque paramètre (nom: type) et le retour après les parenthèses ; l'inférence suffit souvent pour le retour.
  • Une fonction a un type-valeur écrit avec une flèche : (a: number, b: number) => number, idéal pour les callbacks.
  • x?: T (optionnel), x = v (par défaut) et ...xs: T[] (rest) couvrent les arités variables.
  • void = pas de retour utile (et tolérant pour les callbacks) ; unknown = à vérifier ; never = ne revient jamais.
  • Les surcharges donnent un retour précis selon les arguments ; le paramètre this fictif sécurise le contexte.

Vérifie ta compréhension

  1. Quelle différence concrète y a-t-il entre titre?: string et titre: string | undefined au moment de l'appel ?
  2. Pourquoi peut-on passer un callback qui renvoie un number là où le type attend (n: number) => void ?
  3. Dans quel ordre place-t-on deux surcharges, et pourquoi cet ordre compte-t-il ?
