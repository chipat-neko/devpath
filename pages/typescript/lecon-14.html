Module 05 · TypeScript appliqué — Leçon 14

TypeScript avec React

~40 min Intermédiaire Bases de React utiles

À la fin de cette leçon, tu sauras

  • typer les props d'un composant ;
  • typer useState, useRef et les événements ;
  • typer children et les composants génériques ;
  • éviter les pièges courants de React + TS.
Sommaire de la leçon

TypeScript + React est aujourd'hui le duo standard du développement front. Toute la documentation, les bibliothèques et les offres d'emploi le supposent. Pourtant, beaucoup apprennent React en JavaScript pur, puis butent sur le typage des composants. Cette leçon comble ce pont : comment typer proprement props, état, références et événements. On écrit du TSX (du JSX typé), dans des fichiers .tsx.

Le bénéfice est immédiat : l'éditeur connaît tes composants, autocomplète les props, et signale une erreur si tu oublies un champ ou te trompes de type — avant d'ouvrir le navigateur.

Typer les props

Les props d'un composant se décrivent par un type (ou une interface). Le composant est une fonction qui reçoit cet objet typé.

L'objet de props est typé : utiliser <Bouton /> sans libelle, ou avec une variante inconnue, devient une erreur de compilation. Les unions de littéraux ("primaire" | "secondaire") garantissent qu'on ne passe qu'une valeur prévue.

Typer l'état : useState

useState infère souvent le type depuis la valeur initiale. Mais dès que l'état peut être null ou d'un type plus riche, on l'indique explicitement avec le générique.

La forme useState<User | null>(null) est très courante : « pas encore de user, puis un User ». TypeScript force alors à gérer le cas null avant d'utiliser user.

Typer les références et les événements

Deux endroits où le typage aide beaucoup : useRef (référence vers un élément du DOM) et les gestionnaires d'événements.

Grâce à React.ChangeEvent<HTMLInputElement>, l'éditeur sait que e.target.value existe et est une chaîne. Plus de devinette sur la forme de l'événement.

Typer children

Pour un composant qui enveloppe d'autres éléments, on type children avec React.ReactNode — le type de « tout ce que React peut afficher ».

Un composant générique

Pour un composant réutilisable qui s'adapte au type de ses données (une liste de n'importe quoi), on utilise un paramètre de type générique.

Le type T est inféré à l'appel : si elements est un tableau de User, alors rendu reçoit un User. Un seul composant, typé pour n'importe quelle donnée.

Cas réel

Une équipe convertit une grosse application React de JavaScript vers TypeScript. Au tout premier tsc, le compilateur signale un <UserCard avatarUrl={…} /> alors que le composant déclare avatarURL (avec un grand R). Ce simple écart de casse affichait une image cassée depuis des mois, sans que personne ne comprenne pourquoi : en JavaScript, une prop mal nommée est juste undefined, silencieusement. Le typage des props a transformé un bug fantôme en erreur de compilation immédiate — c'est le bénéfice le plus concret du duo React + TS.

Astuce

Pour un composant qui enrobe un élément natif, hérite de ses attributs avec React.ComponentProps : type Props = React.ComponentProps<"button"> & { variante?: "primaire" | "secondaire" }. Ton <Bouton> accepte alors type, disabled, aria-*… sans que tu redéclares chaque prop.

Piège fréquent

Abuser de any dès qu'un type résiste (props, événements). any désactive toute vérification : tu perds précisément ce que TypeScript t'apporte. Si tu ne connais pas encore le type exact d'un événement ou d'une donnée, utilise unknown (qui force à vérifier avant usage) ou cherche le bon type React (ils existent presque tous : React.MouseEvent, React.ReactNode…). Évite aussi l'ancien React.FC au profit du typage direct des props, plus simple et plus souple.

Pour aller plus loin

Le même soin s'applique aux hooks personnalisés (leur valeur de retour se type comme n'importe quelle fonction) et au Context (createContext<MonType | null>(null)). Et pour les données qui entrent dans ton app (réponses d'API), ne te contente pas de les typer : valide-les à la frontière (prochaine leçon : unknown et Zod). Un type n'est qu'une promesse à la compilation ; à l'exécution, une donnée externe peut tout être.

Antisèche

Glossaire

TSX
Le JSX écrit dans un fichier TypeScript (.tsx) : du balisage React vérifié par le compilateur.
Props
Objet d'entrée d'un composant, décrit par un type ou une interface ; l'éditeur autocomplète et vérifie les attributs.
React.ReactNode
Type de « tout ce que React peut afficher » (éléments, chaînes, nombres, fragments, null) ; utilisé pour children.
React.ChangeEvent<T>
Type d'un événement de changement sur un élément T (ex. HTMLInputElement), qui rend e.target.value connu et typé.
useRef<T>
Hook renvoyant une référence mutable vers un élément du DOM de type T, initialisée à null.
Composant générique
Composant paramétré par un type <T> inféré à l'appel, pour s'adapter à n'importe quelle donnée (une liste, un tableau…).
React.FC
Ancien type d'écriture d'un composant fonction ; déconseillé aujourd'hui au profit du typage direct des props, plus simple.
Inférence de props
Déduction automatique du type T d'un composant générique à partir des valeurs passées, sans l'écrire explicitement.

Récap et vérification

  • On écrit du TSX (.tsx) ; les props se typent par un type/interface.
  • useState<T> quand l'inférence ne suffit pas (souvent T | null) ; useRef<HTMLInputElement>.
  • Événements : React.ChangeEvent<…>, React.FormEvent ; children : React.ReactNode.
  • Composants génériques (<T>) ; éviter any et React.FC.
