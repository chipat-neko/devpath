Configurer le compilateur : tsconfig et le mode strict

~36 min Intermédiaire Leçon 09 recommandée

À la fin de cette leçon, tu sauras

  • à quoi sert tsconfig.json et comment le générer ;
  • lire les options clés : sortie, résolution, rigueur ;
  • ce que le mode strict active réellement ;
  • durcir le typage au-delà de strict (accès indexés, etc.).
Sommaire de la leçon

Jusqu'ici, le compilateur a fait son travail « par défaut ». Mais un vrai projet a besoin de lui dire quoi produire, où chercher les modules et à quel point être sévère. Tout cela tient dans un seul fichier : tsconfig.json. Le maîtriser, c'est passer d'un TypeScript qui « tourne » à un TypeScript qui protège. Et au cœur de ce fichier se trouve l'option la plus importante du langage : strict.

À quoi sert tsconfig.json ?

Placé à la racine d'un projet, tsconfig.json est le mode d'emploi du compilateur tsc. Il indique quels fichiers compiler et avec quelles règles. On le génère avec un commentaire par option :

Ses dizaines d'options se rangent en trois familles : ce qu'on produit, comment on résout les imports, et la rigueur du typage.

Famille 3 — la rigueur : le mode strict

Voici l'option la plus importante. "strict": true n'est pas un réglage : c'est un interrupteur maître qui en active une famille entière. En désactivant strict, on désactive d'un coup toutes les vérifications qui font l'intérêt de TypeScript.

Le drapeau vedette est strictNullChecks. Sans lui, null et undefined se glissent dans n'importe quel type sans un mot : c'est l'erreur « à un milliard de dollars ». Avec lui, tu dois gérer explicitement l'absence de valeur :

Plus strict que strict

strict ne couvre pas tout. Quelques drapeaux, hors du groupe, attrapent des bugs supplémentaires — souvent recommandés sur un projet neuf :

  • noUncheckedIndexedAccess : tableau[i] et objet[cle] deviennent T | undefined.
  • exactOptionalPropertyTypes : distingue « propriété absente » de « propriété = undefined ».
  • noImplicitReturns, noUnusedLocals, noFallthroughCasesInSwitch : petits garde-fous quotidiens.

Cas réel

Une équipe migre un vieux projet JavaScript vers TypeScript. Activer strict d'un coup fait apparaître plus de 900 erreurs : impossible à corriger en un jour. La bonne méthode : démarrer avec strict: false, puis rallumer les drapeaux un par un (noImplicitAny, puis strictNullChecks…), en corrigeant chaque vague avant la suivante. Le premier drapeau qui déclenche le plus de corrections — et attrape le plus de bugs — est presque toujours strictNullChecks : il révèle tous les endroits où le code supposait qu'une valeur existait sans jamais le vérifier.

Astuce

Un tsconfig.json peut en étendre un autre avec "extends" : on garde une base commune (par exemple @tsconfig/strictest) et chaque paquet d'un monorepo ne surcharge que le strict nécessaire. Un seul endroit à mettre à jour pour toute l'équipe.

Piège fréquent

Baisser strict (ou parsemer le code de any et @ts-ignore) pour « faire taire » les erreurs revient à débrancher l'alarme incendie : le compilateur cesse de te protéger là où tu en as le plus besoin. Chaque erreur strict signale un endroit où le code suppose quelque chose que rien ne garantit. On corrige, on ne masque pas.

Pour aller plus loin

Dans un projet web moderne, ce n'est souvent pas tsc qui produit le JavaScript : un bundler (Vite, esbuild) transpile chaque fichier séparément et très vite, tandis que tsc --noEmit ne sert plus qu'à vérifier les types. Pour les gros dépôts, "incremental" et les project references ne recompilent que ce qui a changé. La configuration devient alors le contrat partagé entre l'éditeur, le bundler et l'intégration continue.

Glossaire

tsconfig.json
Fichier à la racine du projet qui configure le compilateur : fichiers à compiler et options.
target
Version de JavaScript générée ; une cible basse fait réécrire le code moderne (down-leveling).
module
Format des import/export produits (ESNext, CommonJS…).
moduleResolution
Stratégie pour retrouver le fichier derrière un import (bundler, nodenext…).
strict
Interrupteur maître activant d'un coup une famille de vérifications ; recommandé partout.
strictNullChecks
Drapeau rendant null et undefined explicites : on doit gérer l'absence de valeur.
noUncheckedIndexedAccess
Rend tout accès indexé (t[i], o[k]) potentiellement undefined.
noEmit
Mode « vérifier seulement » : tsc contrôle les types sans écrire de .js.

Récap et vérification

  • tsconfig.json pilote quoi produire, comment résoudre et quelle rigueur.
  • target fixe la version JS ; une cible basse réécrit le code moderne.
  • strict est un interrupteur maître ; son drapeau clé est strictNullChecks.
  • On peut aller plus loin (ex. noUncheckedIndexedAccess) et migrer un vieux projet drapeau par drapeau.

Exercice 3Défi

Explique pourquoi mettre "strict": false pour supprimer des erreurs est une mauvaise idée.

Voir une solution

Parce que chaque erreur strict signale un endroit où le code suppose quelque chose que rien ne garantit (une valeur non nulle, un type précis…). Désactiver strict ne corrige rien : cela masque le problème, exactement là où TypeScript apporte le plus de sécurité. La bonne approche est de corriger les erreurs — au besoin drapeau par drapeau sur un projet existant.
