Module 04 · TypeScript en profondeur — Leçon 12

Patterns de typage avancés

~35 min Avancé Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • savoir modéliser un domaine avec des unions discriminées et garantir l'exhaustivité via never ;
  • savoir simuler le typage nominal avec des branded types et écrire des assertion functions et type predicates ;
  • savoir utiliser as const et satisfies pour préserver les littéraux sans élargir ;
  • savoir valider des données externes à la frontière et bannir any/as au profit de unknown + narrowing.
Sommaire de la leçon

Tu maîtrises les types, les unions, les génériques et les types utilitaires. Il est temps d'utiliser ces briques pour modéliser un domaine de façon à ce que les états impossibles soient inexprimables, et à ce que les données qui entrent dans ton programme soient prouvées plutôt que supposées. C'est la différence entre un code qui compile et un code dans lequel tu as confiance.

Dans cette leçon, on enchaîne sept patterns concrets. Chacun répond à une question récurrente : comment représenter un état métier sans ambiguïté, comment empêcher de confondre deux string, comment prouver un type au lieu de le caster, comment figer des littéraux, et comment faire confiance à une réponse réseau. Tous se compilent avec tsc en mode strict ; les sorties et erreurs sont en commentaire.

Unions discriminées avancées

Une union discriminée associe à chaque variante un champ littéral commun (le discriminant) que le narrowing exploite. Pour modéliser le résultat d'une requête, c'est l'outil idéal : chaque état porte exactement les données qui ont du sens pour lui, et aucune autre.

Accéder à state.data dans le cas "loading" serait une erreur de compilation : la propriété n'existe pas sur cette variante.

Le cas default est le cœur du pattern. Si tu ajoutes demain une variante { status: "cancelled" } et que tu oublies son case, state ne sera plus réduit à never dans le default et tsc signale l'affectation impossible. Tu transformes un oubli silencieux en erreur de compilation.

Branded types : du nominal en TS structurel

TypeScript est structurel : deux types de même forme sont interchangeables. Un UserId et un PostId, tous deux des string, se confondent donc librement, ce qui ouvre la porte à des bugs idiots. Un branded type ajoute une marque fantôme qui n'existe qu'au moment de la compilation.

La marque n'a aucun coût à l'exécution : un UserId reste un string ordinaire en JavaScript.

La clé est l'encapsulation : le as UserId ne doit vivre que dans toUserId, derrière une validation. Si tu disperses des as UserId partout, la garantie s'évapore. Utiliser un unique symbol plutôt qu'un champ __brand: string rend la marque réellement infalsifiable, car personne ne peut en fabriquer une autre.

Assertion functions et type predicates

Tu connais les type predicates (x is T). TypeScript offre aussi les assertion functions (asserts x is T) : au lieu de renvoyer un booléen, elles lèvent une exception et, en cas de retour normal, le compilateur narrow la variable dans la suite du flux.

Sans la signature asserts, tsc ne saurait pas que le code après l'appel ne s'exécute que si la condition est vraie.

Note

Une fonction asserts doit avoir une annotation de retour explicite. Une fonction fléchée stockée dans une variable ne peut pas porter de signature asserts sans annotation de type complète sur la variable : préfère une déclaration function.

const assertions et types littéraux dérivés

Par défaut, TypeScript élargit les littéraux : const dir = "up" a le type string dès qu'il est rangé dans un objet mutable. as const fige tout en lecture seule et conserve les types littéraux, ce qui permet d'en dériver des unions.

Une seule source de vérité (le tableau) génère à la fois la valeur runtime et le type. Plus de duplication entre un enum et une liste.

satisfies : valider sans élargir

Le piège classique : annoter une config avec : Type élargit les valeurs au type déclaré, et tu perds les littéraux. À l'inverse, ne rien annoter ne valide pas la forme. satisfies (TS 4.9) vérifie qu'une valeur respecte un type sans changer son type inféré.

Retiens la règle : : Type contraint vers le bas (élargit), satisfies Type vérifie sans toucher au type inféré.

Astuce

Tu peux chaîner les deux : const routes = { home: "/" } as const satisfies Record<string, string>. Tu obtiens à la fois les littéraux figés en lecture seule (grâce à as const) et la vérification de conformité (grâce à satisfies), sans jamais élargir le type inféré.

Builders typés et overloads

Un builder accumule un état dont le type évolue à chaque appel. En faisant porter cet état par un paramètre générique, tu peux refuser une construction incomplète à la compilation. Les overloads, eux, expriment des relations entrée/sortie qu'une signature unique ne capture pas.

Le paramètre this typé est une technique sous-estimée : il conditionne la disponibilité d'une méthode à l'état du builder.

Valider les données externes à la frontière

Une réponse fetch n'est jamais du type que tu écris à la main : caster un await res.json() en User est un mensonge au compilateur. La bonne pratique : valider à la frontière avec un schéma, et dériver le type du schéma via z.infer.

Si l'API change et renvoie age en string, parse échoue à l'exécution — au point d'entrée — au lieu de propager une donnée fausse dans tout ton code.

Cas réel

Une équipe consomme une API météo tierce qui renvoie temperature en nombre. Un jour, le fournisseur passe le champ à une chaîne ("21.4") « pour homogénéiser ». Avec un simple as WeatherData, le front continue de compiler et affiche NaN °C un peu partout, sans la moindre erreur — le bug remonte par les utilisateurs, plusieurs heures plus tard. Avec un schéma validé à la frontière, le parse échoue au point d'entrée avec un message clair (« expected number, received string »), l'incident est localisé en une minute et un repli propre s'affiche. La validation transforme une panne diffuse en erreur précise et immédiate.

Bannir any et as : unknown + narrowing

any désactive toute vérification et contamine ce qu'il touche ; as affirme un type sans le prouver. Le remplaçant correct est unknown : il t'oblige à narrow avant de l'utiliser, donc à prouver le type.

Règle d'or : à chaque as dans ta tête, demande-toi « est-ce que je peux le prouver avec une garde ? ». Si oui, fais-le. Sinon, c'est un bug en attente.

Pièges fréquents

Piège fréquent

Caster avec as au lieu de prouver le type. value as Foo dit au compilateur « fais-moi confiance » sans aucune garantie à l'exécution. Réserve as à l'intérieur des smart constructors, après une validation, et bannis-le ailleurs.

Piège fréquent

Oublier le contrôle d'exhaustivité. Sans la branche never, ajouter une variante à une union ne provoque aucune erreur là où tu l'avais oubliée : le bug ne se révèle qu'en production. Confondre aussi : Type (qui élargit) et satisfies Type (qui préserve) fait perdre les littéraux sans prévenir.

Piège fréquent

Branded types mal encapsulés, et faire confiance à des données réseau non validées. Un as UserId dispersé dans le code annule la protection ; un await res.json() as User injecte une donnée non prouvée. Centralise la création et valide toujours à la frontière.

Pour aller plus loin

Pour aller plus loin

Compare les validateurs de schéma zod, valibot (plus léger, tree-shakable) et arktype (syntaxe proche des types TS). Regarde tRPC pour partager les types client/serveur sans génération de code, XState pour des machines à états typées qui généralisent l'union discriminée, et le pattern Result/Either (par exemple neverthrow) pour modéliser l'erreur dans le type de retour plutôt qu'avec des exceptions.

Antisèche

Glossaire

Union discriminée
Union d'objets partageant un champ littéral commun (le discriminant) qui permet au narrowing d'ouvrir l'accès aux données propres à chaque variante.
Contrôle d'exhaustivité
Affectation d'une valeur à never dans la branche default : si un cas d'union n'est pas traité, la compilation échoue.
Branded type
Type structurel auquel on ajoute une marque fantôme (unique symbol) pour simuler le typage nominal et empêcher deux types de même forme de se confondre.
Smart constructor
Fonction unique qui valide une donnée brute puis renvoie un type marqué ; seul endroit où le as de marquage est toléré.
Assertion function
Fonction à signature asserts x is T qui lève une exception si la condition est fausse et narrow la variable sinon.
satisfies
Opérateur (TS 4.9) qui vérifie qu'une valeur respecte un type sans remplacer son type inféré, préservant les littéraux exacts.
Validation à la frontière
Vérification de la forme d'une donnée externe (réseau, stockage) au point d'entrée, avec un schéma, avant de la traiter comme typée.
unknown
Type « valeur inconnue » qui, contrairement à any, oblige à narrow (prouver le type) avant tout usage.

Récap et vérification

  • Unions discriminées + branche never : états impossibles inexprimables et exhaustivité garantie.
  • Branded types via unique symbol : du nominal en TS structurel, encapsulé dans un smart constructor.
  • Assertion functions (asserts x is T) et type predicates : narrow le flux après une preuve.
  • as const dérive des unions de littéraux ; satisfies valide sans élargir.
  • Builders typés (paramètre this, génériques d'état) et overloads pour des relations entrée/sortie.
  • Validation à la frontière (zod + z.infer) et unknown + narrowing à la place de any/as.

Vérifie ta compréhension
