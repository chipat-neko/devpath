Les types de base

~34 min Intermédiaire Leçon 1 recommandée

À la fin de cette leçon, tu sauras

  • Savoir annoter une variable avec les types primitifs (string, number, boolean) et distinguer inférence et annotation explicite ;
  • Savoir typer des collections avec les tableaux (number[]) et les tuples ([string, number]) ;
  • Comprendre any, unknown, void et never, et gérer l'absence avec null/undefined sous strictNullChecks ;
  • Savoir choisir entre enum et union de littéraux, et utiliser une assertion as à bon escient.
Sommaire de la leçon

En JavaScript, une variable peut tout contenir : tu écris let total = 0 aujourd'hui, et rien n'empêche total = "beaucoup" trois lignes plus bas. C'est souple, mais c'est aussi la source d'une bonne partie des bugs qu'on ne voit qu'à l'exécution. TypeScript ajoute une couche de types : une étiquette qui dit « cette variable contient un texte », « cette fonction renvoie un nombre ». Le compilateur vérifie ces promesses avant que le code tourne.

Dans cette leçon, on parcourt le vocabulaire de base : les primitifs, les tableaux, les tuples, les types spéciaux (any, unknown, void, never), la gestion de l'absence, les enum et les assertions. On suppose le mode strict activé (le réglage recommandé) ; les résultats du compilateur sont montrés en commentaire dans le code.

Annoter une variable : les primitifs

Une annotation s'écrit après le nom, séparée par un deux-points : nom: type. Les trois types primitifs que tu utiliseras le plus correspondent aux valeurs JavaScript que tu connais déjà : string pour le texte, number pour tous les nombres (entiers et décimaux, pas de distinction), boolean pour true/false.

Remarque que les types s'écrivent en minuscules : string, pas String. Les versions avec majuscule existent mais désignent autre chose (les objets wrapper) ; tu n'en as pas besoin ici.

Inférence ou annotation explicite ?

TypeScript n'a pas toujours besoin que tu annotes. Quand tu initialises une variable, il infère son type tout seul à partir de la valeur. Annoter une variable déjà initialisée est donc souvent redondant.

La règle pratique : laisse inférer les variables locales, mais annote les paramètres de fonction (TS ne peut pas les deviner) et, pour une fonction publique ou exportée, annote aussi le retour. Cela documente le contrat et évite qu'une modification interne change silencieusement le type de sortie.

Astuce

Survole une variable dans ton éditeur : il affiche le type inféré. C'est le meilleur moyen de vérifier ce que TypeScript a compris sans écrire d'annotation.

Les tableaux

Un tableau de nombres se type number[] : « tableau d'éléments de type number ». Il existe une syntaxe générique équivalente, Array<number> ; les deux sont identiques, la première est la plus courante.

Le | dans string | number est une union : « soit l'un, soit l'autre ». On la détaillera plus tard, mais retiens que les parenthèses comptent : (string | number)[] est un tableau de valeurs mixtes, alors que string | number[] signifierait « une chaîne, OU un tableau de nombres ».

Les tuples : longueur et positions fixes

Un tableau classique a une longueur libre et un seul type d'éléments. Un tuple fige le nombre d'éléments et le type à chaque position. C'est utile pour une paire de coordonnées ou un couple clé/valeur.

Un tuple reste un tableau JavaScript à l'exécution : c'est seulement TypeScript qui en contraint la forme à la compilation.

Les types spéciaux : any, unknown, void, never

Quatre types sortent du lot. any désactive toute vérification : la variable redevient « du JavaScript libre ». C'est une porte de sortie à éviter, car tu perds l'intérêt de TypeScript. unknown est son cousin sûr : il accepte n'importe quelle valeur, mais t'oblige à vérifier le type avant de t'en servir.

void décrit une fonction qui ne renvoie rien d'utile (pas de return avec valeur). never décrit ce qui ne se termine jamais normalement : une fonction qui lève toujours une erreur, ou une boucle infinie.

null, undefined et strictNullChecks

En JavaScript, null et undefined représentent l'absence de valeur. Avec l'option strictNullChecks (incluse dans le mode strict), TypeScript ne les laisse plus se glisser partout : si une valeur peut être absente, tu dois l'inclure explicitement dans le type et gérer ce cas.

Sans strictNullChecks, ce code compilerait sans broncher et planterait à l'exécution. C'est précisément le genre de bug que TypeScript existe pour attraper.

Cas réel

L'informaticien Tony Hoare, qui a introduit la référence null en 1965, l'a plus tard appelée son « erreur à un milliard de dollars » tant les null reference errors ont coûté cher en plantages et en failles au fil des décennies. C'est exactement ce trou que strictNullChecks vient boucher : en forçant à écrire string | null et à traiter le cas d'absence, TypeScript transforme un plantage d'exécution en une simple erreur soulignée dans l'éditeur.

enum ou union de littéraux ?

Un enum nomme un ensemble fixe de valeurs liées (des statuts, des rôles…). C'est lisible, mais l'enum génère du code JavaScript réel et a quelques subtilités. Une alternative plus légère, souvent préférée aujourd'hui, est l'union de littéraux : tu listes directement les valeurs autorisées comme un type.

L'union de littéraux donne la même sécurité (seules les valeurs listées passent), reste de simples chaînes à l'exécution, et s'autocomplete dans l'éditeur. On reviendra sur les types littéraux dans une prochaine leçon.

Les assertions de type : as

Parfois tu en sais plus que le compilateur sur le type réel d'une valeur. L'assertion value as Type lui dit « fais-moi confiance, traite ceci comme un Type ». Légitime quand tu as une certitude que TS ne peut pas déduire ; dangereuse car elle ne fait aucune vérification réelle.

Une assertion ne convertit ni ne valide rien : elle change seulement le regard du compilateur. Si tu mens, le bug réapparaît à l'exécution, sans filet.

Pièges fréquents

Piège fréquent

Abuser de any pour faire taire une erreur revient à éteindre TypeScript sur cette valeur : tout ce qui en découle n'est plus vérifié. Si tu ne connais pas encore le type, utilise unknown et affine-le avec une vérification.

Piège fréquent

Confondre any et unknown : les deux acceptent tout en entrée, mais any autorise tout en sortie (et donc les plantages), tandis que unknown bloque tant que tu n'as pas prouvé le type. Sans strictNullChecks, null se faufile aussi partout : garde le mode strict actif. Et méfie-toi d'une assertion as qui ment — elle ne vérifie rien.

Glossaire

Primitif
Type de base non-objet : string, number, boolean (et aussi bigint, symbol, null, undefined).
Tableau
Collection de longueur libre dont tous les éléments partagent un type : number[] ou Array<number>.
Tuple
Tableau à longueur fixe où chaque position a son propre type : [string, number]. Reste un tableau JS à l'exécution.
any
Type « échappatoire » qui désactive toute vérification ; à éviter car il rouvre la porte aux bugs d'exécution.
unknown
Cousin sûr de any : accepte toute valeur mais interdit de l'utiliser tant qu'on n'a pas prouvé son type (narrowing).
void / never
void = fonction sans valeur de retour ; never = fonction qui ne rend jamais la main (erreur systématique, boucle infinie).
strictNullChecks
Option (incluse dans strict) qui empêche null/undefined de se glisser dans un type sans être déclarés et gérés.
Assertion (as)
Forme valeur as Type qui impose un type au compilateur sans aucune vérification réelle ; dangereuse si elle ment.

Récap et vérification

  • Les primitifs s'annotent en minuscules : string, number, boolean.
  • Laisse inférer les variables locales ; annote les paramètres et les retours publics.
  • Tableaux : number[] ou Array<number> ; mixtes via union (string | number)[].
  • Tuples : [string, number] figent longueur et types par position.
  • any à éviter, unknown à affiner ; void = pas de retour, never = jamais de retour.
  • strictNullChecks force à gérer null/undefined explicitement.
  • Préfère souvent une union de littéraux à un enum ; une assertion as ne vérifie rien.
