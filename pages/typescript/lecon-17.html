Le typage structurel : compatibilité, variance et types nominaux

~37 min Avancé Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • pourquoi TypeScript compare les types par leur forme ;
  • ce qu'est le contrôle des propriétés en trop ;
  • lire la variance (paramètres, retours, tableaux) ;
  • simuler un typage nominal avec les branded types.
Sommaire de la leçon

Une question revient sans cesse en TypeScript : « pourquoi cette valeur est-elle acceptée ici ? » ou « pourquoi est-elle refusée ? ». La réponse tient à une seule règle qui gouverne tout le langage : TypeScript compare les types par leur forme, pas par leur nom. Comprendre cette règle — et ses trois conséquences (propriétés en trop, variance, absence de typage nominal) — éclaire d'un coup une foule de comportements du compilateur.

Comparer par la forme, pas par le nom

La variance : types composés

Quand des types s'emboîtent (fonctions, tableaux), leur compatibilité suit des règles de variance. Prenons Chat sous-type de Animal (tout chat est un animal). Pour les fonctions : le retour suit le même sens (covariant), le paramètre suit le sens inverse (contravariant, activé par strictFunctionTypes).

Simuler un typage nominal : les branded types

Le revers du structurel : deux types de même forme sont confondus, même s'ils ne devraient jamais se mélanger. Un UserId et un OrderId sont tous deux des string : rien n'empêche de passer l'un pour l'autre. La parade : y ajouter une marque fantôme qui les distingue.

La marque n'existe qu'à la compilation (à l'exécution, ce sont de simples chaînes) : coût nul, sécurité réelle. On recrée ainsi le typage nominal (comparaison par nom) là où on en a besoin.

Cas réel

En 1999, la sonde Mars Climate Orbiter est perdue parce que deux équipes échangent des poussées sans s'accorder sur l'unité : l'une en livres-force, l'autre en newtons. Les deux valeurs sont de simples nombres : rien ne signale le mélange. C'est exactement le trou du typage structurel. Un branded type — type Newtons = number & { __unite: "N" } distinct de PoundForce — aurait rendu l'addition impossible à compiler. Même logique au quotidien : brander UserId, OrderId, Cents évite de les intervertir dans une signature de fonction.

Astuce

Grâce au structurel, tu n'as presque jamais besoin d'implements : si un objet a la forme attendue, il convient. C'est pratique pour les mocks de test — un objet minimal { get: () => 1 } peut remplacer une grosse dépendance, tant qu'il expose la forme utilisée.

Piège fréquent

Croire que le contrôle des propriétés en trop te protège toujours. Il ne s'applique qu'aux littéraux directs. Dès qu'un objet transite par une variable ou vient d'une fonction, une propriété superflue passe sans alerte : la seule règle de fond reste « a-t-il les propriétés requises ? ». Ne compte pas dessus pour garantir l'absence de champs parasites.

Pour aller plus loin

Il existe une entorse native au structurel : une classe avec un membre private (ou #champ) n'est compatible qu'avec elle-même. Deux classes de forme identique mais aux privés distincts sont incompatibles — un typage presque nominal offert par la présence d'un membre privé. Quant à la variance des tableaux, TypeScript la traite comme covariante par ergonomie, au prix d'un petit trou de sûreté assumé : Chat[] est accepté là où on attend Animal[].

Glossaire

Typage structurel
Règle de TypeScript : deux types sont compatibles s'ils ont la même forme, indépendamment de leur nom.
Duck typing
Image du typage structurel : « si ça marche comme un canard, c'est un canard ».
Typage nominal
Règle inverse : deux types ne sont compatibles que s'ils portent le même nom ; TypeScript ne l'applique pas par défaut.
Excess property check
Contrôle supplémentaire des propriétés « en trop », actif uniquement sur un littéral d'objet passé directement.
Assignabilité
Fait qu'une valeur d'un type puisse être affectée là où un autre type est attendu.
Covariance
Variance « dans le même sens » : le retour d'une fonction suit la relation de sous-typage.
Contravariance
Variance « en sens inverse » : le paramètre d'une fonction accepte un type plus général.
Branded type
Type auquel on ajoute une marque fantôme (compilation seulement) pour distinguer des types de même forme.

Récap et vérification

  • TypeScript compare les types par leur forme (structurel), pas par leur nom.
  • Le contrôle des propriétés en trop ne s'applique qu'aux littéraux directs.
  • Pour les fonctions : retour covariant, paramètre contravariant.
  • Les branded types recréent un typage nominal là où le structurel est dangereux (IDs, unités).

Exercices

Exercice 1Échauffement

Un objet { x: 1, y: 2, z: 3 } est-il acceptable pour un paramètre de type { x: number; y: number } ? Distingue le cas littéral direct et le cas via variable.

Voir une solution

Via une variable : oui (il possède x et y). En littéral direct : non, le contrôle des propriétés en trop signale z.

Exercice 3Défi

Explique pourquoi une (a: Animal) => void peut remplacer une (c: Chat) => void, mais pas l'inverse.

Voir une solution

Le paramètre est contravariant : une fonction qui sait traiter n'importe quel Animal saura forcément traiter un Chat (qui est un animal) ; elle est donc plus générale et peut remplacer celle qui n'attend qu'un chat. L'inverse serait dangereux : une fonction spécialisée (c: Chat) qui lit c.ronronne planterait si on lui passait un Animal quelconque dépourvu de cette propriété.
