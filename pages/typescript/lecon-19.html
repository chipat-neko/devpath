Module 06 · Pour aller plus loin — Leçon 19

Migrer un projet JavaScript vers TypeScript

~36 min Intermédiaire Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • faire coexister JavaScript et TypeScript avec allowJs ;
  • analyser un .js sans le renommer (checkJs, // @ts-check) ;
  • absorber les erreurs avec des échappatoires temporaires maîtrisées ;
  • durcir la configuration par paliers et typer les dépendances.
Sommaire de la leçon

Rares sont les projets qui démarrent en TypeScript. Le plus souvent, on hérite d'une base JavaScript déjà en production, et on veut lui offrir un filet de sécurité sans tout réécrire d'un coup. Bonne nouvelle : TypeScript est un sur-ensemble de JavaScript, pensé pour une adoption progressive. Cette leçon décrit la méthode éprouvée : faire cohabiter les deux langages, puis convertir fichier par fichier, et enfin resserrer les vis.

Une migration progressive, pas un « big bang »

Réécrire tout un projet en une fois est risqué : des semaines sans livrer, un unique commit géant impossible à relire, et des régressions invisibles. La bonne stratégie est incrémentale : on active TypeScript, on laisse les .js et les .ts vivre côte à côte, et on migre un fichier à la fois. La clé est l'option allowJs dans le tsconfig.json, qui autorise le compilateur à lire (et à laisser importer) les fichiers JavaScript :

Étape 1 — analyser sans renommer (checkJs, // @ts-check)

Avant même de renommer quoi que ce soit, on peut demander à TypeScript d'inspecter le JavaScript existant. Deux leviers : l'option globale "checkJs": true, ou le commentaire // @ts-check en tête d'un fichier précis. TypeScript déduit alors les types du code JS et signale les incohérences — souvent des bugs réels dormant depuis des mois :

On peut aussi typer sans quitter le JavaScript, grâce aux annotations JSDoc : elles ajoutent des types dans des commentaires, que // @ts-check prend au sérieux. C'est un excellent tremplin avant le renommage :

Astuce

Commence par // @ts-check fichier par fichier plutôt que checkJs global : tu contrôles le flot d'erreurs et tu récoltes les bugs les plus juteux d'abord, sans noyer l'équipe sous des milliers de messages.

Étape 2 — renommer et absorber les erreurs

Vient le renommage : utils.js devient utils.ts. Aussitôt, des erreurs apparaissent — paramètres au type any implicite, propriétés inconnues, valeurs possiblement undefined. On les traite, mais quand l'une résiste, mieux vaut la marquer proprement et avancer que de rester bloqué. TypeScript offre deux échappatoires ligne à ligne, très différentes :

Piège fréquent

La tentation est de tout typer en any pour « faire taire » le compilateur. Mais any désactive toute vérification et se propage : une valeur any contamine tout ce qu'elle touche. Réserve-le à un usage temporaire et préfère unknown quand tu ne connais pas encore la forme : il force à vérifier avant d'utiliser.

Étape 3 — durcir par paliers (le mode strict progressif)

Activer "strict": true d'emblée sur un vieux projet fait souvent exploser le compteur d'erreurs. On préfère allumer les vérifications une par une, en résorbant les erreurs à chaque palier avant de passer au suivant :

Typer les dépendances externes

Ton code appelle des bibliothèques : d'où viennent leurs types ? Trois cas de figure. Les paquets modernes livrent leurs propres déclarations (un index.d.ts dans le paquet). Les paquets JavaScript plus anciens ont souvent des types communautaires publiés à part, sur DefinitelyTyped, qu'on installe via @types/…. Cas réel

Une équipe reprend un tableau de bord de 60 000 lignes de JavaScript. Plutôt qu'un gel de trois mois, elle active allowJs + checkJs un lundi : dès le premier passage, TypeScript déterre une dizaine de bugs (un montant parfois undefined, un appel de fonction avec un argument en trop). Les fichiers sont ensuite renommés au rythme des tickets — quand on touche un module, on le migre. Les cas coriaces sont marqués @ts-expect-error avec un lien vers un ticket. Six semaines plus tard, "strict": true passe au vert, et le nombre d'incidents en production a nettement baissé. Le projet n'a jamais cessé de livrer.

Pour aller plus loin

Sur de très grosses bases, des outils automatisent le premier jet : ts-migrate (créé par Airbnb) renomme les fichiers en masse et injecte des any explicites (avec un commentaire de suivi) là où le type est inconnu, transformant une migration manuelle en point de départ que l'on affine ensuite. À l'inverse, la config @tsconfig/strictest sert de cible finale une fois le gros du travail fait.

Antisèche

Glossaire

allowJs
Option du tsconfig qui autorise le projet à contenir et importer des fichiers .js aux côtés des .ts.
checkJs
Option qui soumet aussi les fichiers .js à l'analyse de types, comme si chacun portait // @ts-check.
// @ts-check
Commentaire en tête d'un fichier .js qui active la vérification de types pour ce seul fichier.
JSDoc
Annotations de type écrites dans des commentaires (@param, @returns), comprises par TypeScript sans renommer le fichier.
@ts-expect-error
Supprime l'erreur de la ligne suivante et signale une erreur si… il n'y en a plus : une dette qui se rappelle à toi.
@ts-ignore
Supprime l'erreur de la ligne suivante sans jamais vérifier qu'elle existe : dette silencieuse, déconseillée.
Mode strict progressif
Activation des vérifications strictes une par une (noImplicitAny, strictNullChecks…) pour absorber les erreurs par paliers.
DefinitelyTyped
Dépôt communautaire de fichiers de déclaration, publiés sous @types/nom, qui fournit les types des bibliothèques JavaScript.

Récap et vérification

  • On migre incrémentalement : allowJs fait cohabiter .js et .ts.
  • On analyse avant de renommer avec checkJs/// @ts-check et JSDoc.
  • On absorbe les erreurs résistantes avec @ts-expect-error (jamais @ts-ignore).
  • On durcit strict par paliers et on type les dépendances via @types ou declare module.

Vérifie ta compréhension

  1. Quelle option permet à un .ts d'importer un .js sans erreur ?
  2. Pourquoi préférer @ts-expect-error à @ts-ignore ?
  3. Où trouver les types d'une bibliothèque JS qui n'en fournit pas ?

Exercice 3Défi

Pourquoi activer strict par paliers (option par option) plutôt que d'un coup sur un vieux projet ?

Voir une solution

Parce que "strict": true allume d'un seul geste toutes les vérifications strictes : sur une base ancienne, cela peut produire des milliers d'erreurs simultanées, décourageantes et impossibles à traiter dans un seul lot. En allumant noImplicitAny, puis strictNullChecks, etc., chaque palier reste borné : on résorbe un type d'erreur à la fois, chaque étape est livrable et vérifiable en CI, et l'équipe garde le moral et le contrôle. C'est la même philosophie que la migration fichier par fichier, appliquée à la configuration.
