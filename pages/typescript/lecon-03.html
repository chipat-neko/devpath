Module 01 · Démarrer avec TypeScript — Leçon 03

Objets, interfaces et alias de types

~34 min Intermédiaire Leçon 2 recommandée

À la fin de cette leçon, tu sauras

  • savoir décrire la forme d'un objet avec un type en ligne, une interface ou un type ;
  • savoir choisir entre interface et alias de type, et marquer une propriété optionnelle ou readonly ;
  • savoir typer un dictionnaire avec une index signature et composer des formes avec extends ou l'intersection & ;
  • comprendre que TypeScript compare les formes (typage structurel), pas les noms.
Sommaire de la leçon

En JavaScript, un objet est une collection de propriétés que tu manipules librement : tu lis user.nom, tu ajoutes user.age, et rien ne t'avertit si tu te trompes de nom. Le revers, tu le connais : une faute de frappe (user.naem) renvoie undefined au lieu d'une erreur, et le bug se révèle seulement à l'exécution. TypeScript règle ce problème en te laissant décrire la forme attendue de tes objets : quelles propriétés existent, et de quel type.

Dans cette leçon, tu vas apprendre à écrire cette forme de trois façons (type en ligne, interface, alias de type), à marquer des propriétés optionnelles ou en lecture seule, à typer un dictionnaire, puis à composer des formes entre elles. On termine par l'idée la plus surprenante quand on vient de JavaScript : TypeScript compare les formes, pas les noms.

Le type d'un objet en ligne

La forme la plus directe consiste à écrire la structure de l'objet juste après le nom de la variable ou du paramètre. La syntaxe ressemble à un objet, mais avec des types à la place des valeurs, et des ; entre les propriétés.

Le compilateur vérifie que chaque propriété requise est présente et bien typée. Pratique pour un usage ponctuel, mais dès que la même forme revient à plusieurs endroits, la répéter devient lourd : on lui donne alors un nom.

Nommer une forme avec une interface

Une interface donne un nom réutilisable à une forme d'objet. Tu la déclares une fois, puis tu l'utilises comme n'importe quel type.

Le code devient plus lisible : le type s'appelle Utilisateur partout, et corriger la forme à un seul endroit met tout le projet à jour. Par convention, on nomme les interfaces avec une majuscule (PascalCase).

Cas réel

Sur une équipe, le back-end renomme un champ de sa réponse JSON : creeLe devient dateCreation. Côté front, une simple interface Article partagée transforme ce changement silencieux en erreurs de compilation ciblées, exactement aux endroits qui lisent l'ancien champ — au lieu d'un undefined qui se serait affiché « Invalid Date » en production. C'est le rôle quotidien d'une interface : un contrat vérifié à la frontière entre deux morceaux de code (ou deux équipes), qui casse tôt et visiblement plutôt que tard et discrètement.

L'alias de type : interface ou type ?

Un alias de type fait la même chose avec le mot-clé type et un signe = :

Pour décrire un objet, interface et type se valent à 99 %. Deux différences comptent :

  • une interface est extensible : deux déclarations du même nom fusionnent, et elle se prête bien à l'héritage avec extends ;
  • un type est plus général : lui seul peut nommer une union, une intersection ou un type primitif.

Astuce

Recommandation pratique simple : utilise interface pour la forme des objets, et type dès que tu as besoin d'une union, d'une intersection ou d'un alias sur un primitif. En cas d'hésitation, interface est un bon défaut.

Propriétés optionnelles et readonly

Toutes les propriétés ne sont pas toujours présentes. Un ? après le nom marque une propriété optionnelle : elle peut être absente. Le préfixe readonly interdit, lui, de réécrire une propriété après création.

En mode strict, lire c.age donne le type number | undefined : TypeScript t'oblige à gérer le cas « absent » avant d'utiliser la valeur, ce qui élimine une classe entière de bugs.

Typer un dictionnaire avec une index signature

Parfois tu ne connais pas les noms des clés à l'avance : un objet qui sert de dictionnaire (associer un mot à un score, un identifiant à un compteur…). L'index signature décrit « n'importe quelle clé de ce type donne une valeur de ce type ».

Le nom joueur entre crochets est purement documentaire : il rappelle ce que représente la clé. Ce qui compte, c'est le type de la clé (string) et celui de la valeur (number).

Imbrication et tableaux d'objets

Une forme peut en contenir une autre, ou contenir un tableau d'objets. On compose les types comme on compose les données.

La vérification descend dans chaque niveau : l'adresse imbriquée doit elle aussi respecter sa forme. Noter au passage que Personne[] est la façon courte d'écrire Array<Personne>.

Composer : extends et intersection &

Pour construire une grande forme à partir de plus petites, deux outils selon que tu utilises interface ou type. Une interface hérite avec extends ; un alias de type combine avec l'intersection & (le ET logique des types).

Le résultat est équivalent dans les deux cas : Article exige id, creeLe et titre. extends exprime une relation « est un », tandis que & fusionne mécaniquement les propriétés.

Le typage structurel : les formes, pas les noms

Voici le point qui surprend le plus. TypeScript est structurel (parfois appelé « duck typing ») : deux types sont compatibles si leurs formes correspondent, même s'ils n'ont aucun lien de parenté ni le même nom.

Retiens deux choses. D'abord, un nom de type ne crée aucune barrière : c'est la forme qui décide. Ensuite, un objet littéral écrit directement à l'endroit attendu subit un contrôle supplémentaire (l'excess property check) qui rejette les propriétés « en trop » ; passer par une variable intermédiaire (comme coord) lève ce contrôle.

Pièges fréquents

Piège fréquent

Confondre age?: number et age: number | undefined. Avec ?, la propriété peut être absente de l'objet. Avec l'union, la clé doit être présente mais peut valoir undefined : { nom: "Inès" } est refusé car age manque.

Piège fréquent

Oublier readonly sur des données qui ne doivent jamais muter (un id, une config figée). Sans lui, rien n'empêche une réaffectation accidentelle plus loin dans le code. Et croire que TypeScript est nominal alors qu'il est structurel : ne t'étonne pas qu'un objet « de la bonne forme » soit accepté sans porter le bon nom de type. À l'inverse, l'excess property check ne s'applique qu'aux littéraux directs, pas aux variables.

Pour aller plus loin

Pour aller plus loin

Le débat interface vs type a des cas-limites (fusion de déclarations, performances de compilation sur de grosses unions). L'héritage d'interfaces accepte plusieurs parents (extends A, B). Les formes peuvent être récursives pour décrire des arbres (un nœud qui contient des nœuds enfants). Pour un dictionnaire, Record<string, number> est une alternative idiomatique à l'index signature. Enfin, les utility types (Partial, Pick, Record…), vus à la leçon 7, transforment une forme existante sans la réécrire.

Antisèche

Glossaire

Interface
Nom donné à une forme d'objet (ses propriétés et leurs types). Extensible et adaptée à l'héritage via extends.
Alias de type
Nom donné à n'importe quel type avec type X = … : objet, union, intersection ou primitif.
Propriété optionnelle
Propriété marquée ? qui peut être absente de l'objet ; sa lecture donne T | undefined.
readonly
Modificateur qui interdit de réaffecter une propriété après la création de l'objet.
Index signature
Écriture [cle: string]: T qui type un dictionnaire aux clés inconnues d'avance ; proche de Record<string, T>.
Intersection (&)
Combinaison de plusieurs types en un seul qui possède toutes leurs propriétés (le ET des types).
Typage structurel
Règle selon laquelle deux types sont compatibles s'ils ont la même forme, indépendamment de leur nom (duck typing).
Excess property check
Contrôle supplémentaire appliqué aux objets littéraux passés directement : une propriété non prévue est refusée.

Récap et vérification

  • Une forme d'objet s'écrit en ligne { nom: string; age: number }, ou se nomme avec interface / type.
  • interface pour les objets (extensible, extends) ; type pour les unions, intersections et primitifs.
  • ? rend une propriété optionnelle ; readonly la verrouille en lecture seule.
  • Une index signature { [cle: string]: number } type un dictionnaire de clés inconnues (ou Record<string, number>).
  • On compose avec extends (interface) ou l'intersection & (type).
  • TypeScript est structurel : il compare les formes, pas les noms ; les littéraux directs subissent en plus l'excess property check.

Vérifie ta compréhension

  1. Quelle différence concrète entre age?: number et age: number | undefined sur l'objet { nom: "Inès" } ?
  2. Tu dois nommer une union "clair" | "sombre" : utiliserais-tu interface ou type, et pourquoi ?
  3. Pourquoi distance(coord) passe-t-il alors que distance({ x: 3, y: 4, label: "x" }) échoue ?
