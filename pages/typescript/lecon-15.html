Module 05 · TypeScript appliqué — Leçon 15

Valider à la frontière : unknown, Zod et satisfies

~40 min Avancé Leçon 14 recommandée

À la fin de cette leçon, tu sauras

  • pourquoi un type ne garantit rien à l'exécution ;
  • recevoir une donnée externe en unknown et la vérifier ;
  • valider à la frontière avec Zod (z.infer) ;
  • utiliser satisfies pour vérifier sans élargir.
Sommaire de la leçon

TypeScript vérifie les types à la compilation. Mais à l'exécution, les types ont disparu : une donnée venue du dehors — une réponse d'API, un localStorage, un fichier JSON — peut avoir n'importe quelle forme, quoi qu'en dise ta déclaration. Croire un as User sur une réponse fetch est une illusion de sécurité. La règle professionnelle : valider les données aux frontières. Cette leçon t'apprend à le faire proprement, avec unknown, Zod et satisfies.

Le danger du as

L'assertion as dit au compilateur « fais-moi confiance, c'est de ce type » — sans aucune vérification. Sur une donnée externe, c'est un mensonge potentiel.

Le as trompe le compilateur, mais pas la réalité. Pour une donnée dont tu ne contrôles pas la source, il faut vérifier, pas asserter.

unknown : le type « à vérifier »

Le type unknown représente « une valeur dont on ne sait rien ». Contrairement à any, il force à vérifier avant tout usage : c'est exactement ce qu'on veut pour une entrée externe.

unknown est le bon type d'entrée d'une fonction qui reçoit du « tout-venant ». Mais écrire ces vérifications à la main est fastidieux et fragile : c'est là qu'intervient Zod.

Valider avec Zod

Zod permet de décrire un schéma et de valider une donnée contre lui à l'exécution — et, atout majeur, d'en déduire le type TypeScript. Une seule définition sert à la fois de validateur et de type.

Contrairement au as, parse vérifie vraiment la forme : si l'API renvoie autre chose, il lève une erreur claire au lieu de laisser passer une donnée fausse. La frontière entre le monde externe (non sûr) et ton code (typé) est gardée.

Cas réel

Une application stocke les préférences de l'utilisateur dans localStorage au format JSON. La version 2 change la forme de cet objet. Au retour d'un ancien utilisateur, le code lit le cache avec JSON.parse(...) as Prefs : la vieille structure ne correspond plus, et l'app plante au démarrage — mais seulement pour les anciens utilisateurs, jamais en test avec un cache neuf. En passant le cache par un PrefsSchema.safeParse qui retombe sur les valeurs par défaut en cas d'échec, le bug disparaît : une donnée périmée est détectée et remplacée proprement au lieu de tout casser.

Astuce

Préfère safeParse à parse quand tu veux gérer l'échec sans try/catch : il renvoie une union discriminée { success: true; data } | { success: false; error }. Un simple if (result.success) narrow vers la donnée validée — exactement le patron d'union discriminée vu plus tôt dans le cours.

L'opérateur satisfies

Côté interne, un autre outil moderne : satisfies. Il vérifie qu'une valeur respecte un type, sans élargir son type inféré (au contraire de l'annotation classique). On garde ainsi les types précis tout en attrapant les erreurs.

satisfies dit « vérifie que ceci correspond au type, mais laisse-moi le type le plus précis possible ». C'est l'outil idéal pour les objets de configuration : conformité garantie et autocomplétion fine.

Piège fréquent

Confondre typer et valider. Écrire const user: User = await res.json() (ou as User) ne fait que déclarer un type : à l'exécution, aucune vérification n'a lieu, et une donnée malformée passe sans bruit. Un type est une promesse de compilation ; une validation (Zod) est une vérification réelle. Réserve les annotations/as aux données dont tu contrôles l'origine, et valide toute donnée qui franchit une frontière (réseau, stockage, fichier).

Pour aller plus loin

Cette idée — « parse, don't validate » — est un principe fort : au lieu de vérifier une donnée puis de continuer à la traiter comme unknown, on la transforme en un type sûr une fois pour toutes à l'entrée. Couplé au cours Node.js (où Zod valide les requêtes) et à la leçon précédente (React + TS), tu obtiens une chaîne typée de bout en bout : de la requête HTTP validée jusqu'au composant. C'est l'état de l'art du TypeScript moderne.

Antisèche

Glossaire

Frontière
Point où une donnée externe (réponse d'API, localStorage, fichier) entre dans le programme ; c'est là qu'il faut valider.
unknown
Type « valeur inconnue » qui oblige à vérifier (narrow) avant usage ; le bon type d'entrée pour une donnée non fiable.
any
Type qui désactive toute vérification et se propage silencieusement ; à bannir pour les données externes.
Type guard
Fonction à signature x is T qui, si elle renvoie true, narrow la variable vers T dans la suite du code.
Zod
Bibliothèque de schémas qui valide une donnée à l'exécution et permet d'en déduire le type TypeScript.
z.infer
Utilitaire qui extrait le type TypeScript d'un schéma Zod, garantissant que type et validateur restent synchronisés.
satisfies
Opérateur qui vérifie qu'une valeur respecte un type sans élargir son type inféré ; idéal pour les objets de configuration.
Parse, don't validate
Principe consistant à transformer une donnée en un type sûr une fois à l'entrée, plutôt que de la re-vérifier partout ensuite.

Récap et vérification

  • Un type disparaît à l'exécution : as User sur une donnée externe est un mensonge potentiel.
  • unknown force à vérifier avant usage (contrairement à any).
  • Zod valide à l'exécution et déduit le type (z.infer) : une seule source de vérité.
  • satisfies vérifie la conformité sans élargir le type : idéal pour les configs.

  2. Avec Zod, pourquoi n'a-t-on pas besoin d'écrire l'interface du User en plus du schéma ?
  3. Qu'apporte satisfies par rapport à une annotation de type ?

Voir une solution

Parce qu'un type n'existe qu'à la compilation et disparaît à l'exécution : il déclare une forme attendue sans la vérifier, si bien qu'une réponse réellement malformée passe sans erreur. Valider (avec Zod) effectue une vérification à l'exécution de la forme réelle de la donnée et garantit qu'elle correspond bien au type — ou échoue clairement sinon.
