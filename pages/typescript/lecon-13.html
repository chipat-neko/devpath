TypeScript en production : décorateurs et outillage

~35 min Avancé Leçon 12 recommandée

À la fin de cette leçon, tu sauras

  • Savoir écrire un décorateur standard (TC39) de classe ou de méthode et le distinguer du legacy experimentalDecorators ;
  • Savoir enrichir un type existant par declaration merging et module augmentation ;
  • Savoir configurer un tsconfig.json strict (noUncheckedIndexedAccess, exactOptionalPropertyTypes) et des project references ;
  • Savoir intégrer tsc --noEmit en CI, publier un paquet typé et accélérer le compilateur sur un gros projet.
Sommaire de la leçon

Tu sais écrire du TypeScript. Reste à le faire vivre dans un vrai projet : un compilateur qui ne ralentit pas l'équipe, une CI qui bloque les régressions de types, un paquet publié avec ses définitions, et quelques mécanismes avancés (décorateurs, augmentation de modules) que les frameworks modernes exploitent à fond.

Cette leçon est volontairement orientée production : moins de syntaxe nouvelle, plus de décisions d'outillage. On termine sur les réglages tsconfig qui font la différence entre un projet sûr et un projet qui « compile quand même ».

Les décorateurs standard (TC39, TS 5)

Un décorateur est une fonction qui reçoit l'élément décoré et un objet context, et qui peut le remplacer ou l'observer. Depuis TypeScript 5.0, les décorateurs standard (étape 3 du TC39) sont actifs sans aucune option : tu n'as plus besoin de experimentalDecorators.

Le décorateur retourne une nouvelle méthode qui enrobe l'originale (mesure + journalisation).

Le typage est précis : ClassMethodDecoratorContext expose name, kind, private, static et un addInitializer. Il existe une variante par cible : ClassDecoratorContext, ClassGetterDecoratorContext, ClassFieldDecoratorContext, etc.

Note

Angular et NestJS reposent massivement sur des décorateurs (@Component, @Injectable, @Controller) mais utilisent encore la version legacy avec experimentalDecorators et emitDecoratorMetadata (pour l'injection de dépendances par réflexion). Ne mélange pas les deux dans un même projet.

Declaration merging et module augmentation

TypeScript fusionne plusieurs déclarations de même nom (deux interface identiques se complètent). On exploite ce mécanisme pour enrichir un type existant sans le posséder : ajouter une propriété globale, ou étendre les types d'une bibliothèque tierce.

Le export {} transforme le fichier en module ; sans lui, declare global est refusé.

Piège fréquent

L'augmentation doit cibler exactement le bon module (le specifier d'import, pas le nom du paquet npm s'ils diffèrent) et la bonne interface. Un declare module "expres" mal orthographié ne lèvera pas d'erreur : TypeScript croira que tu déclares un nouveau module ambiant.

tsconfig en profondeur

L'option "strict": true est un méta-flag qui en active une famille (strictNullChecks, noImplicitAny, strictFunctionTypes…). Mais deux options strictes ne sont pas incluses et méritent une activation explicite.

noUncheckedIndexedAccess est l'option qui rend l'accès indexé sûr : un trou non détecté devient une erreur de type.

Astuce

Ne duplique pas ta configuration : place les réglages communs dans un tsconfig.base.json et fais "extends": "./tsconfig.base.json" dans chaque paquet. Les presets @tsconfig/strictest ou @tsconfig/node20 fournissent une base stricte et éprouvée que tu affines ensuite.

Compilation : tsc vs bundlers

Les bundlers modernes (esbuild, swc, Vite) transpilent TypeScript en supprimant simplement les annotations, fichier par fichier, sans aucune vérification de types. C'est rapide, mais ça veut dire qu'un bug de types peut passer en build.

Sépare les rôles : le bundler émet, tsc --noEmit vérifie.

Piège fréquent

Croire que « le build passe » équivaut à « les types sont corrects ». Un projet Vite peut builder avec des dizaines d'erreurs de types. Le filet, c'est tsc --noEmit exécuté en CI, jamais le bundler.

Cas réel

Une startup migre son front sur Vite pour gagner en vitesse de build. Pendant un refactor, un développeur renomme userId en user_id dans une interface, mais oublie deux appels. vite build passe au vert et le déploiement part en production… où la page de profil plante, car userId vaut désormais undefined. Le post-mortem est sans appel : le pipeline ne lançait que le bundler. L'équipe ajoute tsc --noEmit comme étape bloquante avant tout merge ; la même erreur, réintroduite un mois plus tard, est cette fois arrêtée en CI en quelques secondes.

.d.ts et publication d'un paquet typé

Pour qu'un paquet publié soit utilisable en TypeScript par tes utilisateurs, il doit fournir ses définitions. Active declaration: true : tsc génère un .d.ts à côté de chaque .js.

Le champ "types" (ou "typings") indique au compilateur du consommateur où trouver l'API. Avec declarationMap, un « Go to definition » saute directement dans ton code source plutôt que dans le .d.ts.

Performance du compilateur

Sur un gros projet, deux leviers changent tout. incremental stocke un fichier .tsbuildinfo et ne recompile que le delta. skipLibCheck saute la vérification interne des .d.ts des dépendances — qui peuvent être nombreux et contradictoires.

Piège fréquent

Oublier skipLibCheck sur un projet avec beaucoup de dépendances : tsc vérifie alors des milliers de lignes de .d.ts tiers, ce qui peut multiplier le temps de compilation. Active-le sauf si tu publies une bibliothèque où la cohérence des types tiers est critique.

Bonnes pratiques d'équipe

Le compilateur vérifie les types ; il ne dit rien des promesses oubliées, des variables inutilisées ou du style. C'est le rôle d'ESLint typé via typescript-eslint, qui lit le programme TypeScript pour des règles « type-aware » (par ex. no-floating-promises).

Faire échouer la CI sur la moindre erreur de types ou de lint garantit que main reste vert.

Pièges fréquents

  • Décorateurs legacy vs standard : la signature change ((target, propertyKey, descriptor) en legacy contre (value, context) en standard). Vérifie si experimentalDecorators est activé avant d'écrire.
  • Augmentation mal ciblée : mauvais nom de module ou fichier non-module (declare global sans export {}).
  • Faux sentiment de sécurité du bundler : il transpile sans vérifier, d'où tsc --noEmit obligatoire.
  • tsconfig trop laxiste : strict sans noUncheckedIndexedAccess laisse passer des undefined sur les accès indexés.
  • Compilation lente : pas de skipLibCheck ni d'incremental sur un gros graphe.

Glossaire

Décorateur (standard)
Fonction recevant (value, context) qui observe ou remplace une classe/méthode ; actif sans option depuis TS 5, distinct du décorateur legacy.
Declaration merging
Fusion par TypeScript de plusieurs déclarations de même nom (deux interface) en une seule qui cumule leurs membres.
Module augmentation
Ajout de membres au type d'un module tiers via declare module "…", sans modifier son code source.
Project references
Découpage d'un monorepo en sous-projets (composite: true) compilés dans le bon ordre et mis en cache séparément avec tsc --build.
Fichier .d.ts
Fichier de déclaration qui décrit les types d'un module sans code exécutable ; publié pour rendre un paquet utilisable en TypeScript.
noUncheckedIndexedAccess
Option (hors strict) qui ajoute | undefined au type d'un accès indexé, forçant à gérer le cas hors limites.
tsc --noEmit
Vérification des types sans génération de fichiers ; sert de garde-fou en CI quand un bundler assure l'émission.
skipLibCheck
Option qui saute la vérification interne des .d.ts des dépendances pour accélérer nettement la compilation.

Récap et vérification

  • Les décorateurs standard (TS 5) n'exigent plus d'option ; les frameworks utilisent souvent la version legacy.
  • Le declaration merging et la module augmentation enrichissent des types qu'on ne possède pas.
  • strict n'inclut pas tout : ajoute noUncheckedIndexedAccess et exactOptionalPropertyTypes.
  • Les bundlers transpilent sans vérifier → tsc --noEmit en garde-fou CI.
  • declaration: true + champ "types" pour publier un paquet typé ; skipLibCheck et incremental pour la vitesse.
