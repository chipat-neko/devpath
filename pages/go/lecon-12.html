Module 04 · Go en profondeur — Leçon 12

Génériques, réflexion et le runtime

~35 min Avancé Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire des fonctions et types génériques avec des contraintes (any, comparable, ~int) et choisir entre générique et interface ;
  • savoir inspecter des valeurs avec reflect (types, tags de struct) et mesurer son coût ;
  • savoir expliquer le modèle GMP, le garbage collector et l'escape analysis du runtime ;
  • savoir profiler un programme avec pprof (CPU, mémoire, goroutines).
Sommaire de la leçon

Tu maîtrises déjà la syntaxe, les interfaces, les goroutines et les channels. Cette leçon descend d'un cran sous le capot : les génériques qui te permettent d'écrire du code réutilisable sans sacrifier le typage, la réflexion qui inspecte les valeurs à l'exécution, et le runtime qui orchestre tes goroutines et nettoie ta mémoire pendant que tu dors.

Ce sont des outils puissants — et faciles à mal employer. On va voir quand les sortir, et surtout quand ne pas le faire. Tout est en Go moderne (1.22+) et se compile avec go build ; les sorties sont en commentaire dans le code.

Les génériques : fonctions et types paramétrés

Avant Go 1.18, écrire une fonction qui marche sur n'importe quel type imposait soit de la dupliquer, soit de passer par interface{} et des assertions. Les génériques règlent ça avec des paramètres de type entre crochets.

Remarque que l'appel Map(noms, ...) ne précise pas les types : le compilateur les infère depuis les arguments. [T, U any] déclare deux paramètres de type, tous deux contraints par any (alias de interface{}, donc « n'importe quel type »).

On peut aussi paramétrer un type, pas seulement une fonction :

Le var zero T est l'idiome pour produire la valeur zéro d'un type paramétré (0, "", nil… selon T).

Note

Une limite à connaître : en Go, les méthodes ne peuvent pas introduire leurs propres paramètres de type. Une méthode sur Pile[T] peut utiliser le T du type, mais tu ne peux pas écrire func (p *Pile[T]) Convertir[U any]() Pile[U]. Pour ça, passe par une fonction libre comme Map.

Les contraintes : limiter ce qu'on accepte

any autorise tout, mais alors tu ne peux presque rien faire de la valeur. Pour additionner ou comparer, il faut une contrainte plus précise. comparable autorise == et != ; les interfaces de contrainte listent des types concrets avec | ; le ~ (tilde) signifie « ce type et tous ceux qui le prennent comme sous-jacent ».

Sans le ~, Somme([]Age{...}) ne compilerait pas : Age n'est pas int, juste basé dessus.

Note

Depuis Go 1.21, la stdlib fournit cmp.Ordered, une contrainte prête à l'emploi qui regroupe tous les types comparables par < (entiers, flottants, chaînes). Inutile de réécrire Nombre à la main dans la plupart des cas — et le package golang.org/x/exp/constraints en propose d'autres comme Integer ou Float.

Les packages slices, maps et cmp de la stdlib

Depuis Go 1.21, la bibliothèque standard expose des helpers génériques qui remplacent des dizaines de boucles écrites à la main. Connais-les : tu réinventerais sinon des fonctions déjà testées et optimisées.

cmp.Compare renvoie -1, 0 ou +1, exactement ce qu'attend SortFunc. Côté maps, attention : depuis Go 1.23 maps.Keys et maps.Values renvoient un itérateur (iter.Seq), pas une slice. Pour obtenir une slice, combine avec slices.Collect(maps.Keys(m)). maps.Clone, lui, renvoie bien une copie de la map.

Générique ou interface ? Le bon réflexe

Les deux résolvent le « code qui marche sur plusieurs types », mais pas de la même façon. La règle pratique :

  • Interface : quand tu veux un comportement (chaque type sait faire quelque chose à sa manière) et que tu acceptes le dispatch dynamique. Exemple : io.Writer, fmt.Stringer.
  • Générique : quand l'algorithme est identique pour tous les types et que tu veux conserver le type concret en sortie (pas de any à déballer). Exemple : un conteneur, Map, Filter.

Piège fréquent

Ne mets pas un générique partout « parce que c'est moderne ». Si une fonction prend une seule slice et appelle une méthode dessus, une interface est plus lisible. Les génériques alourdissent les signatures ; réserve-les aux cas où ils gagnent vraiment quelque chose (type de retour préservé, conteneur, algorithme uniforme).

La réflexion : inspecter à l'exécution

Le package reflect permet d'examiner — et même de modifier — des valeurs dont tu ne connais pas le type à la compilation. C'est ce qui alimente la sérialisation JSON, les ORM et les frameworks de validation. Les deux portes d'entrée sont reflect.TypeOf et reflect.ValueOf.

Les tags de struct (entre backticks) sont de simples chaînes que reflect sait découper par clé via Tag.Get. C'est exactement ce que fait encoding/json en coulisses.

Piège fréquent

reflect est lent (10 à 100× un accès direct), déplace les erreurs de la compilation vers l'exécution (un mauvais nom de champ panique au lieu de ne pas compiler), et casse l'analyse statique. Utilise-le uniquement quand tu ne peux pas connaître le type à l'avance : sérialiseur générique, mapping ORM. Pour tout le reste, les génériques ou une interface font mieux.

unsafe en aperçu

Le package unsafe permet de contourner le système de types : convertir un pointeur d'un type vers un autre, lire la disposition mémoire brute. Il sert dans des cas extrêmes (interop C via cgo, optimisations de bas niveau dans la stdlib).

unsafe.Sizeof est inoffensif et utile pour comprendre la mémoire. Mais les conversions de pointeurs via unsafe.Pointer contournent les garanties du compilateur et du GC : un changement de version de Go peut casser ton code silencieusement. Règle simple : n'y touche pas tant que tu n'as pas une raison mesurée et que tu ne maîtrises pas exactement les règles de unsafe.Pointer.

Le runtime : le modèle GMP et le scheduler

Quand tu lances go maFonction(), tu ne crées pas un thread système. Le runtime Go multiplexe des milliers de goroutines sur une poignée de threads grâce au modèle GMP :

  • G (goroutine) : ta tâche, très légère (quelques Ko de pile, qui grandit au besoin).
  • M (machine) : un thread du système d'exploitation.
  • P (processor) : un contexte d'exécution logique ; leur nombre est fixé par GOMAXPROCS.

Le scheduler attache des G à un P, qu'un M exécute. Quand une goroutine se bloque (I/O, channel), le runtime la met de côté et fait tourner une autre sur le même thread. Un P à court de travail peut voler des goroutines à la file d'un autre P (work-stealing) : c'est ce qui répartit la charge et rend la concurrence Go si peu coûteuse.

Depuis Go 1.5, GOMAXPROCS vaut par défaut le nombre de cœurs. Le passer à 1 sérialise l'exécution parallèle (utile pour déboguer une data race).

Piège fréquent

Ne suppose jamais l'ordre dans lequel le scheduler exécutera tes goroutines, ni qu'une boucle « rendra la main » à un moment précis. L'ordre n'est pas garanti. Si ton programme en dépend, c'est un bug : synchronise avec des channels, un sync.WaitGroup ou un sync.Mutex.

Le garbage collector et l'escape analysis

Go a un GC concurrent à faibles pauses : il marque les objets vivants pendant que ton programme continue de tourner, ce qui maintient les pauses sous la milliseconde même sur de gros tas. Son rythme (pacing) est piloté par GOGC (100 par défaut) : le GC se déclenche quand le tas a grossi de 100 % depuis le dernier passage. Augmenter GOGC réduit la fréquence du GC au prix de plus de mémoire.

Mais le meilleur déchet est celui qu'on ne crée pas. Le compilateur fait de l'escape analysis : si une valeur ne « s'échappe » pas de la fonction, il l'alloue sur la pile (gratuit, libéré au retour) plutôt que sur le tas (coûteux, suivi par le GC).

Astuce

Renvoyer un pointeur, passer une valeur à interface{} (donc à fmt.Println) ou capturer une variable dans une closure provoque souvent un échappement vers le tas. Ne micro-optimise pas à l'aveugle : mesure d'abord avec un benchmark, puis lis -gcflags=-m sur le chemin chaud.

Pièges fréquents

  • Sur-utiliser les génériques. Si une interface exprime mieux l'intention (un comportement), garde l'interface. Un générique avec une seule contrainte triviale n'apporte rien.
  • Abuser de reflect. Lent, fragile, repousse les erreurs à l'exécution. Réserve-le à la sérialisation et au mapping où le type est inconnu.
  • Utiliser unsafe sans raison. Tu perds les garanties du compilateur et du GC ; un upgrade de Go peut tout casser.
  • Supposer le comportement du scheduler. L'ordre des goroutines n'est pas garanti ; synchronise explicitement.
  • Ignorer les allocations cachées. Un pointeur renvoyé ou une closure peut forcer une allocation sur le tas ; vérifie avec -gcflags=-m sur le chemin chaud.
  • Profiler en production sans précaution. Endpoints exposés, surcoût CPU : protège-les.

Pour aller plus loin

Pour aller plus loin

Explore pprof en profondeur (vue web en flamegraph, profils de blocage et de mutex). Couple go build -gcflags=-m à des benchmarks avec go test -bench=. -benchmem pour chasser les allocations (colonnes allocs/op et B/op). Pour le GC, joue avec la variable d'environnement GOGC et la limite mémoire GOMEMLIMIT. Enfin, sache que go:linkname existe pour relier des symboles internes — mais c'est de la magie noire à éviter dans du code applicatif.

Un cas réel : reflect qui mangeait 40 % du CPU

Cas réel

Un service sérialisait chaque réponse via une petite bibliothèque maison qui, à coups de reflect, parcourait les champs de chaque struct à l'exécution. Tant que le trafic restait faible, personne n'a rien vu. À la montée en charge, un profil pprof a parlé sans détour : près de 40 % du temps CPU passait dans reflect.Value et les allocations associées. Le correctif n'a pas touché la logique métier : pour les quelques structs du chemin chaud, l'équipe a généré le code d'encodage à la compilation (via go:generate) — plus de reflect à l'exécution sur ces types. Le CPU a chuté, la latence p99 aussi. La leçon : reflect est parfait pour un cas générique rare, désastreux dans une boucle chaude. Mesure d'abord (pprof), puis remplace de façon ciblée.

Antisèche

Glossaire

Générique
Fonction ou type paramétré par un ou plusieurs types ([T any]) ; écrit un algorithme unique réutilisable en conservant le type concret.
Contrainte
Ensemble des types acceptés par un paramètre de type : any, comparable, une interface avec |, ou cmp.Ordered.
Tilde (~T)
Dans une contrainte, autorise T et tout type dont le type sous-jacent est T (ex. ~int accepte type Age int).
Réflexion (reflect)
Inspection et modification de valeurs à l'exécution (types, champs, tags) ; puissante mais lente et fragile — à réserver à la sérialisation/mapping.
Modèle GMP
Ordonnancement Go : G (goroutine), M (thread système), P (processeur logique). GOMAXPROCS fixe le nombre de P, donc le parallélisme.
Garbage collector
Récupérateur de mémoire concurrent à faibles pauses ; son rythme est piloté par GOGC (100 par défaut) et plafonné par GOMEMLIMIT.
Escape analysis
Analyse du compilateur qui alloue sur la pile (gratuit) une valeur qui ne s'échappe pas, sinon sur le tas (suivi par le GC).
pprof
Profileur intégré : mesure où le programme passe son temps (CPU) ou alloue (tas), et l'état des goroutines. go tool pprof analyse le profil.

Récap et vérification

  • Les génériques (func F[T any], type C[T any]) écrivent du code réutilisable et typé ; les contraintes (any, comparable, ~int, interfaces avec |) limitent les types acceptés.
  • Les packages slices, maps et cmp fournissent des helpers génériques standards (Sort, Contains, SortFunc, Compare).
  • Choisis une interface pour un comportement variable, un générique pour un algorithme uniforme qui préserve le type.
  • reflect inspecte types et tags à l'exécution — puissant mais lent et fragile, à réserver à la sérialisation.
  • Le runtime repose sur le modèle GMP piloté par GOMAXPROCS, un GC concurrent réglé par GOGC, et l'escape analysis (pile vs tas).
  • pprof profile CPU, mémoire, goroutines et blocage.
