Module 05 · Go en pratique — Leçon 18

Projet : un outil en ligne de commande

~40 min Intermédiaire Leçon 17 recommandée

À la fin de cette leçon, tu sauras

  • lire les arguments bruts avec os.Args et des drapeaux typés avec le package flag ;
  • offrir une aide automatique et des valeurs par défaut à ton outil ;
  • utiliser correctement les trois flux stdin, stdout, stderr et un code de sortie ;
  • assembler un vrai outil en ligne de commande, réutilisable dans un pipeline Unix.
Sommaire de la leçon

Go est un langage de prédilection pour les outils en ligne de commande : un binaire unique, sans dépendances, qui démarre instantanément. Docker, Kubernetes, Terraform, la CLI de GitHub : tous sont écrits en Go. Cette dernière leçon rassemble ce que tu sais pour construire un outil propre — arguments, drapeaux, flux standard et code de sortie — puis referme le cours avec un projet fil rouge.

On compile un outil avec go build -o monoutil ., puis on le lance ./monoutil …. En développement, go run . … fait tourner le même code directement.

Les arguments bruts : os.Args

Le plus direct : os.Args est une []string qui contient le nom du programme suivi de ses arguments. L'index 0 est toujours le nom de l'exécutable ; les vrais arguments commencent à 1.

os.Args suffit pour un outil trivial, mais il te laisse tout faire à la main : reconnaître les options, convertir les nombres, gérer l'ordre. Dès qu'il y a des options, on passe au package flag.

Des drapeaux typés avec le package flag

Le package flag (dans la bibliothèque standard) déclare des options typées : une valeur par défaut, un texte d'aide, et Go se charge de l'analyse et des conversions.

Chaque flag.String/Int/Bool renvoie un pointeur — d'où le *nom pour lire la valeur après flag.Parse(). Les formes -nom=Go, -nom Go et --nom Go sont toutes acceptées ; un booléen s'active par sa seule présence (-maj).

Positionnels, aide et valeurs par défaut

Après flag.Parse(), les arguments qui ne sont pas des drapeaux (les positionnels, typiquement des noms de fichiers) sont dans flag.Args(). Et l'aide (-h ou --help) est générée automatiquement à partir des textes que tu as fournis.

Les trois flux et le code de sortie

Un programme en ligne de commande dialogue par trois flux standard : stdin (l'entrée), stdout (la sortie normale, le résultat) et stderr (les messages d'erreur et de diagnostic). La règle d'or : le résultat exploitable sur stdout, tout le reste (erreurs, logs, progression) sur stderr. En prime, un code de sortie nul signale le succès, non nul l'échec.

Piège fréquent

Écrire les messages d'erreur avec fmt.Println (donc sur stdout) pollue le résultat. Si quelqu'un fait outil | autre-outil, tes messages d'erreur se retrouvent mélangés aux données et cassent la suite du pipe. Les erreurs vont toujours sur os.Stderr. De même, ne fais pas os.Exit au milieu d'une fonction avec des defer en attente : os.Exit saute les defer. Réserve-le à main.

Lire l'entrée standard

Un bon outil Unix sait lire depuis un pipe : os.Stdin est un io.Reader (revois la leçon précédente). On le parcourt avec un bufio.Scanner, exactement comme un fichier.

Astuce

Un outil vraiment souple lit un fichier si on lui en passe un, sinon l'entrée standard : var r io.Reader = os.Stdin; if len(flag.Args()) > 0 { r, _ = os.Open(flag.Args()[0]) }. Grâce à io.Reader, le reste du code ne change pas d'une ligne.

Les sous-commandes

Les gros outils (git commit, docker run) ont des sous-commandes, chacune avec ses propres drapeaux. On les construit avec flag.NewFlagSet : un jeu de drapeaux par sous-commande, sélectionné selon le premier argument.

Pour aller plus loin

Le package flag couvre l'immense majorité des besoins. Pour un outil riche (sous-commandes imbriquées, auto-complétion du shell, aide colorée), l'écosystème propose Cobra (celui de Docker, Kubernetes et GitHub CLI) et urfave/cli. Pense aussi à intégrer un numéro de version à la compilation via -ldflags "-X main.version=1.2.3", et à respecter les conventions POSIX pour les options courtes/longues.

Un cas réel : l'outil qui cassait les pipes

Cas réel

Une équipe avait écrit un petit outil Go qui extrayait des identifiants d'un export et les affichait, un par ligne, pour les enchaîner : extraire donnees.csv | traiter. En développement tout allait bien. En production, l'étape suivante recevait par moments des lignes parasites du genre « attention : ligne 4210 ignorée » — des messages de diagnostic écrits sur stdout avec fmt.Println, qui se mélangeaient aux vrais identifiants et faisaient planter le script en aval. Le correctif : router tous les diagnostics vers os.Stderr (fmt.Fprintln(os.Stderr, …)), et renvoyer os.Exit(1) quand un fichier était illisible, pour que l'orchestrateur détecte l'échec. Depuis, stdout ne porte que la donnée, et le pipe est propre. C'est LA convention Unix : la sortie standard est un canal de données, pas de bavardage.

Antisèche

Glossaire

os.Args
La []string des arguments bruts du programme ; os.Args[0] est le nom de l'exécutable, les arguments réels commencent à l'index 1.
Package flag
Analyseur d'options de la bibliothèque standard : déclare des drapeaux typés (String/Int/Bool) avec défaut et aide, remplis par flag.Parse().
Drapeau (flag)
Une option nommée passée en ligne de commande, par exemple -fois=3 ou -v ; les fonctions flag.* renvoient un pointeur vers sa valeur.
Argument positionnel
Un argument sans nom (souvent un fichier), récupéré via flag.Args() après l'analyse des drapeaux.
stdin / stdout / stderr
Les trois flux standard : entrée, sortie du résultat, sortie des erreurs. Exposés par os.Stdin, os.Stdout, os.Stderr.
Code de sortie
L'entier rendu par le programme (os.Exit(n)) : 0 signale un succès, toute autre valeur un échec, testé par le shell ou l'orchestrateur.
os.Exit
Termine immédiatement le programme avec un code ; attention, il saute les defer, à réserver au niveau de main.
Sous-commande
Une commande secondaire avec ses propres drapeaux (comme git commit), construite avec flag.NewFlagSet.

Récap et vérification

  • os.Args donne les arguments bruts ; le package flag gère des drapeaux typés avec défaut, aide et positionnels (flag.Args()).
  • Le résultat va sur stdout, les erreurs sur stderr ; un code de sortie non nul signale l'échec.
  • os.Stdin est un io.Reader : on lit un pipe avec un bufio.Scanner, comme un fichier.
  • Les sous-commandes se construisent avec flag.NewFlagSet, une par verbe de l'outil.
  • os.Exit saute les defer : on le garde pour main.

Vérifie ta compréhension

  1. Pourquoi les messages d'erreur d'un outil doivent-ils partir sur stderr plutôt que sur stdout ?
  2. Après flag.Parse(), où récupères-tu les noms de fichiers passés sans option ?
  3. Pourquoi éviter os.Exit ailleurs que dans main quand des defer sont en jeu ?

Mini-projet fil rouge — un inventaire

Pour clore ce cours, écrivons un petit inventaire. Il réunit un type structuré, une méthode à récepteur, une slice, la boucle for ... range et fmt.Printf — un condensé idiomatique de Go.

Ce que tu vas construire

Un type Produit (nom, prix, quantité) avec une méthode Valeur(), une slice de produits, et un calcul du total du stock affiché ligne par ligne.

Étapes

Le type Produit

Définis une struct avec Nom string, Prix float64 et Qte int.

Une méthode sur le type

Ajoute func (p Produit) Valeur() float64 qui renvoie Prix * Qte (pense à convertir Qte en float64).

Une slice de produits

Construis une []Produit et initialise-la avec quelques articles.

Parcourir avec range

Écris total(produits []Produit) qui accumule les valeurs avec for _, p := range produits.

Afficher

Dans main, affiche chaque produit puis le total avec fmt.Printf("%.2f", ...).
