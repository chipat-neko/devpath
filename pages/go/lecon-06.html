Module 02 · Go idiomatique — Leçon 06

La gestion d'erreurs

~28 min Intermédiaire Leçon 5 recommandée

À la fin de cette leçon, tu sauras

  • savoir renvoyer et vérifier une error avec le pattern if err != nil ;
  • savoir créer, envelopper avec %w et inspecter une erreur via errors.Is et errors.As ;
  • savoir libérer une ressource proprement avec defer (ordre LIFO) ;
  • savoir quand réserver panic/recover aux cas vraiment exceptionnels.
Sommaire de la leçon

En Go, il n'y a pas d'exceptions ni de try/catch. Une fonction qui peut échouer te le dit franchement : elle renvoie une valeur d'erreur en plus de son résultat. À toi de la vérifier. Ça paraît verbeux au début, mais c'est ce qui rend le flot du programme explicite : tu vois, ligne par ligne, ce qui peut mal tourner et ce que tu en fais.

Dans cette leçon, on couvre le pattern if err != nil, le type error, l'enveloppement (%w) avec errors.Is/errors.As, les erreurs sentinelles, le mot-clé defer pour le nettoyage, et enfin panic/recover — à réserver aux vrais cas exceptionnels.

Pas d'exceptions : l'erreur est une valeur de retour

La convention en Go : si une fonction peut échouer, elle renvoie l'erreur en dernier retour, avec le type error. Quand tout va bien, cette valeur vaut nil.

Note la signature : func Diviser(a, b float64) (float64, error). Le résultat « utile » d'abord, l'erreur ensuite. C'est l'ordre que toute la bibliothèque standard respecte. En cas d'échec, on renvoie une valeur « neutre » pour le résultat (ici 0) et l'erreur ; en cas de succès, le vrai résultat et nil.

Note

Quand une fonction échoue, le résultat renvoyé à côté de l'erreur n'a en général aucune valeur exploitable. Ne l'utilise qu'après avoir vérifié que l'erreur est nil.

Le pattern omniprésent : if err != nil

Juste après un appel qui peut échouer, tu vérifies l'erreur. Si elle n'est pas nil, tu réagis : souvent tu la renvoies à l'appelant.

Ce bloc if err != nil { return err }, tu vas l'écrire des milliers de fois. C'est le rythme de Go : appel, vérification, suite. Le « chemin heureux » reste aligné à gauche, sans indentation profonde, ce qui rend le code facile à suivre de haut en bas.

Astuce

Vérifie l'erreur immédiatement après l'appel, avant toute autre instruction. Gérer l'échec tôt évite d'utiliser par mégarde un résultat invalide.

Envelopper une erreur avec %w

Quand tu remontes une erreur, ajoute du contexte sans perdre l'erreur d'origine. C'est l'enveloppement (wrapping) : fmt.Errorf avec le verbe %w.

Pour inspecter une erreur enveloppée, n'utilise pas == (qui ne regarde que la couche extérieure). Utilise errors.Is (compare à une erreur cible à travers les couches) et errors.As (récupère une erreur d'un type donné dans la chaîne).

errors.Is répond true parce qu'il déballe les couches une à une jusqu'à retrouver ErrPermission. La comparaison ==, elle, ne voit que l'enveloppe extérieure et répond false.

Les erreurs sentinelles

Une erreur sentinelle est une variable d'erreur exportée et stable, que l'appelant peut tester précisément. La bibliothèque standard en regorge (io.EOF, sql.ErrNoRows…). Convention de nom : préfixe Err.

L'appelant teste errors.Is(err, ErrIntrouvable) pour réagir au cas précis, même si l'erreur a été enveloppée en chemin. C'est plus robuste que de comparer des chaînes de texte.

defer : différer le nettoyage

defer reporte l'exécution d'un appel jusqu'à la sortie de la fonction englobante — que la sortie soit normale ou via une erreur. Idéal pour libérer une ressource juste après l'avoir obtenue, sans risquer de l'oublier.

Astuce

Place ton defer f.Close() juste après avoir vérifié que l'ouverture a réussi. Ainsi la ressource est libérée par tous les chemins de retour, présents et futurs.

panic et recover : pour l'exceptionnel

Une panic interrompt le flot normal et remonte la pile en exécutant les defer, jusqu'à faire planter le programme — sauf si un recover (placé dans un defer) la rattrape. Réserve ça aux situations vraiment anormales : un bug irrécupérable, un invariant violé. Pour une erreur attendue (fichier absent, saisie invalide), utilise une error, pas panic.

recover ne fonctionne que dans une fonction différée. Ici il transforme la panique en error renvoyée proprement, et le programme poursuit. C'est un pattern utile aux frontières (un serveur web qui ne doit pas tomber à cause d'une requête), mais pas un remplaçant du retour d'erreur classique.

Pièges fréquents

Piège fréquent

Ignorer une erreur. Écrire r, _ := Diviser(a, b) jette l'erreur à la poubelle et te laisse avec un résultat possiblement faux. Sauf cas vraiment anodin et conscient, vérifie toujours err. go vet et les linters signalent ces oublis.

Piège fréquent

Comparer avec == au lieu d'errors.Is. Dès qu'une erreur a pu être enveloppée (%w), err == ErrX renvoie false. Utilise errors.Is(err, ErrX) qui traverse les couches.

Piège fréquent

defer dans une boucle. Un defer ne s'exécute qu'à la sortie de la fonction, pas de l'itération. Dans une boucle qui ouvre mille fichiers, les mille Close s'accumulent jusqu'à la fin — fuite garantie. Extrais le corps dans une fonction, ou ferme explicitement à chaque tour.

Autres pièges : oublier complètement le defer Close (fuite de descripteurs) ; remonter une erreur sans contexte (return err nu partout rend le diagnostic pénible — enveloppe avec %w) ; et utiliser panic pour une erreur attendue, ce qui casse le contrat normal des appelants.

Pour aller plus loin

Pour aller plus loin

errors.Join (Go 1.20) combine plusieurs erreurs en une seule, et errors.Is sait inspecter chacune. Tu peux aussi définir tes erreurs personnalisées : un struct qui implémente Error() string, récupérable ensuite via errors.As pour lire ses champs. Enfin, pour les messages et le diagnostic, regarde le logging structuré avec le paquet log/slog (Go 1.21).

Un cas réel : l'erreur nue qui coûtait des heures de diagnostic

Cas réel

Une équipe exploitait une API de paiement écrite en Go. Chaque couche remontait l'erreur avec un return err nu. En production, quand un virement échouait, les journaux n'affichaient qu'une ligne cryptique — EOF ou context deadline exceeded — sans dire quelle étape (validation ? banque ? base de données ?) avait lâché. Diagnostiquer un incident prenait des heures de fouille. Le correctif a tenu en une règle : envelopper à chaque étage avec fmt.Errorf("étape X : %w", err) et journaliser avec log/slog. Désormais un message ressemble à « règlement : appel banque : délai dépassé » : la chaîne raconte tout le trajet, et errors.Is(err, ErrReseauTemporaire) permet de brancher une reprise automatique sur les pannes réseau passagères. Le temps moyen de diagnostic est tombé de quelques heures à quelques minutes.

Antisèche

Glossaire

error
Interface standard { Error() string } : tout type qui possède cette méthode est une erreur. Renvoyée en dernière position d'une fonction faillible.
nil
Valeur « absence d'erreur » : une opération réussie renvoie nil. On teste if err != nil avant d'exploiter le résultat.
Enveloppement (wrapping)
Ajout de contexte autour d'une erreur avec le verbe %w de fmt.Errorf, sans perdre l'erreur d'origine.
errors.Is
Teste si une erreur (même enveloppée) correspond à une cible donnée, en déballant les couches ; remplace == pour les sentinelles.
errors.As
Cherche dans la chaîne une erreur d'un type donné et l'extrait dans une variable, pour lire ses champs.
Erreur sentinelle
Variable d'erreur exportée et stable (var ErrX = errors.New(…)) que l'appelant reconnaît via errors.Is. Convention : préfixe Err.
defer
Diffère un appel jusqu'à la sortie de la fonction englobante (ordre LIFO) ; idéal pour libérer une ressource à coup sûr.
panic / recover
panic interrompt le flot et remonte la pile ; recover, dans un defer, la rattrape. Réservés à l'exceptionnel, pas aux erreurs attendues.

Récap et vérification

  • Une fonction faillible renvoie l'erreur en dernier : func f() (T, error) ; nil signifie « tout va bien ».
  • Le pattern if err != nil { return err } se place juste après l'appel ; garde le chemin heureux aligné à gauche.
  • error est l'interface { Error() string } ; on crée une erreur avec errors.New ou fmt.Errorf.
  • Enveloppe avec %w pour ajouter du contexte, puis inspecte avec errors.Is (cible) et errors.As (type).
  • Les sentinelles (var ErrX = errors.New(...)) se testent avec errors.Is, jamais avec == si l'erreur a pu être enveloppée.
  • defer libère les ressources à la sortie de la fonction, en ordre LIFO ; panic/recover restent pour l'exceptionnel.

Vérifie ta compréhension

  1. Dans quel ordre place-t-on le résultat et l'erreur dans la signature d'une fonction Go, et que vaut l'erreur en cas de succès ?
  2. Pourquoi préférer errors.Is(err, ErrX) à err == ErrX ?
  3. Si tu ouvres un fichier dans une boucle for et écris defer f.Close(), quand les fermetures ont-elles lieu, et quel est le risque ?
