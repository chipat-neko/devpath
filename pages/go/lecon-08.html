Module 03 · Go en pratique — Leçon 08

Packages, modules et bibliothèque standard

~31 min Intermédiaire Leçon 7 recommandée

À la fin de cette leçon, tu sauras

  • savoir créer des packages et contrôler la visibilité avec les noms exportés (Majuscule) ou privés (minuscule) ;
  • savoir initialiser un module avec go mod init et gérer ses dépendances (go get, go mod tidy) ;
  • savoir importer la bibliothèque standard et sérialiser des données avec encoding/json ;
  • savoir structurer un projet Go typique (cmd/, internal/) et lire sa documentation.
Sommaire de la leçon

Jusqu'ici, tu as écrit du code dans un seul fichier. Mais un vrai projet, c'est des dizaines de fichiers répartis dans des dossiers, qui s'appuient sur des bibliothèques externes et sur la riche boîte à outils fournie avec Go. Dans cette leçon, tu vas apprendre à organiser ton code en packages, à le rendre installable et versionné grâce aux modules, et à tirer parti de la bibliothèque standard de Go, réputée comme l'une des meilleures du marché.

Go a fait des choix radicalement simples ici : un dossier = un package, des noms qui commencent par une majuscule sont publics, le reste est privé. Pas de fichiers de configuration tentaculaires. Voyons ça.

Les packages : regrouper des fichiers

Un package est un ensemble de fichiers .go situés dans le même dossier et déclarant le même nom de package en première ligne. Le package main est spécial : c'est celui qui produit un exécutable. Tous les autres sont des bibliothèques réutilisables.

La règle de visibilité est purement typographique : un identifiant (fonction, type, variable, constante, champ) qui commence par une Majuscule est exporté (visible hors du package) ; en minuscule, il est privé au package.

Note

Le nom du package (ici geometrie) est ce qu'on tape pour l'utiliser : geometrie.Aire(2). Par convention, on lui donne un nom court, en minuscules, sans underscore ni majuscule.

Les modules : versionner et partager

Un module est l'unité de distribution et de versionnage : c'est une arborescence de packages avec, à sa racine, un fichier go.mod. On le crée avec go mod init, suivi du chemin du module (souvent une URL, même fictive, pour garantir l'unicité).

Crée le fichier go.mod à la racine du projet.

Pour ajouter une dépendance externe, on utilise go get, puis go mod tidy qui fait le ménage : il ajoute ce qui manque et retire ce qui n'est plus importé.

Astuce

Lance go mod tidy avant chaque commit. Il garantit que go.mod reflète exactement les imports de ton code, ni plus, ni moins. Le fichier go.sum (sommes de contrôle, généré par go get et go mod tidy) ne se modifie jamais à la main.

Importer : stdlib et chemins de module

On importe avec le mot-clé import. Les packages de la bibliothèque standard ont un chemin court (fmt, strings, encoding/json) ; tes propres packages se référencent par chemin de module + sous-dossier.

Note

En Go, un import non utilisé est une erreur de compilation, pas un avertissement. C'est volontaire : le code reste propre. gofmt (et ton éditeur) range et regroupe les imports automatiquement.

Tour de la bibliothèque standard

La stdlib couvre énormément de besoins sans aucune dépendance externe. Quelques incontournables :

  • fmt : affichage et formatage (Println, Printf, Sprintf).
  • strings / strconv : manipulation de texte et conversions (strconv.Atoi, Itoa).
  • os : système (arguments, variables d'environnement, fichiers).
  • time : dates, durées, horodatage.
  • errors : création et inspection d'erreurs.
  • sort, et surtout slices / maps (génériques, modernes) pour trier et manipuler les collections.
  • encoding/json : sérialisation JSON.
  • net/http : client et serveur HTTP complets, en standard.

Les packages slices et maps (Go 1.21+) s'appuient sur les génériques : une seule fonction slices.Sort trie n'importe quel type ordonné, sans que tu écrives le moindre comparateur.

Un exemple JSON avec encoding/json

Le package encoding/json convertit des structs vers du JSON (Marshal) et inversement (Unmarshal). Le lien entre les champs Go et les clés JSON se règle avec des tags de struct. Important : seuls les champs exportés (Majuscule) sont sérialisés.

Piège fréquent

Un champ en minuscule (email string) ne sera jamais sérialisé en JSON : il est privé, donc invisible pour encoding/json. Si une clé n'apparaît pas dans ta sortie, vérifie d'abord la majuscule, puis le tag.

La structure d'un projet Go typique

Go n'impose pas d'arborescence, mais une convention s'est imposée dans la communauté :

cmd/ regroupe les points d'entrée (un dossier par binaire), internal/ contient le code que le compilateur interdit d'importer depuis l'extérieur du module, et pkg/ (optionnel) regroupe les bibliothèques publiques. Pour un petit projet, ne sur-structure pas : un seul main.go suffit souvent.

La documentation : go doc et commentaires

En Go, la documentation est le code : un commentaire placé juste avant une déclaration exportée devient sa doc officielle. La commande go doc l'affiche en console, et l'outil génère automatiquement la page web sur pkg.go.dev.

Pièges fréquents

Piège fréquent

Le nom de package n'est pas forcément le nom du dossier, mais il est fortement recommandé qu'ils coïncident. Un dossier monpkg/ dont les fichiers déclarent package autre compile, mais sème la confusion à l'import. Garde-les identiques.

Autres erreurs classiques :

  • Oublier go mod tidy : ton go.mod liste des dépendances fantômes, ou le build casse chez un collègue.
  • Import non utilisé : erreur de compilation. Supprime-le (ou préfixe par _ si tu n'en veux que les effets de bord).
  • Export par erreur : une fonction interne nommée Helper devient publique sans que tu le veuilles. Mets une minuscule par défaut.
  • Tags JSON mal cassés : json:"Nom" au lieu de json:"nom" change la clé produite. Vérifie la casse attendue par l'API distante.
  • Cycle d'import : si le package A importe B et que B importe A, Go refuse de compiler. C'est un signal que ton découpage est mauvais : extrais le code commun dans un troisième package.

Pour aller plus loin

Pour aller plus loin

Le dossier internal/ est une vraie barrière imposée par le compilateur : un package sous internal/ n'est importable que par du code partageant son module parent. Pratique pour cacher des détails d'implémentation. Côté versions, Go suit le versionnage sémantique (v1.2.3) ; à partir de v2, le numéro majeur entre même dans le chemin d'import. Explore aussi le vendoring (go mod vendor, qui copie les dépendances dans le projet) et les workspaces (go work init) pour travailler sur plusieurs modules locaux en même temps. Publier un module se résume souvent à pousser un dépôt Git public et à le taguer.

Un cas réel : l'API qui renvoyait des champs vides

Cas réel

Une équipe migrait un service vers Go. Leur point d'accès /profil renvoyait un JSON où le prénom et l'e-mail apparaissaient bien, mais le champ telephone restait toujours absent. Aucune erreur, aucun log. La cause : dans la struct, le champ avait été écrit telephone string (minuscule) au lieu de Telephone. Comme encoding/json travaille par réflexion et ne voit que les champs exportés, il ignorait purement et simplement ce champ privé. Le correctif : passer l'initiale en majuscule et ajouter le tag json:"telephone". La règle à retenir : « une clé manque dans mon JSON ? je vérifie d'abord la majuscule, ensuite le tag. »

Glossaire

Package
Ensemble de fichiers .go d'un même dossier partageant la ligne package x. main produit un exécutable ; les autres sont des bibliothèques.
Module
Unité de distribution et de versionnage : une arborescence de packages avec un go.mod à la racine. Créé par go mod init.
go.mod / go.sum
go.mod déclare le chemin du module et ses dépendances ; go.sum stocke leurs sommes de contrôle. Jamais édités à la main.
Identifiant exporté
Nom commençant par une majuscule, visible hors de son package ; en minuscule, il reste privé.
go mod tidy
Synchronise go.mod/go.sum avec les imports réels : ajoute ce qui manque, retire ce qui ne sert plus.
Tag de struct
Métadonnée entre accents graves sur un champ (json:"nom") qui pilote, par exemple, le nom de la clé JSON produite.
Marshal / Unmarshal
Fonctions d'encoding/json : Marshal convertit une valeur Go en JSON, Unmarshal fait l'inverse. Seuls les champs exportés comptent.
internal/
Dossier spécial dont les packages ne sont importables que par le code du même module : une barrière imposée par le compilateur.

Récap et vérification

  • Un package = un dossier de fichiers .go partageant le même package x ; Majuscule = exporté, minuscule = privé.
  • Un module se crée avec go mod init chemin et se maintient avec go get + go mod tidy.
  • On importe la stdlib par nom court et ses propres packages par chemin de module + dossier ; un import inutilisé est une erreur.
  • La stdlib couvre l'essentiel : fmt, strings, strconv, os, time, errors, slices, encoding/json, net/http.
  • encoding/json sérialise les champs exportés, avec des tags pour nommer les clés.

Vérifie ta compréhension

  1. Pourquoi une fonction calcul() en minuscule ne peut-elle pas être appelée depuis un autre package ?
  2. Quelle commande synchronise go.mod avec les imports réellement présents dans ton code ?
  3. Dans une struct, quels champs encoding/json va-t-il ignorer lors d'un Marshal, et pourquoi ?
