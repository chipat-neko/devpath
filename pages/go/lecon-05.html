Module 02 · Go idiomatique — Leçon 05

Interfaces et polymorphisme

~33 min Intermédiaire Leçon 4 recommandée

À la fin de cette leçon, tu sauras

  • comprendre qu'une interface Go est satisfaite implicitement, sans implements ;
  • faire du polymorphisme avec des variables et slices d'interface, et manipuler any via type assertion et type switch ;
  • implémenter les interfaces idiomatiques de la stdlib comme fmt.Stringer et io.Writer ;
  • appliquer l'idiome « accept interfaces, return structs » et garder des interfaces petites, définies côté consommateur.
Sommaire de la leçon

En Go, les interfaces sont l'outil principal d'abstraction. Mais elles ne ressemblent à rien de ce que tu connais peut-être en Java ou C# : pas de mot-clé implements, pas de hiérarchie de classes. Une interface décrit un comportement (un ensemble de méthodes), et tout type qui possède ces méthodes la satisfait automatiquement. C'est simple, discret, et incroyablement puissant.

Dans cette leçon, tu vas découvrir comment Go fait du polymorphisme sans héritage, comment manipuler des valeurs de type inconnu avec any et les type switch, et surtout quelles sont les règles idiomatiques pour écrire des interfaces que les Gophers approuvent : petites, définies du bon côté, et utilisées avec parcimonie.

Une interface, c'est un ensemble de méthodes

Une interface déclare ce qu'un type doit savoir faire, pas ce qu'il est. On liste des signatures de méthodes, rien d'autre.

La variable f est de type Forme : on ne peut appeler dessus que les méthodes déclarées dans l'interface. Peu importe le type concret rangé dedans, le contrat est respecté.

L'implémentation implicite : le « duck typing » statique

Voici le point central. Rectangle n'a écrit nulle part qu'il implémente Forme. Il a juste une méthode Aire() float64, et cela suffit. Le compilateur vérifie la conformité au moment de l'affectation.

La ligne var _ Forme = Cercle{} est une astuce idiomatique : elle force le compilateur à vérifier que Cercle satisfait bien Forme, et échoue à la compilation sinon. Le _ jette la valeur. Si on appelle ça « duck typing statique », c'est parce que la vérification a lieu à la compilation (sécurité du typage fort) tout en restant implicite (souplesse).

Note

L'absence de implements a une conséquence forte : un type peut satisfaire une interface définie dans un autre paquet (même la stdlib) sans le savoir. Le couplage est minimal.

Le polymorphisme : un slice de Forme

Comme plusieurs types satisfont Forme, on peut les ranger ensemble et les traiter uniformément. C'est le polymorphisme à la Go.

La fonction TotalAires ne connaît ni Rectangle ni Cercle. Elle parle uniquement le langage de Forme. Ajoute un Triangle demain : aucune ligne de TotalAires ne change.

L'interface vide : interface{} et any

Une interface sans aucune méthode est satisfaite par tous les types. On l'écrivait interface{} ; depuis Go 1.18, any en est un alias officiel et plus lisible.

any peut tout contenir, mais en échange tu perds tout typage : tu ne peux plus appeler de méthode spécifique dessus tant que tu n'as pas récupéré le type concret. C'est puissant mais à manier avec retenue (voir les pièges).

Type assertions et type switch

Pour extraire le type concret d'une valeur any (ou d'une interface), on utilise une type assertion. Utilise toujours la forme à deux retours v, ok := : la forme à un seul retour panique si le type ne correspond pas.

Quand tu dois discriminer plusieurs types, le type switch est l'outil idiomatique. La variable v prend automatiquement le bon type dans chaque branche.

Les interfaces idiomatiques de la stdlib

Go fournit des interfaces minuscules et omniprésentes. La plus simple : fmt.Stringer, qui définit comment un type s'affiche.

Autres stars de la stdlib : io.Reader (une méthode Read) et io.Writer (une méthode Write). Elles sont si petites qu'elles se combinent partout : copier un fichier, une réponse HTTP ou un buffer mémoire passe par les mêmes interfaces.

« Accept interfaces, return structs »

C'est la maxime la plus citée de Go. Une fonction devrait accepter des interfaces (pour rester flexible sur ses entrées) et retourner des types concrets (pour donner au consommateur toute la richesse du type). Et garde tes interfaces petites : une ou deux méthodes, idéalement.

Et surtout : définis l'interface du côté qui la consomme, pas du côté qui l'implémente. Le code qui a besoin d'un io.Reader déclare ce dont il a besoin ; les types qui le fournissent n'ont même pas à le savoir.

Pièges fréquents

Piège fréquent

La type assertion sans , ok panique si le type ne correspond pas. s := x.(string) fait planter le programme quand x n'est pas une chaîne. Utilise s, ok := x.(string) sauf si tu es absolument certain du type.

Piège fréquent

L'interface nil n'est pas une valeur nil dans une interface. Une interface qui contient un pointeur nil (avec un type concret non-nil) n'est pas égale à nil. C'est le bug le plus célèbre de Go : retourner un *MonErreur nil via une variable error rend la comparaison err != nil vraie. Retourne nil littéralement, jamais une variable de pointeur nil typée.

Piège fréquent

Grosses interfaces et abus de any : une interface à dix méthodes est difficile à satisfaire et à tester ; préfère plusieurs petites interfaces. Et chaque any que tu écris est un trou dans ton typage — depuis Go 1.18, les génériques remplacent avantageusement la plupart des usages de any.

Pour aller plus loin

Pour aller plus loin

Embedding d'interfaces : on compose de petites interfaces en plus grandes, comme io.ReadWriter qui embarque io.Reader et io.Writer. Génériques vs any : func Max[T cmp.Ordered](a, b T) T garde le typage là où any le perdait. Explore aussi errors.As qui fait un type-switch sur les erreurs proprement.

Un cas réel : l'erreur nil qui rejetait toutes les requêtes valides

Cas réel

Un service Go exposait func valider(...) error qui déclarait var e *ValidationError et finissait par return e. Quand la validation réussissait, e restait nil… mais côté appelant, if err := valider(...); err != nil se déclenchait toujours, même sur une entrée parfaitement valide : l'interface error portait le type *ValidationError (non nil) avec une valeur pointeur nil, donc elle n'était pas égale à nil. Résultat : toutes les requêtes valides repartaient en 400 Bad Request. Le correctif : renvoyer nil littéralement quand il n'y a pas d'erreur (et ne jamais renvoyer une variable de pointeur d'erreur qui pourrait être nil). Aujourd'hui, go vet repère certains de ces cas — mais c'est resté le piège n°1 des débutants en Go.

Antisèche

Glossaire

Interface
Type qui décrit un comportement sous forme d'un ensemble de signatures de méthodes, sans dire ce qu'un type est.
Satisfaction implicite
En Go, un type satisfait une interface dès qu'il possède ses méthodes ; aucun mot-clé implements. La conformité est structurelle et vérifiée à la compilation.
Polymorphisme
Traiter uniformément des types différents à travers une même interface ; en Go, il passe par les interfaces, pas par l'héritage de classes.
any (interface{})
Interface sans méthode, satisfaite par tous les types ; pratique mais fait perdre le typage tant qu'on n'a pas récupéré le type concret.
Type assertion
Extraction du type concret d'une valeur d'interface : v, ok := x.(T). La forme sans ok panique si le type ne correspond pas.
Type switch
Aiguillage sur le type dynamique d'une valeur (switch v := x.(type)) ; dans chaque branche, v prend automatiquement le type correspondant.
fmt.Stringer
Interface de la stdlib à une méthode String() string ; en l'implémentant, un type contrôle son affichage par fmt.
Interface nil
Une valeur d'interface est une paire (type, valeur) ; elle ne vaut nil que si les deux le sont. Une interface portant un pointeur nil typé n'est pas nil.

Récap et vérification

  • Une interface est un ensemble de méthodes ; un type la satisfait implicitement dès qu'il les possède (pas de implements).
  • Le polymorphisme passe par des variables ou slices d'interface, traités uniformément.
  • any (alias de interface{}) contient tout, mais on récupère le type concret via type assertion v, ok := x.(T) ou type switch.
  • fmt.Stringer, io.Reader et io.Writer sont les interfaces minuscules à connaître.
  • Idiomes : accepte des interfaces, retourne des structs ; garde-les petites ; définis-les côté consommateur.
