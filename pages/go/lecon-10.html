Module 03 · Go en pratique — Leçon 10

Construire une application et aller plus loin

~34 min Intermédiaire Leçon 9 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire un petit serveur HTTP qui renvoie du JSON avec net/http ;
  • savoir gérer la configuration avec flag et les variables d'environnement, et arrêter le serveur proprement via context et les signaux ;
  • savoir cross-compiler un binaire unique avec GOOS/GOARCH pour le déployer (Docker, Linux) ;
  • connaître les bonnes pratiques Go et les briques majeures de l'écosystème (frameworks, CLI, base de données, gRPC).
Sommaire de la leçon

Tu connais maintenant la syntaxe, les types, les interfaces, les erreurs et les goroutines. Il est temps d'assembler tout ça en un vrai programme. Et quoi de mieux qu'un domaine où Go brille particulièrement : les services web. Avec la seule bibliothèque standard, tu écris un serveur HTTP solide en quelques lignes, sans installer le moindre framework.

Dans cette leçon, on construit un petit serveur qui renvoie du JSON, on le rend configurable, on l'arrête proprement, puis on le compile en un binaire unique prêt à déployer. On termine par un tour de l'écosystème et un récap du parcours.

Un serveur HTTP qui renvoie du JSON

Le paquet net/http contient tout le nécessaire. Tu enregistres des handlers (des fonctions qui répondent à une route) avec http.HandleFunc, puis tu lances le serveur. Pour produire du JSON, on encode une struct avec encoding/json. Les balises de champ (json:"...") contrôlent les noms en sortie.

Un serveur web complet en une trentaine de lignes, sans dépendance externe.

Note

Le nil passé à ListenAndServe utilise le routeur global par défaut (http.DefaultServeMux), celui que remplit http.HandleFunc. Pour un projet sérieux, tu créeras plutôt ton propre http.ServeMux et un http.Server explicite, comme dans la section sur l'arrêt propre.

Configurer avec les flags et les variables d'environnement

Un programme utile ne code pas son port en dur. Le paquet flag de la stdlib lit les arguments de la ligne de commande ; les variables d'environnement (os.Getenv) servent surtout en conteneur. Un schéma courant : la variable d'env fournit la valeur par défaut, le flag permet de la surcharger.

flag.String renvoie un pointeur ; on le déréférence avec *addr après flag.Parse().

Astuce

Pour des CLI riches (sous-commandes, flags imbriqués) ou de la config par fichier, l'écosystème propose cobra et viper. Mais pour un service web simple, flag + os.Getenv suffisent largement. Reste simple.

Arrêter le serveur proprement

Quand on coupe un service (Ctrl+C, ou un orchestrateur qui envoie SIGTERM), il faut finir les requêtes en cours avant de fermer. On écoute les signaux du système, et on appelle Shutdown qui draine les connexions. Le context porte une limite de temps : si le drainage traîne, on abandonne.

On reçoit le signal via signal.NotifyContext, on bloque sur <-ctx.Done(), puis on draine avec Shutdown.

Note

ListenAndServe renvoie toujours une erreur non nulle quand on l'arrête. À la fermeture normale, c'est http.ErrServerClosed : on l'ignore avec errors.Is pour ne pas crasher le programme par erreur.

Le context : un fil conducteur pour l'annulation

Le type context.Context traverse tout Go moderne. Il transporte une demande d'annulation et une échéance à travers les appels. Par convention, c'est le premier paramètre d'une fonction, nommé ctx. Dans un handler, r.Context() est annulé si le client se déconnecte : tu peux ainsi abandonner un travail inutile.

Le select écoute deux channels : le premier qui parle gagne. Ici, le travail ou l'annulation.

Compiler pour plusieurs plateformes

Un programme Go se compile en un binaire unique, sans runtime à installer sur la machine cible. Mieux : tu peux compiler pour un autre système depuis le tien en réglant deux variables d'environnement, GOOS (le système) et GOARCH (l'architecture).

Aucun cross-compilateur à installer : la chaîne d'outils Go gère tout en natif.

Astuce

Pour Docker, ce binaire statique unique permet des images minuscules. Compile avec CGO_ENABLED=0, copie le seul binaire dans une image scratch ou distroless : tu obtiens une image de quelques mégaoctets, sans système d'exploitation complet ni dépendances.

Les bonnes pratiques Go

Go a une culture forte de la simplicité. Quelques règles qui font les bons programmes Go :

  • Gère toutes les erreurs. Pas de _ = faire() qui ignore une erreur sans raison. Si une fonction renvoie error, traite-la ou propage-la avec du contexte (fmt.Errorf("lecture config : %w", err)).
  • Petites interfaces. « Accept interfaces, return structs » : accepte une interface minimale en paramètre (souvent une seule méthode, comme io.Reader), mais renvoie un type concret. L'appelant garde ainsi toute l'information.
  • Formate et vérifie. gofmt (intégré à go fmt) impose un style unique : aucune discussion sur les espaces. go vet repère les bugs courants. Lance-les avant chaque commit.
  • Évite la sur-abstraction. N'ajoute pas une interface « au cas où ». En Go, on duplique un peu plutôt que d'introduire une mauvaise abstraction. Le code direct est lisible.

Trois commandes à connaître par cœur ; ./... signifie « ce paquet et tous les sous-paquets ».

L'écosystème Go

La stdlib couvre énormément, mais l'écosystème offre des briques éprouvées quand un besoin grandit :

  • Frameworks web : chi (léger, fidèle à net/http), Gin et Echo (plus complets, routage et middlewares confortables). Commence sans, ajoute-en un seulement si la stdlib te freine.
  • CLI : cobra pour des outils en ligne de commande structurés (c'est ce qui propulse kubectl ou gh), souvent associé à viper pour la config.
  • Base de données : database/sql (stdlib) avec un pilote (pgx pour PostgreSQL), ou un générateur de code comme sqlc. Les ORM existent (GORM) mais sont moins idiomatiques.
  • gRPC : pour des API performantes entre services, avec contrats typés (Protocol Buffers). Une référence dès qu'on assemble plusieurs microservices.

Note

Depuis Go 1.21, la stdlib inclut log/slog pour des logs structurés (JSON, niveaux). Avant d'ajouter une bibliothèque de log tierce, regarde slog : il couvre la plupart des besoins d'observabilité de base.

Pièges fréquents

Piège fréquent

Dégainer un gros framework trop tôt. Pour une poignée de routes, net/http suffit. Ajouter Gin « par habitude » alourdit le binaire et te lie à une API tierce sans bénéfice réel. Mesure le besoin avant d'ajouter une dépendance.

Piège fréquent

Oublier les timeouts du serveur. Un http.Server sans ReadTimeout/WriteTimeout laisse une connexion lente (ou malveillante) immobiliser des ressources indéfiniment. Fixe-les toujours en production.

Piège fréquent

Ignorer le context. Ne pas propager ctx jusqu'aux appels réseau ou base de données, c'est se priver d'annulation et de timeout : une requête abandonnée par le client continue de consommer le serveur. Passe toujours ctx en premier paramètre.

Pour aller plus loin

Pour aller plus loin

Approfondis le context (valeurs, deadlines, propagation) et les patrons de concurrence avancés. Compare Gin, Echo et chi sur un vrai projet. Construis une image Docker à partir d'un binaire statique (scratch/distroless). Découvre gRPC et Protocol Buffers, l'observabilité (logs slog, métriques Prometheus, traçage), et cobra/viper pour outiller une CLI complète.

Un cas réel : d'une image de 900 Mo à un binaire de 12 Mo

Cas réel

Une équipe faisait tourner une petite API interne en Node.js : l'image Docker pesait près de 900 Mo (runtime, gestionnaire de paquets, dépendances système) et chaque déploiement traînait à télécharger puis démarrer. Réécrite en Go, la même API a compilé en un binaire statique unique (CGO_ENABLED=0). Copié seul dans une image distroless, le conteneur est tombé à ~12 Mo, le démarrage à froid sous la seconde, et la surface d'attaque a fondu (plus de shell ni de gestionnaire de paquets dans l'image). Rien de magique : un seul artefact à livrer, aucun runtime à installer sur la cible. Le déploiement, autrefois redouté, est devenu anodin.

Glossaire

Handler
Fonction func(w http.ResponseWriter, r *http.Request) qui répond à une route ; enregistrée par HandleFunc.
ServeMux
Routeur HTTP de la stdlib qui associe des chemins à des handlers. Le nil passé à ListenAndServe utilise le mux global par défaut.
encoding/json
Paquet d'encodage/décodage JSON ; les balises de champ json:"…" contrôlent les noms en sortie.
flag
Paquet stdlib de lecture des arguments de ligne de commande ; flag.String renvoie un pointeur, déréférencé après flag.Parse().
context.Context
Objet qui porte annulation et échéance à travers les appels ; par convention le premier paramètre, nommé ctx.
Arrêt propre
Graceful shutdown : cesser d'accepter de nouvelles connexions et laisser les requêtes en cours finir (via srv.Shutdown) avant de sortir.
GOOS / GOARCH
Variables fixant le système et l'architecture cibles d'une compilation ; permettent la cross-compilation sans outil externe.
Binaire statique
Exécutable sans dépendance système (obtenu avec CGO_ENABLED=0) ; tient seul dans une image scratch/distroless.

Récap et vérification

  • net/http + encoding/json suffisent pour un service web : HandleFunc, un handler, ListenAndServe.
  • On configure avec flag (ligne de commande) et os.Getenv (environnement), souvent combinés.
  • L'arrêt propre passe par signal.NotifyContext, <-ctx.Done() et srv.Shutdown ; on fixe toujours des timeouts.
  • Le context porte l'annulation et l'échéance ; il se met en premier paramètre.
  • Un seul binaire à déployer ; la cross-compilation se règle avec GOOS/GOARCH.
  • Bonnes pratiques : gérer les erreurs, petites interfaces, gofmt/vet, rester simple.

Vérifie ta compréhension

  1. Quelles deux variables d'environnement contrôlent la cible d'une cross-compilation, et à quoi sert chacune ?
  2. Pourquoi ListenAndServe renvoie-t-il http.ErrServerClosed à l'arrêt, et comment éviter de planter à cause de cette erreur ?
  3. Cite deux raisons de fixer des timeouts sur un http.Server en production.
