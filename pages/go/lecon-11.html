Module 04 · Go en profondeur — Leçon 11

Patterns de concurrence et context

~36 min Avancé Cours Go recommandé

À la fin de cette leçon, tu sauras

  • savoir propager annulation, timeout et deadline avec context.Context et ctx.Done() ;
  • savoir structurer un worker pool, un fan-out/fan-in et un pipeline avec des channels ;
  • savoir choisir entre sync.Mutex et un channel, et utiliser errgroup pour erreurs et annulation ;
  • savoir détecter les data races avec -race et éviter les fuites de goroutines.
Sommaire de la leçon

Tu sais lancer des goroutines et faire passer des valeurs dans un channel. Mais en production, la vraie difficulté n'est pas de démarrer du travail concurrent : c'est de l'arrêter proprement, de le borner, de propager une annulation à travers dix appels imbriqués, et de garantir qu'aucune goroutine ne reste bloquée pour l'éternité. C'est exactement ce que cette leçon couvre.

On va structurer la concurrence avec trois patterns éprouvés (worker pool, fan-out/fan-in, pipeline), le package context comme colonne vertébrale de l'annulation, les primitives de sync quand un channel est de trop, et les outils pour traquer ce qui casse vraiment : data races et fuites de goroutines.

Le package context : annuler proprement

Un context.Context est un objet que tu passes en premier argument de toutes tes fonctions qui font du travail potentiellement long. Il porte un signal d'annulation et, éventuellement, une deadline. Quand le contexte est annulé, le channel renvoyé par ctx.Done() se ferme ; toute goroutine qui écoute ce channel peut alors s'arrêter.

Le timeout ferme ctx.Done() ; le select du worker le détecte et sort.

Trois constructeurs à connaître : context.WithCancel(parent) donne un cancel() que tu appelles à la main ; context.WithTimeout(parent, d) annule après une durée ; context.WithDeadline(parent, t) annule à une heure précise. L'annulation est propagée : annuler un contexte parent annule tous ses enfants. ctx.Err() renvoie context.Canceled ou context.DeadlineExceeded.

Note

Appelle defer cancel() même quand tu utilises WithTimeout. Si la fonction se termine avant la deadline, cancel() libère immédiatement la goroutine interne du timer. L'oublier est une petite fuite de ressources que le compilateur ne signale pas (mais go vet, si).

Le worker pool : borner le parallélisme

Lancer une goroutine par tâche marche pour dix tâches, pas pour dix millions. Le worker pool fixe un nombre constant de goroutines qui consomment un channel de tâches et écrivent sur un channel de résultats. Tu contrôles ainsi la charge (CPU, connexions, fichiers ouverts).

Trois workers, cinq tâches ; close(tâches) termine les range, le WaitGroup sait quand fermer les résultats.

Le point clé : c'est le producteur qui ferme tâches (jamais le récepteur), et le channel résultats n'est fermé qu'après que tous les workers ont fini, d'où la goroutine wg.Wait(); close(résultats).

Fan-out / fan-in : distribuer puis fusionner

Le fan-out consiste à brancher plusieurs goroutines sur la même source pour paralléliser. Le fan-in fusionne plusieurs channels en un seul. Combinés, ils forment la base d'un traitement scalable.

Deux carré consomment in en parallèle (fan-out) ; fanIn rassemble les deux flux.

Note

Brancher deux carré sur le même in répartit les valeurs entre eux de façon non déterministe : l'ordre d'arrivée dans fanIn peut varier d'une exécution à l'autre. Seule la somme (91) est stable ici, car l'addition est commutative. Ne suppose jamais un ordre stable en sortie d'un fan-in.

Le pipeline : des étapes reliées par des channels

Un pipeline est une chaîne de fonctions où chacune reçoit un channel d'entrée et renvoie un channel de sortie. Chaque étage est une goroutine indépendante ; les données coulent d'un bout à l'autre. Avantage : chaque étage est testable seul, et la mémoire reste bornée (rien n'est matérialisé en entier).

Deux étages reliés : la sortie de générer devient l'entrée de filtrerPairs.

Astuce

Pour qu'un pipeline soit annulable, ajoute un ctx context.Context à chaque étage et un select sur l'envoi : select { case out <- v: case <-ctx.Done(): return }. Sans ça, un consommateur qui abandonne en plein milieu laisse les étages amont bloqués sur leur envoi.

sync en profondeur : quand un mutex bat un channel

« Ne communique pas en partageant la mémoire, partage la mémoire en communiquant » reste un bon guide, mais pour protéger un simple compteur ou un cache, un sync.Mutex est plus clair et plus rapide qu'un channel. Tour d'horizon des primitives.

Un Mutex sérialise les accès à n ; sans lui, le résultat varierait à chaque exécution.

  • sync.WaitGroup : attendre la fin de N goroutines (vu plus haut). Add avant de lancer, Done en defer, Wait pour bloquer.
  • sync.Mutex / sync.RWMutex : exclusion mutuelle. Le RWMutex autorise plusieurs lecteurs simultanés (RLock) mais un seul écrivain ; utile quand les lectures dominent largement.
  • sync.Once : garantit qu'un bloc s'exécute une seule fois, même appelé par plusieurs goroutines. Idéal pour l'initialisation paresseuse : once.Do(func() { ... }).
  • sync.Pool : réservoir d'objets réutilisables pour réduire la pression sur le garbage collector (buffers, etc.). À ne sortir que sous profil mémoire.

Note

Pour un simple compteur partagé, regarde aussi le package sync/atomic et son type atomic.Int64 (Go 1.19+) : var n atomic.Int64; n.Add(1). Sans verrou explicite, c'est souvent le plus rapide quand l'état tient dans un seul entier.

Détecter les courses et gérer erreurs + annulation

Une data race survient quand deux goroutines accèdent à la même variable sans synchronisation, dont au moins une en écriture. Le résultat est indéfini. Le détecteur de course intégré au compilateur les attrape : go run -race, go test -race, go build -race.

Le détecteur pointe les deux écritures concurrentes et les goroutines responsables.

Pour combiner annulation et propagation d'erreurs, le package golang.org/x/sync/errgroup est le standard de fait. Si une goroutine renvoie une erreur, le groupe annule le contexte des autres ; Wait() renvoie la première erreur.

errgroup.WithContext annule automatiquement les autres goroutines dès la première erreur.

Les fuites de goroutines : toujours une sortie

Une fuite de goroutine, c'est une goroutine qui reste bloquée pour toujours : bloquée sur un envoi que personne ne lit, sur une réception sur un channel jamais fermé, ou dans une boucle sans condition de sortie. Elle ne plante pas le programme ; elle consomme de la mémoire en silence jusqu'à l'épuisement.

Sans le case <-ctx.Done(), la goroutine resterait bloquée sur out <- i après la 3e lecture.

Règle d'or : toute goroutine doit avoir un chemin de sortie garanti. En pratique, ce chemin passe presque toujours par un select qui écoute ctx.Done() ou un « done channel » dédié.

Pièges fréquents

Piège fréquent

Fermer un channel côté récepteur. Seul le producteur doit appeler close. Fermer côté récepteur (ou deux fois) provoque un panic: close of closed channel. Et écrire sur un channel fermé panique aussi.

Piège fréquent

Mutex copié par valeur. Un sync.Mutex ne doit jamais être copié après usage. Passe toujours un pointeur vers la struct qui le contient (*Compteur, pas Compteur). go vet détecte la copie avec l'avertissement « passes lock by value ».

Piège fréquent

Deadlock. fatal error: all goroutines are asleep - deadlock! apparaît quand toutes les goroutines attendent. Causes classiques : un range sur un channel jamais fermé, un envoi sur un channel non bufferisé que personne ne lit, ou un WaitGroup dont le compteur ne revient jamais à zéro (Add/Done déséquilibrés).

Piège fréquent

Oublier de respecter le context. Recevoir ctx en argument ne sert à rien si tu ne lis jamais ctx.Done(). Le contexte ne tue pas tes goroutines : il leur demande de s'arrêter. C'est à ton code de coopérer.

Pour aller plus loin

Pour aller plus loin

Explore golang.org/x/sync : errgroup pour erreurs + annulation (et son SetLimit pour borner le parallélisme), semaphore (semaphore.Weighted) pour limiter par poids, et singleflight pour dédupliquer des appels identiques. Étudie le pattern « done channel » (ancêtre de context), la structured concurrency (toute goroutine vit dans une portée qui attend sa fin), et l'outil runtime/trace + go tool trace pour visualiser goroutines, blocages et latences réelles de ton programme.

Un cas réel : la fuite de goroutines qui vidait la mémoire chaque nuit

Cas réel

Un service d'agrégation lançait, pour chaque requête, une goroutine qui interrogeait un service tiers et renvoyait le résultat sur un channel. Quand le client abandonnait (timeout côté navigateur), plus personne ne lisait ce channel : la goroutine restait bloquée pour toujours sur son envoi. Invisible au début — rien ne plantait. Mais en quelques jours, le nombre de goroutines grimpait de quelques centaines à plusieurs centaines de milliers ; la mémoire enflait jusqu'à l'OOM kill par Kubernetes, toutes les nuits vers 2 h. Le diagnostic est venu de /debug/pprof/goroutine : des milliers de goroutines bloquées sur la même ligne d'envoi. Le correctif : un select sur ctx.Done() à chaque envoi, et un contexte annulé dès le départ du client. Depuis, la courbe de goroutines est plate.

Antisèche

Glossaire

context.Context
Porte l'annulation, le timeout et la deadline à travers les appels ; ctx.Done() se ferme à l'annulation, ctx.Err() en donne la cause.
Worker pool
Nombre fixe de goroutines qui consomment un channel de tâches ; borne la charge (CPU, connexions) au lieu d'une goroutine par tâche.
Fan-out / fan-in
Fan-out : plusieurs goroutines lisent la même source pour paralléliser. Fan-in : fusionner plusieurs channels en un seul (sans garantie d'ordre).
Pipeline
Chaîne d'étages, chacun recevant un channel d'entrée et renvoyant un channel de sortie ; les données coulent, la mémoire reste bornée.
Data race
Accès concurrent à une même variable, dont au moins une écriture, sans synchronisation ; résultat indéfini. Détectée par -race.
sync.Mutex
Verrou d'exclusion mutuelle protégeant un état partagé ; Lock/Unlock, à ne jamais copier par valeur (passer un pointeur).
errgroup
Groupe de goroutines de golang.org/x/sync : la première erreur annule le contexte des autres ; Wait() renvoie cette erreur.
Fuite de goroutine
Goroutine bloquée pour toujours (envoi sans récepteur, channel jamais fermé) ; consomme la mémoire en silence. Parade : une sortie via ctx.Done().

Récap et vérification

  • context propage annulation, timeout et deadline ; écoute ctx.Done() et lis ctx.Err(). defer cancel() systématique.
  • Worker pool : N goroutines bornent la charge ; le producteur ferme le channel de tâches, les résultats se ferment après wg.Wait().
  • Fan-out/fan-in parallélise puis fusionne (sans garantie d'ordre) ; le pipeline enchaîne des étages reliés par des channels.
  • sync : Mutex/RWMutex, Once, Pool (et sync/atomic) ; un mutex bat un channel pour protéger un état simple.
  • -race détecte les data races ; errgroup gère erreurs + annulation ; chaque goroutine doit avoir une sortie garantie.

Vérifie ta compréhension

  1. Pourquoi appeler defer cancel() même avec context.WithTimeout ?
  2. Dans un worker pool, qui doit fermer le channel des tâches, et pourquoi pas un worker ?
  3. Donne deux causes typiques d'une fuite de goroutine et la parade commune.
