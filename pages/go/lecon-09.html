Tests et outillage

~31 min Intermédiaire Leçon 8 recommandée

À la fin de cette leçon, tu sauras

  • savoir écrire un test avec func TestXxx(t *testing.T) et le lancer avec go test ;
  • savoir structurer des table-driven tests avec t.Run et mesurer la couverture ;
  • savoir écrire un benchmark et un exemple testable avec // Output: ;
  • savoir utiliser l'outillage intégré : go fmt, go vet, go doc et le -race.
Sommaire de la leçon

En Go, tester n'est pas une option qu'on ajoute : le framework de test est dans la bibliothèque standard. Pas de dépendance à installer, pas de configuration. Tu écris un fichier, tu lances go test, et c'est tout. Cette philosophie « tout est intégré » s'étend à l'outillage : formatage, analyse statique, détection de bugs de concurrence, génération de doc—chaque outil vit dans la commande go.

Dans cette leçon, tu vas apprendre à écrire des tests idiomatiques (l'incontournable table-driven test), à mesurer leur couverture, à mesurer la performance avec des benchmarks, et à maîtriser les outils qui gardent un projet Go propre.

Le package testing

Un test Go vit dans un fichier dont le nom se termine par _test.go, placé dans le même dossier que le code testé. Une fonction de test commence par Test suivi d'une majuscule, et reçoit un *testing.T.

Sans argument, go test compile et lance tous les tests du package courant.

Deux drapeaux essentiels : -v (verbeux, affiche chaque test) et -run (filtre par expression régulière sur le nom).

t.Error contre t.Fatal

Deux familles de méthodes signalent un échec. t.Error / t.Errorf marquent le test comme échoué mais continuent l'exécution. t.Fatal / t.Fatalf marquent l'échec et arrêtent immédiatement la fonction de test (via runtime.Goexit).

Règle simple : utilise Fatal quand continuer n'a pas de sens (une erreur a rendu la suite invalide, risque de nil pointer), sinon préfère Error pour collecter un maximum d'informations en une seule exécution. Attention : t.Fatal ne doit être appelé que depuis la goroutine de test, jamais depuis une goroutine lancée par le test.

Les table-driven tests

C'est l'idiome Go par excellence. Plutôt que d'écrire une fonction par cas, tu décris tes cas dans une slice de structures anonymes, puis tu boucles dessus. Combiné à t.Run, chaque cas devient un sous-test nommé, isolé et filtrable.

Ajouter un cas, c'est ajouter une ligne. Et grâce aux sous-tests, tu peux cibler un seul cas : go test -run TestAdd/négatifs (les espaces des noms deviennent des _ dans le filtre).

Astuce

Donne un name parlant à chaque cas : il apparaît dans la sortie -v et dans le message d'échec, ce qui te dit immédiatement quel cas a cassé.

Comparer autre chose que des scalaires

L'opérateur == fonctionne pour les nombres, chaînes et booléens. Mais il ne compile pas sur des slices ou des maps, et compare les structs champ par champ (ce qui casse dès qu'il y a un pointeur ou une slice à l'intérieur). Pour comparer des valeurs composées, utilise reflect.DeepEqual.

Dans les projets réels, beaucoup préfèrent github.com/google/go-cmp/cmp, qui produit un diff lisible et gère mieux les cas particuliers (options de comparaison, champs non exportés).

La couverture

Le drapeau -cover mesure quel pourcentage de tes lignes de code sont exécutées par les tests. Pas besoin d'outil tiers.

Note

Un fort pourcentage de couverture ne garantit pas que ton code est correct—seulement qu'il est exécuté. Vise des cas pertinents (limites, erreurs) plutôt qu'un chiffre.

Les benchmarks

Un benchmark mesure la performance. La fonction commence par Benchmark et reçoit un *testing.B. Historiquement, tu places le code à mesurer dans une boucle for i := 0; i < b.N; i++ : Go ajuste lui-même b.N pour obtenir une mesure stable.

Les exemples testables

Une fonction ExampleXxx sert deux objectifs : elle apparaît dans la documentation générée (go doc, pkg.go.dev) et elle est vérifiée par go test. Le secret est le commentaire // Output: : Go compare la sortie standard réelle à ce qui est annoncé.

Si Add renvoyait autre chose que 5, le test échouerait. Tes exemples de doc restent ainsi toujours à jour—impossible qu'ils mentent. Sans commentaire // Output:, l'exemple est compilé mais pas exécuté.

L'outillage intégré

La commande go embarque tout ce qu'il faut pour garder un projet sain.

  • go fmt (qui appelle gofmt) : reformate ton code selon le style canonique. En Go, il n'y a qu'un seul style—fini les débats sur l'indentation. Lance-le, ou configure ton éditeur pour le faire à la sauvegarde.
  • go vet : analyse statique qui repère les erreurs probables que le compilateur laisse passer (verbe Printf incohérent avec ses arguments, copie d'un mutex, condition toujours vraie…).
  • go doc : affiche la documentation d'un package ou d'un symbole directement au terminal.

Le race detector mérite une mention spéciale : go test -race instrumente le code pour détecter les accès concurrents non synchronisés. Si deux goroutines lisent/écrivent la même variable sans verrou, il le signale. C'est l'un des outils les plus précieux de l'écosystème.

Pièges fréquents

Piège fréquent

Oublier le suffixe _test.go : un fichier nommé tests.go ou add_test.txt ne sera jamais ramassé par go test. De même, une fonction testAdd (minuscule) ou Testadd (pas de majuscule après Test) n'est pas reconnue comme un test.

Piège fréquent

Tests dépendants de l'ordre ou d'un état global : chaque test doit être autonome. Avec t.Parallel(), Go change l'ordre et lance les tests en parallèle. Évite les variables globales mutables partagées entre tests ; recrée l'état dans chaque test.

Piège fréquent

Comparer des slices/maps/structs avec == : ça ne compile pas pour les slices et maps, et donne de faux résultats pour les structs contenant des pointeurs. Utilise reflect.DeepEqual ou cmp.Equal. Et n'oublie pas de lancer go vet avant chaque commit—il attrape beaucoup d'erreurs silencieuses.

Pour aller plus loin

Pour aller plus loin

La bibliothèque testify (stretchr/testify) offre des assertions concises (assert.Equal) et des mocks—pratique, mais l'idiome Go reste les if explicites. Pour tester du code qui dépend de services externes, fais-le dépendre d'interfaces que tu remplaces par de fausses implémentations en test. Explore aussi le fuzzing intégré (func FuzzXxx(f *testing.F), Go 1.18+) qui génère des entrées aléatoires pour débusquer des bugs, le -race en intégration continue, et l'exécution de toute la suite avec go test ./....

Un cas réel : 90 % de couverture, et pourtant un crash en production

Cas réel

Une équipe affichait fièrement 90 % de couverture sur son parseur. Un lundi, le service a planté (panic: index out of range) sur une entrée… vide. Les tests exécutaient bien 90 % des lignes, mais aucun cas ne couvrait la chaîne vide : la couverture mesure ce qui est exécuté, pas ce qui est pensé. Le correctif a tenu en une ligne ajoutée à la table de cas — {"entrée vide", "", …} — qui a immédiatement reproduit le crash en test, puis validé le garde-fou. Depuis, la revue de code réclame systématiquement les cas limites (vide, nil, zéro, valeur maximale) dans chaque table-driven test, et l'intégration continue lance go test -race ./....

Glossaire

Package testing
Framework de test de la bibliothèque standard ; aucune dépendance à installer. Fournit *testing.T, *testing.B et *testing.F.
Fichier _test.go
Fichier de tests, dans le même dossier que le code ; compilé uniquement par go test, jamais inclus dans le binaire final.
t.Error vs t.Fatal
Error marque l'échec mais poursuit ; Fatal marque et arrête la fonction de test immédiatement.
Table-driven test
Idiome Go : décrire les cas dans une slice de structures puis boucler dessus, souvent avec t.Run pour des sous-tests nommés.
Sous-test (t.Run)
Test imbriqué et nommé, isolé et filtrable (go test -run Test/cas) ; apparaît individuellement dans la sortie -v.
Couverture
Pourcentage de lignes exécutées par les tests (-cover) ; mesure ce qui est exécuté, pas la justesse du code.
Benchmark
Fonction BenchmarkXxx(b *testing.B) qui mesure la performance (-bench, -benchmem) ; boucle moderne for b.Loop().
Exemple testable
Fonction ExampleXxx avec un commentaire // Output: : sert de documentation ET est vérifiée par go test.

Récap et vérification

  • Les tests vivent dans des fichiers _test.go, fonctions TestXxx(t *testing.T), lancées par go test (-v, -run).
  • t.Error continue, t.Fatal arrête le test courant.
  • Le table-driven test + t.Run est l'idiome standard : une slice de cas parcourue en boucle.
  • Compare les valeurs composées avec reflect.DeepEqual ou cmp, jamais ==.
  • -cover mesure la couverture, BenchmarkXxx + -bench la performance, ExampleXxx + // Output: documente et teste.
  • L'outillage intégré : go fmt, go vet, go doc, et le précieux -race.
