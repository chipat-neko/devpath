Module 02 · Administrer — Leçon 05

Réseau, SSH & sécurité de base

~32 min Intermédiaire Module 01 conseillé

À la fin de cette leçon, tu sauras

  • te connecter à un serveur à distance avec SSH ;
  • préférer l'authentification par clé au mot de passe ;
  • filtrer les connexions avec un pare-feu ;
  • appliquer les bases du durcissement d'un serveur.
Sommaire de la leçon

Un serveur, par définition, est fait pour être joint à distance. Mais qui dit accessible dit exposé : il faut savoir s'y connecter en sécurité et limiter ce qui est ouvert sur le réseau. Cette leçon couvre l'essentiel pour administrer un serveur sans lui ouvrir la porte aux intrus.

Un peu de réseau : adresse et ports

Sur un réseau, chaque machine a une adresse IP (par ex. 192.168.1.10). Sur cette machine, chaque service écoute sur un port numéroté : un serveur web sur le 80 (HTTP) ou le 443 (HTTPS), SSH sur le 22. Une connexion, c'est donc une adresse + un port.

SSH : la porte d'entrée sécurisée

SSH (Secure Shell) permet d'ouvrir un terminal sur une machine distante, à travers une connexion chiffrée. C'est l'outil universel d'administration des serveurs Linux :

Clés SSH plutôt que mot de passe

Se connecter par mot de passe est vulnérable aux essais en masse (force brute). La bonne pratique est l'authentification par clé : une paire clé privée (qui reste chez toi, secrète) / clé publique (qu'on dépose sur le serveur). On se connecte alors sans mot de passe, et bien plus sûrement.

La clé privée ne sort jamais

Tu déposes ta clé publique sur les serveurs ; ta clé privée reste sur ta machine et ne doit jamais être partagée ni copiée ailleurs. Une fois les clés en place, on désactive souvent l'authentification par mot de passe côté serveur.

Le pare-feu : n'ouvrir que le nécessaire

Un pare-feu (firewall) contrôle quels ports sont joignables depuis l'extérieur. Le principe : tout fermer, puis n'ouvrir que les ports réellement utiles (SSH, HTTP, HTTPS…). Sur Ubuntu, ufw simplifie cela :

C'est encore le moindre privilège (leçon 3), appliqué au réseau : moins de ports ouverts, moins de surface d'attaque.

Les bases du durcissement

Quelques gestes simples réduisent énormément le risque sur un serveur exposé :

  • Mettre à jour régulièrement (apt update && apt upgrade) — les failles corrigées ne te concernent plus.
  • Clés SSH et désactivation du mot de passe ; ne pas autoriser la connexion directe en root.
  • Pare-feu n'ouvrant que le strict nécessaire.
  • Services inutiles désactivés (systemctl disable) — ce qui ne tourne pas ne peut pas être attaqué.
  • Comptes dédiés et moindre privilège pour chaque service.

La sécurité, par couches

Aucune mesure ne suffit seule : c'est leur accumulation qui protège (mises à jour + clés + pare-feu + moindre privilège). C'est la défense en profondeur, qu'on retrouve dans le cours Sécurité applicative.

Cas réel — le port 22 sous le feu des bots

Mets un serveur en ligne avec un mot de passe, et en quelques minutes journalctl -u ssh (ou /var/log/auth.log) se remplit de milliers de tentatives : Failed password for root, Failed password for admin… Ce ne sont pas des pirates ciblés, mais des robots qui balaient Internet en essayant des identifiants courants. Avec un mot de passe faible, la compromission n'est qu'une question de temps. En passant aux clés SSH et en désactivant l'authentification par mot de passe, ces milliers d'essais deviennent inoffensifs : sans la clé privée, il n'y a tout simplement rien à deviner.

Pour aller plus loin

Trois outils prolongent ces bases : fail2ban bannit automatiquement une adresse IP après trop d'échecs de connexion ; un fichier ~/.ssh/config crée des alias (ssh monserveur au lieu de ssh deploy@203.0.113.10 -p 2222) ; et les mises à jour de sécurité automatiques (unattended-upgrades sous Ubuntu) appliquent les correctifs sans intervention. Aucun ne remplace les bases (clés + pare-feu), mais chacun ajoute une couche.

Antisèche

Glossaire

Adresse IP
L'identifiant numérique d'une machine sur un réseau (par ex. 203.0.113.10). Elle permet de la joindre parmi toutes les autres.
Port
Un numéro qui identifie un service sur une machine : SSH sur le 22, HTTP sur le 80, HTTPS sur le 443. Une connexion vise une adresse + un port.
SSH (Secure Shell)
Le protocole qui ouvre un terminal chiffré sur une machine distante. L'outil standard d'administration des serveurs Linux.
scp
SSH copy : copie des fichiers d'une machine à l'autre à travers le même canal chiffré que SSH.
Clé privée / clé publique
Une paire de clés. La privée reste secrète sur ta machine ; la publique se dépose sur les serveurs. Se connecter prouve qu'on détient la privée, sans jamais la transmettre.
Pare-feu (firewall)
Un filtre qui décide quels ports sont joignables depuis l'extérieur. Sous Ubuntu, ufw le simplifie. Bon réglage : tout fermer, n'ouvrir que le nécessaire.
Force brute
Une attaque qui essaie des quantités de mots de passe jusqu'à trouver le bon. Les clés SSH la rendent vaine : il n'y a pas de mot de passe à deviner.
Durcissement (hardening)
L'ensemble des réglages qui réduisent la surface d'attaque d'un serveur : mises à jour, clés SSH, pare-feu, services inutiles coupés, moindre privilège.

Récap et vérification

  • Une connexion = une adresse IP + un port (SSH=22, HTTP=80, HTTPS=443).
  • SSH ouvre un terminal distant chiffré ; scp copie des fichiers.
  • Préférer les clés SSH (privée secrète, publique sur le serveur) au mot de passe.
  • Pare-feu : tout fermer, ouvrir le nécessaire ; mettre à jour et durcir par couches.

Exercices

Exercice 1Échauffement

Associe chaque service à son port standard : (a) SSH ; (b) HTTP ; (c) HTTPS.

Voir une solution

(a) SSH → port 22. (b) HTTP → port 80. (c) HTTPS → port 443. Connaître ces ports « par cœur » aide à lire une configuration de pare-feu ou à diagnostiquer un service injoignable (le bon port est-il ouvert et à l'écoute ?).

Exercice 2Application

Tu mets en place un serveur web. Quels ports ouvres-tu sur le pare-feu, et pourquoi pas davantage ?

Voir une solution

Pour un serveur web administré à distance, on ouvre : le 22 (SSH, pour administrer), le 80 (HTTP) et le 443 (HTTPS, pour servir le site). Rien d'autre. Pourquoi pas davantage ? Parce que chaque port ouvert est une porte d'entrée potentielle : un service qui écoute peut avoir une faille. En appliquant « tout fermer par défaut, n'ouvrir que le nécessaire » (ufw default deny incoming puis allow 22/80/443), on réduit la surface d'attaque au strict minimum. Si plus tard une base de données tourne sur la même machine, on ne l'expose pas sur Internet : elle reste accessible en local uniquement. C'est le moindre privilège appliqué au réseau.

Exercice 3Défi

On te confie un serveur fraîchement installé, accessible en SSH par mot de passe avec le compte root. Liste les premières mesures que tu prends pour le sécuriser, et explique chacune.

Voir une solution

Un plan de durcissement initial : 1) Mettre à jour (apt update && apt upgrade) — applique les correctifs de sécurité connus, le geste le plus rentable. 2) Créer un utilisateur dédié non-root avec sudo, et cesser d'utiliser root directement — moindre privilège : on n'opère pas tout-puissant en permanence. 3) Mettre en place les clés SSH (ssh-keygen + ssh-copy-id) puis désactiver l'authentification par mot de passe et la connexion root en SSH — supprime la prise aux attaques par force brute, qui ciblent justement root par mot de passe. 4) Configurer le pare-feu (ufw) : tout fermer, n'ouvrir que SSH (et les ports du service prévu) — réduit la surface. 5) Désactiver les services inutiles (systemctl disable) — ce qui ne tourne pas ne peut pas être attaqué. 6) Activer les mises à jour de sécurité automatiques si possible. Chaque mesure est une couche : aucune n'est suffisante seule, mais ensemble elles rendent le serveur bien plus difficile à compromettre. C'est la défense en profondeur.
