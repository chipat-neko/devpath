Module 02 · Administrer — Leçon 04

Paquets, services (systemd) & journaux

~33 min Intermédiaire Module 01 conseillé

À la fin de cette leçon, tu sauras

  • installer et mettre à jour des logiciels avec un gestionnaire de paquets ;
  • piloter des services avec systemd (systemctl) ;
  • activer un service au démarrage ;
  • lire les journaux (journalctl) pour diagnostiquer.
Sommaire de la leçon

Administrer un serveur, c'est surtout trois gestes répétés mille fois : installer des logiciels, démarrer/arrêter des services, et lire les journaux quand quelque chose cloche. Cette leçon te donne ces trois réflexes.

Installer des logiciels : les paquets

On n'installe pas un logiciel en téléchargeant un .exe sur un site. On utilise un gestionnaire de paquets, qui télécharge le logiciel et ses dépendances depuis des dépôts officiels, vérifiés. Sur Debian/Ubuntu, c'est apt :

Chaque famille a son gestionnaire

Debian/Ubuntu utilisent apt, Fedora/Red Hat dnf, Alpine apk. Le principe est le même partout : des dépôts de paquets signés, et une commande qui gère l'installation et les dépendances à ta place.

Erreur fréquente

Lancer apt install sans avoir fait apt update d'abord. Sans mise à jour de l'index, apt travaille sur une liste périmée : il peut ne pas trouver un paquet récent, ou tenter d'installer une version obsolète. Le réflexe : sudo apt update, puis sudo apt install.

Piloter les services : systemd

Un service (ou démon) est un programme qui tourne en arrière-plan : un serveur web, une base de données, SSH… Sur la plupart des distributions modernes, c'est systemd qui démarre et supervise ces services, via la commande systemctl.

Très important : démarrer un service maintenant ne le relance pas après un redémarrage de la machine. Pour qu'il démarre automatiquement au boot, on l'active :

start ≠ enable

Le piège classique : on start un service, tout marche… puis le serveur redémarre et le service ne revient pas. Pense à enable pour le démarrage automatique. start = maintenant ; enable = à chaque boot.

Cas réel — le site qui disparaît après la coupure de courant

Un développeur met en ligne son premier serveur : apt install nginx, systemctl start nginx, le site répond, tout va bien. Trois semaines plus tard, l'hébergeur redémarre la machine pour une maintenance. Au réveil, le site renvoie une erreur de connexion. Panique : rien n'a changé dans le code ! La cause ? nginx avait été start mais jamais enable : au reboot, systemd ne l'a pas relancé. Un simple sudo systemctl enable --now nginx aurait évité la mésaventure. C'est l'erreur numéro un des débutants en administration serveur.

Lire les journaux : journalctl

Quand un service refuse de démarrer ou se comporte mal, la réponse est presque toujours dans les journaux. systemd les centralise, et on les consulte avec journalctl :

Beaucoup de services écrivent aussi dans des fichiers sous /var/log (vu en leçon 2). Entre systemctl status, journalctl et /var/log, tu as de quoi diagnostiquer la plupart des problèmes.

Le réflexe diagnostic

Un service ne marche pas ? Dans l'ordre : systemctl status <service> (état + dernières lignes), puis journalctl -u <service> -e (détails). Le message d'erreur exact t'attend presque toujours là.

Pour aller plus loin

journalctl accepte des filtres puissants qu'on combine : journalctl -u nginx --since "today" (depuis ce matin), journalctl -b (uniquement depuis le dernier démarrage), ou journalctl -u nginx -p err --since "1 hour ago" (erreurs de la dernière heure). Sur les serveurs de longue vie, pense aussi à journalctl --disk-usage pour voir la place occupée par les journaux : systemd peut les faire grossir, et on limite leur taille dans /etc/systemd/journald.conf.

Antisèche

Glossaire

Paquet
Une unité logicielle prête à installer (le programme, ses fichiers et la liste de ses dépendances), distribuée par un dépôt : .deb sous Debian/Ubuntu, .rpm sous Fedora.
Gestionnaire de paquets
L'outil qui installe, met à jour et supprime les logiciels en résolvant leurs dépendances : apt, dnf, apk…
Dépôt (repository)
Une source de paquets signés hébergée en ligne. Le gestionnaire y télécharge les logiciels après avoir vérifié leur signature.
Dépendance
Un autre paquet nécessaire au fonctionnement de celui qu'on installe. Le gestionnaire les tire automatiquement.
Service (démon)
Un programme qui tourne en arrière-plan, sans interface : serveur web, base de données, SSH… Souvent nommé daemon en anglais.
systemd
Le système d'initialisation qui démarre et supervise les services sur la plupart des distributions modernes. On le pilote avec systemctl.
enable vs start
start lance un service maintenant ; enable le configure pour démarrer à chaque boot. Ce sont deux réglages indépendants.
journalctl
L'outil qui consulte le journal centralisé de systemd : état, messages et erreurs des services, filtrables par unité, priorité ou date.

Récap et vérification

  • On installe via un gestionnaire de paquets (apt/dnf/apk), pas en téléchargeant à la main.
  • systemd pilote les services : systemctl start/stop/restart/status.
  • enable = démarrage au boot ; start = maintenant (ne pas confondre).
  • On diagnostique avec systemctl status, journalctl et /var/log.

Exercices

Exercice 1Échauffement

Remets dans l'ordre pour installer puis activer un serveur web : (a) systemctl enable --now nginx ; (b) apt update ; (c) apt install nginx.

Voir une solution

Ordre : (b) sudo apt update (rafraîchir la liste des paquets), (c) sudo apt install nginx (installer), puis (a) sudo systemctl enable --now nginx (démarrer maintenant ET au prochain boot). On met à jour l'index, on installe, on active.

Exercice 2Application

Tu as démarré un service avec systemctl start et tout fonctionnait. Après un redémarrage du serveur, le service est arrêté. Pourquoi, et comment corriger durablement ?

Voir une solution

systemctl start démarre le service uniquement pour la session en cours : il ne dit rien sur le comportement au démarrage de la machine. Après un reboot, comme le service n'a pas été activé, il ne se relance pas. Correction durable : sudo systemctl enable nginx (ou directement enable --now qui active et démarre). « enable » inscrit le service dans la liste de ceux à lancer au boot. Règle à retenir : start = maintenant, enable = à chaque démarrage. Pour un service censé tourner en permanence sur un serveur, il faut les deux.

Exercice 3Défi

Tu installes un serveur web, mais systemctl status indique qu'il est en échec (failed). Décris ta démarche méthodique pour trouver et comprendre la cause.

Voir une solution

Une démarche par étapes, du général au précis : 1) systemctl status <service> — il donne l'état, le code de sortie et souvent les dernières lignes du journal, qui suffisent parfois à comprendre. 2) journalctl -u <service> -e — pour lire le détail des messages (l'option -e saute à la fin, la plus récente) ; on y cherche le premier message d'erreur. 3) Causes fréquentes à vérifier : un port déjà utilisé par un autre programme, une erreur de configuration (un fichier sous /etc mal formé — beaucoup de serveurs ont une commande de test de config), un fichier ou dossier manquant, ou un problème de permissions (le service tourne sous un compte qui n'a pas accès à un fichier). 4) Après correction, systemctl restart <service> puis re-vérifier le status. L'idée clé : ne pas tâtonner au hasard, mais lire le message d'erreur que le système fournit — il pointe presque toujours la cause.
