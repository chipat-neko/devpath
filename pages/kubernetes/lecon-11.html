Helm : empaqueter ses manifestes

~38 min Avancé Leçon 10

À la fin de cette leçon, tu sauras

  • expliquer le problème que résout Helm (dupliquer et paramétrer des manifestes) ;
  • décrire la structure d'un chart (templates, values.yaml, Chart.yaml) ;
  • installer, mettre à jour et revenir en arrière avec helm ;
  • réutiliser un chart public pour déployer un logiciel courant.
Sommaire de la leçon

Tu sais désormais décrire une application avec des manifestes YAML : Deployment, Service, ConfigMap, sondes… Mais dès qu'il faut déployer la même application dans plusieurs environnements (dev, staging, production), ou la partager avec d'autres équipes, le copier-coller de YAML devient vite ingérable. Helm est le « gestionnaire de paquets » de Kubernetes : il empaquette tes manifestes et te laisse les paramétrer.

Le problème : dupliquer des manifestes

Imagine la même app en trois environnements. Le YAML est identique à quelques valeurs près : le nombre de répliques, le tag de l'image, l'URL de la base. Sans outil, tu maintiens trois copies qui divergent avec le temps : un correctif appliqué à l'une est oublié sur les autres. On veut un modèle unique et des valeurs par environnement.

Un chart : le paquet Helm

Un chart est un dossier qui contient tout le nécessaire pour déployer une application. Trois éléments comptent : Chart.yaml (les métadonnées : nom, version), values.yaml (les valeurs par défaut), et le dossier templates/ (tes manifestes, avec des trous à remplir).

La commande helm create mon-app génère cette arborescence prête à modifier. Regardons un template et ses values.

Templates + values = manifestes

Les {{ ... }} sont des trous. Helm y injecte les values (et quelques variables comme .Release.Name) pour produire du YAML Kubernetes classique. Le template reste unique ; seules les values changent d'un environnement à l'autre.

Le rendu : voir avant d'appliquer

Avant d'installer, tu peux demander à Helm de rendre les templates avec un jeu de values, sans rien envoyer au cluster. C'est le meilleur moyen de vérifier ce qui sera réellement appliqué.

Surcharger une valeur en ligne de commande

Pas besoin d'un fichier pour un réglage ponctuel : --set replicaCount=5 surcharge une value directement. Pratique pour tester, mais préfère un fichier values-*.yaml versionné pour les configurations durables.

Release et révisions : mettre à jour, revenir en arrière

Quand tu installes un chart, Helm crée une release : une instance nommée et suivie de ton application dans le cluster. Chaque helm upgrade crée une nouvelle révision. Et si une mise à jour tourne mal ? Un helm rollback te ramène à une révision précédente, d'un seul geste.

Helm gère SES ressources, pas les tiennes

Helm ne suit que les objets qu'il a créés pour une release : si tu modifies ces objets « à la main » avec kubectl edit, le prochain helm upgrade risque d'écraser tes changements. Choisis : soit une ressource est gérée par Helm, soit elle ne l'est pas — pas les deux.

Réutiliser des charts publics

L'un des grands intérêts de Helm : des milliers de charts prêts à l'emploi (PostgreSQL, Redis, Prometheus, ingress-nginx…) publiés sur des dépôts (repositories) et recensés sur Artifact Hub. Installer un logiciel courant devient une poignée de commandes.

Helm ou Kustomize ?

Helm templatise (des trous remplis par des values) ; Kustomize (intégré à kubectl) superpose des correctifs à une base sans variables. Deux philosophies : Helm brille pour empaqueter et partager une app paramétrable ; Kustomize pour de simples variantes internes. Beaucoup d'équipes utilisent les deux.

Cas réel

Cas réel — trois environnements, un seul chart

Une équipe déployait son API en copiant un dossier k8s/ vers k8s-staging/ puis k8s-prod/, en changeant à la main les répliques et le tag d'image. Un jour, un correctif de sonde est appliqué en staging… mais oublié en prod, restée sur l'ancienne version. Migration vers Helm : un chart unique, trois fichiers values-dev.yaml / values-staging.yaml / values-prod.yaml versionnés. Désormais, chaque environnement est déployé par helm upgrade --install ... -f values-<env>.yaml dans le pipeline : le modèle est toujours le même, seules les valeurs diffèrent, et un helm rollback répare une mise en prod ratée en quelques secondes.

Pour aller plus loin

Pour aller plus loin

Les templates Helm peuvent contenir de la logique (conditions {{ if }}, boucles {{ range }}, fonctions d'aide dans _helpers.tpl). C'est puissant, mais un chart trop « intelligent » devient illisible : garde des templates simples et déporte la complexité dans les values. Pour valider un chart avant publication : helm lint.

Glossaire

Helm
Gestionnaire de paquets de Kubernetes : empaquette des manifestes en charts paramétrables et gère leur cycle de vie (install, upgrade, rollback).
Chart
Paquet Helm : un dossier réunissant Chart.yaml, values.yaml et des templates/ pour déployer une application.
values.yaml
Fichier des valeurs injectées dans les templates ; on en fournit un par environnement pour paramétrer le même chart.
Template
Manifeste « à trous » contenant des expressions {{ .Values.x }} que Helm remplace par les values pour produire du YAML final.
Release
Instance nommée d'un chart installée dans le cluster ; Helm en suit l'historique de révisions.
Révision
Version successive d'une release ; chaque helm upgrade en crée une, et helm rollback permet d'y revenir.
Repository (dépôt)
Source de charts publiés ; on l'ajoute avec helm repo add pour installer des charts publics (Bitnami, ingress-nginx…).
Kustomize
Alternative intégrée à kubectl qui superpose des correctifs à des manifestes de base, sans variables ; complémentaire de Helm.

Récap et vérification

  • Helm résout la duplication des manifestes en séparant un modèle (templates) des valeurs.
  • Un chart = Chart.yaml + values.yaml + templates/.
  • Une release a un historique de révisions ; helm rollback répare une mise à jour ratée.
  • Des charts publics installent des logiciels courants en quelques commandes.

Exercices

Exercice 1Échauffement

Écris la commande qui rend (sans installer) le chart ./mon-app avec le fichier values-prod.yaml, pour vérifier les manifestes produits.

Exercice 2Application

Dans un template, écris la ligne qui fixe le nombre de répliques à partir d'une value replicaCount, puis la ligne correspondante dans values.yaml pour 4 répliques.

Voir une solution
Exercice 3Défi

Une équipe maintient trois dossiers de manifestes presque identiques (dev/staging/prod) et oublie régulièrement d'y reporter les correctifs. Décris la solution avec Helm, en nommant les fichiers concernés.

Voir une solution

Créer un seul chart (helm create mon-app) dont les templates/ remplacent les valeurs variables par {{ .Values.x }}. Fournir un fichier de values par environnement : values-dev.yaml, values-staging.yaml, values-prod.yaml (répliques, tag d'image, URL…). Déployer chacun avec helm upgrade --install mon-site ./mon-app -f values-<env>.yaml. Les correctifs se font une fois dans les templates et profitent à tous les environnements ; un helm rollback répare une mise à jour ratée.
