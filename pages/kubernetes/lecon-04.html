Services & exposition

~34 min Intermédiaire Leçon 03

À la fin de cette leçon, tu sauras

  • expliquer pourquoi des pods éphémères ont besoin d'un service ;
  • créer un Service qui cible des pods par leurs labels ;
  • distinguer ClusterIP, NodePort et LoadBalancer ;
  • joindre un service par son nom DNS interne.
Sommaire de la leçon

Tes pods tournent, répliqués et auto-réparés. Mais comment les joindre ? Leurs adresses IP changent à chaque recréation. Le Service résout ce problème : il offre une adresse stable et répartit le trafic vers les bons pods.

Le problème des adresses éphémères

Chaque pod a une IP, mais cette IP est temporaire : quand un pod est recréé (incident, mise à jour, montée à l'échelle), il en reçoit une nouvelle. Impossible donc de coder en dur l'adresse d'un pod. Il faut un point d'entrée stable qui suit les pods, quels qu'ils soient à l'instant T.

Le Service : une adresse stable

Un Service est une ressource qui expose un groupe de pods sous une adresse IP et un nom fixes. Il retrouve « ses » pods grâce à un selector de labels (comme le déploiement), et répartit le trafic entre eux. Les pods vont et viennent ; le service, lui, ne bouge pas.

Le lien, ce sont les labels

Le service ne connaît pas les pods un par un : il sélectionne tous ceux qui portent le bon label. Ajoute une réplique, elle entre automatiquement dans la rotation ; supprime-en une, elle en sort. Aucun réglage à refaire.

Trois types de services

Le champ type décide de la portée de l'exposition :

  • ClusterIP (par défaut) : accessible uniquement à l'intérieur du cluster. Idéal pour qu'un service en appelle un autre.
  • NodePort : ouvre un port sur chaque nœud, accessible depuis l'extérieur. Pratique pour tester.
  • LoadBalancer : demande à l'hébergeur (cloud) un équilibreur de charge externe avec une vraie adresse publique. Le choix habituel en production sur le cloud.

Le DNS interne

Kubernetes fournit un DNS interne : chaque service est joignable par son nom. Depuis un autre pod du même espace de noms, on appelle simplement http://web (ou web:80). Plus besoin d'IP : le nom est stable et lisible.

Communiquer entre services

Un front-end joint son back-end via http://api, un back-end joint sa base via postgres:5432… On utilise les noms de service, jamais les IP. C'est ce qui rend l'architecture souple et lisible.

Cas réel — les microservices se trouvent par leur nom

Une application découpée en dizaines de microservices (paiement, catalogue, panier…) les fait dialoguer par leur nom de service : http://paiement, http://catalogue, sans jamais connaître l'IP ni l'emplacement des pods. C'est le DNS interne de Kubernetes (CoreDNS) qui rend cela possible. Sans lui, il faudrait reconfigurer des centaines d'adresses à chaque redéploiement : ingérable.

Et pour le HTTP avec des règles ? L'Ingress

Pour exposer plusieurs services HTTP derrière une seule entrée, avec des règles par nom de domaine ou par chemin d'URL (et du TLS), on ajoute un Ingress devant les services. On l'évoque ici ; en pratique on commence par un Service, l'Ingress vient ensuite.

Pièges fréquents

  • Selector qui ne matche aucun pod. Le service existe mais ne route vers rien : vérifie que les labels correspondent.
  • Confondre port et targetPort. port = le port du service ; targetPort = le port écouté par les conteneurs.
  • Vouloir exposer en NodePort en production. Préfère un LoadBalancer (ou un Ingress) ; NodePort est surtout pour tester.
  • Coder en dur une IP de pod. Toujours passer par le service et son nom DNS.

Pour aller plus loin

La répartition par défaut d'un service est simple (tourniquet entre les pods sains). Kubernetes vérifie la « disponibilité » des pods via les sondes (leçon 7) : seuls les pods déclarés prêts reçoivent du trafic.

Pour aller plus loin

Il existe un type headless (sans IP de service) pour les cas où l'on veut joindre chaque pod individuellement, utile avec les bases de données répliquées. À garder pour plus tard.

Glossaire

Service
Ressource qui expose un groupe de pods sous une IP et un nom stables, et répartit le trafic entre eux.
ClusterIP
Type de service par défaut, accessible uniquement à l'intérieur du cluster (appels entre services).
NodePort
Type de service qui ouvre un port sur chaque nœud pour un accès depuis l'extérieur ; surtout utile pour tester.
LoadBalancer
Type de service qui demande un équilibreur externe à l'hébergeur cloud et fournit une adresse publique ; le choix habituel en production.
port / targetPort
port est le port du service (celui qu'on appelle) ; targetPort est le port écouté par les conteneurs des pods.
DNS interne (CoreDNS)
Composant qui résout les noms de service en IP : un pod joint web via http://web, sans connaître son IP.
Endpoints
Liste des pods réellement ciblés par un service ; si elle est vide, le selector ne correspond à aucun pod.
Ingress
Entrée HTTP placée devant des services pour router par domaine ou chemin d'URL (et gérer le TLS).

Récap et vérification

  • Les IP de pods sont éphémères : on expose les pods via un Service, stable.
  • Le service cible ses pods par labels (selector) et répartit le trafic.
  • Types : ClusterIP (interne), NodePort (test), LoadBalancer (public, cloud).
  • On joint un service par son nom DNS interne (http://web).

Exercice 2Application

Dans un manifeste de Service, explique la différence entre port et targetPort.

Voir une solution

port est le port du service (celui qu'on appelle, ex. web:80). targetPort est le port écouté par les conteneurs des pods cibles. Le service reçoit le trafic sur port et le transmet vers targetPort des pods.

Exercice 3Défi

Ton service « web » est créé mais ne reçoit aucun trafic vers les pods. Les pods tournent pourtant. Quelle est la cause la plus probable, et comment la diagnostiquer ?

Voir une solution

Le selector du service ne correspond probablement pas aux labels des pods : le service ne sélectionne donc aucun pod. On diagnostique avec kubectl describe service web (regarder les « Endpoints » : s'ils sont vides, aucun pod n'est ciblé) et on compare spec.selector aux labels des pods (kubectl get pods --show-labels). Il faut aligner les deux.
