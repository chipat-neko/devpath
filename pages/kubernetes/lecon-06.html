Volumes & stockage

~35 min Intermédiaire Leçon 05

À la fin de cette leçon, tu sauras

  • expliquer pourquoi le stockage d'un conteneur est éphémère ;
  • attacher un volume à un pod ;
  • réclamer du stockage durable avec un PersistentVolumeClaim ;
  • comprendre le rôle d'une StorageClass.
Sommaire de la leçon

Quand un conteneur redémarre, son système de fichiers repart à zéro. Pour une base de données ou des fichiers téléversés, c'est inacceptable. Kubernetes répond avec les volumes et le stockage persistant.

Le stockage d'un conteneur est éphémère

Par défaut, ce qu'un conteneur écrit sur son disque vit et meurt avec lui : redémarrage, recréation par le déploiement, déplacement sur un autre nœud… et les données sont perdues. C'est voulu (les conteneurs sont jetables), mais il faut une solution pour les données qui doivent survivre.

Les volumes

Un volume est un espace de stockage attaché au pod et monté dans un ou plusieurs conteneurs. Le volume le plus simple, emptyDir, vit le temps du pod : utile pour un cache ou pour partager des fichiers entre conteneurs d'un même pod — mais il disparaît avec le pod.

Volume ≠ persistance

Un emptyDir n'est pas durable : il disparaît avec le pod. Pour des données qui doivent survivre à la recréation d'un pod, il faut du stockage persistant (la suite).

Stockage persistant : PV et PVC

Pour des données durables, Kubernetes sépare deux notions : le PersistentVolume (PV) est un morceau de stockage réel (un disque), et le PersistentVolumeClaim (PVC) est une demande de stockage faite par l'application (« j'ai besoin de 5 Gio »). Le pod référence le PVC ; Kubernetes le relie à un PV qui satisfait la demande.

La bonne image mentale

Le PVC est un « bon de commande » de stockage ; le PV est le disque livré. L'application décrit son besoin (taille, mode d'accès) sans savoir quel disque la satisfera : c'est Kubernetes qui apparie.

La StorageClass : du stockage à la demande

Créer les PV à la main serait fastidieux. Une StorageClass permet le provisionnement dynamique : quand un PVC arrive, le cluster crée automatiquement le disque correspondant (chez l'hébergeur cloud, par exemple). On indique simplement la classe voulue dans le PVC (ou on laisse la classe par défaut).

Pièges fréquents

  • Croire qu'emptyDir persiste. Il disparaît avec le pod : pour durer, il faut un PVC.
  • Stocker une base sur un déploiement banal. Les applications « avec état » se gèrent souvent avec un StatefulSet + PVC.
  • Mode d'accès inadapté. ReadWriteOnce = un seul nœud à la fois ; vérifie ce que ton stockage supporte.
  • PVC qui reste « Pending ». Aucune StorageClass ne le satisfait : vérifie la classe et le provisionneur disponibles.

Pour aller plus loin

Les bases de données en cluster (répliquées, avec une identité stable par instance) se déploient avec un StatefulSet, qui crée un PVC dédié par réplique. C'est le cousin du déploiement, conçu pour les charges « avec état ».

Pour aller plus loin

Question de fond : faut-il héberger sa base de données dans Kubernetes ? Beaucoup d'équipes préfèrent une base gérée par l'hébergeur (hors cluster) et réservent Kubernetes aux applications « sans état ». Les deux approches se défendent.

Cas réel — une base PostgreSQL sans stockage durable perd tout

Une équipe déploie PostgreSQL dans un pod nu (ou avec un simple emptyDir), sans volume persistant. Tout fonctionne… jusqu'à la première recréation du pod : mise à jour de l'image, incident sur le nœud, rééquilibrage du planificateur. Le nouveau pod démarre avec un disque vierge et toutes les données sont perdues — tables, comptes, historique. La bonne pratique : un StatefulSet qui attribue à chaque réplique un PVC durable (relié à un PV), de sorte que la base retrouve ses données à chaque redémarrage, même déplacée sur un autre nœud.

Antisèche

Glossaire

Volume
Espace de stockage attaché à un pod et monté dans un ou plusieurs conteneurs via volumeMounts.
emptyDir
Volume le plus simple, créé vide au démarrage du pod et supprimé avec lui ; utile pour un cache ou pour partager des fichiers entre conteneurs d'un même pod.
PersistentVolume (PV)
Morceau de stockage réel (un disque) dans le cluster, indépendant du cycle de vie des pods.
PersistentVolumeClaim (PVC)
Demande de stockage émise par l'application (taille, mode d'accès) ; Kubernetes l'apparie à un PV. Le pod la référence via claimName.
StorageClass
Décrit un type de stockage et son provisionneur ; permet la création automatique du PV à l'arrivée d'un PVC.
Provisionnement dynamique
Création automatique du disque (PV) au moment où un PVC est créé, sans préparer les volumes à la main.
accessModes / ReadWriteOnce
Mode d'accès d'un volume ; ReadWriteOnce autorise la lecture-écriture depuis un seul nœud à la fois.
StatefulSet
Contrôleur pour les charges « avec état » (bases répliquées) : identité stable par instance et un PVC dédié par réplique.

Récap et vérification

  • Le disque d'un conteneur est éphémère ; pour durer, il faut un volume persistant.
  • emptyDir = stockage temporaire lié au pod.
  • PVC (demande) + PV (disque réel) = stockage durable ; le pod référence le PVC.
  • Une StorageClass provisionne le stockage automatiquement à la demande.

Vérifie ta compréhension

  1. Que devient ce qu'un conteneur écrit sur son disque quand il est recréé ?
  2. Quelle est la différence entre un PV et un PVC ?
  3. À quoi sert une StorageClass ?

Exercices

Exercice 1Échauffement

Écris la commande qui liste les demandes de stockage (PVC) et leur état.

Voir une solution

La colonne STATUS indique Bound quand le PVC est relié à un PV, ou Pending sinon.

Exercice 2Application

Pourquoi un emptyDir ne convient-il pas pour stocker les données d'une base de données ?

Voir une solution

Parce qu'un emptyDir est lié au cycle de vie du pod : dès que le pod est supprimé ou recréé (mise à jour, incident, déplacement), son contenu est perdu. Une base de données a besoin de données durables, donc d'un volume persistant (PVC relié à un PV).

Exercice 3Défi

Tu crées un PVC mais il reste indéfiniment à l'état Pending. Quelles pistes vérifies-tu ?

Voir une solution

Un PVC Pending n'a pas trouvé de PV qui le satisfait. Pistes : (1) y a-t-il une StorageClass (par défaut ou nommée) capable de provisionner dynamiquement ? (2) le provisionneur est-il installé et fonctionnel sur le cluster ? (3) la taille ou le mode d'accès demandés sont-ils disponibles ? On inspecte avec kubectl describe pvc <nom> (ses événements expliquent souvent le blocage) et on vérifie kubectl get storageclass.
