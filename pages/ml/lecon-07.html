Module 03 · Pratique — Leçon 07

Assembler un projet complet

~38 min Intermédiaire Tout le cours

À la fin de cette leçon, tu sauras

  • enchaîner toutes les étapes d'un projet ML sur un vrai jeu de données ;
  • écrire un script complet : charger → préparer → entraîner → évaluer ;
  • utiliser un pipeline pour préparer sans fuite de données ;
  • reconnaître les points où l'on itère pour améliorer données et modèle.
Sommaire de la leçon

On relie tout. Cette leçon déroule un projet complet, du fichier brut à l'évaluation honnête, pour voir comment chaque brique apprise s'emboîte naturellement. Les modules suivants iront ensuite plus loin — clustering, forêts, réglage — avant le projet final.

Le workflow, en un script

Reprenons le déroulé du module 1, mais cette fois en code, sur un cas de classification : prédire si un passager survit, à partir de quelques caractéristiques. Le squelette est toujours le même.

Tout y est : le chargement, la préparation minimale, le découpage, l'entraînement et l'évaluation honnête sur le jeu de test. À partir de là, on itère : ajouter des caractéristiques, en créer de nouvelles, essayer un autre modèle.

Cas réel

Le jeu « passagers » ci-dessus n'est pas fictif : c'est le célèbre jeu Titanic, la compétition d'initiation la plus suivie de Kaggle. On y prédit la survie à partir de la classe, du sexe, de l'âge et du tarif — exactement les colonnes de notre script. C'est devenu le « bonjour, monde ! » du machine learning : assez simple pour tenir en un fichier, assez riche pour illustrer valeurs manquantes, encodage et évaluation honnête.

Le script n'affiche pas qu'un score : il imprime aussi une matrice de confusion. Elle croise ce qui est réel et ce qui est prédit, et sépare les deux fautes qu'une simple exactitude mélange : annoncer un survivant à tort, ou en rater un.

L'exactitude peut mentir

Sur un jeu déséquilibré — par exemple 90 % de « ne survit pas » — un modèle qui répond toujours « ne survit pas » atteint 90 % d'exactitude sans rien apprendre. La matrice de confusion le démasque aussitôt : sa colonne « survit » est vide. Regarde le rappel et la précision, pas seulement le score global.

Le pipeline : préparer sans fuite

Pour garantir que la préparation s'apprend sur l'entraînement et s'applique au test (pas de fuite), on enferme préparation et modèle dans un pipeline. On l'entraîne et on l'utilise comme un seul modèle.

Pourquoi c'est mieux

Le pipeline applique chaque étape au bon moment et de façon cohérente entre entraînement et test. C'est le moyen le plus sûr d'éviter la fuite de données, et le code reste court.

Et après ?

Tu tiens l'essentiel : vocabulaire, workflow, préparation, régression, classification, évaluation. Le module suivant va plus loin — clustering, évaluation fine, forêts aléatoires et réglage des hyperparamètres (GridSearchCV) — avant le projet final qui réunit toutes ces briques.

Pour aller plus loin

Le meilleur entraînement, c'est la pratique : prends un jeu de données qui t'intéresse et refais ce workflow. La compétence clé n'est pas de connaître mille modèles, mais de préparer de bonnes données et d'évaluer honnêtement.

Glossaire

Workflow ML
L'enchaînement des étapes d'un projet : charger → préparer → séparer → entraîner → évaluer → itérer.
Pipeline
Objet scikit-learn qui met bout à bout préparation(s) et modèle ; on l'entraîne et on l'utilise comme un seul modèle (make_pipeline).
Fuite de données (data leakage)
Quand une information du jeu de test influence la préparation ou l'entraînement : elle gonfle le score et trompe. Le pipeline la prévient.
train_test_split
Fonction qui découpe les données en jeu d'entraînement et jeu de test (souvent 80 / 20), avec random_state pour un découpage reproductible.
Jeu de données intégré
Petit jeu fourni avec scikit-learn (load_iris, load_breast_cancer…) pour s'exercer sans chercher de fichier.
Itération
Boucle d'amélioration : à la lumière de l'évaluation, on retouche les caractéristiques, le modèle ou ses réglages, puis on réévalue.
Matrice de confusion
Tableau qui croise classes réelles et prédites : sur la diagonale les bonnes réponses, hors diagonale les faux positifs et les faux négatifs. Elle montre quelles erreurs le modèle commet, là où l'exactitude n'en donne que le total.
Surapprentissage (overfitting)
Quand le modèle colle trop à l'entraînement et généralise mal : score élevé sur l'entraînement, bien plus bas sur le test. On le repère en comparant les deux scores.

Récap et vérification

  • Un projet ML = charger → préparer → séparer → entraîner → évaluer → itérer.
  • Le pipeline enchaîne préparation et modèle sans fuite de données.
  • On évalue sur le test et on compare à l'entraînement pour détecter le surapprentissage.
  • L'essentiel du métier : de bonnes données et une évaluation honnête.

Vérifie ta compréhension

  2. Dans quel ordre s'enchaînent les étapes d'un projet ML ?

Exercices

Exercice 1Échauffement

On veut standardiser les données puis entraîner une régression logistique, sans que la standardisation « voie » le jeu de test (fuite de données). Quel objet scikit-learn enchaîne ces deux étapes en un seul bloc entraînable ?

Voir une solution

Un pipeline, créé avec make_pipeline(StandardScaler(), LogisticRegression()) : le prétraitement est ré-ajusté sur les seules données d'entraînement, à chaque pli de validation.

Exercice 2Application

Ton script sépare les données en entraînement et test, entraîne le modèle, puis affiche un score. Sur quel jeu ce score final doit-il être calculé pour être honnête ?

Voir une solution

Sur le jeu de test, mis de côté avant l'entraînement : c'est la seule mesure de performance sur des données que le modèle n'a jamais vues.

Exercice 3Réflexion

Sur 100 passagers, 38 survivent et 62 non. Un modèle paresseux répond toujours « ne survit pas ». Quelle est son exactitude (en %) ? Et que révèle sa matrice de confusion ?

Voir une solution

62 % : il classe correctement les 62 non-survivants et rate les 38 survivants. Sa matrice de confusion a une colonne « survit » entièrement vide (38 faux négatifs, 0 vrai positif) : le score paraît honorable mais le modèle n'a rien appris. D'où l'intérêt de lire la matrice, pas seulement l'exactitude.
