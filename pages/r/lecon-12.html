Module 4 · R en pratique — Leçon 12

Rapports reproductibles et écosystème

~50 min Intermédiaire Prérequis : leçon 11

À la fin de cette leçon, tu sauras

  • comprendre ce qu'est un rapport reproductible et pourquoi R Markdown / Quarto changent la donne ;
  • savoir structurer un projet R avec des chemins relatifs (here) et figer ses dépendances avec renv ;
  • situer les grandes briques de l'écosystème (Shiny, data.table) et leurs usages ;
  • tracer un plan d'apprentissage et un panorama des métiers de la donnée en R.
Sommaire de la leçon

Tu sais maintenant manipuler des vecteurs, des data frames, filtrer, regrouper, visualiser. Mais à quoi sert tout ce travail s'il vit seulement dans ta console, et s'évapore dès que tu fermes RStudio ? Cette leçon répond à la question « où mène R ? ». La réponse tient en un mot : reproductibilité — produire des documents qui mêlent texte, code et résultats, et qui se régénèrent à l'identique d'un seul geste.

On va découvrir R Markdown et Quarto, apprendre à organiser un projet proprement, puis prendre de la hauteur : l'écosystème R (Shiny, data.table) et les métiers qu'il ouvre. C'est la leçon qui transforme tes scripts en livrables.

Le problème : un résultat qu'on ne peut pas rejouer

Imagine : tu calcules une moyenne dans la console, tu la copies-colles dans un document Word, tu ajoutes un graphique exporté en PNG. Trois semaines plus tard, les données changent. Tu dois TOUT refaire à la main : recalculer, ré-exporter, re-coller. À la moindre étape oubliée, ton rapport ment.

Un rapport reproductible résout ça : le texte, le code et les résultats vivent dans un seul fichier source. Tu changes les données, tu relances, et le document entier — chiffres, tableaux, figures — se met à jour tout seul. C'est l'idée centrale, et R la pousse plus loin que presque tout autre langage.

Note

On parle de « programmation lettrée » (literate programming) : l'idée, due à Donald Knuth, qu'un document destiné aux humains et le code qui le produit ne devraient faire qu'un. R Markdown et Quarto en sont l'incarnation moderne.

R Markdown : texte + code dans un même document

Un fichier .Rmd est un document texte simple (format Markdown : # pour les titres, **gras**, etc.) dans lequel on insère des blocs de code (chunks). Quand tu « tisses » (knit) le document, R exécute chaque bloc et insère le résultat — texte, tableau ou figure — à sa place.

Les trois tirets --- en haut délimitent l'en-tête YAML : titre, auteur, et surtout output qui décide du format final. Les blocs ouverts par ```{r} contiennent du code R ; tout le reste est du texte. En tissant ce fichier, R produit une page HTML propre où la valeur 128.75 apparaît, calculée en direct.

Les options de bloc : contrôler ce qui s'affiche

Chaque bloc accepte des options qui pilotent son comportement. Tu peux exécuter du code sans le montrer, montrer le code sans l'exécuter, masquer les messages d'avertissement, ou régler la taille d'une figure.

Les options les plus courantes : echo (montrer le code ?), eval (l'exécuter ?), include (inclure quoi que ce soit ?), warning et message (afficher avertissements et messages ?), fig.width/fig.height (taille des figures). Pour un rapport destiné à un public non technique, tu mets souvent echo=FALSE partout : on ne voit que le texte et les résultats.

Quarto : le successeur, multi-langage

Quarto est l'évolution de R Markdown, sortie en 2022. Même philosophie, même syntaxe de blocs, mais c'est un outil indépendant de R (il marche aussi avec Python, Julia, Observable) et plus riche : sites web, livres, présentations, le tout depuis des fichiers .qmd.

Note la nouveauté : les options de bloc s'écrivent désormais ligne par ligne avec #| (le « hash-pipe »), plus lisible que l'ancienne accolade. Ici format: revealjs transforme le document en présentation. Le même fichier, en remplaçant juste revealjs par pdf ou html, devient un PDF ou une page web. Un seul code, plusieurs sorties.

Astuce

Pour un nouveau projet en 2026, commence directement par Quarto : c'est la direction recommandée et tu réutilises tout ce que tu sais de R Markdown. Le format .qmd deviendra ton réflexe.

Projets RStudio et chemins relatifs avec here

Un rapport reproductible doit aussi savoir où sont ses fichiers. Le piège classique : écrire un chemin absolu comme "C:/Users/noah/Documents/data/ventes.csv". Sur l'ordinateur d'un collègue, ce chemin n'existe pas : le rapport casse.

La solution : un projet RStudio (un fichier .Rproj à la racine d'un dossier) qui définit un point d'ancrage. Combiné au paquet here, tu décris les chemins relativement à la racine du projet.

here("data", "ventes.csv") donne le bon chemin chez toi, chez ton collègue, et dans un rapport tissé. Plus jamais de setwd() en dur. C'est une habitude qui sépare le script jetable du projet partageable.

Figer les dépendances avec renv

Dernier maillon de la reproductibilité : les versions des paquets. Ton analyse marche aujourd'hui avec dplyr 1.1 ; dans deux ans, une mise à jour pourrait changer un comportement. Le paquet renv photographie l'état exact de tes paquets dans un fichier renv.lock, que tu partages avec le code.

Le couple snapshot() / restore() garantit que quiconque ouvre ton projet installe les mêmes versions. C'est la différence entre « ça marche chez moi » et « ça marche partout ».

Survol de l'écosystème : Shiny et data.table

R ne s'arrête pas aux rapports statiques. Deux paquets ouvrent des horizons très différents.

Shiny transforme ton code R en application web interactive, sans écrire une ligne de HTML ou de JavaScript. L'utilisateur déplace un curseur, l'analyse se recalcule en direct.

Le principe : une partie ui décrit l'interface, une partie server décrit la logique. Quand input$n change, tout ce qui en dépend se recalcule — c'est la réactivité. Des tableaux de bord entiers se construisent ainsi.

data.table, lui, vise la performance brute. Sur des tables de plusieurs millions de lignes, là où dplyr peut peiner, data.table reste rapide grâce à une syntaxe concise dt[i, j, by] et un traitement en mémoire très optimisé.

Note

Tu n'as pas à choisir un camp : dplyr pour la lisibilité au quotidien, data.table quand le volume l'exige. Les deux manipulent des data frames ; tu passes de l'un à l'autre selon le besoin.

Où mène R : science des données et métiers

R est né en statistique et y reste un pilier. On le retrouve massivement en : biostatistique et recherche médicale (essais cliniques, épidémiologie), recherche académique (sciences sociales, écologie, psychologie — où la reproductibilité est exigée), data analyse en entreprise (reporting, tableaux de bord Shiny), et finance/assurance pour les modèles de risque.

Côté métiers : data analyst, biostatisticien, chercheur, data scientist. R brille particulièrement là où il faut comprendre les données (modélisation statistique, communication des résultats) plus que déployer des systèmes à grande échelle — terrain où Python domine souvent. Maîtriser les deux est un atout, mais R seul ouvre déjà de vraies portes.

Pièges fréquents

Piège fréquent

Compter sur l'état de ta console. Un rapport doit tourner « à blanc », dans une session vide : si tu as défini ventes à la main dans la console mais oublié de le faire dans un bloc, le tissage échouera avec Error: object 'ventes' not found. Tisse souvent pour détecter ces oublis tôt.

Piège fréquent

Les chemins absolus et setwd("C:/...") en tête de script. Ils cassent dès que le code voyage. Utilise un projet .Rproj + here() et tes chemins survivront au changement de machine.

Cas réel

Cas réel

Pendant la pandémie de COVID-19, des agences sanitaires (Santé publique France, le Robert Koch Institut en Allemagne) ont publié des tableaux de bord mis à jour chaque jour : cas, cartes, courbes. Refaire tout cela à la main quotidiennement aurait été intenable et truffé d'erreurs. La réponse : des rapports reproductibles (R Markdown / Quarto). Un seul document source, relancé automatiquement dès l'arrivée des nouvelles données, régénérait chiffres, graphiques et texte à l'identique. Même exigence dans les revues scientifiques, qui réclament de plus en plus le code et les données pour qu'un résultat soit vérifiable : la « crise de la reproductibilité » a fait de cette pratique un standard. Ce que tu apprends ici est exactement l'outillage de ces livrables critiques.

Pour aller plus loin

Pour aller plus loin

Le livre gratuit R for Data Science (Wickham, Çetinkaya-Rundel, Grolemund) est la référence pour consolider tout le tidyverse. Pour Quarto, la documentation officielle quarto.org est claire et illustrée. Et pour publier : shinyapps.io héberge une appli Shiny en quelques clics, Quarto Pub ou GitHub Pages pour un rapport.

Glossaire

Rapport reproductible
Document où texte, code et résultats vivent dans une source unique qui se régénère à l'identique.
R Markdown (.Rmd)
Format mêlant Markdown et blocs de code R, tissé (knit) en HTML, PDF ou Word.
Quarto (.qmd)
Successeur multi-langage de R Markdown ; options de bloc en #|, sorties web, PDF, diapos.
Chunk (bloc de code)
Portion de code exécutée au tissage, dont le résultat s'insère dans le document.
Option de bloc
Réglage d'un chunk (echo, eval, include, fig.width…) contrôlant ce qui s'affiche.
here()
Construit des chemins relatifs à la racine du projet (.Rproj), portables d'une machine à l'autre.
renv
Fige les versions des paquets dans renv.lock (snapshot()/restore()) pour un environnement reproductible.
Réactivité (Shiny)
Mécanisme où toute sortie dépendant d'une entrée se recalcule automatiquement quand cette entrée change.

Récap et vérification

Tu as bouclé le parcours : de la leçon 1 où tout était un vecteur, jusqu'au document final qui se régénère seul. Voici les acquis de cette leçon :

  • Un rapport reproductible réunit texte, code et résultats dans une source unique qui se régénère.
  • R Markdown (.Rmd) et Quarto (.qmd) tissent ce document en HTML, PDF ou slides ; les options de bloc (echo, include, fig.width…) contrôlent l'affichage.
  • Un projet RStudio + here() rendent les chemins portables ; renv fige les versions de paquets.
  • L'écosystème s'étend de Shiny (apps web réactives) à data.table (performance), avec des débouchés en data analyse, biostatistique et recherche.

Vérifie ta compréhension

  1. Quelle option de bloc utilises-tu pour qu'un graphique apparaisse dans le rapport sans montrer le code qui le génère ?
  2. Pourquoi here("data", "ventes.csv") est-il préférable à un chemin absolu écrit en dur ?
  3. Dans une appli Shiny, que se passe-t-il quand l'utilisateur modifie un sliderInput dont dépend un renderPlot ?
