Configurer Git à son goût : config, alias, includeIf

~33 min Intermédiaire Leçon 02 recommandée

À la fin de cette leçon, tu sauras

  • distinguer les trois niveaux de configuration (system, global, local) et leur priorité ;
  • lire et écrire des réglages avec git config, et connaître les plus utiles ;
  • créer des alias pour raccourcir tes commandes ;
  • changer d'identité selon le dossier avec includeIf, et poser un .gitignore global.
Sommaire de la leçon

Git ne cache aucune « préférence » secrète : tout son comportement se règle par des paires clé/valeur lisibles, rangées dans de simples fichiers texte. Depuis la leçon 2, tu as posé user.name et user.email sans forcément savoir où ni à quel niveau. Cette leçon ouvre le capot de la configuration : comprendre la cascade des niveaux, connaître les réglages qui changent le quotidien, et personnaliser Git avec des alias et une identité par projet.

Piège fréquent

Les fins de ligne (core.autocrlf) empoisonnent les équipes mixtes Windows/macOS/Linux : un fichier entier apparaît « modifié » alors que seuls les retours chariot ont changé. La solution durable n'est pas qu'un réglage personnel : c'est un fichier .gitattributes versionné avec * text=auto, qui impose la même normalisation à toute l'équipe.

Les alias : des raccourcis de commandes

Tu tapes git status et git checkout cinquante fois par jour ? Un alias leur donne un nom court. Un alias qui commence par ! exécute même une commande shell arbitraire.

Astuce

Un alias lg pour un graphe compact d'historique est le premier que la plupart des développeurs posent. Édite directement ~/.gitconfig (section [alias]) pour les gérer en lot : c'est plus rapide que d'enchaîner les git config.

Une identité par projet avec includeIf

Beaucoup de développeurs jonglent entre une identité professionnelle et une identité personnelle. Poser user.email à la main dans chaque dépôt est fastidieux et source d'oublis (des commits pro signés avec l'adresse perso, ou l'inverse). La directive includeIf charge un fichier de configuration selon le chemin du dépôt.

Tout dépôt cloné sous ~/pro/ utilisera automatiquement l'adresse professionnelle ; ceux sous ~/perso/, l'adresse personnelle.

Cas réel

Une développeuse contribue à des projets internes de son employeur et à des dépôts open source personnels le week-end. Longtemps, elle a corrigé après coup des commits envoyés avec la mauvaise adresse — jusqu'au jour où un commit pro signé de son adresse perso a atterri dans un dépôt public de l'entreprise. Depuis, deux blocs includeIf (un pour ~/travail/, un pour ~/oss/) fixent la bonne adresse selon le dossier : le bon courriel est appliqué dès le clone, sans qu'elle ait à y penser. Fini les commits mal attribués.

Un .gitignore global

Certains fichiers ne concernent que ta machine, pas le projet : fichiers de ton éditeur, .DS_Store de macOS, dossiers d'IDE. Les mettre dans le .gitignore du dépôt imposerait tes outils aux autres. Mieux vaut un .gitignore global, propre à ton compte :

Pièges fréquents

  • Oublier --global : un git config user.email … sans niveau écrit en local et ne vaut que pour le dépôt courant. Tu recommences à chaque clone.
  • Ne pas savoir d'où vient une valeur : git config --list --show-origin révèle le fichier exact — indispensable quand une identité « colle » sans raison.
  • Croire que core.autocrlf suffit en équipe : c'est un réglage personnel ; la vraie solution partagée est .gitattributes.
  • Exposer une adresse privée : les commits publient user.email ; utilise au besoin l'adresse de no-reply fournie par la plateforme.

Pour aller plus loin

Pour aller plus loin

Regarde les credential helpers (git config --global credential.helper) pour mémoriser tes accès HTTPS sans retaper de mot de passe, la signature automatique des commits (commit.gpgSign avec une clé GPG ou SSH), et includeIf "hasconfig:remote.*.url:…" qui conditionne la config non plus au dossier mais à l'URL du dépôt distant. Enfin, versionne un fichier d'alias et de réglages d'équipe dans un dépôt de dotfiles pour retrouver ton environnement sur chaque machine.

Antisèche

Glossaire

git config
Commande unique pour lire et écrire les réglages de Git, à l'un des trois niveaux (--system, --global, --local).
Niveau system
Configuration valable pour toute la machine et tous les comptes ; fichier /etc/gitconfig. Priorité la plus faible.
Niveau global
Configuration de ton compte utilisateur, valable pour tous tes dépôts ; fichier ~/.gitconfig.
Niveau local
Configuration d'un seul dépôt ; fichier .git/config. Priorité la plus forte : elle écrase global et system.
Alias
Raccourci de commande défini sous [alias] ; un alias préfixé de ! exécute une commande shell au lieu d'une sous-commande Git.
includeIf
Directive qui inclut conditionnellement un autre fichier de config selon un critère (souvent gitdir:, le chemin du dépôt) — pratique pour changer d'identité par dossier.
core.autocrlf
Réglage de conversion des fins de ligne entre systèmes ; à compléter par un .gitattributes partagé pour une équipe multi-OS.
core.excludesFile
Chemin d'un .gitignore global, appliqué à tous tes dépôts en plus du .gitignore de chaque projet.

Récap et vérification

  • La config vit à trois niveaux (system → global → local) ; le plus proche du dépôt gagne.
  • git config --list --show-origin dit d'où vient chaque valeur.
  • Quelques clés bien posées (init.defaultBranch, pull.rebase, core.editor…) évitent bien des surprises.
  • Les alias raccourcissent les commandes ; un ! initial permet d'appeler le shell.
  • includeIf applique une identité par dossier ; core.excludesFile pose un .gitignore global.

Vérifie ta compréhension

  1. Si user.email est défini en global et en local, laquelle Git utilise-t-il ?

  3. Comment créer un alias git lg pour un graphe d'historique ?
