Rebase et historique propre

~34 min Intermédiaire Module 3 recommandé

À la fin de cette leçon, tu sauras

  • rejouer ta branche sur une base à jour avec git rebase main pour un historique linéaire ;
  • choisir entre merge et rebase selon le contexte, et nettoyer ton travail avec un rebase interactif (squash, reword) ;
  • reprendre un commit précis avec git cherry-pick et résoudre un conflit pendant un rebase (--continue / --abort) ;
  • appliquer la règle d'or : ne jamais réécrire un historique déjà partagé, et utiliser --force-with-lease avec prudence.
Sommaire de la leçon

Tu as branché ta fonctionnalité il y a trois jours, tu as fait sept petits commits (« wip », « oups typo », « ça marche enfin »), et pendant ce temps main a avancé. Quand tu ouvres ta pull request, l'historique ressemble à un brouillon. Cette leçon t'apprend à le réécrire pour le rendre propre : rejouer tes commits au-dessus d'une base à jour, regrouper et renommer tes commits, et reprendre un commit précis d'une branche à l'autre.

C'est puissant, donc on pose tout de suite la limite : réécrire l'historique se fait uniquement sur ton travail local, jamais sur ce que les autres ont déjà récupéré. Garde cette frontière en tête, on y revient à la fin.

git rebase : rejouer ses commits

Un rebase prend tes commits et les rejoue un par un au-dessus d'une autre base. Au lieu d'avoir une branche qui part d'un vieux point de main, c'est comme si tu avais commencé ton travail à partir du main d'aujourd'hui.

Visuellement, avant le rebase ta branche part d'un ancêtre commun pendant que main a avancé de son côté :

Le rebase produit un historique linéaire : tes commits viennent proprement après le dernier état de main. Note les A', B', C' : ce sont de nouveaux commits (nouveaux identifiants), pas les originaux déplacés.

Note

Comme le rebase recrée chaque commit, leur empreinte (le sha) change. Ce sont les mêmes modifications, mais techniquement d'autres commits. C'est précisément ce qui rend le rebase dangereux sur des commits déjà partagés : voir la règle d'or plus bas.

merge ou rebase : lequel choisir

Les deux intègrent le travail d'une branche dans une autre, mais le résultat n'a pas la même forme.

  • git merge crée un commit de fusion qui réunit deux historiques. Il préserve l'histoire réelle : on voit que la branche a existé en parallèle puis a rejoint main.
  • git rebase réécrit tes commits pour les aligner : l'historique devient linéaire et propre, mais la fusion parallèle disparaît du récit.

Règle pratique simple : utilise le rebase pour mettre à jour ta propre branche en cours de travail (tu restes seul dessus), et garde le merge pour intégrer dans main une branche partagée si ton équipe veut tracer les fusions.

Mettre à jour ta branche par rebase évite les commits de fusion « Merge branch main into… » qui polluent l'historique d'une fonctionnalité encore en cours.

Le rebase interactif : réécrire avant la PR

Le rebase interactif est l'outil de nettoyage par excellence. Tu lui dis combien de commits récents tu veux retravailler avec HEAD~n (ici les 3 derniers), et Git ouvre une liste éditable.

Git affiche une « todo list » où chaque ligne est une action à appliquer à un commit. Tu remplaces le mot-clé devant chaque ligne, tu enregistres, et Git exécute.

Ici, les deux squash regroupent les trois commits en un seul : Git te proposera ensuite d'écrire le message final. Quelques usages concrets :

  • squash / fixup : regrouper des commits « wip » en un commit cohérent. fixup est squash sans garder le message de la rustine.
  • reword : corriger un message de commit mal formulé sans toucher au code.
  • réordonner : déplace simplement les lignes pour changer l'ordre des commits.
  • drop : jeter un commit devenu inutile (un essai abandonné).

Astuce

Nettoie ta branche juste avant d'ouvrir la PR, pas pendant que tu codes. Tant que tu travailles, commite vite et souvent ; le rebase interactif fera le ménage en fin de course.

Cas réel

Le projet Git lui-même et le noyau Linux exigent un historique atomique : chaque commit doit compiler seul et ne faire qu'une chose, pour rester git bisect-able. Leurs contributeurs nettoient donc systématiquement leur branche au rebase interactif avant de la soumettre. À l'inverse, beaucoup d'équipes en entreprise délèguent ce ménage à GitHub via « Squash and merge », qui condense toute la PR en un commit unique sur main. Même objectif dans les deux cas : un main où chaque ligne d'historique raconte une intention claire.

git cherry-pick : reprendre un commit précis

Parfois tu veux un seul commit d'une autre branche, pas toute la branche. Par exemple, une correction urgente faite sur une branche de dév que tu veux porter immédiatement sur main. C'est le rôle de cherry-pick : il rejoue le commit désigné sur ta branche actuelle.

Le commit est recréé sur main avec un nouvel identifiant : il s'agit d'une copie de la modification, pas du commit d'origine déplacé.

La règle d'or de la réécriture

Voici la seule règle à ne jamais oublier de toute la leçon :

Piège fréquent

Ne jamais rebaser ou réécrire des commits déjà poussés et partagés. Comme le rebase change les empreintes, tes collègues se retrouvent avec un historique divergent et des conflits pénibles. Réécris seulement tes commits locaux, encore à toi seul.

Si tu as déjà poussé une branche qui n'appartient qu'à toi et que tu l'as ensuite rebasée, le git push normal sera refusé : le distant et le local ont divergé. Tu peux forcer, mais avec le bon garde-fou.

--force-with-lease vérifie que personne n'a poussé depuis ta dernière synchro avant d'écraser. Si quelqu'un a publié entre-temps, Git refuse et t'évite d'effacer son travail.

Résoudre un conflit pendant un rebase

Comme le rebase rejoue tes commits un par un, un conflit peut surgir à n'importe quel commit. Git s'arrête alors et attend. Pas de panique : tu as toujours deux issues, continuer ou tout annuler.

git rebase --abort est ta corde de rappel : il défait le rebase en cours et te ramène exactement où tu étais avant de le lancer. Tant que tu n'as pas terminé, tu ne risques rien.

Note

Au cours d'un rebase, le même conflit peut apparaître plusieurs fois si plusieurs de tes commits touchent la même zone. C'est normal : tu résous, tu fais git add, puis git rebase --continue, et tu recommences jusqu'à la fin.

Pièges fréquents

  • Rebaser une branche publique partagée. Si d'autres travaillent sur la branche, tu casses leur historique. La réécriture est réservée à ton travail local non partagé.
  • git push --force brutal. Il écrase le distant sans vérifier : tu peux supprimer les commits d'un collègue poussés entre-temps. Préfère toujours --force-with-lease.
  • Se perdre dans un rebase interactif. Trop d'actions, des conflits en cascade, tu ne sais plus où tu en es ? git rebase --abort et tu repars de zéro, sans dégât.
  • Cherry-pick qui duplique des commits. Si tu fais un cherry-pick puis fusionnes plus tard la branche d'origine, le même changement peut apparaître deux fois dans l'historique. N'utilise cherry-pick que pour des reprises ponctuelles.

Pour aller plus loin

Quelques outils à découvrir quand tu seras à l'aise avec les bases :

  • git rebase --onto : déplacer une série de commits depuis une base vers une autre base précise, utile pour « rebrancher » une branche partie du mauvais endroit.
  • L'autosquash : git commit --fixup <sha> marque une rustine, puis git rebase -i --autosquash la replace et la fusionne automatiquement au bon endroit.
  • git reflog : le journal de tous tes déplacements de HEAD. C'est ton filet de sécurité : même après un rebase raté, tu y retrouves l'ancien état pour le récupérer.
  • Les politiques d'équipe : certaines équipes imposent un historique linéaire (rebase obligatoire), d'autres préfèrent les commits de fusion. Suis la convention de ton projet.

Pour aller plus loin

Si un rebase tourne mal, ouvre git reflog : tu y verras une ligne comme HEAD@{5} pointant sur l'état d'avant. Un git reset --hard HEAD@{5} te ramène à ce point. Tant que les commits existent dans le reflog, rien n'est vraiment perdu.

Antisèche : réécrire l'historique

Le mémo des commandes de rebase, cherry-pick et sauvetage.

Glossaire

Rebase
Rejouer une série de commits au-dessus d'une autre base ; produit un historique linéaire en recréant les commits (nouveaux SHA).
Rebase interactif
git rebase -i : une « todo list » où l'on choisit pour chaque commit pick, squash, fixup, reword, edit, drop ou l'ordre.
squash / fixup
Fondre un commit dans le précédent. squash garde les deux messages ; fixup jette celui de la rustine.
cherry-pick
Rejouer un seul commit d'une branche sur la branche courante, sous forme d'une copie au nouvel identifiant.
Règle d'or
Ne jamais réécrire (rebase, amend, squash) des commits déjà poussés et partagés ; ne réécrire que du travail local.
--force-with-lease
Variante prudente de --force : refuse de pousser si le distant a bougé depuis ton dernier fetch, pour ne pas écraser le travail d'autrui.
git reflog
Journal local des déplacements de HEAD ; filet de sécurité pour restaurer un état antérieur à un rebase.

Récap et vérification

  • git rebase main rejoue tes commits au-dessus de main pour un historique linéaire (le merge, lui, crée un commit de fusion et garde l'histoire réelle).
  • Le rebase recrée les commits : leurs empreintes changent, d'où la règle d'or.
  • git rebase -i HEAD~n permet de squash/fixup (regrouper), reword (renommer), edit, drop et réordonner : idéal pour nettoyer avant une PR.
  • git cherry-pick <sha> reprend un commit précis sur une autre branche.
  • Règle d'or : ne jamais réécrire des commits partagés ; si tu dois forcer un push sur ta branche, utilise --force-with-lease.
  • Pendant un rebase : résoudre puis git add et git rebase --continue, ou tout annuler avec git rebase --abort.

Vérifie ta compréhension

  1. Quelle différence d'historique obtient-on avec git merge main contre git rebase main sur sa branche ?
  2. Pourquoi ne faut-il jamais rebaser des commits déjà poussés et partagés ?
  3. À quoi sert un rebase interactif (git rebase -i) juste avant d'ouvrir une pull request ?
