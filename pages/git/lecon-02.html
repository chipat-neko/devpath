Module 01 · Démarrer avec Git — Leçon 02

Premier dépôt et commits

~30 min Débutant Leçon 01 recommandée

À la fin de cette leçon, tu sauras

  • configurer ton identité Git avec git config --global pour signer tes commits ;
  • initialiser un dépôt avec git init et comprendre les trois zones (travail, index, dépôt) ;
  • indexer tes fichiers avec git add et enregistrer un instantané avec git commit ;
  • lire l'historique avec git log et écrire de bons messages de commit.
Sommaire de la leçon

Dans la leçon précédente, tu as installé Git et compris pourquoi versionner son code : garder un historique, pouvoir revenir en arrière, collaborer. Place maintenant à la pratique. Cette leçon te fait créer ton premier dépôt et enregistrer tes premières versions, qu'on appelle des commits.

Tu vas voir trois commandes que tu taperas des dizaines de fois par jour : git status, git add et git commit. Mais avant tout, une étape de réglage à ne faire qu'une seule fois sur ta machine.

La configuration initiale : qui es-tu ?

Chaque commit est signé : Git y inscrit un nom et un e-mail. Si tu ne les renseignes pas, tes commits seront anonymes (ou Git refusera de les créer). On règle ça une fois pour toutes avec git config --global, qui écrit dans ton profil utilisateur et vaut donc pour tous tes futurs dépôts.

Remplace par ton vrai nom et l'e-mail que tu utiliseras (le même que ton compte GitHub, idéalement).

Note

Le réglage init.defaultBranch main garantit que tes nouveaux dépôts utilisent main comme branche par défaut (la norme moderne). Git lui-même reste sur master tant que ce réglage n'est pas posé ; seules des plateformes comme GitHub choisissent main pour les dépôts qu'elles créent. Pose-le une fois pour toutes.

Créer un dépôt : git init

Un dépôt (ou repo), c'est simplement un dossier que Git surveille. Pour le transformer en dépôt, place-toi dedans et lance git init. Ça marche aussi bien sur un dossier vide que sur un projet déjà commencé.

Git vient de créer un sous-dossier caché .git/ : c'est là qu'il range tout l'historique. Ne le supprime pas et ne touche pas à son contenu ; c'est le « cerveau » de ton dépôt. Le reste du dossier, c'est ton projet normal.

Sur un dossier déjà rempli, git status listerait au contraire tous les fichiers existants comme « non suivis ».

Les trois zones : le cœur de Git

C'est l'idée la plus importante de la leçon. Entre ton dossier et l'historique, Git met une zone intermédiaire. Un fichier passe par trois zones :

Tu modifies tes fichiers dans le répertoire de travail. Avec git add, tu déposes une version dans l'index (la zone de préparation, aussi appelée staging). Avec git commit, tu enregistres le contenu de l'index dans le dépôt. Cette zone intermédiaire te laisse choisir précisément quoi inclure dans chaque commit.

Indexer avec git add (et se rétracter avec git restore)

git add place un fichier dans l'index. Tu peux viser un fichier précis, un dossier, ou tout d'un coup avec . (le point = le dossier courant).

Après un git add index.html, le statut change : le fichier passe en vert, prêt à être committé.

Tu as indexé un fichier par erreur ? Pas de panique : git restore --staged le retire de l'index sans toucher à ton fichier sur le disque. Tu le sors juste de la zone de préparation.

Note

git restore --staged est la commande moderne. Tu croiseras encore l'ancienne forme git reset HEAD <fichier> dans de vieux tutoriels : elle fait la même chose pour désindexer.

Cas réel — committer par petits paquets

Tu as corrigé une faute de frappe et commencé une nouvelle fonctionnalité avant de t'arrêter. Plutôt que de tout mélanger dans un seul commit fourre-tout, tu te sers de l'index comme d'un panier : git add correction.txt puis git commit -m "Corrige la faute d'orthographe", et seulement ensuite tu prépares le reste. La zone de préparation te laisse découper ton travail en commits propres et cohérents, même quand tout a été fait d'un bloc.

Enregistrer un instantané : git commit

Tout ce qui est dans l'index, tu le figes avec git commit. L'option -m permet de donner le message directement, sans ouvrir l'éditeur.

Tu viens de créer ton premier commit. Un commit, c'est un instantané (une photo) de ton projet à un instant T. Git lui attache :

  • un identifiant SHA unique (le a1b2c3d ci-dessus, en réalité 40 caractères abrégés à 7) ;
  • un auteur et une date (d'où la config du début) ;
  • ton message ;
  • un lien vers le commit parent (le précédent), ce qui forme la chaîne de l'historique.

Le tout premier commit n'a pas de parent : c'est pour ça que Git l'annonce comme root-commit dans la sortie ci-dessus. Après le commit, git status redevient calme : il n'y a plus rien en attente.

Écrire de bons messages de commit

Un bon message explique ce que fait le commit, en une ligne courte (≈ 50 caractères) et à l'impératif, comme un ordre donné au code : « Ajoute… », « Corrige… », « Supprime… ». Imagine que la phrase complète soit « Ce commit va… ».

Si tu veux détailler, lance git commit sans -m : Git ouvre ton éditeur pour écrire une ligne de titre, une ligne vide, puis un paragraphe d'explications.

Voir l'historique : git log

git log affiche la liste des commits, du plus récent au plus ancien. Fais un deuxième commit pour voir la chaîne grandir.

Pour une vue compacte, une ligne par commit, utilise les options --oneline et --graph :

HEAD -> main indique où tu te trouves : la branche main, pointée sur le dernier commit.

Pièges fréquents

Piège fréquent

git add ne sauvegarde rien. Il prépare seulement le commit. Tant que tu n'as pas tapé git commit, rien n'est enregistré dans l'historique. add puis commit vont toujours ensemble.

  • Oublier git config. Tes commits portent alors un auteur inconnu (ou Git refuse de committer). Règle ton identité avant le premier commit.
  • Committer des fichiers non voulus avec git add . : fichiers temporaires, dossiers lourds, secrets… Relis toujours git status avant de committer. La leçon 3 réglera ça avec .gitignore.
  • Messages vagues comme « update » ou « fix » : inutilisables quand tu relis l'historique des mois plus tard. Décris l'intention.
  • Confondre les zones. Modifier un fichier après l'avoir indexé ? Il faut le re-adder : l'index garde la version du moment du add.

Pour aller plus loin

Pour les fichiers déjà suivis par Git (déjà committés au moins une fois), le raccourci git commit -a -m "…" fait l'add et le commit en une seule commande. Attention : il n'ajoute pas les fichiers non suivis.

Pour aller plus loin

Tu peux te créer des alias pour les commandes longues : git config --global alias.st status rend git st équivalent à git status. Et le fichier .gitignore (leçon 3) dira à Git quels fichiers ignorer définitivement.

Antisèche : premiers commits

Le mémo des commandes de cette leçon.

Glossaire

Dépôt (repository)
Dossier surveillé par Git ; son historique est stocké dans le sous-dossier caché .git/.
Répertoire de travail
Tes fichiers réels sur le disque, ceux que tu édites avant de les indexer.
Index (staging)
Zone de préparation où git add place ce qui entrera dans le prochain commit.
Commit
Instantané figé du projet, identifié par un SHA, avec auteur, date, message et parent.
SHA
Empreinte unique de 40 caractères (souvent abrégée à 7) qui identifie un commit sans ambiguïté.
HEAD
Pointeur sur le commit courant ; HEAD → main signifie « je suis sur la branche main, au dernier commit ».
Branche main
Ligne de développement par défaut des dépôts modernes (fixée par init.defaultBranch).
git config --global
Réglage écrit dans ton profil utilisateur, valable pour tous tes dépôts (nom, e-mail, éditeur…).

Récap et vérification

  • On signe ses commits via git config --global user.name et user.email (à faire une fois).
  • git init crée un dépôt (le dossier .git/) ; git status dit où en sont les fichiers.
  • Trois zones : répertoire de travail → index (git add) → dépôt (git commit).
  • git restore --staged <fichier> désindexe sans rien perdre.
  • Un commit = un instantané avec un SHA, un auteur, une date, un message et un parent ; git log le relit.

Vérifie ta compréhension

  1. Tu viens de créer un fichier contact.html encore non suivi. Pourquoi git commit -a -m "…" ne le mettra-t-il pas dans le commit ?
  2. Tu as fait git add brouillon.txt par erreur. Quelle commande le retire de l'index sans supprimer le fichier ?
  3. Cite trois informations que Git attache à chaque commit, et dis d'où vient le nom de l'auteur.
