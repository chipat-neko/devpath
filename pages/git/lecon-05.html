Module 02 · Branches & corrections — Leçon 05

Fusionner des branches

~32 min Débutant Leçon 04 recommandée

À la fin de cette leçon, tu sauras

  • lancer une fusion depuis la bonne branche avec git merge <branche> ;
  • distinguer une fusion fast-forward d'une vraie fusion à trois branches ;
  • forcer un commit de fusion avec git merge --no-ff et nettoyer avec git branch -d ;
  • visualiser l'historique fusionné avec git log --graph --oneline.
Sommaire de la leçon

Jusqu'ici tu as appris à créer une branche pour travailler à l'écart de main. Mais une branche n'a d'intérêt que si, un jour, tu réunis son travail avec le reste du projet. C'est exactement le rôle de la fusion (en anglais merge) : prendre les commits d'une branche et les intégrer dans une autre.

Dans cette leçon, on suppose que tout se passe bien : les deux branches ne touchent pas aux mêmes lignes. Quand ce n'est pas le cas, Git signale un conflit — un sujet à part entière qu'on traite à la leçon suivante. Ici, concentrons-nous sur les fusions sans accroc, qui représentent l'immense majorité des cas.

Le principe : intégrer une branche dans une autre

Fusionner, c'est dire à Git : « prends tous les commits de cette branche-là et amène-les dans la branche où je me trouve ». La règle d'or à graver dès maintenant : on fusionne VERS la branche courante. Tu te places d'abord sur la branche de destination (le plus souvent main), puis tu indiques la branche source.

On se met sur main, puis on y intègre la branche connexion.

L'ordre compte énormément. Après ces deux commandes, c'est main qui contient le travail de connexion, et non l'inverse. La branche connexion, elle, n'a pas bougé : on l'a simplement recopiée dans main.

La fusion fast-forward

Imagine que tu as créé connexion à partir de main, puis ajouté deux commits dessus, sans toucher à main pendant ce temps. Du point de vue de Git, main est resté en arrière sur le même commit, et connexion a juste avancé tout droit devant lui.

Comme il n'y a pas de divergence, Git n'a rien à réconcilier : il lui suffit de faire avancer le pointeur de main jusqu'au dernier commit de connexion. C'est ce qu'on appelle une fusion fast-forward (« avance rapide »). Aucun nouveau commit n'est créé : on déplace simplement une étiquette.

Le mot Fast-forward dans la sortie te confirme qu'aucun commit de fusion n'a été fabriqué : l'historique reste une ligne droite, parfaitement linéaire.

La fusion à trois branches (vrai commit de fusion)

Le cas précédent est le plus simple, mais pas le plus fréquent en équipe. Souvent, pendant que tu travaillais sur connexion, quelqu'un (ou toi) a aussi ajouté des commits sur main. Les deux branches ont alors divergé : elles partagent un ancêtre commun, mais chacune a sa propre suite de commits.

Ici, Git ne peut pas se contenter d'avancer un pointeur : il doit combiner deux histoires. Il regarde l'ancêtre commun (o) et les deux pointes (B et Y) — d'où le nom de fusion à trois branches (three-way merge). Il fabrique alors un commit spécial, le commit de fusion (ici M), qui a la particularité d'avoir deux parents : il relie les deux lignes d'histoire.

Cette fois, la sortie indique Merge made by the 'ort' strategy et non Fast-forward : c'est ta preuve qu'un commit de fusion a bien été créé. Git ouvrira souvent ton éditeur pour que tu valides un message de fusion (un message par défaut, du type Merge branch 'connexion', est déjà proposé).

Note

Tu n'as pas à choisir entre fast-forward et trois branches : Git décide tout seul selon que les branches ont divergé ou non. Ton seul travail, c'est de te placer sur la bonne branche avant de lancer git merge.

Forcer un commit de fusion avec --no-ff

Parfois, même quand un fast-forward serait possible, tu veux un commit de fusion. Pourquoi ? Pour garder une trace visible : « ici, la fonctionnalité connexion a été intégrée ». Avec un fast-forward, cette information disparaît dans une ligne droite. L'option --no-ff (no fast-forward) force la création du commit de fusion.

Le -m fournit directement le message du commit de fusion, sans ouvrir l'éditeur.

Résultat : même si main n'avait pas bougé, l'historique montre clairement un point d'intégration. Beaucoup d'équipes adoptent --no-ff par convention pour que chaque fonctionnalité apparaisse comme un « bloc » repérable dans le graphe.

Cas réel — le bouton « Merge pull request »

Sur GitHub, GitLab ou Bitbucket, le bouton vert « Merge pull request » applique par défaut exactement un git merge --no-ff : chaque fonctionnalité intégrée laisse un commit de fusion du type Merge pull request #42 from…. C'est ce qui te permet, des mois plus tard, de repérer d'un coup d'œil quand et par quelle demande de fusion une fonctionnalité est entrée dans main. Les deux autres options du menu (Squash and merge, Rebase and merge) correspondent aux variantes évoquées en fin de leçon.

Après la fusion : supprimer la branche

Une fois que connexion est intégrée dans main, la branche connexion ne sert plus à rien : son travail vit désormais dans main. Garder des dizaines de vieilles branches encombre le projet. On la supprime donc avec git branch -d.

Le -d minuscule est une sécurité : Git refuse de supprimer une branche dont le travail n'a pas encore été fusionné, pour t'éviter de perdre des commits. (Son grand frère -D majuscule force la suppression — à n'utiliser que si tu es sûr de vouloir jeter ce travail.)

Astuce

Supprimer une branche n'efface aucun commit : ceux-ci ont été recopiés dans main lors de la fusion. Tu ne perds que l'étiquette connexion, pas le travail.

Visualiser l'historique fusionné

Après quelques fusions, la vue en ligne droite ne suffit plus : tu veux voir les branches se séparer et se rejoindre. C'est le rôle de l'option --graph, à combiner avec --oneline pour rester lisible.

Lis-le de bas en haut : on part d'un ancêtre commun, main et connexion divergent (les deux colonnes), puis le commit du haut, avec ses deux traits qui rejoignent, est le commit de fusion. C'est le portrait fidèle d'une fusion à trois branches.

Pièges fréquents

Piège fréquent

Fusionner depuis la mauvaise branche. git merge intègre la branche nommée dans la branche courante. Si tu es resté sur connexion et tapes git merge main, tu fais l'inverse de ce que tu crois : tu ramènes main dans connexion. Vérifie toujours où tu es avec git status ou git branch avant de fusionner.

  • Croire qu'un fast-forward crée un commit de fusion. Non : un fast-forward ne fait qu'avancer un pointeur, sans nouveau commit. Si tu tiens à un commit de fusion, c'est --no-ff qu'il te faut.
  • Oublier de mettre main à jour avant de fusionner. Sur un projet partagé, main a souvent évolué côté distant. Récupère d'abord les derniers commits (git switch main puis un pull, vu plus tard) avant de fusionner, sinon tu intègres dans une version périmée.

Pour aller plus loin

  • Merge ou rebase ? La fusion préserve l'histoire telle qu'elle s'est produite (avec ses commits de fusion). Le rebase réécrit l'histoire pour la rendre linéaire. On compare les deux à la leçon 12.
  • git merge --squash. Cette variante intègre tous les changements d'une branche mais les regroupe en un seul commit, sans lien de parenté : pratique pour condenser une branche brouillonne en un commit propre.
  • Les stratégies de fusion. Git utilise par défaut la stratégie ort, capable de combiner intelligemment les modifications. Tu rencontreras parfois son nom dans les messages ; tu n'as pas à la configurer pour débuter.

Pour aller plus loin

Quand deux branches modifient les mêmes lignes, Git ne peut pas trancher seul : il déclare un conflit de fusion. La prochaine leçon t'apprend à lire ces conflits et à les résoudre calmement.

Antisèche : la fusion

Le mémo des commandes de fusion de cette leçon.

Glossaire

Fusion (merge)
Opération qui intègre les commits d'une branche source dans la branche courante.
Fast-forward
Fusion où la branche courante n'a pas divergé : Git avance simplement le pointeur, sans créer de commit.
Fusion à trois branches (three-way merge)
Fusion de deux branches ayant divergé ; Git combine l'ancêtre commun et les deux pointes.
Commit de fusion
Commit spécial à deux parents, créé lors d'une fusion à trois branches ; il relie les deux lignes d'histoire.
--no-ff
Option de git merge qui force la création d'un commit de fusion même quand un fast-forward serait possible.
Ancêtre commun
Dernier commit partagé par deux branches avant qu'elles ne divergent ; point de départ du calcul de fusion.
--graph
Option de git log qui dessine en ASCII les branches qui se séparent et se rejoignent.
Stratégie ort
Algorithme de fusion par défaut de Git, capable de combiner intelligemment les modifications de deux branches.

Récap et vérification

  • On fusionne vers la branche courante : git switch main puis git merge <branche>.
  • Si main n'a pas divergé, la fusion est un fast-forward : le pointeur avance, sans commit de fusion.
  • Si les deux branches ont divergé, Git crée un commit de fusion à deux parents (fusion à trois branches).
  • git merge --no-ff force un commit de fusion pour un historique explicite ; git branch -d supprime une branche déjà fusionnée.
  • git log --graph --oneline dessine les branches qui se séparent et se rejoignent.

Vérifie ta compréhension

  1. Tu veux intégrer connexion dans main : sur quelle branche dois-tu te placer avant de taper git merge ?
  2. Quelle différence entre une fusion fast-forward et une fusion à trois branches ?
  3. Que fait l'option --no-ff et dans quel cas s'en sert-on ?
