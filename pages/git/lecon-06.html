Module 02 · Branches & corrections — Leçon 06

Résoudre les conflits

~32 min Intermédiaire Leçon 05 recommandée

À la fin de cette leçon, tu sauras

  • reconnaître quand et pourquoi un conflit survient lors d'une fusion ;
  • lire et comprendre les marqueurs de conflit <<<<<<<, ======= et >>>>>>> dans un fichier ;
  • résoudre un conflit proprement avec git add puis git commit, et te laisser guider par git status ;
  • annuler une fusion en cours avec git merge --abort et réduire les conflits à l'avenir.
Sommaire de la leçon

Tu as appris à fusionner deux branches avec git merge. La plupart du temps, Git s'en sort tout seul : il combine les changements sans rien te demander. Mais un jour, deux branches auront modifié les mêmes lignes du même fichier, et là Git va s'arrêter net en affichant le mot qui fait peur : CONFLICT. Pas de panique : un conflit n'est ni une erreur ni une catastrophe. C'est simplement Git qui te dit « je ne peux pas deviner laquelle des deux versions tu veux ; à toi de choisir ».

Dans cette leçon, tu vas voir exactement quand un conflit apparaît, comment lire ce que Git écrit dans le fichier, comment le résoudre étape par étape, et comment tout annuler si tu préfères repartir au calme.

Quand un conflit survient

Un conflit n'arrive pas par hasard. Il faut une condition bien précise : deux branches ont touché la même portion d'un fichier, de deux manières incompatibles.

  • Deux modifications des mêmes lignes. Sur main tu écris « Bonjour » en haut du fichier ; sur ta branche feature/accueil tu écris « Salut » au même endroit. Git ne peut pas garder les deux : il y a conflit.
  • Modification contre suppression. Une branche supprime un fichier que l'autre a modifié. Git ne sait pas s'il doit le garder (avec tes changements) ou le jeter.

À l'inverse, si une branche modifie le début du fichier et l'autre la fin, il n'y a aucun conflit : Git assemble les deux moitiés sans broncher. Le conflit, c'est uniquement le chevauchement.

Git a fusionné ce qu'il pouvait, puis s'est arrêté sur accueil.html en te laissant la main.

Note

Quand la fusion échoue, Git ne défait rien : il met le dépôt « en pause » au milieu de la fusion. Les fichiers sans conflit sont déjà fusionnés ; seuls les fichiers en conflit attendent ta décision. Tu n'as donc rien perdu.

Lire les marqueurs de conflit

Quand Git ne peut pas trancher, il écrit les deux versions côte à côte dans le fichier, encadrées par des marqueurs très visibles. Ouvre accueil.html dans ton éditeur, tu y verras quelque chose comme :

Trois marqueurs structurent la zone de conflit. Apprends à les lire et tout devient simple :

  • <<<<<<< HEAD ouvre la version de ta branche actuelle (celle sur laquelle tu es, ici main). HEAD, c'est « là où tu te trouves ».
  • ======= est la frontière entre les deux versions. Au-dessus : toi. En dessous : l'autre.
  • >>>>>>> feature/accueil ferme la version de la branche que tu fusionnes.

Autrement dit : entre <<<<<<< et =======, c'est ton travail ; entre ======= et >>>>>>>, c'est celui de l'autre branche. Ton job : décider ce qui reste.

Astuce

Pour repérer d'un coup d'œil quels fichiers contiennent encore des marqueurs, lance git diff : Git surligne les zones en conflit. Et git diff --check te signale précisément les lignes qui contiennent encore un marqueur — pratique juste avant de committer.

Résoudre le conflit

Résoudre, c'est éditer le fichier à la main pour obtenir la version finale correcte, puis enlever les trois marqueurs. Tu as trois choix possibles à chaque conflit.

  • Garder ta version (celle de HEAD) et jeter l'autre.
  • Garder l'autre version et jeter la tienne.
  • Combiner les deux en écrivant une troisième version qui réconcilie tout — souvent le meilleur choix.

Imaginons qu'on veuille combiner. On réécrit la zone proprement, sans aucun marqueur :

Plus de <<<<<<<, plus de =======, plus de >>>>>>> : le fichier est redevenu un fichier normal.

Une fois le fichier corrigé et enregistré, tu dis à Git « c'est réglé » avec git add, puis tu termines la fusion avec un commit.

Le git add sur un fichier en conflit a un sens spécial : il signifie « j'ai fini de résoudre celui-ci ». Quand tous les fichiers en conflit sont ajoutés, le commit (ou git merge --continue) scelle la fusion.

Se laisser guider par git status

Tu n'as rien à mémoriser : à chaque étape, git status te dit précisément où tu en es et quoi faire ensuite. C'est ta boussole pendant toute la fusion.

Lis ces messages : Git te donne littéralement la prochaine commande à taper. La ligne both modified liste les fichiers encore à résoudre ; quand elle disparaît, tu peux committer.

Tout annuler avec --abort

Tu t'es lancé dans une fusion, tu vois trop de conflits, tu n'es pas serein ? Tu n'es jamais coincé. Une seule commande efface la fusion en cours et te ramène exactement à l'état d'avant git merge.

Après ça, plus de marqueurs, plus de conflit : c'est comme si tu n'avais jamais lancé la fusion. C'est le filet de sécurité absolu. Quand tu doutes, --abort d'abord, tu réfléchiras ensuite.

Astuce

Tu as commencé à éditer un fichier puis tu veux juste annuler tes changements de résolution sur ce fichier, sans tout annuler ? git restore --merge accueil.html remet les marqueurs de conflit d'origine pour repartir proprement sur ce seul fichier.

Les outils pour t'aider

Éditer les marqueurs à la main fonctionne toujours, mais des outils rendent la tâche plus confortable, surtout sur de gros conflits.

  • Ton éditeur ou IDE. VS Code, par exemple, affiche au-dessus de chaque conflit des boutons « Accepter actuel » / « Accepter entrant » / « Accepter les deux ». Il enlève les marqueurs pour toi ; il te reste juste à faire git add et git commit.

Réduire les conflits à l'avenir

Le meilleur conflit est celui qui n'arrive pas. Tu ne les supprimeras jamais à 100 %, mais quelques habitudes les rendent rares et petits.

  • Commits petits et fréquents. Plus tes changements sont petits, plus les zones qui se chevauchent sont réduites — et plus le conflit, s'il arrive, est facile à lire.
  • Fusionner souvent. Ramène régulièrement main dans ta branche de travail. Mieux vaut dix mini-conflits étalés qu'un énorme conflit après trois semaines.
  • Communiquer. Si toi et un collègue touchez au même fichier, mettez-vous d'accord. La plupart des gros conflits sont des problèmes d'organisation avant d'être des problèmes Git.

Cas réel — le fichier que tout le monde touche

Dans presque toutes les équipes, un fichier concentre les conflits : le CHANGELOG.md, le fichier de traductions ou le package-lock.json. Chacun y ajoute sa ligne… au même endroit (souvent tout en haut), et c'est le conflit à quasiment chaque fusion. La parade des équipes aguerries : intégrer main dans sa branche avant d'ouvrir la demande de fusion, et pour les fichiers générés (comme package-lock.json), les régénérer plutôt que de résoudre les marqueurs à la main.

Pièges fréquents

Piège fréquent

Committer en laissant des marqueurs <<<<<<< dans le fichier. Ton code part alors cassé dans l'historique. Avant de committer, relis le fichier — ou lance git diff --check — et vérifie qu'aucun marqueur ne traîne.

  • Paniquer et taper n'importe quoi. Au moindre doute, git merge --abort te ramène à l'état d'avant. Respire, puis recommence calmement.
  • Oublier git add après résolution. Éditer le fichier ne suffit pas : tant que tu n'as pas fait git add, Git considère le conflit comme non résolu et refusera de committer.
  • Écraser le travail de l'autre sans le lire. Garder bêtement « ta » version efface peut-être une correction importante du collègue. Lis les deux versions avant de choisir.

Antisèche : les conflits

Le mémo des commandes utiles pendant un conflit de fusion.

Glossaire

Conflit de fusion
Situation où deux branches modifient la même portion d'un fichier ; Git s'arrête et demande à un humain de trancher.
Marqueur de conflit
Les repères <<<<<<<, ======= et >>>>>>> que Git insère pour délimiter les deux versions.
<<<<<<< HEAD
Ouvre la version de ta branche courante ; le texte qui suit jusqu'à ======= est le tien.
=======
Frontière qui sépare ta version (au-dessus) de la version entrante (en dessous).
>>>>>>>
Ferme la version de la branche fusionnée (le côté entrant).
git merge --abort
Annule la fusion en cours et restaure le dépôt tel qu'il était juste avant git merge.
git merge --continue
Termine la fusion après résolution ; équivalent d'un git commit du commit de fusion.
git diff --check
Signale les lignes contenant encore un marqueur de conflit : le dernier filet avant de committer.

Récap et vérification

  • Un conflit survient quand deux branches modifient les mêmes lignes (ou modif contre suppression). Git s'arrête et marque le fichier.
  • Les marqueurs <<<<<<< HEAD, ======= et >>>>>>> délimitent ta version et celle de l'autre branche.
  • Résoudre = éditer le fichier pour obtenir la bonne version, supprimer les marqueurs, puis git add et git commit (ou git merge --continue).
  • git status guide chaque étape ; git merge --abort annule tout et revient en arrière.
  • Commits petits, fusions fréquentes et communication réduisent les conflits.

Vérifie ta compréhension

  1. Que représentent les lignes situées entre <<<<<<< HEAD et ======= ?
  2. Tu as édité un fichier en conflit pour le réparer. Quelles deux commandes te restent à taper pour terminer la fusion ?
  3. Tu te sens dépassé au milieu d'une fusion. Quelle commande te ramène à l'état d'avant le git merge ?
