Module 05 · Git en profondeur — Leçon 15

Sous le capot : les objets de Git

~34 min Intermédiaire Cours Git recommandé

À la fin de cette leçon, tu sauras

  • décrire le modèle de Git comme un magasin clé-valeur adressé par contenu et nommer les quatre types d'objets ;
  • explorer un dépôt avec les commandes de plomberie git cat-file, git hash-object et git ls-tree ;
  • expliquer qu'une branche n'est qu'une référence (un fichier contenant un SHA) et situer HEAD, refs/heads et refs/tags ;
  • distinguer les commandes plumbing des commandes porcelain et comprendre que Git stocke des instantanés, pas des différences.
Sommaire de la leçon

Tu sais déjà committer, fusionner, rebaser et pousser. Mais que se passe-t-il réellement quand tu tapes git commit ? Cette leçon ouvre la boîte noire. Tu vas découvrir que Git n'est, au fond, qu'une petite base de données très simple : un magasin d'objets adressés par leur contenu. Une fois ce modèle compris, des comportements qui semblaient magiques (l'intégrité des données, la rapidité des branches, le reflog) deviennent évidents.

Tout ce qui suit s'observe avec des commandes de plomberie (bas niveau). On ne va rien casser : on regarde, on inspecte, on comprend. Garde sous la main un dépôt avec au moins un commit pour suivre les exemples.

Git, un magasin clé-valeur adressé par le contenu

Le cœur de Git est un magasin clé-valeur : tu lui donnes du contenu, il te rend une clé ; tu lui rends la clé plus tard, il te ressort le contenu exact. La particularité : la clé n'est pas arbitraire, c'est le hash du contenu lui-même (SHA-1 historiquement, SHA-256 dans les dépôts récents). On parle de stockage content-addressed.

Conséquence directe : si deux fichiers ont le même contenu, ils partagent le même objet et donc la même clé. Et si un seul octet change, le hash change entièrement. C'est ce qui garantit l'intégrité : un objet corrompu ne correspond plus à son identifiant.

Le hash est calculé à partir du contenu (plus un petit en-tête) : il est déterministe.

Cas réel — la déduplication chez GitHub et l'affaire SHAttered

Un dépôt très populaire (le noyau Linux, par exemple) est forké des milliers de fois. Grâce à l'adressage par contenu, les objets identiques entre un dépôt et ses forks ne sont stockés qu'une seule fois côté serveur : des téraoctets économisés. Revers de la médaille : puisque toute l'intégrité repose sur le hash, une collision serait dangereuse. C'est arrivé en 2017 (attaque SHAttered : deux PDF différents au même SHA-1). Git a réagi en activant une détection de collision, puis en ajoutant le support de SHA-256 pour les nouveaux dépôts.

Les quatre types d'objets

Tout l'historique de Git tient dans quatre types d'objets, tous stockés de la même manière dans le magasin.

  • blob : le contenu d'un fichier, et rien d'autre. Pas de nom, pas de date, pas de permissions. Juste les octets.
  • tree : un répertoire. Il associe des noms à des blobs (fichiers) et à d'autres trees (sous-dossiers), avec leur mode.
  • commit : un instantané. Il pointe vers un tree racine (l'état complet du projet), vers son ou ses parents, et porte l'auteur, le committer, les dates et le message.
  • tag annoté : un objet nommé qui pointe vers un autre objet (souvent un commit), avec un message et un signataire.

Un commit pointe vers un tree ; un tree pointe vers des blobs et d'autres trees.

Note

Le nom d'un fichier ne vit pas dans le blob, mais dans le tree qui le référence. Renommer un fichier sans changer son contenu ne crée donc pas de nouveau blob : seul le tree change.

Explorer les objets : cat-file, hash-object, ls-tree

Trois commandes de plomberie suffisent pour fouiller le magasin. git cat-file -t donne le type d'un objet ; git cat-file -p l'affiche joliment (pretty-print).

Un commit, en clair : un pointeur vers un tree, un parent, un auteur et un message.

git ls-tree montre l'association nom → objet, avec le mode (100644 = fichier, 040000 = dossier).

Les références : une branche n'est qu'un pointeur

Voici la révélation la plus utile : une branche ne contient pas de commits. Une branche, c'est un simple fichier texte qui contient un SHA, celui de son dernier commit. Ce fichier vit dans .git/refs/heads/.

Créer une branche, c'est juste écrire un SHA dans un nouveau fichier : voilà pourquoi c'est instantané.

Et HEAD ? C'est généralement une référence symbolique : un fichier qui dit « je pointe vers telle branche ». Quand tu committes, Git fait avancer la branche pointée par HEAD.

Une tête détachée (detached HEAD), c'est simplement HEAD contenant un SHA au lieu de ref: ….

Note

Avec git pack-refs ou sur un dépôt fraîchement cloné, certaines refs sont regroupées dans le fichier .git/packed-refs au lieu d'un fichier par branche. git rev-parse et git show-ref les lisent indifféremment : c'est pourquoi on préfère ces commandes à un cat brut.

Tour d'horizon du dossier .git

Tout le dépôt tient dans le dossier caché .git. En voici les pièces maîtresses.

Le magasin d'objets est dans objects/ ; les pointeurs lisibles sont dans refs/.

Piège fréquent

N'édite jamais .git à la main pour « réparer » quelque chose. Passe par les commandes Git : elles maintiennent la cohérence entre objets, refs et index. Un fichier index bricolé à la main peut corrompre ton staging.

Un commit contient tout l'historique

Comme chaque commit pointe vers son ou ses parents, et ceux-ci vers les leurs, un seul SHA de commit « contient » implicitement toute la chaîne qui le précède. C'est cette chaîne de hash qui rend l'historique infalsifiable : changer un vieux commit change son hash, donc celui de tous ses descendants.

%h = hash court du commit, %p = hash de son parent.

Note

Un commit de fusion a simplement deux parents (ou plus). Le premier parent est la branche sur laquelle tu étais, le second celle que tu as fusionnée.

Instantanés, pas différences

Contrairement à beaucoup de systèmes plus anciens, Git ne stocke pas des diffs entre versions. Chaque commit référence un tree qui décrit l'état complet du projet à cet instant : un instantané. Les diffs que tu vois (git diff, git show) sont calculés à la volée entre deux instantanés.

« Mais ce serait énorme ! » En fait non : si un fichier ne change pas d'un commit à l'autre, le tree réutilise exactement le même blob (même contenu = même hash = un seul objet). Et plus tard, Git compresse les objets ensemble dans des packfiles, où il peut alors stocker des deltas pour gagner de la place. Le modèle reste l'instantané ; la compression est un détail de stockage.

Astuce

Pour visualiser le partage de blobs, compare deux trees : git ls-tree HEAD et git ls-tree HEAD~1. Les fichiers inchangés affichent le même SHA de blob.

Plomberie (plumbing) vs convivial (porcelain)

Git distingue deux familles de commandes. Le porcelain, c'est ce que tu utilises au quotidien : git status, git commit, git log, git push — pensé pour les humains, l'affichage peut changer d'une version à l'autre. La plomberie (plumbing), c'est le bas niveau : git cat-file, git hash-object, git rev-parse, git update-ref — stable, pensé pour les scripts.

Dans un script, préfère la plomberie : sa sortie ne bougera pas entre les versions de Git.

Pièges fréquents

Piège fréquent

Croire qu'une branche « contient » ses commits. Une branche est un pointeur vers un seul commit ; les commits accessibles le sont via la chaîne des parents. Supprimer une branche n'efface pas les commits (ils restent atteignables tant qu'une autre ref ou le reflog les retient).

Piège fréquent

Confondre un blob (du contenu, sans nom) et un fichier (un nom listé dans un tree). Deux fichiers identiques pointent vers un seul et même blob. Et ne crois pas que Git stocke des différences : il stocke des instantanés, la compression en deltas n'arrive qu'ensuite.

Pour aller plus loin

Pour aller plus loin

Explore les packfiles et git gc (qui compresse et range les objets), git fsck (qui vérifie l'intégrité et liste les objets inaccessibles, les dangling), et le git reflog (le journal local des déplacements de HEAD et des branches, ton filet de sécurité après un reset). Tu verras alors comment Git récupère un commit « perdu » tant qu'il n'a pas été nettoyé.

Antisèche : objets et références

Le mémo du modèle interne de Git et des commandes de plomberie pour l'explorer.

Glossaire

Adressage par contenu (content-addressed)
Principe où la clé d'un objet est le hash de son contenu : même contenu = même clé, d'où la déduplication et la détection de corruption.
blob
Objet Git contenant uniquement le contenu d'un fichier — ni nom, ni date, ni permissions.
tree
Objet Git représentant un répertoire ; il relie des noms à des blobs (fichiers) et à d'autres trees (sous-dossiers).
commit
Objet Git = un instantané : il pointe vers un tree racine, vers son ou ses parents, et porte l'auteur, les dates et le message.
Référence (ref)
Fichier contenant un SHA qui désigne un objet : une branche (refs/heads/), un tag (refs/tags/) ou HEAD.
HEAD
Référence généralement symbolique qui désigne la branche — donc le commit — courante ; une « tête détachée » contient directement un SHA.
Plomberie / porcelain
Commandes bas niveau, stables et scriptables (plumbing : cat-file, rev-parse…) par opposition aux commandes conviviales du quotidien (porcelain : status, log…).
Instantané (snapshot)
État complet du projet à un commit ; les blobs inchangés sont réutilisés et non dupliqués, et les diffs sont calculés à la volée entre deux instantanés.

Récap et vérification

  • Git est un magasin clé-valeur adressé par contenu : la clé est le hash du contenu, d'où l'intégrité.
  • Quatre objets : blob (contenu), tree (noms → objets), commit (tree racine + parents + métadonnées), tag annoté.
  • On inspecte avec git cat-file -t/-p, git hash-object, git ls-tree.
  • Une branche est un fichier contenant un SHA dans refs/heads/ ; HEAD pointe vers la branche courante ; les tags sont dans refs/tags/.
  • Git stocke des instantanés (réutilisant les blobs inchangés), pas des diffs ; la plomberie est stable, le porcelain est convivial.

Vérifie ta compréhension

  1. Pourquoi modifier un seul octet d'un fichier change-t-il complètement le hash de son blob ?
  2. Où se trouve le nom d'un fichier : dans le blob ou dans le tree ? Pourquoi ?
  3. Que contient exactement le fichier .git/refs/heads/main, et qu'est-ce que cela implique sur ce qu'est une branche ?
