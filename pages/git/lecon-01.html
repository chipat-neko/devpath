Module 01 · Les bases — Leçon 01

Pourquoi le contrôle de version

~28 min Débutant Terminal de base utile

À la fin de cette leçon, tu sauras

  • expliquer pourquoi le contrôle de version résout le chaos des dossiers « version finale » ;
  • décrire le modèle mental de Git : dépôt, zone de préparation et commit ;
  • créer ton premier dépôt et enregistrer un commit avec git init, git add et git commit ;
  • lire l'historique et rédiger un bon message de commit.
Sommaire de la leçon

Tu as déjà vécu ça : un dossier qui finit par contenir projet_final, projet_final_v2, projet_final_v2_vraiment_final. Tu n'oses plus rien supprimer, tu as peur de casser ce qui marche, et quand un ami modifie le même fichier que toi, c'est la pagaille. Cette leçon t'explique pourquoi un outil comme Git existe pour régler ce problème, puis te fait faire tes tout premiers pas concrets.

On part du connu (tes dossiers en désordre) pour aller vers l'inconnu (un historique propre et fiable). À la fin, tu sauras créer un dépôt et enregistrer un premier instantané de ton travail.

Le problème sans contrôle de version

Sans outil dédié, on bricole. Et chaque bricolage a un coût concret :

  • La multiplication des copies. Pour ne rien perdre, tu dupliques le dossier avant chaque grosse modif. Au bout d'une semaine, tu ne sais plus laquelle est la bonne.
  • La peur de casser. Comme revenir en arrière est pénible, tu n'oses plus expérimenter. Or expérimenter, c'est apprendre.
  • La collaboration chaotique. À deux sur le même fichier, vous vous envoyez des pièces jointes par e-mail et l'un écrase le travail de l'autre.

Le point commun de ces trois douleurs : il n'existe aucune mémoire fiable de qui a changé quoi, quand, et pourquoi. C'est exactement ce trou que Git vient combler.

Ce qu'est Git

Git est un système de contrôle de version : un programme qui enregistre l'historique de ton projet sous forme d'instantanés successifs. Chaque instantané s'appelle un commit : c'est une photo datée de l'état complet de tes fichiers à un moment donné, accompagnée d'un message qui explique ce que tu as fait.

Au lieu de garder dix copies du dossier, tu gardes un seul dossier et une suite de photos. Tu peux à tout moment consulter une ancienne photo, comparer deux versions, ou revenir en arrière sans rien perdre.

Note

Git est distribué : chaque personne qui clone le projet possède la totalité de l'historique sur sa machine. Pas besoin d'un serveur central en permanence pour consulter le passé ou enregistrer un commit ; tu travailles d'abord en local.

Le modèle mental : dépôt, préparation, commit

Trois mots suffisent pour comprendre tout le reste. Garde-les en tête comme trois zones distinctes.

  • Le dépôt (repository, ou « repo ») : le dossier de ton projet suivi par Git, avec tout son historique. C'est la mémoire complète.
  • La zone de préparation (staging area, ou « index ») : un sas où tu choisis précisément quelles modifications iront dans le prochain instantané. C'est ta liste de courses avant de passer en caisse.
  • Le commit : l'instantané lui-même. Daté, signé de ton nom, accompagné d'un message. Une fois créé, il fait partie de l'histoire.

L'image utile : tu travailles dans ton dossier (tu modifies des fichiers), tu prépares ce que tu veux photographier (tu remplis le sas), puis tu photographies (tu commites). La préparation est l'étape que les débutants oublient le plus souvent.

Premier dépôt — les commandes

Place-toi dans le dossier de ton projet, puis suis ces étapes dans l'ordre. Chaque commande a un rôle unique.

Décortiquons chaque ligne :

  • git init crée un sous-dossier caché .git : c'est lui qui contiendra tout l'historique. Sans cette étape, Git ne suit rien.
  • git status est ta boussole. Lance-le souvent : il te dit ce qui est modifié, ce qui est préparé, et ce qui n'est pas encore suivi.
  • git add met une modification dans le sas de préparation. Il n'enregistre rien dans l'histoire ; il dit seulement « celle-ci ira dans la prochaine photo ».
  • git commit -m "…" prend tout ce qui est dans le sas et en fait un instantané daté. C'est là, et seulement là, que l'histoire s'écrit.

Astuce

Avant ton premier commit, présente-toi à Git une fois pour toutes, sinon il ne saura pas signer tes instantanés : git config --global user.name "Ton Nom" puis git config --global user.email "toi@exemple.fr".

Lire l'historique

Une fois que tu as quelques commits, tu veux relire l'histoire. La commande de base est git log.

git log affiche, du plus récent au plus ancien, chaque instantané avec son identifiant (une longue empreinte), son auteur, sa date et son message. La variante --oneline compresse tout sur une ligne par commit : c'est la vue que tu utiliseras le plus pour avoir un panorama rapide.

Tu comprends maintenant pourquoi un bon message compte : c'est lui que tu liras dans six mois pour retrouver « le commit où j'ai corrigé le bug de connexion ».

Un bon message de commit

Un message de commit n'est pas une formalité : c'est une note laissée à ton futur toi (et à ton équipe). Trois règles simples le rendent utile.

  • À l'impératif présent. Écris Ajoute la validation du formulaire, pas J'ai ajouté… ni Ajouté…. Convention courante : le message complète la phrase « Ce commit va… ».
  • Concis et précis. Une ligne de résumé courte (vise une cinquantaine de caractères) qui dit quoi.
  • Le pourquoi compte plus que le comment. Le « comment » est déjà dans le code ; ce qui se perd, c'est l'intention. Corrige le calcul de TVA arrondi au mauvais sens vaut mille fois mieux que modif.

Cas réel — le bug qui vient d'apparaître

Lundi, une page qui marchait vendredi plante. Sur un projet sans historique, on cherche à l'aveugle. Avec Git, on tape git log --oneline, on repère le commit suspect grâce à son message, puis on compare les versions. En trente secondes, on sait quel changement a introduit le bug : c'est exactement pour ce genre de journée qu'on écrit des messages clairs et qu'on commite souvent.

Ignorer ce qui ne doit pas être suivi

Tout ne mérite pas d'entrer dans l'histoire. Un fichier nommé .gitignore, placé à la racine du dépôt, liste les fichiers et dossiers que Git doit ignorer : dépendances réinstallables, fichiers générés, et surtout secrets.

Piège fréquent

Crée le .gitignore avant ton premier git add .. Un secret committé reste dans l'historique même après suppression : il faut alors le considérer comme compromis et le changer.

Pièges fréquents

  • Oublier git init. Si tu lances git status dans un dossier ordinaire, Git répond qu'il n'y a pas de dépôt. Pas de init, pas de suivi.
  • Confondre add et commit. git add prépare, git commit enregistre. Faire un add seul ne crée aucun instantané ; tes changements restent en attente dans le sas.
  • Committer sans message clair. "maj", "truc", "." ne t'aideront jamais à retrouver quoi que ce soit. Le message est la moitié de la valeur d'un commit.
  • Tout committer sans réfléchir. Un git add . sans .gitignore embarque secrets et fichiers générés. Regarde toujours git status avant de committer.

Pour aller plus loin

Quelques repères pour la suite du cours, sans entrer dans le détail tout de suite :

  • Git n'est pas GitHub. Git est l'outil qui tourne sur ta machine et gère l'historique en local. GitHub (comme GitLab ou d'autres) est un service qui héberge une copie distante de ton dépôt pour le sauvegarder et collaborer. On peut très bien utiliser Git sans GitHub.
  • Un commit = une intention. Vise un commit par changement cohérent (« ajoute le formulaire », « corrige le bug X »), pas un fourre-tout de dix choses sans rapport.
  • Commite souvent et petit. Des commits fréquents et focalisés rendent l'historique lisible et le retour en arrière indolore.

Pour aller plus loin

Ceci est une leçon d'exemple du cours Git & GitHub. Les leçons suivantes (branches, fusion, dépôt distant, pull requests) arrivent bientôt ; ce que tu viens d'apprendre en est la fondation indispensable.

Antisèche : le flux de base

Les commandes de cette leçon, dans l'ordre où tu les utilises.

Glossaire

Contrôle de version
Système qui enregistre l'historique d'un projet sous forme d'instantanés successifs, plutôt que des copies de dossiers.
Dépôt (repository)
Dossier suivi par Git avec tout son historique ; les données vivent dans le sous-dossier caché .git.
Zone de préparation (index / staging)
Sas où l'on choisit précisément les modifications qui entreront dans le prochain commit, via git add.
Commit
Instantané daté et signé de l'état des fichiers, accompagné d'un message ; une fois créé, il fait partie de l'histoire.
Message de commit
Note attachée au commit, à l'impératif et concise, qui explique le quoi et surtout le pourquoi.
Distribué
Propriété de Git : chaque copie du dépôt contient la totalité de l'historique, sans serveur central obligatoire.
.gitignore
Fichier à la racine qui liste les fichiers et dossiers que Git ne doit pas suivre (dépendances, fichiers générés, secrets).
git status
Commande qui affiche l'état courant du dépôt : fichiers modifiés, préparés ou non suivis.

Récap et vérification

  • Le contrôle de version remplace les copies de dossiers par un historique d'instantanés fiable.
  • Git distingue trois zones : le dépôt, la zone de préparation et le commit.
  • Le flux de base : git init → git add → git commit -m "…", et git status comme boussole.
  • git log relit l'histoire ; un bon message (impératif, concis, le pourquoi) la rend exploitable.
  • Le .gitignore garde hors de l'historique les dépendances et surtout les secrets.

Vérifie ta compréhension

  1. Quelle est la différence entre git add et git commit ?
  2. Que se passe-t-il si tu lances git status dans un dossier où tu n'as jamais fait git init ?
  3. Pourquoi un message comme "maj" est-il un mauvais message de commit ?
