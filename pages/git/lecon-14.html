Module 04 · Maîtrise & workflows — Leçon 14

Workflows d'équipe & bonnes pratiques

~32 min Intermédiaire Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • choisir un modèle de branches adapté (GitHub Flow, Git Flow, trunk-based) ;
  • rédiger de bons messages de commit, y compris au format Conventional Commits ;
  • protéger la branche main, gérer le .gitignore et les secrets d'équipe ;
  • comprendre l'intégration continue (CI/CD) et les hooks pour automatiser les vérifications.
Sommaire de la leçon

Jusqu'ici, tu as appris à versionner ton code, à créer des branches, à fusionner et à pousser sur un dépôt distant. Travailler seul, c'est une chose ; travailler à plusieurs sans se marcher dessus, c'en est une autre. Cette dernière leçon réunit les conventions et les bonnes pratiques qui font qu'une équipe avance vite sans casser main.

On va passer en revue les modèles de branches, l'art du message de commit, la protection des branches, la gestion des secrets, l'intégration continue et les hooks. Rien d'ésotérique : ce sont des habitudes simples qui, mises bout à bout, rendent un projet sain et agréable. C'est aussi la synthèse de tout le cours.

Les modèles de branches

Un modèle de branches (ou workflow) est une convention d'équipe : où vit le code stable, où on développe, comment on intègre. Trois grands modèles dominent.

GitHub Flow est le plus simple, et celui qu'on recommande pour débuter. Une seule branche durable, main, toujours déployable. Pour chaque travail, tu crées une branche de fonctionnalité, tu ouvres une pull request (PR), on la relit, et on fusionne. Déploiement continu : ce qui arrive sur main part en production.

Git Flow est plus lourd : deux branches durables (main pour les versions publiées, develop pour l'intégration), plus des branches release/* et hotfix/*. Utile pour des logiciels livrés par versions numérotées (un installeur, une appli mobile), mais souvent excessif pour un site web déployé en continu.

Trunk-based development pousse la simplicité à l'extrême : tout le monde intègre très souvent sur une seule branche (le trunk), avec des branches qui vivent quelques heures à peine. C'est le modèle des grosses équipes qui déploient plusieurs fois par jour, appuyées par une CI solide.

Note

Quand choisir quoi ? Pour un projet web ou un débutant en équipe, GitHub Flow. Pour un logiciel versionné avec des correctifs sur d'anciennes versions, Git Flow. Pour une grosse équipe qui déploie en continu, trunk-based. En cas de doute, commence simple.

De bons messages de commit

Tu l'as vu en leçon 1 : un message s'écrit à l'impératif présent, avec une ligne de résumé courte (vise ~50 caractères). En équipe, on ajoute souvent un corps séparé par une ligne vide pour expliquer le pourquoi.

Pour aller plus loin, beaucoup d'équipes adoptent les Conventional Commits : un préfixe de type suivi de deux-points. C'est lisible par les humains et par les outils (génération automatique de changelog, numéro de version).

Les types courants sont feat, fix, docs, style, refactor, test et chore. Tu peux préciser une portée entre parenthèses, par exemple feat(panier): ....

Protéger la branche principale

Sur un dépôt partagé, main doit rester sacrée. GitHub permet d'activer des règles de protection de branche (dans les réglages du dépôt) pour imposer un minimum de discipline, sans compter sur la bonne volonté de chacun.

  • Pas de push direct sur main : tout passe par une pull request.
  • Revue obligatoire : au moins une approbation avant fusion.
  • CI verte : les tests et le lint doivent passer pour pouvoir fusionner.

Résultat : on ne peut plus casser la branche déployable par accident. Un push direct est refusé, et tu passes par le flux normal.

.gitignore d'équipe et secrets

Le .gitignore est partagé : versionné à la racine, il s'applique à toute l'équipe. On y met les dépendances réinstallables, les fichiers générés et surtout les secrets (mots de passe, clés d'API, jetons). Un secret ne doit jamais entrer en clair dans l'historique.

La bonne pratique : garder un fichier d'exemple sans valeurs réelles, lui, versionné, pour que l'équipe sache quelles variables fournir.

Piège fréquent

Un secret poussé sur le distant est compromis, même si tu le supprimes ensuite : il reste dans l'historique et dans les clones des autres. La seule réponse sûre est de révoquer la clé et d'en générer une nouvelle. Ajoute le fichier au .gitignore avant le premier git add.

Cas réel

Des robots scrutent en permanence les commits publics de GitHub à la recherche de clés d'API. Une clé AWS ou Stripe poussée par erreur peut être détectée et exploitée en quelques minutes — avec, à la clé, des factures de plusieurs milliers d'euros. C'est pourquoi GitHub propose le secret scanning avec push protection, qui bloque un push contenant un secret reconnu, et pourquoi la seule vraie parade après une fuite reste de révoquer puis régénérer la clé.

L'intégration continue (CI/CD) en bref

L'intégration continue (CI) consiste à lancer automatiquement des vérifications à chaque PR : tests, lint, build. Si quelque chose casse, tu le sais en quelques minutes, avant la fusion. Sur GitHub, c'est GitHub Actions : un fichier YAML dans .github/workflows/ décrit quoi exécuter et quand.

À chaque push ou pull request, GitHub installe le projet, lance les tests et le lint. La PR affiche une coche verte si tout passe, une croix rouge sinon. Couplée à la protection de branche (« CI verte obligatoire »), la CI empêche concrètement de fusionner du code cassé. Le CD (déploiement continu) va plus loin : il déploie automatiquement une fois main à jour.

Les hooks (pre-commit)

Un hook est un script que Git lance automatiquement à un moment donné. Le plus utile pour débuter est pre-commit : il s'exécute avant chaque commit et peut le bloquer si une vérification échoue. Tu attrapes ainsi les erreurs avant qu'elles ne partent, sans attendre la CI.

Place ce script dans .git/hooks/pre-commit et rends-le exécutable.

Astuce

Les hooks du dossier .git/ ne sont pas versionnés : chacun doit les installer. Pour les partager dans toute l'équipe, on utilise des outils dédiés comme Husky (JS) ou le framework pre-commit (Python), qui versionnent la configuration et installent les hooks automatiquement.

Et après

Félicitations : tu sais désormais versionner ton code, gérer des branches, collaborer via des pull requests, et organiser le travail d'une équipe. C'est la fondation sur laquelle reposent tous les projets logiciels modernes.

Pour continuer à progresser, voici quelques pistes : la CI/CD avancée (pipelines de déploiement, environnements de préproduction) ; les monorepos (plusieurs projets dans un seul dépôt) ; d'autres plateformes comme GitLab ou Bitbucket ; la signature de commits (GPG/SSH) pour prouver leur authenticité ; et surtout, la contribution à l'open source — le meilleur terrain d'entraînement réel. Chaque dépôt public est une occasion de pratiquer le flux fork → branche → PR.

Checklist de bonnes pratiques

  • Une branche par tâche, nommée clairement (feat/..., fix/...), jamais de travail directement sur main.
  • Commits petits et focalisés, à l'impératif, idéalement au format Conventional Commits.
  • Mets ta branche à jour souvent depuis main pour limiter les conflits de fusion.
  • Ouvre une pull request pour toute fusion vers main ; fais relire ton code.
  • Protège main : revue obligatoire, CI verte, pas de push direct.
  • Jamais de secret en clair : .env dans le .gitignore, un .env.example versionné.
  • Garde la CI verte : ne fusionne pas une PR dont les tests échouent.
  • Relis avant de committer : git status et git diff sont tes garde-fous.

Pour aller plus loin

Pour aller plus loin

Explore les templates de PR et d'issues (dans .github/) pour standardiser les contributions, la signature de commits pour l'authenticité, et les outils Husky ou pre-commit pour partager les hooks. Pour t'exercer en conditions réelles, choisis un petit projet open source étiqueté « good first issue » et propose ta première pull request.

Antisèche : collaborer proprement

Le mémo des conventions d'équipe vues dans cette leçon.

Glossaire

Pull request (PR)
Demande de fusion d'une branche vers une autre, ouverte sur GitHub : support de la revue de code et point d'ancrage de la CI avant intégration.
GitHub Flow
Modèle simple : une seule branche durable (main, toujours déployable) et de courtes branches de fonctionnalité fusionnées par PR.
Git Flow
Modèle à deux branches durables (main, develop) plus release/* et hotfix/* ; adapté aux logiciels livrés par versions numérotées.
Trunk-based development
Modèle où toute l'équipe intègre très souvent sur un seul tronc, avec des branches de quelques heures ; exige une CI solide.
Conventional Commits
Convention de message type(scope): description (feat, fix…), lisible par les humains et exploitable par les outils (changelog, SemVer).
Protection de branche
Règles GitHub sur main : interdiction du push direct, revue obligatoire, CI verte requise avant fusion.
CI / CD
Intégration continue : vérifications automatiques (tests, lint, build) à chaque PR. Déploiement continu : mise en production automatique une fois main à jour.
Hook
Script lancé automatiquement par Git à un moment clé ; pre-commit s'exécute avant chaque commit et peut le bloquer si une vérification échoue.

Récap et vérification

  • GitHub Flow (simple) convient à la plupart des projets ; Git Flow aux logiciels versionnés ; trunk-based aux grosses équipes en déploiement continu.
  • Un bon message est à l'impératif, court, et explique le pourquoi ; les Conventional Commits (feat:, fix:…) standardisent tout ça.
  • On protège main : pas de push direct, revue obligatoire, CI verte.
  • Les secrets restent hors de l'historique grâce au .gitignore ; un secret poussé est compromis.
  • La CI (GitHub Actions) et les hooks (pre-commit) automatisent les vérifications avant la fusion.
