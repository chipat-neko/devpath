Module 03 · Collaborer avec GitHub — Leçon 10

Pull requests et revue de code

~30 min Intermédiaire Leçon 09 recommandée

À la fin de cette leçon, tu sauras

  • ouvrir une pull request depuis une branche poussée (git push -u, base ← compare sur GitHub) ;
  • participer à une revue de code : commentaires ligne par ligne, mise à jour automatique de la PR, lecture de la CI ;
  • choisir la bonne fusion entre merge commit, squash et rebase, et lier une issue avec closes #12 ;
  • garder ta branche à jour et la supprimer après fusion.
Sommaire de la leçon

Jusqu'ici, tu as appris à versionner ton code et à le pousser sur un dépôt distant. Mais comment proposer tes changements à une équipe sans casser le travail des autres, et comment relire le code d'un collègue avant qu'il n'atterrisse dans main ? La réponse tient en deux lettres : PR, pour pull request.

Dans cette leçon, on part de ta branche locale et on suit tout le parcours : créer la branche, la pousser, ouvrir une pull request sur GitHub, la faire relire, la mettre à jour, puis la fusionner proprement. Tu verras les commandes côté local (dans ton terminal) et les étapes côté GitHub (dans le navigateur).

La pull request : proposer, discuter, intégrer

Une pull request (parfois appelée merge request ailleurs) est une demande : « voici une branche, j'aimerais la fusionner dans une autre ». Mais contrairement à un git merge que tu ferais seul dans ton coin, la PR ajoute une couche essentielle : une page de discussion où l'équipe peut voir le diff, commenter, demander des corrections et approuver avant l'intégration.

Une PR met toujours en jeu deux branches :

  • La branche base (la destination) : souvent main. C'est là que tu veux que ton travail arrive.
  • La branche compare (la source) : ta branche de travail, qui contient tes nouveaux commits.

Tant que la PR n'est pas fusionnée, main reste intact. C'est un filet de sécurité : rien n'entre dans la branche principale sans passer par cette porte.

Note

La pull request est un concept de la plateforme (GitHub, GitLab…), pas de Git lui-même. Git ne connaît que les branches et les commits ; la PR est l'enveloppe sociale qu'on met autour d'une fusion pour la discuter.

Le flux typique, de la branche à la PR

Voici le parcours standard. Tout commence en local, dans ton terminal.

Le drapeau -u (pour --set-upstream) relie ta branche locale à sa jumelle distante : les prochains git push n'auront plus besoin d'arguments.

Après le push, GitHub te donne souvent un lien direct pour ouvrir la PR :

Sinon, va dans l'onglet Pull requests du dépôt, clique New pull request, choisis base : main et compare : ta branche, puis rédige un titre clair et une description (ce que tu as changé et pourquoi). Clique enfin sur Create pull request.

Astuce

Si tu as installé le CLI officiel de GitHub, tu peux ouvrir la PR sans quitter le terminal : gh pr create --base main --fill. L'option --fill reprend automatiquement ton titre et ton message de commit.

La revue de code

Une fois la PR ouverte, tes coéquipiers la relisent. Sur l'onglet Files changed, ils voient le diff ligne par ligne et peuvent :

  • commenter une ligne précise (clic sur le « + » en marge) pour poser une question ou suggérer une amélioration ;
  • demander des changements (Request changes) : la PR ne pourra pas être fusionnée tant que ce n'est pas réglé ;
  • approuver (Approve) quand tout leur convient.

Le point magique : tu n'as pas besoin de fermer puis rouvrir la PR pour corriger. Tu travailles en local, tu commites, tu repousses sur la même branche, et la PR se met à jour automatiquement.

Les nouveaux commits apparaissent dans la PR, et les relecteurs peuvent résoudre les conversations au fur et à mesure. Réponds aux commentaires, même pour dire « corrigé, merci » : la revue est une conversation, pas un examen.

Cas réel

Sur les grands projets open source (le noyau Linux, VS Code, React…), aucune ligne n'entre sans passer par une revue : même un correctif d'une virgule est proposé en PR, relu et validé par un mainteneur. En entreprise, c'est la norme : la plupart des équipes interdisent le push direct sur main et exigent au moins une approbation. La revue n'est pas une défiance ; c'est ainsi qu'on diffuse la connaissance du code et qu'on attrape les bugs avant la production.

Les vérifications automatiques (CI)

Beaucoup de dépôts lancent des vérifications automatiques à chaque push sur la PR : c'est l'intégration continue (CI). Une machine exécute pour toi les tests, le linter (vérification du style de code), parfois un build complet.

En bas de la PR, tu vois alors une liste de checks avec une pastille :

Une croix rouge bloque (ou devrait bloquer) la fusion. Clique sur « Details » pour lire les logs, corrige en local, recommite, repousse : la CI relance toute seule.

Une CI verte ne garantit pas que ton code est parfait, mais une CI rouge garantit qu'il y a un problème à régler avant de fusionner. Ne la contourne jamais.

Fusionner une PR : trois stratégies

Quand la PR est approuvée et la CI verte, le bouton de fusion s'active. GitHub propose souvent trois variantes. Comprendre la différence t'évite un historique en désordre.

  • Merge commit (fusion classique) : garde tous tes commits et ajoute un commit de fusion qui relie les deux branches. L'historique est complet mais peut devenir touffu.
  • Squash and merge : écrase tous les commits de la branche en un seul commit propre sur main. Idéal quand ta branche contient des commits intermédiaires du genre « wip », « oups typo ».
  • Rebase and merge : rejoue tes commits un par un au sommet de main, sans commit de fusion. Historique linéaire, mais réécrit les identifiants des commits.

Pour une équipe débutante, squash and merge est souvent le plus sûr : un historique de main où chaque ligne = une fonctionnalité.

Lier une issue et nettoyer après fusion

Si ta PR répond à un ticket (une issue), écris un mot-clé de fermeture suivi du numéro dans la description de la PR. GitHub fermera l'issue automatiquement au moment de la fusion.

Une fois la PR fusionnée, supprime la branche. GitHub propose un bouton « Delete branch » juste après la fusion. Puis, en local, fais le ménage et reviens sur un main à jour.

Garder sa branche à jour

Si ta PR traîne plusieurs jours, main avance pendant ce temps (d'autres PR sont fusionnées). Ta branche devient en retard et risque des conflits. Mets-la régulièrement à jour.

Utilise --force-with-lease plutôt que --force : il refuse d'écraser le travail distant si quelqu'un a poussé entre-temps.

Pièges fréquents

Piège fréquent

La PR géante qui change 40 fichiers est un cauchemar à relire : personne ne la lit vraiment, et les bugs passent. Préfère des PR petites et ciblées (une fonctionnalité, une correction). Une PR de 50 lignes est relue ; une de 2000 est juste approuvée à l'aveugle.

  • Brancher depuis un main périmé. Si tu oublies le git pull avant git switch -c, tu repars d'une vieille base et tu t'exposes à des conflits inutiles.
  • Ignorer les retours de revue. Une demande de changement n'est pas une attaque : c'est le mécanisme même de la PR. Réponds, corrige ou explique pourquoi tu ne changes pas.
  • Fusionner avec la CI rouge. Une croix rouge signale un test cassé ou un style invalide. Forcer la fusion par-dessus, c'est introduire le problème dans main pour toute l'équipe.
  • Oublier de supprimer la branche fusionnée. Au bout de quelques semaines, la liste des branches devient illisible. Supprime après chaque fusion.

Pour aller plus loin

  • Templates de PR. Un fichier .github/pull_request_template.md pré-remplit la description (checklist, lien d'issue) pour chaque nouvelle PR.
  • CODEOWNERS. Un fichier qui désigne automatiquement les relecteurs responsables de certains dossiers : ils sont ajoutés d'office à la revue.
  • Protections de branche. Des règles côté GitHub qui interdisent de pousser directement sur main et exigent au moins une approbation et une CI verte avant fusion.
  • Brouillons de PR (draft). Ouvre une PR en mode Draft pour partager un travail en cours et recueillir des avis précoces, sans demander encore une revue formelle.

Pour aller plus loin

Combine ces outils : une protection de branche qui exige une approbation, un CODEOWNERS qui désigne le bon relecteur et un template qui rappelle de lier l'issue ; tu obtiens un flux de revue fiable où rien n'entre dans main par accident.

Antisèche : pull requests

Le mémo du parcours d'une PR, du terminal à la fusion.

Glossaire

Pull request (PR)
Demande de fusionner une branche dans une autre, assortie d'une page de discussion et de revue. Concept de la plateforme (GitHub…), pas de Git.
Branche base
La destination de la fusion, souvent main : c'est là que le travail doit arriver.
Branche compare
La source de la PR : ta branche de travail, qui contient les nouveaux commits à intégrer.
Revue de code
Relecture du diff par l'équipe : commentaires ligne par ligne, demande de changement ou approbation avant fusion.
CI (intégration continue)
Vérifications automatiques (tests, linter, build) rejouées à chaque push sur la PR ; une CI rouge bloque la fusion.
Squash and merge
Stratégie de fusion qui écrase tous les commits de la branche en un seul commit propre sur la base.
Mot-clé de fermeture
closes/fixes/resolves suivi d'un numéro d'issue ; ferme cette issue automatiquement à la fusion.
--force-with-lease
Variante prudente de --force : refuse d'écraser le distant si quelqu'un a poussé entre-temps. Utile après un rebase.

Récap et vérification

  • Une pull request propose de fusionner une branche compare dans une branche base, avec discussion et revue avant l'intégration.
  • Le flux : main à jour → branche → commits → git push -u → ouvrir la PR sur GitHub.
  • Pousser de nouveaux commits met la PR à jour automatiquement ; la CI rejoue tests et lint à chaque fois.
  • Trois fusions : merge commit (tout garder), squash (un commit propre), rebase (historique linéaire).
  • closes #12 ferme l'issue liée ; on supprime la branche et on met main à jour après fusion.

Vérifie ta compréhension

  1. Dans une PR, laquelle des deux branches est la base et laquelle est la compare ?
  2. Tu reçois une « demande de changement » : faut-il fermer la PR et en ouvrir une nouvelle ? Que fais-tu ?
  3. Pourquoi vaut-il mieux découper un gros chantier en plusieurs petites PR ?
