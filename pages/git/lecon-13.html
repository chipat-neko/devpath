Module 04 · Maîtrise & workflows — Leçon 13

Stash, tags, bisect et autres outils

~32 min Intermédiaire Leçon 12 recommandée

À la fin de cette leçon, tu sauras

  • mettre de côté ton travail en cours avec git stash et le récupérer ensuite ;
  • marquer une version avec un tag annoté et le pousser avec git push --tags ;
  • retrouver le commit fautif par dichotomie grâce à git bisect ;
  • utiliser git blame, git clean, les alias et git reflog comme filets de sécurité.
Sommaire de la leçon

Tu connais déjà le cœur de Git : committer, brancher, fusionner, pousser. Mais au quotidien, il te manque encore une poignée d'outils qui font gagner un temps fou : mettre du travail de côté en urgence, marquer une version livrée, retrouver le commit qui a introduit un bug, savoir qui a écrit telle ligne, ou récupérer un travail qu'on croyait perdu.

Cette leçon est une boîte à outils : chaque section présente une commande indépendante des autres. Tu n'as pas besoin de tout retenir aujourd'hui ; garde plutôt cette page comme aide-mémoire et reviens-y quand le besoin se présente.

git stash : mettre son travail de côté

Situation classique : tu es en plein milieu d'une modification, rien n'est prêt à être committé, et soudain il faut tout de suite changer de branche pour corriger un bug urgent. Git refuse de te laisser changer de branche si ça écrase ton travail. La solution : git stash, qui range tes modifications non committées dans un tiroir et te rend un dossier propre.

Une fois le bug urgent réglé, tu reviens sur ta branche et tu ressors ton travail du tiroir.

La différence entre les deux est importante : git stash pop applique le dernier stash puis le supprime du tiroir, tandis que git stash apply l'applique mais le garde au cas où. Tu peux empiler plusieurs stash et les lister à tout moment.

Note

Un stash n'est pas un commit : il n'apparaît pas dans git log et n'est jamais poussé sur le dépôt distant. C'est un rangement local et temporaire, pratique mais à ne pas oublier (voir les pièges plus bas).

Les tags : marquer une version

Un tag est une étiquette posée sur un commit pour dire « ici, c'est la version 1.0 ». Contrairement à une branche, un tag ne bouge jamais : il pointe toujours le même commit. C'est ce qui te permet de retrouver précisément le code d'une version livrée.

Il existe deux sortes de tags. Le tag annoté (recommandé pour les vraies versions) contient un message, un auteur et une date, comme un mini-commit. Le tag léger est juste un alias de nom vers un commit, sans métadonnées.

Point crucial : les tags ne partent pas automatiquement sur le dépôt distant quand tu fais git push. Il faut les pousser explicitement.

Astuce

Sur GitHub, un tag poussé peut devenir une Release : depuis l'onglet « Releases » du dépôt, tu transformes ton tag v1.0 en page de version avec des notes de version et, si besoin, des fichiers téléchargeables (binaires, archive). C'est la façon standard de publier une version.

git bisect : trouver le commit fautif

Un bug est apparu, mais tu ne sais pas quand. Il marchait il y a deux semaines, il est cassé aujourd'hui, et il y a 80 commits entre les deux. Tester chaque commit un par un serait long. git bisect fait une recherche par dichotomie : il coupe l'intervalle en deux à chaque étape, ce qui trouve le coupable parmi 80 commits en ~7 essais seulement.

À chaque étape, Git te place sur un commit du milieu : tu testes ton programme, puis tu dis à Git si ce commit est bon ou cassé. Il réduit l'intervalle de moitié à chaque réponse.

Quand Git a trouvé le commit fautif, tu termines la session pour revenir à ton état de départ. N'oublie jamais cette étape, sinon tu restes « détaché » sur un vieux commit.

Voici l'idée en schéma : à chaque étape, on élimine la moitié restante.

Cas réel

Les très gros projets comme le noyau Linux ou Firefox reçoivent des milliers de commits par version. Quand une régression est signalée (« ça marchait à la version précédente »), les mainteneurs lancent git bisect, souvent en mode automatique avec git bisect run <script-de-test> : Git teste tout seul les commits par dichotomie et désigne le coupable parmi des milliers d'autres en une quinzaine d'essais. C'est l'une des raisons pour lesquelles ces projets tiennent à un historique où chaque commit compile et fonctionne seul.

git blame : qui a écrit cette ligne ?

Tu tombes sur une ligne bizarre et tu veux savoir qui l'a écrite, quand, et dans quel commit. git blame annote chaque ligne d'un fichier avec ces informations. Le mot « blame » (blâmer) est mal choisi : le but n'est pas d'accuser, mais de retrouver le contexte d'un changement.

Chaque ligne te donne l'identifiant du commit, l'auteur, la date et le numéro de ligne. Tu peux ensuite inspecter le commit complet avec git show a1b2c3d pour voir pourquoi ce changement a été fait.

git clean : supprimer les fichiers non suivis

Au fil du travail, ton dossier accumule des fichiers que Git ne suit pas : artefacts de compilation, fichiers de test, brouillons. git clean fait le ménage en supprimant ces fichiers non suivis. Mais attention : cette suppression est définitive, ces fichiers n'étant dans aucun historique.

La règle d'or : toujours simuler d'abord avec l'option -n (pour « dry run », essai à blanc), qui montre ce qui serait supprimé sans rien toucher.

Piège fréquent

git clean -f efface définitivement les fichiers non suivis : ils ne sont nulle part dans l'historique, donc aucune commande Git ne les récupère. Lance toujours git clean -n avant, et relis la liste.

Les alias : des raccourcis sur mesure

Tu tapes git status et git log --oneline cinquante fois par jour ? Crée des alias : des raccourcis personnels pour tes commandes fréquentes, enregistrés une fois pour toutes dans ta configuration Git.

Les alias sont stockés dans ton fichier de config global (~/.gitconfig). Ils sont strictement personnels : ils ne sont pas partagés avec ton équipe via le dépôt, donc chacun peut avoir les siens.

git show et git reflog : inspecter et récupérer

Deux dernières commandes à garder dans ta poche. git show affiche le détail d'un commit (ou d'un tag) : son message, son auteur et les différences qu'il introduit.

Enfin, le filet de sécurité ultime : git reflog. Git tient un journal de tous les endroits où ta branche a pointé, y compris les commits que tu croyais perdus après un reset brutal ou une branche supprimée. Tant qu'un commit est dans le reflog, il est récupérable.

Note

Dans le reflog, les anciennes opérations apparaissent parfois sous le nom checkout même si tu utilises git switch aujourd'hui : les deux partagent la même mécanique interne. C'est normal, et ça n'enlève rien à la fiabilité de ce journal.

Pièges fréquents

  • Oublier un stash et croire son travail perdu. Après un git stash, le dossier paraît vide de tes modifs ; pas de panique, ton travail est rangé. Lance git stash list pour le retrouver, puis git stash pop.
  • Un tag non poussé. git push seul n'envoie pas tes tags. Si ta version n'apparaît pas sur GitHub, c'est qu'il manque git push --tags (ou git push origin v1.0).
  • Un git clean -f trop rapide. Les fichiers non suivis effacés sont définitivement perdus. Essaie toujours git clean -n d'abord.
  • Confondre tag léger et tag annoté. Pour une vraie version livrée, utilise le tag annoté (git tag -a v1.0 -m "…") : lui seul conserve date, auteur et message.
  • Oublier git bisect reset. Après une session bisect, tu es sur un vieux commit en mode « détaché ». Termine toujours par git bisect reset pour revenir à ta branche.

Pour aller plus loin

Quand ces outils te seront familiers, plusieurs prolongements existent :

  • git worktree : travailler sur plusieurs branches en même temps dans des dossiers séparés, sans stash ni changement de branche.
  • Les submodules : inclure un autre dépôt Git à l'intérieur du tien (utile pour une bibliothèque partagée), au prix d'une certaine complexité.
  • git bisect run : automatiser entièrement la dichotomie en fournissant un script de test, pour que Git trouve le commit fautif tout seul.

Pour aller plus loin

Plusieurs de ces outils (notamment git clean et les tags de version) gagnent à être automatisés. La leçon suivante aborde les hooks Git : des scripts déclenchés automatiquement à des moments clés (avant un commit, après un push) pour vérifier ou nettoyer ton code.

Antisèche : la boîte à outils Git

Le mémo des commandes du quotidien vues dans cette leçon.

Glossaire

Stash
Tiroir local et temporaire où git stash range les modifications non committées ; il n'apparaît pas dans git log et n'est jamais poussé sur le dépôt distant.
Tag annoté
Étiquette de version créée avec git tag -a : un objet Git complet portant message, auteur et date. À privilégier pour une vraie version livrée.
Tag léger
Simple nom pointant un commit (git tag v1.0-beta), sans métadonnée : un marque-page rapide, sans trace de sa création.
Dichotomie (bisect)
Stratégie de git bisect qui coupe l'intervalle de commits en deux à chaque test ; trouve un coupable parmi n commits en environ log₂(n) essais.
git blame
Annotation de chaque ligne d'un fichier avec le commit, l'auteur et la date qui l'ont introduite ; sert à retrouver le contexte, pas à accuser.
git clean
Suppression des fichiers non suivis. Irréversible : toujours simuler avec -n avant de confirmer avec -f.
Alias
Raccourci personnel pour une commande fréquente, enregistré dans ~/.gitconfig via git config --global alias.… ; propre à chacun, non partagé par le dépôt.
git reflog
Journal local de tous les déplacements de HEAD ; filet de sécurité pour récupérer un commit « perdu » après un reset ou une branche supprimée.

Récap et vérification

  • git stash range tes modifs non committées ; git stash pop les ressort (et vide le tiroir), git stash list montre ce qui reste.
  • Un tag annoté (git tag -a v1.0 -m "…") marque une version ; il faut le pousser avec git push --tags, et GitHub peut en faire une Release.
  • git bisect trouve le commit fautif par dichotomie : start, bad, good, puis reset pour terminer.
  • git blame dit qui a écrit chaque ligne ; git clean -n simule un ménage avant le -f définitif.
  • Les alias raccourcissent tes commandes ; git show détaille un commit et git reflog est le filet de sécurité pour récupérer du « perdu ».

Vérifie ta compréhension

  1. Quelle est la différence entre git stash pop et git stash apply ?
  2. Tu as créé v2.0 avec git tag -a mais il n'apparaît pas sur GitHub. Quelle commande as-tu oubliée ?
  3. Pourquoi faut-il lancer git clean -n avant git clean -f ?
