Module 06 · Collaboration et automatisation — Leçon 19

Gros dépôts et récupération avancée

~34 min Avancé Leçon 18 recommandée

À la fin de cette leçon, tu sauras

  • savoir gérer les gros fichiers et les gros dépôts avec Git LFS, le sparse-checkout et le partial clone ;
  • savoir réécrire l'historique en profondeur avec git filter-repo et en mesurer les conséquences ;
  • savoir récupérer un travail perdu avec le reflog et git fsck, et localiser un bug avec git bisect ;
  • savoir retirer un secret de tout l'historique et comprendre qu'il faut le révoquer.
Sommaire de la leçon

Tu maîtrises désormais le cycle complet du versionnement et de la collaboration. Reste un terrain plus rugueux : celui de l'échelle (dépôts de plusieurs gigaoctets, monorepos, gros assets binaires) et celui des situations difficiles (un secret commité, un reset qui a effacé du travail, un bug qui s'est glissé entre deux versions). Ces problèmes ne se résolvent pas avec les commandes du quotidien : ils demandent des outils spécialisés et une bonne compréhension de ce que Git stocke réellement.

Cette leçon est une boîte à outils de survie. Chaque section répond à une question concrète : comment ne pas faire exploser la taille du dépôt, comment ne cloner qu'une partie, comment effacer définitivement un fichier, comment retrouver ce qu'on croyait perdu, comment isoler un commit fautif. On ne réexplique pas les bases : on suppose que commit, rebase et reset te sont familiers.

Les gros fichiers : pourquoi Git souffre, et Git LFS

Git est conçu pour du texte. Quand tu modifies une ligne d'un fichier source, il stocke efficacement la différence. Mais un fichier binaire (image PSD, vidéo, build, modèle 3D) est opaque : à chaque modification, Git en garde une copie complète compressée dans l'historique. Un asset de 50 Mo modifié vingt fois, c'est potentiellement 1 Go dans .git, cloné par chaque membre de l'équipe, à jamais.

Git LFS (Large File Storage) résout cela en remplaçant le contenu du fichier par un petit pointeur texte dans l'historique. Le contenu réel est stocké sur un serveur LFS séparé et téléchargé à la demande.

Mettre en place LFS après avoir déjà commité des binaires ne nettoie pas l'historique : les anciennes versions restent dans .git. Pour migrer rétroactivement, il faut git lfs migrate import, qui réécrit l'historique (donc avec les mêmes précautions que la section suivante).

Les gros dépôts : ne cloner qu'une partie

Un monorepo regroupe plusieurs projets dans un seul dépôt. Pratique pour partager du code, mais le clone peut devenir énorme. Trois leviers permettent de ne récupérer que le nécessaire.

Réécrire l'historique en profondeur avec filter-repo

Supprimer un fichier d'un seul commit est trivial. Le supprimer de tout l'historique (parce qu'il contient un secret ou un binaire géant) demande de réécrire chaque commit où il apparaît. L'ancien outil git filter-branch est lent et truffé de pièges ; l'outil recommandé aujourd'hui est git-filter-repo (un script Python à installer séparément).

--invert-paths inverse la sélection : on retire le chemin au lieu de le garder.

La réécriture change tous les identifiants de commit à partir du premier commit touché. Conséquence : ton historique local n'a plus rien à voir avec celui du distant. Il faudra push --force et prévenir tout le monde, car chaque collègue devra re-synchroniser son clone.

Piège fréquent

Réécrire un historique déjà partagé casse les clones des autres : leurs branches divergent, leurs rebase et merge repartent sur les anciens commits, et les doublons s'accumulent. Ne réécris l'histoire publique qu'en dernier recours, sur une fenêtre annoncée, avec l'équipe au courant.

La récupération : reflog et fsck

Le reflog est ton filet de sécurité. Git y journalise chaque déplacement de HEAD et des branches : commits, reset, rebase, checkout. Même un commit qui n'est plus pointé par aucune branche y reste accessible (par défaut 90 jours). C'est ainsi qu'on annule un reset --hard ou un rebase raté.

Chaque entrée HEAD@{n} est une position passée de HEAD ; on y revient comme à n'importe quel commit.

Quand même le reflog ne suffit pas (par exemple un commit d'un autre clone, ou après un nettoyage agressif), git fsck inspecte la base d'objets et liste les commits orphelins (« dangling »), non rattachés à une branche :

rerere et stratégies de fusion

Si tu rebases souvent une longue branche, tu résous parfois plusieurs fois le même conflit. rerere (« reuse recorded resolution ») mémorise comment tu as résolu un conflit donné et rejoue automatiquement cette résolution la prochaine fois qu'il réapparaît.

Piège fréquent

Ne confonds pas l'option -X ours avec la stratégie -s ours. -X ours n'agit que sur les lignes en conflit. -s ours, elle, ignore totalement le contenu de l'autre branche : la fusion garde exactement ton arbre. Très utile pour neutraliser une branche, dévastateur si déclenché par erreur.

Sécurité : retirer un secret commité

Un mot de passe, un token, une clé d'API se sont glissés dans un commit. Premier réflexe, contre-intuitif mais vital : considère le secret comme compromis et révoque-le immédiatement. Tant qu'il a existé dans l'historique (poussé sur un distant, vu par la CI, présent dans un fork), tu dois partir du principe qu'il a fuité.

Le retirer du dernier commit ne suffit jamais : il reste dans tous les commits antérieurs. Il faut le purger de tout l'historique, comme un fichier ordinaire, puis force-pusher :

On préfère --force-with-lease à --force : il refuse d'écraser si le distant a bougé depuis ta dernière synchro.

Note

Réécrire l'historique ne purge pas les copies déjà existantes : caches de la plateforme, forks, clones des collègues. C'est pourquoi la révocation prime sur le nettoyage : seule la rotation de la clé garantit que le secret ne sert plus à rien.

Cas réel

Un développeur a poussé par mégarde une clé d'accès AWS dans un dépôt public : des robots qui scrutent GitHub en continu l'ont trouvée en quelques minutes et ont démarré des dizaines de serveurs de minage, laissant une facture de plusieurs milliers d'euros avant la fin de la journée. La leçon du terrain : dès qu'un secret a touché un dépôt, filter-repo nettoie l'historique mais n'efface pas l'exposition passée — seule la révocation immédiate de la clé stoppe l'hémorragie. C'est pourquoi les plateformes proposent le secret scanning, qui alerte automatiquement les fournisseurs quand un jeton connu apparaît dans un commit.

Pièges fréquents

Piège fréquent

Committer de gros binaires sans LFS fait gonfler .git de façon irréversible : chaque version reste stockée pour toujours. Mets LFS en place avant d'ajouter le premier asset, pas après.

  • Croire qu'un secret retiré du dernier commit est parti : il vit dans tout l'historique tant que tu ne réécris pas. Et même après, considère-le comme fuité : révoque.
  • Force-pusher sur main sans prévenir : tu casses la branche de référence de toute l'équipe. Protège la branche côté plateforme et utilise --force-with-lease.
  • Réécrire un historique partagé en douce : annonce-le, planifie une fenêtre, accompagne la re-synchronisation des clones.
  • Ignorer le reflog : la plupart des « j'ai tout perdu » sont en réalité récupérables pendant 90 jours.

Pour aller plus loin

Pour aller plus loin

Creuse git-filter-repo (callbacks de réécriture, remplacement de contenu via --replace-text) et BFG Repo-Cleaner, une alternative plus rapide et plus simple pour purger fichiers et secrets. Côté monorepos, regarde Nx et Turborepo (orchestration des builds) et Scalar (intégré à Git, il optimise les très gros dépôts via partial clone, sparse-checkout et maintenance en arrière-plan). Pour la sécurité, étudie la signature des commits, l'audit, et les hooks de détection de secrets (par exemple gitleaks ou trufflehog en pre-commit) pour bloquer une fuite avant le commit plutôt que d'avoir à la nettoyer.

Antisèche

Glossaire

Git LFS
Extension qui remplace un gros fichier par un pointeur texte dans l'historique et héberge le contenu réel sur un serveur séparé, téléchargé à la demande.
Pointeur LFS
Petit fichier texte (une centaine d'octets) stocké dans le dépôt à la place du binaire ; il contient l'empreinte (oid) et la taille du contenu réel.
Shallow clone
Clone tronqué en profondeur (--depth N) qui ne récupère que les N derniers commits, pas tout l'historique.
Partial clone
Clone (--filter=blob:none) qui télécharge la structure des commits mais diffère les contenus de fichiers (blobs), récupérés paresseusement.
Sparse-checkout
Mécanisme qui ne matérialise dans le répertoire de travail qu'un sous-ensemble choisi de fichiers ou de dossiers.
Reflog
Journal local de chaque déplacement de HEAD et des branches ; il garde accessibles ~90 jours des commits même « perdus », d'où la récupération d'un reset raté.
git bisect
Recherche dichotomique entre un commit bon et un commit mauvais pour isoler celui qui a introduit un bug, en ~log₂(N) essais.
filter-repo
Outil de réécriture d'historique en profondeur (purge d'un fichier, découpe d'un dépôt) ; il change tous les identifiants de commit et impose un force-push coordonné.

Récap et vérification

  • Git LFS remplace les gros binaires par des pointeurs ; configuré via .gitattributes, à mettre en place avant le premier asset.
  • Shallow (--depth), partial (--filter=blob:none) et sparse-checkout permettent de cloner et travailler vite sur de gros dépôts.
  • git filter-repo réécrit l'historique en profondeur (purge, découpe) mais change tous les identifiants : force-push et coordination obligatoires.
  • reflog et git fsck rattrapent un travail perdu ; bisect localise un commit fautif, manuellement ou via un script.
  • rerere rejoue les résolutions de conflits ; -X ours/theirs et -s ours orientent une fusion.
  • Un secret commité doit être révoqué puis purgé : le retirer du dernier commit ne suffit pas.
