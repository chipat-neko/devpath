Module 03 · Collaborer avec GitHub — Leçon 09

GitHub : héberger et publier

~28 min Débutant Leçon 08 recommandée

À la fin de cette leçon, tu sauras

  • distinguer Git (l'outil local) de GitHub (le service qui héberge et ajoute la collaboration) ;
  • créer un dépôt et pousser un projet existant avec git remote add et git push -u ;
  • t'authentifier de façon moderne par token (HTTPS) ou clé SSH, et savoir pourquoi le mot de passe est refusé ;
  • rédiger un README.md, ouvrir des issues et publier un site avec GitHub Pages.
Sommaire de la leçon

Jusqu'ici, ton dépôt vit uniquement sur ta machine : si ton disque rend l'âme, tout l'historique disparaît avec lui. Et pour collaborer, tu n'as toujours rien de mieux que l'e-mail. Cette leçon comble ce manque : tu vas héberger ton dépôt en ligne sur GitHub, le pousser en une commande, et débloquer la collaboration (issues, revues, pages publiques).

On part du connu — ton dépôt local avec ses commits — pour le publier sur un service distant. À la fin, ton projet sera sauvegardé, partageable par un simple lien, et prêt à recevoir des contributions.

Git n'est pas GitHub

C'est la confusion numéro un, alors clarifions-la tout de suite. Git est le programme qui tourne sur ta machine et gère l'historique en local : git commit, git log, git switch… ne parlent à aucun serveur. GitHub est un service en ligne qui héberge une copie distante de dépôts Git et ajoute par-dessus tout un écosystème de collaboration : suivi de bugs (issues), propositions de modifications relues (pull requests), pages publiques, automatisations.

  • Git = l'outil de versionnage, gratuit et libre, installé chez toi.
  • GitHub = un hébergeur de dépôts Git parmi d'autres (GitLab, Bitbucket, Codeberg…), avec sa surcouche sociale.

Tu peux très bien utiliser Git sans GitHub. Mais publier sur GitHub te donne une sauvegarde distante et les outils pour travailler à plusieurs.

Note

Dans le vocabulaire Git, le dépôt en ligne s'appelle un remote (dépôt distant). Par convention, le remote principal se nomme origin. Ce n'est qu'un surnom pointant vers une URL ; tu pourrais en avoir plusieurs.

Créer un dépôt : public ou privé ?

Crée d'abord un compte sur github.com, puis un nouveau dépôt via le bouton New repository. Tu choisis un nom (par exemple mon-portfolio) et surtout sa visibilité :

  • Public : visible par tout le monde sur Internet. Idéal pour un projet open source, un portfolio, un exercice que tu veux montrer.
  • Privé : visible par toi seul (et les personnes que tu invites). Pour un travail confidentiel, un projet client, ou tant que ce n'est pas prêt à être montré.

Au moment de la création, ne coche aucune option d'initialisation (README, .gitignore, licence) si tu pousses un projet qui existe déjà : sinon GitHub crée un premier commit de son côté et tu auras un conflit au moment de pousser.

Pousser un projet existant

Ton dossier est déjà un dépôt Git avec au moins un commit (vu en leçon 01). Il ne reste qu'à le relier au dépôt distant et à l'envoyer. GitHub t'affiche l'URL de ton dépôt ; remplace-la dans les commandes ci-dessous.

Décortiquons : git remote add origin <url> enregistre l'adresse du dépôt distant sous le nom origin. git push -u origin main envoie tes commits vers la branche main du remote ; l'option -u (pour upstream) crée le lien de suivi, si bien qu'ensuite un simple git push suffira.

Sortie typique d'un premier push réussi : la branche distante main est créée et suivie.

Erreur fréquente

Si Git répond error: remote origin already exists, c'est qu'un remote origin est déjà enregistré (souvent après un clone ou un premier essai). Ne relance pas git remote add : corrige plutôt l'URL avec git remote set-url origin <url>, ou supprime d'abord l'ancien avec git remote remove origin.

L'authentification moderne : token ou SSH

Quand tu pousses pour la première fois, GitHub veut vérifier que c'est bien toi. Important : le mot de passe de ton compte n'est plus accepté pour ces opérations Git. Deux méthodes modernes le remplacent.

Méthode 1 — token d'accès personnel (avec les URLs HTTPS). Tu génères un personal access token dans les réglages GitHub (Settings → Developer settings → Tokens). C'est une longue chaîne secrète que tu colles à la place du mot de passe quand Git le demande. Pour ne pas le retaper sans cesse, active un gestionnaire d'identifiants :

Méthode 2 — clé SSH (avec les URLs SSH). Tu génères une paire de clés sur ta machine, puis tu ajoutes la clé publique à ton compte GitHub. Ensuite, plus aucun mot de passe ni token à saisir.

Astuce

Sur ta machine personnelle, la clé SSH est la plus confortable : tu la configures une fois et tu oublies. Le token HTTPS dépanne sur une machine de passage ou derrière un réseau qui bloque SSH. Tu peux changer de méthode à tout moment avec git remote set-url.

Le README et la licence

Le fichier README.md, à la racine du dépôt, est la vitrine de ton projet : GitHub l'affiche automatiquement sur la page d'accueil du dépôt. Il est écrit en Markdown, une syntaxe légère où # fait un titre, **gras** met en gras, et - commence une liste.

Un bon README répond à trois questions : qu'est-ce que ce projet ?, comment l'installer ?, comment l'utiliser ?. Ajoute une licence (MIT, Apache, GPL…) pour dire clairement ce que les autres ont le droit de faire avec ton code ; GitHub propose de l'ajouter en un clic via le bouton Add file → Create new file → LICENSE.

Issues, tags et releases

Une fois en ligne, GitHub ajoute des outils que Git seul n'a pas. Les plus utiles au début :

  • Les issues : des fiches pour suivre les bugs, les idées et les tâches. Chacune a un titre, une description, des étiquettes (bug, enhancement…) et une discussion. C'est ton carnet de bord public.
  • Les tags et releases : un tag marque un commit précis comme une version. Une release habille un tag d'une page de présentation et de fichiers téléchargeables.

Sur GitHub, ce tag apparaîtra dans l'onglet Releases, où tu pourras rédiger les notes de version. Pratique pour communiquer « voici ce qui a changé entre la 1.0 et la 1.1 ».

Publier un site avec GitHub Pages

Si ton dépôt contient un site statique (HTML, CSS, JS — comme ce portfolio), GitHub peut l'héberger gratuitement à une vraie adresse web. C'est GitHub Pages. Aucune commande spéciale : tu actives la fonctionnalité dans les réglages.

  • Va dans Settings → Pages du dépôt.
  • Choisis la source : la branche main et le dossier / (root) (ou /docs si ton site y est rangé).
  • Valide : après une minute, ton site est en ligne à https://ton-pseudo.github.io/mon-portfolio/.

Ensuite, chaque git push vers main met le site à jour automatiquement. Ton index.html doit être à la racine du dossier source pour servir de page d'accueil.

Cas réel

Une bonne partie des sites de documentation que tu consultes tournent sur GitHub Pages : la doc de projets open source, d'innombrables portfolios d'étudiants et de développeurs, des blogs générés par Jekyll. C'est gratuit, servi en HTTPS, et lié au dépôt : le même git push qui sauvegarde ton code met le site à jour. Pour beaucoup, c'est leur premier site publié en ligne — sans louer de serveur.

Profil, étoiles et écosystème

Au-delà du code, GitHub est un réseau. Ton profil agrège tes dépôts publics et ton activité : c'est devenu une carte de visite pour les développeurs. Les étoiles (le bouton Star) servent de marque-page et de signal de popularité ; on « star » un projet qu'on veut retrouver ou soutenir. Le bouton Fork, lui, copie un dépôt sur ton compte pour y contribuer (on y reviendra avec les pull requests).

Astuce de profil : un dépôt portant exactement ton pseudo (par exemple ton-pseudo/ton-pseudo) avec un README.md s'affiche en haut de ta page de profil. C'est l'endroit idéal pour te présenter.

Pièges fréquents

  • Utiliser ton mot de passe pour pousser. GitHub le refuse depuis 2021 : tu verras une erreur d'authentification. Il faut un token (en HTTPS) ou une clé SSH. Le token se colle à la place du mot de passe.
  • Pousser des secrets dans un dépôt public. Une clé d'API ou un .env committé devient lisible par le monde entier — et reste dans l'historique même après suppression. Mets ces fichiers dans .gitignore avant de committer, et considère tout secret exposé comme compromis.
  • Confondre Git et GitHub. « Pousser sur GitHub » n'est pas « faire un commit ». Le commit est local (Git) ; le push l'envoie au distant (GitHub). Tant que tu n'as pas poussé, GitHub ne voit rien.
  • Choisir la mauvaise visibilité. Un projet client en public par erreur, c'est une fuite. Un exercice de cours en privé, et personne ne peut l'admirer. Tu peux changer la visibilité dans Settings → General → Danger Zone.

Pour aller plus loin

Quelques pistes une fois ton projet en ligne :

  • GitHub Pages pour un site plus ambitieux (générateurs de sites statiques, domaine personnalisé).
  • GitHub Actions : de l'automatisation (CI/CD) déclenchée à chaque push — lancer des tests, déployer, vérifier le code. Un univers à part entière.
  • Les organisations : regrouper plusieurs dépôts et membres sous une entité commune (équipe, asso, entreprise).
  • La sécurité : stocker les secrets dans Settings → Secrets plutôt que dans le code, et soigner ton .gitignore.

Pour aller plus loin

Ton dépôt est maintenant en ligne et sauvegardé. Les prochaines leçons exploitent vraiment la collaboration : cloner un dépôt distant, pull les changements des autres, et proposer ton travail via une pull request. La fondation, c'est ce push que tu viens de réussir.

Glossaire

GitHub
Service en ligne qui héberge des dépôts Git et ajoute une surcouche de collaboration (issues, pull requests, Pages, Actions). À distinguer de Git, l'outil local.
Dépôt (repository)
L'espace qui contient ton projet et tout son historique ; sur GitHub, sa visibilité est publique ou privée.
origin
Nom court conventionnel du dépôt distant principal ; alias d'une URL, enregistré par git remote add.
Token d'accès personnel (PAT)
Chaîne secrète générée dans les réglages GitHub, utilisée à la place du mot de passe pour s'authentifier en HTTPS.
Clé SSH
Paire de clés (privée gardée sur ta machine, publique déposée chez GitHub) qui authentifie tes push sans rien saisir.
README.md
Fichier Markdown à la racine du dépôt, affiché automatiquement comme page d'accueil : la vitrine du projet.
Issue
Fiche de suivi (bug, idée, tâche) avec titre, description, étiquettes et discussion : le carnet de bord du projet.
GitHub Pages
Hébergement gratuit d'un site statique tiré d'une branche du dépôt ; chaque push vers main le met à jour.

Récap et vérification

  • Git est l'outil local ; GitHub héberge le dépôt et ajoute issues, pull requests et revues.
  • On publie un projet existant avec git remote add origin <url> puis git push -u origin main.
  • L'authentification passe par un token (HTTPS) ou une clé SSH — jamais le mot de passe du compte.
  • Le README.md en Markdown sert de vitrine ; une licence précise les droits d'usage.
  • Les issues suivent bugs et tâches ; GitHub Pages héberge gratuitement un site statique poussé sur main.
