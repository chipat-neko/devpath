Module 02 · Branches & corrections — Leçon 07

Annuler et corriger

~35 min Intermédiaire Leçon 06 recommandée

À la fin de cette leçon, tu sauras

  • corriger ton dernier commit avec git commit --amend (message ou fichier oublié), sans toucher à un commit déjà poussé ;
  • jeter ou désindexer des modifications avec git restore et git restore --staged ;
  • distinguer git reset --soft, --mixed et --hard, et choisir entre reset (local) et revert (partagé) ;
  • retrouver un commit « perdu » grâce à git reflog, ton filet de sécurité.
Sommaire de la leçon

Tu viens de committer, et là, tu réalises : tu as oublié un fichier, le message contient une faute, ou pire, tu as enregistré quelque chose que tu ne voulais pas. Pas de panique. Git est conçu pour qu'on puisse presque toujours revenir en arrière — encore faut-il choisir le bon outil, parce qu'ils n'ont pas tous les mêmes conséquences.

Dans cette leçon, on va du moins risqué au plus puissant : corriger le dernier commit, jeter des modifications en cours, déplacer l'historique avec reset, annuler proprement avec revert, et enfin retrouver ce qu'on croyait perdu avec reflog. La règle d'or à garder en tête dès maintenant : réécrire l'historique en local est sans danger ; le réécrire après l'avoir partagé l'est beaucoup moins.

Corriger le dernier commit : git commit --amend

C'est le cas le plus fréquent : ton dernier commit est presque bon. Tu veux juste corriger son message, ou y glisser un fichier que tu as oublié de préparer. git commit --amend remplace le dernier commit par un nouveau qui le combine avec ce que tu prépares.

Important : --amend ne modifie pas l'ancien commit, il en crée un nouveau à la place. L'ancien identifiant disparaît au profit d'un nouveau. C'est exactement pour ça qu'il faut être prudent dès qu'un commit a quitté ta machine.

Piège fréquent

N'utilise --amend que sur un commit pas encore poussé. Si tu modifies un commit déjà partagé (git push déjà fait), tu réécris l'historique commun : les autres se retrouveront avec deux versions du même travail et des conflits pénibles.

Jeter ou désindexer : git restore

Avant même de parler de commits, tu veux souvent juste annuler des modifications en cours. Deux situations, deux usages de git restore (la commande moderne, plus claire que l'ancien checkout pour ça).

Retiens la distinction : git restore <fichier> efface tes modifications pour revenir au dernier commit, tandis que git restore --staged <fichier> ne touche pas à ton travail — il le fait simplement sortir de la zone de préparation. Quand tu hésites, lance git status : Git lui-même te rappelle ces deux commandes selon la situation.

Note

Tu verras parfois git checkout -- app.js pour jeter des changements : c'est l'ancienne façon de faire. git restore et git restore --staged font la même chose avec des noms qui disent enfin ce qu'ils font.

git reset : trois modes à bien distinguer

git reset déplace le pointeur HEAD (qui marque « où tu en es » dans l'historique) vers un commit antérieur. Ce qui change d'un mode à l'autre, c'est ce qu'on fait du travail qui se trouvait après ce point. Prends HEAD~1 comme « le commit juste avant le dernier ».

Voici l'effet de chacun, du plus doux au plus brutal :

  • --soft : le commit est défait, mais ses changements restent préparés. Idéal pour « je veux refaire ce commit avec un meilleur découpage ».
  • --mixed (le défaut) : le commit est défait, ton travail est toujours là dans tes fichiers, mais plus dans le sas. Tu repars de zéro côté préparation.
  • --hard : le commit est défait et les modifications sont effacées du disque. Tes fichiers reviennent à l'état du commit cible. Rien à récupérer dans le sas.

Piège fréquent

git reset --hard détruit aussi les modifications non commitées qui traînaient dans tes fichiers. Si tu n'avais rien enregistré, ce travail-là est vraiment perdu (le reflog ne sauve que ce qui a été commité). Vérifie toujours git status avant un --hard.

git revert : annuler sans réécrire l'histoire

reset réécrit l'historique en supprimant des commits. Sur une branche partagée, c'est interdit. La bonne solution est git revert : il crée un nouveau commit qui annule les changements d'un commit passé. L'ancien commit reste dans l'historique, et un commit « inverse » vient par-dessus.

C'est sûr : personne ne voit son historique modifié, on ajoute seulement un nouveau commit visible et explicable. C'est la méthode à privilégier dès qu'un commit a été poussé et que d'autres l'ont peut-être déjà récupéré.

Reset ou revert : lequel choisir ?

La question n'est pas « lequel est le meilleur » mais « ce commit a-t-il déjà été partagé ? ».

  • Travail encore local, jamais poussé → git reset est parfait. Tu nettoies ton historique avant de le rendre public, personne n'est gêné.
  • Commit déjà poussé / branche partagée → git revert. Tu annules l'effet sans toucher au passé commun, donc sans casser le dépôt des autres.

Formule à retenir : reset réécrit, revert ajoute. Réécrire ne se fait que sur ce que toi seul possèdes ; ajouter est toujours sans risque.

Note

Si tu as vraiment besoin de réécrire une branche déjà poussée (cas avancé, sur ta propre branche de travail), pousse avec git push --force-with-lease plutôt que --force : cette variante refuse d'écraser le travail d'un collègue arrivé entre-temps. Sur une branche partagée comme main, préfère toujours revert.

Cas réel — le secret poussé par erreur

Tu commites un fichier .env avec une clé d'API, et tu pousses. Réflexe fréquent : « je fais un revert et c'est réglé ». Faux : revert ajoute un commit qui retire le fichier de la version actuelle, mais la clé reste visible dans l'historique (le commit fautif existe toujours). Même en réécrivant l'historique (reset puis push --force), considère la clé comme compromise dès la première seconde où elle a été publique. La seule vraie parade : révoquer et régénérer le secret immédiatement, puis purger l'historique avec un outil dédié (git filter-repo ou BFG). Annuler un commit n'annule jamais une fuite.

Le filet de sécurité : git reflog

Tu as fait un reset --hard de trop et tu paniques ? Bonne nouvelle : Git garde une trace de tous les endroits où HEAD est passé, même les commits « décrochés ». Cette trace, c'est le reflog.

Tu repères l'identifiant du commit perdu (ici 3a7d4e0, ton commit « Ajoute la page de contact »), puis tu y retournes ou tu le récupères.

Astuce

Avant toute manipulation risquée (reset --hard, --amend, rebase), prends le réflexe de noter l'identifiant courant avec git log --oneline -1. Avec ça plus le reflog, tu peux presque toujours revenir à l'état d'avant.

Pièges fréquents

  • git reset --hard sur du travail non sauvegardé. Les modifications jamais commitées sont effacées sans recours. Commite (ou git stash) avant, ou au minimum relis git status.
  • --amend ou reset sur un commit déjà poussé. Tu réécris l'historique des autres. Sur du partagé, passe par git revert.
  • Confondre reset et revert. reset supprime des commits (local) ; revert ajoute un commit d'annulation (partagé). Le mauvais choix casse le dépôt de l'équipe.
  • Oublier le reflog. Beaucoup de débutants croient un commit « perdu » définitivement après un mauvais reset. Tant qu'il a été commité, git reflog le retrouve.

Pour aller plus loin

  • git restore en profondeur : on peut restaurer un fichier depuis un commit précis avec git restore --source=HEAD~2 app.js, pas seulement depuis le dernier.
  • git clean : pour supprimer les fichiers non suivis (que reset ne touche pas). Toujours tester avec git clean -n (simulation) avant git clean -f.
  • Le rebase interactif (leçon 12) : pour réorganiser, fusionner ou réécrire plusieurs commits locaux d'un coup, bien plus fin que --amend.

Pour aller plus loin

Le reflog n'est pas éternel : Git nettoie les entrées anciennes (typiquement après 90 jours). Ce n'est pas une sauvegarde ; c'est un filet pour rattraper une erreur récente. La vraie sauvegarde, c'est de pousser régulièrement ton travail sur un dépôt distant.

Antisèche : annuler et corriger

Le mémo des commandes pour revenir en arrière, de la plus douce à la plus radicale.

Glossaire

git commit --amend
Remplace le dernier commit par un nouveau qui le combine avec ce qui est préparé ; à réserver aux commits non encore poussés.
HEAD
Pointeur sur « où tu en es » dans l'historique, c'est-à-dire le commit courant de ta branche.
HEAD~1
Le commit juste avant HEAD (son parent) ; HEAD~2 désigne deux commits en arrière, etc.
Sas (index)
La zone de préparation où git add place ce qui ira dans le prochain commit ; --soft la conserve, --mixed la vide.
Répertoire de travail
Tes fichiers réels sur le disque, tels que tu les édites ; seuls reset --hard et restore peuvent y effacer du travail.
git reset
Déplace HEAD vers un commit antérieur et, selon le mode, ajuste le sas et les fichiers : réécrit l'historique, donc réservé au local.
git revert
Crée un nouveau commit qui annule les changements d'un commit passé, sans supprimer ni réécrire l'historique : sûr sur une branche partagée.
reflog
Journal des positions successives de HEAD ; permet de retrouver un commit décroché (conservé environ 90 jours). Ce n'est pas une sauvegarde.

Récap et vérification

  • git commit --amend corrige le dernier commit (message ou fichier oublié) — jamais sur du déjà poussé.
  • git restore <fichier> jette les changements en cours ; git restore --staged <fichier> désindexe sans rien perdre.
  • git reset déplace HEAD : --soft garde le sas, --mixed garde le travail, --hard jette tout.
  • git revert <sha> ajoute un commit qui annule un commit passé — sûr sur une branche partagée.
  • reset = réécrire l'historique (local) ; revert = annuler proprement (partagé) ; git reflog est ton filet pour retrouver un commit perdu.

Vérifie ta compréhension

  1. Tu as poussé un commit fautif sur la branche main partagée. Utilises-tu reset ou revert, et pourquoi ?
  2. Quelle différence concrète entre git reset --mixed HEAD~1 et git reset --hard HEAD~1 ?
  3. Après un git reset --hard malheureux, quelle commande te permet de retrouver le commit « perdu » ?
