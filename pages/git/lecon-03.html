Module 01 · Démarrer avec Git — Leçon 03

Lire l'historique et ignorer des fichiers

~30 min Débutant Leçon 02 recommandée

À la fin de cette leçon, tu sauras

  • lire et filtrer l'historique avec git log (--oneline, --graph, --stat, -p) ;
  • inspecter un commit avec git show et comparer des versions avec git diff et git diff --staged ;
  • désigner un commit avec les références HEAD, HEAD~1 et un SHA court ;
  • écrire un .gitignore pour exclure fichiers générés et secrets, même un fichier déjà suivi.
Sommaire de la leçon

Tu sais maintenant créer des commits. Mais un historique ne sert à rien si tu ne sais pas le relire. Cette leçon t'apprend à explorer le passé de ton projet : qui a changé quoi, quand, et pourquoi ; comparer deux versions ; et désigner précisément un commit. Puis on verra l'autre face de la médaille : empêcher Git de suivre ce qui ne le mérite pas (fichiers générés, secrets) grâce au .gitignore.

Tout ce qui suit se lit dans le terminal. Aucune commande de cette leçon ne modifie ton projet : log, show, diff et blame sont des outils de lecture. Tu peux les lancer sans crainte, autant de fois que tu veux.

git log et ses options

git log affiche l'historique du plus récent au plus ancien. Brut, il est verbeux ; ce sont ses options qui le rendent vraiment utile. Voici celles que tu emploieras tous les jours.

Décortiquons les plus importantes : --oneline donne un panorama ; --graph dessine les branches (indispensable dès que tu en auras plusieurs) ; --stat répond à « quels fichiers ? » ; -p répond à « quel changement exactement ? ». Les filtres -n, --since et --author se combinent entre eux.

Astuce

git log ouvre un « pager » quand la sortie est longue : navigue avec les flèches ou Espace, et quitte en tapant la touche q. La vue --oneline --graph --all est si pratique qu'on s'en crée souvent un raccourci : git config --global alias.lg "log --oneline --graph --all", puis on tape simplement git lg.

Lire un commit précis avec git show

Quand un commit t'intrigue dans le log, git show en affiche tout le détail : l'auteur, la date, le message complet, et le diff exact (ce qui a été ajouté et retiré).

Tu n'as pas besoin de taper le SHA en entier : les premiers caractères suffisent tant qu'ils restent uniques dans le dépôt. Sept caractères, comme dans --oneline, conviennent presque toujours.

Comparer des versions avec git diff

git diff montre les différences entre deux états. Le point qui piège tout le monde au début : par défaut, il ne compare pas avec le dernier commit, mais ton travail en cours avec la zone de préparation (l'index).

Retiens la règle : git diff seul = « ce que je n'ai pas encore add ». git diff --staged = « ce que mon prochain commit contiendra ». Lance ce dernier juste avant de committer : c'est ta dernière relecture avant de figer l'instantané.

Les références : HEAD, parents et SHA

Pour désigner un commit, tu n'es pas obligé de copier son SHA. Git fournit des références relatives, bien plus lisibles.

  • HEAD : le commit sur lequel tu es actuellement (le bout de ta branche courante).
  • HEAD~1 (ou HEAD^) : le commit parent, c'est-à-dire celui juste avant HEAD. HEAD~2 remonte de deux crans, et ainsi de suite.
  • Un SHA court (ex. a1b2c3d) : pointe un commit précis, où qu'il soit dans l'histoire.

Le .gitignore : exclure ce qui ne doit pas être suivi

Tout ne mérite pas d'entrer dans l'historique : les dépendances réinstallables, les fichiers générés automatiquement, et surtout les secrets. Un fichier .gitignore, placé à la racine du dépôt, liste des motifs de chemins que Git doit ignorer.

Quelques règles de syntaxe : la barre finale / cible un dossier ; l'étoile * remplace n'importe quelle suite de caractères ; une barre en tête / ancre le motif à la racine du dépôt ; le point d'exclamation ! ré-inclut quelque chose qu'un motif précédent excluait. Les lignes commençant par # sont des commentaires.

Piège fréquent

Le .gitignore n'agit que sur les fichiers pas encore suivis. Si tu as déjà committé un fichier, l'ajouter au .gitignore ne change rien : Git continue de le suivre. Il faut d'abord le retirer du suivi.

Pour cesser de suivre un fichier déjà committé sans le supprimer de ton disque, utilise git rm --cached :

L'option --cached est cruciale : sans elle, git rm .env supprimerait aussi le fichier de ton dossier. Avec --cached, Git oublie le fichier mais le laisse sur ton disque.

Qui a écrit quoi avec git blame

Quand tu tombes sur une ligne mystérieuse, git blame t'indique, pour chaque ligne d'un fichier, le commit, l'auteur et la date qui l'ont introduite.

Cas réel — l'enquête sur une régression

Le total du panier est faux depuis hier. Tu ouvres panier.js, tu repères la ligne du calcul et tu lances git blame -L 40,50 panier.js : elle a été modifiée dans le commit 3f2a1b0. Un git show 3f2a1b0 affiche alors le diff complet et le message « Applique la TVA au sous-total » : la remise était calculée après la taxe. En trois commandes de lecture seule — log, blame, show — tu as trouvé le quand, le qui et le pourquoi, sans rien modifier ni risquer de casser quoi que ce soit.

Pièges fréquents

  • Committer un secret ou node_modules/. Un git add . sans .gitignore embarque ton .env et tes dépendances. Un secret committé reste dans l'historique même après suppression : considère-le comme compromis et change-le.
  • Ajouter au .gitignore un fichier déjà suivi. C'est sans effet : Git continue de le suivre. Il faut git rm --cached <fichier> puis committer.
  • Confondre git diff et git diff --staged. Le premier montre ce qui n'est pas préparé ; le second, ce qui est prêt à committer. Si git diff ne montre « rien » alors que tu as modifié des fichiers, c'est sûrement que tu les as déjà add : regarde avec --staged.
  • Oublier le q pour quitter le pager. Si ton terminal semble « bloqué » après un git log, tu es dans le pager : tape la touche q.

Pour aller plus loin

Quelques pistes pour explorer plus tard, sans t'éparpiller maintenant :

  • Les templates de .gitignore. Le dépôt github/gitignore rassemble des fichiers prêts à l'emploi par langage et outil (Node, Python, Visual Studio…). Inutile de tout écrire à la main.
  • Chercher dans les messages. git log --grep="frais" filtre les commits dont le message contient un mot.
  • Résumer par auteur. git shortlog -s -n compte les commits par personne — pratique pour voir qui a contribué.
  • Formats personnalisés. git log --pretty=format:"%h %an %s" compose ta propre ligne (empreinte, auteur, sujet) quand les options toutes faites ne suffisent pas.

Pour aller plus loin

Combine les options : git log --oneline --author="Noah" --since="1 month ago" -- panier.js répond à « quels commits Noah a-t-il faits sur panier.js ce dernier mois ? ». Le -- sépare les options des noms de fichiers.

Le mémo des commandes de lecture de cette leçon.

Glossaire

git log
Affiche l'historique des commits, du plus récent au plus ancien ; ses options (--oneline, --graph, --stat, -p) et ses filtres le rendent exploitable.
SHA (court)
Empreinte unique d'un commit (40 caractères, souvent abrégée à 7). Les premiers caractères suffisent à le désigner tant qu'ils restent uniques dans le dépôt.
HEAD
Référence sur le commit courant (la pointe de la branche active). HEAD~1 (ou HEAD^) désigne son parent, HEAD~2 le grand-parent, et ainsi de suite.
diff (patch)
Liste des différences entre deux états : les lignes préfixées de - ont été retirées, celles préfixées de + ont été ajoutées.
--staged (alias --cached)
Option qui fait porter la comparaison sur l'index (le contenu préparé) plutôt que sur le répertoire de travail.
.gitignore
Fichier listant des motifs de chemins que Git doit ignorer ; n'agit que sur les fichiers pas encore suivis.
git blame
Annote chaque ligne d'un fichier avec le commit, l'auteur et la date qui l'ont introduite : sert à comprendre le contexte, pas à accuser.
Pager
Afficheur paginé qu'ouvre Git pour les longues sorties ; on y navigue avec les flèches ou Espace et on quitte avec la touche q.

Récap et vérification

  • git log relit l'historique ; ses options --oneline, --graph, --stat, -p et les filtres -n, --since, --author le rendent exploitable.
  • git show <sha> détaille un commit ; un SHA court de quelques caractères suffit à le désigner.
  • git diff compare le travail à l'index ; git diff --staged compare l'index au dernier commit ; git diff <sha1> <sha2> compare deux commits.
  • HEAD est le commit courant, HEAD~1 son parent : des références plus lisibles qu'un SHA.
  • Le .gitignore exclut fichiers générés et secrets ; pour un fichier déjà suivi, il faut git rm --cached.
  • git blame indique qui a introduit chaque ligne, pour comprendre le contexte d'un changement.

Vérifie ta compréhension

  1. Quelle est la différence entre git diff et git diff --staged ?
  2. Tu ajoutes .env au .gitignore, mais Git continue de le suivre. Que s'est-il passé, et quelle commande corrige ça ?
  3. À quoi correspond HEAD~1, et comment l'utiliser pour voir ce que tu as changé depuis le commit précédent ?
