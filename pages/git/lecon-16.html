Module 05 · Git en profondeur — Leçon 16

Submodules, worktrees, hooks et signature

~34 min Intermédiaire Leçon 15 recommandée

À la fin de cette leçon, tu sauras

  • savoir inclure un dépôt avec un submodule et le récupérer via --recursive ;
  • savoir ouvrir plusieurs branches en parallèle avec git worktree ;
  • savoir automatiser des vérifications avec les hooks côté client ;
  • savoir signer ses commits (-S) pour obtenir le badge Verified.
Sommaire de la leçon

Tu maîtrises déjà le quotidien de Git : commits, branches, fusion, distant, pull requests, rebase. Cette leçon ouvre la boîte à outils des projets complexes : inclure un dépôt dans un autre, travailler sur plusieurs branches en parallèle sans stash, automatiser des vérifications avant chaque commit, et prouver cryptographiquement que tu es bien l'auteur d'un commit.

Aucune de ces fonctionnalités n'est obligatoire au démarrage, mais chacune résout un problème précis qui revient vite sur les gros dépôts. On termine par un guide « quand utiliser quoi ».

Les submodules : un dépôt dans le dépôt

Un submodule (sous-module) te permet d'inclure un autre dépôt Git à l'intérieur du tien, à un emplacement précis. Typiquement : une bibliothèque maison, un thème, ou un SDK partagé entre plusieurs projets. Tu ajoutes le sous-module avec son URL.

Git crée un fichier .gitmodules qui mémorise le chemin et l'URL de chaque sous-module. Ce fichier est versionné dans ton dépôt parent.

Contenu du fichier .gitmodules.

Point crucial : le dépôt parent ne stocke pas le contenu du sous-module, seulement le SHA exact du commit sur lequel il est positionné (un objet spécial de type gitlink, visible en mode 160000 dans l'arborescence). Le commit du parent fige donc une version précise du sous-module. C'est ce qui garantit la reproductibilité : tout le monde récupère exactement la même version de ui-kit.

Cloner et mettre à jour un projet avec sous-modules

Quand quelqu'un clone ton projet de façon classique, les dossiers de sous-modules existent mais sont vides. Il faut le dire explicitement à Git, soit au clonage, soit après.

Note

L'option moderne est --recurse-submodules. L'ancienne forme --recursive reste un alias accepté par git clone, d'où sa présence dans de nombreux tutoriels ; préfère la forme longue, plus explicite et cohérente avec les autres commandes.

Pour faire avancer un sous-module vers un commit plus récent, tu entres dedans, tu mets à jour, puis tu valides le nouveau SHA dans le parent.

Les worktrees : plusieurs dossiers, un seul dépôt

Un worktree (arbre de travail) te donne un second répertoire de travail rattaché au même dépôt. Au lieu de stash ou de re-cloner pour traiter un correctif urgent pendant que tu développes une fonctionnalité, tu ouvres simplement la branche dans un autre dossier.

Tu as maintenant deux dossiers : ton dossier principal sur ta branche de feature, et ../app-hotfix sur hotfix. Les deux partagent le même historique et la même base d'objets (un seul dossier .git), sans duplication ni stash.

Cas réel — le bug P1 qui tombe en plein chantier

Tu es au milieu d'un gros remaniement, ton arbre de travail est à moitié cassé, et un bug critique tombe en production. Avec git stash, tu risques d'empiler puis d'oublier ton travail ; recloner prend du temps. À la place : git worktree add ../app-hotfix hotfix, tu corriges dans un dossier propre, tu déploies, puis git worktree remove. Ton chantier principal n'a pas bougé d'un octet. C'est aussi ce que font les serveurs de CI pour compiler plusieurs branches en parallèle sur un seul clone.

Astuce

Une même branche ne peut être active que dans un seul worktree à la fois. C'est une sécurité : impossible de modifier hotfix à deux endroits en même temps. Pour créer une branche neuve directement dans le worktree, utilise git worktree add -b nouvelle-branche ../dossier.

Les hooks côté client : automatiser avant le commit

Un hook est un script que Git exécute automatiquement à un moment précis. Côté client, les plus utiles sont pre-commit (avant d'enregistrer le commit), commit-msg (pour valider le message) et pre-push (avant l'envoi). Ils vivent dans .git/hooks.

Si le script se termine avec un code de sortie non nul (exit 1), Git annule le commit. Tu automatises ainsi le formatage, les tests rapides ou l'interdiction de certains motifs.

Piège fréquent

Le dossier .git/hooks n'est jamais versionné : tes coéquipiers ne reçoivent pas tes hooks. Pour les partager, utilise un outil dédié comme Husky (écosystème Node) ou le framework pre-commit (multi-langage), qui versionnent la config et installent les hooks pour toute l'équipe. Git permet aussi de pointer vers un dossier versionné via core.hooksPath.

Signer ses commits : prouver l'auteur

Le champ « auteur » d'un commit est du simple texte : n'importe qui peut écrire ton nom. La signature cryptographique (GPG ou SSH) résout ça : elle prouve qu'un commit vient bien de toi. Avec une clé SSH, la configuration est rapide (signature SSH disponible depuis Git 2.34).

Sur la plateforme distante, déclare ta clé publique de signature (différente d'une clé de connexion). GitHub affiche alors un badge Verified à côté des commits signés dont la clé est reconnue.

Note

Pour que git log --show-signature dise « Good signature » avec une clé SSH, Git doit retrouver la clé dans un fichier allowedSignersFile (option gpg.ssh.allowedSignersFile). Côté GitHub, c'est la plateforme qui joue ce rôle de validation.

Piège fréquent

Si tu signes mais que tu oublies de publier ta clé publique sur GitHub, tes commits resteront sans badge « Verified ». La signature locale ne suffit pas : la plateforme doit connaître la clé pour la valider.

Git LFS : versionner les gros fichiers

Git LFS (Large File Storage) gère les gros binaires (vidéos, PSD, modèles 3D, jeux de données) sans gonfler l'historique. Au lieu de stocker le fichier dans Git, LFS enregistre un petit pointeur texte et range le binaire à part.

Le motif suivi est mémorisé dans .gitattributes (versionné). Sans LFS, chaque révision d'un fichier de 200 Mo s'ajoute à l'historique de tout le monde, pour toujours : le dépôt devient vite ingérable.

Quand utiliser quoi

  • Submodule : tu dépends d'un autre dépôt Git dont tu veux figer une version précise et garder l'historique séparé.
  • Worktree : tu dois travailler sur deux branches en parallèle (correctif urgent + feature) sans stash ni nouveau clone.
  • Hooks : tu veux automatiser lint, formatage ou tests à des moments clés ; partage-les via Husky / pre-commit.
  • Signature : ton équipe ou ta plateforme exige des commits authentifiés (badge « Verified »).
  • LFS : ton dépôt contient de gros binaires qui ne doivent pas alourdir l'historique.

Pièges fréquents

Piège fréquent

Cloner un projet à sous-modules sans --recurse-submodules : les dossiers sont vides et la compilation échoue. Réflexe de secours : git submodule update --init --recursive.

Autres erreurs classiques :

  • Modifier un sous-module sans committer dans les deux dépôts : un commit dans libs/ui-kit n'est visible que si tu valides aussi le nouveau SHA dans le parent. Sinon, tes coéquipiers récupèrent l'ancienne version.
  • Compter sur des hooks dans .git/hooks : ils ne suivent pas le clone. Ce qui marche chez toi ne s'exécute pas chez les autres.
  • Signer sans publier la clé publique : pas de badge « Verified ».

Pour aller plus loin

Pour aller plus loin

Explore les subtrees (git subtree), une alternative aux submodules qui fusionne le code étranger dans ton historique sans dépendance externe. Les worktrees servent aussi en CI pour builder plusieurs branches en parallèle. Côté automatisation, regarde les hooks côté serveur (pre-receive) qui imposent des règles à tout le monde, et sigstore / gitsign pour signer sans gérer ses propres clés.

Antisèche : la boîte à outils des projets complexes

Le mémo des cinq outils de cette leçon et de leurs fichiers de configuration.

Glossaire

Submodule (sous-module)
Dépôt Git imbriqué dans un autre à un chemin donné ; le parent en fige un commit précis (gitlink) sans copier le contenu.
gitlink
Entrée d'arbre spéciale (mode 160000) qui stocke le SHA d'un commit d'un sous-module au lieu d'un blob.
Worktree (arbre de travail)
Répertoire de travail supplémentaire rattaché au même dépôt ; permet d'ouvrir une autre branche sans stash ni re-clone.
Hook
Script lancé automatiquement par Git à un moment clé (pre-commit, commit-msg, pre-push…) ; peut annuler l'action s'il échoue.
core.hooksPath
Réglage Git pointant les hooks vers un dossier versionné, afin de les partager avec toute l'équipe.
Signature de commit
Preuve cryptographique (GPG ou SSH) de l'auteur d'un commit ; validée par la plateforme grâce à la clé publique.
Verified
Badge affiché par GitHub quand la signature d'un commit correspond à une clé publique déclarée sur le compte.
Git LFS
Extension qui stocke les gros binaires hors de l'historique et ne versionne qu'un pointeur texte.

Récap et vérification

  • Un submodule imbrique un dépôt et fige son SHA via .gitmodules ; clone avec --recurse-submodules.
  • Un worktree ouvre une branche dans un dossier séparé, sans stash ni re-clone.
  • Les hooks automatisent des vérifications ; versionne-les avec Husky ou pre-commit.
  • La signature (-S, commit.gpgsign) prouve l'auteur ; publie ta clé pour le badge « Verified ».
  • Git LFS garde les gros binaires hors de l'historique.

Vérifie ta compréhension

  1. Que stocke exactement le dépôt parent à propos d'un sous-module, et pourquoi est-ce important ?
  2. Pourquoi un hook placé dans .git/hooks ne suffit-il pas pour toute l'équipe ?
  3. Tu vois « Unverified » sur GitHub alors que tu signes en local : quelle est la cause la plus probable ?
