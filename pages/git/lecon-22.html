Enquêter dans l'historique : blame, log et pickaxe

~36 min Avancé Leçon 03 recommandée

À la fin de cette leçon, tu sauras

  • retrouver qui a écrit une ligne, et dans quel commit, avec git blame ;
  • filtrer l'historique avec git log (par auteur, message, date, contenu) ;
  • traquer l'apparition d'une chaîne avec la pioche -S et -G ;
  • suivre une fonction avec -L et un fichier renommé avec --follow.
Sommaire de la leçon

Un dépôt, c'est une archive vivante de toutes les décisions prises sur le code. Mais l'archive ne sert à rien si on ne sait pas l'interroger. « Depuis quand cette ligne est-elle là ? Qui l'a écrite, et pourquoi ? Quand cette variable a-t-elle disparu ? Dans quel commit ce mot-clé est-il apparu ? » — autant de questions dont la réponse est déjà dans l'historique.

Cette leçon fait de toi un enquêteur. Trois outils : git blame annote chaque ligne, git log filtre les commits selon mille critères, et la pioche (pickaxe) retrouve le commit exact où un bout de texte est apparu ou a disparu. On travaille en lecture seule : aucune de ces commandes ne modifie ton dépôt.

git blame : qui a écrit cette ligne

git blame <fichier> affiche le fichier ligne par ligne, chacune précédée du dernier commit qui l'a touchée : son SHA court, l'auteur et la date. C'est le point de départ de toute enquête sur une ligne suspecte.

Un blame ciblé, et sans le bruit

Sur un gros fichier, on cible quelques lignes avec -L. Et pour ne pas « accuser » à tort le commit qui a seulement reformaté le code, deux options précieuses :

  • -w ignore les changements d'espaces (indentation, reformatage) et remonte à l'auteur du vrai changement ;
  • -C suit le code déplacé ou copié depuis un autre fichier ;
  • --ignore-rev (et le fichier .git-blame-ignore-revs) écarte des commits entiers de reformatage massif.

Piège fréquent

blame désigne le dernier commit à avoir touché la ligne, pas forcément celui qui a introduit la logique. Un simple reformatage (indentation, passage d'un formateur automatique) « vole » la paternité de toute la ligne. Le réflexe : -w pour ignorer les espaces, et un fichier .git-blame-ignore-revs pour neutraliser les gros commits cosmétiques.

Cas réel

Une régression apparaît en production : le montant des commandes est faux depuis « quelque temps ». git blame sur la ligne de calcul pointe un commit de reformatage — fausse piste. La développeuse dégaine alors la pioche : git log -S"* 1.20" -p retrouve en une commande le commit exact où le taux de TVA a été codé en dur à 1.20 au lieu d'être lu depuis la configuration, trois semaines plus tôt. Message du commit, auteur, contexte : toute l'histoire tient en un écran. Sans la pioche, il aurait fallu relire des dizaines de diffs à la main.

Suivre une fonction, suivre un fichier renommé

Deux options ferment l'arsenal. -L suit l'évolution d'une plage de lignes ou d'une fonction au fil du temps. Et --follow permet à git log de traverser un renommage : sans lui, l'historique d'un fichier s'arrête net au commit qui l'a rebaptisé.

Astuce

Combine les outils : blame pour repérer le commit d'une ligne, puis git show <sha> pour le pourquoi, et la pioche -S quand la ligne a bougé ou disparu. L'enquête va presque toujours de la ligne (blame) vers le commit (show), puis vers le contenu (pickaxe).

Pièges fréquents

  • Accuser le reformateur : blame montre le dernier toucher, pas l'auteur de la logique. Utilise -w et .git-blame-ignore-revs.
  • Confondre -S et -G : -S traque un changement de nombre d'occurrences (apparition/disparition) ; -G matche la présence dans le diff (regex), plus large mais plus bruyant.
  • Oublier --follow et croire qu'un fichier « n'a pas d'histoire » alors qu'il a juste été renommé.
  • Chercher un texte avec --grep : --grep fouille les messages de commit, pas le code. Pour le code, c'est la pioche.

Pour aller plus loin

Pour aller plus loin

Regarde git log --pickaxe-regex (traiter l'argument de -S comme une regex), git grep qui cherche dans l'état du code à une révision donnée (et non dans les diffs), et l'intégration blame des éditeurs (l'extension GitLens pour VS Code affiche l'auteur en bout de ligne, en direct). Pour l'archéologie lourde, git log --follow -p -- <fichier> déroule tout le film d'un fichier, renommages compris.

Glossaire

git blame
Commande qui annote chaque ligne d'un fichier avec le dernier commit l'ayant modifiée (SHA, auteur, date).
Pioche (pickaxe)
Recherche de git log qui fouille le contenu des diffs : -S (le nombre d'occurrences d'une chaîne change) et -G (la chaîne/regex apparaît dans le diff).
-S
Variante de la pioche qui isole les commits où une chaîne apparaît ou disparaît (son décompte varie) : idéale pour dater une introduction ou une suppression.
-G
Variante de la pioche qui retient tout commit dont le diff contient le motif (expression régulière) : plus large, elle capte aussi les lignes modifiées ou déplacées.
--grep
Filtre de git log portant sur le message des commits (et non sur le code).
-L
Option qui suit l'évolution d'une plage de lignes ou d'une fonction (-L :fonction:fichier) au fil de l'historique.
--follow
Option qui fait suivre à git log l'historique d'un fichier au-delà d'un renommage.
.git-blame-ignore-revs
Fichier listant des commits (reformatages massifs) que blame doit ignorer pour ne pas fausser la paternité des lignes.

Récap et vérification

  • git blame relie chaque ligne à son dernier commit ; -w et .git-blame-ignore-revs écartent le bruit du reformatage.
  • git log filtre par auteur, message (--grep), date et fichier, avec -p pour voir les diffs.
  • La pioche fouille le contenu : -S pour l'apparition/disparition d'une chaîne, -G pour toute présence (regex).
  • -L suit une fonction ; --follow traverse un renommage.
  • L'enquête va de la ligne (blame) au commit (show) puis au contenu (pickaxe).

Vérifie ta compréhension

  1. Pourquoi git blame peut-il désigner un commit qui n'a fait que reformater ? Comment l'éviter ?
  2. Tu veux dater l'apparition du mot API_KEY dans le code : quelle commande ?
  3. Quelle est la différence entre -S et -G ?
  4. Un fichier semble n'avoir que trois commits alors qu'il est ancien : quelle option manque probablement ?
