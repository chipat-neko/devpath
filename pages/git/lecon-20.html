Cherry-pick : transplanter un commit

~34 min Intermédiaire Leçon 07 recommandée

À la fin de cette leçon, tu sauras

  • recopier un commit précis sur ta branche courante avec git cherry-pick ;
  • backporter un correctif d'une branche vers une autre sans tout fusionner ;
  • gérer une plage de commits, un conflit (--continue/--abort) et les options -x, -n ;
  • reconnaître quand cherry-pick est un mauvais choix et préférer merge ou rebase.
Sommaire de la leçon

Fusionner une branche, c'est intégrer tout son travail. Mais il arrive qu'on ne veuille qu'un seul commit : un correctif urgent posé sur main qu'il faut aussi appliquer sur la version en production, un commit isolé d'une branche par ailleurs abandonnée, une amélioration à récupérer sans embarquer le reste. C'est exactement le rôle de git cherry-pick : « cueillir » une cerise précise sur une branche et la reposer sur la tienne.

Tu maîtrises déjà merge et rebase ; cette leçon ajoute l'outil chirurgical qui manque à ta panoplie. On verra comment il fonctionne, ses cas d'usage légitimes (surtout le backport), la gestion des conflits, et — tout aussi important — quand ne pas s'en servir.

Recopier un commit, pas fusionner une branche

Un cherry-pick prend la différence (le patch) introduite par un commit et la rejoue sur ta branche courante. Le résultat est un nouveau commit : même modification, même message par défaut, mais un identifiant (SHA) différent, car son parent et sa date de commit ne sont plus les mêmes.

Le SHA affiché (9c1f0ab) n'est pas celui d'origine (4b8d2e1) : c'est bien un nouveau commit.

Le cas roi : backporter un correctif

Le scénario le plus fréquent est le backport. Le développement avance sur main, mais une version plus ancienne reste en production sur une branche release/1.x. Un bug critique est corrigé sur main par le commit a1b2c3d : il faut le porter sur la branche de maintenance sans y ramener les nouveautés de main.

Cas réel

Les grands projets qui maintiennent plusieurs versions en parallèle vivent de cherry-pick. Le noyau Linux, PostgreSQL ou un navigateur comme Chromium corrigent un bug sur la branche de développement, puis backportent le commit sur chaque version encore supportée (les LTS). Une faille de sécurité découverte sur la version 17 est ainsi cueillie et rejouée sur les 16, 15 et 14, à l'identique : même patch, un commit par branche. Sans cherry-pick, il faudrait refaire le correctif à la main sur chacune — source d'erreurs et d'oublis.

Quand ça coince : les conflits

Le commit d'origine a été écrit dans un certain contexte. Rejoué sur une autre branche où les lignes autour ont évolué, il peut entrer en conflit. Git s'arrête alors au milieu du cherry-pick et te laisse trancher, exactement comme pour un merge : tu édites les fichiers, tu les add, puis tu poursuis.

Les options qui comptent

Quelques drapeaux transforment cet outil brut en instrument précis :

  • -x ajoute au message une ligne « (cherry picked from commit …) ». Indispensable pour un backport : on garde la trace du commit d'origine.
  • -n / --no-commit applique les changements dans l'index sans committer. Pratique pour empiler plusieurs cerises et n'en faire qu'un commit, ou pour ajuster avant de valider.
  • -e ouvre l'éditeur pour retoucher le message.
  • -m <n> est requis pour cueillir un commit de fusion : il faut dire quel parent (généralement 1, la branche principale) sert de référence au diff.

Astuce

Prends l'habitude du -x pour tout backport. Six mois plus tard, en lisant l'historique de release/1.x, la mention « cherry picked from… » te dira d'où vient le correctif et t'évitera de le rejouer deux fois.

Quand NE PAS cherry-picker

cherry-pick duplique le changement : le même diff existe désormais sous deux identifiants. Ce n'est pas un problème pour un backport (les branches ne se rejoindront pas), mais c'est un piège si les deux branches doivent plus tard fusionner. Git est souvent capable de repérer un doublon (via le patch-id), mais pas toujours : tu peux te retrouver avec le commit en double ou des conflits inutiles.

Piège fréquent

N'utilise pas cherry-pick pour intégrer durablement une branche de fonctionnalité, commit par commit : tu recrées son travail sous de nouveaux SHA et tu sèmes des doublons. Pour intégrer une branche, c'est merge (ou rebase puis merge). Réserve cherry-pick aux transferts ponctuels : un hotfix à backporter, un commit isolé à récupérer d'une branche abandonnée.

Pièges fréquents

  • Oublier que A..D exclut A : le premier commit « manque ». Utilise A^..D pour l'inclure.
  • Backporter sans -x : tu perds la traçabilité et risques de re-cueillir le même commit plus tard.
  • cherry-pick un commit de merge sans -m : Git refuse, car il ne sait pas quel parent utiliser comme base du diff.
  • Confondre cherry-pick et merge : le premier copie un patch, le second relie deux historiques. Choisir le mauvais crée des doublons ou des conflits évitables.

Pour aller plus loin

Pour aller plus loin

Explore git rebase --onto, qui déplace toute une série de commits d'une base à une autre — un « cherry-pick de plage » plus puissant. Regarde aussi git cherry (sans tiret), qui liste les commits d'une branche pas encore présents (par contenu) sur une autre : parfait pour savoir ce qui reste à backporter. Enfin, les plateformes comme GitHub proposent des backports semi-automatiques via des étiquettes de pull request, qui déclenchent un cherry-pick sur les branches de version.

Glossaire

cherry-pick
Opération qui rejoue la modification d'un commit précis sur la branche courante, créant un nouveau commit au contenu identique mais au SHA différent.
Backport
Report d'un correctif d'une branche récente vers une branche plus ancienne (souvent une version encore maintenue), typiquement par cherry-pick.
Patch
La différence (le diff) introduite par un commit : c'est elle que cherry-pick applique, pas le commit lui-même.
Plage de révisions
Notation debut..fin désignant un ensemble de commits ; la borne de gauche est exclue (d'où A^..D pour inclure A).
patch-id
Empreinte du contenu d'un changement, indépendante du SHA ; elle aide Git à reconnaître qu'un commit dupliqué par cherry-pick est « le même » lors d'une fusion ultérieure.
-x
Option qui inscrit dans le message la ligne « (cherry picked from commit …) », conservant la trace du commit d'origine.
--no-commit (-n)
Applique le changement dans l'index sans créer de commit, pour regrouper plusieurs cerises ou ajuster avant de valider.

Récap et vérification

  • cherry-pick recopie le patch d'un commit sur la branche courante : même changement, nouveau SHA.
  • Son usage roi est le backport : porter un correctif sur une branche de version sans y ramener le reste.
  • Une plage A..D exclut A ; écris A^..D pour l'inclure.
  • En cas de conflit : éditer → git add → --continue, ou --abort pour tout annuler.
  • -x trace l'origine, -n applique sans committer, -m gère les commits de fusion.
  • Pour intégrer une branche, préfère merge/rebase : cherry-pick duplique et sème des doublons.
