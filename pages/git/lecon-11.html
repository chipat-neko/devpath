Module 03 · Collaborer avec GitHub — Leçon 11

Forks et contribution open source

~32 min Intermédiaire Leçon 10 recommandée

À la fin de cette leçon, tu sauras

  • savoir forker un dépôt et dérouler le flux fork → clone → branche → push → pull request ;
  • savoir distinguer les remotes origin (ton fork) et upstream (le dépôt d'origine) ;
  • savoir synchroniser son fork avec git fetch upstream puis merge ou rebase ;
  • savoir appliquer les bonnes pratiques open source (CONTRIBUTING.md, PR ciblée, cycle de revue).
Sommaire de la leçon

Jusqu'ici, tu as poussé du code sur tes dépôts, ceux où tu as le droit d'écrire. Mais l'open source, c'est surtout corriger un bug ou ajouter une fonctionnalité à un projet qui n'est pas le tien — un projet dont tu n'es ni propriétaire ni collaborateur. Tu ne peux donc pas git push dessus directement. La solution standard de GitHub s'appelle le fork : tu travailles sur ta propre copie, puis tu proposes tes modifications à l'équipe d'origine.

Dans cette leçon, tu vas voir le flux complet « fork → clone → branche → push → pull request », comment garder ta copie à jour avec le projet original grâce au remote upstream, et les bonnes pratiques qui font qu'une contribution est acceptée plutôt qu'ignorée.

Le fork : ta copie personnelle

Un fork est une copie complète d'un dépôt, placée sur ton compte GitHub. Tu la crées en un clic depuis l'interface web, avec le bouton « Fork » en haut de la page du projet. Tu obtiens alors un nouveau dépôt à toi, par exemple toncompte/super-projet, qui part du contenu de projet-officiel/super-projet.

Sur ce fork, tu as tous les droits : tu peux pousser des branches, expérimenter, casser des choses. Le dépôt d'origine, lui, reste intact : tes changements n'y arrivent que si les mainteneurs acceptent ta proposition. Retiens cette distinction de vocabulaire :

  • origin : ton fork, le dépôt que tu clones et sur lequel tu pousses.
  • upstream : le dépôt d'origine, la « source de vérité » que tu ne peux que lire.

Note

Forker n'est pas la même chose que cloner. Forker crée une copie distante sur GitHub (côté serveur). Cloner télécharge un dépôt distant sur ton ordinateur (côté local). Pour contribuer, tu fais les deux : tu forkes, puis tu clones ton fork.

Astuce

Avec le CLI officiel de GitHub, forker et cloner tient en une seule commande : gh repo fork projet-officiel/super-projet --clone. Elle crée ton fork, le clone en local et configure même le remote upstream automatiquement.

Brancher, committer, pousser sur ton fork

Avant de coder, crée une branche dédiée à ta contribution. On ne travaille jamais directement sur main (on verra pourquoi dans les pièges). Donne-lui un nom parlant : fix-typo-readme, feat-export-csv…

Il ne reste plus qu'à ouvrir la pull request. Sur la page de ton fork, GitHub propose un bouton « Compare & pull request ». Vérifie bien la cible : la base doit être projet-officiel/super-projet (branche main), la source ta branche toncompte:fix-typo-readme. Donne un titre clair, décris ce que tu changes et pourquoi, puis crée la PR.

Le remote upstream : rester synchronisé

Ton fork est une photo prise à l'instant du clic « Fork ». Pendant que tu travailles, le projet d'origine continue d'avancer : d'autres PR sont fusionnées. Si tu ne fais rien, ton fork prend du retard et tes futures branches partiront d'une base périmée. Pour suivre l'original, tu ajoutes un second remote nommé upstream.

Note

git merge upstream/main crée un historique fidèle mais parfois encombré de commits de fusion. Beaucoup de projets préfèrent un historique linéaire : dans ce cas on utilise git rebase upstream/main, qui rejoue tes commits par-dessus la dernière version d'origine. On y revient plus bas.

Astuce

Pas de terminal sous la main ? La page de ton fork sur GitHub affiche un bouton « Sync fork » qui remet ta branche main au niveau d'upstream en un clic. Pratique pour un rattrapage rapide ; pour intégrer ces changements dans une branche de travail, reste toutefois git fetch + merge/rebase en local.

Les bonnes pratiques open source

Une contribution acceptée n'est pas qu'une question de code : c'est aussi du savoir-vivre dans un projet collectif. Avant même de coder :

  • Lis le CONTRIBUTING.md à la racine du dépôt : il décrit le processus attendu (style, tests, format des messages de commit, étapes de validation).
  • Lis le CODE_OF_CONDUCT.md : le code de conduite fixe les règles de courtoisie de la communauté.
  • Discute d'abord dans une issue. Pour une fonctionnalité ou un gros changement, ouvre une issue et demande l'avis des mainteneurs avant d'écrire 500 lignes qui seront peut-être refusées.
  • Respecte le style du projet : conventions de nommage, formatage, outils de lint. Lance les vérifications indiquées par le projet avant de pousser.
  • Garde une PR ciblée : une PR = un sujet. Ne mélange pas une correction de bug, un renommage massif et une nouvelle feature dans la même proposition : c'est impossible à relire.

Le cycle de revue avec les mainteneurs

Une fois la PR ouverte, le travail n'est pas fini : commence la revue de code. Un ou plusieurs mainteneurs lisent ton diff, lancent l'intégration continue (CI) et laissent des commentaires. Tu n'as pas besoin de recréer une PR pour répondre : tu corriges sur ta branche locale, et chaque nouveau push met automatiquement la PR à jour.

Reste poli et réactif : réponds aux commentaires, explique tes choix, accepte les demandes raisonnables. Quand tout est vert et que les mainteneurs sont satisfaits, ils fusionnent ta PR. Tes commits entrent alors officiellement dans le projet : ta première contribution open source est en ligne. Tu peux ensuite supprimer ta branche, locale et distante.

Cas réel

Des projets comme VS Code, Homebrew ou DefinitelyTyped reçoivent chaque semaine des centaines de PR, dont beaucoup de premières contributions. Le dépôt d'entraînement first-contributions sur GitHub, forké des dizaines de milliers de fois, existe uniquement pour répéter ce flux : forker, ajouter son nom, ouvrir une PR. C'est exactement le parcours de cette leçon, grandeur nature — et une PR fusionnée là-bas est une vraie ligne dans ton historique GitHub.

Pièges fréquents

Piège fréquent

Travailler directement sur le main de ton fork. Si tu committes sur main, tu ne peux plus le synchroniser proprement avec upstream/main (il a divergé), et ta PR mélange ton travail avec l'historique de la branche principale. Crée toujours une branche dédiée avec git switch -c <branche> et garde main comme miroir propre de l'upstream.

  • Fork qui diverge sans synchroniser. Tu forkes, tu ne touches plus à upstream pendant des semaines, et ta branche part d'un état périmé : ta PR provoque des conflits inutiles. Fais git fetch upstream régulièrement.
  • PR qui ignore les conventions du projet. Mauvais format de commit, lint en échec, tests cassés : la CI passe au rouge et les mainteneurs t'écartent. Lance les vérifications du projet avant de pousser.
  • Ne pas lire CONTRIBUTING.md. Tu réinventes un processus que le projet a déjà documenté ; ta PR se fait refermer avec un « merci de suivre le guide de contribution ».

Pour aller plus loin

Pour aller plus loin

Pour synchroniser ta branche tout en gardant un historique linéaire, beaucoup de projets recommandent git pull upstream main --rebase. Cherche les issues étiquetées « good first issue » pour débuter en douceur. Découvre la signature des commits avec GPG (badge « Verified » sur GitHub) que certains projets exigent, et les GitHub Discussions pour poser des questions hors du suivi de bugs.

Glossaire

Fork
Copie complète d'un dépôt placée sur ton compte GitHub (côté serveur), pour contribuer à un projet sur lequel tu n'as pas le droit d'écrire.
origin
Le remote qui pointe vers ton fork : le dépôt que tu clones et sur lequel tu pousses tes branches.
upstream
Le remote qui pointe vers le dépôt d'origine (la source) : tu le lis pour te synchroniser, mais tu n'y pousses pas.
Pull request (PR)
Demande de fusionner ta branche (depuis ton fork) dans le dépôt d'origine, assortie d'une revue et d'une discussion avant l'intégration.
Synchroniser un fork
Ramener dans ton fork les commits ajoutés à l'original : git fetch upstream puis git merge (ou rebase) upstream/main.
CONTRIBUTING.md
Fichier à la racine d'un projet décrivant le processus de contribution attendu : style, tests, format des commits, étapes de validation.
good first issue
Étiquette posée par les mainteneurs sur des tickets faciles, réservés aux nouveaux venus pour une première contribution en douceur.

Récap et vérification

  • Un fork est une copie d'un dépôt sur ton compte, pour contribuer sans droit d'écriture sur l'original.
  • Flux : fork → clone de ton fork → branche dédiée → commit → push sur ton fork (origin) → PR vers le dépôt d'origine.
  • origin = ton fork (lecture/écriture) ; upstream = le dépôt d'origine (lecture).
  • Tu synchronises avec git fetch upstream puis git merge upstream/main (ou rebase).
  • Lis CONTRIBUTING.md et le code de conduite ; garde une PR ciblée ; réponds aux revues en repoussant sur la même branche.

Voir une solution

Trois bonnes pratiques (parmi d'autres) :

  • Lire le CONTRIBUTING.md — pour suivre le processus exact attendu (style, tests, format des commits) et éviter un refus immédiat.
  • Synchroniser avec upstream (git fetch upstream + merge/rebase) — pour partir de la dernière version et éviter des conflits inutiles.
  • Garder la PR ciblée sur un seul sujet — pour qu'elle soit facile à relire et donc plus vite acceptée.

On peut ajouter : discuter dans une issue avant un gros changement, lancer les tests/lint en local, et travailler sur une branche dédiée plutôt que sur main.
