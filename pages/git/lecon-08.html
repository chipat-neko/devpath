Module 03 · Collaborer avec GitHub — Leçon 08

Les dépôts distants

~33 min Débutant Module 2 recommandé

À la fin de cette leçon, tu sauras

  • lier un dépôt local à un dépôt distant avec git remote add origin et le vérifier ;
  • récupérer un projet existant avec git clone et envoyer tes commits avec git push -u origin main ;
  • distinguer git fetch (télécharge) de git pull (télécharge et fusionne) ;
  • lire les branches de suivi (origin/main) et comprendre « en avance »/« en retard ».
Sommaire de la leçon

Jusqu'ici, ton dépôt vit entièrement sur ta machine : tout ton historique tient dans le dossier caché .git. C'est solide, mais fragile à une chose près : si ton disque dur lâche, tout disparaît. Et tant que ton code reste chez toi, personne ne peut collaborer avec toi. Cette leçon ajoute la pièce manquante : un dépôt distant, une copie de ton projet hébergée ailleurs (sur GitHub, GitLab, ou un autre serveur).

Tu vas apprendre à lier ton dépôt local à un dépôt distant, à récupérer un projet existant, puis à synchroniser les deux dans les deux sens : envoyer tes commits (push) et récupérer ceux des autres (fetch et pull). C'est le cœur du travail à plusieurs.

Ce qu'est un dépôt distant (remote)

Un remote est simplement une copie de ton dépôt hébergée à une autre adresse que ta machine. Le local et le distant partagent le même historique de commits ; ils se synchronisent en s'échangeant les commits qui manquent à l'un ou à l'autre.

Un dépôt peut connaître plusieurs remotes, chacun désigné par un nom court. Par convention, le remote principal s'appelle origin : c'est juste un alias pratique pour une URL, pour ne pas la retaper à chaque commande. Quand tu écris git push origin main, tu dis « envoie la branche main vers le remote nommé origin ».

Note

origin n'a rien de magique : c'est un nom comme un autre, choisi par défaut. Tu pourrais l'appeler github ou serveur. Mais tout l'écosystème utilise origin, alors garde-le pour ne pas te perdre.

Lier un dépôt local à un remote

Si tu as créé ton dépôt en local avec git init, il ne connaît encore aucun remote. Tu en ajoutes un avec git remote add, en lui donnant un nom (origin) et une URL (celle que GitHub t'affiche après avoir créé un dépôt vide sur le site).

On lie d'abord le dépôt, puis on vérifie tout de suite ce que Git a enregistré.

Cloner un dépôt existant

Le cas précédent (init puis remote add) sert quand tu pars d'un dossier local. Mais le plus souvent, le projet existe déjà sur GitHub et tu veux en récupérer une copie. C'est le rôle de git clone.

En une commande, git clone fait beaucoup : il télécharge tout l'historique (pas seulement la dernière version), crée le dossier, et configure automatiquement le remote origin vers l'URL d'où tu viens. Tu n'as donc pas à faire git remote add après un clone : c'est déjà fait.

Astuce

Juste après un clone, lance git remote -v pour confirmer que origin pointe bien là où tu crois. C'est un réflexe utile quand tu jongles avec plusieurs forks d'un même projet.

Envoyer ses commits : git push

Tes commits restent locaux tant que tu ne les pousses pas. La commande git push envoie au remote les commits qu'il n'a pas encore. Pour le tout premier envoi d'une branche, il faut établir le suivi entre ta branche locale et la branche distante, avec l'option -u (raccourci de --set-upstream).

Grâce au -u du premier push, Git mémorise que ta main locale « suit » origin/main. Ensuite, git push et git pull tout courts savent sur quelle branche distante agir, sans que tu aies à le répéter.

Récupérer : git fetch contre git pull

Quand un collègue pousse du travail, ton dépôt local ne le voit pas par magie : tu dois le récupérer. Deux commandes existent, et la confusion entre elles est la source de bien des surprises.

  • git fetch télécharge les nouveaux commits du remote, mais ne touche pas à tes fichiers de travail. Il met seulement à jour ta connaissance du distant (les branches de suivi comme origin/main). Rien ne change dans ton dossier ; tu peux d'abord regarder.
  • git pull fait deux choses d'affilée : un fetch, puis un merge qui fusionne les commits récupérés dans ta branche courante. Tes fichiers sont mis à jour immédiatement.

Autrement dit : git pull ≈ git fetch suivi de git merge. Le fetch est l'option prudente (je regarde avant d'intégrer) ; le pull est l'option rapide (j'intègre tout de suite).

Les branches de suivi : origin/main

Après un fetch, Git met à jour des branches spéciales en lecture seule appelées branches de suivi, nommées origin/<branche>. origin/main est la photo de « où en était main sur le remote la dernière fois que je l'ai contacté ». Elle ne bouge que lors d'un fetch, pull ou push.

En comparant ta main locale à origin/main, Git te dit si tu es en avance (ahead, tu as des commits non poussés) ou en retard (behind, le remote a des commits que tu n'as pas). C'est ce que résume git status :

HTTPS ou SSH : deux façons de s'authentifier

Les URL de remote existent sous deux formes, et tu choisis l'une ou l'autre selon ta méthode d'authentification (le remote vérifie que tu as le droit de pousser).

Les deux donnent accès au même dépôt ; seule la poignée de main diffère. HTTPS est le plus simple pour démarrer : GitHub te demande un identifiant, en pratique un jeton d'accès personnel (les mots de passe de compte ne sont plus acceptés pour Git). SSH repose sur une paire de clés à configurer une fois, puis ne te redemande plus rien. On détaillera l'authentification dans la leçon suivante.

Cas réel — le mot de passe HTTPS qui ne marche plus

Tu fais ton premier git push en HTTPS, GitHub demande un mot de passe, tu tapes celui de ton compte… et il est refusé. Ce n'est pas une erreur de ta part : depuis août 2021, GitHub n'accepte plus le mot de passe du compte pour Git. Il faut créer un jeton d'accès personnel (Personal Access Token, dans les réglages du compte) et le coller à la place du mot de passe — ou bien passer en SSH une bonne fois. C'est le blocage n°1 des débutants sur GitHub.

Pièges fréquents

  • Confondre fetch et pull. git fetch télécharge sans rien changer à tes fichiers ; git pull télécharge et fusionne. Si tu t'étonnes que ton dossier n'ait pas changé après un fetch, c'est normal : il manquait le merge (ou un pull).
  • Push refusé car le distant a de l'avance. Si quelqu'un a poussé avant toi, Git rejette ton push (! [rejected], message fetch first). Fais d'abord git pull pour intégrer ses commits, résous un éventuel conflit, puis repousse.
  • Oublier -u au premier push. Sans lui, le suivi n'est pas établi ; un simple git push ensuite se plaindra de ne pas savoir où envoyer. Le premier push d'une branche prend git push -u origin <branche>.
  • Pousser sur la mauvaise branche. Vérifie sur quelle branche tu es avec git status avant de pousser. Envoyer du travail sur main alors qu'il devait aller sur une branche de fonctionnalité crée du désordre pour toute l'équipe.

Pour aller plus loin

Quelques pistes une fois la synchronisation de base acquise :

  • Changer l'URL d'un remote sans le recréer, par exemple pour passer de HTTPS à SSH : git remote set-url origin git@github.com:ton-pseudo/mon-projet.git.
  • Plusieurs remotes. Sur un projet forké, on garde souvent origin (ton fork) et un second remote upstream (le dépôt d'origine) pour récupérer les mises à jour : git remote add upstream <url>.
  • Un historique plus net en récupérant. git pull --rebase rejoue tes commits locaux au-dessus des commits récupérés au lieu de créer un commit de fusion. On y reviendra avec les branches.

Pour aller plus loin

L'authentification (jetons d'accès personnels côté HTTPS, clés côté SSH) mérite sa propre leçon : c'est l'étape qui débloque réellement git push vers GitHub. C'est précisément le sujet de la leçon suivante.

Antisèche : dépôts distants

Le mémo des commandes pour lier, cloner et synchroniser avec un remote.

Glossaire

Dépôt distant (remote)
Copie de ton dépôt hébergée à une autre adresse (GitHub, GitLab…), avec laquelle le local se synchronise.
origin
Nom court (alias) conventionnel du remote principal ; il désigne une URL pour ne pas la retaper.
git clone
Télécharge tout l'historique d'un dépôt distant, crée le dossier et configure origin automatiquement.
git push
Envoie au remote les commits qu'il n'a pas encore ; le premier push d'une branche prend -u pour établir le suivi.
git fetch
Télécharge les nouveaux commits distants sans toucher à tes fichiers ; met seulement à jour les branches de suivi.
git pull
Enchaîne git fetch puis git merge : met à jour ta branche courante et ton répertoire de travail.
Branche de suivi (origin/main)
Photo locale, en lecture seule, de l'état d'une branche distante au dernier contact (fetch/pull/push).
Suivi (upstream)
Lien entre une branche locale et sa branche distante ; établi par git push -u, il permet ensuite git push/git pull sans arguments.

Récap et vérification

  • Un remote est une copie distante de ton dépôt ; le remote principal s'appelle par convention origin.
  • git remote add origin <url> lie un dépôt local ; git clone <url> récupère un projet existant et configure origin tout seul.
  • git push -u origin main envoie tes commits et établit le suivi ; ensuite un simple git push suffit.
  • git fetch télécharge sans fusionner ; git pull fait fetch puis merge.
  • Les branches de suivi (origin/main) indiquent si tu es en avance ou en retard sur le distant.

Vérifie ta compréhension

  1. Que configure automatiquement git clone que tu devrais faire à la main après un git init ?
  2. Pourquoi le premier push d'une branche s'écrit-il git push -u origin main plutôt que git push ?
  3. Quelle différence concrète y a-t-il entre git fetch et git pull du point de vue de tes fichiers ?
