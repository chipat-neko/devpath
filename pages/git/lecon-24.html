Module 07 · Pour aller plus loin — Leçon 24

Projet : prendre en main et assainir un dépôt inconnu

~40 min Avancé Capstone du cours

À la fin de cette leçon, tu sauras

  • explorer un dépôt inconnu en lecture seule avant d'y toucher ;
  • cartographier son historique et sa structure avec les bons outils ;
  • l'assainir sans casser : identité, .gitignore, gros fichiers, secrets, branches mortes ;
  • réunir en un scénario les réflexes de tout le cours.
Sommaire de la leçon

Un jour ou l'autre, tu hérites d'un dépôt que tu n'as pas écrit : un nouveau poste, un projet repris à une équipe partie, un logiciel legacy sans documentation. La tentation est de plonger et de coder tout de suite. Le réflexe professionnel est l'inverse : comprendre avant de modifier. Git contient déjà l'essentiel de ce qu'il faut savoir — qui travaille dessus, comment il est structuré, ce qui cloche.

Ce capstone réunit les outils du cours en une démarche : on explore (sans rien changer), on cartographie, puis on assainit avec prudence. C'est exactement ce qu'on fait le premier jour sur une base de code inconnue.

Explorer avant de toucher

Toutes les commandes de cette première phase sont en lecture seule : aucune ne modifie le dépôt. On prend la température avant de sortir la clé à molette.

En quelques commandes, on sait déjà beaucoup : le projet est-il actif ou dormant, combien de personnes le portent, existe-t-il des versions étiquetées, y a-t-il des branches abandonnées ?

Cartographier : la bonne question, le bon outil

Prendre en main, c'est répondre à des questions précises. Chaque question a son outil, tous vus dans ce cours : on les mobilise ici ensemble.

Assainir sans casser

Maintenant seulement on agit — prudemment, sur une branche, un correctif à la fois. L'assainissement typique d'un dépôt négligé tient en une checklist.

Piège fréquent

git rm --cached retire le fichier du suivi mais le garde sur ton disque ; git rm tout court le supprime aussi. Sur un dépôt inconnu, la nuance est vitale : tu veux dé-suivre node_modules/, pas l'effacer. Et si tu découvres un secret dans l'historique, l'ignorer ne suffit pas : il faut le révoquer puis le purger (leçon 19).

Cas réel

Une développeuse reprend un service legacy dont l'auteur est parti, sans la moindre documentation. Plutôt que deviner, elle interroge le dépôt : git shortlog -sn révèle que 90 % du code vient d'une seule personne ; git log -1 montre que rien n'a bougé depuis quatorze mois ; git count-objects -vH affiche 800 Mo — des exports de base de données commités par erreur, qu'un .gitignore aurait dû arrêter. Une pioche git log -S"password" déterre même un mot de passe en clair dans un vieux commit : révoqué le jour même. En une matinée d'exploration en lecture seule, elle a compris le projet et dressé la liste des dettes à rembourser — sans avoir écrit une ligne de code.

Astuce

Termine par la documentation : un README qui explique comment lancer le projet, et un CONTRIBUTING.md qui fixe les conventions de commits et de branches. Ce que tu viens de reconstituer à la main, le prochain arrivant le lira en cinq minutes.

Antisèche

Glossaire

Prise en main (onboarding)
Phase d'appropriation d'un projet inconnu : comprendre son historique, sa structure et son état avant d'y contribuer.
Legacy (code hérité)
Base de code ancienne, souvent sans documentation ni auteur disponible, qu'on doit reprendre et maintenir.
Lecture seule
Ensemble des commandes d'inspection (log, blame, shortlog, count-objects) qui ne modifient pas le dépôt : sûres à lancer d'emblée.
git shortlog -sn
Résumé des contributions par auteur, trié par nombre de commits (-s compte, -n ordonne) : qui porte le projet.
git count-objects -vH
Indique la taille de la base d'objets Git en unités lisibles ; un size-pack énorme trahit de gros binaires dans l'historique.
git rm --cached
Retire un fichier du suivi Git tout en le conservant sur le disque : sert à dé-versionner ce qu'un .gitignore aurait dû exclure.
Branche morte
Branche déjà fusionnée (ou abandonnée) qui encombre le dépôt ; git branch --merged les liste, -d les supprime sans risque.
Assainir
Remettre un dépôt en état : identité, ignorés, gros fichiers, secrets, branches — par petits changements réversibles, pas d'un bloc.

Récap et vérification

  • Sur un dépôt inconnu, on explore d'abord en lecture seule : log --graph, shortlog -sn, count-objects.
  • Chaque question a son outil : blame/shortlog (qui), bisect (quel bug), la pioche -S (quel code), count-objects (le poids).
  • On assainit ensuite, prudemment : identité, .gitignore + rm --cached, LFS, branches mortes.
  • Un secret découvert se traite en priorité : révocation immédiate, puis purge de l'historique.
  • On finit en documentant (README, CONTRIBUTING.md) pour le prochain qui reprendra le projet.

Vérifie ta compréhension

  1. Pourquoi commencer par des commandes en lecture seule avant de modifier quoi que ce soit ?
  2. Quelle commande révèle vite qui porte le projet ?
  3. Le dépôt pèse 800 Mo : quelle commande le confirme, et quelle en est la cause probable ?
  4. Quelle est la différence entre git rm --cached fichier et git rm fichier ?

Mini-projet fil rouge — le cycle complet d'une fonctionnalité

Pour clore ce cours, déroulons le cycle de vie complet d'une fonctionnalité avec Git. Il réunit l'initialisation, une branche dédiée, des commits, une fusion, un tag de version et la publication — le flux de travail réuni en une séquence.

Ce que tu vas construire

La suite de commandes qui mène d'un dossier vide à une v1.0.0 publiée : init, branche de fonctionnalité, fusion sur main, étiquetage et push.

Étapes

Démarrer

git init, puis un premier git add / git commit.

Une branche de fonctionnalité

Crée et bascule avec git switch -c feature/connexion, puis committe ton travail.

Fusionner

Reviens sur main et fusionne avec git merge --no-ff (garde la trace de la branche).

Étiqueter et nettoyer

Pose un tag annoté git tag -a v1.0.0 et supprime la branche fusionnée.

Publier

git push origin main --tags.

ProjetFil rouge

Assemble les étapes en une séquence complète. Essaie d'abord par toi-même, puis compare avec la solution de référence.
