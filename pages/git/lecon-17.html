Module 06 · Collaboration et automatisation — Leçon 17

Stratégies de branches et revue de code

~34 min Intermédiaire Cours Git recommandé

À la fin de cette leçon, tu sauras

  • comparer Git Flow, GitHub Flow et Trunk-Based Development et choisir selon le contexte ;
  • configurer la protection de main (PR obligatoire, revues, checks, CODEOWNERS) ;
  • rédiger et reviewer une pull request et choisir une stratégie de merge (merge, squash, rebase) ;
  • appliquer les Conventional Commits et le SemVer pour versionner et publier des releases.
Sommaire de la leçon

Tu sais déjà créer des branches, fusionner, ouvrir une pull request et rebaser. Cette leçon change d'échelle : il ne s'agit plus de savoir manipuler une branche, mais de décider comment toute une équipe organise ses branches, protège son code de production et fait circuler les changements sans se marcher dessus. C'est moins une affaire de commandes que de conventions partagées : un modèle de branches mal choisi ou une main non protégée coûtent bien plus cher qu'une commande mal tapée.

On va parcourir les trois grands modèles de branches, la protection de main sur GitHub, l'anatomie d'une bonne PR et de sa revue, puis les conventions de commits, de versions et de releases qui rendent l'historique exploitable par des humains et par des outils.

Trois modèles de branches

Un modèle de branches (branching model) répond à une question : où vit le code stable, où vit le code en cours, et comment l'un devient l'autre. Trois familles dominent.

Git Flow repose sur deux branches longues — main (ce qui est en production) et develop (l'intégration en cours) — autour desquelles gravitent des branches feature/*, release/* et hotfix/*. Structuré et explicite, mais lourd : beaucoup de branches, beaucoup de merges, peu adapté à la livraison continue.

GitHub Flow simplifie radicalement : une seule branche longue, main, toujours déployable. Chaque travail part d'une branche courte, passe par une PR, est reviewé, puis fusionné dans main. C'est le modèle par défaut pour le web et la livraison continue.

Trunk-Based Development pousse l'idée plus loin : des branches très courtes (souvent moins d'un jour), intégrées plusieurs fois par jour directement sur le trunk (main). Le code non terminé est masqué par des feature flags plutôt que de vivre longtemps sur une branche. C'est exigeant en outillage (tests automatisés solides) mais ça supprime l'enfer du merge.

Note

Quand choisir quoi ? Git Flow convient aux logiciels versionnés avec releases planifiées et plusieurs versions maintenues en parallèle. GitHub Flow est le bon défaut pour un service web déployé en continu. Trunk-Based vise les équipes matures qui déploient plusieurs fois par jour. En cas de doute, commence par GitHub Flow.

Protéger main sur GitHub

Quel que soit le modèle, une règle ne se négocie pas : personne ne pousse directement sur main. Tu l'imposes avec une branch protection rule (ou un ruleset) dans Settings > Branches. Une règle solide combine :

  • Require a pull request before merging — tout passe par une PR, jamais de push direct.
  • Require approvals — au moins une revue approuvée (souvent deux sur du code sensible).
  • Require status checks to pass — la CI (tests, lint) doit être verte avant le merge.
  • Require branches to be up to date — la branche doit être à jour avec main avant fusion.
  • Require conversation resolution — tous les commentaires de revue doivent être résolus.
  • Do not allow bypassing the above settings — la règle s'applique aussi aux admins, sinon elle est cosmétique.

Le fichier CODEOWNERS désigne automatiquement les reviewers selon les chemins modifiés. Place-le à la racine, dans .github/ ou docs/.

Couplé à « Require review from Code Owners », un changement dans src/paiement/ ne peut pas être mergé sans l'aval de l'équipe paiement.

Astuce

Tu peux versionner ces réglages avec le CLI GitHub plutôt que de cliquer. Par exemple : gh api repos/:owner/:repo/branches/main/protection pour lire la protection en place, ou la définir via un ruleset en JSON commité dans le dépôt.

Cas réel

Dans une petite équipe où tout le monde poussait directement sur main, un développeur rebase sa copie locale puis lance git push --force un vendredi soir : il écrase sans le voir deux jours de commits d'une collègue, déjà partis en production. Personne ne s'en aperçoit avant le lundi ; la reconstruction se fait au git reflog, dans la douleur. Le correctif tient en une case cochée : activer la protection de main (PR obligatoire, push forcé interdit) aurait rendu la manœuvre tout bonnement impossible.

Anatomie d'une bonne pull request

Une PR n'est pas un dépotoir de commits : c'est une unité de revue. Les meilleures sont petites (idéalement moins de 400 lignes modifiées), focalisées sur un seul objectif, bien décrites et liées à une issue. Un mot-clé dans la description ferme l'issue automatiquement au merge.

La revue a trois leviers : commenter (poser une question, signaler un risque), suggérer (proposer un diff que l'auteur applique en un clic) et approuver ou demander des changements. Une suggestion s'écrit directement dans la conversation de la PR :

Au merge, GitHub propose trois stratégies :

  • Merge commit — conserve tous les commits de la branche plus un commit de fusion. Historique complet mais touffu.
  • Squash and merge — écrase la branche en un seul commit sur main. Historique linéaire et lisible ; idéal quand les commits intermédiaires sont du bruit.
  • Rebase and merge — rejoue les commits sur main sans commit de fusion. Linéaire, mais garde chaque commit.

Note

Le squash est le défaut le plus sûr pour la plupart des équipes : chaque PR devient un commit propre sur main, et le titre de la PR devient le message — d'où l'intérêt de soigner ce titre.

Conventional Commits et SemVer

Des messages cohérents transforment l'historique en source de vérité automatisable. La convention Conventional Commits impose un préfixe : <type>(<portée>): <description>.

Ces types se mappent sur le Semantic Versioning (MAJEUR.MINEUR.CORRECTIF) : un fix incrémente le CORRECTIF (1.4.0 → 1.4.1), un feat incrémente le MINEUR (1.4.1 → 1.5.0), et tout changement cassant incrémente le MAJEUR (1.5.0 → 2.0.0). Comme les messages sont structurés, un outil peut générer le changelog tout seul.

Garder un historique lisible

Sur main, vise un historique qu'on peut lire à voix haute. Deux outils : le squash au merge (vu plus haut) et le rebase de mise à jour avant de demander la revue, pour repartir d'une main récente sans commit de fusion parasite.

Piège fréquent

Utilise toujours --force-with-lease et jamais --force brut pour repousser une branche rebasée. Le premier refuse d'écraser des commits que tu n'as pas vus ; le second les détruit silencieusement si un collègue a poussé entre-temps.

Tags et releases

Une release est un point figé et nommé de l'historique. On la matérialise par un tag annoté, qu'on pousse, puis on l'enrichit d'une GitHub Release (notes de version, binaires).

--generate-notes construit les notes à partir des PR mergées depuis le tag précédent — d'où l'importance de titres de PR clairs.

Pièges fréquents

Piège fréquent

Les branches de fonctionnalité trop longues sont l'erreur n°1. Plus une branche vit longtemps, plus elle diverge de main, et plus le merge devient un cauchemar de conflits. La parade : découper en petites PR et intégrer souvent. Une fonctionnalité non terminée se cache derrière un feature flag, elle ne reste pas en quarantaine sur une branche pendant trois semaines.

Les autres pièges classiques : pousser directement sur main (corrigé par la protection de branche) ; les PR énormes que personne ne peut reviewer sérieusement (on approuve sans lire) ; des messages de commit incohérents qui rendent l'historique illisible et le changelog impossible à générer ; merger sans revue ou laisser des commentaires non résolus ; et tout simplement ne pas protéger main, ce qui rend toutes les règles précédentes optionnelles.

Pour aller plus loin

Pour aller plus loin

Les feature flags (LaunchDarkly, Unleash) découplent déployer et activer, condition du trunk-based. Côté structure, le monorepo (plusieurs projets dans un dépôt) impose des workflows et des outils dédiés (Nx, Turborepo, builds ciblés sur les chemins changés). Pour automatiser versions et changelogs, regarde semantic-release et changesets. Enfin, les environnements de préproduction par PR (preview deployments) déploient chaque PR sur une URL jetable pour la tester avant merge.

Antisèche

Glossaire

Modèle de branches (branching model)
Convention d'équipe qui définit où vit le code stable, où vit le code en cours et comment l'un devient l'autre (Git Flow, GitHub Flow, Trunk-Based).
Trunk-Based Development
Modèle où l'on intègre plusieurs fois par jour sur une branche unique (le trunk) via des branches très courtes, l'inachevé étant masqué par des feature flags.
Feature flag
Interrupteur qui active ou désactive une fonctionnalité sans redéployer : il découple le fait de déployer le code et celui d'activer la fonctionnalité.
Branch protection rule
Règle GitHub qui verrouille une branche (souvent main) : PR obligatoire, revues, checks verts, interdiction du push forcé, non contournable.
CODEOWNERS
Fichier qui associe des chemins du dépôt à des propriétaires ; GitHub réclame alors automatiquement leur revue sur toute PR touchant ces chemins.
Conventional Commits
Convention de message type(portée): description (ex. feat, fix) qui rend l'historique lisible par des humains et des outils.
SemVer
Versionnage sémantique MAJEUR.MINEUR.CORRECTIF : un correctif monte le patch, une fonctionnalité le mineur, un changement cassant le majeur.
Squash and merge
Stratégie de fusion qui écrase tous les commits d'une PR en un seul commit sur la branche cible, pour un historique linéaire et lisible.

Récap et vérification

  • Modèles : Git Flow (structuré, releases planifiées), GitHub Flow (un défaut sain), Trunk-Based (intégration ultra-fréquente + feature flags).
  • Protéger main : PR obligatoire, revues, checks verts, branche à jour, CODEOWNERS, règle non contournable par les admins.
  • Bonne PR : petite, focalisée, décrite, liée à une issue ; merge en squash par défaut.
  • Conventions : Conventional Commits (feat:, fix:…) + SemVer (MAJEUR.MINEUR.CORRECTIF) pour automatiser changelog et releases.
  • Historique lisible : rebase de mise à jour, --force-with-lease, tags annotés + GitHub Releases.
