L'intégration continue avec GitHub Actions

~36 min Intermédiaire Leçon 17 recommandée

À la fin de cette leçon, tu sauras

  • savoir lire et écrire l'anatomie d'un workflow GitHub Actions (on, jobs, steps, runs-on) avec actions uses: et commandes run: ;
  • savoir construire une CI qui linte et teste sur une matrice de versions avec mise en cache des dépendances ;
  • savoir gérer les secrets, les variables et les environnements protégés sans jamais exposer de jeton ;
  • savoir mettre en place un déploiement continu conditionné à main et aux tests verts (needs:, if:).
Sommaire de la leçon

Tu sais déjà signer tes commits et installer des hooks Git locaux. Mais un hook local ne s'exécute que sur ta machine : rien n'empêche un collègue de pousser du code non testé. L'intégration continue (CI) déplace ces vérifications sur un serveur neutre qui s'exécute à chaque push et chaque pull request, pour toute l'équipe, sans rien à installer.

Dans cette leçon, tu vas écrire des workflows GitHub Actions qui installent, lintent, testent sur plusieurs versions, gèrent des secrets et déploient automatiquement quand main est vert. Tu verras aussi comment éviter les pièges classiques : CI lente, secrets en clair, déclenchements en boucle et coûts qui explosent.

Pourquoi la CI/CD : déplacer les hooks sur le serveur

Un hook pre-commit ou pre-push est utile mais contournable : il vit dans .git/hooks/, n'est pas versionné, et un git commit --no-verify le saute. La CI résout exactement ce problème : c'est un hook côté serveur, partagé, non contournable, qui fait autorité.

On distingue deux idées. L'intégration continue (CI) : à chaque proposition de code, on lance build, lint et tests pour détecter les régressions tôt. Le déploiement continu (CD) : dès que la branche principale est vérifiée, on livre automatiquement (un site, une image Docker, un binaire) sans intervention humaine.

Note

Les hooks locaux restent utiles pour un retour rapide (formater avant de commiter). La CI est le filet de sécurité : elle re-vérifie tout, indépendamment de la machine du contributeur. Les deux sont complémentaires, pas concurrents.

Anatomie d'un workflow GitHub Actions

Un workflow est un fichier YAML rangé dans .github/workflows/. GitHub le détecte automatiquement et l'exécute selon ses déclencheurs. La structure de base : un name, une clé on (les événements), et des jobs qui contiennent des steps.

Le workflow minimal : un job build sur Ubuntu qui exécute une seule commande.

Chaque job tourne dans sa propre machine virtuelle fraîche, isolée des autres. Les jobs sont parallèles par défaut ; les steps d'un même job sont séquentiels. Un step échoue dès qu'une commande renvoie un code de sortie non nul, et l'échec stoppe le job.

Actions réutilisables et commandes

Un step fait l'une de deux choses : exécuter une commande shell avec run:, ou réutiliser une action publiée avec uses:. Les actions sont des briques versionnées : actions/checkout récupère ton code, actions/setup-node installe Node.

checkout est presque toujours le premier step : sans lui, le runner est vide.

Piège fréquent

Utilise npm ci (à partir du package-lock.json) et non npm install en CI. ci est déterministe et échoue si le lockfile et le package.json divergent ; install peut silencieusement résoudre d'autres versions et masquer un bug.

Une CI concrète : matrice et cache

Tu veux souvent tester sur plusieurs versions du langage. La strategy.matrix démultiplie un job : une exécution par combinaison. Et pour ne pas réinstaller le monde à chaque fois, tu actives le cache des dépendances.

Trois jobs test tournent en parallèle : # test (18), # test (20), # test (22).

Le cache: 'npm' de setup-node calcule une clé à partir du package-lock.json : tant que le lockfile ne change pas, les dépendances sont restaurées en quelques secondes au lieu d'être retéléchargées. La syntaxe ${{ ... }} est l'interpolation d'expressions de GitHub Actions.

Secrets, variables et environnements protégés

Un workflow a besoin de jetons (clé de déploiement, token de registre). Ne les écris jamais en clair dans le YAML : il est versionné et lisible sur chaque fork. Stocke-les dans Settings → Secrets and variables, puis lis-les via le contexte secrets.

GitHub masque la valeur d'un secret dans les logs (elle apparaît comme ***).

Les variables (contexte vars) servent aux valeurs non sensibles (URL, nom d'environnement). Un environnement protégé comme production peut exiger une revue manuelle ou restreindre les branches autorisées avant qu'un job ne s'y exécute : c'est ta porte avant la mise en production.

Piège fréquent

Les secrets ne sont pas transmis aux workflows déclenchés par une PR venant d'un fork (avec pull_request). C'est volontaire : sinon un inconnu pourrait soumettre une PR qui exfiltre tes clés. Garde le déploiement (qui a besoin de secrets) sur push vers main, jamais sur les PR de forks.

Le déploiement continu : déployer quand main est vert

On combine maintenant CI et CD dans un même fichier : un job test à chaque PR, et un job deploy qui dépend du test (needs:) et ne tourne que sur main (if:). Le déploiement ne part donc jamais sans tests verts.

Sur une PR : seul test tourne. Sur un push vers main : test puis deploy.

Un artefact (upload-artifact) transporte des fichiers d'un job à l'autre ou les met à disposition au téléchargement. Pour déployer sur un serveur classique plutôt que Pages, tu remplacerais le job deploy par une connexion SSH :

La clé privée vient d'un secret ; rsync synchronise le build vers le serveur.

Bonnes pratiques d'une CI saine

Une CI utile est une CI à laquelle on fait confiance. Quatre principes :

  • Rapide : cache des dépendances, jobs parallèles, tests segmentés. Une CI de 30 minutes finit ignorée.
  • Déterministe : npm ci, versions épinglées, pas de dépendance au réseau extérieur dans les tests. Une CI qui « échoue parfois » (flaky) détruit la confiance.
  • Échouer tôt : lance le lint et les tests unitaires (rapides) avant les tests d'intégration (lents). Pas la peine de builder une image Docker si le lint est rouge.
  • Statuts requis : configure la protection de branche pour que la fusion sur main exige le job test au vert. La CI ne sert à rien si on peut fusionner par-dessus.

Astuce

Ajoute concurrency à ton workflow pour annuler une exécution obsolète quand un nouveau commit arrive sur la même PR : concurrency: { group: ${{ github.ref }}, cancel-in-progress: true }. Tu économises des minutes de runner et tu obtiens un retour sur le dernier état du code.

Cas réel

Sur un projet web réel, la CI mettait 22 minutes : le temps qu'elle finisse, l'équipe fusionnait déjà « puisque ça passait la dernière fois ». Des régressions arrivaient donc en production malgré une CI verte… mais ignorée. La reprise a tenu en trois gestes : activer cache: 'npm', lancer lint et tests unitaires avant le build et les tests d'intégration, et réduire la matrice aux seules versions qui comptent. Repassée sous 5 minutes, la CI est redevenue un vrai garde-fou qu'on attend avant de fusionner.

Pièges fréquents

  • Secret en clair dans le YAML. Tout token écrit en dur fuite : le fichier est dans l'historique, lisible sur chaque fork. Passe toujours par secrets.XXX.
  • CI lente faute de cache. Sans cache: 'npm' (ou équivalent), chaque exécution retélécharge tout. C'est le premier levier de vitesse.
  • Déployer sans tests verts. Un job de déploiement sans needs: test peut livrer du code cassé. Chaîne toujours deploy derrière la vérification.
  • Déclenchement en boucle. Un workflow qui pousse un commit (changelog, version) peut redéclencher on: push et tourner à l'infini. Filtre avec if, [skip ci] dans le message, ou des chemins exclus.
  • GITHUB_TOKEN trop permissif. Selon les réglages du dépôt, le token peut écrire par défaut. Mets permissions: contents: read au niveau global et n'élève les droits que dans le job qui en a besoin.
  • Matrice qui explose. Une matrice à 3 OS × 4 versions × 2 options = 24 jobs par push : ton quota de minutes fond. Limite les combinaisons, utilise include/exclude pour ne garder que celles qui comptent.

Pour aller plus loin

Pour aller plus loin

Factorise avec les workflows réutilisables (workflow_call) et les actions composites. Découvre les runners auto-hébergés pour du matériel spécifique, et les autres plateformes (GitLab CI, Jenkins). Côté sécurité, remplace les secrets cloud de longue durée par l'OIDC (jetons éphémères vers AWS/GCP/Azure), et épingle les actions par leur SHA de commit plutôt que par un tag mutable pour te protéger d'une action compromise.

Antisèche

Glossaire

Intégration continue (CI)
Pratique consistant à lancer automatiquement build, lint et tests à chaque push ou PR, sur un serveur neutre, pour détecter les régressions au plus tôt.
Déploiement continu (CD)
Prolongement de la CI : dès que la branche principale est vérifiée, la livraison (site, image, binaire) part automatiquement, sans intervention manuelle.
Workflow
Fichier YAML rangé dans .github/workflows/ qui décrit quand (on:) et quoi exécuter (jobs et steps).
Job
Ensemble de steps s'exécutant sur une même machine (runs-on). Les jobs tournent en parallèle par défaut ; on les ordonne avec needs:.
Step
Étape d'un job : soit une action réutilisable (uses:), soit une commande shell (run:). Les steps s'enchaînent en séquence.
Matrix (matrice)
Stratégie qui démultiplie un job en une exécution par combinaison de valeurs (versions, OS), lancées en parallèle.
Secret
Valeur sensible stockée par GitHub, injectée via secrets.XXX et masquée dans les logs ; non transmise aux PR issues de forks.
Artefact
Fichiers produits par un job (upload-artifact) et transmis à un autre job ou mis à disposition au téléchargement.

Récap et vérification

  • La CI est un hook côté serveur, partagé et non contournable : elle re-vérifie chaque PR.
  • Un workflow = name + on + jobs ; chaque job a un runs-on et des steps (uses: ou run:).
  • strategy.matrix démultiplie un job sur plusieurs versions ; cache accélère l'installation.
  • Les secrets se lisent via secrets.XXX, jamais en clair ; les environnements protègent la production.
  • Le CD chaîne deploy derrière test avec needs: et le restreint à main avec if:.
  • Vise rapide, déterministe, échouer tôt, et impose les statuts requis sur main.
