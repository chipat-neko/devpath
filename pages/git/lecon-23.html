Module 07 · Pour aller plus loin — Leçon 23

Échanger sans serveur : patch, bundle et archive

~35 min Avancé Leçon 09 recommandée

À la fin de cette leçon, tu sauras

  • transformer des commits en fichiers .patch avec git format-patch et les rejouer avec git am ;
  • distinguer git am (recrée le commit complet) de git apply (applique le seul diff) ;
  • empaqueter un dépôt entier ou un sous-ensemble dans un fichier .bundle transférable ;
  • exporter un instantané des fichiers, sans historique, avec git archive.
Sommaire de la leçon

Jusqu'ici, partager du code voulait dire pousser vers un serveur commun — git push vers origin sur GitHub, et chacun tire depuis là. Mais ce serveur central n'est pas toujours disponible. Comment contribuer à un projet qui n'accepte pas les pull requests ? Comment transférer un dépôt vers un réseau isolé, sans accès internet ? Comment livrer une version à quelqu'un qui n'a même pas Git ?

Git a été conçu, dès l'origine, pour fonctionner sans serveur : chaque clone est un dépôt complet. Cette leçon présente trois façons d'échanger de main à main, par simple fichier — un courriel, une clé USB, un partage réseau — sans jamais passer par un dépôt distant partagé : le patch (des commits par courriel), le bundle (un dépôt entier dans un fichier) et l'archive (un instantané des fichiers).

format-patch : des commits en fichiers

git format-patch transforme une série de commits en fichiers texte, un par commit. Chaque fichier est un courriel complet : en-tête From (l'auteur), date, ligne de sujet (le titre du commit), corps du message, puis le diff unifié. On indique quels commits emballer, en général une plage.

Pour une série de plusieurs patchs, l'option --cover-letter ajoute un fichier 0000-cover-letter.patch : une lettre d'accompagnement où résumer l'ensemble avant d'énumérer chaque changement.

Astuce

Quand tu renvoies une deuxième version d'une série après retours, ajoute -v2 : les sujets deviennent [PATCH v2 1/3]. Le relecteur voit tout de suite qu'il s'agit d'une révision, et non de doublons.

am : rejouer les patchs reçus

Côté destinataire, git am (« apply mailbox ») lit un ou plusieurs fichiers .patch et recrée les commits — avec l'auteur d'origine, sa date, son message. Le contributeur n'apparaît pas comme « toi qui appliques », mais bien comme l'auteur réel : la paternité est préservée.

Attention à ne pas confondre git am avec git apply. git apply se contente d'appliquer le diff au répertoire de travail : aucun commit n'est créé, l'auteur et le message sont perdus. C'est utile pour essayer un correctif, pas pour intégrer une contribution.

Piège fréquent

git apply fichier.patch modifie tes fichiers sans créer de commit et sans conserver l'auteur d'origine. Pour intégrer une contribution en gardant la paternité et le message, c'est git am qu'il faut. Retiens : apply pose le diff, am reconstruit le commit.

bundle : un dépôt dans un fichier

Un patch transporte des commits récents. Pour déplacer un dépôt entier — historique, branches, tags — vers un endroit sans réseau commun, on utilise git bundle. Il empaquette des objets Git et des références dans un seul fichier .bundle, qui se comporte ensuite comme un dépôt distant : on peut clone ou fetch depuis lui.

Le cas d'usage typique : un réseau isolé (air-gapped), sans connexion vers l'extérieur. On crée le bundle d'un côté, on le copie sur une clé USB, on l'importe de l'autre — tout l'historique traverse, alors qu'aucun git push n'aurait été possible.

Note

Un bundle est aussi une excellente sauvegarde hors-ligne : git bundle create sauvegarde.bundle --all tient tout le dépôt — historique compris — dans un unique fichier facile à archiver ou à chiffrer, contrairement à un dossier .git éclaté en milliers d'objets.

archive : un instantané sans historique

Parfois on ne veut pas partager l'historique : juste livrer les fichiers d'une version. git archive produit un .zip ou un .tar.gz du contenu d'un commit, d'une branche ou d'un tag — sans le dossier .git. C'est la commande pour empaqueter une release ou envoyer le code à quelqu'un qui n'utilise pas Git.

Comme l'archive part d'un commit, elle est reproductible : le même tag donne toujours exactement les mêmes fichiers, sans les éléments non suivis qui traînent dans ton répertoire de travail. L'option --prefix= évite le classique dossier qui « déballe en vrac » dans le répertoire courant.

Cas réel

Le développement du noyau Linux repose depuis 2005 sur l'échange de patchs par courriel : des milliers de contributeurs préparent leurs changements avec git format-patch, les envoient sur la liste de diffusion LKML avec git send-email, et les mainteneurs les intègrent avec git am. Il n'y a pas de « bouton Merge » : la revue se fait dans les réponses au courriel, et c'est précisément ce flux que Git a été créé pour servir. Git lui-même, PostgreSQL et bien d'autres projets fonctionnent ainsi. À l'inverse, pour transférer un dépôt vers un site classifié coupé d'internet, les équipes copient un .bundle sur support amovible : l'historique complet franchit la barrière réseau dans un seul fichier vérifiable.

Pièges fréquents

  • Confondre am et apply : apply pose le diff sans commit ni auteur ; am reconstruit le commit complet. Pour intégrer une contribution, c'est am.
  • Croire qu'une archive est un dépôt : git archive ne contient aucun historique ni dossier .git ; on ne peut ni clone ni fetch depuis un zip. Pour l'historique, c'est bundle.
  • Oublier la plage de format-patch : sans borne, il peut emballer bien plus de commits que prévu. Précise origin/main..HEAD ou -N.
  • Appliquer des patchs dans le désordre : la numérotation 0001, 0002… est là pour l'ordre. git am *.patch les prend triés ; ne les renomme pas.

Pour aller plus loin

Pour aller plus loin

Regarde git send-email (envoi direct via un serveur SMTP, la configuration sendemail.*) et git request-pull, qui génère un message résumant les commits à tirer depuis une URL publique — le « pull request » d'origine, par courriel. Explore aussi git apply --3way (fusion à trois points quand le patch ne s'applique pas net), git format-patch --stat pour joindre un résumé, et les forges décentralisées (git-appraise, SourceHut) bâties autour de ce flux. Enfin, git archive peut lire directement un dépôt distant avec --remote.

Antisèche

Glossaire

format-patch
Commande qui sérialise une plage de commits en fichiers .patch, un par commit, chacun au format courriel (auteur, date, sujet, diff).
git am
« Apply mailbox » : applique des fichiers .patch en recréant les commits, en préservant l'auteur et le message d'origine.
git apply
Applique le seul diff d'un patch au répertoire de travail, sans créer de commit ni conserver l'auteur.
Bundle
Fichier unique .bundle contenant des objets Git et des références : un dépôt complet (historique inclus) transportable, depuis lequel on peut clone ou fetch.
Archive
Fichier .zip/.tar.gz produit par git archive contenant les fichiers d'un commit donné, sans le dossier .git ni l'historique.
Cover letter
Fichier 0000-cover-letter.patch généré par --cover-letter : une lettre d'accompagnement résumant une série de patchs.
send-email
Commande (git send-email) qui envoie des fichiers .patch directement par courriel via un serveur SMTP configuré.
Air-gapped
Se dit d'un réseau volontairement isolé d'internet ; on y transfère un dépôt via un bundle sur support amovible, faute de pouvoir pousser.

Récap et vérification

  • git format-patch emballe une plage de commits en fichiers courriel ; --cover-letter ajoute une lettre d'ensemble.
  • git am recrée les commits (auteur préservé) ; git apply ne pose que le diff, sans commit.
  • git bundle met un dépôt entier (historique compris) dans un fichier, clonable : idéal pour les réseaux isolés.
  • git archive exporte un instantané des fichiers d'un commit ou d'un tag, sans .git : pour livrer une version.
  • Le choix dépend du besoin : contribution → patch, dépôt à déplacer → bundle, fichiers à livrer → archive.
