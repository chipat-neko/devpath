Les protocoles

~50 min Intermédiaire Prérequis : leçon 7

À la fin de cette leçon, tu sauras

  • savoir définir un protocole et y conformer un struct, une class ou un enum ;
  • savoir exploiter les protocoles de la bibliothèque standard (Equatable, Comparable, Hashable, CustomStringConvertible, Identifiable) ;
  • savoir factoriser du comportement avec une extension de protocole et une implémentation par défaut ;
  • savoir utiliser un protocole comme type (any) et composer des protocoles avec &.
Sommaire de la leçon

En Swift, on ne conçoit pas d'abord avec l'héritage de classe, mais avec des protocoles. Un protocole, c'est un contrat : il déclare quelles propriétés et quelles méthodes un type doit fournir, sans dire comment. Un struct, une class ou un enum peut ensuite conformer à ce contrat et, du moment qu'il le respecte, on peut le manipuler à travers le protocole sans connaître son type concret. C'est l'idée du « protocol-oriented programming », au cœur de la philosophie du langage : sûreté et expressivité, du petit script jusqu'à l'app iOS.

Dans cette leçon, tu vas définir tes propres protocoles, adopter ceux de la bibliothèque standard, et surtout découvrir la grande force des extensions de protocole : ajouter du comportement partagé à tous les types conformes, en une seule fois.

Un protocole, c'est un contrat

On déclare un protocole avec le mot-clé protocol. À l'intérieur, on liste les exigences : des propriétés (avec { get } ou { get set }) et des méthodes (signature seule, sans corps).

Le protocole ne contient aucune implémentation : il dit seulement « tout type qui veut être une Forme doit savoir calculer son aire et se décrire ». Remarque le { get } : il indique que le protocole exige au minimum de pouvoir lire la propriété. Un type conforme peut la fournir comme propriété calculée, stockée, constante ou variable, tant que la lecture est possible.

Pour adopter un protocole, on l'écrit après le nom du type, séparé par :. Le compilateur vérifie alors que toutes les exigences sont satisfaites. Privilégions les value types : ici des struct.

Traiter des types différents, uniformément

Voilà tout l'intérêt : une fonction qui accepte une Forme fonctionne avec n'importe quel type conforme, présent ou futur. Le code appelant ne dépend que du contrat.

Implémentation par défaut via extension

On peut étendre un protocole pour fournir une implémentation par défaut. Tout type conforme en hérite automatiquement, sans avoir à la réécrire. C'est la force la plus distinctive du langage.

Ni Cercle ni Rectangle n'ont défini résumé() : l'extension du protocole le leur donne. Un type conforme peut tout de même fournir sa propre version de résumé(), qui prendra alors le dessus lorsqu'on l'appelle sur ce type concret.

Astuce

Mets dans le protocol ce qui varie d'un type à l'autre (les exigences nues) et dans l'extension ce qui peut être dérivé de ces exigences (le comportement partagé). Tu écris le contrat une fois, le comportement une fois, et chaque nouveau type n'a plus qu'à fournir le strict minimum.

Les protocoles de la bibliothèque standard

Swift fournit des protocoles que tu rencontreras partout. Y conformer débloque des opérations toutes faites.

  • Equatable : comparer avec == et !=.
  • Comparable : ordonner avec <, >, et trier.
  • Hashable : utiliser comme clé de dictionnaire ou élément de Set.
  • CustomStringConvertible : personnaliser l'affichage via description.
  • Identifiable : exposer un id stable (omniprésent en SwiftUI).

Pour Equatable et Hashable, le compilateur peut synthétiser la conformité automatiquement si tous les membres stockés sont eux-mêmes conformes : tu écris juste le nom du protocole.

Pour Comparable, en revanche, il faut indiquer le critère d'ordre : on implémente l'opérateur <, et Swift en déduit >, <=, >= et le tri.

Note

Comparable hérite lui aussi de Equatable. Pour un struct dont tous les membres sont Equatable, le == reste synthétisé tout seul ; tu n'as à fournir que l'opérateur <. Attention toutefois : si ton ordre ne porte que sur certains champs (ici valeur), == synthétisé, lui, compare tous les champs — pense à les aligner si la cohérence compte.

Cas réel

Le protocole Identifiable est incontournable dès qu'on affiche une liste en SwiftUI. Un List(articles) ou un ForEach exige que chaque élément expose un id stable : c'est ainsi que le framework sait quelle ligne a bougé, est apparue ou a disparu, et n'anime que le strict nécessaire au lieu de tout redessiner. Concrètement, il suffit d'ajouter Identifiable à ton struct Article et de lui donner un let id: UUID. De même, Codable (autre protocole synthétisé) rend un type décodable depuis le JSON d'une API en une ligne. En Swift, « se rendre conforme à un protocole » est le geste de base qui débloque des pans entiers de bibliothèques.

Composer et utiliser un protocole comme type

Un protocole peut servir de type pour une variable ou un paramètre. Comme la valeur concrète n'est connue qu'à l'exécution, on l'annote avec le mot-clé any (un « existential ») : any Forme signifie « n'importe quelle valeur conforme à Forme ».

On peut aussi exiger qu'un type respecte plusieurs protocoles à la fois, en les combinant avec &. C'est la composition de protocoles.

Note

Là où l'héritage de classe impose une seule super-classe et fonctionne uniquement avec des types référence, un type peut conformer à autant de protocoles que voulu, et ce mécanisme marche pour les struct et enum (value types). C'est pourquoi, en Swift, on préfère composer des protocoles plutôt que bâtir des hiérarchies de classes.

Pièges fréquents

Piège fréquent

L'implémentation par défaut d'une extension n'est pas répartie dynamiquement comme une méthode surchargeable en POO classique. Si une méthode existe seulement dans l'extension (pas déclarée dans le protocol) et qu'on l'appelle via un any Forme, c'est la version de l'extension qui s'exécute, même si le type concret en fournit une autre. Pour un comportement vraiment polymorphe, déclare l'exigence dans le protocole en plus de l'extension.

Piège fréquent

Conformer à Hashable implique Equatable : si tu redéfinis == à la main sans aligner hash(into:), deux valeurs « égales » pourraient avoir des hachages différents et casser ton Set ou ton dictionnaire. Laisse le compilateur synthétiser les deux ensemble quand c'est possible.

Pour aller plus loin

Pour aller plus loin

Les protocoles peuvent avoir un type associé (associatedtype) pour rester génériques — c'est ainsi qu'est défini Collection. On peut aussi écrire some Forme (opaque type) au lieu de any Forme quand le type concret est unique mais masqué : plus performant car sans « boîte » existentielle. Ces sujets sont approfondis dans les leçons sur la généricité de ce module.

Glossaire

Protocole
Contrat listant des exigences (propriétés, méthodes) qu'un type doit fournir.
Conformité
Fait pour un type de satisfaire toutes les exigences d'un protocole (struct T: P).
Extension de protocole
Ajoute une implémentation par défaut héritée par tous les types conformes.
Synthèse automatique
Génération par le compilateur de == / hash pour Equatable / Hashable.
any (existentiel)
Boîte masquant le type concret derrière un protocole, connu à l'exécution.
Composition de protocoles
A & B : exiger la conformité à plusieurs protocoles à la fois.
Programmation orientée protocole
Concevoir avec des contrats composables plutôt que des hiérarchies de classes.
Identifiable
Protocole exposant un id stable, requis par les listes SwiftUI.

Récap et vérification

  • Un protocol est un contrat : il liste des exigences (propriétés { get }, méthodes) sans implémentation.
  • Un struct, une class ou un enum conforme en satisfaisant toutes les exigences ; sinon la compilation échoue.
  • Une extension de protocole fournit une implémentation par défaut partagée par tous les conformants.
  • Equatable/Hashable sont souvent synthétisés automatiquement ; Comparable demande d'implémenter <.
  • Un protocole peut être un type avec any, et se composer avec & ; on préfère cette approche à l'héritage de classe.

Vérifie ta compréhension

  1. Quelle est la différence entre une exigence déclarée dans le protocol et une méthode ajoutée seulement dans une extension du protocole ?
  2. Pourquoi peut-on écrire Equatable sans définir ==, mais pas Comparable sans définir < ?
  3. Que signifie le type any Forme & CustomStringConvertible pour un paramètre de fonction ?
