Module 4 · Swift en pratique — Leçon 13

Premiers pas vers SwiftUI

~50 min Intermédiaire Prérequis : leçon 12

À la fin de cette leçon, tu sauras

  • Savoir lire une vue SwiftUI : struct ContentView: View, some View et les modificateurs en chaîne ;
  • Savoir gérer l'état d'une interface avec @State et le relier à un champ via @Binding ;
  • Savoir afficher une collection avec ForEach sur des types Identifiable ;
  • Savoir situer SwiftUI dans l'écosystème Apple (UIKit, Xcode, App Store) et tracer un plan d'apprentissage.
Sommaire de la leçon

Tu as parcouru un long chemin : les types valeur, les optionnels, les protocoles, les closures, les génériques. Toutes ces notions n'étaient pas des exercices isolés — elles forment le socle de SwiftUI, le framework moderne d'Apple pour construire des interfaces sur iPhone, iPad, Mac, Watch et Apple TV. Dans cette leçon, on assemble les pièces : tu vas voir que chaque concept que tu as appris se retrouve, presque mot pour mot, dans une vraie app.

SwiftUI est déclaratif : au lieu de décrire les étapes pour construire l'écran (« crée un label, place-le ici, change son texte »), tu décris l'écran tel qu'il doit être pour un état donné, et le framework se charge du reste. Tu ne pourras pas exécuter ces exemples sans Xcode, mais ils sont volontairement lisibles : l'objectif ici est de comprendre la structure, pas de tout faire tourner.

Une vue est une struct qui adopte un protocole

Le bloc de base de SwiftUI est la vue. Une vue est une struct (un type valeur, comme au chapitre 6) qui adopte le protocole View. Ce protocole exige une seule chose : une propriété calculée body qui décrit ce qui s'affiche.

Reconnais-tu some View ? C'est l'opaque type de la leçon 9. Il signifie : « body renvoie un type concret qui adopte View, mais je ne te dis pas lequel ». C'est exactement ce dont SwiftUI a besoin : le compilateur connaît le type réel (pour optimiser), mais toi tu n'as pas à l'écrire — il serait imprononçable.

Note

Une vue SwiftUI est une struct, donc un type valeur léger. SwiftUI en crée et détruit beaucoup, très souvent, sans coût notable : ce n'est qu'une description, pas l'objet à l'écran. Tu retrouves ici le réflexe « value type par défaut » du cours.

Empiler des vues : VStack, HStack, List

Un body ne renvoie qu'une vue. Pour en afficher plusieurs, on les regroupe dans un conteneur : VStack (empile verticalement), HStack (horizontalement), ZStack (en profondeur). Ces conteneurs prennent une closure — encore une notion connue !

Le bloc { ... } après VStack est une closure spéciale (un result builder) où chaque ligne devient une sous-vue. Pour une liste défilante, on utilise List, qui prend la même forme mais affiche ses enfants dans un tableau scrollable, façon Réglages iOS.

Les modificateurs : configurer en chaîne

On ajuste une vue avec des modificateurs, des méthodes qui renvoient une nouvelle vue. On les enchaîne, comme le chaînage de méthodes vu plus tôt : chaque appel emballe la vue précédente.

L'ordre compte : .padding().background(.yellow) met le fond autour de la marge, alors que .background(.yellow).padding() met la marge autour du fond. Chaque modificateur renvoie « la vue d'avant, modifiée » — d'où le some View qui masque cet empilement de types.

@State : la donnée qui redessine l'écran

Voici le cœur de SwiftUI. Une vue est une fonction de son état : données → vue. Quand une donnée change, SwiftUI recalcule body et met à jour l'écran automatiquement. Tu ne touches jamais directement aux pixels.

Pour qu'une donnée déclenche ce redessin, on la marque @State. C'est un property wrapper qui dit à SwiftUI : « surveille cette valeur ; si elle bouge, refais la vue ».

Note le private : l'état appartient à la vue, personne d'autre ne doit le modifier. C'est une convention si forte qu'Apple la recommande systématiquement. Le { total += 1 } du Button est, là encore, une closure : l'action à exécuter au tap.

Astuce

Ne pense jamais « comment changer le texte à l'écran ». Pense « quelle donnée doit changer ». Tu modifies la donnée, la vue suit. C'est le renversement mental que SwiftUI te demande — et il rend le code beaucoup plus simple à raisonner.

Cas réel — tu connais déjà ce paradigme

Le modèle « données → vue » n'a rien de propre à Apple. C'est celui que React (Facebook, 2013) a imposé sur le web, puis qu'ont repris Flutter (Google) et Jetpack Compose (Android). Quand une équipe migre une app d'UIKit impératif vers SwiftUI déclaratif, le gain est très concret : on supprime des dizaines de lignes de synchronisation manuelle — et avec elles la classe de bugs « l'écran affiche encore l'ancienne valeur ». Apprendre ce réflexe, c'est acquérir une compétence transférable à presque tout le développement d'interfaces moderne.

@Binding : partager un état modifiable

@State possède la donnée. Mais parfois un sous-composant doit pouvoir la modifier sans en être propriétaire. C'est le rôle de @Binding : une référence vers l'état d'une autre vue. On la crée avec le préfixe $.

Le cas typique : un TextField lié à une chaîne. Le champ lit et écrit la même variable.

Le $prenom fournit un Binding<String> au TextField. Quand tu tapes, le champ écrit dans prenom ; comme c'est un @State, la vue se recalcule, et le Text en dessous se met à jour. Une seule source de vérité, deux endroits synchronisés.

ForEach : afficher une collection d'Identifiable

Pour répéter une vue sur chaque élément d'une collection, on utilise ForEach. Pour suivre quel élément est lequel (et animer ajouts/suppressions), SwiftUI a besoin d'une identité stable : chaque élément doit adopter le protocole Identifiable, vu au chapitre sur les protocoles.

Parce que Tache est Identifiable (via sa propriété id), ForEach(taches) suffit : pas besoin de préciser l'identité. La closure { tache in ... } reçoit chaque élément et renvoie sa vue. Données → vue, à nouveau : change le tableau, la liste suit.

Le reste de l'écosystème : un survol honnête

SwiftUI ne vit pas seul. Quelques repères pour situer la suite :

  • UIKit / AppKit — l'ancien monde, impératif (« crée ce bouton, ajoute-le à cette vue »). Encore très présent dans les apps existantes ; SwiftUI sait s'y interfacer, mais les nouveaux projets partent en SwiftUI.
  • Xcode — l'éditeur d'Apple, gratuit, uniquement sur Mac. Il intègre l'aperçu en direct (#Preview) qui dessine ta vue sans relancer l'app.
  • Le simulateur — un iPhone/iPad virtuel sur ton Mac pour tester sans appareil physique.
  • L'App Store — la distribution passe par un compte développeur Apple payant et un processus de revue.

Note

Côté emploi, Swift ouvre l'iOS, macOS, watchOS, visionOS — un marché de plusieurs milliards d'appareils. La demande iOS reste forte et SwiftUI est désormais la compétence attendue sur les nouveaux postes, souvent en duo avec une connaissance résiduelle d'UIKit.

Pièges fréquents

Piège fréquent

Modifier une propriété sans @State ne redessine rien — pire, dans une struct immuable, le compilateur refuse : // error: cannot assign to property: 'self' is immutable. Si une valeur doit changer dans le temps, elle a besoin de @State (ou d'un wrapper équivalent).

Piège fréquent

Oublier le $ sur un TextField : TextField("...", text: prenom) passe une copie, pas une liaison, et le compilateur proteste car il attend un Binding<String>. Le $ transforme l'état en liaison ; sans lui, pas de synchro à double sens.

Pour aller plus loin

Pour aller plus loin

Quand l'état dépasse une seule vue, on le sort dans une classe observable avec @Observable (macro moderne, Swift 5.9+), injectée via @Environment. Explore aussi NavigationStack pour la navigation, .sheet pour les modales, et async/await dans .task { } pour charger des données réseau — autant de portes vers une vraie app.

Glossaire

Déclaratif
Décrire l'écran voulu pour un état donné et laisser le framework produire le résultat, au lieu d'énumérer les étapes (impératif).
Vue (View)
Brique d'interface : une struct conforme au protocole View, dotée d'une propriété body.
body
Propriété calculée décrivant le contenu d'une vue ; SwiftUI la recalcule à chaque changement d'état.
Opaque type (some View)
Type de retour garantissant « une View » sans nommer le type concret, choisi par le compilateur.
Modificateur
Méthode (.font, .padding…) qui renvoie une nouvelle vue configurée ; s'enchaîne, l'ordre compte.
@State
Property wrapper d'un état local possédé par la vue ; sa modification déclenche le redessin.
@Binding
Référence partagée (préfixe $) vers l'état d'une autre vue : lecture et écriture à double sens.
Identifiable
Protocole exigeant un id stable, utilisé par ForEach pour suivre chaque élément.

Récap et vérification

  • Une vue est une struct adoptant View, avec une propriété body: some View (opaque type).
  • VStack, HStack, List regroupent des sous-vues via une closure ; les modificateurs (.font, .padding) s'enchaînent.
  • @State rend une donnée observable : la modifier redessine l'écran (cycle données → vue).
  • @Binding (préfixe $) partage un état modifiable, par exemple avec un TextField.
  • ForEach répète une vue sur une collection d'éléments Identifiable.
  • Autour : UIKit (l'ancien monde), Xcode et son simulateur, l'App Store pour distribuer.

Vérifie ta compréhension

  1. Que signifie some View dans le type de retour de body, et à quelle leçon antérieure ça renvoie ?
  2. Pourquoi une variable modifiée à l'écran doit-elle être marquée @State ?
  3. Quel protocole un élément doit-il adopter pour être listé proprement avec ForEach, et pourquoi ?
