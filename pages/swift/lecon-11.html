Concurrence : async/await et actors

~55 min Avancé Prérequis : leçon 10

À la fin de cette leçon, tu sauras

  • savoir écrire et appeler des fonctions async avec await, et lancer du travail concurrent via Task et async let ;
  • savoir protéger un état mutable partagé avec un actor et revenir sur le thread UI avec @MainActor ;
  • savoir parcourir un flux asynchrone avec for await et annuler proprement une Task ;
  • savoir expliquer pourquoi le compilateur Swift 6 attrape les data races et ce qu'apporte async/await face aux completion handlers.
Sommaire de la leçon

Quand ton app télécharge une image, interroge une API ou lit un gros fichier, ce travail prend du temps. Si tu le fais sur le thread principal — celui qui dessine l'interface — l'écran gèle : plus de scroll, plus d'animation, l'utilisateur croit que l'app a planté. La concurrence, c'est l'art de faire ce travail ailleurs sans bloquer l'UI, puis de revenir poser le résultat à l'écran.

Depuis Swift 5.5, le langage offre un modèle de concurrence intégré : async/await, Task, les actor. Sa promesse colle au fil conducteur du cours — sûreté et expressivité : tu écris du code asynchrone qui se lit comme du code séquentiel, et le compilateur attrape une grande classe de bugs (les data races) avant même que le programme tourne.

Le problème : bloquer le thread principal

Avant de voir la solution, regardons la douleur. Une fonction synchrone qui « dort » trois secondes bloque tout ce qui l'attend.

Le souci n'est pas la durée, c'est que rien d'autre ne peut s'exécuter pendant ce temps. Il faut une façon de dire « mets ce travail en pause, libère le thread, reviens-moi quand c'est prêt ». C'est exactement ce que fait await.

async et await : lire l'asynchrone de haut en bas

On marque une fonction async quand elle peut se suspendre. À l'appel, on écrit await devant : c'est un point de suspension. Le thread n'est pas bloqué — il part faire autre chose — et la fonction reprend ici dès que le résultat arrive.

Le gain de lisibilité est énorme : trois lignes qui se lisent de haut en bas, comme du code classique, alors qu'il se passe une suspension au milieu. Chaque await signale « ici, l'exécution peut faire une pause » — utile pour raisonner sur l'ordre des choses.

Note

Une fonction async ne peut être appelée que depuis un contexte asynchrone : une autre fonction async, ou une Task. C'est cette règle qui empêche d'appeler du code asynchrone « par accident » au mauvais endroit.

Task : lancer du travail asynchrone

Comment franchir la frontière entre le monde synchrone (un bouton tapé, le démarrage d'une vue) et le monde async ? Avec une Task : elle crée un contexte asynchrone et démarre le travail immédiatement, sans bloquer l'appelant.

La Task expose aussi sa valeur si tu en as besoin : let t = Task { … } puis await t.value. Elle peut aussi propager une erreur lancée par son contenu — tu la récupères avec try await t.value.

async let : faire deux choses en parallèle

Avec un seul await à la suite, les travaux s'enchaînent. Mais si deux téléchargements sont indépendants, autant les lancer en même temps. C'est le rôle d'async let : la valeur démarre tout de suite, et tu n'attends qu'au moment où tu en as besoin.

Séquentiel, ce serait 2 s + 2 s = 4 s. En parallèle avec async let, c'est ~2 s. Retiens la règle : enchaîner avec await quand une étape dépend de la précédente, async let quand elles sont indépendantes.

Le data race, et comment Swift l'attrape

Le danger du parallélisme : deux tâches qui écrivent au même moment dans la même variable. Le résultat devient imprévisible — c'est un data race. Historiquement, ces bugs étaient invisibles à la compilation et surgissaient au pire moment en production.

Swift 6 active la strict concurrency : le compilateur refuse le code qui pourrait provoquer un data race. Ce n'est plus un avertissement à l'exécution, c'est une erreur de compilation.

Au lieu de te laisser livrer un bug intermittent, le langage te force à dire comment cet état est protégé. La réponse idiomatique s'appelle l'actor.

actor : protéger un état mutable partagé

Un actor ressemble à une classe, mais avec une garantie forte : un seul accès à la fois à son état interne. Le runtime sérialise les appels, donc deux tâches ne peuvent jamais écrire en même temps. De l'extérieur, lire ou modifier son état demande un await (l'appel peut attendre son tour).

Compare avec une class classique : rien ne t'empêcherait d'écrire compteur.valeur += 1 depuis deux threads et de finir parfois à 1. L'actor rend ce bug impossible à écrire.

@MainActor : revenir sur le thread de l'UI

Toute mise à jour d'interface doit se faire sur le thread principal. Swift modélise ce thread par un actor global : @MainActor. Tu annotes une fonction, une propriété ou une classe entière, et le compilateur garantit que son code tourne sur le thread principal.

Astuce

Dans une app SwiftUI, marque tes classes de vue-modèle en @MainActor. Tu n'as plus à te demander « suis-je sur le bon thread ? » : le compilateur t'oblige à await dès que tu sors du thread principal.

AsyncSequence et for await

Parfois la valeur n'arrive pas en une fois mais en flux : lignes d'un fichier, événements, messages d'un WebSocket. Une AsyncSequence se parcourt avec for await — chaque tour de boucle peut se suspendre en attendant l'élément suivant.

Annulation et Sendable

Une Task peut être annulée (l'utilisateur quitte l'écran, une nouvelle recherche remplace l'ancienne). L'annulation est coopérative : le code doit la vérifier et s'arrêter proprement.

Note

Le protocole Sendable marque les types qu'on peut transférer sans danger entre tâches concurrentes. Les value types (struct/enum) composés de membres sûrs le sont automatiquement — encore une raison de privilégier les value types. Le compilateur t'avertit quand un type non-Sendable franchit une frontière de concurrence.

L'ancien monde : completion handlers

Avant async/await, l'asynchrone passait par des completion handlers : tu passais une closure rappelée à la fin. Honnêtement, ça marchait — mais ça imbriquait le code, dispersait la gestion d'erreurs et invitait à oublier d'appeler le callback.

Même comportement, mais la version async se lit de haut en bas, gère les erreurs avec try et le parallélisme avec async let. C'est l'expressivité de Swift appliquée à la concurrence.

Cas réel

Ouvre n'importe quel écran de profil d'une app moderne (un réseau social, un client bancaire, une boutique) : il affiche d'un coup un avatar, une bannière et une liste de publications, chacun venant d'une requête réseau distincte. En completion handlers, ce chargement s'imbriquait en « pyramide » difficile à relire ; avec async let, les trois requêtes partent ensemble et l'écran s'affiche en ~1 fois le temps de la plus lente, pas la somme des trois. Mieux : en SwiftUI, le modificateur .task { … } lance ce travail à l'apparition de la vue et l'annule automatiquement quand l'utilisateur quitte l'écran — exactement le comportement d'une barre de recherche qui abandonne l'ancienne requête à chaque nouvelle frappe.

Pièges fréquents

Piège fréquent

Enchaîner deux await indépendants au lieu d'async let : let a = await f(); let b = await g() exécute en série (temps additionné). Si a et b ne dépendent pas l'un de l'autre, utilise async let pour les paralléliser.

Piège fréquent

Mettre à jour l'UI hors du thread principal. Sans @MainActor, modifier l'interface depuis une Task quelconque est un bug. Annote ta couche de présentation en @MainActor et laisse le compilateur t'imposer un await au bon endroit.

Glossaire

async / await
Écrire l'asynchrone linéairement ; await marque un endroit où l'exécution peut se suspendre.
Point de suspension
Endroit (await) où la fonction rend le thread et pourra reprendre plus tard.
Task
Unité de travail asynchrone ; pont entre le monde synchrone et le monde async.
async let
Démarre une valeur asynchrone immédiatement pour la paralléliser ; on l'attend au moment de l'utiliser.
actor
Type de référence dont l'état n'est accessible qu'un accès à la fois (isolation), éliminant les data races.
@MainActor
Actor global représentant le thread principal ; garantit que le code annoté y tourne (UI).
Data race
Accès concurrent non synchronisé au même état mutable, dont au moins une écriture : résultat imprévisible.
Sendable
Protocole marquant les types transférables sans danger entre contextes concurrents.

Récap et vérification

  • async/await : écrire de l'asynchrone qui se lit de haut en bas ; chaque await est un point de suspension qui libère le thread.
  • Task : pont du synchrone vers l'asynchrone ; async let : lancer des travaux indépendants en parallèle.
  • actor : un seul accès à la fois à son état → pas de data race ; @MainActor : garantir l'exécution sur le thread de l'UI.
  • Swift 6 strict concurrency transforme les data races en erreurs de compilation ; Sendable marque les types sûrs à transférer.
  • for await parcourt une AsyncSequence ; les Task s'annulent de façon coopérative via Task.checkCancellation().

Vérifie ta compréhension

  1. Pourquoi let a = await f(); let b = await g() est-il plus lent que la version avec async let quand f et g sont indépendantes ?
  2. Qu'est-ce qu'un data race, et par quel mécanisme un actor le rend impossible ?
  3. À quoi sert @MainActor, et quel risque court-on si on l'oublie en mettant à jour l'interface ?
