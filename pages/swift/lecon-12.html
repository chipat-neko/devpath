Module 4 · Swift en pratique — Leçon 12

Outils, paquets et tests

~45 min Intermédiaire Prérequis : leçon 11

À la fin de cette leçon, tu sauras

  • savoir créer et configurer un paquet avec Swift Package Manager (Package.swift, build, run, test) ;
  • savoir écrire un même test en Swift Testing (@Test, #expect) et en XCTest ;
  • savoir mener une courte session de TDD et ajouter une dépendance distante ;
  • savoir documenter et structurer un module avec swift-format, SwiftLint et DocC.
Sommaire de la leçon

Jusqu'ici, tu as écrit du Swift dans des fichiers isolés. Mais un vrai projet — qu'il s'agisse d'un outil en ligne de commande, d'une bibliothèque partagée ou d'une app iOS — a besoin d'un squelette : un moyen de déclarer ses sources, ses dépendances, ses tests, et de les compiler de façon reproductible. C'est exactement le rôle de Swift Package Manager (SPM), l'outil officiel livré avec la toolchain Swift.

Dans cette leçon, on passe du script au module : on crée un paquet, on le compile et on le lance, on lui ajoute une dépendance, puis on écrit des tests dans les deux frameworks modernes (Swift Testing et XCTest). On terminera par une mini-session de TDD et un tour des outils qui gardent un projet propre. Fil rouge habituel : Swift t'aide à rester sûr et expressif, et son outillage est pensé pour que ça reste vrai même à grande échelle.

Créer un paquet avec swift package init

Tout commence par un dossier vide et une commande. SPM génère pour toi la structure de base et un manifeste.

Le type library crée plutôt une bibliothèque réutilisable ; executable crée un programme lançable.

Tu obtiens une arborescence minimale. La convention est stricte et SPM s'y appuie : pas besoin de lister chaque fichier, il découvre les sources automatiquement.

Note

Chaque sous-dossier de Sources/ correspond à une cible (target). Tout fichier .swift qu'il contient en fait partie : la structure des dossiers est la configuration, ce qui réduit le code de manifeste à écrire. Les versions récentes de SPM placent le code dans Sources/<Cible>/ et utilisent l'attribut @main comme point d'entrée, à la place de l'ancien main.swift posé directement sous Sources/.

Lire et écrire Package.swift

Le manifeste est lui-même du Swift : un fichier Package.swift exécuté par SPM pour décrire ton paquet. La première ligne, le tools-version, indique la version minimale de Swift requise.

Trois notions à retenir. Les products sont ce que d'autres paquets (ou l'utilisateur) peuvent consommer : une bibliothèque ou un exécutable. Les targets sont les unités de compilation internes. Les dependencies sont les paquets externes. Une cible de test dépend de la cible qu'elle vérifie, d'où dependencies: ["Calculatrice"].

build, run, test : la boucle de travail

Trois commandes couvrent l'essentiel du quotidien. Écrivons d'abord un peu de code à compiler. Comme le fichier ne s'appelle plus main.swift, on marque le point d'entrée avec @main.

swift run calc permet de viser un produit précis quand il y en a plusieurs.

Astuce

Ajoute -c release pour une compilation optimisée (swift build -c release). Par défaut, SPM compile en debug, plus rapide à construire mais plus lent à l'exécution.

Ajouter une dépendance distante

Une dépendance se déclare en deux endroits : dans dependencies au niveau du paquet (où la trouver et quelle version), puis dans la cible qui l'utilise (quel produit importer). Prenons une bibliothèque d'algorithmes d'Apple.

La contrainte from: "1.2.0" applique le versionnage sémantique : SPM accepte toute version 1.x.y >= 1.2.0 mais jamais 2.0.0, qui pourrait casser l'API. Au premier swift build, SPM résout le graphe et écrit un fichier Package.resolved qui épingle les versions exactes — commite-le pour des builds reproductibles.

Cas réel

Sur un projet d'équipe, le fichier Package.resolved est ce qui évite le fameux « ça marche sur ma machine ». Il épingle la version exacte de chaque dépendance (par exemple swift-algorithms 1.2.1, et non « n'importe quel 1.x »). Commité dans le dépôt, il garantit que tes collègues et le serveur d'intégration continue compilent tous avec les mêmes sources : un correctif publié en 1.2.2 ne s'invitera pas dans un build sans que quelqu'un mette à jour ce fichier volontairement. C'est le pendant Swift du package-lock.json de npm ou du Cargo.lock de Rust.

Tester avec Swift Testing

Swift Testing est le framework moderne (Swift 6, Xcode 16+). Il repose sur deux macros principales : @Test pour marquer une fonction de test, et #expect pour exprimer une attente. Pas de préfixe test obligatoire, pas de classe : une simple fonction suffit.

La différence clé entre les deux macros : #expect enregistre l'échec mais laisse le test continuer (pratique pour voir toutes les erreurs d'un coup), tandis que #require lève et stoppe net — utile quand la suite du test n'a plus de sens, typiquement après avoir déballé un optionnel. Le @testable import donne accès aux membres internal de la cible testée.

Le même test en XCTest

XCTest reste très répandu (projets existants, anciennes versions d'Xcode). Il fonctionne par classes héritant de XCTestCase, avec des méthodes dont le nom commence par test, et des assertions de la famille XCTAssert.

Le tableau des correspondances est facile à mémoriser : @Test func ↔ méthode test… dans une XCTestCase ; #expect(a == b) ↔ XCTAssertEqual(a, b) ; try #require(x) ↔ try XCTUnwrap(x). Les deux frameworks cohabitent dans la même cible de test, donc une migration peut se faire progressivement, fichier par fichier.

Note

Pour un nouveau projet, privilégie Swift Testing : paramétrage de tests via @Test(arguments:), parallélisme par défaut, messages d'échec plus lisibles. Garde XCTest pour les tests d'UI (XCUIApplication), encore non couverts par Swift Testing.

Une session de TDD : FizzBuzz

Le TDD (développement piloté par les tests) suit un cycle court : rouge (écrire un test qui échoue) → vert (le faire passer au plus simple) → refactor. Construisons fizzBuzz, qui renvoie « Fizz » pour les multiples de 3, « Buzz » pour ceux de 5, « FizzBuzz » pour les deux, le nombre sinon.

Étape rouge : le test d'abord, alors que la fonction n'existe pas encore.

Étape vert : l'implémentation la plus directe qui satisfait le test.

Le test passe : on est au vert. L'étape refactor consiste à améliorer le code sans changer son comportement, en s'appuyant sur le filet de sécurité des tests. Ici, le switch sur un tuple est déjà lisible et exhaustif (le compilateur vérifie que les quatre cas sont couverts) — on peut s'arrêter là.

Outils de qualité et documentation DocC

Trois outils complètent l'écosystème. swift-format (officiel, intégré à la toolchain) réindente et normalise le style. SwiftLint détecte les odeurs de code et fait respecter des règles d'équipe. DocC transforme tes commentaires en documentation navigable.

Selon ta toolchain, l'outil officiel s'invoque swift format (sous-commande) ou via le binaire swift-format ; swiftlint s'installe à part (Homebrew ou plugin SPM).

La documentation se rédige directement dans le code avec des commentaires ///. DocC en extrait un site complet, et Xcode l'affiche dans l'aide rapide.

Pour la structuration d'un module, retiens trois principes : une cible = une responsabilité ; expose le minimum (marque public uniquement ce qui doit l'être, le reste reste internal par défaut) ; fais miroir entre Sources/ et Tests/ pour qu'on retrouve facilement le test d'un fichier donné.

Pièges fréquents

Piège fréquent

La ligne // swift-tools-version: doit être la toute première du fichier Package.swift, sans ligne vide au-dessus. Sinon SPM échoue avec error: 'Package.swift' should have a leading 'swift-tools-version' directive.

Deuxième écueil : oublier @testable import. Avec un simple import Calculatrice, tes tests ne voient que les symboles public ; toute fonction internal (le cas par défaut) déclenche error: cannot find 'somme' in scope. Le mot-clé @testable ouvre l'accès aux membres internes pour les tests uniquement.

Troisième écueil : confondre product et target dans dependencies. Au niveau du paquet, on déclare le dépôt ; au niveau de la cible, on relie un produit via .product(name:package:). Mettre le nom du paquet là où SPM attend le nom du produit donne error: product 'swift-algorithms' not found — il fallait "Algorithms".

Pour aller plus loin

Pour aller plus loin

Explore les tests paramétrés de Swift Testing : @Test(arguments: [(3, "Fizz"), (5, "Buzz")]) exécute le même corps pour chaque jeu de données. Regarde aussi les traits comme .tags(...) et .disabled("raison"), et les plugins de build SPM qui branchent SwiftLint directement dans swift build.

Récap et vérification

  • SPM décrit un paquet via Package.swift (products, targets, dependencies) et le pilote avec swift build, swift run, swift test.
  • Une dépendance distante se déclare au niveau du paquet (.package(url:from:)) puis se relie à une cible via .product(name:package:).
  • Swift Testing utilise @Test, #expect (continue) et #require (arrête) ; XCTest utilise XCTestCase, XCTAssertEqual, XCTUnwrap.
  • Le TDD suit le cycle rouge → vert → refactor ; @testable import donne accès aux membres internes.
  • swift-format, SwiftLint et DocC (commentaires ///) gardent un module propre et documenté.

  3. Pourquoi un test a-t-il besoin de @testable import plutôt qu'un simple import ?
