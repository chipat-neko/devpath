Codable : lire et écrire du JSON

~48 min Intermédiaire Prérequis : leçon 14

À la fin de cette leçon, tu sauras

  • Rendre un type sérialisable avec Codable (conformance synthétisée automatiquement) ;
  • Encoder un objet en JSON avec JSONEncoder et le décoder avec JSONDecoder ;
  • Renommer des clés avec CodingKeys et gérer le snake_case d'une API ;
  • Gérer proprement l'échec d'un décodage avec try et DecodingError.
Sommaire de la leçon

Une app ne vit pas seule : elle appelle des API web, lit des fichiers de configuration, sauvegarde l'état de l'utilisateur. Dans l'immense majorité des cas, ces échanges se font au format JSON, ce texte fait d'accolades, de clés et de valeurs. La grande force de Swift, c'est de transformer un objet en JSON — et l'inverse — presque sans écrire de code, grâce au protocole Codable.

Encodable, Decodable, Codable

Deux protocoles encadrent la sérialisation (transformer un objet en données) et la désérialisation (l'inverse) :

  • Encodable — le type sait se transformer en données (objet → JSON) ;
  • Decodable — le type sait se reconstruire depuis des données (JSON → objet).

Codable n'est qu'un raccourci pour « les deux à la fois » : typealias Codable = Encodable & Decodable. La plupart du temps, on écrit simplement Codable.

Conformance automatique

Le tour de force : si toutes les propriétés d'un type sont déjà Codable (c'est le cas de String, Int, Double, Bool, Date, des tableaux et dictionnaires de types Codable…), il suffit d'écrire : Codable. Le compilateur synthétise tout le code de lecture/écriture pour toi.

Encoder : objet → JSON

On confie l'objet à un JSONEncoder. Sa méthode encode renvoie un Data (une suite d'octets), que l'on peut convertir en texte pour l'inspecter. L'opération peut échouer : elle est marquée throws, d'où le try (leçon 10).

Astuce

.outputFormatting = .prettyPrinted n'est utile qu'au débogage, pour lire le JSON à l'œil. En production (envoi réseau, stockage), laisse le format compact par défaut : plus léger, plus rapide.

Décoder : JSON → objet

Le sens inverse est le plus fréquent : on reçoit du JSON d'une API et on veut un objet Swift. On donne au JSONDecoder le type attendu (avec .self) et les données. C'est throws aussi : si le JSON ne correspond pas, ça lève une erreur plutôt que de planter en silence.

Note le Utilisateur.self : on passe le type comme argument, pour dire au décodeur quelle forme reconstruire. C'est un métatype, la même idée que Magasin.self croisé à la leçon précédente.

Renommer les clés : CodingKeys

Problème classique : une API renvoie "user_name" (style snake_case, courant côté serveur), mais en Swift on veut une propriété nomUtilisateur (style camelCase). On règle ça avec une énumération imbriquée CodingKeys qui associe chaque propriété à sa clé JSON.

Quand toutes les clés suivent le snake_case, inutile d'écrire un CodingKeys à la main : un réglage du décodeur fait la conversion en masse.

Imbrication et tableaux

Un type Codable peut en contenir d'autres, et des tableaux : tant que tout est Codable, la synthèse descend récursivement. Décoder une liste d'objets, c'est décoder un [Type].

Gérer l'échec d'un décodage

Le décodage échoue si le JSON est mal formé, si une clé attendue manque, ou si un type ne correspond pas (un texte là où on attend un nombre). Comme c'est throws, on l'entoure d'un do/catch ; DecodingError décrit précisément le problème.

Piège fréquent

Une propriété non optionnelle absente du JSON fait échouer tout le décodage. Si un champ peut manquer, déclare-le optionnel (let age: Int?) : il vaudra nil au lieu de lever une erreur. Choisir entre « obligatoire » et « optionnel » est une décision de conception, pas un détail.

Cas réel — consommer une API en deux lignes

Le duo async/await (leçon 11) et Codable est la manière standard d'appeler une API dans une app iOS. On récupère les octets avec URLSession, on les décode dans un type, et c'est fini : let (data, _) = try await URLSession.shared.data(from: url) puis let météo = try JSONDecoder().decode(Météo.self, from: data). Avant Codable (arrivé avec Swift 4 en 2017), il fallait éplucher des dictionnaires [String: Any] à la main, avec des transtypages partout et des bugs à la pelle. Codable a rendu cette corvée sûre et quasi automatique — c'est l'une des raisons de la popularité de Swift côté réseau.

Glossaire

Sérialisation
Transformer un objet en un format d'échange (ici JSON) ; la désérialisation fait l'inverse.
Codable
Alias de Encodable & Decodable : un type qui sait s'encoder et se décoder.
Conformance synthétisée
Code de lecture/écriture généré par le compilateur quand toutes les propriétés sont déjà Codable.
JSONEncoder / JSONDecoder
Objets qui réalisent la conversion objet → Data JSON et l'inverse.
Data
Suite d'octets bruts ; le résultat d'un encodage, converti en texte via String(data:encoding:).
CodingKeys
Énumération imbriquée (: String, CodingKey) associant chaque propriété à sa clé JSON.
DecodingError
Erreur décrivant un décodage impossible : clé manquante, type incompatible, données corrompues.
snake_case / camelCase
Deux conventions de nommage : user_name (fréquent côté serveur JSON) contre nomUtilisateur (style Swift). CodingKeys ou .convertFromSnakeCase font le pont entre les deux.

Récap et vérification

  • Codable = Encodable & Decodable ; un simple : Codable suffit si les propriétés le sont toutes.
  • JSONEncoder().encode(obj) produit du Data ; JSONDecoder().decode(X.self, from:) reconstruit l'objet — les deux sont throws.
  • CodingKeys renomme des clés ; .convertFromSnakeCase traite tout le snake_case d'un coup.
  • Types imbriqués et tableaux ([X]) fonctionnent tant que tout est Codable.
  • Une clé absente fait échouer le décodage : rends la propriété optionnelle si elle peut manquer, et gère DecodingError.

Vérifie ta compréhension

  1. Que faut-il écrire pour qu'une struct à propriétés simples devienne sérialisable, et que fait alors le compilateur ?
  2. À quoi sert CodingKeys, et quelle alternative existe si toutes les clés sont en snake_case ?
  3. Que se passe-t-il si une clé non optionnelle manque dans le JSON, et comment l'anticiper ?
