Gestion de la mémoire et des erreurs

~45 min Intermédiaire Prérequis : leçon 9

À la fin de cette leçon, tu sauras

  • savoir définir et lever des erreurs typées avec Error, throws et les variantes try / try? / try! ;
  • savoir structurer un do-catch avec pattern matching, nettoyer avec defer et choisir entre erreurs lancées et Result ;
  • savoir expliquer l'ARC, repérer un cycle de référence fort et le briser avec weak, unowned ou [weak self] ;
  • savoir choisir un value type (struct) pour éviter d'emblée les problèmes de mémoire partagée.
Sommaire de la leçon

Deux dangers guettent tout programme un peu sérieux : les opérations qui peuvent échouer (lire un fichier absent, parser un JSON malformé, appeler un réseau qui tombe) et la mémoire qui fuit (des objets qu'on n'arrive plus à libérer). Swift traite les deux avec la même philosophie que le reste du langage : rendre le risque visible dans le code, à la compilation, plutôt que de te laisser découvrir le problème en production.

Dans cette leçon, tu vas d'abord apprendre à modéliser et propager des erreurs de façon typée, puis à comprendre comment Swift gère la mémoire des classes via l'ARC — et surtout comment éviter les cycles de référence qui empêchent la libération. Le fil conducteur reste le même : sûreté et expressivité, du petit script à l'app iOS.

Modéliser une erreur avec le protocole Error

En Swift, une erreur est une simple valeur conforme au protocole Error. Le plus idiomatique est d'utiliser une enum : chaque cas décrit une cause précise, et tu peux y attacher des données associées pour donner du contexte.

Comparé à un code d'erreur entier ou à un booléen success, l'enum est exhaustive : le compilateur peut t'aider à traiter tous les cas, et chaque cas porte un nom métier clair, conforme aux API Design Guidelines d'Apple.

Note

Une erreur Swift n'est pas une exception coûteuse façon Java. Le mécanisme throws est un chemin de retour alternatif, vérifié à la compilation, sans pile d'exception déroulée à l'exécution.

Déclarer et appeler une fonction throws

Une fonction qui peut échouer annonce throws dans sa signature. À l'appel, tu dois écrire try devant elle : c'est un marqueur visuel obligatoire qui dit « cette ligne peut partir en erreur ».

Ce try ne « gère » rien tout seul ; il rend l'appel légal et signale au lecteur le point de sortie possible. Reste à décider comment réagir : c'est le rôle de do-catch.

do-catch et pattern matching sur les cas d'erreur

Le bloc do contient le code risqué ; les blocs catch interceptent l'erreur. Et comme une erreur est une valeur d'enum, tu peux faire du pattern matching sur ses cas, exactement comme dans un switch.

L'ordre compte : Swift essaie chaque catch de haut en bas. Le dernier catch sans motif attrape tout le reste et expose la valeur sous le nom error. Tu peux aussi filtrer avec where, par exemple catch ErreurReseau.codeHTTP(let c) where c >= 500.

try?, try! et le bon usage de chacun

Parfois, tu ne veux pas écrire un do-catch complet. Swift offre deux raccourcis — à manier avec discernement.

Utilise try? quand l'échec et le succès se résument à « j'ai une valeur ou non » et que la cause exacte t'est égale. Réserve try! aux cas où l'échec serait un bug de programmation (ex. charger une ressource embarquée dans l'app), jamais sur une donnée externe.

Piège fréquent

Un try! qui plante en production est presque toujours un raccourci pris « pour aller vite ». Traite chaque try! comme une assertion forte : s'il peut échouer un jour, il échouera un jour.

defer : nettoyer quoi qu'il arrive

Quand une fonction acquiert une ressource (fichier ouvert, connexion, verrou), il faut la libérer même si une erreur survient en cours de route. Le mot-clé defer planifie un bloc qui s'exécutera à la sortie du scope, quel que soit le chemin emprunté — retour normal ou erreur lancée.

Les defer multiples s'exécutent en ordre inverse de leur déclaration (comme une pile), ce qui correspond à l'ordre naturel de libération : on referme d'abord ce qu'on a ouvert en dernier.

Result<Success, Failure> : l'erreur comme valeur

Le type Result encapsule « soit une réussite, soit un échec » dans une seule valeur que tu peux stocker, passer en argument ou renvoyer d'un callback asynchrone. Utile quand l'erreur ne peut pas être lancée directement, typiquement dans une closure de complétion.

Retiens la complémentarité : throws pour le code synchrone linéaire, Result quand tu dois transporter l'issue (callbacks, files d'attente). Le type Failure étant générique, tu gardes ton erreur typée de bout en bout.

ARC : comment Swift libère la mémoire des classes

Les classes sont des types par référence : plusieurs variables peuvent pointer vers la même instance. Swift suit chaque instance avec l'ARC (Automatic Reference Counting) : il compte combien de références fortes pointent dessus. Dès que ce compte tombe à zéro, l'instance est libérée et son deinit appelé. Pas de ramasse-miettes, pas de pause : la libération est déterministe.

Tant qu'au moins une référence forte existe, l'instance survit. C'est exactement ce mécanisme qui peut se retourner contre toi.

Cycles de référence forts, et comment les briser

Si deux instances se référencent mutuellement avec des références fortes, leur compte ne descend jamais à zéro : chacune maintient l'autre en vie. C'est un cycle de référence fort (retain cycle), et la mémoire fuit.

Pour casser le cycle, on rend l'une des deux références non possessive avec weak ou unowned. Une référence weak ne fait pas grimper le compteur ; elle est forcément optionnelle et devient automatiquement nil quand la cible est libérée.

Choisis entre les deux selon les durées de vie : weak (optionnel) quand la cible peut disparaître avant le détenteur ; unowned (non optionnel) quand la cible vit au moins aussi longtemps que le détenteur — accéder à un unowned déjà libéré plante, comme un try! raté.

[weak self] dans les closures

Une closure capture les valeurs qu'elle utilise. Si elle capture self fortement et que cette même closure est stockée par self, tu obtiens un cycle. La parade idiomatique est la liste de capture [weak self].

Le guard let self else { return } est le motif moderne : à l'intérieur de la closure, soit self existe encore et tu travailles normalement, soit il a été libéré et tu sors proprement.

Cas réel

Le cycle de référence est la fuite mémoire classique sur iOS. Un écran (UIViewController) lance une requête réseau et conserve sa closure de réponse ; cette closure capture self fortement. Tant que la requête n'est pas revenue — ou si un minuteur la rejoue en boucle — l'écran ne peut pas être libéré, même après que l'utilisateur l'a quitté. On empile alors des écrans invisibles en mémoire, l'app enfle, puis le système finit par la tuer. Le correctif tient en deux mots dans la liste de capture : [weak self]. Les instruments « Leaks » et « Memory Graph » de Xcode servent précisément à traquer ces instances qui refusent de mourir.

Pourquoi les structs n'ont pas ce problème

Les structs (et enums) sont des value types : on les copie au lieu de les partager. Il n'y a pas de compteur de références, donc aucun cycle possible et aucune fuite de ce genre. C'est l'une des raisons pour lesquelles Swift conseille de privilégier les structs par défaut, et de réserver les classes aux cas qui exigent vraiment l'identité partagée (héritage, ressource unique, interop Objective-C).

Astuce

Quand tu modélises une donnée, commence par struct. Tu n'auras à penser à l'ARC, weak et [weak self] que le jour où tu auras une vraie raison d'utiliser une class.

Pièges fréquents

  • Abuser de try! sur des données externes : un plantage garanti tôt ou tard. Préfère try + do-catch ou try?.
  • Avaler l'erreur avec try? alors que la cause t'intéresse : tu perds le diagnostic. Garde le do-catch quand tu dois distinguer les cas.
  • Oublier weak sur une relation enfant vers parent (vue vers contrôleur, délégué) : c'est la source n°1 de fuites mémoire en iOS.
  • Capturer self fortement dans une closure stockée. Réflexe : si self détient la closure, capture [weak self].
  • Confondre weak et unowned : unowned n'est pas optionnel et plante si la cible a disparu. Dans le doute, weak.

Glossaire

Error
Protocole que toute valeur d'erreur adopte ; souvent une enum à cas nommés.
throws / try
La fonction annonce le risque avec throws ; l'appel le marque avec try.
do-catch
Bloc qui exécute le code risqué et intercepte l'erreur pour la traiter.
defer
Bloc exécuté à la sortie du scope quel que soit le chemin (retour normal ou erreur).
Result
Type portant soit .success, soit .failure : l'issue devient une valeur manipulable.
ARC
Automatic Reference Counting : libère une instance de classe dès que son compte de références fortes atteint zéro.
Cycle de référence
Deux instances se retenant mutuellement par des références fortes : elles ne sont jamais libérées.
weak / unowned
Références exclues du comptage ARC ; elles brisent les cycles (weak optionnelle, unowned non).

Récap et vérification

  • Une erreur est une valeur conforme à Error ; une enum avec données associées est le choix idiomatique.
  • throws annonce le risque, try le marque ; try? donne un optionnel, try! plante en cas d'échec.
  • do-catch permet le pattern matching sur les cas ; defer garantit le nettoyage ; Result transporte l'issue comme valeur.
  • L'ARC libère une instance de classe quand son compte de références fortes atteint zéro.
  • Deux références fortes mutuelles forment un cycle ; weak, unowned et [weak self] le brisent.
  • Les structs sont copiées, donc immunisées contre ces cycles : privilégie-les par défaut.
