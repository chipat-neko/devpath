Module 2 · Collections et valeurs — Leçon 06

Structs et classes

~50 min Intermédiaire Prérequis : leçon 5

À la fin de cette leçon, tu sauras

  • distinguer un struct (type valeur, copié) d'une class (type référence, partagé) et prévoir les conséquences d'une mutation ;
  • écrire des propriétés stockées et calculées, ajouter des observateurs willSet/didSet et marquer une méthode mutating ;
  • exploiter l'initialiseur memberwise gratuit des structs, écrire un init de classe et utiliser lazy et static ;
  • choisir struct par défaut et réserver class aux cas d'identité, de partage voulu ou d'héritage.
Sommaire de la leçon

Jusqu'ici tu as manipulé des valeurs simples et des collections. Pour modéliser le monde — un compte bancaire, un utilisateur, une position à l'écran — Swift te donne deux outils qui se ressemblent mais ne se comportent pas pareil : le struct et la class. Les deux regroupent des données et du comportement. La différence tient en un mot : copie ou partage. C'est la distinction centrale de Swift, et la comprendre change ta façon d'écrire du code sûr.

La règle d'or, posée d'emblée par Apple : choisis un struct par défaut, et ne passe à une class que si tu as une raison précise. On va voir pourquoi, en construisant un compte bancaire.

Un struct, c'est un type valeur (copié)

Un struct regroupe des propriétés sous un nom. Déclare-le, instancie-le, et tu obtiens une valeur indépendante : chaque affectation en fait une copie.

Tu remarques aussi qu'on a écrit Point(x: 1, y: 2) sans avoir défini d'initialiseur : Swift en offre un gratuitement aux structs, on y revient plus bas. Le point clé ici : a et b sont deux valeurs distinctes. Modifier l'une n'affecte jamais l'autre.

Une class, c'est un type référence (partagé)

Une class se déclare presque pareil, mais ses instances sont des références : une affectation ne copie pas l'objet, elle copie le pointeur vers le même objet. Deux variables peuvent désigner la même instance.

L'opérateur === (identité) demande : « est-ce littéralement le même objet ? ». Il n'existe que pour les classes, car lui seul a un sens quand on partage une référence. Remarque aussi que x est déclaré avec let et qu'on modifie pourtant valeur : avec une classe, let fige la référence (tu ne peux pas réassigner x), pas le contenu de l'objet.

Note

Image mentale : un struct est comme une feuille que tu photocopies avant de la donner ; chacun griffonne sur sa copie. Une class est un tableau blanc accroché au mur : tout le monde écrit dessus, tout le monde voit la même chose.

Modéliser un CompteBancaire avec un struct

Construisons le fil conducteur. Un compte a un titulaire et un solde, et expose des opérations. On commence par un struct, comme le recommande Apple.

L'appel CompteBancaire(titulaire:solde:) utilise l'initialiseur memberwise que Swift génère pour toi tant que tu n'écris pas le tien : un paramètre par propriété stockée, dans l'ordre de déclaration. Gratuit, et nommé clairement façon API Apple.

Propriétés calculées et observateurs

Toutes les propriétés ne sont pas stockées en mémoire. Une propriété calculée n'occupe pas d'espace : elle se recalcule à chaque lecture à partir d'autres données. On la reconnaît à son bloc { ... } au lieu d'une valeur.

À l'inverse, un observateur se greffe sur une propriété stockée et réagit quand sa valeur change. willSet s'exécute juste avant l'affectation (la future valeur s'appelle newValue), didSet juste après (l'ancienne s'appelle oldValue).

Muter un struct : le mot-clé mutating

Voici une conséquence directe du « type valeur ». Une méthode de struct ne peut pas modifier ses propres propriétés sauf si tu la marques mutating. Sans ce mot-clé, le compilateur refuse : il protège la valeur.

Conséquence : appeler une méthode mutating exige une variable var. Sur un compte déclaré let, perso.deposer(50) ne compile pas — la valeur est figée dans son intégralité. C'est de la sûreté : tu vois au type de la déclaration si l'objet peut changer.

Initialiseurs : memberwise gratuit vs init explicite

Les classes n'ont pas d'initialiseur memberwise gratuit. Si tes propriétés n'ont pas de valeur par défaut, tu dois écrire un init qui les remplit toutes ; sinon le code ne compile pas. À l'intérieur, self distingue la propriété du paramètre quand ils portent le même nom.

lazy var et static

Deux modificateurs utiles. Une propriété lazy var n'est calculée qu'au premier accès — parfait pour un calcul coûteux qu'on veut éviter tant qu'on n'en a pas besoin. Une propriété ou méthode static appartient au type lui-même, pas à une instance : une seule, partagée par tous.

Note

Une lazy var est forcément déclarée avec var (jamais let), et son premier accès écrit sa valeur dans l'instance. Lire b.rapportComplet revient donc à muter b : il faut un var, et cette propriété ne peut pas être lue sur un struct rangé dans une constante let. C'est pour ça que b est un var ci-dessus.

Quand choisir struct, quand choisir class

Apple est clair : struct par défaut. La sémantique de copie élimine des classes entières de bugs (personne ne modifie ta valeur dans ton dos). Tu passes à une class seulement si l'un de ces besoins apparaît :

  • Identité : tu veux savoir si deux variables désignent le même objet (===), pas juste deux valeurs égales.
  • Partage voulu : plusieurs parties du code doivent voir et modifier le même état (ex. : un gestionnaire central, une session).
  • Héritage : tu veux qu'un type dérive d'un autre ; seules les classes héritent en Swift.

Pour notre fil conducteur, un struct CompteBancaire reste le bon choix tant que chaque compte est une valeur autonome. On bascule en classe le jour où plusieurs écrans doivent partager exactement le même compte vivant.

Cas réel

SwiftUI, le framework d'interface d'Apple, illustre la règle à la perfection. Une vue y est un struct jetable, recréé des dizaines de fois par seconde à chaque rafraîchissement de l'écran : la sémantique de copie la rend légère et sans surprise. Mais l'état partagé qui doit survivre à ces recréations et être vu par plusieurs écrans — le modèle de données, un panier, la session — est une class (marquée @Observable ou ObservableObject). Value type pour l'affichage éphémère, reference type pour l'état vivant partagé : exactement le « partage voulu » de cette leçon.

Astuce

Dans le doute, commence toujours par un struct. Le jour où un vrai besoin de partage ou d'identité apparaît, passer à class est un petit refactor local ; l'inverse — traquer un partage involontaire qui corrompt ton état à distance — coûte bien plus cher à déboguer.

Pièges fréquents

Piège fréquent

Croire qu'un struct en let peut quand même muter ses propriétés. Non : let perso = CompteBancaire(...) fige toute la valeur, et perso.deposer(...) ne compile pas. À l'inverse, une class en let ne fige que la référence : x.valeur = 42 reste permis. Confondre les deux mène à des surprises.

Piège fréquent

Utiliser une class « par habitude » (réflexe venu d'autres langages) et se retrouver avec un objet modifié par surprise ailleurs dans le code. En Swift, ce partage involontaire est la source numéro un de bugs d'état. Pars d'un struct ; tu changeras en connaissance de cause.

Pour aller plus loin

Pour aller plus loin

Les structs et enums de Swift adoptent le copy-on-write pour les grosses collections internes : la copie est différée jusqu'à la première écriture, donc « tout copier » reste performant. Tu croiseras aussi class avec final (interdire l'héritage), les deinit (nettoyage à la libération) et la gestion mémoire par comptage de références (ARC). Ce sont les sujets naturels après cette leçon.

Antisèche

Glossaire

Type valeur
Type dont chaque affectation crée une copie indépendante (struct, enum, collections).
Type référence
Type dont l'affectation partage la même instance en mémoire (class).
Identité (===)
Test « est-ce littéralement le même objet ? », réservé aux classes.
Init memberwise
Initialiseur gratuit généré par Swift pour un struct : un paramètre par propriété stockée.
Propriété calculée
Propriété sans stockage, recalculée à chaque lecture à partir d'autres données.
Observateur
willSet / didSet : bloc exécuté juste avant / après l'écriture d'une propriété stockée.
mutating
Mot-clé autorisant une méthode de struct à modifier ses propres propriétés.
lazy
Propriété calculée au premier accès seulement, puis mémorisée.

Récap et vérification

  • struct = type valeur : chaque affectation copie ; les valeurs sont indépendantes.
  • class = type référence : l'affectation partage le même objet ; === teste l'identité.
  • Propriété calculée (var aire: Double { ... }) vs stockée ; observateurs willSet/didSet sur le stocké.
  • mutating autorise une méthode de struct à modifier ses propriétés (et exige une instance var).
  • Init memberwise gratuit pour les structs ; init obligatoire pour une classe sans valeurs par défaut ; self lève l'ambiguïté.
  • lazy var = calcul différé au premier accès ; static = membre du type, partagé.
  • Choisis struct par défaut ; class pour identité, partage voulu ou héritage.

Vérifie ta compréhension

  1. Tu écris var b = a puis b.x = 9. Dans quel cas a.x change-t-il aussi : si a est un struct, ou une classe ? Pourquoi ?
  2. Pourquoi perso.deposer(50) ne compile-t-il pas quand perso est déclaré avec let et que deposer est mutating ?
  3. Quelle est la différence entre une propriété calculée et une propriété stockée munie d'un didSet ?
  4. Cite un cas concret où une class est préférable à un struct, et nomme la raison.
