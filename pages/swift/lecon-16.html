Result et le style fonctionnel

~48 min Intermédiaire Prérequis : leçon 15

À la fin de cette leçon, tu sauras

  • Représenter un succès ou une erreur comme une valeur avec Result<Success, Failure> ;
  • Transformer un Result sans le déballer avec map, mapError et flatMap ;
  • Faire le pont avec throws grâce à Result(catching:) et .get() ;
  • Enchaîner map, flatMap et compactMap sur les optionnels et les collections.
Sommaire de la leçon

Tu connais déjà deux manières de signaler qu'une opération peut rater : l'optionnel (une valeur ou nil, mais sans dire pourquoi c'est nil) et throws (une erreur lancée immédiatement, attrapée sur place). Il manque un troisième outil : pouvoir transporter « le résultat d'une opération — réussie ou échouée » comme une valeur ordinaire, à stocker et à passer plus tard. C'est exactement Result.

Result : deux branches dans une valeur

Result est une énumération générique (chapitre 7) à deux cas : success qui porte la valeur produite, failure qui porte l'erreur. Ses deux paramètres de type disent « quel type de succès » et « quel type d'erreur ».

Produire et lire un Result

Une fonction renvoie un Result comme n'importe quelle valeur — pas de throws, pas de try chez l'appelant. Pour l'exploiter, le switch exhaustif (chapitre 3) tombe à pic : deux cas, le compilateur vérifie que tu les traites tous les deux.

Transformer sans déballer : map, mapError, flatMap

Le vrai intérêt de Result est de le transformer sans écrire un switch à chaque étape. Trois méthodes, dans l'esprit du map des collections (chapitre 4) :

  • map — transforme la valeur de succès, laisse l'échec intact ;
  • mapError — transforme l'erreur, laisse le succès intact ;
  • flatMap — enchaîne une étape qui renvoie elle-même un Result (et évite le Result<Result<…>>).

flatMap sert quand l'étape suivante peut elle aussi échouer. Sans lui, tu obtiendrais un Result imbriqué dans un Result ; flatMap l'aplatit — d'où son nom.

Le pont avec throws

Result et throws ne s'opposent pas : on passe de l'un à l'autre. Result(catching:) exécute un bloc throws et emballe son issue : succès si le bloc renvoie, échec s'il lance. Dans l'autre sens, .get() déballe le succès ou relance l'erreur — utilisable avec try.

Le style fonctionnel de Swift, en résumé

map, flatMap, compactMap, filter, reduce forment une famille cohérente qui traverse tout Swift : sur les collections (chapitre 4), sur les optionnels, sur Result. L'idée commune : transformer une valeur « dans son contexte » (dans un tableau, dans un optionnel, dans un succès) sans en sortir manuellement.

Astuce

Retiens la règle : map transforme la valeur et reste dans le même contexte ; flatMap transforme vers le même contexte (optionnel → optionnel, Result → Result) et aplatit. compactMap, lui, est un map qui écarte les nil. Une fois ce trio compris sur les tableaux, il se lit à l'identique sur les optionnels et sur Result.

Cas réel — pourquoi Result existe

Result a été ajouté à la bibliothèque standard avec Swift 5 (2019), après des années où chaque projet réinventait le sien. Sa raison d'être : les completion handlers asynchrones d'avant async/await. Une requête réseau ne pouvait pas throw (elle finit plus tard, dans une closure) ; on lui passait donc une closure (Result<Data, Error>) -> Void, appelée avec .success ou .failure une fois la réponse arrivée. Aujourd'hui async/await (leçon 11) couvre ce besoin plus élégamment, mais Result reste précieux : stocker une issue, la transporter, la tester, ou modéliser un état « chargé / en erreur » dans une vue.

Pièges fréquents

Piège fréquent

Le type d'échec d'un Result doit être un Error : enum ErreurRecherche: Error. Oublier la conformance à Error provoque une erreur de compilation dès que tu écris Result<…, ErreurRecherche>.

Piège fréquent

Ne confonds pas le map d'une collection (qui s'applique à chaque élément) et le map d'un Result ou d'un optionnel (qui s'applique à l'unique valeur de succès/présente). Même nom, même esprit — mais l'un boucle, l'autre non.

Pour aller plus loin

Pour aller plus loin

Result brille dans les tests : on stocke l'issue d'un appel et on vérifie ensuite .success ou .failure tranquillement. Regarde aussi les typed throws de Swift 6 (func f() throws(MonErreur)), qui rapprochent throws et Result en typant précisément l'erreur lancée — un pas de plus vers la sûreté à la compilation.

Antisèche

Glossaire

Result
Énumération générique à deux cas, success et failure, transportant respectivement une valeur ou une erreur.
success / failure
Les deux cas d'un Result ; un Result est toujours exactement l'un des deux.
map (sur Result)
Transforme la valeur de succès ; laisse un échec passer inchangé.
mapError
Transforme l'erreur d'un Result ; laisse un succès inchangé.
flatMap
Enchaîne une étape qui renvoie elle-même un Result (ou un optionnel), en aplatissant le résultat.
Result(catching:)
Constructeur qui exécute un bloc throws et emballe son issue en Result.
get()
Méthode throws d'un Result : rend la valeur de succès ou relance l'erreur.
compactMap
Variante de map sur une collection qui transforme puis écarte les résultats nil.

Récap et vérification

  • Result<Success, Failure> transporte un succès ou une erreur comme une valeur (le Failure doit être un Error).
  • On le lit avec un switch exhaustif sur .success / .failure.
  • map agit sur le succès, mapError sur l'erreur, flatMap enchaîne une étape renvoyant un Result.
  • Result { try f() } emballe un throws ; try r.get() refait le chemin inverse.
  • map / flatMap / compactMap se lisent pareil sur les collections, les optionnels et Result.
