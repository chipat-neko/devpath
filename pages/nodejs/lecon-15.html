Module 06 · Données, authentification & temps réel — Leçon 15

Connecter une base de données

~36 min Intermédiaire Cours Node.js + notions SQL recommandés

À la fin de cette leçon, tu sauras

  • connecter Node à PostgreSQL avec un pool du pilote pg et une URL lue dans process.env ;
  • exécuter des SELECT et INSERT en async/await avec try/catch et lire result.rows ;
  • protéger tes requêtes de l'injection SQL avec les paramètres $1, $2 au lieu de la concaténation ;
  • enchaîner plusieurs opérations dans une transaction (BEGIN/COMMIT/ROLLBACK) en libérant le client.
Sommaire de la leçon

Depuis la leçon sur l'API REST, ton serveur Express stocke ses livres dans un simple tableau JavaScript. Le problème saute aux yeux dès que tu relances le processus : tout disparaît. Un redémarrage, un crash, un déploiement, et l'historique est vidé. Pour qu'une application garde ses données entre deux exécutions, il lui faut un stockage persistant : une vraie base de données, écrite sur disque et partagée entre plusieurs instances du serveur.

Dans cette leçon, tu remplaces le tableau en mémoire par PostgreSQL, la base relationnelle de référence côté Node. Tu vas installer le pilote, ouvrir un pool de connexions, écrire des requêtes paramétrées pour parer l'injection SQL, brancher tout ça sur tes routes Express, puis gérer une transaction. On reste sur du Node moderne : ESM, async/await et gestion d'erreurs systématique.

Le problème : la mémoire ne survit pas au redémarrage

Un tableau ou une Map vit dans la RAM du processus Node. Quand le processus s'arrête, sa mémoire est rendue au système : les données sont perdues. C'est acceptable pour un cache ou un prototype, jamais pour des données qui comptent.

Deux grandes familles de bases répondent à ce besoin. Les bases relationnelles (PostgreSQL, MySQL, SQLite) organisent les données en tables avec des colonnes typées et des relations, et se requêtent en SQL — c'est l'objet du cours SQL. Les bases NoSQL comme MongoDB stockent des documents proches du JSON. Ici, on choisit PostgreSQL : robuste, gratuit, standard SQL, parfait pour une API REST.

Note

Pour un petit projet local ou des tests, SQLite suffit : tout tient dans un fichier. Node 22+ embarque même un module expérimental node:sqlite, et better-sqlite3 reste une valeur sûre. La logique (requêtes, paramètres) est la même ; seul le pilote change.

Installer et connecter avec un pool

Le pilote officiel de PostgreSQL pour Node s'appelle pg. On l'installe avec npm.

On ne crée pas une connexion unique réutilisée partout : on crée un pool. Un pool maintient un petit groupe de connexions ouvertes et les prête aux requêtes à la demande. C'est plus rapide (pas de poignée de main réseau à chaque appel) et ça encaisse la charge sans saturer la base.

Un seul pool pour toute l'application, exporté depuis un module dédié. On l'importe partout où on requête.

Piège fréquent

Ne mets jamais l'URL ou le mot de passe en dur dans le code. Ils finiraient dans Git, visibles de tous. Lis-les depuis process.env (vu en leçon process/env) et garde le secret dans un fichier .env ignoré par Git, ou dans les variables de ton hébergeur.

Requêter avec async/await

La méthode pool.query() renvoie une promesse. On l'attend avec await, dans un try/catch pour ne jamais laisser une erreur réseau ou SQL filer sans réponse. Le résultat est un objet ; les lignes renvoyées sont dans result.rows (un tableau d'objets).

Chaque ligne de result.rows est un objet dont les clés sont les noms de colonnes. Un SELECT id, titre FROM livres te donne donc [{ id: 1, titre: "..." }, ...], prêt à être renvoyé en JSON.

Piège fréquent

Oublier le try/catch autour d'un await pool.query(...) produit un rejet de promesse non géré. En Node moderne, un unhandled rejection peut faire tomber tout le processus. Enveloppe toujours tes requêtes.

Requêtes paramétrées : la défense anti-injection

Voici la règle la plus importante de la leçon. Quand une requête dépend d'une donnée venue de l'utilisateur (un id, un titre, un filtre), tu ne la concatènes jamais dans la chaîne SQL. Tu utilises des paramètres numérotés $1, $2, et tu passes les valeurs dans un tableau à part. Le pilote les transmet séparément du texte SQL : elles ne peuvent plus être interprétées comme des instructions.

Le second argument de query() est le tableau des valeurs, dans l'ordre des $1, $2, etc. PostgreSQL les traite comme des données pures : un titre piégé est cherché tel quel et ne trouve rien, au lieu de s'exécuter.

Astuce

Mémorise la règle : aucune donnée utilisateur dans la chaîne SQL. Si tu te surprends à écrire un `${...}` à l'intérieur d'une requête, arrête-toi : c'est presque toujours un $1 qu'il faut.

Cas réel — pourquoi $1 n'est pas un détail

L'injection SQL n'est pas une curiosité théorique : elle est restée pendant des années en tête du classement OWASP des risques web les plus courants, et figure encore aujourd'hui dans la catégorie « Injection ». De grandes fuites de données — millions d'identifiants, d'e-mails, parfois de numéros de carte — sont parties d'un seul champ concaténé dans une requête : un formulaire de recherche, un paramètre d'URL, un login. Le correctif est presque toujours le même que ta leçon : remplacer la concaténation par des requêtes paramétrées. La blague de la BD « Bobby Tables » (un élève prénommé Robert'); DROP TABLE eleves;-- qui efface le fichier de l'école) illustre exactement ce que $1 empêche. Prendre ce réflexe dès le premier SELECT, c'est fermer d'emblée la faille la plus exploitée du web.

Brancher sur des routes Express

On remplace maintenant le tableau en mémoire par de vraies lectures et écritures en base. La route GET /livres lit toutes les lignes ; POST /livres insère un livre et le renvoie grâce à la clause RETURNING, qui demande à PostgreSQL de retourner la ligne créée (avec son id généré).

Chaque route enveloppe sa requête dans try/catch et choisit un code HTTP : 201 pour une création, 400 pour une entrée invalide, 500 pour une panne base.

Les transactions : tout ou rien

Certaines opérations touchent plusieurs lignes et doivent réussir ensemble ou échouer ensemble. L'exemple classique est un virement : débiter un compte et créditer un autre. Si la première écriture passe mais que la seconde échoue, l'argent s'évapore. Une transaction garantit l'atomicité : BEGIN ouvre, COMMIT valide tout d'un coup, ROLLBACK annule tout en cas de pépin.

Une transaction doit se dérouler sur un même client du pool (sinon les commandes partiraient sur des connexions différentes). On en emprunte un avec pool.connect(), et on le libère impérativement dans un finally.

Le finally garantit la libération même si COMMIT ou ROLLBACK lève une erreur.

Piège fréquent

Oublier client.release() est une fuite silencieuse : le client n'est jamais rendu, le pool s'épuie connexion après connexion, et au bout de quelques requêtes l'application se fige en attendant un client qui ne reviendra jamais. Mets toujours la libération dans un finally.

Un mot sur les ORM et query builders

Écrire du SQL à la main reste formateur et donne un contrôle total. Mais sur un gros projet, des outils automatisent la corvée. Un query builder comme Knex construit les requêtes en JavaScript. Un ORM comme Prisma ou Drizzle va plus loin : il génère un client typé, gère les migrations (l'évolution du schéma de la base dans le temps) et fait correspondre tes tables à des objets.

Ces outils restent paramétrés contre l'injection par construction. Pour cette leçon, on garde pg et le SQL explicite : tu comprends ce qui se passe vraiment avant de déléguer.

Pièges fréquents

  • Concaténer une entrée dans le SQL. C'est la faille d'injection ; utilise toujours $1, $2 et le tableau de valeurs.
  • Ouvrir une connexion par requête. Crée un seul Pool au démarrage et réutilise-le ; ne fais pas new Pool() à chaque appel.
  • Oublier le try/catch. Un rejet non géré peut faire tomber le processus ; enveloppe chaque await pool.query(...).
  • Mettre l'URL ou le mot de passe en dur. Lis-les depuis process.env ; garde les secrets hors de Git.
  • Ne pas libérer le client d'une transaction. Sans client.release() dans un finally, le pool s'épuie et l'app se fige.

Antisèche

Glossaire

Persistance
Capacité d'une application à conserver ses données entre deux exécutions. La RAM (tableau, Map) est volatile ; une base écrite sur disque survit au redémarrage.
Pool de connexions
Petit groupe de connexions ouvertes vers la base, prêtées aux requêtes puis récupérées. Plus rapide qu'ouvrir une connexion par appel, et il encaisse la charge concurrente.
Pilote pg
Paquet npm officiel qui relie Node à PostgreSQL. Fournit Pool, la méthode query(text, params) et les clients pour les transactions.
Requête paramétrée
Requête où les valeurs utilisateur sont passées à part ($1, $2 + un tableau) plutôt que concaténées. Le moteur les traite comme des données, jamais comme du code.
Injection SQL
Attaque où une entrée piégée, concaténée dans le SQL, détourne la requête (lecture, modification ou destruction de données). Les requêtes paramétrées la neutralisent.
RETURNING
Clause PostgreSQL ajoutée à un INSERT/UPDATE/DELETE pour renvoyer les lignes affectées (avec l'id généré), sans requête supplémentaire.
Transaction
Groupe d'opérations « tout ou rien » : BEGIN ouvre, COMMIT valide l'ensemble, ROLLBACK annule tout en cas d'erreur. À exécuter sur un même client.
ORM / query builder
Outils qui automatisent le SQL : un query builder (Knex) construit les requêtes en JS ; un ORM (Prisma, Drizzle) génère un client typé et gère les migrations du schéma.

Récap et vérification

  • Les données en mémoire disparaissent au redémarrage ; une base relationnelle comme PostgreSQL les rend persistantes.
  • On se connecte avec un Pool du pilote pg, alimenté par process.env.DATABASE_URL (jamais de secret en dur).
  • On requête avec await pool.query(text, params) dans un try/catch ; les lignes sont dans result.rows.
  • Les paramètres $1, $2 protègent de l'injection ; on ne concatène jamais une entrée utilisateur.
  • Une transaction (BEGIN/COMMIT/ROLLBACK) sur un client emprunté, libéré dans un finally, garantit le « tout ou rien ».

Vérifie ta compréhension

  1. Pourquoi préfère-t-on un Pool à une connexion unique réutilisée partout ?
  2. Réécris SELECT * FROM livres WHERE auteur = '${nom}' en version sûre : à quoi ressemblent le SQL et le tableau de valeurs ?
  3. Dans une transaction, où places-tu client.release() et pourquoi ?
