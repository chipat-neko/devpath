Module 04 · Construire un serveur — Leçon 10

Créer un serveur HTTP

~35 min Intermédiaire Module 3 recommandé

À la fin de cette leçon, tu sauras

  • savoir créer un serveur avec http.createServer et server.listen(port), et comprendre le cycle requête/réponse
  • savoir lire une requête (req.method, req.url, req.headers) et consommer son corps par morceaux
  • savoir écrire une réponse (res.statusCode, res.setHeader, res.end) en texte, HTML ou JSON ;
  • savoir router à la main selon la méthode et l'URL, et renvoyer les bons codes de statut (200, 201, 404, 500).
Sommaire de la leçon

Tu sais déjà manipuler fetch et consommer une API depuis le navigateur. Côté serveur, c'est l'autre bout du fil : c'est toi qui reçois les requêtes et qui décides quoi répondre. Node fournit pour cela un module intégré, node:http, sans aucune dépendance à installer. Avant de prendre un framework comme Express (la leçon suivante), il faut comprendre ce qu'il automatise — et pour ça, rien ne vaut un serveur écrit à la main.

Dans cette leçon, tu construis pas à pas un petit serveur HTTP : tu lis la requête entrante, tu écris la réponse, tu routes selon la méthode et l'URL, et tu renvoies du JSON sur quelques routes. Le code est en ES Modules (fichiers .mjs ou "type": "module" dans le package.json) ; je signale les rares différences avec CommonJS.

Le module node:http

Tout part de http.createServer. Tu lui passes une fonction appelée à chaque requête, avec deux objets : req (la requête entrante) et res (la réponse à construire). Puis server.listen(port) met le serveur à l'écoute.

Le préfixe node: indique sans ambiguïté qu'il s'agit du module intégré, pas d'un paquet npm nommé http.

Le processus ne se termine pas : il reste en vie tant qu'il écoute. Ouvre http://localhost:3000 dans un navigateur, ou teste en ligne de commande avec curl. Pour arrêter le serveur, fais Ctrl+C dans le terminal.

Note

En CommonJS, on écrirait const http = require("node:http"); en haut du fichier ; tout le reste est identique. Le module est le même, seule la syntaxe d'import change.

Lire la requête (req)

L'objet req décrit ce que le client demande. Les trois propriétés les plus utiles : req.method (le verbe HTTP, "GET", "POST"…), req.url (le chemin demandé, query string comprise) et req.headers (un objet d'en-têtes, clés en minuscules).

Pour analyser proprement le chemin et la query string, construis une URL à partir de req.url — l'API URL est globale dans Node moderne.

Le corps d'une requête (envoyé avec un POST ou un PUT) n'arrive pas d'un coup : il transite par morceaux (chunks). req est un flux lisible. La façon idiomatique en Node moderne est de l'attendre avec for await, puis d'assembler les morceaux.

Lire le corps est asynchrone par nature : les données arrivent du réseau, on les attend sans figer le serveur. C'est pourquoi le callback de createServer est ici déclaré async.

Écrire la réponse (res)

Trois gestes pour répondre. res.statusCode fixe le code de statut. res.setHeader(nom, valeur) ajoute un en-tête — le plus important étant Content-Type, qui dit au client comment interpréter le corps. res.end(corps) envoie le corps et termine la réponse.

Pour du HTML, change seulement le Content-Type : le navigateur affichera alors une vraie page au lieu d'afficher les balises comme du texte.

Pour du JSON — le cas le plus courant pour une API — sérialise ton objet avec JSON.stringify et annonce le bon type.

Astuce

Tu peux poser code et en-têtes en un seul appel avec res.writeHead(200, { "Content-Type": "application/json; charset=utf-8" }). C'est équivalent à un statusCode suivi d'un setHeader, en plus compact.

Les codes de statut

Le code de statut est la première chose que lit le client : il dit comment s'est passée la requête, indépendamment du corps. Quatre suffisent pour démarrer.

  • 200 OK — la requête a réussi, le corps contient la réponse attendue.
  • 201 Created — une ressource a été créée (réponse typique d'un POST qui ajoute un élément).
  • 404 Not Found — la route ou la ressource demandée n'existe pas.
  • 500 Internal Server Error — une erreur est survenue côté serveur (exception non gérée, par exemple).

Mettons-les en pratique avec une route POST qui crée un produit, et une gestion d'erreur via try/catch. Comme on attend le corps, le callback de createServer doit être async (et l'on réutilise lireCorps vu plus haut).

Note

Choisir le bon code n'est pas cosmétique : les clients, les caches et les outils (navigateur, fetch, monitoring) s'en servent pour décider quoi faire. Un 404 renvoyé avec un statut 200 trompe tout le monde.

Cas réel — les codes de statut, partout autour de toi

La page « 404 » que tu croises sur le web, c'est littéralement res.statusCode = 404. Quand une API te répond « 429 Too Many Requests », un serveur te demande de ralentir. Ces codes ne sont pas décoratifs : Google déréférence les pages en 404, un CDN comme Cloudflare met en cache selon le code, et ton fetch côté client teste response.ok — vrai seulement pour les 2xx. Renvoyer un 200 alors que la ressource n'existe pas, c'est mentir à toute cette chaîne : le client croit avoir réussi, le cache mémorise une erreur, le moteur de recherche indexe une page fantôme. Le bon code au bon moment, c'est ce qui fait qu'un serveur « dialogue » correctement avec tout l'écosystème.

Pourquoi un framework ?

Le serveur ci-dessus fonctionne, mais regarde tout ce qu'on a écrit à la main : parser l'URL, lire le corps morceau par morceau, comparer méthode et chemin avec des if en cascade, sérialiser le JSON, poser les bons en-têtes, gérer le 404… Pour dix routes, ce code devient vite répétitif et fragile.

Pièges fréquents

Piège fréquent

Oublier res.end. Si tu ne termines jamais la réponse, le client attend… jusqu'au timeout. Chaque chemin de ton code doit aboutir à un res.end (ou un res.json avec Express). C'est la cause numéro un des requêtes qui « tournent dans le vide ».

Trois autres pièges classiques :

  • Mauvais Content-Type. Renvoyer du JSON avec text/plain, ou du HTML sans charset=utf-8 (accents cassés). Le type doit correspondre au corps réellement envoyé.
  • Ne pas gérer les routes inconnues. Sans branche « sinon » finale, une URL non prévue ne reçoit aucune réponse — ou une réponse incohérente. Termine toujours par un 404 explicite.
  • Lire le corps de façon synchrone. Le corps arrive par le réseau, en morceaux : il n'existe pas « tout de suite ». Il faut l'attendre (for await sur le flux), jamais le lire d'un coup en supposant qu'il est déjà là.

Pour aller plus loin

Pour aller plus loin

Express (prochaine leçon) reste la référence pour démarrer ; Fastify propose une approche plus rapide et typée. Pour servir en chiffré, regarde node:https (ou, en pratique, un reverse proxy comme Nginx devant ton serveur). Pour pousser des événements du serveur vers le client en continu, explore les Server-Sent Events (un flux text/event-stream qu'on n'arrête jamais). Enfin, dès que le routage se complexifie (paramètres d'URL comme /produits/:id, middlewares), un framework devient indispensable.

Glossaire

HTTP
Protocole du web fondé sur un échange requête → réponse : le client demande, le serveur répond, puis la connexion se libère. Node l'implémente via node:http.
req (requête)
Objet décrivant ce que le client demande : method (verbe), url (chemin), headers (en-têtes) et, pour un POST, un corps lu en flux.
res (réponse)
Objet que tu remplis pour répondre : statusCode, setHeader, puis end(corps) qui envoie et clôt l'échange.
Méthode HTTP
Verbe de la requête indiquant l'intention : GET (lire), POST (créer), PUT/PATCH (modifier), DELETE (supprimer).
Code de statut
Nombre résumant l'issue : 2xx succès (200, 201), 4xx erreur du client (404), 5xx erreur du serveur (500). Lu par navigateurs, caches et moteurs.
Content-Type
En-tête qui annonce le format du corps (text/plain, text/html, application/json) ; sans lui, le client peut mal interpréter la réponse.
Corps (body)
Données transportées : le contenu renvoyé côté réponse, ou envoyé par le client côté requête. Sur une requête, il arrive par morceaux qu'on assemble.
Routage
Choix de la réponse selon la méthode et le chemin. Fait à la main avec des conditions ici ; automatisé par un framework comme Express.

Récap et vérification

  • http.createServer((req, res) => …).listen(port) crée et démarre un serveur sans dépendance.
  • Requête : req.method, req.url, req.headers ; le corps se lit par morceaux avec for await.
  • Réponse : res.statusCode, res.setHeader("Content-Type", …), et res.end(corps) qui termine.
  • JSON : JSON.stringify(objet) + Content-Type: application/json.
  • Routage manuel selon méthode + chemin ; toujours une branche 404 finale et les bons codes (200, 201, 404, 500).

Vérifie ta compréhension
