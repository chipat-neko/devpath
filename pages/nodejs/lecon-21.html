Module 08 · Données et robustesse — Leçon 21

Accès aux données avec un ORM (Prisma)

~35 min Intermédiaire Leçon 15 (bases de données) recommandée

À la fin de cette leçon, tu sauras

  • décrire ton modèle de données dans un schéma Prisma ;
  • créer et appliquer des migrations ;
  • écrire des requêtes typées (création, lecture, relations) ;
  • comprendre l'apport d'un ORM par rapport au SQL brut.
Sommaire de la leçon

Dans la leçon sur les bases de données, on écrivait du SQL brut : efficace, mais verbeux, non typé, et exposé aux fautes de frappe dans les noms de colonnes. La quasi-totalité des projets Node modernes passent par un ORM (Object-Relational Mapping) — une couche qui traduit ton code en SQL, gère les migrations et te donne l'autocomplétion et le typage. Le plus populaire aujourd'hui est Prisma. Cette leçon te le fait adopter.

Un ORM ne remplace pas la compréhension du SQL (le cours SQL reste essentiel) : il la rend plus sûre et plus rapide à écrire.

Pourquoi un ORM ?

Trois apports décisifs :

  • le typage : tes requêtes sont vérifiées par TypeScript ; un nom de champ erroné est une erreur de compilation, pas un bug à l'exécution ;
  • les migrations : l'évolution du schéma est versionnée et reproductible ;
  • la productivité : autocomplétion, relations gérées, moins de code répétitif.

Le schéma Prisma

Tout part d'un fichier schema.prisma qui décrit tes modèles (les tables) et leurs champs. C'est la source de vérité du modèle de données.

On déclare la base (datasource), le générateur de client, puis les modèles. Les relations se décrivent par des champs (posts Post[] côté User, auteur User côté Post) : Prisma gère les clés étrangères pour toi.

Les migrations

À partir du schéma, Prisma génère et applique les migrations — les scripts SQL qui font évoluer la base. Une commande suffit.

Chaque migration est un fichier versionné : l'historique du schéma vit dans le dépôt Git, et l'on peut recréer la base à l'identique sur n'importe quelle machine. Fini les « ALTER TABLE » appliqués à la main et oubliés.

Attention — migrate dev n'est pas pour la production

En développement, prisma migrate dev crée les fichiers de migration et peut réinitialiser la base (perte de données) pour la resynchroniser. En production, on applique les migrations déjà créées avec prisma migrate deploy : cette commande ne fait qu'exécuter les fichiers versionnés, sans jamais réinitialiser. Lancer migrate dev sur une base de prod est une erreur qui peut effacer des données : réserve-le au poste de développement.

Des requêtes typées

On interagit avec la base via le client Prisma, entièrement typé. Création, lecture, filtres : tout est autocomplété et vérifié.

Compare au SQL brut : prisma.user.findMany(...) renvoie un tableau d'objets typés (l'éditeur connaît leurs champs), sans concaténer de chaînes SQL ni risquer d'injection. La requête est aussi protégée par paramétrage automatique.

Charger les relations

Le point fort d'un ORM : récupérer des données liées sans écrire de jointure à la main, grâce à include.

Cas réel — le tableau de bord qui faisait 500 requêtes

Une page liste 200 commandes et, pour chacune, affiche le nom du client. Le code récupère les commandes avec findMany, puis dans une boucle appelle findUnique pour charger le client de chaque commande : 1 requête + 200 requêtes, le fameux N+1. En local avec 5 lignes de test, invisible ; en production avec 200, la page rame et la base sature. La correction tient en une ligne : un seul findMany({ include: { client: true } }) charge tout d'un coup. La leçon générale : quand une liste devient lente, active la journalisation des requêtes de Prisma (new PrismaClient({ log: ['query'] })) et regarde combien de SELECT partent réellement.

Astuce

La commande npx prisma studio ouvre une interface web pour visualiser et éditer tes données directement : un tableur connecté à ta base, idéal en développement pour vérifier ce que tes requêtes ont écrit.

Pour aller plus loin

Un ORM n'est pas magique : il faut surveiller les requêtes générées (Prisma peut les journaliser) pour éviter le piège du N+1 (une requête par élément d'une boucle). include et select permettent de charger juste ce qu'il faut. Pour des cas pointus, Prisma offre aussi $queryRaw pour du SQL brut typé. L'ORM gère 95 % des cas ; ta connaissance du SQL gère les 5 % restants — c'est pourquoi les deux comptent.

Antisèche

Glossaire

ORM
Object-Relational Mapping : couche qui traduit ton code en SQL et fait correspondre les lignes d'une table à des objets. Apporte typage, migrations et productivité, sans remplacer la compréhension du SQL.
Prisma
ORM moderne pour Node/TypeScript : un schéma déclaratif, un client entièrement typé, un système de migrations et un outil visuel (Studio).
schema.prisma
Fichier qui décrit la source de données, le générateur de client et les modèles (tables) avec leurs champs et relations. Source de vérité du modèle de données.
Migration
Script SQL versionné qui fait évoluer le schéma de la base. Rangé dans Git, il rend l'évolution reproductible sur toutes les machines.
Client Prisma
Objet généré (@prisma/client) qui expose des méthodes typées : create, findMany, findUnique… avec autocomplétion et vérification des champs.
Relation
Lien entre deux modèles (par ex. un User a plusieurs Post). Prisma gère la clé étrangère ; include charge les données liées en une requête.
Problème N+1
Anti-pattern où l'on déclenche une requête par élément d'une liste (1 requête + N requêtes). On l'évite avec include/select qui chargent le nécessaire d'un coup.
connect
Option de create/update qui relie l'enregistrement à un autre déjà existant via son identifiant, plutôt que d'en créer un nouveau.

Récap et vérification

  • Un ORM traduit ton code en SQL : typage, migrations, productivité.
  • Le schéma Prisma (schema.prisma) décrit modèles et relations ; prisma migrate versionne l'évolution.
  • Le client typé : create, findMany, findUnique, filtres where ; include charge les relations.
  • L'ORM complète, sans remplacer, la compréhension du SQL ; surveiller le N+1.

  2. À quoi sert une migration Prisma ?
  3. Comment charge-t-on les données liées d'un modèle ?
