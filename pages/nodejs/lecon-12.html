Middleware, données et erreurs

~30 min Avancé Leçon 11 recommandée

À la fin de cette leçon, tu sauras

  • comprendre la chaîne de middlewares Express et le rôle de next() ;
  • brancher les middlewares intégrés et tiers (express.json, logger, cors, fichiers statiques) et écrire les tiens ;
  • centraliser les erreurs avec le middleware spécial à quatre arguments et transmettre les erreurs asynchrones à next(err) ;
  • renvoyer les bons codes HTTP (400, 401, 404, 500) avec des messages clairs.
Sommaire de la leçon

Tu sais maintenant créer une application Express et déclarer des routes. Mais une vraie API ne se limite pas à répondre : il faut lire le corps des requêtes, journaliser le trafic, vérifier une autorisation, et surtout ne jamais planter sur une erreur. Tout cela passe par un seul concept central : le middleware.

Dans cette leçon, tu vas comprendre la chaîne de traitement d'Express, écrire tes propres middlewares, et mettre en place un gestionnaire d'erreurs robuste qui renvoie des codes HTTP corrects. Les exemples utilisent les ES Modules (import) avec un Node LTS récent.

Le middleware : une fonction dans la chaîne

Un middleware est simplement une fonction qui reçoit trois arguments : (req, res, next). À chaque requête, Express exécute les middlewares dans l'ordre de leur déclaration, comme une chaîne de montage. Chaque maillon peut lire ou modifier req et res, puis appelle next() pour passer la main au suivant — ou répond directement pour arrêter la chaîne.

Un middleware déclaré avec app.use s'exécute avant la route.

Une route comme app.get('/', handler) n'est rien d'autre qu'un middleware monté sur un chemin et une méthode précis. Le gestionnaire final ne rappelle pas next() : il termine la chaîne en envoyant une réponse.

La gestion des erreurs : le middleware à quatre arguments

Express reconnaît un middleware d'erreur à sa signature : il prend quatre arguments, (err, req, res, next). Tu le déclares en dernier, après toutes tes routes. Dès qu'un middleware appelle next(err) avec un argument, Express saute directement à ce gestionnaire.

Le gestionnaire d'erreurs centralise toutes les réponses d'échec à un seul endroit.

Note

Express 5 transmet désormais les rejets de promesses à next(err) tout seul : un handler async qui lève une erreur atteint le gestionnaire sans wrapper. Tant que tu vises Express 4 (encore très répandu), garde le wrapper ou try/catch.

Les bons codes et messages HTTP

Un client (navigateur, app mobile, autre service) lit d'abord le code de statut. Choisis-le avec soin :

  • 400 Bad Request : l'entrée est invalide (champ manquant, mauvais type).
  • 401 Unauthorized : authentification absente ou erronée (jeton invalide).
  • 404 Not Found : la ressource demandée n'existe pas.
  • 500 Internal Server Error : un bug ou une panne côté serveur (à ne jamais détailler au client).

Une entrée invalide se solde par un 400 explicite, jamais par un plantage.

Cas réel — la pile de middlewares que tu traverses sans le voir

Quand tu te connectes à un site ou que ton app mobile charge ton fil d'actualité, la requête ne tombe pas directement sur « la route » : elle traverse d'abord une pile de middlewares. Chez la plupart des API en production, l'ordre ressemble à ceci : helmet (en-têtes de sécurité), cors (origines autorisées), un logger qui horodate chaque appel, un rate limiter qui bloque les abus, express.json() qui décode le corps, puis l'authentification (le middleware qui vérifie ton jeton ou ton cookie de session et refuse avec un 401 si tu n'es pas connecté). Ta route n'est atteinte qu'ensuite. Et tout au bout, le gestionnaire d'erreurs central transforme la moindre exception en réponse JSON propre — jamais une trace technique exposée au client. Le petit logger et le requireToken que tu viens d'écrire sont exactement ces maillons-là, en miniature.

Brancher une vraie source de données

Jusqu'ici nos données vivent dans un tableau en mémoire — elles disparaissent au redémarrage. En production, tu interroges une base de données (PostgreSQL, MySQL, SQLite…) via un pilote ou un ORM. L'accès est asynchrone, donc les middlewares async et le gestionnaire d'erreurs prennent tout leur sens.

Note

Écrire les requêtes SQL elles-mêmes dépasse Node : vois le cours SQL du catalogue. Côté Node, retiens surtout d'isoler l'accès aux données dans un module dédié et de laisser remonter les erreurs vers next(err).

Pièges fréquents

Piège fréquent

Oublier next(). Si un middleware ne répond pas et n'appelle pas next(), la requête reste suspendue indéfiniment : le client attend jusqu'au timeout. Chaque chemin de code doit soit répondre, soit appeler next().

Piège fréquent

Le gestionnaire d'erreurs sans ses 4 arguments. Express identifie un middleware d'erreur uniquement par son arité. Si tu écris (err, req, res) à la place de (err, req, res, next), Express le traite comme un middleware normal et ne lui transmet jamais les erreurs.

Piège fréquent

L'ordre des middlewares compte. express.json() doit venir avant les routes qui lisent req.body ; le 404 et le gestionnaire d'erreurs doivent être déclarés après toutes les routes, en dernier.

Pour aller plus loin

Pour aller plus loin

Le paquet express-async-errors capture automatiquement les rejets de promesses sous Express 4 (plus besoin de wrapper). helmet ajoute des en-têtes de sécurité en une ligne. Pour valider les entrées proprement, regarde zod ou joi plutôt que des if manuels. Enfin, dès que l'app grossit, sépare les couches (routes, services, accès aux données) pour garder un code testable.

Glossaire

Middleware
Fonction (req, res, next) intercalée dans le traitement d'une requête. Express les exécute dans l'ordre de déclaration ; chacun lit ou modifie req/res puis passe la main.
next()
Appel qui passe la requête au middleware (ou à la route) suivant. Sans lui, et sans réponse, la requête reste suspendue jusqu'au délai d'expiration du client.
next(err)
Variante avec un argument : elle court-circuite les routes restantes et saute directement au gestionnaire d'erreurs.
Gestionnaire d'erreurs
Middleware spécial à quatre arguments (err, req, res, next), déclaré en dernier. Express l'identifie à son arité et lui transmet les erreurs passées via next(err).
express.json()
Middleware intégré qui lit le corps JSON entrant et peuple req.body. Sans lui, req.body vaut undefined sur un POST.
Middleware tiers
Middleware installé via npm et importé : morgan (journalisation), cors (requêtes cross-origin), helmet (sécurité), etc.
Code de statut HTTP
Nombre qui résume l'issue : 2xx succès, 4xx faute du client (400, 401, 404), 5xx faute du serveur (500).
Erreur asynchrone
Rejet de promesse dans un handler async. Sous Express 4 il faut le transmettre à next(err) (via try/catch ou un wrapper) ; Express 5 le fait tout seul.

Récap et vérification

  • Un middleware est une fonction (req, res, next) exécutée dans l'ordre de déclaration.
  • next() passe au maillon suivant ; next(err) saute au gestionnaire d'erreurs.
  • express.json(), un logger, cors et express.static couvrent les besoins courants.
  • Le gestionnaire d'erreurs a quatre arguments et se déclare en dernier.
  • Dans un handler async (Express 4), transmets les erreurs avec next(err) (try/catch ou wrapper).
  • Choisis le bon code : 400, 401, 404, 500.
