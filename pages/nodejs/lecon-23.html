Module 09 · Node.js en pratique — Leçon 23

Construire un outil en ligne de commande (CLI)

~36 min Intermédiaire Leçon 09 recommandée

À la fin de cette leçon, tu sauras

  • lire les arguments d'une commande avec process.argv ;
  • écrire sur stdout/stderr et renvoyer un code de sortie ;
  • rendre un script exécutable (shebang, champ bin, npx) ;
  • parser proprement les options avec une bibliothèque comme commander.
Sommaire de la leçon

Beaucoup d'outils que tu utilises chaque jour — git, npm, eslint, prettier, vite — se pilotent depuis le terminal, et bon nombre d'entre eux sont écrits en Node.js. Un outil en ligne de commande (CLI, pour command-line interface) lit des arguments, fait un travail, écrit un résultat et renvoie un code de sortie. Node est idéal pour en fabriquer : cette leçon te fait passer d'un script lancé à la main à un vrai outil distribuable.

Lire les arguments : process.argv

Quand tu tapes node salut.js Ada --cri, Node te donne tous les mots de la ligne dans le tableau process.argv. Les deux premiers éléments sont toujours ajoutés par Node : le chemin de l'exécutable node et le chemin de ton script. Tes arguments commencent donc à l'index 2.

Pour un petit script, lire process.argv à la main suffit. Mais dès qu'il y a plusieurs options, des valeurs (--sortie=fichier.txt) ou un ordre libre, ça devient vite fragile : on verra plus bas comment déléguer ce travail.

Entrée, sortie et code de sortie

Un programme de terminal communique par trois flux standard : l'entrée stdin, la sortie stdout et la sortie d'erreur stderr. console.log écrit sur stdout ; console.error écrit sur stderr. À la fin, le programme renvoie un code de sortie : par convention 0 signifie « succès », toute autre valeur « erreur ». C'est ce code que le shell (et une CI) inspecte pour savoir si l'étape a réussi.

Astuce — préfère process.exitCode à process.exit()

process.exit(1) coupe le processus immédiatement : des écritures encore en tampon sur stdout peuvent être perdues. En affectant plutôt process.exitCode = 1 et en laissant la fonction se terminer normalement, Node vide ses tampons puis quitte avec le bon code. Réserve process.exit() aux cas où tu veux vraiment arrêter tout de suite.

Rendre le script exécutable

Taper node salut.js … à chaque fois est fastidieux. On veut une vraie commande salut. Deux ingrédients : un shebang en première ligne du fichier (il indique au système quel interpréteur utiliser), et un champ bin dans package.json (il relie un nom de commande à ton fichier).

La première ligne de salut.js devient #!/usr/bin/env node. En développement, npm link installe la commande localement ; npx salut Ada permet même de l'exécuter sans installation. Une fois publié sur npm, n'importe qui l'obtient d'un npm install -g salut.

Parser proprement : commander

Pour un outil sérieux — options courtes et longues, valeurs, sous-commandes, --help généré automatiquement — on ne réinvente pas le parsing. La bibliothèque commander (ou yargs) fait tout :

Gratuitement, on obtient : la validation de l'argument obligatoire <nom>, l'option --cri, un --version, et un --help propre listant tout. L'outil ressemble désormais aux commandes professionnelles.

Piège fréquent — parser les options à la main

Écrire soi-même la lecture des drapeaux paraît simple, jusqu'à ce qu'il faille gérer --sortie=out.txt et --sortie out.txt, les options combinées -abc, l'ordre libre, les valeurs manquantes, un --help… On réécrit alors, mal, ce que commander fait bien. Node propose aussi parseArgs dans node:util pour les besoins simples, sans dépendance. Réserve le parsing manuel de process.argv aux scripts d'une poignée de lignes.

Cas réel — du script bricolé à l'outil d'équipe

Une équipe automatise la génération de son rapport hebdomadaire avec un rapport.js lancé à la main, aux arguments codés en dur. À chaque nouveau besoin (changer la période, exporter en CSV), quelqu'un édite le fichier. En le transformant en CLI — rapport --semaine 27 --format csv, sous-commandes, --help, champ bin et publication sur le registre npm privé — l'outil devient utilisable par tous sans toucher au code. C'est le chemin qu'ont suivi la plupart des outils du quotidien : eslint, prettier, la CLI de Vite ou de Next.js sont des programmes Node avec un champ bin et un parseur d'arguments.

Pour aller plus loin

Un CLI agréable soigne aussi l'expérience : lire des variables d'environnement (process.env) pour la configuration, colorer la sortie (picocolors, chalk) mais seulement si process.stdout.isTTY, poser des questions interactives (@inquirer/prompts), afficher une barre de progression, et respecter les conventions Unix (--help, --version, code de sortie non nul en cas d'échec). Pour distribuer sans imposer Node, des outils comme pkg empaquettent le tout en un binaire autonome.

Antisèche

Glossaire

CLI
Command-line interface : programme piloté depuis le terminal par des arguments, qui écrit un résultat et renvoie un code de sortie.
Argument / option / drapeau
Un argument est une valeur positionnelle (Ada) ; une option (ou flag) commence par un tiret (--cri, -c) et modifie le comportement.
process.argv
Tableau de tous les mots de la ligne de commande. Les index 0 et 1 sont l'exécutable node et le script ; tes arguments commencent à l'index 2.
stdout / stderr
Les deux sorties standard. stdout porte le résultat (destiné à être réutilisé) ; stderr porte les diagnostics (destinés à l'humain).
Code de sortie
Nombre renvoyé par un programme en se terminant. 0 = succès ; toute autre valeur = erreur. Le shell et la CI s'en servent pour enchaîner ou stopper.
Shebang
Première ligne #!/usr/bin/env node d'un script : elle indique au système d'exploitation quel interpréteur utiliser pour l'exécuter directement.
Champ bin
Section de package.json qui associe un nom de commande à un fichier. C'est ce qui transforme un paquet npm installé en commande disponible dans le terminal.
npx
Commande qui exécute un paquet (souvent un CLI) sans installation préalable, en le téléchargeant temporairement si besoin.

Récap et vérification

  • Tes arguments sont dans process.argv.slice(2) ; les deux premiers éléments appartiennent à Node.
  • Écris le résultat sur stdout, les diagnostics sur stderr, et renvoie 0 en cas de succès.
  • Un shebang + un champ bin transforment ton script en commande ; npx l'exécute sans installation.
  • Pour un vrai outil, délègue le parsing à commander (ou parseArgs) plutôt que de lire process.argv à la main.

Vérifie ta compréhension

  1. Que contiennent process.argv[0] et process.argv[1] ?
  2. Pourquoi écrire les erreurs sur stderr plutôt que stdout ?
  3. À quoi sert le champ bin de package.json ?

Exercice 3Défi

Pourquoi vaut-il mieux process.exitCode = 1 que process.exit(1) juste après un console.log ?

Voir une solution

process.exit(1) arrête le processus immédiatement, sans forcément laisser Node vider ses tampons d'écriture : une sortie encore en attente sur stdout peut être tronquée ou perdue. En affectant process.exitCode = 1 et en laissant le programme se terminer naturellement, Node termine ses écritures puis quitte avec le code voulu. On garde process.exit() pour les arrêts vraiment immédiats.
