Module 05 · Qualité & production — Leçon 13

Environnement, débogage et tests

~32 min Intermédiaire Module 4 recommandé

À la fin de cette leçon, tu sauras

  • savoir séparer config et code avec process.env et un fichier .env chargé via --env-file ou dotenv ;
  • savoir déboguer efficacement avec un console.log structuré, util.inspect et le débogueur node --inspect ;
  • savoir écrire et lancer des tests avec le runner intégré node:test (test, describe, assert) sans framework externe ;
  • savoir outiller la qualité du projet avec ESLint et Prettier, et éviter les pièges de production.
Sommaire de la leçon

Ton code marche sur ta machine. Mais « ça marche chez moi » n'est pas un critère de production. Pour qu'une application Node soit fiable, il faut trois réflexes : sortir la configuration du code, savoir déboguer autrement qu'à coups de console.log dispersés, et tester la logique critique pour qu'une régression se voie tout de suite.

Bonne nouvelle : Node moderne (LTS récent) intègre l'essentiel sans dépendance. Un drapeau natif charge un .env, un débogueur est branché sur les DevTools, et un test runner officiel (node:test) rend les frameworks externes optionnels. On fait le tour, exemples à l'appui.

Configuration par variables d'environnement

Une règle d'or : ce qui change selon l'environnement (URL de base de données, clé d'API, port, niveau de log) ne doit jamais être écrit en dur dans le code. On le lit depuis l'environnement via process.env, un objet dont toutes les valeurs sont des chaînes (ou undefined si absentes).

Le motif « valeur d'env, sinon défaut » avec ?? évite de planter quand une variable optionnelle manque.

En développement, on regroupe ces variables dans un fichier .env à la racine du projet : une ligne CLÉ=valeur par variable. Node sait le charger nativement avec le drapeau --env-file (disponible sur les versions LTS récentes), sans aucune dépendance.

Si tu cibles une version de Node sans --env-file, le paquet historique dotenv fait la même chose. On l'appelle au tout début du point d'entrée pour que process.env soit peuplé avant le reste.

Piège fréquent

Le .env contient des secrets : il ne doit jamais être versionné. Ajoute .env à ton .gitignore et commite plutôt un .env.example sans valeurs sensibles, pour documenter les variables attendues.

Déboguer avec console.log… mais bien

console.log reste l'outil de débogage le plus rapide, à condition de l'utiliser proprement. Passe-lui plusieurs arguments plutôt que de concaténer : il les sépare par une espace et n'écrase pas les types. Et préfère une étiquette explicite pour retrouver la ligne.

Pour les objets profonds, console.log tronque l'affichage au-delà de quelques niveaux. Le module intégré node:util et sa fonction inspect donnent le contrôle : profondeur, couleurs, etc.

Note le préfixe node: pour les modules intégrés : il lève toute ambiguïté avec un éventuel paquet npm du même nom.

Le débogueur intégré : node --inspect

Quand semer des console.log ne suffit plus, mets des points d'arrêt. Lance le script avec --inspect : Node ouvre un canal de débogage que les DevTools de Chrome (ou VS Code) peuvent piloter.

Ouvre ensuite chrome://inspect dans Chrome, clique sur « inspect » en face de ta cible : tu obtiens un débogueur complet (pas-à-pas, pile d'appels, inspection des variables). Dans le code, l'instruction debugger; agit comme un point d'arrêt déclaratif.

Astuce

Pour des logs en production, abandonne console.log au profit d'un logger structuré comme pino ou winston : ils émettent du JSON horodaté, gèrent des niveaux (info, warn, error) et se branchent sur l'agrégateur de logs de ton hébergeur.

Tester avec le runner intégré node:test

Node moderne inclut un test runner officiel : plus besoin d'installer Jest, Mocha ou Vitest pour commencer. On importe test (ou describe/it) depuis node:test et les assertions depuis node:assert. Voici une fonction à tester :

On lance la suite avec node --test : sans argument, Node découvre automatiquement les fichiers nommés *.test.js (ou .mjs/.cjs), les fichiers test.js, ainsi que tout fichier placé dans un dossier test/.

Un test qui échoue fait sortir Node avec un code non nul : parfait pour une intégration continue.

Note

Ajoute un raccourci dans package.json : "scripts": { "test": "node --test" }. Tu lances alors simplement npm test, la convention attendue par la plupart des outils de CI.

Tester une route HTTP

Tester une fonction pure est direct. Pour une route, on veut envoyer une vraie requête et vérifier la réponse, sans démarrer un serveur sur un port fixe. Le runner intégré gère déjà l'asynchrone : une fonction de test async est attendue, et tu peux await un fetch (global depuis Node 18) contre ton serveur de test.

Les hooks before/after montent et démontent le serveur autour des tests.

Pour des suites de tests d'API plus riches (en-têtes, cookies, corps multipart), le paquet supertest reste très répandu : il enveloppe ton serveur et offre une API d'assertions fluide. Mais pour démarrer, fetch + node:test suffisent largement.

Linting et formatage

Deux outils complémentaires verrouillent la qualité du code. ESLint détecte les erreurs probables et les mauvaises pratiques (variable non utilisée, await oublié…). Prettier impose un formatage uniforme, pour ne plus jamais discuter d'indentation en revue. On les installe en dépendances de développement.

Branche-les dans tes scripts package.json ("lint": "eslint .", "format": "prettier --write .") pour que toute l'équipe — et la CI — utilise les mêmes commandes.

Cas réel — comment une équipe tue le « ça marche chez moi »

Sur un vrai projet, ces trois réflexes s'articulent. Config : chaque développeur a son propre .env local (jamais commité), et la production reçoit ses secrets via le tableau de bord de l'hébergeur — le même code tourne partout, seules les valeurs changent. Tests + qualité : à chaque push ou Pull Request sur GitHub, une intégration continue (GitHub Actions) relance automatiquement npm test, npx eslint . et npm audit. Si un test rougit ou qu'ESLint trouve un await oublié, la fusion est bloquée tant que ce n'est pas corrigé. Résultat : une régression ne peut plus arriver en production sans que quelqu'un l'ait vue passer. Le node --test que tu viens d'écrire est exactement la commande qu'exécute ce robot, à chaque contribution.

Pièges fréquents

  • Committer un .env. Tes secrets se retrouvent dans l'historique Git, public ou non. Ajoute-le au .gitignore dès la création du projet, et fais tourner les clés si l'accident est arrivé.
  • Des console.log oubliés en production. Ils polluent les logs, ralentissent, et peuvent fuiter des données. Utilise un logger avec niveaux et coupe le debug en prod via LOG_LEVEL.
  • Aucun test sur la logique critique. Le calcul d'un prix, l'authentification, la validation d'entrée : ce sont précisément les endroits où une régression coûte cher. Teste-les en priorité.
  • Des logs non structurés. Une bouillie de chaînes concaténées est illisible à grande échelle. Émets du JSON (un objet par événement) pour pouvoir filtrer et alerter.

Pour aller plus loin

Pour aller plus loin

pino produit des logs structurés ultra-rapides, jolis en dev via pino-pretty. Le runner intégré mesure la couverture avec node --test --experimental-test-coverage : tu vois quelles lignes ne sont jamais exécutées. Branche ensuite npm test dans une intégration continue (GitHub Actions) pour bloquer toute fusion qui casse les tests. Enfin, node --prof et l'onglet « Performance » des DevTools permettent le profilage quand tu chasses une lenteur.

Antisèche

Glossaire

Variable d'environnement
Valeur fournie au processus par l'extérieur (shell, fichier .env, hébergeur) plutôt que codée en dur. Sert à la config qui change selon l'environnement.
process.env
Objet Node qui expose toutes les variables d'environnement du processus. Ses valeurs sont des chaînes (ou undefined) ; on convertit avec Number(...) au besoin.
.env / --env-file
Fichier CLÉ=valeur regroupant la config de développement. Node le charge nativement avec le drapeau --env-file. Il ne doit jamais être versionné.
dotenv
Paquet npm historique qui charge un .env dans process.env, utile si ta version de Node n'a pas --env-file. Appelé au tout début du point d'entrée.
node:test
Lanceur de tests officiel intégré à Node : test, describe/it, hooks before/after. Aucune dépendance externe pour démarrer.
Assertion
Vérification qui échoue en levant une erreur si une condition n'est pas remplie. node:assert/strict fournit equal, deepEqual, throws, etc.
Débogueur (--inspect)
Canal ouvert par node --inspect que les DevTools ou VS Code pilotent : points d'arrêt, pas-à-pas, inspection des variables. debugger; pose un arrêt dans le code.
ESLint / Prettier
Deux outils complémentaires : ESLint repère les erreurs probables et mauvaises pratiques ; Prettier impose un formatage uniforme pour clore les débats d'indentation.

Récap et vérification

  • Config : lis l'environnement via process.env, regroupe-le dans un .env chargé par --env-file (natif) ou dotenv, et n'oublie jamais le .gitignore.
  • Débogage : console.log avec arguments séparés, util.inspect pour les objets profonds, node --inspect + DevTools pour le pas-à-pas.
  • Tests : node:test + node:assert/strict, structurés avec describe/test, lancés par node --test ou npm test.
  • Routes : fetch contre un serveur sur le port 0, ou supertest pour les cas avancés.
  • Qualité : ESLint repère les bogues, Prettier uniformise le format.

Vérifie ta compréhension

  1. Pourquoi le fichier .env ne doit-il jamais être versionné, et que commite-t-on à la place ?
  2. Quel module et quelle fonction utilises-tu pour afficher un objet profond sans troncature ?
  3. Quelle commande lance toute la suite de tests écrite avec node:test ?
