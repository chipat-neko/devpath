Module 09 · Node.js en pratique — Leçon 27

Projet : concevoir et livrer un service Node complet

~40 min Avancé Synthèse du cours

À la fin de cette leçon, tu sauras

  • organiser un service en couches claires (HTTP, validation, métier, données) ;
  • suivre le parcours d'une requête à travers ces couches ;
  • placer le travail long dans une file et observer le service ;
  • dérouler une checklist « prêt pour la production » avant de livrer.
Sommaire de la leçon

Ce cours a présenté les briques du back-end Node : modules et npm, asynchrone et streams, fichiers et process, serveur HTTP et Express, base de données et authentification, architecture, performance, observabilité, ORM et validation, CLI, parallélisme, tests, files d'attente. Cette dernière leçon les assemble : comment ranger tout cela en un service cohérent, comment une requête le traverse, et ce qu'il faut vérifier avant de le mettre en production. Moins une nouveauté qu'une carte pour relier ce que tu sais déjà.

Une architecture en couches

Un service maintenable se lit comme un empilement de couches, chacune avec une responsabilité unique. La couche HTTP (routes et middleware) traduit le monde extérieur ; la validation (Zod) garantit qu'aucune donnée douteuse ne descend plus bas ; les services portent la logique métier, ignorants d'Express ; la couche données (ORM) parle à la base. À côté, deux préoccupations transverses : une file pour le travail asynchrone, et l'observabilité (journaux, métriques) qui traverse tout.

Le parcours d'une requête

Suivre une requête de bout en bout révèle le rôle de chaque couche. Une POST /taches traverse les middleware (journalisation, authentification), passe la validation du corps, atteint le contrôleur qui appelle un service, lequel écrit via l'ORM ; la réponse remonte. Si le service doit aussi notifier par courriel, il dépose un job dans la file au lieu d'attendre.

Astuce — un service testable sans serveur

Si la logique vit dans des services purs (des fonctions qui reçoivent des données et renvoient des données, sans toucher à req/res), tu peux les couvrir avec node --test sans lancer Express, et même les réutiliser depuis le CLI de la leçon 23. La couche HTTP devient une simple traduction entre le protocole et tes services : fine et sans logique métier.

Prêt pour la production

Un service qui « marche sur ma machine » n'est pas encore livrable. Avant de déployer, on déroule une checklist qui reprend les leçons de production : configuration par variables d'environnement (jamais de secret en dur), tests qui passent en CI, journaux structurés (JSON, pas des console.log épars), arrêt propre (fermer la base et le serveur sur SIGTERM), conteneur reproductible, et pipeline CI/CD.

Piège — la logique métier collée aux routes

La faute la plus fréquente est d'écrire tout le traitement dans le gestionnaire de route : requêtes SQL, règles métier et réponse HTTP mêlées. Ça marche… jusqu'à ce qu'il faille tester, réutiliser depuis un CLI, ou changer d'ORM. Garde les routes maigres (valider, appeler un service, formater la réponse) et mets la substance dans des services indépendants. Le jour où tu remplaces Express par Fastify, seule la fine couche HTTP change.

Cas réel — du prototype au service

Un prototype d'API tenait dans un seul fichier index.js de 800 lignes : routes, SQL et logique entremêlés, secrets en clair, aucun test. Fonctionnel en démonstration, ingérable dès la première évolution. La reprise s'est faite par petits pas : extraire les services (la logique quitte les routes), passer la config en variables d'environnement, ajouter Zod à l'entrée, écrire des tests sur les services, sortir l'envoi de courriels dans une file, enfin conteneuriser et brancher la CI. Aucune réécriture d'un bloc : à chaque étape, l'application tournait toujours. Six semaines plus tard, le même service acceptait de nouvelles fonctionnalités en une après-midi — la structure, invisible pour l'utilisateur, avait tout changé pour l'équipe.

Pour aller plus loin

Pour aller vers l'échelle et la robustesse, explore Fastify (plus rapide, schémas intégrés) ou NestJS (structure en modules et injection de dépendances, à la Angular). Côté exploitation : santé et readiness (/health), OpenTelemetry pour tracer une requête à travers plusieurs services, et un déploiement sans coupure (bleu-vert ou rolling). La forme change, le fond reste celui de cette leçon : des couches nettes, des entrées validées, du travail long délégué, et un service qu'on observe.

Antisèche

Glossaire

Architecture en couches
Organisation d'un service en niveaux à responsabilité unique (HTTP, validation, services, données) où les dépendances pointent vers le bas.
Middleware
Fonction insérée dans le traitement d'une requête Express (authentification, journalisation, gestion d'erreurs). S'exécute avant ou autour du contrôleur.
Service (couche métier)
Code qui porte la logique de l'application, indépendant d'Express et du HTTP : testable seul et réutilisable (CLI, worker).
ORM
Bibliothèque qui traduit objets et requêtes vers la base (ici Prisma). Isole la couche données du reste du service.
Préoccupation transverse
Sujet qui traverse toutes les couches (observabilité, sécurité, file) plutôt que d'appartenir à une seule.
Arrêt propre
Fermeture ordonnée du service sur SIGTERM : on cesse d'accepter des requêtes, on termine celles en cours, on ferme base et connexions.
Variables d'environnement
Configuration fournie hors du code (process.env) : ports, URL de base, secrets — jamais écrits en dur dans les sources.
CI/CD
Intégration et déploiement continus : un pipeline qui, à chaque poussée, build, teste et livre le service automatiquement.

Récap et vérification

  • Un service se range en couches (HTTP, validation, services, données) aux dépendances descendantes.
  • Une requête traverse middleware → validation → contrôleur → service → ORM ; le travail long part dans une file.
  • La logique vit dans des services purs ; les routes restent maigres et remplaçables.
  • Avant de livrer : config par env, tests en CI, journaux structurés, arrêt propre, conteneur, CI/CD.

  3. Où délègue-t-on l'envoi d'un courriel dans ce parcours ?

Exercices

Exercice 1Échauffement

Classe ces éléments dans la bonne couche : app.post("/taches", …), TacheSchema.parse(body), creerTache(data), prisma.tache.create(...).

Voir une solution

HTTP : app.post("/taches", …) (route/middleware). Validation : TacheSchema.parse(body) (Zod). Service : creerTache(data) (logique métier). Données : prisma.tache.create(...) (ORM). L'appel descend HTTP → validation → service → données.

Exercice 2Application

Écris un gestionnaire SIGTERM qui ferme le serveur HTTP puis se déconnecte de la base avant de quitter.

Voir une solution
Exercice 3Défi

Un collègue met tout le code d'une fonctionnalité dans le gestionnaire de route. Donne deux problèmes concrets que cela pose et la correction.

Voir une solution

Problème 1 — non testable : pour tester la logique, il faut lancer un vrai serveur et simuler req/res, ce qui est lourd et lent ; avec un service pur, un simple node --test suffit. Problème 2 — non réutilisable et couplé : impossible d'appeler la même logique depuis un CLI ou un worker, et changer d'ORM ou de framework HTTP oblige à tout rouvrir. Correction : extraire la logique dans un service (fonction qui reçoit des données validées et renvoie un résultat, sans toucher à req/res). La route se réduit à : valider (Zod), appeler le service, formater la réponse. Le code devient testable, réutilisable et découplé du transport.

Mini-projet fil rouge — une petite API HTTP

Pour clore ce cours, écrivons un petit serveur HTTP qui renvoie du JSON. Il réunit le module node:http, createServer, le routage selon req.url et req.method, les codes de statut, l'en-tête Content-Type et JSON.stringify — un condensé de Node.js.

Ce que tu vas construire

Un serveur qui répond à GET /taches par la liste en JSON (200), et par une erreur JSON (404) sur toute autre route.

Étapes

Importer http

Charge le module avec require("node:http") et prépare des données.

Créer le serveur

Avec http.createServer((req, res) => { ... }).

Router

Teste req.url et req.method pour distinguer GET /taches du reste.

Répondre en JSON

Utilise res.writeHead(code, headers) puis res.end(JSON.stringify(...)).

Écouter

Démarre avec serveur.listen(3000, ...).

ProjetFil rouge
