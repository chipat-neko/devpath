Module 07 · Node.js à l'échelle — Leçon 19

Performance et montée en charge

~32 min Avancé Leçon 18 recommandée

À la fin de cette leçon, tu sauras

  • savoir exploiter tous les cœurs avec cluster/PM2 et déporter le CPU-bound dans des worker threads
  • savoir mettre en place un cache (LRU, Redis) et un rate limiting avec expiration et invalidation
  • savoir rendre une application stateless pour la scalabilité horizontale derrière un load balancer
  • savoir mesurer la charge et le lag de l'event loop avec autocannon, clinic et --prof avant d'optimiser.
Sommaire de la leçon

Tu sais déjà construire une API REST, l'authentifier, brancher une base de données et la déployer. Mais une chose est de faire tourner ton application sur ta machine, une autre est de la faire tenir sous des milliers de requêtes par seconde sans s'écrouler. C'est tout l'enjeu de la montée en charge (scaling).

Cette leçon part d'une contrainte fondamentale de Node : son modèle mono-thread. À partir de là, on déroule les leviers concrets — clustering, worker threads, caching, rate limiting, instances stateless — et surtout la discipline qui les sous-tend : mesurer avant d'optimiser.

Le mur du mono-thread

Rappel essentiel : ton code JavaScript s'exécute sur un seul thread, piloté par l'event loop. Les opérations d'I/O (réseau, disque, base) sont déléguées au système et ne bloquent rien. Mais un calcul CPU lourd exécuté en JS monopolise ce thread unique : pendant ce temps, aucune autre requête n'est servie.

Note

Node n'est pas lent : il excelle pour l'I/O concurrent. Le problème vient uniquement du travail CPU-bound exécuté en JS synchrone. La règle d'or : ne jamais bloquer l'event loop plus de quelques millisecondes.

Clustering : utiliser tous les cœurs

Un process Node = un cœur exploité. Sur une machine 8 cœurs, tu en gaspilles 7. Le module cluster lance un process par cœur ; ils partagent le même port, le système répartit les connexions.

En production, on délègue ce travail à PM2, qui gère le clustering, le redémarrage et les logs sans toucher au code applicatif.

PM2 en mode cluster : -i max détecte le nombre de cœurs automatiquement.

Worker threads pour le CPU-bound

Le clustering distribue des requêtes, mais une requête seule contenant un calcul lourd bloque toujours son worker. Pour un calcul intensif ponctuel (traitement d'image, hachage, parsing massif), déporte-le dans un worker thread : un vrai thread séparé qui ne gèle pas l'event loop principal.

Astuce

Créer un worker a un coût. Pour des calculs répétés, utilise un pool de workers (librairie piscina) plutôt que d'en instancier un à chaque appel.

Cas réel — un seul endpoint qui met tout le service à genoux

Scénario classique en production : une API va très bien jusqu'au jour où l'on ajoute un endpoint « générer le rapport PDF » ou « exporter tout l'historique en Excel ». Ce traitement est synchrone et CPU-intensif ; quelques utilisateurs le déclenchent en même temps, et soudain toutes les autres routes — même un simple /ping — deviennent lentes ou expirent. Les tableaux de bord montrent le lag de l'event loop qui explose à plusieurs centaines de millisecondes. Le service n'est pas « tombé » : un unique calcul monopolise le thread. La correction tient en deux temps, exactement ceux de cette leçon : sortir le travail lourd du cycle requête/réponse (worker thread, ou mieux une file d'attente traitée en arrière-plan) et mesurer le lag pour confirmer que le thread principal est de nouveau libre.

Caching : ne pas recalculer deux fois

Le moyen le plus rentable de tenir la charge est souvent de ne pas faire le travail. Un cache stocke un résultat coûteux (requête base, calcul, appel externe) pour le resservir instantanément.

Cache en mémoire (LRU) : rapide, mais local à une instance et perdu au redémarrage.

Cache Redis : partagé entre toutes tes instances, persistant, avec expiration native. C'est le choix pour le scaling horizontal.

Piège fréquent

Un cache sans expiration ni invalidation finit par servir des données fausses. Cache surtout ce qui est coûteux à produire et change peu (catalogue, config, agrégats), pas ce qui doit être exact à la seconde.

Streams : la performance mémoire

Charger un fichier de 2 Go en mémoire pour le renvoyer, c'est multiplier la RAM consommée par le nombre de requêtes simultanées — et tomber en panne. Les streams traitent la donnée par morceaux, à mémoire quasi constante, quelle que soit la taille.

Rate limiting : se protéger de l'abus

Sans limite, un seul client (ou une attaque) peut saturer ton service. Le rate limiting plafonne le nombre de requêtes par IP ou par clé d'API sur une fenêtre de temps.

Sans store partagé, chaque instance compte de son côté : la limite réelle est multipliée par le nombre d'instances.

Scalabilité horizontale : des instances stateless

Scaler verticalement (plus gros serveur) a une limite physique. Scaler horizontalement (plus d'instances derrière un load balancer) est sans plafond — à une condition : chaque instance doit être stateless. Aucun état important ne doit vivre dans la mémoire locale d'un process, car la requête suivante du même utilisateur peut tomber sur une autre instance.

Piège fréquent

Tout état stocké en variable locale (sessions, cache Map, sockets) casse le scaling horizontal dès qu'il y a plus d'une instance. Externalise systématiquement vers Redis ou la base.

Mesurer : profilage et charge

Optimiser sans mesurer, c'est deviner. Avant de toucher quoi que ce soit, génère de la charge et profile pour trouver le vrai goulot d'étranglement.

Surveille en continu le lag de l'event loop : c'est l'indicateur le plus parlant. Un lag qui grimpe = du travail bloque le thread ou une fuite mémoire s'installe.

Pièges fréquents

Piège fréquent

Les erreurs qui reviennent le plus :

  • Bloquer l'event loop : un calcul CPU synchrone gèle toutes les requêtes. Déporte-le en worker thread.
  • État en mémoire locale : sessions ou cache Map en variable globale — casse le scaling horizontal. Externalise vers Redis.
  • Cache sans invalidation ni TTL : sert des données périmées indéfiniment. Toujours une expiration et un del à la mutation.
  • Pas de rate limiting : un seul client peut saturer le service (DoS). Plafonne par IP/clé, avec store partagé.
  • Optimiser au jugé : tu accélères du code qui n'était pas le goulot. Profile d'abord avec autocannon et clinic.
  • Fuite mémoire : event loop lag et RAM qui montent lentement. Surveille, prends des heap snapshots.

Pour aller plus loin

Pour aller plus loin

Au-delà de cette leçon : les files de messages (BullMQ, RabbitMQ) pour sortir le travail lourd du cycle requête/réponse et le traiter en arrière-plan ; le CDN pour décharger les assets statiques ; la mise à l'échelle automatique via Kubernetes (HPA) ; l'observabilité poussée de l'event loop (OpenTelemetry) ; et le tuning V8 (--max-old-space-size, garbage collector) pour les charges mémoire extrêmes.

Antisèche

Glossaire

Event loop
Boucle unique qui pilote l'exécution du JavaScript dans Node. Elle enchaîne les tâches sans bloquer sur l'I/O ; un calcul CPU synchrone la monopolise et fige tout le service.
CPU-bound
Se dit d'un travail limité par le processeur (calcul, hachage, compression), par opposition à l'I/O-bound (réseau, disque). C'est le CPU-bound synchrone qui bloque l'event loop.
Clustering
Lancer plusieurs processus Node (un par cœur) qui partagent le même port ; l'OS répartit les connexions. Géré par le module cluster ou par PM2.
Worker thread
Thread séparé dans le même processus, dédié à un calcul lourd. Il libère l'event loop principal, qui continue de répondre aux requêtes.
Cache
Stockage d'un résultat coûteux pour le resservir vite. En mémoire (LRU, local) ou dans Redis (partagé). Exige une expiration (TTL) et une invalidation à la mutation.
Rate limiting
Plafonnement du nombre de requêtes par IP ou par clé sur une fenêtre de temps. Au-delà, on répond 429 Too Many Requests. Le compteur doit être partagé entre instances.
Stateless
Se dit d'une instance qui ne garde aucun état important en mémoire locale. Condition du scaling horizontal : l'état (sessions, cache) vit dans un store externe.
Event loop lag
Retard accumulé par la boucle d'événements : le meilleur indicateur de santé. Quelques millisecondes est sain ; des dizaines ou centaines signalent un blocage ou une fuite.

Récap et vérification

  • Node est mono-thread : un calcul CPU synchrone bloque toute l'application.
  • Cluster / PM2 exploitent tous les cœurs ; les worker threads déportent le CPU-bound.
  • Le caching (LRU local, Redis partagé) évite de recalculer — avec TTL et invalidation obligatoires.
  • Les streams gardent la mémoire stable sur les gros volumes.
  • Le rate limiting protège de l'abus ; les instances stateless (état en Redis) rendent le scaling horizontal possible.
  • On mesure (autocannon, clinic, --prof, event loop lag) avant d'optimiser.

  2. Quelle différence pratique entre cluster (ou PM2) et un worker thread ?
  3. Pourquoi une session stockée en mémoire locale casse-t-elle le scaling horizontal, et où la mettre à la place ?
