L'asynchrone et la boucle d'événements

~34 min Intermédiaire Module 1 recommandé

À la fin de cette leçon, tu sauras

  • Expliquer pourquoi Node est mono-thread mais non bloquant grâce à la boucle d'événements ;
  • Distinguer le code bloquant (fs.readFileSync) du code asynchrone (fs.readFile) ;
  • Écrire et lire un callback error-first en traitant err en premier ;
  • Convertir une fonction à callback en promesse avec util.promisify.
Sommaire de la leçon

Tu connais déjà async/await et les promesses en JavaScript. Mais d'où vient cette obsession de Node pour l'asynchrone ? La réponse tient en une idée : Node exécute ton code sur un seul thread, et pourtant il encaisse des milliers de requêtes réseau ou de lectures de fichiers en parallèle. Le secret, c'est la boucle d'événements (event loop).

Dans cette leçon, on remonte sous le capot : comment un programme mono-thread reste réactif, pourquoi le code « synchrone » est un piège côté serveur, et comment les premiers patterns asynchrones de Node (les callbacks) fonctionnent. Ça pose les bases avant de passer aux promesses à la leçon suivante. Les exemples sont en ESM (fichier .mjs ou package.json avec "type": "module") ; je signale les différences avec CommonJS quand elles comptent.

Mono-thread mais non bloquant

Quand Node lance ton script, ton code JavaScript tourne sur un unique thread. Il n'y a pas dix copies de ton programme qui s'exécutent en même temps. Pourtant, Node n'attend jamais bêtement qu'un fichier soit lu ou qu'une réponse réseau arrive : il délègue ces opérations d'entrée/sortie (E/S) au système, puis continue à exécuter le reste du code. Quand le résultat est prêt, Node le récupère et déclenche la fonction que tu avais prévue.

C'est le rôle de la boucle d'événements : une boucle infinie qui, à chaque tour, regarde s'il y a des résultats d'E/S terminés et exécute les fonctions associées (les callbacks).

Le « 2 » s'affiche avant le « 3 » : Node n'a pas bloqué sur la lecture, il a continué puis est revenu plus tard.

Note

Le thread qui exécute ton JavaScript est unique, mais Node s'appuie sur une bibliothèque C appelée libuv qui gère, elle, un petit pool de threads pour certaines opérations (fichiers, DNS via dns.lookup, certaines fonctions de chiffrement…). Le parallélisme existe donc, mais en dehors de ton code JavaScript.

Bloquant vs non bloquant

La plupart des modules de Node proposent deux variantes : une version synchrone (suffixe Sync) qui bloque tout le thread jusqu'au résultat, et une version asynchrone qui rend la main immédiatement.

Sur un script en ligne de commande qui lit un fichier puis s'arrête, readFileSync est parfaitement acceptable : c'est simple à lire. Le danger apparaît dans un serveur. Comme le thread est unique, un appel Sync qui prend 200 ms gèle tous les clients connectés pendant ces 200 ms : personne n'est servi tant que l'opération n'est pas finie.

À éviter : la version Sync dans le gestionnaire de requêtes transforme ton serveur en file d'attente à guichet unique.

Piège fréquent

Utiliser une fonction …Sync dans un serveur ou dans une boucle chaude. Réserve le synchrone au démarrage (charger un fichier de config une seule fois) ou aux petits scripts CLI, jamais dans le chemin d'une requête.

Le pattern callback « error-first »

Avant les promesses, l'API historique de Node repose sur les callbacks : tu passes une fonction qui sera appelée quand l'opération est terminée. La convention de Node est stricte : le callback reçoit l'erreur en premier argument, et le résultat ensuite. On parle de callback error-first.

La règle d'or : teste err avant de toucher à data. Si err n'est pas null, le second argument est généralement undefined et n'a aucun sens. Le return après la gestion de l'erreur évite de continuer avec des données absentes.

Piège fréquent

Oublier le premier argument err. Si tu écris (data) => … au lieu de (err, data) => …, ta variable data contient en réalité l'erreur, et la vraie donnée disparaît. Une erreur silencieuse qui plante plus loin sans explication.

Le « callback hell »

Le problème des callbacks apparaît dès qu'on enchaîne plusieurs opérations asynchrones dépendantes. Chaque étape s'imbrique dans le callback de la précédente, et le code dérive vers la droite en escalier : c'est le callback hell (ou « pyramide de la mort »).

Trois opérations seulement, et déjà trois niveaux d'imbrication, avec if (err) répété partout.

Lisibilité en chute, gestion d'erreurs dupliquée, refactoring pénible : c'est exactement ce que les promesses et async/await vont résoudre (leçon 5). Garde ce code en tête, on le réécrira proprement.

Un coup d'œil aux phases de la boucle

La boucle d'événements n'est pas une simple file : elle tourne en phases, chacune dédiée à un type de tâche (minuteries, E/S, etc.). Pas besoin de tout mémoriser, mais trois mécanismes reviennent souvent :

  • setTimeout(fn, 0) : planifie fn dans la phase des minuteries, après un délai minimal.
  • setImmediate(fn) : planifie fn juste après la phase d'E/S du tour courant.
  • process.nextTick(fn) : exécute fn avant que la boucle ne passe à la phase suivante ; c'est le plus prioritaire.

Retiens surtout deux choses : tout le code synchrone s'exécute d'abord, puis l'asynchrone ; et process.nextTick passe avant les autres callbacks. Abuser de nextTick peut d'ailleurs « affamer » la boucle et empêcher les E/S de progresser.

Convertir un callback en promesse avec util.promisify

Beaucoup d'API anciennes n'existent qu'en version callback. Plutôt que de les emballer à la main, Node fournit util.promisify : il transforme une fonction error-first en fonction qui renvoie une promesse, directement utilisable avec await.

promisify attend une fonction respectant la convention error-first ; il rejette la promesse si err est présent, la résout avec data sinon.

Note

Le await au niveau racine (top-level await) n'existe que dans les modules ESM. En CommonJS, place ton await dans une fonction async (par exemple async function main() { … } que tu appelles ensuite).

Astuce

Pour le système de fichiers, tu n'as même pas besoin de promisify : importe node:fs/promises, qui expose directement les versions promesse (import { readFile } from 'node:fs/promises'). Garde promisify pour les bibliothèques tierces qui ne proposent que des callbacks.

Cas réel : une seule requête bloque les mille autres

Cas réel

Une API Node répond en 20 ms… sauf un endpoint qui, à chaque requête, relit et parse un gros fichier de configuration avec readFileSync + JSON.parse (≈ 80 ms de CPU synchrone). Avec peu de trafic, personne ne le remarque. En pic, ces 80 ms figent la boucle d'événements pour tout le monde : la latence P99 grimpe à plusieurs secondes alors qu'aucune requête n'est, prise seule, réellement lente. Le correctif tient aux deux idées de cette leçon : charger le fichier une seule fois au démarrage (là, le synchrone est acceptable) et sortir tout calcul lourd du chemin d'une requête. Sur un thread unique, bloquer une requête, c'est bloquer les mille autres.

Pièges fréquents

  • Appeler une fonction …Sync dans un serveur : le thread unique se bloque et tous les clients attendent. Réserve le synchrone au démarrage ou aux scripts CLI.
  • Oublier de gérer err : le premier argument du callback contient l'erreur. Ne pas le tester, c'est risquer de manipuler des données invalides ou de masquer un échec.
  • Tomber dans le callback hell : au-delà de deux niveaux d'imbrication, passe aux promesses plutôt que de continuer à imbriquer.
  • Croire que ton JavaScript tourne sur plusieurs threads : il s'exécute sur un seul thread. Un calcul lourd et synchrone (boucle massive, parsing géant) bloque tout, même sans E/S.

Pour aller plus loin

Pour aller plus loin

Les promesses et async/await (leçon 5) remplacent les callbacks et aplatissent le callback hell. Pour du vrai calcul parallèle (et non de l'E/S), regarde les worker threads. Et pour comprendre le pool de threads sous le capot, explore libuv : c'est lui qui exécute les lectures de fichiers en arrière-plan sans bloquer ta boucle d'événements.

Antisèche

Glossaire

Boucle d'événements
Boucle interne de Node qui, à chaque tour, exécute les callbacks dont le résultat d'E/S est prêt ; c'est elle qui rend Node non bloquant malgré son thread unique.
Mono-thread
Ton code JavaScript s'exécute sur un seul fil d'exécution : un calcul lourd et synchrone y bloque tout le reste.
Bloquant / non bloquant
Une opération bloquante (…Sync) fige le thread jusqu'au résultat ; une opération non bloquante rend la main aussitôt et prévient plus tard via un callback.
libuv
Bibliothèque C sous Node qui gère la boucle d'événements et un pool de threads pour certaines E/S (fichiers, DNS…), en dehors de ton thread JavaScript.
Callback error-first
Convention Node : le callback reçoit l'erreur en premier argument ((err, data)) ; on teste err avant de toucher à data.
Callback hell
Empilement de callbacks imbriqués qui fait dériver le code « en escalier » ; résolu par les promesses et async/await.
util.promisify
Utilitaire qui transforme une fonction à callback error-first en fonction renvoyant une promesse, utilisable avec await.

Récap et vérification

  • Node exécute ton JavaScript sur un seul thread mais reste non bloquant grâce à la boucle d'événements, qui délègue les E/S.
  • Les fonctions …Sync bloquent le thread : à éviter dans un serveur.
  • Les callbacks suivent la convention error-first : (err, data) => …, et on traite err d'abord.
  • L'imbrication des callbacks mène au callback hell, que les promesses résolvent.
  • util.promisify convertit une fonction à callback en fonction renvoyant une promesse.
