Module 09 · Node.js en pratique — Leçon 24

Paralléliser : worker_threads, child_process et cluster

~38 min Avancé Leçon 04 recommandée

À la fin de cette leçon, tu sauras

  • distinguer un travail I/O-bound (déjà géré) d'un travail CPU-bound (qui bloque) ;
  • décharger un calcul lourd dans un worker_thread ;
  • lancer un programme externe avec child_process ;
  • exploiter plusieurs cœurs derrière un même port avec cluster.
Sommaire de la leçon

Node exécute ton code JavaScript sur un seul thread. C'est un atout pour les entrées/sorties : pendant qu'une requête réseau ou une lecture de fichier est en cours, la boucle d'événements sert d'autres requêtes (leçon 4). Mais un calcul lourd — hacher des milliers de mots de passe, redimensionner des images, parcourir un énorme JSON — occupe ce thread unique : tant qu'il tourne, rien d'autre ne peut avancer. Cette leçon montre comment sortir ce travail du thread principal.

I/O-bound vs CPU-bound

Tout se joue sur cette distinction. Un travail I/O-bound passe l'essentiel de son temps à attendre (disque, réseau, base) : Node délègue l'attente au système et reste libre. Un travail CPU-bound passe son temps à calculer sur le processeur : il n'y a rien à déléguer, et il bloque la boucle.

worker_threads : un thread pour le calcul

Le module node:worker_threads lance un vrai thread JavaScript séparé, avec sa propre boucle d'événements et sa propre mémoire. Le thread principal et le worker communiquent par messages (postMessage / événement message). Pendant que le worker calcule, le principal reste réactif.

child_process : lancer un programme externe

Parfois le travail n'est pas du JavaScript : convertir une vidéo avec ffmpeg, interroger git, appeler un script Python. Le module node:child_process lance un autre programme dans un processus séparé. spawn expose des flux (idéal pour de gros volumes), tandis que exec met toute la sortie en tampon (pratique pour de courtes commandes).

Piège — trois outils, trois problèmes différents

Ne confonds pas : async/await résout l'attente d'I/O (un seul thread suffit) ; worker_threads résout le calcul qui bloque (partager de la mémoire est possible) ; cluster et child_process lancent des processus séparés (mémoire totalement isolée, communication par messages). Mettre un await devant un calcul CPU ne le rend pas parallèle : il bloque toujours la boucle. Mesure d'abord — la plupart des serveurs Node sont I/O-bound et n'ont besoin d'aucun de ces outils.

cluster : exploiter tous les cœurs

Un processus Node n'utilise qu'un cœur. Sur une machine à 8 cœurs, on en gaspille 7. Le module node:cluster duplique le processus en plusieurs workers qui partagent le même port : hors Windows, c'est le processus primaire qui accepte les connexions et les distribue en tourniquet (SCHED_RR), précisément parce que la répartition par le système d'exploitation se révèle mauvaise. On multiplie ainsi le débit d'un serveur I/O-bound.

Astuce — réutilise les workers (un pool)

Créer un thread ou un processus a un coût. Pour un calcul répété, ne fabrique pas un worker à chaque appel : garde un pool de workers déjà démarrés et distribue-leur les tâches. La bibliothèque piscina fournit exactement cela pour worker_threads, avec file d'attente et équilibrage.

Cas réel — l'endpoint qui gelait tout le serveur

Une API génère à la volée une miniature à chaque upload d'image, dans le gestionnaire de la requête. En test, tout va bien. En production, dès que plusieurs utilisateurs envoient des photos en même temps, toutes les requêtes — même les plus simples — se mettent à timer out : le redimensionnement, purement CPU-bound, monopolise le thread unique et bloque la boucle d'événements. Le correctif : déplacer le traitement d'image dans un worker_thread (ou, mieux, dans une file de tâches en arrière-plan — leçon 26). Le thread principal se contente d'accepter la requête et de déléguer ; il redevient instantanément réactif. La leçon générale : sur un serveur Node, traquer le moindre travail CPU synchrone dans le chemin d'une requête.

Pour aller plus loin

Pour partager vraiment de la mémoire entre threads (sans copie), SharedArrayBuffer et Atomics permettent des opérations concurrentes sûres — puissant mais délicat. MessageChannel établit un canal direct entre deux workers. Côté navigateur, les Web Workers reposent sur le même modèle de messages, ce qui rend le concept transférable. Enfin, en production, l'échelle horizontale se fait souvent au niveau orchestrateur (plusieurs conteneurs derrière un load balancer, cf. Kubernetes) plutôt qu'avec cluster seul : les deux approches se combinent.

Antisèche

Glossaire

Thread principal
Le fil d'exécution unique sur lequel Node lance ton code JavaScript et sa boucle d'événements. Le bloquer bloque tout le programme.
I/O-bound
Travail dont le temps est dominé par l'attente d'entrées/sorties (réseau, disque, base). Node le gère nativement sans thread supplémentaire.
CPU-bound
Travail dont le temps est dominé par le calcul sur le processeur. Il bloque la boucle d'événements : il faut un autre thread ou processus.
worker_threads
Module qui lance un vrai thread JavaScript séparé, à mémoire isolée, communiquant par messages (postMessage / parentPort). Pour décharger un calcul.
child_process
Module qui lance un autre programme dans un processus séparé. spawn expose des flux ; exec bufferise la sortie.
cluster
Module qui duplique le processus Node en plusieurs workers partageant le même port ; le primaire répartit les connexions en tourniquet (l'OS s'en charge sous Windows). Exploite plusieurs cœurs.
Pool de workers
Ensemble de workers créés une fois et réutilisés pour enchaîner des tâches, afin d'éviter le coût de création répété (ex. piscina).
IPC
Inter-process communication : échange de messages entre processus séparés (worker de cluster, child_process), la mémoire n'étant pas partagée.

Récap et vérification

  • Node exécute ton code sur un seul thread : parfait pour l'I/O, dangereux pour le calcul.
  • worker_threads décharge un calcul lourd ; la communication se fait par messages.
  • child_process lance un programme externe (spawn en flux, exec bufferisé).
  • cluster (ou PM2) duplique le serveur sur plusieurs cœurs derrière le même port.

Exercices

Exercice 1Échauffement

Classe ces tâches en I/O-bound ou CPU-bound : (a) lire 10 000 lignes d'un fichier, (b) calculer le hachage bcrypt d'un mot de passe, (c) appeler une API météo.

Voir une solution

(a) et (c) sont I/O-bound (attente disque et réseau) : la boucle d'événements les gère sans thread supplémentaire. (b) est CPU-bound : bcrypt calcule intensément et bloque le thread principal — bon candidat pour un worker_thread.

Exercice 2Application

Dans un worker, lis workerData (un tableau de nombres) et renvoie leur somme au thread principal.

Voir une solution
Exercice 3Défi

Un collègue met await devant une fonction qui fait une grosse boucle de calcul, pensant « rendre le serveur non bloquant ». Pourquoi cela ne suffit-il pas ?

Voir une solution

await ne crée aucun parallélisme : il ne fait que suspendre la fonction en attendant qu'une promesse se résolve. Si la promesse enveloppe un calcul synchrone (une boucle qui tourne sur le CPU), ce calcul s'exécute quand même sur le thread principal et bloque la boucle d'événements tout du long. await résout l'attente (I/O), pas le calcul. Pour ne pas bloquer, il faut réellement déplacer le travail hors du thread principal : worker_threads, child_process ou une file de tâches.
