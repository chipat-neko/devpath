Module 09 · Node.js en pratique — Leçon 25

Tester avec le runner natif (node:test)

~36 min Intermédiaire Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • écrire et lancer des tests sans dépendance avec node:test ;
  • structurer avec describe/it et les hooks ;
  • isoler une dépendance avec un mock et de faux timers ;
  • mesurer la couverture et surveiller avec --watch.
Sommaire de la leçon

Longtemps, tester en Node imposait d'installer un framework (Mocha, Jest…). Depuis Node 20, un lanceur de tests est intégré au runtime : le module node:test et la commande node --test. Zéro dépendance, une API stable, un rapport clair et un code de sortie exploitable en CI. La leçon 13 a introduit le pourquoi des tests ; celle-ci en fait un réflexe outillé, du premier assert à la couverture.

Un premier test

Un test associe un nom à une fonction qui exécute du code et affirme un résultat avec assert. Si une assertion échoue, elle lève : le test est marqué en échec. On importe node:assert/strict pour une égalité stricte (pas de coercition surprise).

On lance tout avec node --test : Node découvre les fichiers de test (par convention *.test.js), les exécute et affiche un bilan. Le code de sortie vaut 0 si tout passe, 1 sinon — exactement ce qu'une intégration continue attend.

Organiser : describe, it et les hooks

Pour regrouper des tests liés, on utilise describe (une suite) et it (un cas). Les hooks beforeEach/afterEach s'exécutent autour de chaque test : ils garantissent un état frais, sans fuite d'un test à l'autre.

Isoler : mocks et faux timers

Un test unitaire doit être rapide et déterministe : on ne veut ni vrai réseau, ni vraie horloge. Le runner fournit mock pour remplacer une fonction et observer ses appels, et mock.timers pour contrôler le temps.

mock.fn() crée une fonction espionne qui enregistre chaque appel (callCount, calls[i].arguments). Pour une méthode existante, mock.method(obj, "nom") la remplace le temps du test. Avec mock.timers.enable(), on peut « avancer » le temps (tick) pour tester un setTimeout sans attendre réellement.

Astuce — la boucle rouge/vert avec --watch

node --test --watch relance automatiquement les tests à chaque sauvegarde. Couplé au cycle TDD (écrire un test qui échoue → le rendre vert → refactorer), c'est un retour immédiat, sans quitter l'éditeur. Nomme tes fichiers *.test.js pour qu'ils soient découverts automatiquement, et place-les à côté du code ou dans un dossier test/.

Couverture et surveillance

Le runner sait aussi mesurer la couverture — quelle part du code est exercée par les tests — sans outil tiers : node --test --experimental-test-coverage. Le rapport indique les lignes non couvertes, utile pour repérer un chemin oublié (une branche else, une gestion d'erreur).

Piège — tester l'implémentation plutôt que le comportement

Un test qui vérifie comment le code s'y prend (l'ordre exact des appels internes, une variable privée) casse au moindre refactor, même quand le résultat reste correct : il devient un frein. Teste le comportement observable : pour une entrée donnée, la sortie attendue ; pour une action, l'effet visible. Un bon test survit à une réécriture de l'intérieur tant que le contrat public ne change pas.

Cas réel — le test qui a figé un bug pour de bon

Une fonction totalPanier applique une remise, mais un client signale un total négatif quand la remise dépasse le sous-total. Le correctif tient en une ligne (Math.max(0, …)). Le vrai geste professionnel : avant de corriger, on écrit un test qui reproduit le bug (remise de 30 € sur un panier de 20 € → total attendu 0), on le voit passer au rouge, puis on corrige jusqu'au vert. Ce test de non-régression reste dans la suite : six mois plus tard, une refonte du calcul qui réintroduirait le bug le fera immédiatement échouer en CI. Le test transforme un bug ponctuel en garde-fou permanent.

Pour aller plus loin

Le runner natif suffit pour démarrer et pour la plupart des projets. Vitest ou Jest apportent un confort supplémentaire (snapshots, watch intelligent, écosystème de matchers) si le projet grandit. Pour les tests d'intégration d'une API, supertest envoie de vraies requêtes à ton serveur Express en mémoire. Et l'on complète la pyramide : beaucoup de tests unitaires rapides, quelques tests d'intégration, une poignée de tests bout-en-bout — le tout branché en CI pour bloquer toute régression.

Antisèche

Glossaire

node:test
Lanceur de tests intégré à Node (depuis Node 20). Fournit test, describe, it, les hooks et mock, sans dépendance externe. Se lance avec node --test.
Assertion
Affirmation vérifiable sur un résultat (assert.equal, deepEqual, throws). Si elle est fausse, elle lève et le test échoue. assert/strict évite la coercition.
describe / it
describe regroupe une suite de tests liés ; it (synonyme de test) décrit un cas précis. Pour la lisibilité du rapport.
Hook
Fonction exécutée autour des tests : beforeEach/afterEach (avant/après chaque test) et before/after (une fois par suite). Sert à préparer et nettoyer l'état.
Mock
Remplaçant contrôlé d'une fonction ou méthode (mock.fn, mock.method) qui enregistre ses appels. Isole le test des vraies dépendances (réseau, base).
Faux timers
Horloge simulée (mock.timers) qui permet d'« avancer » le temps à volonté pour tester setTimeout/setInterval sans attendre réellement.
Couverture de code
Proportion du code exécutée par les tests (--experimental-test-coverage). Indicateur des zones non testées, à ne pas confondre avec la qualité des tests.
Test de non-régression
Test écrit pour reproduire un bug corrigé : il reste dans la suite et échoue si le bug réapparaît un jour, figeant définitivement la correction.

Récap et vérification

  • Un test = un nom + une assertion (node:test + assert/strict), lancé par node --test.
  • describe/it organisent ; beforeEach garantit un état frais à chaque test.
  • mock.fn() espionne les appels ; les faux timers contrôlent le temps.
  • La couverture et --watch sont intégrés ; un test de non-régression fige chaque bug corrigé.

Exercice 3Défi

Pourquoi une couverture de 100 % ne garantit-elle pas que le code est correct ?

Voir une solution

La couverture mesure les lignes (ou branches) exécutées par les tests, pas la pertinence des assertions. On peut traverser 100 % du code sans jamais vérifier le bon résultat : un test qui appelle une fonction sans affirmer sa sortie « couvre » la ligne mais ne prouve rien. Pire, la couverture ne dit rien des cas non prévus (entrée vide, valeur limite, erreur) qui n'apparaissent pas dans le code testé. C'est un indicateur des zones non testées, pas une preuve de correction : la qualité vient des cas choisis et des assertions, pas du pourcentage.
