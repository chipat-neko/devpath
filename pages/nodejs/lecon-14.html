Module 05 · Qualité & production — Leçon 14

Bonnes pratiques, sécurité & déploiement

~33 min Avancé Leçon 13 recommandée

À la fin de cette leçon, tu sauras

  • savoir structurer un projet Node sérieux en couches (routes, services, accès aux données) avec une config par environnement ;
  • savoir mettre en place une gestion d'erreurs robuste et un arrêt propre sur SIGTERM ;
  • savoir appliquer les bases de la sécurité (secrets, validation, helmet, npm audit, rate limiting) ;
  • savoir choisir une stratégie de déploiement (pm2, Docker, variables d'environnement) et connaître les pistes pour aller plus loin.
Sommaire de la leçon

Tu sais désormais construire des outils en ligne de commande, lire des fichiers, monter un serveur HTTP et une API REST avec Express. Cette dernière leçon répond à une question différente : comment transformer ce code qui « marche sur ma machine » en une application qu'on peut déployer, exploiter et maintenir sans crainte ? C'est aussi la synthèse du cours : on assemble tout ce que tu as vu.

Le passage en production ne consiste pas à ajouter une fonctionnalité de plus. Il s'agit d'organiser le code, de prévoir ce qui va mal tourner, de fermer les portes aux attaquants et de tenir la charge. On va parcourir cinq chantiers — structure, erreurs, sécurité, performance, déploiement — puis ouvrir les pistes pour la suite.

Structurer un projet sérieux

Un seul fichier app.js de 800 lignes devient vite ingérable. Le réflexe en production est de séparer les responsabilités en couches : les routes reçoivent la requête HTTP, les services contiennent la logique métier, et la couche d'accès aux données parle à la base. Chaque couche ignore les détails de l'autre.

Sépare app.js (qui construit l'application) de server.js (qui la démarre) : tu pourras importer l'app dans les tests sans ouvrir de port.

La config par environnement centralise la lecture de process.env en un seul endroit. Le reste du code importe un objet propre, jamais process.env directement : ainsi tu valides les valeurs une fois pour toutes.

Note

Depuis Node 20.6, tu peux charger un fichier .env sans dépendance avec node --env-file=.env server.js. Pratique en dev ; en production, on injecte plutôt les variables via l'hébergeur ou l'orchestrateur.

Une gestion d'erreurs robuste

En développement, une exception non gérée affiche une trace et tu corriges. En production, elle peut faire tomber le process et couper le service. Deux événements globaux servent de dernier filet de sécurité : uncaughtException (erreur synchrone non rattrapée) et unhandledRejection (promesse rejetée sans catch).

Ces gestionnaires ne sont pas une excuse pour ignorer les erreurs : après une telle erreur, l'état de l'application est inconnu. La bonne pratique est de logger puis de laisser le process redémarrer (un gestionnaire comme pm2 ou l'orchestrateur s'en charge). À côté de ce filet, chaque opération asynchrone garde son try/catch habituel.

L'autre moitié de la robustesse, c'est l'arrêt propre (graceful shutdown). Quand l'hébergeur veut arrêter ton app, il envoie le signal SIGTERM. Plutôt que de couper net au milieu d'une requête, tu fermes le serveur (il finit les requêtes en cours puis n'en accepte plus), tu fermes les connexions à la base, et tu quittes.

.unref() évite que ce minuteur empêche le process de se terminer s'il a fini avant les 10 secondes.

La sécurité, sans compromis

La sécurité n'est pas une option qu'on ajoute à la fin : c'est une discipline. Quelques règles couvrent l'immense majorité des risques d'une API Node.

D'abord, ne jamais committer de secrets. Les clés d'API, mots de passe de base et jetons vivent dans des variables d'environnement, et .env figure dans .gitignore. On versionne seulement un .env.example qui liste les noms attendus, sans valeurs.

Ensuite, valider toutes les entrées. Ne fais jamais confiance au corps d'une requête. Une bibliothèque de schéma comme zod rend la validation explicite et te donne des données déjà typées.

Côté en-têtes HTTP, helmet pose des défenses par défaut (anti-clickjacking, etc.) en une ligne de middleware, et cors contrôle quelles origines peuvent appeler ton API.

Enfin, surveille tes dépendances avec npm audit, et préviens l'injection SQL en utilisant toujours des requêtes paramétrées — jamais de concaténation de chaînes dans une requête (point détaillé dans le cours SQL).

Piège fréquent

Construire une requête par concaténation ("SELECT * FROM users WHERE id = " + req.params.id) ouvre une faille d'injection SQL classique. Passe toujours par des paramètres ("… WHERE id = $1", [id]) : le pilote échappe la valeur pour toi.

Tenir la charge : la performance

Node brille tant que tu restes non bloquant : privilégie les API en version promesse (comme fs/promises), jamais leurs variantes synchrones (readFileSync) dans le chemin d'une requête. Une opération synchrone gèle la boucle d'événements et bloque toutes les requêtes simultanément.

Pour un travail intensif en CPU (calcul lourd, traitement d'image), Node propose deux outils. Le module node:cluster lance plusieurs processus pour exploiter tous les cœurs de la machine ; les worker_threads déportent un calcul dans un fil séparé sans bloquer le principal.

Enfin, la mise en cache évite de recalculer ou de re-interroger la base pour des données stables. Un cache mémoire simple suffit souvent pour commencer ; à plus grande échelle, on utilise un service dédié comme Redis.

Déployer : le tour d'horizon

En local tu lances node server.js. En production, tu veux que l'app redémarre seule si elle plante et qu'elle utilise tous les cœurs. Un gestionnaire de process comme pm2 s'en charge.

L'approche moderne consiste à empaqueter l'app dans un conteneur Docker : une image qui contient Node, ton code et ses dépendances, identique en dev comme en prod. Plus de « ça marchait chez moi ».

npm ci installe exactement les versions du package-lock.json : reproductible, et plus rapide que npm install en CI.

Cette image se déploie ensuite chez un hébergeur (Render, Railway, Fly.io, un VPS, un fournisseur cloud…). Dans tous les cas, les variables d'environnement de production (URL de base, secrets) se configurent via le tableau de bord de l'hébergeur, jamais dans le code ni dans l'image.

Cas réel — le déploiement sans coupure

Chaque fois qu'un service met à jour son code sans « fenêtre de maintenance », c'est un rolling update. L'orchestrateur (Kubernetes, Render, Fly.io…) démarre d'abord les nouveaux conteneurs, attend qu'ils répondent au health check, bascule le trafic dessus, puis envoie un SIGTERM aux anciens. C'est précisément là que ton arrêt propre entre en jeu : les requêtes déjà en vol se terminent (le paiement s'enregistre, le fichier finit de s'uploader), et seulement ensuite le vieux process s'éteint. Sans server.close(), chaque déploiement couperait des connexions en pleine action — l'utilisateur verrait une 502 au pire moment. Les grandes plateformes déploient des dizaines de fois par jour : c'est ce mécanisme, invisible, qui rend ces mises à jour indolores.

Et après

Tu as parcouru tout le chemin : du premier console.log dans un terminal jusqu'à une API structurée, sécurisée et prête à déployer. Tu sais lire des fichiers, gérer l'asynchrone, monter un serveur HTTP, exposer une API REST, écrire des tests avec node:test et mettre tout cela en production. C'est une base solide et très employable.

Pour continuer, voici les pistes naturelles selon ce qui t'attire :

  • Un framework structurant comme NestJS, qui impose une architecture en modules et injecte les dépendances : idéal pour les grosses API d'équipe.
  • Une vraie base de données. Suis le cours SQL, puis branche un ORM comme Prisma pour manipuler tes données en objets typés.
  • TypeScript, qui ajoute des types à JavaScript : moins de bugs, une autocomplétion bien meilleure sur de gros projets.
  • Le temps réel avec les WebSocket (chat, notifications, tableaux de bord vivants).
  • Le full-stack en associant ton API Node à un front React : tu maîtrises alors les deux bouts de la chaîne.

Le serveur n'a plus de secret pour toi. Choisis un projet qui te motive, et construis-le pour de vrai : c'est en livrant qu'on progresse le plus vite.

Checklist production & sécurité

Avant de mettre une app Node en ligne, passe en revue cette liste.

Production :

  • Code séparé en couches ; app.js distinct de server.js.
  • Toute la config lue depuis process.env, validée au démarrage.
  • uncaughtException et unhandledRejection loggés, jamais ignorés.
  • Arrêt propre sur SIGTERM (fermeture du serveur et des connexions).
  • Aucune opération bloquante (...Sync) dans le chemin des requêtes.
  • Process supervisé (pm2 ou orchestrateur) avec redémarrage automatique.
  • NODE_ENV=production, dépendances installées avec npm ci --omit=dev.

Sécurité :

  • Aucun secret dans le dépôt ; .env dans .gitignore, .env.example versionné.
  • Toutes les entrées validées (schéma zod ou équivalent), taille du corps bornée.
  • helmet et cors configurés ; rate limiting actif.
  • Requêtes base paramétrées (jamais de concaténation).
  • npm audit propre ; dépendances à jour.
  • HTTPS en façade ; messages d'erreur sans détails internes côté client.

Pour aller plus loin

Pour aller plus loin

En production, le console.log ne suffit plus : on utilise un logger structuré (comme pino) qui sort du JSON exploitable par les outils d'observabilité. Ajoute une route de health check (GET /health) que l'hébergeur interroge pour savoir si ton app est vivante, et mets en place un pipeline d'intégration continue (GitHub Actions) qui lance npm test et npm audit à chaque push avant tout déploiement.

Antisèche

Glossaire

Architecture en couches
Découpage d'une app par responsabilité : routes (HTTP), services (logique métier), repositories (accès aux données). Chaque couche n'appelle que celle du dessous, ce qui rend le code testable.
Graceful shutdown (arrêt propre)
Séquence d'arrêt qui laisse finir les requêtes en cours : on cesse d'accepter (server.close()), on ferme les ressources, puis on quitte — au lieu de couper net.
SIGTERM
Signal système envoyé par l'hébergeur ou l'orchestrateur pour demander l'arrêt d'un process. On l'écoute avec process.on("SIGTERM", …) pour déclencher l'arrêt propre.
uncaughtException / unhandledRejection
Événements globaux du process : dernier filet pour une erreur synchrone non rattrapée ou une promesse rejetée sans catch. On logge puis on quitte, on n'ignore jamais.
helmet
Middleware Express qui pose en une ligne des en-têtes HTTP de sécurité par défaut (anti-clickjacking, etc.), réduisant la surface d'attaque.
Rate limiting
Limitation du nombre de requêtes par client et par fenêtre de temps (ex. 100 / 15 min / IP) pour contrer les abus et les attaques par force brute.
pm2
Gestionnaire de process Node : relance l'app si elle plante, lance un process par cœur (-i max), centralise les logs. Alternative : l'orchestrateur (Kubernetes).
Conteneur (Docker)
Empaquetage de Node, du code et des dépendances dans une image identique en dev et en prod. npm ci --omit=dev installe des versions exactes et reproductibles.

Récap et vérification

  • Structure : sépare routes, services et accès aux données ; centralise la config ; isole le point d'entrée.
  • Erreurs : pose un filet (uncaughtException, unhandledRejection) et un arrêt propre sur SIGTERM.
  • Sécurité : pas de secrets versionnés, valide les entrées, helmet + cors + rate limiting, npm audit, requêtes paramétrées.
  • Performance : reste non bloquant, node:cluster / worker_threads pour le CPU, cache pour les données stables.
  • Déploiement : un gestionnaire de process (pm2), des conteneurs (Docker), des variables d'environnement injectées par l'hébergeur.
