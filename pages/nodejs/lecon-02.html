Les modules (CommonJS et ESM)

~33 min Intermédiaire Leçon 01 recommandée

À la fin de cette leçon, tu sauras

  • savoir exporter et importer du code avec CommonJS (module.exports, require) ;
  • savoir activer et écrire des ES Modules (export/import) via "type": "module" ou l'extension .mjs ;
  • savoir identifier les différences entre CJS et ESM, dont l'absence de __dirname remplacé par import.meta.url ;
  • savoir charger un module intégré avec le préfixe node: et comprendre la résolution des chemins.
Sommaire de la leçon

Tu connais déjà les modules ES du navigateur : import, export, un graphe de dépendances chargé par balise <script type="module">. Côté serveur, Node ajoute une couche d'histoire : il existait avant que JavaScript ait des modules standardisés, et a donc inventé le sien — CommonJS. Aujourd'hui les deux systèmes coexistent, et savoir lequel tu utilises (et pourquoi) est la première compétence pratique d'un développeur Node.

Cette leçon te donne les deux syntaxes côte à côte, les règles qui décident laquelle s'applique à un fichier .js, et les pièges classiques de la migration. À la fin, tu sauras lire n'importe quel projet Node et écrire des modules propres dans les deux dialectes.

Pourquoi des modules

Un module, c'est un fichier qui encapsule son code et n'expose au reste du programme que ce qu'il décide explicitement d'exporter. Trois bénéfices concrets : découper un gros programme en fichiers à responsabilité unique, réutiliser une fonction à plusieurs endroits sans copier-coller, et encapsuler les détails internes — une variable non exportée reste privée au fichier, elle ne pollue aucun espace global.

La constante TAUX n'existe que dans taxes.js : un autre fichier ne peut ni la lire ni l'écraser.

CommonJS : le système historique

CommonJS (souvent abrégé CJS) est le format d'origine de Node, et reste le format par défaut pour un fichier .js tant que le projet ne déclare pas le contraire. Deux primitives suffisent : module.exports pour publier une valeur depuis un fichier, et require(...) pour la récupérer dans un autre.

Trois cibles, trois écritures : "./fichier" (local), "node:..." (intégré), "nom" (paquet).

Tu peux exporter un objet de plusieurs fonctions (comme ci-dessus) ou une valeur unique. Réassigner module.exports remplace tout l'export ; ajouter des clés à exports les accumule.

Note

Dans un module CJS, Node te fournit gratuitement les variables module, exports, require, __dirname et __filename. Elles ne sont pas globales : Node enveloppe chaque fichier dans une fonction qui les reçoit en paramètres. C'est précisément ce wrapping qui n'existe plus en ESM.

Les ES Modules : le standard moderne

Les ES Modules (ESM) sont la syntaxe officielle du langage : export pour publier, import pour consommer — exactement comme dans le navigateur. Node sait les exécuter, mais il faut le lui signaler, par l'un de ces deux moyens : ajouter "type": "module" dans le package.json (tous les .js du projet deviennent alors des ESM), ou nommer le fichier en .mjs.

Le filet de secours de Node 22.7+

Si le package.json ne dit rien, Node inspecte le fichier : un .js qui contient import/export est réexécuté en ES Module (vérifié : le fichier tourne, sans erreur). C'est un filet, pas une déclaration — il coûte une double analyse, et il s'éteint dès que "type" est posé, fût-ce à "commonjs". Les deux moyens explicites ci-dessus restent donc la bonne pratique.

Avec "type": "module", chaque fichier .js du projet est interprété comme un ES Module.

En ESM, le chemin d'import doit inclure l'extension du fichier ("./taxes.mjs") : pas de résolution implicite comme en CJS.

Astuce

Pour un nouveau projet, choisis l'ESM : c'est le standard, il s'aligne avec le navigateur et les outils modernes. Garde CJS quand tu maintiens du code existant ou que tu dépends d'un paquet uniquement CommonJS. Dans tous les cas, ne mélange pas les deux syntaxes dans un même fichier.

CJS vs ESM : les différences qui comptent

Au-delà de la syntaxe, trois différences de fond changent la façon d'écrire le code.

Cas réel

Beaucoup de paquets très populaires sont passés en ESM pur : chalk (couleurs dans le terminal) depuis la v5, node-fetch depuis la v3, ne s'importent plus avec require(). Un projet CommonJS qui écrit const chalk = require("chalk") après une mise à jour tombe alors sur l'erreur ERR_REQUIRE_ESM. Deux issues : rester sur l'ancienne version majeure (chalk@4), ou migrer le projet en ESM. C'est l'une des raisons concrètes qui poussent tout l'écosystème vers import/export.

Synchrone vs statique. require() est une fonction synchrone : tu peux l'appeler n'importe où, même conditionnellement, et elle bloque jusqu'à ce que le module soit chargé. import est une déclaration statique, analysée avant l'exécution : elle doit être au niveau supérieur du fichier, pas dans un if ni dans une fonction.

Pas de __dirname en ESM. Les variables magiques __dirname et __filename n'existent pas dans un module ES. Pour retrouver le dossier du fichier courant, on part de import.meta.url (une URL file://) qu'on convertit en chemin.

En CJS, __dirname est fourni directement. En ESM, on le dérive de import.meta.url.

Note

Sur Node récent (≥ 20.11 / 21.2), import.meta.dirname et import.meta.filename existent en ESM et te donnent directement l'équivalent de __dirname/__filename — sans passer par fileURLToPath. La forme manuelle ci-dessus reste utile pour les versions plus anciennes.

Les modules intégrés et le préfixe node:

Node embarque une bibliothèque standard : fs (fichiers), path (chemins), http (serveur), os, crypto… Tu n'installes rien, ils sont là. La bonne pratique moderne est de les importer avec le préfixe explicite node:.

Même en CJS, écris require("node:fs") plutôt que require("fs").

Pourquoi ce préfixe ? Il lève toute ambiguïté : node:fs désigne sans équivoque le module intégré, jamais un paquet du même nom que quelqu'un aurait publié sur npm. C'est plus sûr et plus lisible — on voit immédiatement qu'il s'agit d'une API de la plateforme.

La résolution des modules

Quand tu écris un import, Node applique des règles précises selon la forme du spécificateur. Trois familles :

Un spécificateur qui commence par ./ ou ../ est un chemin relatif au fichier courant : c'est ainsi qu'on importe son propre code. Un nom nu (sans ./, sans node:) déclenche la recherche dans node_modules : Node remonte les dossiers parents jusqu'à trouver le paquet. C'est ce mécanisme qui fait fonctionner require("express") sans jamais indiquer le chemin réel du paquet.

Piège fréquent

Oublier le ./ pour un module local : require("utils") ne charge pas ton fichier utils.js voisin, Node va le chercher dans node_modules et lève Error: Cannot find module 'utils'. Pour ton propre code, c'est toujours "./utils".

Pièges fréquents

Piège fréquent

Mélanger require et import sans configuration cohérente. Dans un fichier ESM, require n'est pas défini (ReferenceError: require is not defined) ; dans un fichier CJS, import statique lève une SyntaxError. Décide du format du fichier (via "type" ou l'extension) et tiens-t'y.

  • Attendre __dirname en ESM : tu obtiens ReferenceError: __dirname is not defined. Utilise import.meta.dirname (Node récent) ou dérive-le de import.meta.url.
  • Oublier le ./ ou l'extension : en ESM, import x from "./utils" sans le .js échoue (la résolution d'extension n'est pas automatique comme en CJS). Écris le chemin complet : "./utils.js".
  • Croire que require est paresseux : require("./gros-module") exécute tout le code du module au moment de l'appel, de façon synchrone et bloquante. Un module qui ouvre une connexion ou lit un fichier au chargement le fait dès qu'on l'importe.

Pour aller plus loin

Pour aller plus loin

Plusieurs sujets prolongent cette leçon. Les exports nommés vs défaut : un module peut combiner les deux, mais un seul export default par fichier. L'interopérabilité CJS/ESM : un module ESM peut import un paquet CommonJS (Node expose alors son module.exports comme export par défaut) ; l'inverse — require d'un ESM — passait historiquement par import() dynamique, et fonctionne désormais directement sur les versions récentes de Node (≥ 22.12, rétroporté en 20.19) pour un ESM sans top-level await. Le champ "exports" du package.json permet à un paquet de déclarer ses points d'entrée et de fournir des versions différentes pour CJS et ESM. Enfin, l'import dynamique const m = await import("./module.js") renvoie une promesse : c'est le moyen de charger conditionnellement en ESM, et il fonctionne aussi pour charger un ESM depuis un fichier CJS.

Glossaire

Module
Fichier qui encapsule son code et n'expose au reste du programme que ce qu'il exporte explicitement.
CommonJS (CJS)
Système de modules historique de Node (require/module.exports), synchrone ; format par défaut d'un fichier .js.
ES Modules (ESM)
Système de modules standard du langage (import/export), statique ; activé par "type":"module" ou l'extension .mjs.
export / export default
Publie une valeur d'un module ES : exports nommés (autant qu'on veut) ou export par défaut (un seul par fichier).
require
Fonction CommonJS qui charge un module de façon synchrone et renvoie son module.exports.
import.meta.url
URL file:// du module ES courant ; sert à reconstituer __dirname/__filename, absents en ESM.
Spécificateur
La chaîne passée à import/require : relative (./), intégrée (node:) ou nue (paquet de node_modules).
Import dynamique
import() renvoie une promesse ; il permet le chargement conditionnel en ESM et de charger un ESM depuis un fichier CJS.

Récap et vérification

  • Un module encapsule son code et n'expose que ce qu'il exporte : découper, réutiliser, encapsuler.
  • CommonJS (par défaut pour .js) : module.exports pour exporter, require("./fichier") pour importer.
  • ES Modules : export/import, activés par "type": "module" ou l'extension .mjs.
  • require est synchrone et utilisable partout ; import est statique et au top-level. __dirname existe en CJS, pas en ESM (utilise import.meta.url).
  • Modules intégrés avec le préfixe node: ; résolution : ./ pour le local, nom nu pour node_modules.
