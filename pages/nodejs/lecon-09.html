Process, environnement et système

~26 min Intermédiaire Leçon 08 recommandée

À la fin de cette leçon, tu sauras

  • lire les arguments, variables d'environnement et infos d'exécution via process ;
  • configurer ton app par variables d'environnement au lieu de coder les valeurs en dur ;
  • réagir aux événements du process (exit, SIGINT) et lire le système avec le module os ;
  • construire un petit outil en ligne de commande qui lit process.argv et lance un autre programme avec child_process.
Sommaire de la leçon

Un programme Node ne vit pas dans le vide : il tourne dans un système d'exploitation, lancé par une commande, avec des arguments, un dossier courant et un environnement. Savoir lire ce contexte — et parfois le piloter — c'est ce qui transforme un simple script en véritable outil.

Dans cette leçon, tu vas explorer l'objet global process, apprendre à configurer ton application par variables d'environnement, réagir aux signaux du système, interroger la machine avec le module os, lancer d'autres programmes avec child_process, et enfin assembler tout ça dans un petit CLI.

L'objet global process

process est disponible partout, sans import ni require : c'est le point de contact entre ton code et le processus système qui l'exécute. Voici ses propriétés les plus utiles.

Note

Ces API fonctionnent à l'identique en CommonJS et en ESM : process est un global, tu n'as rien à importer. C'est le rare cas où le choix du système de modules ne change rien.

Lire les arguments avec process.argv

Le piège classique : process.argv ne contient pas que tes arguments. Les deux premiers éléments sont toujours le chemin de node et celui du script. Tes vrais arguments commencent donc à l'indice 2.

Les variables d'environnement pour la configuration

process.env expose les variables d'environnement du système, sous forme d'objet dont toutes les valeurs sont des chaînes (ou undefined si absentes). C'est le moyen standard de configurer une application sans toucher au code : numéro de port, URL de base de données, clé d'API…

Piège fréquent

Ne code jamais un secret en dur (clé d'API, mot de passe) dans un fichier source : il finirait dans Git, visible par tous. Passe toujours par process.env. On verra la gestion fine des secrets et des fichiers .env en leçon 13.

Cas réel — la même image en dev et en prod

Les plateformes modernes (Docker, Heroku, Vercel, Railway…) déploient un artefact unique de ton app. Comment tourne-t-il alors sur un port différent en local et en production, avec une autre base de données ? Réponse : rien n'est codé en dur. Le port vient de process.env.PORT, l'URL de base de process.env.DATABASE_URL, et la plateforme injecte ces variables au démarrage. C'est le principe de la « 12-factor app » : un même code, configuré par l'environnement. Changer un réglage = modifier une variable et redémarrer, sans recompiler ni retoucher une ligne.

Les événements du process

L'objet process est aussi un émetteur d'événements : tu peux écouter des moments clés du cycle de vie ou des signaux envoyés par le système. Les plus courants : exit (le programme se termine), SIGINT (l'utilisateur a fait Ctrl+C) et uncaughtException (une erreur n'a pas été rattrapée).

Le gestionnaire exit doit rester synchrone : à ce stade, plus aucune tâche asynchrone ne s'exécutera.

Note

uncaughtException est un dernier recours, pas un remplaçant du try/catch. Après une telle erreur, l'état du programme est incertain : journalise et quitte, ne reprends pas comme si de rien n'était.

Le module os : interroger la machine

Le module intégré os donne des informations sur le système hôte : processeurs, mémoire, plateforme, dossier personnel. On l'importe avec le préfixe node:, qui rend explicite qu'il s'agit d'un module intégré.

Lancer d'autres programmes avec child_process

Parfois, ton outil doit appeler un autre programme (git, un convertisseur, un script shell). Le module node:child_process sert à ça. Deux approches : exec (simple, met toute la sortie en mémoire — pratique pour de petites commandes) et spawn (en flux, idéal pour de gros volumes ou des sorties continues).

Piège fréquent

Ne construis jamais une commande exec en y concaténant une entrée utilisateur (exec("rm " + nom)) : c'est une faille d'injection de commande. Préfère spawn avec un tableau d'arguments, qui sépare proprement la commande de ses paramètres.

Construire un mini-CLI

Assemblons les pièces : un petit outil qui lit une sous-commande dans process.argv et agit en conséquence. C'est exactement le squelette d'un vrai outil en ligne de commande.

Astuce

Renvoie un code de sortie cohérent : 0 en cas de succès, un code non nul en cas d'erreur. Les scripts qui appellent ton outil (CI, Makefile, autre script) s'appuient dessus pour savoir si tout s'est bien passé.

Pièges fréquents

  • Coder les secrets en dur. Une clé d'API dans le source finit sur Git. Passe toujours par process.env.
  • Supposer un seul OS. Les chemins, séparateurs et dossiers diffèrent. Utilise les modules node:path et node:os plutôt que d'écrire / ou C:\ en dur.
  • Mal lire process.argv. Les indices 0 et 1 sont node et le script : tes arguments commencent à l'indice 2 (d'où le slice(2)).

Piège fréquent

process.exit() coupe le processus immédiatement : une écriture de fichier ou un envoi réseau en cours peut être interrompu. Laisse plutôt le programme se terminer naturellement (en sortant de la fonction), ou réserve exit() aux cas où il n'y a plus aucune tâche asynchrone en attente.

Antisèche

Glossaire

process
Objet global (aucun import) représentant le processus Node en cours : ses arguments, son environnement, son cycle de vie, ses entrées/sorties.
process.argv
Tableau des mots de la ligne de commande. Les indices 0 et 1 sont node et le script ; slice(2) donne les arguments de l'utilisateur.
Variable d'environnement
Réglage fourni hors du code, lu via process.env. Sert à configurer une app (port, URL, clé) selon l'environnement, sans modifier les sources.
Code de sortie
Entier renvoyé au système en fin de programme : 0 signale un succès, toute autre valeur une erreur. Les scripts appelants s'en servent pour enchaîner ou stopper.
Signal
Message envoyé au processus par le système ou l'utilisateur ; SIGINT vient de Ctrl+C, SIGTERM d'un arrêt demandé. On l'écoute pour fermer proprement.
child_process
Module pour lancer d'autres programmes. exec met la sortie en mémoire (petites commandes) ; spawn l'expose en flux (gros volumes, sorties continues).
Module os
Renseigne sur la machine hôte : plateforme, processeurs (cpus()), mémoire (totalmem/freemem), dossier personnel (homedir).
Injection de commande
Faille survenant quand on concatène une entrée utilisateur dans une commande shell. On l'évite avec spawn et un tableau d'arguments séparés.

Récap et vérification

  • process est global : argv (arguments), env (environnement), cwd() (dossier), platform, exit(code).
  • Configure ton app par variables d'environnement ; ne code jamais un secret en dur.
  • Écoute les événements exit, SIGINT et uncaughtException pour réagir au cycle de vie et aux signaux.
  • Le module node:os renseigne sur la machine ; node:child_process lance d'autres programmes (exec vs spawn).
  • Un CLI lit process.argv.slice(2) et renvoie un code de sortie cohérent.

Vérifie ta compréhension

  1. Que contiennent process.argv[0] et process.argv[1], et à quel indice commencent tes propres arguments ?
  2. Pourquoi faut-il lire une clé d'API depuis process.env plutôt que de l'écrire dans le code ?
  3. Dans quel cas exec est-il préférable à spawn, et inversement ?
