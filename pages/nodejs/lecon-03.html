npm et l'écosystème

~33 min Intermédiaire Leçon 02 recommandée

À la fin de cette leçon, tu sauras

  • savoir initialiser un projet Node avec npm init et lire un package.json ;
  • savoir installer des paquets en distinguant dependencies et devDependencies, et comprendre le rôle de node_modules/ et package-lock.json ;
  • savoir écrire et lancer des scripts npm et exécuter un paquet ponctuel avec npx ;
  • savoir interpréter le SemVer (^, ~, version exacte) et auditer la sécurité avec npm audit.
Sommaire de la leçon

Tu sais déjà écrire des modules JavaScript et combiner du code en plusieurs fichiers. Mais un vrai projet ne vit pas isolé : il s'appuie sur du code écrit par d'autres — un framework web, une bibliothèque de dates, un outil de test. npm (le gestionnaire de paquets livré avec Node) est l'outil qui télécharge ce code, en fige les versions, et automatise tes tâches de développement.

Dans cette leçon, tu vas apprendre à initialiser un projet, à installer des dépendances en distinguant ce qui sert en production de ce qui ne sert qu'au développement, à écrire des scripts pour automatiser tes commandes, et à lire les numéros de version pour ne plus jamais « casser » une installation par mégarde. Tout se passe dans un terminal : Node et npm ne tournent pas dans un navigateur.

npm, le gestionnaire de paquets de Node

npm a deux visages. C'est d'abord un outil en ligne de commande (la commande npm, installée automatiquement avec Node). C'est aussi un registre public, npmjs.com, qui héberge des centaines de milliers de paquets réutilisables. Quand tu installes une bibliothèque, npm la récupère depuis ce registre et la dépose dans ton projet.

npm est fourni avec Node : si node répond, npm aussi.

Note

« npm » désigne l'outil, le registre et l'entreprise qui le maintient. Dans la pratique, on dit « npm » pour la commande : npm install, npm run… Les alternatives pnpm et yarn partagent le même registre et des commandes très proches.

Initialiser un projet : package.json

Un projet Node est défini par un fichier package.json à sa racine. Il décrit le projet (nom, version), liste ses dépendances et ses scripts. La commande npm init le crée pour toi ; l'option -y (pour yes) accepte toutes les valeurs par défaut sans poser de questions.

Sans -y, npm pose une série de questions (nom, version, description…).

Le package.json est du JSON strict : pas de commentaires, pas de virgule finale. Si tu en ajoutes, npm refusera de lire le fichier. Pour annoter une config, garde tes notes ailleurs (README, ce cours…).

Installer des dépendances

Pour ajouter un paquet, on utilise npm install (raccourci : npm i). Un paquet utile à l'exécution de ton application va dans dependencies. Un paquet utile seulement pendant le développement (un outil de test, un linter, un formateur) va dans devDependencies, avec l'option -D (ou --save-dev).

zod sert au runtime : c'est une dependency. prettier ne formate ton code qu'en dev : c'est une devDependency.

La distinction compte : en production, on installe souvent avec npm install --omit=dev, qui ignore les devDependencies pour un déploiement plus léger.

L'installation crée (ou met à jour) deux choses : le dossier node_modules/, qui contient le code réel des paquets (et de leurs propres dépendances), et le fichier package-lock.json.

Piège fréquent

On ne versionne jamais node_modules/ : il est volumineux, propre à ta machine, et entièrement reconstructible avec npm install. Ajoute-le à ton .gitignore. À l'inverse, package-lock.json doit être versionné.

package-lock.json : figer les versions exactes

Ton package.json indique des plages de versions (par ex. ^4.4.3). Le package-lock.json, lui, enregistre la version exacte de chaque paquet réellement installé, jusqu'aux dépendances imbriquées. C'est ce qui garantit que toi et tes collègues (et le serveur de déploiement) obtenez exactement le même arbre de dépendances.

npm ci exige un package-lock.json cohérent avec le package.json et ne le modifie jamais.

Astuce

En clonant un projet, lance npm install (ou npm ci) pour recréer node_modules/ à partir des fichiers versionnés. Tu n'as besoin de récupérer que package.json et package-lock.json : le reste se télécharge.

Les scripts npm

Le champ scripts du package.json associe un nom à une commande de terminal. Tu lances ensuite ce nom avec npm run <nom>. Cela évite de retaper de longues commandes et documente les tâches du projet au même endroit.

node --watch relance le script à chaque modification ; node --test lance le test runner intégré (node:test).

start et test sont des noms spéciaux : ils se lancent sans le mot-clé run. Tous les autres scripts exigent npm run.

Un avantage clé : à l'intérieur d'un script, npm ajoute node_modules/.bin/ au PATH. Tu peux donc écrire prettier au lieu d'un chemin complet, alors même que Prettier n'est installé que localement dans le projet.

npx : exécuter sans installer globalement

npx exécute le binaire d'un paquet. S'il n'est pas déjà présent, npx le télécharge temporairement, l'exécute, puis l'oublie : rien n'encombre ton projet ni ta machine. C'est parfait pour les outils qu'on ne lance qu'une fois, comme un générateur de projet.

npx privilégie une version locale si elle existe ; sinon il récupère la dernière version publiée.

Note

Évite npm install -g (installation globale) pour les outils liés à un projet : une dépendance globale n'est pas tracée dans le package.json, donc invisible pour tes collègues. Réserve le global aux utilitaires véritablement transversaux, ou préfère npx.

SemVer : lire et mettre à jour les versions

Les versions suivent le SemVer (Semantic Versioning), au format MAJEUR.MINEUR.CORRECTIF. On incrémente le correctif pour un bug corrigé sans changement d'API, le mineur pour une fonctionnalité rétrocompatible, le majeur pour une rupture de compatibilité. Les préfixes dans package.json indiquent quelles mises à jour npm s'autorise :

Les trois plages, dans l'ordre : ^4.4.3 autorise tout 4.x.x (mineur + correctif, c'est le défaut) ; ~3.7.2 n'autorise que 3.7.x (correctif seulement) ; 1.3.0 sans préfixe verrouille la version exacte.

Ainsi, ^ bloque le passage à une version majeure (potentiellement cassante), ~ est plus strict, et l'absence de préfixe fige la version. Pour suivre l'état de tes dépendances :

npm update respecte les plages : il ne franchit pas une frontière majeure imposée par ^. Pour cela, change la version à la main puis réinstalle.

Sécurité et alternatives

Une dépendance peut contenir une vulnérabilité connue. npm audit compare ton arbre de dépendances à une base de failles publiques et te signale les problèmes, avec leur sévérité.

Lis toujours le rapport avant --force : une montée majeure peut casser ton code.

npm n'est pas seul. pnpm stocke les paquets dans un cache partagé et les relie par liens symboliques : installations plus rapides et bien moins gourmandes en disque. yarn est une autre alternative historique. Les trois lisent le même package.json et le même registre ; les commandes se ressemblent (pnpm install, pnpm add -D <paquet>).

Cas réel

En mars 2016, un développeur retire du registre un paquet minuscule : left-pad, onze lignes qui complètent une chaîne à gauche. En quelques minutes, des milliers de projets — dont React et Babel — cessent de compiler partout dans le monde : ils ne dépendaient pas de left-pad directement, mais l'une de leurs dépendances, oui. C'est toute la leçon de node_modules/ : ton arbre réel est bien plus profond que les quelques lignes de ton package.json. D'où l'importance du package-lock.json (retrouver l'arbre exact) et de npm audit (surveiller ce que tu ne vois pas).

Pièges fréquents

Piège fréquent

Versionner node_modules/ ou supprimer package-lock.json. Le premier alourdit le dépôt pour rien ; le second fait perdre les versions exactes, et chacun se retrouve alors avec un arbre de dépendances potentiellement différent. Règle simple : node_modules/ dans le .gitignore, package-lock.json dans Git.

Piège fréquent

Confondre dependencies et devDependencies, ou installer en global ce qui devrait être local. Si ton code importe un paquet au runtime, il doit être en dependencies : placé dans devDependencies, il manquera en production. Et un outil installé en -g n'apparaît dans aucun package.json : personne ne saura qu'il est requis. Enfin, n'ignore pas npm audit : une faille non traitée dans une dépendance devient ta faille.

Pour aller plus loin

Pour aller plus loin

Les workspaces permettent de gérer plusieurs paquets dans un seul dépôt (un monorepo) : déclare un tableau "workspaces" dans le package.json racine. Explore aussi pnpm pour ses gains de place, la publication d'un paquet avec npm publish (après npm login), et les scripts pre/post : un script nommé prebuild s'exécute automatiquement avant build, et postinstall juste après l'installation des dépendances.

Glossaire

npm
Gestionnaire de paquets de Node : à la fois un outil en ligne de commande et un registre public (npmjs.com).
package.json
Fichier qui décrit le projet, ses scripts et ses dépendances (sous forme de plages de versions).
package-lock.json
Fichier qui fige les versions exactes de tout l'arbre de dépendances ; garantit des installations reproductibles. À versionner.
node_modules/
Dossier contenant le code réel des paquets installés ; volumineux, propre à la machine, non versionné et recréable par npm install.
dependency / devDependency
Paquet requis à l'exécution / paquet requis seulement en développement (tests, lint, build).
SemVer
Semantic Versioning : format MAJEUR.MINEUR.CORRECTIF où chaque niveau signale l'ampleur du changement.
^ (caret) / ~ (tilde)
Plages de mise à jour : ^ autorise mineur + correctif (sans franchir la majeure), ~ le correctif seul.
npx
Exécute le binaire d'un paquet en le téléchargeant temporairement si besoin : parfait pour un outil ponctuel, sans installation durable.

Récap et vérification

  • npm init -y crée le package.json, qui décrit le projet, ses scripts et ses dépendances.
  • npm install <paquet> ajoute une dependency ; -D ajoute une devDependency. node_modules/ n'est pas versionné, package-lock.json oui.
  • Les scripts (npm run <nom>, avec start/test en raccourci) automatisent les tâches ; npx exécute un paquet sans l'installer à demeure.
  • Le SemVer (^, ~, exact) pilote les mises à jour ; npm outdated, npm update et npm audit maintiennent les dépendances à jour et sûres.
