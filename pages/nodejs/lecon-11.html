Module 04 · Construire un serveur — Leçon 11

Une API REST avec Express

~37 min Intermédiaire Leçon 10 recommandée

À la fin de cette leçon, tu sauras

  • Savoir installer Express, créer une app et démarrer un serveur avec app.listen(), puis déclarer des routes qui renvoient du JSON via res.json() et res.status() ;
  • Savoir lire les paramètres de route (req.params), de requête (req.query) et le corps JSON (req.body après express.json()) ;
  • Savoir construire une API CRUD complète en respectant les verbes et les codes de statut HTTP corrects ;
  • Savoir servir des fichiers statiques avec express.static et organiser le code avec express.Router.
Sommaire de la leçon

Tu sais déjà lancer un serveur HTTP « à la main » avec le module node:http : écouter un port, lire req.method et req.url, écrire la réponse avec res.writeHead et res.end. C'est instructif, mais dès qu'il faut router une dizaine de chemins, parser le JSON entrant et gérer les codes de statut, le code devient une forêt de if. Express est le framework qui industrialise tout ça : c'est de loin le plus répandu de l'écosystème Node, et la base que tu retrouveras dans presque tous les projets.

Dans cette leçon, tu construis une vraie petite API REST (des « livres » stockés en mémoire) du premier npm install jusqu'à un Router propre. Tout tourne dans un terminal : tu lances node, le serveur écoute, et tu l'interroges avec curl ou un navigateur. Ton point d'appui : tu maîtrises déjà les fonctions, les objets et l'asynchrone. Ce que tu débloques : exposer des données via HTTP sans réinventer le routage.

Installer Express et démarrer une app

Express est un paquet npm. On part d'un projet vierge, on l'initialise, puis on l'installe.

On choisit ici les ES Modules ; en CommonJS, voir la note ci‑dessous.

Le callback de app.listen confirme que le serveur écoute.

Le processus reste vivant tant que le serveur écoute : arrête‑le avec Ctrl+C.

Note

En CommonJS (sans "type": "module"), remplace l'import par const express = require("express");. Tout le reste est identique. Pour développer, lance node --watch app.js : Node redémarre automatiquement à chaque sauvegarde, sans dépendance externe.

Les routes : verbes, JSON et statut

Une route associe un verbe HTTP et un chemin à un gestionnaire (req, res) => …. Express expose une méthode par verbe : app.get, app.post, app.put, app.delete, app.patch. Pour renvoyer du JSON, res.json() sérialise l'objet et pose le bon en‑tête Content-Type. Pour fixer le code de statut, res.status(code), qui se chaîne avec .json().

Le statut par défaut est 200 ; à toi de l'ajuster selon le résultat.

Les paramètres : route, requête et corps

Trois sources d'entrée à ne pas confondre. Les paramètres de route sont des segments nommés du chemin, déclarés avec : et lus dans req.params. Les paramètres de requête (la query string après ?) arrivent dans req.query. Le corps de la requête (POST/PUT) se trouve dans req.body, mais seulement si tu as activé le parseur JSON.

req.params et req.query contiennent toujours des chaînes : convertis avec Number(...) si besoin.

Piège fréquent

Si tu oublies app.use(express.json()), req.body vaut undefined sur tes routes POST/PUT : une erreur que tout le monde rencontre une fois. Ce middleware ne s'active que pour les requêtes dont le Content-Type est application/json ; pense donc à l'envoyer côté client.

Construire une API CRUD REST

Le style REST mappe les opérations sur les verbes HTTP : GET liste ou détail, POST crée, PUT/PATCH modifie, DELETE supprime. À chaque cas correspond un code de statut conventionnel. Voici une API complète sur une collection en mémoire (un simple tableau : parfait pour apprendre, à remplacer par une base de données en vrai).

Note le return devant chaque res d'erreur : il stoppe le gestionnaire et évite d'envoyer deux réponses.

Quelques requêtes curl pour exercer l'API sans écrire de client.

Note

Mémo des statuts utiles : 200 OK, 201 Créé, 204 Pas de contenu, 400 Requête invalide (faute du client), 404 Introuvable, 500 Erreur serveur (faute du serveur). Un 400 dit « tu m'as mal parlé » ; un 500 dit « j'ai planté ».

Cas réel — les API REST que tu utilises sans le savoir

L'API de GitHub (api.github.com) suit exactement ces conventions : GET /users/octocat renvoie 200 + JSON, une ressource absente renvoie 404. L'API de paiement Stripe : POST /v1/charges crée un paiement (201), une carte refusée répond 402 Payment Required. Quand une app mobile affiche ta liste de tâches, c'est un GET ; quand tu ajoutes une tâche, un POST qui répond 201 ; quand tu la coches, un PATCH. L'API à livres que tu viens d'écrire parle la même grammaire — verbes, chemins, codes — que celle qui fait tourner des services à des millions d'utilisateurs. Apprendre REST une fois, c'est savoir lire des centaines d'API.

Servir des fichiers statiques

Une API sert souvent aussi un peu de front (HTML, CSS, images). Le middleware intégré express.static expose le contenu d'un dossier tel quel, sans écrire de route par fichier.

En CommonJS, __dirname est déjà fourni : express.static(path.join(__dirname, "public")).

Structurer avec un Router

Quand l'app grossit, empiler toutes les routes dans app.js devient ingérable. express.Router() crée un mini‑routeur isolé, que tu montes sous un préfixe avec app.use. Chaque ressource vit dans son propre fichier.

Le préfixe est défini une seule fois, au montage : le routeur ignore où il est branché.

Astuce

Garde le routeur fin : il valide les entrées et formate les réponses, rien de plus. La logique métier (calculs, accès aux données) part dans des modules « services » réutilisables et testables sans démarrer Express. Tu pourras alors tester ta logique avec node:test sans même lancer de serveur.

Pièges fréquents

Piège fréquent

L'ordre des routes compte : Express essaie les routes dans l'ordre de déclaration et s'arrête à la première qui correspond. Si tu déclares app.get("/livres/:id") avant app.get("/livres/nouveau"), le second ne sera jamais atteint car nouveau est capté comme un :id. Place toujours les chemins spécifiques avant les chemins paramétrés. Autres classiques : oublier express.json() (corps undefined) ; choisir le mauvais verbe ou le mauvais code (un POST qui répond 200 au lieu de 201, une erreur client renvoyée en 500) ; et entasser toute la logique métier dans les gestionnaires de route au lieu de l'isoler.

Pour aller plus loin

Pour aller plus loin

La prochaine leçon détaille les middlewares — ces fonctions (req, res, next) qui s'intercalent dans le traitement (journalisation, authentification, gestion d'erreurs centralisée). Au‑delà d'Express, regarde Fastify (plus rapide, validation de schéma intégrée) et NestJS (architecture structurée pour gros projets). Pour fiabiliser une API : la validation des entrées (Zod, Joi), l'authentification par jetons JWT, et surtout le remplacement du tableau en mémoire par une vraie base de données (voir le cours SQL pour les requêtes et la modélisation).

Antisèche

Glossaire

Express
Framework web minimaliste et le plus répandu de l'écosystème Node : il industrialise routage, lecture du corps, en-têtes et codes de statut au-dessus de node:http.
Route
Association d'un verbe HTTP et d'un chemin à un gestionnaire (req, res) => …. Déclarée via app.get, app.post, etc.
Middleware
Fonction (req, res, next) intercalée dans le traitement d'une requête (parsing, journalisation, authentification). On l'enregistre avec app.use ; express.json() en est un.
req.params / req.query / req.body
Les trois entrées : segment nommé du chemin (:id), chaîne après le ?, et corps JSON de la requête (après express.json()).
REST
Style d'API qui mappe les opérations sur les verbes HTTP : GET lit, POST crée, PUT/PATCH modifie, DELETE supprime, chacun avec son code conventionnel.
CRUD
Les quatre opérations de base sur des données : Create, Read, Update, Delete. En REST, elles correspondent à POST, GET, PUT/PATCH et DELETE.
express.static
Middleware intégré qui expose le contenu d'un dossier (HTML, CSS, images) sans écrire de route par fichier.
express.Router()
Mini-routeur isolé regroupant les routes d'une ressource dans son propre fichier ; monté sous un préfixe via app.use('/livres', router).

Récap et vérification

  • Express s'installe via npm install express ; on crée une app, on déclare des routes, on écoute avec app.listen(port).
  • Une route lie un verbe et un chemin à un gestionnaire ; res.json() renvoie du JSON et res.status(code) fixe le statut.
  • Trois entrées distinctes : req.params (route :id), req.query (?clé=valeur) et req.body (corps, après express.json()).
  • Une API CRUD respecte les verbes (GET/POST/PUT/DELETE) et les codes (200/201/204/400/404).
  • express.static sert un dossier de fichiers ; express.Router() découpe les routes par ressource.

Vérifie ta compréhension

  1. Quelle ligne dois‑tu ajouter pour que req.body ne soit plus undefined sur une route POST, et à quelle condition sur le Content-Type s'active‑t‑elle ?
  2. Quelle est la différence entre req.params.id (issu de /livres/:id) et req.query.tri (issu de ?tri=titre), et pourquoi faut‑il souvent passer un paramètre à Number(...) ?
  3. Pourquoi app.get("/livres/nouveau") doit‑il être déclaré avant app.get("/livres/:id") ?
