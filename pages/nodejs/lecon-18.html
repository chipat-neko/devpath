Module 07 · Node.js à l'échelle — Leçon 18

Architecture d'une application robuste

~30 min Intermédiaire Cours Node.js recommandé

À la fin de cette leçon, tu sauras

  • savoir séparer une API en couches routes/contrôleurs, services et repositories testables isolément ;
  • savoir valider les entrées à la frontière avec un schéma Zod et centraliser la gestion d'erreurs via un middleware et des classes AppError ;
  • savoir charger une configuration validée par environnement sans secret en dur ;
  • savoir appliquer les bonnes pratiques REST (statuts, pagination, versioning) avec un wrapper async.
Sommaire de la leçon

Une API qui démarre dans un seul index.js grandit vite : routes, requêtes SQL, validation, règles métier et gestion d'erreurs finissent entremêlées sur 800 lignes. Le moindre changement devient risqué, rien n'est testable isolément, et chaque endpoint répond les erreurs à sa façon. Le problème n'est pas la taille du fichier : c'est le mélange des responsabilités.

Dans cette leçon, tu vas restructurer une API Express en couches aux frontières nettes, valider les entrées avec Zod, centraliser les erreurs et charger une configuration validée. L'objectif : un code où chaque pièce a un rôle unique et se teste seule.

Le problème de l'app « tout dans index.js »

Regarde ce contrôleur typique : il parle HTTP, valide, accède à la base et applique une règle métier. Pour le tester, il faut un vrai serveur et une vraie base. C'est le symptôme d'un manque de séparation.

L'idée directrice : séparer en trois couches. Le contrôleur ne connaît que HTTP (lire la requête, renvoyer un statut). Le service porte la logique métier, sans rien savoir d'Express ni de SQL. Le repository encapsule l'accès aux données. Chacune se teste isolément en remplaçant la couche en dessous.

Structure de dossiers et injection de dépendances

Une arborescence lisible reflète les couches. Pas besoin d'un framework lourd : chaque module exporte une factory qui reçoit ses dépendances en argument. C'est de l'injection de dépendances « à la main », suffisante et explicite.

Note

Une factory qui reçoit { userRepository } rend le test trivial : tu passes un faux repository en mémoire. Pas de mock magique, juste un objet avec les mêmes méthodes.

Câbler les couches sans tout coupler

L'assemblage se fait à un seul endroit : on construit le repository, on l'injecte dans le service, puis le contrôleur appelle le service. Le contrôleur reste mince : il traduit HTTP vers métier, rien d'autre.

Valider les entrées à la frontière avec Zod

Toute donnée venant du client est suspecte. On la valide une fois, à l'entrée, avant qu'elle n'atteigne le métier. Zod décrit un schéma, vérifie body, params et query, et — bonus en TypeScript — infère le type des données validées.

Astuce

safeParse ne lève pas d'exception : il renvoie { success, data, error }. Pratique pour décider du flux sans try/catch. Utilise z.coerce pour convertir les query (toujours des chaînes) en nombres ou booléens.

Gestion d'erreurs centralisée

Une réponse d'erreur cohérente passe par des classes d'erreur portant un statut HTTP, et un middleware d'erreur unique en fin de chaîne. On distingue les erreurs opérationnelles (prévues : 404, 409, validation) des bugs (imprévus) : les premières sont sûres à exposer, les seconds non.

Place errorHandler après toutes les routes dans app.js. Comme nos contrôleurs sont en async, il faut router les rejets de promesse vers ce middleware : c'est le rôle du wrapper de la section suivante.

async/await partout avec un wrapper

Si un await rejette dans un handler Express classique, l'erreur n'atteint pas le middleware d'erreur : la requête reste pendante. Un petit wrapper attrape le rejet et le passe à next(), sans try/catch répété partout.

Note

Express 5 (stable depuis 2024) propage automatiquement les rejets des handlers async vers le middleware d'erreur : le wrapper devient optionnel. Sur Express 4, garde asyncHandler.

Configuration validée par environnement

Les secrets et réglages vivent dans l'environnement, jamais en dur dans le code. Mais une variable d'env est toujours une chaîne, parfois absente : on la valide au démarrage avec un schéma, et on échoue tôt si la config est incomplète plutôt que de planter à la première requête.

Piège fréquent

Ne mets jamais de valeur par défaut pour un secret (JWT_SECRET, clé d'API). Un défaut « pour dépanner » finit en production et devient une faille. Préfère un échec au démarrage.

Cas réel — le secret par défaut qui traîne partout

Un grand classique des fuites : un tutoriel ou un modèle de projet pose un secret « pour dépanner », du genre JWT_SECRET = 'secret' ou SECRET_KEY = 'changeme'. Des milliers de développeurs copient-collent le squelette, oublient de le changer, et déploient. Résultat : comme la clé de signature est publiquement connue, n'importe qui peut forger un jeton d'administrateur valide sur ces applications. Des scanners automatisés parcourent d'ailleurs le web à la recherche de ces valeurs par défaut. La parade est exactement celle de cette leçon : aucune valeur par défaut pour un secret, et un échec au démarrage (process.exit(1)) si la variable manque. Mieux vaut un serveur qui refuse de booter qu'un serveur ouvert à tous les vents.

Bonnes pratiques REST et documentation

Une API prévisible respecte les conventions. Statuts justes (201 à la création, 204 sans corps, 400/404/409 côté client). Pagination pour les listes : jamais « tout retourner ». Versioning dans l'URL (/api/v1) pour évoluer sans casser les clients.

Pour la documentation, expose un contrat OpenAPI (anciennement Swagger) : un fichier décrit endpoints, schémas et réponses, et des outils génèrent une UI interactive. Des bibliothèques dérivent même l'OpenAPI directement de tes schémas Zod, gardant code et doc synchronisés.

Pièges fréquents

Piège fréquent

Mettre la logique métier dans le contrôleur le rend intestable sans HTTP, et duplique les règles quand un second endpoint en a besoin. Le contrôleur ne fait que traduire entre HTTP et service.

Autres erreurs classiques : ne pas valider les entrées (bugs et failles à la première requête malformée) ; des erreurs non centralisées qui produisent des réponses incohérentes (parfois { error }, parfois { message }, parfois rien) ; fuiter la stack en production ; des secrets en dur committés dans Git ; et le fameux fichier unique géant qu'on n'ose plus toucher.

Pour aller plus loin

Pour aller plus loin

NestJS impose une structure en modules avec injection de dépendances intégrée. L'architecture hexagonale (ports/adapters) pousse plus loin l'isolement du métier. Côté types de bout en bout : tRPC (RPC typé sans schéma manuel), GraphQL (le client choisit ses champs), et Zod qui infère les types depuis tes schémas de validation. Génère ton OpenAPI depuis ces schémas pour une doc toujours à jour.

Antisèche

Glossaire

Séparation en couches
Découpage d'une application par responsabilité (HTTP, métier, données) avec des frontières nettes. Chaque couche ne dépend que de la suivante et se teste isolément.
Contrôleur
Couche qui traduit HTTP vers le métier : elle lit la requête (déjà validée) et renvoie un statut. Elle ne contient aucune règle métier ni accès aux données.
Service
Couche de la logique métier pure : elle applique les règles (unicité, calculs, autorisations) sans rien savoir d'Express ni du SQL sous-jacent.
Repository
Couche d'accès aux données : la seule qui exécute des requêtes SQL ou passe par un ORM. Elle expose des méthodes (findByEmail, insert) au service.
Injection de dépendances
Fournir à un module ses dépendances de l'extérieur (via une factory qui reçoit { repository }) plutôt que de les créer en dur. Rend le remplacement en test trivial.
Zod
Bibliothèque de validation de schémas : décrit la forme attendue d'une donnée, la vérifie (safeParse) et, en TypeScript, en infère le type.
Erreur opérationnelle
Erreur prévue et sûre à exposer (404, 409, validation), portée par une classe AppError avec son statut. À distinguer d'un bug imprévu, journalisé et masqué en 500.
Fail-fast
Échouer tôt et bruyamment : valider la configuration au démarrage et refuser de booter si elle est incomplète, plutôt que de planter à la première requête en production.

Récap et vérification

  • Sépare en couches : contrôleurs (HTTP), services (métier), repositories (données), chacune testable seule.
  • Injecte les dépendances via des factories : pas d'accès DB ni d'Express dans le métier.
  • Valide body, params, query à la frontière avec Zod ; renvoie des messages clairs.
  • Centralise les erreurs : classes AppError avec statut, middleware unique, pas de fuite de stack en prod.
  • Charge une config validée au boot ; aucun secret en dur ni par défaut.
  • Respecte REST : statuts justes, pagination, versioning ; documente en OpenAPI.

Vérifie ta compréhension

  1. Quelle couche a le droit d'exécuter une requête SQL, et laquelle ne doit connaître ni SQL ni Express ?
  2. Pourquoi distinguer une erreur isOperational d'un bug imprévu dans le middleware d'erreur ?
  3. Pourquoi faire échouer le démarrage quand JWT_SECRET est absent, au lieu de prévoir une valeur par défaut ?
