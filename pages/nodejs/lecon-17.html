Le temps réel avec les WebSockets

~36 min Avancé Leçon 16 recommandée

À la fin de cette leçon, tu sauras

  • Comprendre la limite de HTTP et savoir quand ouvrir une connexion WebSocket persistante ;
  • Savoir écrire un serveur avec la bibliothèque ws et diffuser un message à tous les clients connectés ;
  • Savoir connecter un client navigateur et gérer les événements onopen/onmessage/onclose ;
  • Savoir rendre une connexion robuste : heartbeat, authentification par JWT et montée en charge multi-instances.
Sommaire de la leçon

Jusqu'ici, tes serveurs suivaient toujours le même schéma : le client demande, le serveur répond, la connexion se ferme. Ce modèle requête/réponse de HTTP est parfait pour une API REST, mais il a une limite fondamentale : le serveur ne peut jamais prendre l'initiative. Impossible de pousser spontanément une notification, un nouveau message de chat ou un cours de bourse vers le navigateur. Cette leçon ajoute la pièce manquante : une communication bidirectionnelle et en temps réel.

Tu vas découvrir le protocole WebSocket, écrire un serveur avec la bibliothèque ws, diffuser des messages à plusieurs clients, connecter un client navigateur, puis comparer avec Socket.IO et durcir tout ça pour la production (heartbeat, authentification, montée en charge).

La limite de HTTP et l'idée du WebSocket

Avec HTTP, pour savoir s'il y a du nouveau, le client doit redemander. C'est le polling : interroger le serveur en boucle, toutes les quelques secondes. C'est lourd (une requête complète à chaque fois, avec ses en-têtes), ça gaspille des ressources quand il n'y a rien de neuf, et ça reste en retard sur l'événement réel.

Le WebSocket résout ce problème : après une poignée de main (handshake) qui commence comme une requête HTTP classique mais contient un en-tête Upgrade: websocket, la connexion TCP n'est jamais fermée. Elle devient un tuyau persistant dans lequel client et serveur s'envoient des messages quand ils veulent. L'URL utilise le schéma ws:// (ou wss:// chiffré en TLS, l'équivalent de HTTPS — à utiliser en production).

Note

Le WebSocket ne remplace pas HTTP : il le complète. Le handshake initial est une requête HTTP. Tu continues d'utiliser ton API REST pour le CRUD classique, et le WebSocket uniquement pour ce qui doit arriver en temps réel.

Un serveur avec la bibliothèque « ws »

La bibliothèque ws est l'implémentation de référence côté Node. On l'attache à un serveur HTTP existant pour partager le même port.

Lancé avec node server.js, le terminal affiche « WebSocket sur ws://localhost:3000 », puis « Client connecté… » dès qu'un client se branche.

Diffuser un message à tous les clients (broadcast)

Le vrai intérêt du temps réel, c'est de relayer un message d'un client vers tous les autres : c'est le principe d'un chat. Le serveur garde la liste de ses connexions dans wss.clients (un Set). On la parcourt en vérifiant que chaque socket est bien ouvert avant d'envoyer.

Avec deux clients connectés, ce que l'un envoie s'affiche chez l'autre instantanément, sans qu'il ait à recharger quoi que ce soit.

Piège fréquent

Appeler client.send() sur un socket en train de se fermer lève une erreur. Le test client.readyState === WebSocket.OPEN n'est pas optionnel : entre le moment où un client se déconnecte et celui où l'événement 'close' est traité, son socket est encore dans wss.clients mais déjà inutilisable.

Le client côté navigateur

Le client d'un WebSocket est généralement du JavaScript qui tourne dans le navigateur, avec l'API WebSocket native (pas besoin de bibliothèque). Rappelle-toi : ce code ne s'exécute pas dans Node, mais dans la page web servie au visiteur.

Dans la console du navigateur, on verrait « Connecté » puis « Message du serveur : Bienvenue ! ». L'envoi doit toujours se faire après onopen : envoyer avant que la connexion soit ouverte échoue.

Socket.IO : la couche au-dessus

La bibliothèque ws est volontairement minimaliste. Socket.IO est une surcouche qui ajoute ce dont une vraie application a besoin : reconnexion automatique si le réseau saute, découpage en rooms (salons) pour n'envoyer qu'à un sous-ensemble de clients, événements nommés, et un repli automatique (long-polling HTTP) si le WebSocket est bloqué par un pare-feu ou un proxy.

Attention : un client Socket.IO ne peut pas parler à un serveur ws brut, et inversement — le protocole de Socket.IO est plus riche. Choisis ton camp dès le départ.

Astuce

Préfère ws quand tu veux un protocole léger, maîtrisé et standard (par exemple une API publique). Préfère Socket.IO pour une application produit où reconnexion, rooms et repli te feraient perdre des jours à réécrire à la main.

Cas réel — le temps réel que tu utilises tous les jours

Les curseurs qui bougent en direct dans un document partagé (Google Docs, Figma, Notion), la messagerie instantanée d'une équipe (Slack, Discord), le fil d'un match sportif ou d'un cours de bourse qui se met à jour sans recharger, les notifications « 3 nouveaux messages » qui apparaissent d'elles-mêmes : tous reposent sur une connexion persistante de type WebSocket. Le point commun, c'est que la donnée naît côté serveur (quelqu'un d'autre a écrit, le prix a bougé) et doit atteindre ton écran sans que ton navigateur ait pensé à demander. Là où beaucoup d'équipes trébuchent, c'est au passage à l'échelle : le chat parfait en local se met à « perdre » des messages en production, précisément à cause du multi-instances décrit plus bas — d'où l'adaptateur partagé.

Robustesse : heartbeat, authentification, montée en charge

Un socket peut mourir sans prévenir (coupure réseau brutale) : aucun événement 'close' n'arrive, le serveur croit le client vivant et garde la connexion en mémoire. Le heartbeat (ping/pong) détecte ces morts silencieuses.

Pour l'authentification, réutilise le JWT de la leçon précédente : le client le passe en paramètre d'URL ou via un sous-protocole, et on le vérifie avant d'accepter la connexion. Une connexion non authentifiée est immédiatement fermée.

Encore plus propre : vérifier le JWT pendant l'événement 'upgrade' du serveur HTTP et refuser le handshake avant même de créer le socket. Passer le token en query string l'expose dans les logs ; un en-tête ou un cookie de session est préférable en production.

Piège fréquent

Dès que tu lances plusieurs instances de ton serveur derrière un répartiteur de charge, wss.clients ne contient que les clients de l'instance locale. Un broadcast ne touche donc qu'une fraction des utilisateurs. La solution : un adaptateur Redis (avec Socket.IO) qui propage chaque message entre toutes les instances via un canal pub/sub partagé.

Pièges fréquents

  • Croire que WebSocket remplace HTTP. Il le complète. Garde REST pour le CRUD, WebSocket pour le temps réel.
  • Envoyer sans vérifier readyState. Sur un socket fermé ou en fermeture, send() lève une erreur. Teste toujours === WebSocket.OPEN.
  • Oublier 'close' et 'error'. Sans eux, tu accumules des sockets morts (fuite mémoire) et une erreur non gérée peut faire tomber le process entier.
  • Ne pas authentifier. Un endpoint WebSocket ouvert est aussi sensible qu'une route HTTP : vérifie le JWT au handshake.
  • Ignorer le multi-instances. En production scalée, un broadcast naïf ne touche qu'une partie des clients sans adaptateur partagé.

Glossaire

WebSocket
Protocole d'une connexion persistante et bidirectionnelle entre client et serveur, ouverte après un handshake HTTP. Client et serveur s'envoient des messages à tout moment.
Handshake (Upgrade)
Poignée de main initiale : une requête HTTP portant l'en-tête Upgrade: websocket transforme la connexion TCP en tuyau WebSocket, qui reste ensuite ouvert.
Polling
Technique où le client réinterroge le serveur à intervalle régulier pour savoir s'il y a du nouveau. Simple mais coûteux et toujours en retard ; le WebSocket le remplace pour le temps réel.
Broadcast (diffusion)
Relayer un message reçu d'un client vers tous les autres. Avec ws, on parcourt wss.clients en n'envoyant qu'aux sockets OPEN.
readyState
État d'un socket (CONNECTING, OPEN, CLOSING, CLOSED). On teste === WebSocket.OPEN avant tout send() pour éviter une erreur sur une connexion fermée.
Heartbeat (ping/pong)
Sondage périodique qui détecte les connexions mortes silencieusement : le serveur envoie un ping, le client répond un pong ; sans réponse, le socket est fermé.
Socket.IO
Surcouche de haut niveau au-dessus des WebSockets : reconnexion automatique, rooms, événements nommés et repli en long-polling. Son protocole n'est pas compatible avec ws brut.
Room (salon)
Regroupement logique de clients dans Socket.IO : on peut n'émettre qu'aux membres d'une room, plutôt qu'à tous les connectés.

Récap et vérification

  • HTTP est requête/réponse ; le WebSocket ouvre une connexion persistante et bidirectionnelle après un handshake Upgrade (ws://, wss:// en TLS).
  • Avec ws : WebSocketServer, événements 'connection' puis 'message'/'close'/'error', envoi via socket.send().
  • Broadcast : parcourir wss.clients et n'envoyer qu'aux sockets readyState === OPEN.
  • Côté navigateur : new WebSocket(url) avec onopen/onmessage/onclose.
  • Production : heartbeat ping/pong, authentification JWT au handshake, adaptateur Redis pour le multi-instances.

Vérifie ta compréhension

  1. Pourquoi le polling HTTP est-il un mauvais choix pour afficher des messages de chat en temps réel ?
  2. Avant d'appeler client.send() dans une boucle de broadcast, quelle propriété dois-tu vérifier et pourquoi ?
  3. Tu déploies deux instances de ton serveur derrière un répartiteur de charge : pourquoi un broadcast ne touche-t-il plus tous les utilisateurs, et comment corriger ?
