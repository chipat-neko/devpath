Module 2 · Scripts et fonctions — Leçon 05

Écrire des scripts

~50 min Intermédiaire Prérequis : leçon 4

À la fin de cette leçon, tu sauras

  • structurer un script .ps1 et comprendre l'ExecutionPolicy ;
  • déclarer des paramètres de script avec param() ;
  • documenter avec des commentaires d'aide (.SYNOPSIS) ;
  • retourner des objets plutôt que du texte.
Sommaire de la leçon

Jusqu'ici, tu as travaillé surtout en console. Mais la vraie force de PowerShell, c'est l'automatisation : rassembler des commandes dans un script qu'on relance à volonté. Un script PowerShell est un fichier .ps1. Dans cette leçon, on passe de la frappe interactive au script réutilisable : politique d'exécution, paramètres, documentation et sortie propre.

La politique d'exécution

Par sécurité, Windows bloque par défaut l'exécution des scripts. C'est l'ExecutionPolicy. Pour ton usage, le réglage RemoteSigned (les scripts locaux passent, ceux téléchargés doivent être signés) est un bon compromis.

Le -Scope CurrentUser évite d'avoir à modifier la machine entière.

Anatomie d'un script

Un script s'exécute de haut en bas. On y place des commandes, des variables, des fonctions. Crée info-disque.ps1 :

Lance-le avec .\info-disque.ps1. Tu obtiens un vrai tableau d'objets.

Des paramètres avec param()

Un bon script ne code pas ses valeurs en dur : il accepte des paramètres. Le bloc param(), placé en tout début de fichier, les déclare. On peut typer chaque paramètre et lui donner une valeur par défaut.

On l'appelle en nommant les paramètres : .\salue.ps1 -Nom "Ada" -Fois 3.

Rendre un paramètre obligatoire ou validé

Deux attributs, posés juste avant un paramètre, fiabilisent l'appel. [Parameter(Mandatory)] rend le paramètre obligatoire : s'il manque, PowerShell le demande au lieu de planter. [ValidateSet("dev","prod")] restreint les valeurs acceptées : tout autre argument est rejeté avant la moindre ligne exécutée. On attrape ainsi les erreurs d'usage à la porte d'entrée.

Lire une entrée et l'environnement

Read-Host demande une saisie à l'utilisateur ; les variables d'environnement sont accessibles via le lecteur $env:.

Des chemins fiables avec $PSScriptRoot

Un script qui lit un fichier voisin par chemin relatif casse dès qu'on le lance depuis un autre dossier. La variable automatique $PSScriptRoot donne le dossier du script lui-même : écris "$PSScriptRoot\config.json" et le script retrouve son voisin, peu importe le répertoire courant.

Documenter avec les commentaires d'aide

PowerShell sait générer une vraie page d'aide à partir de commentaires structurés. Place un bloc <# … #> en tête du script avec des sections .SYNOPSIS, .DESCRIPTION, .PARAMETER, .EXAMPLE.

Désormais Get-Help .\salue.ps1 affiche cette documentation. Le commentaire devient utile à tout le monde, toi compris.

Retourner des objets, pas du texte

Un script réutilisable émet des objets : ils pourront être filtrés, triés, exportés par celui qui l'appelle. Évite de tout transformer en chaîne avec Write-Host.

Un script complet, de bout en bout

Cas réel : un rapport quotidien automatisé

Une administratrice veut, chaque matin, la liste des services censés tourner mais arrêtés, dans un fichier daté. Elle en fait un script paramétré puis le programme dans le Planificateur de tâches Windows : le paramètre -Sortie rend le chemin configurable, et la sortie objet se prête à un Export-Csv propre.

Comme le cœur du script émet des objets, on aurait tout aussi bien pu les afficher à l'écran ou les convertir en HTML : la même logique sert plusieurs usages.

Pièges fréquents

Piège fréquent

Le bloc param() doit être la toute première instruction du script (après un éventuel commentaire d'aide). Le placer plus bas provoque une erreur de syntaxe.

Pour aller plus loin

Pour aller plus loin

Ajoute #Requires -Version 7.0 en tête pour exiger une version minimale, ou #Requires -RunAsAdministrator pour imposer les droits administrateur : le script refusera de tourner sinon.

Antisèche — anatomie d'un script

Glossaire

Script .ps1
Fichier texte contenant des commandes PowerShell, exécuté de haut en bas.
ExecutionPolicy
Politique de sécurité qui autorise ou bloque l'exécution des scripts (ex. RemoteSigned).
param()
Bloc en tête de script déclarant ses paramètres, typés et avec valeurs par défaut.
Commentaire d'aide
Bloc <# .SYNOPSIS … #> lu par Get-Help pour documenter le script.
Read-Host
Cmdlet qui demande une saisie interactive à l'utilisateur.
$env:
Lecteur donnant accès aux variables d'environnement ($env:USERNAME).
Scope
Portée d'un réglage ; -Scope CurrentUser limite l'effet au compte courant.
Pipeline
Chaîne d'objets passés d'une commande à la suivante par le | ; cœur de PowerShell, où chaque étape reçoit des objets, pas du texte.

Récap et vérification

  • L'ExecutionPolicy contrôle l'exécution des scripts (RemoteSigned pour ton usage).
  • param(), en tête de fichier, déclare des paramètres typés avec valeurs par défaut.
  • Un bloc <# .SYNOPSIS … #> alimente Get-Help.
  • Un bon script retourne des objets, réutilisables par l'appelant.
