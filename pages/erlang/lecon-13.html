Module 5 · Tester et consolider — Leçon 13

Tester son code : EUnit et les propriétés

~50 min Avancé Prérequis : leçon 12

À la fin de cette leçon, tu sauras

  • écrire des tests avec EUnit et ses macros d'assertion ;
  • regrouper des tests avec les générateurs (_test_) ;
  • lancer la suite avec rebar3 eunit ;
  • découvrir les tests de propriétés (PropEr) et le shrinking.
Sommaire de la leçon

Le « let it crash » (leçon 6) protège un système en marche : quand une entrée imprévue survient, le processus fautif tombe et un superviseur le relance. Mais cela n'attrape pas les bugs de logique : une fonction qui calcule un total faux ne plante pas, elle rend juste un mauvais résultat, silencieusement. Pour ces erreurs-là, il faut des tests : du code qui vérifie ton code. Erlang livre pour cela un cadre intégré, EUnit, et l'écosystème BEAM y ajoute une arme rare et puissante : les tests basés sur les propriétés.

EUnit : le cadre de test intégré

EUnit est livré avec Erlang. On l'active en incluant son fichier d'en-tête, puis toute fonction dont le nom se termine par _test (sans argument) devient un cas de test. À l'intérieur, on emploie des macros d'assertion qui décrivent le résultat attendu :

La macro ?assertEqual(Attendu, Expression) compare : si les deux diffèrent, le test échoue en affichant précisément la valeur attendue et la valeur obtenue. On dispose aussi de ?assert(Booléen), ?assertNot/1, et de ?assertError(Motif, Expr) pour vérifier qu'une expression plante bien comme prévu.

Générateurs : regrouper et nommer des tests

Écrire une fonction par assertion devient vite lourd. Les générateurs de tests — une fonction dont le nom se termine par _test_ (avec un tiret bas final) — renvoient une liste de tests. Lancer les tests

Dans un projet rebar3, une seule commande : rebar3 eunit compile et exécute tous les modules de test. Au shell, eunit:test(maths). lance ceux du module maths. Pratique : convention d'écrire les tests dans un module séparé maths_tests.erl pour ne pas les mêler au code de production — EUnit associe automatiquement maths et maths_tests.

Tester des propriétés, pas des exemples

Les tests ci-dessus vérifient des exemples choisis à la main : « pour cette entrée, j'attends ce résultat ». C'est utile mais limité : on ne teste que les cas auxquels on a pensé. Les tests basés sur les propriétés renversent l'idée. On énonce une règle générale qui doit tenir pour toutes les entrées, et l'outil (PropEr ou QuickCheck) génère lui-même des centaines de cas aléatoires pour tenter de la mettre en défaut :

La macro ?FORALL(Variable, Générateur, Propriété) se lit : « pour toute L tirée du générateur list(integer()), la propriété doit être vraie ». proper:quickcheck(prop_reverse_involutif()). lance alors des centaines d'essais.

Cas réel : QuickCheck, né dans les télécoms

Le test par propriété a été popularisé par QuickCheck (en Haskell), puis porté sur la BEAM par la société suédoise Quviq, fondée par des vétérans d'Erlang. Des équipes comme Ericsson et Volvo l'ont employé pour tester des protocoles télécoms et des composants automobiles : là où une trame mal formée sur un million provoque un bug, générer des milliers de cas trouve ce que la relecture humaine manque. L'alternative libre, PropEr, apporte la même approche gratuitement à tout projet Erlang. Le shrinking est la clé de son utilité : sans lui, le contre-exemple serait une liste de 300 nombres illisible ; avec lui, on obtient le minuscule cas [0, 1] qui suffit à reproduire le bug.

Un test qui ne peut pas échouer ne teste rien

Le piège classique : écrire une assertion tautologique, par exemple ?assert(true), ou tester une fonction en réimplémentant sa logique dans le test (les deux se trompent alors de la même façon). Vérifie toujours qu'un test peut devenir rouge : casse volontairement le code une fois pour voir le test échouer, puis répare. Un test jamais rouge est un faux sentiment de sécurité.

Pour aller plus loin

EUnit gère aussi les fixtures : un couple setup/cleanup qui prépare puis démonte un contexte (démarrer un processus, ouvrir une table ETS) autour d'un test, via {setup, fun démarrer/0, fun arrêter/1, Tests}. Pour les scénarios d'intégration plus lourds (plusieurs nœuds, systèmes distribués), Erlang fournit Common Test : un cadre à part, orienté suites et journaux HTML, complémentaire d'EUnit qui reste, lui, le choix pour les tests unitaires rapides.

Glossaire

EUnit
Le cadre de tests unitaires intégré à Erlang ; reconnaît les fonctions *_test() et fournit des macros d'assertion.
Assertion
Vérification d'une condition attendue ; ?assertEqual, ?assert, ?assertError échouent le test si elle n'est pas remplie.
Générateur de tests
Fonction *_test_() (tiret bas final) qui renvoie une liste de tests, écrits avec les macros préfixées ?_assert….
Test unitaire
Test qui vérifie une petite unité de code (une fonction) sur des exemples précis, indépendamment du reste.
Propriété
Règle générale censée tenir pour toutes les entrées, énoncée avec ?FORALL et vérifiée sur des cas générés.
PropEr / QuickCheck
Outils de test basé sur les propriétés pour la BEAM : ils génèrent des entrées aléatoires pour réfuter une propriété.
Shrinking
Réduction automatique d'un contre-exemple trouvé jusqu'à sa plus petite forme, pour le rendre lisible.
Common Test
Cadre de tests d'intégration d'Erlang, orienté suites et journaux ; complète EUnit pour les scénarios lourds.

Récap et vérification

  • EUnit reconnaît les fonctions *_test() ; les macros ?assertEqual, ?assert, ?assertError décrivent l'attendu.
  • Un générateur *_test_() renvoie une liste de tests (macros ?_assert…) et peut les nommer.
  • rebar3 eunit lance toute la suite ; on sépare souvent code et tests en deux modules.
  • Les tests de propriétés (PropEr) énoncent une règle et génèrent des cas ; le shrinking réduit un contre-exemple.

Vérifie ta compréhension

  1. Quel suffixe de nom fait d'une fonction un cas de test EUnit ?
  2. Quelle macro vérifie qu'une expression plante bien ?
  3. Qu'apporte le test par propriété qu'un test par l'exemple n'a pas ?

Exercices

Exercice 1Échauffement

Écris un cas de test EUnit qui vérifie que lists:max([3, 7, 2]) vaut 7.

Voir une solution

Le nom finit par _test : EUnit l'exécute tout seul. ?assertEqual compare l'attendu 7 au résultat.

Exercice 2Application

Transforme trois vérifications de lists:reverse/1 en un seul générateur de tests.

Voir une solution

Nom en _test_ (tiret bas final) et macros ?_assertEqual préfixées : EUnit reçoit une liste de trois tests d'un coup.

Exercice 3Défi

Énonce, en pseudo-code ou avec ?FORALL, une propriété vraie pour tout entier N à propos de lists:sort/1 appliqué à une liste. Indice : que garantit un tri sur la longueur ?

Voir une solution

Autres propriétés possibles : la liste triée est croissante, ou sort(sort(L)) =:= sort(L) (idempotence). L'intérêt : une seule règle, testée sur des centaines de listes générées, sans en écrire aucune à la main.
