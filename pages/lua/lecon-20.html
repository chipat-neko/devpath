Module 7 · Projet — Leçon 20

Projet : un moteur de configuration

~60 min Avancé Prérequis : leçons 7, 17 et 18

À la fin de cette leçon, tu sauras

  • expliquer pourquoi Lua est un excellent langage de configuration — de la donnée qui se calcule ;
  • charger un fichier de config dans un bac à sable sûr avec load et un _ENV restreint ;
  • appliquer des valeurs par défaut et la lecture seule avec des métatables ;
  • offrir un petit DSL déclaratif, valider le résultat, et assembler le tout en un moteur réutilisable.
Sommaire de la leçon

Ce cours t'a mené des tables aux métatables, des coroutines au bac à sable, de la sérialisation aux tests. Il est temps de tout réunir dans un projet qui montre pourquoi Lua existe : un moteur de configuration. C'est le rôle emblématique de Lua — il pilote la config de Neovim, de Redis, de Nginx (via OpenResty), du gestionnaire de fenêtres Awesome et d'innombrables jeux. On va construire le nôtre, pas à pas.

Pourquoi Lua comme format de config ?

Un fichier JSON, INI ou YAML ne contient que des valeurs littérales figées. Un fichier de config en Lua, lui, est du code : il peut déclarer des variables, faire des calculs, une boucle, appeler une fonction. La configuration devient de la donnée qui se calcule.

Attention : config exécutable = code exécuté

Si le fichier est du code, le charger l'exécute. Un fichier de config venu d'ailleurs (téléchargé, envoyé par un utilisateur) pourrait appeler os.execute ou lire tes fichiers. La parade est celle de la leçon 17 : un bac à sable. C'est la première brique de notre moteur.

Charger la config dans un bac à sable

On reprend load(source, nom, mode, env) de la leçon 17. Deux réglages sont décisifs : le mode "t" (texte seul : on refuse le bytecode compilé, qui pourrait être malveillant) et l'environnement env, une table qui remplace les variables globales visibles par le fichier. On n'y met que ce qu'on autorise.

Valeurs par défaut et lecture seule : les métatables

Une bonne config a des valeurs par défaut : si l'utilisateur ne précise pas volume, on prend 1.0. C'est exactement le rôle de __index (leçon 7) : quand une clé manque, Lua la cherche dans la table de défauts. Et pour éviter qu'un module modifie la config par accident, on la rend en lecture seule avec __newindex.

Pourquoi la lecture seule ?

Une config lue partout dans le programme doit rester stable. Si n'importe quel module pouvait écrire conf.volume = 0, un bug deviendrait introuvable. __newindex transforme une écriture accidentelle en erreur immédiate, avec la ligne fautive — bien plus facile à corriger.

Un mini-DSL déclaratif

Renvoyer une table, c'est bien. Mais on peut aller plus loin : exposer dans le bac à sable des fonctions que le fichier de config appelle. Le fichier devient déclaratif, presque un langage à lui seul — un DSL (domain-specific language). Chaque appel range une valeur dans la structure.

Valider avant de faire confiance

Charger ne suffit pas : une config peut être syntaxiquement correcte mais logiquement fausse (largeur négative, titre oublié). On la valide avec des assert clairs — l'état d'esprit des tests de la leçon 19, appliqué aux données.

Astuce : échouer tôt, échouer fort

Valide la config au démarrage, pas au moment où une valeur bancale provoque un crash mystérieux dix minutes plus tard. Un message comme « largeur : nombre positif attendu » dès le lancement fait gagner des heures de débogage.

Cas réel : Lua, roi des fichiers de config

Ce que tu viens de construire est partout : Neovim se configure en init.lua ; Redis et Nginx (via OpenResty) embarquent Lua pour scripter leur comportement ; le gestionnaire de fenêtres Awesome lit un rc.lua ; le jeu World of Warcraft a bâti tout son écosystème d'extensions dessus ; et LÖVE (leçon 12) démarre en lisant un conf.lua. Tous exécutent du Lua comme configuration — exactement le moteur de cette leçon.

Pour aller plus loin

Trois évolutions naturelles : (1) un rechargement à chaud — relire le fichier quand il change, pour ajuster sans redémarrer ; (2) une sérialisation (leçon 18) pour réécrire la config modifiée ; (3) un schéma décrivant les champs attendus et leurs types, pour générer la validation automatiquement. Des bibliothèques comme lua-schema ou etlua explorent ces pistes.

Antisèche

Glossaire

Moteur de configuration
Le code qui charge, complète, valide et expose les réglages d'un programme à partir d'un fichier.
DSL
Domain-specific language : un mini-langage taillé pour un besoin précis. Ici, quelques fonctions (titre, fenetre…) forment un langage de config déclaratif.
Bac à sable (sandbox)
Environnement d'exécution restreint : le code chargé ne voit que les fonctions qu'on lui expose, jamais os ou io par défaut.
_ENV
La table qui tient lieu de « variables globales » pour un morceau de code. La fournir à load, c'est définir ce bac à sable.
load
Compile une chaîne en fonction exécutable. Ses arguments mode ("t" pour texte seul) et env en font l'outil clé d'un chargement sûr.
Métatable
Table attachée à une autre pour changer son comportement. __index gère les clés absentes (défauts), __newindex intercepte les écritures (lecture seule).
Valeur par défaut
Réglage utilisé quand l'utilisateur ne le précise pas ; fourni ici via __index pointant vers une table DEFAUTS.
Validation
Vérifier qu'une config est cohérente (champs présents, bons types, valeurs plausibles) avant de s'en servir, avec des messages d'erreur clairs.

Récap et vérification

Un moteur de configuration en Lua tient en quelques briques du cours : load avec un environnement restreint compile le fichier en sécurité ; pcall l'exécute sans risque de crash ; les métatables ajoutent défauts (__index) et lecture seule (__newindex) ; des fonctions exposées offrent un DSL déclaratif ; et assert valide le résultat. Assemblées, elles expliquent pourquoi Lua équipe tant de logiciels : une config qui se calcule, chargée proprement.

  • Lua comme config : de la donnée exécutable — puissante, donc à charger dans un bac à sable.
  • load(src, nom, "t", env) : "t" refuse le bytecode, env restreint ce que voit le fichier.
  • __index → valeurs par défaut ; __newindex → lecture seule.
  • Un DSL = des fonctions exposées : plus lisible et plus sûr qu'une table libre.
  • Toujours valider au démarrage : échouer tôt, avec un message clair.

Vérifie ta compréhension

  1. Pourquoi charger un fichier de config avec un _ENV restreint plutôt que l'environnement global ?
  2. Quel argument de load refuse le bytecode et n'accepte que du texte ?
  3. Quelle métaméthode rend une table de config en lecture seule ?
  4. Qu'apporte un DSL par rapport à un fichier qui renvoie simplement une table ?

Mini-projet fil rouge — un moteur de configuration

Pour clore le cours, construis le moteur complet, étape par étape. Il réunit tout Lua : tables, fonctions, load et le bac à sable, les métatables (__index/__newindex), pcall et la validation — un condensé des vingt leçons.

Ce que tu vas construire

Une fonction config(chemin) qui lit un fichier .lua, l'exécute en sécurité, complète les valeurs manquantes par des défauts, valide le résultat et le renvoie en lecture seule.

Étapes

Lire le fichier

Ouvre le fichier avec io.open et lis tout son contenu avec :read("a"). Protège l'ouverture par assert.

Le bac à sable

Compile la source avec load(source, nom, "t", bac) où bac n'expose que math et string. Le mode "t" refuse le bytecode.

Exécuter

Lance le morceau avec pcall ; en cas d'erreur, signale-la clairement. Récupère la table renvoyée.

Défauts

Attache une métatable { __index = DEFAUTS } pour compléter les clés absentes.

Valider + figer

Vérifie les champs requis avec assert, puis renvoie une vue en lecture seule grâce à __newindex.

ProjetFil rouge

Assemble les cinq étapes en un moteur complet. Essaie d'abord par toi-même, puis compare avec la solution de référence.
