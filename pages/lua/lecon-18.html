Module 6 · Maîtriser Lua — Leçon 18

Sérialiser et persister des données

~50 min Intermédiaire Prérequis : leçons 9 et 17

À la fin de cette leçon, tu sauras

  • transformer une table en texte que l'on peut écrire dans un fichier (sérialiser) ;
  • relire ce texte pour reconstruire la table (désérialiser) avec load ;
  • lire et écrire un fichier avec io.open, write et read ;
  • choisir entre le format Lua et le JSON selon la provenance des données.
Sommaire de la leçon

Un programme qui oublie tout à sa fermeture est vite frustrant : un jeu doit retenir le meilleur score, un outil ses réglages, une application son état. Persister, c'est écrire ces données sur le disque pour les retrouver au prochain lancement. Le cœur du problème : une table vit en mémoire, un fichier ne contient que du texte. Il faut donc traduire dans les deux sens.

Sérialiser une table en texte Lua

Lua a un atout rare : son propre code est un excellent format de données. Une table écrite { score = 1200, nom = "Zoé" } est à la fois de la donnée et du Lua valide. Sérialiser revient donc à produire une chaîne qui, relue, redonne la table. Écrivons une fonction récursive qui gère nombres, booléens, chaînes et tables imbriquées.

Astuce : %q échappe pour toi

string.format("%q", s) entoure la chaîne de guillemets et échappe correctement les guillemets, retours à la ligne et antislashs qu'elle contient. C'est la bonne façon d'écrire une chaîne réinjectable en Lua : ne bricole pas la concaténation de guillemets à la main.

Attention : l'ordre des clés n'est pas garanti

pairs parcourt les paires d'une table dans un ordre non spécifié : deux sérialisations de la même donnée peuvent produire des textes différents. Sans conséquence pour relire la table, mais gênant dès que tu compares des fichiers — un diff Git, un test — car la sauvegarde « change » sans que la donnée bouge. Pour une sortie stable, récupère les clés, trie-les, puis écris-les dans cet ordre.

Désérialiser avec load

Comme la chaîne produite est du Lua valide, la relire est immédiat : on la fait précéder de return et on la passe à load (leçon 17), puis on appelle le chunk obtenu.

Écrire et relire un fichier

Reste à poser le texte sur le disque. La bibliothèque io (leçon 9) ouvre un fichier avec io.open(nom, mode) : mode "w" pour écrire (écrase), "r" pour lire, "a" pour ajouter. On n'oublie jamais de close().

Cas réel : les sauvegardes de jeu et les configs

Ce motif est partout. Dans un jeu LÖVE (leçon 12), love.filesystem écrit exactement ce genre de fichier dans un dossier dédié à la sauvegarde. Les configurations de Neovim (init.lua), du gestionnaire de fenêtres awesome ou de nombreux outils sont, littéralement, des fichiers Lua chargés au démarrage : le fichier de données est du code, lu par load ou require.

Pour aller plus loin : load, dofile, require

Trois façons de charger du Lua, pour trois usages. load compile une chaîne (le plus bas niveau). dofile("f.lua") lit et exécute un fichier, à chaque appel. require("mod") cherche un module dans le package.path, l'exécute une seule fois puis met son résultat en cache (package.loaded) : c'est pourquoi les modules d'une configuration Neovim se chargent avec require, jamais deux fois — l'init.lua lui-même, lui, est exécuté directement au démarrage.

Format Lua ou JSON ? La question de la confiance

Le format Lua est parfait pour tes propres données : sauvegardes, réglages, niveaux. Mais désérialiser, c'est exécuter du code (load). Si le fichier vient d'ailleurs — un serveur, un autre joueur, un import — un contenu piégé peut faire des dégâts. Pour des données externes ou non fiables, on préfère le JSON, un format de données pur qui ne s'exécute pas.

Attention : les limites de notre serialize

Notre fonction ne gère ni les cycles (une table qui se référence elle-même : boucle infinie), ni les clés numériques et textuelles mêlées avec finesse, ni les fonctions. Pour un usage sérieux, prends une bibliothèque éprouvée comme serpent ou binser : elles gèrent les cycles, les nombres spéciaux et produisent un texte compact et sûr.

Glossaire

Sérialisation
Transformer une donnée en mémoire (table…) en une suite de caractères stockable ou transmissible.
Désérialisation
Opération inverse : reconstruire la donnée en mémoire à partir de son texte.
Persistance
Conserver l'état d'un programme au-delà de son exécution, en général sur disque.
io.open
Ouvre un fichier et renvoie un objet fichier (ou nil + message). Modes : "r", "w", "a".
string.format("%q", s)
Produit une représentation de la chaîne s réinjectable en Lua, guillemets et échappements compris.
JSON
Format de données textuel universel, lu par un analyseur qui n'exécute rien : sûr pour des données non fiables.
load
Compile une chaîne de texte en fonction Lua, sans l'exécuter (leçon 17). Ici, il reconstruit une table à partir de son texte.
Poignée de fichier
Objet renvoyé par io.open sur lequel on appelle :write, :read et :close : il représente le fichier ouvert.

Récap et vérification

Persister, c'est traduire une table en texte, l'écrire sur disque, puis faire le chemin inverse. En Lua, le format le plus naturel est… du Lua : serialize produit une table écrite en toutes lettres, load la relit. Simple et rapide pour tes propres sauvegardes et configurations. Mais désérialiser exécute du code : pour tout ce qui vient de l'extérieur, passe par un vrai analyseur JSON, qui lit sans exécuter.

  • Sérialiser : table → texte ; désérialiser : texte → table.
  • Le code Lua est un format de données : serialize + load("return "..t)().
  • io.open(chemin, mode), write, read("a"), puis close().
  • string.format("%q", s) échappe correctement une chaîne.
  • Données non fiables → JSON (lit sans exécuter) ; cycles → serpent/binser.

Vérifie ta compréhension

  1. Quelle est la différence entre sérialiser et désérialiser ?
  2. Pourquoi ajoute-t-on return devant le texte avant de le passer à load ?
  3. Quel mode de io.open écrase le contenu existant ?
  4. Pourquoi éviter load pour des données reçues du réseau ?
