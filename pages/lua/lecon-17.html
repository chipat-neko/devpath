Module 6 · Maîtriser Lua — Leçon 17

Environnements et bac à sable

~55 min Avancé Prérequis : leçons 7 et 15

À la fin de cette leçon, tu sauras

  • ce que sont _G (la table globale) et _ENV (l'environnement d'un morceau de code) ;
  • compiler du code à partir d'une chaîne avec load, et gérer ses erreurs ;
  • construire un bac à sable : un environnement restreint pour exécuter du code non fiable ;
  • reconnaître les cas où Lua sert de langage « invité » sécurisé (Redis, jeux, plugins).
Sommaire de la leçon

La plus grande force de Lua, c'est de se glisser dans d'autres programmes pour leur donner un langage de script. Mais si un jeu, un serveur ou un éditeur exécute du code écrit par ses utilisateurs, il ne peut pas le laisser tout faire : effacer des fichiers, lancer des commandes système… Il lui faut un bac à sable. Cette leçon montre le mécanisme qui rend cela possible : les environnements.

_G : la table des globales

On l'a vu à la leçon 15 : une variable globale n'est pas une case isolée, c'est une entrée dans une table. Cette table porte un nom : _G. Écrire x = 42 revient à écrire _G.x = 42. Même print est un champ de _G !

_ENV : l'environnement d'un morceau de code

Depuis Lua 5.2, chaque morceau de code (un chunk) voit ses globales à travers une variable spéciale nommée _ENV. Quand tu écris print("salut"), Lua comprend en réalité _ENV.print("salut"). Par défaut, _ENV pointe vers _G — mais rien n'oblige à ce que ce soit le cas. Changer l'environnement d'un chunk, c'est changer le monde qu'il peut voir. C'est toute l'idée du bac à sable.

Note : versions de Lua

_ENV existe depuis Lua 5.2. En Lua 5.1 et LuaJIT, on manipulait l'environnement d'une fonction avec setfenv/getfenv, aujourd'hui disparus. Les exemples ici visent Lua 5.3/5.4 (le plus répandu) ; l'idée reste la même.

Compiler du texte : load

Jusqu'ici, ton code venait d'un fichier. Mais Lua sait aussi transformer une chaîne de caractères en fonction exécutable : c'est load. Il compile le texte et renvoie une fonction (le chunk), qu'il suffit d'appeler.

Attention : load exécute ce qu'on lui donne

Par défaut, un chunk chargé par load voit toutes les globales, os et io compris. Charger du texte venu de l'extérieur (un fichier téléchargé, une saisie utilisateur) sans précaution, c'est offrir les clés de la machine. La règle : si le code n'est pas de toi, mets-le en bac à sable — la suite de la leçon.

Construire un bac à sable

Depuis Lua 5.2, load accepte un 4ᵉ argument : l'environnement du chunk. Sa signature complète est load(texte, nom, mode, env). Il suffit de fournir une petite table ne contenant que ce qu'on autorise. Tout le reste — os, io, load lui-même — devient invisible pour le code invité.

Que se passe-t-il si le code invité tente quelque chose d'interdit ? Comme os n'est pas dans son environnement, os vaut nil : l'accès échoue proprement, capturé par pcall.

Attention : un vrai bac à sable va plus loin

Retirer os et io bloque le système de fichiers, mais un code hostile peut encore boucler à l'infini ou épuiser la mémoire. Une isolation sérieuse ajoute une limite de temps et de mémoire (hooks de débogage, collectgarbage), et filtre finement chaque fonction exposée. Ne réinvente pas cela pour de la sécurité critique : appuie-toi sur l'hôte (Redis, un moteur de jeu) qui l'a déjà durci.

Cas réel : pourquoi Redis a choisi Lua

La base de données Redis laisse ses clients envoyer des scripts (EVAL) exécutés côté serveur, au plus près des données. Ces scripts tournent dans un interpréteur Lua en bac à sable : pas d'accès aux fichiers, pas de fonctions globales dangereuses, une exécution déterministe. Même principe pour les mods de jeux (World of Warcraft), les règles de nginx/OpenResty, ou les extensions de Wireshark : Lua est le langage « invité » idéal parce qu'on maîtrise exactement ce qu'il voit.

Astuce : un bac réutilisable garde l'état

Rien n'oblige à recréer l'environnement à chaque exécution. En réutilisant la même table bac d'un appel de load au suivant, les variables que le code invité y définit persistent d'un appel à l'autre. C'est ainsi qu'une console de commandes de jeu ou un petit REPL se souviennent de ce que le joueur a tapé à la ligne précédente, tout en restant enfermés dans le même bac à sable.

Un environnement « presque complet » avec les métatables

Parfois, tu veux autoriser toutes les fonctions de lecture mais tracer ou interdire les écritures de globales. Une métatable (leçon 7) sur l'environnement le permet : __index délègue les lectures à _G, __newindex intercepte les créations de globales.

Antisèche

Glossaire

_G
Table qui contient toutes les variables globales du programme. x = 1 équivaut à _G.x = 1.
_ENV
Variable propre à chaque chunk (Lua ≥ 5.2) à travers laquelle il accède à ses globales. Par défaut, elle pointe vers _G.
Chunk
Un morceau de code Lua compilé — le contenu d'un fichier ou d'une chaîne passée à load. C'est une fonction.
load
Compile du texte (ou du bytecode) en fonction, sans l'exécuter. Renvoie nil + message en cas d'erreur de syntaxe.
Bac à sable (sandbox)
Environnement restreint dans lequel on fait tourner du code non fiable, en ne lui exposant qu'un jeu de fonctions choisi.
Mode "t"
Option de load qui n'accepte que du code source texte, pas du bytecode précompilé (plus sûr).
__index
Champ de métatable consulté quand on lit une clé absente d'une table. Pointé vers _G, il rend un environnement transparent en lecture.
__newindex
Champ de métatable déclenché quand on écrit une clé absente. Il permet de tracer ou d'interdire la création de nouvelles globales.

Récap et vérification

Les globales de Lua vivent dans une table (_G), et chaque chunk y accède via son environnement (_ENV). Comme on choisit cet environnement, on choisit ce qu'un code peut voir. Combiné à load — qui transforme du texte en fonction — et à pcall — qui isole les erreurs —, cela donne le bac à sable : le mécanisme qui fait de Lua le langage embarqué de référence pour exécuter du code d'utilisateurs sans lui livrer la machine.

  • _G est la table des globales ; print, math… en sont des champs.
  • _ENV est l'environnement d'un chunk : le remplacer restreint ce qu'il voit.
  • load(texte, nom, "t", env) compile une chaîne dans l'environnement fourni.
  • Un bac à sable n'expose que des fonctions sûres ; pcall attrape les erreurs.
  • Pour de la sécurité réelle, il faut aussi borner temps et mémoire — appuie-toi sur l'hôte.
