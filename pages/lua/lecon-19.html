Module 6 · Maîtriser Lua — Leçon 19

Tester et fiabiliser son code

~50 min Intermédiaire Prérequis : leçons 9 et 10

À la fin de cette leçon, tu sauras

  • vérifier une hypothèse avec assert et comprendre pourquoi les tests protègent ton code ;
  • écrire un mini-framework de tests maison en une vingtaine de lignes ;
  • tester qu'une fonction lève bien une erreur, avec pcall ;
  • utiliser busted (describe/it) et luacheck, les outils standards de l'écosystème.
Sommaire de la leçon

Ton code marche ? Vraiment ? Sur tous les cas ? Un test répond à ces questions automatiquement, encore et encore. Tester, c'est écrire du code qui vérifie ton code : chaque fois que tu modifies quelque chose, les tests confirment que rien n'est cassé. C'est le filet de sécurité qui te permet de refactoriser sans peur.

assert : la brique de base

assert(condition, message) ne fait rien si la condition est vraie, et lève une erreur si elle est fausse. C'est le vérificateur le plus simple qui soit : un test, c'est au fond un assert sur un résultat attendu.

Rappel de la leçon 10

assert stoppe au premier échec — utile pour une garde, gênant pour une suite de tests où l'on veut tous les résultats. La parade : exécuter chaque test dans un pcall, qui attrape l'erreur au lieu de tout interrompre. C'est exactement ce que fait le mini-framework ci-dessous.

Un mini-framework de tests maison

Pas besoin d'outil externe pour commencer : une fonction test qui exécute un cas dans un pcall, compte les réussites et les échecs, et affiche un rapport, suffit à structurer des dizaines de vérifications.

On l'utilise en décrivant chaque comportement attendu. Pour vérifier qu'une fonction refuse une mauvaise entrée, on teste que pcall renvoie false.

busted : le framework standard

Pour de vrais projets, l'écosystème Lua a son outil de référence : busted (installable via LuaRocks). Il organise les tests en describe (un groupe) et it (un cas), et fournit des assertions riches via assert (couche luassert) : assert.are.equal, assert.are.same (comparaison en profondeur), assert.has_error…

Attention : un test sans assertion ment

Un it("…", function() … end) qui n'appelle aucune assertion est compté comme réussi : il passe au vert sans rien vérifier. De même, un pcall(fn) dont on ignore la valeur de retour n'affirme rien. Vérifie toujours un résultat concret — eq, assert.are.equal, assert.has_error — sinon un test « vert » peut couvrir un code cassé.

luacheck : attraper les fautes sans exécuter

Avant même de lancer les tests, un linter relit ton code et signale les erreurs probables : variable jamais utilisée, globale créée par accident (un local oublié !), argument redéfini. luacheck est le linter standard de Lua.

Astuce : la globale accidentelle

Le piège nº 1 en Lua : oublier local et créer une globale sans le vouloir (leçon 4). luacheck la repère instantanément (« setting non-standard global »). L'ajouter à ton flux de travail élimine toute une classe de bugs avant qu'ils n'existent.

Cas réel : l'intégration continue d'un module Lua

Un module publié sur LuaRocks décrit ses tests dans un fichier .rockspec et une CI type GitHub Actions enchaîne, à chaque commit : luacheck . (style et fautes), puis busted (comportement), parfois sur plusieurs versions de Lua (5.1 à 5.4 et LuaJIT). Si le moindre test rougit, la fusion est bloquée. C'est ainsi que des bibliothèques comme Penlight restent fiables sur des années.

Pour aller plus loin : la couverture de code

Tes tests passent, mais quelle part de ton code exécutent-ils vraiment ? La couverture mesure les lignes atteintes par la suite de tests. En Lua, busted --coverage s'appuie sur luacov pour un rapport ligne par ligne. Garde en tête que 100 % de couverture prouve que chaque ligne a été exécutée, pas qu'elle a été bien vérifiée : c'est un indice, pas une garantie.

Glossaire

Test unitaire
Petit programme qui vérifie automatiquement qu'un morceau de code produit le résultat attendu.
Assertion
Vérification d'une condition qui doit être vraie ; sinon elle signale un échec. assert en est la forme de base.
busted
Framework de test standard de Lua : organise les cas en describe/it et fournit des assertions riches.
luassert
Bibliothèque d'assertions utilisée par busted (assert.are.equal, assert.are.same, assert.has_error).
luacheck
Linter : analyse le code sans l'exécuter pour repérer variables inutilisées, globales accidentelles, etc.
TDD
Test-Driven Development : écrire le test avant le code, puis coder le minimum pour le faire passer.
Régression
Bug réapparu : un test de régression garde en mémoire un cas déjà corrigé pour qu'il ne casse plus jamais en silence.
Couverture de code
Proportion des lignes d'un programme réellement exécutées par la suite de tests. Mesurée en Lua avec luacov (busted --coverage).

Récap et vérification

Tester, c'est déléguer à la machine la question « est-ce que ça marche encore ? ». assert en est l'atome ; pcall permet d'enchaîner les cas sans s'arrêter au premier échec ; un mini-framework de vingt lignes suffit à démarrer. Pour de vrais projets, busted structure les tests en spécifications lisibles et luacheck attrape les fautes avant même l'exécution. Ensemble, ils forment le filet qui rend le refactoring serein.

  • assert(cond, msg) : la vérification de base, mais elle stoppe au premier échec.
  • pcall isole chaque test : on obtient tous les résultats, et on teste les erreurs attendues.
  • busted : describe groupe, it décrit un cas, assert.are.same compare en profondeur.
  • luacheck repère variables inutiles et globales accidentelles, sans exécuter.
  • En CI : luacheck + busted à chaque commit, sur plusieurs versions de Lua.

Vérifie ta compréhension

  1. Que fait assert(x == 5) si x vaut 4 ?
  2. Pourquoi enrober chaque test dans un pcall dans une suite de tests ?
  3. À quoi servent describe et it dans busted ?
  4. Quel genre d'erreur luacheck attrape-t-il sans exécuter le code ?
