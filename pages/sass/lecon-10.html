Module 05 · Sass avancé & production — Leçon 10

Les modules natifs de Sass

~34 min Avancé Leçon 06 conseillée

À la fin de cette leçon, tu sauras

  • charger un module intégré avec @use 'sass:…' ;
  • utiliser math, color, string, list, map et meta ;
  • remplacer la division / dépréciée par math.div() ;
  • inspecter et déboguer avec meta.
Sommaire de la leçon

Aux débuts de Sass, toutes les fonctions intégrées vivaient dans un seul espace global : lighten(), percentage(), map-get()… se côtoyaient sans préfixe. Le Sass moderne (Dart Sass) a rangé tout ça dans des modules thématiques que l'on charge à la demande avec @use. Plus lisible, sans collision de noms, et prêt pour l'avenir : c'est la manière officielle d'écrire du Sass aujourd'hui.

Charger un module : @use 'sass:…'

Un module intégré se charge exactement comme un partial, mais son nom commence par sass:. Ses fonctions deviennent alors accessibles sous un préfixe (le namespace), par défaut le nom du module.

Un préfixe qui clarifie

Écrire math.div plutôt que div indique d'où vient la fonction. On peut renommer le préfixe (@use 'sass:math' as m; → m.div) ou tout aplatir avec as *, mais garder le préfixe explicite reste la bonne pratique.

Et si on écrivait as * pour tout court ?

La forme @use 'sass:math' as *; importe les fonctions sans préfixe : on retrouve div(), round()… comme au temps des globales. Tentant, mais déconseillé : on perd l'indication d'où vient chaque fonction, et surtout on rouvre la porte aux collisions de noms — deux modules (ou tes propres fonctions) peuvent définir un même nom, et Sass lèvera une erreur au chargement. Le préfixe explicite n'est pas de la verbosité : c'est exactement ce que les modules sont venus régler.

sass:math — calculs et unités

Le module math couvre l'arithmétique : arrondis, valeur absolue, pourcentage, constantes, et surtout la division.

La division « / » est dépréciée

Historiquement, / servait à la fois de séparateur (comme dans font: 16px/1.5) et d'opérateur de division. Cette ambiguïté a mené Sass à déprécier $a / $b comme division : il faut désormais écrire math.div($a, $b). C'est le changement le plus courant lors d'une modernisation de code Sass.

sass:color — manipuler les couleurs

Les vieilles fonctions lighten(), darken(), saturate()… sont remplacées par un module color plus expressif : on ajuste, on met à l'échelle ou on change une composante.

Préfère scale à adjust

color.scale travaille en proportion (« 20 % plus clair » sans jamais dépasser les bornes), là où color.adjust ajoute une valeur fixe qui peut « saturer » et donner du blanc pur. Pour des variantes harmonieuses, scale est presque toujours le bon choix.

sass:string, sass:list, sass:map

Trois modules pour manipuler des données. Les chaînes en Sass sont indexées à partir de 1 (et non 0) !

sass:meta — introspection et débogage

Le module meta parle du code lui-même : quel type a une valeur, telle variable existe-t-elle, et surtout meta.inspect() pour afficher une valeur telle quelle (indispensable pour déboguer une map).

Cas réel — la modernisation de Bootstrap

Quand Bootstrap 5 a migré vers Dart Sass, ses feuilles ont été truffées de ces modules : math.div() a remplacé des centaines de divisions /, et les fonctions de couleur tint-color() / shade-color() du framework s'appuient sur color.mix() et color.scale() du module sass:color. Sans cette migration, chaque compilation crachait des avertissements de dépréciation ; avec elle, le code est resté compatible avec les futures versions de Sass. C'est très exactement le travail que tu feras sur n'importe quel projet un peu ancien : charger les bons modules et remplacer les anciennes écritures globales.

Glossaire

Module natif
Bibliothèque intégrée à Sass (sass:math, sass:color…) chargée avec @use, regroupant des fonctions par thème.
Namespace (préfixe)
Nom sous lequel les fonctions d'un module sont accessibles (math.div) ; par défaut le nom du module, renommable avec as.
math.div()
Division explicite qui remplace l'opérateur / désormais déprécié pour diviser.
Dépréciation
Fonctionnalité encore acceptée mais vouée à disparaître ; Sass émet un avertissement invitant à migrer.
Fonction globale
Ancienne fonction intégrée appelée sans préfixe (lighten(), map-get(), unquote()…), aujourd'hui dépréciée au profit de son équivalent namespacé dans un module.
color.scale()
Éclaircit ou assombrit une couleur en proportion, sans jamais dépasser les bornes (contrairement à adjust).
meta.inspect()
Renvoie la représentation textuelle exacte d'une valeur ; idéal avec @debug pour inspecter une map ou une liste.
Dart Sass
Implémentation officielle et actuelle de Sass (les anciennes, LibSass et Ruby Sass, ne sont plus maintenues).

Récap et vérification

  • Sass moderne range ses fonctions dans des modules chargés avec @use 'sass:…'.
  • Chaque module expose ses fonctions sous un préfixe (math.div, color.scale).
  • La division / est dépréciée : utilise math.div().
  • meta.inspect() + @debug = l'outil pour déboguer une map ou une liste.

Vérifie ta compréhension

  1. Comment charger le module mathématique et l'utiliser pour diviser ?
  2. Pourquoi color.scale est-il souvent préférable à color.adjust ?
  3. Quelle fonction affiche le contenu exact d'une map pour la déboguer ?

Exercices

Exercice 1Échauffement

Ce code déclenche un avertissement de dépréciation : .col { width: 100% / 3; }. Corrige-le à l'aide du bon module.

Voir une solution

La division avec / est dépréciée : il faut passer par le module sass:math. On le charge en haut du fichier avec @use 'sass:math';, puis on remplace l'opérateur par la fonction math.div : .col { width: math.div(100%, 3); }. Le résultat est le même (33.3333333333%) mais l'intention est explicite — on divise, on ne sépare pas deux valeurs — et Sass ne crie plus d'avertissement. C'est le correctif le plus fréquent quand on modernise une base de code Sass : chercher tous les / utilisés comme divisions et les convertir. Astuce : l'outil sass-migrator peut le faire automatiquement sur tout un projet (module division).

Exercice 2Application

Tu veux, à partir d'une couleur de marque $base, générer une version « survol » 15 % plus sombre et une version « désactivée » à 40 % d'opacité. Quelles fonctions du module color utilises-tu ?

Voir une solution

On charge d'abord le module : @use 'sass:color';. Pour la version survol plus sombre, on privilégie color.scale, qui assombrit en proportion sans risque de « saturer » vers le noir : color.scale($base, $lightness: -15%). Pour la version désactivée, on ne touche pas à la teinte mais à l'opacité : color.change permet de forcer une composante à une valeur précise, ici l'alpha : color.change($base, $alpha: 0.4). On obtient par exemple : .btn { background: $base; &:hover { background: color.scale($base, $lightness: -15%); } &:disabled { background: color.change($base, $alpha: 0.4); } }. Pourquoi ce choix ? scale pour une variation relative et harmonieuse (parfait pour un survol), change pour imposer une valeur exacte (parfait pour fixer une opacité). On aurait pu utiliser color.adjust, mais il ajoute une quantité fixe et peut donner des résultats plats sur des couleurs déjà très claires ou très sombres. Ces fonctions remplacent les anciennes darken()/transparentize() globales, aujourd'hui découragées.

Exercice 3Défi

Un collègue te montre une map de breakpoints qui « ne marche pas » et ne comprend pas pourquoi map.get renvoie parfois null. Comment utiliserais-tu sass:meta et sass:map pour diagnostiquer le problème ?

Voir une solution

La démarche est celle d'un vrai débogage : rendre visible l'invisible. 1) Inspecter la map elle-même. On charge sass:meta et on affiche la map telle qu'elle est réellement compilée : @use 'sass:meta'; @debug meta.inspect($breakpoints);. Très souvent, le problème saute alors aux yeux : une clé mal orthographiée ('medium' au lieu de 'md'), une virgule oubliée qui a fusionné deux entrées, ou une valeur qui n'est pas du type attendu. 2) Vérifier le type. Toujours avec meta, on confirme qu'on manipule bien une map : @debug meta.type-of($breakpoints); // doit afficher : map. Si le résultat est list ou string, la déclaration est fautive (souvent des parenthèses ou des deux-points manquants). 3) Vérifier la présence de la clé. Avant d'appeler map.get, on teste avec sass:map : @use 'sass:map'; @debug map.has-key($breakpoints, 'md');. Si c'est false, on liste les clés réellement disponibles pour comparer : @debug map.keys($breakpoints);. 4) Sécuriser l'accès. Enfin, pour éviter qu'un null se propage silencieusement dans le CSS, on entoure l'accès d'une garde qui signale l'erreur au lieu de la taire : @if not map.has-key($breakpoints, $nom) { @error "Breakpoint inconnu : #{$nom}"; }. La leçon : meta.inspect et meta.type-of transforment une map opaque en objet observable, et map.has-key/map.keys disent exactement ce que la map contient. Un null renvoyé par map.get signifie presque toujours « clé absente » : c'est une faute de frappe ou une entrée manquante, pas un bug de Sass. Ces trois modules ensemble forment la trousse de diagnostic standard.
