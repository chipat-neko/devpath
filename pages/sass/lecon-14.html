Module 06 · Projet — Leçon 14

Composer un design system Sass complet

~36 min Projet Tout le cours conseillé

À la fin de cette leçon, tu sauras

  • ranger tes tokens dans une map imbriquée unique ;
  • exposer un accesseur jeton() propre avec map.get ;
  • gérer le responsive et la thématisation clair/sombre ;
  • assembler le tout en un mini design system réutilisable.
Sommaire de la leçon

Cette dernière leçon est un projet de synthèse : on réunit tout ce que le cours a couvert — variables, maps, fonctions, mixins, @each, @use/@forward, modules natifs — pour construire un design system minuscule mais complet. C'est exactement le squelette que les équipes produit maintiennent : une source de vérité pour les couleurs, les espacements et la typo, et des outils Sass qui la transforment en CSS.

Un design system, c'est quoi ?

Un design system réunit les décisions visuelles d'un produit (couleurs, échelles d'espacement, rayons, typographie, points de rupture) et les outils qui les appliquent de façon cohérente. En Sass, le cœur est une map de tokens unique : on la lit partout via une fonction, jamais en écrivant des valeurs « en dur » dans les composants.

1. Les tokens dans une map imbriquée

On centralise tout dans un partial privé, chargé une fois. La map imbriquée regroupe les tokens par famille : on lit sa structure d'un coup d'œil.

Astuce — !default pour un système réutilisable

En marquant la map !default, un projet qui charge ton système peut la surcharger à l'import (@use 'tokens' with ($tokens: (…))) sans toucher à ton fichier. C'est ce qui distingue une bibliothèque d'un simple fichier de variables.

2. Un accesseur propre : jeton()

Plutôt que d'écrire map.get(map.get($tokens, "espace"), "m") partout, on expose une fonction. Le module natif sass:map gère l'accès profond en passant plusieurs clés.

Attention — échoue tôt avec @error

Sans garde-fou, une clé mal orthographiée renvoie null et produit un CSS invalide silencieux (padding: null disparaît). Le @error arrête la compilation avec un message clair : tu corriges à l'écriture, pas en debug dans le navigateur.

3. Responsive : une map de points de rupture

On applique la même logique aux media queries : une map de points de rupture et un mixin respond-to qui prend un bloc via @content.

4. Thématisation clair/sombre

La pratique moderne : Sass génère des custom properties CSS (--c-fond…) à partir d'une map de thèmes. On garde la puissance de Sass à la compilation et le basculement instantané au runtime (pas de recompilation pour changer de thème).

5. Générer des utilitaires

Enfin, @each transforme une famille de tokens en classes utilitaires : une par valeur, sans copier-coller.

Cas réel — les design systems que tu utilises déjà

Les plus grands systèmes de l'industrie fonctionnent exactement sur ce principe. Bootstrap génère toute sa grille et ses utilitaires d'espacement avec des @each sur des maps Sass. Le Primer de GitHub, le Lightning Design System de Salesforce ou Material partent tous d'une source de tokens unique déclinée par des outils. Aujourd'hui la tendance est d'écrire les tokens en JSON partagé (lisible aussi par le design et le mobile), puis de les injecter dans Sass : mais la mécanique « une source → des fonctions → du CSS » que tu viens de construire est rigoureusement la même. Ce petit projet est une maquette fidèle de ce qui tourne en production dans des équipes de centaines de personnes.

Glossaire

Design system
Ensemble cohérent de décisions visuelles (couleurs, espaces, typo…) et des outils qui les appliquent partout.
Design token
Plus petite décision réutilisable : une couleur, un espacement, un rayon, nommé et centralisé.
Map imbriquée
Map dont les valeurs sont elles-mêmes des maps : regroupe les tokens par famille.
Accesseur (jeton())
Fonction unique qui lit un token, plutôt que d'écrire une valeur « en dur ».
Custom property
Variable CSS native (--c-fond), modifiable au runtime ; idéale pour la thématisation.
Utilitaire
Classe à but unique (.p-m) souvent générée en boucle depuis les tokens.
Point de rupture
Largeur seuil d'une media query, centralisée dans une map ($points).
@content
Emplacement où un mixin injecte le bloc qu'on lui passe (cœur de respond-to).

Récap et vérification

  • Un design system Sass part d'une map de tokens imbriquée, marquée !default.
  • On y accède par une fonction (jeton()) qui échoue tôt (@error) — jamais de valeur en dur.
  • Le responsive passe par un mixin respond-to + @content ; le thème par @each → custom properties.
  • @each génère les utilitaires ; @forward assemble le tout en une API de dossier.

Vérifie ta compréhension

  1. Pourquoi lire les tokens via jeton() plutôt qu'en écrivant les valeurs directement ?
  2. Pourquoi générer des custom properties pour le thème au lieu de tout figer en Sass ?
  3. Quel rôle joue @content dans respond-to ?

Exercices

Exercice 1Échauffement

À partir de la map $tokens de la leçon, écris une règle .badge dont le padding vaut le token "espace" / "s" et le border-radius le token "rayon" / "pill", en passant par jeton().

Voir une solution

Le point important : aucune valeur en dur. On ne tape ni 8px ni 999px mais on demande le token au système. Si demain la charte décide que l'espacement "s" passe à 6px, ce badge — et tous les autres éléments qui utilisent ce token — suivent automatiquement. C'est toute la valeur d'un accesseur unique : la cohérence est garantie par construction, pas par discipline.

Exercice 2Application

Ajoute une famille "ombre" à tes tokens ("basse" et "haute"), puis génère des classes utilitaires .ombre-basse / .ombre-haute avec @each.

Voir une solution

On étend le système sans changer sa mécanique : une nouvelle famille dans la map, puis le même patron @each + interpolation #{$nom} qu'on a utilisé pour les espacements. C'est la force d'une architecture pilotée par les données : chaque nouveau besoin est une entrée de map, pas du code à recopier. Note que @each déstructure la paire $nom, $valeur à chaque tour, et que l'interpolation .ombre-#{$nom} construit dynamiquement le nom de classe.

Exercice 3Défi

Rends ton système réutilisable comme une bibliothèque : comment un projet tiers pourrait-il charger tes abstracts d'un seul @use et surcharger la couleur primaire sans éditer tes fichiers ?

Voir une solution

Deux ingrédients : un point d'entrée et des variables configurables. 1) Le point d'entrée. On crée abstracts/_index.scss qui ne fait que ré-exposer les partials du dossier : @forward 'tokens'; @forward 'fonctions'; @forward 'responsive'; @forward 'themes';. Grâce à @forward, tout ce que ces fichiers déclarent devient accessible à quiconque chargera le dossier. Un projet tiers charge alors l'ensemble d'un seul geste : @use 'abstracts' as ds; puis ds.jeton('espace', 'm'). 2) La configuration. Comme la map $tokens est déclarée avec !default, elle est surchargeable au chargement. Le _index.scss ré-expose aussi cette configurabilité (@forward 'tokens' with ($tokens: …) n'est pas nécessaire ici — on laisse le consommateur configurer). Côté projet tiers : @use 'abstracts/tokens' with ($tokens: ("couleur": ("primaire": #e0245e, …))); — les valeurs fournies remplacent les !default, sans jamais modifier tes sources. Le résultat : tu livres un design system que d'autres consomment et thèment sans le forker — exactement le contrat d'une bibliothèque Sass sérieuse. Le trio gagnant est toujours le même : !default pour l'ouverture, @forward pour l'API de dossier, membres privés (-/_) pour cacher la tuyauterie.

Mini-projet fil rouge — ton design system de A à Z

Pour clore le cours, assemblons le tout en un mini design system autonome. Il réunit une map de tokens imbriquée, un accesseur, un mixin responsive, la thématisation par custom properties et des utilitaires générés — un condensé de tout Sass.

Ce que tu vas construire

Un fichier abstracts complet : tokens → jeton() → respond-to → thème clair/sombre → utilitaires d'espacement. De quoi styler n'importe quel composant sans jamais écrire une valeur en dur.

Étapes

Les tokens

Déclare la map imbriquée $tokens (couleur, espace, rayon), marquée !default.

L'accesseur

Écris @function jeton($groupe, $cle) avec map.get profond et un @error si la clé manque.

Le responsive

Une map $points et @mixin respond-to($nom) qui enveloppe @content dans une media query.

Le thème

Une map $themes et un mixin qui émet des custom properties --c-* pour :root et [data-theme="sombre"].

Les utilitaires

Un @each sur les espacements pour générer .p-* et .gap-*.

ProjetFil rouge

Assemble les cinq étapes en un fichier abstracts complet. Essaie d'abord par toi-même, puis compare avec la solution de référence.

Voir une solution complète

Ce fichier unique est ton design system : chaque décision visuelle vit dans une map, chaque usage passe par jeton(), le responsive et le thème sont centralisés, et les utilitaires se régénèrent depuis les tokens. Ajoute une couleur ? Une ligne dans la map. Change l'échelle d'espacement ? Une ligne, et .p-*, .gap-* et tous les composants suivent. C'est l'aboutissement du cours : du CSS qui se pilote par les données au lieu de se répéter.
