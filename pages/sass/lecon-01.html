Module 1 · Les bases — Leçon 01

Découvrir Sass

~25 min Intermédiaire Prérequis : CSS

À la fin de cette leçon, tu sauras

  • dire ce qu'est un préprocesseur CSS ;
  • expliquer ce que Sass ajoute au CSS ;
  • distinguer les syntaxes SCSS et Sass indentée ;
  • comprendre comment Sass se compile en CSS.
Sommaire de la leçon

Quand un projet grandit, le CSS (cours CSS) devient vite répétitif : on recopie les mêmes couleurs partout, on duplique des blocs de règles, et la moindre refonte oblige à des recherches-remplacements fastidieux. Sass répond à ce problème. C'est un préprocesseur CSS : un langage qui ressemble à du CSS mais lui ajoute des super-pouvoirs (variables, imbrication, fonctions…), et qui se transforme en CSS classique que le navigateur sait lire. Cette première leçon pose le décor ; tu écriras du Sass dès la suivante.

Qu'est-ce qu'un préprocesseur ?

Un préprocesseur est un outil qui prend un fichier écrit dans un langage enrichi et produit, avant que le navigateur n'intervienne, un fichier dans le langage final. Pour Sass : tu écris un fichier .scss, un programme le compile en un fichier .css, et c'est ce .css que la page charge. Le navigateur ne voit jamais ton Sass : il ne connaît que le CSS final.

« Sass » signifie Syntactically Awesome Style Sheets. C'est le préprocesseur le plus répandu, mûr et bien outillé. Son rôle : rendre l'écriture du CSS plus concise, plus organisée et plus réutilisable.

Sass n'est pas seul : Less et Stylus

Sass a eu deux concurrents directs : Less (écrit en JavaScript, longtemps associé à Bootstrap 3) et Stylus (à la syntaxe très souple). Les trois rendent le même service — préprocesser du CSS —, mais Sass s'est imposé : c'est aujourd'hui le plus utilisé et le mieux outillé, d'où son choix dans ce cours.

Ce que Sass ajoute au CSS

Voici, en avant-goût, les apports que l'on étudiera tout au long du cours :

  • les variables ($couleur-primaire) pour nommer une valeur une seule fois ;
  • l'imbrication (nesting) pour refléter la structure HTML ;
  • les partials et @use pour découper le style en plusieurs fichiers ;
  • les mixins et fonctions pour réutiliser des blocs et calculer des valeurs ;
  • les boucles et conditions pour générer du CSS de façon programmatique.

On a écrit la couleur une seule fois (la variable), imbriqué le :hover dans .bouton, et même calculé une teinte plus sombre. Le CSS produit, lui, est tout à fait ordinaire : c'est tout l'intérêt : la puissance à l'écriture, la simplicité à l'arrivée.

Deux syntaxes : SCSS et Sass indentée

Sass existe en deux variantes d'écriture :

  • SCSS (extension .scss) : une surcouche du CSS. Tout CSS valide est du SCSS valide : on garde les accolades { } et les points-virgules. C'est la syntaxe la plus utilisée, et celle de ce cours.
  • la Sass indentée (extension .sass) : plus ancienne, elle supprime accolades et points-virgules au profit de l'indentation (comme Python). Plus rare aujourd'hui.

En Sass indentée, le même bloc s'écrirait sans accolades ni points-virgules, par simple décalage. Retiens surtout : SCSS = du CSS, en mieux. Comme c'est un sur-ensemble, tu peux renommer un fichier .css en .scss et il fonctionne déjà ; tu y ajoutes ensuite les fonctionnalités Sass à ton rythme.

Tu n'es pas obligé d'utiliser la ligne de commande : les outils de build (Vite, Webpack…) compilent le Sass tout seuls, et dans VS Code l'extension Live Sass Compiler fait le travail d'un clic. Dans tous les cas, le principe est identique : tu édites du .scss, l'outil produit du .css, la page charge le .css.

Ne modifie jamais le CSS généré

Le fichier .css produit par Sass est jetable : à la compilation suivante, il est entièrement réécrit. Si tu corriges un souci directement dans le .css, ta modification est écrasée au prochain --watch. La règle : on ne touche qu'au .scss source, jamais au .css de sortie.

Versionne le .scss, pas le .css

Puisque le CSS est régénéré à partir du Sass, beaucoup d'équipes ne mettent que le .scss sous Git et ajoutent le .css compilé au .gitignore (il est reconstruit au moment du déploiement). On évite ainsi les conflits de fusion sur un fichier que personne n'édite à la main.

Le CSS a-t-il rattrapé Sass ?

En partie : le CSS moderne a désormais des variables (les propriétés personnalisées --ma-var) et même l'imbrication native. Mais Sass garde des atouts que le CSS n'a pas : les mixins, les fonctions personnalisées, les boucles, et un vrai système de modules (@use). Sass et variables CSS se combinent d'ailleurs très bien ; on y reviendra.

Cas réel — Bootstrap, personnalisable grâce à Sass

Bootstrap, l'un des frameworks CSS les plus utilisés au monde, est écrit en Sass et distribué avec ses fichiers .scss. Pour obtenir ton Bootstrap — tes couleurs, tes espacements, tes rayons de bordure —, tu ne touches pas au code source : tu surcharges des variables ($primary, $spacer, $border-radius…) puis tu recompiles. Des milliers de sites obtiennent ainsi un thème sur mesure à partir d'une base commune, sans dupliquer ni modifier des milliers de lignes de CSS. C'est exactement la promesse de Sass : écrire peu, générer beaucoup.

Glossaire

Préprocesseur
Outil qui transforme un fichier écrit dans un langage enrichi en fichier final, avant exécution ; pour Sass : .scss → .css.
Sass
Syntactically Awesome Style Sheets : le préprocesseur CSS le plus répandu, qui ajoute variables, imbrication, mixins, fonctions et modules.
SCSS
La syntaxe de Sass qui est un sur-ensemble du CSS (accolades et points-virgules) ; extension .scss.
Sass indentée
L'ancienne syntaxe, sans accolades ni points-virgules, fondée sur l'indentation ; extension .sass.
Compilation
L'étape qui produit le CSS final à partir du Sass, exécutée par un outil (pas par le navigateur).
Dart Sass
L'implémentation officielle et à jour de Sass, invoquée par la commande sass.
Partial
Fichier Sass fragmentaire (nom préfixé d'un _) destiné à être inclus dans un autre via @use.
Mixin
Bloc de déclarations réutilisable et paramétrable : un des apports que le CSS n'a pas en natif.

Récap et vérification

  • Sass est un préprocesseur CSS : on écrit un langage enrichi, compilé en CSS classique avant le navigateur.
  • Il ajoute variables, imbrication, partials, mixins, fonctions, boucles et conditions.
  • Deux syntaxes : SCSS (.scss, surcouche du CSS, recommandée) et la Sass indentée (.sass).
  • La compilation (Dart Sass, sass --watch, outils de build, ou Live Sass Compiler) transforme le .scss en .css.

Exercices

Exercice 1Échauffement

Explique en une phrase pourquoi on dit que Sass est un « préprocesseur » et non un remplaçant du CSS.

Voir une solution

Sass est un préprocesseur parce qu'il s'exécute avant le navigateur : il transforme un fichier enrichi (.scss) en CSS ordinaire (.css). Il ne remplace pas le CSS : au contraire, il en produit ; le navigateur, lui, ne lit toujours que du CSS classique.

Exercice 2Application

Un collègue te donne un fichier theme.css et veut commencer à utiliser Sass. Quelle est la première étape la plus simple, et pourquoi est-ce possible ?

Voir une solution

Il peut simplement renommer theme.css en theme.scss et le compiler : ça marche immédiatement. C'est possible parce que SCSS est un sur-ensemble du CSS : tout CSS valide est déjà du SCSS valide. À partir de là, il peut introduire progressivement variables, imbrication et mixins, sans tout réécrire d'un coup.

Exercice 3Défi

On entend parfois : « maintenant que le CSS a les variables et l'imbrication, Sass ne sert plus à rien ». Cite une fonctionnalité de Sass qui n'a toujours pas d'équivalent natif en CSS, puis explique en quoi Sass et le CSS se complètent plutôt qu'ils ne s'opposent.

Voir une solution

1) Le CSS n'a pas tout rattrapé : les mixins (blocs paramétrables réutilisables), les fonctions personnalisées, les boucles (@each, @for) et les conditions n'ont pas d'équivalent natif ; le système de modules @use/@forward pour organiser un gros projet non plus. 2) Les deux se complètent : on peut utiliser les variables CSS (qui, elles, vivent dans le navigateur et changent à l'exécution, par exemple pour un thème) et les outils Sass à la compilation. Le choix dépend du besoin ; Sass reste très utile sur les projets structurés, même si pour une petite feuille de style le CSS natif peut désormais suffire.
