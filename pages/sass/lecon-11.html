Module 05 · Sass avancé & production — Leçon 11

Media queries et responsive avec Sass

~34 min Avancé Leçon 10 conseillée

À la fin de cette leçon, tu sauras

  • centraliser tes breakpoints dans une map ;
  • écrire un mixin de media query avec @content ;
  • choisir une stratégie mobile-first ;
  • générer une typographie fluide avec clamp().
Sommaire de la leçon

Le responsive en CSS pur, c'est vite le chaos : des @media (min-width: 768px) recopiés partout, des valeurs « magiques » qui varient d'un fichier à l'autre, et le jour où un breakpoint change, une chasse au trésor dans tout le projet. Sass résout le problème avec deux outils déjà connus — les maps et les mixins — plus une nouveauté : @content.

Centraliser les breakpoints

Première étape : une source de vérité unique pour les seuils, dans une map.

Plus aucun nombre « en dur » dispersé : on parlera de 'md', pas de 768px. Changer la valeur une fois la répercute partout.

@content : passer un bloc à un mixin

Jusqu'ici, un mixin recevait des arguments. Avec @content, il peut aussi recevoir un bloc de règles entier : tout ce qu'on écrit entre les accolades de @include vient s'insérer là où le mixin place son @content.

Ce que Sass génère

Le @include respond-to('md') { padding: 2rem; } compile en @media (min-width: 768px) { .carte { padding: 2rem; } }. On écrit une intention lisible (« à partir de md »), Sass produit la media query correcte — et le @error t'avertit tout de suite si tu tapes un nom de breakpoint qui n'existe pas.

Variable dans un @media : pense à l'interpolation

Une variable Sass placée dans la condition d'une media query ne fonctionne pas toujours telle quelle. @media (min-width: $valeur) passe parce que la valeur est simple, mais dès qu'on construit une chaîne — par exemple @media (min-width: $valeur) and (orientation: landscape) assemblée dynamiquement — Sass exige une interpolation #{} : @media #{'(min-width: ' + $valeur + ')'}. La règle sûre : si tu fabriques le texte de la requête, enveloppe-le dans #{…} pour que Sass l'insère littéralement.

Mobile-first : min-width d'abord

La convention dominante est le mobile-first : on écrit d'abord les styles du petit écran (sans media query), puis on ajoute avec des min-width pour les écrans plus larges. Les styles s'empilent du plus petit au plus grand, ce qui évite d'annuler sans cesse des règles.

Piège fréquent

En mobile-first, l'ordre des blocs compte autant que les seuils. Deux min-width ont la même spécificité : si tu écris respond-to('lg') avant respond-to('md'), sur un écran de 1200 px les deux media queries s'appliquent et c'est celle de 'md', venue en dernier, qui gagne — ton style « grand écran » a l'air ignoré. Empile toujours tes paliers du plus petit seuil au plus grand.

Nomme, ne code pas en dur

Un breakpoint doit avoir un nom ('md'), pas une valeur nue (768px). Le nom décrit une intention stable ; la valeur, elle, peut être ajustée sans rien casser ailleurs. C'est la même logique que les jetons d'un design system.

Typographie fluide avec clamp()

Les media queries font varier une taille par paliers (saut brusque à chaque seuil). Pour une taille qui évolue en continu avec la largeur, la fonction CSS clamp(min, idéal, max) est idéale — et Sass peut la générer à partir de deux tailles cibles.

Pour aller plus loin — paliers ou continu ?

Les media queries restent parfaites pour changer de mise en page (une colonne → trois colonnes). clamp() brille pour faire respirer une valeur (taille de police, marges) sans à-coups. Les deux approches se complètent : layout par paliers, tailles en fluide.

Cas réel — les mixins de Bootstrap

Bootstrap repose entièrement sur ce pattern : une map $grid-breakpoints (sm, md, lg, xl, xxl) alimente des mixins media-breakpoint-up() et media-breakpoint-down() qui utilisent @content exactement comme notre respond-to. Tout le système de grille et les classes utilitaires responsive du framework en découlent : écrire @include media-breakpoint-up(md) { … } partout garantit que les 1 300 fichiers de Bootstrap parlent des mêmes seuils. Le jour où l'équipe ajuste un breakpoint, elle édite une map. C'est la démonstration à grande échelle de ce que tu viens d'écrire en dix lignes.

Glossaire

Breakpoint
Seuil de largeur à partir duquel la mise en page change ; nommé ('md') et centralisé dans une map.
Map de breakpoints
Map Sass ($breakpoints) associant chaque nom de seuil à sa largeur : la source de vérité unique que le mixin consulte via map.get.
Media query
Règle CSS @media qui applique des styles selon une condition (souvent min-width).
@content
Emplacement, dans un mixin, où Sass insère le bloc de règles passé à @include.
Mobile-first
Stratégie où l'on écrit d'abord le style mobile puis on ajoute des min-width pour les écrans larges.
clamp()
Fonction CSS bornant une valeur entre un minimum et un maximum autour d'une taille idéale : valeur fluide.
Typographie fluide
Taille de texte qui varie continûment avec la largeur de la fenêtre, plutôt que par paliers.
@error
Interrompt la compilation avec un message ; sert à refuser un argument invalide (breakpoint inconnu).

Récap et vérification

  • Une map centralise les breakpoints : on nomme les seuils au lieu de les coder en dur.
  • Un mixin avec @content enveloppe un bloc dans la bonne media query.
  • Mobile-first : styles du petit écran d'abord, puis min-width pour agrandir.
  • clamp() (généré par Sass) fait varier une taille en continu, sans palier.

Exercices

Exercice 1Échauffement

Tu as la map $breakpoints: ('md': 768px). Écris l'appel qui donne à .menu un display: flex uniquement à partir de md, en supposant le mixin respond-to déjà défini.

Voir une solution

On appelle le mixin avec le nom du breakpoint et on lui passe le bloc de règles à appliquer au-delà de ce seuil : .menu { @include respond-to('md') { display: flex; } }. À la compilation, Sass récupère 768px dans la map, enveloppe le bloc dans la bonne media query et produit : @media (min-width: 768px) { .menu { display: flex; } }. Points importants : on écrit 'md' (l'intention) et non 768px (la valeur) — si le seuil change un jour, on n'édite que la map. Et parce que le mixin contient un @error, taper 'mdd' par erreur ferait échouer la compilation avec un message clair, plutôt que de générer silencieusement une media query vide. C'est tout l'intérêt d'un mixin de breakpoint : lisibilité et garde-fou.

Exercice 2Application

Un projet a des @media (min-width: 768px) recopiés dans une dizaine de fichiers, avec parfois 767px ou 770px par inadvertance. Décris la refactorisation Sass qui règle le problème de fond.

Voir une solution

Le symptôme (des seuils légèrement différents un peu partout) révèle un problème de fond : il n'y a pas de source de vérité. La refactorisation se fait en trois temps. 1) Centraliser. On crée un partial abstracts/_breakpoints.scss avec la map $breakpoints: ('sm': 480px, 'md': 768px, 'lg': 1024px, 'xl': 1280px) : désormais, un seul endroit définit ce que valent les seuils. 2) Outiller. On écrit (ou on charge) le mixin respond-to($nom) qui lit la map avec map.get, enveloppe @content dans un @media (min-width: …), et lève un @error si le nom est inconnu. Ce mixin devient le seul moyen autorisé d'écrire une media query dans le projet. 3) Remplacer partout. On substitue chaque @media (min-width: 768px) { … } par @include respond-to('md') { … }. Les 767px et 770px accidentels disparaissent : tout le monde passe par la map. Le bénéfice : cohérence immédiate (impossible d'avoir deux valeurs pour md), maintenance triviale (changer md à 800px = éditer une ligne, répercutée partout), et robustesse (une faute de frappe dans un nom échoue à la compilation au lieu de produire un bug visuel silencieux). On a transformé une constante dupliquée et fragile en un système nommé, centralisé et vérifié — exactement la démarche des grands frameworks CSS.

Exercice 3Défi

Un designer veut que le titre principal passe « en douceur » de 1,6 rem sur mobile à 2,8 rem sur grand écran, sans saut visible. Media queries ou clamp() ? Justifie et esquisse la solution.

Voir une solution

Le mot « en douceur » tranche la question : c'est un travail pour clamp(), pas pour des media queries. Avec des media queries, la taille change par paliers : elle resterait figée à 1,6 rem puis sauterait brusquement à 2,8 rem au franchissement du seuil — exactement le « saut visible » que le designer veut éviter. clamp(min, idéal, max), lui, fait évoluer la valeur continûment avec la largeur de la fenêtre, tout en la bornant pour qu'elle ne devienne jamais trop petite ni trop grande. La solution : plutôt que de calculer à la main le terme central (le Xrem + Yvw), on capitalise sur une fonction Sass fluid($min, $max) qui interpole entre les deux tailles cibles sur une plage de largeurs donnée. Concrètement : h1 { font-size: fluid(1.6rem, 2.8rem); }. La fonction calcule la pente (math.div($max - $min, $w2 - $w1)), en déduit l'ordonnée à l'origine, et renvoie un clamp(1.6rem, [base] + [pente]vw, 2.8rem). Résultat : sous 480 px le titre reste à 1,6 rem (plancher), au-delà de 1280 px il plafonne à 2,8 rem, et entre les deux il grandit progressivement, pixel par pixel, au fil du redimensionnement. Le bon partage : on garde les media queries pour ce qu'elles font de mieux — changer de mise en page (une colonne devient trois) — et on confie à clamp() les valeurs qui doivent respirer (tailles de texte, marges, gouttières). Encapsuler clamp() dans une fonction Sass rend le tout réutilisable et lisible : on déclare deux tailles, la mécanique reste cachée. C'est le mariage typique « Sass calcule, CSS anime ».
