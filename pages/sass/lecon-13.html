Module 05 · Sass avancé & production — Leçon 13

Migration @import → @use/@forward

~33 min Avancé Leçon 04 conseillée

À la fin de cette leçon, tu sauras

  • pourquoi @import est déprécié ;
  • migrer vers @use (namespaces, chargement unique) ;
  • ré-exposer une API avec @forward (show/hide) ;
  • configurer un module avec @use … with.
Sommaire de la leçon

Pendant quinze ans, @import fut la façon d'assembler des fichiers Sass. Il est aujourd'hui déprécié et sera retiré. Son remplaçant, le duo @use / @forward, corrige ses défauts de conception : pollution de l'espace global, fichiers ré-exécutés en boucle, aucune notion de « privé ». Savoir migrer est une compétence pratique : la plupart des vieux projets Sass en ont besoin.

Ce qui cloche avec @import

@import a trois défauts majeurs. Tout est global : chaque variable, mixin ou fonction importé se retrouve dans un seul grand sac, avec les collisions de noms qui vont avec. Rien n'est privé : impossible de cacher un détail d'implémentation. Et un même fichier importé plusieurs fois est ré-exécuté à chaque fois (CSS dupliqué, compilation plus lente).

Une dépréciation, pas une suppression immédiate

@import fonctionne encore, mais Dart Sass affiche des avertissements et prévoit son retrait. Migrer maintenant, c'est éviter une compilation qui cassera à une future version — et gagner tout de suite en clarté.

@use : charger avec un namespace

@use charge un fichier une seule fois et range ses membres sous un namespace (par défaut le nom du fichier, sans _ ni extension). On accède aux membres avec le préfixe.

Membres privés et configuration

Un membre dont le nom commence par - ou _ est privé : invisible hors de son fichier. Et une variable marquée !default devient configurable à l'import via @use … with.

with remplace les variables globales de config

À l'époque de @import, on configurait un module en redéfinissant ses variables avant l'import — fragile et implicite. @use 'x' with (…) rend la configuration explicite et locale : on voit d'un coup d'œil ce qu'on personnalise.

@forward : ré-exposer une API

@forward ne charge pas un fichier pour l'utiliser ici, mais pour le ré-exposer à ceux qui chargeront le fichier courant. C'est l'outil des points d'entrée (un index.scss qui regroupe tout un dossier).

Pour aller plus loin — show et hide

@forward 'mixins' show a, b ne ré-expose que a et b ; hide c ré-expose tout sauf c. On peut aussi préfixer les noms (@forward 'boutons' as btn-*) pour éviter les collisions dans un gros point d'entrée. C'est ainsi qu'une bibliothèque expose une API propre en cachant ses rouages.

Migrer sans tout casser

La migration est mécanique mais réelle : chaque référence « nue » doit être préfixée. L'outil officiel sass-migrator automatise l'essentiel.

Cas réel — la migration de grandes bases Sass

Des projets comme Bootstrap ou d'immenses design systems d'entreprise ont dû franchir ce cap. La stratégie gagnante n'est pas de tout réécrire à la main : on lance sass-migrator module --migrate-deps qui parcourt le graphe de dépendances, transforme les @import en @use, préfixe automatiquement les références et crée les index.scss avec @forward. Puis on relit les cas ambigus à la main (variables de configuration, membres à rendre privés). Résultat : fin des avertissements de dépréciation, compilation plus rapide (fichiers chargés une seule fois), et une API de dossier claire. C'est un chantier typique de « dette technique CSS » que tu rencontreras en entreprise ; le connaître te rend immédiatement utile sur un projet legacy.

Glossaire

@import (Sass)
Ancienne directive d'inclusion, dépréciée : tout global, ré-exécutée, sans notion de privé.
@use
Charge un fichier une seule fois et range ses membres sous un namespace préfixé.
Namespace
Préfixe sous lequel les membres d'un fichier chargé sont accessibles (couleurs.$primaire).
@forward
Ré-expose les membres d'un fichier à ceux qui chargeront le fichier courant ; base des points d'entrée.
show / hide
Filtrent ce que @forward ré-expose (liste blanche / liste noire de membres).
Membre privé
Variable, mixin ou fonction préfixé -/_, invisible hors de son fichier.
@use … with
Configure les variables !default d'un module au moment de le charger.
sass-migrator
Outil officiel qui convertit automatiquement @import en @use/@forward.

Récap et vérification

  • @import est déprécié (global, ré-exécuté, pas de privé) : migre vers @use/@forward.
  • @use charge une fois sous un namespace ; with configure, préfixe -/_ = privé.
  • @forward ré-expose (avec show/hide) : idéal pour un index.scss de dossier.
  • sass-migrator module --migrate-deps automatise le gros de la migration.

Vérifie ta compréhension

  1. Cite deux défauts de @import corrigés par @use.
  2. À quoi sert @forward par rapport à @use ?
  3. Comment configurer un module au chargement ?

Exercices

Exercice 1Échauffement

Convertis en Sass moderne : @import 'couleurs'; suivi de .a { color: $primaire; }, où $primaire vient de _couleurs.scss.

Voir une solution

On remplace l'import par @use et on préfixe la référence par le namespace du fichier. Version directe : @use 'couleurs'; puis .a { color: couleurs.$primaire; }. Le namespace par défaut est le nom du fichier sans le underscore initial ni l'extension (_couleurs.scss → couleurs). Si ce préfixe est trop long à ton goût, un alias règle ça : @use 'couleurs' as c; puis .a { color: c.$primaire; }. Pourquoi ce changement ? Avec @import, $primaire était une variable « nue » jetée dans l'espace global : si un autre fichier définissait aussi $primaire, l'un écrasait l'autre en silence. Avec @use, la variable reste rattachée à son fichier d'origine (couleurs.$primaire) : aucune collision possible, et on sait toujours d'où vient chaque valeur. C'est plus verbeux, mais infiniment plus sûr et lisible sur un vrai projet.

Exercice 2Application

Tu ranges tes abstracts (variables, fonctions, mixins) dans un dossier et tu veux pouvoir les charger d'un seul @use. Comment structures-tu le dossier ?

Voir une solution

La bonne pratique est de créer un point d'entrée (barrel file) pour le dossier : un fichier abstracts/_index.scss dont le seul rôle est de ré-exposer les partials du dossier avec @forward. Concrètement, _index.scss contient : @forward 'variables'; @forward 'fonctions'; @forward 'mixins';. Chaque @forward rend les membres du partial visibles pour quiconque chargera le dossier. Ensuite, depuis main.scss, un seul chargement suffit : @use 'abstracts' as a; (Sass trouve automatiquement le _index.scss). On accède alors à tout : a.$primaire, a.jeton(…), @include a.respond-to('md') { … }. Les avantages : un import unique et propre au lieu d'une pile de @use ; une API de dossier maîtrisée — on peut affiner avec @forward 'mixins' show respond-to, jeton; pour ne ré-exposer que l'utile et cacher les helpers internes ; et un préfixage possible (@forward 'boutons' as btn-*) pour éviter les collisions entre partials. C'est exactement l'organisation « 7-1 » modernisée : chaque dossier a son _index.scss, et main.scss assemble une poignée de points d'entrée clairs. Le graphe de dépendances devient lisible et chaque fichier n'est chargé qu'une fois.

Exercice 3Défi

On te confie un projet legacy : 60 fichiers en @import, des variables globales partout, des avertissements de dépréciation à chaque build. Décris ta stratégie de migration vers @use/@forward.

Voir une solution

Une migration de cette taille se mène avec méthode, pas à la main fichier par fichier. 1) Sécuriser le terrain. D'abord vérifier qu'on est bien sur Dart Sass (les anciennes implémentations ne connaissent pas le module system), figer une version, et s'assurer d'avoir un moyen de comparer le CSS produit avant/après (idéalement des tests visuels ou un diff du .css compilé) : l'objectif est une migration sans changement de rendu. 2) Automatiser le gros œuvre. Lancer l'outil officiel sass-migrator module --migrate-deps main.scss : il parcourt le graphe de dépendances depuis le point d'entrée, convertit les @import en @use, préfixe automatiquement toutes les références par le bon namespace, et peut générer les @forward. En un passage, l'écrasante majorité des 60 fichiers est traitée. 3) Relire les cas ambigus. L'outil ne devine pas tout : il faut repasser à la main sur (a) les variables de configuration — les marquer !default et remplacer les anciennes redéfinitions-avant-import par des @use … with (…) ; (b) les détails d'implémentation — préfixer d'un -/_ les helpers qui ne devraient pas fuir ; (c) créer un _index.scss par dossier avec @forward pour offrir des points d'entrée propres. 4) Nettoyer et vérifier. Recompiler : les avertissements de dépréciation doivent avoir disparu. Comparer le CSS de sortie au diff de référence pour confirmer qu'aucun style n'a bougé. Profiter du chantier pour supprimer le code mort désormais visible (un membre privé jamais utilisé saute aux yeux). 5) Verrouiller. Ajouter une règle de lint interdisant @import pour empêcher la régression. Le bénéfice final : plus de collisions globales (chaque membre est namespacé), compilation plus rapide (chaque fichier chargé une seule fois), API de dossier claire via @forward, et surtout un build pérenne qui ne cassera pas quand @import sera retiré. La clé est l'ordre : outil d'abord pour le volume, relecture humaine ensuite pour la finesse, vérification du rendu à chaque étape.
