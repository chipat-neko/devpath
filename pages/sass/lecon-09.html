Module 04 · Sass à l'échelle — Leçon 09

Design system en Sass (maps, thèmes)

~32 min Intermédiaire Leçon 08 conseillée

À la fin de cette leçon, tu sauras

  • centraliser des jetons (tokens) dans des maps Sass ;
  • générer des classes utilitaires par boucle ;
  • gérer un thème clair/sombre proprement ;
  • combiner maps Sass et custom properties CSS ;
  • générer les custom properties d'un thème et vérifier qu'aucun jeton ne manque.
Sommaire de la leçon

Un design system, c'est l'ensemble cohérent des décisions visuelles d'un produit : couleurs, espacements, typographies, rayons… Plutôt que de les disséminer en valeurs « en dur », on les centralise sous forme de jetons (design tokens). Sass offre exactement les outils pour ça : les maps et les boucles.

Les jetons dans une map

Une map Sass associe des clés à des valeurs (un peu comme un dictionnaire). Parfaite pour rassembler une échelle de valeurs liées : la palette de couleurs, les espacements…

Une source de vérité

Centraliser les jetons dans des maps, c'est garantir la cohérence (tout le monde puise dans la même palette) et la facilité de changement (modifier une couleur à un endroit la met à jour partout). C'est le cœur d'un design system.

Générer des utilitaires par boucle

En combinant une map et la boucle @each (vue en leçon 7), on génère automatiquement des classes utilitaires : une par jeton, sans les écrire à la main. Ajouter une couleur à la map crée la classe correspondante.

Même principe pour une échelle d'espacements (générer .m-1, .m-2… et .p-1, .p-2…). On obtient un petit framework utilitaire cohérent avec très peu de code, entièrement piloté par les jetons.

Thématisation : le problème du clair/sombre

Les variables Sass sont résolues à la compilation : une fois le CSS généré, elles n'existent plus. Or un thème clair/sombre doit pouvoir changer dans le navigateur, à l'exécution. Sass seul ne suffit donc pas : il faut les custom properties CSS (les variables --maVar), qui, elles, vivent dans le navigateur et se redéfinissent par contexte.

Variable Sass ≠ variable CSS

Une variable Sass ($x) est calculée puis disparaît à la compilation : idéale pour les jetons « fixes ». Une custom property CSS (--x) vit dans le navigateur et peut changer à l'exécution (selon un attribut, une media-query) : indispensable pour le thème. On les combine.

La bonne combinaison : Sass définit, CSS expose

Le pattern qui marche : utiliser Sass (maps, boucles) pour générer les custom properties, puis redéfinir ces dernières dans le thème sombre. Le reste du CSS ne référence que les var(--…) et bascule automatiquement.

C'est exactement ainsi que fonctionne le thème sombre de ce site (l'attribut data-theme sur <html>). Sass structure et génère ; les custom properties rendent le tout dynamique.

Cas réel — le mode sombre de GitHub

Quand GitHub a ajouté son mode sombre (puis ses thèmes « dimmed » et à contraste élevé), il n'a pas réécrit ses feuilles de styles : son design system Primer définit chaque couleur comme un jeton exposé en custom property CSS. Basculer de thème revient à charger un autre jeu de valeurs pour les mêmes variables ; tous les composants, qui ne référencent que des var(--…), suivent instantanément. C'est très exactement le pattern « Sass définit, CSS expose » de cette leçon — et ce qui permet d'ajouter un thème après coup sans toucher au reste.

Générer les custom properties depuis la map

Le fichier theme.scss plus haut tape les couleurs à la main, une fois par thème. Avec trois couleurs, ça passe ; avec trente, une faute de frappe finit toujours par se glisser. Et la couleur primaire n'est pas la même dans les deux thèmes : #3a6df0 atteint un rapport de contraste de 4,54:1 sur le blanc, mais seulement 4,02:1 sur le fond sombre, sous le seuil de 4,5:1 que les WCAG demandent pour un texte courant. Le thème sombre prend donc un bleu plus clair, #8aa2ff, qui monte à 7,56:1. Un thème sombre n'est pas une inversion des couleurs : chaque jeton se choisit pour le fond sur lequel il sera posé.

Dans une custom property, $valeur reste du texte

Écris --couleur-#{$nom}: $valeur; sans les accolades, et Sass n'émet ni erreur ni avertissement : il recopie le texte $valeur tel quel dans le CSS (essai fait avec Dart Sass 1.108.1, qui produit --couleur-fond: $valeur;). La documentation de Sass le dit en toutes lettres : dans la déclaration d'une custom property, tout est transmis au CSS sans être évalué, sauf l'interpolation #{…}, seule façon d'y injecter une valeur calculée. Le navigateur accepte $valeur comme valeur de variable ; c'est à l'usage que ça casse : background: var(--couleur-fond) devient invalide, et la propriété retombe sur sa valeur héritée ou initiale (ici, un fond transparent). D'où la règle : dans une custom property, toujours #{$valeur}.

Un jeton oublié ne prévient pas

Ce système a un point faible : rien n'oblige le thème sombre à redéfinir tous les jetons. Si 'texte' manque dans $theme-sombre, la compilation réussit, aucune ligne --couleur-texte n'est écrite pour [data-theme=dark], et la page en mode sombre garde la valeur de :root : un texte #1a1a2e sur un fond #14141f. Rapport de contraste calculé : 1,07:1, c'est-à-dire un texte presque invisible. Et personne ne s'en aperçoit avant d'avoir cliqué sur le bouton du mode sombre.

Où ranger le garde-fou

Place la boucle de contrôle juste sous les maps, dans le même partial : elle tourne à chaque compilation sans que personne ait à y penser, et elle n'ajoute aucune ligne au CSS, car @each, @if et @error ne laissent rien dans le fichier final (compilé avec les trois clés présentes, le fichier ci-dessus produit un CSS vide). Pour être complet, fais la même boucle dans l'autre sens : un jeton présent seulement dans le thème sombre n'aurait aucune valeur en mode clair.

Suivre le réglage du système

Le bouton n'est pas la seule source de préférence : le système d'exploitation a lui aussi un réglage clair/sombre, que CSS lit avec la media query prefers-color-scheme. Pour aller plus loin : color-scheme

Les custom properties ne colorent que ce que ton CSS dessine. Les contrôles natifs (cases à cocher, listes déroulantes, champs de saisie), les barres de défilement et le fond du canevas sont peints par le navigateur, avec ses propres couleurs. La propriété color-scheme lui dit dans quel jeu de couleurs la page peut s'afficher : avec color-scheme: dark, il peint ces éléments dans leur version sombre (source : MDN, page color-scheme). Sans elle, une page au thème sombre soigné garde, par défaut, des champs de formulaire clairs.

Glossaire

Design system
Ensemble cohérent des décisions visuelles d'un produit (couleurs, espacements, typographies…) et des composants qui les appliquent.
Jeton (token)
Valeur de design nommée et centralisée (ex. couleur-primaire), plutôt qu'écrite « en dur » à chaque usage.
Map Sass
Structure clé→valeur qui rassemble une échelle de jetons liés ; on y accède avec map.get.
Classe utilitaire
Petite classe à but unique (.texte-primaire, .m-2) souvent générée par boucle depuis une map.
Custom property
Variable CSS native (--x) qui vit dans le navigateur et se redéfinit par contexte ; lue avec var(--x).
Thématisation
Capacité à changer l'apparence (clair/sombre, marque) à l'exécution en redéfinissant les mêmes custom properties.
Source de vérité
Endroit unique où une décision est définie ; la modifier là met à jour tous ses usages.
Interpolation
Écriture #{…} qui insère la valeur d'une expression Sass dans un nom de classe, de propriété, ou dans la valeur d'une custom property, où $x seul serait recopié tel quel.
prefers-color-scheme
Media query qui lit le réglage clair/sombre du système d'exploitation ; elle fournit le thème par défaut tant que la personne n'a rien choisi.

Récap et vérification

  • Un design system centralise les décisions visuelles en jetons (tokens).
  • Les maps Sass = une source de vérité (palette, espacements) ; map.get pour y accéder.
  • @each + map = génération de classes utilitaires cohérentes sans répétition.
  • Pour la thématisation : variables Sass (fixe, compilation) + custom properties CSS (dynamique, exécution).
  • Un mixin + @each écrit les custom properties de chaque thème depuis sa map ; la valeur s'y injecte avec #{$valeur}, jamais $valeur seul.
  • Un jeton oublié ne fait pas d'erreur : une garde map.has-key + @error le fait apparaître dès la compilation.
  • prefers-color-scheme donne le thème par défaut, data-theme le choix de la personne, color-scheme la couleur des contrôles natifs.

Exercices

Exercice 1Échauffement

Tu as une map $espacements: ('1': 4px, '2': 8px, '3': 16px). Écris la boucle qui génère les classes de marge .m-1, .m-2, .m-3.

Voir une solution

On parcourt la map avec @each en récupérant à la fois la clé (le nom, ici '1', '2', '3') et la valeur (la taille), puis on construit le nom de classe par interpolation #{$nom} : @each $nom, $taille in $espacements { .m-#{$nom} { margin: $taille; } }. Sass génère alors .m-1 { margin: 4px; }, .m-2 { margin: 8px; }, .m-3 { margin: 16px; }. L'intérêt : si demain on ajoute '4': 24px à la map, la classe .m-4 apparaît automatiquement, sans toucher la boucle ; et toutes les marges restent cohérentes avec l'échelle d'espacement du design system (pas de valeurs arbitraires éparpillées). On peut étendre le principe pour générer d'un coup marges et paddings, voire les variantes directionnelles (haut, bas…), toujours à partir de la même source de vérité. C'est toute la puissance « map + boucle » : beaucoup de CSS cohérent à partir de très peu de code et d'une seule définition centralisée.

Exercice 2Application

Un développeur a écrit tout son thème sombre en dupliquant ses règles avec des variables Sass ($fond-sombre, etc.) et se demande pourquoi le bouton « mode sombre » ne change rien à l'exécution. Explique le problème et la solution.

Voir une solution

Le problème vient d'une confusion fondamentale entre variables Sass et variables CSS. Les variables Sass ($fond-sombre…) sont résolues à la compilation : au moment où Sass transforme le .scss en .css, chaque $fond-sombre est remplacé par sa valeur littérale, puis la variable disparaît. Le CSS final ne contient plus que des couleurs fixes, « gravées dans le marbre ». Or le bouton « mode sombre » agit dans le navigateur, à l'exécution (il ajoute typiquement un attribut comme data-theme="dark" sur la page). Mais comme les valeurs sont déjà figées dans le CSS compilé, il n'y a plus aucune variable à changer à ce moment-là : le JavaScript a beau basculer l'attribut, rien ne réagit. (Au mieux, le développeur a dû dupliquer chaque règle pour la version sombre, ce qui est verbeux, fragile et n'explique toujours pas comment basculer.) La solution : utiliser des custom properties CSS (variables --x), qui, elles, vivent dans le navigateur et peuvent être redéfinies par contexte à l'exécution. Concrètement : 1) définir les couleurs comme custom properties sur :root pour le thème clair (--couleur-fond: #fff; --couleur-texte: #1a1a2e;) ; 2) redéfinir les mêmes variables sous un sélecteur de thème sombre ([data-theme='dark'] { --couleur-fond: #14141f; --couleur-texte: #e8e8f0; }) ; 3) dans tout le reste du CSS, ne référencer que var(--couleur-fond), var(--couleur-texte), etc. Désormais, quand le bouton ajoute data-theme="dark", le navigateur applique les nouvelles valeurs des custom properties ; comme toutes les règles pointent vers ces var(--…), toute la page bascule instantanément, sans duplication. Où Sass intervient alors ? Il reste très utile en amont : on peut s'en servir (maps + boucles) pour générer proprement ces custom properties à partir des jetons, structurer les fichiers, etc. La bonne répartition : Sass définit et génère au build, les custom properties exposent et rendent dynamique au runtime. C'est précisément cette combinaison qui permet un thème clair/sombre robuste — et c'est ainsi que fonctionne le sélecteur de thème de ce site.

Exercice 3Défi

Synthèse du module « Sass à l'échelle » : une petite équipe veut transformer son CSS désordonné en un vrai design system maintenable et thématisable. Quels outils des leçons 8 et 9 mobilises-tu, et dans quel ordre ?

Voir une solution

On combine les deux leçons du module dans une démarche progressive, de la structure vers la systématisation : Étape 1 — Mettre de l'ordre (leçon 8) : d'abord assainir l'architecture. Adopter le pattern 7-1 pour ranger les partials par responsabilité (abstracts/, base/, components/, layout/…), assemblés par un main.scss via @use : on sait enfin où vit chaque chose. Adopter BEM (bloc__element--modificateur) pour des classes uniques à spécificité plate, éliminant les guerres de spécificité et les !important ; combiner BEM avec le sélecteur parent & de Sass pour composer les noms sans répétition, en évitant l'imbrication profonde. À ce stade, le CSS est navigable et prévisible, mais les valeurs (couleurs, espacements) sont peut-être encore éparpillées. Étape 2 — Centraliser les jetons (leçon 9) : extraire toutes les décisions visuelles en jetons rangés dans des maps Sass (palette, échelle d'espacements, rayons, typographies), placées dans abstracts/ : une source de vérité unique. On accède aux valeurs avec map.get, et surtout on remplace les valeurs « en dur » par ces jetons partout : la cohérence devient structurelle et un changement de couleur se fait à un seul endroit. Étape 3 — Générer (leçon 9) : à partir de ces maps, utiliser @each pour générer automatiquement les classes utilitaires cohérentes (couleurs de texte/fond, marges, paddings…) : beaucoup de CSS fiable pour très peu de code, et toute nouvelle entrée de jeton crée sa classe sans effort. Étape 4 — Rendre thématisable (leçon 9) : pour le clair/sombre, comprendre que les variables Sass (résolues au build) ne suffisent pas ; définir les couleurs en custom properties CSS sur :root, les redéfinir sous [data-theme='dark'], et ne référencer que var(--…) dans les composants : la bascule de thème devient instantanée et globale, sans duplication. On peut même générer ces custom properties depuis les maps Sass, unifiant jetons et thème. Le résultat : d'un CSS désordonné, on est passé à un design system — organisé (7-1), prévisible (BEM, spécificité plate), cohérent et centralisé (maps de jetons), productif (génération par boucle) et thématisable dynamiquement (Sass + custom properties). L'ordre compte : on structure avant de systématiser, et on garde tout piloté par les jetons. C'est l'aboutissement du module : Sass n'est plus seulement « du CSS en mieux » au niveau syntaxe, mais le socle d'un système visuel maintenable à l'échelle et en équipe.
