Voici la fonctionnalité qui a fait la légende de Lisp : les macros. Parce que le code Lisp est une liste de données (l'homoiconicité de la leçon 2), un programme peut écrire et transformer du code Lisp. Les macros te permettent d'ajouter de nouvelles constructions syntaxiques au langage — comme si tu en étendais la grammaire. Aucun autre langage n'offre cela aussi naturellement.

Fonction vs macro : l'évaluation des arguments

La différence clé : une fonction reçoit ses arguments déjà évalués. Une macro reçoit ses arguments non évalués, sous forme de code (de listes), qu'elle transforme en un nouveau code — lequel sera ensuite évalué. La macro agit donc avant l'exécution, à la transformation du programme.

Pourquoi une fonction ne suffit pas toujours

Imagine vouloir créer ta propre construction (sauf condition corps) qui n'exécute le corps que si la condition est fausse. Avec une fonction, impossible : le corps serait évalué avant l'appel, même si la condition est vraie. Il faut contrôler quand les arguments sont évalués — c'est précisément le rôle d'une macro.

Définir une macro simple

En Scheme, on utilise define-syntax avec un motif de réécriture (syntax-rules). La macro dit : « quand tu vois cette forme, remplace-la par celle-ci ».

La macro réécrit (sauf C corps...) en (if (not C) (begin corps...)) avant l'évaluation.

L'équivalent en Common Lisp

Common Lisp utilise defmacro, qui construit le nouveau code avec le quasiquote (leçon 2). C'est plus puissant (du vrai code dans la macro) mais demande plus de soin.

Le , insère la condition, le ,@ « déplie » la liste du corps : on construit littéralement le code à produire.

Construire un mini-langage

Les macros permettent d'écrire des DSL (langages dédiés) : une syntaxe sur mesure pour un domaine. Beaucoup de formes de Lisp lui-même (comme when, unless, cond) sont en réalité des macros bâties sur if. Tu peux en ajouter de nouvelles, indiscernables des formes natives.

Pièges fréquents

Piège fréquent

Abuser des macros : si une fonction suffit, utilise une fonction (plus simple, composable, débogable). Réserve les macros aux cas où tu dois contrôler l'évaluation ou créer une syntaxe — pas pour ce qu'une fonction ferait très bien.

Pour aller plus loin

Pour aller plus loin

Le grand danger des macros est la capture de variable (une variable introduite par la macro entre en collision avec celle de l'utilisateur). Le syntax-rules de Scheme est hygiénique : il évite ce piège automatiquement. En Common Lisp, on génère des noms uniques avec gensym.

Récap et vérification

  • Une macro reçoit ses arguments non évalués (du code) et les réécrit en un nouveau code.
  • Contrairement à une fonction, elle contrôle quand et si les arguments sont évalués.
  • define-syntax/syntax-rules (Scheme) ou defmacro (Common Lisp) les définissent.
  • Les macros permettent d'étendre le langage et de créer des DSL ; à n'utiliser que si une fonction ne suffit pas.

Exercice 1Échauffement

Explique pourquoi (sauf (vrai?) (effacer-tout)) ne peut pas être une fonction.

Voir une solution

Parce qu'une fonction évalue ses arguments avant l'appel : (effacer-tout) s'exécuterait toujours, même quand la condition est vraie. Seule une macro peut empêcher l'évaluation du corps selon la condition.

Écris une macro echange ne servant qu'avec des effets de bord… non : explique plutôt pourquoi les macros rendent Lisp si extensible, en une phrase.

Voir une solution

Parce que le code étant une simple liste de données, une macro peut générer n'importe quelle structure de code avant l'exécution : on peut donc ajouter au langage de nouvelles formes de contrôle ou des syntaxes entières, indiscernables des formes natives, sans modifier le compilateur.
