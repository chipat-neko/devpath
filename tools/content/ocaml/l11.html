Le système de types d'OCaml est l'un des plus puissants qui soient : il infère les types tout seul, et il sait exprimer des garanties que peu de langages atteignent. Au-delà des variants et du pattern matching que tu connais, deux mécanismes avancés repoussent encore les limites : les variants polymorphes (souples et réutilisables) et les GADT (types algébriques généralisés), qui permettent d'encoder des invariants dans le type lui-même. Cette leçon t'ouvre ces portes — un aperçu de ce qui fait la réputation d'OCaml.

Rappel : les variants ordinaires

Un variant ordinaire définit un type fermé par une liste de constructeurs. C'est la base de la modélisation en OCaml.

Pratique, mais chaque constructeur appartient à un seul type. Si deux types ont un cas Rouge, ce sont deux constructeurs distincts. Les variants polymorphes lèvent cette contrainte.

Les variants polymorphes

Un variant polymorphe utilise un tag précédé d'un accent grave (`). Il n'a pas besoin d'être déclaré dans un type fermé : on peut l'utiliser à la volée, et le partager entre plusieurs types.

Les variants polymorphes brillent quand plusieurs modules partagent des étiquettes communes, ou pour des types « ouverts » qu'on étend. Leur souplesse a un coût : des messages d'erreur plus complexes ; on les réserve donc aux cas où leur réutilisabilité est vraiment utile.

Le problème que résolvent les GADT

Imagine un petit langage d'expressions : des entiers, des booléens, des additions. Avec un variant ordinaire, rien n'empêche d'écrire une expression mal typée, comme « additionner un booléen ». L'évaluateur doit alors gérer des cas absurdes à l'exécution.

Les GADT : des invariants dans le type

Un GADT (Generalized Algebraic Data Type) permet à chaque constructeur de préciser le type de son résultat. On peut ainsi paramétrer l'expression par le type qu'elle produit — et rendre les expressions mal typées impossibles à construire.

La magie : Add n'accepte que des int expr. Écrire Add (Bool true, Int 1) est désormais rejeté à la compilation. Et eval renvoie un int pour une int expr, un bool pour une bool expr — la justesse de typage est garantie par le compilateur, pas par des vérifications à l'exécution.

Pourquoi c'est puissant

Les GADT permettent d'encoder des règles dans les types : un état impossible devient inexprimable. C'est l'idéal du « make illegal states unrepresentable » poussé à son extrême. On les emploie pour des interpréteurs typés, des encodeurs/décodeurs sûrs, des machines à états où chaque transition est vérifiée à la compilation. C'est l'une des raisons pour lesquelles OCaml est prisé là où la correction compte (compilateurs, finance, vérification).

Pièges fréquents

Piège fréquent

Atteindre les GADT trop tôt. Ce sont des outils avancés : pour la plupart des programmes, un variant ordinaire et du pattern matching suffisent amplement et restent plus lisibles. Les GADT (et leur annotation type a. … obligatoire sur les fonctions récursives polymorphes) ne se justifient que lorsqu'on a réellement besoin de garantir des invariants au niveau du type. N'alourdis pas un code simple avec de la machinerie de types dont il n'a pas besoin.

Pour aller plus loin

Pour aller plus loin

OCaml possède un système de types parmi les plus expressifs du monde fonctionnel : au-delà des GADT, il offre les modules de première classe, les foncteurs (vus en leçon 8) et l'inférence de type complète. C'est cette richesse qui en fait le langage des compilateurs (le compilateur Rust a longtemps été écrit en OCaml, ainsi que de nombreux outils de preuve et de finance). Comprendre les GADT, c'est entrevoir pourquoi des équipes choisissent OCaml quand une erreur de logique coûte cher.

Récap et vérification

  • Les variants polymorphes (`Tag) sont ouverts et partageables, sans déclaration préalable (souples, mais plus délicats).
  • Un variant ordinaire laisse construire des valeurs « absurdes » ; les GADT l'empêchent.
  • Un GADT précise le type de résultat de chaque constructeur : il encode des invariants dans le type.
  • On rend les états illégaux inexprimables ; outil avancé, à réserver aux cas qui le justifient.

Dans le GADT expr, pourquoi Add (Bool true, Int 1) est-il rejeté ?

Voir une solution

Parce que le constructeur Add a le type int expr * int expr -> int expr : il n'accepte que des int expr. Or Bool true a le type bool expr. Le compilateur détecte l'incompatibilité et refuse de compiler — l'expression mal typée est tout simplement impossible à construire.

Exercice 3Défi

En une phrase, quel principe de conception les GADT poussent-ils à l'extrême ?

Voir une solution

« Rendre les états illégaux inexprimables » (make illegal states unrepresentable) : en encodant des invariants directement dans le type, on fait en sorte que le compilateur rejette toute valeur qui violerait les règles, plutôt que de devoir les vérifier à l'exécution.
