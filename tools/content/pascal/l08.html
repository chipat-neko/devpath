Un programme sérieux ne tient pas dans un seul fichier. Pour le garder lisible et réutilisable, on le découpe en modules indépendants. En Pascal, ce module s'appelle l'unité (unit), une invention de Turbo Pascal devenue centrale dans Delphi et Free Pascal. Une unité regroupe des types, procédures et fonctions liés, et expose une interface claire. Cette leçon t'apprend à structurer un vrai projet en plusieurs fichiers.

Qu'est-ce qu'une unité ?

Une unité est un fichier (.pas) qui rassemble du code réutilisable : par exemple, toutes les fonctions mathématiques d'un projet, ou la gestion d'une liste de clients. D'autres parties du programme l'utilisent sans connaître ses détails internes. C'est l'encapsulation à l'échelle du module.

Interface et implémentation

Une unité se divise en deux sections clés :

  • interface — la partie publique : ce que les autres peuvent voir et utiliser (les en-têtes des procédures, les types exposés) ;
  • implementation — la partie privée : le code réel, caché de l'extérieur.

Dans l'interface, on ne met que les en-têtes (signatures) ; le corps complet va dans l'implementation. Qui utilise UMaths voit Carre et Cube, mais ignore comment ils sont écrits : on peut réécrire l'implémentation sans rien casser ailleurs.

Utiliser une unité : uses

Pour employer une unité dans un programme (ou une autre unité), on la déclare avec uses, juste après l'en-tête.

On peut lister plusieurs unités séparées par des virgules : uses UMaths, SysUtils, Crt;. Beaucoup de fonctionnalités de Pascal vivent dans des unités standard — par exemple SysUtils (utilitaires) ou Crt (gestion de l'écran texte).

La section d'initialisation

Une unité peut comporter un bloc final, exécuté automatiquement au démarrage du programme : pratique pour préparer un état initial.

Pourquoi découper en unités ?

La modularité apporte des bénéfices concrets :

  • lisibilité : chaque unité a une responsabilité claire ;
  • réutilisation : une unité UMaths sert dans plusieurs projets ;
  • compilation séparée : modifier une unité ne force pas à tout recompiler ;
  • travail en équipe : chacun développe ses unités sans se gêner.

Pièges fréquents

Piège fréquent

Les dépendances circulaires : si l'unité A fait uses B dans son interface, et B fait uses A dans la sienne, le compilateur refuse. La solution est souvent de déplacer un uses dans la section implementation (où les dépendances croisées sont tolérées) plutôt que dans l'interface. Pense tes unités en couches : les plus basses ne dépendent pas des plus hautes.

Pour aller plus loin

Pour aller plus loin

Le modèle interface/implémentation des unités Pascal a marqué l'histoire : il préfigure les modules et la séparation en-tête/source qu'on retrouve partout (les .h/.c du C, les modules de bien des langages). Delphi a poussé l'idée très loin avec sa vaste bibliothèque de composants visuels (VCL), où chaque composant est une unité réutilisable — une des raisons de son succès durable en entreprise.

Récap et vérification

  • Une unité (unit) regroupe du code réutilisable dans un fichier séparé.
  • interface = partie publique (en-têtes) ; implementation = code privé.
  • uses importe une ou plusieurs unités ; initialization s'exécute au démarrage.
  • Bénéfices : lisibilité, réutilisation, compilation séparée, travail en équipe.
