Écrire un contrat n'est que la moitié du chemin : il faut ensuite le compiler, le déployer sur un réseau, et permettre à des applications d'interagir avec lui. Heureusement, on n'expérimente jamais directement avec de l'argent réel : on utilise d'abord des réseaux de test gratuits. Cette leçon te guide du code à un contrat vivant, accessible depuis une application web.

Remix : l'atelier dans le navigateur

Remix est un environnement de développement Solidity qui tourne directement dans le navigateur, sans rien installer. On y écrit le contrat, on le compile, et on le déploie en quelques clics ; il intègre aussi un débogueur et une machine virtuelle locale pour tester instantanément. C'est l'outil idéal pour apprendre : tu peux y coller les exemples de ce cours et les exécuter.

Les réseaux : mainnet et testnets

Ethereum a plusieurs réseaux :

  • le mainnet : le réseau principal, avec de l'ether réel (de la vraie valeur) ;
  • les testnets (Sepolia, Holesky…) : des réseaux de test où l'ether n'a aucune valeur, qu'on obtient gratuitement via un « robinet » (faucet).

Règle absolue : on développe et on teste toujours sur un testnet avant d'envisager le mainnet. Déployer un contrat non testé sur le mainnet, c'est risquer de l'argent réel sur du code potentiellement bogué.

Déployer un contrat

Déployer, c'est envoyer le bytecode compilé du contrat dans une transaction spéciale. Le réseau lui attribue alors une adresse unique et permanente. Le déploiement coûte du gas (proportionnel à la taille du contrat). Une fois déployé, le contrat vit à son adresse, et n'importe qui peut appeler ses fonctions publiques.

L'ABI : le mode d'emploi du contrat

Pour qu'une application sache comment parler à un contrat, elle a besoin de deux choses : son adresse et son ABI (Application Binary Interface). L'ABI est une description (en JSON) des fonctions du contrat — leurs noms, paramètres et types de retour. Le compilateur la génère automatiquement. C'est le « contrat d'interface » entre le monde extérieur et le bytecode EVM.

Interagir depuis une application web (dApp)

Une application décentralisée (dApp) est une page web qui dialogue avec un contrat. On utilise une bibliothèque JavaScript — ethers.js ou web3.js — et un portefeuille (comme MetaMask) qui signe les transactions pour l'utilisateur.

On retrouve la distinction de la leçon 3 : lire est gratuit et immédiat ; écrire crée une transaction que l'utilisateur doit signer et payer (en gas), puis attendre sa confirmation. La dApp écoute aussi les événements (leçon 5) pour réagir à l'activité du contrat.

Pièges fréquents

Piège fréquent

Déployer sur le mainnet par inadvertance, ou y déployer un contrat insuffisamment testé. Vérifie toujours sur quel réseau ton portefeuille est connecté avant de cliquer sur « déployer » : une transaction mainnet coûte de l'ether réel et est irréversible. De même, ne confonds pas la clé privée d'un compte de test avec celle d'un compte réel : ne mets jamais de vrais fonds sur une adresse dont la clé a traîné dans du code de test.

Pour aller plus loin

Pour aller plus loin

Pour des projets sérieux, on dépasse Remix au profit de frameworks professionnels comme Hardhat ou Foundry (leçon 9) : ils automatisent la compilation, les tests (avec des milliers de scénarios), le déploiement reproductible et la vérification du code sur Etherscan (pour que tout le monde puisse lire et auditer ton contrat). La vérification du code source est d'ailleurs une attente forte de l'écosystème : un contrat dont le code n'est pas public inspire la méfiance.

Récap et vérification

  • Remix : éditeur/compilateur/déployeur dans le navigateur, idéal pour apprendre.
  • On teste toujours sur un testnet (ether sans valeur) avant le mainnet (ether réel).
  • Déployer donne au contrat une adresse permanente ; l'ABI décrit ses fonctions.
  • Une dApp (ethers.js/web3.js + portefeuille) lit gratuitement et écrit via des transactions signées.

Exercice 2Application

Quelles sont les deux informations dont une dApp a besoin pour interagir avec un contrat ?

Voir une solution

L'adresse du contrat (où il se trouve sur la blockchain) et son ABI (la description de ses fonctions, qui dit comment les appeler).

Exercice 3Défi

Pourquoi une opération de lecture depuis une dApp est-elle instantanée et gratuite, contrairement à une écriture ?

Voir une solution

Parce qu'une lecture (fonction view/pure) ne modifie pas l'état de la blockchain : elle peut être servie directement par un nœud à partir de l'état actuel, sans créer de transaction, donc sans gas ni attente. Une écriture, elle, modifie l'état : elle doit passer par une transaction signée par l'utilisateur, payée en gas, diffusée au réseau, puis incluse dans un bloc et confirmée — ce qui prend du temps et coûte de l'argent.
