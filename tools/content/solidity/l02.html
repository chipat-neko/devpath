Pour programmer un contrat, il faut connaître ses types de données et — concept crucial en Solidity — comprendre où les données sont rangées. Car ici, le stockage n'est pas anodin : écrire une donnée de façon permanente sur la blockchain coûte de l'argent. La distinction entre storage (permanent) et memory (temporaire) est donc fondamentale. Cette leçon explore les types et le stockage.

Les types de base

Solidity est fortement typé : chaque variable a un type fixe. Les principaux :

  • uint — entier non signé (positif), souvent uint256 (256 bits) ;
  • int — entier signé (peut être négatif) ;
  • bool — booléen (true/false) ;
  • address — une adresse Ethereum (un compte ou un contrat) ;
  • string — du texte ;
  • bytes — des données binaires.

Le type address est propre à la blockchain : il désigne un compte (utilisateur) ou un contrat. C'est avec lui qu'on identifie « qui » dans un contrat.

Les entiers de taille fixe

Particularité : les entiers ont une taille en bits précise (uint8, uint256…). uint256 est le plus courant. Depuis la version 0.8, Solidity vérifie automatiquement les débordements (overflow) : une addition qui dépasserait la capacité du type provoque une erreur au lieu de « repartir à zéro » silencieusement — une protection précieuse, car des débordements ont causé des failles célèbres.

Les variables d'état

Une variable d'état est déclarée au niveau du contrat (hors des fonctions). Elle est stockée de façon permanente sur la blockchain : sa valeur persiste entre les appels, et fait partie de l'« état » du contrat.

Chaque modification d'une variable d'état est une écriture sur la blockchain — donc une opération payante (en gas, leçon 6). C'est pourquoi on minimise le stockage : il a un coût réel.

Storage contre memory

Voici la distinction centrale. Solidity gère deux emplacements de données :

  • storage — le stockage permanent sur la blockchain (les variables d'état). Coûteux, persistant.
  • memory — la mémoire temporaire, le temps d'un appel de fonction. Moins coûteuse, effacée après.

Pour les types complexes (chaînes, tableaux, structs) passés en paramètre ou déclarés localement, on doit préciser memory ou storage. Les types simples (uint, bool, address) sont copiés par valeur et n'ont pas besoin de cette annotation.

Les valeurs par défaut

En Solidity, il n'existe pas de null : une variable non initialisée prend une valeur par défaut. Un uint vaut 0, un bool vaut false, une address vaut l'adresse zéro (0x0000...0000), une string est vide.

Pièges fréquents

Piège fréquent

Oublier que l'adresse zéro (address(0)) est la valeur par défaut d'une address, et l'accepter par mégarde. Envoyer des jetons ou des droits à address(0) revient souvent à les détruire définitivement (personne ne possède la clé de cette adresse). Vérifie systématiquement qu'une adresse fournie n'est pas address(0) avant de lui transférer quoi que ce soit — un contrôle de sécurité élémentaire mais vital.

Pour aller plus loin

Pour aller plus loin

Le coût du storage a façonné le style Solidity : on cherche à minimiser les écritures, à regrouper plusieurs petites variables dans un même « emplacement » de 256 bits (le packing), et à privilégier les calculs en memory. Optimiser le gas n'est pas un détail : sur un contrat très utilisé, une écriture évitée représente des économies réelles pour tous ses utilisateurs. La performance, ici, se mesure en argent.

Récap et vérification

  • Types : uint/int (taille fixe, overflow vérifié en 0.8+), bool, address, string, bytes.
  • Une variable d'état est permanente (en storage) ; chaque écriture coûte du gas.
  • storage = permanent (blockchain) ; memory = temporaire (le temps d'un appel).
  • Pas de null : valeurs par défaut (0, false, address(0), "").

Exercice 3Défi

Dans une fonction prenant un string en paramètre, quelle annotation faut-il préciser, et pourquoi ?

Voir une solution

Il faut préciser memory (ou calldata) pour un paramètre de type complexe comme string, car Solidity exige de savoir où la donnée est rangée. memory indique une copie temporaire, valable le temps de l'appel ; on l'utilise pour les paramètres qu'on ne veut pas stocker de façon permanente. Les types simples (uint, bool...) n'ont pas besoin de cette annotation.
