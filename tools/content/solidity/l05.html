Un contrat sécurisé doit contrôler qui peut faire quoi, signaler ce qui se passe, et refuser les actions invalides. Solidity offre trois mécanismes pour cela : les modificateurs (des gardes réutilisables), les événements (un journal des actions), et la gestion d'erreurs avec require et revert. Ces outils sont au cœur de la sécurité d'un contrat. Cette leçon les met en place.

Identifier l'appelant : msg.sender

À tout moment, une fonction connaît l'adresse de celui qui l'appelle : msg.sender. C'est la base du contrôle d'accès : comparer msg.sender à une adresse autorisée (le propriétaire) pour décider si l'action est permise.

Le constructeur (constructor) s'exécute une seule fois, au déploiement. Ici, il enregistre le déployeur comme propriétaire : un patron quasi universel.

La gestion d'erreurs : require

require vérifie une condition : si elle est vraie, l'exécution continue ; si elle est fausse, toute la transaction est annulée (revert), et les modifications déjà faites sont défaites. C'est la garde de validation par excellence.

Si le solde est insuffisant, require annule tout et renvoie le message "Solde insuffisant". Crucial : une transaction annulée laisse l'état intact (comme si rien ne s'était passé), ce qui protège contre les états incohérents. On utilise aussi revert("message") pour annuler explicitement, et require pour valider les entrées et les conditions.

Les modificateurs : des gardes réutilisables

Un modificateur (modifier) encapsule une vérification qu'on veut réutiliser sur plusieurs fonctions. Le _; à l'intérieur marque l'endroit où s'insère le code de la fonction décorée.

Le modificateur seulementProprietaire s'applique en l'ajoutant à la signature de la fonction. Avant d'exécuter le corps, Solidity lance le modificateur : s'il échoue, la fonction n'est jamais exécutée. C'est le moyen idiomatique de protéger des fonctions sensibles, sans répéter la même vérification partout.

Les événements : journaliser les actions

Un événement (event) émet une trace dans le journal de la blockchain, qu'on peut écouter depuis l'extérieur (une application web). Les contrats ne peuvent pas « notifier » directement ; les événements sont le moyen de signaler ce qui s'est passé.

On déclare l'événement avec event, et on l'émet avec emit. Le mot indexed sur certains paramètres permet de les filtrer efficacement (par exemple « tous les transferts vers cette adresse »). Les applications web (dApps) s'abonnent à ces événements pour réagir et afficher l'activité du contrat.

Pièges fréquents

Piège fréquent

Croire qu'un événement change l'état ou renvoie une valeur à l'appelant : ce n'est pas le cas. Un événement n'est qu'un journal, lisible hors de la blockchain (par les applications), pas par les contrats. À l'inverse, ne te repose pas sur la valeur de retour d'une fonction qui modifie l'état : depuis l'extérieur, une transaction ne renvoie pas sa valeur de retour directement. Pour communiquer un résultat à une dApp, utilise un événement.

Pour aller plus loin

Pour aller plus loin

Solidity moderne (0.8.4+) propose les erreurs personnalisées (error), plus économes en gas que les longs messages de require : error SoldeInsuffisant(uint256 demande, uint256 dispo); puis revert SoldeInsuffisant(montant, solde);. Elles transmettent des données structurées sur l'échec tout en coûtant moins cher à déployer et à exécuter. C'est devenu la bonne pratique pour les contrats soucieux du gas.

Récap et vérification

  • msg.sender identifie l'appelant ; le constructor s'exécute une fois au déploiement.
  • require(condition, "msg") valide ; sinon annule toute la transaction (état intact). revert annule explicitement.
  • Un modificateur (modifier + _;) factorise une garde réutilisable (ex. contrôle d'accès).
  • Un événement (event/emit, indexed) journalise pour les applications externes.
