L'héritage de classe ne suffit pas toujours à structurer un programme. Objective-C offre deux mécanismes complémentaires, très utilisés dans les frameworks Apple : les protocoles (des contrats de méthodes, comme les interfaces d'autres langages) et les catégories (un moyen d'ajouter des méthodes à une classe existante, même qu'on n'a pas écrite). Ces deux outils reflètent l'esprit dynamique et flexible du langage.

Les protocoles : des contrats

Un protocole déclare une liste de méthodes qu'une classe s'engage à fournir, sans dire comment. C'est l'équivalent des interfaces en Java ou des protocols en Swift. Une classe qui adopte un protocole promet d'implémenter ses méthodes.

Les chevrons <Dessinable> après la classe parente indiquent l'adoption. Cercle doit alors implémenter dessiner et surface, sinon le compilateur avertit. Un avantage : on peut traiter de façon uniforme tout objet conforme à Dessinable, quelle que soit sa classe.

Méthodes optionnelles

Un protocole peut distinguer des méthodes obligatoires (@required, le défaut) et optionnelles (@optional). Avant d'appeler une méthode optionnelle, on vérifie qu'elle est implémentée.

respondsToSelector: demande à un objet « sais-tu répondre à ce message ? » — une introspection rendue possible par le runtime dynamique.

La délégation : le patron roi d'Apple

Les protocoles sous-tendent un patron omniprésent dans les frameworks Apple : la délégation. Un objet (par exemple une liste à l'écran) confie certaines décisions à un autre objet, son delegate, qui adopte un protocole défini. C'est ainsi que ton code « réagit » aux composants du système.

Le type id<Dessinable> signifie « n'importe quel objet conforme au protocole Dessinable ». id est le type « objet quelconque » d'Objective-C.

Les catégories : étendre une classe existante

Une catégorie permet d'ajouter des méthodes à une classe déjà écrite — y compris une classe d'Apple comme NSString — sans en hériter ni toucher son code source. C'est une capacité étonnante, propre aux langages dynamiques.

Le nom entre parenthèses (Inversion) est celui de la catégorie. Après ça, toutes les NSString du programme disposent de chaineInversee. On enrichit ainsi des classes sans héritage : pratique pour regrouper des méthodes utilitaires.

Pièges fréquents

Piège fréquent

Utiliser une catégorie pour remplacer une méthode existante d'une classe : c'est possible mais dangereux : le comportement devient imprévisible (laquelle des deux s'exécute ?) et peut casser le framework. Les catégories servent à ajouter de nouvelles méthodes, pas à écraser celles qui existent. Pour modifier un comportement, préfère l'héritage ou la composition.

Pour aller plus loin

Pour aller plus loin

La délégation explique pourquoi le développement iOS classique tourne autour de protocoles comme UITableViewDelegate et UITableViewDataSource : un tableau à l'écran demande à ton objet « combien de lignes ? que mettre dans chacune ? que faire au clic ? » via les méthodes du protocole. Maîtriser les protocoles, c'est comprendre l'architecture même des applications Apple — un savoir qui se transpose directement à Swift, où le patron est identique.

Récap et vérification

  • Un protocole est un contrat de méthodes ; une classe l'adopte avec <Protocole>.
  • Méthodes @required / @optional ; respondsToSelector: teste leur présence.
  • La délégation (delegate, id<Protocole>) est le patron clé des frameworks Apple.
  • Une catégorie ajoute des méthodes à une classe existante (sans héritage).
