Copie de travail `D:\test-claude-v18-a5`, branche `v18/a5`, partie de `13164d9`. Cinq autres agents
faisaient tourner Chrome en même temps sur la machine : toutes les mesures ci-dessous ont été prises
**sous charge**. La machine n'a jamais été au repos pendant la case (voir « Charge de la machine »).

## 1. `tools/preuves/git-graphe.js` : le premier chargement

### Comment l'outil se lance
`node tools/preuves/git-graphe.js` (étape `gitgraf` de `verif.js`, hors `--rapide`). Il appelle
`tools/preuve-hors-reseau.js pages/git-bac-a-sable.html --attendre=<pilote> --ms=25000`, qui
navigue, attend **400 ms**, puis évalue l'expression du pilote (`tools/preuves/git-graphe-pilote.js`)
en boucle jusqu'à ce qu'elle rende autre chose que `null`. Ensuite, cinq « volets » ouvrent chacun
une leçon dans un nouveau Chrome pour contrôler l'encart du bac à sable.

### Reproduction (avant correction) — l'outil réel, 10 passages
`node scratchpad/a5/boucle.js 10 gitgraf-avant tools/preuves/git-graphe.js` (le script de boucle note,
avant chaque passage, la charge CPU sur 1 s et le nombre de `chrome.exe`) :

```
gitgraf-avant : 2 echec(s) sur 10 · CPU avant 25.7 a 38.8 % · chrome.exe 68 a 81
   echec passage 1 (code 1)
   echec passage 4 (code 1)
   premiere attente (ms) : 416 514 448 409 444 530 428 432 430 431
```
Message exact des deux échecs :
```
})() » : {"ok":false,"erreur":"la page n'a ni champ de saisie ni formulaire"} en 416 ms
ECHEC dans le navigateur : la page n'a ni champ de saisie ni formulaire
```
(409 ms au passage 4.) C'est la signature du rapport D du V16 (« échec en 413 ms »). Même les
passages verts jouent dès la première évaluation (409 à 530 ms) : le verdict dépend de l'état de la
page à cet instant-là.

### Cause établie — un témoin de même forme, qui note l'état au moment du jeu
Copie du pilote et de l'outil dans `scratchpad/a5/gg-trace/` (hors dépôt), **même outil, mêmes
options, même ordre, un Chrome à la fois comme l'original** ; seul ajout : le pilote note
`location`, `readyState`, la présence de `#bac-saisie` et du SVG, et l'âge du document. 10 passages,
2 échecs. L'échec du premier chargement (passage 1) :
```
ECHEC dans le navigateur : la page n'a ni champ de saisie ni formulaire · ETAT {"href":"5/pages/git-bac-a-sable.html","readyState":"loading","saisie":false,"svg":false,"terminal":0,"ageDoc":638}
```
Dans les passages verts : `"readyState":"complete"`, `"ageDoc"` de 409 à 436 ms.

C'est donc **la bonne page** (pas `about:blank`), encore en cours d'analyse : l'analyseur n'avait pas
atteint le formulaire (ligne 95 du fichier). Il attend `js/theme.js`, script bloquant de l'en-tête.
Le pilote jouait quand même, figeait `{ok:false}`, une valeur non nulle, et l'attente s'arrêtait.
Le pilote voisin `git-scenarios-pilote.js` (D4) porte déjà la garde
`if (document.readyState !== "complete") return null;` ; celui de D3 ne l'avait pas.

### Correction
`tools/preuves/git-graphe-pilote.js` rend `null` (« pas prêt ») tant que le document n'est pas
`pages/git-bac-a-sable.html` à l'état `complete`. Les scripts de la page sont en `defer` : à
`complete`, `init()` de `js/git-bac.js` a posé ses écouteurs. La vérification de l'adresse est une
précaution : `about:blank` est lui aussi `complete`. Ce cas n'a jamais été observé : les 16
passages instrumentés ont tous évalué la page du bac à sable, aucun `about:blank`.

### Épreuve par injection — le pilote corrigé voit toujours une vraie faute
`node scratchpad/a5/epreuve-gitgraf.js` : chaque faute est posée dans `pages/git-bac-a-sable.html`,
l'outil réel tourne, et le fichier est restauré **à l'octet** (empreinte SHA-256 vérifiée) :
```

  code 1 · premiere attente 4997 ms · 6.7 s
  ECHEC dans le navigateur : aucun SVG dans le graphe
  restauration : identique a l'octet
G2 : le champ #bac-saisie est renomme
  code 1 · premiere attente 4287 ms · 7.4 s
  ECHEC dans le navigateur : la page n'a ni champ de saisie ni formulaire
  restauration : identique a l'octet
SANS faute (page restauree)
  code 0 · premiere attente 465 ms · 40.9 s

verdict : G1 -> 1, G2 -> 1, sans faute -> 0 : le pilote corrige VOIT les deux fautes et reverdit
```

### Preuve après correction — l'outil réel, 10 passages, mêmes conditions
`node scratchpad/a5/boucle.js 10 gitgraf-apres tools/preuves/git-graphe.js` :
```
gitgraf-apres : 0 echec(s) sur 10 · CPU avant 25.9 a 85.3 % · chrome.exe 70 a 109 · duree 31.388 a 134.996 s
   premiere attente (ms) : 449 4117 4108 457 449 443 4095 6422 3729 5379
```
Dans 5 passages sur 10, la page n'a été `complete` qu'après 3,7 à 6,4 s : le pilote a attendu au
lieu de jouer à ~400 ms. Que l'ancien pilote aurait échoué dans ces 5 passages est une **déduction**,
pas une mesure : il échouait quand le formulaire n'était pas encore analysé, et le blocage décrit au §2
retient justement l'analyseur sur `theme.js`.

## 2. `tools/verif-rendu.js` sur `bdd/lecon-01`

### Le cas réel, retrouvé dans les traces du V16
Le journal de la passe de B5-E2 (`D:\test-claude\scratchpad\v16-parallele\b5e2\verif-rendu.log`,
hors git, lu sans le modifier) donne sa **forme exacte** : 186 pages dans un seul Chrome, et
`bdd/lecon-01` est **la page 1 sur 186**. Résultat de cette passe :
```
  ⚠ NON STABILISEES apres 3 s (mesurees quand meme, verdict a prendre avec prudence) : 160
      · pages/bdd/lecon-01.html [375px/light]
      · pages/bdd/lecon-01.html [320px/dark]
[DEBORDEMENT] 2
  · pages/bdd/lecon-01.html [320px/dark]
      +317 px — code.language-sql (droite 559) · code.language-sql (droite 622) · code.language-plaintext (droite 545)
```
Les coupables sont des `<code>` **dans des `<pre>`**. Or la sonde ignore tout élément qui vit dans un
ancêtre défilant, et `css/components.css` donne `.code-block { overflow: hidden }` et
`.code-block pre { overflow-x: auto }`. Pour que ces `<code>` soient accusés, `components.css` ne
s'appliquait donc pas à l'instant de la mesure : la page n'avait pas fini de charger.

Comment l'outil cible une page : `node tools/verif-rendu.js --pages=pages/bdd/lecon-01.html` (3
largeurs × 2 thèmes, un Chrome neuf, la page en premier). La page 1 d'une passe est mesurée avant
toutes les autres : cette commande a donc la même forme que le cas réel pour cette page.

### Reproduction (avant correction) — l'outil réel, 10 passages
```
rendu-avant : 0 echec(s) sur 10 · CPU avant 32.3 a 96.9 % · chrome.exe 77 a 132 · duree 13.462 a 21.192 s
   mesures non stabilisees : 19 · non chargees : 0
```
Détail des 19 : `[375px/light]` 10 fois sur 10, `[320px/dark]`, `[375px/dark]` et `[1280px/dark]` 3 fois
chacune. **Le faux débordement ne s'est pas reproduit (0 sur 10)**, mais sa condition, une mesure
prise sur une page qui n'a pas conclu, est revenue **à chaque passage**.

### Ce que fait la page pendant ces mesures — copie instrumentée de l'outil
`scratchpad/a5/rendu-trace.js` est une copie de l'outil, hors dépôt. Elle note à chaque relevé de
stabilité : `readyState`, l'état des polices, la largeur et les feuilles chargées. Elle pose aussi
dès la création du document un observateur qui date l'insertion de chaque `<script>` et de chaque
`<link>`. Extraits :
```

    1ms w=375 loading fonts=loaded css=0/0/0 doc+1195ms
    ...
    2337ms w=375 loading fonts=loaded css=0/0/0 doc+3531ms
    2526ms w=360 interactive fonts=loading css=6/6/6 doc+3720ms
```
```
[375px/light] CHRONO creation 331, script theme.js 333, link fonts.css 3676, ... interactive 3697, complete 4603
[320px/dark]  CHRONO creation 852, script theme.js 854, link fonts.css 5454, ... interactive 5470, complete 5555
[1280px/dark] CHRONO creation 604, script theme.js 606, link fonts.css 4813, ... interactive 4830, complete 4856
```
Le document reste en `loading` **sans aucune feuille de style** pendant 3,3 à 4,6 s, et le fil
principal répond tout ce temps : les relevés reviennent toutes les ~155 ms. Sur 48 navigations de la
leçon exacte (deux séries ci-dessous), la feuille suit `theme.js` en 3 à 130 ms dans 23 cas, et en
1 900 à 5 143 ms dans les 25 autres.

### Bissection : ce qui n'est pas la cause
Expériences sur des copies hors du site (`scratchpad/a5/temoin/`, `scratchpad/a5/miroir/`, copies
exactes des fichiers que charge la leçon). Chaque variante est passée à la copie instrumentée, en
alternance pour que la charge pèse pareil. Mesure : l'attente entre l'insertion du premier script
bloquant et la feuille suivante.

| variante | navigations > 1 000 ms | plus longue |
|---|---:|---:|
| page minimale hors du site (`vide.html` : un script, une feuille, un bloc de code), deux séries | 1 / 12 · 1 / 12 | 1 122 · 1 118 ms |
| la même + gros script neutre de 707 Ko | 1 / 12 | 1 032 ms |
| la même + copie exacte de `js/data.js` | 1 / 12 | 1 063 ms |
| la même + l'icône de la leçon | 1 / 12 | 1 031 ms |
| leçon exacte (miroir) | 7 / 12 | 3 662 ms |
| leçon **sans aucun script différé** (ni `data`, `main`, `lecon`, `runner`, Prism), deux séries | 5 / 12 · 6 / 12 | 3 512 · 3 527 ms |
| leçon sans `runner.js` | 8 / 12 | **7 195 ms** |
| leçon sans `lecon.js` · sans `main.js` | 5 / 12 · 5 / 12 | 2 842 · 3 140 ms |
| leçon sans icône | 6 / 12 | 4 212 ms |
| leçon sans `fonts.css` | 3 / 6 | 3 965 ms |
| leçon exacte, cache de retour arrière **actif** / **désactivé** (`--disable-features=BackForwardCache`) | 9 / 18 · 9 / 18 | 4 823 · 5 143 ms |
| leçon sans script différé, outil **sans redimensionnement** entre les navigations | 5 / 12 | 3 468 ms |
| la même, outil **sans semis de `localStorage`** | 5 / 12 | 3 629 ms |
| la même, **sans les deux** | 6 / 12 | 3 569 ms |

Avec des marqueurs dans une copie de `theme.js` : `script theme-trace.js 1144, theme-debut 4043,
theme-apres-getItem 4043`. Le script **commence** 2,9 s après son insertion, et sa lecture de
`localStorage` est instantanée. L'attente est donc **avant** l'exécution, dans le chargement.
**Sans** `theme.js`, elle se reporte sur les feuilles (`complete` à 4 630, 3 449 et 3 586 ms, contre
156 à 394 ms). Ce sont **toutes** les sous-ressources du nouveau document que Chrome retarde.

Conclusion établie : **aucun script du site n'en est la cause** (le blocage demeure quand on les retire
tous), ni `localStorage`, ni les polices, ni l'icône, ni le cache de retour arrière, ni les deux gestes
de l'outil entre deux navigations. Il n'apparaît que quand on recharge une **vraie leçon** (son HTML
et ses feuilles). D'après l'alternance observée, il faut aussi que la précédente soit restée chargée
et inactive un moment ; c'est une déduction, la durée n'a pas été mesurée directement. Cela
expliquerait que la 2ᵉ combinaison, qui suit les 25 tabulations du test de focus, soit lente 10 fois
sur 10.

**Ce qui reste incertain** : le mécanisme interne de Chrome. Est-ce la taille du document, ses
feuilles, la charge de la machine (CPU entre 31,1 et 100 % dans les séries où la charge a été
notée) ? Je ne l'ai pas isolé. Je ne sais pas non plus si un apprenant qui passe d'une leçon à l'autre le subit. On ne l'a vu
qu'en rechargeant la même adresse par CDP. Un passage de la copie instrumentée est sorti en code 2
sans rien mesurer (variante sans Prism, CPU 100 %), et mon script de bissection n'en a pas gardé la
sortie.

### Le faux rouge, reproduit à volonté hors du site
`scratchpad/a5/temoin/lent.html` est une page qui reste `interactive` 6 s sans bloquer son fil
principal (un cadre ouvert par `document.open()`, fermé par une minuterie). Elle ne reçoit sa feuille
qu'à la fin. Tant qu'elle charge, son bloc de code déborde ; une fois chargée, il défile dans son
cadre. C'est la forme exacte de `bdd/lecon-01` pendant le blocage.

**E1** — l'outil d'avant (extrait par `git show HEAD:tools/verif-rendu.js`) contre l'outil corrigé :
```
=== scratchpad/a5/verif-rendu-avant.js
  ERREURS ............ 4
  ⚠ NON STABILISEES apres 3 s (mesurees quand meme, verdict a prendre avec prudence) : 6
[DEBORDEMENT] 4
      +505 px — code (droite 825)
      +450 px — code (droite 825)
      +505 px — code (droite 825)
      +450 px — code (droite 825)
code=1
=== tools/verif-rendu.js
  ERREURS ............ 0
code=0
```

### Correction
Dans `tools/verif-rendu.js`, il y a désormais deux plafonds au lieu d'un seul plafond de 3 s
(20 relevés) :
- attendre l'état `complete` jusqu'à `PLAFOND_CHARGEMENT`, 20 s par défaut. Le plus long blocage
  relevé ici est de 7 195 ms. L'option `--plafond=<ms>` sert à éprouver l'outil ;
- une fois `complete`, laisser 3 s (l'ancien budget) à la largeur et aux polices pour se poser.
  Au-delà, la combinaison est mesurée et **nommée** « non stabilisée », comme avant ;
- une page qui n'a **pas** atteint `complete` n'est **pas mesurée**. Elle devient une erreur de
  catégorie `chargement`, qui dit ce qui s'est passé, au lieu d'un débordement ou d'un contraste
  qu'elle n'a pas. Elle compte dans le bilan (« ✗ NON CHARGEES … ») et fait sortir l'outil en code 1.

## 3. Trouvé en route : les « volets » de `git-graphe` (cause non établie)

Dans le témoin instrumenté (§1), le passage 4 a échoué **ailleurs** que dans le premier chargement.
Il a duré 141,5 s au lieu de ~35 s :
```
  pages/python/lecon-05.html → ECHEC : aucune mesure rendue
```

Sur les 33 passages où les volets ont tourné (8 + 9 + 10 + 6 dans les quatre boucles), c'est le seul
où un volet est resté muet. Un témoin de 6 passages qui chronomètre chaque volet
(`scratchpad/a5/gg-trace/`, même forme) a donné 6 verts sur 6 :

**n'est pas établie** : l'outil jetait la sortie de `preuve-hors-reseau.js`, qui la disait (attente
expirée, port non écrit, Chrome muet).

**Correction (diagnostic, pas de cause)** : `tools/preuves/git-graphe.js` garde maintenant les lignes
que `preuve-hors-reseau.js` écrit lui-même (attente, échecs de chargement, requêtes distantes,
« Chrome n'a pas… »), et la durée du volet. Le verdict ne change pas : il reste rouge.

## Charge de la machine

16 cœurs logiques (8 physiques), 61,7 Go de mémoire. Au début de la case : CPU 20 %, 61 `chrome.exe`,
16 `node.exe`. Au plus fort : CPU 96 %, 152 `chrome.exe`, 36 `node.exe`. Avant chaque passage des
boucles, le CPU mesuré sur 1 s variait de 22,8 à 100 %. L'antivirus temps réel est **désactivé**
(`Get-MpComputerStatus` : `RealTimeProtectionEnabled False`), il n'est donc pas en cause. Aucune
mesure « au repos » n'a été possible : les cinq autres agents travaillaient. Les boucles « avant » et
« après » d'un même outil ont tourné l'une après l'autre, jamais en même temps qu'une autre de mes
mesures.

## Ce qui reste ouvert

1. **Le mécanisme de Chrome** qui retarde de 1,9 à 5,1 s (7,2 s au pire) les sous-ressources d'une leçon rechargée
   n'est pas isolé, et je ne sais pas si un apprenant le subit (§2, « Ce qui reste incertain »).
2. **Les volets de `git-graphe`** : 1 passage sur 33 a vu deux volets muets, cause inconnue. Au
   prochain échec, la raison sera imprimée. Une piste non vérifiée : `tools/preuve-hors-reseau.js`
   relance chaque Chrome sur le **même profil persistant** `scratchpad/.chrome-preuve`. Or la règle
   posée au A1 du V16 (`tools/lib/profil-chrome.js`) veut un profil neuf par exécution. Ce fichier sert
   six outils (`git-modele`, `git-commandes`, `git-graphe`, `git-scenarios`, `chrome-absent` et la
   preuve elle-même) : je ne l'ai pas changé sans preuve que le profil soit en cause.
3. **`pages/etude-inconnu.html`** est déclarée périmée par toute copie fidèle à git (6 566,0 Ko
   publiés, 6 563,7 Ko mesurés), parce qu'elle a été assemblée sur un disque où 62 pages sont en
   CRLF (voir « Contrôles finaux »). C'est hérité de `13164d9`, sans lien avec A5, et c'est le
   terrain de A6.
4. **Vu, non corrigé (hors case)** : `tools/verif-rendu.js` choisit encore son port DevTools par
   `9222 + (pid % 500)`, pas par `--remote-debugging-port=0` comme les outils passés par le A6 du V17
   (`tools/lib/port-chrome.js`). 9222 est pris sur cette machine (fifine Genie). Une collision fait
   mesurer la page d'un autre Chrome.
